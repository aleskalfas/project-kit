# What the check reports

`pkit visual check` judges a project's visual work and draws nothing. Each problem it finds is a *finding*. `pkit validate` runs the same check as one of its members. What the command reads, prints and exits with is under *Commands* in the README. The examples come from the capability's test files: the test brand `test-brand` and the test library `tests` exist for the tests only.

## Severities

Each finding takes one of three levels (DEC-002 point 7). Validation reads each level as one of its severities.

| Level | When | Severity in `pkit validate` |
|---|---|---|
| fails | An invariant a record of the capability owns is broken in a file the project can correct, or the check owed an answer and gave none. | `error` |
| asks for attention | Someone is expected to act. Where the tables below name who, the finding names them too. | `warning` |
| states a fact | No act is expected. | `info` |

Only an `error` fails `pkit validate` ([CLI reference](../../cli/README.md#validate)).

**A lock behind.** A published piece's lock may stay behind a newer released version, and nothing is broken. A person moves it, so its finding, `lock-behind`, states a fact (DEC-003 point 9). It fails nothing and refuses no export.

**An output that goes stale.** An output people or other software read directly fails when something it read changed: a published piece's current copy, and written code. One that reaches a reader only through a piece asks for attention, since the piece's exports guard it (DEC-006 point 8).

**A version handed out.** Its files are what went out, so a file that is missing or changed fails (DEC-006 point 8). A state or a lock that no longer agrees with the version fails too (DEC-017 point 6). So does `state: final` with no version behind it. The project mends each in its own files.

**A library version the project does not correct.** A finding the project cannot correct in its own files never fails (DEC-002 point 7). A finding that lies in a library version names that version. Where the project does not correct the version, a finding that would fail there asks for attention instead, and names who does:

- **A released version,** which the project's list of libraries marks released, and which still matches its release. The finding names the library's owner: only the owner corrects it, in a new release.
- **A copy of a library the capability ships,** released or not, which the list names from the source `shipped`. The finding names whoever maintains the capability (DEC-013 point 6). No project corrects it, since the command that brings the library in writes it as it is authored.

This level, and who it names, are worked out each time the check reads a finding, and are never stored.

A released version whose folder no longer matches its release is the project's copy to restore (DEC-002 point 7, DEC-003 point 9). So its findings fail, `library-changed` among them, whatever the library's source. A finding in a version of the project's own library not yet released fails as well. The list, with each library's source and which versions are released, is described in [The files of the visual work](files.md#the-library-folder).

A few findings that lie in a library folder name no version, so their level stands. `library-folder` and the findings on the list itself always fail. `copy-not-shipped` and `copy-hash-differs` ask the project for attention: each compares a copy with what the installed capability ships (DEC-013 point 6).

`library-unreadable` fails too where a version needs a newer release of the capability than the one installed (DEC-014 point 5). That number is no fault in the version, released or not. Only the project corrects the finding: it upgrades the capability, or takes out a version no lock names (DEC-003 point 4). So the finding names the project as who acts, never the library's owner.

## What a finding says

- **A label,** a short name of what was found, such as `text-overflow`. Each label is in the tables below.
- **A location:** `<file>#<where>`, or `<file>` where nothing within the file is named, or `.` where no file is. The file is relative to the project root. `<where>` is one of:
  - a key path in a YAML file, written as a content source's path is ([sources](components.md#sources)), such as `body.steps[plan].head`, or a run's, such as `body.say#2`;
  - a key path in a component's file, such as `parts.head.height`;
  - a trace id of the scene, such as `figure/body/steps[plan]/head` ([trace ids](components.md#trace-ids));
  - a token path of a brand, such as `space.5`.
- **A message:** what was found. Then ` — for <who>` where someone is named, and ` — <fix>` where the finding names its fix.

## What each run judges

Without a piece named, each run judges, in order: the configuration, the location, the binding of each file of the capability's format in the location, the library folder and its list, then each library version checked alone, then each piece, then each declaration of written code. For each piece it judges, in order, the ids of its content, what its brief names, its lock, what its state owes of its current copy, whether a published lock is behind, the libraries its lock names read under it (its brand and the own roles of each library of components), the names of those libraries, its notations, its content against the components it fills, its produced pictures and its scenes.

**A version checked alone.** The newest version the project holds of each major of each library is checked alone, once (DEC-005 point 7, DEC-008 point 1). It is resolved with the newest version the project holds of each major it names, and of each major those name. A brand is read over its base, and the foundations' declarations are read. A component library's own roles are judged against the libraries it builds on. So is each of its patterns against the default component of each list it declares fields for, a drawing of a top's layout included. Its findings are `arrangement-clash`, `end-clash` and `tie-default` (DEC-010 point 9, DEC-011 point 8). Its components are read as a piece's are, from the versions it is resolved with, with no piece and no brand behind them, so each role stands for the type it declares. What a version shows alone lies in that version. A version that names majors no versions fit, or one of which the project holds no version, cannot be checked alone: that is its finding (`alone-majors`, `alone-missing`). An older version of a major is checked only under the locks that name it.

**A version a release reads.** `pkit visual release` reads the version it releases in full on the installed capability, beside what the check of it alone judges (DEC-014 point 1). It reads each file of the capability's format in the version against its schema, and every component, a component no piece places included. It reads a brand's tokens over its base, and opens each font the version holds. It reads each file directly in the version's `pictures/` under a bare name, as the engine reads it, named or not ([picture files](files.md#picture-files)). A bare name is one a part can give, so a file of another name, or in a folder within, is not read (DEC-025 point 2). It judges each name its components give by `file`, as the engine judges it where it draws the image. It computes no scene. Each finding takes the label it takes in the check, and the level it takes in a version not yet released. It points at the version's file. A finding that fails refuses the release (DEC-003 point 6).

**Under a lock.** A piece's lock combines versions, so each version it names is judged at that lock too (DEC-008 point 9). A fault the version shows alone as well lies in the version, and is reported once. A fault only the lock's combination of versions shows lies at the lock, `<piece>/piece.yaml#lock`. It names no version, so its level stands, and its message names the version and the place it was seen in. A fault of the lock itself, such as a base the lock names at another major, names no version either.

**A final piece.** The check reads its files, its lock and the version handed out, and no more (DEC-002 point 7, DEC-017 point 4). A piece is final by its state or by its record of exports, and one whose record cannot be read reads as final ([the lock](files.md#the-lock)). The check reads the binding of each of its files, and what its lock names. It holds the piece's state and lock to the version handed out, and each file of that version to its hash. No finding at the lock stops this (*The version handed out*, under [Exports](#exports)). It computes no scene and reads no findings record. It leaves out the piece's ids, what its brief names, its content against its components, the libraries read under its lock, its brand, its notations, its produced pictures and its current copy. So a content file may be missing, or hold what its components refuse, and no finding follows. A library its content came to use is no finding either. A content file that cannot be read, or whose binding is broken, takes its finding as any file does, and the lock is still read. A version its lock names that no longer matches what was released fails as `library-changed`, once, in a run on the piece alone too. A finding at its lock fails only where something other than a move mends it (*At a final piece's lock*, under [Libraries and locks](#libraries-and-locks)). The summary counts the piece apart, as left out as final.

`pkit visual check <piece>` judges that piece alone: the binding of its own files, and all of the above for it. It judges neither the library folder, nor its list, nor written code. It runs no pass of versions checked alone: it checks alone only the versions its lock names, to tell where each finding under the lock lies, and reports only what the lock shows.

Some findings stop a piece. A piece that cannot be read is judged no further. A lock with a finding stops it after its current copy and before its brand, so a stale copy stands beside that finding, and so does the fact that the lock is behind. On a final piece it stops nothing. A brand that cannot be read, or a mode the brand lacks, stops it before its notations, its content, its produced pictures and its scenes. A notation's findings stop nothing. An error the check does not expect stops the piece where it arises (`unexpected-error`), and the check goes on to the next piece. The summary counts such a piece as not checked.

Where the configuration records no location and the default folder holds no visual work, the summary says so, and only the configuration is judged. Where the configuration records a location that is refused or missing, or an empty `location:`, the check reports `location`, and judges nothing but the configuration.

## Findings by area

In the tables, `<piece>/` is the piece's folder, `<location>/pieces/<piece>/`, and `<version>/` is a library version's folder, `<location>/libraries/<library>/<version>/` ([The files of the visual work](files.md#what-the-location-holds)). *Fails* is the level where the project can correct the file.

| `files-unlisted` | git cannot list the location's files, or those of a version's `pictures/` folder. | fails | `.`, or `<version>/pictures/` | The message gives git's error. |
| `file-unreadable` | The configuration, or a file of the capability's format, cannot be read ([how files are read](files.md#how-the-files-are-read)). | fails | the file | Mend the file. |
| `binding` | The file names no schema, or another schema than its name and place call for. A file at another format number is the core's data validation's to report. | fails | the file | Write the binding the message names ([the binding](files.md#the-binding)). |

### Scenes

Each points at the file a person edits to mend it:

- **A finding in a component** points at that component's file: a library's in the locked version, `<version>/components/<component>.yaml`, and the piece's own at `<piece>/components/<component>.yaml`.
- **A finding in what a component's part gave** the component it places, or left out, points at the file of the component whose part it is.
- **A finding in what the content gave** points at the content file, `<piece>/content.<language>.yaml`, a value a part passed on from the content included.

- **A text that overflows on a phone alone** is one finding, whose message opens with `` `device.phone`: ``.

- **`contrast-drawn`** is measured in each combination on the scene of its key. Its message names the combination, so it never reads alike at two keys.

**A finding on several pages.** A page drawn in a layout draws the top's other fields ([Layouts](components.md#layouts)), such as a site's header and footer ([The foundations](files.md#the-foundations)). A finding in what such a field draws is read alike on each page that draws it, and is reported once (DEC-022 point 8). It lies at the first such page, and its message ends naming each page. ## The findings record

`findings.yaml` in the piece's folder keeps what computing the piece's scenes found (DEC-005 point 13). `pkit visual render` writes it at each render of a piece that is not final, replacing the one before. Of a final piece it writes none, and one left from before stays. A refused render writes none. `pkit visual upgrade` writes it too, under the lock it moves ([the lock](files.md#the-lock)). Commit it, so the check reads it on a fresh clone.

It holds the scene findings, the losses among them. The findings on files, libraries, locks, brands, notations, content, produced pictures and written code are not in it: the check works them out at every run. Its fields:

- `pkit_schema: visual-communication:findings` and `schema_version: 1`.
- `key`: a fingerprint of every file the scenes were computed from ([input sets](#the-input-set-of-each-kind)).
- `findings`: each finding, with its `code` (its label), its `level` (`fails`, `attention` or `fact`, the level where the project can correct the file), its `message` and its `where`. It may hold `file`, `fix`, `library` (`<library>@<version>`, where it lies in a library version) and `who`.
- A finding's `file` is relative to the piece's folder, or, where it lies in a library version, to that version's folder. So the record holds when the location moves or the piece is copied. The check gives each file relative to the project root.

The record of the test piece `flow`, with a word too wide for its card, trimmed:

```yaml
pkit_schema: visual-communication:findings
schema_version: 1
key:
  form: 1
  hash: sha256
  format: 1
  value: b9492f2342da8abf3282f55b53644e4a2a3df64544d631c10dd11465fb25cabc
  inputs:
    - file: content.en.yaml
      sha256: 3eeb969325991cb4f61075bf821753e3c0268895b07d047a8a96b80add7ff239
    - file: piece.yaml
      sha256: bf975523102ee6d20fbc3c580a3c5971670f75f37a3a2e34de91c5016acb542a
    - library: foundations
      version: 1.0.0
      path: roles.yaml
      sha256: 439695a0673cb3a57d31976625bf7f90ffeb8435b8f6283a4d0f1ef1aed9e798
    # ... every other file of each locked version
findings:
  - code: text-overflow
    level: fails
    message: "figure/body/steps[plan]/head: a word of content:body.steps[plan].head is wider than the text's width 288.0 px: 3431.04 px"
    file: content.en.yaml
    where: figure/body/steps[plan]/head
```

### When the check reads it

For each piece that is not final, and whose lock and brand let its scenes be computed:

- **The record verifies.** Its key verifies against the files as they are now, so its findings are the piece's scene findings. The summary counts the piece as read from its findings record.
- **It is missing, or does not verify.** The check computes the piece's scenes in that run, from the files alone, and counts the piece as computed now. A record that cannot be read, or is not bound, does not verify.

The key holds no version of the engine. A new release of the capability reaches a piece's scene findings at the next render a person runs (DEC-005 point 13).

### The validation's bound

`pkit validate` runs each member under a fixed bound, and tells the check its deadline in `PKIT_COMMAND_DEADLINE`, in seconds since the epoch ([the lifecycle README, "How a registered command is run"](../../lifecycle/README.md#how-a-registered-command-is-run)). Computing scenes takes time, so the check stops computing them one second before the deadline. Each piece left whose record is missing or does not verify fails as `not-checked`, at `<piece>/findings.yaml`. The fix: run `pkit visual render <piece>`, and commit its findings record. The summary counts the piece as not checked. Without a deadline, as when a person runs `pkit visual check`, the check computes every piece that needs it.

## The fingerprint

A *fingerprint* says what an output was read from, so the check can tell when the output is stale (DEC-006 points 5 and 6). A command writes it. Nobody writes one by hand. Form 1 has these fields:

| Field | Holds |
|---|---|
| `form` | `1`, the form's version. |
| `hash` | `sha256`. |
| `format` | `1`, the format number its inputs were read at. |
| `value` | The SHA-256 of the canonical text of `inputs`, in lower-case hexadecimal. |
| `inputs` | Each input: its identity, and the `sha256` of what was read. They are sorted by the canonical text of their identity, and no identity appears twice. |

A form fixes how each kind of thing is read, apart from the fields an input names (DEC-006 point 6). So a change of those fields takes no new form.

### An input's identity

An identity says what was read, apart from where the work lies. So moving the location, or copying a piece, makes nothing stale.

| Identity | What was read | Its `sha256` is the hash of |
|---|---|---|
| `{file}` | A file of the piece, by its path within the piece's folder. | the file's reading |
| `{file, without}` | A file of the piece, read without the fields `without` names. | the file's reading, without those fields |
| `{file, keys}` | A part of a file of the piece, by the keys that lead to it. | the part's canonical text |
| `{library, version, path}` | A file of a library version, by its path within the version's folder. | the file's reading |
| `{font}` | A font of the location's `fonts/`, by its SHA-256. | the font's bytes |
| `{plugin, version}` | A producer's or a code writer's version. | the identity's canonical text |
| `{value, key}` | A brand's value at a token path, in the combination a key names. | the value's canonical text |
| `{pixels, width, height}` | A variant's pixel size. | the identity's canonical text |
| `{code}` | A declaration of written code, by its name. | the file's reading |
| `{frame}` | An element's measured frame, by its trace id. No input set of form 1 holds one. | the frame's canonical text |

### The reading

A file is read once, one way, so the same file gives the same hash on every machine. YAML and JSON are read as [How the files are read](files.md#how-the-files-are-read) says.

- **A YAML file of the capability's format** is read as its value, at the format number the fingerprint names. Its hash is taken of the value's canonical text. So a comment, the order of keys or the quoting changes nothing. Format 1 has no converter: a file at another number cannot be read, and the fingerprint does not verify.
- **A file read without fields** loses them from its value, at its top level, before the hash is taken. Only a YAML file of the capability's format loses a field. Any other file is read as this list says, whatever its input names.
- **A JSON file** is read as its value, and hashed as its canonical text.
- **Any other file,** a YAML file not of the format or one that does not parse included, is hashed as its bytes.
- **A brand's value** is hashed in its resolved form. A colour is `colorSpace`, `components` and `alpha`, the alpha `1` where the token gives none, and its `hex` left out. A dimension is `value` and `unit`, a font family a list of names. So a value written another way gives the same hash.
- **Canonical text** is the JSON Canonicalization Scheme (RFC 8785). Keys come in the order of their UTF-16 code units, with no white space. Strings are escaped as ECMAScript's `JSON.stringify` escapes them. Numbers are written as ECMAScript writes them, so `1.0` is `1`. An integer beyond 2⁵³ − 1 is refused. Its text is hashed as UTF-8.

### The input set of each kind

| Kind | Kept in | Its inputs |
|---|---|---|
| A piece's findings | `findings.yaml`, as `key` | The piece's own files. Every file of each version the lock names. Each font of the location's `fonts/` that its scenes read. |
| A produced picture | the output's `record.yaml` ([its record](outputs.md#the-record-of-a-produced-output)) | The part of `piece.yaml` at `produced.<output>`. Each value its inputs name, in each combination the piece names. Each variant's pixel size. The producer's version. |
| Written code | `<out>.record.yaml` ([its record](outputs.md#the-record-beside-the-code)) | The declaration's file. Each value written, in each combination of the brand's axes. The code writer's version. |
| An export | each version of `exports.yaml` ([the record of exports](outputs.md#the-record-of-exports)) | As a piece's findings, and the part of `piece.yaml` at `exports`. Two files are read as [What an export leaves out](#what-an-export-leaves-out) says. |
| A released library version | its entry in the list, as `hash` ([files](files.md#the-library-folder)); for a version the capability ships, its entry in the library's record too ([files](files.md#the-libraries-the-capability-ships)) | Every file of the version's folder, its `library.yaml` with the release it needs included. |

A piece's *own files* are the files of its folder as git lists them, tracked or untracked but not ignored. Each picture file of its `pictures/` is one, whether or not an image shows it (DEC-025 point 2). They leave out `findings.yaml` and `exports.yaml`. They leave out the piece's brief, `brief.yaml`, too, which nothing drawn reads, so a change to it stales nothing (DEC-029 point 4). Under `produced/`, only each output's `record.yaml` is one of them, since it holds the hash of each of its pictures. A library version's files are listed the same way.

No fingerprint reads a file under two folders of a piece, whatever its name (DEC-016 point 3). `handed-out/` holds the files of a version handed out, and `current-copy/` a published piece's current copy.

### What an export leaves out

An export reads two files without some of their fields. Each field can change no exported file, or changes one only as a fact of that export (DEC-016 point 1).

| File | Fields it is read without |
|---|---|
| `piece.yaml` | `state`, `pinned`, `audience`, `shown`, `explains`, `accept-losses`, and `copy-place`, the place of a published piece's current copy |
| A produced output's `record.yaml` | `recorded` |

- **What this leaves verifying.** Pinning a draft or setting its state changes no export's fingerprint. Nor does running a producer again with the same pixels.
- **What still counts.** Every other field counts, the lock and the formats among them. A field added later counts until a change adds it to this list.
- **What the input says.** It names each field of the list it applied, whether the file held that field or not. So a field set later stays left out.
- **Only an export.** Every other kind of fingerprint leaves no field out (DEC-016 point 2). So a listed field can still change a piece's findings.

### How a fingerprint verifies

The check works out the input set again from the files as they are now, under the form the fingerprint names. It reads a file without the fields its kept input names, whatever the list holds today. An input that names none reads the whole file. So a fingerprint verifies as it was written (DEC-016 point 4). It compares each input's hash with the one kept, and names each input that changed, is no longer read, or is read now. A fingerprint does not verify where any of these differs. Nor does one whose `value` is not the hash of its own `inputs` (it was edited), or whose form, hash or format number the capability does not read.

### What makes an output stale

- **A produced picture** is stale when its fingerprint does not verify, or when a combination the piece names maps to no variant in its record. Its inputs are values, not the engine's version, so a release of the capability makes no picture stale; the producer's version is compared (DEC-006 point 5).
- **Written code** is stale when its fingerprint does not verify. Where it verifies with the writer's version the fingerprint names, the code is stale only by its writer's version, and asks for attention (`code-stale-writer`). Otherwise it fails (`code-stale`).
- **An export** has changed since it was made when its fingerprint does not verify (DEC-016 point 1). One made before [What an export leaves out](#what-an-export-leaves-out) read `piece.yaml` whole, so a pin reads as a change since it. Each later export writes the new reading.
- **A published piece's current copy** is stale when the fingerprint of the version that wrote it does not verify (DEC-016 point 1). That version is not always the last. A draft's export writes no copy, so a piece set back to published is held to the older version (DEC-017 point 5).
- **Never compared:** the outside programs a producer called, the machine, the time and the capability's release. A record keeps them beside the fingerprint (DEC-006 point 5).

## In `pkit validate`

The capability registers its check as the validator `check` in the `validators` block of its `package.yaml`. So `pkit validate` runs it as the member `visual-communication:check`, with `--json`, from the project root (DEC-002 point 6). The check reads only the project's files: it is offline, writes nothing and runs no program of the project's. `pkit sync` provisions its dependencies.

With `--json` it prints one document. `summary` holds one line. `findings` holds each finding with its `severity`, its `location`, its `message` (who and fix included) and its `label`:

```json
{"summary": ["1 piece(s) in `visual`: the scenes of 1 read from their findings record, of 0 computed now, of 0 not checked."],
 "findings": [
   {"severity": "error",
    "location": "visual/pieces/flow/content.en.yaml#figure/body/steps[plan]/head",
    "message": "figure/body/steps[plan]/head: a word of content:body.steps[plan].head is wider than the text's width 288.0 px: 3431.04 px",
    "label": "text-overflow"}]}
```
