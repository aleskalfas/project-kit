# What is made from a piece

Plugins make what the capability gives out. A renderer draws a piece's scenes as previews and exports. A producer makes a picture a piece shows. A code writer writes a brand out as code. What each command reads, writes and refuses as a whole is under *Commands* in the README.

## Plugins

A *plugin* is code that meets the engine at one *seam*: what the engine hands it, and what it takes back. There are three kinds:

- A *renderer* draws a scene in one medium.
- A *producer* makes a picture while a piece is prepared. A person or an agent runs it with `pkit visual produce`. No render, check or export runs it.
- A *code writer* writes a brand's resolved values as code in one language.

Every plugin is the capability's, and a project adds none (DEC-005 point 12): no file, setting or environment variable adds one. The capability ships:

- the `svg` renderer, at version 1.5.0, which draws the formats `svg` and `svg-modes`
- the `pdf` renderer, at version 1.6.0
- the `html` renderer, at version 1.8.0
- the `css` code writer, at version 1.0.0
- the `json` code writer, at version 1.0.0

No producer ships yet.

Each plugin declares what it can take, so the capability knows it without running the plugin. A renderer declares each primitive it draws, and each property of it. Under `physical-size` it also declares whether its format has a physical page, `page`, and whether it maps a top's physical size onto it, `maps` (DEC-034 point 3). A producer declares its inputs, each a role of one *value type* (a token's DTCG type, such as `color`), and the value types it uses. A code writer declares the value types its language has a form for, the forms of its spelling, the kinds of axis it spells, and whether it takes a `prefix`.

Each plugin also declares what it needs beyond the project's files: the outside programs it calls (`programs`) and the services it reaches (`services`), each a list of names (DEC-005 point 9). The SVG, PDF and HTML renderers and the CSS and JSON code writers call no outside program and reach no service. A producer that names a service is refused before it runs, since a plugin that reaches a service runs only where the project's configuration turns it on, and format 1's configuration turns none on (DEC-002 point 8). So is a producer that names a program the machine lacks.

### Versions

- **A plugin's own version,** `X.Y.Z`, is apart from the capability's. It rises when the same input could give another output. Reference outputs pinned to it in the capability's tests catch a change made without a new version (DEC-005 point 9).
- **The seam's version** is 9. A plugin's declaration names the seam version it reads, and the capability refuses a plugin of another version. Version 2 hands a renderer a text's runs, each with its own paint and fonts ([What a scene holds](components.md#what-a-scene-holds)). Version 3 hands it a line's arrowheads, and a tie's connector with its points and the elements its ends meet (DEC-011). Version 4 hands a renderer of a format that holds modes every key of one file in one call ([Modes](#modes)). Version 5 hands a renderer, for each language and combination it draws, the picture each image shows there, by the image's trace id: the file and its kind, a PNG or a JPEG (DEC-025 point 7). It is handed one for every source of an image, and reads nothing else for a picture. Version 6 hands a renderer the physical size of the piece's top on the scene's root ([What a scene holds](components.md#what-a-scene-holds)). Version 7 hands it a path, the outline of a concept's sign, mapped into its frame (DEC-036 point 1). Version 8 hands it, on a text's line, each run's sign and ground with the run's piece and the room the engine gave them (DEC-036 point 3). Version 9 hands it a paint that names a step of an order, and the step's value in each combination it draws, among that combination's colours, by the step's name ([What a scene holds](components.md#what-a-scene-holds), DEC-032 point 5). What a producer and a code writer are handed and return is as version 1 had it, the document of values apart.
- **What rose with ties.** The seam rose to 3, since a renderer must read a line's new properties. The SVG renderer stays at 1.0.1, and the CSS code writer at 1.0.0. A scene of seam 2 holds no arrowhead and no connector, and each draws it as before. The PDF renderer reads seam 3 from its first version, 1.0.0.
- **What rose with modes.** The seam rose to 4, and every plugin's declaration names it, the code writers' included. No output of the SVG and PDF renderers or the code writers changes, so their versions stay. The HTML renderer rose to 1.1.0, since its file now holds modes.
- **What rose with picture files.** The seam rose to 5, and every plugin's declaration names it. The SVG renderer rose to 1.1.0, and the HTML renderer to 1.2.0, since each draws a picture file and a JPEG. The PDF renderer rose to 1.1.0 when it came to draw every image. The code writers draw nothing new, so their versions stay.
- **What rose with web pages.** The PDF renderer rose to 1.2.0, since it draws a page too large for a PDF smaller. Every other page draws as before, and the seam stayed at 5.
- **What came with switching files.** The SVG renderer came to draw a second format, `svg-modes` ([The switching file](#the-switching-file)). A one-key file draws as before, so its version stays at 1.1.0, and the switching file is pinned to that version beside it. Seam 5 already hands a renderer of a format that holds modes every key of one file in one call, so the seam stayed at 5 too.
- **What rose with fixed pages.** The scene's root came to say whether its pages are fixed pages ([What a scene holds](components.md#what-a-scene-holds)). The HTML renderer rose to 1.3.0, since it shows fixed pages each inside a keyline, on a backdrop ([Fixed pages](#fixed-pages)). A renderer that does not read the fact draws every page as before, so the seam stayed at 5, and no other plugin's version rose.
- **What rose with print.** The HTML renderer rose to 1.4.0, since its file prints each page as [Printing](#printing) says. It read nothing new from the scene, so the seam stayed at 5, and no other plugin's version rose.
- **What rose with a physical size.** The scene's root came to hold the physical size of the piece's top. A renderer that did not read it would draw a printed page at a wrong size with no error, so the seam rose to 6, and every plugin's declaration names it. The PDF renderer rose to 1.3.0, since it draws each page at that size ([The PDF renderer](#the-pdf-renderer)). A scene with none draws as before. The SVG and HTML renderers draw as before, and the code writers read no scene, so their versions stay.
- **What rose with signs.** A scene came to hold a path, which a sign part draws, so the seam rose to 7, and every plugin's declaration names it (DEC-036 point 7). The SVG renderer rose to 1.2.0, the PDF renderer to 1.4.0 and the HTML renderer to 1.5.0, since each draws a path. A scene with no path draws as before. The code writers read no scene, so their versions stay.
- **What rose with a run's sign and ground.** A text's line came to hold each run's sign and ground, and a renderer that did not read them would draw the run's text over the room the engine left for them, with no error. So the seam rose to 8, and every plugin's declaration names it (DEC-036 point 3). The SVG renderer rose to 1.3.0, the PDF renderer to 1.5.0 and the HTML renderer to 1.6.0, since each draws them. A text with no sign and no ground draws as before. The code writers read no scene, so their versions stay.
- **What rose with round turns.** A connector came to hold `rx`, the radius its turns are drawn round at, and a line that ends in an arrowhead came to stop at the head's base ([Ties and connectors](components.md#ties-and-connectors), [Primitives](components.md#primitives)). A renderer that does not declare `rx` is reported as leaving it out before it runs ([The loss report](#the-loss-report)), so the seam stayed at 8. The SVG renderer rose to 1.4.0, the PDF renderer to 1.6.0 and the HTML renderer to 1.7.0, since each draws round turns, and a line with an arrowhead shorter by the head. A line with no arrowhead and no `rx` draws as before. The code writers read no scene, so their versions stay.
- **What rose with an order's steps.** A paint came to name a step of an order, whose value no document of values holds, and which a renderer takes from the colours it is handed with the scene. A renderer that wrote a paint's name where a step's name cannot go would draw nothing there, with no error, so the seam rose to 9, and every plugin's declaration names it (DEC-032 point 5). The SVG renderer rose to 1.5.0, since a switching file gives the arrowhead of a step an id of its own, and the HTML renderer to 1.8.0, since it paints each step with a custom property of its own. The PDF renderer paints a step as any colour it is handed, so its version stays at 1.6.0. A scene with no step draws as before. The code writers read no scene, so their versions stay.
- **The document of values** that producers and code writers read has its own version, 2 ([The hand-over](#the-hand-over)). Version 2 holds the file a brand gives each picture role, and version 1 held none.
- **What rose with picture roles.** The document rose to 2, and the seam stayed at 5. A brand with no picture role gets the same code, so the code writers' versions stay. Each renderer draws a picture role's file as it draws any picture it is handed, so the renderers' versions stay too.
- **A code writer's spelling** has versions of its own, called *forms*. A declaration of written code names its form, and a writer keeps writing every form it shipped (DEC-005 point 8). The CSS writer writes form 1. The JSON writer writes forms 1 and 2, each that version of the document of values ([The JSON code writer](#the-json-code-writer)).
- **None of these versions** is the format number of the files a project keeps.

### The loss report

A *loss* is something a plugin cannot take as it is given. Every loss has one form:

| Field | What it holds |
|---|---|
| `plugin` | the plugin's name |
| `what` | what was lost: an element's [trace id](components.md#trace-ids), such as `figure/body/steps[plan]/box`, or a token path |
| `did` | what the plugin did instead: `approximated`, `picture` (drew it as a picture), `left-out` or `refused` |
| `why` | why, in words |
| `key` | only in a file of several keys, the key the loss lies in, where it lies in that key alone. No other loss carries it |

Before a plugin runs, the capability compares what the plugin is handed with its declaration, and reports what the plugin cannot take. A renderer whose format has a physical page, and which maps no physical size onto it, would draw each page at its own unit: where the scene's root holds a physical size, that is `approximated`, at the top's trace id (DEC-034 point 3). No renderer the capability ships loses one. A renderer also reports what it finds while it draws. An input a producer cannot take is refused before it runs ([Declaring a produced output](#declaring-a-produced-output)). What a producer could not make as it was handed, it returns with its picture, and its record keeps ([What a producer writes and returns](#what-a-producer-writes-and-returns)).

### Accepting a loss

A person accepts a known loss where the output is declared: a renderer's or a producer's under `accept-losses` in the piece's `piece.yaml`, a code writer's under `accept-losses` in the declaration of written code ([The declaration](#the-declaration)). Each entry names the plugin, what it loses, and a reason that is not blank:

```yaml
accept-losses:
  - plugin: svg
    what: figure/body/steps[plan]/box
    reason: Thin.
```

An entry matches a loss by its `plugin` and its `what` alone, whatever its `key`. The command that runs the plugin no longer prints an accepted loss, and the check no longer reports it (*Losses* in *What the check reports*).

## The SVG renderer

The `svg` renderer draws a scene as SVG files: one for each page, each language and each combination of modes the piece names. The previews and the SVG exports are its files. Each is a *one-key file*, the file of one combination, which a key names. In the format `svg-modes` it draws a *switching file* instead, which holds several combinations and follows the reader's mode ([The switching file](#the-switching-file)).

- **Elements.** A group is drawn as `<g>`, a box as `<rect>`, an ellipse as `<ellipse>`, a line as `<line>`, a text as `<text>`, an image as `<image>` and a path as `<path>`, its outline as `d`, with `fill-rule` where its rule is `evenodd`. A tie's connector whose route turns is drawn as `<polyline>`, through each of its points, or as a `<path>` of lines and arcs, `L` and `A`, where its turns are round ([Ties and connectors](components.md#ties-and-connectors)). Every element carries its trace id as `data-id`. A connector names the elements its ends meet, `data-start` and `data-end`. A group a component drew names it as `data-component`, and its library's version, if any, as `data-version`, the page's own group included.
- **The file.** The `<svg>` element names the piece, the page's trace id, the language, the combination's key, and the renderer with its version: `data-piece`, `data-page`, `data-language`, `data-key`, `data-renderer`.
- **Colours.** A colour stays a role in the scene. The renderer takes its value from the brand's resolved values in the combination it draws, as `#rrggbb`, with a `fill-opacity` or `stroke-opacity` where the colour is translucent. A step of an order takes the value that comes with the scene in that combination, as a role's, and the renderer spreads nothing ([What a scene holds](components.md#what-a-scene-holds)).
- **Shapes and text.** A box's stroke lies inside its frame, and a path's on its outline. An arrowhead is a `<marker>` that the page's `<defs>` holds once for each colour it is drawn in. It is a triangle five strokes long, in the line's stroke, placed by its base where the line stops ([Primitives](components.md#primitives)). Each line of a text is drawn as the engine broke it, at its own baseline, anchored at the start, the middle or the end of the text's width. The `<text>` takes the font and the paint of the text's first run. Each run that looks otherwise, in its family, size, weight or paint, is drawn in a `<tspan>` of its own that names all four. So a text of one run is drawn as it was before runs. A run's ground and sign are each a `<path>` before the `<text>`, marked `data-ground` and `data-sign` with the text's trace id. The ground is a box behind its span, its corners rounded where it starts and ends, in its role. The sign is its outline, moved into place, in the run's paint. On a line that holds either, each `<tspan>` stands at the place the engine gave it, and the line at its start, so the room lies where the engine left it.
- **Pictures.** Each picture is embedded whole, as the data of its kind: a PNG as PNG data, a JPEG as JPEG data. A colour profile it carries stays with it (DEC-025 point 5). A produced picture draws the variant that serves the combination drawn ([Variants](#variants)), and a picture role the file the brand gives it there ([Primitives](components.md#primitives)). A picture file draws itself.
- **Fonts.** Each font the page draws in, for each family and weight a run is drawn in, is embedded as an `@font-face` rule, from the brand's committed font file, never from the machine's fonts, cut down to the characters drawn in it. The renderer draws in the brand's default font profile. A family's name is written as a CSS string in double quotes, in its `@font-face` rule and in each text's `font-family`. A `"` or a `\` takes a `\` before it. Each `<`, `>` and `&`, each control character and each character XML 1.0 does not allow is written as the escape of its code point: a `\`, the code point in hexadecimal, and a space. So no name a brand gives can end the drawing's `<style>` element, or leave the file malformed XML.
- **A physical size.** An SVG file is a picture, drawn at the size whatever shows it gives, so its format has no physical page. Its declaration says so under `physical-size`, and it draws a top with a physical size as any other, losing nothing (DEC-034 point 3).
- **The same bytes.** Lengths are written to 1/100 px, and attributes in one order, so the same scene and values give the same file.

### Previews

A *preview* is a render for a person to look at, which `pkit visual render` draws. It uses up no version number, and is never an export (DEC-006 point 7). Where a component shows a version's number or its date, a preview shows them as this clone's next export would, where it can ([The facts of an export](components.md#the-facts-of-an-export)). The previews of a piece lie in `.pkit/capabilities/visual-communication/project/local/previews/<piece>/`, a folder local to the clone, of which no file is committed (DEC-002 point 1; [The clone's local folder](files.md#the-clones-local-folder)). Each is named `<piece>.<language>.<key>.svg`, such as `flow.en.colour-scheme.dark.svg`, where the key names the combination of modes ([Keys of combinations](files.md#keys-of-combinations)). A piece of more than one page adds the page's number, from 1: `<piece>.<language>.<key>.<n>.svg`. The scenes `pkit visual add` draws both ways take the same names ([The clone's local folder](files.md#the-clones-local-folder)).

### The switching file

A *switching file* is one SVG file that holds several combinations of modes, and draws the one the reader's signal names (DEC-018). A page shows it as any image, `![alt](path)`, and it follows the mode the browser tells it. The format `svg-modes` takes one for each page, each language and each set of combinations that share one. The file's extension stays `svg`.

- **Which combinations share a file.** In one language, combinations that differ only in modes of a pair the format reads share a file. So a file serves one key over the size axes, as a page file does ([Modes](#modes)). A mode the combinations hold alike parts nothing.
- **What the format reads.** The renderer's declaration names `svg-modes` under `holds-modes`, with the colour scheme's pairs alone: `light` and `dark` pair with the same values of `prefers-color-scheme`. It names no contrast pair, since `prefers-contrast` did not reach an image in a test. No pair lies in the foundations or in a scene. Another pair is a new version of the renderer, after a test of its own.
- **A mode of no pair.** A piece in this format whose combinations differ in a value axis's mode of no pair it reads, such as `contrast`'s `standard` and `high`, fails the check, and every export refuses it. No file could hold that mode beside another. Draw it in a piece of its own, or export the piece as `svg`.
- **The file's key** is the first it serves, in [key order](files.md#keys-of-combinations). So a piece of light and dark takes the default key, and a piece of dark alone takes dark's.
- **The plain drawing** is the first key's one-key file, attribute for attribute. So a tool that reads no rule, such as a converter to PNG, draws a whole figure in that combination.
- **A paint a rule reaches.** Each element a colour role paints carries the role as a mark beside its paint: `data-fill` or `data-stroke`. A second `<style>` holds a rule for each other key, under the reader's signals that part it from the first, such as `@media (prefers-color-scheme:dark)`. The rule repaints each mark in that key's colour and opacity, or `none` where the role has no colour there. Every selector is one attribute's, so a later rule wins.
- **What a rule changes.** A colour, and which picture shows. Layout, text and fonts are drawn once.
- **Arrowheads.** The page's `<defs>` holds an arrowhead for each end and each role a line's stroke takes. Its triangle carries the role as a fill mark, so the rule that repaints the role repaints it.
- **A step of an order** is marked by its name, as a role is, and each rule repaints it in the value that comes with the scene in its key. A step's name holds what no id takes, so its arrowhead's id names it `--_step-<n>`, numbered in the order the page first draws one.
- **Pictures.** A picture every key shows alike is drawn once. One that another key shows otherwise, such as a produced picture's dark variant, is drawn once for each picture the keys show. Each is marked `data-shown-in` with the keys it shows in, and a rule shows those of its key alone.
- **One mode alone.** A piece of one mode gives a file of one key, under no rule.
- **What stays one-key.** The format `svg` keeps a file for each combination. The previews and the viewing step go on drawing one key at a time. So a person looks at each mode through the one-key file, and each export holds the switching file to it ([What refuses an export](#what-refuses-an-export)).

**What a reader sees.** The file reads the reader's signal and nothing else. The capability neither sets the mode nor sees it. What it promises is a floor: a browser that reads the rules and one that ignores them each show a whole figure, in one of the piece's modes, unless a person let a difference through an export. How far browsers carry the reader's mode, as tested:

- **On 6 November 2026,** a switching file stood on a temporary page on GitHub. Chrome 157 followed the reader's system and each GitHub theme setting, and repainted at a change in an open page. Firefox 148 followed the system and repainted at a change in an open page. WebKit on macOS, through a web view, drew light under a light system. Under a dark system it drew dark on some loads only, and no GitHub setting moved it. On an iPhone, browsers generally run on WebKit.
- **On 9 November 2026,** a person signed in to GitHub saw the file draw light under GitHub's light theme over a dark system, and switch when the computer's mode switched.
- **A site's own switch** reaches the file only where the site sets a single CSS `color-scheme` on the page, as GitHub's stylesheets do. A site that sets none leaves the file on the system's mode, so a light site read under a dark system shows a dark figure.
- **Not seen:** Safari itself, GitHub's other settings and surfaces, any other host or documentation site, Windows and Linux.
- **A figure that misses the mode** stays readable where it paints its own ground. So a page of a switching file with no ground of its own asks for attention ([Scenes](checks.md#scenes)).

### What the SVG renderer loses

Before it draws, the capability compares each scene with the renderer's declaration. An element of a type the declaration does not name is `refused`, and left out of the file. A property the declaration does not name for its type is `left-out`. The declaration names every primitive and property a scene of format 1 holds, so this finds no loss in format 1. While it draws, the renderer reports four losses of its own. Two are `left-out`:

- **a fill or a stroke** whose role has no colour under the brand in the combination drawn, a run's fill included. A fill is then `none`. A library's role the brand gives no value is drawn at its default ([`roles.yaml`](files.md#rolesyaml)), so it is lost only where its chain of defaults reaches no colour.
- **an image** with no picture for the combination drawn: a produced picture with no variant for it, or a picture file that is missing or cannot be read. The message says which.

Two are `refused`, and left out of the file: a line that holds neither its ends nor its points, and a path that holds no outline, `d`. Every line of a scene the engine computes holds its ends, and every path its outline ([What a scene holds](components.md#what-a-scene-holds)).

In a [switching file](#the-switching-file) of several keys, a fill, a stroke or an image lost in one key alone names that key (`key` in [The loss report](#the-loss-report)). A role with no colour in one key paints nothing there, and an image with no picture in one key shows none there.

## The PDF renderer

The `pdf` renderer draws a scene as one PDF file for each language and each combination of modes the piece names. The file holds the scene's pages in order, one PDF page for each. It draws the exports a piece declares as `pdf` ([Exports](#exports)); previews stay SVG.

- **Pages.** Where the scene's root holds the physical size of the piece's top ([A physical size](components.md#a-physical-size)), every page is that size, at 72 pt to 25.4 mm, and is drawn by one scale: the page's width in pt over its width in px (DEC-034 point 3). The page's height follows its width in that proportion, so the scale fits it too. So the page's width, a brand's value, sets how large the brand's type prints: a poster 640 px wide at A1, 594 by 841 mm, is drawn at about 2.63 pt to a px. Elsewhere a page is as large as its frame, each px of the scene 0.75 pt of the page, CSS's 96 px to the inch. The renderer's declaration states that mapping as its `unit` (DEC-001 point 2), and says under `physical-size` that its format has a physical page and that it maps a top's physical size onto it.
- **The largest page.** A PDF reader holds a page of at most 14,400 pt on a side, which is 19,200 px at 0.75 pt to a px, or 5,080 mm. A larger page, such as a phone's page of a long site, is drawn smaller to fit. It keeps its proportions, and its long side is 14,400 pt. The renderer reports it ([What the PDF renderer loses](#what-the-pdf-renderer-loses)).
- **Shapes and lines.** A box's stroke lies inside its frame, as in the SVG renderer. Rounded corners and ellipses are cubic Bézier curves. A path is drawn through its outline's moves, lines and curves, filled by its rule, nonzero or even-odd, with its stroke on its outline. A line, or a tie's connector through each of its points, is stroked with SVG's miter limit. A round turn is the cubic Bézier curve of its arc. An arrowhead is the SVG renderer's triangle: five strokes long, its base where the line stops ([Primitives](components.md#primitives)), in the line's stroke.
- **Colours.** A colour stays a role in the scene. The renderer takes its value from the brand's resolved values in the combination it draws, as DeviceRGB. A translucent colour takes an opacity of its own. A step of an order takes the value that comes with the scene in that combination, as a role's.
- **Text.** Each line of a text is drawn as the engine broke it, at its own baseline, anchored at the start, the middle or the end of the text's width. Each run is drawn in its own font, size and paint. A run's ground and sign are drawn before the line's text, as the SVG renderer draws them, and on a line that holds either each span stands at the place the engine gave it. The renderer shapes each span again with HarfBuzz from the committed font file, as the engine shaped it (DEC-005 point 4). It places each glyph at the advance shaped, so kerning is kept.
- **Fonts.** Each family a run draws in is embedded once in the file, from the brand's committed font file, never from the machine's fonts. It is cut down to the glyphs the file draws in it. Each keeps a map from each glyph back to its characters, so the text can be searched and copied. A CFF font is embedded as CFF, and a TrueType font as TrueType. A font of other outlines is not embedded ([What the PDF renderer loses](#what-the-pdf-renderer-loses)).
- **Pictures.** Each picture lies in its frame as the SVG renderer draws it ([Primitives](components.md#primitives)). A produced picture draws the variant that serves the combination drawn ([Variants](#variants)), and a picture role the file the brand gives it there. A picture file draws itself. A JPEG is embedded as its own data. A PNG keeps its transparency: an alpha channel's or a palette's as a soft mask, and one transparent colour as a colour key. A colour profile a picture carries goes into the file with it, so a PDF viewer draws its colours as a browser does (DEC-025 point 5). Each picture lies once in the file, however often it is drawn.
- **The file** names its language, `/Lang`, and the renderer with its version, `/Producer`.
- **The same bytes.** The file holds no date. A picture keeps its file's own data, and what the renderer decodes, such as a soft mask, it writes uncompressed, as it writes its other streams. So the same scene and values give the same file on every machine.

### What the PDF renderer does not carry yet

The PDF is not tagged. It carries no alternative text, no reading order and no structure such as headings (DEC-005 point 5). Its declaration says so under `not-carried`, and a later version adds them ([project-kit#2570](https://github.com/aleskalfas/project-kit/issues/2570)).

The file is PDF 1.7. In the later version that tags it, three of the cases DEC-033 settles take a form of their own. This page names two of them now, and the third when that version comes (DEC-033 point 1):

- **Emphasis.** PDF 1.7's standard structure types hold none for emphasis. That version writes `emphasis` and `strong` as structure types of the file's own, `Em` and `Strong`, each mapped to `Span`. A tool that reads the file's own types reads the emphasis. Some tools read them as less than the element an HTML page writes for emphasis. That this form counts as carried is a judgement, not a test's finding. That version's declaration names both words, and no loss stands for them (DEC-033 point 7).
- **An instance's text,** the text a component gives to the whole its instance draws, such as a diagram. A reader's tools take it before the texts the instance holds, never in their stead, since a text read in their stead would hide them and the links and headings among them. That version writes it in a form that keeps them, which this page names when the version comes (DEC-033 point 5).
- **A picture not drawn.** That version writes a picture it leaves out, where the picture has a text, as a `Figure` element whose `Alt` holds the picture's text, with the image's frame as its bounding box, and nothing drawn in it. So a reader's tools read the text at the picture's place in the reading order (DEC-033 point 8).
- **PDF 2.0, later.** PDF 2.0 holds both kinds of emphasis as standard types. A move to it is a version of the renderer of its own, after a test of the tools that read it (DEC-033 point 7).

### What the PDF renderer loses

Before it draws, the capability compares each scene with the renderer's declaration, as for the SVG renderer ([What the SVG renderer loses](#what-the-svg-renderer-loses)). The declaration names every primitive and property a scene of format 1 holds, the image among them, so this finds no loss in format 1.

While it draws, the renderer reports six losses of its own:

- **a page** larger than a PDF reader holds, `approximated`, under the page's trace id. It is drawn smaller, to fit.
- **a fill or a stroke** whose role has no colour under the brand in the combination drawn, `left-out`. It is not drawn, but a run's text is drawn unpainted, so it can still be searched.
- **a font file** whose outlines are neither CFF nor TrueType, such as CFF2, `left-out`. Its family is not embedded, and the text drawn in it is left out, keeping its place in the line. The renderer never draws that text in another font (DEC-005 point 10).
- **a line** that holds neither its ends nor its points, `refused`, and left out of the file.
- **a path** that holds no outline, `d`, of moves, lines, cubic curves and closes, `refused`, and left out of the file.
- **an image** with no picture for the combination drawn, `left-out`, as for the SVG renderer. So is a picture the renderer cannot read or decode, such as a PNG whose image data is damaged, or one that would take more than 128 MiB decoded. The message says which.

## The HTML renderer

The `html` renderer draws a scene as one *page file*: the scene's pages in one web document. [Modes](#modes) says which keys a file serves, and how it holds their modes. Writing it takes no browser. It draws the exports a piece declares as `html` ([Exports](#exports)); previews stay SVG. The viewing step draws its pages through a browser ([The HTML renderer's pages](#the-html-renderers-pages)).

- **A page** is real text over shapes. Each text of the scene is HTML text. Boxes, ellipses, lines, paths and pictures lie in SVG *layers*, each written as the SVG renderer writes it ([The SVG renderer](#the-svg-renderer)).
- **The draw order.** The file keeps the scene's order. Each run of shapes between two texts is one layer, the size of the page, so a later shape lies over an earlier text. A layer takes no pointer, so the text under it can still be selected.
- **Text.** A text is one element at its frame: its left, top and width. Each line is a child of it, placed alone at the baseline the engine gave it, and never wraps. A line's alignment in the frame is the text's anchor. Each run on a line is a span in its own font, size and paint. Spans follow each other at the browser's own widths. A run's ground is its span's background in its role, with the room the engine gave it as padding where it starts and ends, and its corners rounded there. Its height is the browser's: the span's font's ascent and descent. A run's sign is an inline SVG at the start of its span, as wide as the run's font size, raised as the engine placed it, with the gap as its margin, in the run's paint. So both keep to their run at the browser's widths. A reader's tools pass over a sign (DEC-036 point 5).
- **Size.** Every length on a page is a share of the page's width, written in `cqw`, so a page scales with no script. In a narrower window a page shrinks and keeps its proportions. In a wider one it keeps its own size, and no rule of the file clips a text.
- **Pages** follow each other down the document in the scene's order, each in the middle of the window, 24 px apart. Each keeps its own size. The file sets no colour value around them. It holds no rule on a window's width. A deck's slides lie inside a keyline, on a backdrop ([Fixed pages](#fixed-pages)). In print the pages follow each other down the sheets ([Printing](#printing)).
- **A physical size.** A page file is read in a window, and prints on the sheets its reader picks, since it holds no page rule (DEC-026 point 4). So its format has no physical page of its own, and it draws a top with a physical size as any other, losing nothing (DEC-034 point 3). The PDF export draws each page at that size.
- **The head** declares the file's encoding, UTF-8, its language and its viewport.
- **What the file holds.** A file asks for nothing. Its pictures lie inside it, each as the SVG renderer embeds it ([The SVG renderer](#the-svg-renderer)). Each font lies once, from the brand's committed font file, cut down to every character the file draws in it. Each arrowhead lies once for each colour role, and every page reaches it.
- **Names and words.** A family's name is written as the SVG renderer writes it. Whatever else a brand or a piece names is escaped. So none of it can end the file's `<style>` element or start another element.
- **Marks.** A page takes `data-page` and a text `data-text`, each holding its trace id. A shape keeps `data-id`. A layer takes `data-layer`, a line `data-line`, the part of a run on one line `data-span`, and a run's sign `data-sign`. A line opens with an empty `data-strut`, which places its baseline. The `<html>` element names the piece, the file's key, and the renderer with its version: `data-piece`, `data-key`, `data-renderer`.
- **The same bytes.** The same scene and values give the same file.

### Modes

A page file holds each mode a reader's signal names, such as `prefers-color-scheme: dark`. The reader's system or browser picks one, and an open page repaints.

- **Which keys share a file.** In one language, keys that differ only in modes paired with a signal share one file ([What the HTML renderer declares](#what-the-html-renderer-declares)). So a file serves one language, and one key over the size axes: the file's size.
- **A mode with no pair** takes a file of its own, drawn from the scene of its size.
- **The file's key** is the first it serves, in [key order](files.md#keys-of-combinations). So a piece of light and dark takes the default key, and a piece of dark alone takes dark's.
- **A paint is a custom property.** Each colour role the file paints is one property, in the CSS writer's spelling, such as `--ink`. Text and shapes read the same property, and a colour's alpha lies in its value.
- **A step of an order** takes a property of its own, `--_step-<n>`, numbered in the order the file first paints it. The CSS writer joins a role's lower-case words by hyphens, so no role's property takes a step's name. Its value in each key is the one that comes with the scene, among that key's colours, and the file's arrowhead for it takes that name too (DEC-023 point 3, DEC-032 point 5).
- **The plain rule** holds the first key's values. Each other key's values lie in a rule under the signals that part it from the first.
- **At the file's size.** Each mode takes its key's values at the file's size. So a colour a size changes takes that size's value in every mode.
- **The same elements.** Every element lies in the same place in every mode. Only the values of the properties differ.
- **No control and no script.** Nothing in the page switches a mode, so a renderer adds no words and no focus stop.
- **One mode alone.** A piece of one mode gives a file of one key, under no signal's rule. So dark alone draws dark for every reader. An axis with no mode named stays at its default.
- **Its schemes.** CSS `color-scheme` names the scheme of each mode paired with `prefers-color-scheme`, so the browser's own ground follows the mode. A file with no such mode names none.
- **Forced colours.** Under a reader's forced colours, lines, strokes and arrowheads take the reader's text colour, `CanvasText`. A fill opaque in every key takes the reader's background colour, `Canvas`, with a 1 px edge in `CanvasText`. A translucent fill stays as drawn, so a line over it may fade. A sign's path takes what any shape takes, by the same rules, so its outline stays where colours no longer part concepts (DEC-036 point 4). So does a run's sign, and a run's ground takes what the browser gives a text's background. Around fixed pages, the backdrop and each page take `Canvas`, and the keyline `CanvasText` ([Fixed pages](#fixed-pages)).
- **Pictures.** A produced picture draws the first key's variant, and a picture role the first key's file ([What the HTML renderer loses](#what-the-html-renderer-loses)). A picture file is the same in every key, so it draws as it is.

### Fixed pages

A deck's page file shows its slides as a viewer of slides does, each at its own size (DEC-031). The file does this where the scene says its pages are *fixed pages* ([What a scene holds](components.md#what-a-scene-holds)): the pages of a top whose layouts are its pages' forms, where the top asks for a height, as the deck does. A site's pages, a figure and what a slot of pages places are none. They lie as *Pages* in [The HTML renderer](#the-html-renderer) says, with nothing around them.

- **A keyline,** a thin line, lies around each slide. So a slide's empty part reads as the slide's.
- **A backdrop** fills the window around and between the slides. So the gap after a slide reads as a gap.
- **Their colours** mix the browser's own. The backdrop is 7% of the browser's text colour mixed into its ground colour, and the keyline 48%. So they follow the page's mode: a dark page lies on a dark backdrop. Inside its keyline a slide lies on the browser's own ground. The file writes no colour value for them, and reads no role of the brand.
- **The keyline reads.** It contrasts at least 3 to 1 against the backdrop and against the browser's ground, in light and in dark.
- **More contrast.** Where the reader asks for more contrast, the keyline takes the browser's text colour, whatever modes the file holds.
- **Forced colours.** The backdrop and each slide take the reader's background colour, and the keyline the reader's text colour.
- **A browser that cannot mix colours** draws the keyline in its text colour and the backdrop in its ground colour.
- **Size.** The keyline is 1 px wide and takes no room, so a slide keeps its size and its proportions. The backdrop shows 32 px wide on every side, or 4% of the window's width where that is less. In a narrower window a slide shrinks with the room that leaves it, and its keyline stays 1 px wide. In a window 500 px wide, a slide 1280 px wide is 460 px wide. Nothing scrolls sideways.
- **The same elements.** The file holds the same elements as it would with no keyline. Only its rules differ.
- **On screen alone.** The backdrop, the gutter and the keyline as an outline are a screen's. In print a slide lies inside its keyline as its border, with no backdrop ([Printing](#printing)).

### Printing

The renderer prints a page file as DEC-026 decides: its pages follow one another down the sheets, as many to a sheet as fit, each whole where it fits one. Only a fixed page prints inside its keyline, and no backdrop prints. The file holds these rules for print alone, beside the screen's, and the screen's rules hold nothing of print.

- **Each page whole on one sheet.** The file asks the browser to keep each page on one sheet, by CSS's `break-inside: avoid`, so a page that does not fit the rest of a sheet moves whole to the next. A page taller than the sheet's area runs on. No rule forces a break, and two pages lie the screen's gap apart (DEC-026 point 1).
- **A deck's slides fit a sheet.** A 16:9 slide fits the area of a sheet of A4 or Letter, upright or turned, so none is cut there, and none runs on (DEC-026 point 1). Two 16:9 slides share a sheet of A4 upright, and each takes a sheet of its own turned, in Chrome and in Firefox ([the print runs](https://github.com/aleskalfas/project-kit/issues/3010)).
- **The scale.** A page shrinks to the area's width and never grows past its own size, so it prints at the area's width over its own width, at most 1, and a fixed page at the area less its keyline over its own width (DEC-026 points 2 and 3). A page 1,280 px wide prints at about 0.56 of its size on A4 upright, at margins of 0.4 in. A deck's slides share one shape, a site's pages take the top's width (DEC-022 point 3), and a page alone is one page, so each of these prints at one scale.
- **A fixed page inside its keyline.** In print the keyline is the page's border, of the width and the colour the keyline takes on screen, under more contrast and forced colours too. The page is at most the sheet's area less the keyline on each side, 2 px in all, so the page and its keyline move to a sheet together (DEC-026 point 3).
- **The keyline on a white sheet.** The keyline's share, 48 ([What the HTML renderer declares](#what-the-html-renderer-declares)), keeps at least 3 to 1 against a white sheet, in light and in dark (DEC-026 point 3). Under more contrast a dark page's keyline is white on the white sheet, and the page's own ground marks its edge there. In a dark mode, the page's dark ground, printed in its own colours, also sets it apart from the white sheet (DEC-026 point 5).
- **Each page in its own colours.** Each page lies on the browser's ground colour, and the file asks the browser to print the page, and what it holds, in their own colours, by CSS's `print-color-adjust: exact`. The document around the pages takes neither, so the sheet around them prints as the reader's setting for backgrounds says. No mode is picked for print: the reader's signals pick it, as the browser sets them when it prints (DEC-026 point 5).
- **The sheet is the reader's.** The file holds no page rule, so the reader's print dialog sets the sheet's size, its margins and its orientation, with its header, its footer and its scale (DEC-026 point 4).
- **Where a page that runs on breaks** is the browser's pick, until a record of its own decides it (DEC-026 point 1). A page that runs on breaks where the sheet ends. The renderer places each line alone, so a break may cut a line of text or move it off its place, and cut or lose a shape. In the print runs, Chrome cut each shape the sheet's end crossed, a part on each sheet, and kept each text on its shapes. Firefox printed a page's shapes on its first sheet alone, and lost the line the first sheet's end crossed ([the print runs](https://github.com/aleskalfas/project-kit/issues/3010)). WebKit printed nothing under the tool the runs used, so Safari's only check is a person's print (DEC-026 point 7).
- **Firefox and a page narrower than the area.** In Firefox, the text of a page narrower than the sheet's area prints at a larger scale than its shapes, near the area's width over the page's, so its lines drift off their boxes. A page the area shrinks, such as a deck's slide, keeps its text on its shapes there ([the print runs](https://github.com/aleskalfas/project-kit/issues/3010)).

### What the HTML renderer declares

The renderer draws in the default font profile, and it declares each primitive and property the SVG renderer declares. It calls no outside program and reaches no service. Under `pages`, its declaration names each choice a scene leaves open (DEC-001 point 2). They are how pages lie, the gap between two of them, 24 px, and how a page scales.

- **`holds-modes`** names the format `html`, with each signal pair it reads ([Modes](#modes)). `colour-scheme`'s `light` and `dark` pair with the same values of `prefers-color-scheme`. `contrast`'s `standard` and `high` pair with `prefers-contrast`'s `no-preference` and `more`. No pair lies in the foundations or in a scene.
- **`forced-colours`** names what each paint takes under a reader's forced colours: lines, opaque fills, their edge with its width, and translucent fills.
- **`physical-size`** says that its format has no physical page, and maps no physical size (*A physical size* in [The HTML renderer](#the-html-renderer)).
- **`pages.fixed`** names how the file shows [fixed pages](#fixed-pages) (DEC-031 point 3). The keyline's `width`, 1 px, and its `share`, 48. The backdrop's `share`, 7. The gutter's `width`, 32 px, and its `window-share`, 4. Each share is the percent of the browser's text colour mixed into its ground colour. The gutter is the backdrop's width at each side of a page, or that share of the window's width where it is less. No project setting changes them.
- **`pages.print`** names how the file prints ([Printing](#printing), DEC-026 point 6): its pages down the sheets, each kept whole on one sheet where it fits, the sheet's area as the window, a fixed page inside its keyline as a border, and each page on the browser's ground in its own colours. It leaves the sheet to the reader and the break to the browser. Print has no width or share of its own: the keyline's are those of `pages.fixed`.

### What the HTML renderer does not carry yet

The file carries no alternative text, no reading order and no structure such as headings (DEC-005 point 5). Its declaration says so under `not-carried`, and a later version adds them ([project-kit#2740](https://github.com/aleskalfas/project-kit/issues/2740)).

### What the HTML renderer loses

Before it draws, the capability compares each scene with the renderer's declaration, as for the SVG renderer. While it draws, the renderer reports that renderer's four losses, under its own name ([What the SVG renderer loses](#what-the-svg-renderer-loses)). A run whose role has no colour is written `transparent`. It never takes the browser's own colour.

In a file of several keys, these losses lie in one key alone (`key` in [The loss report](#the-loss-report)):

- **A role with no colour in one key** draws nothing in that key, and reports the loss there.
- **A picture** that another key shows in another file is `approximated` in that key, such as a dark logo (*Pictures* in [Modes](#modes)).
- **A picture with no file for a key,** such as a produced picture with no variant for it, is left out in that key.

## Exports

An *export* is a set of files a piece is handed out as. Each export run is one *version*, numbered within its piece (DEC-006 point 7).

- **Formats.** A piece names its formats under `exports` in its `piece.yaml`. Format 1 knows four. The SVG renderer draws `svg` and `svg-modes`, the PDF renderer `pdf`, and the HTML renderer `html`. `svg-modes` is an addition format 1 allows (DEC-003 point 3). A piece names `svg` or `svg-modes`, never both, since the two write files of one name.
- **What a run makes:** for `svg`, one file for each page, each language and each combination of modes the piece names; for `svg-modes`, one [switching file](#the-switching-file) for each page, each language and each set of combinations that share one; for `pdf`, one file for each language and combination, which holds every page in order. For `html`, it makes the [page files](#the-html-renderer) that serve every language and combination the piece names ([Modes](#modes)). Each is drawn from the scenes under the lock `piece.yaml` holds.
- **The number.** A run takes the number one higher than the highest version the piece's `exports.yaml` records or any file of its exports folder carries, or 1 where there is none. Every file of the run carries it, so version 3 in English matches version 3 in Czech. A file the record does not name, such as one a failed run could not remove, is never overwritten, and refuses no later run.
- **What a file shows of its export.** A component may show the version's number and its date. Each file shows the run's own ([The facts of an export](components.md#the-facts-of-an-export)).
- **The name:** `<piece>.v<N>.<language>.<key>.<format>`, such as `flow.v1.en.colour-scheme.dark.svg`. It carries the piece and the version, since an exported file travels alone. An SVG file of a piece of more than one page adds the page's number, from 1, as a [preview](#previews) does: `<piece>.v<N>.<language>.<key>.<n>.svg`, such as `deck.v1.en.default.2.svg`. A switching file is named as an SVG file, under the first key it serves: `flow.v1.en.default.svg`. A PDF holds every page, so its name carries none: `deck.v1.en.default.pdf`. A [page file](#the-html-renderer)'s name carries none either, and takes the file's key ([Modes](#modes)): `deck.v1.en.default.html`.
- **Where:** `.pkit/capabilities/visual-communication/project/local/exports/<piece>/`, local to the clone and never committed. No export overwrites another. What is committed lies in the piece's folder: the record of exports, a published piece's [current copy](#the-current-copy), but for a copy at a place it names, and the files of the version handed out ([The lock](files.md#the-lock)).

### The current copy

A published piece keeps a *current copy*, an unnumbered copy of each file of an export. A page links to it, since a link cannot follow a number (DEC-006 point 7).

- **Where:** `current-copy/`, in the piece's folder, committed with the piece, unless the piece names a place.
- **When.** Each export of a published piece writes it, in the same change as the numbered files. So does the export run of `pkit visual upgrade`, under the same rules ([The lock](files.md#the-lock)). A piece in any other state writes none, and a copy it already holds stays. `pkit visual render` writes none.
- **Replaced whole.** A run replaces the folder whole, so a file the new version does not write goes. The folder holds nothing else (DEC-017 point 7).
- **A file's name** is its version's with the number left out: `flow.v3.en.colour-scheme.dark.svg` gives `flow.en.colour-scheme.dark.svg`.
- **A file's bytes** are its version's, so the two keep one hash, the SHA-256 of the whole file.
- **Whose it is.** A current copy is a piece's own where the record of exports names that piece, or a piece the location no longer holds. So a rename keeps it, and a folder copied by hand brings none while the original stands.
- **At a place.** A piece that names `copy-place` ([`piece.yaml`](files.md#pieceyaml)) takes its copy in that folder, in place of `current-copy/`. Where a documentation page shows the copy, name the folder the documentation's rules give that page's produced images. The export takes the path as you write it, and reads no rule of the documentation. Commit the copy there (DEC-006 point 7, DEC-017 point 8).
- **Left behind.** An export removes no file at a place. It names each file of the last copy it did not write again. That file may lie at the place, at a place the piece stopped naming, or in `current-copy/` once the piece names a place. It stays where it lies, so remove it once no page shows it (DEC-017 point 7).

### The record of exports

`exports.yaml` lies in the piece's folder. `pkit visual export` and `pkit visual upgrade` rewrite it, and nobody edits it. It holds one entry for each version, the oldest first. Here it is with its fingerprint left out:

```yaml
pkit_schema: visual-communication:exports
schema_version: 1
versions:
  - version: 1
    files:
      flow.v1.en.default.svg: 59e59277986cb50595fbea07b1a4ee396639d94e4bea63570b70232d8f6816e6
      flow.v1.en.colour-scheme.dark.svg: ed229c228ca2eaff8c0b5e30a09556b34010ed772f224a6fa54e3eb50fd13179
    recorded: {time: '2026-11-02T09:52:03Z', state: draft, capability: 0.1.0, renderers: {svg: 1.0.0}, used: {square: 7c4d18f3637685d8a16ab729007003c4a6b4536218d54ff7302fd7beb5850bd5}, used-stale: []}
```

| Field | What it holds |
|---|---|
| `version` | the version's number, from 1 |
| `fingerprint` | the version's fingerprint, whose inputs *The input set of each kind* in *What the check reports* lists |
| `files` | each file the run made, by name, with the SHA-256 of the file |
| `recorded` | only recorded, never compared, so a new release of the capability makes no export stale: the `time` in UTC, the piece's `state` then ([`piece.yaml`](files.md#pieceyaml)), the release of the `capability`, each of the `renderers` with its version, each produced output the run used with the version of its picture, the `value` of its record's fingerprint (`used`), and each of those it used while it was stale (`used-stale`). A version that let a number or a date through names each under `let-through`, and one that let an element of a switching file through names each under `differing` (below) |

A version that let a version's number or its date through, though it does not fit ([What refuses an export](#what-refuses-an-export)), names each text in `recorded`:

```yaml
let-through:
  - {fact: version, text: v1, element: figure/body/narrow, component: tests/stamp, version: 1.0.0}
```

| Field | What it holds |
|---|---|
| `fact` | `version` or `date` |
| `text` | the text the version's files show |
| `element` | the trace id of the text that overflows its width, or of a component around it that gets less than it asks for |
| `component` | the component that element lies in |
| `version` | the version of the library that component lies in, absent for the piece's own |

A version that let an element of a switching file through, though it paints a combination otherwise than the one-key file ([What refuses an export](#what-refuses-an-export)), names each in `recorded`:

```yaml
differing:
  - {file: flow.v1.en.default.svg, key: colour-scheme.dark, element: figure/body/steps[plan]/box}
```

| Field | What it holds |
|---|---|
| `file` | the switching file, by its name in the version |
| `key` | the combination it paints otherwise |
| `element` | the trace id of the element, or of the page where the file's styles differ |

`pkit visual mark-final` ends the record with one line, which names the version handed out ([The lock](files.md#the-lock)):

```yaml
handed-out: 1
```

Once a published piece is exported, the record also says who wrote its [current copy](#the-current-copy), above `versions`. An export in another state keeps these lines as they stand.

```yaml
current-copy:
  piece: flow
  version: 1
  files:
    current-copy/flow.en.default.svg: 59e59277986cb50595fbea07b1a4ee396639d94e4bea63570b70232d8f6816e6
    current-copy/flow.en.colour-scheme.dark.svg: ed229c228ca2eaff8c0b5e30a09556b34010ed772f224a6fa54e3eb50fd13179
```

| Field | What it holds |
|---|---|
| `piece` | the piece that wrote the copy |
| `version` | the version that wrote it |
| `files` | each file of the copy, by its path, with the SHA-256 of the file. A path in `current-copy/` is read from the piece's folder, so a rename, or a move of the location, leaves it true. A path at a place is read from the repository's root |

### What refuses an export

An export run is refused, and writes nothing, when:

- the piece is final: a final piece takes no export (DEC-017 point 3);
- the piece is published, and its lock differs from the lock of the version that wrote its current copy, or that lock cannot be read (below);
- the piece names no format under `exports`;
- the piece names both `svg` and `svg-modes`, which write files of one name;
- the piece exports as `svg-modes`, and its combinations differ in a value axis's mode of no pair that format reads ([The switching file](#the-switching-file));
- the piece has no lock yet, or its lock does not hold: a version the project does not hold or cannot read, a library the piece uses that the lock leaves out, or a major that does not fit what a library builds on;
- the piece is published, and its lock names a version not yet released (DEC-003 point 9);
- the brand cannot be read, or the piece names a mode its brand lacks;
- a font has no file, or a character has no font family that can measure it;
- a produced picture the piece shows is missing: it has no record, or its record names a variant file that is missing;
- a picture file an image shows is missing or cannot be read, the piece's, a library's or a brand's (DEC-025 point 9). The refusal names it, and why;
- a produced picture is stale (*What makes an output stale* in *What the check reports*), unless `--use-stale <output>` names it;
- `--use-stale` names an output the piece does not declare under `produced`: the refusal names those it declares;
- the piece has no page in one of its languages, so the version would hold no file in it;
- a version's number or its date does not fit where the run fills it, unless `--use-overflowing <fact>` names the fact (below);
- `--use-overflowing` names the language or the state, which the check measures as they stand;
- a switching file paints a combination otherwise than the one-key file of that combination, unless `--use-differing <element>` names each such element (below);
- a file the run would write, `exports.yaml` among them, is reached through a link;
- a file lies where a published piece's `current-copy/` goes;
- a published piece's `copy-place` is a place the rules refuse (DEC-017 point 8):
  - it lies outside the repository, at its top, under `.pkit/` or under a hidden folder;
  - it lies in the location, or is `current-copy`, which the record would read as the piece's own folder;
  - version control does not keep a file the run would write there;
  - a link leads to it, or a file lies where a folder of it goes;
- a path the run writes at a place holds anything but a file of the piece's own current copy, with the hash the record keeps. The refusal names each one: name another place, or remove a file you mean to replace;
- `exports.yaml` cannot be read, holds no list of numbered versions, or holds a `current-copy` that names no piece, version and files.

Each of these is found before the first write, so a refused run records no location either. `--use-stale` naming a declared output that is not stale refuses nothing: the run uses the picture as it is, and says it was not stale.

**A number or a date that does not fit.** A run fills each with real text, so it measures that text where it fills it (DEC-016 point 6).

- **What it measures.** Each element that shows the number or the date, and each component around it, from a font file, as the check does. A text wider than its width stops the run. So does a component that gets less than it asks for.
- **What it names.** The fact, its text and the element. It stops whether or not the stand-in overflowed too, and in any library.
- **The way past.** `--use-overflowing version` or `--use-overflowing date` uses that text as it is, and may repeat. A fact nobody named still stops. The record of exports keeps each text let through. A fact named that does not overflow refuses nothing, and the run says so.
- **Measured otherwise.** An overflow measured from a table or by an estimate stops nothing, and the run says it.
- **The language and the state** stop nothing here: they come from the piece's files, and the check measures them as they stand.
- **What no run sees.** A longer text may wrap within its box and move what lies beside it, with nothing overflowing. Look at the pages for that ([The viewing step](#the-viewing-step)).

**A switching file that differs.** The previews, the viewing step and a reviewer all see the one-key file, so nobody sees the file a page shows before a reader does. So a run holds each switching file to the one-key file of each combination it holds (DEC-018 point 1).

- **What it compares.** It reads the switching file in each combination, as a browser reads its rules under that combination's signals, and the one-key file as it stands. With no browser, it compares the two element by element: each element drawn, its attributes, what it paints and its text, and the styles that hold the fonts. What the switching file writes only so a rule can reach it is left out: its marks, and the key the file names. An arrowhead is compared as it paints, whatever its id.
- **What it names.** Each element that differs, the file, the combination's key and what differs, such as a fill. A rule the reading cannot read as a browser would is a difference at the page.
- **The way past.** `--use-differing <element>` writes the file as it is, and may repeat. An element nobody named still stops. The record of exports keeps each element let through, and a published piece's current copy made with one asks for attention, naming whoever maintains the capability as the fault's owner. An element named that does not differ refuses nothing, and the run says so.
- **Whose fault.** A difference is the renderer's, which only a release of the capability mends. Report it to whoever maintains the capability.

**A published piece's lock.** A state changed and changed back, or a lock written by hand, brings no new library version to a page (DEC-017 point 5).

- **Two ways named.** The refusal names that lock and both ways past. One is `pkit visual upgrade`, to propose a move of the lock ([The lock](files.md#the-lock)). The other is writing back that lock, which is no move of it.
- **It reads the record, not the files,** so removing the copy changes nothing.
- **No copy of its own.** Where the record holds no current copy of the piece's own, the export runs.
- **A fingerprint it cannot read** refuses, and names the record.

## Produced pictures

A *produced picture* is a picture a producer makes for one piece while it is prepared, such as a 3D render (DEC-006 point 1). It takes every value from the brand, and holds none of the piece's words: the piece places each label as its own text (DEC-006 point 2).

No producer ships yet ([Plugins](#plugins)), so `pkit visual produce` refuses every producer a piece names, and no piece has a produced picture. What follows is the contract every producer meets. The capability's tests run a producer kept for them alone.

`pkit visual produce` refuses a final piece before it reads anything else of it, and writes nothing. Making a final piece's pictures again would change it (DEC-017 point 3).

### Declaring a produced output

A piece declares each produced output under `produced` in its `piece.yaml`, by the output's name:

```yaml
produced:
  marker:
    producer: square
    inputs: {fill: accent}
    pixels: {width: 64, height: 64}
```

- **`producer`:** the producer's name.
- **`inputs`:** each input names a role of the brand by its token path, never a raw value or a component token, which only its component reads ([Tokens](components.md#tokens)). The producer must take the input, the brand must have the role, and the role must be of the value type the input takes. Every input the producer requires is given. The values come from the brand version the piece's lock names.
- **`pixels`:** the width and the height of every variant, in whole pixels from 1, fixed before the producer runs (DEC-006 point 3).

### Variants

A producer makes one picture for each distinct set of the values its inputs read, never one for each combination of modes. Each such picture is a *variant*. The command resolves each role in every combination the piece names, and the combinations that give the same values share one variant (DEC-006 point 3).

A variant is named by the first key it serves, in key order ([Keys of combinations](files.md#keys-of-combinations)). For example, the test brand's `accent` changes with the colour scheme, and not with contrast. A piece drawn in both modes of both axes has four combinations and two variants: `default` serves `default` and `contrast.high`, and `colour-scheme.dark` serves `colour-scheme.dark` and `colour-scheme.dark+contrast.high`.

### The hand-over

The *hand-over* is what a producer receives. The command writes it as JSON before the producer runs, at `.pkit/capabilities/visual-communication/project/local/handover/<piece>/<output>.json`, local to the clone.

It opens with the *document of values* of the roles the inputs name alone (DEC-005 point 7), which `document` and `version` name: `visual-communication/values`, 2. `lock` holds the versions of the brand and of the foundations library it builds on, and `keys` each combination the piece names, in key order. `tokens` holds each role by its token path, with its value type and its value in each combination. A value is in its DTCG form, made canonical: a colour with `alpha` and without `hex`, a font family a list of names. A [picture role](files.md#picture-roles)'s value is its file's bare name and the brand whose version holds it, such as `{"file": "logo.png", "library": "test-logo"}`. In a combination where the brand gives it none, it is `null`. Three keys follow. `inputs` gives the token path each input reads. `variants` gives each variant's key, the combinations it serves, and its pixels. `frames` holds the measured frames of the scene a producer reads; format 1 hands over none. A variant's values are those of its own key:

```json
{
  "document": "visual-communication/values",
  "version": 2,
  "lock": {"foundations": "1.0.0", "test-brand": "1.0.0"},
  "keys": ["default", "colour-scheme.dark", "contrast.high", "colour-scheme.dark+contrast.high"],
  "tokens": {
    "accent": {
      "type": "color",
      "values": {
        "default": {"colorSpace": "srgb", "components": [0.0353, 0.4118, 0.8549], "alpha": 1},
        "colour-scheme.dark": {"colorSpace": "srgb", "components": [0.2667, 0.5765, 0.9725], "alpha": 1},
        "contrast.high": {"colorSpace": "srgb", "components": [0.0353, 0.4118, 0.8549], "alpha": 1},
        "colour-scheme.dark+contrast.high": {"colorSpace": "srgb", "components": [0.2667, 0.5765, 0.9725], "alpha": 1}
      }
    }
  },
  "inputs": {"fill": "accent"},
  "variants": {
    "default": {"serves": ["default", "contrast.high"], "pixels": {"width": 64, "height": 64}},
    "colour-scheme.dark": {"serves": ["colour-scheme.dark", "colour-scheme.dark+contrast.high"], "pixels": {"width": 64, "height": 64}}
  },
  "frames": {}
}
```

### What a producer writes and returns

The command runs the producer with the hand-over and an empty folder, `.pkit/capabilities/visual-communication/project/local/handover/<piece>/<output>/`.

- **It writes** one PNG for each variant, `<variant key>.png`, at the variant's pixels. Nothing else it writes is kept.
- **It returns** a mapping with `points`, each exposed point with its place in each variant; `programs`, each outside program it called with its version, which its declaration names; and `losses`, what it could not make as it was handed, each loss in the one form ([The loss report](#the-loss-report)) and naming the producer as its `plugin`. `programs` and `losses` may be left out. `programs` is only recorded. Any other key refuses the run.
- **Its losses** are kept in the record, each once. The command prints each one the piece does not accept, as `loss: the <producer> producer <did> `<what>`: <why>`, and the check reports it until the piece accepts it ([Accepting a loss](#accepting-a-loss)).

*Exposed points* are named points in a picture's pixels that the piece may point at, such as to place a label (DEC-005 point 5). They follow these rules (DEC-006 points 2 and 3):

- **A point's name** takes the name shape ([Shapes](files.md#shapes)).
- **Its place** in each variant is an `x` and a `y` in that variant's pixels, from the top-left corner, with `y` going down. `x` lies from 0 to the width, and `y` from 0 to the height.
- **Every variant** exposes the same points, by name. The variants one scene holds share one pixel size, and keep each point at the same place.

What `pkit visual produce` then keeps is under *Commands* in the README. Commit the `produced/<output>/` folder: the render and the check read the picture from it on a fresh clone (DEC-006 point 4).

### The record of a produced output

`produced/<output>/record.yaml` lies in the piece's folder, beside the variants. `pkit visual produce` writes it, never a person. Here it is with its fingerprint left out:

```yaml
pkit_schema: visual-communication:produced-record
schema_version: 1
variants:
  default: {file: default.png, pixels: {width: 64, height: 64}, sha256: 846391bd55eb7c3ca617975b950a628e2b19d5ed4a6d8d7789d06b9e0895bb26}
  colour-scheme.dark: {file: colour-scheme.dark.png, pixels: {width: 64, height: 64}, sha256: cccb5b8de0fa626953e4d7fbce1441a4911bd1050f9eebb4ce355c8722042258}
combinations:
  default: default
  colour-scheme.dark: colour-scheme.dark
  contrast.high: default
  colour-scheme.dark+contrast.high: colour-scheme.dark
points:
  tip: {default: {x: 32.0, y: 0}, colour-scheme.dark: {x: 32.0, y: 0}}
losses: []
recorded: {plugins: {square: 1.0.0}, programs: {}, machine: darwin arm64, time: '2026-11-02T07:33:38Z', capability: 0.1.0}
```

| Field | What it holds |
|---|---|
| `fingerprint` | the fingerprint of what the producer read (*The fingerprint* in *What the check reports*) |
| `variants` | each variant by its key: its `file`, its `pixels`, and the SHA-256 of the file |
| `combinations` | each combination the piece names, by its key, with the variant that serves it |
| `points` | each exposed point, with its place in each variant |
| `losses` | each loss the producer reported, in the one form ([The loss report](#the-loss-report)); empty where it lost nothing |
| `recorded` | only recorded, never compared: the producer with its version (`plugins`), each outside program it called with its version (`programs`), the `machine`, the `time` in UTC, and the release of the `capability` |

### A label at an exposed point

The piece places a label at an exposed point in its content, and the label stays ordinary text. The component that draws the picture exposes its image part, and so the picture's points ([Exposes](components.md#exposes)). The component that places the label declares an option that names an item and one of its points, and reads the point in a formula ([Options](components.md#options)). The content gives that option an item's id and a point's name. Here the test library's `callout` places its label `Here` at the point `tip` of the picture `square`:

```yaml
- id: note
  use: tests/callout
  pictures: [{id: square, output: square}]
  label: Here
  at: {item: square, point: tip}
```

The engine maps the point from the variant's pixels into the frame the picture fills, so the point scales with the picture (DEC-006 point 3). How a picture fills its frame is under [Primitives](components.md#primitives).

## Written code

*Written code* is a brand written out by a code writer, such as the CSS custom properties a web page reads. A project declares it in the location, as it declares a piece (DEC-002 point 1).

### The declaration

A declaration is `code/<name>.yaml` in the location. Its name is the file's name, of the name shape, and `pkit visual write-code <name>` writes the code it asks for:

```yaml
pkit_schema: visual-communication:code
schema_version: 1
writer: css
form: 1
brand: test-brand
lock:
  foundations: 1.0.0
  test-brand: 1.0.0
out: web/brand.css
```

| Field | What it holds |
|---|---|
| `writer` | the code writer: `css` or `json` |
| `form` | the form of the writer's spelling: `1`; the `json` writer also takes `2` |
| `brand` | the brand, by its library's name |
| `lock` | a version of the brand and of every library it builds on, and of any other library whose roles the code holds, each one the project holds and the capability reads, whose majors fit what each builds on |
| `out` | where the code goes: a file of the project's tree |
| `prefix` | optional: a name that opens every name the code writes. The `json` writer takes none ([The JSON code writer](#the-json-code-writer)) |
| `accept-losses` | optional: the losses a person accepted ([Accepting a loss](#accepting-a-loss)) |

- **The lock is the declaration's own.** A person moves it on purpose, and no command moves it (DEC-005 point 7). So the code changes only when the declaration changes, or when the person names the declaration to `pkit visual add`. Naming it lets the command replace a copy not yet released that the lock names, under the same number ([The lock](files.md#the-lock), DEC-013 point 5). The run that leaves the copy prints the difference in the code first.
- **What the code holds:** the document of values under the lock: every token the brand exports, and every other role of each library of components the lock names, at the brand's value or at its default (DEC-008 point 5), at the versions the lock names. It holds them in every combination of the brand's axes ([Axes and modes](files.md#axes-and-modes)) whose kind the writer spells, each other axis at its default. A library's role that has no value under the brand is left out. Code that reads a library's role names that library's major in its lock, since the library promises its names by major. A brand built on a base is read over the base the lock names. The code follows no piece's modes.
- **Where `out` may not lie:** outside the repository, under `.pkit/`, under a hidden folder, or in the location's library folder, its `code/` folder or its `pieces/` folder. Nor may it be reached through a link, or be a folder.
- **Committing the code** is the project's choice, as for any file its build writes. Its record goes with it (DEC-006 point 4).

### The record beside the code

`pkit visual write-code` writes a record beside the code, `<out>.record.yaml`, such as `web/brand.css.record.yaml`. After its binding, it holds the `fingerprint` of what the code was written from (*The fingerprint* in *What the check reports*), the `sha256` of the code as written, and what is only `recorded`, never compared: the writer with its version (`plugins`), the outside programs (`programs`, none), the `machine`, the `time` in UTC, and the release of the `capability`.

### The CSS code writer

The CSS writer writes one style sheet. Form 1 spells it as follows.

- **Names.** Each token path gives one custom property: `--`, then the `prefix` and `--` where the declaration names one, then the path's segments joined by `--`. A segment keeps its own single hyphens, so no two paths give one name: `space.1` gives `--space--1`, `text-primary` gives `--text-primary`, a library's role `test-parts.note` gives `--test-parts--note`, and `space.1` with the prefix `brand` gives `--brand--space--1`.
- **Values.** A `color` is `#rrggbb`, each channel rounded to 8 bits, half up, or `#rrggbbaa` where its alpha is not 1. A `dimension` is its number and `px`. A `fontFamily` is its names, each in double quotes, joined by `, `. A `fontWeight` or a `number` is the number, in the capability's canonical text, such as `1.4` or `16`.
- **Modes.** Each mode is switched by an attribute, `data-<axis>="<mode>"`, on one element: the page's root by default. An area that changes modes sets every axis's attribute on its own element; the root may leave out an axis at its default. Form 1 spells value axes alone. Of a brand that gives a size, it writes every value at each size axis's default (DEC-021 point 8). No rule follows a window's width.

The rules come in this order:

1. **`:root`** holds every token, at the combination of every default.
2. **One rule for each mode** of each axis, `[data-<axis>="<mode>"]`: the axes in the order of their names, each axis's modes in the order the foundations declare them, or the brand an axis of its own. A mode that is not the default holds every token the axis changes in some combination, at that mode, with every other axis at its default. The default mode holds each token whose first axis that changes it, in name order, is this axis, at every default. So an area may set a default mode inside another area.
3. **One rule for each combination** of two or more modes that are not their axis's default, in key order, its selectors joined: `[data-colour-scheme="dark"][data-contrast="high"]`. It holds only the tokens whose value there differs from what the rules before it give. More attributes are more specific, so it wins over the rules of fewer.

A rule with no token is not written. A rule holds each token once, in the order of the token paths. A comment opens the sheet, and names the form and the lock. The test brand gives this sheet, its comment left out and its rules cut short:

```css
:root { --accent: #0969da; --font--body: "Source Sans Pro"; --space--1: 4px; }
[data-colour-scheme="light"] { --accent: #0969da; }
[data-colour-scheme="dark"] { --accent: #4493f8; }
[data-contrast="high"] { --line: #000000; }
[data-colour-scheme="dark"][data-contrast="high"] { --line: #ffffff; }
```

It holds no `[data-contrast="standard"]` rule: every token the contrast axis changes, the colour scheme changes too, and its name comes first. The writer writes each declaration on a line of its own.

**Losses.** A token of a value type the writer has no form for is left out, as a loss known before the writer runs. In form 1 those types are `typography`, such as the test brand's `type.body`, and `picture`, such as a brand's logo. Each other token a size changes is written at the size axis's default, and reported as approximated.

### The JSON code writer

The JSON writer writes the [document of values](#the-hand-over) as one file, for a program that reads data, such as a game's runtime. It adds nothing to the document, and leaves out only what its form's version does not hold. A declaration names `writer: json`, `form: 2` and an `out` such as `game/brand.json`.

- **Its forms.** Each form is that version of the document, and the writer keeps writing each ([Versions](#versions)). A schema states each, so a program can check the file against it:
  - **Form 2,** version 2, holds a picture role's file. Its schema is `.pkit/capabilities/visual-communication/schemas/values-2.schema.json`.
  - **Form 1,** version 1, holds no picture role. Its schema is `.pkit/capabilities/visual-communication/schemas/values.schema.json`.
- **What it holds.** It holds what the code holds ([The declaration](#the-declaration)), in the fields the hand-over opens with, and no others.
- **Names.** A token keeps its path as the brand exports it, such as `space.1`. So the writer takes no `prefix`, and refuses a declaration that names one, saying why.
- **Modes.** A token's `values` holds its value under the key of each combination ([Keys of combinations](files.md#keys-of-combinations)). A program picks a set of values by its key. Value axes and size axes are written alike, so the keys of each size the brand gives are among them (DEC-021 point 8).
- **Values.** Each value is in the form the hand-over gives it: its DTCG form, or a picture role's file and brand.
- **The text.** Each key of an object lies on its own line, down to a token's values. Each value then keeps to one line, in the capability's canonical text. So a changed value changes one line, and the same document gives the same file on every machine.
- **Losses.** Form 2 takes every value type and every kind of axis, so it reports no loss. Form 1 has no form for a picture role, so it leaves each out, as a loss known before the writer runs.

The check reads this code as it reads any written code (*Written code* in *What the check reports*). The test brand, which gives no picture role, gives this file in form 1, cut short:

```json
{
  "document": "visual-communication/values",
  "version": 1,
  "lock": {
    "foundations": "1.0.0",
    "test-brand": "1.0.0"
  },
  "keys": ["default","colour-scheme.dark","contrast.high","colour-scheme.dark+contrast.high"],
  "tokens": {
    "accent": {
      "type": "color",
      "values": {
        "default": {"alpha":1,"colorSpace":"srgb","components":[0.0353,0.4118,0.8549]},
        "colour-scheme.dark": {"alpha":1,"colorSpace":"srgb","components":[0.2667,0.5765,0.9725]},
        "contrast.high": {"alpha":1,"colorSpace":"srgb","components":[0.0353,0.4118,0.8549]},
        "colour-scheme.dark+contrast.high": {"alpha":1,"colorSpace":"srgb","components":[0.2667,0.5765,0.9725]}
      }
    }
  }
}
```

## The viewing step

The *viewing step* draws a piece's pages as images, for a person or an agent to read (DEC-015 point 1). `pkit visual look <piece>` runs it, and `pkit visual pages <piece>` lists what it can draw.

- **No render, and no export.** It moves no lock and keeps no findings. It uses up no version number, writes no `exports.yaml` and records no location.
- **An export's facts** show as in a [preview](#previews): a number shown is the next export's, which the run leaves for it. Where an image shows a stand-in, the command says so, and why, after what the report says ([The facts of an export](components.md#the-facts-of-an-export)).
- **Under the lock.** It reads the lock `piece.yaml` holds, and computes the piece's scenes under it (DEC-015 point 4).
- **It runs no helper or producer.** A produced picture is drawn as it stands, stale or not. One with no variant for the key is left out, as a loss. So is a picture file that is missing or cannot be read.
- **Which renderer.** It reads a piece that declares `html` through [the HTML renderer](#the-html-renderer), and any other piece through [the SVG renderer](#the-svg-renderer). `--renderer svg` or `--renderer html` names one.
- **What it draws.** By default, every page in the piece's source language, in the first key in [key order](files.md#keys-of-combinations). That is the combination of defaults wherever the piece names it. `--page`, `--language` and `--key` pick others. `--every-language` and `--every-key` take them all.
- **Each size.** A piece on a size axis is drawn at one size by default. Name each other size's key with `--key`, a phone's among them, or take every key with `--every-key`.
- **The size of an image.** A page is drawn 1568 pixels on its long edge, or larger where its smallest text would land under 10 pixels. No image passes 1568 pixels on either edge.
- **Bands.** A page too tall for one such image is drawn in *bands* (DEC-022 point 7). Each band is a strip of its height as wide as the page, and all share one scale. Each band overlaps the next by the page's tallest line, so every line lies whole in one band. Where a gap between elements lies in that overlap, the band ends in it. Read every band of a page before you judge it, and a band's edge is no fault of the page.
- **A page too wide** for one image whose smallest text reads is drawn 1568 pixels wide. Its smallest text may not read, and the report says so.
- **Under forced colours.** `--forced-colours` also draws each page file of the HTML renderer as a reader who forces their own colours sees it, in the browser's two forced palettes ([Under forced colours](#under-forced-colours)).
- **The ground.** Where a page draws no ground of its own, the SVG renderer's image lies on white, which the piece never set. The HTML renderer's lies on the browser's own ground in the mode drawn, which differs between browsers, and under a forced palette on that palette's ground. Judge a text over nothing knowing this.
- **No promise about pixels.** An image may change with the tool, its version or the machine (DEC-015 point 6).

### The SVG renderer's pages

resvg draws them, with no network. It draws from the fonts the page embeds, never one on the machine. An image shows resvg's drawing, not a browser's.

### The HTML renderer's pages

A browser draws them. No other format needs one, and the capability installs none.

- **Which browser.** A browser of the Chromium family: the first found where Chrome and Chromium install themselves, or the one the project names ([The browser](files.md#the-browser)).
- **The page file.** The browser reads each [page file](#the-html-renderer) as the renderer wrote it, in one start for each file. The pages drawn from one file share one scale, the largest any of them asks, as far as the widest page fits 1568 pixels. So a page's image may be larger than its own text needs. The browser draws the same bands of a page as resvg does at that scale.
- **The window** is as wide as the widest page, with the gutter the renderer declares, 32 px, on each side. So a [fixed page](#fixed-pages) keeps its own size. The step widens the window so for every file. Each image is still one page, or one band of it, so the keyline and the backdrop lie outside every image (DEC-031 point 5).
- **Each mode.** Each key the run draws out of a file is drawn in that start, with no reload. The step sets every signal the file reads by the browser's emulation, so the machine's own settings play no part. Each read the report names runs in each key drawn.
- **What an image shows.** One browser's drawing, which stands for no other browser. The report names that browser and its version.
- **What an image does not show.** Another browser's engine, a reader's own settings, a narrow window, printing, and the keyline and the backdrop around a fixed page. Open the page file in your own browsers to see those. Forced colours in the browser's two forced palettes are drawn where you ask ([Under forced colours](#under-forced-colours)).
- **The fonts.** The browser reads the faces the file embeds. A span it draws in a font of the machine is reported.
- **The first read.** Each start first reads a small page of its own, planted with one fault of each kind the report names. Where the report does not name each, the run stops. The page also holds a box for each signal the file reads. Where setting the signal does not repaint its box, the run stops too.
- **Its profile** lies in a throwaway folder of the clone's local folder, which the run removes, even one that stops. The browser may write files of its own elsewhere, such as a crash report.
- **Its own sandbox** stays on. The step passes no flag that turns it off or weakens it. A sandbox around the browser, such as a session's, may still stop it ([When the browser stops](#when-the-browser-stops)).

### Under forced colours

Some readers have their browser replace a page's colours with a few of their own, such as white text on black. `pkit visual look <piece> --forced-colours` draws what such a reader gets, as well as the keys it draws (DEC-027).

- **When it is worth asking.** Forced colours leave the layout, the words and the fonts as they are, so most looks need none. Ask where colour carries something a forced palette may lose: a translucent fill, or a picture under a text or a line. The run takes about twice as long.
- **Two forced palettes.** The browser draws each page file in its own two: `light`, dark text on a light ground, and `dark`, the reverse. The step sets them, so the machine's own setting plays no part.
- **Which key each shows.** A browser sets a scheme and more contrast with its forced palette. So each palette shows the key the page file holds for those signals, whichever keys you pick: the dark palette shows the dark mode where the file holds one. Your keys pick the page files, each at its size.
- **A start of its own.** After a file's start, a second start draws it under the browser's flag that forces its colours, `--force-high-contrast`, at the same scale. The browser's emulation alone forces the text in some browsers and not in others, so the step never draws without the flag.
- **Its first read.** That start reads its own planted page in each forced palette. It stops the run where a span left to forcing shows no ink, since the palette did not reach the text, and where a palette's ground is not lighter than its text in `light`, or darker in `dark`. Each read the report names runs in each forced image too.
- **What it shows.** That browser's forced palettes, not a reader's own, which may hold other colours, such as a link's. A reader whose browser reports another scheme or contrast beside its forced palette may see something else. The report says so.
- **The SVG renderer's pages** are never drawn so: resvg knows no forced colours, and the run is refused ([What refuses a run](#what-refuses-a-run)).

### When the browser stops

A run stops where no browser runs, where one stops part way, or where its first read fails (DEC-020 point 8). This holds of the start under forced colours too.

- **What it writes.** The page files and `report.json`, in the HTML renderer's folder, and no image ([What a run writes](#what-a-run-writes)).
- **What the report says.** What stopped it, and under which lock. It names what is missing: where the step looked for a browser, or the program it started and what that said.
- **A sandbox.** Where the browser's words show a sandbox, the run says that a sandbox stopped the browser. Otherwise it names what the browser said.
- **A browser run as root.** Chrome run as root, as a container may run it, refuses to start with its own sandbox on. The run says so, apart from a sandbox, and never turns that sandbox off.
- **How to go on.** The command exits 3, and names three ways on, in this order (DEC-024 point 4), and a fourth after a stop under forced colours (DEC-027 point 4):
  1. a build pipeline's drawings of the piece's pages, where the project has its pipeline draw them ([A pipeline's drawings](#a-pipelines-drawings)). They show a pushed commit, not your working tree.
  2. the same look, run once by a person outside any sandbox, such as in their own terminal. This line is addressed to a person. It runs the clone's scripts as they stand, with that person's rights.
  3. the SVG renderer's pages, through `pkit visual look <piece> --renderer svg`. They show the layout, never the page file.
  4. where the start under forced colours stopped, the same look without `--forced-colours`, which draws the page files in their own colours.
- **For an agent,** a last line says what it does (DEC-024 point 6). It reads a pipeline's drawings, or asks a person, and never takes the command out of the sandbox itself. It never runs a look over the folder a person's run left.

### What a run writes

A run writes in its renderer's folder, local to the clone ([The clone's local folder](files.md#the-clones-local-folder)). Both lie in `.pkit/capabilities/visual-communication/project/local/look/`.

- **`<piece>/`** holds the SVG renderer's pages.
- **`<piece>.html/`** holds the HTML renderer's. No piece's name holds a `.`, so no piece takes this name.
  - **`forced-light/` and `forced-dark/`** inside it hold the images and frames of each forced palette, where the run drew them ([Under forced colours](#under-forced-colours)). Each takes the names below, by the key its palette shows. No file of the folder takes a name without a `.`, so none takes these.

A run replaces what an earlier run left in its own folder, so a folder never mixes two runs. It leaves the other renderer's folder where it lies.

| File | What it holds |
|---|---|
| `<piece>.<language>.<key>.png` | one page drawn. A piece of more than one page adds the page's number, from 1, to this name and the next: `<piece>.<language>.<key>.<n>.png` |
| `<piece>.<language>.<key>.band-<k>.png` | one [band](#the-viewing-step) of a page, numbered from 1 at the page's top, in place of the page's one image. A piece of more than one page puts the page's number first: `<piece>.<language>.<key>.<n>.band-<k>.png` |
| `<piece>.<language>.<key>.frames.json` | beside each image, its language, key, page and pixels, and the lock it was drawn under. Then each element's frame in the image's pixels, with its [trace id](components.md#trace-ids). Beside a band, it names the band. It frames each element the band shows, in part or whole, so a frame a band's edge crosses reaches past the image |
| `<piece>.<language>.<key>.html` | through the HTML renderer, the [page file](#the-html-renderer) the images were drawn from, whichever pages and keys the run draws. Its `<key>` is the file's key ([Modes](#modes)). Open it in your own browser. It is no export, and is never committed |
| `report.json` | [What the report says](#what-the-report-says) |

### What the report says

`report.json` says what the images cannot show as the renderer set it, and the command prints the same (DEC-015 point 3). It holds the piece, the lock, the renderer with its version, the tool, and the lists below. Each entry but an image's names the language, key and page it lies on.

- **`images`:** each image, with its frames' file and its pixels. Through the SVG renderer, `on-white` is true where the page draws no ground of its own. Through the HTML renderer, `on-browser-ground` is true there instead. That image lies on the browser's own ground in the mode drawn, not on white, or under a forced palette on that palette's ground.
  - **`band`:** on each band of a page, its `number` from 1, how many the page has, `of`, and its `top` and `height` in the page's px. A page's bands follow one another in order.
  - **`too-wide`:** true on each image of a page too wide for its smallest text to read. Another image holds no such key.
- **`dropped`:** each text or run the tool drew nothing of, whatever the cause, with its element and its characters. `whole` is true for a whole text, and false for a run lost from a line. A text in the colour of what lies beneath it, or under a later element, was drawn, so it is not here. Through the HTML renderer, an entry is a span that left no ink, or lies off its page. A span's ink is its letters alone: the read hides its sign and its ground. Its `why` says which: `no ink` or `off the page`. Each page is read whole, once, so a text in two bands is listed once.
- **`losses`:** each [loss](#the-loss-report) the renderer reports. A loss that names a key is listed under that key alone. `accepted` is true for one the piece [accepts](#accepting-a-loss), which the report names all the same.
- **`drawn-otherwise`:** each run measured in more than one family, with its element, its characters and the families. resvg may set the whole run on a line in one of them, where a browser sets only the characters the first family lacks. Through the HTML renderer, an entry is a span with `why`:
  - `no face`: the file holds no face of its family at its weight, with that family and weight;
  - `font of the machine`: the browser drew it, even in part, in a font of the machine, with each such font.
- **`profiles`:** through the SVG renderer, each picture a page shows that carries a colour profile, with its element and its file's name. resvg may draw it without its profile, where a browser draws it by it (DEC-025 point 5).

Through the HTML renderer the report holds these too:

- **`forced`,** on each image and each entry: the forced palette it was drawn in, `light` or `dark`, and `null` for none. An image's path names its palette's folder.
- **`tool`:** the browser's name, its version and its program. `stands-for` says that each image stands for that browser alone.
- **`forced`,** of the report itself: `null` where the run drew no forced palette. Otherwise the `palettes` drawn, the browser's `flag` that forced them, the `folders` they lie in, and what their images do not show, `does-not-show`.
- **`page-files`:** each page file, with its language, its key, and `keys`, each key it holds.
- **`words`:** each text whose spans differ between the scene and the page file, in their words, order or number, with each side's spans. The page file lost part of that text.
- **`refused`:** each request the page made, which the browser refused. A page file asks for nothing, so each request is a fault of the file.
- **`stopped`:** `null` where the browser drew. After [a stop](#when-the-browser-stops), what stopped it, where the step looked, the program it started and what that said. Then `sandbox`, whether a sandbox stopped it, and `as-root`, whether the browser ran as root. `forcing` is whether the start that stopped forced its colours. `go-on` lists the ways on in their order, and `for-an-agent` says what an agent does.

### What refuses a run

A refused run leaves its renderer's folder as it was. The fonts it held in a temporary folder of the local folder are gone, and that folder itself may remain. Any fault that stops a piece being drawn refuses a run, through either renderer, before the browser is asked. Among them:

- a piece with no lock, naming the render that writes one, or, for a final piece, the lock to write back ([The lock](files.md#the-lock));
- a lock that does not hold, naming why;
- a page, a language or a key the piece does not have, naming those it has;
- a renderer other than `svg` and `html`;
- forced colours through the SVG renderer. Where the piece goes through it by default, the refusal names `--renderer html`;
- a brand that cannot be read;
- a font with no file, or a character no font holds;
- a page with no size, or an image of one past 134217728 pixels at [its size](#the-viewing-step). Unless the piece is final, `pkit visual check <piece>` names what it still owes, such as a picture never produced;
- through the HTML renderer, a `browser` in the configuration that names no path ([The browser](files.md#the-browser)).

A version not yet released under a final or a published piece's lock refuses no run: the lock holds, and the piece draws.

### A pipeline's drawings

A project's build pipeline may draw each piece's HTML pages on every change it checks, such as a pull request (DEC-024 point 5). An agent whose session cannot run the browser then reads those. Whether the pipeline does so is the project's choice. No setting of the capability's says so, and the capability ships no pipeline file.

- **What it runs.** On a runner with a browser of the Chromium family, `pkit visual look <piece> --renderer html --every-language --every-key` for each piece of the location. It runs the command as the project writes it. It sets nothing that turns off the browser's own sandbox.
- **What it keeps.** The look's folder, `look/`, with each piece's images, frames, page files and report, as one artefact of the run. Its name is `visual-drawings-<commit>`, with `<commit>` the full hash of the commit drawn. On a pull request that is its head commit, not a merge the pipeline may check out.
- **A stop fails the job.** A look that does not draw fails the job, so a stop never reads as a clean run. Its report is kept with the rest.
- **No standing reach.** The job runs the change's own scripts, which an agent may have written. So it holds no secret, and its token only reads.
- **What they show.** The commit drawn, as that runner's browser drew it, not your working tree. An image stands for that browser alone.

**Fetching them.** Take the commit, such as a pull request's head, and fetch its drawings into a folder of their own, named by that commit.

- **A folder of its own.** Never fetch them into `look/`, where a look replaces its renderer's folder ([What a run writes](#what-a-run-writes)). Read the fetched folder as a look's folder, `report.json` first.
- **The hosts it reaches.** In a session's sandbox, each host the fetch needs is the project's own allowance to add. The capability declares none.
- **A run the permission model confines,** such as a builder's, reaches no such host. Only the SVG renderer's pages remain in it.
