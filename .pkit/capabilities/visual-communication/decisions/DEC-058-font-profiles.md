**In plain terms:** a whiteboard service draws text in fonts of its own, and a brand has no file for them. So a brand gives a *font profile* for that medium: the medium's fonts its roles take there. Profiles are the modes of one shared axis, of a kind of its own: a renderer chooses the profile it draws in, a piece never names one, and no component reads one. Its default, `files`, draws the brand's own font files, and each other mode is one medium's, the first `mural`. A profile changes font families and weights alone, and reaches a plugin only in a scene, so written code, and the programs that make pictures, get the brand's own fonts alone. What a medium imposes on its text is the capability's: it ships, for each medium, the fonts the medium holds, an estimate of each and for some a table of widths, and the engine measures with them. A brand says only which of its families are the medium's own. A piece gets scenes of its own in each profile its exports' renderers name. They are checked and previewed, and a preview draws the medium's text in the brand's own fonts, showing the widths the engine measured. The lock's search places no profile, and the seam's version rises once.

## Context

The record of brands decides that the fonts a brand gives a group of renderers are a *font profile*, a mode of one shared size axis, and that the default profile measures and draws the brand's own font files. Each profile says how each font is measured: from a file, from a table of widths, or by an estimate. A table or an estimate stands only for a font a medium holds itself, and the table ships with the renderer for the medium ([visual-communication:DEC-004-brands-and-notations] points 2 and 9). So font profiles need no mechanism of their own (DEC-004, Rationale). This record overturns three of those choices: that font profiles are a size axis, that a profile chooses between a table and an estimate, and that the table ships with the renderer (Implications). The record of the engine adds that each renderer names its profile, that a brand without that profile is drawn in its default with each font reported lost, and that one scene is computed for each combination of size modes, profiles included ([visual-communication:DEC-005-engine-and-plugins] points 6 and 10). The record of size and shape left open how a profile joins a piece's keys, since a piece's `modes` name none ([visual-communication:DEC-021-size-and-shape], Implications).

The engine resolves a brand's values into one document, which holds its tokens in each combination asked for. Renderers, code writers, producers of pictures and helpers all read it, and the code writer for JSON writes it out unchanged (DEC-005 point 7). Written code is public: code outside the capability reads a brand's axes, modes and keys, and no lock protects that code (DEC-004 point 5).

Nothing builds a profile yet. The engine measures only from font files, every renderer draws in the default profile, and the foundations declare no profile axis. Each reader of a brand's axes in the capability's code tells a size axis from a value axis by the kind it is declared with. Most select the axes of one kind and leave the others out. A few take every axis not of one kind as of the other. The command that writes code is one: it reports each token changed by an axis its writer does not spell as a loss. The check of a switching file's pairs is another: it takes every axis but a size as a value axis. And the finding that refuses an axis of a brand's own of any other kind shares one list of kinds with the reader of the foundations' axes.

The first medium with fonts of its own is a whiteboard service, Mural, which a renderer is to draw a piece for without signing in ([project-kit#2569](https://github.com/aleskalfas/project-kit/issues/2569)). Its default font is commercial, so no brand can ship its file, and a tool that already draws on it measures that font's text at a line height of 1.15. The talk generator behind the capability's design estimated each text's width as its count of characters times one constant, and 6 of 2,479 texts wrapped past their box (DEC-005, Context).

A brand may hold an axis of its own, so once that ships, a new shared axis breaks (DEC-004 point 5). [visual-communication:DEC-057-own-axis-prefix] proposes that the name of a brand's own axis take the prefix `own-`, which no shared axis's name takes, so that every new shared axis lands as an addition all the same. That record is proposed, and this record rests on it for the prefix.

## Decision

**The foundations declare the shared axis `font-profile`, of a kind of its own, `profile`. Its default mode, `files`, measures and draws a brand's own font files, and each other mode is the profile of one medium with fonts of its own. A renderer chooses its profile, a piece never names one, and no component reads one. Every plugin is handed the document of values in `files` alone, so a profile reaches a plugin only in a scene. A brand gives a profile as it gives a size, and a profile changes font families and weights alone. What a medium imposes on its text is the capability's: it ships the fonts each medium holds, with an estimate of each and perhaps a table of widths, and a brand says only which of its families are the medium's own. A piece's scenes are computed, checked and previewed in each profile its exports' renderers name, a preview drawing the medium's text in the brand's own fonts and showing the widths measured. The lock's search places no profile, and the seam's version rises once.**

### 1. The axis, its kind and its modes

- **The axis, named `font-profile`.** It is an axis of the foundations, so its name takes no prefix, which only a brand's own axis takes (DEC-057 points 1 and 2).
- **A kind of its own, `profile`,** beside `value` and `size` (DEC-004 point 2). An axis of the kind has a scene for each of its modes, as a size axis has, since a text measured in other fonts moves what lies after it. A renderer chooses its mode, no piece names it, and no component reads it (point 2). Its modes change only font families and font weights, member by member (point 4).
- **Read only where code opts in.** Each reader of a brand's axes selects the kinds it reads, such as the size axes a component reads, and so leaves the axis out unless it is changed to read it. Only the code that builds a scene's key reads it (point 6), and the first Task has every other reader select its kinds (Implications). So a switch or a `when` that reads `:font-profile` reads no size axis a piece can name, and fails as DEC-021 points 3 and 7 already say.
- **Only the foundations declare one.** A brand's own axis takes the kind `value` or `size`, so one that takes `profile` fails, by the finding that refuses an axis of a brand's own of any other kind (`own-axis`). The kinds a brand's own axis takes are kept apart from those the foundations declare, so that finding never admits `profile` (Implications).
- **Its default, `files`.** It measures and draws each font from the brand's committed files (DEC-004 point 9). Every renderer that can draw those files draws in it (DEC-005 point 10).
- **A mode for each medium with fonts of its own** that a renderer of the capability draws in, named after the medium. The first is `mural`. A profile serves every renderer of its medium, such as one that writes a file for the medium and one that draws into it.
- **Declared first, with two modes.** An axis with one mode is not declared (DEC-004 point 2), so the foundations declare it with `files` and `mural` together. A brand gives the modes of a shared axis only once the foundations declare it, since a modifier that is no shared axis, and declares no axis of the brand's own, fails (`brand-axis`). So the first Task that builds this record declares the axis, and every other follows it (Implications), the `mural` mode thus coming before the renderer that draws in it. Declaring it changes no brand, since a brand has the axis only where it or its base gives it, as it has a size (point 4). A later medium's mode is a new mode, which breaks nothing (DEC-004 point 5).
- **Declared with the findings no rule gives yet.** The kind is new, so the release that first reads it is the one that declares the axis. Two of its rules have no finding yet: a piece whose `modes` name an axis of the kind, which DEC-005 point 6 already denies a piece, and a mode of one that changes a value other than a font family or a font weight. Once released, neither could be refused while the format changes only by additions ([visual-communication:DEC-003-change-over-time] point 3). So the Task that declares the axis builds both findings (point 9), and the capability is never released with the axis and without them.

### 2. A renderer chooses the profile, a piece never names it, and no component reads it

This is how the axis differs from `device`, the size a piece chooses (DEC-021 point 1).
- **A renderer chooses.** Each renderer's declaration names the mode it draws in (DEC-005 point 10).
- **A piece never names it.** A piece's scenes take each profile that a renderer of a format the piece exports names (point 6). A piece whose `modes` name an axis of the kind `profile` fails validation (point 9).
- **No component reads it.** A switch or a `when` reads only a size axis a piece can name, and an axis of profiles is none, so one that reads `:font-profile` fails validation as DEC-021 points 3 and 7 say (point 1). So a profile changes nothing a component draws but how its text measures.
- **A brand without the profile** is drawn in its default, and the renderer reports each font it cannot draw as a loss (DEC-005 point 10). A piece whose brand lacks a size fails instead (DEC-021 point 2), since the piece named that size, and no piece names a profile.

### 3. A profile reaches a plugin only in a scene, and written code carries none

This point says which of the engine's readers sees the axis. Renderers, code writers, producers and helpers each read the document of a brand's values, in the combinations asked for (DEC-005 point 7).
- **Every plugin is handed the document of values in `files` alone.** A renderer takes from it the colours and pictures a scene's roles name, which no profile changes (point 4), and takes each run's fonts from the scene, which names them (DEC-005 point 5). So a profile reaches a plugin only in a scene, which a renderer draws, whether for an output, for a preview or for a part placed as a picture.
- **So written code carries no profile.** A declaration of written code asks for the document in `files` alone. The JSON writer, which writes the document unchanged, writes no key that holds the axis, though it writes those of a brand's size axes (DEC-021 point 8). No code writer is handed the axis, whatever kinds of axis it spells. Nor does the command report a loss for it, as it reports each token a size changes to a writer that spells no size, such as the CSS writer: a writer may spell a size, and none may spell a profile. A profile a brand gives, changes or ceases to give leaves every name in written code as it was.
- **So a brand exports no profile.** It exports its axes, modes and keys (DEC-004 point 5), but for the axis of font profiles, its modes and the keys that hold it, though a brand built on it names them (below).
- **So a picture is made in `files`.** A producer or a helper is handed the values it declares, and the frames it reads, in combinations in `files` alone (DEC-005 point 7). So a picture serves only those combinations, and has no variant in another profile ([visual-communication:DEC-006-work-outside-the-engine-and-outputs] point 3). A scene in another profile shows the variant of its combination with `files` in place of its profile, as a run's default fonts are found (point 6). Whatever fonts a picture draws are in its pixels, so every medium shows them as they were made. A brand's new profile makes no picture stale (DEC-006 point 5).
- **Carrying the profile later is an addition.** Written code that comes to carry it gains keys and keeps its form (DEC-021 point 8), and moves to it only when its declaration moves (DEC-005 point 8). Carried and then dropped, the axis would break code outside the capability, which no lock protects (DEC-004 point 5).
- **A brand that ceases to give a profile still breaks,** as removing a mode does (DEC-004 point 5), though no written code, piece or component names one. A brand built on it may give values in that profile by its name, as on its base's other axes (DEC-004 point 6), and would then add a mode its base lacks, which fails validation (DEC-004 point 11). For a piece it changes only how the piece looks: the renderer of that profile draws it in `files`, reporting each font lost (DEC-005 point 10), and a change of look breaks nothing (DEC-003 point 6).

### 4. A brand gives a profile as it gives a size, and a profile changes font families and weights alone

- **As a size.** A brand with no base gives its profiles as the modes of a `font-profile` modifier in its Resolver document, the default among them. A brand built on another has its base's (DEC-021 point 2, DEC-004 point 6). So a brand has the axis, and its modes, only where it or its base gives them, and a brand that gives no profile keeps its combinations and its keys.
- **Font families and weights alone.** A mode of the axis changes only tokens of the types `fontFamily` and `fontWeight`, and of a `typography` token only those two members. A typography's size, line height and letter spacing stay the default's, as every other value does. The capability's schema for a brand names them member by member, as it names the kinds of value a value axis may change (DEC-004 point 2). So a profile's scene keeps the default's spacing and sizes, and differs only where its text measures otherwise. A mode that changes another value, or another member of a typography, fails validation (point 9).
- **A family the medium holds is marked as the medium's own.** The brand marks it in the capability's extension point, where it names a family's file (DEC-004 point 1), by one new value of the `measure` member, `medium`, beside `file`, and names no file for it. That is all the brand says of it: no table, no estimate and no width (point 5). A family the brand gives a file for is measured from it, in any profile. In `files`, every family is measured from its file (DEC-004 point 9).
- **A font the medium lacks may stay.** A family may keep its file in a profile, such as a monospace font the medium has no match for. Its runs are measured from the file, never by the medium's measures, so a renderer of the medium meets them as a font the medium cannot draw, even where the medium holds a font of that name, whose letters nobody measured against the file. What the renderer does with a font it cannot draw is its own, reported as a loss (DEC-005 point 9). So a brand chooses between giving the medium's nearest font and keeping its own.

### 5. What a medium imposes is the capability's, and the engine applies it

- **The medium's facts, kept once.** What a medium imposes on its text is a fact of the medium, such as the widths of its fonts, their ascent and descent, a line height it fixes, and which fonts it holds. The capability keeps each once, for the medium's profile. The engine applies those it measures by, and the medium's renderers apply the rest, such as how far the medium sets text in from its box, or report one as a loss. What a brand chooses for a medium is its fonts (point 4).
- **The fonts the medium holds.** For each mode other than `files`, the capability lists the fonts its medium holds, each family at the one weight or more the medium draws it in, each weight a number as a font weight token's is, with an estimate of each family at each weight, and for some a table of widths, as data of the profile. The engine measures every scene in that profile by them. A brand ships none, and a project adds none, as it adds no plugin (DEC-005 point 12). A renderer of the medium reads from it the name the medium knows each family by, and whether the medium still draws it.
- **The list keeps what it lists.** A font or a weight the medium ceases to draw stays in it, marked as no longer drawn, and is still measured by, since a brand accepted before may name it and would otherwise be refused. A brand that names one asks for attention (point 9).
- **An estimate for each family at each weight:** one advance for every character, as a share of the em, with the font's ascent and descent as shares of the em, which place a line's baseline.
- **A table of widths for some:** for each weight it measures, of those the list gives the family, each character's advance, as a share of the em. A span's width is the sum of its characters' advances, with no kerning.
- **A table where one ships, else the estimate.** The engine measures a family the brand marks as the medium's own from the capability's table of it where one ships, and by its estimate otherwise. A character a table lacks, or a weight it holds no widths for, takes the estimate. So such a family measures every character, and no family after it in its role's list measures any.
- **A family the medium does not hold is a missing font.** A family marked as the medium's own that the capability does not list for that profile fails validation (point 9), and refuses the render, as a font file that nothing holds does (DEC-004 point 9).
- **A weight the medium does not draw fails at the brand, and still draws,** as a weight a family has no file for does ([visual-communication:DEC-059-font-files-by-weight] point 3). A typography role, in any combination of the brand's axes that holds the profile, that takes a family marked as the medium's own at a weight the list does not give it is a finding of the brand's (point 9). In a scene its runs are measured, and drawn, at the nearest weight the list gives the family, chosen as DEC-059 point 2 chooses a file's weight, and the scene names, for that family, the weight it is drawn at.
- **The scene says which.** Each run says it was measured from a file, from a table or by an estimate (DEC-005 point 5). A run any character of which was measured from a file says it was measured from a file, and otherwise a run any character of which took an estimate says it was measured by an estimate.
- **In a file of the capability's format,** checked by a schema it ships, one for each profile.
- **Measured from the medium,** from how it draws each character. A table holds no outline or other part of a font file, so a font the capability may not ship can still be measured. Each table names where its widths were measured.
- **An estimate errs wide.** A line measured too wide leaves room on the medium. One measured too narrow overflows there, where no check sees it.
- **A line height the medium fixes** may later join its measures, as data of the engine. Whether Mural's does is left to the record of its renderer ([project-kit#3278](https://github.com/aleskalfas/project-kit/issues/3278)), on what it finds. Until then it is a fact the medium's renderers apply (below), and that renderer's declaration says it draws no line height but the medium's, so the capability reports the loss before a run (DEC-005 point 9). Joining the measures moves it: every scene of the profile changes, as a new engine changes them, the renderers' declared loss of it goes, and their versions rise.
- **Data of the engine.** A table or an estimate arrives with a release of the capability, as a language's line-breaking rules do (DEC-005 point 4). Its numbers are fixed, so the same files give the same scene on every machine. It reaches a piece as a new engine does, at a render a person runs, and makes no findings record or export stale (DEC-005 point 13, DEC-006 point 7). So a table that arrives for a family a brand marks as the medium's own refines its measure, and the brand needs no new version.
- **A fact a renderer applies** is data of the profile too, kept in the same file, but no measure. It counts as part of each renderer that applies it, as a program the renderer pins does, not as its input, so the same scene then gives another output, and a change of it raises the version of each such renderer (DEC-005 point 9). Which such facts a medium has is the record of its renderers' to decide.
- **A fact both read follows both rules.** The list of the fonts the medium holds is one: the engine measures by it, and a renderer of the medium reads from it the name the medium knows each family by, and whether the medium still draws it. So a change of what a renderer reads there, a family, a weight, a name or a mark, arrives as data of the engine and raises the version of each renderer that reads it, while a table or an estimate, a measure alone, raises none.

### 6. A profile's scenes are checked and previewed, in the brand's own fonts and showing the widths measured

- **Which scenes.** A piece's scenes are computed in each of its languages, in each combination of the modes it names, in each profile that a renderer of a format it exports names (DEC-005 point 6). A piece whose exports name no profile, as one that exports nothing, takes `files`. A renderer whose profile the brand lacks draws the scenes of `files` (DEC-005 point 10). Each renderer is handed only the scenes and combinations of the profile it draws, and the values at a scene's key with `files` in place of the profile (point 3). The renderer that draws previews adds no profile: it draws the scenes the exports' renderers name. So a piece handed out on a board alone, under a brand that gives the board's profile, has no scene in `files`, and never fails for an overflow in fonts it is never handed out in.
- **Checked as any scene.** Its findings join the piece's record (DEC-005 point 13). An overflow measured from a table or by an estimate asks for attention, and one measured from a file fails (DEC-005 point 14).
- **A run's default fonts.** A run measured from a table or by an estimate also names its *default fonts* in the scene: the families, and the weight, its typography role takes at the scene's key with `files` in place of its profile. The scene names them as it names any run's fonts, each family with the file chosen for it and that file's hash (DEC-005 point 5), and they are drawn, and named, at that weight. So a renderer that draws them takes them from the scene, and adds no font of its own (the founding record, [visual-communication:DEC-001-visual-communication-discipline] point 2).
- **Previewed in them, showing the widths measured.** A renderer that cannot draw the medium's fonts, such as the renderer of vector pictures that draws previews, draws each such run in its default fonts, and shows the width the engine measured for each of its spans. A part that a renderer of the medium draws through the renderer of vector pictures, as a picture, is drawn the same way (DEC-005 point 9).
- **What the engine measured, not what the medium draws.** A preview shows the lines and breaks the engine measured, and every box. The medium's letters differ, and a medium that wraps text itself may break its lines otherwise (DEC-005 point 4), as the record of its renderer decides ([project-kit#3278](https://github.com/aleskalfas/project-kit/issues/3278)).
- **How, left to the build.** How a preview shows a span's width, such as by fitting the span to it, is the Task's that builds previews in a profile. No renderer of the capability yet draws a text to a width, and whether the rasteriser the capability pins honours one is untried. Whatever the Task chooses keeps the brand's own fonts, shows each span's width measured, and is reported as below.
- **No loss in a preview.** A preview is no output, so drawing it so is no loss. A preview's name carries its key, the profile in it (DEC-004 point 3). The viewing step's report states, once for each scene, how many of its runs are drawn so, as drawn otherwise ([visual-communication:DEC-015-viewing-step-and-reviewer] point 3), so a reviewer judges no type from them.
- **A loss in an output.** A renderer of the medium that places such a part in its output, as a picture, reports the picture as a loss (DEC-005 point 9), and the loss names each run the picture draws in its default fonts, or, where the renderer reports it once at the typography role whose font those runs take, that font.

### 7. The lock's search places no profile

The search for a lock places a piece at each key it names (DEC-021 point 7), and no piece names a profile. Whether a tie's end is found depends on which parts are drawn, and no profile changes that, since no component reads one (point 2). So placing a piece in its profiles would find nothing more, at the cost of another search for each.

### 8. The seam's version rises once

A renderer must read something new: a run measured from a table or by an estimate, with its default fonts. So the seam's version rises in the change that first hands a renderer a scene in a profile other than `files` (DEC-005 point 8).

### 9. What the checks report, and how severely

Each finding below fails validation where it lies in a file the project can correct, and elsewhere asks for attention, as DEC-004 point 11 says.
- **Fails validation:**
  - a piece whose `modes` name an axis of the kind `profile`
  - a mode of an axis of profiles that changes a value other than a font family or a font weight, or a typography's member other than those two
  - a family marked as the medium's own in `files`
  - a family marked as the medium's own that the capability does not list among the fonts that profile's medium holds, which also refuses the render as a missing font (DEC-004 point 9)
  - a typography role, in a combination that holds a profile, that takes a family marked as the medium's own at a weight the list does not give it, whose runs still draw at the nearest weight the list gives (point 5)
- **Failed already by findings that exist,** which the axis's kind brings it under: a switch or a `when` that reads `:font-profile`, as DEC-021 point 7 says, and a brand's own axis of the kind `profile` (`own-axis`), once the first Task keeps the kinds a brand's own axis takes apart from the foundations' (point 1).
- **Stated as a fact,** once for each scene: how many of its texts were measured from a table, and how many by an estimate. The scene keeps how each run was measured.
- **Asks for attention:** an overflow measured from a table or by an estimate, as DEC-005 point 14 says, and a family or a weight a brand takes as the medium's own that the list marks as no longer drawn (point 5).

### 10. When to revisit

- **When a project may add a renderer of its own** (DEC-005 point 12). Its medium would need a profile, a mode only the foundations add, and measures only the capability ships. Both open with that point.
- **When a reader of written code needs a medium's fonts,** such as an email, or a runtime that draws its platform's. Carrying the profile is then an addition (point 3).

## Rationale

**Why a kind of its own.** The axis shares one trait with a size axis, a scene for each mode, and reverses the rest: a renderer chooses its mode, no piece names it, no component reads it, it changes only fonts, and only a scene carries it. So it belongs in one reader, the code that builds a scene's key, and out of every other. Declared a size axis, it would come into every reader of sizes, and each that a piece, a component or written code meets would need an exception keyed on its name, as would each rule the records give a size axis. Of a kind of its own, the code that builds a scene's key opts in, a reader that selects the axes of one kind leaves it out unchanged, and a reader that takes every axis not of one kind as of the other meets it. So the kind changes more of the code now: six places besides the scene's key, all named in the first Task, where a size axis would except two besides the findings both need, the code every reader of a component's sizes goes through and the command that writes code. What decides is which way a miss errs. A reader of sizes that missed its exception, now or written later, would admit the axis silently where a piece, a component or written code meets it, past refusing once released (DEC-003 point 3). A place the first Task missed would mostly show the axis as a loss or a finding that should not be there, which can be withdrawn. Two would not show it: the list of kinds that the finding on a brand's own axis shares with the reader of the foundations' axes, and the kinds the command lets a code writer spell, each of which admits the axis if widened to it, so the first Task tests both. Once each reader selects the kinds it reads, a reader written later leaves the axis out unless it opts in.

**Why the kind is spelt `profile`.** It is the word the record of brands already gives these modes: a *font profile* is the set of fonts a brand gives a group of renderers (DEC-004 point 2), so the word carries both traits of the kind, fonts, and the renderers that choose among them. `font` would read as any axis that changes fonts, such as one tuned for an audience, which a piece would name. A picture's colour profile ([visual-communication:DEC-025-picture-files] point 5) never meets the word here, since the kind `profile` is written only in the foundations' declaration of their axes, and enters no key and no name in code.

**Why the axis is named `font-profile`.** The name says what the axis switches: a brand's font profiles, each the set of fonts it gives a group of renderers (DEC-004 point 2). It is a shared axis, so it takes no prefix, which a brand's own axis alone takes (DEC-057 points 1 and 2). The kind's word alone would not do: unlike the kind, the axis's name enters each key that holds it, such as a preview's name (point 6), where `profile` would read as a picture's colour profile (DEC-025 point 5).

**Why a renderer chooses.** Which fonts a medium can draw is a fact of the medium, so the renderer that draws there names the profile (DEC-005 point 10). A piece that named it would say again what its exports say, and could say it wrong.

**Why a profile reaches a plugin only in a scene.** A renderer takes only colours and pictures from the document, which no profile changes, and each run's fonts from the scene. Handing it the document in its profile would add a second way for fonts to reach it. Drawn at the scene, one line says for every plugin at once where a profile can be met.

**Why written code carries no profile.** Leaving the axis out of written code can be undone, and carrying it cannot. Carried, a profile's keys reach code outside the capability, which no lock protects, so dropping them would break that code (DEC-004 point 5). Left out, they can be carried later as an addition, as opening a token later breaks nothing, while closing one does (DEC-004, Rationale). Whether a reader of written code needs a medium's fonts, such as an email or a runtime that draws its platform's, is open, and waiting for one costs only that addition.

**Why a producer and a helper are handed `files` alone.** A picture is made once for each set of values it reads (DEC-006 point 3). Handed a profile, a producer that reads a font role would be asked for a variant in a medium's font it has no file for. A picture's fonts are in its pixels, so the variant made in the brand's own serves every medium. The cost: a picture that reads a text's measured frame reads it as measured in `files`, and does not follow that text where a profile measures it otherwise.

**Why ceasing to give a profile still breaks.** No written code, piece or component names a profile, so for them it changes only a look. A brand built on it may name the profile, as it names its base's other modes, and fails once its base lacks it.

**Why a profile changes font families and weights alone.** A profile is the set of fonts a brand gives a medium (DEC-004 point 2). No component reads it, so no component could answer a profile that moved its spacing, and a board would differ from the page by more than its letters. A typography's size, line height and letter spacing move text as a size does, so a profile leaves them too, and what a medium imposes on its text, such as a line height it fixes, is no choice of a brand's, so it is the medium's, kept with its measures (point 5). Kept to fonts, a profile keeps one design across media, and a board's scene keeps the shape of the page's.

**Why `files`.** The other shared axes name their default for what it is, such as `light` or `desktop`. `default` would make one word both a mode and the reserved key of the combination of defaults (DEC-004 point 3).

**Why what a medium imposes is the capability's.** A width is a fact of the medium, not a choice of design, and so are a font's ascent and descent, a line height the medium fixes and which fonts it holds. One owner keeps them, so two brands that give one medium font measure it alike, and a piece switched between them keeps its layout where their fonts agree. The record of brands already has the capability ship the table, with the renderer for the medium (DEC-004 point 9). This record keeps it with the profile instead, since two renderers may draw one medium (below), and an estimate is the same fact, coarser. The cost: a medium font the capability lists nothing for waits for a release, and its estimate is three numbers.

**Why the brand says only that a family is the medium's own.** Which tables the capability holds grows with its releases. A brand that chose between a table and an estimate would tie its own releases to them, and fail for a table only the capability can ship. Saying that a family is the medium's own, the brand says what it knows, and a table that arrives later refines the measure with no release of the brand. So the value names that fact, `medium`, and no way of measuring.

**Why the measures are the profile's.** Two renderers may draw one medium, and the engine measures one scene for both. Measures kept with one of them would tie that scene to whichever renderer asked for it.

**Why a character a table lacks takes the estimate.** The medium draws it in a font of its own, which no file or table describes. Refusing would stop a board for one letter whose width is approximate anyway. Passing it to the role's next family would pretend the medium follows the brand's list, which it does not. The scene says the run was estimated, and an overflow asks for attention.

**Why a weight the medium does not draw fails at the brand, and still draws.** A role that takes a medium's family at a weight the medium does not draw is a mistake the brand can mend, since its profile may give the role a weight the medium draws (point 4), so the brand's check fails it. But a released brand is mended only by its owner, and a refusal would stop every piece under it that is drawn for the medium until then. So the run is measured and drawn at the nearest weight the medium draws, as DEC-059 has a run do where its family has no file at its weight, and the scene names that weight, so the run is measured as it is drawn. A family the medium does not hold has no nearest, so it stays a missing font. A character a table lacks is no mistake of the brand's: it is the content's, and no brand can mend it.

**Why a renderer's facts raise its version, and the measures do not.** A measure changes the scene, which every renderer of the medium is handed alike, as a new engine changes it. A fact a renderer applies changes what that renderer makes of the same scene, which is what a plugin's version follows (DEC-005 point 9).

**Why measure what is drawn.** The engine measures a run in the letters it is drawn in, so a weight drawn from a family's file is measured from that file, whichever weight the file is, while a weight a table lacks takes the estimate, since the medium draws it in letters no other weight's widths describe.

**Why an estimate errs wide.** The two errors are not even. Too wide leaves room to spare on the board, which costs only space. Too narrow pushes a word past its box on the board, where nothing measures it.

**Why scenes only in the exports' profiles.** A profile's scene is what its medium is handed. A scene in a profile no export uses would fail a piece for an overflow nobody gets. A piece handed out in two profiles pays for both, as its check computes each, and a piece with no exports takes `files`, so it is still checked and previewed.

**Why a preview shows the widths measured, in the brand's own fonts.** The preview shows where the engine placed the medium's text. Drawn at its own width alone, a line in the brand's font would end past its box, or short of it, where the engine measured otherwise, so a person would see an overflow the engine did not find, or miss one it did. The brand's own fonts are the ones a renderer of previews can draw. How the width is shown waits for the build, since the capability's previews have yet to draw a text to a width, and no one has looked at one so drawn.

**Why one fact for each scene.** A deck on a board measures every text so, some hundreds of them. A fact for each would hide the findings that ask for attention. The scene keeps each run's measure, and each overflow is named alone. The viewing step's report counts the runs drawn otherwise once for each scene, for the same reason.

**Why the seam rises.** A renderer handed a run measured otherwise would look for a font file that does not exist.

### Alternatives considered

- **A size axis whose readers make exceptions by its name.** Rejected. It keeps font profiles a size axis, as DEC-004 point 2 has them, so it would overturn nothing of that point, and adds no third kind to the kinds findings name. It changes less of the code now: an exception in the code that every reader of a component's sizes and the lock's search go through, and one in the command that writes code, while the code that builds a scene's key, the check of a switching file's pairs and the code that groups a piece's combinations into a switching format's files would take it rightly unchanged. But a reader of sizes that missed its exception, now or written later, would admit the profile silently where a piece, a component or written code meets it, and once released it could not be refused. Of a kind of its own, a miss mostly shows as a loss or a finding that can be withdrawn, and a reader written later leaves it out where it selects the kinds it reads, as the first Task has every reader do: a convention of the code, not a guarantee (Rationale).
- **The kind spelt `font`.** Rejected, for the reason above.
- **The axis named `profile`.** Rejected, for the reason above.
- **A piece that names its profiles in `modes`.** Rejected. It says again what its exports say.
- **The axis held unreleased, as DEC-021 point 9 held `device`,** until its findings land or a renderer draws in `mural`. Rejected. Its two findings come with the kind, in one Task, so a hold would wait on nothing there. A release fixes only the kind, `files` and `mural`, which only a brand that gives a profile meets, and what a renderer could teach comes as an addition, such as a line height in the measures (point 5). So a hold would guard only against a `mural` mode no renderer draws in, at the cost of the foundations' version being built, with what it already holds, and of the neutral brand's versions. `device` was held since it reaches components and written code, which a profile does not.
- **A renderer handed the document of values in its profile.** Rejected. It takes only colours and pictures from it, which no profile changes, and each run's fonts from the scene (point 3).
- **Written code that carries the axis,** as it carries a brand's size axes. Rejected for now. Carrying it cannot be undone, and leaving it out can.
- **A producer or a helper handed each profile.** Rejected. One that reads a font role would be asked for a font it has no file for, for a picture whose pixels can hold the brand's own.
- **A brand that ceases to give a profile, counted as no break.** Rejected. A brand built on it may name the profile.
- **A profile that may change any size, as `device` may.** Rejected. No component reads it, so none could answer a profile that moved its spacing. What a medium imposes on a text's room, such as a line height it fixes, is a fact of the medium, kept with its measures (point 5), and no choice of a brand's.
- **The brand choosing a table or an estimate for each family.** Rejected. It would tie the brand's releases to which tables the capability ships, and fail a brand for a table only the capability can add.
- **Widths, or an estimate's share, given by the brand.** Rejected. A width is the medium's, and two brands would measure one font two ways.
- **A table kept with one renderer.** Rejected. Two renderers may draw one medium.
- **A weight the medium does not draw refusing the render,** as a family it does not hold does. Rejected. A released brand would stop every piece under it that is drawn for the medium, until its owner mends it, which DEC-059 rejects for a weight a family has no file for.
- **A font the medium ceases to draw taken out of the list.** Rejected. A brand accepted before that names it would be refused, by a change no project made.
- **A character a table lacks refusing the render,** as a character no family measures does. Rejected, for the reason above.
- **A character a table lacks passed to the role's next family.** Rejected. The medium draws it in its own font, not in the brand's next family.
- **Measuring in a browser, or on the service, at each render.** Rejected. A browser is heavy (DEC-005, Alternatives), and the engine reaches no network to draw ([visual-communication:DEC-002-files-and-validation] point 8).
- **Scenes in `files` for every piece.** Rejected. A piece handed out on a board alone would fail for fonts it is never shown in.
- **Previews of `files` alone.** Rejected. A piece handed out on a board alone would have nothing a person can look at before its export.
- **A preview of each line at its own width alone, or as a bar.** Rejected. The first misplaces the line's end, and the second cannot be read.
- **Each span fitted to its width, decided now.** Rejected for now. It is untried in the rasteriser the capability pins, and one advance for every character, fitted span by span, may stretch one word and squeeze the next on a line. The build tries it, or another way to show the width.
- **Look-alike fonts the capability ships for previews.** Rejected. None has the medium's widths, and each brings a licence to keep.
- **A fact for each text,** or a line of the viewing step's report for each run. Rejected, for the count.
- **`default` as the default mode's name.** Rejected, for the reason above.
- **The lock's search in each profile.** Rejected. It would find nothing more (point 7).
