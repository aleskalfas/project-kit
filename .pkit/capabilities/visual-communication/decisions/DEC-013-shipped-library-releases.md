**In plain terms:** a library the capability ships, such as the foundations or the starter, is released by a release of its own, never by a release of the capability. Whoever maintains the capability releases a version as it stands, and only where no change has touched it since the release that wrote the capability's current version, so that release carried it as it is. The release the library's version needs is then the capability's current version, a number already written, so no branch guesses a number. Releasing it adds the version, naming that release, with its hash, and from then on the version never changes. The capability ships every released version of each library, and beside them the version being built, which every change goes into. No release renames or removes a file. The command that brings a shipped library into a project takes the newest released version, and lists it with its hash. It writes over a version the project holds only to bring a copy not yet released up to what the capability ships, or to restore a released copy to its hash. Where a lock that moves only on purpose names a copy not yet released, it replaces that copy only once the person names the piece.

## Context

The record of change over time decides how libraries change ([visual-communication:DEC-003-change-over-time]):
- **Released means fixed.** A released version never changes, and a change is a new version. Releasing a version runs the check on it first (point 6).
- **The release a library needs** is a version of the capability, and an older engine refuses the library (point 1). A released version of a project's own library names the version of the capability installed in the project at its release. The engine checks that number against the installed capability, and computes none ([visual-communication:DEC-014-own-library-needed-release] point 1).
- **The location's list** says which versions the project holds are released, with a hash of each released one (point 4).
- **Shipped libraries.** The capability ships the newest version of each library it ships, and a person brings it into a project by a command (point 5).
- **Locks.** Only a draft may lock a version of the project's own library not yet released, and a final or a published piece locks only released versions (points 6 and 8).

It does not say when a version the capability ships counts as released, nor who releases it.

How the capability ships its libraries today:
- **One folder for each library,** holding its newest version. The foundations ship so, at version 1.0.0, not released yet.
- **The command that brings a shipped library in** copies that version into the location's library folder, and lists it not released, with no hash. It never writes over a version the folder holds.
- **The release it needs** names the version the capability's package metadata carries. Once a release of the capability brings the tools the library uses, that may understate it ([project-kit#2501](https://github.com/aleskalfas/project-kit/issues/2501), Out of scope).
- **The capability has no release yet.** The version its package metadata carries was stamped when the capability was created, and no release wrote it.
- **The next slice** ships the starter and a neutral brand, not released either. The deck the repository that authors the capability draws of itself, a draft, locks them while they grow (#2501, [pkit:PRJ-012]).

In the repository the capability is authored in, a version-bump policy frames the numbers ([pkit:PRJ-002]):
- **A release step** writes all version state, on the default branch only, from the changesets each change declares: the backbone's version, each component's, and the ranges between them. A branch writes none, and cannot know the number of the release that will ship it (D1 and D3).
- **The capability's version** moves at a release only where a pending changeset declares a change of the capability an adopter can observe. A release that ships only changes declared to move nothing leaves it as it was. So several releases may carry one version of the capability.
- **A release carries the capability's folder as the default branch holds it,** with the libraries it ships. A project normally receives the capability at a release that moves the backbone, the only kind that is tagged.
- **Parallel branches** that each write one shared number meet in a merge conflict that carries no real conflict, which is why the release step writes versions ([pkit:PRJ-002], Rationale).

COR-010 asks a migration of a change that renames or removes what an installed project holds. The methodology's check of migrations reads every rename or removal of a file in a capability's folder as such a change, unless the file is a decision record, or lies in a migrations folder or the project's own folder. The default branch's required checks run it on each change.

The founding record makes every library copy the project's file. A *library copy* is a released version held whole, and a copy that a lock names is never rewritten ([visual-communication:DEC-001-visual-communication-discipline] point 11). Written code has a lock too, which a person moves on purpose ([visual-communication:DEC-005-engine-and-plugins] point 7).

The capability's plan for released libraries asks when a shipped version counts as released, how the release it needs, its version and its hash are fixed, how parallel branches change it, and whether the command that brings it in may replace a copy not yet released ([project-kit#2571](https://github.com/aleskalfas/project-kit/issues/2571)).

## Decision

**Whoever maintains the capability releases a version of a library the capability ships, by a release of its own, as it stands, where no change has touched it since the release that wrote the capability's current version. The release the library's version needs is the capability's current version. Releasing it adds the version, naming that version of the capability, with its hash, and refuses a break outside a major release. A release of the capability releases no library. The capability ships every released version of each library, and beside them the version being built, which every change goes into, and no release renames or removes a file. The command that brings a shipped library in takes the newest released version. It writes over a version the project holds only to bring a copy not yet released up to what the capability ships, or to restore a released copy to its hash. It replaces a copy not yet released under a lock that moves only on purpose only where the person names the piece.**

### 1. A shipped version is released by a release of its own

- **Who and where.** Whoever maintains the capability releases a version of a library it ships, in the repository the capability is authored in: where the methodology holds the capability's folder as its source, never as a synced copy. The release takes the steps a project's own library's release takes. It runs the check first, and compares the version with the library's previous release, refusing a break outside a major release (DEC-003 points 6 and 7, [visual-communication:DEC-004-brands-and-notations] point 5).
- **As it stands, untouched since the release that wrote the capability's version.** The capability's *current version* is the version of the capability its tree carries, as the release step wrote it, when the release of a library is made. A release of a library takes the library's version being built as the default branch holds it. It refuses unless no change since the release step's change that wrote the current version has touched the place of the version being built. So the version is, file for file, the one that release carried. The release also refuses where no release wrote the version the tree carries, as before the capability's first release, and where the version being built carries a number already released. The capability's own checks hold the released version to the same condition again, as the release would merge (point 4).
- **A change since that release puts it off.** A change to the version being built after that release, a library added since included, puts the library's release off until the next release that moves the capability's version. Each such change declares at least a patch of the capability (point 4), so the next release that ships it moves that version, and carries the change.
- **Read in that release.** The capability's own checks read every version it ships, the one being built included (point 6), and run on each change as it would merge. A version is released only where the tree at the release step's change held those checks, so they read the version as that release carried it.
- **On released bases.** The release checks it with the newest released version of each library it builds on, within the majors it names, a base released earlier in the same change included. So a released version never rests on a base not yet released, and the foundations are released before a library built on them. While it is built, the capability's own checks read it on the versions being built of its bases instead (point 6).
- **Not by the capability's release.** A release of the capability carries each library as the default branch holds it, released or not, and releases none.
- **Released once it lands, carried by every later release.** Once the change that releases it lands on the default branch, the version is released where the capability is authored. Every later release carries it released. So a version reaches a project as released no earlier than the release after the one that carried it, and normally only at a release that moves the backbone, the only kind that is tagged. The library's owner does not decide when that release comes.

### 2. The capability ships every released version, and the version being built

- **Every released version** of each library, whole, as it was released, each in a place of its own. Its release adds that place, and nothing later renames or removes it. Every project keeps its copies of a version as before (DEC-003 point 4).
- **The version being built:** at most one version of each library, which every change to the library goes into. It keeps the place the library ships in today, apart from the released versions, under a name that names no version. So a change of its number moves no file (point 4). A library's first version starts it, at 1.0.0.
- **Apart from it, the record and the released places.** The library's record and its released places lie outside the place of the version being built. So a release touches no file of the version being built, and the look at the history of point 1 sees only changes to it.
- **While it carries a released number,** it holds that released version's files, but for the release that version needs. It is then that released version, and the command that brings it in takes the released one (point 5). A change to it raises its number first (point 3).
- **A record for each library.** Each library the capability ships keeps a record of its released versions, each with its hash, in the shape and with the hash the location's list gives a released version (DEC-003 point 4). The command that brings the library in copies the hash as it is. One record to a library keeps the releases of two libraries apart.
- **A release only adds.** Releasing a version adds its released place and its entry in the library's record. It changes no other file of the capability's folder, the version being built's included, and renames or removes none.

### 3. What a release fixes: the release the version needs, its number and its hash

- **The release it needs** is the capability's current version, as the release finds it (point 1). The release writes that number into the released place. The release step wrote it, so the version names no release still to come. The release that wrote it carried the version as it is released, everything the version uses included, and the capability's checks read it there. So the number never understates what the version needs, and may overstate it, where its tools are older.
  - **What that rests on.** The checks at that release refuse what its engine does not know, rather than pass over it. The capability's schemas refuse a key they do not declare, a component's fields take a fixed subset of JSON Schema, and the engine refuses a tool it does not name. A check that passed over something unknown would let the number understate.
- **While it is built,** the version names a release no later than the capability's version its tree carries, so that tree reads it. It understates where a change used a tool newer than that number, and the capability's version has not moved since. A project takes it only from an installed capability whose tree reads it (DEC-003 point 5), and its release sets the number.
- **Its number** follows semantic versioning from the newest released version, with the segments the record of change over time sets (DEC-003 point 1). A library's first version is 1.0.0.
  - The version being built carries the highest segment its changes need: a patch at least, a minor once a change adds or changes a look, a major once a change breaks what the newest release promises (DEC-003 points 6 and 7, DEC-004 point 5). A change that needs more than the number says raises it. A change to a version being built that carries a released number raises it first, by the segment the change needs. The release raises no number.
  - The release refuses a break outside a major release. The capability's own checks compare the version being built with a released version of its own major, and fail a break as each change would merge (point 6), so a change raises the number first. Where its major has no released version yet, the release's comparison with the library's previous release is the one that judges it. The release command shows the segment its comparison finds before it writes anything. Whether a change is a patch or a minor is the owner's judgement, as it is for any library.
  - A library's number never falls below one a release has carried for it, since a project's copy may carry it. The release refuses a number below one the version being built carried at an earlier release, as the default branch's history shows, and the capability's own checks fail one below the newest released number (point 6). Once a release has carried a higher number, a number the version being built passed unreleased is never released: a release takes the version as it stands (point 1), and its number cannot fall back. The capability then no longer ships it.
- **Its hash.** The release writes the hash of every file of the released version, the release it needs included, into the library's record. The capability's own checks fail a released version whose files no longer match it.
- **Content, not version state.** The release step writes the version state of the repository the capability is authored in: the backbone's version, each component's, and the ranges between them ([pkit:PRJ-002] D1 and D3). A library's version, the release it needs and its hash are the capability's content, which the library's owner versions, as a schema's version is its schema's. The release it needs names only a version of the capability a release has already written. So does a branch that adds a capability's dependency on another: it writes the floor no higher than the version the tree carries for that capability, and predicts no number ([pkit:PRJ-002] D1). An explicit floor likewise names a version the tree records as released ([pkit:PRJ-002] D4). So no branch predicts a number, and the release step writes nothing for the libraries.

### 4. How parallel changes meet

- **Every change to a version the capability ships is one an adopter can observe,** since the command that brings it in copies it. So each declares at least a patch of the capability under the version-bump policy, never a change that moves nothing. So does each release of a version, which adds one.
  - **A change wrongly declared to move nothing** is shipped by the next release, under the capability's version as it was. It is still a change since the release that wrote that version, so the library's release refuses (point 1) until a later release moves the capability's version. A patch changeset for the capability is the way out.
- **Changes go into the version being built,** and change its files as they change any file. No number moves, except where a change needs a higher one (point 3).
  - Two changes that raise it to the same number write the same line. So they meet only where they change one file differently.
  - Two that raise it to different numbers meet on that line, and the higher holds. The second to merge reads the version again after its rebase.
- **A released version's files never change.** The capability's checks fail a change that alters them, as the change would merge.
- **A library's release and a change to the library merged beside it.** Whichever lands second fails. A change that lands after the release finds the version being built carrying a released number while it differs from that version, and the capability's checks fail it until it raises that number (point 3). A release that lands after the change finds a change since the release that wrote the capability's version, and the capability's own checks fail it as it would merge (point 6). The library's release then waits for the next release that moves the capability's version, and is made again from it.
- **A library's release and a release of the capability.** A release of the capability may land between the library release's branch and its merge. A look at the history made only on the branch then reads a history that has moved on: that release may have shipped, under the number the library's release fixes, files a change put there and a later change took back. So the capability's own checks hold every released version to point 1's condition, read from the tree, its changelog and its history (point 6). No change may have touched the place of the version being built between the release step's change that wrote the version of the capability it names and the change that brings it onto the default branch, that change as it would merge included. They need no diff, so they hold on the default branch too. Where no change touched the library since that release step's change, the check passes though a release landed. The released version then names a version of the capability older than the one the tree carries, whose release carried it unchanged. So every release that carried the number since the one the released version names carried the files it fixes.
- **Releases of two libraries** add two places and change two records, and meet nowhere. Where one builds on the other, the capability's checks read the two together as each would merge (point 6).
  - **A base and a library built on it may each need the other's new version,** as when the base's next version removes an experimental component the library's newest release uses, and the library's next version uses what the base adds. One change then releases both, the base first, and the checks read them together.
- **As each would merge.** These hold where the default branch's required checks run on each change as it would merge, as a merge queue runs them, the release step's own change included. A change that bypasses the queue is caught only after it lands, by the same checks on the default branch. A release caught so is taken back by a change that removes its place, which meets the check of migrations as any removal in the capability's folder does (point 7). Once a release has carried it, it stays, since withdrawing a released version is left open.

### 5. The command that brings a shipped library in takes the newest released version, and brings a copy not yet released up to date

- **By default, the newest released version.** The command copies it whole, checks its files against the hash in the library's record, and lists it released with that hash. It refuses where the files the capability ships no longer match that hash.
- **Any other released version** the capability ships, where a person names its number.
- **The version being built,** when a person asks for it, or where the library has no released version yet. The command lists it not released, with no hash.
- **Every copy of that library, in the same run.** Each run for a library also brings up to date every copy of it the list marks not released, where the capability ships its number, released or still being built: it replaces the copy whole with what the capability ships. Where the version is released, it lists it released, with its hash. It also restores every released copy of it whose files no longer match its hash. Running the command is the consent (DEC-003 point 5), and it names each copy it writes and each piece that locks it.
  - **A replacement moves a copy forward.** A copy not yet released holds what the version being built held under its number when the copy was taken. Nothing a later release of the capability ships under that number is older. A released version holds the files every release carried under its number since the release step's change that wrote the version it names (points 1 and 4), and a change to a released number raises it (point 3). So a replacement moves the copy forward, where the installed capability is no older than the one the copy came from. A project that moves its capability back, or takes a copy from a project on a newer capability, may get older files, as its diff shows. A draft that follows may still lose what it used, as an experimental component may be removed in any release (DEC-003 point 7).
- **Under a lock that follows, or no longer draws.** The command replaces a copy not yet released where each lock that names it is an unpinned draft's, which moves at each render, or a final piece's. A final piece's exports are its freeze, and the check computes no scene for it ([visual-communication:DEC-002-files-and-validation] point 7). Its lock may name only a released version. Where the capability has released the copy's number, the replacement mends that lock without moving it. Where the number is still being built, the replacement changes none of its exports.
- **Under a lock that moves only on purpose,** a pinned draft's, written code's or a published piece's, the command replaces a copy not yet released only where the person names each such piece in the command, after the before-and-after its state asks (DEC-003 point 8). Naming it is the move on purpose: the lock keeps its number, and what it draws changes only then. Otherwise the command leaves that copy as it is, names each such piece, and does the rest of its run. The finding of point 6 stands for that copy.
- **A change the project made in such a copy is lost,** as the project's diff shows. A shipped library changes where it is authored, never in a copy.
- **A released copy is never replaced.** Where the copy matches its hash, the command writes nothing. Where its files no longer match it, the command restores them as released, as the record of files and validation lets a project restore a library copy (DEC-002 point 7). Restoring needs no piece named, since it brings the copy back to what every lock on it names. Where the hash the capability records for that version differs from the list's, it refuses.
- **A new number is a new version.** A version the capability ships under a number the project does not hold is copied beside the others, and replaces none.
- **A number the installed capability does not ship.** A copy not yet released of such a number stays as it is. A draft that follows moves by itself once the project holds a newer version of its major. Where the capability builds no later version of that major, as when the version being built passed the number for the next major, none comes. A person then moves that draft too, and each other draft that locks the copy, on purpose, to a version the capability ships, by pinning it to that version or by taking the new major. Once no lock names the copy, the project removes it (DEC-003 point 4). A final piece that locks such a copy keeps the finding of point 6, since its lock never moves.

### 6. What the checks report, and how severely

Under the policy of the record of files and validation (DEC-002 point 7):
- **Fails, as the record of change over time sets:** a library version that no longer matches its released hash (DEC-003 point 9). Where the capability ships that version, the finding names the command that brings it in, which restores it.
- **Asks for attention:**
  - A finding inside a copy whose source is the capability, released or not. No project corrects it, since the command that brings it in writes the library as it is authored. The finding names whoever maintains the capability.
  - A copy the location's list marks not released, of a library the capability ships, that is not what the installed capability ships under its number: other files, a released version, or a number it does not ship. A draft that locks it draws what the capability no longer ships. The finding names the command that brings it in, or, for a number not shipped, the way out of point 5.
  - A copy the list marks released whose hash differs from the one the capability records for that version, such as a copy from another distribution of the capability. Two contents carry one released number, and the finding names both hashes.
- **The capability's own checks** are its tests in the suite of the repository it is authored in, which the default branch's required checks run on each change as it would merge (point 4). They lie outside a project's validation, which never runs them. They:
  - read every component of each version, the brand's tokens and fonts included, through the routine that reads a version in full (refinement per [visual-communication:DEC-014-own-library-needed-release]). So point 3's ground for the number holds for a component no piece places;
  - hold each released version it ships to the hash its record keeps. Read alone, a released version fails them only where it no longer matches its hash, or where the engine can no longer read its files, which the format's promise forbids (DEC-003 point 3). Any other finding in a released version is reported and fails nothing, as a fault inside a released version never fails (DEC-002 point 7): only a new version corrects it;
  - hold every released version to point 1's condition, read from the history: no change touched the place of the version being built between the release step's change that wrote the version of the capability it names and the change that brings it onto the default branch, as it would merge (point 4);
  - fail the newest released versions of the libraries it ships where the engine cannot read them together, each on the newest released version of each major it builds on, so a new project can lock them together;
  - read and check the version being built on the versions being built of its bases, so a library and its base can be built together. A finding in it fails, as one in a project's own library not yet released does. Its release reads it on released bases instead (point 1);
  - fail a version being built that carries a released number but differs from that version, but for the release it needs, or whose number falls below the newest released one;
  - run the release's comparison of the version being built with the newest released version of its major, and fail a number that does not cover a break it finds. The comparison is a command for a project, never a validator (DEC-002 point 7), and these tests are no project's validation.
- **An engine change that tightens a rule** the engine applies to a library read with its bases may find that the newest released versions no longer read together. The capability's own checks then fail it, and hold it back. They read only the newest released versions together, so a change that refuses an older pair projects still lock passes them, and review holds it to the same rule. Projects hold the same released versions and cannot change them, so the change lands only once the rule reports what it finds in a version written before, asking for attention, rather than refusing to read it, as the format's promise asks (DEC-003 point 3). Releasing versions that meet the rule clears the versions the capability ships, never the copies projects hold.

### 7. What this changes, and what still holds

- **No project file changes shape.** The location's list already says which versions are released, with a hash of each, and a library's file already names the release it needs. Every file a project holds reads and draws as before.
- **The capability's own folder gains places:** each released version's, and each library's record. The version being built keeps the place each library ships in today, so the foundations stay where they are, as the version being built of a library with no released version yet. No release, and no change of this layout, renames or removes a file. So the check of migrations finds nothing for them to cover, and they owe none (COR-010). A change that renames or removes a file within a version being built, such as an experimental component removed, meets that check as any such change to the capability's folder does today: it ships the capability migration the check asks, though nothing installed breaks. This record changes nothing of that.
- **The command that brings a shipped library in** lists a released version with its hash, brings a copy not yet released up to date and restores a released one. A copy listed before stays as it is until a person runs the command.

## Rationale

**Why a release of its own, not the capability's.** The capability's version moves at a release whenever any change of the capability an adopter can observe is pending, whatever part it touches: its engine, its commands or a library. A library released with it would be fixed as each such release found it, whether or not its owner judged it ready. The foundations would be fixed at the capability's first release, while the next slice still shapes their roles. Every shared role added after that costs a default or a major release ([visual-communication:DEC-008-library-role-defaults] point 2). The owner judges a component ready (DEC-003 point 7), and judges a version ready the same way.

**Why as it stands, untouched since the release that wrote the capability's version.** A branch knows only the releases already made ([pkit:PRJ-002] D1). The release that wrote the capability's current version carried the library's version as it stands, with everything it uses, and the capability's checks read it there. So naming that version never understates the need, on the ground point 3 states, and asks for no number still to come. One look at the history of the version's place, whether any change touched it since, is the whole of *as it stands*, and the capability's own checks look again as the release merges.
- **The overstatement costs little.** A project takes a shipped version only through the command that brings it in, from the capability it has installed (DEC-003 point 5), which carries the version released only from a later release on. Only a project that moves its capability back below that version finds the library refused.
- **The cost is time.** A change reaches a project as released no earlier than the release after the one that first ships it, and only at a release that moves the backbone, which the library's owner does not time. A draft may take it as soon as it ships.
- **And now and then a release made again.** A change to the library after the release that wrote the capability's version puts the library's release off until the next release that moves that version. A change that lands while the library's release waits to merge makes it refuse, and it is made again after that release. Releasing soon after a release of the capability keeps the window short.
- **A slip fails closed.** A change wrongly declared to move nothing is a change since that release, so the library's release refuses until a release moves the capability's version. No number is fixed to files other than those a release shipped under it.

**Why every released version ships, beside the version being built.**
- **A final or a published piece locks only released versions** (DEC-003 point 8). Were only the newest version shipped, a project that installs the capability while the next version is built, over several releases, would find no released version at all.
- **A library built on another keeps its base.** A starter released on the foundations' first major stays drawable once their second major is released, since the first is still shipped. Were only the newest kept, a release of the foundations could leave the newest starter with no shipped base, and a release of the starter could not come first, since it rests on released bases only.
- **A piece copied from another project** that locks an older released version takes it by the command, not from the history of the repository the capability is authored in.
- **A release only adds.** Removing the version released before would be a removal in the capability's folder, which the check of migrations reads as owing a migration, for a change that breaks nothing installed. Adding the released version, and keeping the version being built where it is, renames and removes nothing.
- **The cost** is a folder that grows by one version with each release. The methodology carries every capability's folder in each of its distributions, its wheel and its source archive, whether a project installs the capability or not, so every download carries each version. By estimate, a version of the foundations is 5 to 20 KB, and one of the starter 50 to 300 KB. A brand that commits its fonts (DEC-004 point 9) copies them into each version, so a release of the neutral brand may add 1 to 3 MB, which compression barely shrinks. The repository's history stores identical files once; the distributions do not. The Implications name when this is weighed again, and the remedy then.

**Why the version being built keeps its place, and changes raise its number.** Many changes build a library at once, each on its own branch. A number in the name of the version's folder would move every file when it rises, and meet every other change. A number on one line meets only a change that raises it differently, and two changes that raise it alike write the same line. The number cannot wait for the release: a draft takes the newest version within its major (DEC-003 point 8), so a version that breaks a promise carries the next major before any copy of it is drawn. It never falls below a number carried, since a project's stale copy would then hold a higher number than the version it should give way to, and its drafts would keep it.

**Why a copy not yet released is brought up to date.** A version not yet released may change, and a draft that follows its libraries sees each change at its next render, as its author expects (DEC-003 point 8). The founding record protects a library copy, a released version, from being rewritten (DEC-001 point 11), and a copy not yet released is none. Were it never replaced, a draft's copy could not follow the version it locks. The project may not remove it while a lock names it (DEC-003 point 4), so a person would copy it by hand.
- **A final piece draws from its exports.** Its lock on a version not yet released is a fault only the released version of that number mends, since its lock never moves. Replacing the copy changes none of its exports.
- **A lock that moves only on purpose** would see its drawing, or its written code, change with no move. The released version keeps the number of the copy, so the lock has nowhere else to move. Naming the piece in the command, after its before-and-after, is the one move on purpose left.

**Why a finding inside a shipped version only asks for attention.** The project cannot correct it: a change it made would be lost when the command brings the library in again. Failing it would fail every project that took the version being built for a fault only the capability's owner can correct, which the record of files and validation forbids (DEC-002 point 7).

**Why inside the capability.** The release step could fix a shipped version instead. A branch would mark the version, run its check and its comparison, and leave the release it needs as a word the release step replaces with the version it writes for the capability, as it does for a floor declared on the release ([pkit:PRJ-002] D4). That spares the wait. Its costs:
- **The tier.** A process belongs to the backbone where the backbone needs it to exist, evolve or ship (COR-010). Releasing a library is none of these: it is the capability's own discipline, as a component's status is its library owner's.
- **The hash.** It covers the file the release step rewrites. So either the release step computes the capability's hash, and the backbone's release could not complete without the capability's code, which the version-bump policy's backbone-internal release step rules out, or the hash leaves out the release the version needs, so that a released version's files may differ from its hash.
- **A third state:** marked, but not yet released, which the check, the command that brings a library in and every lock must tell from the other two.
- **A mechanism with one user.** A seam in the release step for one capability's libraries is a general mechanism built before any second use (COR-007).

Inside the capability, the releases of the capability and of its libraries meet only through what the release step has already written: a number, its changelog entry and the change that wrote them. The capability reads what the release step wrote, and writes nothing of it.

### Alternatives considered

- **Every release of the capability releases the libraries it ships.** Rejected. A library would be fixed whenever the capability's version moves, for whatever change, ready or not: the foundations at the capability's first release.
- **The release step fixes a version marked on a branch, with the version it writes for the capability.** Not chosen. It spares the wait of one release, but changes the release step of the repository the capability is authored in (Rationale). It would need a project record of policy, beside the version-bump policy ([pkit:PRJ-002]) or as a refinement of its D4, deciding that a release writes, for a capability that declares it, content derived from the version the release writes. It would also need an architecture record of the mechanism, with the release mechanics: how a capability declares it, what the release step may write, how the hash covers what it wrote, and what a failure holds back. Both would be the methodology maintainer's to decide.
- **The library's version declared on each branch, and written at the release,** as the version-bump policy treats a component's version. Rejected. It needs the release step to write the capability's content, the seam above. The raises it would spare meet rarely: two changes that raise a version alike write the same line, and only differing raises meet.
- **Released from history:** the version as the release that wrote the capability's version carried it, with the number of the version being built raised where it changed since. Rejected. It spares the wait a later change puts on the library's release. Its costs are a raise of the version being built's number inside the release, and a walk over every later release to refuse files shipped since under the same number. A copy taken after that release holds newer files under the number than the release fixes, so bringing it up to date would move it back. Released as it stands, the release costs instead one look at the history, and now and then a release made again. Either way the check must run again as the release merges, since a release of the capability may land before it.
- **Released as it stands where its files still match what that release carried,** though changes touched them since. Rejected. A release between them may have shipped other files under the same number.
- **Released at once, naming the first version of the capability after the one its tree carries.** Rejected. The tree that releases the library's version carries the capability's version before. It, and any install from a commit between releases, would refuse a library whose tools it holds, unless the engine read such a tree as later than its own version. The field would also gain a second form.
- **Released at once, where the engine finds every tool and field the version uses in the capability's current version.** Rejected. The engine would have to know the release that brought each tool and field, which the branch that adds one cannot write.
- **Released at once, naming the oldest release whose own check, run from history, reads the version.** Rejected for now. It removes the wait, and names the oldest release exactly. But the release would run the capability's code of an older release, with its own dependencies, in a location built for it. The wait asks for no older code.
- **The release it needs as the version the capability's package metadata carries at each change,** as the shipped libraries name it today. Rejected. Once a release brings tools a library uses, it understates (#2501).
- **One version shipped, released or not.** Rejected. While the next version is built, a project would find no released version to lock in a final piece.
- **Only the newest released version shipped, beside the version being built.** Rejected. Each release would remove the version released before, which the check of migrations reads as owing a migration, though nothing installed breaks. A release of a base could also leave the newest release of a library built on it with no shipped base.
- **Projects receive released versions only.** The command would never bring in a version being built, so no project would hold a copy not yet released of a shipped library: nothing to replace, no piece to name, no number left behind. Not taken. A draft could take a change only once it is released, at least a release later and then at a release that moves the backbone. A library with no released version could not be brought in at all, as the foundations today and the next slice's starter and brand, and the deck that grows with them would wait for each release (#2501). A draft is meant to take an improvement at once, and may lock a version not yet released (DEC-003 point 8).
- **An exemption in the check of migrations for a capability's shipped libraries,** as decision records are exempt. Not chosen here. A layout that only adds needs none for its releases. The exemption would still spare a change that renames or removes a file within a version being built the migration the check asks today, though nothing installed breaks. It changes the backbone's check, so it is the methodology maintainer's to weigh, apart from this record.
- **A migration with each release, which does nothing.** Rejected. Every release would owe one, though nothing installed breaks, where a layout that only adds owes none.
- **Released versions kept as tags of the repository the capability is authored in, fetched whole** when a project brings one in, as a library from another repository is (DEC-003 point 4). Rejected. The folder would not grow, but bringing a library in would need the network and a fetch not built yet, and could not run offline.
- **A version being built for each major.** Not chosen for now. It would let a fix reach the current major while its next major is built. Majors are rare while a library's components are experimental, so one place keeps the shipped folder simple until a library needs more.
- **A pre-release number for each state of the version being built,** so a copy is never replaced. Rejected. Every change would take a number, and parallel branches would meet on it each time. Copies would multiply, and a version would gain a second form.
- **A hash recorded for a copy not yet released, as it is copied,** so the command can tell a change the project made from a change the capability made. Rejected. A project changes no shipped library in its copy, and the diff shows what a replacement drops. The list's hash would gain a second meaning beside a released version's.
- **The command that brings a shipped library in never writes over a version the project holds.** Rejected. A draft's copy could not follow the version it locks.
- **Under a lock that moves only on purpose, the copy stays until no such lock names it.** Rejected. The released version keeps the copy's number, so written code's lock, or a pinned draft's, has nowhere to move, and the copy would stay as no release left it.

## Implications

- **Edits to accepted records,** each citing this record once it is accepted. A person accepts each edit (the decisions README, "Refining an accepted record").
  - The record of change over time:
    - point 1: a shipped library's released version names the capability's version current when it is released, whose release carried it as it stands. While it is built, it names a version no later than its tree carries.
    - point 4: the command that brings a shipped library in lists a released version with the hash the capability records.
    - point 5: the capability ships every released version of each library and the version being built. The command takes the newest released one, and writes over a version the project holds only as point 5 of this record says. A copy not yet released is no library copy, so the founding record's protection of a library copy covers only a released one.
    - point 6: whoever maintains the capability releases a shipped version as it stands, where no change has touched it since the release that wrote the capability's current version, where the capability is authored. A change after that release puts the library's release off until the next release that moves the capability's version.
    - point 9: the findings of point 6 of this record. A shipped version being built that names an older release than it needs raises no finding.
  - The founding record's point 11: a version not yet released, held in a project, is no library copy, and the command that brought it in may bring it up to date. Restoring a library copy to its released hash rewrites nothing.
  - The record of files and validation's point 9: no command writes the capability's own folder, but the release of a version it ships, where the capability is authored. Restoring a library copy to its released hash is no rewrite of it.
  - The record of change over time's point 8, and the record of the engine's point 7, need no edit. Both protect what a lock draws from a released version, and a version not yet released may change under the lock that names it. The command moves no lock, and replaces a copy not yet released under a lock that moves only on purpose only where the person names the piece, after its before-and-after (point 5).
  - The record of library role defaults' point 2 ([visual-communication:DEC-008-library-role-defaults]) needs no edit. The foundations' first release takes their version as it stands (point 1), so a role added before it is in it. A role with no default added after it goes into the next version, a break of the released one, which the capability's own checks find (point 6).
- **The Tasks of #2571 it implies:**
  - **The capability's own checks** come first, since a version is released only where they read it (point 1): tests in the suite of the repository the capability is authored in, in one module, `tests/test_visual_communication_shipped_libraries.py`, which hold the checks point 6 lists.
  - **The shipped folder.** Each released version in a place of its own, and each library's record, added beside the place the library ships in today, which stays the version being built's, and outside it. The capability's reference describes both, and says where a changeset's author reads it that every change to a shipped version declares at least a patch (point 4).
  - **The command that brings a shipped library in.** The newest released version by default, with its hash; another released version, or the version being built, when asked; every copy of the library brought up to date or restored in one run; the refusals and the naming of point 5. The capability's check gains the findings of point 6.
  - **The release of a shipped version.** It finds, in the default branch's history, the release step's change that wrote the capability's current version: the change that added the changelog's entry for that version, never a tag, since a release that moves only components is not tagged, and never a change that stamped the number by hand. It refuses where that history is not at hand, or records no release of that version, or where the tree at that change holds no `tests/test_visual_communication_shipped_libraries.py`. It refuses where `git log --full-history <that change>..HEAD -- <place>` lists any change to the place of the version being built; `--full-history` keeps a change and its take-back on one side of a merge from being pruned. It refuses where the version being built carries a released number, or a number below one it carried at an earlier release. It then checks the version on released bases as a step of its own, runs the comparison with the previous release and shows the segment it finds. Only then does it add the released version with the release it needs, and write its hash in the library's record. It writes the change's patch changeset for the capability, which the person may raise. It refuses where the methodology holds the capability's folder as a synced copy, by the methodology's own answer to that question. Its look at the history is the one the capability's own checks repeat for every released version (point 4): from the release step's change that wrote the version it names to the change on the default branch's first-parent line that brings it in, with `--full-history`, failing where the history is not at hand. The release mechanics name it among what reads the release step's work. The comparison is the one the plan builds for a project's own library.
  - **The first releases.** Once a release has written a version of the capability and carried them, the foundations, then the starter and the neutral brand, are released, each naming the capability's version current when it is released. Released in one change, they name the same one. Each library release declares a patch of the capability, so one released after the next release names a later version. That closes what #2501 left out of scope.
- **A project's own library** is released by a command of its own (#2571), which writes the release the library needs. The record of the release a project's own library needs decides it ([visual-communication:DEC-014-own-library-needed-release]), and this record decides nothing of it. Should the engine come to know the release that brought each tool and field, the wait of point 1 may give way to it, by a refinement of this record.
- **No change to the backbone's code or policy.** The release step writes nothing for the libraries, and a release adds files the check of migrations needs no migration for. So this record needs no project record beside the version-bump policy, and no architecture record. The release mechanics' page gains a line, naming the release of a shipped version among what reads the release step's work.
- **Growth.** Weigh this record again once the released versions of the libraries the capability ships pass 10 MB together, about what every capability's folder holds today. The remedy then weighed: a shipped brand names its fonts by hash, as DEC-004 point 9 lets a brand name a font it may not ship; the capability holds each font once, apart from the versions; and the command that brings the brand in copies each font into the location's font folder (DEC-002 point 1). Each font is then held once, not once in each version. It changes those two points, and the founding record's library copy, a released version held whole (DEC-001 point 11), so it waits for the need.
- **Revisit this record** if the release step changes how it writes a capability's version, or how its changelog records one; if the version-bump policy changes when a capability's version moves; or if the release of a project's own library needs a seam in the release step, so that its rejection here is weighed again with it.
- **Left open:**
  - a fix to the current major while its next major is built, and a fix to an older major once a newer one is released, since the capability builds one version of each library at a time;
  - withdrawing a released version, such as one whose font turns out not to be the brand's to ship (DEC-004 point 9), since nothing removes a released version.
