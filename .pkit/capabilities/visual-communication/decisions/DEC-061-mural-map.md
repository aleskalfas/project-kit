**In plain terms:** a piece can be handed out for a whiteboard on Mural without anyone signing in. The `mural` renderer writes a *map* for each language and each combination of modes: one JSON file listing the objects a board would hold, each under its element's trace id, every value resolved. The map is an export. It is numbered, never read back, and holds nothing of any board: no id the service gives, and no record of what was drawn there. Drawing on a board is a second renderer's job, which keeps that record. Both renderers draw through one projection of the scene. On a board, the pages lie in one row, each in a frame. Each text keeps the lines the engine broke it into. The board draws a run as its own text only where the engine measured it by the board's own measures, in a font the board still draws. What the board cannot draw, or cannot set as the engine measured it, the SVG renderer draws, and it is placed as a PNG picture, element by element: a sign's outline, a text with a run's sign or ground, a text with a run measured from the brand's own font file or in a font the board no longer draws, or a text whose runs the board cannot set as measured, such as runs that differ in a font or a size the board sets once for a whole text. Anything else the board cannot set, such as a text's line height, is reported as lost, before a run wherever the renderer's declaration already knows it, and a text the board's line height pushes past its box is reported where it lies. No loss is reported twice. What the record assumes of a board is listed, and measured on one before the renderer's declaration and the map's form are fixed.

## Context

The founding record has a renderer project the scene and decide only what its medium needs and the scene leaves open, such as how pages lie on a board. The renderer declares each such choice ([visual-communication:DEC-001-visual-communication-discipline] point 2). The record of the engine and its plugins says three more things:
- **A medium with fonts of its own** has a renderer that names the font profile it draws in ([visual-communication:DEC-005-engine-and-plugins] point 10).
- **A renderer that draws into a lasting medium,** such as a board, commits a record of what it last drew. A renderer that writes files keeps none, since its files are exports (DEC-005 point 11).
- **What a renderer cannot draw** it may draw through the renderer of vector pictures, the SVG renderer, and place as a picture. The fields under such a picture are marked never to be taken back from that medium (DEC-005 point 9).

A plugin that reaches a service runs only where the project has turned it on ([visual-communication:DEC-002-files-and-validation] point 8). An export is drawn from the scene by a renderer that needs no service, and is never fetched from a board ([visual-communication:DEC-006-work-outside-the-engine-and-outputs] point 7).

The Feature [project-kit#2569](https://github.com/aleskalfas/project-kit/issues/2569) asks for a piece drawn for a Mural board without signing in. No renderer for a board exists yet. A separate record will cover a lasting medium: each object's id on the board, conflicts between branches, and edits taken back. [project-kit#2578](https://github.com/aleskalfas/project-kit/issues/2578) plans it, and it is not yet drafted. The talk behind the capability's design drew its code on a board as pictures, by hand, since the board had no monospace font (DEC-005, Context).

A Mural board, as the service's public interface describes it, holds objects of a few kinds:
- **frames,** which the service calls areas, hold other objects and set the order the board is presented in;
- **shapes;**
- **text objects,** which wrap their text themselves and whose line height the board sets. A text's words are marked up, with tags for bold, italics and colour among them, while its font, its size and a link are set once for the whole object;
- **connectors,** drawn through points, which may attach to the objects they join;
- **pictures,** uploaded as image files.

No object draws an outline from path data, and a text holds no picture. No board has been drawn from a scene yet, and nothing this record says of how a board behaves has been checked on one. Point 13 lists what it assumes, and a Task measures each fact on a board before the renderer's declaration and the map's schema are written (Implications).

This record rests on four records, which land before it, in this order:
- **[visual-communication:DEC-057-font-profile-axis-name]** names the shared axis of font profiles `font-profile`.
- **[visual-communication:DEC-059-font-files-by-weight]** lets a brand give a font family a file for each weight. A family of one file has that file at every weight, and a renderer draws each run from the file the scene names.
- **[visual-communication:DEC-058-font-profiles]** decides the font profile `mural`, in which the engine measures the board's own fonts from data the capability ships, with the list of the fonts the board holds. A run measured there from a brand's file is one the board cannot draw. It leaves to this record whether the board wraps text itself, whether the line height the board fixes joins the engine's measures, which facts of the board its renderers apply, and what they do with a font the board cannot draw.
- **[visual-communication:DEC-060-losses-accepted-by-limit]** decides that a declaration may state which outcome a plugin gives a primitive or a property, and which losses are *limits*, accepted across a piece. A renderer reports a font it cannot draw once at each typography role that gives it.

A record drafted under [project-kit#3083](https://github.com/aleskalfas/project-kit/issues/3083) proposes ties that share a trunk, and nothing here rests on it.

Four terms:
- A *map* is a file that lists the objects a Mural board would hold for one scene.
- The *projection* is the rule by which a scene becomes a board's objects: which objects, each property's value and form, and each loss.
- The *board drawer* is the renderer that draws on a board itself, planned under #2578.
- A *frame* is a board's object that holds other objects and moves them with it.

## Decision

**A renderer named `mural` writes a map for each language and each combination of modes. The map is a JSON file in the capability's own format. It lists the objects a Mural board would hold, each under the trace id of the element it draws, every value resolved. A map is an export and never a source of truth, and holds nothing of a board. The board drawer draws through the same projection, onto the board itself, and keeps the record of a lasting medium. The pages lie in one row of frames. Each text keeps the engine's lines. What the board cannot draw, or cannot set as measured, the SVG renderer draws, one element at a time, placed as a PNG picture. Every other loss is reported, before a run where the declaration knows it. What the record assumes of a board is measured on one before the declaration and the map's schema are written.**

### 1. Two renderers of one medium share one projection

- **The writer, `mural`.** It projects a scene onto a Mural board's objects and writes them to a map. It reaches no service and declares none, so it runs with no setting of the project's (DEC-002 point 8). It only draws: it updates nothing in place and reads nothing back (DEC-005 point 9). Its files are exports, and it keeps no record (DEC-005 point 11).
- **The board drawer** is a renderer of its own, which #2578 plans. It reaches the service and declares it, runs only where the project turned it on, and keeps the record of a lasting medium (DEC-005 point 11).
- **One projection.** The projection is one module of the capability, and no plugin. From a scene and the board's facts in the data of the board's profile (point 8), it gives the board's objects, each fallback picture's marker and each loss. The writer writes what it gives as a map, and the board drawer draws it on a board. So a board drawn from a scene holds what that scene's map lists, and both renderers report the same losses, by construction. Neither keeps a copy of the board's facts. Their declarations take the outcomes they state from that one module, name the same primitives and properties, and state only what the accepted records have a renderer declare (point 12). They differ only in the service and in what the board drawer updates in place or recreates.
- **Kept to Mural.** The projection serves the Mural board alone. A second medium with a board of its own shares it only once the two show what they have in common (COR-007).
- **The scene, never a map.** The board drawer projects the scene it is handed and reads no map, as no plugin reads another plugin's output (DEC-005 point 7). The fallback is the one exception, which DEC-005 point 9 makes: a renderer of the board hands the SVG renderer a scene and places what it draws (point 9).
- **One profile.** Both draw in their medium's font profile, `mural` ([visual-communication:DEC-058-font-profiles] point 1, DEC-005 point 10).
- **Each has its own version** (DEC-005 point 9). A change of the projection raises both. So does a change of a fact of the board that they apply, kept in the profile's data, since the same scene then gives another map (DEC-058 point 5; Implications). A change of a measure the engine applies raises neither: it changes the scene, which both are handed alike, as a new engine does. Each also counts the SVG renderer's version, and the pin of resvg that the fallback's step carries, as part of itself, since its fallback pictures are drawn through them (point 9).
- **Built under this record: the projection and the writer.** The board drawer, its service, its record and what it updates or recreates are #2578's.

### 2. The map is an export, never a source of truth

- **Made at each export.** An export run that names the format `mural` writes one map for each language and each combination of modes the piece names. It draws them from the piece's scenes in the medium's profile, or in the default profile where the brand gives none (point 8), numbers them with the run, and never overwrites another export (DEC-006 point 7). A board shows one combination at a time, so a map holds one.
- **Never read back.** No command of the capability reads a map, so a map edited by hand changes nothing. An edit made on a board changes the source only when it is taken back into the logical layer, as a change a person reviews (DEC-001 point 2). A later record decides how edits are taken back.
- **Nothing of a board.** A map holds no board's id, no id the service gives an object, no hash of what was drawn and no state of a sync. Those belong to the record of a lasting medium, which #2578 is to decide, keyed by the board it draws to, citing this record for the projection.
- **Room for that record.** Each object of a map is named by its element's trace id, which is the key the record of a lasting medium maps to the service's ids (DEC-005 point 11). Every place in a map is measured from one origin, so a reader puts the whole map anywhere on a board by one offset. Where it goes is the reader's choice.
- **Committed only as any export is:** the version a person hands out, and a published piece's current copy (DEC-006 point 7).

### 3. The map's format is the capability's own

- **A JSON document.** It names what it is, `visual-communication/mural-map`, and its version, as the document of a brand's values names its own (DEC-005 point 8).
- **A schema for each version.** The capability ships one for each version of the map and lists it in its reference. The schema stands alone: no file of the capability's own format binds to it (DEC-002 point 3). It refuses a key it does not name.
- **A version of its own,** a major and a minor, as in `1.0`, apart from the format number of the files a project keeps, from the seam's and from each renderer's. A schema refuses what it does not name, so every change of the map's form raises the map's version, and the renderer's with it.
- **A minor only adds:** keys that a reader that does not know them may pass over, still placing every object as before. A new kind of object, or any other change, raises the major.
- **A reader refuses only a major it does not know.** It reads the version first. It reads a map of a later minor of a major it knows, passing over the keys it does not know, and checks a map against the schema of the map's own version.
- **The newest version alone.** The renderer writes the newest form only. An export is made once and handed out, and no declaration with a lock picks its form, as one does for written code (DEC-005 point 8).
- **Only what a board holds.** The map holds objects of the board's kinds, each with its place, its size and its values, in one flat list. It holds no template, instance, layout, theme, role, formula or placeholder, so a reader can push it to a board without knowing the capability's libraries. Nor does it hold the ids or the state a tool keeps to hold a board in step with a file (point 2).
- **The same map for the same scene.** Its text is canonical, and its numbers are rounded as the scene's are. So the same scene, values and export's number give the same bytes, except the pixels of its pictures (point 9).
- **Its name** is an export's (DEC-006 point 7), ending `.mural.json`: `<piece>.v<N>.<language>.<key>.mural.json`.

### 4. What a map holds

- **Its head:** the document's name and version; the piece, its lock and the number of the export that wrote it (DEC-006 point 7); its language; the full key of the combination it holds, over the value axes and the size axes the piece names and the axis of font profiles (DEC-004 point 3, DEC-058 point 1); and the renderer's name and version. A map travels alone, as every exported file does, so its head tells it from every other map, a light and a dark map of one scene among them. It names no seam's version, since the seam is never kept (DEC-005 point 8).
- **Its frames,** one for each page, in the piece's order of pages (point 5).
- **Its objects,** in one list in the scene's draw order, bottom first. That is the order in which a reader stacks them on the board (point 13).
- **Each object** holds:
  - its `id`, the trace id of the element it draws, exactly as the scene gives it, whatever characters it holds (DEC-005 point 5);
  - its kind, one of the board's (point 6);
  - the frame it lies in, named by its page's trace id;
  - its place and size, measured from the map's origin in the scene's unit. One unit of the board is one unit of the scene, so every length keeps its number, a font's size among them (point 13);
  - its properties, each resolved.
- **One form for each property.** A property takes the same form everywhere in the map, whatever object holds it. Where the scene's name means the same thing, the property takes that name. A colour is its value in the map's combination, written `#rrggbbaa`, never a role. A step of an order takes the value that comes with the scene (DEC-005 point 5). A length is a number, a font family is named as the board names it, and a connector's route is a list of points.
- **A text's lines and runs.** A text holds the parts of its style that the board sets once for a text, and its paragraphs. Each paragraph is a list of its lines, as the engine broke them, and each line a list of its runs. Each run holds its text and those parts of its style that the board sets run by run (points 7 and 8).
- **Pictures, held whole.** Each picture an object shows lies in the map once, as the data of its kind, PNG or JPEG, in a list that each object showing it points to, as the SVG renderer embeds its pictures whole. So a map travels alone, as every exported file does (DEC-006 point 7).
- **A fallback picture's marker.** A picture drawn through the fallback (point 9) names the elements it draws, by trace id, and the content fields they show, by their sources. It marks those fields as never to be taken back from the board (DEC-005 point 9).

### 5. How pages lie on a board

The scene does not say how its pages lie on a board, so the renderer declares it (DEC-001 point 2).
- **In frames.** Each page lies in a frame of its own, at the page's size, which holds every object drawn on that page.
- **In one row,** left to right in the piece's order, with their top edges on one line. The gap between any two pages is the same, and the declaration names it in the scene's unit. The first page's top-left corner is the map's origin.
- **In the order the board presents them.** The frames' order is the piece's order of pages, as frames are assumed to set it (point 13).
- **Nothing on the page.** A frame takes no colour, edge or title from the piece. Where the board lets a frame show none of its own, it shows none (point 13). So it adds nothing to a page, and anything the board shows of a frame is the board's own (DEC-001 point 2).
- **No physical page.** A board has no physical page, so the renderer loses nothing of a top's physical size, and its declaration says so ([visual-communication:DEC-034-brand-drawings] point 3).

### 6. What each element becomes

- **A page's group** becomes its frame. **Any other group** becomes no object: each element under it takes its own place on the board, and its trace id keeps the path of the groups above it (DEC-005 point 5).
- **A box or an ellipse** becomes a shape.
- **A text** becomes a text object of its own, at the text's frame, grown by the board's inset (point 7). It never becomes text inside a shape, since the board sets the text inside a shape by rules of its own.
- **A line** becomes a board connector through the points of its route. The route is the one the connector tool gave it, not one the board would choose (DEC-005 point 2). Each end that meets an element names that element by trace id, as a hint that a reader may attach the connector there (DEC-005 point 5), which a board is assumed to allow without routing it again (point 13). Ties that share a trunk are the concern of the record drafted under #3083.
- **An image** becomes a picture, placed at the rectangle its fit gives the picture within the image's frame.
- **A path,** a sign's outline, which no object of the board draws, becomes a picture through the fallback (point 9).
- **What the board draws in its own way,** such as a connector's turns or an arrowhead, is approximated, and the declaration says so (points 10 and 13).

### 7. Each text keeps the engine's lines

- **The lines as given.** The renderer gives the board each text as the engine broke it into lines. Each line ends in a break written into the text, and each paragraph in a break between paragraphs (point 13).
- **Not the board's own wrapping.** A renderer draws the lines as given. A medium that wraps text itself may wrap within the measured width, as a declared choice, only where its edits come back as plain text (DEC-005 point 4). A text's edits on the board come back marked up, as far as the board's public interface shows (point 13), so this renderer takes none of that choice. Its declaration says it draws the lines as given, and they are no loss.
- **In an object as wide as measured.** A text's object lies at the text's frame, grown on each side by the board's inset: how far the board sets a text in from its object's edges. The inset is a fact of the medium that the renderers apply, kept with the profile's data (DEC-058 point 5). So the text's lines lie within the frame, where the engine placed them.
- **Where the board breaks a line again.** The engine broke each line against the frame's width less a small margin, 2% of the em today (DEC-005 point 4). A line keeps to one line on the board only where the board sets it no wider than the profile's widths and that margin allow (point 13). An estimate errs wide (DEC-058 point 5). A table measured from the board need not, and no width of the profile has yet been compared with a board's. Where the board sets a line wider, it breaks it again, at a place its own rules choose, and the text takes more lines than the engine's and runs past its frame. The renderer never sees a board, so it cannot report such a line. That is why the measuring Task compares the board's widths with the profile's before the declaration is written (Implications).
- **What a preview shows.** A preview shows the engine's lines (DEC-058 point 6), which are the board's wherever the board keeps them.
- **How far apart the lines lie** is the board's own (point 8).

### 8. A run's style, a link, a font and a line height the board cannot set

- **Run by run, or once for a text.** The board sets each part of a run's style, its family, size, weight, paint and link, either for each run or only once for a whole text. Which of the two holds for each part is a fact of the medium that the renderers apply. It is kept with the data of the board's profile, beside its inset and its line height (DEC-058 point 5). Every renderer of the board reads it there, and none keeps its own. The declaration states none of it: of each part, it states only what DEC-005 point 9 has a renderer declare, with the outcome [visual-communication:DEC-060-losses-accepted-by-limit] point 2 adds. What the board does with each part is assumed, and measured before the profile's data holds it (point 13).
- **Only a run in a board font is the board's own.** A run is in a *board font* where the scene says it was measured from a table or by an estimate, and the list of the board's fonts says the board still draws its family at the weight the scene draws it at (DEC-058 point 5). The board draws a run as its own text only where it is in a board font. Any other run is in a font the board cannot draw, and its text becomes a picture through the fallback (point 9). A font here is a family at a weight.
- **A run measured from a file.** A family the brand gives a file for is measured from that file in the board's profile too, never by the board's measures. So the board cannot draw it, even where the list gives a family of that name at that weight, whose letters nobody measured against the file (DEC-058 point 4). A file that serves every weight measures a run at 600 in its regular letters ([visual-communication:DEC-059-font-files-by-weight] point 2), where the board would draw a semibold of its own. The picture draws the run from the file the scene names (DEC-059 point 5), so the text keeps the font it was measured in.
- **A run in a font the board no longer draws.** The list keeps a family or a weight the board ceases to draw, marked as no longer drawn, and the engine measures by it (DEC-058 point 5). Handed over, the board would draw it in another font, with no loss reported (DEC-005 point 10). So it is no board font. The picture draws the run in its default fonts, at the widths the engine measured (DEC-058 point 6), and the brand that names the font asks for attention (DEC-058 point 9).
- **Reported at its role.** Each font the board cannot draw is reported once at each typography role that gives it, never at each text drawn in it, with `picture` as what the renderer did (DEC-060 point 5). The loss says how the picture draws the font's runs: from the brand's file, or in their default fonts where the board no longer draws it. An entry that accepts it at its role accepts no loss of another role (DEC-060 point 5). So the text is reported at its trace id too where it also holds a run in a board font, or a link, as point 9 says. A run of another role whose font the board cannot draw either is that role's loss, which that role's own entry judges. A text whose every run is in a font the board cannot draw, with no link, is reported at those fonts' roles alone.
- **A brand's choice.** So a brand chooses, in its profile for the board, between one of the board's own fonts, which the board draws as its own text where nothing else makes the text a picture, and its own file, which draws as a picture (DEC-058 point 4).
- **A brand that gives no profile for the board** is drawn in its default profile (DEC-005 point 10), in which every run is measured from a file (DEC-058 point 4). So each of its texts becomes a picture, drawn from the brand's files, and each of its fonts is reported at each role that gives it.
- **The list of the board's fonts** is the one DEC-058 point 5 keeps with the profile's data: each family the board holds, under the name the board knows it by, at the weights the board draws it in, each marked where the board no longer draws it. A release of the capability adds to it. Every renderer of the board reads from it the name the board knows a family by, and whether the board still draws it, and none keeps a list of its own. So the renderer hands the board no font the list does not say the board still draws, which the board would draw in another font with no loss reported (DEC-005 point 10).
- **No character in a style it was not measured in.** A text stays the board's own text only where every run of it is in a board font and the board can set every run as the scene gives it. A part the board sets run by run is set so. A part the board sets only once for a text, other than a link, is set so where every run of the text takes the same value. Where runs differ in such a part, as a run of inline code differs from the words around it in family and size, the whole text becomes a picture through the fallback (point 9). So the board draws no character in a family, size, weight or spacing it was not measured in.
- **A weight, as the board's regular or its bold.** The board sets a run's weight by marking it bold or not, and draws each family at its regular and its bold alone (point 13). So a text stays the board's own only where each of its runs takes the regular or the bold that the list gives its family, and a text whose runs differ in weight, only where they take that regular and that bold. Otherwise it becomes a picture (point 9).
- **Letter spacing, as the font's own.** The board sets no letter spacing of a piece's, and draws each run at its font's own spacing, which the profile's widths measure (point 13). So a text stays the board's own only where each of its runs takes a letter spacing of zero, and becomes a picture otherwise (point 9).
- **Reported where it lies.** A text these rules make a picture is reported as point 9 says, naming what made it one: the part its runs differ in, a weight other than its family's regular and bold, or a letter spacing. Whether a text is one depends on the values a piece gives, so the loss is no limit (DEC-060 point 1), and is accepted at its place (DEC-060 point 3).
- **A link, never taken from most of a text.** Where every run of a text holds the same link, the text's object takes it. Elsewhere the object takes none, and each link its runs hold is left out, reported at the text's trace id and accepted at its place. The text stays the board's own, since a picture holds no link either ([visual-communication:DEC-033-structure-for-readers] point 8).
- **A run's sign or ground** makes its text a picture through the fallback (point 9), since no text on the board holds either. A sign tells a concept apart where colour alone would not. A ground is the fill behind a run, the one its colour is measured against ([visual-communication:DEC-036-concept-signs] point 3). Leaving either out would change what a reader reads, not only how the text looks. Both lie within a text's lines, where no term of the formats names them, so their loss is of no limit (DEC-060 point 1). The text is reported as point 9 says, naming the sign or the ground.
- **A text's line height, never set.** The board sets a text's lines apart by a line height of its own (point 13). The renderer takes none of a text's line height, so its declaration states the line height approximated: a limit known before a run, which one entry accepts across a piece (DEC-060 points 1, 2 and 3). The capability finds a limit before a run, so it reports this one at every text, those drawn as pictures among them, though a picture keeps the line height the engine measured. The board's line height is a fact of the medium that the renderers apply, as its inset is, kept with the profile's data (DEC-058 point 5). It joins none of the engine's measures, so the engine still sets a board's texts at the line heights their roles give.
- **A text the board's line height pushes past its frame.** Where the board's line height is greater than a text's, the lines of a text the board draws as its own take more height on the board than the engine gave them, and the text runs past its frame, over what lies below it. The renderer finds each such text from the two line heights and the text's lines, and reports it at the text's trace id, as approximated, naming how far it runs past its frame. That loss depends on the text's values and is found while drawing, so it is no limit, and the entry that accepts the line height across a piece accepts none of it (DEC-060 point 3). A text drawn as a picture keeps the engine's line height in its picture, so the board pushes none of it past its frame, and none is reported so. So a person learns of each text the board pushes past its frame, and by how much. They accept it at its place, or give its role a line height no smaller than the board's, which then holds in every medium, since a profile changes fonts alone (DEC-058 point 4). Where the board's line height is no greater than a text's, the text runs past nothing, and the limit alone is reported.

### 9. What the board cannot draw, the SVG renderer draws, element by element

- **The element alone.** The fallback draws one element at a time: an element the board cannot draw, such as a path, or a text that point 8 makes a picture, whole, with its signs and grounds. Every other element of the same component instance stays a board object, such as the box a code block draws its text on. So a person can still move and edit everything else the board holds.
- **Drawn by the SVG renderer, through the seam.** The renderer hands the SVG renderer a scene that holds the element alone, at the element's frame, with its trace ids and its sources as the piece's scene gives them, and places what that renderer draws. DEC-005 point 9 lets a renderer draw so, and this is the one output of another plugin that a renderer of the board places (point 1). The picture has no ground of its own, so what lies under it shows through (DEC-005 point 9), as a board is assumed to show it (point 13). The SVG renderer cannot draw a run measured from a table or by an estimate, so it draws such a run in its default fonts, at the widths the engine measured (DEC-058 point 6). It draws a run measured from a file from the file the scene names (DEC-059 point 5).
- **A text's picture holds every line.** A text's picture is as wide as the text's frame, and as tall as all the text's lines as the engine measured them, from the frame's top. So a line the engine set past the frame's foot lies in the picture too, where the engine placed it, and the picture cuts nothing it draws.
- **Its losses are the renderer's.** Each loss the SVG renderer reports is what the picture lost, so the renderer reports it as its own, at the element's trace id. The SVG renderer's version counts as part of the renderer's, as the pin of resvg does (point 1).
- **As PNG,** at a scale the declaration names in pixels for each unit of the scene, at least two, so that its text stays sharp when a person zooms in on the board.
- **By resvg, in a step of its own.** The renderer's pictures are turned into pixels by resvg, at the version the capability pins, through the one module of the capability that calls resvg, which the viewing step uses too ([visual-communication:DEC-015-viewing-step-and-reviewer] point 2). So what resvg needs to draw a page rightly, such as each face handed over under the name its rule gives, is kept once for both. For an export, that module runs in a step of its own: a script of the capability that carries resvg's package, pinned, and runs resvg as a library in its own process. It calls no outside program and reaches no network to draw (DEC-002 point 8). An export runs the step only where a renderer draws a fallback picture, so only an export of the format `mural` needs the package, and the export command carries none. How the drawings reach the step, and their pixels come back, is the fallback Task's.
- **Each pin held equal.** resvg's package is pinned in each script that draws through it: the viewing step's, and this step's. The capability's tests hold every script's pins equal to one lock, so these pins agree. The pin the step carries counts as part of the renderer, so a change of it raises the renderer's version, since its pictures may change (DEC-005 point 9). It is the pin that the test of the writer's version reads (Implications). Should DEC-015's revisit reopen resvg, it reopens this point too.
- **No painted run drawn to nothing.** That module finds each run resvg drew to nothing, as it does for the viewing step (DEC-015 point 3). Where it finds one in a fallback picture, of a run that is painted in a colour with some opacity, and that the SVG renderer reported no loss of, the renderer stops, naming the element and the run, and the export stops with it. A run with no paint, or none that shows, leaves no ink by design, and stops nothing. The module does not find a run resvg drew only in part, such as one some of whose letters it left out, nor one drawn in other letters than the engine measured: such a run passes, as it does in the viewing step.
- **Its pixels.** No test has yet checked whether resvg gives the same pixels on every kind of machine. So the capability's tests pin each map with its pictures' SVG drawings in place of their pixels. They pin the pixels only once those are shown to be the same on each machine the tests run on.
- **Its text.** The picture takes the text that DEC-033 point 8 gives it. Of what is lost inside it, the links are reported as below, and the structure and the words as point 11 says. A picture of a sign's outline takes no text, since its element shows no words. A content image keeps its own picture's text.
- **Marked** as point 4 says.
- **Reported once.** The capability reports each limit's loss before a run (point 10), such as a path drawn as a picture, and the renderer reports no such picture again. The renderer reports a text drawn as a picture, whatever made it one, at the text's trace id where the text holds a run in a board font, or a link: what no entry at a role judged (point 8). That loss names what made the text a picture, its links, and each run the picture draws in its default fonts (DEC-058 point 6). A text whose every run is in a font the board cannot draw, with no link, is reported at those fonts' roles alone (point 8), each of whose losses says how the picture draws that font's runs. Point 11 adds a report at a text's place where a board's pictures hold no text for a reader.

### 10. What the declaration states before a run

DEC-060 point 2 lets a declaration state which outcome a renderer gives each primitive and property. The capability then knows each such loss before the renderer runs (DEC-005 point 9). This renderer's declaration states:
- **Drawn as a picture:** a path (point 6).
- **Approximated:**
  - a line's turns, at the board's own radius;
  - an arrowhead, of the board's own shape and size;
  - a text's line height (point 8).
- **Left out:** each word of the reader's side that no board object holds (point 11).
- **Not a loss:** how pages lie, which is a declared choice (point 5).

Each loss above is of a primitive, a property or a word of the reader's side that the renderer takes none of, wherever it is present. So each is a limit of the medium (DEC-060 point 1), and one entry in a piece can accept each across the piece (DEC-060 point 3). A text's lines are drawn as given, so they are no loss (point 7).

The renderer reports other losses as it draws. Each depends on the values a piece gives, or lies where no term of the formats names it, so none is a limit (DEC-060 point 1):
- a text drawn as a picture that holds a run in a board font, or a link, at the text's place, naming what made it a picture: runs that differ in a part of the style the board sets only once for a text, a weight other than its family's regular and bold, a letter spacing, a run's sign or ground, or a font the board cannot draw (points 8 and 9);
- a text drawn as a picture, at the text's place, where a board's pictures hold no text for a reader (point 11);
- a link that some of a text's runs hold and others do not, left out, at the text's place (point 8);
- a text the board draws as its own that the board's line height pushes past its frame, approximated, at the text's place (point 8);
- a font the board cannot draw, drawn as a picture, once at each typography role that gives it (point 8);
- each loss the SVG renderer reports in a fallback picture, at the element's place (point 9);
- a value outside the range the board takes, such as a stroke wider than its widest, drawn at the nearest value it takes, as approximated, at its place;
- the losses every renderer reports, such as a role with no colour.

An entry at a text's trace id accepts every loss the renderer reports at that text, whatever its cause, those a later change brings included (DEC-060 point 3). So once a person accepts one loss at a text, each later loss there is accepted unseen: a link left out, the board's line height pushing the text past its frame, or a run of code that makes it a picture. That is the cost of accepting a loss where it lies, which the losses above share with every renderer's.

### 11. The reader's side

- **Not read whole.** A board is not an image inside a document. A reader moves through its objects one by one, so the format is not read whole, and it carries the reader's side (DEC-033 point 9).
- **DEC-033's revisit, made provisionally.** DEC-033 revisits its point 9 at a renderer whose medium is no picture yet holds no reader's side, such as a whiteboard service's. This record makes that revisit provisionally, on a fact it assumes: a board is no picture, its objects are assumed to hold words of the reader's side (point 13), and DEC-033 point 9 stands. The measuring checks that fact, and the revisit fires again if it finds that a board's objects hold none.
- **Spelled where the board holds it.** The declaration names each word of the reader's side that a board's objects hold, as the measuring finds them (point 13), and the renderer puts it there (DEC-033 point 1). Every other word is a loss known before a run, left out.
- **Structure inside a picture.** While no board object holds a word of a text's structure, such as a heading, that word is left out of every text by a limit (point 10), so a text drawn as a picture loses nothing more of it. Should the measuring find one held, a text drawn as a picture that holds that word is reported at its trace id too, as one that holds a link is (point 9).
- **Words inside a picture.** A text drawn as a picture keeps its words for a reader who does not see it only where a board's picture holds a text that a reader's tools read (point 13). Where the declaration names no such text, a text drawn as a picture is reported at its trace id too, naming its words as lost to that reader, as one that holds a link is (point 9). So no entry by a limit accepts a paragraph's words unseen.
- **Only where no seeing reader sees it.** A picture's text never becomes a caption the board shows, since a renderer adds nothing to a page (DEC-001 point 2).
- **Under a fallback picture,** as point 9 says (DEC-033 point 8).

### 12. Who reads a map, and what this adds

- **Before the board drawer exists,** a map is read by a person, or by a tool of the person's own that pushes it to a board. The capability's reference says what a map holds, and its schema checks one, so such a tool needs nothing else from the capability.
- **No part of the capability reads one.** The export writes a map and records its hash (DEC-006 point 7), and the capability's tests check it against its schema. A person who wants to see what a board will show looks at the SVG renderer's previews of the scenes in the board's profile (DEC-058 point 6), not at the map. Once the board drawer exists, it reads no map either (point 1).
- **To the format, by addition:** the export format `mural`, which a piece may name. No file that format 1 accepted is refused ([visual-communication:DEC-003-change-over-time] point 3).
- **To the seam, nothing.** The renderer reads the scene as DEC-058 and DEC-059 leave it, its texts' lines and each run's measure, files and default fonts included. Its declaration states only what the accepted records have a renderer declare (DEC-001 point 2, DEC-005 points 4 and 9), the outcomes DEC-060 point 2 adds among them, which only the capability reads. The board's facts it reads are the data of the board's profile, as the fonts the board holds are (point 8). The seam's version stays the same (DEC-005 point 8).
- **No new finding.** Its losses ask for attention until someone accepts them (DEC-005 point 14).
- **Revisit:**
  - once the measuring Task, or a board the board drawer draws, finds false a fact point 13 assumes;
  - once a board's edits are shown to come back as plain text (point 7);
  - once the board's line height, measured, is greater than that of the roles pieces commonly give, so that many texts run past their frames (point 8);
  - at the first change of the map's form after version 1.0, which asks whether a reader needs an older form kept (point 3);
  - once a board refuses a row as wide as a piece's pages (point 5);
  - once DEC-015's revisit reopens resvg (point 9).

### 13. What this record assumes of a board

Each fact below is read from the service's public interface or from earlier work, and none has been checked on a board. Each sentence above that rests on one points here. The measuring Task checks each fact on a board before the writer's declaration and the map's schema at version 1.0 are written (Implications). Where a fact is false, this record makes the change named beside it before a Task rests on it.
- **A text object keeps the width it is given,** sets each line within it to the left, centred or to the right, and grows down to hold its lines. If not, a text's lines do not lie where the engine placed them, and point 7 is revisited.
- **A break written into a text is kept,** and the board tells a break within a paragraph from one between paragraphs. If no break is kept, the engine's lines cannot be drawn as given, and point 7 is revisited, with DEC-005 point 4. If the two breaks are one, a paragraph ends as a line does, and taking edits back must tell them apart from the record of a lasting medium (#2578).
- **A text's edits come back marked up,** as the public interface describes a text's words, not as plain text. If they come back as plain text, DEC-005 point 4 allows the board's own wrapping, and the alternative deferred for it is revisited (point 7).
- **The board sets a text in from its object's edges by an inset** the profile's data can state, the same for every text object or for each font and size. If it cannot be so stated, a text's lines cannot be placed within their frame, and point 7 is revisited.
- **The board sets a line no wider than the profile's widths and the engine's margin allow.** An estimate errs wide (DEC-058 point 5), and a table need not. If the board sets a line wider, it breaks it again, and the text runs past its frame with no loss reported (point 7). The profile's data is then corrected, or point 7 revisited.
- **The board sets a text's lines a fixed share of its size apart,** for each font, and places a line's letters within that height in a way the measuring can state. If the spacing depends on more, such as the object's size, the renderer cannot find a text it pushes past its frame, and point 8 is revisited.
- **Which parts of a run's style the board sets run by run.** The public interface suggests that a font, a size and a link are set once for a text, and bold or not, and colour, run by run. If a part is set the other way, the profile's data says so (point 8), and point 8's rule moves texts between the board's own text and pictures as it says, with nothing else changed. If a part is set neither run by run nor once for a text, as a link would be if no text object held one, point 8 is revisited, since it gives such a part no rule.
- **Which weight the board's bold is.** The board marks a run bold or not, and draws each family at two weights at most: its regular for a run not marked, and its bold for one marked. The list gives a family at those weights alone, the lighter its regular (DEC-058 point 5). If the board's bold of a family is a weight the list does not give, the list is corrected. If the board draws a family at a third weight, such as through a weight set once for a text, point 8 is revisited, so that the board may draw that weight as its own.
- **The board sets no letter spacing of a piece's,** run by run or once for a text, and draws each run at its font's own spacing. If it sets one, letter spacing joins point 8's parts, the profile's data saying how the board sets it, and point 8's rule moves texts between the board's own text and pictures as it says.
- **The fonts the board holds, with their weights,** as the profile's list names them (DEC-058 point 5), and among them no monospace family (DEC-005, Context). If the list names a font the board lacks, the board draws its text in another font, and nothing reports it (DEC-005 point 10). The list then marks it as no longer drawn, the renderer draws its runs in pictures (point 8), and a brand that names it asks for attention (DEC-058 point 9).
- **A font's size is in the unit the board places objects by,** so one unit of the board is one of the scene for every length (point 4). If not, each font size is scaled by the ratio found, and point 4 says so.
- **The board takes a colour's opacity,** on a shape, a connector and a run. If not, a colour that is not opaque is approximated, at its place (point 10).
- **A picture keeps its transparency,** so what lies under a PNG's clear ground shows through. If not, a fallback picture hides what lies under it, such as a code block's box, and point 9 is revisited.
- **Objects stack in an order a reader gives,** such as the order they are made in, or a value of their own. If not, the order of point 4 cannot be kept where objects overlap, and point 4 is revisited.
- **A connector keeps the points it is given,** whether or not its ends are attached. If attaching an end makes the board route it again, the map names no attached end, and each connector keeps its route, unattached (point 6).
- **A connector's turns, its arrowheads and its stroke** are drawn in the board's own way: turns at a radius of its own, arrowheads of the few kinds it offers, and widths within a range of its own (point 10). Where the board draws one as given, that loss leaves the declaration.
- **A frame holds what is laid in it,** moves it with itself, sets the order in which the board presents frames, and can show no fill, edge or title of its own. If it shows any, that is the board's own (point 5). If frames set no order, the piece's order of pages holds only from left to right.
- **No object draws an outline from path data, and a text holds no picture** (Context). If one does, the fallback draws less (points 6 and 9).
- **Which words of the reader's side a board's objects hold,** a picture's alternative text first: a text that a reader's tools read in a picture's place, and that the board does not show. A text object is assumed to hold a link set once for it (point 8). No object is assumed to hold a heading, a list, a run's structure or a reading order. The declaration names each word the measuring finds held, and every other is left out, a limit (points 10 and 11). If a picture holds no alternative text, a text drawn as a picture is reported at its place (point 11). If a board's objects hold none of these words, DEC-033's revisit for a whiteboard service's renderer fires (point 11).
- **A board takes a row as wide as a piece's pages** (point 5). If not, pages in a grid are revisited.

## Rationale

**Why two renderers.** Writing a file needs no service, and drawing on a board does. A renderer that declares a service runs only where the project turned it on (DEC-002 point 8). So one renderer that both wrote maps and drew boards would need that setting just to write a file. Two renderers sharing one projection give a board and a map the same objects and the same losses, and the signed-out one never reaches a service. Two renderers that each stated the rule would drift apart, so the rule is one module both call. Their objects, their losses and their declared outcomes are then equal by construction, and their versions move together. It is kept to the Mural board, since no second board medium yet shows what two would share (COR-007).

**Why an export, and nothing of a board.** An export is made from the scene and never fetched back (DEC-006 point 7). A file that also held a board's ids and the state of a sync would be the record of a lasting medium. That record is committed, rewritten at each render and keyed by its board (DEC-005 point 11). A map holding those ids would be a second copy of the record, and its ids would go stale with every edit on the board. Keeping the map free of them leaves that record to #2578, keyed by the trace ids the map already names.

**Why the capability's own format.** The map carries the projection out of the capability to tools that know nothing of its libraries. So it needs a form that only the capability changes, and a version a reader can check, as the document of values has (DEC-005 point 8). The service's own interface changes when the service changes it. The map's form should change only when the projection does. JSON is read by every reader of JSON, and by every reader of YAML too.

**Why the newest version alone.** Written code keeps each form it shipped, because code outside the capability reads it under a lock that moves only when a person moves it (DEC-005 point 8). An export has no such lock. It is made once and handed out, and its reader reads the version it holds. Keeping each form would cost a writer for each version, with no reader asking for one.

**Why a major and a minor.** A reader outside the capability checks the version before it reads. With one number, each addition would make every such reader refuse every later map, though it could still place each object. A minor adds only keys a reader may pass over, so a reader refuses only a map it cannot read rightly. The first change of the map's form after version 1.0 is where an older form could first be needed, so the revisit is tied to it, and not to a reader outside the capability saying so, which nothing carries back.

**Why pictures held whole.** An exported file travels alone (DEC-006 point 7). A map with its pictures in files beside it would arrive at a board without them.

**Why one unit of the board for each unit of the scene.** Any other scale would be a choice the scene does not make, and would change every number in the map for no reader's gain. How far a person zooms into a board is up to them.

**Why one row.** A row keeps the pages in reading order, left to right, as the frames are presented. A grid would add a choice of columns that the scene does not make.

**Why each text keeps the engine's lines.** A renderer draws the lines as given, and only a medium whose edits come back as plain text may wrap within the measured width (DEC-005 point 4). The board's public interface describes marked-up text, so the accepted records give this renderer no such choice. The engine's own reason holds on a board too: a medium that wrapped by its own widths would move a word wherever they differ from the profile's, and push its text past its box (DEC-005, Rationale). The cost: a person who edits a text on the board edits lines broken by hand, which do not flow again as they type, and taking edits back must tell the breaks the renderer wrote from those a person wrote (#2578).

**Why a run's sign or ground makes a picture.** Each says something a reader reads (DEC-036 point 3). A sign placed beside the board's text would have to lie where the board sets its run, which the renderer cannot know, since the board's widths are its own. Left out, the run would lose its meaning or its contrast in silence. A picture keeps both, at the cost of that text no longer being editable on the board. No term of the formats names a run's sign or ground, since both lie within a text's lines, so no entry by a limit can accept them ([visual-communication:DEC-060-losses-accepted-by-limit] point 1), and the loss is reported at the text's place. A text whose every run is in a font the board cannot draw is a picture already, and loses nothing more by them, since the picture draws them, so it is reported at its roles alone. In the deck below, every run that draws a sign lies in a block of code, so no text of it is reported for a sign.

**Why only a run in a board font goes to the board.** A run measured from a file was measured in the file's letters, and a family of the board's that shares its name was never measured against them ([visual-communication:DEC-058-font-profiles] point 4). A file that serves every weight measures a semibold run in its regular letters ([visual-communication:DEC-059-font-files-by-weight] point 2), and a board's family of that name may differ in every width. Handed to the board, the run would be drawn wider or narrower than measured, and could push its text past its box, where no check sees it. Drawn as a picture from that file, it keeps its measure. A font the board no longer draws the board would swap for another in silence (DEC-005 point 10). The SVG renderer cannot draw it either, so the picture draws it in its default fonts, at the widths measured (DEC-058 point 6), which keeps the text's lines and box, in other letters. A brand that wants native text on the board gives one of the board's own fonts, at a weight the board draws, in its profile (DEC-058 point 4). The loss at the font's role covers the font alone. A text that also holds a run in a board font, or a link, loses those as a picture too, which no entry at the role judged. So the text is reported at its place as well. A later change that adds a run of code to a long linked paragraph is then reported, not accepted unseen by the entry at the code's role (DEC-060 point 5), unless an entry at that paragraph already accepts its losses (point 10). A run of another role whose font the board cannot draw either loses nothing its own role's entry did not judge, so it asks for no report at the text's place. Read as any run of another role, the rule would report at its place nearly every text of a brand that gives no profile for the board, each already judged at its roles.

**Why a text whose runs the board cannot set becomes a picture.** A run drawn in its text's family or size, in place of its own, was measured in another, so it could push the text past its box, where no check sees it, as a font the board cannot draw could. A run of code or of a strong phrase drawn as the words around it would also change what a reader reads. A picture keeps both. The cost: the text can no longer be edited on the board, its structure and links are reported lost (DEC-033 point 8), and its runs in board fonts are drawn in their default fonts in the picture (DEC-058 point 6), so it looks unlike the board's text beside it. Every text that holds a run of inline code becomes such a picture. In the deck project-kit draws of itself, four slides of some sixty texts in each language, two texts hold inline code, beside seven set in code alone: four blocks of code and the names of three slots. The board holds no monospace font (DEC-005, Context), and the brand's code font is measured from its file, so all nine become pictures for their font in any case. The font is reported once at each typography role that gives it (DEC-060 point 5): the code block's role, and the shared role of code that the slots' names and the inline code take. The two that hold inline code are also reported each at its place, since they hold runs in a board font, and the loss names the runs around the code. The seven set in code alone hold no such run and no link, so they are reported at their roles alone. So the missing monospace font asks the deck for four entries, one at each of the two roles and one at each of the two texts, or three if the code block's role, an alias of the shared one, counts as that role, wherever a board's pictures hold a text for a reader (point 11). Were a board font to serve code, the two would still become pictures, since the brand sets code smaller than the words around it, each reported at its place. Six more texts of that deck set a strong phrase in another family than the words around it. They stay the board's own text only where the brand's profile for the board gives strong runs the body's family, at the bold the list gives that family (point 13). On that deck, then, the rule makes a picture of no text that the missing monospace font does not, where the brand's profile keeps strong runs in the body's family, and of six more texts in each language where it does not.

**Why the board's regular and bold alone, and no letter spacing.** The board sets a weight only by marking a run bold or not, so a run at a third weight would be drawn at the regular or the bold, in letters it was not measured in. A letter spacing the board does not set would draw a run's letters at its font's own spacing, wider or narrower than measured. Either could push a text past its box where no check sees it, as a font the board cannot draw could, so either makes a picture. The engine draws no text of a role that spaces its letters (the capability's reference, the typography role), so the second rule makes no picture until the engine measures letter spacing, and then keeps point 8's rule whole.

**Why how the board sets a run's style is the profile's data.** Whether the board sets a part of a run's style run by run or once for a text is a fact of the board, as the fonts it holds and its inset are, not a choice of a renderer. Kept once, with the data of the board's profile, both renderers read the same fact, so their projections cannot drift apart, as two declarations kept by hand could. The renderers apply it and the engine measures by none of it, so a change of it raises their versions and changes no scene (DEC-058 point 5). A declaration states what the accepted records have a renderer declare, and none has it say how a medium sets a run's style, so keeping the fact in a declaration would need DEC-005 point 9 edited. A part the board sets neither way would need a rule point 8 does not give, so the data holds no third value, and a measurement that finds one revisits point 8.

**Why a link is never taken from most of a text.** A link set on a whole text would send a reader from words that hold none, and one dropped for the rest's sake would be lost with no word said. Left off the object and reported, the link alone is lost, and the words still read as the board's own text. A picture would lose the link too (DEC-033 point 8), and the text's editing with it.

**Why a text the board's line height pushes past its frame is reported at its place.** The entry that accepts the line height across a piece accepts how the board spaces lines. It does not accept a text pushed over what lies below it, which befalls only some texts: those whose role sets lines closer than the board does. So it is a loss of its own, at each such text, which a person sees and judges. The board's line height could instead join the engine's measures (DEC-058 point 5), so that no text runs past its frame. That would lay out a board's scenes at a line height no brand chose, and move every box with text in it, which is weighed once the board's line height is measured (Alternatives).

**Why the board's facts are listed, and measured first.** Each sentence of this record about a board rests on its public interface or on earlier work, not on a board. The map's schema and the renderer's declaration are what tools outside the capability, and people who accept losses, build on, and a released map changes only with a new version (point 3). So the facts they rest on are measured before either is written, and a fact found false changes this record, not a released map.

**Why the element alone.** A picture of a whole component instance would turn into pictures things the board could draw natively, such as a code block's box. A page is an instance too, so one sign would turn a whole page into a picture. Element by element, the board keeps everything it can draw as its own, movable and editable.

**Why a text's picture holds every line.** A picture cut at its text's frame would drop a line the engine set past the frame's foot, an overflow the check already reports, and the stop would take it for a run resvg drew to nothing. As tall as the text's lines, the picture shows the overflow where the engine measured it, as the board's own text would.

**Why PNG, through resvg.** PNG holds exactly what the SVG renderer drew, with sharp edges and a transparent ground. A picture kept as vector data would be drawn again by whatever draws the board, in fonts and by rules the capability does not control. resvg is already pinned and runs as a library (DEC-015 point 2), so an export needs no outside program and no network to draw. DEC-015 chose it for images that promise nothing of their pixels, and here its pixels are handed out. So the tests pin a picture's drawing, not its pixels, and a reopening of resvg reopens point 9.

**Why a step of its own, through the one module.** That module alone knows what resvg needs to draw a page rightly, such as each face handed over under the name its rule gives, and how to find a run it drew to nothing (DEC-015 points 2 and 3). A second caller would keep a second copy of that knowledge, and a mend of one would miss the other. A script's packages are all fetched before it runs, and none of them is optional. Carried by the export command, resvg's package would reach every export of every project, a binary wheel on each machine that exports, though only a piece handed out on a board draws through it. Where the wheel runs is among what DEC-015 left unmeasured (DEC-015, Context), so a project that exports only a PDF could lose its export to it. The browser's module takes no wheel for the same reason, so every other format pays nothing for it ([visual-communication:DEC-020-html-page-drawing] point 9). The cost: a second process for an export that draws fallback pictures, and a pin more, which the capability's tests hold equal to the others.

**Why a painted run drawn to nothing stops the export, with no let-through.** A picture short of words its scene holds misleads every reader of the board, who cannot tell it from one drawn whole. The picture holds its text's every line, and the stop asks only of a painted run inside it, so a run that leaves no ink by design stops nothing. What is left is a fault, of the capability's handing of faces to resvg, of resvg, or of a font file resvg cannot read. Reported as a loss at the element's place, it would be accepted unseen by an entry that accepted the element's picture, since an entry at a place accepts every loss there (DEC-060 point 3). A let-through, as an export gives for a stale output, a number that overflows, or an element of a switching file painted otherwise (DEC-006 point 7), was weighed. Each of those hands out all that its scene holds: an output older than its source, a text past its box, a mode painted otherwise. A run drawn to nothing hands out a page short of its words. A let-through would also need the record of exports to name each run let through, a refinement of DEC-006 point 7. The stop is new: no accepted point has a renderer stop an export. The cost: an export that meets one stops until a release of the capability, or the brand whose font file resvg cannot read, mends its cause. A person who must hand the piece out meanwhile hands out another format, or leaves `mural` out of its exports.

**Why the SVG renderer is handed a scene, and its losses are the renderer's.** Through the seam, the SVG renderer draws the element as it draws any scene, with its trace ids and sources, and reports what it lost in the one form (DEC-005 point 9). What it lost is what the picture lost, so the renderer reports it at the element's place. A change of the SVG renderer may change the picture, so its version counts toward the renderer's, as resvg's pin does. This is the one output of another plugin that a renderer of the board places, as DEC-005 point 9 allows, and it is drawn from the scene, so it gives the board drawer no reason to read a map.

**Why the reader's side is carried.** A format read whole is one a document shows as a single image, giving its text (DEC-033 point 9). A board is no such thing: a reader moves through its objects. So the board spells what its objects hold, and the rest is reported lost, as for every renderer whose format is not read whole. A text drawn as a picture is a paragraph's words, not a picture's, so where no picture holds a text for a reader, its loss is reported at its place, where no entry by a limit reaches it.

### Alternatives considered

- **A board's id named by the piece or the export.** Rejected. A board belongs to the record of a lasting medium, and a signed-out export draws for no particular board.
