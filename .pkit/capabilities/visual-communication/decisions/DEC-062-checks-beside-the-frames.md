**In plain terms:** the graphic-design reviewer relies on what the checks found, in several places. Where the checks of boxes judged, it does no sums of its own over the frames. A part a size hides is no part missing. A drawing that shows a fault a check passed is one of its faults. So it must know what the checks found on the very pages it sees. A piece's findings record cannot tell it: it holds what the last render found, on scenes that may differ from the ones drawn. So the viewing step, which already computes the scenes it draws, runs on them the code a render runs, and gives every finding in its report, image by image. The reviewer reads what any check found from that report alone. Where a check found nothing at a place, the reviewer reads the place as judged and clean only where the check judges that kind of place, as the list of checks says, and did not state that it could judge nothing there. The check of edges that nearly line up states that at a key whose brand gives no step of space.

## Context

[visual-communication:DEC-046-faults-lower-grades] point 3 adds two checks that measure the boxes of siblings: edges that nearly line up, and boxes that overlap. Where they ran, the reviewer does no sums over the frames, and where they did not, it reads the offsets from the frames. The point does not say where the reviewer learns which holds, nor at which places. Point 5 of the same record has a like need for a check of a text's size, which the capability does not ship yet. It has the reviewer tell from the capability's list of checks whether one exists. The reviewer reads what a check found in three more places, today from the piece's findings record: a part a size hides is no part missing ([visual-communication:DEC-021-size-and-shape] point 5), a drawing that shows a fault a check passed is a fault, and a fault a check already reports is named in one line ([visual-communication:DEC-030-design-agents] points 6 and 7).

The words it uses:
- **The viewing step** draws a piece's pages as images, in the clone's local folder. Beside them it writes the *frames*, each drawn element's box in the image's pixels, and a *report* ([visual-communication:DEC-015-viewing-step-and-reviewer]). It computes the piece's *scenes*, its pages as the engine lays them out, from the files as they stand, under the piece's lock (DEC-015 point 4). The frames are the boxes of those scenes. Its scenes fill an export's facts as a preview's do, with the next number and the date of the run ([visual-communication:DEC-016-what-an-export-reads] point 5).
- **A check** is a measurement a command makes on every render, with no judgement ([visual-communication:DEC-002-files-and-validation] point 7). Its *label* is the name its findings carry. **The capability's list of checks** is its page that lists each check and its findings.
- **The scene findings** are what computing a piece's scenes finds, such as boxes that overlap, a text that leaves its box, or content a size hides.
- **The findings record** is the file each render of a piece that is not final keeps beside the piece, holding its scene findings. Its scenes take *stand-ins*, fixed texts measured in place of an export's number and date (DEC-016 point 5). Its key fingerprints every file the scenes were computed from, and the check reads it while the key verifies against the files ([visual-communication:DEC-005-engine-and-plugins] point 13).
- **A place** is what a finding names on one page at one key: an element, a pair or group of elements, or content.
- **A covered entry** is an entry of the report's list of texts the page does not show, for a text a part drawn after it hides in part ([visual-communication:DEC-037-text-the-page-hides] point 1).
- **The reviewer** is the capability's agent that reads the images, the frames and the report, and reports what no check measures (DEC-015 point 7). It runs no command that could verify a key (DEC-030 point 7).

The findings record does not describe the pages the reviewer sees. It holds the last render's findings, while the frames show the scenes the step computed from the files as they stand. The two part whenever the files change after a render: a look that follows an edit with no render between, or a build pipeline's drawings of one commit beside a working tree's record. They part across releases too. The key holds no version of the engine, so a record written before the checks of boxes still verifies, and holds none of their findings. They part even with no file changed, since the step's scenes fill the real number and date where the record's take the stand-ins. The reviewer can tell none of these cases. The capability's list of checks cannot tell it either, since it says what the installed release ships, not what ran on the scenes drawn.

## Decision

**The viewing step's report gives every scene finding on the scenes its images were drawn from, image by image, computed by the code a render runs. The reviewer reads what any check found from that report alone, and reads a check's silence at a place as judged and clean only where the check judges that kind of place.**

### 1. The report gives every scene finding on what the images show

- **What it gives.** For each image of the run, the report gives the scene findings on the scene the image was drawn from. The step computes them with the code a render runs over the scenes it computes, run here over the step's own scenes, the ones the frames come from. So what the report says of the checks, and what the images show, are always one state of the piece, whatever changed since a render.
- **Every check's, with no class.** It gives the findings of every check that runs on a scene, and picks none out. Calling the one code a render calls binds no check to the step, and a new check reaches the report as it reaches a render.
- **The unit is the image.** Each finding is named by the language, the key and, where its place lies on one, the page of the image it holds for, and under a forced palette by that palette too, as the report's other entries are named. A band is read as its page. So a finding of the layout, which holds for every key of one size, is given under each key of that size the run drew. A finding of colour is given under its own key alone. A finding whose place lies on no page, such as content a size hides, is given for the scene's images without a page. One on a page the run did not draw is not given, since no image of the run shows it.
- **Given once.** A finding the report already lists in an entry of its own, such as a loss in its list of losses, is not given again.
- **One difference from a render: the cover.** The check of boxes that overlap leaves out a text the report names as covered, so that one defect is not shown twice. On a render it can only approximate that, since no check reads the report (DEC-015 point 1). The step holds its own covered entries before it computes the findings, so it hands them to the code in place of the approximation. It leaves out an overlap of two siblings only where a covered entry of the same image names the one drawn under, or a text it holds, and names as its cover the one drawn over, or a part it holds. Where a covered entry names no cover, the step leaves out no overlap of that text, so the place may show twice and is never hidden. Through the SVG renderer the report reads no cover, so the step leaves out none.
- **Which release.** The report names the capability's version whose code computed its findings.
- **Where computing them stops.** Where the checks' code stops on a scene, the step still draws its images. The report says, for each image of that scene, that no check judged it, and why.
- **Whatever the piece's state.** The step gives them for a final piece too, since they describe what its images show as the engine draws them today. That judges nothing of the piece for validation, which computes no final piece's scenes (DEC-002 point 7).

### 2. A check's silence is read only where it judges

- **Each check's entry says where it judges.** A check's entry in the capability's list of checks says which kinds of place it judges, and which it leaves out. For example, the checks of boxes compare only siblings, the parts one group holds directly, and leave out lines and arrows (DEC-046 point 3).
- **Where it could judge nothing, it says so.** At a place of a kind it judges, a check that can judge nothing there states that as a fact, at that place, with the reason. The check of edges that nearly line up states it at a key whose brand gives no step of space, where nothing is near. Such a statement is a finding like any other, so validation states it, and the report gives it. DEC-046 point 5 has the check of a text's size do so, and this point has every check do so.
- **How the reviewer reads a check's silence:**
  - **Judged and clean:** a place of a kind the check's entry says it judges, where the report gives, for that image, no finding of the check there and no statement that it could judge nothing there.
  - **Not judged:** every other place. That takes in a kind of place the entry leaves out, such as two parts of different groups, or a line, for the checks of boxes, and a place where the check states that it could judge nothing. It also takes in each image the report says no check judged, and every image the report does not give.
  - **From the list of the version that ran.** The reviewer reads each entry from the list of checks of the version the report names. Where the capability it reads is of another version, it reads every place of those images as not judged, and reads only the findings the report gives.
- **Where a check did not judge,** the reviewer does what the record that decides the check says for that case. For the checks of boxes it reads the offsets and the overlaps from the frames (DEC-046 point 3). For a check of a text's size, its report names the gap (DEC-046 point 5).

### 3. The reviewer reads what any check found from the report alone

- **Never from the findings record.** The reviewer reads what any check found from the report of the run whose images it reads. It never reads it from the findings record, which holds the last render's scenes, under a key it cannot verify.
- **One run's images.** A report speaks for the images of its own run alone. For any other image, such as one a session hands the reviewer beside the step's (DEC-015 point 7), the reviewer reads no check as having judged it. A build pipeline's drawings are a look's folder, report and all, so their report speaks for their images, at the commit drawn ([visual-communication:DEC-024-outside-programs-sandbox] point 5).
- **What it reads there:**
  - **The places the checks of boxes name,** each judged on the image as DEC-046 point 3 says, and where neither judged, the frames.
  - **A part a size hides.** A part the report gives as hidden by its size at the image's key is no part missing, since its component hides it there (DEC-021 point 5). Any other part missing on the image is the fault of a part missing.
  - **A drawing that disagrees with a passing check.** A check passed a place where it judged it and found nothing, as point 2 reads it. Where the page shows a fault there all the same, such as a text that leaves its box with no finding that it does, that is the fault of such a drawing. Where the check did not judge the place, the fault the page shows is of its own kind, and blames no check.
  - **A fault a check already reports,** named in one line (DEC-030 point 7), where the report gives that check's finding.
- **A place validation names and the report does not.** A finding of the checks of boxes in validation asks the reviewer for attention. The reviewer gives it on a look's images, whose report gives each such place on what they show. A place validation names that the report does not lies on no image the reviewer reads: the files changed since the render, the facts filled differ, or the report names the text as covered. So the reviewer judges the places the report gives.
- **The findings record stays the check's.** It keeps what a render found, for the check, as DEC-005 point 13 decides, and gains no field.
- **The report stays no record of findings.** It lies in the clone's local folder, nothing commits it, and no check reads it (DEC-015 points 1 and 4).

## Rationale

**Why the report, and not the findings record.** The step computes the scenes it draws, so the checks' findings on them cost only the checks' arithmetic, and describe the images exactly. A field in the findings record could say only which checks the last render ran, on files that may have changed since. With the report, nothing has to be kept in step: no field, no rule for reading a record a release wrote before a check existed, and no render to ask for first. The look a calibration runs gives the findings of the release it runs on, too ([visual-communication:DEC-042-grades-bar-and-loop] point 9).

**Why every check's findings, and no class of checks.** The reviewer reads what a check found in many places. These include the places the checks of boxes name, a part a size hides, a drawing that disagrees with a passing check, a text's size, and a fault a check already reports. A rule that carried only some checks would leave the rest on a stale record. The finding of content a size hides shows the risk. Out of date, it says a part is hidden when it is missing, or misses a part hidden since, so the reviewer passes a fault or names one that is not there. A test that picks the checks the reviewer relies on can also misjudge a check. Calling the one code a render calls gives every finding, and binds no single check to the step.

**Why a check's silence is read only where it judges.** A check that judged a scene names nothing at a place it never compares. Take a header group holding a title and a body group holding a paragraph, whose groups' left edges agree, the title set 0 px in and the paragraph 3 px. The checks of boxes compare the two groups, and the parts inside each only with each other, so they never compare the title with the paragraph. A reviewer that read their silence as "judged" would do no sums there, and pass an offset across groups, the craft the first calibration found the review weak on (DEC-046, Context). A line that stops 2 px short of its end fails the same way. So the reviewer reads silence per check and per place, against what each check's entry says it judges.

**Why a check states where it could judge nothing, in validation too.** The check of edges that nearly line up judges nothing where the brand gives no step of space, since nothing is near without one. Told only that it found nothing, a reviewer would skip the sums there. The statement is the check's own finding, made by the code a render and the step both run, so validation and the report agree. A person who runs the check sees it too. A fact asks no act, so it fails nothing.

**Why the image is the unit.** A finding of the layout holds for a size, and one of colour for a key. A covered entry, which decides what the step leaves out of the overlaps, differs by key and by forced palette (DEC-037, Context). The reviewer reads one image at a time, a forced image among them, for a part missing or blank. So the report gives each image what holds for it, and repeats a finding where it holds for several.

**Why in the report, and not in each image's frames.** An image's frames file names the image too. But a band has frames of its own, so a page's findings would repeat in each band's file. Frames are in the image's pixels, and findings in px of the page. A finding whose place lies on no page, such as content a size hides, has no image to lie beside. The report is already where the step gives what it found, each entry by language, key and page, and the list of images the reviewer takes.

**Why the step leaves out only an overlap its report names as a covered text and its cover.** One defect shown twice costs the reader a line. One left out of both lists is seen by no one. The step holds its covered entries, so where an entry names the cover it leaves out exactly that pair. Where it cannot tell the cover, as where two parts drawn after a text both meet the ink the page hides, leaving out every overlap of that text could hide one the report does not name. So it leaves out none.

**Why the report names its version.** The reviewer reads where each check judges from the list of checks it has. A pipeline's drawings of an older commit, or a folder an older release left, may come from a release whose checks judge otherwise, or one with no check of a text's size. Told the version, the reviewer reads such images as not judged rather than read another release's silence by this one's list.

**Why the step draws where the checks' code stops.** The images still show the page, and the reviewer, told that no check judged them, does its own sums and names its gaps. A look that drew nothing would leave the designer nothing to see.

### What it costs

- **Findings shown twice.** A place the checks name shows in the check's findings, at a render, when a person runs the check and in validation, and again in the report. A person who reads both reads it twice. The report grows too: a finding of the layout repeats under each key of its size and each forced palette drawn.
- **Two answers that may differ,** for three causes. The files changed between a render and a look. The step's scenes fill the next number and the date of the run where the record's take the stand-ins, so with no file changed a fact's text has another width, and its boxes and findings may differ from one day to the next. The step leaves out what its covered entries name, where a render approximates. Each answer is true of its own scenes, and the reviewer reads only the report, so it never chooses between them. The render already prints what the previews' scenes find that the stand-ins do not, and keeps none of it (DEC-016 point 5), so the report gives what a render prints, and more.
- **The step's work.** Each look does the checks' arithmetic, over the scenes it computes anyway.
- **One version, two codes.** Where the capability is authored, two commits of one version may hold checks that judge otherwise. A pipeline there draws the change's own commit, and a look's folder holds the run the session just made, so the reviewer reads them with the list of the code that ran, as long as it reads the change's own tree.

### Alternatives considered

- **A field in the findings record naming the checks that ran.** Rejected. The record holds the last render's findings, and the frames show the files as they stand. Where the two part, the field still names the checks, so it tells the reviewer they judged a layout they never measured, and the reviewer, which verifies no key, would skip the sums there. It would also add a committed field, a rule for which checks it names and a rule for reading a record without it.
- **That field, with the report saying whether the findings record matches what the step drew.** Rejected. Where the record matches, the report tells the reviewer no more than its own findings would. Where it does not, as after any edit not yet rendered, or with any fact the preview fills, the reviewer falls back to its own sums, which the checks exist to spare it (DEC-046 point 3). It keeps a field and a comparison, to give less.
- **The session renders before each look.** Rejected. A render of a draft moves its lock and rewrites a committed file ([visual-communication:DEC-003-change-over-time] point 8, DEC-005 point 13), which the viewing step exists to avoid (DEC-015 point 1). The reviewer could not confirm that the render happened, and a pipeline's drawings of one commit would still lie beside a working tree's record.
- **The reviewer reads the capability's list of checks alone,** as DEC-046 point 5 has it for a text's size. Rejected. The list says what the installed release ships, not what judged the scenes drawn. Read beside the report's version, it says where each check judges (point 2), never whether one judged these images.
- **Only the checks whose judgement stands in for part of the reviewer's reading.** Rejected. Its test took in checks it named as outside it, such as a text that leaves its box, and left out one it needed, the finding of content a size hides. So such a finding stayed on a stale record, or read as never judged, which made every part hidden on purpose a fault.
- **The checks of boxes in the report alone.** Rejected. They are checks, run on every render (DEC-046 point 3), so a person sees each place at a render and in validation, with nothing drawn. Moving them into the step would overturn that point.
- **Each image's findings in its frames file.** Rejected, for the reasons above: findings repeated in each band, two units in one file, and no home for a finding on no page.
- **The step leaves out overlaps as a render's check does.** Rejected. The check guesses from the scene which texts the report names covered. It may leave out an overlap the report does not name, which no one would then see, or give one the report names, twice.
- **No look where the checks' code stops.** Rejected: the images still show the page.
- **The report names each check it ran.** Not needed. The step runs every check a render runs, so the version names them, and a scene where the code stopped is named apart.
