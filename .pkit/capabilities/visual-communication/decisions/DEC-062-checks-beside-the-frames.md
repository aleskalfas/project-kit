**In plain terms:** the graphic-design reviewer leaves to the checks what they measure. Where the checks of boxes judged a place, it does no sums over the frames. A part a size hides is no part missing. A drawing that shows a fault a check passed is a fault of its own. So the reviewer must know what the checks found on the very pages it sees. A piece's findings record cannot tell it: it holds what the last render found, on scenes that may differ from the ones drawn. So the viewing step runs the checks a render runs on a scene, over scenes it computes from the files as they stand, and its report gives each image the findings that hold on it. For each image the report names the checks that judged it, and it carries what each judges, as the code that ran states it. The reviewer reads what any check found from that report alone, and reads a check's silence there as [visual-communication:DEC-063-where-a-check-judges] says. No check leaves out an overlap because the report names a covered text: the reviewer reads such an overlap as the covered text's fault. The review's calibration waits for this report.

## Context

[visual-communication:DEC-046-faults-lower-grades] point 3 adds two checks that measure the boxes of siblings: edges that nearly line up, and boxes that overlap. Where they ran, the reviewer does no sums over the frames, and where they did not, it reads the offsets from the frames. The point does not say where the reviewer learns which holds. Point 5 of the same record has a like need for a check of a text's size, which the capability does not ship yet, and has the reviewer tell from the capability's list of checks whether one exists. The reviewer reads what a check found in three more places, today from the piece's findings record: a part a size hides is no part missing ([visual-communication:DEC-021-size-and-shape] point 5), a drawing that shows a fault a check passed is a fault, and a fault a check already reports is named in one line ([visual-communication:DEC-030-design-agents] points 6 and 7). How a check's silence is read, place by place and check by check, is DEC-063's.

The words it uses:
- **The viewing step** draws a piece's pages as images, in the clone's local folder. Beside them it writes the *frames*, each drawn element's box in the image's pixels, and a *report* ([visual-communication:DEC-015-viewing-step-and-reviewer]). It computes the piece's *scenes*, its pages as the engine lays them out, from the files as they stand, under the piece's lock (DEC-015 point 4). The frames are the boxes of those scenes. Its scenes fill an export's facts as a preview's do, with the next number and the date of the run ([visual-communication:DEC-016-what-an-export-reads] point 5).
- **A key** names one combination of a piece's modes ([visual-communication:DEC-004-brands-and-notations] point 3). A scene is computed at one *key over the size axes*, its sizes alone, and serves each key that adds to it the modes of the other axes, such as light and dark (DEC-004 point 2).
- **A check** is a measurement a command makes on every render, with no judgement ([visual-communication:DEC-002-files-and-validation] point 7). Its *label* is the name its findings carry. **The capability's list of checks** is its page that lists each check and its findings. A check's *reach* is the kinds of place it judges and those it leaves out, which its entry there states (DEC-063 point 1).
- **The scene findings** are what the checks that run on a scene find, such as boxes that overlap, a text that leaves its box, or content a size hides. Other checks run on no scene, such as a check of content against the components it fills, of a lock, or of the record a produced picture keeps.
- **The findings record** is the file each render of a piece that is not final keeps beside the piece, holding its scene findings. Its scenes take *stand-ins*, fixed texts measured in place of an export's number and date (DEC-016 point 5). Its key fingerprints every file the scenes were computed from, and the check reads it while the key verifies against the files ([visual-communication:DEC-005-engine-and-plugins] point 13).
- **A place** is what a finding names in one scene: an element, a pair or group of elements, or content (DEC-063, Context).
- **A covered entry** is an entry of the report's list of texts the page does not show, for a text a part drawn after it hides in part ([visual-communication:DEC-037-text-the-page-hides] point 1).
- **A forced image** is one the step draws under a browser's forced palette, the colours a browser gives a page under forced colours ([visual-communication:DEC-027-forced-colours-viewing]).
- **The reviewer** is the capability's agent that reads the images, the frames and the report, and reports what no check measures (DEC-015 point 7). It runs no command but a read-only query (DEC-030 point 7), so it verifies no key.

The findings record does not describe the pages the reviewer sees. It holds the last render's findings, while the frames show the scenes the step computed from the files as they stand. The two part whenever the files change after a render: a look that follows an edit with no render between, or a build pipeline's drawings of one commit beside a working tree's record. They part across releases too. The key holds no version of the engine, so a record written before the checks of boxes still verifies, and holds none of their findings. They part even with no file changed, since the step's scenes fill the real number and date where the record's take the stand-ins. The reviewer can tell none of these cases. The capability's list of checks cannot tell it either, since it says what the installed release ships, not what ran on the scenes drawn.

## Decision

**The viewing step's report gives each image the scene findings that hold on it, computed by the code a render runs, and names the checks that judged each image, with each check's reach as the code that ran states it. The reviewer reads what any check found from that report alone. The calibration waits for it.**

### 1. The report gives each image the findings that hold on it

- **From the step's own scenes.** The step computes the scene findings with the code a render runs, over scenes it computes itself from the files as they stand, under the piece's lock, filled as its images are (DEC-016 point 5). So what the report says of the checks, and what the images show, are always one state of the piece, whatever changed since a render.
- **Every scene a check reads.** For its findings, the step computes each key over the size axes of each language it draws, as a render does, not only the keys it draws, since a check may compare a piece's sizes, as the finding of content a size hides does. Where a check compares the scenes of several languages, it computes theirs too. So each finding is the one a render would give for the files as they stand. The step still draws only what its caller asked for.
- **Every scene check's, with no class.** The report gives the findings of every check that runs on a scene, and picks none out. Calling the code a render calls binds no check to the step, and a new check reaches the report as it reaches a render. A check that runs on no scene is not the step's to run, and the report gives none of its findings.
- **Each image, only what holds on it.** Each finding carries, as data, its language, the key it holds for and its page, where its place lies on one. The key is a key over the size axes for a finding of the layout, and a whole key for one that holds for one combination of modes, such as a text's contrast. The step gives each image the findings of its language that hold for its key, whether for the key over the size axes its scene was computed at or for the whole key, on its page or on no page. A band is read as its page. A finding on a page the run did not draw is given to no image.
- **These data stop at the report.** A render's code gives once a finding read alike on several pages, at every key, or in several languages, and the findings record keeps that form. The step gives each image its own finding, and the record gains no field.
- **A forced image** is given the findings of its language, its key over the size axes and its page, and none that holds for one combination of modes. It keeps its key's layout, and its colours are the forced palette's, which no check measures (DEC-027 point 6).
- **Given once.** A finding the report lists in an entry of its own, such as a loss in its list of losses, is not given again.
- **Every overlap.** Neither the step nor a render leaves out an overlap of two siblings because a covered entry names a text one of them holds. The report gives the overlap and the covered entry, each as its check finds it. How the reviewer reads the two is point 3's.
- **Where computing them stops.** Where the checks' code stops on a scene, the step still draws its images. The report says, for each image of that scene, that no check judged it, and why.
- **Whatever the piece's state.** The step gives them for a final piece too, since they describe what its images show as the engine draws them today. That judges nothing of the piece for validation, which computes no final piece's scenes (DEC-002 point 7).

### 2. The report names the checks that judged each image, and what each judges

- **For each image, the checks that judged it.** The report names, by its label, each check that judged the image: each check that runs on the image's scene, where the checks' code did not stop on it. On a forced image it leaves out a *check of colour*, one whose findings hold for one combination of modes. A check that runs on no scene judged no image, and the report names it for none.
- **Each check's reach, from the code that ran.** For each check it names, the report carries the check's reach, as the code that ran states it. A check's code states its reach in the words of its entry in the list of checks (DEC-063 point 1), and a test holds the two equal.
- **The release.** The report names the capability's version that ran, so that whoever reads it can tell which release drew the findings. No reader reads a check's reach from it.

### 3. The reviewer reads what any check found from the report alone

- **Never from the findings record.** The reviewer reads what any check found from the report of the run whose images it reads. It never reads it from the findings record, which holds the last render's scenes, under a key it cannot verify.
- **One run's images.** A report speaks for the images of its own run alone. For any other image, such as one a session hands the reviewer beside the step's (DEC-015 point 7), the reviewer reads no check as having judged it. A build pipeline's drawings are a look's folder, report and all, so their report speaks for their images, at the commit drawn ([visual-communication:DEC-024-outside-programs-sandbox] point 5).
- **A check the report does not name for an image did not judge it.** That takes in every check that runs on no scene, a check of colour on a forced image, and every check on an image whose scene the checks' code stopped on. It takes in every check on each image of a report that names no check, such as one a release wrote before this record, and every check on an image the report does not list among its images.
- **A check's silence,** on an image the report names it for, is read as DEC-063 point 3 says, by the reach the report carries for that check, never by the entry of the list of checks the reviewer has at hand.
- **What it reads there:**
  - **The places the checks of boxes name,** each judged on the image as DEC-046 point 3 says, and where a check did not judge, the frames, as DEC-063 point 4 says.
  - **A part a size hides.** A part the report gives as hidden by its size at the image's key is no part missing, since its component hides it there (DEC-021 point 5). Any other part missing on the image is the fault of a part missing.
  - **A drawing that disagrees with a passing check.** Where a check the report names for the image judged a place and found it clean, and the page shows a fault there all the same, such as a text that leaves its box with no finding that it does, that is the fault of such a drawing. Elsewhere the fault the page shows is of its own kind, and blames no check (DEC-063 point 4).
  - **A fault a check already reports,** named in one line (DEC-030 point 7), where the report gives that check's finding.
  - **An overlap of a covered text.** Where the part drawn under, in an overlap the report gives, is or holds a text that a covered entry of the same image names, the reviewer reads the covered text as that entry's fault alone, a part missing, as it reads a text another text covers. What else the overlap hides, such as a picture, stays its to judge on the image (DEC-037 point 4).
- **A place validation names and the report does not.** A finding of the checks of boxes in validation asks the reviewer for attention. The reviewer gives it on a look's images, whose report gives each such place on what they show. A place validation names that the report does not lies on no image the reviewer reads: the files changed since the render, or the facts filled differ. So the reviewer judges the places the report gives.
- **The findings record stays the check's.** It keeps what a render found, for the check, as DEC-005 point 13 decides, and gains no field.
- **The report stays no record of findings.** It lies in the clone's local folder, nothing commits it, and no check reads it (DEC-015 points 1 and 4).

### 4. The calibration waits for the report

A check the reviewer's body is written to read has landed for a calibration of [visual-communication:DEC-042-grades-bar-and-loop] point 9 only once the viewing step's report gives its findings and its reach, since the reviewer reads every check from there. So the calibration DEC-046 point 8 holds back waits for this report too.

## Rationale

**Why the report, and not the findings record.** The step computes scenes from the files as they stand, so the checks' findings on them cost only the scenes and the checks' arithmetic, and describe the images exactly. A field in the findings record could say only which checks the last render ran, on files that may have changed since. With the report, nothing has to be kept in step: no field, no rule for reading a record a release wrote before a check existed, and no render to ask for first. The look a calibration runs gives the findings of the release it runs on, too (DEC-042 point 9).

**Why every scene check's findings, and no class of checks.** The reviewer reads what a check found in many places. These include the places the checks of boxes name, a part a size hides, a drawing that disagrees with a passing check, a text's size, and a fault a check already reports. A rule that carried only some checks would leave the rest on a stale record. The finding of content a size hides shows the risk. Out of date, it says a part is hidden when it is missing, or misses a part hidden since, so the reviewer passes a fault or names one that is not there. A test that picks the checks the reviewer relies on can also misjudge a check.

**Why every key over the size axes, and not only the keys drawn.** A look draws one key by default. Content a size hides is found by comparing a language's sizes, so computed at one key it finds nothing, and every part a phone hides on purpose would read as a part missing. A finding of content a size hides, or of a top as wide at one size as at another, is a render's only because a render computes every size. So the step computes what a render computes for each language it draws, and draws only what it was asked.

**Why the image is the unit, and why the data stop at the report.** A finding of the layout holds for a key over the size axes, and one of colour for a whole key. The reviewer reads one image at a time, a forced image among them, for a part missing or blank. A render gives once a finding read alike on several pages, at the first page, so a report that copied that form would give the second page's place nothing, and the reviewer would read it as judged and clean (DEC-063 point 3). The findings record keeps that form, since validation reads it whole, so the data that tell each image apart stop at the report.

**Why no check of colour on a forced image.** A forced image is named by the key its page file holds for the palette, so a dark key's findings of contrast would land on the dark forced image, drawn in the browser's colours. A text that fades there would then read as a drawing that disagrees with a passing check of contrast, which never measured those colours. Its colours are the browser's, so no finding on it rests on a brand's colour or sets it against the check (DEC-027 point 6).

**Why no overlap is left out.** One defect shown twice costs the reader a line. One left out of both lists is seen by no one. A render cannot read the report (DEC-015 point 1), so a leave-out there can only guess from the scene which texts the report names, and the guess leaves out overlaps the report does not name, as where a sibling lies over the space between two words of a line. The step holds its covered entries, but an entry names the covered text and its share, not the part that covers it, so the step could not tell which pair to leave out. And a pair left out would read as judged and clean by the check of boxes that overlap, while the page shows the overlap, so the reviewer would blame a check that did as it was told. The reviewer already reads a text another text covers as the covered entry's fault alone, so it reads an overlap of a covered text so too.

**Why the report carries each check's reach, and not only the version.** The reviewer must know, for each check, which kinds of place it judged (DEC-063 point 3). Given only the version, it would read the reach from the list of checks it has. That list is of one version, so it could read no image an older release drew, and a report that named no version would have to be told apart by a rule. Where the capability is authored, a version moves only at a release, so every commit of a branch shares one version while a check's reach changes: a pipeline's drawings of one commit, read with the list of another, would read one release's silence by another's reach. Carried in the report from the code that ran, the reach is that of the code that judged, at any version and any commit. A report that carries none, as an older one, names no check, and so reads as judged by none. The cost is that each reach is stated twice, in the check's code and in its entry, and a test holds them equal.

**Why the report names the release too.** It is what identifies the code that ran for a person who reads the report, and costs one field. The reviewer reads no reach from it, for the reasons above.

**Why in the report, and not in each image's frames.** An image's frames file names the image too. But a band has frames of its own, so a page's findings would repeat in each band's file. Frames are in the image's pixels, and findings in px of the page. A finding whose place lies on no page, such as content a size hides, has no image to lie beside. The report is already where the step gives what it found, each entry by language, key and page, and the list of images the reviewer takes.

**Why the step draws where the checks' code stops.** The images still show the page, and the reviewer, told that no check judged them, does its own sums and names its gaps. A look that drew nothing would leave the designer nothing to see.

### What it costs

- **Findings shown twice.** A place the checks name shows in the check's findings, at a render, when a person runs the check and in validation, and again in the report. A person who reads both reads it twice. The report grows too: a finding of the layout repeats under each key and each forced palette drawn. An overlap of a covered text shows both as an overlap and as a covered entry, which the reviewer reads as one defect.
- **Two answers that may differ,** for two causes. The files changed between a render and a look. Or the step's scenes fill the next number and the date of the run where the record's take the stand-ins, so with no file changed a fact's text has another width, and its boxes and findings may differ from one day to the next. Each answer is true of its own scenes, and the reviewer reads only the report, so it never chooses between them. The render already prints what the previews' scenes find that the stand-ins do not, and keeps none of it (DEC-016 point 5), so the report gives what a render prints, and more.
- **The step's work.** Each look computes every key over the size axes of each language it draws, more scenes than a look of one key draws, and does the checks' arithmetic over them.
- **Each reach stated twice,** in the check's code and in its entry, with a test that holds them equal.

### Alternatives considered

- **A field in the findings record naming the checks that ran.** Rejected. The record holds the last render's findings, and the frames show the files as they stand. Where the two part, the field still names the checks, so it tells the reviewer they judged a layout they never measured, and the reviewer, which verifies no key, would skip the sums there. It would also add a committed field, a rule for which checks it names, and a rule for reading a record without it.
- **That field, with the report saying whether the findings record matches what the step drew.** Rejected. Where the record matches, the report tells the reviewer no more than its own findings would. Where it does not, as after any edit not yet rendered, or with any fact the preview fills, the reviewer falls back to its own sums, which the checks exist to spare it (DEC-046 point 3). It keeps a field and a comparison, to give less.
- **The session renders before each look.** Rejected. A render of a draft moves its lock and rewrites a committed file ([visual-communication:DEC-003-change-over-time] point 8, DEC-005 point 13), which the viewing step exists to avoid (DEC-015 point 1). The reviewer could not confirm that the render happened, and a pipeline's drawings of one commit would still lie beside a working tree's record.
- **The reviewer reads the capability's list of checks alone,** as DEC-046 point 5 has it for a text's size. Rejected. The list says what the installed release ships, not what judged the scenes drawn.
- **The report names the version alone, and the reviewer reads each reach from the list of that version.** Rejected, for the reasons above: the reviewer holds one version's list, and in the repository the capability is authored in, one version spans commits whose checks judge otherwise.
- **The step computes only the scenes it draws.** Rejected: a look of one size would find no content a size hides, and every part hidden on purpose would read as missing.
- **Only the checks whose judgement stands in for part of the reviewer's reading.** Rejected. Its test took in checks it named as outside it, such as a text that leaves its box, and left out one it needed, the finding of content a size hides. So such a finding stayed on a stale record, or read as never judged, which made every part hidden on purpose a fault.
- **The checks of boxes in the report alone.** Rejected. They are checks, run on every render (DEC-046 point 3), so a person sees each place at a render and in validation, with nothing drawn. Moving them into the step would overturn that point.
- **Each image's findings in its frames file.** Rejected, for the reasons above: findings repeated in each band, two units in one file, and no home for a finding on no page.
- **The step leaves out an overlap of a covered text, with the cover the browser tells.** Rejected. It needs a read of the browser no probe has measured, as DEC-037 point 5 has each of its reads planted, and a pair left out would still read as judged and clean where the page shows its overlap.
- **The step leaves out overlaps as a render's check does.** Rejected. The check guesses from the scene which texts the report names covered. It may leave out an overlap the report does not name, which no one would then see.
- **No look where the checks' code stops.** Rejected: the images still show the page.
