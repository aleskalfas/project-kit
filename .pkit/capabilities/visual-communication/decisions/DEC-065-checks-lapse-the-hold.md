**In plain terms:** the graphic-design review reads what the checks found, and grades two rules by where they measured. A change to a check, such as a new threshold, can move those grades in every project, as a reworded rule does. So such a change lapses the hold, as a change to the rules' text, the reviewer's definition, the design knowledge or the model does. A check that lands after a calibration then lapses that calibration's hold, so a calibration need not wait for each check to land, as the record of how faults lower grades had it wait ([visual-communication:DEC-046-faults-lower-grades] point 8). This record overturns that wait: waiting becomes a matter of economy, not of safety. The command that gives the verdict sees a change to a check by two digests: one of the capability's code, where each check's code, its own values and its reach lie, and one of its list of checks. A check's code cannot be told apart from the rest of the code file by file, so the code's digest takes all of it, and any change to the code lapses the hold. A hold therefore lasts only while the code stays as it was calibrated, and a calibration pays best on code that is to ship and stay.

## Context

[visual-communication:DEC-042-grades-bar-and-loop] point 9 lapses the hold on anything that could move the grades, and lists what the command that gives the verdict compares with the accepted data: a new major of a covered set, the covered rules' text, the reviewer's definition and the design knowledge, and the model and effort the review ran on. That list names no check.

The review reads what the checks found:
- **The checks of boxes.** It grades `RS-GRAPHIC-002` by the places the check of edges that nearly line up and the check of boxes that overlap name, and does its own sums over the frames where they did not measure (DEC-046 point 3).
- **The check of a text's size.** It grades `RS-GRAPHIC-005` by whether such a check measured a text: where one did, a text under its medium's minimum is the check's finding alone (DEC-046 point 5).
- **Every scene check.** It reads the findings of each, and each one's reach, from the viewing step's report, which computes them by the code a render runs ([visual-communication:DEC-062-checks-beside-the-frames] points 1 to 3). It reads a check's silence by that reach ([visual-communication:DEC-063-where-a-check-measures] point 3).

So a change to a check, such as a new threshold, a new medium's minimum or a new clause of its reach, moves the grades in every project that has the capability. DEC-062's Implications say that, by DEC-042 point 9, the step's code that computes and gives the checks' findings, each check's reach and its statements lapse the hold, whichever command compares them. The command compares none of them. DEC-046 point 8 has a calibration wait for each check the reviewer's body is written to read for that reason: a check that landed after a calibration was accepted would not be seen, and the verdict would go on ending loops for a review that does not run as it was measured. The calibration that is to run next ([project-kit#3230](https://github.com/aleskalfas/project-kit/issues/3230)) waits so for the check of a text's size ([project-kit#3185](https://github.com/aleskalfas/project-kit/issues/3185)).

The words it uses:
- **The hold** is the switch by which the verdict read from the review's grades ends the designer's loop at a project's bar. It is on only where whoever maintains the capability has accepted a calibration's report, and while nothing DEC-042 point 9 names has *lapsed* by differing from the accepted data (DEC-042 points 9 and 10). Where it is off, the verdict informs, and the designer's loop ends after two rounds and the person ([visual-communication:DEC-030-design-agents] point 2).
- **A calibration** is a run of the review on a held-out ladder an outside judge ranked first, read against conditions fixed before it runs (DEC-042 point 9).
- **The accepted data** is the values the change that records a calibration's acceptance writes, which the capability ships (DEC-042 point 9, "Where what was calibrated lives"). **The command** is the capability's command that gives the verdict, and compares those values with the same values as they stand.
- **A digest** is a SHA-256 of what it names, the digest the deploy computes for an agent's definition, which DEC-042 point 9 has the command take of the reviewer's definition and of the design knowledge.
- **A scene check** is a check whose findings come from computing a scene. Its *reach* is the kinds of place it measures and leaves out, and its *statements* are the facts it states where it could measure nothing (DEC-063 points 1 and 2).
- **The capability's list of checks** is its page that lists each check and its findings, `checks.md`. Each row is a check's *entry* (DEC-063, Context).
- **The capability's code** is the program files its commands run: each command's own file, the modules they share and the plugins they load. Every one of them lies in the capability's scripts folder, where a capability keeps its runtime tools ([COR-017](../../../decisions/core/COR-017-capability-pattern.md)), since only the capability ships plugins ([visual-communication:DEC-005-engine-and-plugins] point 12). Its documents, data, schemas, rule sets, libraries and agents are not code.
- **A dependency** is outside code a script names in its header, with the version it takes, such as the code that shapes a text or draws an image. It is none of the capability's libraries.
- **The reviewer's body** is the reviewer's definition, the file of instructions it works by (DEC-046, Context).

## Decision

**A change to a check the review reads lapses the hold. The command sees it by a digest of the capability's code and a digest of its list of checks. So a calibration need not wait for a check to land: waiting is a matter of economy.**

### 1. The checks the review reads lapse the hold

- **Which checks.** Every scene check, since the viewing step's report gives the findings of each, and the review reads what any check found from that report (DEC-062 points 1 and 3). With them go the step's code that computes and gives their findings, each check's reach and its statements (DEC-063 points 1 and 2), and each one's entry in the list of checks, which the review reads for what a check means.
- **What they do not take in.** A check that runs on no scene gives the report nothing, so the review reads none of its findings, and it is not among them. A change to its code lapses the hold all the same, since point 2's digest sees it.
- **Joined to the list of DEC-042 point 9.** That point's list of what lapses the hold gains an item of its own, the capability's code and its list of checks, each by point 2's digest, and its other items stand. The command compares the two digests with the accepted data, as it compares the rest, and says which differs.

### 2. The command sees a change to them by two digests

- **The capability's code.** A digest of each program file in the capability's scripts folder: the SHA-256 of each file, by its path within that folder, as the design knowledge's digest is taken. Unlike that digest, which takes every file in its folder, a file the system writes there among them ([project-kit#3376](https://github.com/aleskalfas/project-kit/issues/3376)), it takes only the files written in the language the commands run in. So a compiled cache, a folder's marker or an editor's file beside the code lapses nothing, while a stray program file left in the folder lapses the hold, which is safe.
- **Held to the files the commands run.** The digest picks the program files by their language, and a test holds that choice to what it stands for: it fails where the capability ships, in its scripts folder, a file the digest leaves out that is not a folder's marker. So a program file of another kind fails the test in the change that brings it, and that change decides how the digest sees it. The record that would let a project add a plugin, at DEC-005 point 12's trigger to revisit, decides how the hold sees a program file of the project's.
- **What lies in it.** A check's code, each value of its own it measures by, its reach, its statements, and the step's code that computes and gives its findings all lie in those files, so the digest sees every change to them.
- **What else it stands for.** A check's code shares its files with the rest of the code, and calls code outside its own. So the digest stands too for the rest of the code that could move the grades, such as the engine that computes the scenes, the renderers that draw the images the review reads, the command that hands the review the brief's intent (DEC-042 point 4) and the command's own code that gives the verdict. It stands too for the version of each dependency a script pins in its header, such as one that shapes a text or draws an image. It sees changes that move no grade as well, such as a change to a command the review never reads through, and each lapses the hold too.
- **The list of checks.** A digest of the body of `checks.md`, after its front matter, as UTF-8, as a rule's text is digested. Its front matter says nothing of what a check means, so a change to it alone lapses nothing.
- **Where a check's values lie.** A check measures some places against a value, which lies in one of two places:
  - **the piece's,** where the piece's files fix it, or a version of a library its lock names, one the capability ships among them, such as its brand's smallest step of space (DEC-046 point 3). It is part of the piece the review reads, as its content is, and lapses nothing;
  - **the check's own,** such as the pixel of rounding by which the check of edges that nearly line up lets two values differ (DEC-046 point 3). It lies in the capability's code, where the digest sees it.

  A check takes a value from nowhere else: not from a project's configuration, and not from any other file the capability ships, such as a schema, a table, or a library's version that no lock of the piece names. A record that would have a check take one from there decides, in the change that lands it, how the command sees a change to that value. The record that decides a check says where each of its values lies, and whoever reviews a change that lands or alters a check holds it to that, as to the audit of its paths (DEC-063 point 1).
- **Written as the other values are.** The two digests are values of the accepted data, which only the change that records a calibration's acceptance writes (DEC-042 point 9). The command gives them as they stand, beside the other values it compares, so that change can take them from the state the calibration ran on. That change edits no program file and not the body of the list of checks, since an edit to either would make the state it lands differ from the data it writes, and the hold it records would lapse as it lands.

### 3. A calibration need not wait for a check

- **A check that lands later lapses the hold.** The change that lands a check changes the capability's code and its list of checks, and the change that teaches the reviewer to read it changes the reviewer's body. So each lapses the hold of any calibration accepted before it (DEC-042 point 9), until a calibration that read the check is accepted: one run once the check has landed for it, as DEC-062 point 4 says. Where the look, the review and the verdict run on one state of the capability, the verdict never ends loops for a review that reads a check its calibration did not, whichever lands first (Left open, "The code that ran").
- **So waiting is economy.** A calibration may run before each check the reviewer's body is written to read has landed. Its report says which checks ran, and where no text's size was compared (DEC-046 point 8). Whoever orders the work chooses whether it waits.
- **What each order costs.** A calibration's hold lasts at most until the next change to the capability's code, and a check that lands is one such change among many. A calibration run before a check lands buys a hold that lasts at most until the check lands, and the calibration that reads the check takes a fresh ladder and an outside judge again (DEC-042 point 9). Waiting spares that calibration only where the code is otherwise left as it is until the check lands. So the economy lies in calibrating on code that is to ship and stay, and waiting for a check known to be coming is one case of it. A hold reaches the projects that receive the capability only where no change to the code lands from the calibration's run to the release that ships its data (Rationale, "What it costs"). Either way, until a calibration that read the check is accepted, the verdict informs.

## Rationale

**Why a check lapses the hold as a rule does.** The review leaves to a check what it measures, and grades `RS-GRAPHIC-002` and `RS-GRAPHIC-005` by where the checks measured (DEC-046 points 3 and 5). A new threshold moves which places a check names. A new clause of its reach moves where the review does its own sums. Either moves the grades in every project that has the capability, as a reworded rule does, so it falls under DEC-042 point 9: anything that could move the grades lapses the hold.

**Why the whole code.** A check's code cannot be told apart from the rest of the capability's code file by file. The module that holds the capability's check gives the scene checks' findings beside the checks of files, and each check calls the code that computes a scene. The engine and the renderers, which draw the images the review reads, can move the grades as a check can. When this record was written, the viewing step ran 53 of the 92 program files, the renderers among them, and of the 106 changes to that code in the month before, 99 touched one of them. So a digest of the files the step runs would spare few lapses, and would need a list of files kept in step with what the step imports and loads. A digest of each check's own files, named in its code, would miss the code a check calls outside them, and the engine and the renderers. The whole code is the one set that neither a check's code nor the code that draws what the review reads can lie outside.

**Why the files are held to the role.** The code is what the commands run, and their language is what marks it today. A program file of another kind, picked by no digest, would move the grades unseen, which a digest exists to prevent. The test makes that addition fail in the change that brings it, rather than wait for a reader to notice, as point 2 makes a check's value taken from elsewhere wait for a record. Every program file lies in the scripts folder only while the capability alone ships plugins, so the record that opens plugins to a project reads this one again.

**Why the list of checks too.** The reviewer's body reads it for what each check means. A test holds each entry's reach equal to the reach its check's code states (DEC-063 point 1), so the code's digest sees a reach change. The rest of an entry, such as what a finding means, lies only in the list. Its front matter holds what no reader of a check reads, such as the paths whose change flags the page to be read again, so the digest takes the body alone, as a rule's text is taken from its set's body.

**Why a value of the piece's lapses nothing.** A calibration measures the review, on a ladder of pieces each under its own lock. A value the piece's files or its lock fix changes what the piece is, as its content does, and the review reads it as it reads the rest of the piece. A library's version that no lock of the piece names reaches no piece, so a check that read one would measure what the piece does not hold. Kept in the code, a value of the check's own is seen with the rest of the check. A value taken from anywhere else the command would not see, or a project could move from its configuration what was calibrated, so no check takes one without a record that says how the hold sees it. No test holds a check to this by the files it reads, since the piece's values lie in files too, so the record that decides the check, and the review of each change that alters it, hold it.

**Why waiting is economy.** DEC-046 point 8 had a calibration wait for each check because the command would not see the check land. Point 2 has it see the check, so a calibration accepted before a check holds at most until the check lands, and the verdict's safety rests on no order of the work. Where the look and the verdict run on different states of the capability, the command compares a code that may not be the one that drew what the review read (Left open). That gap is the same whichever order the work takes, so it moves nothing between the orders. The order still decides how many calibrations the work costs.

**Why DEC-046 point 8 is overturned in part, and not refined.** That point decides that a calibration runs only once each check the reviewer's body is written to read has landed, and rejects calibrating before the check of a text's size. This record decides that a calibration may run before, and takes the alternative that point rejected. Another record then decides otherwise than the point, so the point is overturned in part, as DEC-062 overturned point 5 of the same record. The rejected alternative's trigger to revisit names the work this record decides, and says that waiting then becomes economy. A trigger says when a choice is weighed again, and does not make the choice that replaces it a widening of the first. What point 8 decides beside the wait stands: which checks the reviewer's body is written to read, when one has landed for a calibration, the order of the rest of the work, and what a calibration's report says. The sentences of DEC-042 and DEC-062 that have a calibration wait for a check, or for the report that gives it, state the same wait in their own records, so they are overturned with it.

**What it costs.** Each change to the capability's code lapses the hold, and in the month before this record 106 of the 187 changes to the capability changed its code. In the repository the capability is authored in, a calibration's hold lasts until the next change to that code lands there. A project that receives the capability gets the hold only from a release that ships the code the calibration ran on, since the accepted data holds the digests of that state (point 2). Where a change to the code lands between the calibration's run and the release that ships its data, that release ships data its own code differs from, and no project that receives it gets the hold. So a hold reaches projects only where no change to the code lands from the calibration's run to the release, and lasts there until the next release that changes the code. Where each change to the code lands as soon as it is ready, a hold reaches projects only if those changes are held back for that span. Whether to hold them back, and for how long, the repository the capability is authored in decides, not this record. Keeping the hold in projects then costs one calibration for each release that changes the code, each with a fresh ladder and an outside judge (DEC-042 point 9), until a cheaper way to restore a hold the code alone lapsed is decided (Left open). A hold read once and taken to last would outlast what was calibrated, so whatever waits on the hold reads it as the command gives it at the time. Each lapse costs only the hold (DEC-042, "Why anything that could move the grades lapses the hold").

### Alternatives considered

- **A digest of the files the viewing step runs.** Not taken: when this record was written, the step ran 53 of the 92 program files, and 99 of the 106 changes to the code in the month before touched one of them, so it would spare few lapses, and it would need a list of files kept in step with what the step imports and the plugins it loads. Its trigger to revisit: the step comes to run a small share of the code, or the changes to the rest come to be many.
- **A digest of each check's own files, which its code names.** Rejected: a check calls code outside its own files, such as the code that computes a scene, and the engine and the renderers draw what the review reads, so a change there that moves the grades would go unseen. Its trigger to revisit: the code that computes what the review reads, the engine, the renderers and the checks among it, kept apart from the rest, so that a digest of it alone sees every change to it.
- **Each plugin's own version, for the renderers, beside a digest of the rest of the code.** Rejected: a plugin's version rises where the same input could give another output, and reference outputs pinned to it in the capability's tests catch a change made without one (DEC-005 point 9). Those outputs are the few the tests pin, so a change that moves an output they do not exercise raises no version and goes unseen, as on a piece shipped for the purpose. Its gain would be small too: it would spare only the lapses of the changes to the renderers that move none of their outputs.
- **Each check's reach alone.** Rejected: a reach says which kinds of place a check measures, not how. A new threshold or a new minimum leaves it as it is, and moves which places the check names.
- **A revision each check's author raises, or an answer each change owes on whether it moves what the review reads,** checked at review as a changeset's segment is. Rejected: one change that moves a check's findings, and raises no revision or answers no in error, leaves the hold on for a review that does not run as it was measured, and the review of that change may miss it. A digest misses no change, and a lapse costs only the hold.
- **The checks' findings on a piece the capability ships for the purpose.** Rejected: a change that piece does not exercise goes unseen, and the command would compute scenes to give a verdict.
- **The capability's version.** Rejected, as DEC-042 rejects it for the reviewer's definition: it moves with every release, the one that ships the accepted data included.
- **The digest of the code that ran, carried in the viewing step's report.** Not taken in this record: the command reads nothing of the round but the review's report, and where it would read such data is the question Left open names. Its trigger to revisit: a record decides where the command reads data of the round.
- **Every page the reviewer's definition says it reads, beside the code,** such as the outputs page and the review's schema, with the records left out, since the change that records an acceptance edits DEC-042, which the reviewer reads, and would lapse its own hold. Not taken in this record, which decides the checks: those pages are part of what else the review reads, which Left open leaves to a refinement that weighs them with the records and the outside programs. Its trigger to revisit: that refinement.
- **A digest of the whole folder the capability ships,** leaving out its records, a project's own files and the accepted data. Not taken in this record: it would take in, by a safe excess, the pages and schemas the review reads, and since the code's digest already lapses the hold on most changes, its added lapses would come mostly from changes to documents and libraries. But a library's version reaches a piece only through its lock, where it is the piece's (point 2), so the folder's digest would lapse the hold on changes no piece reads. And it would still leave out the records and the outside programs. Whether it serves is for the refinement Left open names, which weighs it with them. Its trigger to revisit: that refinement.
- **A digest of each program file in the accepted data,** so that the command names each file that differs. Not taken: only whoever maintains the capability answers a lapse, with a calibration, and the repository the capability is authored in keeps the change that recorded the acceptance, against which a comparison names the files. The data every project receives would hold an entry for each program file.
- **A calibration that waits for each check, as a condition.** Not kept: a check that lands after a calibration lapses its hold, so the wait guards nothing the hold does not. A project may still order its work so, for economy.

- **Left open:**
  - **A hold the code alone lapsed, restored without a fresh ladder.** DEC-042 point 9 has each calibration take a fresh ladder and an outside judge, so a lapse by a change to the code costs a calibration like any other. A run on the calibrated ladder could restore the hold at less cost, such as a replay of the viewing step on it whose images, frames and report come out byte for byte as before, or a review of it that grades it as before. A change to the code may move pieces the ladder does not hold, but a calibration's report already reaches from one ladder to every piece in every project, so whether a replay suffices is a policy question, not one this record settles. A refinement of DEC-042 point 9 weighs it ([project-kit#3381](https://github.com/aleskalfas/project-kit/issues/3381)).
  - **Who sees a lapse.** The command tells a lapse only when it gives a verdict, from a round's report. A release that ships accepted data its own code differs from, a project that takes a release, and whatever waits on the hold would each see one, by the digests that rest on no bar and no model: the code, the list of checks, the reviewer's definition and the design knowledge. How they are told is a choice of its own, which a record decides ([project-kit#3382](https://github.com/aleskalfas/project-kit/issues/3382)).
  - **What else the review reads.** The reviewer's body names records and pages among its reading, such as DEC-046 and the outputs page. Outside programs draw some of the images it reads, such as a browser, and the dependencies the code pins rest on others that no header pins. A change to any of them could move the grades, and DEC-042 point 9's list names none. A refinement of that point decides them.
  - **The code that ran.** The command takes the code's digest from the code installed when it gives the verdict, as it takes the digests of the reviewer's definition and the design knowledge. The review read a viewing step's report computed earlier, by code that may differ, such as a build pipeline's drawings at the commit drawn (DEC-062 point 3), or a look before a pull. So the digest stands for the code that ran only where the look, the review and the verdict run on one state of the capability. The viewing step's report already names the version and each check's reach from the code that ran (DEC-062 point 2), and could carry the code's digest too. Where the command reads data of the round from, beside the review's report, is for the record [project-kit#3372](https://github.com/aleskalfas/project-kit/issues/3372) calls for to decide.
  - **Line endings.** Each digest reads bytes as they stand, so a checkout that converts line endings, as one on another platform may, changes every digest and lapses the hold, which is safe. Whether the digests read a text with its line endings made one is a refinement of DEC-042 point 9, for all of them.
