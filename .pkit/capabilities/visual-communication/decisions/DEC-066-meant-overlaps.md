**In plain terms:** a component may place one of its parts on another on purpose, such as a badge on a card's corner. The check of boxes that overlap cannot tell that from a fault, so in every piece that uses the component it asks the reviewer whether the overlap is a fault or is meant. This record lets a part name, under `lies-over`, the parts of its own component that it lies over on purpose, and the engine carries the names into the scene the check reads. Where a released version, still as it was released, names a pair, the check states their overlap as a fact, which asks no one to act: the version's owner has answered what the check would ask, in a version that never changes. Whether the version is still as it was released is read where the finding is read, as a finding's level is, so the scene holds only what the files say. The fact still names the pair and how far they overlap, and the reviewer reads the image there as it reads the rest of the page. Anywhere else, in a piece's own component or in a version not yet released, whoever is under review could write the names to answer the reviewer, so there they give the check nothing: the pair asks for attention exactly as a pair no one named, and the reviewer takes no word it reads in a component's file as a ruling. A release is what turns a version's words into rulings, so it states each `lies-over` the version adds, widens or drops, and the change that carries the release names each for the person who authorises it, as information. The designer may make that release itself, so the person learns of such a ruling when the change comes to land. This record has the record on files and validation say that a reading of taste asks for attention wherever the judgement it calls for is still owed, and that only a record lets a file give that judgement, and says whose ([visual-communication:DEC-002-files-and-validation] point 7). The record on faults gave this work the aim that a meant overlap not be reported for ever ([visual-communication:DEC-046-faults-lower-grades] point 3), and this record overturns that aim: a meant overlap is reported in every piece, as a fact in place of a call for attention.
- **Only the check of overlaps.** The check of edges that nearly line up still compares the pair. That an overlap is meant says nothing of where the two parts' edges lie.
- **A library the capability ships** says it as it makes any other change: in the version it is building, which takes a patch at least, and the names give the fact once that version is released. When this record was drafted, none needed to (Implications).

## Context

DEC-046 point 3 has two checks do the arithmetic of craft among the *siblings* of each scene, the elements one group holds directly. One reports edges that nearly line up. The other reports two siblings whose boxes overlap, where neither holds the other. Both ask the reviewer for attention and never fail, since a component may place one part on another on purpose, such as a badge on a corner. The reviewer judges each place they name on the image, and says whether it is a fault or is meant. The point leaves it to the work that builds the checks to settle how a component says an overlap is meant, "so that it is not reported for ever". Where that adds a field, the work drafts the record first (COR-065 point 3).

[project-kit#3327](https://github.com/aleskalfas/project-kit/issues/3327) is that work. It asks three things: how a component says it; whether saying it also leaves the pair out of the check of edges that nearly line up; and how a library the capability ships says it, in a new version ([visual-communication:DEC-013-shipped-library-releases]).

The answer meets six things that already hold:
- **Parts are drawn in the order written,** and the scene keeps that order among each group's elements. So of two siblings, the later is drawn over the earlier ([visual-communication:DEC-005-engine-and-plugins] point 5). A part's name ends the trace id of what it draws. Parts are written in a component's `parts`, in a top's drawing of a layout, and in a brand's drawing ([visual-communication:DEC-009-layout-defaults] point 1, [visual-communication:DEC-034-brand-drawings] point 1).
- **The checks of boxes read the scene:** each element's box and trace id. They read no component's file.
- **The frames, the report and validation carry a component's word only as a check's finding.** The viewing step's frames hold each element's box and trace id. Its report holds what the checks found on each image and each check's reach ([visual-communication:DEC-062-checks-beside-the-frames] points 1 and 2). Validation shows what the checks found. The reviewer reads the images with the piece, its own components among it, and reads what a check found from the report alone, never from a piece's findings record ([visual-communication:DEC-015-viewing-step-and-reviewer] point 7). It reads a piece's components where a record of its reading has it do so too: where no check measured whether a size hides a part the page does not show, it judges from them whether the part is hidden on purpose (DEC-062 point 3, [visual-communication:DEC-063-where-a-check-measures] point 4). Those records have it judge an overlap on the image and from the frames (DEC-046 point 3, DEC-063 point 4). A check's silence at a place of a kind its reach measures reads as measured and clean (DEC-063 point 3). So DEC-062 gives every overlap, since a pair left out "would read as measured and clean by the check of boxes that overlap, while the page shows the overlap" (DEC-062, "Why no overlap is left out").
- **A finding that never fails asks for attention or states a fact.** It asks for attention when someone is expected to act, and names who, and states a fact when no act is expected. A finding read from a heuristic or a threshold that no record makes an invariant asks for attention (DEC-002 point 7). The check of overlaps is such a reading, since whether an overlap it finds is a defect needs a judgement (DEC-046 point 3), and it names the reviewer. Two kinds of finding state a fact, though a reader still reads the places they name. A check's statement that it could measure nothing at a place is a fact, since a reader that relies on the check "judges the places it covers itself, as part of its own reading, which no finding asks of it" (DEC-063 point 2). And the check of content a size hides states as a fact what a component hides at a size: "So a reviewer sees what a reader at that size does not get" ([visual-communication:DEC-021-size-and-shape] point 5).
- **A released version never changes.** A change goes into the version being built, and raises its number as far as the change needs ([visual-communication:DEC-003-change-over-time] point 6, DEC-013 points 3 and 4). The location's list marks which versions are released, with a hash of each, so the check reads from the files whether a version is released and still holds what was released (DEC-003 point 4). A copy of a library the capability ships is listed released with the hash the capability records for that version (DEC-013 point 5). The check works that out each time it reads a finding that lies in a version, and gives the finding its level from it, never storing it (DEC-002 point 7, DEC-005 point 14). So neither the scene nor the key of a piece's findings record, a hash of every file its scenes were computed from, holds it (DEC-005 points 5 and 13). A release states, as a fact, each change of what a stable component declares of the reader's side (DEC-003 point 7). The owner of a library judges what goes into it by the bar that owner keeps ([visual-communication:DEC-030-design-agents] point 4), and whoever maintains the capability releases a version of a library it ships (DEC-013 point 1).
- **The designer writes what is not yet released.** It writes a piece's own components and a version of the project's own library not yet released, and, where the capability is authored, a shipped library's version being built. It writes no released version. What commands write, a release among them, stays theirs, and the designer runs those commands where its body says (DEC-030 points 4 and 5). Where the verdict ends its loop at a project's bar, under the *hold* that an accepted calibration switches on, it mends each grade that fails the bar (DEC-030 point 2, [visual-communication:DEC-042-grades-bar-and-loop] points 6 and 9). A fault of overlaps holds `RS-GRAPHIC-002` below professional (DEC-046 points 2 and 3). A value that the piece's files fix, or a version of a library its lock names, lapses no hold, released or not, since it is part of the piece the review reads ([visual-communication:DEC-065-checks-lapse-the-hold] point 2).

## Decision

**A part names, under `lies-over`, the parts written before it in the same `parts` that it lies over on purpose. The engine carries those names into the scene, with the version that holds the part. Where that version is released and still as it was released, as read where the finding is read, the check of boxes that overlap states each overlap of a pair named so as a fact, since the version's owner has answered what the check would ask the reviewer: whether the overlap is a fault or is meant. Anywhere else the names give the check nothing: the pair asks for attention exactly as a pair no one named, and the reviewer takes no word it reads in a component as a ruling. A release states each `lies-over` it makes a ruling, and the change that carries it names each for the person who authorises the change. So a reading of taste asks for attention wherever the judgement it calls for is still owed, and only a record lets a file give that judgement, and says whose: at an overlap, the word of a released version still as it was released, alone. No other check reads the names.**

### 1. A part names the parts it lies over on purpose

- **`lies-over`** is a key any part may take: a list of the names of parts written before it in the same `parts`, and so drawn before it. It says that the part lies over each of them on purpose, and this record calls it the part's *word* on each pair it names. A badge drawn over a card's box writes `lies-over: [box]`.
- **Wherever parts are written:** in a library's component or a piece's own, in a top's drawing of a layout, and in a brand's drawing. Where the word gives the fact, and where it gives the check nothing, is point 2's.
- **Only the parts the check compares with it.** It names parts of that same `parts` alone, since the check of overlaps compares siblings alone (DEC-046 point 3), and the parts of one `parts` are drawn as siblings. So it names no part inside a component a part places, and no item of a list. A part that places a component, holds a slot or repeats over a list is named whole, by what it draws, as the check compares it. A change that widens the check of overlaps beyond siblings decides whether `lies-over` may name more.
- **Of boxes, as the check is.** `lies-over` speaks of the parts' boxes, which the check compares, not of what is drawn in them. A component may name a pair whose boxes overlap where their drawing does not, such as a text whose line spacing reaches into the box of the part above it. That use is meant: the overlap of the boxes is the component's design, as any other is. Whether what is drawn touches stays the reviewer's to see on the image, since "a box may differ from what is drawn in it" (DEC-046 point 3).
- **Always, or not at all.** It takes no switch. Wherever the two parts overlap, under any option, at any size and in any language, the component says that the overlap is meant. Where they do not overlap, or where the check does not compare them, as where one is a line or holds the other, it changes nothing.
- **Refused when the component is read:** a name that is no part of the same `parts`, the part's own name, the name of a part written after it, and a name's second writing in the list. The order of drawing decides which part lies over which, so a part that named one drawn after it would say the opposite of what is drawn. A name refused says nothing: at a pair no other writing names, the check asks for attention, as at any pair not named. A name's first writing names its part.
- **Each refusal is a finding** that names the part and the name refused, at the level DEC-002 point 7 gives by who can correct the file that holds it. It fails where the project can, as in a piece's own component or a version of the project's own library not yet released. Elsewhere it asks for attention and never fails, naming who can correct it: a released version's owner; and inside a copy of a library the capability ships, released or not, whoever maintains the capability (DEC-003 point 9). Its message names what the part names, so it is the one finding through which a word that rules nothing reaches the reviewer (Rationale, "Why an unreleased word gives the check nothing").

### 2. The scene carries it, and the check of overlaps states each overlap a released version names as a fact

- **In the scene.** The element that a part with `lies-over` draws holds `lies-over`: the trace ids of the elements the parts it names draw in that scene, and the library's version that holds the part, where a library's version holds it. A piece's own component lies in no library's version, so its word names none. The scene holds no mark of whether that version is released: it states what the files say, and release status is applied where the finding is read (below). A part it names that draws nothing there, such as a slot left empty or a part whose `when` does not hold, adds none.
- **Released, and still as it was released.** The word's version reads so where the location's list marks it released and its folder still holds what was released, as its hash shows (DEC-003 point 4). For a copy of a library the capability ships, the hash the list keeps must also be the one the capability records for that version (DEC-013 point 5): a mark that no release of the capability's gave never reads so. Wherever this record speaks of a released version's word, it means a word in a version that reads so. A piece's own component lies in no version, so its word never does.
- **The mark lies in the list.** The mark that says a version is released, and its hash, lie in the location's list. They are those of a version the piece's lock names, so they are the piece's, as the version's files are (DEC-065 point 2). Only the command that releases a version marks it released, writing its hash and stating each word the release makes a ruling (point 5). A copy of a library the capability ships takes its mark, with its hash, from the command that brings it in, which copies them from the release the capability records (DEC-013 point 5). Marking a version released is an act on the version, made once, and seen in the change as the list's entry and the version's hash.
- **No property the element draws.** It may stand on an element of any type, and no renderer draws it, so it counts among what no element draws, beside the element's type, its trace id, its sources and its children. So it names no source, no renderer's declaration lists it, and no loss names it (DEC-005 points 5 and 9). The seam's version stays as it is, since no plugin must read anything differently (DEC-005 point 8).
- **A released version's word gives a fact.** The check of boxes that overlap compares every two siblings as before. Where two overlap, and the later names the earlier under `lies-over`, its finding carries the version that holds the word, where one does, and its label and message are settled where the finding is read. Where that version is released and still as it was released, the finding states the overlap as a fact, `box-overlap-meant`, in place of the call for attention the list of checks labels `box-overlap`. Its message names the pair, how far they overlap and which lies over which, as the message of an overlap does, and says that the part on top names the part beneath under `lies-over`. It points where `box-overlap` points.
- **Any other word gives the check nothing.** Where the later names the earlier under `lies-over` anywhere else, as in a piece's own component or in a version not yet released, the finding reads as `box-overlap`, a call for attention to the reviewer, exactly as at a pair no one named, and its message says nothing of the word. The reviewer rules on the place as at any overlap, a fault or meant (DEC-046 point 3). The reading of the component still refuses what point 1 refuses, and a word in a version not yet released gives the fact once that version is released (Rationale, "Why an unreleased word gives the check nothing").
- **Read alike wherever findings are read.** Validation reads the finding so from the piece's findings record, which holds it with the word's version and no mark of release, as it works out each finding's level (DEC-005 point 14). The viewing step reads it the same way before it reports. So a release that changes only the list, as one that leaves the version's folder byte for byte as it was, turns the finding into the fact in validation and in the look alike, and changes no scene and no findings record's key (DEC-005 points 5 and 13).
- **Every overlap the part does not name** asks for attention as before: a badge named `lies-over: [box]`, which a long title pushes over the card's head, is reported at the head with `box-overlap`.
- **A fact, since it asks no act.** `box-overlap` asks the reviewer to rule on its place, a fault or meant (DEC-046 point 3). At a pair a released version names, the version's owner has given that ruling, once for every piece, in a version that never changes. So no one is expected to act: not the reviewer; not the piece's author, whom the check never names; and not the version's owner, who said it (Rationale).
- **Who may give the ruling.** A reading of taste asks for attention wherever the judgement it calls for is still owed, and only a record lets a file give that judgement, and says whose file may. This record refines DEC-002 point 7 to say so (Implications). At an overlap of two parts, a released version's word alone gives it. Released is where the owner's ruling is final, and where its release has stated it to the person who authorises the change that carries the release (point 5). A piece's own component and a version not yet released are what the designer writes, and mends, in the loop it is reviewed in, and no release has stated their words (Rationale, "Why only a released version's word is a ruling").
- **The reviewer takes no word as a ruling.** It judges on the image alone whether an overlap a `box-overlap` names is meant, and a `lies-over` it reads in any component's file, released or not, is no ruling. Its records send it to read components: the piece's own, with the piece (DEC-015 point 7), and those that draw a part where no check measured whether a size hides it (DEC-062 point 3, DEC-063 point 4). So it may meet the word there. Its body holds this line (Implications), and this record rests on the reviewer keeping it (What it costs). The line follows DEC-046 point 3, which has the reviewer judge each place the checks name on the image.
- **Measured, with a finding.** The check measured the pair, so the fact is a finding of what it measured, and no statement that it could measure nothing (DEC-063 point 2). Its reach gains no clause, and the pair reads as measured, with a finding (DEC-063 point 3). So no reader takes the pair for measured and clean. The viewing step's report gives the fact on each image the pair shows, as it gives each finding of a check that runs on a scene (DEC-062 point 1), and validation shows it as it shows any fact.
- **The reviewer gives the place no ruling.** At a place of `box-overlap-meant`, it does not judge whether the overlap is a fault or is meant, and its report does not list the place among those the checks ask it to judge. A place of the fact that the viewing step's report lists on no image drawn, it names as a place it has not seen, as it names every place of a check's finding listed so (DEC-015 point 7), since its reading of the image there is owed.
- **No sums for the overlap.** It does no sums there for the overlap, which the check measured (DEC-063 point 3). It reads the image there as it reads the rest of the page (DEC-015 point 7).
- **A defect where the parts meet.** The word says that the two parts need not stand clear of each other, and never what is drawn where they meet. DEC-046 point 3 has the reviewer tell a place that is a fault from one that is meant, and at this place the word has told it, so the overlap is no fault, nor the fault of overlaps. A defect the image shows where they meet is of the kind that names what a reader loses there. Two texts whose letters are lost are the reviewer's fault of text over text. A part beneath that is or holds a text a covered entry names is that text's fault alone, as at any overlap (DEC-062 point 3). Any other part the upper one hides from a reader, whole or in part, such as a picture's subject, is the fault of a part missing or blank.
- **Reported in full.** None of these is a fault a check already reports, which is named in one line (DEC-030 point 7): the fact says that the parts overlap and how far, and judges nothing of what is drawn there. None is a drawing that disagrees with a passing check, since the check gave a finding (DEC-063 point 4).
- **Every other reading of the pair stays.** The viewing step still names a text that a part drawn after it covers, where it reads what covers a text ([visual-communication:DEC-037-text-the-page-hides] point 1), and the reviewer reads that text as the covered entry's fault alone, as it reads every overlap of a covered text (DEC-062 point 3). The check of contrast still measures a text against the fill under it ([visual-communication:DEC-004-brands-and-notations] point 8).

### 3. The check of edges that nearly line up compares the pair as before

- **`lies-over` speaks of an overlap, not of a line.** The check of edges that nearly line up compares the pair as it compares any two siblings (DEC-046 point 3).
- **A meant overlap still has edges meant to land somewhere.** A tab meant to lie over its panel's top edge is meant to lie flush with the panel's left edge too. It may lie off that edge by more than a pixel and by less than the brand's smallest step of space, and the check measures that edge whether or not the two parts overlap.
- **What it costs.** A part centred on another's edge, such as a dot on a card's corner, has its own edge on that side half its size away from the other's. Where that half is more than a pixel and less than the brand's smallest step, as for a dot more than 2 and less than 8 px across under a brand whose smallest step is 4 px, the check reports a near miss on each axis on which the part is so centred, in every piece that draws the component. It follows from a line the check does not compare: a centre set on an edge. Each asks for attention and fails nothing, as every near miss does.
- **Left open:** whether a component may say that a near miss is meant; and whether, for a pair named under `lies-over`, a centre set on the other's edge counts as a line chosen, so that the near misses it gives against that part are not reported. That would remove this point's cost between the two parts named alone: `lies-over` names siblings only (point 1), so a near miss the dot gives against any other part would stay, such as one of another group, were the check to compare parts of different groups. This record decides neither, and leaves each for a later record, which weighs one carrier for an owner's words on a part before it adds a key beside `lies-over` (Implications, "Left open").

### 4. A library the capability ships says it in the version it builds

- **In the version being built.** A component of a library the capability ships, whose parts overlap on purpose, comes to say so in the library's version being built. A released version never changes, so it never says so (DEC-003 point 6, DEC-013 point 4). Whoever maintains the capability judges which overlaps are meant, as the owner of any library does, and releases the version (DEC-013 point 1).
- **A fact once released.** Until that version is released, a piece that draws it, where the capability is authored or from a copy not yet released, is asked for attention at the pair exactly as at a pair no one named (point 2). Its release makes the word give the fact in each piece whose lock names the released version, and states the word (point 5).
- **A patch at least.** Saying it, or ceasing to, changes no look and nothing that a piece or a library built on the library names, so it is no break (DEC-003 point 6). Nor is it an addition to the library, which would take a minor: the comparison of two versions names a library's additions kind by kind, and a part's own keys are of none of those kinds (DEC-003 point 1; the capability's page on files, "What a release compares"). So the version being built takes a patch at least, as for any change to it (DEC-013 point 3). Its release states it all the same, as a fact (point 5).
- **The release it needs reads `lies-over`.** A shipped version's release reads it in full, refusing any key the capability that releases it does not know, and names that capability's current version as the release the version needs (DEC-013 point 3, [visual-communication:DEC-014-own-library-needed-release] point 1). An installed capability older than that release cannot read the version. So the change that teaches the engine `lies-over` lands before, or with, the change that first writes `lies-over` into a shipped library's version being built.
- **A piece under an earlier released version,** which does not say it, is asked for attention at that overlap, until its lock moves to a released version that says it is meant. Who moves the lock is what the piece's state says (DEC-003 point 8). The attention fails nothing meanwhile.

### 5. A release states each word it makes a ruling

- **What it states.** Every release of a library's version states, as a fact, each `lies-over` the version adds, widens or drops against the release it follows: each pair of parts that a part comes to name, or ceases to. A library's first release, which follows none, states each `lies-over` it holds. It states them on a part of any component, whatever its status, a drawing included, since a released version's word is its owner's ruling wherever it lies. This record refines DEC-003 point 7 to say so (Implications).
- **Named in the change.** The change that carries the release names each in its pull request's description. Where the release is committed straight to the default branch, it is told to the person the committer works for, before the commit.
- **As information.** It reaches the person who authorises the merge as information, not as a question, as the designer tells the person what it changed (DEC-030 point 2). No one is asked to act on it.
- **Whoever releases.** The designer may release a version of the project's own library when its work needs one, as it runs the commands its body names (DEC-030 point 5), and its release states the words as any release does. A version of a library the capability ships stays with whoever maintains the capability to release (DEC-013 point 1), and its release states them too (Rationale, "Why a release states each word it makes a ruling").

## Rationale

**Why the component says it, not each piece.** The overlap is the component's design. Every piece that uses the component draws it, and none of their authors chose it. Said once, in a released version, it reaches every piece whose lock names that version, and holds as long as the parts it names do. A piece that accepted the overlap, as it accepts a renderer's loss, would have to say it again in every piece: the repetition this record removes. A piece's own component reaches one piece, and lies where the piece's author writes, so there the word gives the check nothing (point 2).

**Why only a released version's word is a ruling.** The word moves what the review judges, not what is drawn. Where whoever is under review can write it, it would let that party answer the reviewer's question itself. The designer writes a piece's own components and a version not yet released, and, where the capability is authored, a shipped library's version being built (DEC-030 points 4 and 5). Under a hold it mends each grade that fails the bar, and a fault of overlaps holds `RS-GRAPHIC-002` below professional (Context). Were the word a ruling there, adding `lies-over: [x]` would mend that grade with no pixel changed, at a place where two parts crowd each other though nothing a reader needs is lost, and no one but the designer would know it. The hold would not see it, since a value of the piece's lapses nothing (DEC-065 point 2). That rule rests on such a value changing what the piece is, as its content does (DEC-065, "Why a value of the piece's lapses nothing"), and this one would change what the review judges, with nothing drawn changed. DEC-065 rejected a hold that rests on a declaration the declaring party could get wrong, since one wrong declaration keeps the hold on for a review that does not run as it was measured (DEC-065, the alternative "A revision each check's author raises"). A word the reviewed party writes would be such a declaration. A released version never changes (DEC-003 point 6). Marking a version released is an act on the version, made once and seen in the change, as the list's entry and the version's hash, where a word written to answer a finding reads as any other line of a component, and only why it was written tells it apart. The release that marks it states each word it makes a ruling, and the change that carries the release names each for the person who authorises it (point 5). So released is where the owner's ruling is final, and where a person has been told it. That is the line DEC-002 point 7 draws between a file the project can still correct and a released version only its owner corrects, and the line point 4 reads a piece under a released version by. Elsewhere the reviewer rules as at any overlap. At a fact, the reviewer reads the image as it reads every place no check names. The line does not keep the designer from making its own word a ruling, since it may release (point 5). It makes each such ruling one the person is told of, and What it costs names what that leaves to the merge.

**Why a release states each word it makes a ruling.** A release is the act that turns a word into a ruling. A word in a version not yet released gives the check nothing, and the same word gives the fact once the version is released, in each piece whose lock names it, a draft that locked the version before its release among them (DEC-003 point 8). The words land in the commits that write them, often in earlier changes, and the release's own change shows only the list's entry and the version's hash. The comparison names none of them either, since a `lies-over` is neither a break nor an addition (point 4). Unstated, a word written in an earlier loop would become a ruling through a release made for some other reason, and no one would read it. Stating each `lies-over` the version adds, widens or drops puts each ruling before the person who authorises the change that carries the release. That keeps a person in the ruling though an agent makes the release: the person sees each ruling the change makes, and need act on none, as the designer tells the person what it changed, as information (DEC-030 point 2). DEC-003 point 7 has a release state each change of a stable component's reader's side for a like reason, a change that breaks nothing yet reaches every piece that takes the version, and this statement joins it there. It adds to what a release states and decides nothing otherwise than that point, so it refines it. It covers every component, whatever its status, since an experimental component's word rules as a stable one's does. It states and does not ask, since a question at every release would have the person act on each, which the alternative "The designer runs no release" weighs.

**Why an unreleased word gives the check nothing.** The review grades before it reads any account of the loop's work: it is handed the brief's intent without its reasons, reads the brief's file only once its grades are written, and reads no account of what the designer changed (DEC-042 point 4). A `lies-over` in a piece's own component, or in a version not yet released, is such an account: whoever wrote it, inside the loop, says what is meant at a place the review is about to judge. Carried in the message of `box-overlap`, it would put that account before the reviewer as it grades, and ask it to disregard what it had read, where DEC-042 point 4 relies on the order of reading instead. Under a hold, the designer that adds `lies-over` to its own component breaks no instruction, since it is ordinary design work, yet the word would press on the very ruling point 2 keeps from it. So the check gives the pair as a pair no one named. The reviewer reads components where its records send it, the piece's own with the piece (DEC-015 point 7), and those that draw a part where no check measured whether a size hides it (DEC-062 point 3, DEC-063 point 4), so it may meet the word there. This record keeps the findings it is handed free of the word, structurally, and the reviewer's body does the rest: the line of point 2, that it judges on the image alone whether an overlap a `box-overlap` names is meant, and takes no `lies-over` it reads in a component as a ruling. That line rests on DEC-046 point 3's own words, which have the reviewer judge each place the checks name on the image, and on the reviewer keeping it, as DEC-042 point 4's order rests on its restraint (What it costs). The piece's findings record holds the overlap's finding with the word's version, and the reviewer reads no finding from it (DEC-015 point 7). One finding it is handed does carry a word: a refusal of point 1, whose message names the part and the name refused, and which reaches the viewing step's report among the findings found while computing a scene. That can be borne. A name refused says nothing, so it rules nothing. The refusal fails wherever the project can correct the file, as in what the designer writes in its loop, so the loop mends it. And the reviewer's line has it take no word it reads as a ruling. The word is not lost: the reading of the component still refuses what point 1 refuses, and the release of its version makes it give the fact, and states it (point 5).

**Why a fact, and not silence.** A check that left the pair out would bring back what DEC-062 rejected. The frames, the report and validation carry a component's word only as a check's finding, so no reader of them could tell a pair left out by `lies-over` from two siblings the check measured and found clean (Context). The reviewer could tell only by reading the components at every overlap, which costs what the alternative "The reviewer reads each component's `lies-over`" weighs (below), and a reader of validation could not tell at all. A reviewer that saw the overlap and judged it a defect would then blame a check that did as it was told, as a drawing that disagrees with a passing check. A fact keeps the pair measured, with a finding, and reaches every reader through the findings each already reads, so neither the frames nor the report changes form. A fact also says how far the parts overlap, which a silence cannot. So an overlap grown past what the component meant is still put before every reader. A loss a piece accepts falls silent instead (DEC-005 point 9), since the loss report has no reach, so its silence claims no place measured. A scene check with a reach may not fall silent at a place it measured, whose silence reads as measured and clean (DEC-063 point 3), so an owner's word on such a check's finding gives a fact.

**Why a fact, and not a call for attention.** A call for attention expects someone to act, and names who (DEC-002 point 7). `box-overlap` names the reviewer, and the act it expects is a ruling: whether the overlap is a fault or is meant, judged on the image and said in the review's report (DEC-046 point 3). At a pair a released version names, the version's owner has given that ruling once, for every piece. A call there would ask the reviewer, image by image, a question already answered, and its answer would add nothing the version did not say. What is left at the place is the reviewer's own reading of what is drawn where the parts meet. It makes that reading at every place of the page, named by a check or not (DEC-015 point 7), and no finding asks it of the reviewer. DEC-063 point 2 states a fact for the same reason, where a check could measure nothing: a reader that relies on the check "judges the places it covers itself, as part of its own reading, which no finding asks of it". The capability passes on a component's choice so already. The check of content a size hides states as a fact what a component hides at a size (DEC-021 point 5). There too the component's word answers what a reader would otherwise ask, whether a part is missing, and whether the page reads well without it stays the reader's own judgement. The check of overlaps is a reading of taste, which DEC-002 point 7 has ask for attention, so this record refines that bullet: such a reading asks for attention wherever the judgement it calls for is still owed (point 2, and "Why DEC-002 point 7 is refined, and not overturned" below).

**What the fact gains, and what it does not.**
- **Validation's warnings stop counting the overlaps a released version means.** Validation prints a call for attention as a warning and a fact as information, and prints both (COR-055 point 5; the CLI's page, `validate`). So it prints a line for each such overlap in each piece that draws it, as before, and none of those lines is a warning.
- **The review gives those places no ruling,** and no line of its report, and reads the image there as it reads the rest of the page.
- **Every reader still sees each overlap,** with how far.
- **No entry goes away.** The overlap is still reported in every piece that draws it, for ever. That is the departure from DEC-046 point 3 (below).

**Why DEC-046 point 3 is overturned in part, and not refined.** The point's bullet "An overlap that is meant" gives the work its aim: a way for a component to say an overlap is meant, "so that it is not reported for ever". This record has each such overlap reported in every piece that draws it, for ever, as a fact where a released version says it, and as a call for attention elsewhere. Another record then decides otherwise than the point, so that clause is overturned, as DEC-062 overturned point 5 of the same record (DEC-062, "Why DEC-046 point 5 is overturned in part, and not refined"). The bullet's sentence stays as it stood, under the line that names this record. What the rest of the bullet decides stands, and this record carries it out: the work settles how a component says an overlap is meant, and drafts the record first. The edits to the point's bullet on what the two checks ask, "Both ask for attention and never fail", and to its bullet "The reviewer judges each place the checks name" refine them. Each decides what it decided at every place but an overlap a released version names. The reason the first gives, that whether an overlap is a defect needs a judgement since a component may place one part on another on purpose, is what the released word answers for the pairs it names.

**Why DEC-002 point 7 is refined, and not overturned.** The point's bullet "A reading of taste never fails" has a finding read from a heuristic or a threshold that no record makes an invariant ask for attention. The same point says when a finding that never fails asks for attention: when someone is expected to act ("Attention or a fact"). A reading of taste asks for it since whether its result is a defect needs a judgement, which is no check's ([visual-communication:DEC-028-principles-of-visual-communication] point 1), so someone is expected to give it. The edit narrows the bullet to what that reason reaches: a reading of taste asks for attention wherever the judgement it calls for is still owed. Where that judgement has been given, the point's own test, "Attention or a fact", decides the finding. The bullet's decision stands, a reading of taste never fails, and no record decides otherwise than the point, so the edit refines it in place (the decisions README, "Refining an accepted record"). Of who may give a judgement, the edit settles only that no file gives one unless a record lets it, and that such a record says whose file may. A finding may ask the very party that would write a word answering it, where the word is an acknowledgement, or an independent judge, such as the reviewer, where a word of the author's would move the ruling from the judge to the author. So whose word, if any, gives a judgement is for the record that lets one be given, as this record decides for an overlap (point 2). Worded so, the bullet names a principle and no check's label, and generalises nothing from this one case: a later record that lets a file answer another reading, such as a word for a near miss that is meant (point 3), decides itself who may write that word.

**Why a part names parts.**
- **Not a flag on the part.** `lies-over: true` would make every overlap of that part meant. A badge meant to lie over the card's box, but pushed over its head by a long title, would then ask no attention at the head. Naming each part keeps the check's attention on every pair the component did not mean.
- **Not a list of pairs on the component.** It would say the same thing, away from the part it explains. On the part, the key lies beside what it speaks of, as `when` lies beside the part it draws or not, and a reader of the badge sees there that it lies over the box on purpose.

**Why only parts drawn before it.** What the component means is that one part lies on top. The order of drawing decides which does (DEC-005 point 5), so the key reads in that order. A badge moved before the box would be hidden under it, which is a fault. The reading then refuses the name, and the check asks for attention at the pair again, rather than state as meant a badge no one can see.

**Why the scene carries it.** The check reads scenes, and compares siblings by their trace ids. A check that read each component's file would have to find again, for each group, the version and the drawing that drew it, which the engine has already done. A scene says which component drew each group for the same reason. The version that holds the part is carried with the names for the same reason. It is carried on the element, not beside the version its group names, since a part need not lie in that version, as a brand's drawing's parts lie in the brand's version while they draw a top's layout (DEC-034 point 1). Whether that version is released the scene does not carry. The scene states what the files say, and release status is applied where findings are read, as their levels are (Context). So a release that changes only the list, as one that leaves the version's folder byte for byte as it was, changes no scene, as two scenes with one root differ only in the text of an export's facts (DEC-005 point 5). The findings record stays a fact about the files its key covers (DEC-005 point 13), and its finding reads anew in validation and in the look. A mark held in the scene would have needed the list in that key, and one fact read in two places (Alternatives, "The mark in the scene"). A second word an owner says of a part, were one added, would carry the version that holds it in the same way, which the one carrier left open below weighs (Implications, "Left open").

**Why it is no property the element draws.** It may stand on an element of any type, and says nothing a renderer could draw. Listed in a renderer's declaration, it would stand under every type there, in each renderer the capability ships. A renderer added later would have to list it under each type, or report a loss of it in every piece that names a meant overlap. Counted beside an element's type, its trace id, its sources and its children, which stand on every type too, it is one entry, in the code that finds the losses, and no declaration names it. A group's `component`, `version`, `options` and `page` no renderer draws either, yet each renderer's declaration lists them under `group`, which costs a later renderer the same, on that one type alone. This record does not move them. Two treatments then stand for data no renderer draws, so a follow-up picks one rule for both (Implications, "Left open").

**Why no switch.** The fact never hides an overlap: wherever a pair named so overlaps, under any option and at any size, every reader is told, with how far. So an overlap under an option the component did not mean it for is still shown, though it asks no act. A switch would cost the key a second form, with branches, a refusal in each branch, and a rule for which branch an instance's scene names, for a need no component of the libraries the capability ships had when this record was drafted: none placed a part over another that the check compares with it (Implications). Without one, a component that means an overlap under some options or sizes alone has two ways, each with its cost: it leaves the pair unnamed, and asks for attention where the overlap is meant; or it draws the part as two parts, each with its `when`, whose trace ids then differ by option.

**Why the check of edges that nearly line up still compares the pair.** A word a component says reaches only what its words name. That an overlap is meant says where two parts share room, not where their edges lie, and a meant overlap still has edges meant to land somewhere (point 3). Leaving the pair out of both checks would let a meant overlap hide a part set a little off the edge it was meant to lie on. Point 3 names what keeping the check costs: near misses in every piece for a small part centred on an edge. Whether such a near miss is meant is a question of near alignment. This record leaves it open, rather than settle it by a word that speaks of overlaps.

### What it costs

- **A line for each meant overlap a released version names,** in validation and in the viewing step's report, in each piece where the parts overlap, for ever. It states a fact, as a piece that uses an experimental component is stated (DEC-003 point 9), and asks no act. The aim of DEC-046 point 3, that a meant overlap not be reported for ever, is given up.
- **No call, however far the parts overlap,** where a released version names them. A caption band meant to lie over a picture's foot, which a long caption wraps to three lines at one size or in one language, covers the picture's subject and asks no attention. The fact names how far the band overlaps the picture, and the subject the band hides is the reviewer's to see, in its reading of the image, as a part missing or blank (point 2).
- **A call for attention at a pair a version not yet released names,** exactly as at a pair no one named, in every look and review of each piece that draws the version, until it is released. No reader learns from the check that the pair is named. At a pair a piece's own component names, the call stays for as long as the component does. A piece that means an overlap in its own component keeps the call, or moves the component into a library and releases its version, whose release states the word (point 5).
- **A ruling made inside the loop, seen at the merge.** Within a designer's loop, a release can make the designer's own word a ruling at once. A word it writes in a version not yet released, which a draft may lock, gives the fact at the same lock once it releases the version, and so mends a grade of overlaps in the next round with no pixel changed. The hold does not lapse, since a version the lock names is the piece's (DEC-065 point 2). The person sees the ruling only at the merge, in the change's description, or before a commit straight to the default branch, as information (point 5). What remains after the merge, for a piece whose hold the ruling touched, is the ruling itself: it stays in a version that never changes, the grade it mended stays as the review gave it, and the hold stays on. Taking it back takes a new version that drops the word, whose release states the drop, and a move of the piece's lock onto it, as the piece's state says who moves it (DEC-003 point 8). Until then each review of the piece reads the overlap as meant.
- **A mark written by hand bypasses the statement.** Only the command that releases a version marks it released, and that command states each word the release makes a ruling (points 2 and 5). A mark that a person or an agent writes by hand in the list, with the version's hash, gives the fact for a version of the project's own library with no statement made, and no check sees it, since the list holds the mark and the folder matches the hash. A copy of a library the capability ships cannot be marked so, since its word reads as released only where its hash is the one the capability records (point 2).
- **The reviewer's line is an instruction.** This record keeps the findings the reviewer is handed free of a word that rules nothing, but for a refusal's message (point 1). That the reviewer takes no `lies-over` it reads in a component as a ruling rests on its keeping the line its body holds (point 2), as DEC-042 point 4's order of reading rests on its restraint. No check sees a breach.
- **A calibration does not reach the fact.** No component of the libraries the capability ships writes `lies-over` (Implications). So a calibration that restores the hold measures nothing of how the reviewer's body reads `box-overlap-meant`, since no piece it grades gives one, unless a piece draws a released version that writes the word. The hold it restores then covers that reading untested, beside what the item on DEC-042 point 9 says (Implications).
- **No switch.** A component that means an overlap under some options or sizes alone asks for attention where the overlap is meant, or splits the part in two (Rationale).
- **Near misses of a centre set on an edge,** in every piece that draws a small part so (point 3).
- **A piece under an earlier released version** keeps the call for attention until its lock moves (point 4).

### Alternatives considered

- **The check infers what is meant,** such as a small part on a corner. Rejected: whether an overlap is a fault needs a judgement, and only what needs none is a check's (DEC-028 point 1).
- **The check leaves out each pair named so,** its reach naming that kind of place among those it leaves out. Rejected, for the reason above: no reader could tell such a pair from one measured and clean, and DEC-062 gives every overlap for that reason.
- **The fact wherever the word lies,** in a piece's own component and in a version not yet released too. Rejected: whoever is under review writes those, and could mend a fault of overlaps with a word and no pixel changed, which the hold would not see (Rationale, "Why only a released version's word is a ruling").
- **The fact wherever the word lies, with the designer bound to ask the person** before it adds or widens a `lies-over` to answer a finding of the review, a fourth case in which it asks under DEC-030 point 2. Not taken: the hold would rest on an agent keeping an instruction that turns on why a word was written, which no check sees, as on the declaration DEC-065 rejected. This record's line rests on an act instead, marking a version released, which is made once for a version and seen in the change, and the release that makes it states each word it makes a ruling (point 5). A word written to answer a finding reads as any other line of a component (Rationale, "Why only a released version's word is a ruling"). The record rests on one instruction too, the reviewer's line (point 2), but one the reviewer keeps at every overlap alike, whatever a word was written for. A person or another session that writes the word in a version not yet released would not be bound by the designer's instruction. And in a piece's own component the word reaches one piece, so saying it once there gains nothing.
- **The designer runs no release,** so that only a person releases a library's version, and a mend that needs a release is a question to the person (DEC-030 point 2), or a person confirms each release through the permission layer (COR-028). Not taken. The maintainer makes no release by hand: every release is made by an agent, so a rule that only a person releases would bind nothing he would carry out (17 November). The person stays in each ruling through the statement instead (point 5), and What it costs names what that leaves to the merge.
- **A call for attention, with the word in its message, wherever the word lies.** Rejected. For a released version's word, it would ask the reviewer to rule, in every piece, on a place whose ruling the version's owner has made final, and validation's warnings would still count every meant overlap. For any other word, it would show the reviewer, as it grades, the account of whoever is under review, which the next two alternatives weigh.
- **A word not yet released in the message, its risk accepted.** Rejected: under a hold, the designer that adds `lies-over` to its own component breaks no instruction, yet presses on the ruling point 2 keeps from it, through a finding the review reads as it grades, where DEC-042 point 4 has it read no account of what the designer changed (Rationale, "Why an unreleased word gives the check nothing").
- **A word not yet released in the message, read only once the grades are written,** as DEC-042 point 4 orders the brief's reasons. Not taken: like that order, it would rest on the reviewer's restraint, over a clause of a finding it is handed to grade from, where the line of point 2 asks only that it take no word as a ruling. And the word read after the grades would move none of them, while its author, who wrote it, learns nothing from it.
- **`lies-over` refused in a piece's own component,** as a finding that fails, since the project can correct it. There the word gives the check nothing anyway, and the refusal would close the main way the reviewer meets it, in the components it reads with the piece. Not taken: it would fail ordinary design work, and the word would no longer travel with a component promoted into a library. The reviewer would still meet a word in a library's component it reads where no check measured whether a size hides a part (DEC-063 point 4), so the line of point 2 would be needed all the same.
- **The fact stated once, where the component's version is checked alone,** and in no piece, as a check states once for a brand that one of its picture roles has no value. Rejected. A version checked alone draws no piece, so it could state only that a part names others, never that they overlap in a piece, nor how far, which changes with the content, the language and the size. Each piece's findings would then give nothing at the pair, so the viewing step's report, which gives every finding of a check that runs on a scene with no class (DEC-062 point 1), would show the pair as measured and clean, and validation, which shows a piece's findings from its findings record (DEC-005 point 13), would show nothing there either. It would bring back the leave-out above, priced at a line per version rather than a line per piece.
- **The mark in the scene,** whether the word's version is released carried with the names, and the list's entry for each locked version added to the findings record's key, so that a release that changes only the list stales the record. Not taken: the capability already applies release status where it reads a finding, as it sets its level (Context), so the mark would read one fact in two places. And two scenes with one root could then differ in that mark, against DEC-005 point 5, unless the root named it too (Rationale, "Why the scene carries it").
- **`lies-over` in the frames, or a list in the report of each image's pairs left out by `lies-over`,** read by the reviewer. Rejected: it changes the form of the frames or of the report (DEC-015 point 5, DEC-062 point 2), and the reviewer's reading of them, to tell the reviewer what a finding tells every reader, and validation would still show nothing at the pair.
- **The reviewer reads each component's `lies-over`.** Rejected: at every overlap, the reviewer would find again, for each group, the version and the drawing that drew it, as a check that read component files would (Rationale), where the records of its reading have it judge an overlap on the image and from the frames (Context). And validation, which shows what the checks found, would still show nothing at the pair, so its reader would take the pair for measured and clean.
- **`lies-over` with a switch,** on an option of words or on a size, one level deep, as a `repeat` part's `colour` takes one. Not taken, for the reasons above. Its trigger to revisit: a component that overlaps its parts on purpose under some options or sizes, and stands clear under others.
- **A piece that accepts a meant overlap too,** for a component of a library the project does not own, whose owner has not released a version that says it. Not taken: the call fails nothing meanwhile, a piece's word would say again, piece by piece, what the component's owner says once, and it would be a word whoever is under review writes (Rationale).
- **Two items of one list may be named.** When this record was drafted, no component of the libraries the capability ships laid two of its items over each other: each pattern laid out its items one after another in a row or a column, save its ties, which run between the items they join (Implications). A tie is lines alone, which the check leaves out, unless it draws its concept's sign (DEC-046 point 3). So two ties that each draw one, and that leave one item for two others on the same side, may overlap as boxes while their lines stand apart, and that overlap asks for attention. Patterns elsewhere lay their items over each other, such as a row of avatars that overlap, a fanned stack of cards, or the circles of a Venn diagram drawn as a list's items. A pattern lays out its items with an operator, and `lies-over` on a part cannot name them, so an overlap of two items asks for attention as before. Its trigger to revisit: a component, of a library the capability ships or of a project's own, that lays its items over each other on purpose.
- **The name `over`,** as short as a part's other keys. Not taken. When this record was drafted, the starter's card, aside, level and code named a value `over`, how far the sign reaches below the head, which their formulas read. Those are the components with a sign at the end of the head's row, the likeliest to name a meant overlap, so one file would hold one word in two senses. A part's key and a named value never meet in a formula, so nothing would break, but a reader of the file would meet both. `over` may also read as an instruction to draw the part on top, where `lies-over` reads as what it is, a statement of how the parts lie. Nor `drawn-over`, which leaves unclear whether the part it stands on is the one on top or the one beneath.
- **A word for a near miss that is meant,** beside `lies-over`. Not this record's: point 3 leaves it open.
