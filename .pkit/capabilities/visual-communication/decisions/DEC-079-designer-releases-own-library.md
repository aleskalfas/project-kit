**In plain terms:** the graphic designer releases a version of the project's own library itself, and no person need run the release or judge the version. The release writes only in the working tree, files that fix the version. Whatever then carries the version out of the repository, such as a merge, a direct commit to the default branch or a push to a branch others read, is kept for a person where it releases or publishes, and for a merge into the default branch the project's person declares whether it does. The designer releases at the person's ship call on a piece whose lock names the version, after telling the person which versions the call will release, and when the person asks. It marks each component's status, and leaves a new major to the person. A shipped library's release stays with whoever maintains the capability. The capability's checks and its reviewer hold a version to its bar before it is released, and the person judges pieces, not versions. And no release hides a failure a piece's scene shows. The release computes no scene, so it cannot see such a failure. Inside a released version of the project's own library, the failure lies at the piece's lock, since the project corrects it there, and so it fails.

## Context

[visual-communication:DEC-066-meant-overlaps] left to a record of its own whether the designer may release a version of the project's own library ([project-kit#3398](https://github.com/aleskalfas/project-kit/issues/3398)).

What holds:
- **What the designer writes and runs.** It writes a version not yet released of the project's own library, and never a released one. What commands write, a release among them, stays theirs, and the designer runs those commands where its body says ([visual-communication:DEC-030-design-agents] point 5). Its body leaves releasing a library version to the person.
- **What the release does.** It reads the version in full, a component no piece places included, computes no scene, and refuses a finding that fails ([visual-communication:DEC-014-own-library-needed-release] point 1). It compares each stable component with the library's previous release, and refuses a break outside a major release ([visual-communication:DEC-003-change-over-time] point 7). It then writes the release the version needs into the version's file, and the mark of release and the hash into the location's list, which fix the version (DEC-003 points 4 and 6, DEC-014 point 1).
- **What stays a person's.** Releasing and publishing, which leave the repository and which no follow-up takes back, stay a person's at every level of the delegation setting, a merge that starts either among them, and so does a change that loosens what agents may run. Whether a merge into the default branch releases or publishes is a fact the person's declaration states ([COR-072](../../../decisions/core/COR-072-delegation-levels.md) points 7 and 8). Whoever maintains the capability releases a version of a library it ships, where the capability is authored ([visual-communication:DEC-013-shipped-library-releases] point 1).
- **Which pieces need a release.** A draft may lock a version not yet released. A final or published piece locks only released versions (DEC-003 point 8). A piece may be marked final while its lock names a version of the project's own library not yet released, and fails until the version is released ([visual-communication:DEC-017-final-and-published-states] point 2).
- **Where a finding lies, and how severe it is.** A finding fails where it lies in a file the project can correct, a version of its own library not yet released among them. A fault inside a released library version never fails, since only its owner corrects it, in a new release, and a fault that only a combination of versions shows sits at the lock that combines them ([visual-communication:DEC-002-files-and-validation] point 7). Computing a piece's scene places a finding in a library's component at that component's file, in the version the lock names (the capability's list of checks, "Scenes").
- **The designer's loop and the ship call.** The designer mends each failure of a check before any review, and the person makes the ship call on the piece ([visual-communication:DEC-070-ship-call-and-one-round] points 1 and 2).

So a failure a piece's scene shows inside a component of the project's own library fails while the version is not yet released, asks for attention once it is released, and leaves the loop nothing to mend. The release does not see it, since it computes no scene. Such failures include a component given no room by a formula ([visual-communication:DEC-073-zero-sizes-reported] point 4), a division by zero over an empty list, and a stand-in for an export's fact too long for its box ([visual-communication:DEC-016-what-an-export-reads] point 5). Any release does the same, whoever runs it.

The words it uses:
- **The project's own library** is a library the location's list names from the project's own source, neither one the capability ships nor one from another repository (DEC-003 point 4).
- **The release** is the capability's command that releases a version of the project's own library (DEC-003 point 6).
- **A failure a scene shows** is a failure the check finds only by computing a piece's scene: in what the scene draws, or in a value a formula takes there, such as a frame, a size, a text's lines or a division. A finding on what a version declares or holds, such as a component's keys or a picture file, is none, even where computing a scene finds it, since the release reads the version in full.
- **The person, the ship call and a round** are DEC-070's.

## Decision

**The designer releases a version of the project's own library at the person's ship call on a piece that locks it, and when the person asks, and never a shipped library's. The capability's checks and reviewer hold the version to its bar first, and no person need judge it. The designer marks each component's status, and a new major stays the person's. A failure a piece's scene shows inside a released version of the project's own library lies at the piece's lock, where the project corrects it, so it fails.**

### 1. The designer releases the project's own library itself

- **It runs the release.** The release of a version of the project's own library is among the commands the designer runs (DEC-030 point 5), at the times point 2 names. The person need not run it.
- **A write in the working tree.** The release writes only in the working tree, files that fix the version (DEC-003 point 6). It is not the releasing COR-072 point 7 keeps for a person. Whatever carries the version out of the repository, such as a merge, a direct commit to the default branch or a push to a branch others read, is held for a person by that point where it releases or publishes, and for a merge into the default branch the project's person declares whether it does (COR-072 points 7 and 8).
- **Its own, whatever the setting.** The release is the designer's by this record, as what it changes alone is by DEC-070 point 4, and the delegation setting neither widens nor narrows it. This record places no question at a level. The capability's checks and its reviewer check the version first (point 3), and the person is told which versions a ship call will release, and of each version released (point 2).
- **Never by hand.** It writes no released version, and no mark of release, which the release alone writes (DEC-030 point 5).
- **No shipped library, and no other repository's.** Whoever maintains the capability releases a shipped library's version, where the capability is authored (DEC-013 point 1), and the designer releases none. Its body keeps it from that release, as the body keeps apart what a grant cannot (DEC-030 point 5). Nor does it release a library of another repository, which its owner releases.

### 2. When it releases, and what it tells the person

- **When.** It releases a version of the project's own library not yet released in two cases, and in no other:
  - at the person's ship call on a piece whose lock names the version, so the piece may be marked final or published (DEC-003 point 8, DEC-070 point 1);
  - when the person asks for the release, or for a published piece's lock to move to the version, a move the person makes (DEC-003 point 8).
- **Named at the hand-over.** When it hands a piece to the person for the ship call (DEC-070 point 2), it names each version of the project's own library not yet released that the piece's lock names, which the ship call will release. So the person makes the call with the release in view.
- **Dispatched by another agent,** it takes the ship call and the person's ask as whoever dispatched it relays them, as it takes each answer of the person there (DEC-030 point 2).
- **Not before.** A draft may lock a version not yet released, so no round needs a release. A release fixes the version, so each mend the person asked for after it would take a new version.
- **Where the release refuses,** it mends a finding that fails and undoes a break, or asks the person whether to take a new major (point 3), and runs the release again once the version is mended or the person has answered. Where a mend changes what a piece the person shipped draws, that piece goes back to the person, whose ship call was on the piece as it stood (DEC-070 point 1).
- **Never a version that may have gone out.** It changes no version that a final piece's lock names, nor one that an export kept in a piece's record of exports was made under. No file says whether such an export was handed out, and one often goes out before its piece is marked final (DEC-017, Context), so it counts each as handed out. Where the release refuses such a version, it asks the person, and says what it recommends, as for any fix it may not make (DEC-070 point 4).
- **Where the release cannot reach the version** a lock names, such as an older version than the one it takes, which marking a piece final may put back (DEC-017 point 1), it asks the person, and says why.
- **It tells the person** of each version it released, among what it changed (DEC-030 point 2).

### 3. The library's quality is the capability's

- **No person need judge a version.** The person judges each piece, at the ship call (DEC-070 point 1), and need judge no version of the project's own library.
- **The capability's checks and reviewer hold it to the bar.** Before the designer releases a version, the checks of each piece that draws it fail what that piece shows inside it, and the reviewer reads every page of the piece the round drew with it, by the rule sets it reads (DEC-030 point 6, DEC-070 point 2). The release then reads the version in full, a component no piece places included, refuses what fails (DEC-014 point 1), and refuses a break outside a major release (DEC-003 point 7). So in the project's own library, the owner's bar of DEC-030 point 4 is the capability's.
- **The designer marks each component's status.** A release fixes each component's status, which the library's owner marks (DEC-003 point 7). In the project's own library the designer marks it, as it writes the rest of a version not yet released (DEC-030 point 5). No person need judge a version, and the release's comparison holds each stable component to what its status promises (DEC-003 point 7).
- **A new major stays the person's.** Taking a new major is a promise to whatever builds on the library, and the designer cannot see all of it, such as a library or a piece of another repository that takes the version (DEC-003 point 4). So the designer takes none. Where the release refuses a break outside a major release, it undoes the break, or asks the person whether to take a new major, and says what it recommends, as for any fix it may not make (DEC-070 point 4).
- **A project may keep them for a person.** A project's own accepted record may keep the release, or the marking of a status, for a person. The designer then leaves each to the person, as it leaves a write it may not make (DEC-070 point 4).

### 4. No release hides a failure a scene shows

- **The rule.** A failure a scene shows inside a released version of the project's own library lies at the piece's lock, which chose the version. One a record places at what the content placed, as a size the content gave (DEC-073 point 4), lies at the content already, and stays there. The project corrects it in its own files: in the content, or in a new version of its library that the lock then names. So it fails, whoever made the release, and whether or not a loop runs.
- **No reading of the version alone sees it.** The release reads the version in full and computes no scene (DEC-014 point 1), nor does the check of a version alone (the capability's list of checks, "What each run judges"). So the rule places a failure with no check of the version alone. Validation and the viewing step place it alike, a version that cannot be checked alone changes nothing, and a later capability that reads more of a version alone moves no such failure.
- **What it covers.** A fault every piece that draws the component shows, such as a formula that gives no room from roles alone, and one only some piece's content triggers. A fault an edit to a piece triggers inside a version released before.
- **Its message** names the version, the component and the place inside it, and its fix names a new version and the lock's move (DEC-003 point 8).
- **A combination of versions.** A fault only a combination of versions shows lies at the lock that combines them, for every library (DEC-002 point 7). This record changes nothing there: its rule adds the failures a scene shows inside the project's own library. Where the check places such a fault in a version instead, the drift is left open (Implications).
- **What it leaves as it stands:**
  - a finding on what a version declares or holds, which in a released version asks its owner for attention (DEC-002 point 7). The release reads it and refuses each that fails, so no release hides one. One that a later capability finds, by a check it tightened, asks for attention too, since a new version leaves the old version's finding where it lies;
  - a finding read under a lock, which lies in the version where the version shows it alone as well, and at the lock otherwise ([visual-communication:DEC-008-library-role-defaults] point 9);
  - a failure a scene shows inside a released version of a library the project does not own, a copy of a shipped library or a version from another repository, which asks that library's owner for attention (DEC-002 point 7, DEC-013 point 6);
  - a finding that does not fail in a version not yet released, a call for attention or a fact, and the label a released version's word gives in validation (DEC-066 point 2, [visual-communication:DEC-053-letters-across-lines] point 4);
  - a released version whose folder no longer matches its release, whose findings fail (DEC-002 point 7, DEC-003 point 9);
  - a final piece, whose scenes the check does not compute (DEC-002 point 7);
  - a published piece's current copy made with a fact's text the person let through at an export, which no scene shows (DEC-016 point 6).
- **Worked out where it is read.** Where the failure lies, as its level, is worked out each time the check reads it, from the list's mark of release and the library's source, and is never stored. So a scene and a piece's findings record stay as they are ([visual-communication:DEC-005-engine-and-plugins] points 5 and 13), and a release moves such a failure to the lock at once.

## Rationale

**Why the designer releases, and the person need not.** No person need judge a version of the project's own library (point 3). The release reads the version in full and refuses what fails, whoever runs it (DEC-014 point 1), so a person need not run it for the files to be checked. The person's judgement lies on each piece, at the ship call, and point 4 keeps a failure a piece's scene shows from hiding inside a released version.

**Why the release is not the releasing a person keeps.** COR-072 point 7 keeps for a person releasing and publishing, which leave the repository and which no follow-up takes back. The capability's release writes only in the working tree, files that fix a version. Whatever carries the version out of the repository, such as a merge, a direct commit to the default branch or a push to a branch others read, is held for a person by that point where it releases or publishes, and for a merge into the default branch the project's person declares whether it does (COR-072 points 7 and 8). So the record need not say which of those acts releases, and holds however a project's versions leave it. What it widens is what the designer runs, which COR-072 point 7 keeps for a person at every level, so a person accepts it.

**Why the release is the designer's whatever the setting.** The release is no question kept for the person: this record gives it to the designer, as DEC-070 gave it what it changes alone (DEC-070 point 4), so the setting neither widens nor narrows it. What checks the designer's choice is the capability's checks and its reviewer, before the release (point 3), and the person, who sees at the hand-over which versions the ship call will release.

**Why at the ship call and at the person's word.** A draft locks a version not yet released, so a release serves only a piece that may lock nothing else, and a move of a published piece's lock, which the person makes. Before the ship call, the person may still ask for mends, and each mend to a released version takes a new one. At the ship call, the piece stands as the person shipped it, so the release fixes what the person saw. Named at the hand-over, the release is part of what the person decides.

**Why never change a version that may have gone out.** A final piece's lock, and an export handed out, say which versions drew what went out. A version changed after would leave them naming content the files were not made under, and the check, which holds a final piece only to its exported files (DEC-002 point 7), would not see it. No file says whether an export was handed out, so the designer counts each export its piece's record keeps as handed out. A new version serves no final piece, whose lock never moves (DEC-003 point 8). So the person decides.

**Why quality is the capability's.** A version shows its quality in what it draws, which the checks and the reviewer read on each piece that draws it, and in what it holds, which the release reads in full. The ship call reads the version as each piece draws it. A judgement of the version apart from its pieces would be one the person makes with no check beside it. A status is part of the version, which no person need judge, and the release's comparison holds each stable component to what its status promises (DEC-003 point 7), so the designer marks it. A new major is a promise to whatever builds on the library, and the designer cannot see all of it, such as a library or a piece of another repository (DEC-003 point 4), so taking one stays the person's. A project that wants a person to run the release, or to mark each status, keeps either by its own record.

**Why a failure a scene shows lies at the piece's lock.** A released version is fixed, so the project corrects a failure a scene shows inside it in other files of its own: in a new version, which the piece's lock then names, or in the content. The lock is the file it edits, so the finding lies there. DEC-002 point 7 places a fault only a combination of versions shows at the lock for the same reason, since the project chose that lock, and DEC-055 places a text drawn too small at the piece's file, where no library alone is at fault ([visual-communication:DEC-055-smallest-text-size], Rationale, "Why at the piece's file"). So DEC-002 point 7's test fails it where it lies, as the test stands. No release changes that, so the rule holds for every release: the designer's, a person's made while a loop runs, and one made before an edit triggers the fault.

**Why the line runs at what a scene shows.** The release reads what the version declares and holds, in full, and refuses what fails there (DEC-014 point 1). What it cannot read is what a piece's scene computes from the version, with the piece's content and its other versions. A finding on what the version declares or holds lies in the version, since a new version leaves the old version's finding where it lies, and only the old version's removal clears it, which a lock may forbid (DEC-003 point 4). The line is drawn by what a finding judges, not by comparing two readings, so no reading of the version alone places a failure, and none a later capability adds moves one.

**Why DEC-002 point 7 takes one sentence.** Its test stays: a finding fails where it lies in a file the project can correct. Its line between a version not yet released and a released one stays too, and DEC-066's fact from a released version's word rests on that line. Point 4 places a failure a scene shows at the piece's lock, beside the fault only a combination of versions shows, which DEC-002 point 7 places there. One sentence after that one says so, so each record that cites DEC-002 point 7 finds it. Each sentence that says a finding inside a released version asks for attention stays true, since point 4 places this one at the piece.

### What it costs

- **A published piece fails** where its lock names a released version of the project's own library inside which its scene shows a failure, where it asked for attention. Its mend is a chain: a new version, its release, a move of the lock that a person reviews with a before-and-after (DEC-003 point 8), and a new export of the piece's current copy, which fails while it is stale ([visual-communication:DEC-006-work-outside-the-engine-and-outputs] point 8). A pinned draft's mend takes the person's move too. Meanwhile the project's checks fail on every change, where they run validation, and where the project's level is land, no change merges on the person's standing authorisation, since such a merge needs those checks to pass (COR-072 point 5).
- **The upgrade that brings this rule fails pieces in its own change.** Where a failure lies is worked out where it is read (point 4). So once a project takes the release of the capability that carries this rule, each piece that is not final whose findings record holds a failure a scene shows inside a released version of its own library fails, though nothing in the piece changed.
- **A later check reaches a piece at its render.** A release of the capability that adds or tightens a check a scene shows reaches a piece at its next render (DEC-005 point 13). It fails the piece there, where the check finds a failure inside a released version of the project's own library, in a project that changed nothing in it.
- **A message that carries the place.** The finding lies at the lock, so its message names the version, the component and the place inside it.
- **A shipped piece sent back.** Where the release refuses and the mend changes what a piece the person shipped draws, the person makes the ship call again.
- **Only the body keeps the designer from a shipped library's release,** where the capability is authored, as only the body keeps apart what a grant cannot (DEC-030 point 5).
- **No person need read a version.** A version that the checks and the reviewer pass, and that a person would have refused, is released, and so is a status a person would have marked otherwise, unless the project keeps the release or the marking of a status for a person (point 3). The person sees the version only as each piece draws it.
- **A break waits on the person.** Where the release refuses a break that the designer does not undo, the version waits for the person's word on a new major, and so does the release a ship call asked for (point 3).
- **A lowered level takes no release back.** A person who lowers their level does not take the release back from the designer. Their hold on it is its two times: their ship call and their own ask. Where another agent dispatches the designer, both reach it as that agent relays them (point 2), so the hold is only as sure as the relay.
- **A drift left as it is.** A fault only a combination of versions shows that the check places in a version, such as a library's name that meets a top group of the shared roles of the foundations a lock names ([visual-communication:DEC-004-brands-and-notations] point 7), keeps asking for attention inside a released version of the project's own library until the drift is mended (Implications, "Left open").

### Alternatives considered

- **The release left to the person,** as the designer's body has it. Not taken: no person need judge a version (point 3), and the release reads it in full whoever runs it, so each release would wait on a person for a judgement this record does not ask of them.
- **The designer runs the release's read and comparison, and hands the person the command.** Not taken: the person would run a command whose answer the designer already has.
- **The release held for a person as the releasing COR-072 point 7 keeps.** Not taken: it writes only in the working tree, and whatever carries the version out of the repository is already held for a person by that point where it releases or publishes, a merge into the default branch as the project's person declares it (COR-072 points 7 and 8).
- **The designer taking a new major too,** as it marks a status. Not taken: a new major is a promise to whatever builds on the library, and the designer cannot see all of it (point 3).
- **A person marking each status.** Not taken: no person need judge a version, and the release's comparison holds each stable component to what its status promises (DEC-003 point 7). A project that wants it keeps it by its own record (point 3).
- **Released once it lands,** as a shipped version is (DEC-013 point 1). Not taken: the check reads whether a version is released from the files alone, and the mark in the list is that fact (DEC-003 point 4). Nor would a merge judge the version, which no person need judge (point 3).
- **The designer releasing each version once it judges it done,** with no piece needing it. Not taken: a draft needs no release, and a version released before the ship call takes a new version for each mend the person asks for.
- **The release computing the scenes of each piece that locks the version, and refusing a failure it finds inside it.** Not taken: it would not see a fault an edit made after the release triggers, and it would compute scenes in a command that reads a version alone (DEC-014 point 1).
- **The finding kept inside the released version, at the level it takes before the release.** Not taken: it would fail in a file the project cannot correct, which moves DEC-002 point 7's test, and every sentence that says a finding inside a released version asks for attention would need an exception.
- **A mark that a piece's loop runs, read by the check.** Rejected: validation reads the files as they are, no file records a loop, and the designer would write the mark it is judged by.
- **A failure a piece shows told apart from the version's own by checking the version alone,** as a fault under a lock is (DEC-008 point 9). Not taken: the viewing step checks no version alone, so it and validation would place one failure apart, and a later capability whose check of the version alone came to find the failure would move it into the version, where it would only ask for attention.
- **Every finding inside a released version of the project's own library at the piece's lock, one on what the version declares or holds included.** Not taken: the release reads such a finding and refuses each that fails, so one arises only from a later capability's tightened check. At each lock it would fail every piece that locks an older version for what the release of its day passed.
- **Every failure a scene shows inside the project's own library at the piece's lock, released or not,** its fix varying with the version's state, as DEC-055 point 7 places a share's fault at the lock in every state. Not taken: in a version not yet released, the file a person edits to mend it is the version's, where a finding points (the capability's list of checks, "Scenes"), and the rule would move each such finding with no failure gained.
- **The rule for a failure a scene shows inside a copy of a shipped library or a version from another repository.** Not taken: no project corrects such a version, since the command that brings a shipped library in writes the copy as it is authored, and another repository's version is fetched whole at its release (DEC-003 point 4, DEC-013 point 6). Only its owner mends it, in a new release, so it asks that owner for attention (DEC-002 point 7), save a fault only a combination of versions shows, which lies at the lock for every library (point 4).
