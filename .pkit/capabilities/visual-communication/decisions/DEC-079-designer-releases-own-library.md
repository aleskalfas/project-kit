**In plain terms:** the graphic designer releases a version of the project's own library itself, and the person does not. Such a release fixes a version inside the repository, and nothing leaves it: another repository takes a version only by a fetch its own person runs. So it is not the releasing that stays a person's at every level. A shipped library's release stays with whoever maintains the capability, and reaches projects only through the capability's own release, which a person makes. The designer releases at the person's ship call on a piece whose lock names the version, and when the person asks. The library's quality is the capability's: its checks and its reviewer hold a version to its bar before the designer releases it, and the person judges pieces, not versions. And no release hides a piece's failure. A failure the check finds for a piece inside a released version of the project's own library, which the version checked alone does not show, lies at the piece, where the project corrects it, so it fails.

## Context

[visual-communication:DEC-066-meant-overlaps] left to a record of its own whether the designer may release a version of the project's own library ([project-kit#3398](https://github.com/aleskalfas/project-kit/issues/3398)). Its reviews found that such a release turns a failure the designer's loop found into a call for attention, a way for a bad design to pass.

What holds:
- **What the designer writes and runs.** It writes a version not yet released of the project's own library, and never a released one. What commands write, a release among them, stays theirs, and the designer runs those commands where its body says ([visual-communication:DEC-030-design-agents] point 5). Its body leaves releasing a library version to the person.
- **What the release does.** It reads the version in full, alone, computes no scene, and refuses a finding that fails ([visual-communication:DEC-014-own-library-needed-release] point 1). It compares each stable component with the library's previous release, and refuses a break outside a major release ([visual-communication:DEC-003-change-over-time] point 7). It then writes the release the version needs into the version's file, and the mark of release and the hash into the location's list (DEC-003 points 4 and 6, DEC-014 point 1).
- **What stays a person's.** Releasing and publishing, which leave the repository and which no follow-up takes back, stay a person's at every level of the delegation setting ([COR-072](../../../decisions/core/COR-072-delegation-levels.md) point 7). Another repository takes a version of the project's own library by a fetch, whole at its release (DEC-003 point 4). A shipped library's version reaches projects only through a release of the capability, and whoever maintains the capability releases it, where the capability is authored ([visual-communication:DEC-013-shipped-library-releases] point 1).
- **Which pieces need a release.** A draft may lock a version not yet released. A final or published piece locks only released versions (DEC-003 point 8). A piece may be marked final while its lock names a version of the project's own library not yet released, and fails until the version is released ([visual-communication:DEC-017-final-and-published-states] point 2).
- **Where a finding lies, and how severe it is.** A finding fails where it lies in a file the project can correct, a version of its own library not yet released among them. A fault inside a released library version never fails, since only its owner corrects it, in a new release, and a fault that only a combination of versions shows sits at the lock that combines them ([visual-communication:DEC-002-files-and-validation] point 7). The check tells a fault a version shows alone from one only a lock shows by checking the version alone (the capability's list of checks, "Under a lock").
- **The designer's loop and the ship call.** The designer mends each failure of a check before any review, and the person makes the ship call on the piece ([visual-communication:DEC-070-ship-call-and-one-round] points 1 and 2).

So a fault inside a component of the project's own library that only a piece shows fails while the version is not yet released, asks for attention once it is released, and leaves the loop nothing to mend. The release does not see it, since it reads the version alone. Such faults are a division by zero over an empty list, a stand-in for an export's fact too long for its box ([visual-communication:DEC-016-what-an-export-reads] point 5), and a library's name that meets a top group of the shared roles of the foundations a piece's lock names ([visual-communication:DEC-004-brands-and-notations] point 7). Any release does the same, whoever runs it.

The words it uses:
- **The project's own library** is a library the location's list names from the project's own source, neither one the capability ships nor one from another repository (DEC-003 point 4).
- **The release** is the capability's command that releases a version of the project's own library (DEC-003 point 6).
- **A version checked alone** is the check's reading of a library version with no piece, and a *finding for a piece* is one the check gives as it judges a piece, from its scenes or under its lock (the capability's list of checks, "What each run judges").
- **The person, the ship call and a round** are DEC-070's.

## Decision

**The designer releases a version of the project's own library at the person's ship call on a piece that locks it, and when the person asks, and never a shipped library's. The capability's checks and reviewer hold the version to its bar first, and no person judges it. A failure the check finds for a piece inside a released version of the project's own library, which the version checked alone does not show, lies at the piece, where the project corrects it, so it fails.**

### 1. The designer releases the project's own library itself

- **It runs the release.** The release of a version of the project's own library is among the commands the designer runs (DEC-030 point 5), at the times point 2 names. The person does not run it.
- **At every level.** The release is the designer's by this record, and the delegation setting neither widens nor narrows it (COR-072 point 13). The capability's checks and its reviewer check the version (point 3), and the person is told of each version released (point 2).
- **Not the releasing a person keeps.** COR-072 point 7 keeps for a person the releasing that leaves the repository. A release of the project's own library fixes a version inside the repository, and nothing leaves it. Another repository takes the version only by a fetch its own person runs (DEC-003 point 4). So the release is not that releasing, and a merge that lands it starts none.
- **Never by hand.** It writes no released version, and no mark of release, which the release alone writes (DEC-030 point 5).
- **No shipped library, and no other repository's.** Whoever maintains the capability releases a shipped library's version, where the capability is authored, and that version reaches projects only through the capability's own release, which a person makes (DEC-013 point 1). The designer releases none. Where the capability is authored, the same command, with its flag for a shipped library, makes that release, and it cannot tell who runs it. So the designer's body keeps the designer from it, as the body keeps apart what a grant cannot (DEC-030 point 5). Nor does it release a library of another repository, which that repository releases.

### 2. When it releases, and what a refusal leaves

- **When.** It releases a version of the project's own library not yet released in two cases, and in no other:
  - at the person's ship call on a piece whose lock names the version, so the piece may be marked final or published (DEC-003 point 8, DEC-070 point 1);
  - when the person asks for the release, or for a published piece's lock to move to the version, a move the person makes (DEC-003 point 8).
- **Not before.** A draft may lock a version not yet released, so no round needs a release. A release fixes the version, so each mend the person asked for after it would take a new version.
- **Where the release refuses,** it mends the version and runs the release again. Where a mend changes what a piece the person shipped draws, that piece goes back to the person, whose ship call was on the piece as it stood (DEC-070 point 1).
- **Never a version that went out.** It changes no version that a final piece's lock names, nor one that an export of a piece was made under once the person handed that export out. What went out was drawn by the version as it stands. Where the release refuses such a version, it asks the person, and says what it recommends, as for any fix it may not make (DEC-070 point 4).
- **It tells the person** of each version it released, among what it changed (DEC-030 point 2).

### 3. The library's quality is the capability's

- **No person judges a version.** The person does not look after the project's own library, and judges none of its versions. The person judges each piece, at the ship call (DEC-070 point 1).
- **The capability's checks and reviewer hold it to the bar.** Before the designer releases a version, the checks of each piece that draws it fail what that piece shows inside it, and the reviewer reads every page of the piece the round drew with it, by the rule sets it reads (DEC-030 point 6, DEC-070 point 2). The release then reads the version in full, a component no piece places included, refuses what fails (DEC-014 point 1), and refuses a break outside a major release (DEC-003 point 7). So in the project's own library, the owner's bar of DEC-030 point 4 is the capability's.
- **The owner's choices are the designer's.** A release fixes each component's status, which the library's owner marks (DEC-003 point 7). Where the comparison refuses a break, the owner chooses between undoing it and taking a new major. The person does not look after the project's own library, so the designer makes both choices, unless an accepted record keeps them for a person.

### 4. No release hides a piece's failure

- **The rule.** A failure the check finds for a piece inside a released version of the project's own library, which that version checked alone does not show, lies at the piece. It lies at the piece's lock, which chose the version, as a fault only a combination of versions shows does (DEC-002 point 7). One a record places at what the content placed, as a size the content gave ([visual-communication:DEC-073-zero-sizes-reported] point 4), lies at the content already, and stays there. The project corrects it in its own files: in the content, or in a new version of its library that the lock then names. So it fails, whoever made the release, and whether or not a loop runs.
- **Told apart by the version alone.** A finding the version shows alone as well lies in the version, as one found under a lock does (the capability's list of checks, "Under a lock"). So the check checks alone each released version of the project's own library that a piece's lock names, where a finding for the piece lies inside it, as the check of one piece does. That covers an older version of a major, which a run over the whole project checks only under the locks that name it.
- **What it covers.** A fault every piece shows, and one only some piece's content triggers. A fault an edit to a piece triggers inside a version released before. And a fault only the piece's lock shows, inside the version, which the release, reading the version alone, does not judge either.
- **Its message** names the version, the component and the place inside it, and its fix names a new version and the lock's move (DEC-003 point 8).
- **What it leaves as it stands:**
  - a finding the version shows alone, which in a released version asks its owner for attention (DEC-002 point 7). The release refuses each such finding that fails, so no release hides one. One that a later capability finds, by a check it tightened, asks for attention too, since a new version leaves the old version's finding where it lies;
  - a finding inside a released version of a library the project does not own, a copy of a shipped library or a version from another repository, which asks that library's owner for attention (DEC-002 point 7, DEC-013 point 6);
  - a finding that does not fail in a version not yet released, a call for attention or a fact, and the label a released version's word gives in validation (DEC-066 point 2, [visual-communication:DEC-053-letters-across-lines] point 4);
  - a released version whose folder no longer matches its release, whose findings fail (DEC-002 point 7, DEC-003 point 9);
  - a final piece, whose scenes the check does not compute (DEC-002 point 7);
  - a published piece's current copy made with a fact's text the person let through at an export, which no scene shows (DEC-016 point 6).
- **Worked out where it is read.** Where the finding lies, as its level, is worked out each time the check reads it, from the list's mark of release and the library's source, and is never stored. So a scene and a piece's findings record stay as they are (DEC-005 points 5 and 13), and validation and the viewing step place it alike.

## Rationale

**Why the designer releases, and the person does not.** The person judges no version of the project's own library (point 3). The release reads the version in full and refuses what fails (DEC-014 point 1), so a person who runs it adds no check of the files and no judgement of the version, only a wait. The person's judgement lies on each piece, at the ship call, and point 4 keeps a failure a piece shows from hiding inside a released version.

**Why it is not the releasing a person keeps.** COR-072 point 7 keeps for a person what leaves the repository and what no follow-up takes back, since a revert cannot recall what a merge started (COR-072 point 12). A release of the project's own library writes files inside the repository, in a change reviewed and merged as any other. Another repository takes a version by its own person's fetch, an act of that repository. A shipped library's version leaves only with the capability's release, which a person makes. This reading of COR-072 point 7 is the capability's, for its own release, until another capability has a release that stays inside the repository (Implications).

**Why at the ship call and at the person's word.** A draft locks a version not yet released, so a release serves only a piece that may lock nothing else, and a move of a published piece's lock, which the person makes. Before the ship call, the person may still ask for mends, and each mend to a released version takes a new one. At the ship call, the piece stands as the person shipped it, so the release fixes what the person saw.

**Why never change a version that went out.** A final piece's lock, and an export handed out, say which versions drew what went out. A version changed after would leave the lock naming content the files were not made under, and the check, which holds a final piece only to its exported files (DEC-002 point 7), would not see it. A new version serves no final piece, whose lock never moves (DEC-003 point 8). So the person decides.

**Why quality is the capability's.** A version shows its quality in what it draws, which the checks and the reviewer read on each piece that draws it, and in what it holds, which the release reads in full. The ship call reads the version as each piece draws it. A judgement of the version apart from its pieces would be one the person makes with no check beside it. A status and a new major rest on what the library holds and on what builds on it, which the designer that built the library knows.

**Why a failure for a piece lies at the piece.** A released version is fixed, so the project corrects a fault a piece shows inside it in other files of its own: in a new version, which the piece's lock then names, or in the content. DEC-002 point 7 places a fault that only a combination of versions shows at the lock that combines them, which the project chose. A failure a piece shows inside a version that does not show it alone is such a combination: the version with the piece's content, or with the piece's other versions. DEC-055 places a text drawn too small at the piece's file for the same reason, since no library alone is at fault ([visual-communication:DEC-055-smallest-text-size], Rationale, "Why at the piece's file"). So it lies where the project corrects it, and DEC-002 point 7's test fails it there, as the test stands. No release changes that, so the rule holds for every release: the designer's, a person's made while a loop runs, and one made before an edit triggers the fault.

**Why the line runs at what the version shows alone.** The release reads the version alone, and refuses what fails there (DEC-014 point 1). What it cannot read is what a piece does with the version: its content and its lock. A finding the version shows alone lies in the version, since a new version leaves the old version's finding where it lies, and only the old version's removal clears it, which a lock may forbid (DEC-003 point 4). Told apart by the version checked alone, a finding takes one place, whichever reading gives it: validation, a check of one piece, or the viewing step.

**Why DEC-002 point 7 is not edited.** Its test stays: a finding fails where it lies in a file the project can correct. Its line between a version not yet released and a released one stays too, and DEC-066's fact from a released version's word rests on that line. This record places a finding at the piece, as DEC-002 point 7 places a fault only a combination of versions shows. So each sentence that says a finding inside a released version asks for attention stays true, and only those that placed a piece's failure inside a released version change (Implications).

### What it costs

- **A published piece fails** where its lock names a released version of the project's own library inside which its scene shows a failure, where it asked for attention. Its mend is a chain: a new version, its release, a move of the lock that a person reviews with a before-and-after (DEC-003 point 8), and a new export of the piece's current copy, which fails while it is stale ([visual-communication:DEC-006-work-outside-the-engine-and-outputs] point 8). A pinned draft's mend takes the person's move too. Meanwhile the project's validation fails on every change.
- **An upgrade fails pieces nobody touched.** A change to the capability that adds or tightens a check a scene shows can fail a published piece in a project that changed nothing else, and the designer meets failures in pieces it was not asked about. Where the capability is authored, a change that tightens such a check fails that repository's own published pieces in the same change.
- **More checked alone.** The check checks alone each released version of the project's own library that a piece's lock names, where a finding for the piece lies inside it, within validation's bound.
- **A message that carries the place.** The finding lies at the lock, so its message names the version, the component and the place inside it.
- **A shipped piece sent back.** Where the release refuses and the mend changes what a piece the person shipped draws, the person makes the ship call again.
- **Only the body keeps the designer from a shipped library's release,** where the capability is authored, since the command cannot tell who runs it.
- **No person reads a version.** A version that the checks and the reviewer pass, and that a person would have refused, is released. The person sees it only as each piece draws it.

### Alternatives considered

- **The release left to the person,** as the designer's body has it. Not taken: the person judges no version, so the release would wait on someone who adds nothing to it.
- **The designer runs the release's read and comparison, and hands the person the command.** Not taken: the person would run a command whose answer the designer already has.
- **A release of the project's own library counted among the releasing a person keeps** (COR-072 point 7). Not taken: nothing leaves the repository, and another repository's fetch is its own person's act.
- **Released once it lands,** as a shipped version is (DEC-013 point 1). Not taken: the check reads whether a version is released from the files alone, and the mark in the list is that fact (DEC-003 point 4). Nor would a person's merge judge the version, which no person judges (point 3).
- **The designer releasing each version once it judges it done,** with no piece needing it. Not taken: a draft needs no release, and a version released before the ship call takes a new version for each mend the person asks for.
- **The release computing the scenes of each piece that locks the version, and refusing a failure it finds inside it.** Not taken: it would not see a fault an edit made after the release triggers, and it would compute scenes in a command that reads a version alone (DEC-014 point 1).
- **The finding kept inside the released version, at the level it takes before the release.** Not taken: it would fail in a file the project cannot correct, which moves DEC-002 point 7's test, and every sentence that says a finding inside a released version asks for attention would need an exception.
- **A mark that a piece's loop runs, read by the check.** Rejected: validation reads the files as they are, no file records a loop, and the designer would write the mark it is judged by.
- **Every finding inside a released version of the project's own library moved to the piece, one the version shows alone included.** Not taken: a new version leaves the old version's finding where it lies, so only the old version's removal would clear it, which a lock may forbid. A change to the capability that tightens a check would fail every project that holds an older version.
- **The rule for a failure a piece's scene shows, and not for one its lock shows.** Not taken: a name that meets a top group of the shared roles of the foundations the lock names is a failure the release does not see either, and it would ask for attention once the version is released.
- **The rule for every library a piece locks.** Not taken: the project makes no version of a shipped library or of another repository's, so only that library's owner mends a fault inside it (DEC-002 point 7).
