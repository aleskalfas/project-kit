# visual-communication capability

Visual work made from reusable parts. A *piece*, such as a presentation or a figure in a documentation page, keeps its content as data. Libraries give it its look: components that arrange and draw the content, brands that hold the values (colours, fonts, sizes) and may draw a layout their own way, and notations that say what a thing is. Several renderers draw the same piece, as a vector picture, a web page or objects on a whiteboard service, and a piece is handed out as a file such as a PDF. A project installs the capability when its visuals should share a look, reuse what was made before, appear under more than one brand or in more than one language, and be checked like the rest of its work.

## What this capability ships

- **The commands** `pkit visual …`, also reachable as `pkit visual-communication …`. Each is described under [Commands](#commands).
- **The file formats,** format 1: a schema for each kind of file a piece, a library or a command writes, under `schemas/`. Each file names its schema in its first lines ([The binding](files.md#the-binding)), so `pkit validate` checks its shape.
- **The foundations library:** a few shared roles, the shared axes, six colour families, and three top components: `figure`, for a figure, `deck`, for a presentation, and `site`, for a web page or a portal ([The foundations](files.md#the-foundations)). Its version being built adds an order's roles, the two ends a brand gives an order's colour steps and the text on them, apart from the families. Its versions 1.0.0 and 1.1.0 are released, each under `releases/foundations/<version>/`, and its version being built stays under `libraries/foundations/` ([The libraries the capability ships](files.md#the-libraries-the-capability-ships)). Release 1.1.0 is the first to hold `site`, and `pkit visual add foundations` takes it.
- **The starter library:** patterns, such as `layers` and `network`, and blocks, such as `card` and `code`, each experimental. Its README lists each pattern by the question it answers, then each block ([The patterns, by the question they answer](libraries/starter/README.md#the-patterns-by-the-question-they-answer), [The blocks](libraries/starter/README.md#the-blocks)). `pkit visual add starter` brings it in. Its version 1.0.0 is released, under `releases/starter/1.0.0/`, and needs release 0.3.0. Its version being built stays under `libraries/starter/`. It adds the web parts, such as `header` and `form`, which draw a site's pages at every size ([The web parts, by their job on a page](libraries/starter/README.md#the-web-parts-by-their-job-on-a-page)). It draws each concept's sign beside its colour, and adds the pattern `legend`, which says what each colour and sign stands for ([Signs](libraries/starter/README.md#signs)). Its `layers` shades each level by its place, a step of an order, drawn by the block `level`, under foundations that declare an order's ends, as their version being built does ([An order's steps](libraries/starter/README.md#an-orders-steps), [Values, states and colour](components.md#values-states-and-colour)). So `pkit visual add starter --being-built` takes them. They need the foundations' release 1.1.0, which `pkit visual add foundations` takes.
- **The neutral brand:** a brand to start from, with a value for every shared role and the fonts it draws in ([The neutral brand](files.md#the-neutral-brand)). It gives no logo. Its version being built gives a desktop's, a tablet's, a phone's and a projector's sizes, and an order's two ends, in greys. `pkit visual add neutral` brings it in. Its version 1.0.0 is released, under `releases/neutral/1.0.0/`, and its version being built stays under `libraries/neutral/`.
- **Five plugins:** the SVG renderer, which draws the previews and the SVG exports; the PDF renderer, which draws a piece as one PDF for each language and combination of modes; the HTML renderer, which draws a piece's pages as real text over shapes in the HTML exports, and whose pages `pkit visual look` draws through a browser; the CSS code writer, which writes a brand out as CSS variables; and the JSON code writer, which writes a brand's resolved values as one JSON document ([Plugins](outputs.md#plugins), [The SVG renderer](outputs.md#the-svg-renderer), [The PDF renderer](outputs.md#the-pdf-renderer), [The HTML renderer](outputs.md#the-html-renderer), [Written code](outputs.md#written-code), [The JSON code writer](outputs.md#the-json-code-writer)).
- **The check,** the `visual-communication:check` member of `pkit validate` ([In `pkit validate`](checks.md#in-pkit-validate)).
- **Two agents:** `graphic-designer`, which designs a piece from its brief and builds the project's own libraries ([The designer](#the-designer)), and `graphic-design-reviewer`, which reads a piece's drawn pages and reports what no check measures ([The reviewer](#the-reviewer)).
- **The skill** `visual-author`, which guides whoever draws a piece, from its first files to pages that read ([Drawing a piece](#drawing-a-piece)).
- **Its operational rules,** the loaded rule set `VIS` in `rule-sets/vis.md` and the file generated from it, `rules.md` ([COR-070](../../decisions/core/COR-070-capability-loaded-rules.md)). Wherever the capability is installed, every session loads `rules.md` ([A capability's rules](../../rules/README.md#a-capabilitys-rules)). Its rules say how an agent goes on where the session's sandbox stops a look ([visual-communication:DEC-024-outside-programs-sandbox] point 6).
- **The rules of visual communication,** in two rule sets ([visual-communication:DEC-028-principles-of-visual-communication] point 2). `COMM`, in `rule-sets/comm.md`, asks whether a piece says the right thing. `GRAPHIC`, in `rule-sets/graphic.md`, asks whether it looks right. A project's own rule set may inherit either, as in `inherits: [visual-communication:COMM@1]` ([COR-051](../../decisions/core/COR-051-rule-sets.md) point 7). They bind on no piece yet, since a piece's content is not something rules bind on. Until then they guide whoever designs or judges a piece (DEC-028 point 5).
- **Its design knowledge,** in [`design-knowledge/`](design-knowledge/README.md): what the published practice of visual communication teaches, a short file for each topic, each idea credited to its author, and an index that says when to read each topic ([visual-communication:DEC-030-design-agents] point 8). The designer and the reviewer read it. It holds no rule, no value and no threshold.
- `decisions/DEC-NNN-*.md`: the principles every piece, library and renderer follows.

No notation or producer ships ([Notations](files.md#notations), [Plugins](outputs.md#plugins)). A project writes its own notations, and may write its own brand ([Brands](files.md#brands)). `pkit visual produce` has no producer to run yet, so a piece that declares a produced picture cannot be given one ([Produced pictures](outputs.md#produced-pictures)). A piece shows a picture of its own, such as a photo, from a picture file it holds ([Picture files](files.md#picture-files)).

The pages beside this README are the reference:

- [The files of the visual work](files.md): the working folder, the piece, its content, libraries, brands, notations and keys.
- [Components](components.md): a component's file, formulas, layouts and how text is measured.
- [What is made from a piece](outputs.md): renderers, exports, produced pictures and written code.
- [What the check reports](checks.md): every finding, its severity, the findings record and the fingerprint.

## Adopter setup

Install the capability, then sync, so the check's dependencies are in place before `pkit validate` runs it offline ([In `pkit validate`](checks.md#in-pkit-validate)):

```
pkit capabilities install visual-communication
pkit sync
```

The visual work lies in one folder of the repository, the *location*: `visual/` at the top of the repository, unless the project names another. Nothing needs configuring before the first command: the first command that writes there records the location in the capability's configuration. [The location](files.md#the-location) says how it is found and recorded. Installing the capability also grants the designer the location, in the agents overlay ([The designer](#the-designer)).

Every piece's lock names the foundations ([The lock](files.md#the-lock)), so bring them into the location first:

```
pkit visual add foundations
```

A library the capability ships reaches the location only through [`pkit visual add`](#pkit-visual-add-library). No install, sync or upgrade of the capability writes there, so an upgrade alone changes no piece's look ([What the location holds](files.md#what-the-location-holds)). Run the command again after an upgrade to take the newest released version, and to bring each copy of the library up to date.

## Drawing a piece

The skill `visual-author` walks steps 1 to 6 with you, or with the agent that draws for you, such as [the designer](#the-designer). `pkit sync` deploys it with the other skills, in Claude Code as `.claude/skills/visual-author/` ([the Claude Code adapter's README, `deploy-skills.sh`](../../adapters/claude-code/README.md#deploy-skillssh)). Its `piece.md` starts a piece, and its `build-loop.md` renders, checks, reads and mends it until it can stop.

1. **Bring the libraries.** [`pkit visual add <library>`](#pkit-visual-add-library) copies a library the capability ships, such as the foundations, into the location's library folder, and lists it in `libraries/libraries.yaml`. Put each other library version a piece uses there yourself, and list it ([The library folder](files.md#the-library-folder)). A piece needs a brand: bring the neutral brand, or write the project's own ([Brands](files.md#brands)).
2. **Write the piece.** A piece is a folder under `pieces/`: its `piece.yaml` names its libraries, languages, modes and exports, and its content names the components that draw it ([A piece](files.md#a-piece)). [`pkit visual new <piece>`](#pkit-visual-new-piece) stamps its first files from your choices, and you fill its content and its brief. A picture it shows, such as a photo, lies in its `pictures/` folder ([Picture files](files.md#picture-files)). Its brief, where it keeps one, says what each page must show and why its design is as it is ([The brief](files.md#the-brief)).
3. **Draw it.** `pkit visual render <piece>` writes the piece's lock, computes its scenes, keeps their findings in `findings.yaml`, and draws an SVG preview of each scene. Open the previews under `.pkit/capabilities/visual-communication/project/local/previews/<piece>/` ([The clone's local folder](files.md#the-clones-local-folder)).
4. **See it.** [`pkit visual look <piece>`](#pkit-visual-look-piece) draws each page as an image, with a report of what the images cannot show ([The viewing step](outputs.md#the-viewing-step)). [The reviewer](#the-reviewer) can read them for you.
5. **Check it.** `pkit visual check <piece>`, or `pkit validate`, reports what the piece breaks ([What the check reports](checks.md)).
6. **Commit the piece's folder:** `piece.yaml`, the content, its brief, its `pictures/` and `findings.yaml` ([The findings record](checks.md#the-findings-record)). The previews stay local to the clone ([The clone's local folder](files.md#the-clones-local-folder)).
7. **Hand it out.** `pkit visual export <piece>` makes a numbered export in each format the piece declares, and records the version in the piece's `exports.yaml`. Commit `exports.yaml`; the exported files stay local until they are handed out ([Exports](outputs.md#exports)). A published piece's export also writes its current copy, the unnumbered files a page links to. Commit that too ([The current copy](outputs.md#the-current-copy)).

A brand's values reach code the same way: a declaration under the location's `code/` folder names the brand and where the code goes, and `pkit visual write-code <name>` writes it ([Written code](outputs.md#written-code)).

## Commands

Every command runs from anywhere in the project: it finds the project root as the nearest folder, from where it runs upwards, that holds the installed capability. `add`, `new`, `render`, `produce`, `export`, `mark-final`, `take-up`, `upgrade` and `prune` write in the location, so where none is recorded they take `visual/` and record it, or the path `--location <path>` names ([How a command finds it](files.md#how-a-command-finds-it)). `release` writes in a location that holds the library already, and records none. With `--shipped` it writes in the capability's own folder and `.changes/unreleased/` instead. `look` and `before-after` write only in the clone's local folder, and record no location. A command prints `error: …` and exits 1 when it refuses, or when a write fails. Every check that can refuse runs before its first write, so a refused command has written nothing. Where a write fails, the error names the file the command could not write and why, and the command leaves every file as it was before the run: it removes each file the run made, writes back each file it changed, puts back each folder it replaced or removed, and takes back the location it recorded. It names each file it could not put back. Two commands write before they can refuse. `produce` hands the producer its inputs in the capability's local folder, outside the location, and that hand-over stays as it was written ([Produced pictures](outputs.md#produced-pictures)). `look` holds the fonts it hands its tool in a temporary folder there, which the run removes, and it may leave the local folder itself ([The viewing step](outputs.md#the-viewing-step)). Through a browser it holds the page files and the browser's profile there in the same way ([The HTML renderer's pages](outputs.md#the-html-renderers-pages)).

### `pkit visual status`

Shows where the visual work lies, and each piece with its state and its lock.

- **Prints** the location, and whether the configuration records it or it is the default, not recorded yet. Then each piece under `pieces/`, with its state, whether a draft is pinned, and the version of each library its lock names. A draft with no lock yet says that its first render writes one. A published piece with none says to set it back to a draft for that render. A final piece with none says to write back the lock of the version handed out ([The lock](files.md#the-lock)).
- **Writes** nothing.
- **Exits** 1 when the configuration cannot be read, or records a location that is refused or missing; 0 otherwise.

### `pkit visual work-paths`

Answers the paths [the designer](#the-designer)'s grant takes by default. It is the query the capability names for the category `visual-communication.work`, which install and `pkit agents reconcile --write` ask ([the agents README, "A capability's write categories"](../../agents/README.md#a-capabilitys-write-categories)).

- **Prints** the location the configuration records. Where none is recorded, it prints `visual/` where that folder is absent, holds no file, or holds the visual work, as a command that writes there would take it ([How a command finds it](files.md#how-a-command-finds-it)). A `visual/` that holds files of another kind, or cannot be the location, is never granted: it prints no path, and says why. `--json` prints one document, `{"paths": [...]}`, with a `note` where it answers no path.
- **Writes** nothing, and needs no network. [`pkit sync`](../../cli/README.md#sync) provisions it, as it does every query command.
- **Exits** 0 when it answered, with a path or with none; 1 when the configuration cannot be read, or records a location that is refused.

### `pkit visual add <library>`

Copies a library the capability ships into the location's library folder, lists it, and brings every copy of it up to date.

- **Takes** the newest released version the capability ships ([The libraries the capability ships](files.md#the-libraries-the-capability-ships)). `pkit visual add <library>@<version>` names another released version, and `--being-built` asks for the version being built. Where the library has no released version, it takes the version being built. Asked for the version being built while it carries a released number, it takes that released version.
- **Copies** the version whole into a folder of its own, beside the versions the location holds ([What the location holds](files.md#what-the-location-holds)).
- **Lists it** in `libraries/libraries.yaml`, released with its hash or not released ([The list, `libraries.yaml`](files.md#the-list-librariesyaml)).
- **Brings every copy of the library up to date** in the same run ([What the location holds](files.md#what-the-location-holds)):
  - A copy the list marks not released, of a number the capability ships, is replaced whole by what the capability ships under that number. Where that number is released, the list then marks the copy released ([The list, `libraries.yaml`](files.md#the-list-librariesyaml)).
  - Such a copy is replaced only where every lock that names it is the lock of a draft that is not pinned, which moves at each render, or of a final piece, or you name the lock ([The lock](files.md#the-lock)). Under a pinned draft's lock, a published piece's or written code's, left unnamed, the copy stays as it is. The command names each such piece or declaration, and goes on with the rest of the run. A lock it cannot read counts as one that moves only on purpose, and the command names its file. To tell which locks hold a copy, it reads only a piece's `lock`, `pinned` and `state`, and its record of exports. So a fault in the piece's content stops nothing. A record of exports that cannot be read makes the piece final ([The lock](files.md#the-lock)), so its lock holds no copy.
  - A released copy whose files no longer match its hash is restored as released. One that matches is not written.
  - A copy of a number the installed capability does not ship stays as it is, and so does a version folder the list does not name.
  - A version the list names whose folder is missing is brought in as a copy of its kind is: a released one restored, one not released replaced, under the same locks.
- **Shows a before-and-after** of each lock left on a copy it leaves, so you see what replacing the copy changes:
  - For a pinned draft or a published piece, it draws the piece's scenes with the copy as it is, in `before/`, and with what the capability ships, in `after/`. Both lie under `before-after/<piece>/` in [the clone's local folder](files.md#the-clones-local-folder), each file named as its [preview](outputs.md#previews).
  - For written code, it prints the difference in the code the declaration's writer writes with each ([The declaration](outputs.md#the-declaration)).
  - Where it cannot draw or write a side, as for a fault in the piece's content, it says why and goes on.
- **Replaces the copy once you name each lock left on it.** `--piece <name>` names a pinned draft or a published piece, and `--declaration <name>` a declaration of written code. Each may repeat. Naming it is the move on purpose: the lock keeps its number, and the command writes no `piece.yaml` and no declaration ([The lock](files.md#the-lock), [The declaration](outputs.md#the-declaration)). With any left unnamed, the copy stays, and the command prints the line that names them all. Where a lock on the copy cannot be read, it prints no such line: you mend that lock first.
- **Prints** each copy it writes, as copied, replaced or restored, with each piece and declaration whose lock names it. It calls each piece by its state. Then each copy it leaves, with why, and each lock left with its before-and-after. Where it can read each lock left, it adds the line that replaces the copy. Then each version it lists.
- **Refuses** a library the capability does not ship, naming the ones it ships, and a released version it does not ship. It refuses files the capability ships that no longer match the hash the library's record keeps, or whose files of the capability's format lack their binding ([The binding](files.md#the-binding)). It refuses a hash the list keeps for a released version that differs from the one the capability records, naming both. It refuses a version folder the list does not name, where the version is to be copied, and a library the list names from another source ([The list, `libraries.yaml`](files.md#the-list-librariesyaml)). It refuses a piece or a declaration you name that locks no copy the run would replace, naming what it locks, and one whose lock it cannot read.
- **Exits** 0 when it wrote each copy, or left it with why; 1 when it refused, with nothing written, or a write failed ([Commands](#commands)).

Running it is the consent for each copy it writes. A change the project made in a copy it replaces or restores is lost, as the project's diff shows: a shipped library changes where it is authored, never in a copy.

### `pkit visual release <library>`

Releases a version of a project's own library, after it reads the version in full and compares it with the library's previous release.

- **Takes** the newest version the library folder holds of a library the list names from the source `project`, listed `released: false`.
- **Reads it in full,** and names each finding that refuses the release ([What each run judges](checks.md#what-each-run-judges)).
- **Compares it** with the library's previous release, and prints what it finds ([What a release compares](files.md#what-a-release-compares)).
- **Writes** the release the version needs into its `library.yaml` ([`library.yaml`](files.md#libraryyaml)), then lists the version released ([The list, `libraries.yaml`](files.md#the-list-librariesyaml)). It writes nothing else.
- **Refuses** a version the list does not name, one released already, and a library the project does not own: one the capability ships, or one another repository shares.
- **Exits** 0 when it released the version; 1 when it refused, with nothing written, or a write failed ([Commands](#commands)).

Before you release a library for other projects, sync from a tagged install of the methodology. Then the release the version needs covers what it uses ([`library.yaml`](files.md#libraryyaml)). The advice does not apply where the capability is authored, since no sync copies into that tree.

`pkit visual release <library> --shipped` releases the version being built of a library the capability ships, where the capability is authored. It reads and compares the version the same way. Each condition it holds the version to, and each file it writes, is under [The libraries the capability ships](files.md#the-libraries-the-capability-ships). Among the files it writes is a patch changeset for the capability: raise its kind where the release needs more.

### `pkit visual before-after <piece>`

Draws each of a piece's pages under two locks, and prints each page that differs. You ask for one of two looks.

- **`--ahead` looks ahead, before a move of the lock.** The before is the lock of the version that wrote a published piece's [current copy](outputs.md#the-current-copy), and otherwise the lock the piece holds. The after is the newest released versions that fit, within the lock's majors. It prints each newer version it did not take, with why.
- **`<library>@<version>` names versions for the after,** in the form `pkit visual add` takes, and may repeat. The after then moves what you name, and only what that needs. It prints each clash or lost end a version named goes past.
- **Who takes a look ahead** ([The lock](files.md#the-lock)):
  - A published piece, whose names must be released versions.
  - A draft, only with versions named, which may be versions not yet released.
  - A final piece, with none named. Its two locks are one.
- **`--back` looks back, at a change.** The base is where your branch left the default branch, or the branch `--base <ref>` names. The before is the lock of the version that wrote the copy at that commit, or the lock held there where no version did. The after is the lock the piece holds now. A piece the base does not hold has no before, and the command says so.
- **Draws** both sides with today's engine, from the piece's files and [produced pictures](outputs.md#produced-pictures) as they lie, and it runs no program. Both sides fill what a piece shows of its export in one way, as a preview does, so a number the piece shows does not differ ([The facts of an export](components.md#the-facts-of-an-export)).
- **Writes** each page in `before/` and `after/`, under `before-after/<piece>/` in [the clone's local folder](files.md#the-clones-local-folder), each file named as its [preview](outputs.md#previews). It replaces what an earlier run left there, and writes nothing else.
- **Prints** each lock, each page that differs, and each picture that is stale or missing. It says where the two locks are one, and where the engine's release differs from the one the copy's version recorded. Last, it prints each stand-in the sides show, with why ([The facts of an export](components.md#the-facts-of-an-export)).
- **Names what does not follow the after's brand,** looking ahead or back, where the two locks name different brands ([The lock](files.md#the-lock)).
- **Goes on** past a drawing it cannot make, such as where a library version left the project. It says why, and draws the other side.
- **Refuses** a piece with no lock yet, a draft with no version named, and a final piece with one. It refuses a version a move cannot take, and a base that resolves to nothing.
- **Exits** 0 when it drew a side or said why not; 1 when it refused, with nothing written, or a write failed ([Commands](#commands)); 2 on a usage error.

### `pkit visual upgrade <piece>`

- **`<library>@<version>` names versions instead,** in the form `pkit visual add` takes, and may repeat. The run then moves what you name, and only what that needs.

- **Commits nothing,** and makes no branch. Land the diff as you land any change, or discard it.
- **Says so and writes nothing** where nothing moves.

Each may repeat.

- **Names** each finding that fails under the moved lock, and stops on none of them.

- **Refuses** what the search refuses, a fingerprint it cannot read, and whatever refuses an export but a lock that differs ([What refuses an export](outputs.md#what-refuses-an-export)).
- **Exits** 0 when it proposed the move, found nothing to move, or ended a dry run; 1 when it refused, with nothing written, or a write failed ([Commands](#commands)); 2 on a usage error.

### `pkit visual outdated`

## The designer

`graphic-designer` turns a piece's brief into a piece ([visual-communication:DEC-030-design-agents] point 2). It names the content's structure, and the order each page explains in, before it chooses a form. It settles where a page's path starts before it ranks what is seen first, takes type, colour and space from the brand's roles, and writes the reason for each choice into the brief. It writes the piece's own file, its content in every language, its brief and its local components. It also builds the project's own libraries, in a version not yet released. It renders, checks and looks only through the commands, as the skill `visual-author` walks them ([Drawing a piece](#drawing-a-piece)). The adapter deploys it as it deploys any agent ([Deploy mechanics](../../agents/README.md#deploy-mechanics)).

**Its grant.** It writes within the location, which the overlay category `visual-communication.work` grants it ([visual-communication:DEC-030-design-agents] point 5):

- **Installing the capability writes it** into the agents overlay, as the answer of [`pkit visual work-paths`](#pkit-visual-work-paths), such as `visual/`. An install from before the category takes it from `pkit agents reconcile --write` ([the agents README, "A capability's write categories"](../../agents/README.md#a-capabilitys-write-categories)).
- **A value the project sets is kept.** Change the line to name a folder of helpers too, or a location you moved. An empty list you set, `[]`, switches the designer off: it deploys, writes nothing, and runs no command that writes in the location.
- **Held to the location.** `pkit visual check` fails a grant that does not cover the location the configuration records, or that names a path inside `.pkit/` ([`grant`](checks.md#files-and-binding)). So move the grant with the location: each message that says how to move the work names its line, and `pkit agents reconcile --write` moves a line still as `pkit` wrote it ([The location](files.md#the-location)).
- **Never written, though the grant reaches them:** a released version of a library, or a copy of a library the capability ships, which only `pkit visual add` writes. What a command writes, such as a lock or a findings record, stays the command's.

Where its grant names no location yet, it asks you where the visual work goes, writes nothing, runs no command that writes in the location, and stops. You record the location with `pkit visual add foundations --location <path>`, which also brings the foundations library in ([`pkit visual add <library>`](#pkit-visual-add-library), [How a command finds it](files.md#how-a-command-finds-it)). Then you move its grant there, with `pkit agents reconcile --write` ([the agents README, "A capability's write categories"](../../agents/README.md#a-capabilitys-write-categories)). The next `pkit sync` deploys it with the grant ([Deploy mechanics](../../agents/README.md#deploy-mechanics)), and a fresh dispatch of it takes the grant.

To use it:

1. **Ask it for a piece,** saying what it must say, to whom, and where it is shown. It writes the brief's goals and relations from what you say, and shows them to you before it designs against them. Where they give no order in which a page explains, it proposes one from the page's lead or takeaway, and writes it into the brief once you confirm it.
2. **Let it build.** Where no library draws the design, it extends the project's own library, makes a component for the piece alone, or stops and says what is missing ([visual-communication:DEC-030-design-agents] point 4). It never changes what the piece says to fit what a library draws.
3. **Read what it hands back.** Before it stops, [the reviewer](#the-reviewer) reads every page in every language, mode and size. Where the designer can start agents, it dispatches the reviewer itself. Otherwise it asks you to, and says the piece is not reviewed. It mends what it judges right, then tells you what it changed and why, with the reviewer's report as written.

In mending, it asks you only where a fix would change what the piece says, needs a write it may not make, such as to a library the capability ships, or two rounds of mending did not clear a finding. You answer, and it makes the change.

## The reviewer

`graphic-design-reviewer` is the capability's reviewer. It looks at a piece's pages as they were drawn, and reports what no check measures, such as a text over a picture. It also judges whether the pages keep the capability's rules, and show what the piece's brief asks. The adapter deploys it as it deploys any agent ([Deploy mechanics](../../agents/README.md#deploy-mechanics)).

To use it:

1. **Draw the pages.** Run [`pkit visual look <piece>`](#pkit-visual-look-piece), with the pages, languages, modes and renderer you want read. Draw each size the piece names, a phone's among them: `--every-key` takes them all ([The viewing step](outputs.md#the-viewing-step)). Add `--forced-colours` where it should see what a reader who forces their own colours gets ([Under forced colours](outputs.md#under-forced-colours)). The reviewer runs no command, so it sees only what that run drew.
2. **Dispatch it,** naming the piece. It reads the images in the folder of the renderer that drew them, with the frames and the report beside them, and the piece and the brand. It also reads the piece's brief, where the piece keeps one, the capability's design knowledge, and the rule sets the capability ships. It does not read the set sessions load, which binds a session's work, not a piece. You may hand it other images of the same pages, from another tool or renderer, and it says which drew each. It changes nothing.
3. **Read its report.** It opens with the pages, languages and modes it looked at, the bands of each page it read, and the forced palettes it looked at, where the run drew them. It names the brief it read, or that the piece has none, and the rule sets it read. It names what it did not see. What it did not see is not looked at, never clean.

Where a run's folder holds a report and no image, the browser stopped. The reviewer says so, and looks at nothing ([When the browser stops](outputs.md#when-the-browser-stops)). It passes on to you the ways on the stop names, in their order.

You may hand it a build pipeline's drawings instead, fetched into a folder of their own ([A pipeline's drawings](outputs.md#a-pipelines-drawings)). It names those images as drawn by the pipeline, at the commit it drew.

Each finding names the page, the element's trace id where the element was drawn ([Trace ids](components.md#trace-ids)), and where its fix belongs. A finding is one of four kinds, kept apart by what it cites:

- **A fault,** which the agent's list names: a part missing or blank, a wrong font, text over text, a text that does not read over a picture, a wrong picture, an overlap, a fault of alignment, or a drawing that disagrees with a passing check.
- **A rule finding,** which cites a rule by its id. Today it only informs, since no rule binds on a piece's files yet.
- **A brief finding,** which cites the part of the piece's brief that the drawing does not show.
- **A note,** anything else worth a look. A note of taste names the practice it draws on, from the design knowledge. A note never fails.

One observation makes one finding, of the first kind in this list that applies, and it cites each ground it rests on. A page whose path, traced from where the eye enters, does not follow the order its relations and its lead or takeaway give is such an observation. It may break a rule as well as the brief. Where the piece keeps no brief, it is a rule finding where a rule applies, and otherwise a note.

Its findings are advice. They join no validation and hold no merge.

It needs a harness that reads images. Where the harness reads none, it stops and says so, and reports nothing as looked at.

## Citing this capability's decisions

Inside this capability's own content, cite decisions by their filename
stem: `[visual-communication:DEC-001-<slug>]`. Other capabilities and adopter content
use the same form.

## Dependencies

No other capability. The commands run their scripts through `uv`, with the Python packages each script pins; `pkit sync` installs those of the check, so `pkit validate` runs it offline. It installs those of `pkit visual pages` too, which pins every package `pkit visual look` does, so that command draws with no network. The HTML renderer's pages need a browser of the Chromium family besides, which the capability does not install ([The HTML renderer's pages](outputs.md#the-html-renderers-pages)).
