**In plain terms:** in a project whose membership gate is closed, the post-check workflow fails every issue it checks. Its check runs the validation of the issue, which runs the gate first, and the workflow's own token or an App's names nobody the gate can match. This record takes the gate off each command that only reads and reports, one no run of which changes anything, and off no other: such a command runs for anyone, under any credential, the gate open or closed, and refuses nothing for want of knowing who runs it. Each such command declares so in its code. A guard it installs at its start refuses, on every run, a write its own process makes and a program or a connection it does not know to be a read, and a test and review hold what the programs it lets through do. A suite check keeps the gate on every other command, save the few this record names. So the post-check workflow's check validates each issue in a closed project as in an open one, with no member entry and no `PM_INVOKER_LOGIN`.

## Context

**The terms.**

- *The gate* is DEC-021's check of the member list: open where the list is absent or empty, and closed where it names at least one member, when it refuses whoever runs a command unless an entry names them. It is not the check of an issue's card on the board, which [project-management:DEC-071-filing-only-configured-board] and [pkit:ADR-096] call the membership check.
- *A command* of this capability is each command the capability registers in its package, the predicates the lifecycle engine calls among them.
- *A credential that names no user's account* is one for which the hosting service does not answer that it acts as a user's account, such as a workflow's own token or an App's (DEC-021, "Identity resolution"). Under it, the gate can match only the account the service answers the credential acts as, by its login, and nothing where the service gives none (DEC-076 point 2).
- *The post-check workflow* is the workflow template that validates each issue opened, edited or reopened, and comments its findings ([project-management:DEC-019-mandatory-issue-state], "The post-check workflow template").
- *The maintainer* is whoever maintains this capability, in the project that builds it, from which the projects that adopt the capability receive this record.

**What the records say.**

- **DEC-021 gates what mutates, and puts the check in every script.** Its decision has every operation that mutates external state check the member list, and its Context names what the gate guards against: issues filed in the wrong shape, misclassified, moved in bulk or mistitled. Its Tooling surface and its Implications put the check at the startup of every other verb-subject script, those that only read among them.
- **CI runs reads.** [project-management:DEC-020-methodology-as-executable-commands] has CI use the environment check and the validation of an issue and of a pull request as its gating checks, and leaves the commands that mutate to people and agents, save the board sync the post-check workflow runs at an issue's filing, for that issue alone (its Implications).
- **CI's way through the gate.** DEC-021 has a workflow that runs a gated command pass a closed gate as an account the list names, whether a service identity added to it or a person whose own token the workflow holds, or, under a credential that names no user's account, as the bot's account the backbone's reading names, where an entry names that account by its own login (DEC-076 point 2). CI is not exempt by design (its Implications, "CI invocations").
- **The mesh check reads, and still gates.** [project-management:DEC-022-methodology-mesh] has its check make no mutating call, and gate "like every other verb-subject script", so its scheduled workflow needs an entry in the list, or `PM_INVOKER_LOGIN` from a secret, in a closed project ("Authority").
- **DEC-018 is split.** [project-management:DEC-018-workstream-taxonomy-and-lifecycle] has every workstream script, the two that only show and list among them, run the predicate at startup ("Authority"), while its Implications apply the gate to every workstream script that mutates.
- **The prerequisite gate's coverage.** The capability's check of a project's prerequisites ([project-management:DEC-017-prerequisites-bootstrap-migrate-discipline]) is called at the top of each command, and a suite check keeps it complete: each registered command calls it, or is named as exempt, with its reason.
- **Some reads write.** [pkit:ADR-071] has a read of a state issue restore the marker a hand removed from its description, the one write a read makes (point 5).

**The code.** Each command applies the gate's predicate itself and prints its own refusal, or has the shared module that runs it do so. The command that shows the members applies the predicate only to report whether whoever runs it would pass. No check finds a command that applies no gate, and several that write apply none, though no accepted record has them apply none. Some reads take no gate either: the predicates the lifecycle engine calls, the validators `pkit validate` runs, and the command that tells the backbone's context which workstream a branch belongs to, which takes none on purpose, so that a refusal does not turn the context into a gate. Some views write on what they find, as a read of a state issue does, or on one value of an option. Git and the other programs the commands start are started from many modules, each through a helper of its own or directly, and through no runner they share. The resolution of who runs a command answers with a user's login, or with none and a cause in words, alike where the service refused the request for the account to an integration's credential, refused it for a rate limit, did not accept the credential, or never answered.

**The failure** ([project-kit#3290](https://github.com/aleskalfas/project-kit/issues/3290)). In a project whose gate is closed, the post-check workflow fails every issue it checks. Its check runs the validation of the issue, which checks membership before it validates. The step runs under the workflow's own token, an App's, or a person's token the project gives it for the board ([project-kit#3256](https://github.com/aleskalfas/project-kit/issues/3256)). The first two name no user's account ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)), and the workflow sets neither `PM_INVOKER_LOGIN` nor git's email. So the gate resolves nobody and refuses, and the job fails. Only a person's token for a member's own account gets through. The mesh check's scheduled workflow runs under the workflow's own token, and fails behind a closed gate the same way.

**The maintainer's ruling.** Of the ways out the issue names, the maintainer chose this one: a command that only reads and reports, and changes nothing, does not take the gate.

## Decision

**A command that only reads and reports takes no membership gate, and runs for whoever runs it. A command that takes the gate keeps it on every run, its dry runs included, as DEC-021 decides, and this record takes it off no command that can write.**

### 1. A command only reads and reports where no run of it writes

A run *writes* where it changes anything beyond what it prints and its exit code, save what the second list below counts as no write. The change counts wherever it is made: by the run's own process, in the command's script, in a module of the capability it loads or in a library they call, or by a program it starts.

- **On the hosting service, or on any other service:** a request that changes what the service holds, such as an issue, a comment, a label, an assignee, a milestone, a card or a field on a board, a pull request, a review, a merge or a branch.
- **In the repository:** a change to its files, its index, its branches, its tags or any other ref, its stash, its worktrees or its configuration.
- **In what is kept for the project, the clone or the user:** a change to state that the capability, the backbone or another capability keeps, such as the member list, a journal, a claim, a queue of proposals, the clone's instance id or what the agent workspace holds, and a change to a file of the user's outside the repository.

These alone are no writes:

- **What the run prints,** to its output streams, or to a file its caller names to receive what the run would otherwise print. The caller chose that file, as it chooses where the output goes. A file that holds anything the run would not print is a write.
- **Its exit code.**
- **Objects git adds that no ref names,** whatever adds them, such as a fetch, or a merge the run computes only to read its result.
- **A fetch that records what the remote holds, and changes nothing else:** no local branch or tag, no index, worktree, stash or configuration, and no ref but the remote-tracking refs and `FETCH_HEAD`. It runs with git's automatic housekeeping off (`gc.auto` and `maintenance.auto`), so that it prunes nothing.
- **The caches** kept for themselves by the tools the run runs on and by the programs it starts.
- **A file it makes for its own use** in a temporary folder of its own, outside what anyone else keeps, which it removes before it exits.

A command *only reads and reports* where no run of it writes: whatever its options, whatever the services and the stored state hold, and whoever runs it. A command with any run that writes *can write*, and a dry run beside its write leaves it so. So a view that writes on one value of an option, or on what it finds, such as a record a hand has edited or an item that no longer holds, can write.

### 2. A command that only reads and reports takes no gate

- **It runs for whoever runs it:** a member and a non-member alike, in open mode and in closed, under a credential that acts as a user's account or under one that names none.
- **It asks who runs it only where its report rests on that,** such as the work assigned to whoever runs it, or whether whoever runs it would pass the gate. It then resolves the identity as DEC-021 says ("Identity resolution"). A report that rests on nobody asks the hosting service for no account.
- **Where nothing resolves the identity,** the run reports one of two outcomes, and in neither refuses anything for want of the identity. The resolution of the identity says which it is, beside the account it resolves where it resolves one, with the cause in the service's words, so that no command reads the service's error text for itself, as the seam of the board's reads says whether the board answered ([pkit:ADR-096] point 6). Which it is turns on whether the service answered for who the credential is:
  - **The read did not answer.** The service's client is missing; the request did not reach the service or ran out of time; the service failed; it refused the credential itself as one it does not accept, as it refuses a person's token revoked or expired; or it refused the request for a reason other than what the credential is, such as a rate limit. The run says that pkit cannot tell which account is acting, and why, in the place of what rests on that, and gives the rest of its report. It never reports what rests on the identity as a finding that there is none, such as no work assigned. It takes the broken tool's code where its codes tell one, as a read a command only reports takes where the board did not answer (ADR-096 point 4), and elsewhere exits as its own contract has it (DEC-020).
  - **The hosting service answered that the credential names no user's account,** and nothing else names who runs it. It answers so where it refuses the request for the account because the credential is an integration's, as it refuses a workflow's own token and an App's, and where it answers with an account that is no user's. That is a finding, not a read that did not answer. The run says that the credential names no user's account and that nothing names who runs it, reports what rests on the identity as resting on nobody, and exits as on a run whose reads all answered.
- **A report of whether whoever runs it would pass the gate,** which the command that shows the members makes, applies the predicate to say so, and refuses nothing on the answer. It is the exception to the code of the first outcome above: what it reports is the gate's answer, which is definite where the identity is not. Behind a closed gate, an identity it cannot resolve would not pass, and the report says so, and why, and exits as on any clean run of it.
- **Its other checks stand.** This record changes only the gate. The check of the project's prerequisites runs as DEC-017 decides, and the guard on a session's writes to another repository as [pkit:ADR-034] decides.

### 3. A command that takes the gate keeps it on every run

This record takes the gate off no command that can write, on any run. A command that takes it, whether it files, edits, comments, moves, assigns, closes, reopens, reviews, merges or writes the member list, or starts a command that does, takes it at its startup on every run, before any other work, its dry runs included, as DEC-021 decides. Behind a closed gate it refuses whoever no entry names, and whoever it cannot resolve. A workflow that runs such a command behind a closed gate passes only as DEC-021 lets CI pass (its Implications, "CI invocations").

A command that both shows and writes, such as a view with one option that writes or one that writes on what it finds, can write, so it carries no declaration, and where it takes the gate it keeps it for its every run. Where its reads should be open to everyone, the remedy is to split it into a command that only reads and reports and one that writes, or to take the write out of its reads by the record that decides that write.

### 4. A declaration in the code, held on every run by a guard, and sampled by a test

- **The declaration.** A command that takes no gate because it only reads and reports declares so in the code, in a form the suite finds mechanically. The form is the build's: a mark in each command, or one registry beside the gate, as the prerequisite gate keeps its exemptions.
- **The guard.** A command that carries the declaration installs a guard of its process before it loads any other module of the capability, and nothing in the run can remove it. The guard sees what the run's own process does, in the command's script, in each module it loads and in the libraries they call: each file it opens, with its mode, each file or folder it makes, moves or removes, each program it starts, with its arguments and its environment, and each connection it opens. It refuses:
  - **A file written:** one opened for writing, made, moved or removed, save the one file the caller names for the output, what lies in the run's own temporary folder, which the run removes before it exits, and the caches point 1 counts as no write.
  - **A program it does not know to be a read,** with the arguments and the environment it is started with. It knows a request to the hosting service that only reads, a git command that makes no change point 1 counts as a write, a command of the backbone that only reads, and a command of this capability that carries the declaration, which installs a guard of its own.
  - **A connection its process opens,** since a declared command reaches each service through the programs it starts.
- **A refusal ends the run as a failure,** which says what it refused, and which no code of the command can catch into a success, on every run, outside the suite as in it. So a run that would write on a state the test never met fails there, for whoever met it, rather than writing ungated.
- **Where the guard lives.** The guard lives in the capability's shared code while the capability is the one component that uses it, as a pattern is extracted once it recurs ([pkit:COR-007]). Its judging of the hosting service's requests and of git's commands as reads is general, and stays apart from what is the capability's own, the commands that carry the declaration, so that it can move. Its list counts some commands of the backbone as reads, a contract the backbone keeps and this capability only asserts, so a backbone command that came to write would be found only by the test. So once a second component would use the guard, its general part moves to where both reach it, by a record of its own, and the backbone declares its own commands that only read, in place of this capability's list naming them.
- **A check finds it.** A check in the suite finds, statically, that each declared command installs the guard before it loads any other module of the capability.
- **A test samples it.** The suite runs each declared command, its guard installed, and holds each run to point 1:
  - **Its options:** each of them; each value of one that takes a value from a set; for one that takes a free value, a value that names something the fixtures hold and one that names nothing; and for one that names a file to receive the output, a path in a folder of the test's own.
  - **Who runs it, and where:** each such way in open mode and behind a closed gate, for a member, for a non-member, under a credential that names no user's account, under one the service does not accept and under one it gives no answer for, with a terminal and without one, and at a terminal answering each prompt with each choice it offers.
  - **What it finds:** each such way against what the service answers and the stored state holds, in each shape the capability's code treats apart, such as empty and filled, as the capability wrote it and as a hand left it, and holding what still holds and what no longer does.
  - **Cut off:** the test runs with no network, the hosting service's host and every git remote pointed at stand-ins. The stand-in for the hosting service answers only the requests it knows to be reads, and fails every other, so a request the guard took for a read, or a way of reaching the service that the test does not see, fails loudly rather than going through.
  - **What passes:** the command is not refused, by the gate or by the guard, sends no request a stand-in fails, and leaves the repository and what is kept for the project, the clone and the user as they were, save what point 1 counts as no write.
- **What none of them reaches.** A program the guard lets through runs in a process of its own, which the guard does not watch, so the guard's list of known reads is what holds it. Almost every write the capability's commands make leaves through such a program, the hosting service's client, git or a command of the backbone, so that list, which judges each program by its arguments and its environment, carries most of the guard's weight. The test holds the list on the runs it samples, each option, value and state alone, not every combination of them, by its stand-ins and by finding the repository and what is kept as they were. The review of each change that adds a declaration, changes a command that carries one or adds to the list judges the command against point 1 for the rest. Code that acts below the interpreter the command runs in, such as a compiled extension, passes the guard unseen. The guard keeps a command from writing by mistake, and is no wall against code written to pass it, as the gate is none against someone set on passing it.
- **Where they run.** The check runs among the fast checks of the project that builds the capability. The test, which makes many runs of each declared command, runs in its full suite.
- **A declaration that fails** is mended in the command: it takes the gate, it stops writing, or it is split (point 3).
- **The guard's construction** is the build's, and an architecture record records it with the build, as [pkit:ADR-031] records the contract of the write path that [project-management:DEC-037-adoption-ceremony] left to such a record. That record names the means, such as the interpreter's events the guard watches, the settings it gives git, how a run names its output file to it and the form of its list of known reads, and meets these requirements, each held by a test:
  - **Every way the run's process can change a file is a write the guard refuses,** by each of the interpreter's and its standard library's ways to open, make, move, remove, copy, map into memory or alter a file or a folder, save what point 1 counts as none.
  - **A declared command passes on a fresh checkout,** where the interpreter would write its cache of compiled modules inside the repository.
  - **What the run's tools make for their own use lies in the run's own temporary folder,** the first use of the standard library's temporary files among it.
  - **A request to the hosting service counts as a read only where the guard can show that it is one,** whatever fields it is given and wherever its body comes from, a query in the service's query language told from a mutation by its operation, and every other is refused.
  - **Git's commands that only show take no lock that writes the index,** and a fetch runs as point 1 has it.
  - **No code of the command can catch a refusal,** and the run's temporary folder is removed as the run ends, a refused run among them.
  - **The guard is installed only where the command runs as a program,** before it imports any module of the capability, and never on import, since the suite loads some commands into its own process. The check of this point recognises that shape, and the test makes each run in a process of its own.
  - **The guard tells, without loading a command, whether a command of this capability that a run starts carries the declaration,** which bears on the form the first bullet of this point leaves to the build.

### 5. The gate is the default, and the commands that take neither it nor the declaration can only grow fewer

- **The gate function.** The build adds one function that takes the gate and refuses whoever it does not admit, and each command that takes the gate calls it at its startup, in its script or in the shared module that runs it. A command that applies the predicate only to report, as the command that shows the members does, takes no gate by that.
- **The coverage check.** The suite finds, for each command the capability registers, that its run calls the gate function at its startup, or that it carries the declaration, or that it is one of the group below. A command that is none of the three fails the suite. So each command added after this record takes the gate, unless it carries the declaration and passes point 4, or is registered under a name the list holds, in place of the command the list named, which the check, matching by name, does not tell from that command. The coverage check runs among the fast checks of the project that builds the capability, beside point 4's check.
- **The group** holds the commands that take no gate and carry no declaration, and only those the list below names:
  - **The departures,** the list's `departures`: the commands that can write on the evidence of their code and take no gate, so depart from DEC-021. This record mends none of them. [project-kit#3352](https://github.com/aleskalfas/project-kit/issues/3352) takes each up: a departure that comes to take the gate needs no record, and one that is to stay ungated needs a record of its own, since that changes what DEC-021 decides. The coverage check names the departures apart, with #3352.
  - **The reads that cannot yet carry the declaration,** the list's `reads`. A command that takes no gate and only reads and reports on the evidence of its code gains the declaration with the build, where it passes point 4. One that does not pass it stays without the gate, and the change that builds this writes its name into `reads`, and says what keeps it from point 4. No guard holds such a command, so the review of each change to it judges it against point 1, and one found to write moves to `departures`. The list names none of them until then.
  - **Checked again at the build.** The change that builds this writes into `departures` each command that takes no gate and that it finds can write, where the list does not name it, and takes out of `departures` each it finds only reads and reports, which then carries the declaration or joins `reads`. It says so on #3352.
- **A command that joins the group or leaves it, or moves between `reads` and `departures`, is a person's to accept.** Each such move changes what this record decides, so a person accepts the edit of the list that makes it, with the change that makes it ([pkit:COR-064] point 6), and the numbering check lists that edit for them (the decisions README, "Checking a change's numbering"). The change that builds this makes such edits, and so does each change that takes a command out of the group.
- **A rename of a command the list names** renames it in the list, in the change that renames the command, as the coverage check requires. It moves no command into the group, out of it or between `reads` and `departures`, so it changes nothing this record decides, as a citation updated after a rename does not (the decisions README, "Refining an accepted record"). The numbering check lists the edit, and whoever judges the change's edits judges that the command renamed is the one the list named.

**The list.** The names sit in the one fenced block of this point, and the coverage check reads nothing else of this record's text. It finds the point by its number, which no edit changes ([pkit:COR-058] point 3). It fails loudly, naming this record and what it found:

- where it finds no such block, more than one, or one it cannot parse;
- where a name in the list is no command the capability registers;
- where a command the list names takes the gate or carries the declaration;
- where a command in the group is one the list does not name.

departures:
  - answer-question
  - apply-proposals
  - ask-fixers
  - back-fill
  - bootstrap
  - decline-use-case-task
  - fix-drift
  - grant-fixer
  - migrate
  - refuse-proposals
  - revoke-fixer

- **The group only shrinks.** A command leaves it by taking the gate or by carrying the declaration, and the change that takes it out takes its name out of the list too, which the coverage check holds. A command joins the group only by an edit of this record, which is a person's to accept. So a command that can write leaves the gate by no way this record gives, and one that only reads and reports leaves it only by its declaration.
- **No gate added.** This record adds the gate to no command that takes none, a departure or a read.

### 6. A workflow's check passes a closed gate

- **The post-check workflow's check** runs the validation of the issue, which only reads and reports. So in a project whose gate is closed, the check validates each issue under the workflow's own token, an App's or a person's, with no member entry and no `PM_INVOKER_LOGIN`, and passes or fails the issue on its findings alone, as where the gate is open.
- **The mesh check's scheduled workflow** runs the mesh check, which only reads and reports, and passes a closed gate the same way.
- **Each of the two** only reads and reports on the evidence of its code, and drops the gate once it carries the declaration and passes point 4. Should either be found to write, by the guard, the check, the test or the review, it keeps the gate until that write leaves it, by point 3's remedy, and its workflow passes a closed gate only from then.
- **A workflow's own steps,** such as the post-check workflow's comment of its findings, and the mesh workflow's issue on drift, are calls the project's copy of the workflow makes under the credential the project gives it. No command of this capability runs in them, so the gate never bound them, and this record leaves them so. A step in which the copy runs a command of this capability is none of them: the command takes the gate where it can write, as point 3 says, such as a command that adds a missing card to the board, and that step passes a closed gate only as DEC-021 lets CI pass.
- **An entry or a variable for a workflow's check:** the check needs neither. An entry added to the list for a workflow admits, to every command that can write, every session that holds a credential whose account the entry names (DEC-076 point 2). So it stays only for a step of the project's workflows that runs a command that can write.

- **Refined in DEC-021,** narrowed and widened: its Decision's first sentence, which comes to gate every run of a command that can write by point 1, a write in the clone or in the user's files among them, where it gated the operations that mutate external state; its Tooling surface's check at startup, which comes to name every command of the capability where it named the verb-subject scripts; and three of its Implications, "Every verb-subject script", "The project-manager" and "CI invocations", each with the commands that only read and report left out, and the first and the last widened, as its Tooling surface is, to every command of the capability (Implications).
- **Refined in DEC-018, DEC-020 and DEC-022:** each sentence that applies DEC-021's gate to a command that only reads and reports, alike, and with it DEC-022's sentences on the identity its scheduled workflow needs behind a closed gate (Implications).
- **Stands:** DEC-021's open and closed modes, its predicate, its refusal, its identity resolution, its readers of the identity, its bootstrap and its authority over changes to the list, and the gate on every command that takes it. DEC-022's mesh, its check and its workflow stand, save their gate while the check only reads and reports.
- **Not decided here:**
  - **Whether each command that can write and takes no gate should take it.** Point 5 names each, and [project-kit#3352](https://github.com/aleskalfas/project-kit/issues/3352) takes each up.
  - **Whether a read that mends what it finds should stop mending,** such as a read of a state issue that restores the marker a hand removed (ADR-071 point 5). While it mends, the command that makes it can write (point 1), and keeps its gate.
  - **Whether the post-check workflow adds a missing card,** which [project-management:DEC-077-workflow-gives-missing-card] decides ([project-kit#3271](https://github.com/aleskalfas/project-kit/issues/3271)). A step that adds it through a command of this capability takes that command's gate (point 6).

## Rationale

**Why a command that only reads and reports takes no gate.** DEC-021's gate keeps the methodology's mediation with the people the list names. The harms its Context names, issues filed in the wrong shape, misclassified, moved in bulk or mistitled, are each made by a write, and a command that only reads and reports makes none of them. What it reads, the credential reads without it, from the hosting service and the repository, so a refusal keeps nothing from whoever is refused, and only costs a check where it runs. That cost falls hardest where nobody signs in: on a workflow under its own token or an App's, where DEC-020 runs the reads.

**Why not give the workflow an identity the gate admits.** That is the issue's other way out. Under a credential that names no user's account, the gate can match only the account the credential acts as, which every session that holds a credential for that account acts as, or nothing where the service gives no login (DEC-076 point 2). DEC-021 accepts that cost for a command that writes: the gate is "no wall against someone set on passing it", and a workflow that writes needs some identity the list admits. For a command that only reads, the cost buys nothing, since the gate keeps nothing from anyone there. And each project that closes its gate would have to add an entry or set a secret before its check could run.

**Why a write is anything the run changes, save what is named.** A list of writes that counted only what it named would let through whatever it missed: a request to another service, state that another capability keeps, a file of the user's outside the repository. Counting every change as a write, and naming the few that are not, fails closed: a change nobody thought of keeps the gate.

**Why a file the caller names for the output is no write.** The run writes nothing there that it would not print, so the file is the caller's redirection of the output, whatever the output is, a report or a draft. A file that holds anything else is the run's own writing, wherever the caller points it.

**Why a property held in the code, rather than a list.** What keeps a command from writing ungated is what holds its declaration, not where the declaration is written. A list of the commands that take no gate, kept in this record or in the capability's documentation, has nothing behind it: a command that gained a write while the list named it would write ungated, and nothing would find it. So the declaration is held by the guard on every run, by the check and the test in the suite, and by the review where none of them reaches (point 4). A registry of declarations beside the gate is a list in the code with these behind it, which is why the form is left to the build. Point 5's list is no list of the commands that only read: it names those that take neither the gate nor the declaration.

**Why a guard at run time, rather than a scan of the code.** A scan of the code could keep a declared command to shared runners in a read-only mode only by approximating what the command reaches. Counted by the modules it loads, it finds writers that no run of the command calls: the check of the prerequisites, which every command loads, holds the writer of the bootstrap stamp, and the validation of an issue loads the writers of state issues and of answers through the modules it reads with. So the scan would first need those modules split or rerouted, for no run's sake. Counted by the calls the command makes, it misses the runners the capability's modules take as values. Either way, it finds a write only in the forms it knows to look for, and git and the other programs are started from many modules with no runner they share, so the runners would have to be built and every start routed through them first. The guard sees what the run's own process does, whatever code in it does it, on every run, and needs no module split and no runner. It complements the scans that hold the capability's other seams, of the one place that builds a write of a field's value ([pkit:ADR-031] point 4) and of the one place that builds a read of the board ([pkit:ADR-096] point 6): those hold where a call is built, and the guard what a run does and what it starts. Its limits, point 4's "What none of them reaches", each fall on a command that writes by mistake, and a write such a command's own process makes fails loudly rather than going through.

**Why the group is named in this record, though a record lists no present members of a set.** A record captures a rule, and lists no current state, such as commands or the present members of a set, which lives in a reference document the record points at (the decisions README, "Writing a record", its rule "Principles, not inventory"). Point 5's list departs from that rule, for three reasons, and only as far as they reach:

- **The names are the bound the rule sets.** A group that the coverage check accepted for any reason would let a new command that writes leave the gate by an entry and a follow-up that anyone can name, so the gate would be the default in name only. Kept in the code, or in a reference document, the list could be widened by the very change that adds to it, the check and all, with nobody bound to see it. In an accepted record, an edit that widens it changes what the record decides, so it is a person's to accept (COR-064 point 6), and the numbering check lists it for them. No other place makes widening the group a person's act.
- **It cannot go stale unseen,** which is what the rule keeps state out of a record for. The coverage check reads the list and fails where the list and the code part, either way: a command in the group that the list does not name, and a name whose command takes the gate, carries the declaration or is not registered.
- **It is bounded.** It holds the departures, and the reads that cannot yet carry the declaration, which the build names only where they fail point 4. It only shrinks.

The decisions README gives its rule no exception, so this one holds only by the maintainer's sign-off on it (Implications, "Acceptance"). A second record that needs such a list, or a second check that reads a record's body, takes the exception into the README, as a pattern is extracted once it recurs (COR-007).

The list sits in a fenced block apart from the prose, since a wording refined in place around names in the prose could change what the check reads, unseen, where a block the check cannot parse fails it loudly. Calling the writers departures says what they are: DEC-021 has them take the gate, and no record has them take none.

**Why a read that takes no gate keeps none, and is named only where it fails point 4.** A read that takes no gate, and cannot carry the declaration, would otherwise have to take the gate. Behind a closed gate, under a workflow's own token, it would then refuse: the failure this record mends, in a validator `pkit validate` runs, as the prerequisite gate's exemption of the fixers' validator reasons for its own gate. So this record adds the gate to no command that takes none, and the group holds such a read. Yet most of those reads pass point 4 with the build and leave the group in that change, so naming them here would put into the record a list that the build at once empties. So the build names only those that fail point 4, and a person accepts each name with it.

**Why every run of a command that takes the gate, its dry runs included.** A dry run previews the run it stands for, and the gate's refusal is part of what it previews: one that passed where the real run refuses would preview a write the run never makes. Deciding run by run would also rest each command's gate on its own reading of its arguments, where a mistaken reading lets a write through ungated. The guard on a session's writes to another repository (ADR-034) does decide run by run, and skips a run that writes nowhere, since it guards where a run writes and such a run has nothing for it to check. The gate guards who may write, which a preview shows. A command that both shows and writes holds two reaches in one surface, which DEC-020 keeps apart on DEC-017's reasoning ("a read-only `show` script and a destructive `remove` script differ in blast radius"), so the remedy for its reads is the split.

**Why by what the command does, never by a mark of where it runs.** A run in CI could be told by a variable the CI sets, and the gate skipped there. Yet any session can set such a variable, so it would exempt a command that writes as readily as one that reads. A command's writes are a property of the command, which the suite can check. Where it runs is no such property.

**Why the test varies the mode, the identity, the terminal and what it finds.** Some of the capability's commands write only at a terminal or behind a yes, and some views only on what they find or on one value of an option. A command whose write waited on an identity it resolved, on an open gate, on a terminal, on a prompt's answer, on a value or on a state the fixtures lacked would pass a test that never met it, and the guard would then fail it for whoever met it. The test runs cut off from the network, and its stand-in answers only what it knows to be a read, so that a way the test does not see fails, rather than passing unseen, and so that something other than the guard's own list judges the requests the guard lets through.

**Why a fetch, and objects no ref names, are no write.** A fetch of this kind changes nothing the clone's people made or work on: no branch, tag, index, worktree, stash or configuration. It adds objects, which nothing reads until a ref names them, and records what the remote holds in the refs git keeps for that and rewrites on each fetch. A merge a run computes only to read its result, as a view of a pull request does, adds objects too, and names them by no ref, so the same reason covers objects no ref names, whatever adds them. Git's automatic housekeeping, which a fetch can start, can prune what a person made, such as a worktree's entry, so the fetch runs with it off. A view that fetches the head it shows, by name or by the ref the service keeps for a pull request, so as to read it, then stays a command that only reads and reports. A fetch that moved a local branch or brought tags would change what the clone's people work on, and is a write.

**Why ask who runs it only where the report rests on that.** Each request for the account counts against the hosting service's limits (DEC-021, its Implications, "The request for the account"), and under a workflow's token or an App's the service does not answer it with a user's account. A report that rests on nobody needs no account, so it asks for none, and that answer cannot touch its run.

**Why two outcomes where the identity does not resolve, and where the line between them falls.** A command that only reads gains nothing by refusing for want of an identity: the rest of its report holds without it. Where the read did not answer, the identity is unknown, and reading it as an account with nothing, such as one assigned no work, states a finding the command never made, as a board that did not answer is never read as an issue off the board (ADR-096). Where the service answered that the credential names no user's account, that nobody acts as a user is a fact. The service refuses the request for the account to a workflow's own token and to an App's, so the line falls at whether it answered for who the credential is, not at whether the request succeeded: a line at the request would tell a workflow under its own token that every one of its runs failed. A refusal for another reason, such as a rate limit, says nothing of the credential. A refusal of the credential itself meets a person's token revoked or expired, and neither a workflow's own token nor an App's, so it says that the credential is broken, not who acts. Read as a finding that nobody acts as a user, it would hide a broken credential behind a clean run, where a fault of the credential is none of what the command reports, as a fault of the check's credential is none of the issue's (ADR-096 point 5).

The resolution of the identity says which outcome it is, since the line rests on the service's status and words, and a command that read them for itself would decide on its own what counts as the service's answer, as a read of the board made outside its seam would (ADR-096 point 6). The exit code follows ADR-096 point 4, since a code of its own for this read would change the contract of each command whose codes tell no broken tool for one read, and its words say what it could not read. The rule binds in open mode too, since a report that misread a missing identity would misread it there alike. Only the command that shows the members rests its report on the identity on the evidence of the code, and it already reports an identity it cannot resolve, with the cause, so the two outcomes bind chiefly a command that comes to rest its report on the identity, and cost little until one does.

**Why a workflow's own steps stay outside the gate.** The gate binds the commands this capability ships, at their startup. A step of the project's copy of a workflow is a call that project makes, under the credential it gives the workflow, and the workflow runs there because the project installed it (DEC-019, "Why the post-check workflow is adopter-installed rather than kit-deployed"). No command of the capability runs in that step for a gate to sit in.

**Why DEC-021, DEC-018, DEC-020 and DEC-022 are refined in place.**

- **DEC-021.** Leaving the commands that only read out of its Tooling surface and its Implications narrows what it decides, and its decision, its modes, its predicate and its identity resolution stand, so DEC-021 reads true: a refinement in place. Its Decision's first sentence, on the operations that mutate external state, leaves out a write in the clone, such as setting the clone's instance id, which its Tooling surface gates, so it widens to every run of a command that can write, by point 1. Its Tooling surface, on the verb-subject scripts, leaves out the commands named by a noun alone, such as bootstrap and migrate (DEC-017), and the predicates the lifecycle engine calls, which its Decision gates, so it widens to every command of the capability, and its Implications' bullets on every verb-subject script and on CI invocations widen with it, so that they cover each command it gates. Each departure point 5 names then departs from its Decision and its Tooling surface alike.
- **DEC-018, DEC-020 and DEC-022** apply DEC-021's gate, and each narrows with it. A record is refined in place where its decision stands, narrowed, and superseded in part where another record decides otherwise of what it decides (the decisions README, "Refining an accepted record"). DEC-018 decides of the two workstream commands that show and list that they take the gate, and DEC-022 of the mesh check and of what its scheduled workflow needs behind a closed gate, yet each by DEC-021's rule applied, DEC-022 in its words "like every other verb-subject script", not by a choice of its own. With that rule narrowed, DEC-022's own reasoning, that no other authority gate applies since there is no destructive operation to authorise, reaches this record's conclusion, and its new sentences hold while its check only reads and reports, as point 6 has it. What each decides of its own stands, so the four are refined alike. Superseding DEC-022 in part was weighed (Alternatives).

**The costs.**

- In a closed project, a non-member runs the capability's views and checks, and sees through them what the hosting service and the repository already show them.
- An agent that works for a non-member learns that its person is no member at its first command that writes, not at a read before it. The command that shows the members tells it beforehand.
- The departures stay ungated until [project-kit#3352](https://github.com/aleskalfas/project-kit/issues/3352) takes each up. They are named here and in the suite for a person to see, though this record closes none.
- Point 5's list is state that an accepted record holds. Each change that takes a command out of the group edits it, which narrows what this record decides, so a person accepts each such edit, the build's and those #3352 leads to among them.
- A view that writes on what it finds keeps its gate until that write leaves it, so this record opens fewer views than their names suggest.
- The guard refuses a write only once a run reaches it, a program it does not know as a read fails a declared command's run until the build adds it, and its list of known reads is kept by hand, with the limits point 4 names.
- **What the build needs before the post-check workflow's check passes a closed gate:** the guard and its list of known reads, with the architecture record of its construction, the one gate function with each command that takes the gate moved onto it, the check of point 4, the coverage check, the test with its stand-ins, and the validation of an issue held to point 4. It needs no module split and no runner built.

### Alternatives considered
