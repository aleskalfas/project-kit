---
id: DEC-073
title: A command that only reads and reports takes no membership gate
status: proposed
date: 2026-11-16
author: Aleš Kalfas <kalfas.ales@gmail.com>
---

**In plain terms:** the membership gate keeps the methodology's operations with the people the member list names. Most of the capability's commands run it at startup, many that only look among them. So in a project whose gate is closed, the check the post-check workflow runs on each issue refuses whoever it cannot match to the list, and a workflow's own token or an App's names nobody the gate can match: the workflow fails every issue it checks. This record takes the gate off every command that cannot change anything, and off no other. Such a command runs for anyone, under any credential, the gate open or closed. It asks who runs it only where its report rests on that, and refuses nothing for want of the answer: where the hosting service gives none, it reports a read that did not answer, and where the service answers that the credential names no user's account, it says so. A command counts as one that only reads and reports by a property of what its runs do. It declares that in its code, it reaches the hosting service, git and the programs it starts only in a mode that lets nothing but a read through, and a scan and a test check it. A suite check makes the gate the default for every command the capability registers. The commands that can write and take no gate today are departures from [project-management:DEC-021-team-membership-gate], which that check names, and their group only shrinks. A command that takes the gate keeps it on every run, its dry runs included. So the post-check workflow validates each issue in a closed project as in an open one, with no member entry and no `PM_INVOKER_LOGIN`.

## Context

**The terms.**

- *The gate* is DEC-021's check of the member list: open where the list is absent or empty, and closed where it names at least one member, when it refuses whoever runs a command unless an entry names them. It is not the check of an issue's card on the board, which [project-management:DEC-071-filing-only-configured-board] and [pkit:ADR-096] call the membership check.
- *A command* of this capability is each command the capability registers in its package, the predicates the lifecycle engine calls among them.
- *A credential that names no user's account* is one for which the hosting service does not answer that it acts as a user's account, such as a workflow's own token or an App's (DEC-021, "Identity resolution"). Under it, the gate can match only `PM_INVOKER_LOGIN` or git's email.
- *The post-check workflow* is the workflow template that validates each issue opened, edited or reopened, and comments its findings ([project-management:DEC-019-mandatory-issue-state], "The post-check workflow template").
- *The maintainer* is whoever maintains this capability, in the project that builds it, from which the projects that adopt the capability receive this record.

**What the records say.**

- **DEC-021 gates what mutates, and puts the check in every script.** Its decision has every operation that mutates external state check the member list, and its Context names what the gate guards against: issues filed in the wrong shape, misclassified, moved in bulk or mistitled. Its Tooling surface and its Implications put the check at the startup of every other verb-subject script, those that only read among them. The command that shows the members applies the predicate only to report whether whoever runs it would pass.
- **CI runs reads.** [project-management:DEC-020-methodology-as-executable-commands] has CI use the environment check and the validation of an issue and of a pull request as its gating checks, and leaves the commands that mutate to people and agents (its Implications).
- **CI's way through the gate.** DEC-021 has a workflow that runs a gated command pass a closed gate as a service identity added to the list, or, under a credential that names no user's account, by `PM_INVOKER_LOGIN` from a secret. CI is not exempt by design (its Implications, "CI invocations").
- **The mesh check reads, and still gates.** [project-management:DEC-022-methodology-mesh] has its check make no mutating call, and gate "like every other verb-subject script", so its scheduled workflow needs an entry in the list, or `PM_INVOKER_LOGIN` from a secret, in a closed project ("Authority").
- **DEC-018 is split.** [project-management:DEC-018-workstream-taxonomy-and-lifecycle] has every workstream script, the two that only show and list among them, run the predicate at startup ("Authority"), while its Implications apply the gate to every workstream script that mutates.
- **The prerequisite gate's coverage.** The capability's check of a project's prerequisites ([project-management:DEC-017-prerequisites-bootstrap-migrate-discipline]) is called at the top of each command, and a suite check keeps it complete: each registered command calls it, or is named as exempt, with its reason.
- **Some reads write.** [pkit:ADR-071] has a read of a state issue restore the marker a hand removed from its description, the one write a read makes (point 5).

**The code.** Each command calls the gate itself. No check finds a command that does not, and several that write call none, though no accepted record has them run none. Some views write on what they find, as a read of a state issue does, or on one value of an option.

**The failure** ([project-kit#3290](https://github.com/aleskalfas/project-kit/issues/3290)). In a project whose gate is closed, the post-check workflow fails every issue it checks. Its check runs the validation of the issue, which checks membership before it validates. The step runs under the workflow's own token, an App's, or a person's token the project gives it for the board ([project-kit#3256](https://github.com/aleskalfas/project-kit/issues/3256)). The first two name no user's account ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)), and the workflow sets neither `PM_INVOKER_LOGIN` nor git's email. So the gate resolves nobody and refuses, and the job fails. Only a person's token for a member's own account gets through. The mesh check's scheduled workflow runs under the workflow's own token, and fails behind a closed gate the same way.

**The maintainer's ruling.** Of the ways out the issue names, the maintainer chose this one: a command that only reads and reports, and changes nothing, does not take the gate.

## Decision

**A command that only reads and reports takes no membership gate, and runs for whoever runs it. A command that takes the gate keeps it on every run, its dry runs included, as DEC-021 decides, and this record takes it off no command that can write.**

### 1. A command only reads and reports where no run of it writes

A run *writes* where it changes anything beyond what it prints and its exit code, save what the second list below counts as no write. The change counts wherever it is made, by the run or by a command it starts:

- **On the hosting service, or on any other service:** a request that changes what the service holds, such as an issue, a comment, a label, an assignee, a milestone, a card or a field on a board, a pull request, a review, a merge or a branch.
- **In the repository:** a change to its files, its index, its branches, its tags or any other ref, its stash, its worktrees or its configuration.
- **In what is kept for the project, the clone or the user:** a change to state that the capability, the backbone or another capability keeps, such as the member list, a journal, a claim, a queue of proposals, the clone's instance id or what the agent workspace holds, and a change to a file of the user's outside the repository.

These alone are no writes:

- **What the run prints,** to its output streams, or to a file its caller names to receive what the run would otherwise print. The caller chose that file, as it chooses where the output goes. A file that holds anything the run would not print is a write.
- **Its exit code.**
- **A fetch that adds objects and records what the remote holds, and changes nothing else:** no local branch or tag, no index, worktree, stash or configuration, and no ref but the remote-tracking refs and `FETCH_HEAD`. It runs with git's automatic housekeeping off (`gc.auto` and `maintenance.auto`), so that it prunes nothing.
- **The caches** kept for themselves by the tools the run runs on and by the programs it starts.
- **A file it makes for its own use,** outside what anyone else keeps, and removes before it exits.

A command *only reads and reports* where no run of it writes: whatever its options, whatever the services and the stored state hold, and whoever runs it. A command with any run that writes *can write*, and a dry run beside its write leaves it so. So a view that writes on one value of an option, or on what it finds, such as a record a hand has edited or an item that no longer holds, can write.

### 2. A command that only reads and reports takes no gate

- **It runs for whoever runs it:** a member and a non-member alike, in open mode and in closed, under a credential that acts as a user's account or under one that names none.
- **It asks who runs it only where its report rests on that,** such as the work assigned to whoever runs it, or whether whoever runs it would pass the gate. It then resolves the identity as DEC-021 says ("Identity resolution"). A report that rests on nobody asks the hosting service for no account.
- **Where nothing resolves the identity,** the run reports one of two outcomes, and in neither refuses anything for want of the identity:
  - **The hosting service gave no answer** for the credential, since its client is missing, or the request failed or ran out of time. The run treats the identity as a read that did not answer. It says that pkit cannot tell which account is acting, and why, in the place of what rests on that, gives the rest of its report, and exits as its contract has it exit where a read did not answer. It never reports what rests on the identity as a finding that there is none, such as no work assigned. Where its contract has no exit for a read that did not answer, it gains one.
  - **The hosting service answered that the credential acts as no user's account,** and nothing else names who runs it. That is a finding, not a read that did not answer. The run says that the credential names no user's account and that nothing names who runs it, reports what rests on the identity as resting on nobody, and exits as on a run whose reads all answered.
- **A report of whether whoever runs it would pass the gate,** which the command that shows the members makes, applies the predicate to say so, and refuses nothing on the answer. It is the exception to the exit of the first outcome above: what it reports is the gate's answer, which is definite where the identity is not. Behind a closed gate, an identity it cannot resolve would not pass, and the report says so, and why, and exits as on any clean run of it.
- **Its other checks stand.** This record changes only the gate. The check of the project's prerequisites runs as DEC-017 decides, and the guard on a session's writes to another repository as its record decides.

### 3. A command that takes the gate keeps it on every run

This record takes the gate off no command that can write, on any run. A command that takes it, whether it files, edits, comments, moves, assigns, closes, reopens, reviews, merges or writes the member list, or starts a command that does, takes it at its startup on every run, before any other work, its dry runs included, as DEC-021 decides. Behind a closed gate it refuses whoever no entry names, and whoever it cannot resolve. A workflow that runs such a command behind a closed gate passes only as DEC-021 lets CI pass: as a service identity added to the list, or by `PM_INVOKER_LOGIN` where its credential names no user's account.

A command that both shows and writes, such as a view with one option that writes or one that writes on what it finds, can write, so it carries no declaration, and where it takes the gate it keeps it for its every run. Where its reads should be open to everyone, the remedy is to split it into a command that only reads and reports and one that writes, or to take the write out of its reads by the record that decides that write.

### 4. A declaration in the code, held by construction and sampled by a test

- **The declaration.** A command that takes no gate because it only reads and reports declares so in the code, in a form the suite finds mechanically. The form is the build's: a mark in each command, or one registry beside the gate, as the prerequisite gate keeps its exemptions.
- **Held by construction.** A command that carries the declaration reaches the hosting service, git and every other program it starts only through the capability's shared runners, and runs them in a read-only mode. In that mode a runner lets through only a request or a command it knows to be a read, such as a command of this capability that carries the declaration, and fails every other, on every run, outside the suite as in it: one it does not know, such as a change sent in the form of a query, fails. No shared writer of the capability, such as its writer of the substrate, of comments, of state issues and the audit log, of the queue of proposals or of git, can be reached from the declared command's code. The command's own code writes no file save the one its caller names for its output, and starts no program and opens no connection save through those runners.
- **A scan finds it.** A scan in the suite finds each of these for each declared command, statically, as the capability holds its other shared seams by scans ([pkit:ADR-031] point 4).
- **A test samples it.** The suite runs each declared command and holds each run to point 1:
  - **Its options:** each of them; each value of one that takes a value from a set; for one that takes a free value, a value that names something the fixtures hold and one that names nothing; and for one that names a file to receive the output, a path in a folder of the test's own.
  - **Who runs it, and where:** each such way in open mode and behind a closed gate, for a member, for a non-member, under a credential that names no user's account and under one the service gives no answer for, with a terminal and without one, and at a terminal answering each prompt with each choice it offers.
  - **What it finds:** each such way against what the service answers and the stored state holds, in each shape the capability's code treats apart, such as empty and filled, as the capability wrote it and as a hand left it, and holding what still holds and what no longer does.
  - **Cut off:** the test runs with no network, the hosting service's host and every git remote pointed at stand-ins. The stand-in for the hosting service answers only the requests it knows to be reads, and fails every other, so a way of reaching the service that the test does not see fails loudly rather than going through.
  - **What passes:** the command is not refused, sends no request a stand-in fails, and leaves the repository and what is kept for the project, the clone and the user as they were, save what point 1 counts as no write.
- **What neither reaches.** The runners and the scan hold the ways a declared command reaches anything. The test samples its runs, each option, value and state alone, not every combination of them, so it does not hold that no run writes. The review of the change that adds a declaration, or that changes a command that carries one, judges the command against point 1 for what neither reaches.
- **Where they run.** The scan runs among the fast checks of the project that builds the capability. The test, which makes many runs of each declared command, runs in its full suite.
- **A declaration that fails** is mended in the command: it takes the gate, it stops writing, or it is split (point 3).

### 5. The gate is the default, and the commands that write without it can only grow fewer

- **The coverage check.** The suite finds, for each command the capability registers, that it calls the gate at its startup, or carries the declaration, or is one of the departures below. A command that is none of the three fails the suite. So each command added after this record takes the gate, unless it carries the declaration and passes point 4.
- **The departures.** Some commands that can write take no gate on the day this record is accepted, and no accepted record has them take none. Each departs from DEC-021, and this record neither makes nor mends those departures. The coverage check names them apart from the declarations, each with the follow-up the coordinator files, which decides whether each should take the gate.
- **The group only shrinks.** It holds only the commands that can write and took no gate on the day this record is accepted. The check fails on a command added to it later. So a command that can write leaves the gate by no way this record gives, and one that only reads and reports leaves it only by its declaration.

### 6. A workflow that only checks passes a closed gate

- **The post-check workflow's check** runs the validation of the issue, which only reads and reports. So in a project whose gate is closed, the workflow validates each issue under the workflow's own token, an App's or a person's, with no member entry and no `PM_INVOKER_LOGIN`, and passes or fails the issue on its findings alone, as where the gate is open.
- **The mesh check's scheduled workflow** runs the mesh check, which only reads and reports, and passes a closed gate the same way.
- **A workflow's own steps,** such as the post-check workflow's comment of its findings and its add to the board, and the mesh workflow's issue on drift, are calls the project's copy of the workflow makes under the credential the project gives it. No command of this capability runs in them, so the gate never bound them, and this record leaves them so.
- **An entry or a variable a project set for such a workflow** is needed no more. An entry added to the list for a workflow still admits, to every command that can write, any session that sets `PM_INVOKER_LOGIN` to its login under a credential that names no user's account. So it stays only where a workflow of the project runs a command that can write.

### What this refines, what it supersedes in part, and what stands

- **Refined in DEC-021:** its Decision's first sentence, its Tooling surface's check at startup, and three of its Implications, "Every verb-subject script", "The project-manager" and "CI invocations", each with the commands that only read and report left out (Implications).
- **Refined in DEC-018 and DEC-020:** each sentence that applies DEC-021's gate to a script that only reads and reports, alike (Implications).
- **Superseded in part in DEC-022:** what its Authority and its Implications decide of the mesh check's gate, that the check takes it and that its scheduled workflow needs an entry in the list, or `PM_INVOKER_LOGIN`, behind a closed gate (Implications).
- **Stands:** DEC-021's open and closed modes, its predicate, its refusal, its identity resolution, its readers of the identity, its bootstrap and its authority over changes to the list, and the gate on every command that takes it. DEC-022's mesh, its check and its workflow stand, save their gate.
- **Not decided here:**
  - **Whether each command that can write and takes no gate should take it.** Point 5 names each, and the follow-up the coordinator files decides them.
  - **Whether a read that mends what it finds should stop mending,** such as a read of a state issue that restores the marker a hand removed (ADR-071 point 5). While it mends, the command that makes it can write (point 1), and keeps its gate.
  - **Whether the post-check workflow adds a missing card on drift,** open in [project-kit#3271](https://github.com/aleskalfas/project-kit/issues/3271). Should it come to add the card through a command of this capability, that command can write and keeps the gate, and that step of the workflow passes a closed gate again only as DEC-021 lets CI pass.

## Rationale

**Why a command that only reads and reports takes no gate.** DEC-021's gate keeps the methodology's mediation with the people the list names. The harms its Context names, issues filed in the wrong shape, misclassified, moved in bulk or mistitled, are each made by a write, and a command that only reads and reports makes none of them. What it reads, the credential reads without it, from the hosting service and the repository, so a refusal keeps nothing from whoever is refused, and only costs a check where it runs. That cost falls hardest where nobody signs in: on a workflow under its own token or an App's, where DEC-020 runs the reads.

**Why not give the workflow an identity the gate admits.** That is the issue's other way out. Under a credential that names no user's account, the gate can match only `PM_INVOKER_LOGIN` or git's email, which may name anyone. DEC-021 accepts that cost for a command that writes: the gate is "no wall against someone set on passing it", and a workflow that writes needs some identity the list admits. For a command that only reads, the cost buys nothing, since the gate keeps nothing from anyone there. And each project that closes its gate would have to add an entry or set a secret before its check could run.

**Why a write is anything the run changes, save what is named.** A list of writes that counted only what it named would let through whatever it missed: a request to another service, state that another capability keeps, a file of the user's outside the repository. Counting every change as a write, and naming the few that are not, fails closed: a change nobody thought of keeps the gate.

**Why a file the caller names for the output is no write.** The run writes nothing there that it would not print, so the file is the caller's redirection of the output, whatever the output is, a report or a draft. A file that holds anything else is the run's own writing, wherever the caller points it.

**Why a property held in the code, rather than a list.** What keeps a command from writing ungated is what holds its declaration, not where the declaration is written. A list of the commands that take no gate, kept in this record or in the capability's documentation, has nothing behind it: a command that gained a write while the list still named it would write ungated, and nothing would find it. So the declaration is held three ways. The read-only runners hold it on every run, outside the suite as in it, so a write that a run makes only on a state it finds fails there rather than going through. The scan holds that those runners are a declared command's only ways to the service, git and the programs it starts, and that no shared writer is reachable from it, statically and fast. The test samples the rest: a write by a way the scan's form misses, on the modes, the identities, the terminals, the prompts and the states it varies. No test of runs holds that no run writes, so the review completes what the checks do not reach. A registry of declarations beside the gate is a list in the code with these checks behind it, which is why the form is left to the build.

**Why the commands that write ungated are frozen, rather than named with a reason.** A group that the coverage check accepted for any reason would let a new command that writes leave the gate by an entry and a follow-up that anyone can name, so the gate would be the default in name only. Freezing the group at the commands that take no gate on the day this record is accepted keeps the gate the default for every command added after it, and leaves the group only to shrink, as the follow-up decides each. Calling them departures says what they are: DEC-021 has them take the gate, and no record has them take none.

**Why every run of a command that takes the gate, its dry runs included.** A dry run previews the run it stands for, and the gate's refusal is part of what it previews: one that passed where the real run refuses would preview a write the run never makes. Deciding run by run would also rest each command's gate on its own reading of its arguments, where a mistaken reading lets a write through ungated. The guard on a session's writes to another repository does decide run by run, and skips a run that writes nowhere, since it guards where a run writes and such a run has nothing for it to check. The gate guards who may write, which a preview shows. A command that both shows and writes holds two reaches in one surface, which DEC-020 keeps apart on DEC-017's reasoning ("a read-only `show` script and a destructive `remove` script differ in blast radius"), so the remedy for its reads is the split.

**Why by what the command does, never by a mark of where it runs.** A run in CI could be told by a variable the CI sets, and the gate skipped there. Yet any session can set such a variable, so it would exempt a command that writes as readily as one that reads. A command's writes are a property of the command, which the suite can check. Where it runs is no such property.

**Why the test varies the mode, the identity, the terminal and what it finds.** A command that only reads asks who runs it only where its report rests on that. Some of the capability's commands write only at a terminal or behind a yes, and some views write only on what they find, such as a record a hand has edited or an item that no longer holds. A command whose write waited on an identity it resolved, on an open gate, on a terminal, on a prompt's answer or on a state the fixtures lacked would pass a test that never met it, and then write ungated for everyone. Each value of an option taken from a set is run for the same reason, since one value of a view's option may be the one that writes. The test runs cut off from the network, and its stand-in answers only what it knows to be a read, so that a way the test does not see fails, rather than passing unseen.

**Why a fetch is no write.** A fetch of this kind changes nothing the clone's people made or work on: no branch, tag, index, worktree, stash or configuration. It adds objects, which nothing reads until a ref names them, and records what the remote holds in the refs git keeps for that and rewrites on each fetch. Git's automatic housekeeping, which a fetch can start, can prune what a person made, such as a worktree's entry, so the fetch runs with it off. A view that fetches the head it shows, by name or by the ref the service keeps for a pull request, so as to read it, then stays a command that only reads and reports. A fetch that moved a local branch or brought tags would change what the clone's people work on, and is a write.

**Why ask who runs it only where the report rests on that.** Each request for the account counts against the hosting service's limits (DEC-021, its Implications, "The request for the account"), and under a workflow's token or an App's the service does not answer it with a user's account. A report that rests on nobody needs no account, so it asks for none, and that answer cannot touch its run.

**Why two outcomes where the identity does not resolve.** A command that only reads gains nothing by refusing for want of an identity: the rest of its report holds without it. Where the service gave no answer, the identity is unknown, and reading it as an account with nothing, such as one assigned no work, states a finding the command never made, as a board that did not answer is never read as an issue off the board (ADR-096). So the identity takes the way a read that did not answer takes, in words and in exit code. Where the service answered that the credential acts as no user's account, it did answer: that nobody acts as a user is a fact, and reporting it as a read that failed would tell a workflow under its own token that every one of its runs failed. The command that shows the members reports the gate's answer rather than the identity's, and the gate's answer is definite either way, since the gate refuses whoever it cannot resolve. So its exit stays the clean run's. The rule binds in open mode too, since a report that misread a missing identity would misread it there alike.

**Why a workflow's own steps stay outside the gate.** The gate binds the commands this capability ships, at their startup. A step of the project's copy of a workflow is a call that project makes, under the credential it gives the workflow, and the workflow runs there because the project installed it (DEC-019, "Why the post-check workflow is adopter-installed rather than kit-deployed"). No command of the capability runs in that step for a gate to sit in.

**Why DEC-021, DEC-018 and DEC-020 are refined, and DEC-022 superseded in part.**

- **DEC-021.** Its Tooling surface and its Implications put the check in every script, those that only read included. Leaving those out narrows what it decides, and its decision, its modes, its predicate and its identity resolution stand, so DEC-021 reads true: a refinement in place. Its Decision's first sentence names the operations that mutate external state, which leaves out a command whose writes stay in the clone, such as setting the clone's instance id, though its Tooling surface gates it. So that sentence comes to read "every run of a command that can write", by point 1, completing it to match its Tooling surface.
- **DEC-018 and DEC-020** apply DEC-021's gate to every script, and their own Implications or decisions say nothing of a read's gate apart from it, so each sentence narrows with DEC-021's.
- **DEC-022.** Its Authority decides of one named command, the mesh check, that it takes the gate, and of its scheduled workflow that it needs an entry in the list, or `PM_INVOKER_LOGIN`, behind a closed gate, and its Implications say so again. This record decides otherwise of both. A record that another overturns in part keeps its text, and its top line says so (the decisions README, "Refining an accepted record"), so DEC-022 is superseded in part, for the gate on the mesh check and its workflow. Refining it in place was weighed. Its reason is DEC-021's rule, "like every other verb-subject script", and with that rule narrowed, its own reasoning in the same paragraph, that no other authority gate applies since a read authorises no destructive operation, reaches the conclusion this record reaches. Yet its text decides the mesh check's gate by name, and where another record decides otherwise of what a record decides, the README has the first superseded in part. The cost of the supersession is that DEC-022's Authority keeps telling a project to add its workflow's identity to the list, under a top line that sends its reader here, while the documents the build rewrites stop saying it. The maintainer may still choose the in-place edit in accepting this record (Implications).

**The costs.**

- In a closed project, a non-member runs the capability's views and checks, and sees through them what the hosting service and the repository already show them.
- An agent that works for a non-member learns that its person is no member at its first command that writes, not at a read before it. The command that shows the members tells it beforehand.
- The departures stay ungated until the follow-up decides each. They are in the suite for a person to see, though this record closes none.
- A view that writes on what it finds keeps its gate until that write leaves it, so this record opens fewer views than their names suggest.
- Each command that only reads carries a declaration and reaches the service, git and the programs it starts only through the read-only runners, so a read the runners do not know fails until the build adds it to them as a read. The suite runs each declared command's test across modes, identities, terminals, prompts and states.

### Alternatives considered

- **Give the workflow an identity the gate admits:** an account added to the list for it, or `PM_INVOKER_LOGIN` from a secret. Rejected ("Why not give the workflow an identity the gate admits").
- **Have the workflow run its check with a member's own token,** which passes today. Rejected as the way out. Each project's check would rest on one person's token, which lasts until revoked and reaches whatever its scopes reach, and the workflow's own steps would then act in that person's name. An App's token, which expires within the hour, would still fail.
- **Skip the gate where a run is in CI,** told by a variable the CI sets. Rejected ("Why by what the command does, never by a mark of where it runs").
- **Take the gate at a command's first write rather than at its startup,** so that a run that writes nothing never meets it, with no declaration needed. Rejected. A command that writes reaches the hosting service, git and the state it keeps by more than one way, and nothing keeps a writer to one way as point 4 keeps a declared command to its runners, so a write made around such a gate would go ungated. And a command that writes would read, preview and ask its question before it refused, where DEC-021 checks before any other work.
- **Hold the declaration by the test alone,** with no read-only runners and no scan. Rejected. A test samples runs, so a write a run makes only on a state the fixtures lack would pass it, and then go through outside the suite. The runners fail such a write on every run, and the scan keeps a declared command to the runners.
- **Guard a declared command's requests at run time alone,** with no scan. Rejected. A guard in the runners holds only the ways that pass through them, and the scan is what keeps a declared command to those ways.
- **Decide run by run, so that a dry run of a command that can write takes no gate.** Rejected ("Why every run of a command that takes the gate, its dry runs included").
