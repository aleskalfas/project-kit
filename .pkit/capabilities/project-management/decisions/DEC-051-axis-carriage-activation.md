> **In one sentence:** where the adopter's substrate map binds an axis, that binding decides which substrate carries it and the board flag is not consulted for that axis; where the map says nothing, the flag governs carriage exactly as it does today.
>
> This is not a new mechanism. The map already works this way for every other substrate question: a binding activates **per axis**, and the presence of a binding — not a global switch — is what decides where an axis lives. That was chosen deliberately, so that no second declaration could disagree with a binding that exists (the activation ruling in [project-management:DEC-036-substrate-pluggable-adoption], decision point 2). The board flag is a second declaration of exactly that kind, older than the map and unnoticed when the rule was written. This record applies the existing rule to it.

## Context

An adopter reported a gate their own tooling could not satisfy ([#708]). Their config set `has_projects_v2_board: true`; their substrate map bound `priority` to the repo's native `P0/P1/P2` labels — a legitimate brownfield binding. Two accepted records answer the same question, and neither yields:

- **Carriage by board presence.** Priority and workstream "prefer board fields when a Projects v2 board exists; fall back to labels when not" — a per-axis table keyed on whether a board exists ([project-management:DEC-012-classification-axes]). Notably, `type` is a label in *both* columns of that table: it is always a label, board or no board.
- **Carriage by declared binding.** The substrate map lets an adopter bind each axis to what their tracker actually encodes, and its activation is *emergent* — the presence of a binding is the signal, per axis, with no global mode switch, chosen so that "no second source of truth that can disagree" could exist ([project-management:DEC-036-substrate-pluggable-adoption], decision point 2).

Each is coherent alone; together they leave one question — *which substrate carries this axis?* — answerable from two files that cannot see each other. The consequence in the reported repo: the filing verb honoured the flag and wrote no label, nothing wrote the board field, and the reviewer resolved through the map and found nothing. The failure is **silent** rather than loud — the value lands on neither substrate, and the presence gate for those two axes does not run at all when a board is configured, so nothing reports it. (An earlier telling of this report, including in a pending changeset, described a hard-reject from the review path; that description was not reproducible in the code and is corrected here.)

Two halves of the response have already shipped: the prerequisite check now refuses a double claim and the field-setting verb no longer reports success on a write it declined; and a board-carried axis is now **writable**, the field-setting verb resolving the board field and its option by name. What remains is the question those two deliberately did not answer, because answering it inside a verb would have settled it by implementation order: **when both sources speak, which one is the answer?**

## Decision

**In plain terms:** if your map names an axis, your map decides where it lives. If your map is silent about it, nothing changes from today.

1. **A map binding governs the axis it names.** Where the substrate map binds an axis (`label`, `title-prefix`, `derive`, or `unsupported`), that binding is the axis's substrate for **every** consumer — writer and reader alike — and `has_projects_v2_board` is not consulted for that axis. This is what resolves the reported failure: the adopter's `priority` becomes label-carried, so the filing verb writes the label the map names and the reviewer finds it.

2. **Where the map is silent, nothing changes at all.** No map, or a map that omits an axis: carriage stays exactly what it is today — including the rule that an axis omitted from a *present* map degrades rather than falling back to the kit's own labels. This record does not touch that rule.

   *(An earlier draft refined it so an omitted board-claimable axis fell back to the flag. Withdrawn: it conditioned on the axis kind but not on a board actually existing, so with no board configured the fallback became a demand for a kit label the adopter may be unable to create — the precise harm the degrade rule exists to prevent, and a regression of a shipped fix.)*

3. **One accessor encodes this, asked by every consumer.** The rule is "ask the map; if it is silent, ask the flag" — one composition consulted by every writer, reader, prerequisite check and mutator, so no two consumers can form different beliefs about where an axis lives. It sits **beside** the read seam rather than inside it: the seam keeps owning the adopter-immutable remap as a pure function over label names, and the accessor composes that with a config read. The read-path contract already pins this ordering — the adopter-binding question resolves first, and the board-versus-label distinction applies only underneath, in the kit-managed case ([project-management:ADR-026], the composition section) — so point 1 is closer to enforcing an accepted pin than to introducing a rule.

4. **The double-claim refusal becomes advisory.** The prerequisite check currently *refuses* a config that claims an axis on both substrates, because the state was unsatisfiable. Under point 1 it is satisfiable — the map wins and the axis is carried — so the refusal would block a now-legal configuration. It becomes a **warning** naming the consequence ("your map binds `priority` to labels, so the board's Priority field will go unused for it"). The field-setting verb carries a second refusal for the same state; under point 1 that one does not soften but *inverts* into a label write — and its never-report-success-on-a-declined-write posture does **not** survive the inversion unaided: the label path returns success-with-no-change when a write degrades, so a value with no remap entry would land nowhere and still exit zero. Preserving that posture on the path being entered is part of the work, not a consequence of it.

**Not decided here — gate placement.** This record settles *where* an axis lives, not *when* its presence is demanded or who pays when a predecessor omitted it. Those are a separate question, open and tracked: completeness is enforced today at filing and editing only, the Todo→Backlog doorway validates nothing, and an issue that never came through this capability is asked nothing at all. Nothing in this record should be read as settling that.

**Not decided here.** Declaring board carriage *explicitly in the map* — a `board` binding arm beside the existing four — is **named-deferred**. It is the right end state: today the only way to say "this axis lives on my board" inside the map is `unsupported: true`, which softens every rule needing the axis and is therefore a lie about a richly-encoded one. But an axis is not yet *gate-verified* on the board (the read path and its failure semantics are unsettled), and shipping the arm before then would let an adopter declare a substrate the gate cannot check. It lands with that read work.

## Rationale

**Why "the binding wins where it exists" rather than a global winner.** A global rule has to be wrong for one cohort. "The map always wins" breaks every board adopter without a map — carriage would come from a file they never wrote. "The flag always wins" makes the map's per-axis declarations inert, so a value-remap typo becomes undiagnosable and a later flag flip changes behaviour with no file change. Scoping the rule to *the axes an adopter actually declared* is the only version where nobody's working configuration changes meaning: a binding is an explicit statement of intent, and silence is not.

**Why this is the existing rule rather than a new one.** The map's activation is already per-axis and already keyed on the presence of a binding, and its authors rejected a global mode switch as "a second source of truth that can disagree with the actual presence of bindings." The board flag is a second source of exactly that kind. Point 1 applies that principle to it, and nothing else in the map's model is touched — an omitted axis still degrades exactly as it does today.

**Why one accessor, and why beside the seam rather than in it.** The reported failure is a *drift* failure: the writer read one source, the reader read the other, and neither was wrong. Only a single composition makes "they cannot disagree" structural rather than a convention every future script must remember. The read-path contract rejected folding the board-versus-label switch *into* the seam for two stated reasons — layering (the switch is a kit-internal choice, at a different layer from the adopter-immutable remap the seam owns) and speculative generality with no second consumer. The first is respected: the seam is untouched and the accessor sits above it. The second no longer holds in the form it was written — the drift it called speculative is now realised, between the field-setting verb and the review path.

**Why the refusal must soften.** Keeping a hard refusal for a state this record makes legal would block adopters from the very configuration it sanctions. The alarm still has value — an unused board field is worth flagging — but as information, not as a gate.

**Why the `board` arm waits.** Declaring a substrate the gate cannot verify is how the reported failure was built. The write half exists; the read half does not. Naming the arm as deferred keeps the honest sequence: declare it when it can be checked.

### Alternatives considered

- **The map always wins, even where silent.** Rejected — switches board adopters without a map onto kit labels that do not exist, and no migration can repair it: writing a map to declare two axes would degrade all the others, since an axis absent from a present map degrades by design.
- **The flag always wins; the map's conflicting bindings are suppressed at load** (the reporter's second option). Rejected — makes per-axis declarations silently inert, so remap and title-prefix errors become undiagnosable, and a later flag flip changes behaviour with no file change.
- **Refine the absent-axis rule so an omitted axis falls back to the flag** — in either form, for every axis or only for the three a board can claim. Rejected in both: for `type` the flag's answer is the kit's own label, and for any axis with no board configured the fallback is likewise a kit label — which is exactly the demand-for-uncreatable-labels harm the degrade rule exists to prevent. The narrower form additionally regressed a shipped fix. This record therefore refines nothing: a binding governs where it exists, and silence keeps today's behaviour.
- **Rule nothing; keep only the refusal** (the shipped state). Rejected — the refusal tells an adopter to choose but leaves every consumer free to choose differently, and a future consumer reading the flag would silently reintroduce the drift.
- **A `substrate_precedence` declaration.** Rejected — a third source of truth to adjudicate two.
- **A `board` binding arm now, ungated.** Rejected for this record, named-deferred above: it would sanction declaring a substrate no gate can check.
- **Retire `has_projects_v2_board` entirely.** Rejected — the flag has legitimate non-carriage jobs (board existence and identity, membership on filing, board-field hooks) and its removal is an adopter-breaking config change this question does not require.

## Implications

- **The per-axis carriage table is narrowed, not superseded.** It continues to govern wherever the map is silent, which includes every adopter with no map; what changes is its reach — it no longer decides an axis the adopter has explicitly bound elsewhere. Its other rulings (three required axes, type-always-a-label, mutual exclusivity, project-specific workstream values) are untouched. Two of its implications *are* narrowed and must be named in the scope note, not just the table: the parity it asks the project-manager to maintain between board fields and legacy label fallbacks during transition (point 5 blesses a permanently-unused board field instead), and its statement that status is also a board field when a board exists (a `derive`-bound state now governs). [project-management:DEC-012-classification-axes] receives that scope note in the same change-set.
- **The absent-axis rule is untouched** — an axis omitted from a present map still degrades. [project-management:DEC-036-substrate-pluggable-adoption] therefore needs no amendment; its no-second-source-of-truth principle is what this record enforces, and a pointer note recording that is enough.
- **The read-path contract gains a note, not an amendment.** The accessor in point 3 sits beside the seam and composes over it, which is what that contract already prescribes; its composition ordering and its absent-axis rule are both left intact. [project-management:ADR-026] receives a note in the same change-set — authored on the architecture side, where the contract lives — recording that the ordering it pinned now has a concrete consumer.
- **Board membership stays with the flag, deliberately.** The mandatory-state schema's condition over `has_projects_v2_board` governs *membership* — every issue must be on the configured board — not carriage. It must **not** be routed through the carriage accessor: doing so would silently drop that requirement for any board adopter with one label binding. The same applies to the board-identity read.
- **Consumer rewiring is the bulk of the work, and it is not small.** Every site that derives *carriage* from the flag asks the accessor instead: the prerequisite check, the filing verb, the validator, the field-setting verb, the lifecycle mover, the five workstream mutators, bootstrap, the mesh comparison, the self-test's substrate choice, and the back-fill tool. A guard test keeps the flag from re-acquiring carriage meaning by drift; without it point 4 is an assertion, not an invariant.
- **The workstream mutators need more than a substitution.** They gate kit-label *creation* on the flag today, and they build the label with the greenfield constructor rather than the write seam. Swapping the flag for the accessor would turn kit-label creation **on** for a board adopter with a label-bound workstream — creating an unmanaged label, and not even the one the remap names. They need the constructor switched and a label-bound arm that refuses or no-ops.
- **Adopter-facing documentation goes stale** where it states that board adopters skip the kit priority, workstream and state labels, as does the templated CI workflow that encodes the same assumption. Both update with the implementation.
- **Issues filed during the broken window need repair.** They carry the value on neither substrate; once the readers resolve through the seam they will be refused for a missing remapped label. The back-fill tool is the repair path, and whether it can write a remapped label (rather than only board-field intents) must be verified as part of the work.
- **No migration owed.** No adopter file is renamed, removed, or restructured, and no behaviour changes for an adopter who wrote no binding for the axis in question. The behaviour change lands where the adopter's map already asked for it — turning an unsatisfiable gate satisfiable — plus the repair above.
- **Named-deferred:** the `board` binding arm (widening the map's exactly-one-binding constraint to admit it, which means editing the existing arms' exclusion clauses rather than merely adding a fifth), and gate-verification of a board-carried axis, both behind the board read path and its failure semantics.
- **Surface change** for the capability — a resolution rule adopters can depend on, plus a softened check. The change-set declares a changeset; version numbers are written by the release step. The pending changeset that carries the corrected failure description (see Context) is amended in the same change-set rather than contradicted by a second one.
- **The softening lands last.** Relax the double-claim refusal before the consumers are rewired and the validator's board guard is lifted, and the reported state becomes *less* detectable than today — hard failure, then warning, then nothing. Order: accessor and rewiring first, softening last.
- **Acceptance gates the implementation**: the accessor, the rewiring, the two seam-blind readers, the softened check, and the documentation updates may not land while this record is `proposed`.
