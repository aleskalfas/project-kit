> **In one sentence:** where the adopter's substrate map binds an axis to a substrate, that binding decides which substrate carries it and the board flag is not consulted for that axis; where the map says nothing, the flag governs carriage exactly as it does today. The map gains a `board:` arm so that board carriage is among the things it can say — until now it was not, and adopters were being told to spell it `unsupported: true`, which means the opposite.
>
> This is not a new mechanism. The map already works this way for every other substrate question: a binding activates **per axis**, and the presence of a binding — not a global switch — is what decides where an axis lives. That was chosen deliberately, so that no second declaration could disagree with a binding that exists (the activation ruling in [project-management:DEC-036-substrate-pluggable-adoption], decision point 2). The board flag is a second declaration of exactly that kind, older than the map and unnoticed when the rule was written. This record applies the existing rule to it.

## Context

An adopter reported a gate their own tooling could not satisfy ([#708](https://github.com/aleskalfas/project-kit/issues/708)). Their config set `has_projects_v2_board: true`; their substrate map bound `priority` to the repo's native `P0/P1/P2` labels — a legitimate brownfield binding. Two accepted records answer the same question, and neither yields:

- **Carriage by board presence.** Priority and workstream "prefer board fields when a Projects v2 board exists; fall back to labels when not" — a per-axis table keyed on whether a board exists ([project-management:DEC-012-classification-axes]). Notably, `type` is a label in *both* columns of that table: it is always a label, board or no board.
- **Carriage by declared binding.** The substrate map lets an adopter bind each axis to what their tracker actually encodes, and its activation is *emergent* — the presence of a binding is the signal, per axis, with no global mode switch, chosen so that "no second source of truth that can disagree" could exist ([project-management:DEC-036-substrate-pluggable-adoption], decision point 2).

Each is coherent alone; together they leave one question — *which substrate carries this axis?* — answerable from two files that cannot see each other.

There is a third strand, found only after this record was first accepted, and it is why the record's first form was wrong. **The map had no way to say "this axis lives on my board."** No such binding existed. So the prerequisite check's own remediation instructed adopters to write `unsupported: true` for a board-backed axis — a declaration the schema defines as meaning the axis has *no encoding at all* and that the features needing it degrade. The kit was telling adopters to say the opposite of what they meant, and the reporting adopter's map says so in its own comments: both affected axes are marked unsupported, each annotated that the board carries the value because the map cannot express it. Any rule that treats a binding as authoritative therefore has to answer what `unsupported` is, or it silently strips the board from everyone who followed the instructions. The consequence in the reported repo: the filing verb honoured the flag and wrote no label, nothing wrote the board field, and the reviewer resolved through the map and found nothing. The failure is **silent** rather than loud — the value lands on neither substrate, and the presence gate for those two axes does not run at all when a board is configured, so nothing reports it. (An earlier telling of this report, including in a pending changeset, described a hard-reject from the review path; that description was not reproducible in the code and is corrected here.)

Two halves of the response have already shipped: the prerequisite check now refuses a double claim and the field-setting verb no longer reports success on a write it declined; and a board-carried axis is now **writable**, the field-setting verb resolving the board field and its option by name. What remains is the question those two deliberately did not answer, because answering it inside a verb would have settled it by implementation order: **when both sources speak, which one is the answer?**

## Decision

**In plain terms:** if your map names an axis, your map decides where it lives. If your map is silent about it, nothing changes from today.

1. **A map binding governs the axis it names.** Where the substrate map binds an axis to a substrate (`label`, `title-prefix`, `derive`, or `board` — see point 2), that binding is the axis's substrate for **every** consumer — writer and reader alike — and `has_projects_v2_board` is not consulted for that axis. This is what resolves the reported failure: the adopter's `priority` becomes label-carried, so the filing verb writes the label the map names and the reviewer finds it.

   **`unsupported` is not such a binding.** It declares the axis has *no encoding at all* — the schema defines it as degrading the feature that needs it, and as equivalent to omitting the axis. It names no substrate, so it cannot govern which substrate carries the value; an `unsupported` axis is not carried anywhere, by anyone. Treating it as a governing binding was this record's own error at acceptance, and it was not academic: the prerequisite check's remediation was telling board adopters to write `unsupported: true` to *mean* board carriage, so the rule would have silently stopped the board write for every adopter who followed the kit's own instructions — a worse form of the failure this record exists to end. Point 2 gives them the words to say what they meant.

2. **The map gains a `board:` arm, so board carriage can be declared honestly.** `board: true`, admissible on `priority` and `workstream`, says the value lives on a field of the configured Projects-v2 board. It is **parameterless by design**: the field's identity is a *write* parameter and already has a declaration point on the `after_create_issue` hook — a second one was refused in config for exactly this reason ([project-management:DEC-037-adoption-ceremony], which deliberately deferred a map field-binding kind pending "a future read-path consumer [that] genuinely needs the binding resolvable without loading `hooks.yaml`"). The carriage accessor in point 4 is that consumer, so the deferral's stated release condition is met; and because the arm carries no parameters, it does not raise that deferral's objection — it creates no second declaration point for the write parameters, which stay on the hook. A field *name* in the map would also be a claim about a live board the file cannot self-validate, which is the principle the deferral rested on.

   Scope is deliberately narrow. `type` is excluded permanently: PR-title alignment reads the type **label**, and a board field is invisible from a PR, so its label-carriage is a functional dependency rather than a preference. `state` is excluded **for now** and tracked separately — state inference resolves closed→`done`, then a label read, then a milestone, and reading a board Status field needs a new detector kind rather than a new binding. Declaring it before then would sanction a substrate no gate can check, which is how the reported failure was built. `board: true` under a config declaring no board is unsatisfiable and is **refused** — that refusal is new, and must not inherit the softening in point 5. An optional `default:` may accompany the arm as corroborating metadata only, since the hook carries the write; one with no matching hook behind it is reported.

3. **Where the map is silent, nothing changes at all.** No map, or a map that omits an axis: carriage stays exactly what it is today — including the rule that an axis omitted from a *present* map degrades rather than falling back to the kit's own labels. This record does not touch that rule. The two are compatible because they speak about different substrates: the degrade rule governs whether the *kit's own labels* may be demanded, and a board field is not a label — so an axis omitted from a present map under a configured board was never within that rule's reach, and its carriage stays with the flag exactly as today.

   This is deliberate conservatism, not an oversight. Once point 2 exists it is tempting to make a present map *authoritative* — anything unlisted degrades — which is tidier and says what it means. Rejected: that is a silent behaviour change delivered by upgrade to every board adopter with a partial map, whose priority would stop being written and stop being demanded with nothing reported. That is the same failure class as the report this record answers, arriving by our own hand. The cleanliness is bought with a **diagnostic instead of semantics**: the prerequisite check reports each board-claimable axis absent from a present map under a configured board — "carried by your board; declare `board: true` to make it explicit." Same destination, nobody's working configuration changes meaning. Flipping absent-to-degrade later becomes a deliberate breaking change whose migration can, by then, write the repair.

   *(An earlier draft refined it so an omitted board-claimable axis fell back to the flag. Withdrawn: it conditioned on the axis kind but not on a board actually existing, so with no board configured the fallback became a demand for a kit label the adopter may be unable to create — the precise harm the degrade rule exists to prevent, and a regression of a shipped fix.)*

4. **One accessor encodes this, asked by every consumer.** The rule is "ask the map; if it is silent, ask the flag" — one composition consulted by every writer, reader, prerequisite check and mutator, so no two consumers can form different beliefs about where an axis lives. The ordering this rule expresses is **the ordering the read-path contract already pins** — the adopter-binding question resolves first, and the board-versus-label distinction applies only underneath, in the kit-managed case ([pkit:ADR-026], its section on reconciling with the pre-existing in-schema substrate switch). So this rule introduces no new architecture: **it restores that ordering where the code inverted it.** Two guards today resolve board-versus-label *first* and reach the seam only in the no-board branch, so under a configured board priority and workstream never reach the seam at all — which is the mechanism of the reported failure. The `type` axis already resolves in the pinned order in those same files, so the target shape exists in-tree as a working oracle. *Where* the composition lives is a placement question the contract explicitly assigned to implementing work, not to a decision; this record fixes the rule and leaves placement there.

5. **The double-claim refusal becomes advisory.** The prerequisite check currently *refuses* a config that claims an axis on both substrates, because the state was unsatisfiable. Under point 1 it is satisfiable — the map wins and the axis is carried — so the refusal would block a now-legal configuration. It becomes a **warning** naming the consequence ("your map binds `priority` to labels, so the board's Priority field will go unused for it"). The field-setting verb carries a second refusal for the same state; under point 1 that one does not soften but *inverts* into a label write — and its never-report-success-on-a-declined-write posture does **not** survive the inversion unaided: the label path returns success-with-no-change when a write degrades, so a value with no remap entry would land nowhere and still exit zero. Preserving that posture on the path being entered is part of the work, not a consequence of it.

**Not decided here — gate placement.** This record settles *where* an axis lives, not *when* its presence is demanded or who pays when a predecessor omitted it. Those are a separate question, open and tracked: completeness is enforced today at filing and editing only, the Todo→Backlog doorway validates nothing, and an issue that never came through this capability is asked nothing at all. Nothing in this record should be read as settling that.

**Now decided, having been named-deferred here at first authoring.** Declaring board carriage explicitly in the map is point 2. The deferral's ground was that an axis is not *gate-verified* on the board — the read path and its failure semantics unsettled — and shipping the arm before then would let an adopter declare a substrate the gate cannot check. Both halves of that ground have since been answered rather than waived. The read exists and is careful: a board field's current value is read through a query that trusts only a positively-confirming response and treats every other shape as unread. And the failure semantics are now ruled: an unreadable board **raises an error**, scoped to projects that actually expect a value from a board, because a board that will not answer is a broken tool rather than a missing value — distinct from a board that answers *unset*, which is a separate question about missing values. Those semantics are a read-path contract rather than a precedence rule, so they are recorded architecture-side in their own record, not here.

## Rationale

**Why "the binding wins where it exists" rather than a global winner.** A global rule has to be wrong for one cohort. "The map always wins" breaks every board adopter without a map — carriage would come from a file they never wrote. "The flag always wins" makes the map's per-axis declarations inert, so a value-remap typo becomes undiagnosable and a later flag flip changes behaviour with no file change. Scoping the rule to *the axes an adopter actually declared* is the only version where nobody's working configuration changes meaning: a binding is an explicit statement of intent, and silence is not.

**Why this is the existing rule rather than a new one.** The map's activation is already per-axis and already keyed on the presence of a binding, and its authors rejected a global mode switch as "a second source of truth that can disagree with the actual presence of bindings." The board flag is a second source of exactly that kind. Point 1 applies that principle to it, and nothing else in the map's model is touched — an omitted axis still degrades exactly as it does today.

**Why one accessor, and why beside the seam rather than in it.** The reported failure is a *drift* failure: the writer read one source, the reader read the other, and neither was wrong. Only a single composition makes "they cannot disagree" structural rather than a convention every future script must remember. The read-path contract rejected folding the board-versus-label switch *into* the seam for two stated reasons — layering (the switch is a kit-internal choice, at a different layer from the adopter-immutable remap the seam owns) and speculative generality with no second consumer. The first is respected: the seam is untouched and the accessor sits above it. The second no longer holds in the form it was written — the drift it called speculative is now realised, between the field-setting verb and the review path.

**Why the refusal must soften.** Keeping a hard refusal for a state this record makes legal would block adopters from the very configuration it sanctions. The alarm still has value — an unused board field is worth flagging — but as information, not as a gate.

**Why the `board` arm waits.** Declaring a substrate the gate cannot verify is how the reported failure was built. The write half exists; the read half does not. Naming the arm as deferred keeps the honest sequence: declare it when it can be checked.

### Alternatives considered

- **The map always wins, even where silent.** Rejected — switches board adopters without a map onto kit labels that do not exist, and no migration can repair it: writing a map to declare two axes would degrade all the others, since an axis absent from a present map degrades by design.
- **The flag always wins; the map's conflicting bindings are suppressed at load** (the reporter's second option). Rejected — makes per-axis declarations silently inert, so remap and title-prefix errors become undiagnosable, and a later flag flip changes behaviour with no file change.
- **Refine the absent-axis rule so an omitted axis falls back to the flag** — in either form, for every axis or only for the three a board can claim. Rejected in both: for `type` the flag's answer is the kit's own label, and for any axis with no board configured the fallback is likewise a kit label — which is exactly the demand-for-uncreatable-labels harm the degrade rule exists to prevent. The narrower form additionally regressed a shipped fix. This record therefore refines no rule of the map's model: a binding governs where it exists, and silence keeps today's behaviour. (It does narrow the reach of the per-axis carriage table — see Implications — which is a scope refinement of that record, not of the map's.)
- **Rule nothing; keep only the refusal** (the shipped state). Rejected — the refusal tells an adopter to choose but leaves every consumer free to choose differently, and a future consumer reading the flag would silently reintroduce the drift.
- **A `substrate_precedence` declaration.** Rejected — a third source of truth to adjudicate two.
- **A `board` binding arm carrying the field name** (`board: {field: "Priority"}`). Rejected: the field identity is a write parameter with an existing declaration point on the hook, and a third place answering "which board field?" is the second-source-of-truth failure this record exists to end — the equivalent knob was already refused in config on that ground. A field name is also a claim about a live board the map cannot self-validate, where `board: true` is checkable against config alone. The honest tension worth naming: the write path resolves board fields *by name* and tells an adopter to rename their own field when none matches, which is a greenfield posture inside a brownfield feature. That is the trigger that would later earn the parameterised form — on a reported instance, not pre-emptively.
- **Excluding `unsupported` from the governing set, and stopping there** — the cheap repair for the collision point 1 describes, leaving the map still unable to express board carriage. Rejected: it enshrines the workaround rather than ending it, keeps the kit instructing adopters to write a declaration that means the opposite of what they intend, and mis-serves the honest case too — an adopter who genuinely means "I do not track priority" would have the board carry it anyway.
- **Making a present map authoritative for board-claimable axes.** Rejected — see point 3; a silent degrade delivered by upgrade to anyone with a partial map.
- **Retire `has_projects_v2_board` entirely.** Rejected — the flag has legitimate non-carriage jobs (board existence and identity, membership on filing, board-field hooks) and its removal is an adopter-breaking config change this question does not require.

## Implications

- **The per-axis carriage table is narrowed, not superseded.** It continues to govern wherever the map is silent, which includes every adopter with no map; what changes is its reach — it no longer decides an axis the adopter has explicitly bound elsewhere. Its other rulings (three required axes, type-always-a-label, mutual exclusivity, project-specific workstream values) are untouched. Two of its implications *are* narrowed and must be named in the scope note, not just the table: the parity it asks the project-manager to maintain between board fields and legacy label fallbacks during transition (the warning in point 5 blesses a permanently-unused board field instead), and its statement that status is also a board field when a board exists (a `derive`-bound state now governs). [project-management:DEC-012-classification-axes] receives that scope note in the same change-set.
- **The absent-axis rule is untouched** — an axis omitted from a present map still degrades. [project-management:DEC-036-substrate-pluggable-adoption] therefore needs no amendment; its no-second-source-of-truth principle is what this record enforces, and a pointer note recording that is enough.
- **The read-path contract owes an in-place amendment — a factual correction and a placement pin, not a change of direction.** Its as-built claim that board-versus-label "stays an in-schema concern" is false as executed: the two substrate fields are prose descriptions typed as strings with **no code readers**, while the branch runs as inline flag reads scattered across the verbs. Its composition ordering is unchanged and this record's rule restores it. The amendment also pins the placement the contract delegated to implementing work, and records that its reason for deferring a unified resolution surface for v1 — no second demanding consumer — has expired, **without** reversing that rejection: absorbing board-versus-label into the seam's own resolution stays rejected on the layering ground, which holds. Authored on the architecture side under its custody, with the maintainer sign-off that record's own non-self-acceptance clause requires.
- **The flag keeps one carriage job, and it is a legacy default rather than a design.** Under point 3 `has_projects_v2_board` still decides carriage wherever the map is silent. That is retained to avoid a silent behaviour change, not because it is right, and a later decision retires it once `board:` declarations are widespread. Naming it as a residue matters: a future author must not read the retained carriage as endorsed. It also recalibrates the guard test — the flag does not lose carriage meaning entirely, so the guard is "**exactly one** site reads the flag for carriage, the accessor", not a blanket prohibition that would either fail on the accessor or be weakened to uselessness.
- **Board membership stays with the flag, deliberately.** The mandatory-state schema's condition over `has_projects_v2_board` governs *membership* — every issue must be on the configured board — not carriage. It must **not** be routed through the carriage accessor: doing so would silently drop that requirement for any board adopter with one label binding. The same applies to the board-identity read.
- **Consumer rewiring is the bulk of the work, and it is not small.** The rule is that **every site deriving *carriage* from the flag asks the accessor instead** — the roster of those sites, and the per-site judgement of which reads are carriage rather than board identity or membership, belongs with the implementation issue rather than here, where it would rot. A guard test keeps the flag from re-acquiring carriage meaning by drift; without it point 4 is an assertion, not an invariant.
- **The workstream mutators need more than a substitution.** They gate kit-label *creation* on the flag today, and they build the label with the greenfield constructor rather than the write seam. Swapping the flag for the accessor would turn kit-label creation **on** for a board adopter with a label-bound workstream — creating an unmanaged label, and not even the one the remap names. They need the constructor switched and a label-bound arm that refuses or no-ops.
- **Adopter-facing documentation goes stale** where it states that board adopters skip the kit priority, workstream and state labels, as does the templated CI workflow that encodes the same assumption. So does the prerequisite check's own conflict message — the one place the mis-described failure (a hard-reject from the review path, see Context) is actually *shown to an adopter*, in both its docstring and its live remediation text. All update with the implementation.
- **Issues filed during the broken window need repair, and the repair path named at first authoring does not exist.** They carry the value on neither substrate; once the readers resolve through the seam they will be refused for a missing remapped label. This record originally named the back-fill tool as the repair and left its capability to be verified. It has been verified: back-fill knows two change kinds — a board-field write and a milestone assignment — and carries no label-write intent at all. So the strict reader **must not land before a repair exists**, or an adopter goes from a silent miss to every issue blocked with no tool to fix it. Providing that repair is part of this work, not an assumption of it.
- **No migration owed.** No adopter file is renamed, removed, or restructured, and no behaviour changes for an adopter who wrote no binding for the axis in question. The behaviour change lands where the adopter's map already asked for it — turning an unsatisfiable gate satisfiable — plus the repair above.
- **The `board` arm's case was always stronger than convenience, which is why it is now point 2 rather than a deferral.** The board is no longer a kit-internal encoding: the field-setting verb resolves a Projects-v2 field *by name* against the live board and, when none matches, tells the adopter to rename their own field rather than teaching the kit a mapping — so it is substrate the adopter owns and the kit cannot create, governed by its own write contract. Under that reading a `board:` binding in the map is where the substrate structurally belongs, with the flag reduced to existence, identity and membership.
- **The exactly-one-binding constraint grows by one line, not by editing four.** The arm is admitted by a fifth `oneOf` branch. The existing branches' explicit "and not the others" clauses are **redundant** — `oneOf` already means *exactly one*, so a two-arm document matches two branches and fails on the count alone — and are removed in the same change. Verified against the accepted document set rather than asserted: a two-arm axis, an arm-less axis, and an axis carrying only a `default:` are all still refused. No `schema_version` bump, and therefore no migration owed for the schema change itself.
- **Admissibility is enforced per axis, not by convention.** `type` and `state` refuse the arm in the schema. Narrowing later is not possible; widening later is additive, which is why the narrow start is the safe one.
- **The onboarding ceremony is where this failure was manufactured, and it is repaired there.** The brownfield ceremony already *detects* a workstream-shaped board field and then declines to draft a binding for it, directing the adopter to a hook instead, because no such binding kind existed. It can now draft `board: true`. Fixing the ceremony matters more than fixing the message: the live adopter's broken map came out of it.
- **Adopters holding the workaround are told, not rewritten.** The signature is a three-way conjunction — a configured board, an axis marked `unsupported: true`, and a matching `set-board-field` hook — and it is not sound enough to apply silently: a hook writing a differently-named field misses, and an adopter can genuinely mean "disabled for the kit" while running their own board hook. A warn-on-detect migration reports the one-line change and exits; it does not edit the map, which is adopter-owned hand-authored intent the capability already refuses to auto-edit elsewhere.
- **Named-deferred:** gate-verification of a board-carried **state** axis, behind a detector kind that can read a board Status field.
- **Surface change** for the capability — a resolution rule adopters can depend on, a new binding arm, plus a softened check. The change-set declares a changeset; version numbers are written by the release step. This record originally instructed that a *pending* changeset carrying the corrected failure description be amended rather than contradicted. There is no such pending changeset: that text already shipped, and its false claim of a hard-reject from the review path is in a released changelog entry, which a changeset cannot amend. The correction is carried by this record and by the remediation text itself; the released entry stands as history.
- **The softening lands last.** Relax the double-claim refusal before the consumers are rewired and the validator's board guard is lifted, and the reported state becomes *less* detectable than today — hard failure, then warning, then nothing. Order: accessor and rewiring first, softening last.
- **The remaining seam-blind readers must move onto the accessor**, or the rule is unrealised for them: the reviewer-set helper resolves the workstream axis through a kit-prefix read with no map awareness, and the mesh comparison matches the prefix inline. (The validator and the issue display were the other two; both have since been fixed.) Tracked separately, named here because the rule's benefit depends on them.
- **Acceptance gates the implementation.** This record is `accepted`, so the work is unblocked — but the ordering above is part of the ruling, not advice: the ceremony and the corrected guidance land before the carriage rewiring, and the softening lands last.
