**In plain terms:** Tasks reach a worker as they do without messages: a planner or a lead files them, the person schedules them, and the worker takes the next ready Task it may take, whoever filed it. This record fits the harness's messages between sessions to the same topology of seats. A worker's seat may name, in the committed topology, the planner's or the lead's seat that directs it. Where the harness carries messages, that seat's session may message the worker to wake it, or to name a ready Task the worker may take next. A message never carries work the tracker does not hold. The worker counts a message as a **directive** only where it comes from the session its directing seat's state issue records, by the session's name and folder, and any other message is information. The worker reports when a Task is done or stops on what it cannot settle, on the tracker and by message where it can. A question for the person goes to the person, through the directing seat where the worker cannot reach them. No message is the person's authorisation, and neither is a Task. Directives stay within one repository's topology, and without messaging the tracker alone carries the work. The project-manager agent holds the harness's tools for messaging and for listing sessions, through a privilege the capability defines and grants to its own agent, which the permissions overview reports as a widening.

## Context

**What stands.** In a project that runs agents in parallel, the committed topology names each seat, its role and the pools it serves ([project-management:DEC-059-topology-of-seats], [project-management:DEC-061-pools-of-workers]). A planner or a lead files Tasks, a person schedules them, and a worker takes the next ready Task from its pools, or from the one shared pool where the topology declares none, claimed so that no second agent takes it. Several planners may file into one pool. A fresh builder builds each of a worker's Tasks, from a brief written from the Task alone ([project-management:DEC-063-task-builder]). Which clone holds a seat is kept on the seat's state issue ([project-management:DEC-058-state-issues]). The project-manager agent is withheld the harness's tools that message other sessions and list them, since work reaches seats through the pool, not through messages ([project-management:DEC-068-session-agent-tools] point 2).

**What the person decided.** On 17 November 2026 the person decided that the topology and its pools are the one model of delegation, extended to the harness's messages, and that no work exists only in a message ([project-kit#3392](https://github.com/aleskalfas/project-kit/issues/3392)). Only the seat whose role directs a worker, as the committed topology names it, directs it by message, checked against the session the seat's state issue records. Reports go up on the tracker and by message, and a question for the person goes to the person. The agent holds the harness's tools for messaging and for listing sessions. A message is never the person's authorisation, nor is a Task, each session changes only its own repository ([COR-039](../../../decisions/core/COR-039-session-repo-mutation-boundary.md)), and without messaging the tracker alone carries the model. This record holds those decisions, and settles what they leave open.

**Terms.**

- **Messaging** is a harness's tool that sends a message from one session to another session, and, where the harness allows it, to a subagent the session resumes or to a teammate, an agent the harness joins to the session beside its subagents, as Claude Code's agent-teams feature does. **The listing** is its tool that lists what messaging reaches, each session with its name, its folder and the address a message goes to.
- **A worker's directing seat** is the seat the topology names to direct it (point 3). **A directive** is a message from that seat's session that passes the worker's check (point 5). **A report** is a worker's message to its directing seat.
- **The person** is a person who decides what reaches the project's default branch, as [COR-064](../../../decisions/core/COR-064-answer-delegate.md) defines the term.

**What the harness offers.** Read from Claude Code's documentation on 17 November 2026, not measured:

- **Reach.** A session reaches any other session on its machine by default, whatever its folder or repository, and other machines only through the harness's remote control. It reaches no session across a container and its host. A session in its bare mode cannot be reached, a stopped session cannot be messaged, and no queue is documented.
- **Teammates and resumes.** Messaging also reaches a teammate, which a named spawn becomes under the agent-teams feature, and resumes a subagent by its id or name.
- **Names.** The listing names each session by the name the person gives it, or one the harness picks. Names are not unique: sessions that share a name each get a short identifier as their address. Each row shows its session's working folder, except under remote control.
- **The sender.** A message arrives marked as from another session, with the sender's name and a reply address. Nothing proves the sender. A message cannot approve a permission prompt or change configuration, and a command in it never runs.
- **Held messages.** A session that bypasses permission prompts holds a message from a sender that does not, and is delivered one from a sender that also bypasses. A person may approve a held message at its terminal before a deadline of a few minutes, and a session with no terminal to show the approval drops it then.
- **Helpers.** A helper running in the background keeps messaging, but not the listing.

The documentation leaves these unconfirmed, so the build measures them before it rests anything on them:

1. whether an agent definition the project deploys holds messaging and the listing where it withholds neither
2. whether a session can read its own name, and whether an interactive session keeps its name across a restart
3. whether a message's reply address is the address the listing shows for its sender
4. which folder a row of the listing shows: the session's first folder or its current one, a worktree's or its clone's
5. what a held message does at its deadline in each kind of session, and which setting for inbound messages prevails where several set one
6. whether a builder's sandboxed run can send or receive a message

**Where a measurement does not hold.** The record names its way for three outcomes: a session that cannot read its own name is given it (point 4), a reply address the listing does not show falls back to the sender's name (point 5), and a build's run that reaches messaging is denied it (point 2). Any other measurement that does not hold as the documentation reads, such as a listing that shows another folder than the one a session records, leaves point 5's check unable to pass. No message is then a directive, and the tracker carries the work (point 1), until a record decides again. Where the first does not hold, so that no definition the project deploys can hold the tools, this record is reopened before the build goes on.

## Decision

**The topology alone says who directs a worker by message: the planner's or the lead's seat it names on the worker's seat. That seat's session may message the worker to wake it or to name a ready Task it may take next, never work the tracker does not hold, while Tasks reach the worker through its pools, or the one shared pool where the topology declares none, whoever files them. The worker counts a message as a directive only from the session its directing seat's state issue records, reports up, and sends the person's questions to the person. No message or Task is the person's authorisation, directives stay within one repository's topology, and without messaging the tracker alone carries the work.**

### 1. One model, over the tracker and the harness's messages

The topology's seats, roles, pools and claims decide who directs whom and who builds what, whichever way the work travels.

- **On the tracker,** a planner or a lead files Tasks, the person schedules them, and the worker takes the next ready Task it may take: from its pools where the topology declares them, and from the one shared pool otherwise (DEC-061 point 8). A Task reaches the worker so, whoever filed it. What a record lets a directing seat set for its worker, the seat writes on the worker's state issue. This form stands alone where messaging does not reach.
- **Through the harness,** the directing seat's message wakes the worker, or names a Task the tracker already holds ready for it (point 6). A directive that names no Task only wakes the worker, which then reads the tracker. The worker's reports go up the same way (point 8).
- **No work lives only in a message.** A message names a Task, or none. What must outlast it, such as a Task filed, changed, held back or taken out of a pool, is written on the tracker, under the rules for that write. So a lost message costs only the time it would have saved.

### 2. The agent holds messaging and the listing

- **Both tools, wherever the harness gives them.** The project-manager agent holds them. A tool that opens or lists a channel to other sessions is not among the kinds its definition withholds, and DEC-068 point 2's other two kinds stand.
- **Allowed under every posture.** The capability defines a privilege of its own for the two tools, and its grants allow it to the agent. So, once a person realizes the model that carries the grant ([pkit:ADR-095] point 3), the permission model's strict posture refuses neither, and a lenient one leaves neither to ask a person. The grant widens what the agent may do, so the permissions overview reports it as a widening the capability contributes, and a capability grants such a privilege only to an agent it ships ([pkit:ADR-016] and [pkit:ADR-021], refined in place). That bound holds where the permission model's loader checks it, which an installed release older than the build does not: such a release composes the allow without the check, and only realizing's report of the widening shows it. Where a project denies them, the tracker alone carries its seats' work (point 1).
- **Whom it messages.** The agent messages only its directing seat's session, as a worker, the sessions of the workers it directs, as a directing seat, and a session the person names to it in its own session.
- **No build's run.** The agent messages no builder's run, and a build's run messages no session and lists none, since that is the seat's work (DEC-063 point 4, refined in place).
- **Its own subagents, resumed.** The agent resumes by messaging only a subagent it started itself through the harness's tool for starting agents, under its dispatch discipline ([project-management:DEC-029-project-manager-agent-shape]). A resume continues a run that tool started, so it starts no helper other than through it, and DEC-068 point 2's second kind does not reach it. A resumed subagent counts as any other it runs.
- **No teammate.** The agent dispatches no helper in a form its harness makes a teammate, so it has no teammate, and messages none. Under Claude Code, where a named spawn becomes a teammate (the Context), the agent names no helper it dispatches.
- **Another agent a seat names** (DEC-059 point 8) follows points 3 to 12 through the same procedure of the pm skill. It holds the two tools where its own definition does, and where the project's posture would refuse them, the project grants it the capability's privilege, since the capability's grant names only its own agent. Where it holds neither, the tracker alone carries its seat's work.

### 3. The topology names the seat that directs each worker

- **One directing seat, named on the worker's seat.** A worker's seat may name one seat that directs it, a planner's or a lead's, not retired. A directing seat may direct many workers, and directs only those whose seats name it. A planner's or a lead's seat names none, since the person directs it, and a worker directs no seat. So directing has one level, with no chain and no cycle.
- **Read from the default branch,** as the rest of the topology is (DEC-059 point 1). So a change of who directs a worker binds once a merge the person authorised lands it, and no message can name another directing seat.
- **The topology's check refuses** a worker's seat that names a seat the topology does not hold, a retired seat, itself or another worker's seat, and a planner's or a lead's seat that names any.
- **No directing seat named:** the worker counts no message as a directive, and works from the Tasks it may take alone.
- **A lead's own work.** A lead files with no owner the work it leaves to its workers, so that the work becomes ready for them, and owns only what it files for itself to build. So a lead's clone claims at creation only the work it builds itself, not the whole tree it files, as [project-management:DEC-035-instance-ownership] point 3 and DEC-059 point 7 have it.

### 4. Each seat's state issue records the session that runs the seat's loop

- **What it records.** The clone that holds a seat records the session that runs the seat's loop: its name, and the machine and the folder it runs in, a linked worktree's where it runs in one. They are written in a form the listing's rows can be compared with, in which the folder names no user. Where a session cannot read its own name, whoever starts the session gives it, as they give its agent definition (DEC-059 point 4).
- **Only a take for the loop records it.** A session records itself only where it takes the seat up to run the seat's loop: a session started for the seat, or one the person tells to run the loop. Any other session in the clone, such as one the person opens to look at something or to run a held move, takes up the seat as DEC-059 point 4 says, records nothing, and messages nobody as the seat.
- **A recorded session stays** while the listing shows it, and a take for the loop replaces it then only on the person's word, given in the new session. A session already recorded posts nothing again, so the seat's log grows only when its session changes.
- **Which side, and who writes.** The session changes while agents work, and is part of who holds the seat, so it lives on the seat's state issue, found by the number the topology names (DEC-058 point 1). The clone that holds the seat writes it, in an event of its own, under its claim. Another clone's event counts for nothing, and the seat's release clears it.
- **Posted for every reader.** Every reader of the tracker sees the event, so whoever names a seat's session gives it a name fit to post, such as the seat's.
- **Every seat records it,** a worker's as well as a directing seat's, so that each side can address the other and check what it receives.

### 5. A worker checks each message against its directing seat's record

- **The check.** On each message, the worker reads the session its directing seat's state issue records, and lists the sessions messaging reaches. The message is a directive only where all of these hold:
  1. The record names the worker's own machine.
  2. The listing shows exactly one session under the recorded name in the recorded folder.
  3. The message comes from that session: its reply address is that session's address, or, where the harness gives no address to compare, no other listed session holds the sender's name.
- **The check cannot pass** where the worker's seat names no directing seat, that seat is free, no session is recorded, or the record names another machine. So too where the listing shows no folder, where the worker has no listing, and where the harness has no messaging, as under Claude Code's remote control, whose rows show no folder, and for its background helper, which has no listing (the Context). No message is then a directive, and the tracker carries the work (point 1).
- **Two sessions or more match:** none is the directing seat's session, and no message is a directive. The worker tells the person where it can reach them (point 9), and goes on with the Tasks it may take.
- **Any other message is information.** The worker takes no step a directive would take on it. What it says is a hint to check on the tracker, never grounds, and the worker may report it to its directing seat.
- **The same check the other way.** A directing seat messages a worker only where the worker's record names exactly one session it lists, and counts a report as its worker's only where the same check passes.
- **A guard, not a boundary.** Nothing the harness gives proves a sender, and any session in the directing seat's folder can take its name. Like the guard on a claim (DEC-035 point 6), the check catches the mistakes of sessions that follow the procedure, and stops no session that means to pass as another.

### 6. A directive may name the worker's next Task, and widens nothing

- **Which Task.** A directive may name one Task for the worker to take next, ahead of the order it would take its Tasks in. It names only a Task the worker could take of its own choosing: ready, in its seat's scope, and in its pools where the topology declares them (DEC-061 point 5). Work in flight goes on first, as the worker's loop has it. Where two directives name Tasks before the worker takes either, it takes them in the order the directives came.
- **The same take, the same claim.** The worker takes the named Task through the take it uses for any Task, which claims it, so the clash guard keeps a second agent off it whatever channel sent either (DEC-035 point 6). Where one Task is named to two workers, the guard leaves one claim holding, and the other worker reports the loss and takes its next ready Task. A directing seat never claims a Task for a worker, since a claim names the clone that makes it (DEC-059 point 9).
- **Nothing outside.** On a directive, the worker takes no Task that is not ready, lies outside its pools or scope, or is held by another, and reports why. Scheduling such a Task or putting it into a pool is the person's act (DEC-061 point 6). Directing a seat to a Task outside its pools stays the person's own word (DEC-061 point 5), which the worker takes only in its own session.
- **The person's word outranks a directive.** Where they disagree, the worker follows the person's word in its own session, and tells its directing seat.
- **A build reads its brief alone.** A directive reaches the worker's session, never the build it starts, whose brief is written from the Task alone (DEC-063 point 3). So what a directive asks of a Task's work reaches a build only once it is written on the Task.

### 7. A worker keeps its own rules, whatever a message asks

A message changes none of the worker's rules, records, settings or permissions, nor its seat's role. Asked for what they refuse, the worker does not do it and works around nothing. Where the message is a directive, the worker answers its sender with the rule or the refusal that stops it. It answers no other message, whose sender may be a session point 2 does not name, and may report it to its directing seat (point 5). What the message asks that is the person's goes to the person (point 9). That covers a change to another repository, which the worker never makes on a message (COR-039).

### 8. A worker reports when a Task is done, or stops on what it cannot settle

- **At once, on each directive:** that it takes the named Task next, or why it does not. To a directive that names no Task, what it does next: the Task it takes, or that nothing is ready for it, with the reason. The answer tells the directing seat that the directive arrived (point 11).
- **Done:** when a Task moves to Review, naming the pull request.
- **Blocked or in need:** when a Task stops on what the worker cannot settle, with what stops it, such as a build's question waiting on the Task, a refusal, a step that failed again after its one retry, or a claim it lost. So too when nothing is ready for it, with the reason in terms of the Tasks it may take, and when it needs an act of the person's (point 9).
- **What a report holds:** the Task or pull request it concerns, and what the worker would tell the person, word for word. It holds nothing of the work that the tracker lacks, and the directing seat reads the Task or pull request a report names before it acts on it.
- **On the tracker,** the Task's state and its pull request tell every reader the same. Where messaging does not reach, the directing seat reads them at each round of its own.

### 9. A question for the person goes to the person

- **What is the person's:** each act a record keeps for the person, such as scheduling work or putting it into a pool, a held move, an override with its reason, a build's decision and permission questions, authorising a merge, accepting a record or a rule that the delegation setting does not hand to the delegate, and every consent a record asks ([pkit:COR-072] points 6 and 7).
- **Where the worker can reach the person,** in its own session, it asks them there. Where it cannot, as with no terminal at its session, it reports the question to its directing seat, which brings it to the person word for word.
- **The directing seat answers none of them,** nor a build's question, since an answer from its own context would carry that context into the build (DEC-063 point 6).
- **The person acts where the act's command takes their word,** such as on the Task for a build's question. An act whose command takes the person's word only at a terminal, such as a held move, the person makes at a terminal of their own, since a word relayed by message makes none (point 10). The worker reads the outcome on the tracker.
- **Where neither seat reaches the person,** the question waits where the capability already keeps it, as a build's question waits on its Task, and the Task waits with it.

### 10. A message is never the person's authorisation, nor is a Task

No directive, report or other message stands for an act that stays the person's, and neither does a word of the person's that a message relays. Nor does a Task: one that asks for such an act still sends it to the person, whoever filed it. No session takes a message, or a Task's text, that says the person agreed as the person's word for such an act. Where the delegation setting lets the delegate accept a record or a rule, an issue may still hold the agreement it reads ([pkit:COR-072] point 6). The person's own word counts where the act's command takes it, such as their answer to a build's question on its Task (point 9).

### 11. A held message loses no work

- **Where a harness holds a message.** A harness may hold a message until a person approves it at the receiving seat's terminal, and drop it at a deadline where no terminal can show the approval, as the Context reads Claude Code for a seat that bypasses permission prompts and a sender that does not. So an unattended seat may never see a directive or a report.
- **Approving delivers, and authorises nothing.** A held message a person approves then counts as any other message (points 5 and 10), never as the person's word. No seat approves one for itself.
- **Nothing is lost but time.** A dropped directive names a Task the tracker holds, or none, and the worker reaches that Task in its own order at a later take. A dropped report points at what the tracker shows.
- **Counted only once answered.** A directing seat counts a directive received only once the worker answers it (point 8). It sends none again on silence, and reads the tracker instead.
- **No setting changes.** This record changes no session's rule for inbound messages. Whether the seats run in one mode, or accept what the harness would hold, is the person's choice in their own settings, and the capability's documentation says what each choice does for an unattended seat.

### 12. Directives stay within one repository's topology

A directing seat and its workers are seats of one topology, which is one repository's own and outside the mesh, as DEC-059's Implications, "No mesh interaction", have it. A session of another repository is any other session, and its message is information (point 5). Work that spans repositories is filed in each, and each session changes only its own repository (COR-039).

## Rationale

**Why one model.** Two channels with two authorities would need two sets of rules, and a worker could not tell which binds. With the topology deciding who directs and the tracker holding every Task, a message adds speed and an order, and no authority. A harness without messaging loses those two and nothing else.

**Who messaging serves.** Messaging reaches another machine only through remote control, where the listing shows no folder and the check cannot pass, and each of a platform's sandboxes is another machine (DEC-059's Context). A held message is dropped where no terminal shows it, and a stopped session cannot be messaged. So messaging serves seats that run as interactive sessions on one machine. Seats on a platform's sandboxes, or with no terminal, keep the tracker alone, and lose nothing they have without this record.

**Why the topology names the directing seat.** Who may direct a worker is authority, as the organizer seat's release by force is (DEC-059 point 2). In committed configuration read from the default branch, it changes only through a reviewed merge. A default, such as the only planner, would grant authority that no change reviewed.

**Why planners and leads, one level deep.** They are the roles that file work for others to build. A chain of directing seats would pass a directive through a seat that judged none of it, and a worker with one directing seat never meets two directives that disagree.

**Why a session's name and folder.** A message carries its sender's name and reply address, and the listing shows each session's name, folder and address, so these are what a worker can compare. A name alone repeats. Where the listing shows the folder a session runs in (measurement 4), the folder tells the directing seat's clone from every other on the machine, and the name tells its session from another in the same clone. Both change while agents work, so the session's event records both, on the state issue, beside the claim that names the clone.

**Why only a take for the loop records the session.** A clone that holds a seat takes it up in every new session (DEC-059 point 4), such as one the person opens to look at something. Were each such session recorded, the last one opened would become the seat's session, and the loop's own directives and reports would fail the other side's check without a word. Recording only the loop's session, and replacing a live one only on the person's word, keeps the record on the session that directs and reports.

**Why the agent may resume its own subagents.** A resume continues a run the agent started under its dispatch discipline, with the context that run already holds. So it opens no work outside the session's checks, which is what DEC-068 point 2's second kind withholds. Under Claude Code, a teammate exists only where a helper is named, which the agent never does.

**Why the capability grants the tools, reported as a widening.** The agent's reach to other sessions is the capability's policy, and travels with it, as a deny of its own does (ADR-016). Left to each project, a strict posture would keep messaging off with no word, and every project that installs the capability would copy the same grant by hand. A grant only of a privilege the capability defines, and only to an agent it ships, widens nothing else. Reported as a widening, it changes no agent's reach silently.

**Why a failed check falls back to the tracker.** A message names only what the tracker holds, so ignoring one loses no work. A worker that guessed between two matching sessions could take a directive from a stray one. Failing closed costs a directive's speed, never a Task.

**Why a directive may reorder, and nothing more.** The worker's own order serves a worker that chooses alone, and a directing seat may know a sequence it does not show, such as a Task others wait on. The pools and the scope are the person's decisions about who builds what (DEC-061 point 6), so a directive picks within them and widens neither. The claim keeps two agents off one Task whichever seat chose it, so a directive needs no lock of its own. A Task a lead owns is ready for no one else (DEC-059 point 7), so a lead files with no owner what it means its workers to build, as a planner files all its work (DEC-059, "Why a planner files with no owner").

**Why reports at those points.** They are where the directing seat can act: a directive to confirm, a pull request in Review, and a worker that is stuck, in need or idle. A report that adds nothing to the tracker loses nothing when it is lost. The directing seat relays the person's questions and answers none, since the person's decisions stay the person's whichever seat asks (DEC-059 point 8).

**Why accepting held messages stays the person's setting.** Every directive names what the tracker holds, and every answer tells the sender it arrived, so a drop costs time and nothing else. Accepting what a mode would hold widens what reaches an unattended agent, which only the person may choose.

**Why one repository.** The topology, its state issues, its pools and its claims are one repository's own, outside the mesh ([project-management:DEC-022-methodology-mesh]). A directive from another repository would bring another project's governance into this one, against COR-039.

### Alternatives considered

- **Keep messaging withheld, and direct only through the tracker.** Rejected: an idle worker learns of new work only at its next round, and the person decided on messaging. What messaging gains is the setup "Who messaging serves" names.
- **Ship only the privilege's definition, and leave its grant to each project.** Not taken, as "Why the capability grants the tools, reported as a widening" says.
- **Messages that only wake, with the order kept on the tracker.** Not taken: a wake from any session would cost one read of the tracker, and need no check of the sender, no session on the state issue and no take of a named Task. The person decided that a message may point the worker to its Task, and that apparatus is the cost of pointing safely.
- **A lead session named in configuration, apart from the topology.** Not taken: a second authority beside the seats, to keep in step with them.
- **A directing seat derived from the pools,** such as the planner whose Milestones a worker's pools hold. Rejected: a planner names no pool (DEC-061 point 1), several planners may file into one pool, and what keeps planners apart is what the person gives each.
- **Check the sender by its name alone, or by its folder alone.** Rejected: names repeat, and the sessions of one clone share a folder.
- **A token the directing seat writes on its state issue and quotes in each message.** Rejected: every clone reads the state issue, so the token tells no more than the name and the folder, at the cost of a read before each message.
- **Take the first of two matching sessions.** Rejected: a stray session of that name would direct half the time.
- **Record each session that takes the seat up.** Rejected, as "Why only a take for the loop records the session" says.
- **A message from the person's own session counted as a directive.** Rejected: a message is never the person's word, and its sender cannot be proven. The person directs a worker in the worker's own session, or through its directing seat, whose directive is then the seat's.
- **Directives outside the pools, warned of as a person's are.** Rejected: the pools are the person's decision, and a seat is no person (DEC-061 point 5).
- **Directives posted on the tracker too.** Rejected: a directive only reorders what the tracker holds, and a lost reorder costs nothing.
- **Send a directive again on silence.** Rejected: a held message would open another approval, and the tracker already carries the Task.
- **Measure first, and decide after.** Not taken: the person decided the model, and what the build measures changes only how far the check can pass. Each measurement that does not hold leaves the tracker carrying the work, and the first reopens this record (the Context).
- **Directives across repositories, through the mesh.** Named, not built: a later record may decide them, with how a seat of one repository is checked from another.
