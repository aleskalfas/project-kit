**In plain terms:** when an issue moves forward, the forward cascade brings each container above it that stands behind it up to the issue's state, as far as In Progress. Where the board or the tracker gives no answer to a read the cascade is planned on, a move that schedules or starts work, Todo → Backlog or Backlog → In Progress, is refused before it is made, with nothing written, unless its run skips the cascade. A move that ends work, to Review or to Done, is never refused for its cascade: there, as after any move, a read that gets no answer ends the walk, and the cascade warns. Data that is off, where the tool answered, refuses no move: a container its card or label places in no state is left with a warning and the walk goes on past it, while a parent record naming an issue that does not exist ends the walk. The cascade writes only from reads made after the move, and once the move is made takes no exit code. It warns wherever, by what it read and wrote, it did not finish, and says how to finish.

## Context

Two accepted rules meet at the forward cascade:

- **No container is to stand behind the work under it.** The forward cascade keeps to that: when an issue moves forward, it brings the ancestors behind up to the moved issue's state, capped at In Progress ([project-management:DEC-006-state-machine-and-cascade], "Cascade rule").
- **No command acts on a position it could not read** ([project-management:DEC-051-axis-carriage-activation] point 6). Where the board carries the state, a card that does not place an issue, or a board that cannot be read, falls back to neither its labels nor its Milestone.

At an ancestor whose position a read does not give, the two pull apart. [pkit:ADR-074] leaves which gives way to a project-management record (its Boundaries), and its point 5 holds every command that reads the state to two limits: it never guesses, and it keeps a board that would not answer apart from a finding about the issue, the first taking the broken tool's code where a command's codes tell one. [pkit:ADR-096] point 4 adds that once a command's act is made, here the issue's move, nothing it sets off on another issue, such as the forward cascade, gives the command a code that reads as the act not made, and leaves to this record whether the move waits on a read of an ancestor.

The question is what the move does at such an ancestor ([project-kit#3204](https://github.com/aleskalfas/project-kit/issues/3204)): whether it is refused for it, and, where it is not, what the walk does there and above it.

Terms:

- **The walk** is the cascade's pass from the moved issue's parent up its hierarchy, one ancestor at a time. Point 4 says where it ends.
- **An issue's parent records** are its native sub-issue link, where the tracker supports one, and its body's first line ([pkit:ADR-035]).
- **The top** is an issue whose parent records were read and name no parent: it has no native parent, and its first line names no issue, as where it names a Milestone (ADR-035 point 1).
- **The move's target** is the state the move takes the issue to, and **the cascade's target** is the move's target capped at In Progress.
- **A read of where an ancestor stands** places it in a state of the lifecycle, places it in none, or gets no answer.
  - **It places the ancestor in none** where the tool answers with a finding about the ancestor, which is open: that what carries its state places it in no state of the lifecycle. Where the board carries the state, that is one of DEC-051 point 6's findings: the board answered, with the witness [pkit:ADR-096] point 1 asks, that the issue has no card; its card has no Status; or its Status names no open state, such as Done on an open issue. Where labels carry it, that is a label for a state the lifecycle does not have.
  - **It gets no answer** where the tracker did not answer for the ancestor's issue or, where the board carries the state, the board did not answer for its card. Such a read gives no position.
    - **The tracker did not answer** where it said it could not, could not be reached, or replied with anything but one whole, well-formed answer. A parent record ADR-035 point 1 calls *unread* is such a read, while a native substrate its point 2 finds *unsupported*, where the first line is the whole answer, is an answer.
    - **The board did not answer** wherever ADR-096 points 1 and 2 count it so, as for an absence of a card with no witness, a read not whole, or an error placed on the board or its cards, and where ADR-074 point 1 counts it a board that cannot be read, as one with no Status field or whose Status is not single-select.
  - **An ancestor is level** where a read places it at or past the cascade's target.
- **An issue that does not exist** is one a parent record names that the tracker answers is not there. The tracker answered, so this is no read that gets no answer: it finds a parent record that is off, and no ancestor to place.
- **A move that schedules or starts work** is Todo → Backlog, which gives the work its scheduling, or Backlog → In Progress, which starts it (DEC-006), wherever the move runs the cascade. It runs the cascade unless its run skips the cascade, or the project carries the state where the cascade cannot write it, as where the state is derived; a run that does either plans no walk. **A move that ends work** is a move to Done, which records the work's end, or to Review, which puts a Task up for the merge that ends it.
- **A command that calls the move** runs the move as a step of its own, with work of its own around it, as a start of work sets the assignee and cuts the branch first. **The move made again** is the same command run again, the move's own or one that calls it.
- **The first read** of an ancestor is made as the walk is planned: where the run makes the move, before the move and before a person at a terminal confirms it, and where a command calls the move, before the command's prompt and writes, the move planning the walk again (point 1). It reads the ancestor's issue, its parent records included, and, where the board carries the state and the ancestor is open, its card. The moved issue's parent records are read then too. That read and each ancestor's first read are **the first reads**.
- **After the move**, on a run that finds the issue already at the move's target and so makes no move, means after the first reads.
- **A later read** of an ancestor is made after the move, just before the cascade would write to it (point 2).
- **The parent check** reads an issue's parent records alone, once, after the move, to find whether the issue still names the parent it had when the walk was planned (point 2).
- **An ancestor left** is one whose later read places it in none, or whose write of what carries its state is not made (points 2 and 3). A container behind for another cause is not one, such as one for which the lifecycle declares no way from where it stands, one moved back after the first read placed it level, or one at or above where the walk ended (point 4).

## Decision

**A move that schedules or starts work, not yet made, is refused where one of the first reads gets no answer; where a command calls the move, that command is refused before its own writes, and the move it then calls is not. Any other forward move is made whatever its cascade finds above it. The cascade writes to an ancestor only from reads made after the move, of the ancestor and of the issues below it on the walk. An ancestor its later read places in none is not moved, one whose write is not made is moved no further, and the walk goes on past each. The walk ends at an issue that does not exist and, wherever the move is not refused, at a read that gets no answer. Once the move is made, the cascade takes no exit code.**

### 1. A move that schedules or starts work is refused where a first read gets no answer

A move that schedules or starts work, not yet made, is refused where one of the first reads gets no answer, from the tracker or from the board: the read of the moved issue's parent records, or the first read of an ancestor its walk will reach. Each of the moved issue's own gates that refuses without asking a person is checked first, and the first reads are made only for a move they let through. The refusal comes before any prompt, writes nothing, neither the move nor any step of its cascade, and takes the broken tool's code (point 6), in a dry run as in the run itself. It names each such read, the issue it was of and the tool that did not answer, the tracker or the board, with what that tool said of why. It says that the move made again once the read is answered runs its cascade too, and that a run that skips the cascade makes the move and leaves the containers above as they stand.

A move that ends work is never refused for its cascade, nor is a run that finds the issue already at the move's target, as after a merge, a completed close or an earlier run, since it makes no move, nor the move a command calls once the command's plan of the walk got its answers. On each, the walk as planned ends where a first read gets no answer: at that ancestor, with nothing written to it or above it, or, where the read of the moved issue's parent records gets none, with nothing written to any ancestor (point 4).

Otherwise a forward move is made, or refused, on the moved issue's own reads and gates alone: no command refuses or holds a move because a read places an ancestor in none, or finds an issue that does not exist, before the move or after it.

A command that calls a move that schedules or starts work has the move plan its walk, as in the move's dry run, before the command's prompt, the end of its dry run and its own writes. Where one of those first reads gets no answer, the command is refused there, as the move would be, and leaves nothing behind. The move it then calls is not refused for its cascade: it plans its walk again, and a first read that gets no answer ends that walk, as after any move. Such a command carries the skip, and its refusal names its own runs: one that skips the cascade as the way past, and the command made again as the way to finish, which runs the cascade where it finds the issue already at the move's target.

A run that plans no walk makes no first reads and refuses nothing. One that skips the cascade says that no cascade ran, that the containers above may stand behind the work under them, and that the move made again without the skip runs the cascade.

Where the walk is planned before the move, what it found is shown before the move is confirmed, in the run's preview, and a gate that asks a person at a terminal, as for the user's authorisation of a scheduling or for a consent, asks with that confirmation. So a person at a terminal sees which ancestor the first read placed in none, that the run reads it again where the walk reaches it, and where the walk as planned ends, and may decline the move.

### 2. The cascade writes to an ancestor only from reads made after the move

Each ancestor the first read places behind, or in none, gets a later read, once, just before the cascade would write to it. That read reads where the ancestor stands, and the ancestor's issue: its labels, whether it is open, its type, its parent records and where its card is found. Each write to the ancestor takes its inputs from that read, as the writes before it left them.

An ancestor its later read places in none is left where it stands, with nothing written to it: no state, no Status, no journal entry and no comment. Where its later read gets no answer, or finds that its issue does not exist, nothing is written to it or above it, and the walk ends there (point 4). The first read decides which ancestors the walk can reach, which of them get a later read, and what the preview shows. What the cascade writes rests on reads made after the move alone, and never on a position guessed from an ancestor's labels or its Milestone where the board carries the state (DEC-051 point 6).

The later read asks the process engine where the ancestor stands, as the commands that move an issue do ([project-management:DEC-033-rebind-issue-lifecycle-onto-process-substrate] D5), and takes the position the engine gives, in a state or in none. Where the engine evaluates no position, as where it cannot be reached, replies with anything but one well-formed answer, or answers that it could not evaluate the position, the later read is made directly instead, once, as the first read is made. So a later read gets no answer only where that direct read gets none, never for the engine alone, and it is not made again in the run: the walk ends there.

The cascade writes to an ancestor only where each issue below it, down to the moved issue, still names after the move the parent it had when the walk was planned. Each of them is read for that after the move, before the cascade's first write above it: by its later read where one is made, and otherwise by its parent check. Where one of them no longer names that parent, or cannot be read, the cascade writes nothing to that ancestor or above it, and the walk ends there (point 4). No other issue is read for a changed parent, so a parent given after the walk was planned to an issue that gets no later read and has nothing written above it stays behind, with no warning, until a later forward move under it reaches it.

An ancestor the first read places level gets no later read, and nothing is written to it, so one moved back after that read stays behind, with no warning, until a later forward move under it brings it level. Its parent check, where one is made, reads its parent records alone.

### 3. An ancestor whose write is not made is moved no further

Where a write of what carries the ancestor's state fails, as where the tracker or the board refuses it, the ancestor is moved no further, and the steps it took before that write stand, as does the move. What else the cascade writes once the ancestor's state has moved, such as a Status kept only as a mirror of its labels, a comment or a journal entry, is no such write: where it fails, the report warns of it, and the steps stand. A read of the card made only for that mirror is the mirror's (ADR-096 point 4): where the board does not answer it, the mirror is not made, and the walk goes on. So where labels carry the state, a board that does not answer refuses no move, since no card is read before it.

### 4. The walk goes on past an ancestor left, and where it ends

The walk finds an ancestor's parent from its issue, not from where it stands, so a read that places the ancestor in none still gives its parent. Each ancestor is brought up to the cascade's target, never to the state of the ancestor below it, so an ancestor left bears on no move above it. So the walk goes on past it, and each ancestor above is brought level, or not moved, on where its own reads place it.

The walk ends at the top. It ends short of the top where it cannot tell the next ancestor up: at a parent in doubt, in each case where [pkit:ADR-035] point 5 has the forward cascade write nothing on the parent or above it; at an issue whose first line names itself, which names no parent (ADR-035 point 2); at an issue that does not exist, before the move or after it; and at an issue whose later read or parent check finds that it no longer names the parent it had when the walk was planned. Wherever the move is not refused, it ends too where a read gets no answer, and the cascade writes nothing to the issue it could not read or above it: a later read, a parent check, or a first read (point 1). It ends at an issue that is no container, which the cascade does not move, and at one it has passed already.

The walk takes the tracker's answer as given. One that leaves out what the credential may not see, as where a native parent in a repository the credential cannot read comes back as none, is outside this record, and is left to [project-kit#3366](https://github.com/aleskalfas/project-kit/issues/3366): such a walk ends at what reads as the top, under a clean report. Such an answer is whole, where a request the tracker refuses gets no answer.

No later read extends the walk, so the cascade writes on no ancestor the walk did not reach as it was planned.

### 5. When the report is a warning, and how to finish

The cascade's closing report is clean only where, by what the cascade read and wrote, the walk ended at the top, each ancestor it reached stands level, each write it tried was made, each step it took was journaled where a journal is kept, and no open container it reached stands at Review or Done (below). Any other outcome makes the report a warning, such as an ancestor left, an end short of the top that the cascade finds, a mirror or a comment not made, a step it could not journal, or an ancestor for which the lifecycle declares no way from where it stands.

The report lists each ancestor the walk planned, with what became of it. It names each ancestor left and the read or the write that left it, and, where the walk ended short of the top, where and why. It names a read that got no answer as one, and the tool that did not answer, the tracker or the board, with what that tool said of why, so that a cause that lasts can be told from one that passes, and never as a finding about the ancestor, nor a finding as such a read ([pkit:ADR-074] point 5).

A read can place an open ancestor at Review, which DEC-006 keeps for a Task alone, or, where labels carry the state, at Done, which a container reaches only through its close (DEC-006). The cascade does not move such an ancestor, since it is level, and the report warns of it. Where the board carries the state, an open ancestor whose card names Done is placed in none (DEC-051 point 6), so it is left (point 2).

For each ancestor left, each open container at Review or Done, each ancestor for which the lifecycle declares no way from where it stands, and each end short of the top, the report says what to put right and where, in the containment seam's words at a parent in doubt (ADR-035 point 5), and which then finishes the cascade: the move made again, once a read that got no answer is answered, the next forward move under the ancestor, or a move of the ancestor on its own. It says too that a container whose state is set as a person meant it, such as one set outside the lifecycle on purpose, stays where it was put, and that each forward move under it warns of it again.

### 6. Once the move is made, the cascade takes no code, and before it only the refusal takes one

A run that makes the move or finds the issue already at the move's target, and a dry run of either, exit as the move alone has them exit. Whatever makes the cascade's report a warning (point 5) is a warning beside it, never a code: not a refusal's, not the broken tool's, nor any other. That keeps within the limit [pkit:ADR-096] point 4 sets once a command's act is made, so each command that composes the move reads the move as made.

A run refused for a first read that got no answer (point 1), of the move or of a command that calls it, and a dry run of either that would be so refused, take ADR-074 point 5's broken tool's code, where the command's codes tell one, whichever read got no answer, the tracker's or the board's. A run declined at the terminal makes no move, so the cascade gives it no code. Nor does a read that places an ancestor in none, or finds an issue that does not exist, give any run a code, since neither holds the move (point 1).

## Rationale

**Why a move that schedules or starts work is refused where a first read gets no answer.**

- **A read that gets no answer stops what rests on it while nothing is written.** It gives no position, so no cascade can be planned on it. Refused before anything is written, a move that schedules or starts work costs a run made again once the tool answers, which makes the move and runs its cascade. Made with a warning, it would leave each container from the unanswered read up behind the work until someone acted on the warning. Where the fault lasts, a run that skips the cascade leaves those containers as such a move would; what the refusal secures is that no scheduling or start leaves them so unless its run chose to (below). The moved issue's own parent records are held as an ancestor's first read is, since the walk starts from them.
- **Only a move that schedules or starts work.** A move that ends work is not held for another issue's read. A move to Done records an end that rests on a merge or on the user's authorisation of a close (DEC-006), and a move to Review follows the opening of a Task's pull request and leads into its merge. Refusing either would hold work finished, or put up for its merge, as unfinished: a Task held from Review, and its merge with it, or one whose pull request merged left open at Review. Where the move comes after the act, as after a completed close, a refusal could not hold the act at all. A move that schedules or starts work ends nothing, so its refusal costs only the start, until the tool answers or the run skips the cascade. And the containers above work under way were brought up when it was scheduled and started, so a move that ends it most often finds them level.
- **The cost of that narrowing.** A move that ends work brings a container up where the moves before it did not: where a parent was given to the work, or to a container above it, after the work started; where a container was moved back since; where the work's state was set by hand, as a card dragged to In Progress, or a run skipped the cascade; and on a completed close from Todo or Backlog, whose cascade brings each container above up to In Progress. In each, a read that gets no answer leaves each container from it up behind the work, with a warning, until the move made again or the next forward move under it.
- **The gates first, then the reads, then the person and the writes.** The moved issue's gates need no read above it, so each that refuses without asking anyone is checked first: a caller refused for the tool, and only then for such a gate, would wait on the tool for a move its gates refuse anyway. A gate that asks a person at a terminal asks after the first reads, with the confirmation, so the person answers for a move whose cascade could be planned, having seen what its walk found. A refusal leaves nothing behind only where nothing was written before it, so the first reads come before every write. Nothing is written from them (point 2), so their being older costs nothing. Each gate governs a move on its own issue, and the cascade asks for none (DEC-006): the refusal reads nothing of an ancestor's state, and stops for the tool.
- **A command that calls the move has the walk planned before it writes, and the move it calls is not refused.** Such a command writes around the move and calls it as a run of its own, so its refusal leaves nothing behind only where it comes before those writes, and the walk stays the move's. Refused after them, for a fault that began in between, the move would leave them behind with no move made, so its walk ends at the read instead, as after any move, and no plan is handed from one run to the other. The cost: each such call reads the moved issue's parent records and each ancestor twice before the move, which planning again after a prompt is rejected for (Alternatives), here paid for a refusal that leaves the command's writes unmade; and a fault that begins between the two plans leaves each container from it up behind, with a warning, until the command made again.
- **The way past is a run that skips the cascade.** The refusal holds the move for its cascade alone, so a run that runs none has nothing for it to hold. Its caller chooses the skip before the move, and the run says what it leaves, so no scheduling or start leaves containers behind, for a tool that did not answer as its walk was planned, unless its run chose to. A command that calls the move carries the skip, so what it does beside the move, such as a start's branch and claim, goes with the run that gets past. The move made again, which finds the issue at the move's target, then runs the cascade as far as the fault. Who may choose the skip is not decided here (Implications).
- **The costs.** A move whose own reads and gates passed is refused for a read of an issue that is often another person's, and a start of work fails with it. The refusal lasts as long as the fault: a board that is down refuses every such move until it answers, and a lasting error on one ancestor's card, which counts as a board that did not answer (ADR-096 point 2), refuses every such move beneath it until someone, often not the mover, mends the card. A command that chooses a seat's next Task and starts it stops at such a start, as at any start that fails, so that fault stops each seat whose first ready Task sits beneath the card; whether it passes over that Task is left to [project-kit#3370](https://github.com/aleskalfas/project-kit/issues/3370). Where the tracker refuses every request a run makes for an issue's native parent, every such move in the project is refused, since each reads the moved issue's parent records: a request refused gets no answer, as ADR-035 point 2 counts one for a child set, while a parent answered as none is an answer (point 4). A run that skips the cascade gets through, leaving every container above as it stands.
- **Nothing is left to refuse once the move is made.** No code may then read the move as not made (ADR-096 point 4), so where the issue already stands at the move's target, a first read that gets no answer ends the walk, as a later read that gets none does. A fault can begin between the first read and a later one, so a walk cut short after the move has to be handled whatever this record decides.

**Why data that is off is left, and the move goes on.** Where the tool answered, what is off is the data, and a refusal of the move mends none of it.

- **A read that places an ancestor in none** says that it stands outside the lifecycle until whatever carries its state is set right. It cannot be moved without a guess, which DEC-051 point 6 forbids, so a refusal of the work under it would leave it as it was, and would give a state set by hand a meaning no record gives it: a container whose card sits in a column outside the lifecycle, such as Blocked, or is kept off the board, would hold every forward move beneath it, answering by accident what DEC-006 leaves open.
- **A tracker that answers that an issue does not exist** answered too: what is off is the parent record that names it, and a refusal would keep every forward move under it waiting on whoever mends it. The walk ends there, since such an issue names no parent, and the report names the record to mend. The cost: the issue the record meant stays behind, warned of on each forward move under the record, until it is mended.

Data that is off is finished on the data, and a read that gets no answer on the tool, so the report names the two apart, as ADR-074 point 5 asks.

**Why DEC-006's Cascade rule is narrowed here, and not DEC-051's rule.** DEC-006 rejects leaving an ancestor behind and reporting it, where the cascade could move it, because a container behind a started child states something false. Here the cascade cannot move the ancestor without guessing its position, which DEC-051 point 6 forbids, or taking it from a read made before the move, which can move it back. So the Cascade rule keeps its aim, that no container is to stand behind the work under it, and is narrowed to what the cascade can read and write. A container may stand behind the work under it, until a later move brings it level, where:

- a read places it in none, or its write is not made, and the report warns;
- the walk ends below it short of the top, at a read that gets no answer on a move not refused, where the next ancestor up cannot be told, or at an issue that is no container (point 4), and the report warns;
- it was moved back after the first read placed it level, or is a parent given after the walk was planned to an issue that gets no later read and has nothing written above it, with no warning (point 2);
- a run skipped the cascade, which says so.

These are what the cascade itself leaves; a container stands behind too for causes no move sets off, such as a child filed already scheduled, a parent given outside a move or a state set by hand, until a forward move under it brings it level. A first read that gets no answer on a move that schedules or starts work narrows nothing, since it refuses the move.

**Why the walk goes on past an ancestor left, and where it ends.** An ancestor above is brought level on its own reads (point 4), so it moves on a position that was read, and a container ahead of the one below it is a state DEC-006 allows. Stopping the walk would keep every container above behind the work under it, for data that is off on one ancestor. An ancestor whose write failed is passed for the same reason: its reads answered, and where the tool has failed since, the next read gets no answer.

The walk ends where the next ancestor up cannot be told, since a write on a parent in doubt could move a container the moved issue is not under, as ADR-035 point 5 holds. An issue that does not exist, or whose first line names itself, names no parent. One that no longer names the parent it had when the walk was planned names one neither read as the walk was planned nor shown before the move, as would any ancestor a later read extended the walk to. The walk ends at an issue that is no container, which the cascade never moves, and at one it has passed already, where going on would walk in a circle. Only the top is a clean end, since only there do the records name nothing above.

Wherever the move is not refused, a read that gets no answer ends the walk, as in point 1, even where only the ancestor's card went unanswered, since the fault is the tool's and the move made again once it answers finishes the cascade whole, each container above staying behind, with a warning, until then. Where the ancestor's issue could not be read, its parent is in doubt besides.

**Why the cascade writes only from reads made after the move.** The first read is made before a person at a terminal confirms the move, so it can be minutes old when the cascade writes, and another move under the same ancestor may have brought it level in between. A write sets where the ancestor goes without checking where it stands, so a write from the first read would then:

- where the board carries the state, set the ancestor's Status back behind the work under it, a move back DEC-006 holds for the user, which nobody authorised;
- where labels carry the state, take off a label the ancestor no longer carries and add the next, which can leave it two values on one axis, against the rule that an issue carries one value on each axis ([project-management:RS-PM-003]);
- on either, journal a step from a state the ancestor no longer held, which no later move takes back.

A read made just before the write leaves only the window every write leaves between its read and its landing, so the cascade writes from that read alone, and nothing to the ancestor or above it where that read gets no answer, the first read being as old whichever read failed.

Which issues are the ancestors is read before the move too. Where the moved issue or an ancestor is given another parent in between, a write along the walk as planned moves a container the moved issue is no longer under: a container in Todo is taken to In Progress on a commitment given on work no longer beneath it, while the new parent goes unread under a clean report. So the cascade reads each issue below an ancestor after the move, before it writes to that ancestor, and writes nothing where the walk changed. The cost is a parent check of the moved issue, and of each level ancestor below a written one, and none on a move that writes to no ancestor: the check guards the writes, so it reads no issue with no write above it (Alternatives).

**Why the later read is made of each ancestor the first read placed behind or in none, and of no other.** A later read of an ancestor the first read placed in none costs what one of an ancestor placed behind costs, and brings it level where its card or label was set right since. An ancestor the first read places level gets no later read, so a move under ancestors already level costs one read of each. Writing nothing there costs less than a write from an old read: a container moved back after the first read stays behind, with no warning, until the next forward move under it, while a write risks the harms above. A move back already bears a cost of that kind (Implications).

**Why the later read asks the process engine first.** DEC-033 D5 hands a move's mechanics, its position, validation and journal, to the engine, and keeps the cascade among the side-effects project-management retains. This record reads the two clauses together: which ancestors the cascade moves, and how far, is the side-effect kept, while each step it writes is a move whose position, the step's origin, D5 hands on. So the later read, from which each step's origin comes, asks the engine first, at the cost of a second read for each write's inputs, with a moment between the two. The first read sets no step's origin, so it reads directly. A direct read and the engine place an ancestor by one inference over the same inputs ([pkit:ADR-074] point 4), which DEC-033 holds to the same result (its Implications, behaviour parity).

Where the engine evaluates no position, its answer cannot tell a read of the ancestor that failed from a failure of the lifecycle's classifier, the predicate that reads the issue and its card, before it read, as where its code would not load. A direct read then is as fresh as the engine's would have been, and places the ancestor by the same inference, so it is no second account of position. The engine alone never ends the walk, since a read gets no answer only where the tracker or the board did not answer for the ancestor: where only the engine fails, both still answer for it.

Where a journal is kept, a step written from a direct read goes unjournaled wherever the engine still cannot place the ancestor, since the engine journals a step from a stated origin only while its own reading places the ancestor at that origin or at the step's target (the process README, "Why `--from`"). The report warns of each such step, as the run reports any move it could not journal ([project-management:DEC-049-audit-journal-model]).

**Why an open container at Review or Done is read there, and warned of.** The engine and every command place such an ancestor alike (ADR-074 point 4), so the cascade reads it where they do: at Review, or at Done where labels carry the state, past In Progress, so level, and writes nothing to it. Yet DEC-006 keeps Review for a Task alone and has a container reach Done only through its close, so an open container at either states something false, and the report is the one signal of it that reaches whoever moves the work under it. The cost is a warning on each move under it until it is set right or closed, and one falsehood the two substrates report under two names. A closed container is not warned of (Alternatives).

**Why the report is clean only where the cascade finished.** A warning keyed to a list of causes misses each cause the list leaves out, such as a step the engine could not journal, a mirror not made, or an ancestor for which the lifecycle declares no way from where it stands. A report clean only where the cascade finished warns of each, and of any cause found later.

It says how to finish, since an ancestor left can be offered for closing before it is level: the closure cascade makes an ancestor eligible to close once its last open child closes, wherever it stands, while DEC-006's table starts that close only at In Progress. Where no forward move is left to come under it, only a move of the ancestor on its own brings it level, before it is closed. That move is asked for directly, so its gates apply: a container in Todo needs scheduling of its own, though the scheduling given on the work under it covered it (DEC-006).

**Why nothing is written to the ancestor.** A notice on it would repeat on every forward move under a container set outside the lifecycle on purpose, or need a key to post it once, which a later change of its state would have to reset. The report reaches whoever runs the move, where the move's own outcome is read, and its repeating costs the output of the moves, not an issue.

**Why no code once the move is made, and the broken tool's before it.** Commands compose the move and act on its code: a start of work reads a non-zero code as a failed start, and a merge or a close as a step to run again. After the move, a code for the cascade would tell them that a move made was not, or need each to learn a new code for what the report already says. Before the move, nothing is made that a code could misreport, and a tracker that would not answer is as broken as the board ADR-074 point 5 gives the broken tool's code, so a caller tells the refusal from one on the moved issue's own position or gates. A dry run takes the code its run would take, so it shows the refusal before the run meets it. The cost: a caller reading only the exit code of a move made learns nothing of an ancestor left, nor of a walk ended short of the top, whose warning is in the command's output.

### Alternatives considered

- **Refuse for other reads, at another moment, or with a bypass** (see "Why a move that schedules or starts work is refused where a first read gets no answer").
  - **Refuse only where the board cannot be read.** The case: a broken tool stops what rests on it. Taken in part: the move is refused where any first read gets no answer, the tracker's as the board's, and only on a move still to make that schedules or starts work.
  - **Plan the walk again after the move is confirmed at a terminal, before it is made,** as a move reads its own issue again after its prompt ([project-kit#3261](https://github.com/aleskalfas/project-kit/issues/3261)), and refuse where that plan gets no answer. The case: a fault that begins during the prompt is otherwise met only after the move, where it ends the walk. Rejected: it reads every ancestor twice on each such move confirmed at a terminal, only to move that window to the moments before the later reads, where the walk still ends.
  - **Let a person bypass the refusal with an audited reason, the cascade then run as far as the fault** ([project-management:DEC-014-validation-severity-model]). The case: a bypass would bring level in one run each container below a fault that lasts, with the reason on record. Rejected: a run that skips the cascade, and then the move made again, does as much with no override of its own, and the reason an audit would record is about a tool, where DEC-014's audit records a person outweighing a rule on the issue.
- **Write from the first read.** Each variant carries the hazards of a write from a read made before the move (see "Why the cascade writes only from reads made after the move").
  - **Only where no prompt stood between the first read and the move.** The case: the first read is then seconds old. Rejected: it keys what the cascade writes to how the command was run.
- **End the walk at an ancestor the process engine evaluates no position for** (see "Why the later read asks the process engine first").
  - **End the walk at every such ancestor, as at one whose later read gets no answer.** The case: every later read has one reader, the engine (DEC-033 D5), and a kept journal misses no step. Rejected: a direct read places the ancestor by the inference the engine runs (ADR-074 point 4), so this keeps containers behind for as long as a fault in the engine lasts, which the move made again does not mend.
  - **End the walk at such an ancestor only where a journal is kept.** The case: a kept journal is load-bearing (DEC-049). Rejected: what the cascade moves would turn on a project's journal setting.
- **Read other issues again after the move, or fewer** (see "Why the later read is made of each ancestor the first read placed behind or in none, and of no other", and "Why the cascade writes only from reads made after the move").
  - **Read a level ancestor again only where a prompt stood between the first read and the move.** Rejected: it keys what the cascade reads to how the command was run.
  - **Place a level ancestor again where its parent check is made.** The case: its issue is read already. Rejected: placing it asks the engine where it stands, a call for each such ancestor on every move that writes.
  - **Parent-check every issue the walk passes after the move, whether or not a write lies above it.** The case: every parent changed after the walk was planned is then warned of. Rejected: it adds a read of each level ancestor's parent records on every forward move, the common move that writes to no ancestor included, and a check with no write above it guards none.
- **Warn of other states, or of fewer** (see "Why an open container at Review or Done is read there, and warned of" and "Why the report is clean only where the cascade finished").
  - **Pass over an open container at Review, or at Done where labels carry the state, as level, with no warning.** The case: the cascade would not move it either way. Rejected: one falsehood would be a warning where the board carries Done, and pass with no warning elsewhere.
  - **Pass over an open ancestor whose label names a state the lifecycle does not have, as level, with no warning.** The case: such a label may be a project's own, set on purpose. Rejected: no read placed it level, so the report would read clean over a container whose state no read gave.
  - **Warn of a closed container above the moved issue too.** The case: a closed one above work moving forward states something false as well. Rejected: it reached Done through a close, which the user authorises, and whether to reopen it is a question of that close.
- **Bring the ancestor level some other way.**
  - **Retry, within the run, a read that got no answer, until it answers or a limit is reached.** The case: a fault that passes within one run would not cut the cascade short. Rejected here: a retry loop would serve every command that reads the board or the tracker, and for the board it belongs in the read seam ([pkit:ADR-053]); the move made again is the retry.
  - **Move the ancestor on its labels or its Milestone where the board does not place it.** Rejected by DEC-051 point 6: the cascade would act on a position it guessed.
  - **Write In Progress, at the cap, to an ancestor whose card has no Status or that has no card.** The case: the write could never move an open container backward. Rejected: it would follow no transition the schema declares, from a state no read gave, and an ancestor in Todo would read as started without having been scheduled, which DEC-006 rejects for containers. A missing card is the board's membership to repair ([project-management:DEC-019-mandatory-issue-state]).
- **Signal an ancestor left elsewhere than in the report.**
  - **Record in the moved issue's journal that its cascade was left incomplete.** The case: an entry repeats nowhere and outlasts the run's output. Rejected: the journal holds an issue's governed moves (DEC-049), and a cascade left incomplete is no move of the moved issue.
  - **A check, run apart from any move, that lists each container behind the work under it.** The case: it finds such a container whoever ran the move and whatever the cause. Not taken here, and left to [project-kit#3246](https://github.com/aleskalfas/project-kit/issues/3246): it checks the whole hierarchy rather than act at one move.
- **Give the cascade other exit codes** (see "Why no code once the move is made, and the broken tool's before it").
  - **A code of its own for a move made with its cascade left incomplete.** The case: a caller reading only the code would learn of it, and ADR-096 point 4 lets a code that asks for a run again stand where a run again makes nothing twice. Rejected: every composing command would have to learn it, or would read it as the move not made.

## Implications

- **DEC-006 is refined in place by the edits below,** made in this change once this record is accepted; accepting this record accepts them ([COR-066](../../../decisions/core/COR-066-accepted-before-landing.md) point 5). Sorted by the decisions README's test ("Refining an accepted record"):
  - **Three change what DEC-006 decides,** each a decision that stays a person's ([COR-064](../../../decisions/core/COR-064-answer-delegate.md) point 6). The two in its Cascade rule narrow the forward cascade to the ancestors it can read, tell as the parent and write. They add to DEC-006's moves a refusal of a scheduling or a start for a tool that does not answer for another issue, which no row of its transition table holds. And the paragraph's sentence on a run that skips the cascade brings such a run into DEC-006, which calls the forward cascade automatic, leaving who may run one to [project-kit#3369](https://github.com/aleskalfas/project-kit/issues/3369). The one in its Alternatives considered takes in part an alternative DEC-006 rejects. They carry the pointer "(refinement per [project-management:DEC-075-cascade-unread-ancestor])" twice: on the "Cascade rule" heading, for both edits there, and at the end of the Alternatives bullet.
  - **Four change nothing DEC-006 decides,** so they take no pointer. They make the rest of DEC-006 agree with the narrowed rule, where it rests on the claim that no container stands behind the work under it, and say where a move back can set one behind.
- **The edits that change what DEC-006 decides:**
  - **In its Cascade rule,** in the forward-cascade bullet, the sentence "A container is never behind the work under it: when an issue moves forward, … capped at In Progress." reads instead: "No container is to stand behind the work under it: when an issue moves forward, the agent walks its ancestors — its parent, that parent's parent, and so on up to where its walk ends — and brings each one it finds behind up to the moved issue's state, capped at In Progress, wherever it can read where that ancestor stands, tell it as the parent and write to it."
  - **In its Cascade rule,** after the rule's three bullets, before "Review is a Task's state alone", a paragraph is added: "**Where the forward cascade cannot read or write.** A move that schedules or starts work, Todo → Backlog or Backlog → In Progress, is refused before it is made, with nothing written, where the tracker or the board gives no answer to a read its cascade's walk is planned on. Any other forward move is made whatever its walk finds. The cascade writes to an ancestor only from a read of it made just before the cascade writes to it, and only where each issue below it still names the parent it had when the walk was planned. An ancestor it cannot place in a state, tell as the parent or write to is left where it stands, as is each above where the walk ends short of the top, and the cascade's report warns of each. A container read level as the walk was planned and moved back since, or given since as a parent to an issue the cascade does not read again, stays behind with no warning until a later forward move under it brings it level. A run that skips the cascade says that the containers above may stand behind. DEC-075 says which reads refuse a move, which the cascade makes, where its walk ends and what its report warns of."
  - **In its Alternatives considered,** the bullet "Refuse to start a child whose ancestor is unscheduled, or leave the ancestor behind and report it" gains, after "a container behind a started child states something false.": "Leaving an ancestor the walk finds behind is rejected wherever the cascade can read where it stands, tell it as the parent and write to it, up to where the walk ends. Where a read as the walk is planned gets no answer, a move that schedules or starts the child is refused for the broken tool, with nothing written; otherwise an ancestor the cascade cannot place in a state, tell as the parent or write to is left where it stands, with a warning, as is each above where the walk ends short of the top. The child's move is never refused for an ancestor's state (refinement per [project-management:DEC-075-cascade-unread-ancestor])."
- **The edits that change nothing DEC-006 decides:**
  - **In "Moving back from In Progress", its first paragraph,** "since a container is never behind the work under it" reads instead "since no container is to stand behind the work under it". The landing rule that sentence gives stands.
  - **In "Moving back from In Progress", its last paragraph,** "The move back moves no other issue: a container may stand ahead of the work under it, never behind it." reads instead: "The move back moves no other issue: a container may stand ahead of the work under it, and is not to stand behind it. A move back checks a container's children alone, so where a child container stands behind the work under it, moving the container back can set it behind work further down."
  - **In its Rationale, the paragraph on a container moved back over a child,** "Refusing that move keeps the cascade's guarantee" reads instead "Refusing that move keeps to the cascade's aim".
  - **In its Implications,** "The project-manager runs the cascade check after every state-changing operation: forward cascade walks ancestors and bumps any behind;" reads instead "The project-manager runs the cascade check with every state-changing operation: forward cascade plans its walk of the ancestors, before the move where the run makes one, and then bumps each one behind, up to where the walk ends, that it can place, tell as the parent and write to;".
- **Standing in DEC-006:** the forward-cascade bullet's sentence on a completed close, and the `manual-completed` trigger's account of its cascade. Each says that a completed close runs the forward cascade, from Todo, Backlog or In Progress, before the closure cascade, and leaves which ancestors it brings level to the Cascade rule as narrowed.
- **[pkit:ADR-074]'s Boundaries take a fact corrected and a citation added, with no pointer, edits the architect makes:** "DEC-006 holds that a container is never behind the work under it" reads instead "DEC-006 holds that no container is to stand behind the work under it", and "which gives way is a question for a project-management record, not for this one." reads instead "which gives way is a question for a project-management record, not for this one: [project-management:DEC-075-cascade-unread-ancestor] decides it.", linked as ADR-074 links the capability's records. Neither changes what ADR-074 decides: the two rules still pull apart there, and the rest of ADR-074 stands, this record keeping its point 5 as ADR-096 refines it. [pkit:ADR-096] needs no edit: it gives DEC-006's claim as what the cascade is for, which the narrowed rule keeps as its aim.
- **DEC-033 needs no edit.** Its D5 stands as written, read as "Why the later read asks the process engine first" says.
- **[project-management:DEC-026-work-ownership-lifecycle] needs no edit.** Its wrappers compose over the move, which keeps the walk: what this record puts before a wrapper's prompt and writes is the move's plan of its walk, which writes nothing, and the move the wrapper then calls plans and walks as its own. The skip each such wrapper carries, and its run again finishing the cascade, sit beside what DEC-026's table names for it.
- **Who may skip the forward cascade is not decided here,** nor whether an agent may on its own, nor whether a skip owes a reason. That is left to [project-kit#3369](https://github.com/aleskalfas/project-kit/issues/3369). This record decides only that a run that skips it is not refused, is the way past a refusal, and says what it leaves.
- **A move back can set a container behind work further down,** where labels carry the state, as DEC-006's edited last paragraph on it says; where the board carries the state no move back is made. Whether a move back checks every issue under the container is left to [project-kit#3247](https://github.com/aleskalfas/project-kit/issues/3247).
- **The command that moves an issue changes with it, and its tests hold each case the points decide,** in a change that rests on this record once it is accepted. So does each command that calls a move that schedules or starts work.
- **Documents follow, each passage by what it says,** not by the document it sits in:
  - **A passage whose subject is the forward cascade, and which says which ancestors it moves,** carries this record's limit, or sits beside one that does: in the same section, or as a use case's variant sits beside the step it names.
  - **Such a passage that the capability ships with its commands** changes with the code it ships beside, in the change that builds this record, so that what ships says what the shipped commands do. The workflow schema's account of the forward cascade is one, and changes with the commands rather than with DEC-006's edits.
  - **Any other such passage states the lifecycle's rule,** and changes in this record's change, with the DEC-006 edits, marking what the build has yet to make where its document marks such gaps.
  - **A passage that names the cascade by the effect it is for stands,** such as a view's overview or a diagram's node, as does one whose subject is something else, such as a close: it leaves which ancestors the cascade moves to DEC-006 and to the passage that tells how it works.
- **A check that finds, apart from any move, each container standing behind the work under it is not decided here,** and is left to [project-kit#3246](https://github.com/aleskalfas/project-kit/issues/3246) (Alternatives). Without it, a container this record lets stand behind with no warning has no signal (point 2).
- **No migration is owed.** Nothing an adopter holds is renamed, removed or restructured. What the build changes is a surface change of the capability, declared by a changeset in the change that builds it.
