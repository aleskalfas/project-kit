**In plain terms:** when an issue moves forward, the forward cascade brings each container above it that stands behind it up to the issue's state, as far as In Progress. A tool that does not answer is broken: where the board or the tracker gives no answer to a read the walk is planned on, a move that takes the issue past where it stood below In Progress, and so could bring a container up, is refused before it is made, with nothing written. A move on from In Progress is never refused for its cascade, and there, as after any move, a read that gets no answer ends the walk. Data that is off, where the tool answered, is left and warned of, and the move goes on: a container its card or label places in no state is left and the walk goes on past it, while a parent record naming an issue that does not exist ends the walk. The cascade writes only from reads made after the move, warns wherever it did not finish, saying why and how to finish, and once the move is made takes no exit code.

## Context

Two accepted rules meet at the forward cascade:

- **No container is to stand behind the work under it.** When an issue moves forward, each ancestor that is behind is brought up to the moved issue's state, capped at In Progress ([project-management:DEC-006-state-machine-and-cascade], "Cascade rule").
- **No command acts on a position it could not read** ([project-management:DEC-051-axis-carriage-activation] point 6). Where the board carries the state, a card that does not place an issue, or a board that cannot be read, falls back to neither its labels nor its Milestone.

At an ancestor whose position a read does not give, the two pull apart. [pkit:ADR-074] leaves which gives way to a project-management record (its Boundaries), and its point 5 holds every command that reads the state to two limits: it never guesses, and it keeps a board that would not answer apart from a finding about the issue, the first taking the broken tool's code where a command's codes tell one. [pkit:ADR-096] point 4 adds that once a command's act is made, here the issue's move, nothing it sets off on another issue, such as the forward cascade, gives the command a code that reads as the act not made, and leaves to this record whether the move waits on a read of an ancestor.

The question is what the move does at such an ancestor ([project-kit#3204](https://github.com/aleskalfas/project-kit/issues/3204)): whether it is refused for it, and, where it is not, what the walk does there and above it.

Terms:

- **The walk** is the cascade's pass from the moved issue's parent up its hierarchy, one ancestor at a time. Point 4 says where it ends.
- **An issue's parent records** are its native sub-issue link, where the tracker supports one, and its body's first line ([pkit:ADR-035]).
- **The top** is an issue whose parent records were read and name no parent: it has no native parent, and its first line names no issue, as where it names a Milestone (ADR-035 point 1).
- **A read of where an ancestor stands** places it in a state of the lifecycle, places it in none, or gets no answer.
  - **It places the ancestor in none** where the tool answers with a finding about the ancestor, which is open: that what carries its state places it in no state of the lifecycle. Where the board carries the state, that is one of DEC-051 point 6's findings: the board answered, with the witness [pkit:ADR-096] point 1 asks, that the issue has no card; its card has no Status; or its Status names no open state, such as Done on an open issue. Where labels carry it, that is a label for a state the lifecycle does not have.
  - **It gets no answer** where the tracker did not answer for the ancestor's issue or, where the board carries the state, the board did not answer for its card. The tracker did not answer where it said it could not, could not be reached, or replied with anything but one whole, well-formed answer: a parent record ADR-035 point 1 calls *unread* is such a read, while a native substrate its point 2 finds *unsupported*, where the first line is the whole answer, is an answer. The board did not answer wherever ADR-096 points 1 and 2 count it so, as for an absence of a card with no witness, a read not whole, or an error placed on the board or its cards, and where [pkit:ADR-074] point 1 counts it a board that cannot be read, as one with no Status field or whose Status is not single-select. Such a read gives no position.
  - **An ancestor is level** where a read places it at or past the state the cascade brings it up to.
- **An issue that does not exist** is one a parent record names that the tracker answers is not there. The tracker answered, so this is no read that gets no answer: it finds a parent record that is off, and no ancestor to place.
- **The cascade's target** is the state the move takes the issue to, capped at In Progress. A move **could bring a container up** where the cascade's target lies past the state the move takes the issue from: Todo → Backlog, a move into In Progress, and a move to Done from Todo or Backlog that runs the cascade.
- **The first read** of an ancestor is made as the walk is planned: before the move, where the run makes one, and before a person at a terminal confirms it. It reads the ancestor's issue, its parent records included, and, where the board carries the state and the ancestor is open, its card. The moved issue's parent records are read then too. That read and each ancestor's first read are **the first reads**.
- **A later read** of an ancestor is made after the move, just before the cascade would write to it (point 2).
- **The parent check** reads an issue's parent records alone, once, after the move, to find whether the issue still names the parent it had when the walk was planned (point 2).
- **An ancestor left** is one whose later read places it in none, or whose write of what carries its state is not made (points 2 and 3). A container behind for another cause is not one, such as one for which the lifecycle declares no way from where it stands, one moved back after the first read placed it level, or one at or above where the walk ended (point 4).

## Decision

**A forward move not yet made that could bring a container up is refused where one of the first reads gets no answer. Any other forward move is made whatever its cascade finds above it. The cascade writes to an ancestor only from reads made after the move, of the ancestor and of the issues below it on the walk. An ancestor its later read places in none is not moved, one whose write is not made is moved no further, and the walk goes on past each. The walk ends at an issue that does not exist and, wherever the move is not refused, at a read that gets no answer. Once the move is made, the cascade takes no exit code.**

### 1. A move that could bring a container up is refused where a first read gets no answer

A forward move not yet made that could bring a container up is refused where one of the first reads gets no answer, from the tracker or from the board: the read of the moved issue's parent records, or the first read of an ancestor its walk will reach. The refusal comes before any prompt, writes nothing, neither the move nor any step of its cascade, and takes the broken tool's code (point 6), in a dry run as in the run itself. It names each such read and the issue it was of, with what the read said of why, and says that the move made once the read is answered makes the move and its whole cascade.

A move that cannot bring a container up, In Progress → Review, Review → Done or In Progress → Done, is never refused for its cascade. Nor is a run that finds the issue already at its target, as after a merge, a completed close or an earlier run, since it makes no move. On either, the walk as planned ends where a first read gets no answer: at that ancestor, with nothing written to it or above it, or, where the read of the moved issue's parent records gets none, with nothing written to any ancestor (point 4).

Otherwise a forward move is made, or refused, on the moved issue's own reads and gates, never on what its walk finds above it. No command refuses or holds a move because a read places an ancestor in none, or finds an issue that does not exist, whether the walk finds it before the move or after it.

A command that writes before it calls a move that could bring a container up, as a start of work sets the assignee and cuts the branch first, makes the first reads before its own writes, and its move plans the walk on them, so a refusal leaves nothing behind. A run that skips the cascade (`--no-cascade`) plans no walk, so it makes no first reads and refuses nothing, and it says that no cascade ran and that the containers above may stand behind the work under them.

Where the walk is planned before the move, what it found is shown before the move is confirmed. So a person at a terminal sees which ancestor the first read placed in none, that the run reads it again where the walk reaches it, and where the walk as planned ends, and may decline the move.

### 2. The cascade writes to an ancestor only from reads made after the move

Each ancestor the first read places behind, or in none, gets a later read, once, just before the cascade would write to it. That read reads where the ancestor stands, and the ancestor's issue: its labels, whether it is open, its type, its parent records and where its card is found. Each write to the ancestor takes its inputs from that read, as the writes before it left them.

An ancestor its later read places in none is left where it stands, with nothing written to it: no state, no Status, no journal entry and no comment. Where its later read gets no answer, or finds that its issue does not exist, nothing is written to it or above it, and the walk ends there (point 4). The first read decides which ancestors the walk can reach, which of them get a later read, and what the preview shows. What the cascade writes rests on reads made after the move alone, and never on a position guessed from an ancestor's labels or its Milestone where the board carries the state (DEC-051 point 6).

The later read asks the process engine where the ancestor stands, as the commands that move an issue do ([project-management:DEC-033-rebind-issue-lifecycle-onto-process-substrate] D5), and takes the position the engine gives, in a state or in none. Where the engine evaluates no position, as where it cannot be reached, replies with anything but one well-formed answer, or answers that it could not evaluate the position, the later read is made directly instead, once, as the first read is made. So a later read gets no answer only where the tracker did not answer for the ancestor's issue or, where the board carries the state, the board did not answer for its card, never for the engine alone. A direct read that gets no answer is not made again in the run, and the walk ends there.

The cascade writes to an ancestor only where each issue below it, down to the moved issue, still names after the move the parent it had when the walk was planned. Each of them is read for that after the move, before the cascade's first write above it: by its later read where one is made, and otherwise by its parent check. Where one of them no longer names that parent, or cannot be read, the cascade writes nothing to that ancestor or above it, and the walk ends there (point 4). No other issue is read for a changed parent, so a parent given after the walk was planned to an issue with nothing written above it stays behind, with no warning, until a later forward move under it reaches it.

An ancestor the first read places level gets no later read, and nothing is written to it, so one moved back after that read stays behind, with no warning, until a later forward move under it brings it level. Its parent check, where one is made, reads its parent records alone.

### 3. An ancestor whose write is not made is moved no further

Where a write of what carries the ancestor's state fails, as where the tracker or the board refuses it, the ancestor is moved no further, and the steps it took before that write stand, as does the move. What else the cascade writes once the ancestor's state has moved, such as a Status kept only as a mirror of its labels, a comment or a journal entry, is no such write: where it fails, the report says so, and the steps stand. A read of the card made only for that mirror is the mirror's (ADR-096 point 4): where the board does not answer it, the mirror is not made, and the walk goes on. So where labels carry the state, a board that does not answer refuses no move, since no card is read before it.

### 4. The walk goes on past an ancestor left, and where it ends

The walk finds an ancestor's parent from its issue, not from where it stands, so a read that places the ancestor in none still gives its parent. Each ancestor is brought up to the cascade's target, never to the state of the ancestor below it, so an ancestor left bears on no move above it. So the walk goes on past it, and each ancestor above is brought level, or not moved, on where its own reads place it.

The walk ends at the top. It ends short of the top where it cannot tell the next ancestor up: at a parent in doubt, in each case where [pkit:ADR-035] point 5 has a consumer that writes on the resolved parent write nothing on it or above it; at an issue whose first line names itself, which names no parent (ADR-035 point 2); at an issue that does not exist, before the move or after it; and at an issue whose later read or parent check finds that it no longer names the parent it had when the walk was planned. Wherever the move is not refused, it ends too where a read gets no answer, and the cascade writes nothing to the issue it could not read or above it: a later read, a parent check, or a first read (point 1). It ends at an issue that is no container, which the cascade does not move, and at one it has passed already.

The walk takes the tracker's answer as given. One that leaves out what the credential may not see, as where a native parent in a repository the credential cannot read comes back as none, is outside this record: such a walk ends at what reads as the top, under a clean report.

No later read extends the walk, so the cascade writes on no ancestor the walk did not reach as it was planned.

### 5. When the report is a warning, and how to finish

The cascade's closing report is clean only where, by what the cascade read and wrote, the walk ended at the top, each ancestor it reached stands level, each step it took was journaled where a journal is kept, and no open container it reached stands at Review or Done (below). Any other outcome makes the report a warning, such as an ancestor left, an end short of the top that the cascade finds, a step it could not journal, or an ancestor for which the lifecycle declares no way from where it stands. It gives no warning of a container behind the work under it whose position it did not read after the move, as one moved back after the first read placed it level (point 2).

The report lists each ancestor the walk planned, with what became of it. It names each ancestor left and the read or the write that left it, and, where the walk ended short of the top, where and why. It names a read that got no answer as one, with what the read said of why, so that a cause that lasts can be told from one that passes, and never as a finding about the ancestor, nor a finding as such a read ([pkit:ADR-074] point 5).

A read can place an open ancestor at Review, which DEC-006 keeps for a Task alone, or, where labels carry the state, at Done, which a container reaches only through its close (DEC-006). The cascade does not move such an ancestor, since it is level, and the report warns of it. Where the board carries the state, an open ancestor whose card names Done is placed in none (DEC-051 point 6), so it is left (point 2).

For each ancestor left, each open container at Review or Done, each ancestor for which the lifecycle declares no way from where it stands, and each end short of the top, the report says how to finish: what to put right or mend, in the containment seam's words at a parent in doubt (ADR-035 point 5), and the parent record that names it, on the issue the report names, at an issue that does not exist, names itself, is no container or was passed already; and then which of the move made again, the next forward move under the ancestor, or a move of the ancestor on its own finishes the cascade. Where the walk ended at a read that got no answer, that is the move made again, once the read is answered. It says too that a container whose state is set as a person meant it, such as one set outside the lifecycle on purpose, stays where it was put, and that each forward move under it warns of it again.

### 6. Once the move is made, the cascade takes no code, and before it only the refusal takes one

A run that makes the move or finds the issue already at its target, and a dry run of either, exit as the move alone has them exit. Whatever makes the cascade's report a warning (point 5) is a warning beside it, never a code: not a refusal's, not the broken tool's, nor any other. That keeps within the limit [pkit:ADR-096] point 4 sets once a command's act is made, so each command that composes the move reads the move as made.

A run refused for a first read that got no answer (point 1), and a dry run of a move it would refuse, take ADR-074 point 5's broken tool's code, where the command's codes tell one, whichever read got no answer, the tracker's or the board's. A run declined at the terminal makes no move, so the cascade gives it no code. Nor does a read that places an ancestor in none, or finds an issue that does not exist, give any run a code, since neither holds the move (point 1).

## Rationale

**Why a move that could bring a container up is refused where a first read gets no answer.**

- **It is the person's choice.** The person who decides this lifecycle chose that a tool that does not answer is broken, and that a move whose cascade could bring a container up is not made while that cascade cannot be planned. ADR-096 leaves the choice to this record (its point 4 and Boundaries), and ADR-074 point 5 asks only that such a read be kept apart from a finding. The consequence: the move made again once the read is answered makes the move and its whole cascade in one run, and no container stands behind work the move started for a fault met before anything was written. The moved issue's own parent records are held as an ancestor's first read is, since the whole walk starts from them.
- **Only where the move could bring a container up.** Where the issue stood at the cascade's target, In Progress, before the move, each container above was brought up by the move that started it, or was warned of then, or was moved back since, and this move starts nothing above it. So the person's rule is applied to the moves whose cascade could bring a container up. The consequence: neither a Task's move to Review before its merge nor its move to Done after it is refused for another issue's read, so no merge is held for an ancestor, and no merged issue is left open at Review.
- **Before the command's own writes.** A refusal leaves nothing behind only where nothing was written before it, so a command that writes before it calls such a move makes the first reads first. Nothing is written from them (point 2), so their being older costs nothing.
- **Gates are per issue.** Each gate governs a move on its own issue, and the cascade asks for no authorisation (DEC-006). The refusal reads nothing of an ancestor's state: it stops for the tool.
- **The costs.** A move whose own reads and gates passed is refused for a read of an issue that is often another person's, and the commands that compose the move read the refusal as the move not made, so a start of work fails. The refusal lasts as long as the fault: a board that is down refuses every such move under the container until it answers, and an error placed on one ancestor's card that lasts counts as a board that did not answer (ADR-096 point 2), so it refuses every such move beneath that ancestor until someone, often not the mover, mends the card. Meanwhile a run that skips the cascade makes the move, saying that it ran none.
- **Nothing is left to refuse once the move is made.** No code may then read the move as not made (ADR-096 point 4), so where the issue already stands at its target, a first read that gets no answer ends the walk, as a later read that gets none does. A fault can begin between the first read and a later one, so a walk cut short after the move has to be handled whatever this record decides.

**Why data that is off is left, and the move goes on.** Where the tool answered, what is off is the data, and a refusal of the move mends none of it.

- **A read that places an ancestor in none** says that it stands outside the lifecycle until whatever carries its state is set right. It cannot be moved without a guess, which DEC-051 point 6 forbids, so a refusal of the work under it would leave it as it was. A refusal would also give a state set by hand a meaning no record gives it: a container whose card sits in a column outside the lifecycle, such as Blocked, or that is kept off the board, would hold every forward move beneath it, answering by accident what DEC-006 leaves open, what a card a person places by hand means.
- **A tracker that answers that an issue does not exist** answered too: what is off is the parent record that names it, and a refusal would keep every forward move under it waiting on whoever mends it. The walk ends there, since an issue that does not exist names no parent, and the report names the record to mend. The cost: where the record meant another issue, that issue stays behind, warned of on each forward move under the record, until the record is mended.

Data that is off is finished on the data, and a read that gets no answer on the tool, so the report names the two apart, as ADR-074 point 5 asks.

**Why DEC-006's Cascade rule is narrowed here, and not DEC-051's rule.** DEC-006 rejects leaving an ancestor behind and reporting it, where the cascade could move it, because a container behind a started child states something false. Here the cascade cannot move the ancestor without guessing its position, which DEC-051 point 6 forbids, or taking it from a read made before the move, which can move it back. So the Cascade rule keeps its aim, that no container is to stand behind the work under it, and is narrowed to what the cascade can read and write: a container may stand behind until a later move brings it level, where it is placed in none, its write is not made, a read of it gets no answer on a move not refused, with each container above, it was moved back after the first read placed it level, or it is a parent given after the first read that nothing reads. A first read that gets no answer on a move that could bring a container up narrows nothing, since it refuses the move.

**Why the walk goes on past an ancestor left, and where it ends.** An ancestor above is brought level on its own reads (point 4), so it moves on a position that was read, and a container ahead of the one below it is a state DEC-006 allows. Stopping the walk would keep every container above behind the work under it, for data that is off on one ancestor. An ancestor whose write failed is passed for the same reason: its reads answered, and where the tool has failed since, the next read gets no answer.

The walk ends where the next ancestor up cannot be told, since a write on a parent in doubt could move a container the moved issue is not under, as ADR-035 point 5 holds. An issue that does not exist, or whose first line names itself, names no parent. One that no longer names the parent it had when the walk was planned names one neither read as the walk was planned nor shown before the move, as would any ancestor a later read extended the walk to. The walk ends at an issue that is no container, which the cascade never moves, and at one it has passed already, where going on would walk in a circle. Only the top is a clean end, since only there do the records name nothing above.

Wherever the move is not refused, a read that gets no answer ends the walk, since the person's rule has a broken tool stop what rests on it, and where the ancestor's issue could not be read, its parent is in doubt besides. The move made again, once the read is answered, finishes the cascade in one run. The cost falls where the fault reaches that read alone: each container above stays behind, with a warning, until the move made again or the next forward move under it.

**Why the cascade writes only from reads made after the move.** The first read is made before a person at a terminal confirms the move, so it can be minutes old when the cascade writes, and another move under the same ancestor may have brought it level in between. A write sets where the ancestor goes without checking where it stands, so a write from the first read would then:

- where the board carries the state, set the ancestor's Status back behind the work under it, a move back DEC-006 holds for the user, which nobody authorised;
- where labels carry the state, take off a label the ancestor no longer carries and add the next, which can leave it two values on one axis, against the rule that an issue carries one value on each axis ([project-management:RS-PM-003]);
- on either, journal a step from a state the ancestor no longer held, which no later move takes back.

A read made just before the write leaves only the window every write leaves between its read and its landing, so the cascade writes from that read alone, and nothing to the ancestor or above it where that read gets no answer, the first read being as old whichever read failed. The move made again finishes the cascade.

Which issues are the ancestors is read before the move too. Where the moved issue or an ancestor is given another parent in between, a write along the walk as planned moves a container the moved issue is no longer under: a container in Todo is taken to In Progress on a commitment given on work no longer beneath it, while the new parent goes unread under a clean report. So the cascade reads each issue below an ancestor after the move, before it writes to that ancestor, and writes nothing where the walk changed. The cost is a parent check of the moved issue, and of each level ancestor below a written one, bounded by the hierarchy's depth, and none on a move that writes to no ancestor. The check guards the writes, so it reads no issue with no write above it (see "Parent-check every issue the walk passes" under Alternatives).

**Why the later read is made of each ancestor the first read placed behind or in none, and of no other.** A card or a label set right after the first read places an ancestor the first read placed in none, so a later read of it, costing what one of an ancestor placed behind costs already, brings level one the first read alone would leave. An ancestor the first read places level gets no later read, so a move under ancestors already level costs one read of each. Writing nothing there costs less than a write from an old read: a container moved back after the first read stays behind, with no warning, until the next forward move under it, while a write risks the harms above. A move back already bears a cost of that kind (Implications).

**Why the later read asks the process engine first.** DEC-033 D5 hands a move's mechanics, its position, validation and journal, to the engine, and keeps the cascade among the side-effects project-management retains. This record reads the two clauses together: which ancestors the cascade moves, and how far, is the side-effect kept, while each step it writes is a move whose position, the step's origin, D5 hands on. So the later read, from which each step's origin comes, asks the engine first, at the cost of a second read for each write's inputs, with a moment between the two. The first read sets no step's origin, so it reads directly. A direct read and the engine place an ancestor by one inference over the same inputs ([pkit:ADR-074] point 4), which DEC-033 holds to the same result (its Implications, behaviour parity).

Where the engine evaluates no position, its answer cannot tell a read of the ancestor that failed from a failure of the lifecycle's classifier, the predicate that reads the issue and its card, before it read, as where its code would not load. A direct read then is as fresh as the engine's would have been, and places the ancestor by the same inference, so it is no second account of position. It is made once, and where it too gets no answer, the walk ends there (see "Retry, within the run" under Alternatives). That the engine alone never ends the walk is a choice beyond the person's rule, which speaks of a tool that does not answer for the ancestor: where only the engine fails, the tracker and the board still answer for it.

Where a journal is kept, a step written from a direct read goes unjournaled wherever the engine still cannot place the ancestor, since the engine journals a step from a stated origin only while its own reading places the ancestor at that origin or at the step's target (the process README, "Why `--from`"). The report warns of each such step, as the run reports any move it could not journal ([project-management:DEC-049-audit-journal-model]).

**Why an open container at Review or Done is read there, and warned of.** The engine and every command place such an ancestor alike (ADR-074 point 4), so the cascade reads it where they do: at Review, or at Done where labels carry the state, past In Progress, so level, and writes nothing to it. Yet DEC-006 keeps Review for a Task alone and has a container reach Done only through its close, so an open container at either states something false, and the report is the one signal of it that reaches whoever moves the work under it. The cost is a warning on each move under it until it is set right or closed, and one falsehood the two substrates report under two names. A closed container is not warned of (see "Warn of a closed container above the moved issue too" under Alternatives).

**Why the report is clean only where the cascade finished.** A warning keyed to a list of causes misses each cause the list leaves out, such as a step the engine could not journal, or an ancestor for which the lifecycle declares no way from where it stands. A report clean only where the cascade finished warns of both, and of any cause found later.

It says how to finish, since an ancestor left can be offered for closing before it is level: the closure cascade makes an ancestor eligible to close once its last open child closes, wherever it stands, while DEC-006's table starts that close only at In Progress. Where no forward move is left to come under it, only a move of the ancestor on its own brings it level, before it is closed. That move is asked for directly, so its gates apply: a container in Todo needs scheduling of its own, though the scheduling given on the work under it covered it (DEC-006).

**Why nothing is written to the ancestor.** A notice on it would repeat on every forward move under a container set outside the lifecycle on purpose, or need a key to post it once, which a later change of its state would have to reset. The report reaches whoever runs the move, where the move's own outcome is read. It repeats too, and readers may learn to pass over it, but that cost falls on the output of the moves, and on no issue.

**Why no code once the move is made, and the broken tool's before it.** Commands compose the move and act on its code: a start of work reads a non-zero code as a failed start, and a merge or a close as a step to run again. After the move, a code for the cascade would tell them that a move made was not, or need each to learn a new code for what the report already says. Before the move, nothing is made that a code could misreport, and a tracker that would not answer is as broken as the board ADR-074 point 5 gives the broken tool's code, so a caller tells the refusal from one on the moved issue's own position or gates. A dry run takes the code its run would take, so it shows the refusal before the run meets it. The cost: a caller reading only the exit code of a move made learns nothing of an ancestor left, nor of a walk ended short of the top. The warning is in the command's output, as for a cascade a failed write left incomplete.

### Alternatives considered

- **Refuse the move, or end the walk, on the ancestor, or never** (see "Why a move that could bring a container up is refused where a first read gets no answer", "Why data that is off is left, and the move goes on" and "Why the walk goes on past an ancestor left, and where it ends").
  - **Refuse the move wherever an ancestor its walk will reach cannot be placed, a read that places it in none included.** The case: after no move it lets through does a container stand behind the work under it. Rejected for a read that places the ancestor in none, for the reasons data that is off is left.
  - **Refuse only where the board cannot be read.** The case: a broken tool stops what rests on it. Taken in part: the move is refused where any first read gets no answer, the tracker's as the board's, and only on a move still to make that could bring a container up.
  - **Never refuse: make the move whatever the first reads get.** The case: the move rests on its own reads, which answered, and a refusal for another issue's read is a gate nobody set on the move. Rejected: the person chose that a move whose cascade could bring a container up is not made while that cascade cannot be planned. Made all the same, it would leave each container from the unanswered read up behind work it started, under a warning, until the move made again.
  - **Refuse every forward move not yet made, those on from In Progress or Review included.** The case: one rule for every forward move, and no move under a container its run cannot read. Rejected: such a move starts nothing above, so the refusal would hold a Task's move to Review, and with it the merge, for another issue's read, and would leave an issue whose pull request merged open at Review.
  - **Count a tracker's answer that an issue a parent record names does not exist as a read that gets no answer, and refuse the move for it.** The case: the walk cannot finish either way, and a refusal gets the record mended before work moves under it, where a warning may be passed over. Rejected: the tracker answered, so no tool is broken, and a refusal would keep every forward move under the record waiting on whoever mends it, as one for a read that places an ancestor in none would.
  - **Go on past an ancestor whose read gets no answer, as past one a read places in none.** The case: where only the ancestor's card went unanswered, its issue still gives the parent above, so each container above is brought level on its own reads. Rejected: the fault is the tool's, not the ancestor's, and the person's rule stops what rests on a tool that does not answer. The move made again once it answers finishes the cascade whole.
  - **Stop the walk at an ancestor the cascade does not bring level, and report where it stopped.** The case: one line names where the walk ended. Taken where a read gets no answer and the move is not refused. Not taken where a read places the ancestor in none or its write is not made: the containers above could each be read and brought level.
  - **Plan the walk again after the person confirms the move, before it is made,** as a move reads its own issue again after its prompt ([project-kit#3261](https://github.com/aleskalfas/project-kit/issues/3261)), and refuse where that plan gets no answer. The case: a fault that begins during the prompt is otherwise met only after the move, where it ends the walk. Rejected: it reads every ancestor twice on each such move confirmed at a terminal, the level ones included, only to move that window to the moments before the later reads, where the walk still ends, and the move made again finishes it.
  - **Let a person bypass the refusal with an audited reason** ([project-management:DEC-014-validation-severity-model]). The case: a fault that lasts on one ancestor refuses every such move beneath it, and a bypass would run the cascade as far as the fault, with the reason on record. Rejected: the refusal is for a broken tool, not a rule a reason may outweigh, and a run that skips the cascade already lets the move go on, saying that it ran none, at the cost of the containers below the fault.
- **Write from the first read.** Each variant carries the hazards of a write from a read made before the move (see "Why the cascade writes only from reads made after the move").
  - **Where a later read gets no answer, write from the first read where it placed the ancestor.** The case: the cascade could finish in one run through a fault that passes. Rejected: such a write carries those hazards, and ending the walk costs only a run made again.
  - **Only where no prompt stood between the first read and the move.** The case: the first read is then seconds old. Rejected: it keys what the cascade writes to how the command was run, and a move under the same ancestor in those seconds makes the same false move back.
  - **Where the process engine evaluates no position.** The case: the cascade still brings ancestors level where the engine is missing. Rejected: a direct read then is as fresh as the engine's would have been, while the first read is as old as ever.
  - **Write along the walk as planned, and accept the gap where an issue no longer names the parent it had when the walk was planned,** as the gap for an ancestor moved back after the first read is accepted. The case: no read is added. Rejected: it moves a container the moved issue is no longer under, while the gap for an ancestor moved back writes nothing.
- **End the walk at, or read otherwise, an ancestor the process engine evaluates no position for** (see "Why the later read asks the process engine first").
  - **End the walk at every such ancestor, as at one whose later read gets no answer.** The case: every later read has one reader, the engine (DEC-033 D5), and a kept journal misses no step. Rejected: a direct read places the ancestor by the inference the engine runs (ADR-074 point 4), so this keeps containers behind for as long as a fault in the engine lasts, which the move made again does not mend, and keeps the journal whole only where the fault lies with the ancestor alone.
  - **End the walk at such an ancestor only where a journal is kept.** The case: a kept journal is load-bearing (DEC-049). Rejected: what the cascade moves would turn on a project's journal setting, and where the fault lies with the engine, the entry it saves is one the same fault withholds from the move that caused it.
  - **Read directly only where the engine cannot be reached or replies with no well-formed answer, and end the walk where it answers that it could not evaluate the position.** The case: an engine that answers so has made its own read. Rejected: that answer cannot tell a read that failed from a classifier that failed before it read, so the walk would end at every such ancestor while the classifier is broken.
  - **Make every later read directly, and never ask the engine where the ancestor stands.** The case: one read would give the position and each write's inputs, with no window between them. Rejected: it sets aside D5's hand-off of each step's position to the engine, as this record reads D5.
- **Read other issues again after the move, or fewer** (see "Why the later read is made of each ancestor the first read placed behind or in none, and of no other", and "Why the cascade writes only from reads made after the move").
  - **Read again only an ancestor the first read placed behind.** The case: the preview and the report then agree on an ancestor placed in none. Rejected: one whose card or label was set right after the first read would be left though the cascade could bring it level.
  - **Read again every ancestor, those the first read placed level included.** The case: a container moved back after the first read is then brought level. Rejected: it adds a read through the engine of each level ancestor on every forward move, most of which are made under containers already level, and the next forward move under such a container brings it level.
  - **Read a level ancestor again only where a prompt stood between the first read and the move.** Rejected: it keys what the cascade reads to how the command was run, and a container moved back in the seconds a run with no prompt takes stays behind the same way.
  - **Place a level ancestor again where its parent check is made.** The case: its issue is read already. Rejected: placing it asks the engine where it stands, a call for each such ancestor on every move that writes.
  - **Parent-check every issue the walk passes after the move, whether or not a write lies above it.** The case: every parent changed after the walk was planned is then warned of. Rejected: it adds a read of each level ancestor's parent records on every forward move, the common move that writes to no ancestor included, and a check with no write above it guards none.
- **Warn of other states, or of fewer** (see "Why an open container at Review or Done is read there, and warned of" and "Why the report is clean only where the cascade finished").
  - **Place an open ancestor labelled Done in none where labels carry the state.** The case: the two substrates would report one falsehood under one name. Rejected: the cascade would place such an ancestor apart from the inference the engine and every other command run (ADR-074 point 4), while the report warns of it either way.
  - **Pass over an open container at Review, or at Done where labels carry the state, as level, with no warning.** The case: the cascade would not move it either way. Rejected: one falsehood would be a warning where the board carries Done, and pass with no warning elsewhere.
  - **Pass over an open ancestor whose label names a state the lifecycle does not have, as level, with no warning.** The case: such a label may be a project's own, set on purpose. Rejected: no read placed it level, so the report would read clean over a container whose state no read gave.
  - **Warn of a closed container above the moved issue too.** The case: a closed one above work moving forward states something false as well. Rejected: it reached Done through a close, which a person authorises, and whether work opened under it calls for reopening it is a question of that close.
  - **Make the report a warning for a list of causes,** those this record names. The case: the report warns of nothing this record does not name. Rejected: see "Why the report is clean only where the cascade finished".
- **Bring the ancestor level some other way.**
  - **Retry, within the run, a read that got no answer, until it answers or a limit is reached.** The case: a fault that passes within one run would not cut the cascade short. Rejected here: a retry loop would serve every command that reads the board or the tracker, not the cascade alone, and for the board it belongs in the read seam ([pkit:ADR-053]). The direct read made where the engine evaluates no position is one read, not a loop, and the move made again is the retry.
  - **Move the ancestor on its labels or its Milestone where the board does not place it.** Rejected by DEC-051 point 6: the cascade would act on a position it guessed.
  - **Write In Progress, at the cap, to an ancestor whose card has no Status or that has no card.** The case: the write could never move an open container backward. Rejected: it would follow no transition the schema declares, from a state no read gave, so a journal would record a step from nowhere, and an ancestor in Todo would read as started without having been scheduled, which DEC-006 rejects for containers. A missing card is the board's membership to repair ([project-management:DEC-019-mandatory-issue-state]).
- **Signal an ancestor left elsewhere than in the report.**
  - **Post a notice on the ancestor, or on the moved issue.** The case: the report reaches the mover, often an agent, while the ancestor is often someone else's. Rejected: see "Why nothing is written to the ancestor".
  - **Record in the moved issue's journal that its cascade was left incomplete.** The case: an entry repeats nowhere and outlasts the run's output. Rejected: the journal holds an issue's governed moves (DEC-049), and a cascade left incomplete is no move of the moved issue. Nothing reads such an entry to act on it, and it goes stale once a later move brings the ancestor level.
  - **A check, run apart from any move, that lists each container behind the work under it.** The case: it finds such a container whoever ran the move and whatever the cause. Not taken here, and left to [project-kit#3246](https://github.com/aleskalfas/project-kit/issues/3246): it checks the whole hierarchy rather than act at one move, and where it runs and what it reads are choices of their own.
- **Give the cascade other exit codes** (see "Why no code once the move is made, and the broken tool's before it").
  - **A code of its own for a move made with its cascade left incomplete.** The case: a caller reading only the code would learn of it, and ADR-096 point 4 lets a code that asks for a run again stand where a run again makes nothing twice. Rejected: every composing command would have to learn it, or would read it as the move not made.

## Implications

- **DEC-006 is refined in place on this record's acceptance,** by the edits below, each carrying the pointer "(refinement per [project-management:DEC-075-cascade-unread-ancestor])". The edits to its Cascade rule and to its Alternatives considered narrow the Cascade rule to the ancestors the cascade can read and write. The other three restate as an aim DEC-006's claim that no container stands behind the work under it, where the move back rests on it, and name where a move back can set a container behind the work under it:
  - **In its Cascade rule,** two changes:
    - In the forward-cascade bullet, the sentence "A container is never behind the work under it: when an issue moves forward, … capped at In Progress." reads instead: "No container is to stand behind the work under it: when an issue moves forward, the agent walks its ancestors — its parent, that parent's parent, and so on up — and brings each one its walk reaches and finds behind up to the moved issue's state, capped at In Progress, wherever it can read where that ancestor stands and write to it."
    - After the rule's three bullets, before "Review is a Task's state alone", a paragraph is added: "**The forward cascade writes only from reads made after the move.** It writes to an ancestor only from a read of it made just before the write, and only where each issue below it, down to the moved issue, still names the parent it had when the walk was planned. A move that takes the issue past where it stood below In Progress (Todo → Backlog, a move into In Progress, or a move to Done from Todo or Backlog) is refused before it is made, with nothing written, where a read its walk is planned on gets no answer, as where the board or the tracker would not answer for an ancestor or for the moved issue's parent records. On any other forward move, on an issue already at its target and after the move, any read that gets no answer ends the walk, a check of the moved issue's parent records among them. So does a parent the cascade cannot tell, as where two parent records do not agree or one names an issue that does not exist. Either way the cascade writes nothing to the issue it could not read or tell, or above it. An ancestor a read just before the write places in no state of the lifecycle is left where it stands, one whose write is not made is moved no further, and the walk goes on past either. Save the refusal, the move is made or stands in each of these, and the cascade's report warns. A container read level as the walk was planned and moved back after that read, or given as a parent after it to an issue that gets no later read and has nothing written above it, stays behind with no warning until a later forward move under it brings it level. DEC-075 says which moves a read refuses, which reads the cascade makes, where its walk ends and what its report warns of."
  - **In its Alternatives considered,** the bullet "Refuse to start a child whose ancestor is unscheduled, or leave the ancestor behind and report it" gains: "Leaving an ancestor the walk finds behind is rejected wherever the cascade can read where it stands and write to it. Where a read as the walk is planned gets no answer, a move that takes the child past where it stood below In Progress is refused for the broken tool, not for an ancestor's state, with nothing written; on any other move, and after a move, a read that gets no answer ends the walk, leaving each ancestor from there up. One the cascade places in no state of the lifecycle just before it would write to it is left where it stands, and one whose write is not made is moved no further. Each is warned of, and the child's move is never refused for an ancestor's state."
  - **In "Moving back from In Progress", its first paragraph,** "since a container is never behind the work under it" reads instead "since no container is to stand behind the work under it". The landing rule that sentence gives stands.
  - **In "Moving back from In Progress", its last paragraph,** "The move back moves no other issue: a container may stand ahead of the work under it, never behind it." reads instead: "The move back moves no other issue: a container may stand ahead of the work under it, and is not to stand behind it. A move back checks a container's children alone, so where a child container stands behind the work under it, moving the container back can set it behind work further down."
  - **In its Rationale, the paragraph on a container moved back over a child,** "Refusing that move keeps the cascade's guarantee" reads instead "Refusing that move keeps to the cascade's aim".
- **The narrowing costs a move back something.** Where a child container stands behind the work under it, which the narrowed rule allows, a move back of the container above it, which checks its children alone, can set that container behind work further down, until the child is brought level. Where the board carries the state, no move back is made. Whether a move back checks every issue under the container is left to [project-kit#3247](https://github.com/aleskalfas/project-kit/issues/3247).
- **ADR-074 needs no edit.** Its Boundaries leave the question to a project-management record, and this record keeps its point 5, as ADR-096 refines it.
- **DEC-033 needs no edit.** This record reads its D5 as "Why the later read asks the process engine first" says, within what D5 says, so D5 stands as written.
- **This record rests on ADR-096 for one thing:** its narrowing of ADR-074 point 5 once a command's act is made, on which point 6's first paragraph rests, and point 1's on a run that finds the issue already at its target.
- **The command that moves an issue changes with it, and its tests hold each case the points decide,** in a change that rests on this record once it is accepted. So does each command that writes before it calls a move that could bring a container up.
- **Documents follow, each passage by what it says,** not by the document it sits in:
  - **A passage whose subject is the forward cascade, and which says which ancestors it moves,** carries this record's limit, or sits beside a passage that does. A passage sits beside another in the same section, or as a use case's variant sits beside the step it names.
  - **Such a passage that the capability ships with its commands** changes in the change that builds this record, with the code it ships beside, so that what ships says what the shipped commands do. The workflow schema's account of the forward cascade is such a passage, though DEC-006 names the schema as its rule's encoding, so that encoding changes with the commands rather than with DEC-006's edits.
  - **Any other such passage states the lifecycle's rule,** and changes in this record's change, with the DEC-006 edits, marking what the build has yet to make where its document marks such gaps.
  - **A passage that names the cascade by the effect it is for stands,** such as a view's overview, or a diagram's node, relation or description, though it says that the issues above are brought forward: it leaves which ancestors the cascade moves to DEC-006 and to the passage that tells how it works. So does a passage whose subject is something else, such as a close or one run given as an example.
- **No check finds later a container that stands behind the work under it.** The report is the signal for each ancestor left and each walk ended short of the top, until a later move brings the container level. A container behind with no warning, as one moved back after the first read, has no signal until then. A check that lists such containers is left for later (Alternatives).
- **No migration is owed.** Nothing an adopter holds is renamed, removed or restructured. What the build changes, such as a move refused where a first read gets no answer, the walk going on past an ancestor a read places in none, and the code of a dry run, is a surface change of the capability, declared by a changeset in the change that builds it.
