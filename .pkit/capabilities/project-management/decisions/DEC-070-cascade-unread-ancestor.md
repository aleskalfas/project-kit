**In plain terms:** when an issue moves forward, the forward cascade brings each container above it level with it. It reads where each container stands when it plans its walk, and reads again, just before it would write, each container that first read did not find level. Sometimes the cascade cannot tell where a container stands: its latest read places it in no state, as where the board would not answer for its card at both reads, or where its card has no Status. The move goes ahead all the same. That container is left where it stands, since moving it would act on a guess, and so is one whose write the cascade could not make. The cascade says which containers it left, why, and how to finish. A container left does not end the walk: the cascade goes on to the containers above, each moved only on where its own reads place it, and stops where it reaches the top or cannot tell the next container up, or at an issue that is no container or that it has passed already. Once the move is made, the cascade gives the command no exit code: what it left is a warning beside the move's own result.

## Context

Two accepted rules meet at the forward cascade:

- **No container is to stand behind the work under it.** When an issue moves forward, each ancestor that is behind is brought up to the moved issue's state, capped at In Progress ([project-management:DEC-006-state-machine-and-cascade], "Cascade rule").
- **No command acts on a position it could not read** ([project-management:DEC-051-axis-carriage-activation] point 6). Where the board carries the state, a read of an issue's card that does not place it ends in one of four outcomes: the board cannot be read, the issue has no card, its card has no Status, or its Status names no open state. None falls back to the issue's labels or its Milestone.

At an ancestor the cascade cannot place, the two pull apart. Bringing it level needs its position, and its position cannot be read. The record on a board-carried state leaves which rule gives way to a project-management record ([pkit:ADR-074], Boundaries). Its point 5 holds every command that reads the state to two limits: it never guesses, and it keeps a board that would not answer apart from a finding about the issue. Where a command's exit codes tell a broken tool from a refusal, a board that would not answer takes the broken tool's code.

The record on a board that did not answer ([pkit:ADR-096]) narrows that code once a command's act is made. A command's act, in its terms, is the change the command is run to make, here the issue's move, and what the act sets off on another issue, such as the forward cascade, is no part of it. Once the act is made, the command takes no code that reads as the act not made. That record leaves the cascade to this one, within two limits: no ancestor moves on a position not read, which DEC-051 point 6 already holds, and a move once made takes no code that reads as the move not made.

The question names two options ([project-kit#3204](https://github.com/aleskalfas/project-kit/issues/3204)): the move waits on such an ancestor, or it is made with the walk stopped and reported. This record takes the second, and lets the walk go on past the ancestor rather than stop there (point 4).

Terms:

- **The walk** is the cascade's pass from the moved issue's parent up its hierarchy, one ancestor at a time. It ends at the top, where it cannot tell the next ancestor up, at an issue that is no container, and at one it has passed already.
- **A read of where an ancestor stands** places it in a state or in none.
  - **The walk's first read** of an ancestor places it in none where the board carries the state and the read ends in one of DEC-051 point 6's four outcomes, a board that would not answer among them.
  - **A later read** is made after the move, just before the cascade would write to an ancestor, of each ancestor the first read did not place level: behind the state the cascade brings it up to, or in none. It places the ancestor in none only where it answers so.
  - **A later read that gets no answer is no read,** and the read before it stays the latest. It gets no answer where whatever it asks cannot be reached, and where the answer it gets says that the board or the ancestor's issue could not be read.
- **An ancestor the cascade cannot place** is one the walk reaches whose latest read, before any write to it, places it in no state.

This record does not decide what the cascade does where labels carry the state and an ancestor's label names a value that is no state of the lifecycle.

## Decision

**A forward move is made whatever its cascade finds above it. An ancestor the cascade cannot place is not moved, one whose write is not made is moved no further, and each is reported. An ancestor left does not end the walk, and once the move is made, the cascade takes no exit code.**

### 1. The move does not wait on an ancestor

A forward move is made, or refused, on the moved issue's own reads and gates, never on an ancestor's position. No command refuses or holds a move because an ancestor its cascade will reach cannot be placed, whether the walk finds that before the move or after it.

Where the walk is planned before the move, what it found is shown before the move is confirmed. So a person at a terminal sees which ancestor the first read could not place, and may decline the move.

### 2. An ancestor the cascade cannot place is left where it stands

Nothing is written to it: no state, no Status, no journal entry and no comment. Its position is never guessed: not from its labels or its Milestone where the board carries the state (DEC-051 point 6), and not from an earlier read that a later one placed nowhere. An ancestor the first read could not place is read again before the cascade would write to it, and brought level where that read places it.

### 3. An ancestor whose write is not made is moved no further

A write is not made where it fails, or where what it needs cannot be read, such as the ancestor's issue read again for the write. The steps the ancestor took before that write stand, and so does the move.

### 4. An ancestor left does not end the walk

The walk finds an ancestor's parent from the command's own read of that ancestor's issue, not from the read of where it stands. Each ancestor is brought up to the moved issue's state, capped at In Progress, and never to the state of the ancestor below it, so an ancestor left bears on no move above it. So the walk goes on past it, and each ancestor above is brought level, or left alone, on where its own reads place it.

The walk ends where it reaches the top, or where it cannot tell the next ancestor up, as where the read of an ancestor's issue that it takes the parent from cannot be made: a command that writes on a parent writes nothing on one in doubt, or above it ([pkit:ADR-035] point 5). It ends too at an issue that is no container, which the cascade does not move, and at one it has passed already. A later read of an ancestor's issue, made only for the write to it, leaves the walk as it is, since the parent above was told already.

### 5. The report names each ancestor left, why, and how to finish

The cascade's closing report is a warning. It names each ancestor the cascade left, and the read or the write that left it, and, where the walk ended before the top, where and why. A board that would not answer is named as that, with what the board said, and never as a finding about the ancestor's card, nor a finding as a board that would not answer ([pkit:ADR-074] point 5).

The closure cascade makes an ancestor eligible to close once its last open child closes, wherever the ancestor stands, while DEC-006's table starts that close only at In Progress, so an ancestor left behind can be offered for closing before it is level. The report says how to finish:

- **Where what carries the ancestor's state does not place it as meant,** put that right, such as a card with no Status. Where the board would not answer, wait until it does.
- **Then run the move again** where that finishes the cascade, which moves nothing twice. Where running it again does not finish it, as for an issue that reads Done without a close reported as completed, the next forward move under the ancestor brings it level.
- **Where no forward move is left to come under the ancestor,** as when the moved issue was the last open one under it, move the ancestor on its own once a read places it, before it is closed. That move is asked for directly, so its gates apply: a container in Todo needs scheduling of its own, a Milestone or an audited reason, though the scheduling given on the work under it covered it (DEC-006). The cost falls only where nothing under the container is left to bring it level.
- **Where the ancestor's state is set as a person meant it,** such as a container set outside the lifecycle on purpose, the container stays where it was put, and each forward move under it reports it again.

### 6. Once the move is made, the cascade takes no code

A run that makes the move, or finds the issue already at its target, exits as the move alone has it exit, a dry run of an issue already at its target included. An ancestor the cascade left, for any cause, is a warning beside it, never a code: not a refusal's, not the broken tool's, nor any other. That is within the limit [pkit:ADR-096] point 4 sets once a command's act is made: nothing the act sets off on another issue gives the command a code that reads as the act not made. So each command that composes the move reads the move as made.

A run that ends with the move not made, such as a dry run of a move not yet made or a run declined at the terminal, takes ADR-074 point 5's broken tool's code where the board would not answer for the card of an ancestor it previewed. An ancestor whose card is a finding gives it no code, since a finding would not have held the move (point 1).

## Rationale

**Why the move does not wait.**

- **Waiting brings the ancestor no nearer level.** Where the board would not answer, the ancestor's position is unknown, which is not the same as behind. Where its card is a finding, the ancestor stands in no open state: it is known not to be level, yet it stands nowhere the lifecycle moves from. Either way it cannot be moved without a guess, which DEC-051 point 6 forbids, so a hold on the work under it leaves it as it was.
- **Waiting would give a card a meaning no record gives it.** A container whose card sits in a column outside the lifecycle, such as Blocked, or a container kept off the board, would hold every forward move beneath it. What a card a person places by hand means is a question DEC-006 leaves open, and a hold on the work would answer it by accident. The remedy lies on the ancestor's card, often someone else's, not on the work being moved.
- **Gates are per issue.** The cascade is not an authorisation and asks for none, and each gate governs a move on its own issue (DEC-006). A hold on another issue's card would be a gate nobody set on the move, stopping a move whose own gates passed.
- **Waiting could not hold for every move.** Where a merge or a completed close is made before the move to Done that follows it, nothing is left to hold. A walk planned whole can also be cut short after the move, by a later read that places an ancestor nowhere or a write the board refuses. So a move made with an ancestor reported has to be handled whatever this record decides.

**Why DEC-006's Cascade rule is narrowed here, and not DEC-051's rule.** DEC-006 rejects leaving an ancestor behind and reporting it, where the cascade could move it, because a container behind a started child states something false. Here the cascade cannot move the ancestor without guessing, which DEC-051 point 6 forbids. Moving it on a guess would write a position nobody read, and refusing the move would hold the work on a card. So the Cascade rule keeps its aim, that no container is to stand behind the work under it, and is narrowed to what the cascade can read and write: the container may stand behind the work under it until a later move brings it level. The narrowing accepts more than an unknown: where the ancestor's card is a finding, the container is known not to be level, and stays so until its card is set right or a record decides what such a card means. The rule is narrowed the same way at an ancestor whose write is not made: the move is made by then, and only a write made again can bring the ancestor level.

**Why the walk goes on.** The parent comes from the read of the ancestor's issue, which was made: only its position was not read. The state each ancestor is brought up to does not depend on the one below, so an ancestor above, brought level on its own reads, moves on a position that was read. A container ahead of the one below it is a state DEC-006 allows, since a container may stand ahead of the work under it. Stopping the walk would leave every container above behind, for a fault on one card. An ancestor whose write failed is passed the same way, for the same reason. The walk ends where the next ancestor up cannot be told, since a write on a parent in doubt could move a container the moved issue is not under. It ends too at an issue that is no container, which the cascade never moves, and at one it has passed already, where going on would walk in a circle.

**Why the latest read decides, on every substrate.** The cascade writes from the latest answer it has about an ancestor. A later read that answers outweighs an earlier one, whatever it says: where it places the ancestor elsewhere, the cascade writes from it, and where it places the ancestor nowhere, writing from the earlier read would move the ancestor from a position its latest read does not give, wherever the state lives. Any read may have gone stale by the time its write lands, which holds of every write the cascade makes, so staleness tells the reads apart in neither direction: the latest answer is the best the cascade has.

**Why a later read that passes on a failure is no answer.** A read is an answer only where the board, or the ancestor's issue, answered it. Whatever passes on that the board or the issue could not be read gives no position of its own, so the cascade has learnt nothing since the read before. Where that read placed the ancestor, writing from it guesses nothing, and where it placed it nowhere, the ancestor is left. Taking such a read for one that places the ancestor nowhere would leave an ancestor the read before had placed, for a failure that says nothing of where it stands.

**Why the later read is made of an ancestor the first could not place.** A board that would not answer for an ancestor's card when the walk was planned may answer by the write, and a card set right in between places the ancestor. Leaving the ancestor on the first read alone would leave one the cascade could bring level, and the read costs what the read before each write already costs. An ancestor the first read places level is not read again, so a move under ancestors already level costs one read of each.

**Why nothing is written to the ancestor.** A notice on it would repeat on every forward move under a container set outside the lifecycle on purpose, or need a key to post it once that a later change of the card would have to reset. The report reaches whoever runs the move, where the move's own outcome is read. The report repeats too: each forward move under such a container names it again, a warning that recurs until the card changes or a record decides what such a card means, and that readers may learn to pass over. That cost falls on the output of the moves under the container, and on no issue.

**Why no code once the move is made, and ADR-074's code before it.** Commands compose the move and hand on, or act on, its code: a start of work reads a non-zero code as a failed start, and a merge or a close as a step to run again. After the move, a code for the cascade would tell them that a move that was made was not, or need each of them to learn a new code for a state the report already says. Before the move, nothing is made that a code could misreport. The cascade reads each ancestor's state, so ADR-074 point 5 binds those reads, and gives a board that would not answer the broken tool's code until the act is made. A dry run makes no move, nor does a run declined at the terminal, so each takes that code where the board would not answer for an ancestor's card. A finding about the card is no broken tool, and would not have held the move, so it takes none. This record takes the code only where ADR-074 point 5 asks for it: what else a preview may leave unread, such as an ancestor's issue, keeps the code the command gives it. A dry run of an issue already at its target previews a move an earlier run made, so it takes no code for the cascade, as the run would not. The costs: a caller reading only the exit code of a move made learns nothing of an ancestor left behind, and where the board would not answer for an ancestor's card, a dry run exits with a code its run would not take. The warning is in the command's output, as it is for a cascade cut short by a failed write.

### Alternatives considered

- **The move waits: it refuses, writing nothing, where an ancestor its walk will reach cannot be placed.** The case: no move it lets through leaves a container behind the work under it, and the walk can be planned before the move, so the refusal costs no read. Rejected: it holds the work under a container on that container's card, for a position that may not be behind, and it cannot hold where a merge or a close is made before the move.
- **Wait only where the board cannot be read, and go on where the card is a finding.** The case: a board that would not answer is a broken tool, and a broken tool stops what rests on it, while an outage is likely brief. Rejected: the move rests on its own reads, which the board answered, and nothing the move needs rests on the ancestor's read.
- **Stop the walk at the ancestor, and report where it stopped.** The case: one line names where the walk ended, and a fault that left one card unread likely reaches the cards above it too. Rejected: the containers above are left behind though each could be read and brought level, and going on costs at most a few reads, bounded by the hierarchy's depth.
- **Stop the walk only where the board cannot be read, and go on past a finding about one card.** The case: an outage likely reaches every card above, and going on sends more calls to a board already failing, with one line in the report for each. Rejected: the calls are bounded by the hierarchy's depth, and a board that failed on one card may answer for the next.
- **Read again before the write only an ancestor the first read placed behind, and leave one it placed nowhere on that read.** The case: the preview then says for certain which ancestor the run leaves. Rejected: an ancestor a brief failure left unplaced at the plan would be left though the cascade could place it by the write (see "Why the later read is made of an ancestor the first could not place").
- **Take a later read that passes on a board or an issue that could not be read as placing the ancestor nowhere.** The case: whatever the later read asks did answer, and its answer gives no position. Rejected: the failure says nothing of where the ancestor stands, and leaving an ancestor the read before had placed would leave one the cascade could bring level (see "Why a later read that passes on a failure is no answer").
- **Retry, within the run, a read of an ancestor that got no answer.** The case: a brief outage would pass, and the cascade would finish in one run. Rejected here: a retry belongs in the board's read seam, which every read of the board goes through ([pkit:ADR-053]) and where it would serve every command alike. The later read reads again, just before the write, each ancestor the first read could not place, and running the move again, which the report asks for once the board answers, is the retry.
- **Move the ancestor on its labels or its Milestone where the board does not place it.** Rejected by DEC-051 point 6: the cascade would act on a position it guessed.
- **Write In Progress, at the cap, to an ancestor whose card has no Status or that has no card.** The case: no open container stands past In Progress, so the write could never move it backward, and a guess is weakest here, since the value written does not depend on where the ancestor stood. Rejected: the write would follow no transition the schema declares, from a state no read gave, so a journal would record a step from nowhere, and an ancestor that stood in Todo would read as started without having been scheduled, which DEC-006 rejects for containers. A missing card is also the board's membership to repair ([project-management:DEC-019-mandatory-issue-state]), which the cascade does not write. The remedy costs little: set the Status, and the move made again brings the ancestor level.
- **Post a notice on the ancestor, or on the moved issue, so whoever can repair the card learns of it.** The case: the report reaches the mover, often an agent, while the card is often someone else's, and no check finds the container later. Rejected: see "Why nothing is written to the ancestor".
- **Record in the moved issue's journal that its cascade was cut short.** The case: an entry is no comment, so it repeats nowhere, and it outlasts the run's output. Rejected: the journal holds an issue's governed moves ([project-management:DEC-049-audit-journal-model]), and a cascade cut short is no move of the moved issue. Nothing reads such an entry to act on it, it goes stale once a later move brings the ancestor level, and a project that keeps no journal would record nothing.
- **A check, run apart from any move, that lists each container behind the work under it.** The case: it writes nothing and needs no key, so the objections to a notice do not reach it. It finds a container left behind whoever ran the move and whatever became of the report, and it finds containers left behind for other causes too, such as a walk that ended at a parent in doubt. Not taken here, and left to [project-kit#3246](https://github.com/aleskalfas/project-kit/issues/3246): it checks the whole hierarchy rather than act at one move, and where it runs, what it reads and how it reports are choices of their own.
- **No run takes a code for the cascade, not a dry run nor a run declined at the terminal.** The case: one code for every run whatever the cascade found, and a decline reports the person's choice, not a read. Rejected: neither run makes a move, so ADR-074 point 5 gives a board that would not answer for an ancestor's card the broken tool's code, and taking none would need that point narrowed again, for runs where nothing is made that a code could misreport.
- **A code of its own for a move made with its cascade cut short.** The case: a caller reading only the code would learn of the ancestor left, and ADR-096 point 4 lets a code that asks for a run again stand where a run again makes nothing twice. Rejected: every composing command would have to learn it, or would read it as the move not made, for a state the report says.

## Implications

- **DEC-006 is refined in place on this record's acceptance,** by the edits below, each carrying the pointer "(refinement per [project-management:DEC-070-cascade-unread-ancestor])". The first two narrow its Cascade rule to the ancestors the cascade can read and write. The other three restate as an aim DEC-006's claim that no container stands behind the work under it, where the move back rests on it, and name where a move back can leave a container behind:
  - **In its Cascade rule, the forward-cascade bullet,** the sentence "A container is never behind the work under it: when an issue moves forward, … capped at In Progress." reads instead: "No container is to stand behind the work under it: when an issue moves forward, the agent walks its ancestors — its parent, that parent's parent, and so on up — and brings each one it reaches that is behind up to the moved issue's state, capped at In Progress, wherever it can read where that ancestor stands and write to it. It moves an ancestor only from where its latest read of that ancestor places it, and never backward: an ancestor that read places in no state is left where it stands, and one whose write is not made is moved no further. The cascade names each ancestor it leaves behind, and the move stands all the same. An ancestor left does not end the walk. The walk ends at the top, where it cannot tell the next ancestor up, at an issue that is no container, and at one it has passed already, and the cascade names any end short of the top."
  - **In its Alternatives considered,** the bullet "Refuse to start a child whose ancestor is unscheduled, or leave the ancestor behind and report it" gains: "Leaving an ancestor that the walk reaches behind is rejected wherever the cascade can read where it stands and write to it. One its latest read places in no state, or whose write is not made, is left and named, and the child's move is never refused for it."
  - **In "Moving back from In Progress", its first paragraph,** "since a container is never behind the work under it" reads instead "since no container is to stand behind the work under it". The landing rule that sentence gives stands.
  - **In "Moving back from In Progress", its last paragraph,** "The move back moves no other issue: a container may stand ahead of the work under it, never behind it." reads instead: "The move back moves no other issue: a container may stand ahead of the work under it, and is not to stand behind it. A move back checks a container's children alone, so where the forward cascade left a child container behind, it can leave the container behind work further down."
  - **In its Rationale, the paragraph on a container moved back over a child,** "Refusing that move keeps the cascade's guarantee" reads instead "Refusing that move keeps to the cascade's aim".
  - **Checked to agree, and standing as written:**
    - **Which moves run the forward cascade, and on what ground.** The refined Cascade rule says which ancestors the cascade moves, so these stand: the Cascade rule's sentence on a completed close, the `manual-completed` trigger's account of its cascade, the Rationale's "a container behind its descendants is brought level, not moved on anyone's say-so", its paragraph on why a completed close brings its ancestors level, the rejected "Let a completed close from Todo or Backlog move no ancestor", and the Implications' bullet on the cascade check the project-manager runs.
    - **The Implications' open question on a card a person drags by hand,** and whether a cascade reconciles such a move on its own. This record decides only what the cascade does at a card it cannot place, which DEC-051 point 6 forces. A card dragged to an open state is placed, and that question stays open.
- **The narrowing costs a move back something.** A move back keeps a container level with all the work under it only where each child container is level with the work under that child. Where the forward cascade left a child container behind, the container's move back can leave it behind work further down. Where the board carries the state, no move back is made, so the cost does not arise there. It lasts until the child is brought level (point 5). Whether a move back checks every issue under the container is left to [project-kit#3247](https://github.com/aleskalfas/project-kit/issues/3247).
- **ADR-074 needs no edit.** Its Boundaries leave the question to a project-management record, and this record keeps its point 5, as ADR-096 refines it.
- **This record rests on ADR-096 for one thing:** its narrowing of ADR-074 point 5 once a command's act is made, on which point 6's first paragraph rests.
- **The command that moves an issue changes with it,** in a change that rests on this record once it is accepted:
  - the walk goes on past an ancestor it cannot place, whichever read left it unplaced, until one of its ends;
  - an ancestor the first read could not place is read again just before the cascade would write to it, and brought level where that read places it;
  - a later read whose answer says the board or the ancestor's issue could not be read is no read, so the cascade writes from the read before it where that read placed the ancestor. Whatever answers the later read tells a position it could not evaluate from one it placed nowhere, so the build can keep the two apart;
  - the preview names each ancestor the first read could not place, and says the run reads it again, not that the walk stops;
  - the report gives the way to finish for every ancestor it left;
  - a dry run of a move not yet made, and a run declined at the terminal, take the broken tool's code where the board would not answer for an ancestor's card.

  A move made, and the code of a run that makes it, stay as they are. So do the codes of a run on an issue already at its target, a dry run of one included.
- **Tests hold each case:**
  - a walk that goes on past an ancestor its plan leaves unplaced, past one a later read places nowhere, and past one whose write failed or whose issue could not be read again for the write;
  - an ancestor the plan leaves unplaced, brought level where the later read places it;
  - a later read whose answer says the board or the issue could not be read, the ancestor written from the read before it where that read placed it, and left where it did not;
  - each end of the walk: where the read it takes a parent from cannot be made, at an issue that is no container, and at one it has passed already;
  - a report that is a warning wherever an ancestor is left, never a clean one;
  - the preview's words for an ancestor the first read could not place, and the report's ways to finish for one that was left;
  - a board that would not answer for an ancestor, reported apart from a finding about its card;
  - the code of a move made, unchanged by an ancestor left, and the codes of a dry run and of a declined run, for a board that would not answer for an ancestor's card and for a finding;
  - the code of a dry run on an issue already at its target, unchanged by an ancestor the board would not answer for;
  - a command that composes the move, such as the start of work, reading the move as made.
- **Documents follow:**
  - **A document that anchors DEC-006 and states, as a rule of its own, which ancestors the forward cascade moves** changes in this record's change with the DEC-006 edits, where it states that rule without the limit this record sets. A definition that names the cascade by its effect, and a passage that tells of the cascade while it tells of something else, such as a close, stand: which ancestors the cascade moves is DEC-006's to say.
  - **Documents that describe the command that moves an issue,** the capability's README among them, follow the change that builds it.
- **No check finds a container left behind later.** The report is the signal, and the next forward move under the container, or the move made again, brings it level once a read places it. A check that lists the containers behind the work under them is left for later (Alternatives).
- **No migration is owed.** Nothing an adopter holds is renamed, removed or restructured. What the build changes, such as the walk going on past an ancestor the cascade cannot place, and the codes of a dry run and of a declined run, is a surface change of the capability, declared by a changeset in the change that builds it.
