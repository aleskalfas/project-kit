id: DEC-076
title: The account a credential acts as is the actor of each act the commands record, and under a credential that names no user's account it never acts or counts as a person
status: proposed
date: 2026-11-13
author: Aleš Kalfas <kalfas.ales@gmail.com>
---

**In plain terms:** an agent may reach GitHub under a credential that names no user's account, such as a GitHub App installation's token or a CI workflow's. GitHub will not look such an account up as a user, and refuses it as an assignee.

Wherever GitHub does not answer that the credential acts as a user's account, because it answers that the account is an app's, or gives no answer, this capability's commands take no person's identity for the account they act as, in a CI workflow and in an agent's session alike, and no comment the commands post names a person as its authoriser. Where GitHub answers with a user's account, the record on the membership gate already takes that account alone as whoever runs a command, and nothing stands beside it (DEC-021, "Identity resolution").

Under every credential, each act the commands record, a move or another such as a merge by bypass, has one actor, the account GitHub answers the credential acts as. For a move, the engine's check that a merge came from someone else judges it and the journal records it. No comment the commands post names an authoriser beside that account, by name or by email. No value that stands beside that account, such as the person the agent works for, takes its place. Where GitHub gives no login for the account, there is no actor, and the commands refuse a move whose gate needs one, such as the move to Done, until the backbone decides what its engine takes in its place.

The person the agent works for, which the session names, serves only where naming a person grants nothing: as the default assignee, to keep the agent off a Task assigned to someone else, and in a view of the work assigned to whoever runs it. In every project, under every credential, nothing an account GitHub records as a bot writes counts as a person's approval, or as a person's claim on work wherever a claim's author is read, and no approval counts from an account the project registers as a reviewer agent's where a person's is required.

What a person accepting this weighs:

- **No instance ownership.** A clone under such a credential claims no Task, and under an unresolved identity a clone that holds an instance id refuses. In a project with a topology it builds nothing, and takes a planner's seat only where the membership gate is closed and its account is a member. Elsewhere two sessions under one such credential can start the same Task unseen, and a person's own clones read a Task such a clone started for that person as nobody's. Whatever instance id it holds, it is kept off a Task an instance owns, which overturns part of the record on instance ownership (DEC-035).
- **Bots approve nothing in human mode.** In every project, an approval from an account GitHub records as a bot, or one the project registers as a reviewer agent's, does not count where a person's approval is required. This narrows who may approve in the records on the work's lifecycle and on review modes (DEC-026, DEC-027).
- **No answer, no person, under every credential.** Where the service gives no answer about which account a credential acts as, such as with no network, on a timeout, or on a refusal for another cause than what the credential is, such as a rate limit, the identity is unresolved, a person's own credential included. Neither git's email nor `PM_INVOKER_LOGIN` stands in for it at the membership gate, which the gate's record (DEC-021) lets match either there, so that part of it is overturned under every credential. Every command that takes the gate or names who runs it asks GitHub which account it acts as, the variable set or not. Where it learns no login for the account, its acts name no actor (point 9), and the audit record and the journal entry of such an act hold an empty actor, which overturns the parts of the records on the audit facility (DEC-044) and on the audit journal (DEC-049) that give every actor a value. So where an installation's token gets no login, with the variable set as on the trial, its moves name no actor where today they name the variable's person, and a move into a state whose gate is an authorisation artifact, such as Done, refuses until the backbone decides what its engine's gate takes where a command hands it no actor. Today the engine takes `operator` there, which its gate passes on any merge, the agent's own among them.
- **A user's credential keeps DEC-021's membership identity.** Where GitHub answers with a user's account, such as a machine user's or another person's, this record changes nothing in the identity the membership gate checks, which DEC-021 takes as that account's login alone, so `PM_INVOKER_LOGIN` set to the person names nobody the commands take there ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)). The variable's documentation tells a setup to leave it unset under a user's credential that is not the person's own.
- **One actor for each act, under every credential.** The actor of a move, a merge by bypass or another act the commands record is the account GitHub answers the credential acts as, never a value that stands beside it, such as the variable or the person the agent works for: the engine's gate judges a move's, the journal records it, and no comment names another authoriser (point 9). Under a user's credential, a machine user's among them, DEC-021 already takes that account for every reader of the invoker's identity, the actor its moves hand the engine among them, whatever the variable names, so a move to Done after that account's own merge is refused, as a person's own merge is. What this record adds there is that its audit comments name no authoriser beside that account, by name or by email.
- **Closed-mode CI changes, overturning part of DEC-021.** A workflow under its own token passes a closed membership gate, on a command that takes it, only where its account is a member, and neither the variable nor git's email stands for it. A command that only reads and reports takes no gate (DEC-073), so a workflow that runs only such commands needs neither an entry in the member list nor the variable, and this record's change to the variable is built only after DEC-073 is. Whether the service names such a token's account is unmeasured. Until it is, such a workflow's only way through may be a credential that names a user's account. A workflow under a machine user's token with the variable set refuses wherever GitHub gives no answer, since the variable stands for no account GitHub did not answer for.
- **A member that admits every session.** A project that adds an app's account as a member admits every session under that credential, one that works for a non-member among them, as DEC-021 admits every session under a member's own credential, whoever it works for.
- **No audit comment names an authoriser, overturning parts of four records (DEC-014, DEC-044, DEC-050, DEC-052).** Under every credential, the account the credential acts as posts an audit comment and is its act's actor, and the comment names no authoriser beside it, by name or by email. Where DEC-052 keeps an authoriser on a comment another account posts, such as the person a workflow's `PM_INVOKER_LOGIN` names, the comment names none, and a reason the caller gives may report that person's word. So the comments of a bypass and of an override of a reviewer lose the name and the email their templates give the authoriser (DEC-014, DEC-050), the metadata line of each comment's default render shows no actor (DEC-044), and the comment a person's word at a terminal leaves shows who named the head through the account that posts it, as the record on such heads has it (DEC-067). This reaches every project, since the commands put a name and an email on those comments today.
- **An agent's local verdict names no person.** A reviewer agent's verdict posted on the local path attests only what the acting account ran, until the record on who may authorise in an agent's turn exists.
- **The caller's word stays unguarded.** A bypass, a refusal overridden by `--force`, a held move, a release by force and an authorisation to merge given up front each pass on the caller's word, as under any credential. Of the refusals this record adds, only the clash guard's is overridden, by a reason. Who may give that word in an agent's turn is a record of its own.
- **Building waits on where the reading lives.** This record says what the commands need of the reading of the acting account. The backbone reads that account too, so where the reading lives is a record of its own. What reads the acting account is built only once a person accepts that record. The spelling of an account that record settles also decides whether the entries of the member lists projects hold need rewriting, and how a bare entry that names an app's account is treated. Point 5's guards on an author's kind read no acting account, and may be built first, each in the change that moves its read of authors to a surface that gives their kind (point 2), so that none holds a claim, or refuses an approval, only because the read it was built on drops the kind. The human-mode guard's check of an approver against the accounts the project registers as reviewer agents' compares two accounts, and so is built on the one function beside the reading.

Each record this overturns in part stays accepted, and its top line names what this record overturns there. Each passage it narrows, widens or completes is refined in place, and a fact it makes false, where a passage's rule stands, is corrected there.

## Context

**The terms.**

Asking the hosting service which account a credential acts as has three outcomes, as [project-management:DEC-073-reads-take-no-gate] point 2 tells them apart:

- **A credential names a user's account** where the service answers with a user's account.
- **An app's credential** is one for which the service answers that its account is no user's: it answers with an app's account and gives its login, or it refuses the request for the account because the credential is an integration's, which it tells by its status and words and which gives no login.
- **An unresolved identity** is the outcome where the service gives no answer about who the credential is: the request did not reach it or ran out of time, as with no network, something other than the service answered, such as a proxy, the service failed, it refused the credential itself as one it does not accept, as it refuses a person's token revoked or expired, or it refused the request for another cause than what the credential is, such as a rate limit. The commands report it with its cause ([project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162)). A person's own credential leaves the identity unresolved wherever the service gives no answer for it. Without the service's answer, the commands cannot tell an app's credential from a person's.
- **A credential names no user's account,** in this record as in DEC-073, wherever the service does not answer that it acts as a user's account: where it is an app's credential, and where it leaves the identity unresolved.
- **An app's account** is the account an app's credential acts as. Every session that holds the credential acts as it.
- **The commands know no acting account** under an app's credential whose login the service does not give, where they know only that no person acts, and under an unresolved identity.
- **A bot's account** is one the service records as a bot, as it records an app's account.
- **A user account kept for an agent,** a machine user, is a user's account, which the service records as no bot. Its credential names a user's account, so where the service answers for it, this record reaches it only as it reaches every credential: as each act's actor (point 9), through the one spelling and the hold on a claim a missing kind leaves unjudged (point 2), and, where the project registers it as a reviewer agent's, through the guard on an approval in human mode (point 5). Beside it, DEC-021 takes the login the service answers alone, and `PM_INVOKER_LOGIN` stands neither beside it nor in its place at the membership gate (point 3). Where the service gives no answer, its identity is unresolved like any other.
- **The person the agent works for** is the person whose work an agent's session does, or a workflow's run where no agent runs in it, as the session or the run names them (point 3).
- **The setup** is what prepares the machine and starts the agent's session or the workflow, outside this capability.

**What happens today.** On a trial of software that starts agent sessions on hosted machines, an agent reached GitHub under an App installation's token ([project-kit#3004](https://github.com/aleskalfas/project-kit/issues/3004)). The commands resolve the acting account by looking it up as a user ([project-management:DEC-021-team-membership-gate], "Identity resolution"), and the service refuses the lookup as an integration's, `Resource not accessible by integration (HTTP 403)` ([project-kit#3164](https://github.com/aleskalfas/project-kit/issues/3164)):

- **No default assignee.** `create-issue` cannot default the assignee to the filer ([project-management:DEC-019-mandatory-issue-state], "Mandatory assignment").
- **Every assignee is someone else.** `start-work` refuses every Task assigned to the person the agent works for, and sends it to `handoff-issue`, which cannot help ([project-management:DEC-026-work-ownership-lifecycle]).
- **A workaround.** The trial went on by unassigning the person, starting the work, and assigning the person back.
- **The engine's gate takes the person as the actor.** Where `PM_INVOKER_LOGIN` names the person, the commands hand that person to the engine's cross-authority gate as the actor of each move, so the agent's own merge reads as another authority's.
- **Without a login, the engine's gate takes a placeholder, and passes.** Where the commands resolve no login, they hand the engine no actor. The engine then asks the service for the user itself, which refuses an installation's token as it refuses the commands, and takes `operator` as the actor. Its cross-authority gate passes wherever the account that merged is not named `operator`, so the agent's own merge passes it, and the journal records `operator` as the move's actor.

[project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162) has the commands report an identity they cannot resolve, with its cause. How they act under such a credential is this record's.

**What was measured** on the trial ([project-kit#3164](https://github.com/aleskalfas/project-kit/issues/3164)):

- **The setup offers a credential that names the person's account.** It can grant the agent an OAuth sign-in or a personal access token beside the App's. Neither was granted to the trial's agent, so no command has run under one.
- **An app's account is spelled differently on different surfaces.** Read under the person's credential, the comments the trial's App wrote give its login with a `[bot]` suffix and the type `Bot`, and name the App that performed each write. gh's JSON gives the same account, on its pull requests, with an `app/` prefix, marked as a bot.
- **An App installation's token sees none of a user's boards.** Asked for the boards of the person's account, it answered with none, a public one included, and no error. The person's own token saw three.

**What was not measured:**

- **Whether an installation's token, a workflow's among them, can learn its own account's login.** The refusal of the lookup as a user says that the credential is an integration's, and gives no login. Both attempts to ask otherwise from inside the trial's agent failed before reaching the service. Point 1 says what holds without it.
- **Whether the service answers an app's account's write access to a repository, and gives every reader the same answer,** which an open project's state issues read (point 7).
- **Whether a person's sign-in through a host's app marks the agent's writes as that app's.**

**What the records already say.**

- **The membership gate reads the account `gh api user` gives first,** git's email second, as a fallback "when `gh` is unavailable", and `PM_INVOKER_LOGIN` third, where those natural sources do not apply (DEC-021, "Identity resolution"). The service refuses that request to an installation's token. Where the service answers that the credential acts as a user's account, that account's login alone is the invoker's identity, for the gate and for every other reader of it, and neither git's email nor the variable stands beside it or in its place. Where the service does not answer so, a match at the gate on any of them passes. DEC-021 reserves the variable for CI and agent contexts, "sourced from a CI secret or workflow input, never from user-controllable env". Of that case, whether the service "answers with an app's account, refuses, or cannot be asked", its Rationale says "this record decides there only the match on any surface", and that "whether git's email and the variable should name the invoker there rests on evidence of its own", citing this record's issue ("Why a user's login the hosting service answers stands alone"). Its Implications let a CI workflow whose credential the service does not answer for as a user's account pass the gate by setting the variable from a CI secret, and have the commands refuse an agent that works for a non-member where the identity the gate reads is no member's. A command that only reads and reports takes no gate ([project-management:DEC-073-reads-take-no-gate]), so [project-management:DEC-022-methodology-mesh]'s scheduled workflow needs neither an entry in the member list nor the variable while its check only reads and reports ("Authority"). The commands cannot tell where the variable was set.
- **A clone with no instance id behaves as if instance ownership were not there,** with no guard, and the id is the sole activation gate ([project-management:DEC-035-instance-ownership] point 1).
- **A claim on an issue of work counts only from the assignee's account** ([project-management:DEC-043-ownership-substrate-selection] point 3). The ownership fold applies that filter in one place ([pkit:ADR-041]).
- **A gate's authorisation comes from another authority than the actor it gates** ([pkit:COR-033] P4). The engine's cross-authority gate compares the actor a command hands it with the account this capability's predicate reports as having merged the pull request. What the gate takes as its actor where a command hands it none is the backbone's to decide, and today it takes `operator` (above).
- **In human mode, the gate passes on an approving review or an `Approved` comment from any non-author identity,** and the members whose role matches, but the author, are assigned as reviewers ([project-management:DEC-027-review-modes], "Human path"). DEC-026's tables count the comment from a commenter other than the author, and its Rationale ("Why the three-way OR") from the last commenter that is no bot. The commands count it from any commenter but the author, a bot among them.
- **A comment names who authorised an act** only where they differ from the account that posted it, and the actor is taken for the authoriser ([project-management:DEC-049-audit-journal-model] point 4). [project-management:DEC-052-comment-house-style] keeps the authoriser on the bot-authored path, where another account than the authoriser posts the comment. [project-management:DEC-014-validation-severity-model]'s audit-comment template names the authoriser by name and email, `Bypassed by <name> <<email>>: <reason>`, as [project-management:DEC-050-per-reviewer-override] point 4 names the operator of an override of a reviewer. The commands fill the name with the identity the membership gate checks, and the email with git's configured email, on each comment they render from that template. [project-management:DEC-055-pr-lists-answers] point 3 has the comment of a `--force` on the move to review name who gave it, and [project-management:DEC-067-heads-that-start-programs] point 4 has the comment a person's word at a terminal leaves name who named the head. The commands render both from that template too. [project-management:DEC-044-audit-log-facility] point 1 gives every audit record an `actor`, its "login + display name; email where the source has it".

**A rule held provisionally.** project-kit's own record on agent hosts holds that a need that differs between machines is met by reading a property, never a host's name, that a need not worth meeting is a limit, stated by its property with what meeting it would cost, and that a setup uses pkit's public surface as any adopter does, and its choices are its own ([pkit:ADR-091] points 2 and 4, and the first three bullets of its point 7). It holds those rules provisionally, and they reach no adopter as rules, so this record states for itself what it takes from them (points 1, 3 and 8).

## Decision

**Where the hosting service does not answer that a credential acts as a user's account, the commands take no person's identity for the account they act as, and no comment names a person as its authoriser. In every project, nothing an account the service records as a bot writes counts as a person's approval, or as a person's claim wherever a claim's author is read, and no approval counts from an account the project registers as a reviewer agent's where a person's is required. The person the agent works for serves only where naming a person grants nothing. Under every credential, each act the commands record has one actor, the account the service answers the credential acts as, beside which no comment names an authoriser, and which, for a move, the engine's cross-authority gate judges and the journal records. There is none where the commands know no acting account, and there a move into a state whose gate is an authorisation artifact refuses.**

Where the service answers with a user's account, this record changes nothing in the identity the membership gate checks, which DEC-021 takes as that account's login alone, neither git's email nor `PM_INVOKER_LOGIN` standing beside it or in its place ("Identity resolution"). Each act's actor is no part of that identity: point 9 decides it, under every credential.

### 1. The commands read a credential's kind from the service's answer

- **One reading.** Which account a credential acts as, and of which kind, is read once from the hosting service, and every command of this capability takes it from that reading. The backbone reads the acting account too, so where the reading lives is a record of its own (Implications, "First, where the reading lives"). This record decides what the commands need of it.
- **An app's, only from the service's answer.** A credential is an app's only where the hosting service answers, for the credential, that its account is no user's: with an app's account and its login, or by refusing the request for the account because the credential is an integration's, which it tells by its status and words, as [project-management:DEC-073-reads-take-no-gate] point 2 reads it, and which gives no login. DEC-021's first source, `gh api user`, gets that refusal for an installation's token, so the app's login comes only from another request, which the record on where the reading lives names, and this record widens DEC-021's first source to it (Implications). A credential is never read as an app's from a refusal for another cause, such as a rate limit, a suspended account or a network's rule. Nor is it read from the credential's own form (Alternatives), or from the host or the tool that issued the credential, whose names say nothing of the account and may change without notice.
- **No answer leaves the identity unresolved,** under every credential, and the commands act on it as on an app's credential with no account they know. They never fall back to a value that names a person. Without the service's answer they cannot tell an app's credential from a person's, and a fallback would let an app's credential act as a person whenever its lookup fails. So a refusal for another cause than what the credential is, a timeout, a failure of the secure connection and a proxy's error all leave the identity unresolved, and only the cause the commands report differs. Whether an earlier answer the service gave for the same credential, kept on the machine, counts as its answer is the record on where the reading lives to decide.
- **Only a grant and an act's actor need the app's own account.** The membership gate (point 2) and a seat's claim (point 7) read the app's login, since they grant the acting account something, and each act's actor is that account (point 9). Everything else this record decides holds under an app's credential whose login the service does not give, and under an unresolved identity too, except that where the commands know no acting account an act names no actor, and a move into a state whose gate is an authorisation artifact refuses (point 9), and that under an unresolved identity a clone that holds an instance id refuses (point 4). So in this capability's own guards an answer misread grants nothing, and never lets a person's identity stand for the acting account. The engine's cross-authority gate is the backbone's, and point 9 says what the commands hand it.
- **Each guard reads the property it rests on:** the credential's answer for the acting account, and the service's record of an author for what that author wrote (point 5). The credential's kind is a fact of the session, read where the commands act. An author's kind is the same wherever it is read, so the guards that read it hold alike on every machine.

Whether an installation's token receives an answer that gives its login is unmeasured. Under the request DEC-021 names, it receives the integration's refusal, as on the trial (Context). Where it gets no login, it is an app's credential whose account the commands do not know: everything below holds, except that its account can be neither a member (point 2) nor a seat's holder (point 7), and its acts name no actor, so its moves into a state whose gate is an authorisation artifact refuse (point 9). A clone under it that holds an instance id goes on as an app's clone does (point 4), since the service's answer tells that no person acts.

### 2. No person stands for the acting account

Under every credential:

- **One spelling, which keeps the account's kind.** Every comparison of two accounts puts both in one spelling, through one function beside the reading (point 1), whichever surface named each, reading each account's kind from a surface that gives it. The spelling keeps whether the account is a bot's, so a bot's account and a user's never compare equal, though the service lets an app take its owner's own name. So no comparison spells an account its own way, as no command reads the labels its own way ([pkit:ADR-026]). Where no surface gives a kind the comparison turns on, it grants nothing and frees nothing: no account passes on it as a member, an approver or another authority, and a claim it cannot judge is held, in every project. The ownership fold reports such a claim on an issue of work as one it cannot judge, which no consumer treats as free and the clash guard reads as one that counts. A state issue's read is left incomplete by it, as by a call that fails ([pkit:ADR-071] point 3). The edits this record makes to the records of those two seams state both (Implications).
- **An app's account in the member list is no person.** Each member's login is kept in the one spelling, its kind included. So a command that picks members as people, such as reviewers in human mode, tells an app's entry apart and passes over it.

Under a credential that names no user's account, in a CI workflow and in an agent's session alike:

- **The acting account** is the app's, by the login the service gives it. Where the service gives none, the commands know no acting account.
- **Git's configured email does not stand for it.** The email names whoever set up git on the machine, a person the credential does not act as, or one the commands cannot tell it acts as.
- **Nor does `PM_INVOKER_LOGIN`.** Whoever starts the run or the session can set it, and the commands cannot tell who did. It names the person the agent works for (point 3).
- **The closed membership gate** matches an app's account by its own login, in the one spelling, with no person's login beside it. A project lets such an account act by adding it as a member. That admits every session that holds the credential, whoever starts it and for whomever it works, a non-member among them, and the project decides so by adding it.
- **The member list changes under no such credential.** Membership grants authority, and an app's account, or one the commands do not know, has no person to stand behind a change to it. So a command that adds or removes a member refuses, and a person changes the list under their own credential. This holds while the gate is open too, where adding such an account as the first member would close the gate with no person in it.

Where the service answers with a user's account, this record changes nothing in the identity the membership gate checks, which DEC-021 takes as that account's login alone, whatever git's email and the variable name. Where the service gives no answer, under any credential, the identity is unresolved, and everything above holds for it.

### 3. The person the agent works for serves only where naming a person grants nothing

- **Where it comes from.** Under a credential that names no user's account, `PM_INVOKER_LOGIN` names the person the agent works for. The variable is an input of the commands, documented with them, so its meaning is part of their public surface, which a setup uses as any adopter does ([pkit:ADR-091] point 7). One function of this capability reads it, for every command that needs that person.
- **Beside a user's account.** Where the service answers with a user's account, the variable is no identity: DEC-021 takes that account's login alone, for the membership gate and for every other reader of the invoker's identity, and never a person the variable names in its place. Under a user's credential that is not the person's own, such as a machine user's, the variable set to the person names nobody the commands take, neither the identity the gate checks nor an act's actor (point 9). So its documentation tells a setup to leave it unset there.
- **Where it serves.** It stands where the commands would name the acting account as a person, and grant nothing by doing so:
  - the default assignee at filing, and `--me` on an assignment, held like any assignee to a member where the gate is closed (DEC-019);
  - `start-work`'s refusal of a Task assigned to someone else, and the assignee it writes (point 4);
  - which Tasks `next-task` hands out, since it hands out only what `start-work` takes;
  - a report of the work assigned to whoever runs it, which a command that only reads and reports makes ([project-management:DEC-073-reads-take-no-gate] point 2): it reports the work assigned to that person, since the acting account is nobody's assignee. A listing's `mine` stays the clone's own claims (DEC-035 point 7), and such a clone has none (point 5).
- **Where it never serves.** It never stands where naming a person grants: the membership gate, a claim, an approval, or the authoriser a comment names. So `--me` on a command that changes the member list refuses (point 2). Nor does it tell whether anyone is at the terminal, which is a property of the session's process ([pkit:ADR-091] point 5).
- **Without it,** a command that needs a person refuses. It reports why it knows no person: the account is an app's, or the identity is unresolved, with its cause ([project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162)), and it says how the session can name one. A report that rests on that person reports it as resting on nobody, as DEC-073 point 2 has it. `create-issue` still takes an assignee named in the call, as when a person files for another ([project-management:DEC-035-instance-ownership] point 5).

It is the caller's word, as an assignee the caller names is. Set wrongly, it lets the agent past the refusal that keeps it off another person's Task. Like DEC-035's clash guard, that refusal catches the mistakes of agents that follow the procedure, and is no security boundary.

### 4. `start-work` keeps its refusal, against the person the agent works for

Under a credential that names no user's account, in a project with no topology, `start-work`:

- **refuses a Task assigned to someone other than the person the agent works for,** and names `handoff-issue`, as DEC-026 has it;
- **assigns that person a Task with no assignee,** since DEC-019 needs one and the acting account cannot be it, and writes no assignee where that person is one already;
- **posts no claim,** since no claim it wrote would count (point 5);
- **refuses a Task an instance owns,** whatever instance id the clone holds. The clash guard reads the owner for such a clone, though the clone claims nothing. A reason overrides the refusal and posts an audit comment, as for any clash (DEC-035 point 6).

**Under an unresolved identity, a clone that holds an instance id refuses.** Every command that acts as an instance refuses there, says why, and is run again. Without the service's answer the commands cannot tell an app's clone from a person's. A person's clone that holds an id would otherwise start the Task and post no claim, and leave it In Progress with no owner, where another of the person's clones may act on it. A clone with no id claims nothing under any credential (DEC-035 point 1), so it goes on as this point says. So does an app's clone, with or without its login, whatever id it holds, since the service's answer tells that no claim it wrote would count.

Every other ordinary lifecycle verb under such a credential reads the owner the same way. `handoff-issue` hands a Task from one person to another, and never to an app's account.

Two sessions under one such credential, working for one person, can start the same Task, since neither claims it. Nothing tells them apart, as nothing tells apart two of a person's clones with no instance id (DEC-035 point 1). Nor is a person's own clone kept off a Task such a session started for that person: the Task carries no claim, so the person's clones read it as nobody's, and a clone that holds an id meets no clash guard on it (DEC-035 point 6). Each is a limit (point 8).

In a project with a topology, a clone under such a credential starts no Task (point 7).

### 5. Nothing a bot's account writes counts as a person's

The commands read the kind of an author from the service's record of that author, which says whether it is a bot. These guards hold for every account the service records as a bot, under whatever credential the command runs, and whether or not the service lets that account be assigned:

- **A claim on an issue of work** counts only from the assignee's account (DEC-043 point 3), and never from a bot's. So a clone under a credential that names no user's account takes no part in instance ownership on issues of work. The guard reads a claim's author, which the comment log gives. A label names no author, so under the label substrate the guard has nothing to read: a clone under such a credential marks no issue, since it claims nothing (point 4), and a label stamped by other means counts as DEC-035 has it.
- **An approval in human mode.** An `Approved` comment or an approving review counts only from an account the service records as no bot, and that the project does not register as a reviewer agent's ([project-management:DEC-028-agent-as-approver-paths], the remote path's list). Of the reviews, the commands read the latest that approves, requests changes or was dismissed, and pass only where it approves, as they read DEC-026's latest approving review. An approval that does not count is left out of that order. So a bot's request for changes holds the merge until a person approves after it, as a person's request does, and a bot's approval clears nothing. Holding a merge back grants nothing. So `done-work`'s approval check rests on another authority than the actor, as COR-033 P4 asks.
- **A reviewer agent's verdict** counts in agent mode as DEC-028's paths have it. Under a credential that names no user's account, the local path's verdict is posted by the acting account. It attests what that account ran, and names no person responsible for it. That takes a person's name off an attestation no person made: under a person's credential, an agent's session posts the verdict in that person's name, though the person attested nothing. The local path rests on the trust of a bypass (point 6), and is revisited once the record on who may authorise in an agent's turn guards the caller's word.
- **An authoriser in a comment.** The only authoriser the commands know is the acting account, which posts the comment and here is an app's account, or none they know. A comment names the authoriser only where the poster is someone else (DEC-049 point 4), so an override comment names no person as its authoriser. A reason the caller gives may report a person's word, and stays the caller's report.
- **A claim on a state issue** that an app's account writes is that account's own, and names no person ([project-management:DEC-058-state-issues] point 5). Point 7 says where such a clone claims.

### 7. In a project with a topology, a clone under such a credential builds nothing

- **No seat that builds.** A worker's or a lead's seat rests on claims on Tasks that count (DEC-059 point 9), and such a clone's never do. So it takes no such seat (DEC-059 point 4).
- **No Task without a seat.** A clone with no seat marks no issue and is guarded by nothing (DEC-059 point 6). A Task it started would stand In Progress with no claim that counts, which a worker reads as ready to take over (DEC-059 point 7). So under such a credential `start-work` refuses.
- **A planner's seat, where every reader counts its claim.** An app's clone may hold a planner's seat, since its claim on the seat's state issue is its own account's. That claim counts only where DEC-058 point 4 counts its author: as a member where the gate is closed, and otherwise where the service answers that the account may write to the repository. Every clone reads the members as the default branch holds them ([pkit:ADR-071] point 3), so a member's claim counts alike for every reader. Whether the service answers alike about an app's account's write access, to every reader, is unmeasured. So an app's clone claims a seat only where the gate is closed and its own account is a member, which it reads before it claims. Where the gate is open, or where the commands know no acting account, it takes no seat.
- **The organizer seat** is held on the same terms. The seat's privilege goes to whichever clone holds it, under any credential. - **A planner's filings** are assigned to the person the agent works for (point 3). Workers under that person's own credential take them. A worker under another person's credential meets `start-work`'s refusal, as it does with the filings of a planner under any one person's credential.

Under an open gate, a reader whose call about the app's account fails reads the issue as incomplete, since a failed call drops no claim ([pkit:ADR-071] point 3), and nobody in that reading can take the seat. A reader that gets a definite no reads the seat as free while the app's clone holds it, so two clones may hold one seat. ## Rationale

**Why the commands take no person's identity where the service names none.** Where the service does not answer that the credential acts as a user's account, any value that names a person is the caller's word, or git's record of whoever set the machine up. Acting as the person on it would make each act of the account read as the person's own, in the tracker and in every check that reads it. Acting as the account the service names keeps that record true, since the service shows which account wrote each change.

**Why no answer leaves the identity unresolved, under every credential.** Without the service's answer, the commands cannot tell an app's credential from a person's. A fallback to git's email or the variable there would make the person the acting account under an app's credential whenever its lookup times out. That is the very machine a setup prepares for an agent: it names the person in the variable (point 3), and git's email there is likely the person's too. Failing closed costs little, though not nothing:

- **Little else works without the service.** A command that cannot ask the service which account it acts as can rarely do its work there either, since every write it makes goes to the service ([project-management:DEC-003-github-bound-substrate]). It says why it refused, and is run again. A command that writes only on the machine, such as one that stamps the member list, changes nothing until a pull request lands, which needs the service too.
- **One call for each command that takes the gate or names who runs it.** Each such command asks the service which account it acts as, the variable set or not, as DEC-021 has it (its Implications, "The request for the account"), which counts where many agents run at once against the service's limits on calls. A command that only reads and reports asks only where its report rests on who runs it (DEC-073 point 2).
- **A machine user's workflow that sets the variable** refuses wherever that call fails, since the variable stands for no account the service did not answer for.
- **An earlier answer kept for the same credential** would spare both, and whether it counts as the service's answer is the record on where the reading lives to decide (point 1).

The posture is decided only for the acting account's identity, and every other read keeps the posture DEC-021 left to its implementation.

**Why an integration's refusal is an app's answer.** The service tells a refusal because the credential is an integration's from a refusal for any other cause, by its status and words, as DEC-073 point 2 reads it. So that refusal says that no person acts, and reading it as no answer would gain nothing: a clone that holds an instance id would refuse at every command that acts as an instance, though no second run could change the answer, and no claim it wrote would count either way. It gives no login, so the commands know no acting account under it, and what needs one, a grant or an act's actor, waits for a request that gives it (point 1).

**Why `PM_INVOKER_LOGIN` names no acting account where the service names none, in CI as in a session.** Set to the person, it would let `start-work` write the person as assignee. Three things stand against it:

- **It names the person as the actor of every act.** Each override comment would name the person as its authoriser, beside the account that posted it (DEC-052), whether or not the person authorised anything.
- **It hands the engine's gate the wrong actor.** The gate would compare the person with the account that merged, so the agent's own merge would read as another authority's (COR-033 P4).
- **It would not make a claim count.** The ownership fold reads who wrote a claim, never the variable (DEC-043 point 3). So instance ownership stays out of reach.

DEC-021 meant to keep the variable from a value the user controls, and trusted a CI workflow to keep it so. The commands cannot tell whether it did, under any credential. A workflow's input is typed by whoever dispatches the run, and an earlier step can set the environment of later ones. A pipeline that runs an agent's session on one prompt is both a CI workflow and an agent's session. So under a credential that names no user's account, the variable is read the same way in both: as the caller's word, where the caller's word grants nothing. Where the service answers with a user's account, the variable is no identity, since DEC-021 takes that account's login alone ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)). Whether the variable names the person the agent works for or nobody the commands take is told by the service's answer, a property the commands read. Under a user's credential that is not the person's own, the variable set to the person brings back none of the three hazards above. DEC-021 names the account the service answers for wherever a command names who runs it, so the assignee a command writes is the account whose claims count, and that account is each act's actor, which the engine's gate judges for a move and beside which no comment names an authoriser, under every credential (point 9). Its documentation tells a setup to leave it unset there (point 3).

**Why each act's actor is the account the credential acts as, under every credential.** COR-033 P4 asks that an authorisation come from another authority than the actor. This capability's predicate for the gate on Done reports who merged the pull request as an account, so the comparison means something only against an account, and the account that makes the move is the one its credential acts as. A person's name in its place, from the variable or git's email, would make an agent's own merge read as another authority's, the person's. Naming the account makes a person and their agent under one credential one actor, which is what the service records, and where the service answers, the journal's actor is the account GitHub's timeline records for the same change. It holds under a user's credential as under an app's: a machine user's account merges for the agent as an app's does, and which value stands at the membership gate does not change who merged. The journal and the comments take the same actor, so a move has one, as DEC-049 has comments project the journal (points 1 and 2). A comment that named the variable's person would name as the move's authoriser someone the gate never judged, and one move would have two actors. An act that is no move, such as a merge by bypass, has no gate and no journal entry, and its comment is its record: a person named there on the caller's word would read as its authoriser, beside the account the service records as acting. Under a machine user's credential, DEC-021 already names that account, not the variable's person, on a workflow's audit comments, so what this costs such a workflow is the email git's configuration puts beside that account. Wherever a comment loses the name of the variable's person, the caller's reason may still report that person's word, as the caller's word, save on a refusal overridden by `--force`, which takes no reason (DEC-046 point 2).

**Why a move into a state whose gate is an authorisation artifact refuses where no actor is known.** COR-033 P4's gate needs an actor to tell from the authority that authorised. A command that hands the engine none lets it take its own, which today is `operator`, a name the account that merges does not bear, so the gate passes on any merge, the agent's own among them, and the journal records a name the commands never knew (Context). Refusing such a move costs a second run, or a person's own credential, where the service gives no login, and passes nothing the gate would refuse. A move with no such gate grants nothing by its empty actor, so it goes on (Alternatives). The refusal lasts until the backbone decides what its gate takes where a command hands it no actor, since what the engine takes is the backbone's.

**Which edits overturn, and which refine.** One test sorts every edit this record names to an accepted record, by what the passage states for the case this record decides:

- **Overturned in part,** where the passage states, for that case, an outcome this record contradicts: a named fallback or provision, or an explicit no. DEC-021's match on any surface where the service does not answer with a user's account, with git's email as a fallback "when `gh` is unavailable" and the variable among the surfaces it matches there, item 3's "never from user-controllable env", and its workflow that passes by the variable from a CI secret are such provisions or such a no. So are DEC-052's parenthetical that keeps the authoriser on the bot-authored path, and the name and email by which DEC-014's template and DEC-050 point 4 name the authoriser of a bypass or of an override of a reviewer. DEC-035's "no guard" and its id as "the sole activation gate" are such outcomes. A form a passage gives every comment or record of a kind, such as DEC-014's template, the actor of DEC-044 point 1 and of DEC-049 point 1's journal entry, and the actor on DEC-044 point 4's metadata line, grants nothing to a class, so where this record contradicts it the passage is overturned in part, even where an earlier record had already left it one case. The passage stays as it stood, under a top line that names this record, since a refinement in place narrows, widens or completes a decision that still stands.
- **Narrowed in place,** where the passage grants something to a general class, such as anyone, any member, any non-author or any clone, and this record takes out of that class the credentials and accounts it decides for, while the grant stands for the rest. DEC-021's "Bootstrap", "Membership change authority" and "Tooling surface" let anyone while the gate is open, or any member, change the list. DEC-026's and DEC-027's approval passages count an approval from any non-author, and their reviewer passages assign any member whose role matches. DEC-026's `handoff-issue` row, DEC-043 point 3, DEC-058 point 5, DEC-059 points 4 and 6, and ADR-041 grant to any account named, any assignee or any clone.
- **Widened in place,** where the passage names the ways to an outcome, and this record adds one beside them. DEC-021's item 1 names one request for the acting account, which the service refuses to an installation's token, and this record adds the request that gives an app's login.
- **Completed in place,** where the passage states no outcome for that case, as a question it left open or a term it fixes only for a person, and this record supplies one. DEC-021 left the posture on network errors to its implementation (its Rationale, "Why mechanism details are deferred"), and this record settles it for the identity read. It also left to evidence of its own whether git's email and the variable name the invoker, where the service does not answer with a user's account, for every reader but the gate (its Rationale, "Why a user's login the hosting service answers stands alone"), and this record answers it. DEC-019's filer and DEC-026's `start-work` row, which state no outcome where the filer or the current user cannot be an assignee, DEC-028's developer, DEC-044 point 1's actor for an act that names one, and ADR-071 point 3's answer about a bot's access are of this kind.
- **A fact corrected in place,** where the passage's rule stands for that case, and only a fact it states beside the rule, such as an example it quotes, a case it says cannot arise or a value it says a gate can match, reads false once this record holds. DEC-019's parenthetical on `validate-issue.py`'s hard reject at filing, DEC-021's Implications' bullet on the email beside the login on an audit comment, DEC-047 point 5's quotation of DEC-014's line, and DEC-073's term for a credential that names no user's account, its point 6's account of what an entry for a workflow admits and its Rationale's account of what the gate can match under such a credential are of this kind. Such an edit changes no choice, so it takes no refinement pointer, which names a record that narrows, widens or completes another (the decisions README, "Refining an accepted record").

The test asks what a passage states, not what case it was written for. It sorts a passage case by case, so one passage may take two sorts. DEC-044 point 1 gives every actor a login and a display name, which an empty actor contradicts, so it is overturned in part for an act that names no actor. For an act that names one, it leaves open which account is the actor and where its names come from, so it is completed there. Its overturned words stay as they stood, and the completion is a sentence of its own after them. DEC-021 sorts by its readers. For the gate, where the service does not answer with a user's account, it states an outcome: the match on any surface, which passes on git's email and on the variable, and the workflow of "CI invocations" that passes by the variable, so there it is overturned. For every other reader, it says by name that whether git's email and the variable name the invoker rests on evidence of its own, so there it is completed. Its deferral of identity resolution's edge cases covers what it leaves open, such as the order of the sources and how a failed read is reported, but not a surface its match passes on, or a provision its Implications make.

**Why git's email does not stand for the account.** Under any credential the email is a value the user controls, and beside a person's resolved login DEC-021 closes that hole, taking the login alone ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)). Where the service names no user's account, there is a reason of its own: the email names a person the credential does not act as, or one the commands cannot tell it acts as.

**Why the person the agent works for grants nothing.** Most of what the commands do with a person's login says whose the work is: the assignee at filing, and whether a Task is someone else's. A wrong value there misleads, and grants nothing, since a claim, an approval and membership are each read from the account that wrote or acts, never from the assignee. A command that takes an assignee from the caller, when a person files for another, takes the caller's word the same way.

**Why `start-work` keeps its refusal.** Without a person to compare with, an app's account, or one the commands do not know, is nobody's assignee. The refusal would then either catch every assignee, as on the trial, or none, which would let an agent start any member's Task. The refusal is a mistake-catcher, as are its neighbours (DEC-058 point 5, and DEC-059's release by force, which "catches mistakes, and it is no security boundary"). On the caller's word, it keeps catching the mistakes of agents that follow the procedure.

**Why a clone that holds an instance id refuses under an unresolved identity.** A clone that holds an id means to claim what it starts. Under an unresolved identity the commands cannot tell whether its claim would count, since they cannot tell an app's credential from a person's. Going on would start the Task with no claim, and the person's other clones would read it as nobody's. Refusing costs a clone a second run once the service answers, a person's or an app's alike, and that run's answer tells whether its claim would count. An app's clone the service answers for, with or without its login, starts the Task with no claim too, and the person's clones read it as nobody's, but no second run mends that, so it is a limit (point 8), not a refusal. A report that it posted no claim would keep the clone working, but leave the Task with no owner all the same, where a second run would have mended it.

**Why the clash guard reads for such a clone.** A person's clone with no instance id may opt into ownership, and is guarded once it does (DEC-035 point 1). A clone under a credential that names no user's account cannot opt in, since none of its claims counts. Reading the owner is then the only guard it can have, and it grants nothing.

**Why the guards read the author's kind.** A claim means something because only the assignee's own account can make it (DEC-043 point 3). A guard derived from the service refusing a bot as an assignee would fail once a bot can be assigned, as GitHub lets its own coding agent be. Read from the author's kind, the guard holds for every bot, whatever the service lets it be. Counting a bot's claim for its assignee would let anyone who holds the credential claim work for any person.

**Why a bot approves nothing in human mode, in every project.** Human mode asks for a person's approval. DEC-027 counts an approval from any non-author identity, and DEC-026's tables and the commands count the comment from any commenter but the author, a bot among them, while DEC-026's Rationale counts it only from a commenter that is no bot. Reading the author's kind brings the tables, DEC-027 and the commands to the Rationale's rule on a bot, and applies it to reviews too. It also leaves out the accounts the project registers as its reviewer agents', which name no person whatever the service reports. A request for changes stays in the order of reviews, since holding a merge back grants nothing, and a person's later approval clears it as it clears a person's request.

**Why DEC-028's local path stands, for now.** DEC-028 rests the local path on the developer's attestation, the trust of a bypass, rather than on a trace from another authority. Under a credential that names no user's account, a bypass passes all the same (point 6). Refusing the local path would push such an agent to a bypass, which records less: no verdict, no reviewer, no head reviewed. Keeping it loosens nothing: under a person's credential, an agent's session already posts the verdict in the person's name, though the person attested nothing, and under a credential that names no user's account the verdict names no person, which is true. The reason lasts only while a bypass passes on the caller's word. Once the record on who may authorise in an agent's turn guards that word, the local path is the weakest way past the gate under such a credential, and is revisited.

**Why such a clone builds nothing in a topology.** A seat stays taken until it is released (DEC-059 point 5). A clone that took a building seat and could claim no Task would hold the seat while doing none of its work. A Task it started without a seat would read as ready to take over, and a worker would take it over from under the agent.

**Why an app's clone claims a seat only behind a closed gate.** A claim on a state issue counts by its author's standing, which each reader judges when it reads. Behind a closed gate every reader judges it by the same members, read from the default branch. Behind an open gate each reader asks the service about the author's write access, and whether the service answers alike about an app's account, to every reader, is unmeasured. A claim judged differently by different readers splits the seat (point 7), and only a person's hand can end that, so the claim waits until the answers are measured alike.

**Why an app's clone may hold the organizer seat.** The privilege of releasing seats by force already goes to whichever clone takes the seat, a clone of any member's among them. So an app's clone in it grants no more than the project granted by admitting the app's account. Keeping it out would leave such a clone no seat at all, since the planner's seat is typically the organizer's.

**Why act as the account, and not only state a limit.** The setup offers a credential that names the person's account, so every need could be a limit. But most of what the commands do needs no person at all. And under the person's credential, the agent's pull request is the person's own, which the person cannot approve (DEC-028, "Self-approval degrade"). Under a credential that names no user's account, the person can approve it, by a review or an `Approved` comment. `done-work`'s approval check then reads a trace from another authority, as COR-033 P4 asks of a gate. The engine's own gate on the move to Done reads who merged the pull request instead, and refuses the move after the agent merges its own approved pull request, as it refuses a person's own merge today (Implications, "Left out"). Where the commands know no acting account, the move refuses before it is made (point 9).

**Why building waits on where the reading lives.** The acting account is the backbone's concern too: the account `pkit report` posts as, and the account the engine's gate compares, which the commands name as its actor (point 9). Two readings of one credential can disagree, and at the engine's gate they already can. Under an app's credential the two sides may spell one account two ways, and the gate then reads the agent's own merge as another authority's. A reading built in this capability first adds one more copy before its home is decided. A capability's script reaches the backbone only by command ([pkit:ADR-057] point 1), the backbone cannot depend on a capability a project may not install, and a computation keeps one home ([pkit:ADR-057] point 2). So the one home both can read lies outside this capability, and a record of the backbone's places it, as [pkit:ADR-061] placed the hosting service's acts.

### Alternatives considered

- **State a limit and nothing more:** the commands act only under a credential that names a user's account. The case: one sentence, and nothing to build. Rejected: most of what the commands do needs no person, and the person could not approve their agent's pull requests.
- **A limit, plus a mark the commands add to what an agent's session writes.** The case: no edits to other records, and instance ownership keeps working under the person's credential. Rejected: the mark is the session's own word, so the line it draws is weaker than the service's record of which account wrote, and the person still cannot approve the agent's pull requests.
- **`PM_INVOKER_LOGIN` names the acting account,** in an agent's session, or only in a CI workflow as DEC-021 provides. The case: `start-work` and `create-issue` work as under the person's credential, with nothing new, and this record would overturn nothing in DEC-021 or DEC-052. Rejected, for the reasons above, and because no line between a workflow and a session holds.
- **Fall back to git's email and the variable where the service cannot be asked,** as DEC-021 provides. The case: a person's own credential keeps passing the gate with no network, and DEC-021's fallback stands. Rejected: without the answer the commands cannot tell an app's credential from a person's, so under an app's credential a timeout would make the person the acting account, on a machine whose setup names that person. With no network, little the commands do can succeed anyway.
- **Read a credential's kind from its own form,** such as the prefix the service gives each kind of token. The case: a property of the credential, read on the machine, which tells an installation's token from a person's even where the service refuses the lookup. Rejected: it is a second reading of the kind, which can disagree with the service's answer, as on a person's sign-in through a host's app, which is unmeasured (Context). A form the commands do not know leaves the identity unresolved anyway, and the command must read the secret itself to see its form.
- **A variable of its own for the person the agent works for,** leaving `PM_INVOKER_LOGIN` the meaning DEC-021 gives it. The case: each variable has one meaning on every machine, and a setup that names the person primes no fallback of DEC-021's with that person's login. Not taken. Alone it would not keep the person from standing for the acting account, since git's email on an agent's machine names the person too. Where the service names no user's account, neither variable stands for the acting account once no answer leaves the identity unresolved (point 1), so a second name closes nothing more there. Under a user's credential, the one variable stands for no account, since DEC-021 takes the login the service answers alone ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)), so a second name closes nothing there either. A second name costs a documented input that every setup and workflow learns, and the service's answer already tells which meaning the one variable has.
- **One record on identity resolution for every credential,** taking DEC-021's "Identity resolution" whole, in place of a top line that names this record. The case: one place says how the acting account is resolved. Not taken: it would fold in where the reading lives, which is the backbone's. - **The person the agent works for as a second check at a closed gate,** refusing a session under an app's credential that names a non-member. The case: it grants nothing, and catches an agent that works for a non-member, which DEC-021's refusal of such an agent does not reach once the gate reads the app's account, a member. Not taken: it would refuse only a session that names a non-member truthfully, and pass one that names a member or no one, so it keeps out no session the project did not admit by adding the app's account, the reason DEC-021's Alternatives give for rejecting `PM_INVOKER_LOGIN` as the same check beside a user's login. Unlike `start-work`'s refusal, which every credential has today and this record keeps, it would add a check at every command's start that no credential has. A project that wants non-members' agents kept out gives them no credential whose account it admitted.
- **Refine DEC-014, DEC-021, DEC-035, DEC-044, DEC-049, DEC-050 and DEC-052 in place,** whole. The case: each keeps stating its decision whole, and DEC-021 left identity resolution's edge cases to its implementation. Not taken: a refinement in place narrows, widens or completes a decision that stands, and the passages this record overturns each state, for the case it decides, an outcome it contradicts.
- **An interim reading in this capability, in one seam** that every comparison of accounts goes through, for [project-kit#3171](https://github.com/aleskalfas/project-kit/issues/3171) to move into the backbone later. The case: the capability's work starts at once, without waiting on a record of the backbone's, and the later move touches one seam. Not taken: until the move, two readings of one credential run side by side, and they already disagree at the engine's gate. The cost is a second copy of the reading, kept in step with the backbone's by hand until the move, and a spelling every comparison relies on, which changes again if the backbone settles another.

- **Each act's actor only under a credential that names no user's account,** leaving the audit comments of a run under a user's credential as the commands render them today: the identity the membership gate checks, which DEC-021 takes there as the account the credential acts as, with git's configured email beside it. The case: it lasts across sessions, and [pkit:ADR-091] point 7 names such a setting as what a setup writes. Not taken: it needs a command and a stored value of its own, a CI run would write it each time, and the variable already serves these contexts.
- **No clash guard for such a clone,** as for a person's clone with no instance id. The case: one rule for every clone with no id. Rejected: a person's clone can opt in and such a clone cannot, so without the read it would act on a Task another of the person's clones is building, with nothing to warn it.

- **Count a bot's claim for its assignee,** loosening DEC-043 point 3. The case: instance ownership, and building in a topology, under such a credential. Not taken: anyone holding the credential could claim work for any person, and loosening the guard is a person's decision.
