**In plain terms:** an open issue can be left with no card on the configured board: filed outside the capability's commands, its add failed at filing, or its card removed. The command that brings the board in line gives such a card only where the board's Status is the state's projection, and refuses where the board holds the state or the state degrades. This record has it give the missing card in every project with a board, and write a Status only where the Status is the projection. Where the board holds the state, the card it adds has no Status, so the issue's position stays undetermined until a person sets it on the board, and no command guesses it. Yet the board's own automation may set a Status when the card is added, and every command would read that Status as the issue's position. So there the command adds cards only with a person at a terminal, or where the person turned on a switch of the project's that consents to that automation. Afterwards it names each card it added that shows a Status it did not write.

## Context

**The terms.**

- *The configured board*, *the board holds the state*: as [project-management:DEC-070-filing-another-board] defines them.
- *The Status is the state's projection* where a board is configured and the state is carried off it, and *the state degrades* where a present substrate map leaves the state out or marks it unsupported, so that the capability writes no Status ([project-management:DEC-062-axes-chosen-in-the-map] point 5).
- *The board sync* is the command that brings the board's Status in line with the issues' states (DEC-062 point 5).
- *A missing card* is an open issue's lack of any card on the configured board. An archived card is a card, as [pkit:ADR-096] point 5 counts it.
- *A watched run* is one whose standard input and standard output are both terminals, the test [project-management:DEC-069-when-fixers-start] reads for a person at a terminal.

**What the records say.**

- **Every issue belongs on the configured board from its filing** ([project-management:DEC-019-mandatory-issue-state]). A missing card on an existing issue is drift, at warning severity, for a person to fix. The post-check workflow DEC-019 offers, where a project turns its remediation on, adds a card only on a finding that blocks, and drift never blocks, so it adds no missing card. Whether it should is left to this capability (ADR-096, its Implications on the workflow).
- **Membership is the board flag's question, never carriage's:** whether an issue has its card turns on a board being configured, not on what carries any axis (ADR-096 point 5).
- **Where the board holds the state,** an open issue with no card, whose card has no Status, or whose Status names no open state, has a position that is undetermined. It is reported apart, and never guessed from its labels or its milestone. A seat choosing work skips it ([project-management:DEC-051-axis-carriage-activation] point 6), and a move refuses it ([pkit:ADR-074] point 5).
- **Who writes a Status.** Where the Status is the state's projection, the capability writes it from the issue's state (DEC-062 point 5). Where the board holds the state, a move writes it, from a position it read ([project-management:DEC-006-state-machine-and-cascade], its Implications; ADR-074 point 5), and filing writes the first one, the state it files the issue into (ADR-096 point 4). Where the state degrades, the capability writes none, and the Status stays with the people who move it (DEC-062 point 5).
- **A closed issue's card,** where the board holds the state, keeps where its work stood before the close. A command that needs that origin reads it there, such as the forward cascade telling finished work from a won't-do close. When the capability's own move closes the issue, it reads where the issue stood, then writes the card's Status to Done, as a projection of the native close (ADR-074 point 4; ADR-096 point 4). A closed issue is Done whatever its card says (DEC-062 point 5).
- **Runs nobody watches, where a command writes what people own.** DEC-069 lets a fixer run with nobody watching only where the person turned on a switch of the project's (its point 4). It rejects "Watched runs only, with a later record for runs nobody watches", since the maintainer asked that turning such runs on need no new record. [project-management:DEC-017-prerequisites-bootstrap-migrate-discipline] gives the migration command no batch confirmation option, and gives a run nobody watches an approval file the project writes, "a deliberate gesture not an escape hatch" (its rejected alternative "Batch `--yes` flag on migrate"). [project-management:DEC-037-adoption-ceremony] rejects a bulk back-fill behind a single confirmation option for the same reason (its alternative "Silent bulk back-fill with a single `--yes`").

**The board sync, when this record was written.** Where the Status is the state's projection, it reads every card on the board and every open issue, writes the Status on each card that differs, and adds a card for each open issue that has none, then sets its Status. It asks before its first write, testing standard input alone for a terminal, and a run with no terminal writes only with the option that skips the question. Where the board holds the state, or the state degrades, it refuses, and reads nothing.

**A board's own automation.** The host lets a board set a Status by itself, such as when a card is added or its issue is closed, and the capability does not control it. It acts on a card however the card came: by the sync, by filing, or by the host's own means. Which automations a board has on, and when each acts, was not measured. Nor was whether the host answers an add of an issue already on the board with the card it has.

**The routes to a missing card.** An issue filed outside the capability's commands, such as in the host's own interface, gets no card from the capability. Filing reads the board before it creates the issue, and refuses where the board did not answer, yet an add can still fail after the issue exists, and filing then exits saying so (ADR-096 point 4). A person can remove a card on the board. And a filing that names another board, where DEC-019's override stands, puts the issue there in the configured board's place.

**The gap.** Where the board holds the state, nothing but a person gives a missing card. The issue is absent from the board the people place work on, and only a command's warning names it. Where the state degrades, the issue stays workable, since its position is read from the native primitives, yet nothing but a person gives its card either.

**Where the question came from.** The work on filing onto another board ([project-kit#3205](https://github.com/aleskalfas/project-kit/issues/3205)) named it, and left it to [project-kit#3241](https://github.com/aleskalfas/project-kit/issues/3241).

## Decision

**The board sync gives each open issue with a missing card its card on the configured board, in every project with a board, whatever carries the state. It writes a Status only where the Status is the state's projection. Where the board holds the state, it writes none, adds cards only in a watched run or where the project's switch is on, reads back each card it added, and names every open issue whose card does not place it.**

### 1. The sync gives every missing card, wherever a board is configured

- **Where.** Where the board holds the state, and where the state degrades, the sync reads every card on the configured board and every open issue, as it does where the Status is the state's projection, and adds a card for each open issue that has none. What carries the state is no ground for a refusal. Where no board is configured, it refuses, whatever the map says.
- **A board with no Status field.** Where the sync writes no Status, a board with no single-select Status field does not stop its adds. Where the board holds the state, such a board can place no issue, and counts as a board that cannot be read for the state (ADR-074 point 1). The sync names that fault once, with its remedy on the board, and reports no issue's outcome as a finding (ADR-074 point 5).
- **What it reads and leaves alone.** It reads what it reads where the Status is the state's projection, and, where the board holds the state, the cards it added, again (point 3). It leaves alone what it leaves alone there.
- **How it asks.** In every project, it asks before its first write only in a watched run. A run that is not watched is asked nothing: without the option that skips the question, it refuses, as a run it cannot ask, and with that option it goes on, within point 3. A dry run writes nothing.
- **Only the issues a run names.** A run can name issues. Its writes, its plan and its report are then limited to those issues, in every project, so where the Status is the state's projection, it writes no other card's Status either. A named issue it has nothing to do for, or cannot act on, is listed with the reason, and the run goes on with the rest. The reasons are: closed; on the board already, with nothing to write; its only card archived; a state issue ([project-management:DEC-058-state-issues] point 3); or not among this repository's open issues the run read. Such an issue changes no exit code.

### 2. It writes a Status only where the Status is the state's projection

- **Where the Status is the state's projection:** from the issue's state, on each card that differs and on each card it adds, as DEC-062 point 5 has the capability keep it.
- **Where the board holds the state:** no Status, on a card it adds or on any other, a closed issue's card included. The issue's position stays undetermined until a person sets its card's Status on the board (DEC-051 point 6).
- **Where the state degrades:** no Status, and the Status stays with the people who move it (DEC-062 point 5).
- **No other field.** On a card it adds, the sync writes no other field of the board. A field the filing's hooks seed on a new card stays unset there, and the corpus back-fill seeds it on each card that lacks it (DEC-037 point 2).

### 3. Where the board holds the state, it adds cards only in a watched run or with the project's switch on, and reads each back

- **Watched, or the switch on.** The sync adds a card there only in a watched run, or where the switch below is on. A run that is neither adds none there, with the option that skips the question or without it.
  - **With cards to add,** it prints its plan, says that the cards are added only at a terminal or with the project's switch on, gives the command to run at a terminal, and refuses as it refuses a run it cannot ask.
  - **With none to add,** it prints its plan, which names each card that does not place its issue (point 4), and exits as a run with nothing to write does. So a run nobody watches passes clean where no card is owed.
  - **A dry run** prints its plan, says which adds would need a watched run or the switch, and exits as a dry run does.
- **The switch.** A setting of this capability's project configuration lets a run nobody watches add cards where the board holds the state. It takes the form of DEC-069's switch (its point 4):
  - off by default;
  - the person's to turn on: only a change of the project's that the person authorises turns it on, and no install, upgrade or migration does;
  - on only as the default branch holds it, and off at once, from the configuration of the working tree the run starts from;
  - held at every merge: each command of this capability that merges a change into the default branch holds a change that turns it on, until the person authorises that merge themselves, and says in plain words what turning it on means;
  - turning it on is the consent to the board's own automation setting a Status on each card a run nobody watches adds, which every command then reads as the issue's position, named only in that run's output. It consents for every session that runs the sync in the project, a person's or an agent's;
  - what stays open is what DEC-069 point 5 states of its own switch: a merge outside this capability's commands, or a direct commit to the default branch, passes no hold, and a terminal tells only that one is attached, not that a person watches.

  A run nobody watches with the switch on still needs the option that skips the question, as point 1 says.
- **Read back.** After its adds, the sync reads each card it added again. The read:
  - goes through the board read seam, as every read of the board does (ADR-096 point 6);
  - reads each card by the card the add answered with (ADR-096 point 3), not through the issue's own cards, which can lag an add just made;
  - names each added card that shows a Status as showing a Status the sync did not write, which every command now reads as the issue's position, for the person to check on the board. It claims nothing of who set it: the board's automation may have, or the host may have answered the add with a card the issue already had, whose Status may be a person's (Context);
  - suggests clearing no Status;
  - reports a card it does not find as not confirmed, never as a card with no Status nor as no card, and a read the board did not answer as that (ADR-096 point 4);
  - never reads as an all-clear. Where it finds no Status on a card, it says so of the moment it read, and that the board's automation may set one later, so each card it added wants checking on the board;
  - is a note on the act (ADR-096 point 4): where it fails, the run takes no code that reads as the adds not made.
- **What the refusal does not stop.** A card added by the host's own means, by a person in the host's interface or by an agent with the host's commands, sets off the same automation. So it carries the same guess, with no plan to warn of it and no read-back to name it. The refusal keeps the guess out of the sync's runs nobody watches, not off the board. The switch is how a project whose agents do its work gets the sync's guards on its adds.

Where the Status is the state's projection, or the state degrades, a run that is not watched writes with the option that skips the question, and the switch is not read. There the board's automation places no issue, since no command reads an issue's position from the Status, and where it is the projection, the sync writes it itself.

### 4. What it says

- **Its plan** names each card it will add, and, where it writes no Status, says that the card will have none. Where the board holds the state, it says that each added issue's position stays undetermined until a person sets its card's Status on the board, and that the board's own automation may set one when the card is added, which every command would then read as the issue's position.
- **Where the board holds the state,** its plan and its report also name each open issue whose card does not place it, with its outcome (DEC-051 point 6), and each open issue whose only card is archived, which the board's views hide. The state's reader sorts each outcome (ADR-074 point 2), from the sync's walk of the board, as the refinement of ADR-074 point 6 below lets it, and the sync keeps no classifier of its own. It writes nothing to these issues. Where the board has no Status field, it names that fault once in their place (point 1).
- **After the run,** it names each card it added, and each it could not add, with the board's words, and what the read-back found (point 3). Where the project's hooks seed a board field on a new card, it names the corpus back-fill as the way to seed it. It says that the back-fill reads each such hook as an intent for the whole corpus, so it seeds the field on every issue that lacks it, not only on the cards the sync added (DEC-037 point 2).

### What this refines, and what stands

- **Refined in DEC-062 point 5:** its last sentence, "Elsewhere the project's people do both on the board", which reads instead "Elsewhere that command gives each open issue its card, and the project's people set each card's Status on the board."
- **Refined in ADR-074 point 6:** a command that already walks the whole board for its own act may read the positions of the issues it acts on from that walk, through the state's reader. Its choice of the issues' own cards stands for every command whose act needs no walk (Implications).
- **Stands:** DEC-051 point 6, DEC-019's severities and its post-check workflow, DEC-069, ADR-074 point 4's reading of a closed issue's card, ADR-096, and the sync's work where the Status is the state's projection, save how it asks and the issues a run names (point 1).
- **Not decided here:**
  - **Whether the post-check workflow adds a missing card on drift,** which ADR-096 leaves to this capability. That workflow runs under a credential that reaches no board until ADR-096's setting for one is built ([project-kit#3256](https://github.com/aleskalfas/project-kit/issues/3256)), and runs on each issue opened, with nobody watching, which is the run point 3 keeps the sync from where the board holds the state. It wants a record of its own.
  - **What a board's own automation means where it writes the state's source outside the sync's adds.** ADR-074's Boundaries name only a card a person moves by hand. Yet an automation may set a Status after filing writes the first one, or on a close, where it would erase where the work stood before the close (ADR-074 point 4). It is left to a follow-up, which measures the host's defaults first, and then adds a Boundaries bullet to ADR-074 or a record of this capability's.

## Rationale

**Why the sync gives the card.** DEC-019 puts every issue on the configured board, and that is the board flag's question, not carriage's. A card needs no position to be given, only the board's answer. The sync already reads every card and every open issue to give the missing cards where the Status is the state's projection, and the same read finds them where it is not. Nothing else in the capability gives such a card where the board holds the state or the state degrades.

**Why no Status where the board holds the state.** The issue's position is undetermined, and DEC-051 point 6 has no command guess it as it reads. A command that wrote a guess onto the board would do worse: the board holds the state, so the guess would then read as the issue's position, and every command would act on it. A person knows where the issue stands, and sets it on the board, as on any card whose Status places it nowhere. The two writers of the Status there each know the state they write: a move reads the position it moves from, and filing writes the state it files the issue into.

**Why the card helps without its Status.**

- **It moves no issue.** An issue with no card and one whose card has no Status are both undetermined (DEC-051 point 6), so the add changes no issue's position.
- **It brings the issue onto the board.** The issue then stands on the board the people place work on, where a card with no Status is shown apart, rather than off the board, named only in a command's warning. What remains is one value set on the board.
- **It gives later reads their witness.** Under ADR-096, a read of an issue's own cards says a card is absent only where the same request finds a card of another issue from the same repository on the board, so a repository with none of its issues on the board reads as a board that did not answer (ADR-096 point 1). Each card the sync adds can witness for the repository's later reads, as ADR-096 says of a card the workflow adds. The sync decides from a whole walk of the board's own cards (ADR-096 point 2), so it can give such a repository its first cards.

**Why a watched run, or the project's switch, where the board holds the state.** A board's automation that sets a Status when a card is added would write, onto each card the sync adds, the guess this record refuses to write. Every command would read it as the issue's position, and an issue someone worked on would read as moved back, with nothing saying so. Many cards added in a run nobody watches would take that guess with nobody to see it. The option that skips the question is no consent to it. DEC-017 and DEC-037 each refuse a single confirmation option as consent to a bulk write of what people own, and DEC-017 gives a run nobody watches a deliberate gesture of the project's instead (Context). The switch is that gesture here, in the form DEC-069 gives its own, where the maintainer asked that turning runs nobody watches on need no new record. In a watched run, the person sees the plan's warning and the read-back's names, and sets each Status on the board. With the switch on, the person consented to the guess beforehand, and the read-back names it to whoever reads the run's output. This narrows the guess and does not rule it out: the read-back misses automation that acts later, and a terminal tells only that one is attached, as DEC-069 point 5 says of its own test.

**Why the switch, and not adds for the issues a run names.** A run nobody watches that could add the cards of the issues it names, with the read-back, would give an agent a guarded way to add one card with no setting, such as after filing's failed add. Yet it takes the guess with nobody's consent, which the refusal exists to prevent, one issue at a time, and an agent that names issues in a loop makes it a bulk add. The switch puts the guess behind the person's consent once, and every run nobody watches then gets the guards, a run naming issues among them. Its cost is one setting more, and a hold for it at each merge.

**Why one test of a watched run, for the question and the adds.** The question before the first write tested standard input alone, and the adds test standard input and standard output. Kept apart, a run whose output goes to a pipe would be asked, answered yes, and then refused its adds where the board holds the state. With one test, such a run is asked nothing, in every project, and needs the option that skips the question, as a run nobody can ask does. The test is DEC-069's, which the drift command already reads, so the sync reuses it.

**Why read back, and why say so little.** The read-back is the one time the sync can name a Status it did not write on a card it added: once such a Status places the issue, no later run names it (below). It reads the card the add answered with, through the seam, since the issue's own cards can lag an add just made, and a read outside the seam would be a second account of what counts as the board's answer (ADR-096 point 6). It names no setter, since the sync cannot tell the board's automation from a person: the host may answer an add with a card the issue already had, which was not measured. So it names the card for the person to check, and suggests no clearing, which could erase a position a person set. A card it does not find, or a card with no Status, says nothing of what the board holds a moment later, so neither is an all-clear.

**Why name every card that does not place its issue.** After the add, the membership check passes the issue, yet its position is still undetermined. Only a seat's warning on a Task, a move's refusal or a close's refusal names it then, and a container whose card has no Status is named by nothing. The sync reads every card already, so naming them costs no read. A later run names each card an earlier one added while it places nothing. A card the board's automation gave a Status places its issue, so no later run names it, and the read-back is the one place the sync names it.

**Why read the positions from the walk.** The sync walks every card on the board for its own act, whole as ADR-096 point 2 requires, to find the issues with no card. ADR-074 point 6's reasons for reading the listed issues' own cards do not reach it. Its cost grows with the board's history whichever way it reads positions, since it pays for the walk anyway. And by ADR-096's second premise, the walk and the issues' own cards are one account of which card is an issue's, an archived card included. A batched read of the issues' own cards beside the walk would leave ADR-074 point 6 as it stands, at about one call more for each hundred issues. Yet it would give two reads in one run that can disagree on whether an issue has a card. Either way the state's reader sorts each outcome, not a second classifier in the sync.

**Why only when someone runs it.** As where the Status is the state's projection: DEC-019 keeps a scan of every issue's board state out of each command, and the sync is the command a person runs to bring the board level.

**Why DEC-062 and ADR-074 are refined, not superseded in part.**

- **DEC-062.** Its point 5 decides who writes the Status, and this record leaves that whole: the capability writes none where the state degrades, and where the board holds the state only a move or filing writes it. Its last sentence says who gives the card and the Status before a project binds its state to its board. This record has the sync give the card there, and leaves the people their own way. So the edit widens who may give a card, changes nothing DEC-062 decides of the Status, and leaves DEC-062 reading true, which is a refinement in place. A partial supersession would leave "the project's people do both" standing as it stood, false to read, under a top line that overturns it. The sync's refusal where the board already holds the state is the command's, written in its reference, and no accepted record decides it, so giving the card there overturns nothing.
- **ADR-074.** Its point 6 chose the issues' own cards over a walk of the board for a command that needs many issues' states, so that the command's reads are bounded by what it lists. That choice stands for every command whose act needs no walk. The edit widens point 6 to a command whose act already walks the board, a case ADR-074 did not weigh. It widens what ADR-074 decides, so it is a person's to accept, with this record ([COR-064](../../../decisions/core/COR-064-answer-delegate.md) point 6).

**Why it holds with the override or without it.** The routes to a missing card stand without the override: a filing outside the capability, a failed add, a removed card. Where a filing names another board, the sync also gives the issue its card on the configured board, as DEC-019 asks. [project-management:DEC-071-filing-only-configured-board] refuses such a filing in every project with a board.

### Alternatives considered

- **Keep the sync refusing where the board holds the state or the state degrades, and leave each missing card to a person.** Not taken. Each missing card is found from a command's warning, and added by hand, one at a time, on the board or by a command of the host's. This record adds every one in one run, and names what is left, a Status on each card. A project whose agents do its work sets each Status by the host's commands either way, and gains the adds where a person runs the sync at a terminal, or where the person turned the switch on (point 3). Neither writes a Status on a board that holds the state, and the card this record adds changes no issue's position there.
- **Give the card, and write the Status a person names.** Not taken. Where the board holds the state, the capability writes the Status in two places, each from a state it knows. A move writes it from a position it read, through the state machine's transitions and the gates on them (DEC-006, its Implications; ADR-074 point 5). Filing writes the state it files the issue into (ADR-096 point 4). A Status the sync wrote from a person's word would be neither: a write of the state's source from a state the command does not know, which could place an issue in In Progress or Review past the claim that starting work makes. A person dragging a card on the board can do the same, but that is the person's own act on the host, which no command makes or vouches for, and what it means DEC-006 leaves open. A command cannot tell a person's word from an agent's guess either, since an agent passes an option as easily, as DEC-069 weighs for a flag that says a person started a run.
  - **Its narrow form, a Status named in a watched run, and only Todo or Backlog,** the states before work starts, would place no issue past the claim. It is closer to filing's write of the first Status, yet filing knows the issue is new, and the sync does not. It would save a person at a terminal one visit to the board, and nothing for a project run by agents, which sets the Status by the host's commands either way. An issue someone worked on, placed back in Todo by the person's word, would still read as moved back. Not taken: a later record can weigh it, should setting the Status on the board prove too costly.
- **Give the card, and write the Status of the last move the capability's journal records.** The journal records each move the capability makes, so a project whose moves all pass through the capability's commands, such as one run by agents, would get each position back. Not taken. Where the board holds the state, a person moving a card on the board makes a move the journal never sees, so its last entry can lag where the issue stood when its card went. Written on the board, that entry becomes the position every command acts on, the outcome DEC-051 point 6 refuses. A project keeps no journal by default, and a journal kept in one clone records only that clone's moves ([project-management:DEC-049-audit-journal-model] point 1). An issue filed outside the capability has no entry at all. It also costs a read of each issue's journal. A later record can weigh it for a project whose moves all pass through the capability.
- **Give the card, and write the Status filing would: Backlog for an issue with a milestone, Todo otherwise.** Rejected. For an issue someone has worked on, that moves it back, and nothing says so. It is the guess DEC-051 point 6 forbids at reading, written where every command then reads it as the issue's position. Filing writes that state because it is the state it files the issue into. A later run cannot tell which route left an issue without its card, so it cannot know the issue was never worked on.
- **Give the card, and read the Status from the issue's labels and milestone,** as the sync does where the Status is the state's projection. Rejected, for the same reason: where the board holds the state, the labels carry no state, so the read gives only what the milestone gives, the guess above.
- **Let any run that is not watched add the cards where the board holds the state, with the read-back.** A project whose agents do its work would get its cards with no setting. Not taken. The guess would be taken with nobody's consent, in every such run. The read-back names it to whoever ran the command, an agent among them, which cannot tell where the issue stood, and every command acts on it meanwhile. It is the choice to make where the maintainer weighs projects run by agents above the consent.
- **Let a run nobody watches add the cards of the issues it names, with the read-back, and keep a whole run's adds for a watched run.** An agent gets a guarded way to add one card, with no setting. Not taken, as "Why the switch, and not adds for the issues a run names" says. It is the choice to make where the maintainer would rather have no setting than ask a consent.
- **Keep runs nobody watches from adding there, and leave a switch to a later record.** Not taken. Meanwhile a project whose agents do its work would add its cards by the host's own means, with the same guess and no guard (point 3). And DEC-069 rejects the same deferral, "Watched runs only, with a later record for runs nobody watches", since the maintainer asked for a setting rather than a new record.
- **Clear a Status the board set on a card the sync added.** Not taken. It would write the state's source with no move. The read may come before the automation acts, so it clears nothing, or after a person set the Status, so it clears theirs. And it would undo, unasked, an automation the project keeps on its board.
- **Refuse the adds where the board's automation on add is on.** Not taken: whether the host says which automations a board has on, and what each sets, was not measured. Its interface for boards appears to list a board's built-in workflows and whether each is on, which was not checked. A later record can add it once measured.
- **Write Done on a closed issue's card where the board holds the state.** It is the one Status the sync knows without a guess, since a closed issue is Done. Not taken. The capability writes Done itself when its own move closes the issue, after reading where the issue stood (Context). A closed issue's card the sync finds short of Done is one such a move did not reach, and the card keeps where its work stood before the close. The forward cascade reads that origin to tell finished work from a won't-do close (ADR-074 point 4), as DEC-006 needs where it rejects letting a completed close from Todo or Backlog move no ancestor. A sync write to Done would erase it, and change no command's reading, since a closed issue is Done whatever its card says.
- **Restore a card that is archived.** An issue whose only card is archived is on the board (ADR-096 point 5), yet hidden from its views. Not taken. Archiving is how a person takes a card out of view on the host, and the sync cannot tell a card archived on purpose from one archived by mistake. It names each instead (point 4), and the person restores it with one act on the board.
- **Give every missing card or none.** Not taken. A person who wants a few cards would have to decline the whole run, and a project whose people keep some open issues off the board would have to take them all or none. DEC-019 puts every issue on the board, so such a board is drift at warning severity, which stays the project's to mend. Naming the issues lets a person add the cards they want first.
- **Seed, on each card it adds, the board fields filing's hooks seed on a new card.** Not taken. The hooks are filing's, run when an issue is created ([project-management:DEC-024-lifecycle-hooks]). The corpus back-fill already seeds those fields on each card that lacks one, behind a report that is its gate (DEC-037 point 2). A second writer of the same defaults would be one more place that decides them.
- **Name every open issue whose card does not place it.** Taken (point 4). It costs no read beyond the walk, and it lengthens the plan and the report where many cards place nothing.
- **Read back the Status of each card the sync added.** Taken (point 3). It costs one read of the board more in each run that added a card, and sees only what the board set by then.
- **Read the positions in batches of the issues' own cards, beside the walk.** It leaves ADR-074 point 6 as it stands. Not taken, as "Why read the positions from the walk" says: two reads in one run that can disagree. It is the choice to make where the maintainer would keep ADR-074 point 6 as it stands, at a call for each hundred issues.
- **Keep the question's test on standard input alone, and test standard output only for the adds.** No run asked before goes unasked. Not taken, as "Why one test of a watched run" says.
- **A command of its own for missing cards, apart from the sync.** Not taken. It would read the same cards and issues the sync reads, so two commands would each decide which issue has a card, and each would need to meet ADR-096's tests.
- **Have the membership check add the card.** Rejected. The check reports, and writes nothing. It reads one issue at a time, by hand or in the post-check workflow, whose own credential reaches no board (ADR-096). Whether the workflow should add a missing card is left open above.

## Implications

- **The board sync,** where the board holds the state or the state degrades, reads the board and the open issues, and adds a card for each open issue that has none, or for each the run names, writing no Status and no other field, with what points 3 and 4 say. Where no board is configured, it refuses, as point 1 says. Its tests hold:
  - in both cases: that each open issue with no card gets one; that no Status is written on any card; that a board with no Status field does not stop the adds; that a dry run writes nothing; and that a run naming issues writes, plans and reports only for them, and lists a named issue it cannot act on with the reason;
  - where the board holds the state, in a run neither watched nor with the switch on: that it adds no card, with the option that skips the question or without it, and lists what it would add; that it refuses where it has cards to add, and exits as a run with nothing to write where it has none; and that a dry run exits as a dry run does;
  - the switch: that with it on, a run nobody watches adds the cards with the option that skips the question; and that it counts as on only as the default branch holds it, and as off from the working tree's configuration;
  - the read-back: that it reads through the seam, by the card the add answered with; that it names an added card that shows a Status as showing one the sync did not write, and suggests no clearing; that it reports a card it does not find as not confirmed, and a read the board did not answer as that; that where it finds no Status, it says the automation may set one later; and that where it fails, the run's code does not read as the adds not made;
  - where the board holds the state and has no Status field: that the adds go on, that the fault is named once, and that no issue's outcome is reported as a finding;
  - that the plan and the report name each card that does not place its issue, sorted by the state's reader from the walk, and each issue whose only card is archived;
  - that the plan says the added cards will have no Status, and, where the board holds the state, says what point 4 says of the position and the board's automation;
  - that where the Status is the state's projection, the sync writes the Status as point 2 says, and a run that is not watched goes on with the option that skips the question;
  - in every project, that a run whose standard output is not a terminal is asked nothing, and refuses without the option that skips the question.
