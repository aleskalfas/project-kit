**In plain terms:** an open issue can be left with no card on the configured board: filed outside the capability's commands, its add failed at filing, or its card removed. The command that brings the board in line gives such a card only where the board's Status is the state's projection, and refuses where the board holds the state or the state degrades. This record has it give the missing card in every project with a board, and write a Status only where the Status is the projection. Where the board holds the state, the card it adds has no Status, so the issue's position stays undetermined until a person sets it on the board, and no command guesses it. There the command adds cards only with a person at a terminal, and afterwards names any Status the board's own automation set on a card it added, since every command would read that Status as the issue's position.

## Context

**The terms.**

- *The configured board*, *the board holds the state*: as [project-management:DEC-070-filing-another-board] defines them.
- *The Status is the state's projection* where a board is configured and the state is carried off it, and *the state degrades* where a present substrate map leaves the state out or marks it unsupported, so that the capability writes no Status ([project-management:DEC-062-axes-chosen-in-the-map] point 5).
- *The board sync* is the command that brings the board's Status in line with the issues' states (DEC-062 point 5).
- *A missing card* is an open issue's lack of any card on the configured board. An archived card is a card, as [pkit:ADR-096] point 5 counts it.
- *A watched run* is one whose standard input and standard output are both terminals, the test [project-management:DEC-069-when-fixers-start] reads for a person at a terminal.

**What the records say.**

- **Every issue belongs on the configured board from its filing** ([project-management:DEC-019-mandatory-issue-state]). A missing card on an existing issue is drift, at warning severity, for a person to fix. The post-check workflow DEC-019 offers, where a project turns its remediation on, adds a card only on a finding that blocks, and drift never blocks, so it adds no missing card. Whether it should is left to this capability (ADR-096, its Implications on the workflow).
- **Membership is the board flag's question, never carriage's:** whether an issue has its card turns on a board being configured, not on what carries any axis (ADR-096 point 5).
- **Where the board holds the state,** an open issue with no card, whose card has no Status, or whose Status names no open state, has a position that is undetermined. It is reported apart, and never guessed from its labels or its milestone. A seat choosing work skips it ([project-management:DEC-051-axis-carriage-activation] point 6), and a move refuses it ([pkit:ADR-074] point 5).
- **Who writes a Status.** Where the Status is the state's projection, the capability writes it from the issue's state (DEC-062 point 5). Where the board holds the state, a move writes it, from a position it read ([project-management:DEC-006-state-machine-and-cascade], its Implications; ADR-074 point 5), and filing writes the first one, the state it files the issue into (ADR-096 point 4). Where the state degrades, the capability writes none, and the Status stays with the people who move it (DEC-062 point 5).
- **A closed issue's card,** where the board holds the state, keeps where its work stood before the close, which a later move to Done reads to tell finished work from a won't-do close (ADR-074 point 4). A closed issue is Done whatever its card says (DEC-062 point 5).

**The board sync, when this record was written.** Where the Status is the state's projection, it reads every card on the board and every open issue, writes the Status on each card that differs, and adds a card for each open issue that has none, then sets its Status. It asks before its first write, and a run with no terminal writes only with the option that skips the question. Where the board holds the state, or the state degrades, it refuses, and reads nothing.

**A board's own automation.** The host lets a board set a Status by itself, such as when a card is added or its issue is closed, and the capability does not control it. Which automations a board has on, and when each acts, was not measured.

**The routes to a missing card.** An issue filed outside the capability's commands, such as in the host's own interface, gets no card from the capability. Filing reads the board before it creates the issue, and refuses where the board did not answer, yet an add can still fail after the issue exists, and filing then exits saying so (ADR-096 point 4). A person can remove a card on the board. And a filing that names another board, where DEC-019's override stands, puts the issue there in the configured board's place.

**The gap.** Where the board holds the state, nothing but a person gives a missing card. The issue is absent from the board the people place work on, and only a command's warning names it. Where the state degrades, the issue stays workable, since its position is read from the native primitives, yet nothing but a person gives its card either.

**Where the question came from.** The work on filing onto another board ([project-kit#3205](https://github.com/aleskalfas/project-kit/issues/3205)) named it, and left it to [project-kit#3241](https://github.com/aleskalfas/project-kit/issues/3241).

## Decision

**The board sync gives each open issue with a missing card its card on the configured board, in every project with a board, whatever carries the state. It writes a Status only where the Status is the state's projection. Where the board holds the state, it writes none, adds cards only in a watched run, reads back what the board set on each card it added, and names every open issue whose card does not place it.**

### 1. The sync gives every missing card, wherever a board is configured

- **Where.** Where the board holds the state, and where the state degrades, the sync reads every card on the configured board and every open issue, as it does where the Status is the state's projection, and adds a card for each open issue that has none. What carries the state is no ground for a refusal, and nor is a board with no Status field where the sync writes no Status. Where no board is configured, it refuses, whatever the map says.
- **What it leaves alone, and how it asks:** as where the Status is the state's projection. It reads only what it reads there, leaves alone what it leaves alone there, asks before its first write, and writes nothing in a dry run.
- **Only some issues, where the person says so.** A run can name the open issues whose cards it gives, and then gives only theirs.

### 2. It writes a Status only where the Status is the state's projection

- **Where the Status is the state's projection:** from the issue's state, on each card that differs and on each card it adds, as DEC-062 point 5 has the capability keep it.
- **Where the board holds the state:** no Status, on a card it adds or on any other, a closed issue's card included. The issue's position stays undetermined until a person sets its card's Status on the board (DEC-051 point 6).
- **Where the state degrades:** no Status, and the Status stays with the people who move it (DEC-062 point 5).
- **No other field.** On a card it adds, the sync writes no other field of the board. A field the filing's hooks seed on a new card stays unset there, and the corpus back-fill seeds it on each card that lacks it ([project-management:DEC-037-adoption-ceremony] point 2).

### 3. Where the board holds the state, it adds cards only in a watched run, and reads back what the board set

- **Watched only.** The sync adds a card there only in a watched run. A run that is not watched adds none there, with the option that skips the question or without it. It prints its plan, says that the cards are added only with a person at a terminal, gives the command to run there, and refuses as it refuses a run it cannot ask.
- **Read back.** After its adds, it reads each card it added again, and names each that has a Status as one the board set, not the capability, which every command now reads as the issue's position. The person checks it, or clears it, on the board. A read-back the board did not answer is reported as that, never as a card with no Status (ADR-096 point 4).
- **What it cannot see.** Automation that acts after that read is not seen, and the report says so.

Where the Status is the state's projection, or the state degrades, a run that is not watched writes with the option that skips the question. There the board's automation places no issue, since no command reads an issue's position from the Status, and where it is the projection, the sync writes it itself.

### 4. What it says

- **Its plan** names each card it will add, and, where it writes no Status, says that the card will have none. Where the board holds the state, it says that each added issue's position stays undetermined until a person sets its card's Status on the board, and that the board's own automation may set one when the card is added, which every command would then read as the issue's position.
- **Where the board holds the state,** its plan and its report also name each open issue whose card does not place it, with which outcome it is (DEC-051 point 6), and each open issue whose only card is archived, which the board's views hide. It writes nothing to them.
- **After the run,** it names each card it added, and each it could not add, with the board's words, and what the read-back found (point 3). Where the project's hooks seed a board field on a new card, it names the corpus back-fill as the way to seed it on the cards it added.

### What this refines, and what stands

- **Refined in DEC-062 point 5:** its last sentence, "Elsewhere the project's people do both on the board", which reads instead "Elsewhere that command gives each open issue its card, and the project's people set each card's Status on the board."
- **Stands:** DEC-051 point 6, DEC-019's severities and its post-check workflow, ADR-074 point 4's reading of a closed issue's card, ADR-096, and the sync's work where the Status is the state's projection.
- **Not decided here:** whether the post-check workflow adds a missing card on drift, which ADR-096 leaves to this capability. That workflow runs under a credential that reaches no board until ADR-096's setting for one is built ([project-kit#3256](https://github.com/aleskalfas/project-kit/issues/3256)), and runs on each issue opened, with nobody watching, which is the run point 3 keeps the sync from where the board holds the state. It wants a record of its own.

## Rationale

**Why the sync gives the card.** DEC-019 puts every issue on the configured board, and that is the board flag's question, not carriage's. A card needs no position to be given, only the board's answer. The sync already reads every card and every open issue to give the missing cards where the Status is the state's projection, and the same read finds them where it is not. Nothing else in the capability gives such a card where the board holds the state or the state degrades.

**Why no Status where the board holds the state.** The issue's position is undetermined, and DEC-051 point 6 has no command guess it as it reads. A command that wrote a guess onto the board would do worse: the board holds the state, so the guess would then read as the issue's position, and every command would act on it. A person knows where the issue stands, and sets it on the board, as on any card whose Status places it nowhere. The two writers of the Status there each know the state they write: a move reads the position it moves from, and filing writes the state it files the issue into.

**Why the card helps without its Status.**

- **It moves no issue.** An issue with no card and one whose card has no Status are both undetermined (DEC-051 point 6), so the add changes no issue's position.
- **It brings the issue onto the board.** The issue then stands on the board the people place work on, where a card with no Status is shown apart, rather than off the board, named only in a command's warning. What remains is one value set on the board.
- **It gives later reads their witness.** Under ADR-096, a read of an issue's own cards says a card is absent only where the same request finds a card of another issue from the same repository on the board, so a repository with none of its issues on the board reads as a board that did not answer (ADR-096 point 1). Each card the sync adds can witness for the repository's later reads, as ADR-096 says of a card the workflow adds. The sync decides from a whole walk of the board's own cards (ADR-096 point 2), so it can give such a repository its first cards.

**Why a person at a terminal, and a read-back, where the board holds the state.** A board's automation that sets a Status when a card is added would write, onto each card the sync adds, the guess this record refuses to write. Every command would read it as the issue's position, and an issue someone worked on would read as moved back, with nothing saying so. Many cards added in a run nobody watches would take that guess with nobody to see it. In a watched run, the person sees the plan's warning and the read-back's names, and sets each Status on the board. This narrows the guess and does not rule it out: the read-back misses automation that acts later, and a terminal tells only that one is attached, not that a person watches, as DEC-069 point 5 says of its own test.

**Why name every card that does not place its issue.** After the add, the membership check passes the issue, yet its position is still undetermined. Only a seat's warning on a Task, a move's refusal or a close's refusal names it then, and a container whose card has no Status is named by nothing. The sync reads every card already, so naming them costs no read, and a later run names each card an earlier one added until a person sets its Status.

**Why only when someone runs it.** As where the Status is the state's projection: DEC-019 keeps a scan of every issue's board state out of each command, and the sync is the command a person runs to bring the board level.

**Why DEC-062 is refined, not superseded in part.** DEC-062 point 5 decides who writes the Status, and this record leaves that whole: the capability writes none where the state degrades, and where the board holds the state only a move or filing writes it. Its last sentence says who gives the card and the Status before a project binds its state to its board. This record has the sync give the card there, and leaves the people their own way. So the edit widens who may give a card, changes nothing DEC-062 decides of the Status, and leaves DEC-062 reading true, which is a refinement in place. A partial supersession would leave "the project's people do both" standing as it stood, false to read, under a top line that overturns it. The sync's refusal where the board already holds the state is the command's, written in its reference, and no accepted record decides it, so giving the card there overturns nothing.

**Why it holds whether or not DEC-071 is accepted.** The routes to a missing card stand without the override: a filing outside the capability, a failed add, a removed card. Where the override stands, the sync also gives an issue filed onto another board its card on the configured board, as DEC-019 asks, and as the sync did before this record where the Status is the state's projection.

### Alternatives considered

- **Keep the sync refusing where the board holds the state or the state degrades, and leave each missing card to a person.** Not taken. Each missing card is found from a command's warning, and added by hand, one at a time, on the board or by a command of the host's. This record adds every one in one run, and names what is left, a Status on each card. A project whose agents do its work sets each Status by the host's commands either way, and gains the adds only where a person runs the sync at a terminal (point 3). Neither writes a Status on a board that holds the state, and the card this record adds changes no issue's position there.
- **Give the card, and write the Status a person names.** Not taken. Where the board holds the state, each write of the Status the capability makes is a move, from a position it read, through the state machine's transitions and the gates on them (DEC-006, its Implications; ADR-074 point 5). A Status the sync wrote from a person's word would be a write of the state's source that is no move, and could place an issue in In Progress or Review past the claim that starting work makes. A person dragging a card on the board can do the same, but that is the person's own act on the host, which no command makes or vouches for, and what it means DEC-006 leaves open. A command cannot tell a person's word from an agent's guess either, since an agent passes an option as easily, as DEC-069 weighs for a flag that says a person started a run.
  - **Its narrow form, a Status named in a watched run, and only Todo or Backlog,** the states before work starts, would place no issue past the claim. It would save a person at a terminal one visit to the board, and nothing for a project run by agents, which sets the Status by the host's commands either way. An issue someone worked on, placed back in Todo by the person's word, would still read as moved back. Not taken: a later record can weigh it, should setting the Status on the board prove too costly.
- **Give the card, and write the Status of the last move the capability's journal records.** The journal records each move the capability makes, so a project whose moves all pass through the capability's commands, such as one run by agents, would get each position back. Not taken. Where the board holds the state, a person moving a card on the board makes a move the journal never sees, so its last entry can lag where the issue stood when its card went. Written on the board, that entry becomes the position every command acts on, the outcome DEC-051 point 6 refuses. A project keeps no journal by default, and a journal kept in one clone records only that clone's moves ([project-management:DEC-049-audit-journal-model] point 1). An issue filed outside the capability has no entry at all. It also costs a read of each issue's journal. A later record can weigh it for a project whose moves all pass through the capability.
- **Give the card, and write the Status filing would: Backlog for an issue with a milestone, Todo otherwise.** Rejected. For an issue someone has worked on, that moves it back, and nothing says so. It is the guess DEC-051 point 6 forbids at reading, written where every command then reads it as the issue's position. Filing writes that state because it is the state it files the issue into. A later run cannot tell which route left an issue without its card, so it cannot know the issue was never worked on.
- **Give the card, and read the Status from the issue's labels and milestone,** as the sync does where the Status is the state's projection. Rejected, for the same reason: where the board holds the state, the labels carry no state, so the read gives only what the milestone gives, the guess above.
- **Let a run that is not watched add the cards where the board holds the state, naming in its report each Status the board set.** A project whose agents do its work would get its cards with no person at a terminal. Not taken. The report would name the guess after it was written, in output nobody may read, and every command would act on it meanwhile. Such a project adds those cards by the host's own means, as before this record, or has a person run the sync at a terminal. It is the choice to make where the maintainer weighs projects run by agents above the guess.
- **Clear a Status the board set on a card the sync added.** Not taken. It would write the state's source with no move. The read may come before the automation acts, so it clears nothing, or after a person set the Status, so it clears theirs. And it would undo, unasked, an automation the project keeps on its board.
- **Refuse the adds where the board's automation on add is on.** Not taken: whether the host says which automations a board has on, and what each sets, was not measured. A later record can add it once measured.
- **Write Done on a closed issue's card where the board holds the state.** It is the one Status the sync knows without a guess, since a closed issue is Done. Not taken. The card of a closed issue keeps where its work stood before the close, which a later move to Done reads to tell finished work from a won't-do close (ADR-074 point 4). A closed issue is Done whatever its card says, so the write would erase that, and change no command's reading.
- **Restore a card that is archived.** An issue whose only card is archived is on the board (ADR-096 point 5), yet hidden from its views. Not taken. Archiving is how a person takes a card out of view on the host, and the sync cannot tell a card archived on purpose from one archived by mistake. It names each instead (point 4), and the person restores it with one act on the board.
- **Give every missing card or none.** Not taken. A person who wants a few cards would have to decline the whole run, and a project whose people keep some open issues off the board would have to take them all or none. DEC-019 puts every issue on the board, so such a board is drift at warning severity, which stays the project's to mend. Naming the issues lets a person add the cards they want first.
- **Seed, on each card it adds, the board fields filing's hooks seed on a new card.** Not taken. The hooks are filing's, run when an issue is created ([project-management:DEC-024-lifecycle-hooks]). The corpus back-fill already seeds those fields on each card that lacks one, behind a report that is its gate (DEC-037 point 2). A second writer of the same defaults would be one more place that decides them.
- **Name every open issue whose card does not place it.** Taken (point 4). It costs no read, since the sync reads every card already, and it lengthens the plan and the report where many cards place nothing.
- **Read back the Status of each card the sync added.** Taken (point 3). It costs one read of the board more in each run that added a card, and sees only what the board set by then.
- **A command of its own for missing cards, apart from the sync.** Not taken. It would read the same cards and issues the sync reads, so two commands would each decide which issue has a card, and each would need to meet ADR-096's tests.
- **Have the membership check add the card.** Rejected. The check reports, and writes nothing. It reads one issue at a time, by hand or in the post-check workflow, whose own credential reaches no board (ADR-096). Whether the workflow should add a missing card is left open above.

## Implications

- **The board sync,** where the board holds the state or the state degrades, reads the board and the open issues, and adds a card for each open issue that has none, or for each the run names, writing no Status and no other field, with what points 3 and 4 say. Where no board is configured, it refuses, as point 1 says. Its tests hold:
  - in both cases, that each open issue with no card gets one, that no Status is written on any card, that a board with no Status field does not stop it, that a dry run writes nothing, and that a run naming issues adds only their cards;
  - where the board holds the state, that a run that is not watched adds no card, with the option that skips the question or without it, and lists what it would add; that the read-back names a card the board gave a Status, and reports a read-back the board did not answer as that; and that the plan and the report name each card that does not place its issue, and each issue whose only card is archived;
  - that the plan says the added cards will have no Status, and, where the board holds the state, says what point 4 says of the position and the board's automation;
  - that where the Status is the state's projection, the sync writes the Status as point 2 says, and a run that is not watched goes on with the option that skips the question.
- **The messages that report a missing card** name the sync among the ways to add it: a move's refusal, a seat's warning, the membership check's finding and filing's report of a failed add. Where the board holds the state, they say that the sync adds it only at a terminal, and that the Status is set on the board.
- **The sync's reference,** its own help and the capability's README, says where it runs and what it writes in each case. It changes with the build, once this record is accepted.
- **The edit to DEC-062,** made once this record is accepted: point 5's last sentence reads "Elsewhere that command gives each open issue its card, and the project's people set each card's Status on the board", with the refinement pointer *(refinement per [project-management:DEC-072-sync-gives-missing-cards])* on it. The rest of DEC-062 stays as it stood.
- **No other record is edited.** DEC-019, DEC-051 point 6, ADR-074 and ADR-096 stand, and this record follows them.
- **A surface change** for the capability, once built. A call that refused before now writes, after the person's consent, where the board holds the state or the state degrades. Where the state degrades, a run with no terminal and the option that skips the question now adds cards, where it refused before. The build's changeset declares it. It changes no state a project holds and no option's signature, and the option that names issues is new, so it owes no migration.
- **Acceptance:** this record refines the accepted DEC-062, so accepting it needs the maintainer's sign-off.
