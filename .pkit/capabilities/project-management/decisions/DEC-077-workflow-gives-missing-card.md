title: The post-check workflow gives a card missing at filing through the board sync, where the board does not hold the state
status: proposed
date: 2026-11-16
author: Aleš Kalfas <kalfas.ales@gmail.com>
---

**In plain terms:** an issue filed outside the capability's commands, or whose add to the board failed at filing, opens with no card on the configured board. The post-check workflow, which a project copies from the capability's template, checks each issue opened and reports the missing card, yet adds none, even where the project turned its remediation on: that remediation runs only on a finding that blocks, and a missing card never blocks. This record has the workflow give the card at filing, where the project turned its remediation on and gave it a credential the board answers. The workflow makes no add of its own. It runs the board sync for that one issue, so the sync's rules hold, and only where the board does not hold the state. Where the board's Status is the state's projection, the card gets the Status the issue's state gives. Where the state degrades, it gets none. Where the board holds the state, the workflow adds no card and runs no sync, whatever the project's switch for the sync's runs with no terminal says, since a Status the board's own automation set on the card would read as the issue's position. It reports the missing card there, naming the sync, and a later record decides that case once what that automation writes has been measured. The sync's run keeps the membership gate, as every command that writes does. Under a person's token it runs as that person, and passes a closed gate where that person is listed: setting the token with the remediation on is the project's consent to that, for the opened issue's card alone. A repository variable turns the sync at filing off at once, and leaves the check running. The workflow's comment on the issue says what the sync did. The workflow adds no card on an edit or a reopening, or for any other finding.

## Context

**The terms.**

- *The configured board*, *the board holds the state*, *the Status is the state's projection*, *the state degrades*, *the board sync*, *a missing card*, *a run with no terminal* and *the maintainer*: as [project-management:DEC-072-sync-gives-missing-cards] defines them. *The project's switch* is the setting DEC-072 point 3 decides, which lets the board sync's runs with no terminal add cards where the board holds the state.
- *Where the board does not hold the state* is the case that [project-management:DEC-070-filing-another-board]'s term leaves, read in a project with a configured board: where the Status is the state's projection or the state degrades. There no command reads an issue's position from a Status the board's automation sets on a card the sync adds, so a run with no terminal adds cards on the option that skips the question alone, and reads no switch (DEC-072 point 3, its last paragraph).
- *The post-check workflow* is the workflow [project-management:DEC-019-mandatory-issue-state] offers as a template. A project copies it into its own repository, and the host runs it on each issue opened, edited or reopened, with no terminal and nobody watching. *Its remediation* is the toggle DEC-019 gives it, off as the template ships, which the project turns on in its own copy to have the workflow mend what it finds.
- *The membership check* is the check, among an issue's validation, that the issue has its card on the configured board. It finds a card missing only where the same request shows the board answered, and otherwise reports that the board did not answer ([pkit:ADR-096] point 5).
- *The membership gate* is the check of the member list that [project-management:DEC-021-team-membership-gate] decides. Where the list names a member, the gate is closed, and refuses whoever no entry names. It is not the membership check.
- *The token's owner* is the person whose token the project set as the board's credential, where it set a person's token.
- *At filing* means in the workflow's run on the event of the issue's opening, whenever the host makes that run (point 7).

**What the records say.**

- **Every issue belongs on the configured board from its filing** (DEC-019). DEC-019 has the workflow, where its remediation is on, invoke the analogous mutation on a finding that rejects the issue at filing, and only comment on drift on an existing issue. Among the three layers of defence, [project-management:DEC-020-methodology-as-executable-commands] gives the workflow the issues filed outside the capability's commands, on the events of their opening and editing, to detect and optionally remediate, and keeps a scan of every issue's state out of each command ("Three-layer defence model").
- **As the template ships,** the membership check reports a missing card at the drift severity in every run, at filing too, so it never blocks. A copy that remediates only on a finding that blocks adds no missing card (ADR-096, its Implications on the workflow). The template's remediation step makes an add of its own on any event whose run found a finding that blocks. So it adds the card of an issue off the board only where another finding blocks, on any of those events, and writes no Status on it in any kind of project (the template, its step "Auto-remediate board membership").
- **The workflow's own token reaches no board,** so the template has a setting for a credential the board answers, unset as it ships. For a person's board, the one credential the template and the capability's README offer is a person's token, which the template's words name as the token that reads the board and, for the remediation, adds to it. For an organisation's board, they offer an App's (the template, its header). The check's step and the remediation's step both hold it. Whether a copy remediates, on an issue off the board or on one the board did not answer for, ADR-096 leaves to this capability. Where one does, a card it adds is a witness for the repository's later reads (ADR-096 point 1, and its Implications on the workflow). A credential set there reaches the tools the job fetches at run time, in each step that holds it, and anyone who can open an issue starts the job (ADR-096, "What the setting exposes"). Where the substrate map binds an axis to the board, a check that reads that axis fails each issue under a credential the board does not answer (ADR-096, its Implications on the workflow; the template, its header).
- **The board sync** gives every missing card in every project with a board, and writes a Status only where the Status is the state's projection. A run can be limited to the issues it names, and still reads every card on the board and every open issue. Where the board does not hold the state, a run with no terminal writes on the option that skips the question, and reads no switch. Where the board holds the state, it adds cards only in a run at a terminal or with the project's switch on, and reads each card it added back (DEC-072 points 1 to 3). It takes the membership gate at its startup, as every command that writes does (DEC-021).
- **State issues.** A state issue holds no work, and the rules for an issue of work do not bind it, its place on the board among them ([project-management:DEC-058-state-issues] point 3). The sync passes over a state issue it is named for, and says that a state issue takes no card. The membership check, as it ships, does not leave a state issue out, so it reports one off the board.
- **The switch's consent and its hold.** Turning the project's switch on consents for every session that runs the sync in the project, a person's or an agent's. Each command of the capability that merges a change into the default branch holds a change that turns it on, and says in those words what turning it on means. The switch turns off at once from the working tree a run starts from (DEC-072 point 3). [project-management:DEC-069-when-fixers-start] gives a switch of the same form for a fixer's runs nobody watches (its point 4), and holds that a grant given under words that did not say it reaches runs nobody watches counts for none of them (its point 3).
- **Who a run is, under the gate.** Where the host answers that the credential acts as a user's account, that account's login alone is the invoker (DEC-021, "Identity resolution"), and a session under a member's credential acts as that member, whoever it works for (its Implications). So a workflow that runs a gated command passes a closed gate under a credential that acts as an account the list names, such as a service identity added to it like any member, or, where the host does not answer that its credential acts as a user's account, with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list. CI is not exempt from the gate by design (DEC-021, its Implications, "CI invocations"). DEC-021 did not weigh a credential that anyone who can open an issue puts to work. How the workflow's check passes a closed gate is decided apart ([project-kit#3290](https://github.com/aleskalfas/project-kit/issues/3290)).
- **What a board's own automation writes** to the Status, and when, was not measured (DEC-072, Context). It is left to [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272).

**What the host's documentation says,** as read on 2026-11-16:

- **An event the workflow's own token causes starts no run** of a workflow, save for a few kinds of event, and an issue's opening is not among them (on the workflow's token, "When GITHUB_TOKEN triggers workflow runs").
- **A run started again** uses the commit and the reference of the event that first started it (on re-running workflows and jobs). The page does not say whether it reads the repository's variables and secrets again.
- **A concurrency group** runs one job or run at a time. By default it keeps at most one waiting, and cancels the waiting one when another comes. With `queue: max`, it keeps up to 100 waiting, in order, and cancels any beyond; `queue: max` cannot be combined with cancelling the run in progress (on controlling the concurrency of workflows and jobs).
- **Requests made with a person's token** count toward that person's own budget of requests, beside those that apps make on the person's behalf. The host's secondary limits bound the requests made at once and the requests made each minute (on the REST API's rate limits).

**Where the question came from.** DEC-072 left it to a record of its own ("Not decided here"), in [project-kit#3271](https://github.com/aleskalfas/project-kit/issues/3271).

## Decision

**At filing, where the board does not hold the state, and where the project turned the post-check workflow's remediation on and gave it a credential the board answers, the workflow gives an issue the membership check finds without its card, or for which the board did not answer, its card by running the board sync for that issue alone. Where the board holds the state, it runs no sync and adds no card, and reports the missing card, naming the sync. The sync's run keeps the membership gate, and under a person's token runs as that person, which the project consents to by setting the token with the remediation on. A repository variable turns the sync at filing off at once, and leaves the check running. The workflow makes no add of its own, adds no card on any other event or for any other finding, and says on the issue what the sync did.**

### 1. At filing, the workflow runs the board sync for the issue

- **When.** In its run at the issue's opening, where the membership check finds that the issue has no card on the configured board, or that the board did not answer for it, whatever severity the finding takes.
- **Where.** Only where the board does not hold the state (point 2).
- **How.** It runs the board sync, named for that issue alone, with the option that skips the question. The sync decides from its own whole walk of the board whether the issue has a card (ADR-096 point 2), so the workflow decides nothing of the card itself.
- **Only where the project asked.** Only where the project turned the remediation on in its copy, only under the credential the project set for the board, and only where the repository variable of point 3 does not turn the sync off. With no credential set, the workflow runs no sync, and its comment says that it adds a card only under a credential the board answers. With the variable turning the sync off, it runs no sync, and its comment names the variable.
- **At filing alone.** On an edit or a reopening, the workflow adds no card, and reports a missing card as the membership check does, naming the sync. No other finding, one that blocks among them, leads it to add a card.

### 2. What the workflow does in each kind of project

- **Where the Status is the state's projection,** the sync adds the card and writes the Status the issue's state gives, on the option that skips the question alone (DEC-072 point 2, and point 3, its last paragraph).
- **Where the state degrades,** it adds the card and writes no Status, on that option alone.
- **Where the board holds the state,** the workflow runs no sync and adds no card, whatever the project's switch says. Its comment carries the membership check's finding, which names the sync, run for the issue, and says that the sync adds a card there only in a run at a terminal or with the switch on (DEC-072 point 4). The comment also says that the workflow adds no card there. Whether it should is left to a later record, once [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272) has measured what the board's automation writes to the Status.
- **Where no board is configured,** the membership check makes no call to a board and finds nothing, so the workflow runs no sync.
- **How the workflow tells which.** The build must have the workflow read what the board's Status is to the project by the same reading the sync makes, today `board_status.role`, so that the two never part. DEC-062 point 5 decides what the three kinds are. The reading reads the project's configuration and its substrate map, and asks the board nothing, so it needs no credential, and runs in a step that holds none (ADR-096, "What the setting exposes").
- **Where the reading fails,** such as on a configuration or a substrate map it cannot read, the workflow runs no sync. Its comment says that the workflow could not tell what the board's Status is, in the reading's own words, and names the sync, run for the issue.

### 3. The consent where nobody watches, and turning it off

- **The project's own.** Where the board does not hold the state, the consent is the project's: the remediation it turned on in its copy, and the credential it set. Under that credential, the sync's run acts as the account the credential acts as, which under a person's token is the token's owner (point 5). Its writes are those the sync makes in any run with no terminal on the option that skips the question, an agent's among them (DEC-072 point 3), for the opened issue's card alone. Setting the credential with the remediation on is the project's consent to both: to those writes, and to their being made as that account. The workflow asks no consent beyond them.
- **No switch counts for the workflow's runs.** The workflow runs no sync where the board holds the state, and elsewhere the sync reads no switch (DEC-072 point 3). So the project's switch, turned on under words that name the sessions that run the sync, counts for none of the runs that anyone who can open an issue starts. Nor does DEC-069's switch, which consents to a fixer's unconfined runs.
- **Off at once, with the check kept.** A repository variable, `PM_SYNC_AT_FILING`, set to `off`, turns the sync at filing off. The workflow then runs no sync, and its check, its reads of the board and its comment go on as before. It is one act in the repository's settings, and needs no change to reach the default branch. The variable only turns the sync off. Unset, or set to anything else, it leaves the decision to the remediation's toggle, so turning the sync on still takes a change of the project's copy that reaches the default branch.
- **The other ways off.** The host runs the workflow from the copy the default branch holds, so turning the remediation off in that copy takes a change that reaches the default branch. Two other acts turn the sync off at once, each at a cost:
  - **Removing the credential** from the repository's settings. The membership check then reports the board unanswered on each issue, and where the substrate map binds an axis to the board, a check that reads that axis fails each issue (Context).
  - **Disabling the workflow** on the host, which stops the check too.
- **A run started again** runs from the commit of the event it carries (Context). So a change that has reached the default branch since then does not reach it, whether that change turns the remediation off or removes the token's owner from the member list. Whether such a run reads the variable, or the repository's secrets, as they stand when it starts again was not measured (Implications).
- **As the template ships,** the remediation is off and no credential is set. A project's copy is its own (DEC-019), so a copy made earlier keeps its own steps until the project copies the template again.

### 4. The workflow says on the issue what the sync did

- **Its comment** on the issue carries what the sync reported for the issue: the card added, with the Status the sync wrote where the Status is the state's projection, or not added, in the sync's words. Where the membership gate refused the sync, it says so (point 5).
- **What the comment publishes.** The comment is as public as the issue. It carries the sync's report for that issue alone, including the board's own words where an add failed. So a project whose board is private and whose repository is public publishes them with each such filing, as it publishes the check's findings.
- **A card not added fails nothing.** The issue's check ends as the validation's findings make it, whatever the sync's exit code.

### 5. The sync's run keeps the membership gate

- **As every command that writes.** The sync takes the membership gate at its startup in the workflow's run as in any other, and this record leaves DEC-021 as it stands: CI is not exempt. Who the run is follows from the credential, as DEC-021 resolves the invoker ("Identity resolution").
- **Under a person's token,** the host answers that the credential acts as the token's owner's account, so that login alone is the invoker. The sync runs as the token's owner, and passes a closed gate wherever the member list names them, which for a person's board is the common case, since the token's owner is most often the board's. So with the remediation on, each issue anyone opens starts a run of the sync as the token's owner. Setting the token with the remediation on is the project's consent to that, limited to the opened issue's card, where the board does not hold the state (point 3).
- **Under an App's token,** the host does not answer that the credential acts as a user's account. Behind a closed gate, the run passes only with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list, as DEC-021 lets such a workflow pass. The template sets none for the sync's step as it ships. A project that sets one for that step consents as above, for the identity it names.
- **No identity beyond the credential.** The workflow gives the sync's step no identity beyond the credential the project set for the board. Whatever lets the workflow's check through a closed gate, where it is a setting beyond that credential, reaches the sync's step only where a record says so (#3290).
- **A refusal.** Where the gate refuses the sync, the sync adds no card, and the issue's check ends on its findings (point 4). The comment says that the membership gate refused the sync, and names the ways DEC-021 gives a workflow through it.
- **A check the gate refuses.** Where the gate refuses the check itself, the check makes no finding, so the workflow runs no sync (point 1).

### 6. The cost, accepted by name

- **One walk per run.** Each run of the sync the workflow makes reads every card on the board and every open issue (DEC-072 point 1). It runs on a filing whose card the membership check finds missing, or for which the board did not answer, and where the board holds the state, the workflow makes no walk.
- **Where it is more.**
  - A burst of filings outside the capability's commands, such as a loop of raw issue creations, a bulk transfer or an import, starts one run for each, at once, each with its whole walk.
  - Under a credential whose reads of an issue's own cards find no witness, though the board answers a walk, every filing pays the walk, the capability's own whose card is in place among them, and the sync then finds the card and writes nothing. A repository's first issues on a shared board pay it until a card gives the witness.
  - A state issue filed, such as a seat's, is reported off the board by the membership check (Context), so its filing pays a walk, and the sync then passes it over, saying that a state issue takes no card. This record accepts that: state issues are filed rarely, one for each piece of shared state, and the sync's words on the comment tell its reader that no card is owed.
- **Who pays.** The walks spend the budget of requests the host gives the credential. Under a person's token, that is the token's owner's budget for all their work, which every request made on their behalf counts toward, not this workflow's alone (Context), and anyone who can open an issue then spends it. Under an App's token, the App's. Each walk also lengthens the run, so in a private repository it spends the project's minutes on the host's runners.
- **Accepted.** The project takes the cost on by turning the remediation on and setting the credential, and ends it at once with the variable, or with the other acts point 3 names. Serialising the runs, and bounding a named run's read, are weighed below.

### 7. What this leaves open

- **Filing's own add in flight.** The capability's filing command creates the issue before it adds the card, so the workflow can read the board before that add, and both then add. That the host answers an add of an issue already on the board with the card it has was not measured (DEC-072, Context). Where it does not, the filing can report a failed add for an issue the workflow gave its card.
- **An issue moved into the repository.** Whether the host reports an issue transferred into the repository as opened was not measured. Where it does, that run counts as at filing, and the workflow treats the issue as any other opened.
- **At filing is the event, not a time.** A run a person starts again from the host's interface, or one the host held in its queue for hours, still carries the opening. Such a run can give again a card a person removed in between, and a run started again also runs from the copy of the workflow and the member list as they stood at the event (point 3). The run started again is a person's act, and the long queue is nobody's. This record accepts both, since where the board does not hold the state the card places no issue (below), and DEC-019 puts every issue on the board.
- **An issue another workflow opens under its own token** starts no run of this workflow, since the host makes no run from an issue's opening that token causes (Context). Its missing card is one this layer never sees, and a person's run of the sync gives it.
- **Anyone who can open an issue starts the run,** so an issue anyone opens gets its card, as DEC-019 puts every issue on the board. The card places no issue: where the board does not hold the state, every command reads an issue's position from the native primitives, card or not (DEC-062 point 5), so an issue a non-participant opened is no more workable for its card.

### What this refines, and what stands

- **Refined in DEC-019:** the mutation its workflow invokes for an issue that opens with no card on the configured board, which is the board sync, run for that issue on the membership check's finding at filing, whatever its severity, where the board does not hold the state, and none where it does (Implications).
- **Stands:** DEC-019's severities, DEC-021, DEC-069, ADR-096 and DEC-072. This record's edits to DEC-072, in its "Not decided here" and in its rejected alternative "Have the membership check add the card", name this record where DEC-072 left the question open, and change nothing it decides. DEC-072's switch counts for the sessions that run the sync, as its point 3 says, and for none of the workflow's runs (point 3).
- **Not decided here:**
  - **Whether the workflow gives the card where the board holds the state,** left to a later record once #3272 has measured the board's automation (point 2).
  - **Whether a missing card at filing fails the issue's check,** which DEC-019's schema rejects and the check as shipped warns of. The check runs before the sync, so a record that has it fail also decides whether the workflow checks the issue again after the sync gives its card.
  - **Whether the membership check leaves a state issue out,** as DEC-058 point 3 leaves a state issue's place on the board out of the rules for an issue of work. Until it does, a state issue's filing pays a walk (point 6).
  - **Whatever else the remediation mends.**

## Rationale

**Why the workflow gives the card at filing.** DEC-019 puts every issue on the configured board from its filing, and the workflow is the layer that catches the filings the capability's commands do not make (DEC-020). As the template ships, its remediation reaches a missing card only where another finding blocks. At filing, a missing card is nobody's choice: the issue was filed outside the capability's commands, or filing's add failed. A card given then also gives a repository with none of its issues on the board a witness for its later reads (ADR-096 point 1).

**Why through the board sync.** DEC-072 keeps one command that gives missing cards, and rejects a second, since each would decide which issue has a card, and each would need to meet ADR-096's tests. The sync already writes what each kind of project asks, and limits a run to the issues it names. An add of the template's own would have to restate those rules, or break them: a card with no Status where the projection wants one, or a card added where the board holds the state, as the template's step adds one today on a finding that blocks (Context). It would also reach past the command that owns the write, which DEC-020's layer discipline warns against. Limited to the issue, the run writes nothing on another issue with nobody watching, and two runs for issues opened together each write only their own.

**Why only where the board does not hold the state.** There a card the sync adds places no issue a command acts on: where the Status is the state's projection, the sync writes it itself, and where the state degrades, no command reads a position from the Status (DEC-072, "Why no consent where the state degrades"). So the add is a write DEC-072 lets any run with no terminal make, and a project that turned the remediation on and set the credential asked for it.

**Why no card yet where the board holds the state.** There the sync adds cards in a run with no terminal only under the project's switch, which consents to the board's own automation setting a Status that every command then reads as the issue's position (DEC-072 point 3). Carrying that consent to the workflow's runs would widen it past what its hold and its words cover:

- **Nothing holds the change that would widen it.** Each command that merges holds a change to the project's configuration that turns the switch on (DEC-072 point 3), and nothing holds a change to the project's copy of the workflow. So where the switch is on, an agent's change that copies the template with its remediation on could land under an authorisation given up front. From then on, every issue anyone opens would get its card with nobody watching. DEC-069 holds its switch at the merge for that reason: a change of the project's may be an agent's (its Rationale, "Held at the merge").
- **The words named other runs.** The switch's words consent for the sessions that run the sync, a person's or an agent's, and say nothing of runs that anyone who can open an issue starts. DEC-069 point 3 has a grant given under words that did not say it reaches a run count for none of those runs.
- **It would place strangers' issues.** A Status the automation sets on such a card places the issue among the work every command acts on (DEC-051 point 6), though its author may be no participant. Neither record weighed that.
- **Turning it off at once would not reach them.** The switch turns off at once from the working tree a run starts from (DEC-072 point 3). The workflow's working tree is the host's checkout of the default branch, so turning the switch off for the workflow would take a change that reaches the default branch.
- **Reading it would take the backbone.** The sync reads the switch through the backbone, which the template does not install, so the job would fetch one more tool at run time, in a step that holds the board's credential (ADR-096, "What the setting exposes").

A consent of the workflow's own, held at the merge, could answer the first two (Alternatives). It would still consent to a guess nobody can yet describe, since what the board's automation writes, and when, was not measured. So the workflow reports there, naming the sync. A person, or a run under the switch, gives the card, and a later record decides once #3272 has measured the automation.

**Why where the board did not answer too.** The membership check reads the issue's own cards, and finds a card absent only where it sees another issue's card from the same repository as a witness (ADR-096 point 1). Where the repository has no card on the board yet, as with its first issues on a shared board, it reports that the board did not answer. The sync decides from a whole walk of the board, which reads the board itself and needs no witness (ADR-096 points 1 and 2), so it gives the card there. Where the board truly did not answer, the sync fails and says so.

**Why only under the credential the project set.** The workflow's own token reaches no board (ADR-096), so a sync under it would fail on every filing.

**Why the remediation, with the credential, is the consent where the board does not hold the state.** The write is of a kind the sync makes in any run with no terminal on the option that skips the question, since none of these writes sets a Status a command reads as a position it did not know (DEC-072 point 3, its last paragraph). Three things about it are new, and the conclusion has to hold against each:

- **Who starts it.** Anyone who can open an issue, where until now a person or an agent of the project started each run of the sync. Each run is limited to the issue opened and makes only its card, so the issue's author chooses nothing beyond the card DEC-019 gives every issue.
- **Under whose identity.** The account the credential acts as: under a person's token, the token's owner, with the owner's standing behind a closed gate (point 5). The template's words already name the person's token as the add's credential under the remediation (Context). The build has them say, where the project sets the token, that the sync then runs as its owner and passes a closed gate where they are listed (Implications).
- **The credential and the toggle.** A credential set only so the check can read the board becomes the write's credential once the remediation is on, where its scopes allow writes. And the toggle is a change an agent can land under an authorisation given up front, since no command that merges holds it. An agent's change that turns it on lets the workflow make, as the token's owner, only the write the owner's own run with no terminal may make already, for the issue opened alone, and the variable turns it off at once with the check kept (point 3). A project that wants its credential to read and nothing added leaves the remediation off, or sets a token whose scopes only read, under which the sync's add fails and says so.

Unlike the switch where the board holds the state, none of this consents to a guess, so it needs no hold at the merge, as the option that skips the question has none.

**Why the sync keeps its gate, and runs as the token's owner.** The sync writes to the board, and DEC-021 gates every command that writes, CI's runs included by design. Under a person's token, DEC-021 already says who the run is: the account the credential acts as, whoever the session works for (its "Identity resolution" and its Implications). What it did not weigh is a credential that anyone who can open an issue puts to work: each issue opened then starts a write as the token's owner, which a closed gate passes wherever the list names that owner. This record weighs that for this one write, and lets it through, for three reasons:

- The write is limited to the opened issue's card, so whoever opens the issue chooses which card is added, and nothing else.
- Where the board does not hold the state, that card places no issue a command acts on (point 7), so an issue a non-member opened is no more workable for its card than it was without one.
- The project consents to it where it sets the token, under words the build gives the template and the README (Implications).

Exempting the sync from the gate, or giving its step whatever lets the check through, would decide for DEC-021 what it leaves to each workflow's setup. So the step holds the credential alone, and under an App's token a closed gate refuses it until the project sets an identity for that step.

**Why a variable turns it off, and only off.** Of the acts the host gives, removing the credential fails each issue's check where a check reads an axis the map binds to the board, and disabling the workflow stops the check. Neither turns the sync off and leaves the workflow doing its first job. A variable in the repository's settings is read when a run starts, and needs no change to reach the default branch. So a person who sees the sync go wrong, in a burst or under a token whose budget runs low, stops it with one act and keeps the check. It turns the sync on nowhere: an on read from a setting no change carries would take the remediation, which a change reaching the default branch turns on, out of the path the project reviews. Its cost is one more name, which the template reads and the README names.

**Why at filing alone.** On an edit or a reopening, a missing card may be a person's act, a card removed, or an older failure, and the workflow cannot tell which. DEC-019 keeps drift on an existing issue for a person to mend, at the warning severity, while DEC-020 gives the workflow the filings made outside the commands, caught at their event. An edit is no act on the board, and a card added again on each edit would undo a person's removal with nobody watching. An issue whose run at filing gave no card gets it when a person runs the sync.

**Why a walk per filing is not the scan DEC-019 keeps out.** DEC-019 and DEC-020 keep a scan of every issue's board state out of each command, since it would make every command slow, and give the filings that bypass the commands to the workflow, a check made after the event. The sync's walk runs in the workflow, off every command's path, and only on a filing whose card the check could not find, where the project asked for it. So no command waits on it, and its cost falls on the project that turned it on (point 6).

**Why no other finding.** The add mends one finding, the missing card. A finding that blocks for another reason, such as a missing label, says nothing of the board, and a card added for it mends nothing that finding names.

**Why the comment carries the sync's words.** The workflow already comments on an issue whose check found anything, and a missing card is such a finding, so the comment adds no write the run would not make. Without the sync's words, the comment would report an issue off the board that the workflow then gave its card.

**Why a card not added fails nothing.** A missing card is drift, which never blocks as the template ships, and an add the board did not make, or the gate refused, is no fault of the issue's, as a board that did not answer is none of the issue's under the membership check (ADR-096 point 5).

**Why the cost is accepted.** The walk is what lets the sync decide a card's absence with no witness (ADR-096 point 2), the case "Why where the board did not answer too" gives the card in. Bounding a named run's read would change every named run of the sync, and still walk in that case. Serialising the runs would bound how many walks run at once, yet save no walk, delay every card in a burst, and drop the runs the host's queue cannot hold, where a burst that trips the host's limits without it leaves cards that one run of the sync gives (Alternatives). The cost falls only where the project turned the remediation on and set the credential, and only on filings whose card the check could not find, so the project that pays it chose it, and the variable ends it at once.

### Alternatives considered

- **Keep the workflow reporting only.** Taken where the board holds the state, until a later record decides (point 2). Not taken where the board does not hold the state: there the add places no issue, and is the write the sync makes in any run with no terminal. A project that turned the remediation on asked for it, and a card missing at filing is what DEC-019's layer is for. It is the choice to make where the maintainer would keep every write to the board out of the runs that anyone who can open an issue starts.
- **Keep the template's own add, and run it on the membership check's finding.** The workflow would make one add and no walk of the board. Not taken, as "Why through the board sync" says: a second command that gives cards, with the sync's rules restated in the template, or broken there.
- **Where the board holds the state, add the card under the project's switch, as the sync's other runs with no terminal add.** One rule for every run of the sync, and a project whose switch is on gets its cards at filing. Not taken, as "Why no card yet where the board holds the state" says: nothing holds the change that would bring the workflow's runs under the switch, its words named other runs, the runs would place strangers' issues, and turning the switch off at once would not reach them.
- **A consent of the workflow's own, held at the merge,** so that the workflow adds where the board holds the state. Its words would name the workflow's runs, as a value of the switch's setting or a setting beside it in the same block, which the same hold holds at small cost, since the hold reads that block already. A switch turned on under the earlier words would read as off for the workflow. It answers the hold and the words. Not taken: it would consent to a guess nobody can yet describe, since what a board's automation writes, and when, was not measured (#3272). It would consent for runs that anyone who can open an issue starts, on issues whose authors may be no participants, which wants a weighing of its own (below). Turning it off at once would not reach those runs, and reading it would take the backbone into the job. It is the form a later record can weigh once #3272 has measured the automation.
- **Add the card only where the issue's author belongs to the project,** by the author's association with the repository that the event carries, or by the member list. It keeps a stranger's issue out of the positions every command acts on. Not taken: where the board does not hold the state, the card places no issue (point 7), and DEC-019 puts every issue on the board. It matters where the board holds the state, for which the later record can weigh it.
- **At filing, where the board holds the state, add the card and write the first Status filing would: Backlog for an issue with a milestone, Todo otherwise.** At filing the issue was just opened, as filing knows of the issue it files, so the Status would not be the guess DEC-072 refuses where a run cannot tell how an issue lost its card, and the issue would be placed with no person. Not taken. The event does not prove the issue new: whether a transferred issue arrives as opened was not measured, a run can come long after the opening (point 7), and a person may set a Status by hand between the workflow's read and its write, which the write would erase. It makes the workflow a third writer of the state's source, beside a move and filing, from a state it infers. And it needs a write the sync refuses where the board holds the state (DEC-072 point 2), so either DEC-072 is overturned there, or the workflow writes the Status outside the sync. It is the choice to make where the maintainer would place an issue filed outside the capability with no person, at that cost.
- **Give the card on every event the workflow runs on, edits and reopenings too.** An issue whose run at filing failed would get its card at its next edit. Not taken, as "Why at filing alone" says. The sync, run by a person, gives such a card.
- **Give the card only where the membership check finds it missing, not where the board did not answer.** No walk would be made where the board did not answer. Not taken, as "Why where the board did not answer too" says: a repository's first issues on a shared board would get no card, though only a card gives their later reads a witness.
- **Run the sync for the whole board at filing.** Every missing card would be given as issues are opened. Not taken: it writes on issues the event is not about, with nobody watching, and the sync is the command a person runs to bring the whole board level (DEC-072).
- **Serialise the workflow's runs of the sync in one concurrency group of the host's, with `queue: max`,** so that a burst of filings makes its walks one after another. As the host ships a group, it keeps one run waiting and cancels it when another comes, so a burst's filings between the first and the last would get no card. With `queue: max`, it keeps up to 100 waiting, in order, and cancels any beyond (Context). What it gives: no more than one walk at once, so a burst's walks keep under the host's limits on requests made at once and requests made each minute, which a burst of walks under one credential can trip. What it costs:
  - It saves no walk and no request, since each filing still walks the whole board, so the budget point 6 names is spent alike.
  - It delays each card in a burst by every walk before it, and drops each filing past the hundredth waiting.
  - It needs the sync in a job of its own, after the check's, or every issue's check waits in the group too. That job takes the check's finding from the check's job, and comments on the issue a second time, with the sync's words.

  Not taken: what it bounds is a failure one run of the sync mends. A walk the host's limits refuse leaves the board unanswered for that run, so the sync adds no card and says so, and the issue's check fails nothing (point 4). One run of the sync after the burst then gives every card the burst left missing, in one walk, where the group makes one walk for each filing. It is the choice to make where bursts are common enough that their cards should arrive with no person, at the price of a second job, a second comment on each issue, and as many walks as filings.
- **Bound a named run's read:** read the named issues' own cards, with ADR-096's witness, and walk the board only where no witness is found. It keeps one command, and spares most filings the walk. Not taken: it changes what DEC-072 point 1 decides of every named run, whoever starts it, and still walks where no witness is found. That is the case this record gives the card in, and every filing's case under a credential whose reads of an issue's own cards find none. A later record can weigh it for the sync's named runs.
- **Give the sync's step a credential of its own,** such as a secret `PM_BOARD_SYNC_TOKEN` beside the check's, so that the identity behind the write is the project's choice for that step, and a credential set so the check can read never becomes the write's. Not taken. For a person's board, the only credential the host offers is a person's token (ADR-096, "What the setting exposes"), so the write would still run as a person, chosen by a second setting, and pass a closed gate where that person is listed. The second secret is long-lived and as broad as its scopes, and it reaches the tools the job fetches, so it doubles what the setting exposes. And the words where the project sets the one credential already name it as the add's under the remediation, and with the build say that the sync runs as its owner (Implications). A project that wants the check to read and nothing added leaves the remediation off. It is the choice to make where the maintainer would have the identity behind the write chosen for that step alone, at the cost of a second secret.
- **Have the sync itself refuse, before its walk, where the board holds the state,** by an option that counts the switch as off, so that the workflow makes no reading of its own and the rule is tested once, in the sync's tests. Not taken: it adds an option to a command people run, for one caller, to spare the workflow a reading that is already one function, with no call to the board, which the workflow calls as the sync does (point 2). And the workflow would start the sync's step, holding the credential and fetching its tools, in each project where the board holds the state, where this record has it write nothing. A later record that gives the card where the board holds the state can weigh it, since that record decides what the sync reads there.
- **Fail the issue's check where the card is not added.** Not taken, as "Why a card not added fails nothing" says.
