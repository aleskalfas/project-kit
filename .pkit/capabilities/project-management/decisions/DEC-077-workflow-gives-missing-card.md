**In plain terms:** an issue filed outside the capability's commands, or whose add to the board failed, opens with no card on the configured board, and the post-check workflow a project copies from the capability's template, as the template shipped, reports it, adding the card only where another finding blocks the issue. This record has the workflow give that card at filing, by running the board sync for that issue alone, where the project turned the workflow's remediation on and gave it a credential the board answers, and where the board belongs to the repository's own owner and does not hold the state. Where the board holds the state, or is under another owner, which the project may not be in charge of, the workflow only reports, naming the sync for a person to run. Under a person's token the sync runs as that person, by the consent the project gives where it sets the credential, and only for an issue the repository's own people open, so no stranger's filing spends that person's budget; under an App's token it runs for every issue. The sync keeps the membership gate, a repository variable turns it off at once, and the comment carries what the sync said. So CI runs one command that writes, bounded to this one write. Two edits reach past the workflow: in every run with no terminal, the gate's refusal of any command names ways through it that the run's setup can take, and the switch that lets the sync add cards where the board holds the state consents for no run an event on an issue starts, a project's own workflow or agent among them.

## Context

**The terms.**

- *The configured board*, *the board holds the state*, *the Status is the state's projection*, *the state degrades*, *the board sync*, *a missing card*, *a run with no terminal* and *the maintainer*: as [project-management:DEC-072-sync-gives-missing-cards] defines them. *The project's switch* is the setting DEC-072 point 3 decides, which lets the board sync's runs with no terminal add cards where the board holds the state.
- *Where the board does not hold the state* is the case that [project-management:DEC-070-filing-another-board]'s term leaves, read in a project with a configured board: where the Status is the state's projection or the state degrades. There no command reads an issue's position from a Status the board's automation sets on a card the sync adds, so a run with no terminal adds cards on the option that skips the question alone, and reads no switch (DEC-072 point 3, its last paragraph).
- *The post-check workflow* is the workflow [project-management:DEC-019-mandatory-issue-state] offers as a template. A project copies it into its own repository, and the host runs it on each issue opened, edited or reopened, with no terminal and nobody watching. *Its remediation* is the toggle DEC-019 gives it, off as the template ships, which the project turns on in its own copy to have the workflow mend what it finds.
- *The membership check* is the check, among an issue's validation, that the issue has its card on the configured board. It finds a card missing only where the same request shows the board answered, and otherwise reports that the board did not answer ([pkit:ADR-096] point 5).
- *The membership gate* is the check of the member list that [project-management:DEC-021-team-membership-gate] decides. Where the list names a member, the gate is closed, and refuses whoever no entry names. It is not the membership check.
- *An App's token* is the token the template mints on each run from the App the project set for the board. *A person's token* is any other credential the project set for the board, which the template's words name a person's (the template, its header). *The token's owner* is the person whose token it is.
- *The board's owner* is the user or organisation the capability resolves the configured board under: `gh.default_owner` in the project's configuration, else the repository's owner (the template, its header). *The repository's own owner* is the user or organisation that owns the repository, and *a board under another owner* is one whose owner is not it.
- *The repository's own people* are those whose association with the repository, as the event of an issue's opening carries it for the issue's author, is that of its owner, a member of the organisation that owns it, or a collaborator on it. *A stranger* is anyone else who opens an issue, as the association names them, whether or not the project counts them among its people (point 7).
- *At filing* means in the workflow's run on the event of the issue's opening, whenever the host makes that run (point 7).

**What the records say.**

- **Every issue belongs on the configured board from its filing** (DEC-019). DEC-019 has the workflow, where its remediation is on, invoke the analogous mutation on a finding that rejects the issue at filing, and only comment on drift on an existing issue. Among the three layers of defence, [project-management:DEC-020-methodology-as-executable-commands] gives the workflow the issues filed outside the capability's commands, on the events of their opening and editing, to detect and optionally remediate, and keeps a scan of every issue's state out of each command ("Three-layer defence model").
- **CI runs the checks, and the commands that write stay with people and agents.** DEC-020 has CI use the environment check and the validations of an issue and of a pull request as its gating checks, and has the commands that write run by a person or an agent, not by CI (its Implications, "CI integration"). DEC-019's workflow mends what it finds by a mutation of the host's own, not by a command of the capability's.
- **The template, when this record was written.** The membership check reports a missing card at the drift severity in every run, at filing too, so it never blocks, and a copy that remediates only on a finding that blocks adds no missing card (ADR-096, its Implications on the workflow). The template's remediation step makes an add of its own, by a raw call of the host's, as whatever account its credential acts as and outside the membership gate, on any event whose run found a finding that blocks. So it adds the card of an issue off the board only where another finding blocks, whoever opened the issue, and writes no Status in any kind of project (the template, its remediation step).
- **The workflow's own token reaches no board,** so the template has a setting for a credential the board answers, unset as it ships. For a person's board, the one credential the template and the capability's README offer is a person's token, which the template's words name as the token that reads the board and, for the remediation, adds to it. For an organisation's board, they offer an App's, which the template mints for the repository's owner, and a person's token for a board under another owner (the template, its header). The check's step and the remediation's step both hold it. Whether a copy remediates, on an issue off the board or on one the board did not answer for, ADR-096 leaves to this capability. Where one does, a card it adds is a witness for the repository's later reads (ADR-096 point 1, and its Implications on the workflow). A credential set there reaches the tools the job fetches at run time, in each step that holds it, and anyone who can open an issue starts the job (ADR-096, "What the setting exposes"). Where the substrate map binds an axis to the board, a check that reads that axis fails each issue under a credential the board does not answer (ADR-096, its Implications on the workflow; the template, its header).
- **The board sync** gives every missing card in every project with a board, and writes a Status only where the Status is the state's projection. A run can be limited to the issues it names, and still reads every card on the board and every open issue, while its writes, its plan and its report are limited to those issues. Where the board does not hold the state, a run with no terminal writes on the option that skips the question, and reads no switch. Where the board holds the state, it adds cards only in a run at a terminal or with the project's switch on, and reads each card it added back (DEC-072 points 1 to 3). It takes the membership gate at its startup, as every command that writes does (DEC-021).
- **What a copy can read of the capability.** The validation prints, for a program, the issue's number and title and its findings, each with a severity from a listed set, a `label` that names the check, such as `board_membership.missing`, and a `detail` in words. When this record was written, the README listed no values of `label`, and the document carries no version of its own (the README, "The findings"). The sync prints no document for a program: it reports in words. It exits 0 where it wrote, or had nothing to write, a named issue it passed over among them; 1 on the gate's refusal or on the guard against writing to another repository; 3 where the repository, the open issues or the board could not be read, or a write failed; and 2 on the other refusals its reference lists (its reference). Where the Status is the state's projection, it adds a card and then writes its Status, and where that write fails, it says that the card was added and its Status not set, and exits 3. A document printed for a program is a contract with each caller: its keys, what each means and the values of its sets, never its prose, which counts a reason, a label or a message, as a value written for people ([pkit:ADR-097] points 2 and 3). A command's exit codes are set by its own record (ADR-097 point 1).
- **Walks and listing reads.** A command that acts on the whole board, such as the sync, walks every card on the board, and may read from that walk where its own repository's open issues stand. A command that needs only the states or cards of the issues it lists makes a listing read of those issues' own cards, never a walk ([pkit:ADR-074] point 6). A filtered read, such as a listing read, finds a card absent only with a witness, where a whole walk reads the board itself (ADR-096 points 1 and 2).
- **State issues.** A state issue holds no work, and the rules for an issue of work do not bind it, its place on the board among them ([project-management:DEC-058-state-issues] point 3). The sync passes over a state issue it is named for, and says that a state issue takes no card. The membership check, as it ships, does not leave a state issue out, so it reports one off the board.
- **The switch's consent and its hold.** Turning the project's switch on consents for every session that runs the sync in the project, a person's or an agent's. Each command of the capability that merges a change into the default branch holds a change that turns it on, and says in plain words what turning it on means. The switch turns off at once from the working tree a run starts from (DEC-072 point 3). [project-management:DEC-069-when-fixers-start] gives a switch of the same form for a fixer's runs nobody watches (its point 4), and holds that a grant given under words that did not say it reaches runs nobody watches counts for none of them (its point 3).
- **Who a run is, under the gate.** Where the host answers that the credential acts as a user's account, that account's login alone is the invoker (DEC-021, "Identity resolution"), and a session under a member's credential acts as that member, whoever it works for (its Implications). So a workflow that runs a gated command passes a closed gate in one of two ways: under a credential that acts as an account the list names, of which DEC-021 words the case of a service identity added to it like any member, or, where the host does not answer that its credential acts as a user's account, with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list. CI is not exempt from the gate by design (DEC-021, its Implications, "CI invocations"). A closed gate refuses with a message that names the invoker and the remediation of being added to the list (DEC-021, "Two modes; the predicate"). DEC-021 did not weigh a credential that anyone who can open an issue puts to work.
- **The check takes no gate.** The validation only reads and reports, so the workflow's check takes no gate, and validates each issue behind a closed gate with no member entry and no `PM_INVOKER_LOGIN`. A step in which the copy runs a command of the capability's that can write, such as one that adds a missing card to the board, takes that command's gate, and passes a closed gate only as DEC-021 lets CI pass ([project-management:DEC-073-reads-take-no-gate] points 3 and 6).
- **What a board's own automation writes** to the Status, and when, was not measured (DEC-072, Context). It is left to [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272).

## Decision

**At filing, on a board of the repository's own owner that does not hold the state, and where the project turned the post-check workflow's remediation on and gave it a credential the board answers, the workflow gives an issue the membership check finds without its card, or for which the board did not answer, its card by running the board sync for that issue alone: under a person's token, for an issue the repository's own people open, and under an App's, for every issue. Where the board holds the state or is under another owner, or where a stranger opened the issue under a person's token, it runs no sync and adds no card, and reports the missing card, naming the sync. The sync's run keeps the membership gate, and under a person's token runs as that person. The project consents to the write, and to its being made as the credential's account, by setting the credential, an act in the repository's settings outside any merge, and the template's words there say that setting one that can write to the board means the project is in charge of the board, or whoever runs it agreed. A repository variable turns the sync at filing off at once, and leaves the check running. The workflow makes no add of its own, adds no card on any other event or for any other finding, and carries on the issue what the sync said.**

### 1. At filing, the workflow runs the board sync for the issue

- **When.** In its run at the issue's opening, where the membership check finds that the issue has no card on the configured board, or that the board did not answer for it, whatever severity the finding takes. The workflow knows the two findings by their labels in the validation's document, `board_membership.missing` and `board_membership.unverified`, never by a finding's words (Implications).
- **Where.** Only where the board does not hold the state, and only on a board of the repository's own owner, the same user or organisation, as the validation's document tells (point 2). On a board under another owner, under any credential, the workflow runs no sync, and its comment says that it added no card, since the board belongs to an owner other than the repository's and the project may not be in charge of it, and names the sync, run for the issue, for a person to run.
- **Whose issues, by the credential.**
  - **Under a person's token,** only for an issue the repository's own people open, by the association the event carries for the issue's author, never for the event's sender, who for an issue moved into the repository is the person who moved it. For a stranger's issue, the workflow runs no sync, and its comment carries the membership check's finding, which names the sync, run for the issue, and says that under a person's token the workflow adds a card at filing only for the repository's own people. Where the event carries no association, or one other than the owner's, a member's or a collaborator's, such as a value the host adds later, the issue counts as a stranger's.
  - **Under an App's token,** for every issue opened, a stranger's among them, and the workflow reads no association.
- **How.** It runs the board sync, named for that issue alone, with the option that skips the question. The sync decides from its own whole walk of the board whether the issue has a card (ADR-096 point 2), so the workflow decides nothing of the card itself.
- **Only where the project asked.** Only where the project turned the remediation on in its copy, only under the credential the project set for the board, and only where the repository variable of point 3 does not turn the sync off. With no credential set, the workflow runs no sync, since its own token reaches no board (ADR-096), and its comment says that it adds a card only under a credential the board answers. With the variable turning the sync off, it runs no sync, and its comment names the variable.
- **At filing alone.** On an edit or a reopening, the workflow adds no card, and reports a missing card as the membership check does, naming the sync. No other finding, one that blocks among them, leads it to add a card.
- **Which reason the comment gives.** The workflow asks the conditions in this order: that the remediation is on, that the variable does not turn the sync off, that a credential is set, that the report tells (point 2), that the board does not hold the state, that it is under the repository's own owner, and, under a person's token, that one of the repository's own people opened the issue. Its comment gives the reason of the first that fails alone, and carries none of these lines on an edit or a reopening, or with the remediation off.

### 2. What the workflow does in each kind of project

- **Where the Status is the state's projection,** the sync adds the card and writes the Status the issue's state gives, on the option that skips the question alone (DEC-072 point 2, and point 3, its last paragraph).
- **Where the state degrades,** it adds the card and writes no Status, on that option alone.
- **Where the board holds the state,** the workflow runs no sync and adds no card, whatever the project's switch says. Its comment carries the membership check's finding, which names the sync, run for the issue, and says that the sync adds a card there only in a run at a terminal or with the switch on (DEC-072 point 4), and says that the workflow adds none there. Whether it should is left to a later record, once [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272) has measured what the board's automation writes to the Status.
- **Where no board is configured,** the membership check makes no call to a board and finds nothing, so the workflow runs no sync.
- **How the workflow tells which.** From the validation's own report of the issue, the document it prints for a program. Its key `status_role` says what the board's Status is to the project, by the same reading the sync makes of it, which asks first whether a board is configured, so that the two never part. DEC-062 point 5 decides what the three kinds are. The reading reads the project's configuration and its substrate map, and asks the board nothing, and the check's step makes it as it validates the issue, so the workflow fetches no tool more for it (ADR-096, "What the setting exposes"). The workflow reads only what a command of the capability prints, and runs none of the capability's own code beside its commands, so that its copy, fixed when copied, depends on the capability's surface alone (Implications).
- **What the keys hold.** Keys of the document's own carry the reading, and whose the board is:
  - `status_role`, from a set: `no-board`, where no board is configured, whatever the substrate map says; `projection`, where the Status is the state's projection; `source`, where the board holds the state; and `degrade`, where the state degrades. Where the reading failed, such as on a configuration or a substrate map it cannot read, `status_role` is null.
  - `status_role_error`, the reading's words where it failed, and null elsewhere.
  - `board_owner`, from a set: `repository`, where the board's owner, as the capability resolves it for each read and write of the board, is the repository's own owner, and `other`, where it is another. The validation decides it in this order. Where the configuration could not be read, the key is null. Where no board is configured, it is null, which goes with `status_role`'s `no-board`. Where `gh.default_owner` is unset, the board's owner is the repository's by that resolution, so the key is `repository`. Where it is set, the validation reads the repository's owner from the issue's own url, the key is null where the url names none, and otherwise the validation compares the two by login, without regard to letter case, as the host matches a login.

  Their contract says from the start that a null of either key that the contract does not explain reads as could not tell, so a later case of null is an addition, and explains one: `board_owner`'s null beside `status_role`'s `no-board`. Each set may gain a value, as every set may (ADR-097 points 2 to 4). The document carries no version of its own, and gains none (Rationale, "Why the copy reads labels and keys, never words").
- **Where the report does not tell,** the workflow runs no sync: where the validation printed no document, or where `status_role` or `board_owner` is null and the contract does not explain the null, missing, as from a capability installed before this record's build, or a value the workflow does not know. Each of these the workflow reads as could not tell (ADR-097 point 3). Its comment says that the workflow could not tell what the board's Status is, or whose the board is, in the reading's own words where the document carries them, and names the sync, run for the issue.

### 3. The consent where nobody watches, and turning it off

- **The project's own.** On a board of the repository's own owner that does not hold the state, the consent is the project's, given where it sets the credential, in the repository's settings and outside any merge (Context). The template's words there say what the remediation does with the credential, on now or once a change turns it on, and that setting one that can write to the board means the project is in charge of the board, or whoever runs it agreed (Implications). The sync's run acts as the account the credential acts as, under a person's token its owner (point 5). Its writes are those the sync makes in any run with no terminal on the option that skips the question, an agent's among them (DEC-072 point 3), for the opened issue's card alone, on the issues point 1 names. Setting the credential is the project's consent to those writes, and to their being made as that account. The remediation's toggle is a condition of the write, not its consent, since any change of the copy can turn it on (Rationale), and the workflow asks no consent beyond the credential's.
- **No switch counts for a run an issue's event starts.** The workflow runs no sync where the board holds the state, and elsewhere the sync reads no switch (DEC-072 point 3). So the project's switch counts for none of the workflow's runs. Nor does it count for any other run an event on an issue starts, such as a workflow of the project's own that runs the sync when an issue opens, or an agent such an event starts, as DEC-072 point 3 says once this record narrows its words (Implications). A run the host starts on an event on an issue counts as such a run, whoever's act the event records, such as a member's comment or a label a member set. The sync cannot tell such a run from another run with no terminal, so whatever starts the run holds that limit, the template's condition for the post-check workflow. Nor does DEC-069's switch count, which consents to a fixer's unconfined runs.
- **Off at once, with the check kept.** A repository variable, `PM_SYNC_AT_FILING`, set to `off`, turns the sync at filing off, by one act in the repository's settings that needs no change to reach the default branch. The workflow then runs no sync, and its check, its reads of the board and its comment go on as before. The variable only turns the sync off: unset, or set to anything else, it leaves the decision to the remediation's toggle, so turning the sync on still takes a change of the project's copy that reaches the default branch.
- **The other ways off.** The host runs the workflow from the copy the default branch holds, so turning the remediation off in that copy takes a change that reaches the default branch. Two other acts turn the sync off at once, each at a cost:
  - **Removing the credential** from the repository's settings. The membership check then reports the board unanswered on each issue, and where the substrate map binds an axis to the board, a check that reads that axis fails each issue (Context).
  - **Disabling the workflow** on the host, which stops the check too.
- **As the template ships,** the remediation is off and no credential is set. A project's copy is its own (DEC-019), so a copy made earlier keeps its own steps until the project copies the template again.

### 4. The workflow carries on the issue what the sync said

- **Its comment** on the issue carries the sync's output as the sync printed it. So it says, in the sync's words, whether the card was added and, where the Status is the state's projection, whether its Status was set, and, where either was not, why: the gate's refusal (point 5), the board not answering, a write that failed, or an issue the sync passed over, such as a state issue. The workflow decides nothing on those words.
- **On the exit code alone.** The workflow tells only whether the sync exited 0, where it wrote what it planned or had nothing to write, or with another code, where it did not finish what it planned: it refused, or a read or a write failed. A code other than 0 does not tell that no card was given, since the sync may have added the card and failed to set its Status (Context). So on another code, the comment adds that the sync did not finish what it planned, that the sync's words above say what it did, and that the sync, run for the issue, finishes the work, for a person to run.
- **What the comment and the log publish.** The comment is as public as the issue, and the job's log as the repository's workflow runs, which in a public repository anyone reads. Both carry the sync's output. A run named for one issue limits its plan and its report to that issue (DEC-072 point 1), so they publish nothing of another issue's card. Yet the plan names how many cards the board holds and how many issues are open, and where an add failed, the output carries the board's own words. So a project whose board is private and whose repository is public publishes these with each such filing, as it publishes the check's findings.
- **A card not added fails nothing.** The issue's check ends as the validation's findings make it, whatever the sync's exit code.

### 5. The sync's run keeps the membership gate

- **As every command that writes.** The sync takes the membership gate at its startup in the workflow's run as in any other, and this record leaves DEC-021's gate as it stands: CI is not exempt. Who the run is follows from the credential, as DEC-021 resolves the invoker ("Identity resolution"). So a person's token is a case of the first way DEC-021's bullet on CI invocations gives, a credential that acts as an account the list names, as this record's edit of the bullet says, changing nothing DEC-021 decides (Implications).
- **Under a person's token,** the sync runs as the token's owner, whose login alone is the invoker (Context), and passes a closed gate wherever the member list names them, which for a person's board is the common case, since the token's owner is most often the board's. So each issue point 1 names starts a run of the sync as the token's owner, which the project consents to (point 3), and no stranger's issue does.
- **Under an App's token,** the host does not answer that the credential acts as a user's account. Behind a closed gate, the run passes only with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list, as DEC-021 lets such a workflow pass. The template sets none for the sync's step as it ships. A project that sets one for that step consents as above, for the identity it names, on every issue opened, a stranger's among them (point 1). In open mode, every such run passes, as every run does.
- **No identity beyond the credential.** The workflow gives the sync's step no identity beyond the credential the project set for the board, so the step passes a closed gate only as DEC-021 lets CI pass, where the check takes no gate (DEC-073 points 3 and 6).
- **A refusal.** Where the gate refuses the sync, the sync adds no card, and the issue's check ends on its findings (point 4). The comment carries the refusal in the gate's own words, which in a run with no terminal, of any command, also name ways through the gate for how the invoker was resolved, each as an act of the run's setup, as DEC-021's refusal reads once refined (Implications). So the template names nothing of the gate, and the line decides nothing of whom the gate passes.
- **A check the gate refuses.** Where the gate refuses the check itself, the check makes no finding, so the workflow runs no sync (point 1).

### 6. The cost, accepted by name

- **One walk per run.** Each run of the sync the workflow makes reads every card on the board and every open issue (DEC-072 point 1). It runs on an issue point 1 names, whose card the membership check finds missing, or for which the board did not answer. Where the board holds the state or is under another owner, and under a person's token on a stranger's issue, the workflow makes no walk.
- **Where it is more.**
  - A burst of filings outside the capability's commands, such as a loop of raw issue creations, a bulk transfer or an import, starts one run for each, at once, each with its whole walk. Under a person's token, only the repository's own people's filings do. Under an App's, any burst does, a run of spam filings among them.
  - Under a credential whose reads of an issue's own cards find no witness, though the board answers a walk, every filing pays the walk, the capability's own whose card is in place among them, and the sync then finds the card and writes nothing. A repository's first issues on a shared board pay it until a card gives the witness.
  - A state issue's filing, such as a seat's, pays a walk too, since the membership check reports it off the board (Context), and the sync then passes it over, saying that a state issue takes no card. State issues are filed rarely, one for each piece of shared state, so this record accepts that.
- **Who pays.** The walks spend the budget of requests the host gives the credential.
  - **Under a person's token,** that is the token's owner's budget for all their work, which every request made on their behalf counts toward, not this workflow's alone (Context), and the repository's own people's filings then spend it. A stranger's filing spends only the check's reads, as it does without this record (ADR-096, "What the setting exposes").
  - **Under an App's token,** it is the installation's own budget, apart from any person's (Context), and every filing whose card the check could not find spends it, a stranger's too, until someone sets the variable. Whatever else the project runs under that App shares it.
  - Each walk also lengthens the run, so in a private repository it spends the project's minutes on the host's runners.
- **Accepted.** The project takes the cost on by turning the remediation on and setting the credential, and ends it at once with the variable, or with the other acts point 3 names.

### 7. What this leaves open

- **Filing's own add in flight.** The capability's filing command creates the issue before it adds the card, so the workflow can read the board before that add, and both then add. That the host answers an add of an issue already on the board with the card it has was not measured (DEC-072, Context). Where it does not, the filing can report a failed add for an issue the workflow gave its card.
- **An issue moved into the repository.** Whether the host reports an issue transferred into the repository as opened was not measured. Where it does, that run counts as at filing, and the workflow treats the issue as any other opened, its author's association as the event carries it (below).
- **At filing is the event, not a time.** A run a person starts again from the host's interface, or one the host held in its queue for hours, still carries the opening, so it can give again a card a person removed in between. The one is a person's act, and the other nobody's. This record accepts both, since where the board does not hold the state the card places no issue (DEC-062 point 5), and DEC-019 puts every issue on the board. A run started again runs from the commit of the event (Context), so a change since then that turns the remediation off or removes the token's owner from the member list does not reach it; whether it reads the variable and the repository's secrets as they stand then was not measured (Implications).
- **An issue another workflow opens under its own token** starts no run of this workflow, since the host makes no run from an issue's opening that token causes (Context). Its missing card is one this layer never sees, and a person's run of the sync gives it.
- **A board under another owner** gets no card at filing (point 1), even where the project is in charge of it, as of a person's own board for an organisation's repository. A person's run of the sync gives the cards.
- **A board of the repository's own organisation that another team runs** is not told apart from the project's own, since its owner is the repository's, so the workflow gives its cards at filing. The template's words where the credential is set carry that case: setting one that can write to the board means the project is in charge of the board, or whoever runs it agreed, so a project sets one there only once that team agreed, and otherwise one whose scopes only read (Rationale).
- **A credential set before the build,** under the template's earlier words, which named it as the remediation's add and said nothing of whose the board is, counts as set under the new words, since the workflow cannot tell when a credential was set. The earlier remediation already added cards under it, on a board of any owner, and the build's note says so (Implications).
- **A stranger's issue,** under a person's token, gets no card at filing (point 1), and gets it when a person runs the sync while it is open. Until then it lacks only its place in the board's views, since where the board does not hold the state every command reads an issue's position from the native primitives, card or not (DEC-062 point 5). An issue closed before then, such as one filed as spam, gets none, since the sync gives cards to open issues alone.
- **Whom the association reads as strangers,** under a person's token, though the project may count them among its people. Each gets no card at filing, and its comment names the sync (point 1):
  - **A member whose membership of the organisation is private,** as it is by default, whom the forum's report has the association read as none, or as a contributor (Context). The documentation does not say how the event reads one (Implications).
  - **One whose access to the repository comes through a team alone,** whom the association's collaborator, one invited to the repository, may not name. Not measured.
  - **A bot's or an App's account,** each issue a two-way sync from another tracker opens among them, since its App opens each.
  - **An imported issue's placeholder** for an unclaimed user (`MANNEQUIN`).
  - **A stranger's issue that one of the project's people moved in,** where the event carries one, since the association is its original author's.
- **What a person does for them.** A person's run of the sync, named for the issue or for the whole board, gives each its card while it is open. A member whose membership is private can make it public, which the forum's report has the association read as membership. A project whose issues arrive mostly through an App's account, such as from another tracker, runs the sync after each such batch, or, for a board of the repository's own organisation, sets an App's token, under which the workflow reads no association.

## Rationale

**Why the workflow gives the card at filing.** DEC-019 puts every issue on the configured board from its filing, and the workflow is the layer that catches the filings the capability's commands do not make (DEC-020), yet as the template shipped, its remediation reached a missing card only where another finding blocked (Context). At filing, a missing card is nobody's choice: the issue was filed outside the capability's commands, or filing's add failed. A card given then also gives a repository with none of its issues on the board a witness for its later reads (ADR-096 point 1).

**Why through the board sync.** DEC-072 keeps one command that gives missing cards, and rejects a second, since each would decide which issue has a card, and each would need to meet ADR-096's tests. The sync already writes what each kind of project asks, and limits a run to the issues it names. An add of the template's own would have to restate those rules, or break them: a card with no Status where the projection wants one, or a card added where the board holds the state, as the template's step adds one on a finding that blocks (Context). It would also reach past the command that owns the write, which DEC-020's layer discipline warns against. Limited to the issue, the run writes nothing on another issue with nobody watching, and two runs for issues opened together each write only their own.

**Why a command that writes runs in CI.** DEC-020 leaves CI the checks, and the commands that write to people and agents. Yet DEC-019 has the workflow's remediation mend what it finds, and the template, as it shipped, made that add from CI, outside the membership gate (Context). So a write from CI is not new, and moving it into the sync, behind the membership gate and under the sync's rules, within the conditions below, puts it in no other layer. What is new is that a command of the capability runs it, which DEC-020's bullet ruled out, so this record refines that bullet in place (Implications).

It is the first command of the capability's that writes to run in CI, and a later record that has the remediation run another such command will read it as a precedent, while DEC-019 has the remediation mend every other finding by a mutation of the host's own. What lets this write in are its own conditions, and such a record meets each of them, or says why it need not:

- it is one write, limited to the issue the event is about;
- no stranger's filing starts it under a person's token, so a person's budget and name go only to the filings of the repository's own people;
- it places no issue a command acts on;
- it writes only on a board of the repository's own owner;
- it mends state DEC-019 requires of every issue;
- the project turns it on, with its toggle and its credential;
- it turns off at once, with the check kept.

**Why only where the board does not hold the state.** There a card the sync adds places no issue a command acts on: where the Status is the state's projection, the sync writes it itself, and where the state degrades, no command reads a position from the Status (DEC-072, "Why no consent where the state degrades"). So the add is a write DEC-072 lets any run with no terminal make, and a project that turned the remediation on and set the credential asked for it.

**Why no card yet where the board holds the state.** There the sync adds cards in a run with no terminal only under the project's switch, which consents to the board's own automation setting a Status that every command then reads as the issue's position (DEC-072 point 3). Carrying that consent to the workflow's runs would widen it past what its hold and its words cover:

- **Nothing holds the change that would widen it.** Each command that merges holds a change to the project's configuration that turns the switch on (DEC-072 point 3), and nothing holds a change to the project's copy of the workflow. So where the switch is on, an agent's change that copies the template with its remediation on could land under an authorisation given up front, and every issue opened outside the commands would then get its card with nobody watching. DEC-069 holds its switch at the merge for that reason: a change of the project's may be an agent's (its Rationale, "Held at the merge").
- **The words named other runs.** The switch's words consent for the sessions that run the sync, a person's or an agent's, and say nothing of the runs an issue's opening starts. DEC-069 point 3 has a grant given under words that did not say it reaches a run count for none of those runs.
- **It would place issues nobody chose to place.** A Status the automation sets on such a card places the issue among the work every command acts on (DEC-051 point 6), though its author may be no participant of the project. Neither record weighed that.
- **Turning it off at once would not reach them.** The switch turns off at once from the working tree a run starts from (DEC-072 point 3), and the workflow's is the host's checkout of the default branch, so turning it off for the workflow would take a change that reaches the default branch.
- **Reading it would take the backbone.** The sync reads the switch through the backbone, which the template does not install, so the job would fetch one more tool at run time, in a step that holds the board's credential (ADR-096, "What the setting exposes").

A consent of the workflow's own, held at the merge, could answer the first two (Alternatives). It would still consent to a guess nobody can yet describe, since what the board's automation writes, and when, was not measured. So the workflow reports there, naming the sync. A person, or a run under the switch, gives the card, and a later record decides once #3272 has measured the automation.

Each reason above but the last holds of every run an event on an issue starts, so this record narrows DEC-072 point 3's words to leave them all out (point 3; Alternatives).

**Why only on a board of the repository's own owner.** A project that uses the capability need not be in charge of its board: `gh.default_owner` can name a board another user or organisation keeps, and the template offers a person's token for one (Context). The workflow adds with nobody watching, so on such a board it would write cards its owner may never have agreed to. On a user's repository, the person who answers for the repository answers for that user's boards too. On an organisation's, only its owners answer for both, and those who answer for the repository need not be among them, so there the condition rests on how seldom a board of the organisation's is one the project is not in charge of, not on who answers for what. The machine checks it with no setting, from the owner the capability resolves for each read and write of the board, and it fails safe: on a board under another owner, or where an owner could not be read, the comment names the sync for a person to run. Under an App's token, which the template mints for the repository's owner (Context), the token reaches only that owner's boards, so the condition only spares a walk that could not reach the board. Under a person's token, which the template offers for a board under another owner, it keeps the workflow off such a board. What it cannot see, another team's board in the repository's own organisation, the template's words where the credential is set carry (point 7).

**Why no setting by which the project declares itself in charge of the board.** Such a setting, off by default, would tell apart that one case. Yet setting the credential is the project's word already, once the template's words say what it means where it is set. A second word for the same fact adds a name, its schema and its documentation, though the validation would print it as one more key, and a project on its own board, the common case, gets no card until it gives both. And where `gh.default_owner` comes to name another owner, the comparison follows at once, where a declaration made for the earlier owner's board reads as on until a review of the change, in the same file, turns it off; within one owner, neither tells one board from another.

**Why the repository's own people's issues under a person's token, and every issue under an App's.** The card places no issue where the board does not hold the state, so that ground does not tell whose filings should get one. Their cost does, and whose name the write is made in:

- **Under a person's token, the cost falls on one person's whole work,** since each card the workflow gives costs a walk from that person's budget (point 6). On a public repository, a stranger's report is a common filing outside the capability's commands, and a run of spam filings would each spend a walk, until the person's own commands and agents meet the host's limits. The variable ends that at once, yet only once someone sees it, so it ends the drain and does not prevent it.
- **The write acts in that person's name.** Each such filing starts a gated write as the token's owner (point 5). Bounded as it is, the write is the one card, which places no issue, a stranger's as much as a member's (point 7), so this weighs less than the cost. Yet a stranger's filing would put the owner's name, and their standing behind a closed gate, to work, which the person whose name it is may not have weighed for strangers.
- **A stranger's card is worth little at filing.** It places no issue, the issue shows in the repository's own list of issues, card or not, and a person's run of the sync gives the card while the issue is open, so an issue closed as spam before then never reaches the board (point 7).
- **Under an App's token, the first two do not hold.** The walks spend the installation's own budget (point 6). The write is the App's, under no person's name, save an identity the project names for the sync's step behind a closed gate, which it names knowing every filing runs as it (point 5). That is the exposure the project takes on with the App, as every filing already spends the check's reads under it, and the card is worth as little. So the workflow reads no association there, and none of the misreadings point 7 names arise.

The template knows which credential it minted, and offers an App's for an organisation's board (Context), where a private membership the association may misread is common, so the misreadings fall mostly where a project sets a person's token there instead.

So under a person's token, the workflow gives the card at filing only for the accounts the repository's owner, or its organisation, admitted to it. That counts more people than the token's owner might choose, every member of the organisation and every collaborator, yet it leaves out the filer anyone can be, where a burst of spam comes from. Where the association reads one of the project's people as a stranger, the issue is reported and a person's run of the sync gives its card, so the bound fails safe, if not always to a card (point 7). What carries the bound is the walk's cost, so once a named run's read is bounded, and most filings pay no walk, it wants weighing again ([project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358); Not decided here).

**Why the association, and not the member list.** The member list is the methodology's authority over its operations, and in open mode, the state every project installs into, it names nobody (DEC-021), so it would bound nothing in a project that keeps no list. The association is the host's own record of whom the repository's owner admitted to it, a member whose membership is private aside (point 7), which is what is at stake here: whose filings may spend the person's budget and act in their name. It grants no authority over the methodology's operations: the gate still decides whether the sync's run passes (point 5), and DEC-021's reasons for keeping that authority off the repository's permissions stand.

**Why where the board did not answer too.** The membership check reads the issue's own cards, and finds a card absent only where it sees another issue's card from the same repository as a witness (ADR-096 point 1). Where the repository has no card on the board yet, as with its first issues on a shared board, it reports that the board did not answer. The sync decides from a whole walk of the board, which reads the board itself and needs no witness (ADR-096 points 1 and 2), so it gives the card there. Where the board truly did not answer, the sync fails and says so.

**Why setting the credential is the consent where the board does not hold the state.** The write is of a kind the sync makes in any run with no terminal on the option that skips the question, since none of these writes sets a Status a command reads as a position it did not know (DEC-072 point 3, its last paragraph). Three things about it are new, and the conclusion has to hold against each:

- **Who starts it.** Whoever opens an issue: under a person's token, one of the repository's own people, and under an App's, anyone, where otherwise a person or an agent of the project starts each run of the sync (point 1). Each run is limited to the issue opened and makes only its card, so the issue's author chooses nothing beyond the card DEC-019 gives every issue.
- **Under whose identity.** The account the credential acts as: under a person's token, the token's owner, with the owner's standing behind a closed gate (point 5). The template's words already name the person's token as the add's credential under the remediation (Context), and the build has them say whom the sync then runs as (Implications).
- **The credential and the toggle.** A credential set so the check can read the board becomes the write's once the remediation is on, where its scopes allow writes. No command that merges holds the toggle, and an agent can land a change that turns it on under an authorisation given up front, so the toggle can carry no statement only a person can make. So the template's words put the one this write needs, that the project is in charge of the board or whoever runs it agreed, where the credential is set, with what the remediation does with it, on now or once a change turns it on (point 3). Setting it is an act in the repository's settings, outside any merge, and without it the workflow writes nothing (point 1). It takes write access to the repository (Context), so an agent under a credential with that access could set one too, yet no command of the capability's does, and no authorisation given for a merge covers it. A project that wants its credential only to read sets one whose scopes only read, under which the sync's add fails and says so, since a change can turn the remediation on.

So the toggle needs no hold at the merge, as the option that skips the question has none: the statement only a person can make rests on the credential, and unlike the switch where the board holds the state, a change that turns the toggle on consents to no guess.

**Why the sync keeps its gate, and runs as the token's owner.** The sync writes to the board, and DEC-021 gates every command that writes, CI's runs included by design. DEC-021 already says who the run is under a person's token (Context). What it did not weigh is a credential that people other than its owner put to work by opening an issue: each issue they open then starts a write as the token's owner, which a closed gate passes wherever the list names that owner. This record weighs that for this one write, and lets it through, for four reasons:

- Whoever opens the issue chooses only which card is added.
- Where the board does not hold the state, that card places no issue a command acts on (point 7), so an issue a non-member opened is no more workable for it.
- Under a person's token, no stranger's filing runs as the token's owner (point 1), and under an App's, a closed gate passes a stranger's filing only as an identity the project named for that step (point 5).
- The project consents to it where it sets the credential, under words the build gives the template and the README (Implications).

Exempting the sync from the gate would decide for DEC-021 what it leaves to each workflow's setup. So the step holds the credential alone, and under an App's token a closed gate refuses it until the project sets an identity for that step.

**Why a variable turns it off, and only off.** Each other act the host gives costs the check: removing the credential fails each issue's check where a check reads an axis the map binds to the board, and disabling the workflow stops it (point 3). A variable is read when a run starts, and needs no change to reach the default branch, so a person who sees the sync go wrong, in a burst or under a token whose budget runs low, stops it with one act and keeps the check. It turns the sync on nowhere: an on read from a setting no change carries would take the remediation out of the path the project reviews. Its cost is one more name, which the template reads and the README names.

**Why at filing alone.** On an edit or a reopening, a missing card may be a person's act, a card removed, or an older failure, and the workflow cannot tell which. DEC-019 keeps drift on an existing issue for a person to mend, at the warning severity, while DEC-020 gives the workflow the filings made outside the commands, caught at their event. An edit is no act on the board, and a card added again on each edit would undo a person's removal with nobody watching.

**Why a walk per filing is not the scan DEC-019 keeps out.** DEC-019 and DEC-020 keep a scan of every issue's board state out of each command, since it would make every command slow, and give the filings that bypass the commands to the workflow, a check made after the event. The sync's walk runs in the workflow, off every command's path, and only on a filing point 1 names whose card the check could not find, where the project asked for it. So no command waits on it, and its cost falls on the project that turned it on (point 6).

**Why no other finding.** The add mends one finding, the missing card. A finding that blocks for another reason, such as a missing label, says nothing of the board, and a card added for it mends nothing that finding names.

**Why the copy reads labels and keys, never words.** The copy is fixed when copied, while the capability upgrades under it (DEC-019), so what it decides on must keep its meaning across releases. A finding's words and the sync's may change in any release, and a key and the values of its set may not (ADR-097 points 2 and 5). So the copy knows the membership check's findings by their labels, the kind of project by `status_role` and whose the board is by `board_owner`, and the README puts them in the contract. ADR-097 counts a label among the prose written for people (its point 2), yet the validation's `label` is an identifier, which names the check that made the finding, so the README states it as one, and the new keys are additions no caller misreads (ADR-097 point 4). The value `no-board` is an answer, which a failed reading is not, so the one takes a value of the set and the other a null, whose meaning the contract states from the start, so that a later case of a failed reading needs no new value (ADR-097 point 3). `board_owner` leaves that answer to `status_role`, so that one fact has one key, and its null beside `no-board` is the one null its contract explains. It takes a set, not true or false, so that it can gain a value (ADR-097 point 4), which a boolean could not without a new key (ADR-097 point 5). The validation, not the copy, compares the owners, since it resolves the board's owner as the sync does, and a copy that resolved its own would part from it once the capability's resolution changed.

**Why the comment carries the sync's words, and the copy reads only its exit code.** The workflow already comments on an issue whose check found anything, and a missing card is such a finding, so the comment adds no write the run would not make. Without the sync's words, the comment would report an issue off the board that the workflow then gave its card. No step of the copy turns on which outcome the sync had: a card not added fails nothing (point 4), and what follows any card not given is a person's run of the sync, whatever the cause. So the copy needs only whether the sync finished, which its exit code tells, and the sync's words tell the reader the rest, and the less a copy reads, the less a later release can break in it. Telling the outcomes apart in the copy would freeze a set of them, by exit codes or by a document's keys, for a choice no step makes (Alternatives). The gate's refusal names ways through it in its own words, so the template, which cannot tell that refusal from another failure, names none.

**Why a card not added fails nothing.** A missing card is drift, which never blocks as the template ships, and an add the board did not make, or the gate refused, is no fault of the issue's, as a board that did not answer is none of the issue's under the membership check (ADR-096 point 5).

**Why the cost is accepted.** The walk is what lets the sync decide a card's absence with no witness (ADR-096 points 1 and 2), the case "Why where the board did not answer too" gives the card in. ADR-074 point 6 has a command that needs only the cards of the issues it lists make a listing read of their own cards, never a walk. A run named for one issue walks because the sync counts as the command that acts on the whole board, and DEC-072 point 1 has a named run read what a whole run reads. This record rests its walk at each filing on that reading, so it writes the reading into ADR-074 point 6, for the sync alone, rather than leave it to be inferred (Implications). Bounding a named run's read is the cleaner answer for the long run (Alternatives), yet it would change every named run of the sync, whoever starts it, and still walk in the case this record gives the card in, so [project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358) weighs it (Not decided here). The project that pays the cost chose it (point 6), and the variable ends it at once.

### Alternatives considered

- **Keep the workflow reporting only.** Taken where the board holds the state, until a later record decides (point 2). Not taken where the board does not hold the state: there the add places no issue, and is the write the sync makes in any run with no terminal. A project that turned the remediation on asked for it, and a card missing at filing is what DEC-019's layer is for. It is the choice to make where the maintainer would keep every command that writes out of CI, as DEC-020 did before this record.
- **Keep the template's own add, and run it on the membership check's finding.** The workflow would make one add and no walk of the board. Not taken, as "Why through the board sync" says: a second command that gives cards, with the sync's rules restated in the template, or broken there.
- **Where the board holds the state, add the card under the project's switch, as the sync's other runs with no terminal add.** One rule for every run of the sync, and a project whose switch is on gets its cards at filing. Not taken, for the reasons "Why no card yet where the board holds the state" gives.
- **A consent of the workflow's own, held at the merge,** so that the workflow adds where the board holds the state. Its words would name the workflow's runs, under the same hold, and a switch turned on under the earlier words would read as off for the workflow. It answers the hold and the words. Not taken, as "Why no card yet where the board holds the state" says: it would consent to a guess nobody can yet describe (#3272), for runs on issues whose authors may be no participants of the project, and the last two reasons there hold of it too. It is the form a later record can weigh once #3272 has measured the automation.
- **Narrow DEC-072 point 3 for the post-check workflow's runs alone.** The edit would name only the run this record decides. Not taken: each reason that keeps the switch from the workflow's runs, save the backbone it would take, holds of any run an event on an issue starts, a project's own workflow's or an agent's ("Why no card yet where the board holds the state"), and those runs would stay under the switch's words.
- **Have the project declare that it is in charge of the board,** by a setting of its configuration, off by default: in place of the owner check, which would see another team's board in the repository's own organisation; required beside it, for the case the owners cannot tell; or as an opt-in beside it, which would let the workflow add under a person's token on a board under another owner too, such as a person's own board for an organisation's repository. Not taken, as "Why no setting by which the project declares itself in charge of the board" says: each adds a name, its schema and its documentation, the first two hold the common case's cards back until the project gives both words, and the opt-in serves a case a person's run of the sync serves (point 7). - **Put the statement on the toggle,** with the template's words where the remediation is turned on, and accept that an agent's change can turn it on under an authorisation given up front, as an agent's run of the sync with no terminal already adds cards on a board the project may not be in charge of (DEC-072 point 3, its last paragraph). It is the choice to make where most credentials were set under the template's earlier words (point 7).

Not taken, for the reasons "Why the repository's own people's issues under a person's token, and every issue under an App's" gives. It is the choice to make where the repository takes few filings from strangers. A copy that runs the sync for a stranger's issue under a person's token departs from DEC-019 and DEC-020 as this record refines them.
- **Bound the filings otherwise.** Each of these was weighed against the association under a person's token, and not taken:

- **Give the card on every event the workflow runs on, edits and reopenings too.** An issue whose run at filing failed would get its card at its next edit. Not taken, as "Why at filing alone" says.
- **Give the card only where the membership check finds it missing, not where the board did not answer.** No walk would be made where the board did not answer. Not taken, as "Why where the board did not answer too" says: a repository's first issues on a shared board would get no card, though only a card gives their later reads a witness.

It is the choice to make where bursts are common enough that their cards should arrive with no person.
- **Bound a named run's read:** read the named issues' own cards, with ADR-096's witness, and walk the board only where no witness is found. It keeps one command, spares most filings the walk, and follows the last sentence of ADR-074 point 6. Not taken here, as "Why the cost is accepted" says, which leaves it to [project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358).
- **Have the copy tell the sync's outcomes apart,** by a document the sync prints for a named run, under ADR-097, or by exit codes of their own: the card added, the gate's refusal, the board not answering, an issue passed over. Not taken, as "Why the comment carries the sync's words, and the copy reads only its exit code" says, and the sync's codes do not tell them apart (Context). It is the choice to make where a later record has the workflow act on the outcome, such as checking the issue again after the sync gives its card (Not decided here).
- **Give the sync's step a credential of its own,** such as a secret `PM_BOARD_SYNC_TOKEN` beside the check's, so that the identity behind the write is the project's choice for that step, and a credential set so the check can read never becomes the write's. Not taken. For a person's board the host offers only a person's token (ADR-096, "What the setting exposes"), so the write would still run as a person, and a second long-lived secret doubles what the setting exposes, where the words that set the one credential already say what the remediation does with it.
- **Have the sync itself refuse, before its walk, where the board holds the state,** by an option that counts the switch as off, so that this record's limit on DEC-072 point 3 is held and tested in the command. Not taken: a copy that leaves the option out runs the sync under the switch, as one that drops the template's condition does, so it holds the limit no better, and it adds an option for one caller, and a step that holds the credential where this record has the workflow write nothing. A later record that gives the card there can weigh it.
- **Fail the issue's check where the card is not added.** Not taken, as "Why a card not added fails nothing" says.
