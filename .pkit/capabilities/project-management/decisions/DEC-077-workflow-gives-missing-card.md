> **Partially superseded by [project-management:DEC-076-app-credentials].** Under an App's token, a closed gate passes the sync's run only where the backbone's reading names the App's account and an entry names that account, by its own login, and `PM_INVOKER_LOGIN` passes none. A project that adds that account admits every run under the App's token, each issue opened among them. Overturned: point 5's bullet "Under an App's token", its "with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list" and its sentence on a project that sets one for the sync's step, with the Rationale's sentences that restate them, in "Why the repository's own people's issues under a person's token, and every issue under an App's" and "Why the sync keeps its gate, and runs as the token's owner"; the way by `PM_INVOKER_LOGIN` that its Implications add to DEC-021's refusal in a run with no terminal; and point 5's "A refusal", so far as it carries that way. The rest stands.

**In plain terms:** an issue filed outside the capability's commands, or whose add to the board failed, opens with no card on the configured board, and the post-check workflow, as its template shipped, reports it, adding the card only where another finding blocks. This record has the workflow give that card at filing, by running the board sync for that issue alone, on a board of the repository's own owner that does not hold the state, once the project has turned the workflow's remediation on, set a credential the board answers, and set the variable `PM_SYNC_AT_FILING` to `on`. Setting the variable is the consent, an act outside any merge that no command makes, under words that say the project is in charge of the board, or whoever runs it agreed; no credential consents on its own. Under a person's token, only an issue the repository's own people open starts the sync, so no stranger's filing spends a walk from that person's budget. Wherever the sync does not run, the workflow only reports, naming the sync for a person to run. The sync keeps the membership gate, and the variable turns it off at once, so CI runs one command that writes, bounded to this one write. Three edits reach past the workflow: in every run with no terminal, the gate's refusal names ways through it that the run's setup can take; the switch that lets the sync add cards where the board holds the state consents for no run an event on an issue starts; and a run of the sync named for some issues counts as acting on the whole board, so walks it.

## Context

**The terms.**

- *The configured board*, *the board holds the state*, *the Status is the state's projection*, *the state degrades*, *the board sync*, *a missing card*, *a run with no terminal* and *the maintainer*: as [project-management:DEC-072-sync-gives-missing-cards] defines them. *The project's switch* is the setting DEC-072 point 3 decides, which lets the board sync's runs with no terminal add cards where the board holds the state.
- *Where the board does not hold the state* is the case that [project-management:DEC-070-filing-another-board]'s term leaves, read in a project with a configured board: where the Status is the state's projection or the state degrades. There no command reads an issue's position from a Status the board's automation sets on a card the sync adds, so a run with no terminal adds cards on the option that skips the question alone, and reads no switch (DEC-072 point 3, its last paragraph).
- *The post-check workflow* is the workflow [project-management:DEC-019-mandatory-issue-state] offers as a template. A project copies it into its own repository, and the host runs it on each issue opened, edited or reopened, with no terminal and nobody watching. *Its remediation* is the toggle DEC-019 gives it, off as the template ships, which the project turns on in its own copy to have the workflow mend what it finds. *The variable* is `PM_SYNC_AT_FILING`, a variable the host gives a workflow's runs, read as the host resolves it for the template's job, which names no environment: the repository's own value, else its organisation's (the host's documentation, below). Point 3 decides what it does.
- *The membership check* is the check, among an issue's validation, that the issue has its card on the configured board. It finds a card missing only where the same request shows the board answered, and otherwise reports that the board did not answer ([pkit:ADR-096] point 5).
- *The membership gate* is the check of the member list that [project-management:DEC-021-team-membership-gate] decides. Where the list names a member, the gate is closed, and refuses whoever no entry names. It is not the membership check.
- *An App's token* is the token the template mints on each run from the App the project set for the board. *A person's token* is any other credential the project set for the board, which the template's words name a person's (the template, its header). A run is under an App's token only where the template's own step minted one, and so, where both are set, under the App's, the one the template's steps then use (the template, its steps). *The token's owner* is the person whose token it is.
- *The board's owner* is the user or organisation the capability resolves the configured board under: `gh.default_owner` in the project's configuration, else the repository's owner (the template, its header). *The repository's own owner* is the user or organisation that owns the repository, and *a board under another owner* is one whose owner is not it.
- *The project is in charge of a board* where those who run the project run the board too, deciding what it holds; a credential that can write to the board does not make it so.
- *The repository's own people* are those whose association with the repository, as the event of an issue's opening carries it for the issue's author, is that of its owner, a member of the organisation that owns it, or a collaborator on it. *A stranger* is anyone else who opens an issue, as the association names them, whether or not the project counts them among its people (point 7).
- *At filing* means in the workflow's run on the event of the issue's opening, whenever the host makes that run (point 7).

**What the records say.**

- **Every issue belongs on the configured board from its filing** (DEC-019). DEC-019 has the workflow, where its remediation is on, invoke the analogous mutation on a finding that rejects the issue at filing, and only comment on drift on an existing issue. Among the three layers of defence, [project-management:DEC-020-methodology-as-executable-commands] gives the workflow the issues filed outside the capability's commands, on the events of their opening and editing, to detect and optionally remediate, and keeps a scan of every issue's state out of each command ("Three-layer defence model").
- **CI runs the checks, and the commands that write stay with people and agents.** DEC-020 has CI use the environment check and the validations of an issue and of a pull request as its gating checks, and has the commands that write run by a person or an agent, not by CI (its Implications, "CI integration"). DEC-019's workflow mends what it finds by a mutation of the host's own, not by a command of the capability's.
- **The template, when this record was written.** The membership check reports a missing card at the drift severity in every run, at filing too, so it never blocks, and a copy that remediates only on a finding that blocks adds no missing card (ADR-096, its Implications on the workflow). The template's remediation step makes an add of its own, by a raw call of the host's, as whatever account its credential acts as and outside the membership gate, on any event whose run found a finding that blocks. So it adds the card of an issue off the board only where another finding blocks, whoever opened the issue, and writes no Status in any kind of project (the template, its remediation step).
- **The workflow's own token reaches no board,** so the template has a setting for a credential the board answers, unset as it ships. For a person's board, the template and the capability's README offer a person's token, which the template's words name as the token that reads the board and, for the remediation, adds to it. For an organisation's board, they offer an App's, which the template mints for the repository's owner, and a person's token for a board under another owner (the template, its header). The check's step and the remediation's step both hold it, and whether a copy remediates ADR-096 leaves to this capability. A credential set there reaches the tools the job fetches at run time, in each step that holds it, and anyone who can open an issue starts the job (ADR-096, "What the setting exposes"). Where the substrate map binds an axis to the board, a check that reads that axis fails each issue under a credential the board does not answer (ADR-096, its Implications on the workflow; the template, its header).
- **The board sync** gives every missing card in every project with a board, and writes a Status only where the Status is the state's projection. A run can be limited to the issues it names, and still reads every card on the board and every open issue, while its writes, its plan and its report are limited to those issues. Where the board does not hold the state, a run with no terminal writes on the option that skips the question, and reads no switch. Where the board holds the state, it adds cards only in a run at a terminal or with the project's switch on, and reads each card it added back (DEC-072 points 1 to 3). It takes the membership gate at its startup, as every command that writes does (DEC-021).
- **What a copy can read of the capability.** The validation prints, for a program, the issue's number and title and its findings, each with a severity from a listed set, a `label` that names the check, such as `board_membership.missing`, and a `detail` in words. When this record was written, the README listed no values of `label`, and the document carries no version of its own (the README, "The findings"). The sync prints no document for a program: it reports in words. It exits 0 where it wrote, or had nothing to write, a named issue it passed over among them; 1 on the gate's refusal or on the guard against writing to another repository; 3 where the repository, the open issues or the board could not be read, or a write failed; and 2 on the other refusals its reference lists (its reference). Where the Status is the state's projection, it adds a card and then writes its Status, and where that write fails, it says that the card was added and its Status not set, and exits 3. A document printed for a program is a contract with each caller: its keys, what each means and the values of its sets, never its prose, which counts a reason, a label or a message, as a value written for people ([pkit:ADR-097] points 2 and 3). A command's exit codes are set by its own record (ADR-097 point 1).
- **Walks and listing reads.** A command that acts on the whole board, such as the sync, walks every card on the board, and may read from that walk where its own repository's open issues stand. A command that needs only the states or cards of the issues it lists makes a listing read of those issues' own cards, never a walk ([pkit:ADR-074] point 6). A filtered read, such as a listing read, finds a card absent only with a witness, where a whole walk reads the board itself (ADR-096 points 1 and 2).
- **State issues.** A state issue holds no work, and the rules for an issue of work do not bind it, its place on the board among them ([project-management:DEC-058-state-issues] point 3). The sync passes over a state issue it is named for, and says that a state issue takes no card. The membership check, as it ships, does not leave a state issue out, so it reports one off the board.
- **The switch's consent and its hold.** Turning the project's switch on consents for every session that runs the sync in the project, a person's or an agent's. Each command of the capability that merges a change into the default branch holds a change that turns it on, and says in plain words what turning it on means. The switch turns off at once from the working tree a run starts from (DEC-072 point 3). [project-management:DEC-069-when-fixers-start] gives a switch of the same form for a fixer's runs nobody watches (its point 4), and holds that a grant given under words that did not say it reaches runs nobody watches counts for none of them (its point 3).
- **Who a run is, under the gate.** Where the host answers that the credential acts as a user's account, that account's login alone is the invoker (DEC-021, "Identity resolution"), and a session under a member's credential acts as that member, whoever it works for (its Implications). So a workflow that runs a gated command passes a closed gate in one of two ways: under a credential that acts as an account the list names, of which DEC-021 words the case of a service identity added to it like any member, or, where the host does not answer that its credential acts as a user's account, with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list. CI is not exempt from the gate by design (DEC-021, its Implications, "CI invocations"). A closed gate refuses with a message that names the invoker and the remediation of being added to the list (DEC-021, "Two modes; the predicate"). DEC-021 did not weigh a credential that anyone who can open an issue puts to work.
- **The check takes no gate.** The validation only reads and reports, so the workflow's check takes no gate, and validates each issue behind a closed gate with no member entry and no `PM_INVOKER_LOGIN`. A step in which the copy runs a command of the capability's that can write, such as one that adds a missing card to the board, takes that command's gate, and passes a closed gate only as DEC-021 lets CI pass ([project-management:DEC-073-reads-take-no-gate] points 3 and 6).
- **What a board's own automation writes** to the Status, and when, was not measured (DEC-072, Context). It is left to [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272).

**What the host's documentation says,** as read on 2026-11-16 and 2026-11-17:

- **A run started again** uses the commit and the reference of the event that first started it (on re-running workflows and jobs). The page does not say whether it reads the repository's variables and secrets again.
- **A concurrency group** runs one job or run at a time, and with `queue: max` keeps up to 100 waiting, in order, cancelling any beyond (on controlling the concurrency of workflows and jobs).
- **Requests made with a person's token** count toward that person's own budget of requests, beside those that apps make on the person's behalf, and those made with an App's installation token toward the installation's own, apart from any person's, which grows with the organisation's users and repositories. The host's secondary limits bound the requests made at once and the requests made each minute (on the REST API's rate limits).
- **Setting a repository's secret or variable** takes write access to an organisation's repository, and a collaborator's to a person's, in the repository's settings or through the REST API, where a classic token needs the `repo` scope (on using secrets in GitHub Actions; the REST API's reference for secrets).

Where a repository has one of the same name, the repository's own takes precedence. ## Decision

**At an issue's filing, on a board of the repository's own owner that does not hold the state, the post-check workflow gives an issue the membership check finds without its card, or for which the board did not answer, its card by running the board sync for that issue alone, once the project has turned the workflow's remediation on, set a credential the board answers and set the variable to `on`, which is its consent. Under a person's token, only an issue the repository's own people open starts the sync. Elsewhere the workflow runs no sync, and reports the missing card, naming the sync. The sync keeps the membership gate, the workflow makes no add of its own and adds no card on any other event or for any other finding, and its comment carries what the sync said.**

### 1. At filing, the workflow runs the board sync for the issue

- **When.** In its run at the issue's opening, where the membership check finds that the issue has no card on the configured board, or that the board did not answer for it, whatever severity the finding takes. The workflow knows the two findings by their labels in the validation's document, `board_membership.missing` and `board_membership.unverified`, never by a finding's words (Implications).
- **Where.** Only where the board does not hold the state, and only on a board of the repository's own owner, the same user or organisation, as the validation's document tells (point 2). On a board under another owner, under any credential, the workflow runs no sync. Its reason, where the comment gives it (below), says that it added no card, since the board belongs to an owner other than the repository's and the project may not be in charge of it, and names the sync, run for the issue, for a person to run.
- **Whose issues, by the credential.**
  - **Under a person's token,** only for an issue the repository's own people open, by the association the event carries for the issue's author, never for the event's sender, who for an issue moved into the repository is the person who moved it. For a stranger's issue, the workflow runs no sync, and its comment carries the membership check's finding, which names the sync, run for the issue. Its reason, where the comment gives it (below), says that under a person's token the workflow adds a card at filing only for the repository's own people. Where the event carries no association, or one other than the owner's, a member's or a collaborator's, such as a value the host adds later, the issue counts as a stranger's.
  - **Under an App's token,** for every issue opened, a stranger's among them, and the workflow reads no association.
- **How.** It runs the board sync, named for that issue alone, with the option that skips the question. The sync decides from its own whole walk of the board whether the issue has a card (ADR-096 point 2), so the workflow decides nothing of the card itself.
- **Its two conditions, and the project's consent.** Only where the project turned the remediation on in its copy and set a credential for the board, under which alone the sync runs, and set the variable to `on`, its consent (point 3). With the variable not `on`, the workflow runs no sync, and its reason, where the comment gives it (below), names the variable and points to the words point 3 lists, which it does not carry. With no credential set, it runs no sync, since its own token reaches no board (ADR-096), and its reason, where the comment gives it, says that it adds a card only under a credential the board answers.
- **At filing alone.** On an edit or a reopening, the workflow adds no card, and reports a missing card as the membership check does, naming the sync. No other finding, one that blocks among them, leads it to add a card.
- **Which reason the comment gives.** One alone, of a condition other than the remediation that fails, and the variable's only where every other condition holds. So the comment asks for the consent only where setting the variable would start the sync, and leads no project to set `on` where it would start none. With the remediation off, and on an edit or a reopening, it carries none of these lines.

### 2. What the workflow does in each kind of project

- **Where the Status is the state's projection,** the sync adds the card and writes the Status the issue's state gives, on the option that skips the question alone (DEC-072 point 2, and point 3, its last paragraph).
- **Where the state degrades,** it adds the card and writes no Status, on that option alone.
- **Where the board holds the state,** the workflow runs no sync and adds no card, whatever the project's switch says. Its comment carries the membership check's finding, which names the sync, run for the issue, and says that the sync adds a card there only in a run at a terminal or with the switch on (DEC-072 point 4). Its reason, where the comment gives it (point 1), says that the workflow adds none there. Whether it should is left to a later record, once [project-kit#3272](https://github.com/aleskalfas/project-kit/issues/3272) has measured what the board's automation writes to the Status.
- **Where no board is configured,** the membership check makes no call to a board and finds nothing, so the workflow runs no sync.
- **How the workflow tells which.** From the validation's own report of the issue, the document it prints for a program. Its key `status_role` says what the board's Status is to the project, by the same reading the sync makes of it, which asks first whether a board is configured, so that the two never part (DEC-062 point 5 decides the three kinds). The reading asks the board nothing, and the check's step makes it as it validates the issue, so the workflow fetches no tool more for it (ADR-096, "What the setting exposes"). The workflow reads only what a command of the capability prints, so that its copy, fixed when copied, depends on the capability's surface alone (Implications).
- **What the keys hold.** Keys of the document's own carry the reading, and whose the board is:
  - `status_role`, from a set: `no-board`, where no board is configured, whatever the substrate map says; `projection`, where the Status is the state's projection; `source`, where the board holds the state; and `degrade`, where the state degrades. Where the reading failed, such as on a configuration or a substrate map it cannot read, `status_role` is null.
  - `status_role_error`, the reading's words where it failed, and null elsewhere.
  - `board_owner`, from a set: `repository`, where the board's owner, as the capability resolves it for each read and write of the board, is the repository's own owner, and `other`, where it is another. The validation decides it in this order. Where the configuration could not be read, the key is null. Where no board is configured, it is null, which goes with `status_role`'s `no-board`. Where the configuration names no owner for the board, the board's owner is the repository's by that resolution, so the key is `repository`. Where it names one, the validation compares it with the repository's owner by login, without regard to letter case, as the host matches a login, and the key is null where the repository's owner could not be read.

  Their contract says from the start that a null of either key that the contract does not explain reads as could not tell, so a later case of null is an addition, and explains one: `board_owner`'s null beside `status_role`'s `no-board`. Each set may gain a value, as every set may (ADR-097 points 2 to 4). The document carries no version of its own, and gains none (Rationale, "Why the copy reads labels and keys, never words").
- **Where the report does not tell,** the workflow runs no sync: where the validation printed no document, or where `status_role` or `board_owner` is null and the contract does not explain the null, missing, as from a capability installed before this record's build, or a value the workflow does not know. Each of these the workflow reads as could not tell (ADR-097 point 3). Its reason, where the comment gives it (point 1), says that the workflow could not tell what the board's Status is, or whose the board is, in the reading's own words where the document carries them, and names the sync, run for the issue.

### 3. The consent where nobody watches, and turning it off

- **The project's own, by the variable.** On a board of the repository's own owner that does not hold the state, the consent is the project's, given by setting the variable to `on`, in the repository's settings or, for each repository it reaches, its organisation's, an act outside any merge that no command of the capability makes (Rationale). It consents to the writes the sync makes in any run with no terminal on the option that skips the question (DEC-072 point 3), for the opened issue's card alone, on the issues point 1 names, and to their being made as the account the credential acts as (point 5). `on` consents in any letter case, as the host compares strings (Context). Unset, or set to any other value, the variable starts no sync.
- **Its words.** The template's words on the variable, beside its name, and the README's say:
  - that with the remediation on and a credential the board answers, setting it to `on` has the sync run at filing for the opened issue alone, adding its card and, where the Status is the state's projection, writing its Status (point 2), as the account the credential acts as, under a person's token its owner, who passes a closed gate where the member list names them (point 5);
  - that under a person's token only an issue the repository's own people open starts it, and under an App's every issue does, a stranger's too (point 1);
  - that each such filing whose card the check could not find costs one walk of the board from the credential's budget, under a person's token that person's budget for all their work, and in a private repository the project's minutes on the host's runners, and that the sync's output, in the issue's comment and the job's log, publishes how many cards the board holds and how many issues are open (points 4 and 6);
  - that setting it is the project's consent to that write, made as that account, and means the project is in charge of whichever board the configuration names under the repository's owner, or whoever runs it agreed, and, under a person's token, that its owner agreed to the writes in their name;
  - that set for the organisation, it is that consent for every repository it reaches (below);
  - that it starts no sync where the board holds the state or is under another owner (points 1 and 2);
  - how it turns off at once (below);
  - and that whoever sets it sets it themselves, and does not have an agent set it.

  The credential's words say that it serves the check's reads, and the sync's write only with the remediation on and the variable `on`; that while the variable is `on`, a person's token that comes to be the credential runs are under, by being set or by the removal of one that took precedence over it, means that person agreed to the writes in their name; and, of an App, that removing it while a person's token is set moves the write to that person's name (below).
- **Conditions, not consent.** The remediation's toggle and the credential stay conditions of the write, and without either the workflow writes nothing (point 1). Neither is its consent: any change of the copy, an agent's among them, can turn the toggle on, and a credential is set so the check can read the board (below).
- **A credential set before the build,** under the template's earlier words, which named it as the remediation's add and said nothing of whose the board is, counts for the check's reads and for no write of the sync's: the write waits until someone sets the variable under its words, as a grant given under earlier words counts for no run nobody watches until the person answers again (DEC-069 point 3). No copy read the variable before the build, so each `on` is set under the words the build gives it.
- **A person's token that comes to be the credential.** While the variable is `on`, a person's token comes to be the credential runs are under by being set, or by the removal of a credential that took precedence over it: an App's, which wins wherever both are set, or, for a token the organisation sets, the repository's own of the same name (Context). Under the credential's words, either act states that person's agreement to the writes in their name, so whoever acts does so only once that person agreed, and the token carries its own owner's agreement, never one given for the credential it replaced. A token set for the check's reads alone while the variable is `on` so puts its owner's name to the write once a change turns the remediation on, the objection this record raises against a credential as the consent (Alternatives, "Set the credential as the consent"). This record accepts it here, since the token gives only its owner's agreement, under words that say what setting it means while the variable is `on`, and the project's consent stays the variable's.
- **Another board under the same owner,** named by a change of the configuration, an agent's among them, takes the variable's consent with it, since the workflow cannot tell which board whoever set the variable stated about, as the variable's words say (above).
- **Set for the organisation.** A variable the repository's organisation sets is the consent of whoever set it there, for every repository it reaches, those created later among them. The workflow writes only on a board of the repository's own owner, so an organisation's `on` reaches only the organisation's own boards, for which, as for the repository, only its owners answer (Rationale, "Why only on a board of the repository's own owner"). The repository's own value takes precedence (Context): `on` there is that repository's consent, which the organisation's `off` does not reach, and `off` there turns the sync off for that repository alone. A credential that reaches the repository from its organisation counts as set by whoever set it there. So where both the variable and the credential reach a repository from its organisation, as they reach one created later, no act outside a merge is left there: a change that turns the toggle on, an agent's landed under an authorisation given up front among them, turns the write on with nothing more. Whether another team that runs a board there agreed then rests on the organisation's owners alone (point 7). So does whether the owner of a person's token any of those repositories set agreed, a token set before the build among them.
- **No widening.** An `on` set under these words counts for no widening of the write that a later record makes, such as a write where the board holds the state, or for a stranger's issue under a person's token (Not decided here): a widening needs a new act of the project's. The workflow cannot tell an `on` set before a widening's build from one set after, so this commits a later widening to a value or a variable of its own.
- **No switch counts for a run an issue's event starts.** The workflow runs no sync where the board holds the state, and elsewhere the sync reads no switch (DEC-072 point 3). So the project's switch counts for none of the workflow's runs. Nor does it count for any other run an event on an issue starts, such as a workflow of the project's own that runs the sync when an issue opens, or an agent such an event starts, as DEC-072 point 3 says once this record narrows its words (Implications). A run the host starts on an event on an issue counts as such a run, whoever's act the event records, such as a member's comment or a label a member set. The sync cannot tell such a run from another run with no terminal, so whatever starts the run holds that limit, the template's condition for the post-check workflow. Nor does DEC-069's switch count, which consents to a fixer's unconfined runs.
- **Off at once, with the check kept.** Setting the variable to `off` in the repository's settings, or removing it there where no organisation's value reaches the repository, turns the sync at filing off, by one act that needs no change to reach the default branch: the workflow then runs no sync, and its check, its reads of the board and its comment go on as before. While an organisation's `on` reaches the repository, removing the repository's own value turns nothing off. These acts hold of the template's job, which names no environment. A copy whose job names one is the project's own reshaping of the workflow (DEC-019), whose ways off this record does not decide, and which value its condition reads there is a premise the build checks (Implications).
- **The other ways off.** The host runs the workflow from the copy the default branch holds, so turning the remediation off in that copy takes a change that reaches the default branch. Two other acts turn the sync off at once, each at a cost:
  - **Removing every credential set for the board that the steps fall back to,** the repository's and any of its organisation's that reaches it, since removing one can leave another that the steps then use (above). The membership check then reports the board unanswered on each issue, and where the substrate map binds an axis to the board, a check that reads that axis fails each issue (Context).
  - **Disabling the workflow** on the host, which stops the check too.
- **As the template ships,** the remediation is off, no credential is set, and the variable is the project's to set. A project's copy is its own (DEC-019), so a copy made earlier keeps its own steps until the project copies the template again, and the copy it then makes runs no sync until the variable is `on`.

### 4. The workflow carries on the issue what the sync said

- **Its comment** on the issue carries the sync's output as the sync printed it. So it says, in the sync's words, whether the card was added and, where the Status is the state's projection, whether its Status was set, and, where either was not, why: the gate's refusal (point 5), the board not answering, a write that failed, or an issue the sync passed over, such as a state issue. The workflow decides nothing on those words.
- **On the exit code alone.** The workflow tells only whether the sync exited 0, where it wrote what it planned or had nothing to write, or with another code, where it did not finish what it planned: it refused, or a read or a write failed. A code other than 0 does not tell that no card was given, since the sync may have added the card and failed to set its Status (Context). So on another code, the comment adds that the sync did not finish what it planned, that the sync's words above say what it did, and that the sync, run for the issue, finishes the work, for a person to run.
- **What the comment and the log publish.** The comment is as public as the issue, and the job's log as the repository's workflow runs. Both carry the sync's output, which a run named for one issue limits to that issue (DEC-072 point 1). Yet its plan names how many cards the board holds and how many issues are open, and where an add failed, it carries the board's own words. So a project whose board is private and whose repository is public publishes these with each such filing, beside the check's findings, and on a board other repositories share, private ones among them, the count of cards tells what those findings do not. The variable's words say so (point 3).
- **A card not added fails nothing.** The issue's check ends as the validation's findings make it, whatever the sync's exit code.

### 5. The sync's run keeps the membership gate

- **As every command that writes.** The sync takes the membership gate at its startup in the workflow's run as in any other, and this record leaves DEC-021's gate as it stands: CI is not exempt. Who the run is follows from the credential ("Identity resolution"), so a person's token is a case of the first way DEC-021's bullet on CI invocations gives, a credential that acts as an account the list names, as this record's edit of the bullet says (Implications).
- **Under a person's token,** the sync runs as the token's owner, whose login alone is the invoker (Context), and passes a closed gate wherever the member list names them, which for a person's board is the common case, since the token's owner is most often the board's. So each issue point 1 names starts a run of the sync as the token's owner, which the project consents to (point 3), and no stranger's issue does.
- **Under an App's token,** the host does not answer that the credential acts as a user's account. Behind a closed gate, the run passes only with `PM_INVOKER_LOGIN` from a secret, naming an entry of the list, as DEC-021 lets such a workflow pass. The template sets none for the sync's step as it ships. A project that sets one for that step names the identity every issue opened then passes the gate as, a stranger's among them (point 1), under the consent its variable gives (point 3). In open mode, every such run passes, as every run does.
- **No identity beyond the credential.** The workflow gives the sync's step no identity beyond the credential the project set for the board, so the step passes a closed gate only as DEC-021 lets CI pass, where the check takes no gate (DEC-073 points 3 and 6).
- **A refusal.** Where the gate refuses the sync, the sync adds no card, and the issue's check ends on its findings (point 4). The comment carries the refusal in the gate's own words, which in a run with no terminal, of any command, also name ways through the gate for how the invoker was resolved, each as an act of the run's setup, as DEC-021's refusal reads once refined (Implications). So the template names nothing of the gate, and the line decides nothing of whom the gate passes.
- **A check the gate refuses.** Where the gate refuses the check itself, as under a capability from before DEC-073's build, whose check takes the gate, the check makes no finding, so the workflow runs no sync (point 1).

### 6. The cost, accepted by name

- **One walk per run.** Each run of the sync the workflow makes reads every card on the board and every open issue (DEC-072 point 1). It runs on an issue point 1 names, whose card the membership check finds missing, or for which the board did not answer. Where the board holds the state or is under another owner, and under a person's token on a stranger's issue, the workflow makes no walk.
- **Where it is more.**
  - A burst of filings outside the capability's commands, such as a loop of raw issue creations, a bulk transfer or an import, starts one run for each, at once, each with its whole walk: under a person's token, the repository's own people's filings alone, and under an App's, any burst, a run of spam filings among them.
  - Under a credential whose reads of an issue's own cards find no witness, though the board answers a walk, every filing pays the walk, the capability's own whose card is in place among them. A repository's first issues on a shared board pay it until a card gives the witness.
  - A state issue's filing, such as a seat's, pays a walk too, since the membership check reports it off the board (Context), and the sync then passes it over. State issues are filed rarely, so this record accepts that.
- **Who pays.** The walks spend the budget of requests the host gives the credential.
  - **Under a person's token,** that is the token's owner's budget for all their work, not this workflow's alone (Context). A stranger's filing spends only the check's reads, as it does without this record (ADR-096, "What the setting exposes").
  - **Under an App's token,** it is the installation's own budget, apart from any person's (Context), which every filing whose card the check could not find spends, a stranger's too, as does whatever else the project runs under that App.
  - Each walk also lengthens the run, so in a private repository it spends the project's minutes on the host's runners.
- **Accepted.** The project takes the cost on by setting the variable to `on`, under the words point 3 lists, and ends it at once by any of the acts point 3 names.

### 7. The edge cases this accepts

- **Filing's own add in flight.** The capability's filing command creates the issue before it adds the card, so the workflow can read the board before that add, and both then add. That the host answers an add of an issue already on the board with the card it has was not measured (DEC-072, Context). Where it does not, the filing can report a failed add for an issue the workflow gave its card.
- **An issue moved into the repository.** Whether the host reports an issue transferred into the repository as opened was not measured. Where it does, that run counts as at filing, and the workflow treats the issue as any other opened, its author's association as the event carries it (below).
- **At filing is the event, not a time.** A run a person starts again from the host's interface, or one the host held in its queue for hours, still carries the opening, so it can give again a card a person removed in between. The one is a person's act, and the other nobody's. This record accepts both, since where the board does not hold the state the card places no issue (DEC-062 point 5), and DEC-019 puts every issue on the board. A run started again runs from the commit of the event (Context), so a change since then that turns the remediation off or removes the token's owner from the member list does not reach it; whether it reads the variable and the repository's secrets as they stand then was not measured (Implications).
- **An issue another workflow opens under its own token** starts no run of this workflow, since the host makes no run from an issue's opening that token causes (Context). Its missing card is one this layer never sees, and a person's run of the sync gives it.
- **A board under another owner** gets no card at filing (point 1), even where the project is in charge of it, as of a person's own board for an organisation's repository. A person's run of the sync gives the cards.
- **A board of the repository's own organisation that another team runs** is not told apart from the project's own, since its owner is the repository's, so the workflow gives its cards at filing. The variable's words carry that case, so a project sets it there only once that team agreed (point 3).
- **A stranger's issue,** under a person's token, gets no card at filing (point 1), and gets it when a person runs the sync while it is open. Until then it lacks only its place in the board's views, since where the board does not hold the state every command reads an issue's position from the native primitives, card or not (DEC-062 point 5). An issue closed before then, such as one filed as spam, gets none, since the sync gives cards to open issues alone.
- **Whom the association reads as strangers,** under a person's token, though the project may count them among its people. Each gets no card at filing, and its comment names the sync (point 1):
  - **A member whose membership of the organisation is private,** as it is by default, whom the forum's report has the association read as none, or as a contributor (Context; Implications).
  - **One whose access to the repository comes through a team alone,** whom the association's collaborator may not name. Not measured.
  - **A bot's or an App's account,** each issue a two-way sync from another tracker opens among them.
  - **An imported issue's placeholder** for an unclaimed user (`MANNEQUIN`).
  - **A stranger's issue that one of the project's people moved in,** since the association is its original author's.
- **What a person does for them.** A person's run of the sync gives each its card while it is open. A member whose membership is private can make it public. A project whose issues arrive mostly through an App's account runs the sync after each such batch, or, for a board of the repository's own organisation, sets an App's token, under which the workflow reads no association.

## Rationale

**Why the workflow gives the card at filing.** DEC-019 puts every issue on the configured board from its filing, and the workflow is the layer that catches the filings the capability's commands do not make (DEC-020), yet as the template shipped, its remediation reached a missing card only where another finding blocked (Context). At filing, a missing card is nobody's choice: the issue was filed outside the capability's commands, or filing's add failed. A card given then also gives a repository with none of its issues on the board a witness for its later reads (ADR-096 point 1).

**Why through the board sync.** DEC-072 keeps one command that gives missing cards, and rejects a second, since each would decide which issue has a card, and each would need to meet ADR-096's tests. The sync already writes what each kind of project asks, and limits a run to the issues it names. An add of the template's own would have to restate those rules, or break them, as the template's step adds a card with no Status, and where the board holds the state (Context), and would reach past the command that owns the write, which DEC-020's layer discipline warns against. Limited to the issue, the run writes nothing on another issue with nobody watching, and two runs for issues opened together each write only their own.

**Why a command that writes runs in CI.** DEC-020 leaves CI the checks, and the commands that write to people and agents. Yet DEC-019 has the workflow's remediation mend what it finds, and the template, as it shipped, made that add from CI, outside the membership gate (Context). So a write from CI is not new, and moving it into the sync, behind the membership gate and under the sync's rules, within the conditions below, puts it in no other layer. What is new is that a command of the capability runs it, which DEC-020's bullet ruled out, so this record refines that bullet in place (Implications).

It is the first command of the capability's that writes to run in CI, and a later record that has the remediation run another such command will read it as a precedent, while DEC-019 has the remediation mend every other finding by a mutation of the host's own. What lets this write in are its own conditions, and such a record meets each of them, or says why it need not:

- it is one write, limited to the issue the event is about;
- no stranger's filing starts it under a person's token, so a person's budget and name go only to the filings of the repository's own people;
- it places no issue a command acts on;
- it writes only on a board of the repository's own owner;
- it mends state DEC-019 requires of every issue;
- the project consents to it by an act outside any merge that no command of the capability makes, under words that name that write, so a consent given for another write counts for none of it, and this one for no widening of it (point 3);
- it turns off at once, with the check kept.

**Why only where the board does not hold the state.** There a card the sync adds places no issue a command acts on: where the Status is the state's projection, the sync writes it itself, and where the state degrades, no command reads a position from the Status (DEC-072, "Why no consent where the state degrades"). So the add is a write DEC-072 lets any run with no terminal make, and a project that set the variable to `on`, under words that name it, asked for it.

**Why no card yet where the board holds the state.** There the sync adds cards in a run with no terminal only under the project's switch, which consents to the board's own automation setting a Status that every command then reads as the issue's position (DEC-072 point 3). Carrying that consent to the workflow's runs would widen it past what its hold and its words cover:

- **Nothing holds the change that would widen it.** Each command that merges holds a change that turns the switch on (DEC-072 point 3), and nothing holds a change to the project's copy of the workflow. So where the switch is on, an agent's change that copies the template with its remediation on could land under an authorisation given up front, giving every issue opened outside the commands its card with nobody watching. DEC-069 holds its switch at the merge for that reason (its Rationale, "Held at the merge").
- **The words named other runs.** The switch's words consent for the sessions that run the sync, and say nothing of the runs an issue's opening starts, and DEC-069 point 3 has a grant count for no run its words did not say it reaches.
- **It would place issues nobody chose to place.** A Status the automation sets on such a card places the issue among the work every command acts on (DEC-051 point 6), though its author may be no participant of the project.
- **Turning it off at once would not reach them.** The switch turns off at once from the working tree a run starts from (DEC-072 point 3), and the workflow's is the host's checkout of the default branch.
- **Reading it would take the backbone,** which the template does not install, so the job would fetch one more tool at run time, in a step that holds the board's credential (ADR-096, "What the setting exposes").

A consent of the workflow's own, held at the merge, could answer the first two (Alternatives). It would still consent to a guess nobody can yet describe, since what the board's automation writes, and when, was not measured. So the workflow reports there, naming the sync. A person, or a run under the switch, gives the card, and a later record decides once #3272 has measured the automation.

Each reason above but the last holds of every run an event on an issue starts, so this record narrows DEC-072 point 3's words to leave them all out (point 3; Alternatives).

**Why only on a board of the repository's own owner.** A project that uses the capability need not be in charge of its board: `gh.default_owner` can name a board another user or organisation keeps, and the template offers a person's token for one (Context). The workflow adds with nobody watching, so on such a board it would write cards its owner may never have agreed to. On a user's repository, the person who answers for the repository answers for that user's boards too. On an organisation's, only its owners answer for both, so there the condition rests on how seldom a board of the organisation's is one the project is not in charge of. The machine checks it from the owner the capability resolves for each read and write of the board, and it fails safe: on a board under another owner, or where an owner could not be read, the comment names the sync for a person to run. Under an App's token, minted for the repository's owner (Context), the condition only spares a walk that could not reach the board; under a person's token, which the template offers for a board under another owner, it keeps the workflow off such a board. What it cannot see, another team's board in the repository's own organisation, the variable's words carry (point 7).

**Why the owner check beside the variable.** The variable carries the project's word that it is in charge of the board, so no setting of the configuration repeats it, which any change, an agent's among them, could carry, and which would add a name, its schema and its documentation. The check by owner stays beside the variable, since it follows the configuration where the variable cannot: where `gh.default_owner` comes to name another owner, by a change an agent can land, the comparison follows at once, where a variable set for the earlier owner's board reads as on until someone turns it off. Within one owner, neither tells one board from another (point 3).

**Why the repository's own people's issues under a person's token, and every issue under an App's.** The card places no issue where the board does not hold the state, so that ground does not tell whose filings should get one. Their cost does, and whose name the write is made in:

- **Under a person's token, the cost falls on one person's whole work,** since each card the workflow gives costs a walk from that person's budget (point 6). On a public repository, a stranger's report is a common filing outside the capability's commands, and a run of spam filings would each spend a walk, until the person's own commands and agents meet the host's limits. The variable ends that at once, yet only once someone sees it.
- **The write acts in that person's name.** Each such filing starts a gated write as the token's owner (point 5). The write is the one card, which places no issue (point 7), so this weighs less than the cost, yet a stranger's filing would put the owner's name, and their standing behind a closed gate, to work.
- **A stranger's card is worth little at filing.** It places no issue, the issue shows in the repository's own list of issues, and a person's run of the sync gives the card while the issue is open (point 7).
- **Under an App's token, the first two do not hold.** The walks spend the installation's own budget (point 6), and the write is the App's, under no person's name, save an identity the project names for the sync's step behind a closed gate, knowing every filing runs as it (point 5). That is the exposure the project takes on with the App, as every filing already spends the check's reads under it. So the workflow reads no association there, and none of the misreadings point 7 names arise, which fall mostly where a project sets a person's token for an organisation's board, where a private membership is common.

So under a person's token, the workflow gives the card at filing only for the accounts the repository's owner, or its organisation, admitted to it: more people than the token's owner might choose, yet not the filer anyone can be, where a burst of spam comes from. Where the association reads one of the project's people as a stranger, a person's run of the sync gives its card, so the bound fails safe, if not always to a card (point 7). What carries the bound is the walk's cost, so once a named run's read is bounded it wants weighing again ([project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358); Not decided here).

**Why the association, and not the member list.** The member list is the methodology's authority over its operations, and in open mode, the state every project installs into, it names nobody (DEC-021), so it would bound nothing in a project that keeps no list. The association is the host's own record of whom the repository's owner admitted to it, a member whose membership is private aside (point 7), which is what is at stake here: whose filings may spend the person's budget and act in their name. It grants no authority over the methodology's operations: the gate still decides whether the sync's run passes (point 5), and DEC-021's reasons for keeping that authority off the repository's permissions stand.

**Why where the board did not answer too.** The membership check reads the issue's own cards, and finds a card absent only where it sees another issue's card from the same repository as a witness (ADR-096 point 1). Where the repository has no card on the board yet, as with its first issues on a shared board, it reports that the board did not answer. The sync decides from a whole walk of the board, which reads the board itself and needs no witness (ADR-096 points 1 and 2), so it gives the card there. Where the board truly did not answer, the sync fails and says so.

**Why the variable is the consent where the board does not hold the state.** The write is of a kind the sync makes in any run with no terminal on the option that skips the question, since none of these writes sets a Status a command reads as a position it did not know (DEC-072 point 3, its last paragraph). Three things about it are new, and the conclusion has to hold against each:

- **Who starts it.** Whoever opens an issue: under a person's token, one of the repository's own people, and under an App's, anyone, where otherwise a person or an agent of the project starts each run of the sync (point 1). Each run is limited to the issue opened and makes only its card, so the issue's author chooses nothing beyond the card DEC-019 gives every issue.
- **Under whose identity.** The account the credential acts as: under a person's token, the token's owner, with the owner's standing behind a closed gate (point 5). The variable's words say whom the sync then runs as, and that the token's owner agreed (point 3).
- **Whose word it is.** The write needs a statement, that the project is in charge of the board or whoever runs it agreed, made by an act that no command of the capability makes and no authorisation given for a merge covers. The toggle is no such act: it sits in the copy, which any change carries, an agent's landed under an authorisation given up front among them. Nor is the credential, which is set so the check can read the board, those set before the build under words that said nothing of whose the board is among them (point 3; Alternatives). The variable has the one purpose, is set in the repository's settings or its organisation's, outside any merge, and no command of the capability sets it, so the write comes only where someone set it under the new words, for the repository or for its organisation (point 3). Setting it takes write access to the repository, or an organisation's ownership (Context), so an agent with that access could set it too: nothing forbids that, yet no command of the capability does it, no authorisation given for a merge covers it, and the variable's words tell whoever sets it to set it themselves (point 3).

The act itself shows no words: the settings page and the host's command ask only a name and a value. So the consent rests on the words the template and the README give the variable (point 3), from which a project learns its name and the value that turns it on. DEC-072's switch shows its words at the act, through each command that merges; this record trades that for an act outside every merge (Alternatives).

So the toggle needs no hold at the merge, as the option that skips the question has none: the statement rests on the variable, and the write the toggle is a condition of sets no Status a command reads as a position it did not know, unlike the cards the switch lets in where the board holds the state.

**Why the sync keeps its gate, and runs as the token's owner.** The sync writes to the board, and DEC-021 gates every command that writes, CI's runs included by design. DEC-021 already says who the run is under a person's token (Context). What it did not weigh is a credential that people other than its owner put to work by opening an issue: each issue they open then starts a write as the token's owner, which a closed gate passes wherever the list names that owner. This record weighs that for this one write, and lets it through, for four reasons:

- Whoever opens the issue chooses only which card is added.
- Where the board does not hold the state, that card places no issue a command acts on (point 7), so an issue a non-member opened is no more workable for it.
- Under a person's token, no stranger's filing runs as the token's owner (point 1), and under an App's, a closed gate passes a stranger's filing only as an identity the project named for that step (point 5).
- The project consents to it by setting the variable, under the words point 3 lists.

Exempting the sync from the gate would decide for DEC-021 what it leaves to each workflow's setup. So the step holds the credential alone, and under an App's token a closed gate refuses it until the project sets an identity for that step.

**Why the variable also turns it off at once.** Each other act the host gives costs the check: removing the credentials fails each issue's check where a check reads an axis the map binds to the board, and disabling the workflow stops it (point 3). The variable sits in the repository's settings or its organisation's, not in the copy, and each run reads it as the host resolves it for that run (Context), so setting it needs no change to reach the default branch, and a person who sees the sync go wrong, in a burst or under a token whose budget runs low, stops it with one act and keeps the check. The write so takes two acts beside the credential, which the check most often has already: a change of the copy that turns the remediation on, through the path the project reviews, and the variable, outside it, so the variable takes nothing out of that path and adds the project's word beside it. Its cost is one more setting for every project that wants the card.

**Why at filing alone.** On an edit or a reopening, a missing card may be a person's act, a card removed, or an older failure, and the workflow cannot tell which. DEC-019 keeps drift on an existing issue for a person to mend, at the warning severity, while DEC-020 gives the workflow the filings made outside the commands, caught at their event. An edit is no act on the board, and a card added again on each edit would undo a person's removal with nobody watching.

**Why a walk per filing is not the scan DEC-019 keeps out.** DEC-019 and DEC-020 keep a scan of every issue's board state out of each command, since it would make every command slow, and give the filings that bypass the commands to the workflow. The sync's walk runs in the workflow, off every command's path, on a filing point 1 names, where the project asked for it, so no command waits on it, and its cost falls on that project (point 6).

**Why no other finding.** The add mends one finding, the missing card. A finding that blocks for another reason, such as a missing label, says nothing of the board, and a card added for it mends nothing that finding names.

**Why the copy reads labels and keys, never words.** The copy is fixed when copied, while the capability upgrades under it (DEC-019). A finding's words and the sync's may change in any release, and a key and the values of its set may not (ADR-097 points 2 and 5). So the copy knows the membership check's findings by their labels, the kind of project by `status_role` and whose the board is by `board_owner`. ADR-097 counts a label among the prose written for people (its point 2), yet the validation's `label` names the check that made the finding, so the README states it as an identifier, and the new keys are additions no caller misreads (ADR-097 point 4). `no-board` is an answer, which a failed reading is not, so the one takes a value and the other a null, whose meaning the contract states from the start (ADR-097 point 3). `board_owner` leaves that answer to `status_role`, so that one fact has one key, and takes a set, not true or false, so that it can gain a value (ADR-097 points 4 and 5). The validation, not the copy, compares the owners, since it resolves the board's owner as the sync does, which a copy's own resolution would part from once the capability's changed.

**Why the comment carries the sync's words, and the copy reads only its exit code.** The workflow already comments on an issue whose check found anything, a missing card among them, so the comment adds no write, and without the sync's words it would report an issue off the board that the workflow then gave its card. No step of the copy turns on which outcome the sync had: a card not added fails nothing (point 4), and what follows any card not given is a person's run of the sync. So the copy needs only whether the sync finished, and the less a copy reads, the less a later release can break in it. Telling the outcomes apart would freeze a set of them for a choice no step makes (Alternatives). The gate's refusal names ways through it in its own words, so the template, which cannot tell that refusal from another failure, names none.

**Why a card not added fails nothing.** A missing card is drift, which never blocks as the template ships, and an add the board did not make, or the gate refused, is no fault of the issue's, as a board that did not answer is none of the issue's under the membership check (ADR-096 point 5).

**Why the cost is accepted.** The walk is what lets the sync decide a card's absence with no witness (ADR-096 points 1 and 2), the case "Why where the board did not answer too" gives the card in. ADR-074 point 6 has a command that needs only the cards of the issues it lists make a listing read of their own cards, never a walk. A run named for one issue walks because the sync counts as the command that acts on the whole board, and DEC-072 point 1 has a named run read what a whole run reads. This record rests its walk at each filing on that reading, so it writes the reading into ADR-074 point 6, for the sync alone, rather than leave it to be inferred (Implications). Bounding a named run's read is the cleaner answer for the long run (Alternatives), yet it would change every named run of the sync, whoever starts it, and still walk in the case this record gives the card in, so [project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358) weighs it (Not decided here). The project that pays the cost chose it (point 6), and the variable ends it at once.

### Alternatives considered

- **Keep the workflow reporting only.** Taken where the board holds the state, until a later record decides (point 2). Not taken where the board does not hold the state: there the add places no issue, and is the write the sync makes in any run with no terminal. A project that set the variable to `on` asked for it, and a card missing at filing is what DEC-019's layer is for. It is the choice to make where the maintainer would keep every command that writes out of CI, as DEC-020 did before this record.
- **Keep the template's own add, and run it on the membership check's finding.** The workflow would make one add and no walk of the board. Not taken, as "Why through the board sync" says: a second command that gives cards, with the sync's rules restated in the template, or broken there.
- **Where the board holds the state, add the card under the project's switch, as the sync's other runs with no terminal add.** One rule for every run of the sync, and a project whose switch is on gets its cards at filing. Not taken, for the reasons "Why no card yet where the board holds the state" gives.
- **A consent of the workflow's own, held at the merge,** so that the workflow adds where the board holds the state, under words that name its runs. It answers the hold and the words. Not taken, as "Why no card yet where the board holds the state" says: it would consent to a guess nobody can yet describe (#3272), for issues whose authors may be no participants of the project. It is the form a later record can weigh once #3272 has measured the automation.
- **Narrow DEC-072 point 3 for the post-check workflow's runs alone.** The edit would name only the run this record decides. Not taken: each reason that keeps the switch from the workflow's runs, save the backbone it would take, holds of any run an event on an issue starts, a project's own workflow's or an agent's ("Why no card yet where the board holds the state"), and those runs would stay under the switch's words.
- **Have the project declare that it is in charge of the board,** by a setting of its configuration: in place of the owner check, which would see another team's board in the repository's own organisation, or as an opt-in beside it, which would let the workflow add under a person's token on a board under another owner too, such as a person's own board for an organisation's repository. Not taken, as "Why the owner check beside the variable" says: the variable carries that word by an act outside any merge, where a setting of the configuration sits in a file any change carries, and each adds a name, its schema and its documentation. The opt-in serves a case a person's run of the sync serves (point 7), and is the choice to make where projects commonly keep their boards under other owners.
- **Put the statement on the toggle,** with the template's words where the remediation is turned on, and accept that an agent's change can turn it on under an authorisation given up front, as an agent's run of the sync with no terminal already adds cards on a board the project may not be in charge of (DEC-072 point 3, its last paragraph). Not taken: the statement wants an act no command of the capability makes and no authorisation given for a merge covers, and the toggle sits in a file any change carries ("Why the variable is the consent where the board does not hold the state"). That the sync's other runs reach such a board is left to #3371, and is no reason for one more run that does.
- **Hold at the merge a change that turns the remediation on,** as each command that merges holds a change that turns DEC-072's switch on, so that the toggle's words reach a person at the act. Not taken: the toggle sits in the project's copy of the workflow, a file of the project's own, which the project may reshape (DEC-019), so each command that merges would read a file the capability does not keep to tell the toggle turned on, where the variable already carries the statement outside any merge. It is the choice to make where the statement's words should reach a person at the act, as the switch's do.
- **Set the credential as the consent,** with the statement in the template's words on it, and the variable a way off alone, so that the common case takes one act, and a project whose remediation was on keeps its cards at filing once it copies the template again. Not taken, for three reasons. A credential serves the check's reads too, so one set for them alone would become the project's consent to the write once a change turned the remediation on, under scopes the project may not have chosen for writing, as under an App's token, whose permissions are the App's; point 3 takes from a person's token only its owner's agreement, beside the variable's consent, for the reason it gives. One that reaches the repository from its organisation may have been set there for another purpose (point 3). And the workflow cannot tell when a credential was set, so each one set before the build would take the statement on at the next copy of the template, a change an agent can land under an authorisation given up front, where DEC-069 point 3 has a grant given under earlier words count for runs nobody watches only once the person answers again.
- **Count only the repository's own value,** read through the host's API for a repository's variable, so that an organisation's value consents for none of its repositories. Not taken: whoever sets the variable for the organisation consents for every repository it reaches, and since the workflow writes only on a board of the repository's own owner, an organisation's `on` reaches only the organisation's own boards, for which only its owners answer. The workflow reads the variable as the host gives it to every run, with no call more, and a repository that should not take the write sets `off` for itself (point 3).
- **A value scoped to this record's write,** so that a later widening asks for a new value. Not taken as a choice of this record's: since the workflow cannot tell an `on` set before a widening's build from one set after, the clause that an `on` counts for no widening already commits a later widening to a value or a variable of its own, which that record names (point 3).
- **Give the sync's step a write credential of its own,** such as a secret `PM_BOARD_SYNC_TOKEN` that only it holds, whose setting would be the consent. Each step would hold less: the check's step, which runs on every event and fetches tools at run time, would hold a credential that only reads, and the one that writes would reach the sync's step alone, which fetches its tools too. Not taken: each project that wants the card would set and rotate a second long-lived secret, where the variable holds none, and for a person's board the second is a person's token too (ADR-096, "What the setting exposes"). It is the choice to make where a credential that can write, held in the check's step on every event, is an exposure the project will not take.
- **A rule that an agent sets none of the workflow's secrets or variables without the person's confirmation for that act,** which would make setting the variable a person's act alone. Not taken here: it binds every agent's session, not this workflow, and is a choice for a record of its own.
- **Give the card at filing for every issue opened under a person's token too.** One rule would hold for every filing under every credential, with no reading of the author, and none of the misreadings point 7 names. Not taken, for the reasons "Why the repository's own people's issues under a person's token, and every issue under an App's" gives. It is the choice to make where the repository takes few filings from strangers. A copy that runs the sync for a stranger's issue under a person's token departs from DEC-019 and DEC-020 as this record refines them.
- **Bound the filings otherwise.** Each of these was weighed against the association under a person's token, and not taken:
  - *By the association under an App's token too:* there the cost and the name fall on no person, so it would only leave out the people the association misreads; the choice where strangers' filings should not spend an App's budget either.
  - *By the member list:* the methodology's own list of whom it counts would bound the filings, and name a member whose membership is private as one of the project's people; not taken, for the reasons "Why the association, and not the member list" gives.
  - *By the author's permission on the repository,* read under the workflow's own token: it would see access through a team and a private membership, yet whether that token can read it was not measured; the choice once it is, where the association often misreads the project's people.
  - *By the member list where the gate is closed, by the credential's remaining budget, or on a public repository alone:* each adds to the step that decides a write for little, since the first still reads the association wherever the list names nobody, the second guards the budget, not the name, and the third mends the misreadings only in a private repository.
- **At filing, where the board holds the state, add the card and write the first Status filing would: Backlog for an issue with a milestone, Todo otherwise.** The issue was just opened, so the Status would not be the guess DEC-072 refuses, and the issue would be placed with no person. Not taken. The event does not prove the issue new, as a transferred issue or a late run may show (point 7), and the write would erase a Status a person set between the workflow's read and its write. It makes the workflow a third writer of the state's source, from a state it infers, by a write the sync refuses there (DEC-072 point 2).
- **Give the card on every event the workflow runs on, edits and reopenings too.** An issue whose run at filing failed would get its card at its next edit. Not taken, as "Why at filing alone" says.
- **Give the card only where the membership check finds it missing, not where the board did not answer.** No walk would be made where the board did not answer. Not taken, as "Why where the board did not answer too" says: a repository's first issues on a shared board would get no card, though only a card gives their later reads a witness.
- **Run the sync for the whole board at filing.** Every missing card would be given as issues are opened. Not taken: it writes on issues the event is not about, with nobody watching, and the sync is the command a person runs to bring the whole board level (DEC-072).
- **Run the sync on a schedule,** for the whole board, in place of at each filing. Not taken: it fits none of DEC-020's three layers, and writes on issues no event is about, with nobody watching.
- **Serialise the workflow's runs of the sync in one concurrency group, with `queue: max`** (Context). Not taken: it saves no walk, delays every card in a burst, drops what the queue cannot hold, and needs the sync in a job of its own, which comments a second time. It is the choice where bursts are common enough that their cards should arrive with no person.
- **Bound a named run's read:** read the named issues' own cards, with ADR-096's witness, and walk the board only where no witness is found. It keeps one command, spares most filings the walk, and follows the last sentence of ADR-074 point 6. Not taken here, as "Why the cost is accepted" says, which leaves it to [project-kit#3358](https://github.com/aleskalfas/project-kit/issues/3358).
- **Have the copy tell the sync's outcomes apart,** by a document the sync prints for a named run, under ADR-097, or by exit codes of their own: the card added, the gate's refusal, the board not answering, an issue passed over. Not taken, as "Why the comment carries the sync's words, and the copy reads only its exit code" says, and the sync's codes do not tell them apart (Context). It is the choice to make where a later record has the workflow act on the outcome, such as checking the issue again after the sync gives its card (Not decided here).
- **Have the sync refuse where the board holds the state,** by an option that counts the switch as off. Not taken: a copy that leaves the option out runs under the switch, as one that drops the template's condition does, so it holds the limit no better, for an option with one caller.
- **Fail the issue's check where the card is not added.** Not taken, as "Why a card not added fails nothing" says.
