id: DEC-070
title: An account that names no person never acts or counts as a person
status: proposed
date: 2026-11-13
author: Aleš Kalfas <kalfas.ales@gmail.com>

**In plain terms:** an agent may reach GitHub under a credential that names no person, such as a GitHub App installation's token or a CI workflow's. GitHub will not look such an account up as a user, and refuses it as an assignee.

Wherever GitHub does not answer that the credential acts as a user's account, because the account is an app's, or GitHub refuses to say, or cannot be asked, this capability's commands take no person's identity for the account they act as, in a CI workflow and in an agent's session alike, and no comment the commands post names a person as its authoriser. Where GitHub answers with a user's account, what may stand beside that account is a question of its own ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)). The person the agent works for, which the session names, serves only where naming a person grants nothing: as the default assignee, and to keep the agent off a Task assigned to someone else. In every project, under every credential, nothing an account GitHub records as a bot writes counts as a person's approval, or as a person's claim on work wherever a claim's author is read.

What a person accepting this weighs:

- **No instance ownership.** A clone under such a credential claims no Task, and under an unresolved identity a clone that holds an instance id refuses. In a project with a topology it builds nothing, and takes a planner's seat only where the membership gate is closed and its account is a member. Elsewhere two sessions under one such credential can start the same Task unseen. Whatever instance id it holds, it is kept off a Task an instance owns, which overturns part of the record on instance ownership (DEC-035).
- **Bots approve nothing in human mode.** In every project, an approval from an account GitHub records as a bot, or one the project registers as a reviewer agent's, does not count where a person's approval is required. This narrows who may approve in the records on the work's lifecycle and on review modes (DEC-026, DEC-027).
- **No answer, no person, under every credential.** Where the service refuses to say which account a credential acts as, or gives no answer at all, such as with no network, the identity is unresolved, a person's own credential included. Neither git's email nor `PM_INVOKER_LOGIN` stands in for it, where the membership gate's record (DEC-021) has them as fallbacks, so that part of it is overturned under every credential. Every command asks GitHub which account it acts as, the variable set or not.
- **A user's credential stays DEC-021's.** Where GitHub answers with a user's account, such as a machine user's or another person's, this record changes nothing in how the acting account is resolved, so `PM_INVOKER_LOGIN` set to the person would make that person the acting account. The variable's documentation tells a setup to leave it unset under a user's credential that is not the person's own, and [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) decides whether the variable may stand in place of a login GitHub answered, save as the actor the commands hand the engine's gate, which the record on where the reading lives decides.
- **Closed-mode CI changes, overturning part of DEC-021 and DEC-022.** A workflow under its own token passes a closed membership gate only where its account is a member, and neither the variable nor git's email stands for it. Whether the service names such a token's account is unmeasured. Until it is, such a workflow's only way through may be a credential that names a person. A workflow under a machine user's token with the variable set refuses wherever GitHub gives no answer, since the variable stands for no account GitHub did not answer for.
- **A member that admits every session.** A project that adds an app's account as a member admits every session under that credential, one that works for a non-member among them, where DEC-021 has the commands refuse such an agent.
- **No person is named beside a bot, overturning part of the house style for comments (DEC-052).** Under such a credential, an override comment names no person as its authoriser, where DEC-052 keeps one beside the bot that posts it.
- **An agent's local verdict names no person.** A reviewer agent's verdict posted on the local path attests only what the acting account ran, until the record on who may authorise in an agent's turn exists.
- **The caller's word stays unguarded.** A bypass, a held move, a release by force and an authorisation to merge given up front each pass on the caller's word, as under any credential. Who may give that word in an agent's turn is a record of its own.
- **Building waits on where the reading lives.** This record says what the commands need of the reading of the acting account. The backbone reads that account too, so where the reading lives is a record of its own. What reads the acting account is built only once a person accepts that record. The spelling of an account that record settles also decides whether the entries of the member lists projects hold need rewriting, and how a bare entry that names an app's account is treated. Point 5's guards on an author's kind read no acting account, and may be built first.

Each record this overturns in part stays accepted, and its top line names what this record overturns there. Each passage it narrows or completes is refined in place.

## Context

**The terms.**

- **A credential names a person** where the hosting service, asked which account the credential acts as, answers with a user's account.
- **An app's credential** is one for which the service answers that its account is an app's, and gives its login.
- **An unresolved identity** is every other outcome of asking: a refusal, whatever its cause, and no answer at all, such as with no network, on a timeout, or where something other than the service answers, such as a proxy. The commands report it with its cause ([project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162)). A person's own credential leaves the identity unresolved wherever the service refuses its lookup or cannot be asked.
- **A credential names no person,** in this record, where it is an app's credential or leaves the identity unresolved. Without the service's answer, the commands cannot tell an app's credential from a person's.
- **An app's account** is the account an app's credential acts as. Every session that holds the credential acts as it.
- **An account names no person** where the service records it as a bot, as it records an app's account.
- **A user account kept for an agent,** a machine user, is a user's account, which the service records as no bot. Its credential names a person, so where the service answers for it, what this record decides of the acting account does not reach it, and how `PM_INVOKER_LOGIN` stands beside it is [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)'s question (point 3). Where the service gives no answer, its identity is unresolved like any other. Beyond that, this record reaches it only where the project registers it as a reviewer agent's (point 5).
- **The person the agent works for** is the person whose work the agent's session does.
- **The setup** is what prepares the machine and starts the agent's session or the workflow, outside this capability.

**What happens today.** On a trial of software that starts agent sessions on hosted machines, an agent reached GitHub under an App installation's token ([project-kit#3004](https://github.com/aleskalfas/project-kit/issues/3004)). The commands resolve the acting account by looking it up as a user ([project-management:DEC-021-team-membership-gate], "Identity resolution"), and the service refuses the lookup:

- **No default assignee.** `create-issue` cannot default the assignee to the filer ([project-management:DEC-019-mandatory-issue-state], "Mandatory assignment").
- **Every assignee is someone else.** `start-work` refuses every Task assigned to the person the agent works for, and sends it to `handoff-issue`, which cannot help ([project-management:DEC-026-work-ownership-lifecycle]).
- **A workaround.** The trial went on by unassigning the person, starting the work, and assigning the person back.
- **The engine's gate takes the person as the actor.** Where `PM_INVOKER_LOGIN` names the person, the commands hand that person to the engine's cross-authority gate as the actor of each move, so the agent's own merge reads as another authority's.

[project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162) has the commands report an identity they cannot resolve, with its cause. How they act under such a credential is this record's.

**What was measured** on the trial ([project-kit#3164](https://github.com/aleskalfas/project-kit/issues/3164)):

- **The setup offers a credential that names the person.** It can grant the agent an OAuth sign-in or a personal access token beside the App's. Neither was granted to the trial's agent, so no command has run under one.
- **An app's account is spelled differently on different surfaces.** Read under the person's credential, the comments the trial's App wrote give its login with a `[bot]` suffix and the type `Bot`, and name the App that performed each write. gh's JSON gives the same account, on its pull requests, with an `app/` prefix, marked as a bot.
- **An App installation's token sees none of a user's boards.** Asked for the boards of the person's account, it answered with none, a public one included, and no error. The person's own token saw three.

**What was not measured:**

- **Whether an installation's token, a workflow's among them, can learn its own account and kind.** Both attempts to ask from inside the trial's agent failed before reaching it. Point 1 says what holds without it.
- **Whether the service answers an app's account's write access to a repository, and gives every reader the same answer,** which an open project's state issues read (point 7).
- **Whether a person's sign-in through a host's app marks the agent's writes as that app's.**

**What the records already say.**

- **The membership gate reads git's email second,** as a fallback "when `gh` is unavailable", and `PM_INVOKER_LOGIN` third, where those natural sources do not apply, and a match on any of them passes (DEC-021, "Identity resolution"). DEC-021 reserves the variable for CI and agent contexts, sourced from a CI secret or a workflow input and never from a value the user controls. Its Implications let a CI workflow pass the gate by setting the variable from a CI secret, and have the commands refuse an agent that works for a non-member. [project-management:DEC-022-methodology-mesh], "Authority", says the same of its scheduled workflow. The commands cannot tell where the variable was set.
- **A clone with no instance id behaves as if instance ownership were not there,** with no guard, and the id is the sole activation gate ([project-management:DEC-035-instance-ownership] point 1).
- **A claim on an issue of work counts only from the assignee's account** ([project-management:DEC-043-ownership-substrate-selection] point 3). The ownership fold applies that filter in one place ([pkit:ADR-041]).
- **A gate's authorisation comes from another authority than the actor it gates** ([pkit:COR-033] P4). The engine's cross-authority gate compares the actor a command hands it with the account this capability's predicate reports as having merged the pull request. What the gate takes as its actor where a command hands it none is the backbone's to decide.
- **In human mode, the gate passes on an approving review or an `Approved` comment from any non-author identity,** and the members whose role matches, but the author, are assigned as reviewers ([project-management:DEC-027-review-modes], "Human path"). DEC-026's tables count the comment from a commenter other than the author, and its Rationale ("Why the three-way OR") from the last commenter that is no bot. The commands count it from any commenter but the author, a bot among them.
- **A comment names who authorised an act** only where they differ from the account that posted it, and the actor is taken for the authoriser ([project-management:DEC-049-audit-journal-model] point 4). [project-management:DEC-052-comment-house-style] keeps the authoriser on a comment a bot posts.

**A rule held provisionally.** project-kit's own record on agent hosts holds that a need that differs between machines is met by reading a property, never a host's name, that a need not worth meeting is a limit, stated by its property with what meeting it would cost, and that a setup uses pkit's public surface as any adopter does, and its choices are its own ([pkit:ADR-091] points 2 and 4, and the first three bullets of its point 7). It holds those rules provisionally, and they reach no adopter as rules, so this record states for itself what it takes from them (points 1, 3 and 8).

## Decision

**Where the hosting service does not answer that a credential acts as a user's account, the commands take no person's identity for the account they act as, and no comment names a person as its authoriser. In every project, nothing an account the service records as a bot writes counts as a person's approval, or as a person's claim wherever a claim's author is read. The person the agent works for serves only where naming a person grants nothing.**

Where the service answers with a user's account, this record changes nothing in how the acting account is resolved, and how git's email and `PM_INVOKER_LOGIN` stand beside that account is [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)'s to decide (Implications, "Left out").

### 1. The commands read a credential's kind from the service's answer

- **One reading.** Which account a credential acts as, and of which kind, is read once from the hosting service, and every command of this capability takes it from that reading. The backbone reads the acting account too, so where the reading lives is a record of its own (Implications, "First, where the reading lives"). This record decides what the commands need of it.
- **An app's, only from a positive answer.** A credential is an app's only where the hosting service answers, for the credential, that its account is an app's, and gives its login. It is never read from a refusal, whose cause may be a rate limit, a suspended account or a network's rule as well as an app. Nor is it read from the credential's own form (Alternatives), or from the host or the tool that issued the credential, whose names say nothing of the account and may change without notice.
- **Every other outcome leaves the identity unresolved,** under every credential, and the commands act on it as on an app's credential with no account they know. They never fall back to a value that names a person. Without the service's answer they cannot tell an app's credential from a person's, and a fallback would let an app's credential act as a person whenever its lookup fails. So a refusal, a timeout, a failure of the secure connection and a proxy's error all leave the identity unresolved, and only the cause the commands report differs. Whether an earlier answer the service gave for the same credential, kept on the machine, counts as its answer is the record on where the reading lives to decide.
- **Only a grant needs the app's own account.** The membership gate (point 2) and a seat's claim (point 7) read the app's login, since they grant the acting account something. Everything else this record decides holds under an unresolved identity too, except that a clone that holds an instance id refuses there (point 4). So in this capability's own guards an answer misread grants nothing, and never lets a person's identity stand for the acting account. The engine's cross-authority gate is the backbone's, and point 2 says what the commands hand it.
- **Each guard reads the property it rests on:** the credential's answer for the acting account, and the service's record of an author for what that author wrote (point 5). The credential's kind is a fact of the session, read where the commands act. An author's kind is the same wherever it is read, so the guards that read it hold alike on every machine.

Whether an installation's token receives a positive answer is unmeasured. Where it does not, such a token leaves the identity unresolved: everything below holds, except that its account can be neither a member (point 2) nor a seat's holder (point 7), and a clone under it that holds an instance id refuses (point 4).

### 2. No person stands for the acting account

Under a credential that names no person, in a CI workflow and in an agent's session alike:

- **The acting account** is the app's, by the login the service gives it. Under an unresolved identity, the commands know no acting account.
- **One spelling, which keeps the account's kind.** Every comparison of two accounts puts both in one spelling, through one function beside the reading (point 1), whichever surface named each, reading each account's kind from a surface that gives it, and fails closed where none does. The spelling keeps whether the account is a bot's, so a bot's account and a user's never compare equal, though the service lets an app take its owner's own name. So no comparison spells an account its own way, as no command reads the labels its own way ([pkit:ADR-026]).
- **The actor the commands hand the engine.** The actor the commands hand the engine's cross-authority gate is the acting account in that one spelling, and this capability's predicate for the gate reports the account that merged the pull request in the same spelling. The actor is never the person the agent works for. Under an unresolved identity, the commands hand no actor, and what the engine takes then is the backbone's to decide (Implications, "Left out").
- **Git's configured email does not stand for it.** The email names whoever set up git on the machine, a person the credential does not act as, or one the commands cannot tell it acts as.
- **Nor does `PM_INVOKER_LOGIN`.** Whoever starts the run or the session can set it, and the commands cannot tell who did. It names the person the agent works for (point 3).
- **The closed membership gate** matches an app's account by its login alone. A project lets such an account act by adding it as a member. That admits every session that holds the credential, whoever starts it and for whomever it works, a non-member among them, and the project decides so by adding it.
- **The member list changes under no such credential.** Membership grants authority, and an account that names no person has no one to stand behind a change to it. So a command that adds or removes a member refuses, and a person changes the list under their own credential. This holds while the gate is open too, where adding such an account as the first member would close the gate with no person in it.
- **An app's account in the member list is no person.** Each member's login is kept in the one spelling, its kind included. So a command that picks members as people, such as reviewers in human mode, tells an app's entry apart and passes over it.

Where the service answers with a user's account, this record changes nothing in how the acting account is resolved, and [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) settles how git's email and the variable stand beside it. Where the service refuses or gives no answer, under any credential, the identity is unresolved, and everything above holds for it.

### 3. The person the agent works for serves only where naming a person grants nothing

- **Where it comes from.** Under a credential that names no person, `PM_INVOKER_LOGIN` names the person the agent works for. The variable is an input of the commands, documented with them, so its meaning is part of their public surface, which a setup uses as any adopter does ([pkit:ADR-091] point 7). One function of this capability reads it, for every command that needs that person.
- **Beside a user's account.** Where the service answers with a user's account, the variable keeps the place DEC-021 gives it, which [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) settles. Under a user's credential that is not the person's own, such as a machine user's, the variable set to the person would make that person the acting account. So its documentation tells a setup to leave it unset there, or to set it to the account the credential acts as.
- **Where it serves.** It stands where the commands would name the acting account as a person, and grant nothing by doing so:
  - the default assignee at filing, and `--me` on an assignment, held like any assignee to a member where the gate is closed (DEC-019);
  - `start-work`'s refusal of a Task assigned to someone else, and the assignee it writes (point 4);
  - which Tasks `next-task` hands out, since it hands out only what `start-work` takes.
- **Where it never serves.** It never stands where naming a person grants: the membership gate, a claim, an approval, or the authoriser a comment names. So `--me` on a command that changes the member list refuses (point 2). Nor does it tell whether anyone is at the terminal, which is a property of the session's process ([pkit:ADR-091] point 5).
- **Without it,** a command that needs a person refuses. It reports why it knows no person: the account is an app's, or the identity is unresolved, with its cause ([project-kit#3162](https://github.com/aleskalfas/project-kit/issues/3162)), and it says how the session can name one. `create-issue` still takes an assignee named in the call, as when a person files for another ([project-management:DEC-035-instance-ownership] point 5).

It is the caller's word, as an assignee the caller names is. Set wrongly, it lets the agent past the refusal that keeps it off another person's Task. Like DEC-035's clash guard, that refusal catches the mistakes of agents that follow the procedure, and is no security boundary.

### 4. `start-work` keeps its refusal, against the person the agent works for

Under a credential that names no person, in a project with no topology, `start-work`:

- **refuses a Task assigned to someone other than the person the agent works for,** and names `handoff-issue`, as DEC-026 has it;
- **assigns that person a Task with no assignee,** since DEC-019 needs one and the acting account cannot be it, and writes no assignee where that person is one already;
- **posts no claim,** since no claim it wrote would count (point 5);
- **refuses a Task an instance owns,** whatever instance id the clone holds. The clash guard reads the owner for such a clone, though the clone claims nothing. A reason overrides the refusal and posts an audit comment, as for any clash (DEC-035 point 6).

**Under an unresolved identity, a clone that holds an instance id refuses.** Every command that acts as an instance refuses there, says why, and is run again. Without the service's answer the commands cannot tell an app's clone from a person's. A person's clone that holds an id would otherwise start the Task and post no claim, and leave it In Progress with no owner, where another of the person's clones may act on it. A clone with no id claims nothing under any credential (DEC-035 point 1), so it goes on as this point says. An app's clone whose account the service does not name runs with no id, which is its setup's choice.

Every other ordinary lifecycle verb under such a credential reads the owner the same way. `handoff-issue` hands a Task from one person to another, and never to an app's account.

Two sessions under one such credential, working for one person, can start the same Task, since neither claims it. Nothing tells them apart, as nothing tells apart two of a person's clones with no instance id (DEC-035 point 1). This is a limit (point 8).

In a project with a topology, a clone under such a credential starts no Task (point 7).

### 5. Nothing an account that names no person writes counts as a person's

The commands read the kind of an author from the service's record of that author, which says whether it is a bot. These guards hold for every account the service records as a bot, under whatever credential the command runs, and whether or not the service lets that account be assigned:

- **A claim on an issue of work** counts only from the assignee's account (DEC-043 point 3), and never from a bot's. So a clone under a credential that names no person takes no part in instance ownership on issues of work. The guard reads a claim's author, which the comment log gives. A label names no author, so under the label substrate the guard has nothing to read: a clone under such a credential marks no issue, since it claims nothing (point 4), and a label stamped by other means counts as DEC-035 has it.
- **An approval in human mode.** An `Approved` comment or an approving review counts only from an account the service records as no bot, and that the project does not register as a reviewer agent's ([project-management:DEC-028-agent-as-approver-paths], the remote path's list). Of the reviews, the commands read the latest that approves, requests changes or was dismissed, and pass only where it approves, as they read DEC-026's latest approving review. An approval that does not count is left out of that order. So a bot's request for changes holds the merge until a person approves after it, as a person's request does, and a bot's approval clears nothing. Holding a merge back grants nothing. So `done-work`'s approval check rests on another authority than the actor, as COR-033 P4 asks.
- **A reviewer agent's verdict** counts in agent mode as DEC-028's paths have it. Under a credential that names no person, the local path's verdict is posted by the acting account. It attests what that account ran, and names no person responsible for it. That takes a person's name off an attestation no person made: under a person's credential, an agent's session posts the verdict in that person's name, though the person attested nothing. The local path rests on the trust of a bypass (point 6), and is revisited once the record on who may authorise in an agent's turn guards the caller's word.
- **An authoriser in a comment.** The only authoriser the commands know is the acting account, which posts the comment and here names no person, or is none they know. A comment names the authoriser only where the poster is someone else (DEC-049 point 4), so an override comment names no person as its authoriser. A reason the caller gives may report a person's word, and stays the caller's report.
- **A claim on a state issue** that an app's account writes is that account's own, and names no person ([project-management:DEC-058-state-issues] point 5). Point 7 says where such a clone claims.

### 6. What passes on the caller's word stays as it is

Some acts pass on the caller's word under every credential:

- a merge by bypass, and a promotion on a person's request in the session (DEC-026);
- an authorisation to merge given to the landing command before it runs ([project-management:DEC-055-pr-lists-answers] point 3);
- a move the user holds ([project-management:DEC-006-state-machine-and-cascade]);
- a release of a seat by force on a person's word ([project-management:DEC-059-topology-of-seats] point 5).

Under a credential that names no person they pass as they do elsewhere. Each is recorded as the acting account's act, with the caller's reason, and names no person as its authoriser (point 5).

This record guards none of them. Who may give that word in an agent's turn, such as a turn a chat started, is a record of its own ([pkit:ADR-091], Implications).

### 7. In a project with a topology, a clone under such a credential builds nothing

- **No seat that builds.** A worker's or a lead's seat rests on claims on Tasks that count (DEC-059 point 9), and such a clone's never do. So it takes no such seat (DEC-059 point 4).
- **No Task without a seat.** A clone with no seat marks no issue and is guarded by nothing (DEC-059 point 6). A Task it started would stand In Progress with no claim that counts, which a worker reads as ready to take over (DEC-059 point 7). So under such a credential `start-work` refuses.
- **A planner's seat, where every reader counts its claim.** An app's clone may hold a planner's seat, since its claim on the seat's state issue is its own account's. That claim counts only where DEC-058 point 4 counts its author: as a member where the gate is closed, and otherwise where the service answers that the account may write to the repository. Every clone reads the members as the default branch holds them ([pkit:ADR-071] point 3), so a member's claim counts alike for every reader. Whether the service answers alike about an app's account's write access, to every reader, is unmeasured. So an app's clone claims a seat only where the gate is closed and its own account is a member, which it reads before it claims. Where the gate is open, or under an unresolved identity, it takes no seat.
- **The organizer seat** is held on the same terms. An app's clone that holds it releases other seats by force as that seat's clone does (DEC-059 point 5), each release recorded as the acting account's act with its reason. The seat's privilege goes to whichever clone holds it, under any credential. So a project that admits an app's account admits every session that holds the credential to that privilege, as to the gate (point 2).
- **A planner's filings** are assigned to the person the agent works for (point 3). Workers under that person's own credential take them. A worker under another person's credential meets `start-work`'s refusal, as it does with the filings of a planner under any one person's credential.

A claim whose author's standing differs between readers splits the seat. Under an open gate, a reader whose call about the app's account fails reads the issue as incomplete, since a failed call drops no claim ([pkit:ADR-071] point 3), and nobody in that reading can take the seat. A reader that gets a definite no reads the seat as free while the app's clone holds it, so two clones may hold one seat. And this capability never edits a comment on a state issue (DEC-058 point 4), so only a person deleting the comment by hand ends either.

### 8. What stays unmet, and the setup's choice of credential

These needs stay unmet under a credential that names no person. Each is a limit, accepted with this record, stated by its property with what meeting it would cost ([pkit:ADR-091] point 4):

- **Instance ownership on issues of work,** and so building in a project with a topology. Meeting it would count a claim from an account that names no person, which loosens DEC-043 point 3: anyone holding the credential could then claim work for any person. That loosening is a person's decision of its own.
- **Two sessions under one such credential, kept off one Task.** Meeting it needs a mark that such a clone makes and that other such clones read, a design of its own.
- **The closed membership gate under an unresolved identity,** a workflow's token among the credentials that may leave it so. Meeting it needs the service's positive answer for the credential (point 1).
- **A planner's seat behind an open gate.** Meeting it needs the service's answer about an app's account's write access, measured alike for every reader (point 7).

A setup that needs one of them gives the agent another credential:

- **A credential that names the person the agent works for,** which the measured setup offers and which no command has run under yet. The commands then act as the person, and the agent's pull requests are the person's own, which the person cannot approve (DEC-028, "Self-approval degrade").
- **A machine user,** which is not recommended. With `PM_INVOKER_LOGIN` unset, or naming that account, the commands act as it as they act as a person, so the assignee would name no person responsible for the work (DEC-019). Set to anyone else, the variable makes the commands take that person for the acting account, which [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) settles (point 3).

Which credential an agent holds is its setup's choice ([pkit:ADR-091] point 7).

## Rationale

**Why the commands take no person's identity where the service names none.** Where the service does not answer that the credential acts as a user's account, any value that names a person is the caller's word, or git's record of whoever set the machine up. Acting as the person on it would make each act of the account read as the person's own, in the tracker and in every check that reads it. Acting as the account the service names keeps that record true, since the service shows which account wrote each change.

**Why no answer leaves the identity unresolved, under every credential.** Without the service's answer, the commands cannot tell an app's credential from a person's. A fallback to git's email or the variable there would make the person the acting account under an app's credential whenever its lookup times out. That is the very machine a setup prepares for an agent: it names the person in the variable (point 3), and git's email there is likely the person's too. Failing closed costs little, though not nothing:

- **Little else works without the service.** A command that cannot ask the service which account it acts as can rarely do its work there either, since every write it makes goes to the service ([project-management:DEC-003-github-bound-substrate]). It says why it refused, and is run again. A command that writes only on the machine, such as one that stamps the member list, changes nothing until a pull request lands, which needs the service too.
- **One call for every command.** Every command asks the service which account it acts as, the variable set or not, which counts where many agents run at once against the service's limits on calls.
- **A machine user's workflow that sets the variable** refuses wherever that call fails, since the variable stands for no account the service did not answer for.
- **An earlier answer kept for the same credential** would spare both, and whether it counts as the service's answer is the record on where the reading lives to decide (point 1).

The posture is decided only for the acting account's identity, and every other read keeps the posture DEC-021 left to its implementation.

**Why `PM_INVOKER_LOGIN` names no acting account where the service names none, in CI as in a session.** Set to the person, it would let `start-work` write the person as assignee. Three things stand against it:

- **It names the person as the actor of every act.** Each override comment would name the person as its authoriser, beside the account that posted it (DEC-052), whether or not the person authorised anything.
- **It hands the engine's gate the wrong actor.** The gate would compare the person with the account that merged, so the agent's own merge would read as another authority's (COR-033 P4).
- **It would not make a claim count.** The ownership fold reads who wrote a claim, never the variable (DEC-043 point 3). So instance ownership stays out of reach.

DEC-021 meant to keep the variable from a value the user controls, and trusted a CI workflow to keep it so. The commands cannot tell whether it did, under any credential. A workflow's input is typed by whoever dispatches the run, and an earlier step can set the environment of later ones. A pipeline that runs an agent's session on one prompt is both a CI workflow and an agent's session. So under a credential that names no person, the variable is read the same way in both: as the caller's word, where the caller's word grants nothing. Where the service answers with a user's account, the variable keeps the place DEC-021 gives it, and [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) settles how DEC-021 reads that place. Which of the two meanings the variable has is told by the service's answer, a property the commands read. Under a user's credential that is not the person's own, the variable set to the person would bring back the first and third hazards above, and the second wherever the commands hand that person to the engine's gate, which the record on where the reading lives decides, so its documentation tells a setup to leave it unset there (point 3).

**Which edits overturn, and which refine.** One test sorts every edit this record names to an accepted record, by what the passage states for the case this record decides:

- **Overturned in part,** where the passage states, for that case, an outcome this record contradicts: a named fallback or provision, or an explicit no. DEC-021's git email "when `gh` is unavailable", its variable for CI and agent contexts with the match on any surface they pass through, its workflow that passes by the variable from a CI secret, and DEC-022's same option are such provisions, and so is DEC-052's parenthetical that keeps the authoriser beside a bot. DEC-021's refusal of a non-member's agent, and DEC-035's "no guard" and its id as "the sole activation gate", are such outcomes. The passage stays as it stood, under a top line that names this record, since a refinement in place narrows, widens or completes a decision that still stands.
- **Narrowed in place,** where the passage grants something to a general class, such as anyone, any member, any non-author or any clone, and this record takes out of that class the credentials and accounts it decides for, while the grant stands for the rest. DEC-021's "Bootstrap", "Membership change authority" and "Tooling surface" let anyone while the gate is open, or any member, change the list. DEC-026's and DEC-027's approval passages count an approval from any non-author, and their reviewer passages assign any member whose role matches. DEC-026's `start-work` and `handoff-issue` rows, DEC-043 point 3, DEC-058 point 5, DEC-059 points 4 and 6, and ADR-041 grant to any member, any account named, any assignee or any clone.
- **Completed in place,** where the passage states no outcome for that case, as a question it left open or a term it fixes only for a person, and this record supplies one. DEC-021 left the posture on network errors to its implementation (its Rationale, "Why mechanism details are deferred"), and this record settles it for the identity read. DEC-019's filer, DEC-028's developer and ADR-071 point 3's answer about a bot's access are of this kind.

The test asks what a passage states, not what case it was written for. DEC-021's deferral of identity resolution's edge cases covers what it leaves open, such as the order of the sources and how a failed read is reported, but not a source a passage names as a fallback, or a provision its Implications make. Either way, item 2 is overturned by name, so no reading of DEC-021 lets git's email stand where the service gave no answer.

**Why git's email does not stand for the account.** Under any credential the email is a value the user controls, and that hole beside a person's resolved login is no question of this record's ([project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)). Where the service names no person, there is a reason of its own: the email names a person the credential does not act as, or one the commands cannot tell it acts as.

**Why the person the agent works for grants nothing.** Most of what the commands do with a person's login says whose the work is: the assignee at filing, and whether a Task is someone else's. A wrong value there misleads, and grants nothing, since a claim, an approval and membership are each read from the account that wrote or acts, never from the assignee. A command that takes an assignee from the caller, when a person files for another, takes the caller's word the same way.

**Why `start-work` keeps its refusal.** Without a person to compare with, an account that names no person is nobody's assignee. The refusal would then either catch every assignee, as on the trial, or none, which would let an agent start any member's Task. The refusal is a mistake-catcher, as are its neighbours (DEC-058 point 5, and DEC-059's release by force, which "catches mistakes, and it is no security boundary"). On the caller's word, it keeps catching the mistakes of agents that follow the procedure.

**Why a clone that holds an instance id refuses under an unresolved identity.** A clone that holds an id means to claim what it starts. Under an unresolved identity the commands cannot tell whether its claim would count, since they cannot tell an app's credential from a person's. Going on would start the Task with no claim, and the person's other clones would read it as nobody's. Refusing costs a person's clone a second run after a failed lookup, and an app's clone the instance id, which it cannot use anyway. A report that it posted no claim would keep the clone working, but leave the Task with no owner all the same, the one place the reach would fail open.

**Why the clash guard reads for such a clone.** A person's clone with no instance id may opt into ownership, and is guarded once it does (DEC-035 point 1). A clone under a credential that names no person cannot opt in, since none of its claims counts. Reading the owner is then the only guard it can have, and it grants nothing.

**Why the guards read the author's kind.** A claim means something because only the assignee's own account can make it (DEC-043 point 3). A guard derived from the service refusing a bot as an assignee would fail once a bot can be assigned, as GitHub lets its own coding agent be. Read from the author's kind, the guard holds for every bot, whatever the service lets it be. Counting a bot's claim for its assignee would let anyone who holds the credential claim work for any person.

**Why a bot approves nothing in human mode, in every project.** Human mode asks for a person's approval. DEC-027 counts an approval from any non-author identity, and DEC-026's tables and the commands count the comment from any commenter but the author, a bot among them, while DEC-026's Rationale counts it only from a commenter that is no bot. Reading the author's kind brings the tables, DEC-027 and the commands to the Rationale's rule on a bot, and applies it to reviews too. It also leaves out the accounts the project registers as its reviewer agents', which name no person whatever the service reports. A request for changes stays in the order of reviews, since holding a merge back grants nothing, and a person's later approval clears it as it clears a person's request.

**Why DEC-028's local path stands, for now.** DEC-028 rests the local path on the developer's attestation, the trust of a bypass, rather than on a trace from another authority. Under a credential that names no person, a bypass passes all the same (point 6). Refusing the local path would push such an agent to a bypass, which records less: no verdict, no reviewer, no head reviewed. Keeping it loosens nothing: under a person's credential, an agent's session already posts the verdict in the person's name, though the person attested nothing, and under a credential that names no person the verdict names no person, which is true. The reason lasts only while a bypass passes on the caller's word. Once the record on who may authorise in an agent's turn guards that word, the local path is the weakest way past the gate under such a credential, and is revisited.

**Why such a clone builds nothing in a topology.** A seat stays taken until it is released (DEC-059 point 5). A clone that took a building seat and could claim no Task would hold the seat while doing none of its work. A Task it started without a seat would read as ready to take over, and a worker would take it over from under the agent.

**Why an app's clone claims a seat only behind a closed gate.** A claim on a state issue counts by its author's standing, which each reader judges when it reads. Behind a closed gate every reader judges it by the same members, read from the default branch. Behind an open gate each reader asks the service about the author's write access, and whether the service answers alike about an app's account, to every reader, is unmeasured. A claim judged differently by different readers splits the seat (point 7), and only a person's hand can end that, so the claim waits until the answers are measured alike.

**Why an app's clone may hold the organizer seat.** The privilege of releasing seats by force already goes to whichever clone takes the seat, a clone of any member's among them. So an app's clone in it grants no more than the project granted by admitting the app's account. Keeping it out would leave such a clone no seat at all, since the planner's seat is typically the organizer's.

**Why act as the account, and not only state a limit.** The setup offers a credential that names the person, so every need could be a limit. But most of what the commands do needs no person at all. And under the person's credential, the agent's pull request is the person's own, which the person cannot approve (DEC-028, "Self-approval degrade"). Under an account that names no person, the person can approve it, by a review or an `Approved` comment. `done-work`'s approval check then reads a trace from another authority, as COR-033 P4 asks of a gate. The engine's own gate on the move to Done reads who merged the pull request instead, and refuses the move after the agent merges its own approved pull request, as it refuses a person's own merge today (Implications, "Left out").

**Why building waits on where the reading lives.** The acting account is the backbone's concern too: the account `pkit report` posts as, and the actor the engine's gate compares. Two readings of one credential can disagree, and at the engine's gate they already can. Under an app's credential the two sides may spell one account two ways, and the gate then reads the agent's own merge as another authority's. A reading built in this capability first adds one more copy before its home is decided. A capability's script reaches the backbone only by command ([pkit:ADR-057] point 1), the backbone cannot depend on a capability a project may not install, and a computation keeps one home ([pkit:ADR-057] point 2). So the one home both can read lies outside this capability, and a record of the backbone's places it, as [pkit:ADR-061] placed the hosting service's acts.

### Alternatives considered

- **State a limit and nothing more:** the commands act only under a credential that names a person. The case: one sentence, and nothing to build. Rejected: most of what the commands do needs no person, and the person could not approve their agent's pull requests.
- **A limit, plus a mark the commands add to what an agent's session writes.** The case: no edits to other records, and instance ownership keeps working under the person's credential. Rejected: the mark is the session's own word, so the line it draws is weaker than the service's record of which account wrote, and the person still cannot approve the agent's pull requests.
- **`PM_INVOKER_LOGIN` names the acting account,** in an agent's session, or only in a CI workflow as DEC-021 provides. The case: `start-work` and `create-issue` work as under the person's credential, with nothing new, and this record would overturn nothing in DEC-021, DEC-022 or DEC-052. Rejected, for the reasons above, and because no line between a workflow and a session holds.
- **`PM_INVOKER_LOGIN` never stands for the acting account, under any credential,** overturning DEC-021's item 3 whole. The case: the one variable has one meaning on every machine, so a setup that names the person under a machine user's or another person's credential never makes that person the acting account, and a workflow under a machine user passes a closed gate where its own account is a member. Rejected: it takes [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)'s question, whether the variable may stand in place of a login the service answered, which rests on evidence of its own, and it changes the CI setups that pass the gate by the variable under a user's credential, which no credential this record decides reaches.
- **Fall back to git's email and the variable where the service cannot be asked,** as DEC-021 provides. The case: a person's own credential keeps passing the gate with no network, and DEC-021's fallback stands. Rejected: without the answer the commands cannot tell an app's credential from a person's, so under an app's credential a timeout would make the person the acting account, on a machine whose setup names that person. With no network, little the commands do can succeed anyway.
- **Read a credential's kind from its own form,** such as the prefix the service gives each kind of token. The case: a property of the credential, read on the machine, which tells an installation's token from a person's even where the service refuses the lookup. Rejected: it is a second reading of the kind, which can disagree with the service's answer, as on a person's sign-in through a host's app, which is unmeasured (Context). A form the commands do not know leaves the identity unresolved anyway, and the command must read the secret itself to see its form.
- **A variable of its own for the person the agent works for,** leaving `PM_INVOKER_LOGIN` the meaning DEC-021 gives it. The case: each variable has one meaning on every machine, and a setup that names the person primes no fallback of DEC-021's with that person's login. Not taken. Alone it would not keep the person from standing for the acting account, since git's email on an agent's machine names the person too. Where the service names no person, neither variable stands for the acting account once no answer leaves the identity unresolved (point 1), so a second name closes nothing more there. Under a user's credential that is not the person's own, the one variable set to the person would stand for the acting account, so the rejection rests there on the setup guidance that leaves it unset (point 3), and [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175) decides whether the variable may stand in place of a login the service answered. A second name costs a documented input that every setup and workflow learns, and the service's answer already tells which meaning the one variable has.
- **One record on identity resolution for every credential,** taking DEC-021's "Identity resolution" whole, in place of a top line that names this record and later [project-kit#3175](https://github.com/aleskalfas/project-kit/issues/3175)'s. The case: one place says how the acting account is resolved. Not taken: it would hold this record on that issue's question, a person's login beside another person's email, which rests on other evidence, and it would fold in where the reading lives, which is the backbone's. The record that settles that issue, and decides what is left of that section, may state the whole resolution in one place, citing this record.
- **The person the agent works for as a second check at a closed gate,** refusing a session under an app's credential that names a non-member. The case: it grants nothing, and keeps DEC-021's refusal of a non-member's agent as a mistake-catcher. Not taken: it would refuse only a session that names a non-member truthfully, and pass one that names a member or no one, so it keeps out no session the project did not admit by adding the app's account. Unlike `start-work`'s refusal, which every credential has today and this record keeps, it would add a check at every command's start that no credential has. A project that wants non-members' agents kept out gives them no credential whose account it admitted.
- **Refine DEC-021, DEC-022, DEC-035 and DEC-052 in place,** whole. The case: each keeps stating its decision whole, and DEC-021 left identity resolution's edge cases to its implementation. Not taken: a refinement in place narrows, widens or completes a decision that stands, and the passages this record overturns each state, for the case it decides, an outcome it contradicts.

- **Read an app's credential from the service's refusal to look the account up.** The case: it is what the trial saw. Rejected: a refusal has other causes, and gives no account to act as.
