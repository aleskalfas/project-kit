> **Partially superseded by [DEC-065](DEC-065-answers-read-from-check.md).** A pull request's description carries no list of the answers its change wrote, and each reader derives the answers from the change check at the pull request's head. Overturned: points 1, 2 and 4 of this record, and each other passage of it that writes, carries, reads, prints or compares that list. Every other choice stands.

## Context

An agent building a change may give the answers its own change owes — the revalidations, deferrals and revisit entries the change check asks of it — without asking anyone first. A reviewer other than that agent checks them, and the pull request says what changed in each `updated` document. The person who authorises the merge is told what changed and what is left out of date, as information, not a gate: a change with answers merges under the same authorisation as any other (COR-050 point 3). The change check gives the list of answers in its machine-readable output (COR-050 point 12).

This capability is where a pull request is reviewed and its merge authorised: the reviewers' verdicts gate the merge (DEC-028), the person reads the pull request's description, and the landing command stops ready — naming the head and the command that merges it — for them to authorise. If nothing puts the list there, the reviewer and the person rest on an agent copying it by hand.

A reviewer's verdict can carry a question only a person can settle: a `[person]` finding, which judges the change under an accepted rule that does not settle it (DEC-028). It too reaches the person who authorises the merge only if something puts it in front of them first.

An authorisation to merge is given for the head the landing command's ready stop names. A change writes its answers in answer files it adds. Each answer names the other answers on its artefact that it read ([COR-062](../../../decisions/core/COR-062-answers-in-own-files.md) points 1 and 4). A merge of the base can then have the change answer again, which moves the pull request's head ([project-management:DEC-064-base-merge-named], "Why the base is not merged before every landing"). The person is then asked again to authorise a head whose only new changes are answers they do not judge.

Two revalidations of one document made apart, neither reading the other, are reported as debt rather than conflicting (COR-062 point 7). The person who authorises a merge that would leave a document so is told of it only if something puts it in front of them.

Two pull requests can each pass the change check alone and leave a document stale once both have landed. One adds an anchor to a document, and the other changes what the anchor stands on. Each check compared its pull request with the base as it stood when the check ran, so neither saw the two together. Where a project enforces the documentation check on stale documents, the stale document then fails that check on every later pull request until someone answers it ([project-management:DEC-053-doc-check-slot]).

## Decision

**A pull request's description carries the change check's list of the answers its change wrote, written by this capability. No word of it is composed by an agent, apart from the author's sentence on what changed in each updated document, which the list gives beside that document. The command that makes the pull request ready refuses an updated document with no sentence. The command that lands the pull request writes the list for the head it merges and prints it before it stops ready, asks or merges. Beside it, it prints each revalidation the merge would leave answered apart. A change with answers merges under the same authorisation as any other. The command also shows each finding a reviewer left for a person to judge. On an authorisation given up front, it merges only if the run found, at its start, every verdict carrying such a finding, and each stands for the head the run merges. An authorisation for one head also covers a later head where every change the author made since lies in the answer files the change adds, a clean merge of the base counting as no change. A run merges that later head only where nothing there needs the person. Just before it stops ready, asks or merges, the command also runs the change check on the merge of the head with the base's tip as it stands, and refuses where that check fails in the project's mode, naming each document it fails on.**

### 1. The list

This capability writes the answers a change wrote into the pull request's description, in a section of its own, `## Documentation this change affects`, delimited so a command can find, compare and replace it whole. The section speaks to a reader who does not know this methodology: its heading, an opening sentence and each entry say in plain words what the change decided about each document; the change check's own terms stay in the machine-readable list. The list is the change check's own list of the answers the change wrote, derived at the pull request's head against its base, as the change check compares any change (COR-050 point 6). Each entry gives the artefact, the answer, its anchor where it has one, and the justification or reason word for word, with every flag the change check puts on it, and each deferral a revalidation kept; the list counts the files the check could not read. An entry for an `updated` document also gives the sentence the change's author wrote on what changed in it. That sentence is the one part of the list the change check does not supply, and it is shown as the author's. Where the change alters the friction settings that decide what the check asks — the places it reads or the files it leaves out (COR-050 points 1, 7 and 14) — the list also gives each such change as it was and as it is. The section is replaced whole whenever it is written. Apart from the authors' sentences, no word of it is composed by an agent, and a section under that heading that this capability did not write is removed. Where the change wrote no answers and alters no such setting, the landing command removes any list an earlier head left.

### 2. Who writes it

The command that opens the pull request writes it; every edit of the description through this capability carries it unchanged; the landing command derives it again before the merge. Every write carries each `updated` document's sentence from its author.

### 3. The review and the authorisation

The review the merge waits for (DEC-027, DEC-028) includes a reviewer the project chooses, where it chooses one, other than the agent that wrote the change's answers. That reviewer checks every `unchanged` and `deferred` reason among the answers the change owes against the change, and each `updated` document's sentence against the diff. It does not check a deferral the change keeps as it was. The reviewer blocks the merge when a reason does not hold, when a checked deferral names no open follow-up, or when an `updated` document has no sentence or its sentence does not match what changed (COR-050 point 3). The list in the description, and the landing command's printout of it before it stops ready, asks or merges, tell the person who authorises the merge what changed in each updated document, and which documents are left out of date until which follow-up. This is information, not a gate: a change with answers merges under the same authorisation as any other. The authorisation is the person's, to merge the pull request (Review → Done), not the review approval an agent may give (DEC-028). An entry flagged as not asked for, and a reason for having no anchors, needed the person's acceptance, or the decision of the delegate they named ([COR-064](../../../decisions/core/COR-064-answer-delegate.md)), before it was written; authorising the merge does not give it. The reviewer checks each such entry too, whoever decided it, and blocks the merge when one does not hold (COR-064 point 4).
- **Before the review.** The command that makes the pull request ready and requests reviewers (DEC-026) refuses a description whose list marks a document `updated` with no sentence for it. It refuses it as it refuses any description not ready for review, naming each such document and the form a sentence takes. The refusal is a `hard-reject`, which `--force` overrides (DEC-046 point 2). That override leaves no trace on the pull request yet (#2660).
  - **The list at the head.** The list's start marker names the head the list was derived for. Where that is not the pull request's head, the command derives the list at the pull request's head. It refuses exactly what that list marks `updated` with no sentence, a document updated since included. The marker's head alone decides, so a pull request retargeted with its head unmoved keeps the description's list. The reviewer backs the refusal, and the landing command writes the list again before it merges.
  - **A document the list at the head does not mark.** For each document the description's list marks `updated` and the head's does not, with no sentence, it prints one line naming both heads. The line says the description's list is out of date for that document, which needs no sentence. It adds that the landing command writes the list again before it merges, and that a merge through the other merge commands keeps the list as written.
  - **What it cannot read** stops it: a description it cannot read, or a list it cannot derive at the head. Neither is read as a description with no list, and neither draws a refusal.
  - **Under `--force`,** a list it cannot derive at the head gives way to the description's list, with a warning saying so. The refusal on that list is printed as the description gives it, and overridden.
  - **The other commands.** The command that opens the pull request with its list, and the one that edits its description, only warn of a missing sentence.
- **A sentence the list does not show.** The command that opens the pull request with its list warns of a sentence on a document that list does not mark `updated`. So does the command that makes the pull request ready, where it derives the list at the head, and the landing command, before it stops ready, asks or merges. The list never shows such a sentence, and none of the three refuses: the author removes it with the command that edits the description. A run authorised up front holds on it, as on a `[person]` finding, and stops ready until the author removes it.
- **What is shown.** The landing command also prints each `[person]` finding whole (DEC-028) before it stops ready, asks or merges. A run that asks at a terminal asks after the printed answers and findings. The findings come from each reviewer's latest verdict as the merge gate would select it, from a reviewer DEC-032 resolves as required for the pull request and carrying the verdict marker, on either path and in either review mode. A verdict that no longer stands for the head is printed marked stale, with its reason. The findings are printed beside the answers and never join the list.
- **Answered apart.** For each document the change revalidates, the landing command also prints the live revalidations on the base's tip that its answer did not read. Merged, the two are answered apart, which the whole-repository check reports as debt until a revalidation reads both (COR-062 point 7). It derives them against the base's tip, not where the head left the base, and prints them beside the list, which they never join. This is information, as the list is, and stops nothing.
- **The findings' hold.** A `[person]` finding holds a run authorised up front, whether or not the change wrote answers. Such a run merges only if it found, when it started, each of those latest verdicts that carries a `[person]` finding. Each must stand for the head the run merges, by the merge gate's freshness rule (DEC-028). Such a verdict that the run posted, or one posted while it ran, stops the run ready, unless the head has moved or the merge is refused outright. An identical re-run can then merge. Such a verdict that does not stand for the head the run merges stops every run authorised up front, unless the head has moved or the merge is refused outright. Its stop names the review it waits for, ahead of the command that merges. No such run merges until that reviewer posts a verdict that stands for the head.
- **A later head.** An authorisation to merge is given for the head the landing command's ready stop names. It also covers a later head of the same pull request in one case. The later head descends from it along the branch's own line of commits. Every change the author made since, read as the freshness rule reads the author's changes (DEC-028), lies in the answer files the change adds (COR-062 point 1). Those hold the revalidations, deferrals and revisit entries the change check asks of a change, and nothing else.
  - **A merge of the base** counts only for what differs from git's merge of its two parents. An answer file the change adds never conflicts with the base, so a conflict resolved anywhere is a change outside the change's answer files. A later head whose only change is a clean merge of the base is covered too, whether or not the change wrote answers.
  - **An answer file removed** whole drops every answer in it, so it counts as a change outside them. So does a change to an answer file the base holds, which the change check fails too (COR-062 point 3). An answer removed from a file the change adds lies inside it.
  - **Who answers it.** The backbone answers whether the changes lie in the answer files the change adds. This capability never reads an answer file itself.
  - **Any other change** between the two heads stops the run before it checks anything, exactly as a head nobody authorised does. So does a later head the backbone cannot answer for.
  - **The run at the later head** passes as any run must: its checks pass, and each required verdict stands for that head. It also finds no `[person]` finding, no entry the list flags as not asked for, and no reason for having no anchors. So a change with such an entry, such as a new document's deferral, never merges at a later head on an earlier head's authorisation.
  - **Stricter than the findings' hold.** The run stops on such a finding or entry even where it found it at its start. It stops too where the earlier head showed it. The run cannot tell whether the person was shown it before the authorisation (point 5). It stops ready, naming the later head.
  - **What it says.** A run that merges a covered later head says which head it merged, and why the authorisation covered it.
  - **How long it lasts.** This sets which heads an authorisation covers, not how long it lasts (DEC-006).
- **Stops that nothing overrides.** The landing command merges nothing and writes nothing when the list cannot be derived, when a file the change touches cannot be read for answers, when a word of the list reads as a closing reference or holds an HTML comment's delimiter, or when the description cannot hold the list. Nor does it where the base moved on in a way that could land words the list does not show, the case DEC-064 point 1 sets out under "What the list shows". A base that moved on otherwise stops nothing here, as the change check itself only reports it (COR-050 point 12), and point 6 checks the merge with it. Nothing overrides these stops. Merges through other commands, or outside this capability, are point 5's.

### 6. The merge as it would land

Just before it stops ready, asks or merges, the landing command checks the merge it would land, not only the head. It builds the merge of the head with the base's tip as the tip stands then, touching no branch and none of the person's work. It runs the change check on that merge against the tip, and judges what each answer read against the head, as the checks on a pull request judge it (COR-062 point 4). Where the check fails there, the command merges nothing and names each document the check fails on, with the finding on it. Which merge of the base the stop names, so the change can answer what the merge would land, is DEC-064's (point 1): none where the head already holds the base's tip.

- **What fails it.** The check fails at the merge as it fails on any change, in the mode the project sets (COR-050 point 12). Friction fails it, such as an anchor another pull request landed that stands on what this one changes. In warning mode the step stops nothing, and shows the person what the check finds there, as information.
- **A merge that conflicts** stops the landing, as a conflict the host reports does, and DEC-064 point 1 names the merge of the base to make. A check that gives no answer at the merge also stops the landing, since it is never read as a pass, and names no merge.
- **The change check alone.** The whole-repository check is not run at the merge. What a change leaves unanswered is what that check reports once the change merges, apart from the cases COR-050's rationale names under "Where the two checks part". A document the base had already left stale is the base's debt, not this change's.
- **No override.** Nothing overrides it, as nothing overrides point 3's stops. It falls after the list's step, so the list for the head stays written in the description. A base that moved on, where the check passes at the merge, stops nothing.

### 4. Never input

No reader of the description treats the section as input — none that reads closing references or the `## Doc impact` section (DEC-013, DEC-015), or checks the template was filled (DEC-031). Nothing in the section closes an issue. The squash commit carries it as it carries the rest of the description.

### 5. What this does not verify

That a person read the list, or that the reviewer checked every answer on it: the reviewer's verdict is the review's (DEC-028), and the person's authorisation is the same as for any other change. A review bypassed or overridden (DEC-028, DEC-050), or a project that chooses no such reviewer, leaves the answers checked by their writer alone, a limit COR-050 point 3 accepts. A verdict covers the reasons at the head it reviewed: a reviewer whose approval stays fresh across a change to a file that carries a listed answer, or a sentence edited in the description after the verdict, leaves what changed since unchecked. Nobody checks a sentence on a document the list does not mark `updated`: the commands that derive the list warn of it, and a run authorised up front holds until it is removed (point 3). Nor can the command tell that a person read a `[person]` finding, or that its verdict was posted before the authorisation. A verdict replaced at the same head after the person was shown it, and before the run started, passes the findings' hold. So does one posted after the landing command last read the verdicts, in the moments before the merge. Showing each finding is the agent's duty, on every path to the merge. The landing command holds that the list in the description is the list for the head it merges. It holds too that the run found, when it started, each latest verdict that carries a `[person]` finding, and that each stands for the head it merged. A verdict stands across a change outside what its reviewer checks, so it passes the findings' hold even where that change touched a passage its finding judged. A merge through this capability's other merge commands, or outside this capability, takes no such step: after a fix round the description may carry the list of an earlier head, or none. A project that runs no checks on its pull requests lands through those other merge commands, since the landing command waits for checks, so its merges take no such step either. Nor is the person shown the answers written at a covered later head before it merges. They are told that head's list through the description and the run's printout. A reviewer whose verdict goes stale on that change checks those answers there. One whose approval stays fresh across it leaves them unchecked, as above. A change in the answer files the change adds can also take away an answer the earlier head gave. A deferral or an entry removed from them does so. Where the change was asked about it, the change check reports the friction, or the target not revisited, that this leaves, and fails on it only in enforcing mode (COR-050 point 12). Debt it brings back elsewhere is the whole-repository check's (COR-050 point 9).

Nor does the check of the merge (point 6) hold the base still. A commit that reaches the base after the check and before the merge lands without this change being checked against it, and at a terminal that time includes the person's answer to the prompt. A merge queue builds a merge of its own, which only the checks the queue runs judge.

The check of the merge is the change check, not the documentation check (DEC-053). A project that enforces the documentation check on stale documents while its change check runs in warning mode is shown what the merge leaves stale, and is not stopped. Nor is a merge checked for code of the declared surface that it leaves with no anchor (COR-050 point 8), which the whole-repository check measures and the change check does not.

## Rationale

**Why the description.** It is what the person reads before authorising the merge, and the squash commit carries it (DEC-013), so the answers that landed stay beside the change in the default branch's history.

**Why the capability writes it from the check.** What the reviewer checks must be the check's list, never an account the agent composed, so no answer the change wrote escapes it (COR-050 point 3). The sentences on what changed are the author's because the check cannot supply them: it knows that a document changed, not what the change means. The reviewer checks each against the diff. A section derived from the check's document at the pull request's head, and replaced whole on every write, cannot drift from the artefacts and keeps no entry of an earlier head. A section under the heading that this capability did not write is such an account, so it is removed rather than shown beside the list.

**Why the landing command derives it again.** The head that merges is often not the head the pull request was opened at: a fix round rewrites answers and adds others. Deriving at the head the landing command pinned, and comparing with the description, makes "the list in the description" mean the list for the head that merges.

**Why the command that makes the pull request ready refuses a missing sentence.** The reviewer blocks the merge on an `updated` document with no sentence. That spends a round of review on words the author could have written before it. The refusal comes before the reviewers' next round, so it saves that round.
- **Only there.** The command that opens the pull request with its list never refuses over it, and a draft may be unfinished. An edit of the description may come before the sentences are written.
- **The list at the head decides.** The list the description carries can be out of date. A fix round can update a document, answer one otherwise or drop its revalidation, and the command that edits the description carries the list as it was (point 2). A sentence on a document no longer `updated` would describe a change it no longer has. So where the list is for another head, the command derives it at the pull request's head, and refuses exactly what that list marks.
- **One rule, one run.** Every move to review with a list for another head runs the change check once, whatever the list shows. That run is cheaper than the review round a missing sentence would spend.
- **What it cannot read stops it.** Where the list cannot be derived at the head, what failed is the derivation, not the description, and running again may clear it. So the command stops, and asks no edit of the author. A refusal then rests on a list for the pull request's head. An operator who passes `--force` has chosen to pass the refusal, so the description's list stands in, with a warning, rather than a second stop.
- **From the description where it can.** Where the list is for the pull request's head, the command reads it from the description, and runs no change check. It trusts the marker's head alone, since where a head left its base is the backbone's to compute, never this capability's ([COR-054](../../../decisions/core/COR-054-default-branch.md) point 5). That leaves a pull request retargeted with its head unmoved to the reviewer, and to the landing command, which writes its list again (point 3). Where a description carries no list, such as one opened before any answer was written, the command refuses nothing.
- **What it leaves to others.** A head pushed after the move to review, and a description that carries no list, are the reviewer's to block on a missing sentence. The landing command writes the list for the head it merges, which shows such a document with no sentence from the author. A pull request merged through this capability's other merge commands keeps the list as it was last written (point 5).

**Why a sentence the list does not show is warned of, not refused.** The reviewer checks a sentence only beside an `updated` document, so any other sentence stays in the description unchecked. The warning names it, so the author can remove it. The list and its answers stand without it, so nothing is refused. A run authorised up front holds on it all the same: the person authorised before the warning was shown, and the squash commit would carry the sentence unchecked.

**Why a change with answers merges under the same authorisation as any other.** The reviewer checks the answers against the change, with the diff beside them. The person reading them would redo that check without its context, and holding the merge for their acceptance would keep every change that wrote an answer waiting until they are back (COR-050 point 3). What the person needs from the answers is what changed and what is left out of date. So the landing command tells them that, and asks nothing it would not ask of any other change.

**Why a `[person]` finding holds a run authorised up front.** Only a person can settle it, and the person who authorises the merge is the one placed to (DEC-028). So the landing command prints it whole with the answers, before it stops ready or asks. An authorisation given up front came before the run started. A verdict that reached the pull request after that cannot have been shown, so the run stops ready, and the person is shown the finding and asked again. The test is what the run found when it started, never a comparison of clocks, and a read that misses a verdict counts it as new, so it fails toward a stop. The run need not name its head for this hold. This hold turns on when a verdict arrived and whether it stands for the head the run merges. A move of the head that sends the run back to review brings a new verdict, which holds the run if it carries a `[person]` finding.

**Why the findings' hold needs a verdict for the head the run merges.** A `[person]` finding judges a passage at the head its verdict reviewed. At another head the passage may have changed, so the person would judge words that do not merge. The freshness rule keeps a verdict standing only while the author's changes since leave what its reviewer checks untouched, so the passages it judged are the ones that merge, save the case point 5 names. Freshness fails closed for the gate, since a stale approval does not count. Applied to findings, stale must not mean dropped, since a finding dropped is never shown. So a stale verdict's findings are shown, and the verdict holds a run authorised up front. A run that asks at a terminal shows the finding marked stale before it asks, so the person judges it knowing it may be out of date. An authorisation given up front may have come before that showing, and the command cannot tell (point 5), so the hold waits for a verdict that stands. Where the landing command's review step re-runs the reviewer, a required local reviewer in agent review mode, the hold reads the verdict that run posted. For a reviewer it does not re-run, a remote one or any in human review mode, the run stops until that reviewer posts a verdict that stands for the head. The hold reads only what the merge gate would select, the marked verdict of a reviewer the pull request requires. So a comment with no verdict marker, or one from a reviewer the pull request does not require, neither holds a run nor reaches the person as a finding. A local verdict names its reviewer in its own first line, so the hold trusts that name as the gate does (DEC-028).

**Why an authorisation covers a later head whose only changes are answers.** Pull requests whose answers cover the same documents land one after another. A merge of the base then has the next one answer those documents again, which moves its head (DEC-064, "Why the base is not merged before every landing"). Asking the person again then asks about nothing they judge.
- **Only the answer files.** The answer files a change adds hold the answers the change check asks of it, and nothing else. A reviewer checks them (COR-050 points 3 and 16). The authorisation gates the change, and the change's answers are information, not a gate (COR-050 point 3). A change anywhere else alters what the person authorised, so it needs their authorisation again.
- **The answer file is the unit.** A change within an answer file the change adds lies inside it, and one removed whole lies outside.
  - **Dropping one answer within a unit is part of answering.** A revalidation replaces each deferral it read and does not re-state, and an entry for a target that leaves the link's field answers nothing (COR-062 point 5). The change check asks again for what a dropped answer leaves (COR-050 point 12).
  - **Removing the unit is not.** It takes away where the answers are written, so it stops the run, erring as a gate on an authorisation should.
- **Only with nothing for the person.** A `[person]` finding needs the person. An answer the change check did not ask for needs the person, or the delegate they named. The run cannot tell who decided such an answer, or whether the person was shown it before the authorisation, so either holds a run at a covered later head.
- **The backbone's answer.** The answer files' form and folder are the backbone's (COR-062 points 1 and 2). A component reads the answers through the backbone's machine-readable output (COR-050 Implications). Telling a change in them from any other needs their form. So the backbone walks the branch's line itself. The freshness rule's ruled-artefact floor walks the line here instead, and asks the backbone a stretch at a time (DEC-028).

**Why the friction settings are listed.** The settings decide what the change check asks. A change that empties the places, or excludes an artefact's files, makes the check ask nothing of it, and the list then shows no answer where one was owed. Listing the settings the change alters, and stopping the landing when the base changed them since the head left it, tells the person what the change decided about what is asked, not only what it answered. The mode decides whether the check fails, not what it asks: the head's mode governs the change's own check, but friction it leaves unanswered is still found and reported, and stays as debt (COR-050 points 9 and 12), while a change to the places or the exclusions removes the question itself. So a change to the mode adds nothing to the list.

**Why, for the list, only a base that changed the list's files or the friction settings stops the landing.** The change check reports an outdated base and fails nothing on it (COR-050 point 12). What the landing command adds is the list's words, and those can differ from what merges only where the base's commits since the head left it changed a file they are on: the merge then combines two versions of words the list shows one of. The list's words, a kept deferral's among them, sit in the files the change check names for its answers (DEC-064 point 1). An answer file the change adds changes on the base only where a parent's file landed in another form than the head holds, as on a stacked pull request, since a change answers only by adding (COR-062 point 3). An artefact's own file, for an answer in its block or a target revisited by changing it, changes wherever the base changed that artefact. A base that changed the friction settings since the head left it changes what the merged check would ask, so it stops the landing too. Any other outdated base merges the list's words as they are shown.

**Why answers made apart are printed, and stop nothing.** A merge can leave two revalidations of one document made apart. It then lands a combined state nobody judged, until the next revalidation there reads both (COR-062 point 7). The person who authorises the merge learns of it from the printout, as they learn of a document left out of date. Stopping on it would send each change that revalidated a document the merge also revalidated back for one more merge round. The landing command derives it against the base's tip, not where the head left the base. The tip is what the merge combines with the head.

**Why the landing checks the merge as it would land.** A change check that passed compared the change with the base as it stood when the check ran. What merges is the change with the base as it stands at the merge. Two changes that each answer what they change can leave a document stale together, when one adds an anchor and the other changes what the anchor stands on. Only a check of the two together finds that, and the last moment before the merge is the one the landing command holds.

**Why the change check, judged as a pull request's checks judge it.** It is the check the pull request already passed on the host's merge of it, so a merge it fails here is one that check would fail if it ran again now. Judged against the head, an answer is held to the answer files its author could read, as on the pull request (COR-062 point 4). A revalidation the base made meanwhile on the same document is then answered apart, which point 3 prints and stops nothing on. The whole-repository check, run at the merge too, would add as much again to the step's time, and report the base's own debt beside the change's.

**Why a check that fails at the merge stops the landing, where an outdated base does not.** This record rejects a stop on any outdated base (Alternatives considered), since on a busy default branch every change would wait for the base to stand still. This stop falls only where the merge would land what the check fails on, such as a document out of date, which someone must answer before or after the merge. The fix is a merge of the base and the answers it asks for. The rule on a later head (point 3) covers that without a new authorisation, unless an answer updates the document itself.

**Why the mode decides.** A project's mode says whether a change may land what the check finds (COR-050 point 12). The step holds a merge to the same mode, so it stops nothing a project lets one change land on its own. In warning mode the person who authorises the merge is shown what the merge would leave, as point 3 shows them what is left out of date.

**Why a reason that reads as a closing reference is refused, not escaped.** The host reads closing references in the description and the squash commit with its own parser, which this capability cannot make skip a section. Such a reason would close an issue at merge, so it is never written: the artefact's words are reworded. A word holding an HTML comment's delimiter is refused for a kindred reason: it could open or close a comment around the section's markers, hiding the list from the page or from the commands that find it.

**Why nothing reads the section as input.** Each reader of the description answers a question the description's author answers — which issues the change closes, which documents it accounts for, whether the template was filled. The section is written by a command from the artefacts' words and the authors' sentences on them; letting it answer those questions would let words written for an artefact meet obligations they were never written for.

### Alternatives considered

- **The list inside `## Doc impact`.** Rejected. That section is read for the mapping's override and for closing references, so the artefacts' words would become input there.
- **The `[person]` findings inside the list.** Rejected. The list is the change check's own, and no word of it but the authors' sentences is composed by an agent (point 1). A finding is a reviewer's words, so it stays in its verdict and is printed beside the list.
- **Printing a stale verdict's findings without holding on them.** Rejected for a run authorised up front. That authorisation may predate the stale mark, so the person would authorise, unknowing, on a passage judged at a head that does not merge.
- **A pull-request comment.** Rejected. The description is the one place the person reads before authorising and the one the squash commit carries; a comment is a second place, and a later comment does not replace an earlier one.
- **Merging on an authorisation given up front only when the list for the head was already in the description.** Rejected. It makes the authorisation the person's acceptance of every answer, which COR-050 point 3 leaves to the reviewer. Every change that wrote an answer would wait for a second authorisation.
- **A stamp trusted without deriving, for the list the landing command writes.** Rejected. A marker naming the head a list is for, trusted as written, accepts a list edited by hand or left from an earlier head; deriving again and comparing does not. The command that makes the pull request ready trusts the marker's head only to decide whether to derive, and the reviewer backs its refusal.
- **Spilling an over-long list elsewhere.** Rejected. The person would authorise the merge from a description that does not hold what they are told. A list the description cannot hold stops the landing, and the description's own text is shortened, the change split or the anchor narrowed.
- **An authorisation for one head only.** Rejected. Approved pull requests whose answers cover the same documents would each wait for a new authorisation after every merge round, for nothing but re-resolved answers.
- **Each answer as a unit.** Rejected. Writing a change's answers again drops each deferral or revisit entry it no longer owes. Every such round would then stop for an authorisation the person already gave. The file as the unit has a cost of its own: an answer file the change removes whole stops the run.
- **Stopping on answers made apart.** Rejected. Each merge would stop every open change that revalidated a document the merge also revalidated, until it took one more merge round.
- **Covering any later head whose verdicts stand.** Rejected. A verdict stands across a change outside its reviewer's remit, so the person would authorise a change nobody showed them.
- **Stopping on any outdated base where the change wrote answers.** Rejected. The stop falls between the landing command's ready stop and the person's authorisation, so on a busy default branch every such change would wait for it to stand still, each wait asking for a new head, new checks and a new review — while only a base that changed a file the list's words are on can land words the list does not show.
- **A merge queue alone.** Rejected. A queue that runs the checks on each merge it builds catches the same, with a run of the host's checks for every landing, and only where a queue is set up. The check of the merge reads the repository alone, needs no run of the host's checks, and stands beside a queue.
- **The whole-repository check, or the documentation check, at the merge.** Rejected. For stale documents it finds what the change check finds there, save the cases where the two checks part, at as much again of the step's time. It would also report the base's own debt, which a second run at the tip would be needed to tell apart from the change's.
- **A note under the sentences heading, to pass a refusal an out-of-date list makes wrong.** Rejected. The list the description carries would show the note as the author's sentence, on a change the document no longer has.
- **`--force` as the remedy for an out-of-date list.** Rejected. It is the operator's override of a `hard-reject` (DEC-046 point 2), not a step of a fix round. It would also pass every finding on the description at once.
- **The command that makes the pull request ready writing the list it derived.** Rejected. The list would go out of date again on the next fix round, which the landing command meets by writing it for the head it merges. Writing it would also bring the landing command's refusals over an artefact's words into the move to review.
- **Writing the list again in the command that edits the description.** Rejected. That command writes the description's own words and derives nothing (point 2). Deriving there would run the change check on every edit, and an edit of the description's text could fail over an artefact's words.
- **Refusing a missing sentence only where the list is for the pull request's head.** Rejected. Every fix round moves the head, so a document still `updated` with no sentence would pass, and spend the review round the refusal saves.

## Implications

- The command that opens the pull request with its list derives the list at the pushed head and never refuses to open over it: a list it cannot derive, or cannot write, is left out with a warning, and the landing command writes it or refuses. The edit command derives nothing.
- The command that makes the pull request ready and requests reviewers reads the list in the description, and refuses where it marks a document `updated` with no sentence. Where the list is for another head, it derives the list at the pull request's head first, fetching that head where the clone lacks it, and warns of a sentence that list does not show. Under `--force`, a list it cannot derive gives way to the description's. The command that edits the description warns of a missing sentence. The command that opens the pull request with its list, and the landing command, warn of a sentence their list does not show, and the landing command holds a run authorised up front on it. The capability README documents each.
- The landing command gains a step between the review and the merge that derives the list, prints it and writes it into the description. The capability README documents the section and the step.
- The landing command reads the `[person]` findings of each reviewer's latest verdict as the merge gate would select it, prints each whole with the answers, and holds on them. The capability README documents the hold.
- The pull request's head may not be the one authorised. The landing command then asks the backbone whether the changes since lie in the answer files the change adds. It lands the later head only when the backbone answers that they do, and the capability README documents it.
- The landing command asks the backbone, against the base's tip, which revalidations the merge would leave answered apart, and prints them with the list. The capability README documents it.
- The landing command gains a step after the list's that builds the merge of the head with the base's tip, runs the change check on it, and refuses where it fails. The capability README documents the step.
- The commands that write the list take each `updated` document's sentence from the change's author. The reviewer that checks the answers, where the project chooses one, is one of the reviewers the merge waits for.
- Every reader of the description strips the section before it reads.
- The opt-in that fills an unwritten `## Doc impact` from the friction answers writes one line pointing at the section, naming no path and no reason, so it can meet no mapping obligation.
- [project-management:DEC-053-doc-check-slot] point 2 names this section as where the answers are listed. A line of it meets no obligation there.
