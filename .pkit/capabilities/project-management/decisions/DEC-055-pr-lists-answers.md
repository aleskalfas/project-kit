## Context

An agent building a change may give the answers its own change owes — the revalidations and deferrals the change check asks of it — without asking anyone first. A reviewer other than that agent checks them, and the pull request says what changed in each `updated` document. The person who authorises the merge is told what changed and what is left out of date, as information, not a gate: a change with answers merges under the same authorisation as any other (COR-050 point 3). The change check gives the list of answers in its machine-readable output (COR-050 point 12).

This capability is where a pull request is reviewed and its merge authorised: the reviewers' verdicts gate the merge (DEC-028), the person reads the pull request's description, and the landing command stops ready — naming the head and the command that merges it — for them to authorise. If nothing puts the list there, the reviewer and the person rest on an agent copying it by hand.

## Decision

**A pull request's description carries the change check's list of the answers its change wrote, written by this capability. No word of it is composed by an agent, apart from the author's sentence on what changed in each updated document, which the list gives beside that document. The command that lands the pull request writes the list for the head it merges and prints it before it stops ready, asks or merges. A change with answers merges under the same authorisation as any other.**

1. **The list.** This capability writes the answers a change wrote into the pull request's description, in a section of its own, `## Documentation this change affects`, delimited so a command can find, compare and replace it whole. The section speaks to a reader who does not know this methodology: its heading, an opening sentence and each entry say in plain words what the change decided about each document; the change check's own terms stay in the machine-readable list. The list is the change check's own list of the answers the change wrote, derived at the pull request's head against its base, as the change check compares any change (COR-050 point 6). Each entry gives the artefact, the answer, its anchor where it has one, and the justification or reason word for word, with every flag the change check puts on it, and each deferral a revalidation kept; the list counts the files the check could not read. An entry for an `updated` document also gives the sentence the change's author wrote on what changed in it. That sentence is the one part of the list the change check does not supply, and it is shown as the author's. Where the change alters the friction settings that decide what the check asks — the places it reads or the files it leaves out (COR-050 points 1, 7 and 14) — the list also gives each such change as it was and as it is. The section is replaced whole whenever it is written. Apart from the authors' sentences, no word of it is composed by an agent, and a section under that heading that this capability did not write is removed. Where the change wrote no answers and alters no such setting, the landing command removes any list an earlier head left.
2. **Who writes it.** The command that opens the pull request writes it; every edit of the description through this capability carries it unchanged; the landing command derives it again before the merge. Every write carries each `updated` document's sentence from its author.
3. **The review and the authorisation.** The review the merge waits for (DEC-027, DEC-028) includes a reviewer the project chooses, other than the agent that wrote the change's answers. That reviewer checks every `unchanged` and `deferred` reason among the answers the change owes against the change, and each `updated` document's sentence against the diff, and it blocks the merge when a reason does not hold or a deferral names no follow-up that exists (COR-050 point 3). The list in the description, and the landing command's printout of it before it stops ready, asks or merges, tell the person who authorises the merge what changed in each updated document, and which documents are left out of date until which follow-up. This is information, not a gate: a change with answers merges under the same authorisation as any other. The authorisation is the person's, to merge the pull request (Review → Done), not the review approval an agent may give (DEC-028). An entry flagged as not asked for, and a reason for having no anchors, needed the person's acceptance before it was written; authorising the merge does not give it. The landing command merges nothing and writes nothing when the list cannot be derived, when a file the change touches cannot be read for answers, when a word of the list reads as a closing reference or holds an HTML comment's delimiter, when the description cannot hold the list, or — where the change wrote answers or alters those settings — when the base's commits since the head left it changed a file that carries a listed answer or a kept deferral, or changed the settings the list shows, since that merge could land words the list does not show; a base that moved on otherwise stops nothing, as the change check itself only reports it (COR-050 point 12). These are firm stops with no override (DEC-014, DEC-046). Merges through other commands, or outside this capability, are point 5's.
4. **Never input.** No reader of the description treats the section as input — none that reads closing references or the `## Doc impact` section (DEC-013, DEC-015), or checks the template was filled (DEC-031). Nothing in the section closes an issue. The squash commit carries it as it carries the rest of the description.
5. **What this does not verify.** That a person read the list, or that the reviewer checked every answer on it: the reviewer's verdict is the review's (DEC-028), and the person's authorisation is the same as for any other change. A review bypassed or overridden (DEC-028, DEC-050), or a project that chooses no such reviewer, leaves the answers checked by their writer alone, which falls short of COR-050 point 3. A verdict covers the reasons at the head it reviewed: a reviewer whose approval stays fresh across a change to a file that carries a listed answer, or a sentence edited in the description after the verdict, leaves what changed since unchecked. The landing command holds that the list in the description is the list for the head it merges. A merge through this capability's other merge commands, or outside this capability, takes no such step: after a fix round the description may carry the list of an earlier head, or none. A project that runs no checks on its pull requests lands through those other merge commands, since the landing command waits for checks, so its merges take no such step either.

## Rationale

**Why the description.** It is what the person reads before authorising the merge, and the squash commit carries it (DEC-013), so the answers that landed stay beside the change in the default branch's history.

**Why the capability writes it from the check.** What the reviewer checks must be the check's list, never an account the agent composed, so no answer the change wrote escapes it (COR-050 point 3). The sentences on what changed are the author's because the check cannot supply them: it knows that a document changed, not what the change means. The reviewer checks each against the diff. A section derived from the check's document at the pull request's head, and replaced whole on every write, cannot drift from the artefacts and keeps no entry of an earlier head. A section under the heading that this capability did not write is such an account, so it is removed rather than shown beside the list.

**Why the landing command derives it again.** The head that merges is often not the head the pull request was opened at: a fix round rewrites answers and adds others. Deriving at the head the landing command pinned, and comparing with the description, makes "the list in the description" mean the list for the head that merges.

**Why a change with answers merges under the same authorisation as any other.** The reviewer checks the answers against the change, with the diff beside them. The person reading them would redo that check without its context, and holding the merge for their acceptance would keep every change that wrote an answer waiting until they are back (COR-050 point 3). What the person needs from the answers is what changed and what is left out of date. So the landing command tells them that, and asks nothing it would not ask of any other change.

**Why the friction settings are listed.** The settings decide what the change check asks. A change that empties the places, or excludes an artefact's files, makes the check ask nothing of it, and the list then shows no answer where one was owed. Listing the settings the change alters, and stopping the landing when the base changed them since the head left it, tells the person what the change decided about what is asked, not only what it answered. The mode decides whether the check fails, not what it asks: the head's mode governs the change's own check, but friction it leaves unanswered is still found and reported, and stays as debt (COR-050 points 9 and 12), while a change to the places or the exclusions removes the question itself. So a change to the mode adds nothing to the list.

**Why only a base that changed the list's files or the friction settings stops the landing.** The change check reports an outdated base and fails nothing on it (COR-050 point 12). What the landing command adds is the list's words, and those can differ from what merges only where the base's commits since the head left it changed a file they are on: the merge then combines two versions of words the list shows one of. A base that changed the friction settings since the head left it changes what the merged check would ask, so it stops the landing too. Any other outdated base merges the list's words as they are shown.

**Why a reason that reads as a closing reference is refused, not escaped.** The host reads closing references in the description and the squash commit with its own parser, which this capability cannot make skip a section. Such a reason would close an issue at merge, so it is never written: the artefact's words are reworded. A word holding an HTML comment's delimiter is refused for a kindred reason: it could open or close a comment around the section's markers, hiding the list from the page or from the commands that find it.

**Why nothing reads the section as input.** Each reader of the description answers a question the description's author answers — which issues the change closes, which documents it accounts for, whether the template was filled. The section is written by a command from the artefacts' words and the authors' sentences on them; letting it answer those questions would let words written for an artefact meet obligations they were never written for.

### Alternatives considered

- **The list inside `## Doc impact`.** Rejected. That section is read for the mapping's override and for closing references, so the artefacts' words would become input there.
- **A pull-request comment.** Rejected. The description is the one place the person reads before authorising and the one the squash commit carries; a comment is a second place, and a later comment does not replace an earlier one.
- **Merging on an authorisation given up front only when the list for the head was already in the description.** Rejected. It makes the authorisation the person's acceptance of every answer, which COR-050 point 3 leaves to the reviewer. Every change that wrote an answer would wait for a second authorisation.
- **A stamp trusted without deriving.** Rejected. A marker naming the head a list is for, trusted as written, accepts a list edited by hand or left from an earlier head; deriving again and comparing does not.
- **Spilling an over-long list elsewhere.** Rejected. The person would authorise the merge from a description that does not hold what they are told. A list the description cannot hold stops the landing, and the description's own text is shortened, the change split or the anchor narrowed.
- **Stopping on any outdated base where the change wrote answers.** Rejected. The stop falls between the landing command's ready stop and the person's authorisation, so on a busy default branch every such change would wait for it to stand still, each wait asking for a new head, new checks and a new review — while only a base that changed a file the list's words are on can land words the list does not show.

## Implications

- The command that opens the pull request derives the list at the pushed head and never refuses to open over it: a list it cannot derive, or cannot write, is left out with a warning, and the landing command writes it or refuses. The edit command derives nothing.
- The landing command gains a step between the review and the merge that derives the list, prints it and writes it into the description. The capability README documents the section and the step.
- The commands that write the list take each `updated` document's sentence from the change's author. The reviewer that checks the answers is one of the reviewers the merge waits for, and the project chooses it.
- Every reader of the description strips the section before it reads.
- The opt-in that fills an unwritten `## Doc impact` from the friction answers writes one line pointing at the section, naming no path and no reason, so it can meet no mapping obligation.
- [project-management:DEC-053-doc-check-slot] point 2 names this section as where the answers are listed. A line of it meets no obligation there.
