**In plain terms:** in a project that declares a Projects v2 board, pre-check's board check warns, and fails nothing, where the board does not answer it, as when the service's boards are down or the credential cannot reach the board. Pre-check's gate then stops nothing for that alone: the operations the capability's skill runs go on, and so do migrate and a CI job that gates on pre-check. The skill's first step shows the person pre-check's warnings. Pre-check's machine-readable report gives each check, and each warning, a key of its own that stays, so a caller that must know whether the board answered reads the board check's outcome by its key. Each command that reads the board meets its silence at its own read, as [pkit:ADR-096] has every command do, and filing refuses there before it creates an issue. A configuration that declares a board and gives no value its schema admits as a board number fails, since the check finds that in the project's own files. The costs: a board that does not answer is found at the first command that reads it, not at the skill's first step, and a pass of pre-check does not say whether the board answers. This refines [project-management:DEC-017-prerequisites-bootstrap-migrate-discipline], whose gate stands.

## Context

**Terms.**

- **Pre-check** is the capability's read-only diagnostic. **Its gate** is the refusal that follows wherever its exit says a check failed: at the first step of each operation the capability's skill runs, in migrate, and in a CI job that gates on it (DEC-017).
- **The board check** is the check pre-check makes in a project whose configuration declares a Projects v2 board: that the declared board resolves (DEC-017's list of checks).
- **The board number** is the number by which the configuration names the board. **A stored node id** is the board's node id, where the configuration keeps one beside the number. [pkit:ADR-096] calls it a stored board id.
- **The service** is the host the board lives on. **The workflow's own token** is the credential the service gives a CI workflow's run by default.
- **The configured board** is the board the project's configuration names. **A board that did not answer** is one whose own read failed, named no board or another, or was not whole, or one for which a read that lists only what the credential may see found no sign that the board answered. Both terms are [pkit:ADR-096]'s (its Context, and its points 1 and 2). The board check reads the board itself, so for it the board did not answer where that read failed, named no board or another, or was not whole.

**What DEC-017 decides.** Pre-check exits non-zero on any failure, and zero where every check passed, was skipped or reported a non-blocking warning. The gate refuses on a non-zero exit. It is programmatic: the exit code is its contract, not an agent's reading of the report. A declared board that does not resolve fails the board check, so it refuses every operation through the skill, migrate, and a CI job that gates on pre-check. Migrate refuses wherever pre-check fails, since drift in basic prerequisites breaks the assumptions its plan rests on. Other checks warn and let the operation through, as a missing contributed label does ([project-management:DEC-042-label-contributions] D4).

**What this record rests on.** [pkit:ADR-096] decides two things this record's argument needs:

- **A live read.** The board check reads the board on each run, and never passes on a stored node id.
- **Each command meets the board at its own read.** Every command that reads the board meets a board that did not answer there. A command whose act needs a later write to the board reads the board first, and refuses before it acts ([pkit:ADR-096] point 4). Filing is such a command in every project with a board, since an issue owes its card from filing ([project-management:DEC-019-mandatory-issue-state]).

[pkit:ADR-096] leaves to DEC-017 whether the board check fails or warns where the board does not answer. This record decides that on the two choices above, so a record that changes either of them weighs this one again, and refines or supersedes it where its reasons fall.

**What the gate's stop prevents, once each command reads the board.** [pkit:ADR-096]'s Rationale ("Why the health check reads the board") names two cases that a stop at the first step prevents and each command's own read does not:

- an operation of several commands makes its first command's act before a later command refuses on the board;
- a write to the board that no act requires goes unmade, such as a Status that only mirrors a state labels carry, or a hook's write of a value the board holds. It is reported with its repair.

The stop has a price wherever a board is declared. Whenever the board does not answer, it halts every operation through the skill, operations that only read the board and let its silence through among them, and a CI job that gates on pre-check. It halts migrate too, unless the person runs migrate with its flag that skips pre-check, which skips every other check with the board's. So the costs that decide are the skill's operations and a CI job. By the service's documentation, the workflow's own token reaches no board ([pkit:ADR-096], its Context). So a CI job under that token that gates on pre-check would fail on each run.

**Back-fill gates on the board only where it writes to it.** It refuses on the board where it writes a board field, and a back-fill that writes no board field does not gate on it ([project-management:DEC-037-adoption-ceremony] point 2; [pkit:ADR-031] point 5).

## Decision

**Where the configured board does not answer, pre-check's board check warns and fails nothing. A configuration that declares a board and gives no value its schema admits as a board number fails. The gate keeps DEC-017's contract, and the skill's first step shows pre-check's warnings. A caller reads each check's outcome by a key that stays.**

### 1. The board check warns where the board does not answer

- **A warning, not a failure.** Where the configured board did not answer the board check's read, the check reports a warning. Pre-check's exit is then what its other checks make it. So each operation through the skill, migrate, and a CI job that gates on pre-check go on, unless another check fails.
- **What the warning says:** that the board did not answer, and why, in the service's words, with the way out that cause gives ([pkit:ADR-096] point 6). It also says that each command that reads the board meets that silence at its own read, and that filing then refuses before it creates an issue. So the check says what it could not see, and never reports itself passed, as [pkit:ADR-096] point 4 has a check of the setup do where its severity lets the operation through.
- **The checks that need the board's answer** do not run on a board that did not answer, and each says why.
- **Beside the warning on the board's cards.** Where the board answered, yet none of the repository's recent issues that pre-check reads shows a card on it, pre-check warns as [pkit:ADR-096] point 4 has it. The two warnings stand apart, each under a key of its own (point 4): one where the board did not answer, one where it answered and the credential's reach to its cards could not be shown.

### 2. A configuration with no board number its schema admits fails

Where the configuration declares a board and gives no value that the schema of the capability's configuration admits as a board number, the board check fails, whatever else the configuration stores. That covers a number left out, null, empty or zero, and a value of another kind, such as a node id given in the number's place. The check finds the fault in the project's own files, with no call to the service, so no outage, credential or owner bears on it.

A value the schema admits is read through the board, and one the board does not answer to warns, whatever is wrong with it. The check cannot tell a wrong number, or a board under another owner, from a board that does not answer the credential, since each comes back as a board that did not answer ([pkit:ADR-096] point 1).

### 3. The gate keeps its contract, and the skill shows the warnings

- **The exit code stays the gate's contract.** The warning is pre-check's own outcome, computed by the script and given in its report. The gate reads only the exit code, as DEC-017 has it, and nothing reads the report to decide whether an operation goes on.
- **The skill shows the warnings.** Where no check fails, the skill's first step shows the person each warning pre-check reports, and the operation goes on. The first step decides nothing from the report.

### 4. A caller reads each check's outcome by a key that stays

- **A key for each check.** Pre-check's machine-readable report gives each check a key of its own, the same whatever the check's outcome or the wording of its report. A warning pre-check gives beside a check, the warning on the board's cards among them (point 1), is a check of its own in the report, with a key of its own. So a caller tells a board that did not answer from one that answered where the credential's reach to its cards could not be shown.
- **Read by its key.** A caller that reads one check's outcome, such as a CI job or a scheduled run that must know whether the board answered, reads it by the check's key. The key and the outcome under it are that caller's contract, beside the exit code, which stays the gate's (point 3).
- **What the contract holds.** The outcome under a key is one of DEC-017's four, a check passed, skipped, warned or failed, and the value that names it is part of the contract. A check that does not run appears under its key as skipped, such as the board check in a project that declares no board, or a check that needs the board's answer where the board did not answer. A key added breaks no caller. A key that goes, a key that comes to name a check that asks something else, and a change to the value that names an outcome each break a caller, so each is a breaking change of the capability. A key is never reused: a key that went names no later check.

## Rationale

**Why warn.** DEC-017's gate exists so that an operation does not fail halfway through a mutation with an opaque message. Under [pkit:ADR-096], each command serves that purpose for the board at its own read:

- A command whose act needs a later write to the board refuses before it acts where the board does not answer, with the cause and the way out. So filing creates no issue then.
- A read a command only reports says the board did not answer. It never reports a check passed, or an issue off the board, on such a board.

What the gate's stop adds is the two cases in the Context. For them, the stop would turn an outage of the service's boards, or a credential the board does not answer, into a stop of every operation through the skill and of a CI job that gates on pre-check. Operations that touch no board would stop too, such as a comment posted on an issue. So would operations that read the board and let its silence through, such as validating an issue, whose finding on membership then takes the drift severity ([pkit:ADR-096] point 5).

**What a pass of the gate could promise.** The gate never stood before every command. A command run outside the skill meets no pre-check, migrate apart: the check each command makes before it runs asks only whether the project was set up, and reads no board. The first step checks at one moment, so an outage that starts after it meets each command at its own read. So a pass of the board check never said that the board would answer the commands after it, and [pkit:ADR-096] has filing refuse before it acts, through the skill or not. Warning takes from the gate a promise no command could rest on.

**Why this keeps to the board read-path contract.** [pkit:ADR-053] keeps a board outage from becoming a filing outage on code paths that never touch a board. It also rejects raising on every failed read of the board, since a project would then gain a failure from a feature it does not use. A failing board check brings that harm back through another layer: an outage of the boards would stop an operation that only posts a comment. Warning keeps each operation that touches no board out of the board's reach, and each command that touches the board meets it at its own read. [pkit:ADR-053] also says that "a warning that passes is the same failure with better prose". It says so of a gate's verdict on a value the gate could not read, which lets an issue through on a check that computed nothing. Here no verdict rests on the board check's pass: each read that rests on the board's answer stops at that read ([pkit:ADR-096] point 4), and the warning never reports the check passed.

**A check that warns where the command refuses on its own.** DEC-042 D4 has pre-check warn on a missing contributed label, because the command that needs the label refuses on its own where it is missing. The board check warns on the board's silence for the same reason. A gap in the environment that only some operations need is best found at the operation that needs it, as back-fill finds the board only where it writes a board field ([pkit:ADR-031] point 5).

**Why the checks that need the board's answer skip.** A skip is one of the outcomes DEC-017 lets pass, a check legitimately skipped. Run on a board that did not answer, such a check has nothing to judge. Failing it would bring back, through another check, the stop this record lifts.

**Why a configuration with no board number its schema admits fails.** The line between failing and warning is what the check can find with no call to the service. A board number missing, or of a kind the schema does not admit, lies in the project's own files. The check reads it there, its outcome is certain, and the fix is in those files. It is a fault of the kind DEC-017's check of the configuration fails on: a field the configuration needs and does not give. Each case the board must answer for comes back as a board that did not answer: a wrong number, a board under another owner, a stored node id naming another board, the workflow's own token or an outage. The check cannot tell a lasting one of those from one that passes, so each warns. Whether filing refuses on such a configuration is a question of its own ([project-kit#3244](https://github.com/aleskalfas/project-kit/issues/3244)), which this record does not decide, and the check fails on it either way. Failing costs only a project whose configuration is incomplete.

**Why each check's outcome has a key.** The exit code says only whether any check failed. A caller that must tell the board's warning from the rest reads the report, such as a CI job or a scheduled run that must see a board that did not answer. Each check's label in the report is prose. It may change with the check's outcome and with its wording, so a caller reading by it would match prose, and break on an edit no one counts as a change of contract. A key that stays tells such a caller, for the one check it needs, what a failing exit tells it of the whole run, and leaves the gate's contract as DEC-017 has it. The two warnings on the board take a key each: under one key, a caller would meet a warning either way, and could not tell a board that did not answer from a finding on the credential's reach, which [pkit:ADR-074] point 5 keeps apart. The contract holds what a caller relies on, as a document of keys does for its readers ([pkit:ADR-081] point 8). A key added asks nothing of a caller, a key that goes or comes to mean something else breaks one, and a key reused would have a caller read a later check as the one it knew.

**Why the gate keeps its contract, and the skill shows the warnings.** DEC-017 rules out a gate an agent interprets. The warning is the script's own outcome, and the gate reads only the exit code. Without point 3, the skill's first step shows the report only where pre-check fails, so the board's warning would reach nobody there. Showing every warning tells the person, at the first step, what the first command that reads the board will meet. It decides nothing, so no interpretation comes back. Splitting the gate by operation would need an agent to judge which operations need the board, or a list of them that the gate keeps apart from the commands it gates (Alternatives).

### Alternatives considered

- **Keep the failure,** with [pkit:ADR-096]'s live read. Not taken: an outage, or a credential the board does not answer, would stop every operation through the skill and a CI job under the workflow's own token on each run, and migrate unless it ran with no pre-check at all. It would prevent only the two cases in the Context that each command's own read does not.
- **Fail where the board answers that it cannot be seen, and warn only on an error or no answer at all.** Not taken: [pkit:ADR-096] counts an error and an answer naming no board alike as a board that did not answer, and the check has nothing else to tell a wrong number from a credential the board does not answer. The lasting case, a credential the board does not answer, such as the workflow's own token, is the one this record warns on.
- **Narrow the stop to the operations that read or write the board.** Not taken, for each of the gate's three callers:
  - **At the skill's first step,** pre-check runs before the skill dispatches, and is told no operation. So it would need a list of the operations that touch the board, kept apart from the commands that read it, and wrong once one of them changes. Each such command meets the board at its own read, and before its act where it needs a later write. Narrowing would also keep the stop for an operation of several commands that touch the board, the first of the two cases.
  - **Migrate** runs pre-check itself, and could gate on a subset of its outcomes, as back-fill does. Narrowing would reach migrate alone, and leave the stop at the first step and in a CI job. The warning serves migrate as well, since no kind of migration it runs reads the board.
  - **A CI job** is told no operation either. It is the project's own, and can narrow its stop itself, by reading each check's outcome by its key (point 4).
- **A switch that keeps the failure for a caller that asks,** such as a CI job. Not taken now: a caller that needs to know whether the board answered reads the board check's outcome by its key (point 4). Under the workflow's own token, such a switch would fail each run. It can be added once a caller needs the exit code itself ([COR-007](../../../decisions/core/COR-007-pattern-extraction.md)).
- **A reversed switch:** the board check fails by default, and the capability's own gates, the skill's first step and migrate, pass a flag that makes the board's silence a warning. The case: plain pre-check keeps what its exit means for a health run a project wires up. Not taken: a CI job under the workflow's own token that gates on plain pre-check passes where the configuration stores a node id, as long as the check makes no live read. Once the live read is built, that job would fail on each run, unless each project changed it. No release may bring that on a project (Implications, "Order").
- **Drop the board check.** Not taken: its warning tells the person at the first step what the first command that reads the board will meet, the checks that need the board's answer run behind it, and [pkit:ADR-096] sets its read and a warning of its own.
- **Leave the skill's first step as it is.** Not taken: it shows the report only where pre-check fails, so the board's warning would reach nobody at the first step.
- **Show at the first step only the warnings the script marks for it,** the board's among them. The case: a warning that persists, such as a stale bootstrap stamp or one on a choice the project made, would not show before every operation. The mark would be the script's, so no agent reads the report to choose. Not taken now: it needs a rule for which warnings the first step shows, and each check's record to apply it, against a noise no one has yet met at the first step. It can be added once the warnings shown are seen to drown the board's (COR-007). An agent choosing the warnings to show, by reading the report, is not taken: what the person is shown would rest on that reading, not on the script.
- **Overturn DEC-017 in part, with a *Partially superseded by* line.** The case: DEC-017's Rationale gave a board configuration mismatch among the drift that breaks the assumptions of migrate's plan. Under this record, a wrong board number warns and migrate goes on, so that reason, read as one of DEC-017's choices, would be overturned. Not taken: the reason is a statement of fact, and a false one. Migrate's plan reads labels and the issues that carry them, and reads neither the board nor the default branch, as DEC-017's own label-only primitives have it. So both drop out of that sentence's examples as a fact corrected (Implications), and the choice the sentence explains stands: migrate refuses wherever pre-check fails. DEC-017's other choices stand too, a programmatic gate that refuses on a failed prerequisite, with its exit code as the contract. DEC-017 already lets a check warn and pass, and never weighed failing against warning where the board does not answer. This record narrows which of the board check's outcomes fail, and completes what the first step does where none fails and how a caller reads one check's outcome, so it refines DEC-017.
- **Edit DEC-017 in place, with no record of its own.** Not taken: the change is a choice among these alternatives, with its own costs and reasons, resting on [pkit:ADR-096]. A change to what an accepted record decides takes a record of its own ([COR-065](../../../decisions/core/COR-065-records-and-projection.md) point 3).

## Implications

- **Costs,** for the person who accepts this record to weigh:
  - **A pass does not say whether the board answers.** Where a board is declared, a pass of DEC-017's gate says that the configuration gives a board number its schema admits, and leaves whether the board answers to each command's own read. Pre-check's exit code does not tell the skill, migrate or a CI job whether the board answered. A caller that needs to know reads the board check's outcome by its key (point 4).
  - **Found later.** A board that does not answer is found at the first command that reads it, not at the skill's first step.
