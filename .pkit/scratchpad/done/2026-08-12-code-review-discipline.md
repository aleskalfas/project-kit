# Code review discipline — should pkit ship one, and in what shape?

Exploratory note (COR-012). Retires by producing an EPIC + decision(s) (a code-review discipline shipped from the `software-engineering` capability), or being dropped. It frames the question and the candidate shape; it does **not** pre-decide.

## The question

Today pkit's merge gate can pass with **zero code review**, and the vocabulary hides it. Should pkit ship a code-review discipline that plugs into the merge gate — and if so, what is its shape (one reviewer? a panel? how do verdicts aggregate? does the same knowledge inform code *generation*)?

## What prompted this — bug report #715 (`mockingbird`)

Filed against pkit itself by a parallel adopter. The core defect:

- In `agent` mode (the [project-management:DEC-027] default), the merge gate is satisfied by a registered reviewer agent's `APPROVED` verdict ([project-management:DEC-028]). The only registerable reviewer shipped is the pm capability's `reviewer`, which is **conventions-only** by its own body ("you do not review code correctness"). So `review-pr` → `reviewer` → `APPROVED` unlocks the merge having formed **no opinion about the code**.
- Nothing else in the shipped stack fills the gap: `software-engineer` is a *producer* (no verdicts); `critic` reviews *unbaked* designs and has no Bash to run tests; `architect` is advisory/non-gating; `convention-compliance-reviewer` is conventions again.
- **The socket exists but is empty.** [project-management:DEC-032]'s reviewer-contribution mechanism (a capability declares `review-contributions.yaml`; pm collects them from manifest-registered capabilities) works — but no capability ships a code reviewer to register.
- **The naming is a trap.** `review-pr`, `reviewer`, `APPROVED` all imply the code was assessed; each is process-only. A green gate reads as "reviewed".
- **Real evidence:** on a real PR (`mb upgrade`), two genuine security defects passed the gate — an auth token passed as a subprocess **argv** (readable in the process list) and **`shell=True`** interpolating a remote-fetched release tag (command injection). Conventions said `APPROVED` before and after the fixes.

Report link: issue #715.

## What is already known (records + mechanisms in play)

- **[project-management:DEC-028]** — an agent may be an approver; its `APPROVED` verdict (with the `<!-- pkit-verdict -->` marker) is what the merge gate consumes. New code reviewers would emit this same verdict grammar.
- **[project-management:DEC-032]** (accepted) — the reviewer-contribution socket, and it settles more than I first credited: the required-reviewer set **resolves per PR** (baseline ∪ every capability-contributed reviewer whose predicate matches), is **AND-composed** (*all-must-approve* — every required reviewer needs a fresh `APPROVED`), and it **lifts DEC-028's singleton cap** so N≥2 local reviewers are supported. Install-driven activation; recomputed at gate time. There is already a worked second reviewer — `ux-ui-design`'s `design-reviewer`, contributed for `workstream:design`. **Correction to an earlier draft of this note:** the match predicate keys on **classification axes (workstream)**, *not on diff content* — so "run the security reviewer when the diff touches `subprocess`" is an *extension* beyond DEC-032, not something it already does.
- **[project-management:DEC-028]** (accepted) — an agent's `APPROVED` satisfies the gate; **pinned all-must-approve** for the multi-agent case (DEC-032 realises it). So the aggregation policy for N verdicts is **already decided: binary per-reviewer `APPROVED`, AND-composed.**
- **[project-management:DEC-027]** — review mode (`agent` default vs `human`); `review:human` label forces a person.
- **[project-management:DEC-015]** — code→doc mapping / doc-update obligations (the hook a documentation reviewer would build on).
- The `software-engineering` capability ships `software-engineer` (producer) and reads the overlay-resolved `<project-conventions>` corpus first — the mechanism by which specialist knowledge could also inform *generation*.
- The existing reviewer stack uses a `-reviewer` suffix (`convention-compliance-reviewer`, `methodology-reviewer`), read-only, verdict-posting via the governed path.
- The harness ships a built-in `/code-review` **skill** — **not pkit**. **Naming call (maintainer):** the generalist agent is named **`code-reviewer`** anyway. Rationale: it is a *skill* (`code-review`) vs an *agent* (`code-reviewer`) — different namespaces, different strings — so this is *soft confusability*, not a hard collision; DEC-028's own config example already used a `code-review` agent name, so the project has effectively accepted this space; and the self-descriptiveness wins (jargon-free, people can picture it). `code-quality-reviewer` remains the collision-proof fallback if the confusability ever bites.

## Candidate shape (converged in discussion — a lean, not a decision)

A **generalist + four specialists**, coarser than #715's seven, shipped from `software-engineering` and registered via DEC-032:

- **`code-reviewer`** (generalist) — the "reviews it all itself" agent: correctness/logic at its core, plus API-surface-stability (design half) and general code quality. Runs broadly. It is the **basic-review** agent — an adopter can run it *alone* for a self-contained review, or add specialists below for depth (**complex review**). Named `code-reviewer` (not `correctness-reviewer`) for self-descriptiveness; see the naming call above.
- **`security-reviewer`** — auth, secrets-in-argv, `shell=True`/injection, crypto, **dependency hygiene** (supply-chain folded in here, not the generalist). Predicate: diffs touching auth/subprocess/network/deps.
- **`testing-reviewer`** — test adequacy: does the suite pin behaviour, or mock so heavily it would pass against broken code? Predicate: diffs touching code without matching tests, or test files.
- **`performance-reviewer`** — hot paths, complexity, allocations. Predicate: diffs touching designated hot paths.
- **`documentation-reviewer`** — docs-match-behaviour, public surface documented. Justified *here specifically* because pkit is doc-heavy and DEC-015's doc-obligation machinery already exists. Predicate: diffs moving public surface or with doc-mapping obligations.

Naming follows the existing `-reviewer` suffix convention (`security-reviewer`, `docs-reviewer` are self-descriptive and collision-free). The generalist `code-reviewer` brushes the harness `/code-review` *skill* in name, but they are different namespaces (agent vs skill) — accepted as soft confusability per the naming call above; `code-quality-reviewer` is the fallback.

**Review complexity is composable** (maintainer framing): `code-reviewer` alone = *basic* review (one generalist covers all ground itself); `code-reviewer` + specialists = *complex* review (specialists add depth in their domains). This maps directly onto DEC-032's install-driven activation — installing more specialist contributions dials the review up; the generalist is the always-present floor.

Folded away from #715's list: **API-surface stability** (the "did you declare it" half is already gated by convention-compliance + surface-change discipline; the design half → generalist); **dependency hygiene** → security.

## Open questions (the load-bearing ones — where "complete" lives)

1. **Aggregation policy.** How do N verdicts fold into one gate outcome? Any-blocking-blocks? Severity-weighted? Quorum? Undefined today because there is only one reviewer — with a panel it becomes the central mechanism. Interacts with DEC-028's single-`APPROVED` model (does the gate now consume a *set* of verdicts?).
2. **Generation-side knowledge sharing.** Should the specialists' knowledge also feed `software-engineer` (via the `<project-conventions>` corpus), so the producer stops generating the defects the panel then pays to catch? Lean: **yes** — one body of specialist knowledge consumed at two points (generation reads it as conventions; review applies it as verdicts), with *verdict authority* staying review-only (an author must not approve its own work — the separation DEC-028's stack exists to enforce).
3. **The honest-vocabulary sub-fix.** Independent of the panel: should a conventions-only pass stop saying `APPROVED`? (#715's fix option 2 — a scoped `CONVENTIONS_OK`, and `done-work` stating which disciplines actually reviewed.) This is cheap and closes the "trap" half even before the panel ships. Possibly its own small decision.
4. **Where the discipline lives.** A code-review discipline shipped as a *coherent unit* (specialists + their DEC-032 contribution rules + aggregation policy + the generation-side conventions) — is that the `software-engineering` capability growing, or a new `code-review` capability that depends on it?
5. **Cost / activation default.** Predicate-scoped activation answers "N reviewers per PR is expensive" — but what's the default when no predicate matches (generalist always? nothing?), and how does this compose with `human` mode?

## Working resolutions (converging — leans, not yet decisions)

- **Q1 — Aggregation: ALREADY DECIDED (in DEC-028 + DEC-032), not open.** ~~Earlier lean: reuse `validation-severity` with per-finding severity and any-hard-reject-blocks.~~ **Retracted** — it conflicts with the accepted model and would reopen two decisions for no reason. The aggregation is settled: each required reviewer emits a **binary `APPROVED`**; the gate is satisfied when **every** reviewer in the per-PR resolved set has a fresh `APPROVED` (**all-must-approve**, AND-composed per DEC-032 D3; OR across the paths a single reviewer is registered on). No per-finding severity, no new voting math. Running 1..N review agents and folding their verdicts is **built**; the socket is just empty of a code reviewer.

  Reframing the whole note around this: the "basic base" the maintainer wants — *run one or multiple review agents, aggregate their output* — is **already the DEC-028/DEC-032 mechanism** (all-must-approve). The genuinely-open work is therefore NOT aggregation. It is:
  - **G-A — Ship a code-review reviewer agent** into the socket (from `software-engineering`). The mechanism has one contributor today (`design-reviewer`); no *code/security* reviewer exists.
  - **G-B — Activation granularity.** DEC-032 activates on **classification (workstream)**, not diff content. Diff-content-scoped activation ("run `security-reviewer` when the diff touches `subprocess`/auth") is an *extension* — the one real mechanism question left. Options: (i) accept classification-only for v1 (a `workstream:security`-ish label, or "code review runs on all code PRs"); (ii) extend DEC-032's predicate to key on diff paths/content.
  - **G-C — Honest vocabulary via *attribution*, not a scoped token (maintainer call).** ~~Earlier idea: replace `APPROVED` with a scoped `CONVENTIONS_OK`.~~ **Rejected** — `APPROVED`/`REJECTED` must stay **universal**, because all-must-approve ANDs *identical* tokens across the panel; a per-agent custom token fractures the grammar the gate folds over. Instead, keep the universal tokens and deliver honesty by **transparently attributing whose perspective approved**: each `APPROVED` carries its agent + scope, and `done-work`'s gate summary **enumerates the approving perspectives and any required-but-missing one** — a conventions-only pass reads `APPROVED by: conventions (no code/security/docs review ran)`, so the *absence* of a code perspective is the honest signal, nothing hidden. Scales for free with the panel (`APPROVED by: conventions, code, security, docs`). The agent *names* are already perspective-descriptive, so this is even cheaper than a token change — it is a `done-work` gate-summary enhancement, not a verdict-grammar change. Cheap, independent, could ship first.
  - **Rules / knowledge base** — a *separate layer above the base*: a surgical, precise knowledge base a specialist agent consults (the `review-rules/*.yaml` sketch). Not part of the basic multi-agent+aggregate mechanism; layered on once a reviewer agent exists. Generation-side sharing (Q2) sits on top of that.

- **First increment (converging, maintainer-steered): a 3-agent panel, classification activation.** Ship `security-reviewer` + `code-reviewer` + `docs-reviewer` together (not one-at-a-time; DEC-032 already supports N). Activation is DEC-032's existing classification predicate — all three run on code-carrying PRs — so diff-content activation (G-B) and the rules layer stay parked. `docs-reviewer` remit (maintainer): documentation **completeness** (new surface documented), **understandability** (clear), and docs-match-behaviour — leaning on DEC-015's code→doc mapping + `check-doc-mapping`. Rationale for shipping 2–3 rather than 5: cost is affordable at three, but the dominant risk is each agent being *good* (a noisy reviewer under all-must-approve just blocks merges), so a few well-made agents beat many mediocre ones; testing/performance follow.

- **On-demand review with a custom reviewer group (maintainer requirement) — nearly free, no gating change.** Beyond the automatic gate-driven required set, the operator can run a **chosen group** of reviewers on a PR on demand. This needs *no* change to aggregation or gating because DEC-032 already gates **only the required set**: an on-demand reviewer that is not in the resolved required set posts an **advisory** verdict (comments/findings that do not gate). Surface: a `review-pr` flag — **`--with <agents>`** (additive: run the resolved required set *plus* the named ones; my lean) and possibly **`--only <agents>`** (spot-check: run just the named — useful during iteration, but does not unlock merge if it skips a required reviewer). **Invariant (falls out for free):** on-demand can neither *bypass* the gate (the classification-required set must still approve) nor *satisfy* it (naming an always-approver does nothing — the gate consumes only the required set). It only ever *adds* scrutiny. Composes with the basic-vs-complex framing: standing config sets the required floor; `--with` dials scrutiny up per-PR without touching config. Cheap to build (reuses the agents + a CLI flag).

- **Activation (increment 1) — RESOLVED (lean) → match on the `type` axis.** DEC-032 matches `workstream` today and there is no "code" workstream, so activate on the **`type`** axis instead — a realization of DEC-032's declared "keys on classification axes" generality (its predicate gains `type` support), not a reopening. Two-rule map: `code-reviewer` + `security-reviewer` → code-carrying types (`feature`/`bug`/`refactor`/`maintenance`/`test`, i.e. not pure `type:docs`); `docs-reviewer` → all types. Inherits DEC-032's named gate-escape (a PR closing an *unclassified* sub-task/Milestone → baseline only). **v1 simplification:** the generalist's remit *overlaps* the specialists when both run (both may flag the same issue) — accepted, harmless under all-must-approve; dynamically shrinking the generalist when specialists are installed is a later refinement.

- **Q4 — Home: RESOLVED (lean) → extend the `software-engineering` capability.** The three reviewers + the `review-contributions.yaml` ship from `software-engineering` (which already ships the `software-engineer` producer), co-locating production and review so they can later share one knowledge base ("one source, two consumers"). A dedicated `code-review` capability is the split-later option if review grows its own weight. So the reviewers are **contributed** (not baseline) per DEC-032 — which means they need an activation **predicate** (see next).

- **Block-threshold lives per-agent, not in the gate (important — this is where the retracted Q1 severity idea actually belongs).** Because aggregation is binary all-must-approve, a subjective lens (docs understandability, code style) must **not** hard-block on opinion or it becomes a merge-halting subjective veto that gets bypassed. Resolution: **each agent's body defines what makes it withhold `APPROVED`** — only its *objective* failures gate (`docs-reviewer`: missing docs for new public surface / doc contradicts code; `security-reviewer`: a real vuln); everything softer is posted as `APPROVED`-with-comments (advisory observations that don't gate). The gate stays binary and unchanged; the "block vs advise" severity distinction moves *into the agent* as its block-threshold. This is a hard authoring discipline for every reviewer body and reinforces "a few well-made agents beats many".

## Output & delivery mechanics (maintainer requirements — brainstorming)

Two requirements about *how the review is rendered and delivered*, orthogonal to the core review architecture above:

- **O1 — Preview to a file before publishing.** The review must be generatable **into a file first**, so the operator can read (and possibly edit) it before it is sent anywhere (probably GitHub). Implies a **draft → review → publish** flow rather than review-and-immediately-post. Open: draft location (git-ignored scratch); read-only preview vs editable-before-publish (editing raises verdict-provenance questions); default (always draft-then-confirm) vs opt-in flag. Interacts with the on-demand `--with` (both are `review-pr` invocation modes).
- **O2 — Native GitHub PR review states.** Deliver the review as a **native GitHub PR Review** carrying a state — `APPROVE` / `REQUEST_CHANGES` / `COMMENT` — not merely a plain issue-style comment. Maps naturally onto the per-agent binary verdict (`APPROVED` → `APPROVE`, `REJECTED`/withheld → `REQUEST_CHANGES`, advisory → `COMMENT`). Open: does each panel agent submit its *own* PR Review (N native reviews per PR), or does the gate submit one aggregated PR Review? Interaction with DEC-028's current verdict mechanism (a marker-comment the gate parses) — do native states *replace* or *complement* the marker-comment the gate consumes? GitHub's own "review required / changes requested" state could even become part of the gate signal.

## What would resolve this

The aggregation policy (1) and the discipline's home (4) are the two that gate an EPIC; the honest-vocabulary sub-fix (3) can likely ship first as a standalone decision. Retires by producing: an EPIC for the code-review discipline, a decision on aggregation (extending or complementing DEC-028/DEC-032), and the shipped specialist agents + their `review-contributions.yaml` — or being dropped if a simpler answer (single generalist reviewer; or "code review stays the harness's job, pkit only makes the vocabulary honest") wins.

## Critic pass (2026-08-19) — the converged increment-1 design has real holes; reshape needed

Adversarial review against DEC-028/DEC-032. Load-bearing findings (reconcile with the architect pass before crystallizing):

- **R1 — Contributed reviewers are local-path-only → autonomous merge breaks for the *whole* code surface.** DEC-032 D2 pins contributed reviewers to the local path (no GitHub identity a capability can ship). A code panel contributed that way means *every* code PR needs a human `review-pr` — DEC-028's autonomous remote path is dead for all code PRs. DEC-032 named this for one design workstream; we'd inherit it for the entire code surface. **Fork we collapsed without weighing:** ship code review as a **baseline** reviewer (DEC-028 allows remote) vs DEC-032-**contributed**. (C2)
- **R2/R3 — the activation predicate *reproduces #715*.** `type`-axis activation falls back to **baseline-only (conventions)** on unclassified / sub-task / no-closing-issue PRs (DEC-032's named escape) *and* `type` is issue-intent, not diff content — so a `type:docs` PR that touches code gets no code review. #715's own repro (the `mb upgrade` PR) is plausibly one of these shapes → the design could let the very bug it fixes merge unreviewed. **Fix (C3):** a cheap **diff-touches-code floor** — any diff containing code requires the panel regardless of closing-issue classification — shipped *now*, not deferred with full diff-content predicates (G-B).
- **W4/C1 — ship ONE reviewer first, and it should be `security-reviewer`, not the generalist.** Under all-must-approve, spurious-block probability **compounds** (3 agents × ~5% ≈ 14% of clean PRs blocked vs 5% for one) — contradicting our own "few well-made beats many." And #715's actual defects were **security** (token-in-argv, `shell=True`), which a correctness generalist may miss. The minimal agent that closes #715's reported harm is `security-reviewer`. Ship one, observe false-block rate, add others as *grounded* recurrences (the DEC-028/032 deferral discipline) — shipping 3 manufactures 3 cases from 1 need.
- **G1/W1 — the per-agent block-threshold has no teeth.** "Withhold `APPROVED` only on objective failures" is prose in an agent body — no schema/validator/test, unlike DEC-028/032's algorithmic gates. And the only relief from a spurious block is `--bypass`, which discards the *whole* gate — re-teaching the bypass reflex (#715 from the other side). Binary all-must-approve doesn't *avoid* false-blocks; it relocates the risk into unenforced, non-deterministic self-classification. Either the objective/subjective line gets a testable expression, or the note must admit the false-block defense is unenforced convention.
- **G2/G3 — G-C's honesty is silent where it matters and on the wrong surface.** Attribution can only flag a *required-but-missing* perspective — in the R2/R3 escape cases the panel isn't required, so the summary reads a clean `APPROVED by: conventions` with no warning (silent exactly when code slipped through). And G-C narrates at the `done-work` **CLI**, but #715's surface is the **GitHub PR**, where DEC-028's 2026-08-11 amendment already posts a native green `APPROVED`. (Ties to O2 — native states — already partly live.)
- **W3 — placement.** `security-reviewer` plausibly implies a **security discipline**, not `software-engineering`'s (COR-026); `docs-reviewer` was justified by "pkit is doc-heavy" — a *project-specific* rationale for a *universal capability-shipped* agent (COR-014 tension → route to `methodology-reviewer`). Bundling three reviewers + producer into `software-engineering` also collapses DEC-032's install-granularity (install for codegen help ⇒ forced security+docs gate).
- **W2 — `--with` invariant corrections:** it does *not* "fall out for free" — it rests on the unstated constraint **"`--with` adds runs, never requirements."** And "cannot satisfy the gate" must be narrowed to "an on-demand agent **not in the resolved required set** cannot satisfy the gate" (a `--with`-named agent that *is* required does satisfy its slot, correctly). G4: pin one name — `docs-reviewer` vs `documentation-reviewer` (a deployed-file name).

**Critic confirmed the good calls:** the Q1 retraction (don't reopen aggregation — reuse binary all-must-approve) and G-C's rejection of a scoped token (keep universal `APPROVED`/`REJECTED`). The defects are in *placement, activation soundness, count, and where honesty surfaces* — not in the aggregation or token decisions.

**On the parked O1/O2:** critic confirms O1 (file preview) forces **no** core change (orthogonal pre-publish step). O2 (native states) is **already partly live** via DEC-028's native-review amendment — which is what makes G3 real *now*.

**Likely reshaped increment-1 (pending architect):** one `security-reviewer`, shipped **baseline** (not contributed) so autonomous merge survives, with a **diff-touches-code floor** activation, and G-C honesty pushed to the **GitHub PR surface** (via O2). Home/placement (own security discipline vs software-engineering) awaits the architect.

## Architect pass (2026-08-19) — no escalation; boundary + recording rulings

- **No hard authorization needed.** The panel rides accepted mechanisms *as designed*: DEC-032's contribution socket **literally predicted this case** ("a security capability contributing a required security reviewer" — its universal-applicability flag), and ADR-013 names the reviewer stack as `<project-conventions>`'s "obvious second consumer." Not a new cross-cutting concern.
- **Boundary (Fit-1): the `type`-axis widening is pm-owned, not `software-engineering`'s.** The predicate mechanism lives in pm (`required_reviewers.py`, `review-contributions.{yaml,schema.json}`, today hard-keyed to `workstream`). Land it as a **DEC-032 in-place amendment** (pm surface bump); `software-engineering` ships only the *declaration that uses* the widened axis. Don't put a pm gate-mechanism change inside a consumer capability.
- **Type-axis → amend DEC-032 in place (not a new DEC, not an ADR).** DEC-032 D1 already says "keys on classification axes; `workstream` is the axis specified now" — adding `type` realizes that declared generality. Two mechanism points to settle *in* the amendment: (1) `docs-reviewer → all types` needs a **wildcard/axis-present** predicate (cleaner + forward-safe than enumerating the six type values); (2) the gate-escape (unclassified issue → baseline-only) **now lets *code* review be escaped** — state it (stakes rose).
- **Home (Fit-2): co-location in `software-engineering` is defensible, but the note's stated rationale is partly false.** ADR-013 already decoupled the knowledge base (`<project-conventions>` is adopter-owned, capability-independent) — so "co-locate to share the corpus" does NOT discriminate homes. The *real* argument for co-location is the **deferred generation-side feedback** (bidirectional producer⇄reviewer knowledge — splitting it across capabilities makes a mutual dependency) + COR-007 (one instance) + avoiding a second COR-030 edge. The *cost* is COR-017 install-granularity (install for codegen ⇒ acquire the review gate). **Record this as a `software-engineering` DEC citing COR-026**, stating the decision, the granularity trade, and the **split-later seam** — don't leave it a scratchpad lean.
- **Block-threshold caution (DEC-001-derived):** to keep the deferred generation-side sharing a *non-breaking add* (not an extraction migration across N reviewers), split reviewer knowledge **universal-in-body / project-specific-in-`<project-conventions>`** from the start (same posture as `convention-compliance-reviewer`).
- **G-C fits ADR-042** (read surface annotates; gate stays strict) and **composes with native GitHub review states** — which is how the per-perspective picture reaches the PR UI (answers the critic's G3 "wrong surface": push attribution to the PR via native states).
- **O1 (preview):** fine, under two constraints — **read-only-before-publish** (no edit-then-attribute — breaks DEC-028 attestation) and **must not replace posting** (a preview that never posts starves the gate). **O2 (native states):** already partly live via DEC-028's 2026-08-11 amendment; the panel inherits it; not a core change.
- **Crystallization file-plan:** DEC-032 in-place amendment (pm) · a `software-engineering` DEC (agents + home + block-threshold discipline, citing COR-026) · a pm `done-work` gate-summary enhancement (G-C attribution) · an ADR-013 forward-pointer (architect-owned). No new ADR unless a *structured* review-rules corpus later lands.

**Genuine forks for the maintainer (decide before crystallizing):**
1. **Count: ship ONE `security-reviewer` first, or the 3-agent panel?** Critic argues one (compounding false-blocks under all-must-approve ≈14% clean-PR block rate at 3; #715's actual harm was *security*, which a correctness generalist may miss; recurrence discipline). Architect neutral on count. *Lean: security-first.*

Architect treats contributed as DEC-032's predicted use. Real fork: is a required human `review-pr` on code PRs acceptable (contributed), or must autonomous merge survive (baseline)?

### Fork resolutions (maintainer)

- **Fork 1 → the 3-agent panel** (`code-reviewer` + `security-reviewer` + `docs-reviewer`), with **`code-reviewer` as the headline** (a general "review my PR" is the most-wanted; specialists add depth). Overrides the critic's ship-one lean — so the critic's false-block risk must be *actively mitigated*, not deferred: **(m1)** all three bodies well-made with a crisp objective-vs-advisory block-threshold, split universal-in-body / project-in-`<project-conventions>` (architect discipline; keeps generation-side a non-breaking add); **(m2)** a **per-reviewer bypass** (override one agent's block with audit, not the whole gate) — directly answers the critic's "only relief is total `--bypass`" concern. These two are now increment-1 scope, not deferred.
- **Fork 3 → `software-engineering` home.** Centering the generalist *strengthens* co-location: the generation-side feedback loop is `software-engineer` (producer) ⇄ `code-reviewer` (generalist).
