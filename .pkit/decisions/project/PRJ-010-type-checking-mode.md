## Context

pkit's type checker is configured and has never been enforced. PRJ-003 committed the runtime to strict type checking, and `pyproject.toml` names pyright's strict mode, but the check aggregator that the pre-push hook and CI both run has never gated it, because the tree does not pass it. This record decides how the gate starts. pyright checks the package (`src/`) in strict mode and the tests (`tests/`) in its standard mode, set by directory. The tests must pass outright. The package's existing strict findings go into a committed baseline that a change may lower and never exceed, so no change adds a finding while the package is typed module by module.

Four facts carry the decision. They were measured with the locked pyright, 1.1.409, over the 334 files it checks, the package and the tests together:

- **No mode passes.** Strict reports 37,328 errors, standard 257 and basic 255.
- **The lower modes find nothing strict misses.** Every finding standard or basic reports is also a strict finding, on the same line under the same rule.
- **89 files are already strict-clean**, written to strict with no gate holding them to it.
- **Almost every strict finding is a missing or unknown annotation, and almost all of them are in the tests.** The rules for unannotated parameters, bare generics and values of a type pyright cannot know account for 36,715 of the 37,328 findings; 35,471 are in the tests and 1,857 in the package. Strict reports an unknown type at every use rather than once, and the tests take their fixtures as unannotated parameters by the thousand, so one unannotated fixture yields a finding on each line that touches it.

## Decision

**pyright checks the package in strict mode and the tests in standard mode, and the check aggregator gates both: the tests outright, the package through a ratchet — a committed baseline of the strict findings the package carries, which a change may lower and never exceed.**

1. **The mode is set by directory.** pyright's configuration names the package directory as strict, and standard is the mode of everything else it checks. A new module in the package is strict from its first commit without being listed anywhere. Editors, contributors and the gate read the same configuration.
2. **The tests are gated outright.** Outside the package the gate fails on any finding standard mode reports. There is no baseline there.
3. **The package is gated by a ratchet, counted per file and per rule.** The baseline records how many findings each package file has under each rule. A count above its entry, or a finding under a file or rule with no entry, fails the gate with the findings listed: a new module must be strict-clean, and an existing one may not gain a finding under any rule. A count below its entry passes, and the gate names the entries to lower; the change that made the improvement lowers them, and review holds it to that.
4. **The baseline rises only by a deliberate, reviewed edit.** The gate's own tooling writes lowered counts and never raised ones. A raise is a hand edit to the baseline, made in the change that needs it, with the reason in its pull request. It is legitimate only where findings move or are measured differently rather than added: a module moved or split, a dependency or pyright itself upgraded. A finding a change writes is fixed, never admitted.
5. **A finding is fixed, not silenced.** The gate refuses the blanket suppressions: `# type: ignore`, which pyright applies to every rule on its line; `# pyright: ignore` naming no rule; and a file comment that lowers the file's mode. A suppression that names its rules counts, in the package, as a finding under each rule it names, so it can neither admit a new finding nor pass for a fixed one. In the tests it is allowed only where code is ill-typed on purpose — a test handing a function the wrong type to exercise its runtime check — with the reason on the line. A rule is relaxed only in the configuration, with its reason beside it, as `pyproject.toml`'s ruff section does for lint; inside the package strict mode overrides such a relaxation. The gate counts warnings as well as errors.
6. **The pre-push hook checks the working tree, and CI decides.** The hook runs the aggregator over the working tree, as it does every other line; CI runs it over the pushed commit and is the authority. Because an improvement passes, the hook never demands a baseline edit for work that is not committed. Where the working tree differs from the commit, the two verdicts can differ, as they can for the lint and the tests.
7. **The gate runs on the locked environment, and the baseline belongs to it.** The lock pins the Node runtime pyright runs on beside pyright itself, so syncing the development environment installs everything the type check needs. Findings depend on more than the code — on the pyright version, the packages in the environment pyright reads and the import paths it is told about — so the baseline holds for the locked environment and the configured import paths, as CI builds them. A finding that comes and goes with the host, such as an import the tests make through a path pyright is not told about, is fixed in the configuration and never written into the baseline.
8. **No one owns the package's typing, and its stall is accepted.** The ratchet stops the package getting worse; it does not make it better. The package is typed where changes work on it, and the baseline may stay large for a long time without weakening what the gate guarantees.
9. **A branch need not be up to date with `main` to merge.** Two changes can each pass against their base and fail together — one loosens a function's types, the other adds calls to it. The run on `main` after the merge reports it and the next change fixes it, as for a test that two changes break together.

## Rationale

**Why strict for the package and standard for the tests.** PRJ-003 committed to a typed codebase because the package's surface — manifests, version specifications — is genuinely typed, and that reason holds where code is consumed through its types: the package is what adopters run, and its modules call one another through signatures that the reader and the checker both rely on. The tests are consumed by running them. Every line of a test runs on every pass of the suite, so a type confusion in a test mostly shows as a failing test, and standard mode reports the defects a run can miss: an optional value used unchecked, an attribute read off a union, an argument of the wrong type. What strict adds in the tests is the annotation findings of the fourth fact — 35,471 of them, nearly all an unannotated fixture or helper reported again on each line that uses it. Holding the tests to strict would ask every test to annotate its fixtures and type its helpers, for checking the suite largely does by running.

**Why the mode is set by directory.** pyright's strict list accepts a directory, and a file under it is strict whether or not it existed when the list was written. So the package's new modules are strict by default, and the gate holds them to it, because a file with no baseline entry may have no finding. Strict mode in a listed directory also overrides a rule the configuration relaxes, which closes one way around the ratchet with no check of its own.

**Why the tests are gated outright and only the package through a ratchet.** The tests' remaining work is a cleanup: standard reports 172 findings in 28 test files once pyright is told the import path the tests use for the capability `_lib` packages they import, and they are the findings standard exists for — optional values used unchecked, arguments of the wrong type. Fixed once, they leave the most-edited part of the tree under a plain gate — a test passes when pyright reports nothing, with no baseline to read or update. The package's work is a typing migration: 1,857 strict findings in 47 modules, mostly values whose type pyright cannot know because something upstream of them is unannotated. Gating the package outright would wait for that migration; the ratchet starts the gate before it and holds the line while it happens.

**Why count per file and per rule.** Line numbers move whenever code above them does, and messages name the types and symbols they are about, which change with any rename; either key would make the baseline churn on edits that change no finding. A count per file and rule is stable under both, and fine enough that a fix under one rule cannot pay for a regression under another, or a fix in one file for a regression in the next. What it cannot see is one finding swapped for another of the same rule in the same file — the price of stability, and small. The same granularity is what types the package without an owner: a new call to an untyped helper adds findings under the calling module's entries, so a change that works in a module types what it calls rather than fail the gate.

**Why an improvement passes.** Failing the gate on an improvement until the baseline is lowered would keep the baseline exact, but the pre-push hook checks the working tree, so it would demand a lower baseline whenever uncommitted work fixes a finding — a baseline the commit being pushed does not meet, which CI, checking that commit, then fails. A gate whose two runs contradict each other fails for the wrong reason, and the aggregator exists so that the hook and CI cannot drift. An improvement is never a defect: it passes, and the gate names the entries to lower. The cost is slack — a fix left unrecorded can be spent by a later change. The gate names the slack on every run until a change takes it, and review asks the improving change to take it.

**Why the baseline rises only by hand.** Every raise admits a finding the gate would otherwise refuse, so each one should be a decision someone reads. A tool that never raises it, and a raise that is a hand edit in the change needing it, put every admission into a diff with its reason in front of review. The legitimate causes are the ones where no finding is new: a module moved or split carries its findings to a new path, and an upgrade of pyright or a dependency changes what is reported for unchanged code. For anything else, the fix is in the code.

**Why suppressions count.** A ratchet a comment can step around is not a gate. A blanket suppression hides an unknown number of findings, including ones written after it, so the gate refuses it. A suppression that names its rules says what it hides, and in the package it is counted as what it hides, so writing one changes nothing the gate sees. In the tests, held to zero, counting would ban it outright; but a test that hands a function a wrong type on purpose is correct code a checker cannot know is correct, and a suppression naming the rule, with its reason, is the narrowest way to say so — the exception the lint makes for a line that is long on purpose. Relaxing a rule in the configuration stays possible, as for ruff, because it is made in one place, with its reason, under review; and strict mode keeps such a relaxation away from the package. Warnings count so that lowering a rule from error to warning hides nothing.

**Why the hook checks the working tree.** Checking the commit instead would mean building a second copy of the tree on every push, for one line of an aggregator whose other lines all read the working tree. The lint and the tests already accept that a working tree with uncommitted changes can make the hook disagree with CI; with an improvement passing, the type check adds no way to disagree that they lack.

**Why the Node runtime comes from the lock.** pyright's Python package runs pyright on Node, taking it from the host's path or, failing that, downloading one on first run. A contributor without Node, or a session whose network is confined, would fail the pre-push hook on that first run. pyright's package offers the runtime as an extra (`pyright[nodejs]`) that the lock pins like any dependency, so syncing installs it. The cost is one more platform-specific package in the development environment.

**Why the baseline belongs to an environment rather than to the code alone.** pyright resolves imports against the environment and paths it is given. The tests put capability `_lib` packages on their own import path at run time, and import a build backend the development environment does not install; pyright reports what it cannot resolve, and a different environment reports differently. (Measured, macOS and Linux report the same findings, file for file; the host's platform is not what varies.) Treating such a finding as a defect of the configuration keeps the baseline a record of the code's findings, rather than of the differences between hosts.

**Why the stall is accepted.** Naming an owner for 1,857 findings would assign a migration nobody has scheduled, and an owner who never gets to it is the same stall with a name on it. What the gate guarantees — no new untyped code in the package and nothing new wrong in the tests — does not depend on the baseline falling. It falls where the package is worked on; the rest waits for whoever decides to type it.

**Why branches need not be up to date.** Requiring every branch to be re-checked against the latest `main` before it merges serialises merges behind a full aggregator run each, for every change, against a failure the run on `main` after each merge catches anyway. The ratchet adds no new way for two passing changes to fail together: two changes lowering the same entry conflict in the baseline and are reconciled by hand, and a type change that breaks another change's code is the race every check has.

### Alternatives considered

- **Strict everywhere, behind a ratchet over every file.** Rejected. The gate would start from 37,328 findings in 1,203 file-and-rule entries, 35,471 of them in the tests. A test added to any of 198 test files that uses an unannotated fixture adds findings under that file's entries and fails the gate, so writing a test would first mean typing its file's fixtures — a cost on the most-edited part of the tree, for checking the suite largely does by running.
- **Strict by default, with each file that does not pass marked down to standard** by a comment at its top. Rejected. New files of every kind would be strict with no baseline at all, but 245 files would carry the marker — a file-level suppression, which point 5 refuses — and a marked file can grow untyped code freely as long as it passes standard. In the package, where 47 modules would be marked, strict would hold only the modules written from here on; new test files would carry the cost of the first alternative; and the marked files would need standard's 200 findings fixed before the gate could start.
- **Standard everywhere, gated outright after the same cleanup.** Rejected: it stops what standard reports and leaves the strict mode PRJ-003 committed to with nothing behind it, so new package code could arrive untyped.
- **Opt files into strict one at a time**, with pyright's strict list naming files. Rejected: a new file starts outside the list. Naming the package's directory keeps what this offered and closes its gap.
- **mypy.** mypy reports an unannotated function once rather than each use of what it returns, and takes overrides per module, so its counts would be smaller and the tests could be configured looser. Rejected: the per-directory strictness that draws it here pyright already gives; by default mypy does not check the bodies of unannotated functions, so it would check less of the tests than pyright's standard mode; it has no baseline of its own either; and the configuration editors read has been pyright's from the first commit. Switching checkers would buy nothing the measurement shows a need for.
- **basedpyright**, a fork of pyright with a built-in baseline and a package that brings its own Node. Rejected for now. It would replace the ratchet's own tooling with a maintained one, but it moves the gate onto a fork that follows pyright's releases at a distance and adds rules and defaults of its own, so the gate's checker would differ from the pyright editors run. What it brings comes cheaper on pyright: the Node runtime from pyright's own extra, and a baseline for one directory's findings from a short comparison over pyright's report. It is the first alternative to revisit if the ratchet's tooling grows.
- **Ratchet the tests at standard instead of fixing their findings.** Rejected: the cleanup is small, and a baseline over the tests would put its bookkeeping on the part of the tree most changes touch.
- **Fail the gate on an improvement until the baseline is lowered.** Rejected: the hook, checking the working tree, would demand baseline edits that CI then fails (see "Why an improvement passes").
- **Key the baseline by line or by message.** Rejected: the baseline would churn on edits that change no finding.
- **Require branches to be up to date with `main` before they merge.** Rejected: a full re-check per merge, against a failure the run on `main` catches anyway.

## Implications

- **New package code is typed, and a test needs only what standard asks.** A new module in the package is strict-clean from its first commit. A test needs no annotation standard mode does not ask for, its fixtures included.
- **The package's typing advances where it is worked on, and nowhere else.** A change that calls a module's untyped code types that code rather than add findings under the module's entries; modules nobody touches keep their findings.
- **An upgrade of pyright or of a dependency re-measures the baseline in the same change**, and its pull request states the difference, so an upgrade that reports more is a visible decision rather than a silent loosening.
- **Only the package and the tests are checked.** Capability scripts, the permission hook and the build hook run on other interpreters and import paths — their own `_lib` packages, a bare system `python3` — and stay outside what pyright checks; bringing them in needs a configuration of their own.
- **The baseline's location and the command that lowers it are contributor documentation**, kept in CONTRIBUTING.md's "Running checks" and the tests' README rather than in this record.
- **When the baseline is empty, the ratchet retires**, and the package is gated outright like the tests: the gate is pyright's own verdict.
- **Refines PRJ-003's type-checking line**: the checker is pyright, strict for the package and standard for the tests.
