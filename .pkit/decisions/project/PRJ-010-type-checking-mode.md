## Context

The project's type checker is configured but gates nothing. PRJ-003 committed the runtime to strict type checking, and `pyproject.toml` names pyright's strict mode, but the check aggregator that the pre-push hook and CI both run does not run pyright, because the tree does not pass it. This record decides how the gate starts. pyright checks the package (`src/`) in strict mode and the tests (`tests/`) in its standard mode, set by directory. The tests must pass outright. The package's strict findings go into a committed baseline, a count per file and rule that the gate's tooling only ever lowers; a reviewed hand edit may raise it, for moved code and upgrades. The gate fails whenever the package carries more findings than the baseline admits, file by file and rule by rule, while the package is typed module by module.

Every figure in this record was measured with the pyright the lock pins, 1.1.409, on macOS, over the 336 files of the package and the tests at commit `3dca3957`, `main` when the record was proposed. Two setups differ only in the import paths pyright is told about. *As configured*, it is told the package and the repository root, which is what `pyproject.toml`'s configuration resolves to. *With the capability path*, it is also told the project-management capability's `scripts` directory, which the tests put on their import path at run time to import that capability's `_lib` package. The gate runs with that path (point 7), so a figure is with it unless it says otherwise.

Three facts carry the decision:

- **No mode passes.** Strict reports 37,244 findings, standard 200 and basic 198; as configured, 37,939, 257 and 255.
- **The lower modes find nothing strict misses.** In both setups, every finding standard or basic reports is also a strict finding, on the same line under the same rule.
- **Almost every strict finding is a missing or unknown annotation, and almost all of them are in the tests.** The rules for unannotated parameters, bare generics and values of a type pyright cannot know account for 36,666 of the 37,244 findings; 35,387 are in the tests, across 198 files, and 1,857 in the package, across 47 modules. Strict reports an unknown type at every use rather than once, and the tests take their fixtures as unannotated parameters by the thousand, so one unannotated fixture yields a finding on each line that touches it.

## Decision

**pyright checks the package in strict mode and the tests in standard mode, and the check aggregator gates both: the tests outright, the package through a ratchet — a committed baseline of the strict findings the package carries, which the gate's tooling only ever lowers.**

1. **The mode is set by directory.** pyright's configuration names the package directory as strict, and standard is the mode of everything else it checks. A new module in the package is in strict mode from its first commit without being listed anywhere. Editors, contributors and the gate read the same configuration.
2. **The tests are gated outright.** Outside the package the gate fails on any finding standard mode reports. There is no baseline there.
3. **The package is gated by a ratchet, counted per file and per rule.** The baseline records how many findings each package file has under each rule. A count above its entry, or a finding under a file or rule with no entry, fails the gate with the findings listed. So a module new to the package must be strict-clean, unless it is code moved from a module with entries (point 4), and an existing module may not gain a finding under any rule. A count below its entry passes, and the gate names the entries to lower and asks for them to be lowered; the change that made the improvement lowers them, and review holds it to that.
4. **The tooling never raises the baseline; a reviewed hand edit may, for moved code and upgrades.** Once the baseline exists, the command that writes it only lowers counts. A raise is a hand edit in the change that needs it, with the reason in its pull request. It is legitimate only where findings move or are measured differently rather than added: a module moved or split, pyright or a dependency upgraded, pyright's configuration changed. A guard backs the review: the gate fails when the baseline's total for any rule, summed over the package, rises against the change's merge-base, unless the same change alters the lock or pyright's configuration. A move or a split shifts counts between files and keeps every total, so it passes. A finding a change writes is fixed, never admitted.
5. **A finding is fixed, not silenced: in the package without exception, in the tests with a reason on the line.** pyright honours no `# type: ignore`: the configuration sets `enableTypeIgnoreComments = false`. Everywhere it checks, the gate refuses a `# pyright: ignore` that names no rule, and a file comment that sets the file's mode or a rule's severity. In the package it refuses a `# pyright: ignore` that names its rules as well, so no suppression is left there. Nor may the configuration narrow what the package is checked for: the gate fails when an `exclude` or `ignore` entry reaches into the package, when the strict list stops covering it, or when a rule's severity is set below what strict reports there. In the tests, a `# pyright: ignore` names its rules and gives its reason after them on the same line, and the gate refuses one that does not. It is for code that is ill-typed on purpose, such as a test handing a function the wrong type to exercise its runtime check. A rule is relaxed for the tests only in the configuration, with its reason beside it, as `pyproject.toml`'s ruff section does for lint. The gate counts warnings as well as errors.
6. **The pre-push hook checks the working tree, and CI decides.** The hook runs the aggregator over the working tree, as it does for the lint and the tests; CI runs it over the pushed commit and is the authority. Because an improvement passes, the hook never demands a baseline edit for work that is not committed. The command that lowers the baseline measures the commit: it refuses to run while a package file, the lock or pyright's configuration differs from the commit, so the counts it writes are counts the commit meets. Where the working tree differs from the commit, the hook's verdict and CI's can differ, as they can for the lint and the tests.
7. **The gate runs on the locked environment, and the baseline belongs to it.** The Node runtime pyright runs on comes from the lock, through the `pyright[nodejs]` extra, so syncing the development environment installs everything the type check needs. Findings depend on more than the code — on the pyright version, the packages in the environment pyright reads and the import paths it is told about — so the baseline holds for the locked environment and the configured import paths, as CI builds them. A finding that comes and goes with the host or with an import path pyright is not told about, such as the capability `_lib` packages the tests import, is fixed in the configuration and never written into the baseline.
8. **No one owns the package's typing, and its stall is accepted.** The ratchet stops the package getting worse; it does not make it better. The package is typed where changes work on it, and the baseline may stay large for a long time without weakening what the gate guarantees.
9. **The ratchet adds no requirement that a branch be up to date with `main` before it merges.** Two changes can each pass against their base and fail together: one loosens a function's types while the other adds calls to it, as for any check, or both spend the same slack under one entry. The run on `main` after the merge reports it, and the next change fixes it.

## Rationale

**Why strict for the package and standard for the tests.** PRJ-003 committed to a typed codebase because the package's surface — manifests, version specifications — is genuinely typed, and that reason holds where code is consumed through its types: the package is what adopters run, and its modules call one another through signatures that the reader and the checker both rely on. The tests are consumed by running them. Every line of a test runs on every pass of the suite, so a type confusion in a test mostly shows as a failing test, and standard mode reports the defects a run can miss: an optional value used unchecked, an attribute read off a union, an argument of the wrong type. What strict adds in the tests is mostly the annotation findings of the third fact — 34,874 of the 35,387 it reports there, nearly all an unannotated fixture or helper reported again on each line that uses it. Holding the tests to strict would ask every test to annotate its fixtures and type its helpers, for checking the suite largely does by running.

**Why the mode is set by directory.** pyright's strict list accepts a directory, and a file under it is strict whether or not it existed when the list was written. So the package's new modules are strict by default, and the gate holds them to it, because a file with no baseline entry may have no finding. Strict mode in a listed directory also overrides a rule the configuration relaxes, so a relaxation made for the tests cannot reach the package. That leaves the configuration three ways to narrow the package — `exclude`, `ignore` and the strict list itself — and point 5 checks them, with any severity setting strict does not override.

**Why the tests are gated outright and only the package through a ratchet.** The tests' remaining work is a cleanup. Standard reports 172 findings in 28 test files, and they are the findings standard exists for — optional values used unchecked, arguments of the wrong type. Today's suppressions hide more: switching `# type: ignore` off shows 16 more findings, in five more files, behind the tests' 23 such comments. The tests' 13 rule-named suppressions all name `reportPrivateUsage`, a rule standard does not report, so they hide nothing, and they go with the rest. Fixed once, they leave the most-edited part of the tree under a plain gate — a test passes when pyright reports nothing, with no baseline to read or update. The package's work is a typing migration: 1,857 strict findings in 47 modules, mostly values whose type pyright cannot know because something upstream of them is unannotated. With `# type: ignore` switched off and its rule-named suppressions removed, the package reports 1,891 in 49 modules: 34 findings sit behind its 23 suppressions, which point 5 refuses, so the first baseline counts 1,891. Gating the package outright would wait for that migration; the ratchet starts the gate before it and holds the line while it happens.

**Why count per file and per rule.** Line numbers move whenever code above them does, and messages name the types and symbols they are about, which change with any rename; either key would make the baseline churn on edits that change no finding. A count per file and rule is stable under both, and fine enough that a fix under one rule cannot pay for a regression under another, or a fix in one file for a regression in the next. What it cannot see is one finding swapped for another of the same rule in the same file — the price of stability, and small. The same granularity charges a change for what it calls: a new call to an untyped helper adds findings under the calling module's entries, so the change types the helper or fails the gate.

**Why an improvement passes.** Failing the gate on an improvement until the baseline is lowered would keep the baseline exact, but the pre-push hook checks the working tree, so it would demand a lower baseline whenever uncommitted work fixes a finding — a baseline the commit being pushed does not meet, which CI, checking that commit, then fails. A gate whose two runs contradict each other fails for the wrong reason, and the aggregator exists so that the hook and CI cannot drift. An improvement is never a defect: it passes, and the gate names the entries to lower. The cost is slack. A fix left unrecorded leaves room under its entry that a later change can spend, and two changes can spend the same room (see "Why the ratchet adds no up-to-date requirement"). The gate names the slack on every run until a change takes it, and review asks the improving change to take it.

**Why the baseline rises only by hand, behind a guard.** Every raise admits a finding the gate would otherwise refuse, so each one should be a decision someone reads. A tool that never raises it, and a raise that is a hand edit in the change needing it, put every admission into a diff with its reason in front of review. The legitimate causes are the ones where no finding is new: a module moved or split carries its findings to a new path, and an upgrade of pyright or a dependency, or a change to pyright's configuration, changes what is reported for unchanged code. Review can miss a raise, so the guard makes the plainest illegitimate one fail on its own: more findings under a rule across the package, with neither the lock nor the configuration changed. Moves and splits keep every total and pass. What the guard cannot see is a raise in one file paid for by a lowering in another under the same rule, or a raise in a change that touches the lock for another reason; each reaches review as a baseline edit in the diff, and review is the check there.

**Why suppressions are refused in the package and reasoned in the tests.** A ratchet a comment can step around is not a gate. `# type: ignore` hides every rule on its line, including findings written after it, so pyright is told to honour none. A suppression that names its rules is narrower, but it still hides every finding of those rules on its line while reading as one, so in the code the ratchet counts, one comment could admit new findings under cover of an old one. The package has other answers — an annotation, a `cast` to the type the code knows, a typed wrapper around an untyped library — so it refuses suppressions outright. A file comment that sets the mode or a rule's severity, and a configuration entry that reaches into the package, take code out of the count wholesale, so the gate refuses them as well. In the tests, held to zero, a ban would leave no way to write a test that hands a function a wrong type on purpose — correct code a checker cannot know is correct. A suppression naming its rule, with its reason on the line, is the narrowest way to say so, and the exception the lint makes for a line that is long on purpose; requiring the reason makes it something the gate can check rather than something review must remember. Relaxing a rule for the tests stays possible in the configuration, as for ruff, because it is made in one place, with its reason, under review. Warnings count so that lowering a rule from error to warning hides nothing.

**Why the hook checks the working tree, and the lowering command the commit.** Checking the commit in the hook would mean building a second copy of the tree on every push, for one step of an aggregator whose other steps all read the working tree. The lint and the tests already accept that a working tree with uncommitted changes can make the hook disagree with CI; with an improvement passing, the type check adds no way to disagree that they lack — provided the baseline was written from the commit. A lowering command that measured the working tree could write counts that uncommitted work meets and the commit does not, which the hook would pass and CI fail. Refusing while the package, the lock or the configuration differs from the commit closes that at no cost; reading the committed tree instead would need the second copy the hook avoids.

**Why the Node runtime comes from the lock.** pyright's Python package runs pyright on Node, taking it from the host's path or, failing that, downloading one on first run. A contributor without Node, or a session whose network is confined, would fail the pre-push hook on that first run. pyright's package offers the runtime as an extra that the lock pins like any dependency, so syncing installs it. The cost is one more platform-specific package in the development environment.

**Why the baseline belongs to an environment rather than to the code alone.** pyright resolves imports against the environment and paths it is given. The tests put capability `_lib` packages on their own import path at run time, and import a build backend the development environment does not install; pyright reports what it cannot resolve, and a different environment reports differently. (Told to check for Linux, pyright on macOS reports the same strict findings, file for file and rule for rule; the platform is not what varies.) Treating such a finding as a defect of the configuration keeps the baseline a record of the code's findings, rather than of the differences between hosts.

**Why the stall is accepted.** Naming an owner for 1,891 findings would assign a migration nobody has scheduled, and an owner who never gets to it is the same stall with a name on it. What the gate guarantees does not depend on the baseline falling: no new strict finding in the package, and nothing new wrong in the tests. That is not a guarantee of no new untyped code. An explicit `Any` — an annotation, or a `cast(Any, …)` — is not a finding, because strict reports types pyright cannot know, not a type the author declares unknown. The escape is accepted: it is written in the diff, where review sees it, unlike the unknown types strict exists to catch, and closing it would take a rule pyright does not have (see basedpyright below).

**Why the ratchet adds no up-to-date requirement.** Requiring every branch to be re-checked against the latest `main` before it merges serialises merges behind a full aggregator run each, for every change. The race it would close exists without the ratchet: a type change that breaks another change's code. The ratchet adds one of its own, through slack. Where a module's findings sit below its entry, two changes that each add findings within the slack pass against their base and together exceed it, with no conflict in the text, since neither touched the baseline. The race is accepted: it needs slack, slack lasts only until someone lowers it, every run that sees slack asks for it to be lowered, and the run on `main` after the merge reports the failure for the next change to fix.

### Alternatives considered

- **Strict everywhere, behind a ratchet over every file.** Rejected. The gate would start from 37,244 findings in 1,206 file-and-rule entries, 35,387 of them in the tests. A test added to any of the 198 test files with strict findings that uses an unannotated fixture adds findings under that file's entries and fails the gate, so writing a test would first mean typing its file's fixtures — a cost on the most-edited part of the tree, for checking the suite largely does by running.
- **Strict by default, with each file that does not pass marked down to standard** by a comment at its top. Rejected. New files of every kind would be strict with no baseline at all, but 245 files would carry the marker — a file comment setting the mode, which point 5 refuses — and a marked file can grow untyped code freely as long as it passes standard. In the package, where 47 modules would be marked, strict would hold only the modules written from here on; new test files would carry the cost of the first alternative; and the marked files would need standard's 200 findings fixed before the gate could start.
- **Standard everywhere, gated outright after the same cleanup.** Rejected: it stops what standard reports and leaves the strict mode PRJ-003 committed to with nothing behind it, so new package code could arrive untyped.
- **Standard for the tests, with strict's other rules switched on one at a time.** Strict's rules beyond standard, apart from the annotation rules, report 316 findings across the tree, 280 of them `reportPrivateUsage`. Rejected: that rule reports tests reading a module's private names, which tests do on purpose to check its internals, so the rule that yields most would be switched off as soon as it was on.
- **Opt files into strict one at a time**, with pyright's strict list naming files. Rejected: a new file starts outside the list. Naming the package's directory keeps what this offered and closes its gap.
- **mypy.** Weighed for what it does differently: it reports an unannotated function once, at its definition, rather than at each use of what it returns, which is what would make strict tests affordable. Rejected. A smaller count is not less work: strict mypy still asks for every test function and fixture to be annotated, the cost this record declines for the tests. In the package it sees less. An unannotated parameter is `Any` to mypy, and what is computed from it is `Any` too, reported nowhere past the function's one finding; a value from a library that declares no types is reported nowhere at all. pyright's unknown-type rules report each place such a type reaches, so an unknown value cannot travel through annotated code unreported. And the checker editors run on this tree is pyright, reading the same configuration, so a contributor sees the gate's modes while writing. mypy was not measured.
- **basedpyright**, a fork of pyright with a built-in baseline. Weighed on what it would change; not measured. Its baseline keys each finding by file, rule and column, which survives lines moving without reducing findings to counts, and its language server marks the findings the baseline holds, where under this ratchet an editor shows each of the package's 1,891 baselined findings as a live error. It has a rule pyright lacks, `reportExplicitAny`, that would close the explicit-`Any` escape this record accepts, and its package brings its own Node. Against it: by default it rewrites the baseline whenever findings are fixed, which, run by the hook over the working tree, recreates the contradiction "Why an improvement passes" avoids — its `baselineMode` setting turns that off; and the gate would move onto a fork that follows pyright's releases at a distance and adds rules and defaults of its own, with nothing yet measured of how it reports this tree. Rejected for now: the ratchet's own tooling is a count over pyright's report, a smaller step than switching checkers. It is the first alternative to revisit if explicit `Any` becomes a pattern in the package, if the editor noise costs more than it shows, or if the ratchet's tooling grows.
- **Refuse suppressions in the tests as well**, with `cast(Any, …)` for the deliberate wrong type. Rejected: the cast silences every check on that value, where a suppression naming one rule silences that rule on that line.
- **Ratchet the tests at standard instead of fixing their findings.** Rejected: the cleanup is small, and a baseline over the tests would put its bookkeeping on the part of the tree most changes touch.
- **Fail the gate on an improvement until the baseline is lowered.** Rejected: the hook, checking the working tree, would demand baseline edits that CI then fails (see "Why an improvement passes").
- **Key the baseline by line or by message.** Rejected: the baseline would churn on edits that change no finding.
- **Require branches to be up to date with `main` before they merge.** Rejected: a full re-check per merge, against failures the run on `main` catches anyway, the slack race included.

## Implications

- **Writing a test asks for no annotation standard mode does not ask for**, fixtures included.
- **A change answers for its own findings, and for its callers' when it annotates.** A run that names entries to lower for an improvement another change made asks nothing of a change that did not make it; taking that slack is welcome, not owed. Annotating a helper can raise counts in the modules that call it — a value that was unknown becomes a known type a caller misuses — and that raise is not one point 4 admits, so the change that annotates the helper fixes its callers.
- **An upgrade of pyright or a dependency carries its re-measured baseline**, and its pull request states the difference, so an upgrade that reports more is a visible decision rather than a silent loosening.
- **Code that runs on another interpreter or import path stays outside what pyright checks**, since the gate's environment and import paths are those of the package and its tests; bringing such code in needs a configuration of its own. Today that is the capability scripts, the permission hook and the build hook, which run on their own `_lib` packages or a bare system `python3`.
- **Contributor documentation carries the mechanics.** The baseline's location and the command that lowers it belong in CONTRIBUTING.md's "Running checks"; the rules a test author meets — the suppression form and its reason — in `tests/README.md`.
- **When the baseline is empty, the ratchet retires**, and the package is gated outright like the tests: pyright's verdict, with point 5's suppression and configuration checks.
- **Partially supersedes PRJ-003's type-checking line.** PRJ-003 left the checker open between pyright and mypy and asked strict mode of all of it; the checker is pyright, strict for the package and standard for the tests. The rest of PRJ-003, its commitment to a typed codebase included, stands.
