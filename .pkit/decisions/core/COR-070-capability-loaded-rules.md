title: A capability's operational rules load where it is installed, and no layer's rules loosen another's
status: accepted

**In plain terms:** a capability may ship operational rules of its own, as one loaded rule set. The file generated from that set travels with the capability, and names the capability and how its rules stand to core's. Wherever the capability is installed, the adapter delivers that file by the route that carries core's rules where its harness offers one, kept where core's file is, so a session that loads core's rules loads it too, and takes it away when the capability is uninstalled. Installing the capability is the project's consent to those rules, and install, sync and upgrade say which rules they newly bind, core's among them. Rules add up across layers: a capability's never loosen core's, and a project's never loosen core's or a capability's. A rule that binds only where a capability is installed belongs to that capability, not to core. Validation fails where the adapter's delivery is in a checkout and does not carry an installed capability's file as it is. Whether every kind of session really loads it is a harness requirement, reported as indeterminate where it cannot be seen.

## Context

Operational rules are kept in loaded rule sets ([COR-068](COR-068-loaded-rule-sets.md)). A loaded set's accepted rules bind on the work of each session that loads the file generated from it. Core's set binds in every project, and a project's own in that project. COR-068 point 4 leaves a capability's loaded set to the first capability that ships one: how its loaded file reaches the sessions, and how a project's rules relate to a capability's. Until then, validation refuses one.

Some operational rules bind only where a capability is installed. A rule on which tests a session runs while it changes code binds where code is engineered. A rule on how work is linked to the issues that track it binds where that work tracker is in use. Without a loaded set of the capability's, such a rule sits either in core's set, which binds in every project, or in each project's own rules, where every project writes it again. Or a core rule defers to the capability's documentation, which no session loads.

Core's loaded file reaches a session through one include in the project's instruction file, which the adapter inserts where it is absent and the project owns ([COR-002](COR-002-merge-delivery.md)). A capability is installed and uninstalled ([COR-017](COR-017-capability-pattern.md)), so its file must arrive and leave with it.

A session reads the files it loads, not the records behind them ([COR-065](COR-065-records-and-projection.md) point 7). So what a session needs to know of how a capability's rules stand to core's and to a project's must be in the file it loads.

Whether a session loads a file is the harness's behaviour, not the methodology's. A harness may load its start-up files in a session a person starts, and not in some helpers it starts for another agent, or in a run started without the project's settings. A loaded rule binds only on the sessions that load its file (COR-068 point 2), so a session that loads none is bound by nothing, and nothing says so.

## Decision

**A capability may ship one loaded rule set. Its loaded file is generated where the capability is authored, travels with it, and names the capability's layer. Each adapter delivers that file, for as long as the capability is installed, through a file or place of its own and by the route that carries core's rules where the harness offers one, so every session that loads core's rules loads it too. Validation fails where that delivery is in a checkout and does not carry the file as it is. Installing the capability accepts its rules, and no layer's rules loosen another's.**

### 1. A capability ships at most one loaded set, and its loaded file travels with it

- **One set:** a capability may ship one loaded set, beside its ordinary rule sets (refinement of COR-068 point 4). It is a method set of the capability ([COR-051](COR-051-rule-sets.md) point 6), with one loaded set to a component, as COR-068 point 1 says. Its name is its own, and no other set a project holds takes it (COR-051 point 3).
- **Its file:** generated from the set where the capability is authored, as COR-068 point 3 says of every loaded set, and kept among the capability's own files. Sync, install and upgrade deliver it there with the set, and the delivery of point 2 brings it to the harness (refinement of COR-068 point 3). A project neither generates nor edits it.
- **It names its layer:** the set's prose before its first rule, which carries into the loaded file, names the capability, says how its rules stand to core's and to a project's, and says that a clash with another capability's rule stops the step, as point 4 decides. A session reading the file then knows its layer.
- **Which rules it holds:** COR-068 point 1's test, read for a capability's layer. A rule that must bind on a session's work wherever the capability is installed, with no opt-in, goes in its loaded set, a rule about files among them. A rule a project chooses to bind on its own artefacts goes in an ordinary set, and binds through the project set the capability's install declares (COR-017, "Running install is the consent") or one the project writes.
- **Its citations:** its rules are cited by their ids with the capability's name, as a method set's rules are (COR-051 point 6), and by no form of capability and number. The form by layer and number stays core's and a project's (refinement of COR-068 point 6).
- **Its origins:** each rule's origin cites a record that travels with the capability or with the backbone, or gives the decider's words, since the set is validated in every project that installs it.

### 2. The adapter delivers the loaded file by the route that carries core's rules

- **Where:** each adapter delivers an installed capability's loaded file to the sessions its harness starts in the project, from the session's start and for its whole length. Its obligation is relative to core's: every session that core's loaded file reaches. A kind of session that core's route misses, point 6 names.
- **By core's route:** where the harness offers one, the delivery takes the route by which core's loaded file reaches a session, so every session that loads core's rules loads the capability's too. Where a harness offers more than one route, and one reaches fewer kinds of session than core's, the adapter does not take it.
- **Where core's file is:** what the delivery keeps in a checkout is kept where core's loaded file is, wherever the form allows, so a checkout that holds core's holds it too. Where it cannot be, point 6 reports a checkout without it.
- **Through a file or place of its own,** in either of two forms, which the adapter chooses for its harness. Each is one that no file of the project's shares a name with:
  - a place the harness reads at every session's start, into which the adapter puts the file;
  - a file of its own, rendered for the project from what is installed, that reaches each installed capability's loaded file, and which the project's instruction file reaches through one line kept present there, inserted wherever it is absent, as what is absent is inserted (COR-002).
- **The project's text:** nothing done at install, sync or uninstall removes or rewrites the project's own text. The one line is kept present, and the file it reaches carries every change of which capabilities are installed.
- **What it delivers:** the content of the capability's loaded file, as the capability's own files hold it.
- **When:** wherever the lifecycle regenerates derivable state ([COR-010](COR-010-resource-lifecycle.md)), as at install, sync and upgrade. Uninstalling the capability takes its file out of the delivery, and so does unregistering one with its files kept ([COR-031](COR-031-capability-origin.md)).
- **A harness that loads no such files:** its adapter says that it delivers no capability's rules. Its sessions then load none, which point 6 reports.

### 3. Installing a capability accepts its loaded set

- **Consent:** the person who installs a capability consents to its loaded set's accepted rules: running install is the consent, as it is for the project rule set the capability declares (COR-017). The rules bind in the project from the install to the uninstall. No rule is accepted a second time in the project, since a rule a project receives from elsewhere is judged where it is kept ([COR-066](COR-066-accepted-before-landing.md) point 2), and a person accepted it there (COR-066 point 1).
- **Told what binds:** install, sync and upgrade name each loaded set they deliver, core's among them, and list the rules it newly binds, changes or retires since the version it replaces (refinement of COR-068 point 5). That is information, not a gate. Where the harness's adapter delivers no capability's rules (point 2), they say that a capability's rules bind no session there, rather than list them as bound.
- **A later version:** a rule the capability accepts, edits or retires in a later version binds, or stops binding, once the upgrade or sync that brings it lands, as core's rules do (COR-068 point 5).
- **No opt-out while installed:** neither the capability's loaded file nor its delivery is suspendable ([COR-001](COR-001-content-mechanisms.md)). A rule about a session's work has nowhere narrower to bind than the project, so a project chooses only to install the capability or not (COR-068, "Why core's set binds with no opt-in").

### 4. Rules add up across layers, and none loosens another

- **A session is bound by all of them:** every accepted rule of every loaded file the session loads binds it, core's, each installed capability's and the project's.
- **None loosens another:** a capability's rule never loosens a rule of core's, and a project's never loosens one of core's or of an installed capability's (refinement of COR-068 point 4). A capability's rule that loosens core's is a defect of the capability, judged where its rule is accepted. A project's rule that reads as loosening one binds only in what it adds. A project that wants less proposes the change where the rule is kept, or uninstalls the capability.
- **A clash met in a session:** where a rule cannot be kept together with a rule of a layer above it, the upper layer's rule binds: core's above a capability's, and both above the project's. Where rules of two capabilities cannot both be kept, the session stops the step and reports the clash, as it stops a step that keeps failing (backbone:RS-OPS-021), rather than choose between them. The capability's loaded file says so (point 1), since a session does not read this record.
- **Judged, not checked:** whether a rule loosens another, or clashes with it, is read from prose, so no check decides it ([COR-055](COR-055-validation.md)). The person who accepts a rule judges it, in the change that proposes it.

### 5. A rule that binds only with a capability belongs to that capability

- **Where it goes:** a rule that binds a session's work only where a capability is installed belongs in that capability's loaded set, rather than in core's, whose rules bind in every project, or written again in each project. This is the universal-applicability test ([COR-014](COR-014-universal-applicability.md)) between core and a capability, and such a rule goes to the capability's loaded set rather than to its documentation, which no session loads (refinement of COR-014, "Scoping content that fails the test").
- **A rule the project had written itself:** where a capability a project installs ships a rule the project had kept in its own rules, the project's own may retire, keeping what holds only in that project. A project whose rules are a plain file (COR-068 point 7) points from the retired rule to the capability's as it chooses.
- **A rule a project moves into a capability it authors:** where the project authors the capability itself, as an incubated capability is authored in the project (COR-031), the rule is written again for every project that installs the capability, with an origin of its own. What holds only in the project stays the project's.
- **What stays in core:** a core rule that loses such a part to a capability keeps its universal part. It is edited, keeping its id, where its claim stays, or withdrawn where none of it stays (COR-051 point 4).
- **No capability successor:** a core rule never names a capability's rule as its successor. A successor sits in the rule's own set or in one that inherits it, and no loaded set inherits another (COR-051 point 4; COR-068 point 1). A core rule must also read true in a project where the capability is absent (COR-014).

### 6. Validation fails where a delivery is not in step, and whether a session loads it is a harness requirement

- **Delivered:** where the adapter's delivery is in a checkout, validation fails it where it does not carry an installed capability's loaded file as it is. In the first form of point 2, that is a file missing from the place or a file it carries changed. In the second, it is an entry missing from the file, an entry for a capability no longer installed, an entry whose loaded file is absent, or the project's instruction file without the line that reaches it. Where the delivery is not in the checkout, validation reports, without failing, that these files are not delivered there. Where an adapter in use delivers no capability's rules (point 2), validation warns of it.
- **In step:** where the capability is authored, the check COR-068 point 3 sets fails a loaded file out of step with its set.
- **Loaded:** a harness requirement ([COR-047](COR-047-harness-requirement-declaration.md)) states that every session the harness starts in a project holds every layer's loaded files from its start and for its whole length, after the harness shortens the session's context too: a session a person starts, a delegated helper and an unattended run. An adapter's answer grades it, and names apart a kind of session that its own way of starting one leaves without them. Its truth shows only while a session runs, to the session itself or to what the harness runs at its own points during it, so a report run from outside every session resolves it indeterminate, never satisfied. It rests on COR-068 point 2: a loaded rule binds only on the sessions that load its file.

## Rationale

**Why the delivery takes the route that carries core's rules, and is kept where core's file is.** A harness may load its files by more than one route, and the routes need not reach the same sessions: a setting may drop one and leave another, and a checkout may hold one route's files and not another's. A capability's rules delivered by a narrower route, or kept where some checkouts leave them out, would then be missing exactly where core's still bind, and a session would keep the methodology's invariants and break the capability's, with nothing to say so. Taking core's route, and keeping the delivery with core's file, ties the two together: wherever a session is bound by core's rules, it is bound by every installed capability's. Where core's route itself misses a kind of session, both miss it, and point 6's requirement names it once.

**Why through a file or place of its own.** The project's instruction file is the project's, merged by inserting what is absent (COR-002). A line added for each capability at install would have to be taken out at uninstall, and a removal from a file the project writes can take the project's own text with it. A file or place of the delivery's own can have what was delivered added and removed, as a capability's skills are, and never meets a file of the project's under the same name. One line that reaches a file of its own never needs removing: that file carries each install and uninstall. Kept present wherever it is absent, as COR-002 keeps what it inserts, the line leaves a project no opt-out by deleting it (point 3).

**Why the file names its layer.** A session loads files, not records (COR-065 point 7), so how a capability's rules stand to core's and to a project's binds a session only where its loaded file says it. Three files with numbered rules read alike otherwise.

**Why the file is generated where the capability is authored.** COR-068 point 3 decides that a project neither generates nor edits a loaded file it receives. A file generated at install would be the project's to keep in step with a set it does not edit. It could also read differently in two projects that install one version of the capability.

**Why citations by id only.** COR-068 point 6 keeps "core rule N" and "project rule N" because records, documents and decided answers already cite rules that way. No citation of a capability's operational rule exists yet, so none needs keeping. A form by capability and number would be one more form to read from prose, where a capability's name and a number may mean something else.

**Why installing accepts the set.** A capability is chosen by installing it, so its rules bind from that choice and end with it (COR-068, "Why core's set binds with no opt-in"). Its declared project rule set is consented to the same way (COR-017). Accepting each rule again in each project would have every project review again what a person accepted where it is kept (COR-066 point 2). A project that declined one rule would then be bound by a set that nobody authored.

**Why install, sync and upgrade say which rules they bind.** Consent given once at install covers rules a later version adds. Without a word at the upgrade, a project's own rule could stop binding in part, because a new rule now sits above it, and nobody would judge it. Core's set sits above the project too (point 4), so a sync that brings a new core rule does the same, and is named the same way. Naming what newly binds lets the project see it, without a gate that would hold back rules that must reach every session (COR-068, "Why a version that holds nothing back").

**Why no layer loosens another.** Core's rules keep the methodology's invariants, and a capability's keep its discipline's. Other sessions, reviewers and the capability's own commands rely on both. A project's rule that waived one would take away a guarantee that others rely on, unseen. Adding to a rule never breaks it. Loosening one is a change to the rule itself, made where it is kept, where its author and its readers see it. The upper layer wins a clash for the same reason.

**Why rules rank the other way from agents and skills.** Where two layers ship an agent, a skill or a provider of one name, the project's takes the place of a capability's, and a capability's the place of core's ([COR-013](COR-013-agent-architecture.md), "Provider precedence"). That order is deliberate, and so is its reverse here. An agent or a skill is a whole that a layer replaces, to specialise it for its work, and only one of two can run. Rules compose: every layer's bind at once, and a lower layer only adds to an upper one. A project that could replace core's rule would take away what the methodology guarantees, unseen. Core's loaded file says how the layers stand, as a capability's does, so a session in a project with no capability's rules reads it too.

**Why a clash between two capabilities stops the step.** Two capabilities stand side by side, so neither outranks the other. A session that chose between them would decide what no author decided. Asking the person each time would ask the same question in every session, with no answer it could keep, since a project's rule that picks one would loosen the other, and an unattended run has no one to ask. Stopping the step and reporting the clash makes it a defect for the capabilities' authors to settle where their rules are kept.

**Why a core rule never names a capability's rule as its successor.** A capability may be absent from a project, and a successor there would name a rule that does not exist. COR-051 point 4 also keeps a successor in the rule's own set or an inheritor, so that where the old rule bound the successor binds. A core rule keeps what holds everywhere, and the capability's own set holds the rest.

**Why a capability's rule is written for every project that installs it.** A rule in a capability's loaded set binds in every project that installs it, so it states what holds wherever the capability is installed (COR-014). A project's own rule on the same subject was written for that project's tools and checks: the part the capability's rule now covers may retire, and the rest stays the project's. A rule a project moves into a capability it authors is written again the same way, not moved as it stands, since it would otherwise be false in a project without that project's tools.

**Why validation reports, rather than fails, where the delivery is absent.** A checkout without the delivery is one where the lifecycle never regenerated it, or, where the form cannot keep the delivery with core's file, one whose project keeps it out of version control, such as a continuous-integration checkout. Its sessions load none of these files, and only the lifecycle's next run, or a choice of what the project keeps in version control, could change that. Failing there would fail a healthy project for that choice. Where the delivery is there, a missing or differing file is a delivery left incomplete or a file edited by hand, which the next sync mends, so it fails. The check keys on the delivery itself, not on whether the adapter placed something else, since a project may keep one of the adapter's places in version control and not another.

**Why whether a session loads the file is a harness requirement, not a check.** Validation runs outside every session. It can see that the file is where the harness should load it, not that a session loaded it. A harness may start a helper with a context of its own, or a run that skips the project's settings. Reporting that indeterminate keeps "the file is in place" from reading as "every session follows the rules" (COR-047 point 4). A kind of session the adapter's own way of starting one leaves without the files is not a cost an adopter can keep, so the answer names it apart, as COR-047 point 2 keeps "not achievable" apart from "at a cost".

### Alternatives considered

- **A line for each capability in the project's instruction file.** Rejected: uninstall would remove text from a file the project owns.
- **Any route the harness reads at each start, whichever reaches fewer sessions.** Rejected, as "Why the delivery takes the route that carries core's rules" says: a capability's rules would miss sessions where core's bind.
- **A region of the adapter's own inside the project's instruction file.** Rejected: its content would change at each install and uninstall, inside a file the project writes.
- **The harness's start hook, adding the file to a session's context.** Rejected as the means: a project's own hook may take its place, and what a hook adds may not last the session.
- **One loaded file joining core's rules and every installed capability's.** Rejected: one file of several owners breaks the no-shared-files invariant, and it would be generated in the project at each install, which COR-068 point 3 rules out.
- **Generating a capability's loaded file at install or sync.** Rejected, as "Why the file is generated where the capability is authored" says.
- **Loading a capability's rules only in the sessions of its own agents, or only for the files a session touches.** Rejected: a loaded rule binds on any session's work where the capability is installed, and a person may do the capability's work with any agent. Binding on files only where a scope selects them is what ordinary rule sets do (COR-051 point 7).
- **A switch that keeps a capability's loaded set away while it is installed.** Rejected: a rule about a session's work leaves a project only installing the capability or not (COR-068).
- **Accepting each capability rule again in each project.** Rejected, as "Why installing accepts the set" says.
- **Asking the person at each clash between two capabilities.** Rejected, as "Why a clash between two capabilities stops the step" says.
- **Retiring a core rule with a capability's rule as its successor.** Rejected, as "Why a core rule never names a capability's rule as its successor" says.
- **Citing a capability's rules by capability and number.** Rejected, as "Why citations by id only" says.

## Implications

- **COR-068 points 3, 4, 5 and 6** and **COR-014's "Scoping content that fails the test"** gain forward pointers to this record, and validation accepts a capability's set marked loaded.
- **The adapters' shared specification** says how an adapter declares its delivery of a capability's loaded file, and what takes a capability out of it. The architecture record that realises this one decides each harness's form of delivery, the file's path among the capability's files, the form of the prose that names the layer, and where the check runs.
- **The harness requirements** gain the requirement of point 6, and each adapter answers it in its support declaration.
- **The capabilities' reference** names a capability's loaded set and its loaded file among the files a capability may ship (COR-017).
- **Rules that bind only with a capability** go to that capability's loaded set, and a core rule that held such a part keeps its universal part, as point 5 says. The architecture record that realises this one names which, for a person to accept in the change that makes them (COR-066).
- **Core's loaded file says how the layers stand:** its preface gains a short statement that every layer's rules bind at once, that a capability's and a project's add to core's and never loosen them, and that the upper layer's rule binds where two cannot both be kept (point 4). Its closing says that a capability's operational rules are kept in that capability's loaded file, not in its documentation. A person accepts both edits in the change that makes them (COR-066).
- **Stands on these records, all accepted:** COR-001, COR-002, COR-010, COR-013, COR-014, COR-017, COR-031, COR-047, COR-051, COR-055, COR-065, COR-066 and COR-068.
