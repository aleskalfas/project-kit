## Summary

Authoring a process definition today means hand-editing YAML against the full substrate contract ([COR-033](COR-033-process-substrate.md) and its refinements) — slow, un-shareable, and a steep learning curve for every definition owner. This record packages process *authoring* the way schema authoring is already packaged: **a core composite skill walks the declarative half of a definition (its shape) over deterministic authoring commands that do the stamping, and a core owner-scoped agent authors the executable half (its teeth — the detection and gate predicates), each invoked by the definition's owner on the owner's own definition.** The layer sits *over* the substrate: it produces definitions the existing engine validates and the existing operations (`status`, `move`, `validate`, `health`) consume — never a rival engine, never a rival store.

The record fixes four things: **(1)** the shape/teeth boundary — what is data in the definition is skill territory, what is a predicate over reality is agent territory; **(2)** the authoring actor — a new core `process-author` agent, owner-scoped so it never edits a definition it does not own; **(3)** the skill's operation set — closed and data-driven (`new`, `couple`, `hand-off` shipped; definition evolution named-deferred); **(4)** placement — straight to core beside the schema-authoring precedent, because the substrate it authors for is core. A cross-owner composer — one actor wiring *other* owners' definitions — is deliberately not pursued.

## Context

The process substrate is complete enough to author against: shape and engine ([COR-033](COR-033-process-substrate.md)), keyed subjects, waits, invariants, subprocess embedding and cascade, inert cross-process connections ([COR-038](COR-038-process-connections.md)), and checkable hand-off contracts with a health surface ([COR-042](COR-042-process-health.md)). What does not exist is an authoring layer: a definition owner who wants a new process, a coupling, or a checkable hand-off must know the substrate records by heart and hand-edit their definition against them. The first adopter working at this altitude filed the request that produced this record, with two grounding cases: wiring a hand-off between two of their own definitions, and standing up a new process in a non-development domain from scratch.

The corpus already holds the precedent this mirrors. Schemas are a substrate mechanism, not a capability: built-in commands plus a core composite authoring skill ([COR-020](COR-020-skill-folder-form.md)'s worked example) that walks an author through the mechanism's disciplines. Process authoring has the same shape — commands already shipped, authoring knowledge un-packaged.

One property of process definitions makes a skill alone insufficient, and it is the load-bearing observation of this record: **a definition has two halves of different kinds.** The *shape* — subject, states, transitions, couplings, hand-off contracts — is declarative data with a closed vocabulary; a skill can walk it at high abstraction. The *teeth* — the detection predicates ("how do I know a subject is in state X?") and the gate predicates ("what must be true to move?") — are domain logic over the owner's reality; under detection-over-reality the definition is only as good as these predicates, and writing them is real authoring, not form-filling. The halves demand different carriers per [COR-006](COR-006-artifact-roles.md): procedure for the first, a judgment-capable actor for the second.

## Decision

**Process authoring ships at core as a two-carrier layer: a composite skill owning the shape, an owner-scoped agent owning the teeth. Both operate only on definitions their invoker owns.**

### 1. The shape/teeth boundary is the carrier boundary

Anything expressible as data in a process definition — subject and cardinality, states and their meanings, transitions, entry/terminal marks, `depends_on` couplings, hand-off contracts — is **skill territory**: the composite skill walks the authoring questions, stamps the declaration, and scaffolds a predicate *stub* for every evaluable the declared shape demands. The **teeth are every evaluable the shape declares** — that is the durable rule; the shape reference owns the authoritative slot list. As an illustrative snapshot at authoring time: detection predicates, transition gates, entry guards, `resume_when` on an awaiting-condition wait, invariant checks, the cascade fold's membership seams, and both hand-off seams (the candidate source *and* `resolve`). All of these are **agent territory**: the agent turns the owner's plain-language intent ("a document is in review when a review request exists") into a working predicate behind a stub the skill scaffolded. The one executable slot that is neither is the deferred transition resolver — out of scope until that substrate slot ships. The skill never writes predicate logic; the agent never re-derives the shape contract — when teeth-work reveals a shape problem, the agent routes through the skill's operations rather than editing shape by hand.

Each carrier ends its work by running the substrate's own checkers — definition lint always, and where a hand-off contract was touched, the **interpretability half** of the health surface: the contract resolves, the trigger is a real state of the upstream, the seams execute — i.e. *no indeterminates*. A fresh, correct contract routinely reports real *misses* (upstream work waiting is the very situation that motivates declaring it), so miss-count is never the authoring done-signal; an interpretation-only check variant is an implementation implication, not a change to the health surface's own contract.

### 2. The teeth actor is a new core agent, owner-scoped

Predicate authoring gets a dedicated **`process-author` agent at the core agents path**, not a fold into an existing pattern. This is deliberately the **first producing agent at core** — an expansion of degree, not kind: the nearest structural precedent is the architectural-custodian agent, core-shipped with constrained edit authority over overlay-resolved, adopter-owned record paths ([COR-024](COR-024-critic-and-architect-agents.md) / [COR-025](COR-025-adr-decision-space.md)); what is new here is that the authored artifact is **executable predicate code** the engine later evaluates fail-closed, and that the target paths are adopter capability subtrees core cannot enumerate. No new trust channel into the engine opens: authored predicates land through the adopter's normal review-and-commit path like any hand-written predicate — the agent packages the authority the owner already exercises by hand. Folding the work into the general-purpose producer that ships in an opt-in capability is rejected: it would make a *core* substrate's authoring depend on an *optional* install — an inverted dependency — and that body carries a different discipline that fails the substrate-altitude substitution test. The agent passes the core placement bar ([COR-026](COR-026-agent-placement-by-discipline.md) / [COR-014](COR-014-universal-applicability.md)) because the discipline its body implies is the process substrate itself, which every adopter has — while the *artifacts it edits* are adopter-authored files, exactly as the decision-authoring skill is core yet authors the adopter's records.

**Owner-scoping, operationally — two layers, named as such.** The **mechanical layer**: the agent edits only **adopter-authored** definitions and predicate scripts, never core-shipped, sync-managed ones — testable by the capability-origin property ([COR-031](COR-031-capability-origin.md): an incubated-in-repo subtree is adopter-owned; a methodology-shipped one — origin `kit-shipped` in that record's vocabulary — is sync-managed), the no-shared-files invariant applied at the agent surface. The **discipline layer**: within that class, the agent works **only the one definition named at invocation** plus its predicate scripts — single-target scoping that static frontmatter cannot express and body discipline carries (the same honest-interlock posture the cross-repo boundary takes in [COR-039](COR-039-session-repo-mutation-boundary.md)). Couplings compose under this constraint by construction: [COR-038](COR-038-process-connections.md) places every cross-process connection declared via `depends_on` in the *subscriber's* definition (and subprocess embedding lives in the parent's own definition per its dual), so wiring a dependency on an upstream process is always an edit to one's own file, the upstream untouched. How the agent's frontmatter expresses edit authority over paths core cannot enumerate rides [COR-013](COR-013-agent-architecture.md)'s overlay mechanism and lands as an architecture record at implementation (Implications) — not settled here.

### 3. The skill's operation set: three shipped, the rest named-deferred — each backed by a deterministic command

The composite skill ([COR-020](COR-020-skill-folder-form.md) folder form) ships three operations, each grounded in the requesting adopter's real cases and each **paired with a deterministic authoring command that does the stamping** ([COR-005](COR-005-bundle-pattern.md); Implications):

- **`new`** — scaffold a definition: subject, states, transitions, entry/terminal marks, plus stubs for every evaluable the shape demands. A fresh definition's *full* shape surface — waits, invariants, subprocess embedding, cascade folds, open regions — rides inside `new`'s walkthrough, since a from-scratch definition may declare any of it. **`new` begins by establishing the definition's home:** a definition is a capability-instance artifact and its predicates register in the owning capability's package, so the walkthrough routes an adopter with no owning capability through the capability-authoring path first — a real route because an incubated capability is first-class and adopter-owned ([COR-031](COR-031-capability-origin.md)). The layer does not invent a project-side definition home — that would be a substrate-shape decision this record does not make.
- **`couple`** — author a `depends_on` entry into the owner's own definition: relation from [COR-038](COR-038-process-connections.md)'s closed set, mode, the required `why`.
- **`hand-off`** — add a [COR-042](COR-042-process-health.md) hand-off contract to a coupling: trigger state plus both seams (candidate source and `resolve`), surfacing that record's two authoring smells (an ephemeral trigger; a candidate source that silently returns nothing) as questions the walkthrough refuses to complete without answers to.

Within an operation, **closed substrate vocabularies are read as data** — a new relation kind is an enum value `couple` picks up, never a new sub-procedure. But closed vocabularies are not closed *block kinds*: adding a further shape block to an *existing* definition (illustrative snapshot: a wait, an invariant, a subprocess embedding, a cascade fold, an open region — the shape reference owns the authoritative list) is a distinct walkthrough with its own smells, and those operations are **named-deferred** per [COR-016](COR-016-scripted-scenario-storyboards.md)'s name-broad / ship-narrow discipline alongside **`amend`** — evolving a definition's states and transitions under live subjects, riding the definition-version field the shape already carries. Each is built when a real case needs it. The two shipped mutation ops have defined version semantics now: a `couple` or `hand-off` edit is additive and inert or report-only, so it does **not** bump the definition version; state and transition edits are `amend` territory and do.

### 4. Placement: straight to core, beside the mechanism it authors for

The layer ships at core — skill beside the schema-authoring skill, agent beside the core agents, documented in the process area's authoritative spec. No incubation: incubation hedges uncertainty about whether a discipline earns a permanent home, and this layer's home is determined by its subject — the substrate is core, its authoring layer is core, exactly as schema authoring is. Grounding-before-generalising is still honoured: the shipped operations are the ones the first adopter's real processes exercise.

### 5. The cross-owner composer is not pursued

A single actor that wires *other* owners' processes by editing definitions it does not own is rejected, not deferred: [COR-038](COR-038-process-connections.md)'s coupling-in-the-subscriber means the standard wiring need is served by the subscriber editing its own definition, so a composer would centralise the actor without adding capability — while colliding with [COR-013](COR-013-agent-architecture.md)'s one-owner-per-path invariant. Rejection carries supersession weight: a future composer must supersede this point, not reinterpret it — the ruling is flagged for explicit sign-off at acceptance. The one reach owner-scoping genuinely lacks is the **converse** of the standard case: making a definition the adopter does *not* own depend on the adopter's own process — the subscriber file there is core-shipped and sync-managed, so no owner-scoped actor may edit it. That is a project-tier overlay question on the definition artifact, named here and left outside this record.

## Rationale

**Why two carriers instead of one bigger skill.** A skill is procedure — it can ask the shape questions because their answers are entries in a closed vocabulary. Predicate authoring has no closed vocabulary: it is domain logic whose quality determines whether detection-over-reality tells the truth. Packing it into skill prose would produce either a skill that hand-waves the hard half ("now write the predicate") or one that smuggles an agent's judgment into procedure — the carrier-mismatch [COR-006](COR-006-artifact-roles.md) exists to prevent. The split also matches how the substrate itself divides: shape is validated by lint, teeth are exercised by `health` and the engine's live detection.

**Why owner-scoped rather than general.** Ownership is what makes the agent safe to ship at core. An agent that edits any definition would need the cross-owner authority the composer question raises; an agent scoped to its invoker's own artifacts needs none — it is the same authority the owner already exercises by hand, packaged. The substitution test then holds structurally: nothing in either body may assume a development domain (the vocabulary stays at substrate altitude — subject, state, coupling, trigger, hand-off) or a particular project; a document-review flow must walk through the same operations as an issue lifecycle.

**Why straight to core when capabilities exist for opt-in discipline.** [COR-017](COR-017-capability-pattern.md) packages disciplines some adopters want and others do not. The process substrate is not opt-in — it ships with the backbone — and an authoring layer whose subject every adopter has fails the "some adopters don't need this" test that justifies a capability. The schema-authoring precedent settles the *skill* half of this question for the sibling mechanism — core placement, composite form; it carries no agent, so the agent half rests on the [COR-026](COR-026-agent-placement-by-discipline.md) argument alone, stated in Decision point 2.

### Alternatives considered

- **One skill, no agent** — rejected: leaves the teeth (the half that determines whether the process tells the truth) to hand-authoring, which is the status quo this record exists to end; or overloads procedure with judgment.
- **A teeth *skill* instead of an agent** (the middle option: a walkthrough carrying the predicate-runner contract — read-only, structured output, fail-closed, package registration — for whatever producer the adopter has to execute) — rejected as the *primary* carrier: the contract-conformance wrapper is indeed closed and walkable, but the core of teeth-work is the open half (turning intent into domain logic), and a skill that must hand that to "whatever producer is present" reintroduces the optional-install dependency for adopters without one. The contract walkthrough is not lost — it becomes part of what the agent's body carries.
- **Fold teeth-authoring into an existing producer agent** — rejected: the existing producers are capability-shipped and their bodies carry a different discipline; a core mechanism's authoring must not require an optional install, and a general producer's body fails the substrate-altitude substitution test.
- **A capability (`process-authoring`)** — rejected: the subject is core substrate; a capability boundary would let an adopter hold the substrate without its authoring layer for no benefit, and diverge from the schema precedent for no reason.
- **A cross-owner composer** — rejected outright (Decision point 5): centralises the actor without adding capability, collides with one-owner-per-path, and no grounding case demands it.
- **An open-ended op set (one sub-procedure per relation/contract kind)** — rejected: the substrate's vocabularies are closed sets; operations that read them as data absorb vocabulary growth without skill edits, the same property schema-driven operations already established elsewhere in the corpus.

## Implications

- **New artifacts:** the composite skill folder at the core skills path (dispatcher + `new` / `couple` / `hand-off` sub-procedures, per [COR-020](COR-020-skill-folder-form.md)); the `process-author` agent at the core agents path (authored via the agent-authoring skill, [COR-013](COR-013-agent-architecture.md) conventions); the process area README documents the layer as part of the authoritative spec. Skill/agent deployment rides the adapter's existing deploy primitives.
- **Skill/command pairing** ([COR-005](COR-005-bundle-pattern.md)): **each shipped shape operation is paired with a deterministic authoring command underneath it** — the schema-authoring shape exactly: the command owns the stamp (scaffold the definition and its stubs; mutate the declaration for a coupling or contract; correct numbering, layout, lint-clean output), the skill owns the disciplines and the walkthrough, and hand-stamping a definition is as out of bounds as hand-stamping a record. Exact command names and grammar are implementation; the pairing itself is decided here. The teeth have no command half — a predicate is judgment, not a stamp, which is the agent's whole territory.
- **The deferred operation family is named now** ([COR-016](COR-016-scripted-scenario-storyboards.md)): `amend` (state/transition evolution under live subjects, with the version-bump discipline), plus block-kind additions to existing definitions — wait, invariant, subprocess embedding, cascade fold, open region. The dispatcher reserves the names; each is built on a real case.
- **An interpretation-only health-check variant is an implementation implication** — the authoring layer's completion signal is "no indeterminates", which the shipped health surface reports but does not expose separately. Whatever the invocation shape (a flag, a contract-scoped run — the authoring flow touches one contract, `health` walks all), the implementation **consumes the health surface's walker** per [COR-042](COR-042-process-health.md) point 5's design-once rule — never a parallel contract-walker — and never changes that record's exit contract.
- **The agent's edit-authority mechanics land as an architecture record at implementation** (per [COR-025](COR-025-adr-decision-space.md)): expressing constrained edit authority over adopter capability subtrees core cannot enumerate rides [COR-013](COR-013-agent-architecture.md)'s overlay mechanism, including the collision rule against capability-shipped agents' authority over their own subtrees.
- **The authoring smells become questions.** [COR-042](COR-042-process-health.md)'s two documented smells are enforced conversationally at authoring time — the `hand-off` walkthrough refuses to complete without the author answering for trigger stability and candidate-source honesty.
- **Neutrality is testable:** both bodies must pass the substitution test (swap in a non-development domain; nothing breaks) at review time, and the storyboard/walkthrough examples stay illustrations, never the subject.
- **Three rulings are called out for explicit sign-off at acceptance** (the COR-038/COR-042 enumeration precedent): **(i)** the first producing agent at core — a permanent expansion of what the core agent surface may be; **(ii)** the owner-scoping authority model as the boundary — any future cross-owner actor is priced at supersession weight; **(iii)** the composer rejection (Decision point 5), likewise at supersession weight. Accepting this record is the gesture that prices future reversal of each.
- **Implementation work is filed and built only after this record is accepted** (the acceptance gate); acceptance is also the recorded answer to the adopter request that prompted the record.
