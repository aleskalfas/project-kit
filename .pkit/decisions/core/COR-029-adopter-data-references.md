## Context

[COR-019](COR-019-schema-reference-form.md) fixed the typed-token reference form `[<namespace>:<id>]` and a resolver that confirms each id exists in the namespace owner's id collection — reading that collection from the namespace-declaring schema's own YAML, in sibling-file scope. [COR-023](COR-023-schema-binds-inline.md) then added the *adopter-data* layer: an adopter data file binds to a capability schema (a `pkit_schema:` field, or a `binds_to:` path-glob fallback the schema declares), and `pkit data validate` checks that file's shape against the bound schema.

Combining the two produces a relationship neither validates: adopter data that carries cross-file references. A token in one bound file points at an entry in a *sibling bound file* — e.g. a `[transport:<id>]` token in a trip's aggregator file referencing an entry in that trip's transport file. `pkit data validate` checks shape only; COR-019's resolver walks capability `schemas/` directories, not adopter trees. So a dangling reference passes silently — the precise failure referential-integrity validation exists to catch.

Two facts shape the fix. First, a capability schema that *describes* adopter data holds none of the adopter's entries — they live in the adopter tree (that is what `binds_to:` is for). Its own YAML holds no more than examples: entries of its collection, or, for a *document schema*, one whose file is itself one resource, one example document (point 6). None of them joins an adopter's pool. So a reference must not resolve into the schema's own YAML but into the bound data instance. Second, adopter data freely carries *other* bracketed tokens that are **not** references — in prose fields, free-text values, or comments — so a resolver that treated every `[x:y]`-shaped string as a reference would misread them. And adopter data is often split one resource to a file, each file holding its own id and no collection, so its namespace has no collection for a resolver to read.

## Decision

**In adopter data, a typed reference resolves *through the binding to the bound instance*, not into the namespace-declaring schema's own YAML. Resolution runs only at fields the citing schema marks reference-bearing; it locates the namespace's id pool as the **union of files bound to that namespace's schema within the validation scope** (the subtree `pkit data validate` is run on), reading each through the annotation that makes its schema the namespace's owner, and checks the id against that pool.** `pkit data validate` performs this as a default-on pass (`--shape-only` skips it). A schema whose file is itself one resource may own a namespace too, through the id each such file holds (point 6).

### 1. Position-gate annotation

A field that holds references is marked on the citing schema's companion with `x-pkit-reference-namespace: "<namespace>"` — a value-position annotation mirroring the existing key-position `x-pkit-keys-from-namespace` ([COR-019]). The resolver inspects **only** annotated fields. It is a *position-gate*, not a namespace-source: the namespace is already in the token; the annotation declares that this position holds references at all.

### 2. Resolution target is the bound instance

The token's namespace resolves to its schema (by stem, as the existing resolver does); the id is then sought in the adopter file *bound to that schema*, following its companion's `x-pkit-id-collection`, or a document schema's `x-pkit-entry-id` (point 6) — not in the schema's own YAML. This refines COR-019's resolution target for the adopter-data case; see Rationale.

### 3. Resolution scope is the validated subtree

A namespace's id pool is the **union of every file bound to that namespace under the directory `pkit data validate` is run on**. A token resolves iff its id is in that pool. Isolation is by *what you validate*: a narrower target is a stricter universe (validate one instance's subtree and only its data is in scope); a wider target deliberately unions more (validate a parent and a shared file under it serves every instance below). Resolution is not positional — moving a file within the scope does not change what resolves — and there is no shadowing: the pool is a union, so two files defining the **same id** in one scope is a surfaced **duplicate-id error**, never a silent pick.

### 4. Failure surface

A dangling id at an annotated position (the namespace has a pool in scope but the id is absent from it) is a **hard error** — non-zero exit, same severity as a shape violation. A **duplicate id** across bound files in scope is also a hard error (the pool is ambiguous). "No file bound to the namespace anywhere in scope" is a **distinct, softer** outcome: incremental authoring routinely references a not-yet-created sibling. (`--strict` escalation of the soft case is deferred until a need appears.)

### 6. A document schema may own a namespace

A *document schema* describes a file that is itself one resource, not a collection of them. Such a schema may own a namespace, each bound document then being one entry of it. Its companion declares `x-pkit-entry-id`, a JSON Pointer to the field that holds the document's id, in place of `x-pkit-id-collection`, and never both. Each bound document adds its one id to its namespace's pool. Every reader of a namespace's ids reads it so, the capability side included, where the schema's own YAML is its one document: for a schema that describes adopter data, an example whose id the capability's other examples may cite.

- **The pool's rules hold** (points 3 and 4).
- **The id is held, never derived.** It is read from the field the pointer names, not from the file's path or name, since resolution is not positional (point 3). A document in which the companion's pointer reaches no string is an error.
- **A copy repeats its id.** Each document being an entry, a copy of one within the scope, such as a fixture, a template or an archived folder, holds the same id, a duplicate-id error. Whoever copies a document gives the copy an id of its own, or keeps it outside the scope.
- **The soft outcome is judged for each namespace.** A reference into a document namespace with no document in scope is point 4's softer outcome. Once a document of it exists in scope, a reference to one not yet created is a dangling id, as is an entry not yet written in an existing collection file.

### 5. Scope of this decision

Value-position references in adopter data, and which schemas may own a namespace, on both sides (point 6). Two extensions are **deferred** to successor decisions, each pending a real consumer: (a) **cross-scope shared reference roots** — letting a shared catalog serve many instances *without* unioning the instances into one validation scope (a declared search-path entry), wanted only once a real shared-data layout exists; and (b) foreign-keyed **mapping keys** (a document schema exporting a sub-collection so another file's keys validate against it).

## Rationale

**Why "through the binding" refines COR-019 rather than contradicting it.** COR-019's rule — *resolve into the namespace owner's collection* — stays true. What changes is *where that collection lives*. Capability-side, a namespace's entries sit in the namespace-declaring schema's own YAML, so COR-019 read them there. For an adopter-data namespace the entries sit in the bound instance, and the schema's own YAML holds none of them. COR-019 predated COR-023's adopter-data layer, so it never had to distinguish the two locations. This record adds that distinction — *locate the collection by following the binding* — and a second kind of namespace owner, the document schema (point 6), which both sides read. A document namespace's collection is the set of its documents, so COR-019's rule, resolve into the namespace owner's collection, holds, and nothing about the token form changes. COR-019 is cited, not amended.

**Why a position-gate annotation instead of walking all values.** Adopter data carries bracketed tokens that are *not* references — in prose fields, free-text values, or comments. A resolver that scanned every string for `[x:y]` would either error on those (false positives on legitimate, non-reference tokens) or silently ignore any namespace it doesn't recognise — which also silently ignores a *typo'd* real namespace, gutting the check. Marking the reference-bearing field removes the dilemma: the resolver looks only where the schema author declared references, so an incidental token in a free-text field is structurally out of scope, and a malformed token at a *declared* position is unambiguously an error. Key-position references already require this declaration (`x-pkit-keys-from-namespace`); the value-position annotation is its symmetric counterpart.

**Why the validated subtree is the scope.** Two positional rules were considered and rejected. *Same-directory only* forbids the layouts adopter data naturally takes — domain detail in subfolders, references between peer domains, a shared catalog — forcing everything flat or duplicated. *Nearest-ancestor* (resolve against the nearest bound file found walking up) looks more flexible but fails the same layouts: a `_shared/` catalog is a *sibling*, not an ancestor, so it is never seen; subfolder detail is *below* the citing file, never reached by an upward walk; peer domains are siblings; and "nearest wins" *fully shadows* farther files, so adding a partial local file silently breaks references to shared entries. Resolving against the whole validated subtree avoids all of these — subfolders, peer domains, and any shared file under the scope are all in the pool — and it removes positional fragility (moving a file within the scope changes nothing) and shadowing (the pool is a union; a duplicate id is surfaced, never silently picked). Isolation moves from *directory position* to *what you validate*: a per-instance run is a strict universe; a wider run deliberately unions (a shared file under the parent then serves every instance below). That matches how an author already reasons — point the validator at the data set you mean — and makes debug-switching a matter of which subtree you validate, not a schema edit. The spec stays location-agnostic; no path is baked into a schema.

**Why the soft "no bound instance" case.** Capability schema sets are authored complete, so a missing sibling there is a bug (hard error). Adopter data is authored incrementally, so a reference into a namespace with no bound file yet is a normal in-progress state, not a defect — distinct and softer. A dangling id (the namespace has entries in scope, this id is not among them) is wrong regardless, so it stays a hard error. In a document namespace that holds the id's own document not yet created, since once the namespace has documents, a reference to one not yet written cannot be told from a typo.

**Why a document schema may own a namespace.** Point 3 already unions many files into one namespace, so how finely data is split into files is the data's own choice, and a file that is one resource is its limiting case. Without a way to name that document's id, such a namespace has no ids at all, so every reference into it fails, though nothing about the references is wrong. Declaring a pointer for this purpose, instead of reading a document from any collection pointer that reaches a single value, keeps a collection pointer aimed at the wrong field an error. And a schema owns a namespace only where it declares one, so no document joins a pool, with its duplicate check, until its capability has designed ids that hold across the scope.

**Why value-position now and mapping-keys later.** The value-position case has a live consumer, and the cost of the gap is *silent referential corruption* rather than visible friction — which warrants closing it at first occurrence rather than waiting for painful recurrence. The mapping-key case has no live consumer yet; its annotation vocabulary (how a document schema exports a keyable sub-collection) should be chosen against a real second use, not guessed ([COR-007](COR-007-pattern-extraction.md)).

### Alternatives considered

- **Resolve into the namespace schema's own YAML** (COR-019's capability-side behaviour, applied unchanged to adopter data). Rejected — that YAML holds none of the adopter's entries, so every reference would dangle.
- **Walk all string values for tokens.** Rejected — collides with non-reference bracketed tokens in prose (evidence citations), and the only escape (ignore unrecognised namespaces) silently swallows typos in real ones. The position-gate annotation is the fix.
- **Same-directory-only scope.** Rejected — forbids subfolders, peer-domain references, and shared catalogs; forces flat or duplicated data. It is the special case of scope-subtree where the instance happens to be flat.
- **Nearest-ancestor (resolve up the tree, nearest file wins).** Rejected — a sibling `_shared/` catalog is never an ancestor (unreachable), subfolder detail is below the citing file (an upward walk never reaches it), peer domains are siblings, and nearest-wins fully shadows farther files (a partial local file silently breaks shared references). Scope-subtree handles all of these and removes the positional fragility.
- **A repo-wide / global resolution pool.** Rejected — isolation should be the author's scope choice, not an unbounded pool. The scope is exactly the validated subtree; validate narrower for stricter isolation.
- **Build the mapping-key (foreign-key) case now.** Rejected as speculative — deferred until a real consumer fixes the vocabulary (COR-007).
- **Read a document from a collection pointer that reaches a single value.** Rejected — a collection pointer aimed at the wrong field would then pass, silently, as a collection of one.
- **Ownership by convention: a document schema whose companion requires an `id` field owns a namespace.** Rejected — every such schema would join a pool and its duplicate check without its capability choosing to.
- **Derive a document's id from its file's path.** Rejected — resolution is not positional (point 3), so moving or renaming a file would change what resolves.
- **A one-element list or mapping in each document.** Rejected — it shapes the data for the resolver, and every other reader then finds the document's content one level down.
- **Each capability with such data resolves its own references.** Rejected — the capability side would still refuse a token that names a namespace no schema owns, and each such capability would write the same resolver again.

## Implications

- **New companion annotation `x-pkit-reference-namespace`** (value-position), documented alongside `x-pkit-keys-from-namespace` (key-position) in the schemas reference. A capability whose adopter data carries references marks the citing field; the referenced namespace's schema declares the annotation that makes it the namespace's owner, `x-pkit-id-collection` or, for a document schema, `x-pkit-entry-id` (point 6), and (for binding) `binds_to:`.
- **`pkit data validate` gains a default-on reference-resolution pass**, `--shape-only` to skip (mirroring `pkit schemas validate`). It operates on parsed data values, never raw file text, so comment-borne tokens are out of scope by construction as well as by the position-gate.
- **Validation-tightening, not a migration.** A previously-green adopter tree containing a dangling reference turns red on upgrade — an adopter-observable behaviour change → a surface change that bumps the backbone version and earns a release note ([PRJ-002](../project/PRJ-002-version-bump-policy.md)). It is **not** a [COR-010](COR-010-resource-lifecycle.md) migration: the trigger list (file rename/removal in kit-owned trees, `schema_version` bump, breaking CLI signature, capability subtree restructure) does not include tightening a validator.
- **Scope is value-position references in adopter data, and which schemas may own a namespace** (point 5). Foreign-keyed mapping-key validation is explicitly out of scope here and tracked for a successor decision.
- **The `x-pkit-entry-id` annotation,** documented beside `x-pkit-id-collection` in the schemas reference. One reading of a companion's namespace annotations serves every reader of a namespace's ids, so no reader sees one form and misses the other. A companion that declares both is an error of the schemas check.
- **The authoring commands treat a document namespace as holding no collection.** The command that adds an entry to a namespace refuses it, and the one that renames an entry renames its example document's id and the tokens that cite it. The stamp gains no option for it until a second capability stamps one ([COR-007](COR-007-pattern-extraction.md)); the schema skill says how to declare the annotation.
- **No migration for the annotation.** No schema declares it until a capability adopts it, so nothing that passes validation stops passing ([COR-010](COR-010-resource-lifecycle.md)). An adopter can use it, so it is a surface change, and the backbone's version moves under the project's bump policy. A capability that declares it on a schema its adopters already bind tightens their validation, a surface change of that capability and not a migration, as above.
- **Build sanction on acceptance.** Accepting this record sanctions: the `x-pkit-reference-namespace` annotation and its companion/`$defs` support; the binding-aware scope-subtree resolution pass in `pkit data validate` (the id pool is the union of bound files under the validated target, reusing the existing id-collection machinery for the id-check tail); duplicate-id detection; the hard/soft failure split; tests; the schemas-reference update; a backbone version bump with a release note; and the `x-pkit-entry-id` annotation, read through one reading by every reader of a namespace's ids on both sides, and its handling in the authoring commands and the schema skill (point 6).
