## Context

A document describing a system is true only *against* something: the code it explains, a decision it applies, a source it quotes, or another description it builds on. When that something changes and the description does not, the description goes stale. Nobody notices until a reader is misled. People forget to update what depends on what they changed.

Reviews do not catch this reliably. A review looks at the change in front of it, and the stale description is usually somewhere else. What catches it is a recorded link from the description to what makes it true, plus a check that fires when the target of that link changes and the description is not revalidated.

Several parts of a project need this: descriptions of what the system must do, the project's documentation, and the checks that ask whether a change needs documentation work. They are served by different components that must not depend on one another, so the mechanism has to be shared.

## Decision

**Any artefact may declare its anchors (what makes it true) and when it was last revalidated against them. The backbone reports *friction* whenever an anchor has changed since that revalidation. The answer to friction lives in the artefact itself — never in a pull-request description.**

Five terms recur. The **revalidation point** of an artefact is the commit where it first carried the parsed value of its `at` field, or each such commit where lines of work carried it first apart (point 3). The **deferral point** of a deferral entry is the commit that first introduced that entry (point 4). An artefact's **content** is its body text, compared textually, and its own front-matter fields, compared parsed — excluding everything in the methodology's container (point 5). What an anchor **stands on** is, for a path, the files it matches (point 7 says which the excluded paths leave in); for a record, the record's file; for another artefact, that artefact's content; for a registered kind, the files its resolver names (point 2). **The diff** of a pull request is the set of paths changed between its up-to-date base and its head, and the parsed before-and-after of every artefact in a declared place.

### What an artefact carries

1. **Artefacts.** An artefact is either a document with front matter, or one keyed entry in a collection file whose front matter maps entries by id. Each artefact carries its own anchors and its own revalidation. A collection entry's content is its data entry together with the body section headed by its id, if there is one, so that editing an entry's prose is a change to it. The backbone looks for artefacts only in the **places declared to hold anchored artefacts**, so unrelated front matter elsewhere is never misread. Components declare their places in their own package metadata, relative to the document locations they resolve under COR-049; a project declares its own in the backbone configuration. A component may also declare, in the same way, folders of **held documents**: files that belong to it but are not artefacts, such as a log of reviews it has carried out. Such files often sit inside a place another component or the project declares, where they would otherwise be read as unanchored artefacts. The backbone lists each held document with the component that declares it, and no place reads one as an artefact — its own and the rule-set folders included — so neither measure (point 8) counts it. Excluded paths (point 7) reach held documents too: the listing marks one under an excluded path, and its component counts it no more than the measures count an excluded artefact. A held folder lies within one of the component's declared locations and never equals or encloses a documentation root or another declaration's place.

   Everything this record owns in an artefact sits in **one functionality block, named `friction`**, inside the methodology's front-matter container (refinement per COR-053, point 10). For a document the container is in its front matter; for a collection entry it is inside the entry, so each entry carries its own block. The artefact's own fields — its id, status, whatever defines it — stay outside the container and belong to the component that defines the artefact. The functionality's key is the same word as its command group, so a reader sees one name in the file, in the command and in the configuration (the one-name-per-functionality rule of COR-053). The keys this record names are decided here because people write them; layout and casing beyond them belong to the schema the backbone ships. An artefact with nothing to anchor to may carry, instead of anchors, `unanchored-because: <reason>` in its block — written on a person's decision, accepted before it is written (point 3) — saying why it has none, such as a person's part in the work that no code carries out.

2. **Anchors.** An artefact lists its anchors in its block, grouped by kind. The backbone resolves three kinds:
   - a **path**: a file or glob, relative to the repository root, where `**` matches across folders;
   - an identified **record**, such as a decision;
   - **another artefact**, by its id.

   Capabilities may register further kinds, each with a resolver: a command registered in the capability's package metadata. A resolver takes the anchor value as its one subject, as COR-052 point 6 fixes for the commands the backbone queries. It answers with the files the anchor stands on in the state it is asked about: every file whose content decides what the value denotes. A resolver answers within a bounded time, which the backbone enforces. It needs no network, changes nothing in the project, and gives the same output for the same inputs: these are the resolver's obligations, which its capability declares on the command. The backbone requires the declaration before it runs the command and reports a missing one at validation; nothing in this contract holds a running command to them, so they are a declared and trusted contract, not a boundary, and a project that needs a boundary confines the commands where it runs them. Changing nothing in the project means the files the project owns and tracks: what a command, or the tooling that runs it, caches for itself is no change to the project. The limits exist so that a check gives the same answer wherever and whenever it runs and never hangs; they are not a confinement of code the project does not trust. A resolver fails closed: if it exits abnormally, times out, or returns output the backbone cannot read, it has given no answer — which is never an answer naming nothing — and the anchor is reported as having no answer, never as resolved; an artefact that carries one is not judged: the checks say so, never report it current, and the tool-written status records nothing for it (point 10). An artefact without anchors is *unanchored*: a state the backbone reports, not an error.

   The block's fields are owned by this record. Their shape, for single documents and for collection entries, is fixed by a schema the backbone ships and validation applies strictly — a revalidation marked `unchanged` without its justification, or an empty revalidation, fails there. The friction check never skips an artefact it cannot parse. In a declared place, an unparsable or malformed block is a validation finding (point 12); the checks report it too, so it is never silent.

3. **The revalidation.** An artefact records its last revalidation in a `revalidated` block, **written on a person's decision** — by hand, or through the revalidate and defer commands, as the bullet on a person's decision sets out — and never by the after-merge job of point 10:
   - **`at`** — a UTC timestamp, the marker. The timestamp is for people; the **revalidation point** is the commit where the artefact first carried the parsed value of `at` it carries — no commit it descends from carried it. Its history for this is its file's, renames followed, back to where the file, or the entry in it, was last added. What the artefact's anchors stood on at the revalidation point is what that revalidation answered. A commit that writes back a value the artefact carried before — as the revert of a revalidation does — is not a revalidation, and the value keeps its point. Where commits that do not descend from one another each first carried the value — a revalidation copied onto another line of work, say — each is a revalidation point, and an anchor has changed only where it differs from what it stood on at every one of them. Wherever this record measures from the revalidation point, an artefact with several is measured from each. Which came first is read from the history, never from the timestamps. Reformatting, reordering or moving the front matter is not a revalidation. `at` changes on every revalidation. An artefact with no `at` has as its revalidation point the commit that first introduced its block. Because rename detection is a guess that can hide earlier changes behind a later point, **moving an artefact** — renaming its file, or moving an entry between collection files — **requires a revalidation in the same change**.
   - **`outcome`** — `updated` (the content changed with the revalidation) or `unchanged` (the content did not need to change). With `unchanged`, **`unchanged-because`** is required and must itself change in the same diff: the sentence saying why the content still holds against *this* change. It is the one piece of judgment the tool cannot supply, and the only safeguard against a blind marker bump.
   - The outcome is a record of what happened, checked against the diff at the time (point 5); it is never read to compute staleness, which is always recomputed from git.
   - When two lines of work both revalidate the same artefact and conflict, the person resolving the conflict **revalidates the combined state**. This is a rule for people that the check cannot verify; there is no automatic merge, because one would claim a revalidation that never happened.
   - **A person's decision.** An answer is a person's decision when that person was shown it — the artefact, the outcome, and the justification or the deferral's reason, word for word — and accepted it. Acceptance comes before the answer is written, with one exception. An agent making a change may write first the answers the change check asks of that change (point 6), and the revalidation of a combined state it owes after resolving a conflict. Those become a person's decision when the person who authorises the change's merge into the default branch — or, where work is committed there directly, the person the agent works for, before the commit — is shown every answer the change wrote, word for word, and then authorises it. What they are shown is the change check's list of those answers (point 12), never an account the agent composed. An authorisation covers the answers shown and nothing written or reworded after it; one given before the list was shown accepts none of them. Every other answer an agent writes, on an artefact its change was not asked about, and every reason for having no anchors (point 1), is written only after a person was shown it and accepted it. The check verifies none of this: it reads the artefact, whoever wrote it, and cannot tell whether a list was shown or read.

4. **Deferrals.** Inside `revalidated`, a **`deferred`** list holds one entry per anchor whose friction is deliberately postponed: the anchor, written as its kind and value, and a reason.
   - An entry defers the friction of one anchor as the anchor stood at its **deferral point**, the commit that first introduced the entry; rewording the reason does not move it. Where the anchor has changed since — what it stands on differs from what it stood on there (point 5) — that is new friction. An entry a commit puts back, with an anchor and a reason the artefact carried before — as reverting a revalidation that dropped it does — is not introduced there: it keeps the deferral point of the entry it puts back. An entry whose deferral point a revalidation point reaches — one kept through a revalidation — answers no friction, since that revalidation answered what it postponed; it stays listed as deferred debt (point 9) until removed.
   - Only the reason is stored; the entry's origin — author, date, change — comes from git. Entries are kept sorted by anchor, so parallel branches deferring different anchors merge cleanly.
   - Adding a deferral does not change `at`: it is not a revalidation. An artefact never yet revalidated may carry `deferred` without `at`.
   - A revalidation **re-states the deferrals it keeps**: the block is rewritten, and an entry the person keeps is kept deliberately and keeps its deferral point. The check warns about kept entries so that keeping them is a conscious act, not a habit. Removing an entry without revalidating brings that anchor's friction back. Removing an anchor removes its entry; a dangling entry, one naming no anchor of the artefact, is a validation error. Removing the artefact (point 6) removes its entries. Deferrals never expire on their own; their age is shown.

### What the checks compute

5. **When an anchor has changed, and what answers it.** An anchor has changed when what it stands on differs between two states: the change check compares the base with the head — or, for an artefact whose `at` the pull request writes back, that value's revalidation point with the head (point 6) — the whole-repository check the revalidation point with the latest commit. An edit undone before the later state is no change, however many commits made and undid it. A file the excluded paths took from an anchor stands, in the later state, as it was when they took it (point 7).
   - **A path anchor** has changed when a file it matches differs — in content or mode, or added or removed; a change to the excluded paths that moves files in or out of it counts too (point 7).
   - **A record anchor** has changed when the record's file differs, followed across a rename.
   - **An anchor of a registered kind** has changed when a file its resolver names for it differs. A resolver is asked about one state, the later one, so the files are those it names there: one that has left its answer since the earlier state is not followed, since what the anchor stood on there is not known.
   - **An artefact anchor** has changed when that artefact's **content** changed — its body, or its own fields, but nothing inside the methodology's container, whichever functionality's block it is. An upstream correction is exactly what dependants must see; another functionality's bookkeeping is not.
   - **Cycles** between artefacts are errors, because a cycle has no order in which they could be revalidated.
   - **Three answers**, judged from the diff and, for whether an `at` is new, the artefact's history (point 6), clear friction: the artefact's content changed and `at` changed to a new value (*updated*); only `at` changed to a new value, with a new `unchanged-because` (*unchanged*); or a deferral covers the anchor (*deferred*, point 4). A new `at` with none of these behind it, or an `outcome` the diff contradicts, is reported as a bump with nothing behind it. An `at` written back to a value the artefact carried before is not new and answers nothing (point 3); point 6 says how such an artefact is judged.

6. **Friction, in two checks.**
   - **The change check** works on the diff: every artefact with an anchor that changed in the pull request must carry one of the three answers in the same pull request. An artefact anchored to another artefact is included when that artefact's content changed in the pull request. The cascade continues only where a revalidation itself changes content. An artefact new in the pull request counts as revalidated, whatever `at` it carries — one restored after its removal included. An artefact whose `at` the pull request writes back (point 3) is judged against that value's revalidation point instead of the base: it owes an answer for every anchor that differs between that point and the head, and only a deferral that covers the anchor (point 4) answers it. To tell a written-back value from a new one, and to find where a deferral was first introduced, the check reads that artefact's file history behind the base. Changing an artefact's own anchor list also requires a revalidation, because the artefact now claims different grounds. **Removing** an artefact — deleting it, or moving it out of the declared places — turns its dependants' anchors dead (point 7); what a component's own status values mean for an artefact that stays in place is the component's decision.
   - **The whole-repository check** checks every artefact, at the latest commit, against its revalidation point with the rule in point 5.
   - Either runs locally on demand. The change check's default base is the project's default branch, resolved as every reader resolves it; a base named for one run replaces it for that run only (refinement per COR-054). A pull-request result depends on the base it is compared against, so **friction results are valid only against an up-to-date base**: the check reports, as far as the repository it runs in can tell, when the base has moved on, and a project that enforces friction requires branches to be up to date, or merges through a queue that re-runs the check on the merge it is about to make.

   Clearing friction means revalidating. *How* to revalidate belongs to the component that owns the artefact. A pull-request description may *render* the artefacts' answers — a work-tracking component may build its own documentation-impact section from them — but the check reads the artefacts, never the description, so it works for a pull request from any tool, with no description at all, and locally.

7. **Dead anchors, excluded paths and over-broad anchors.** Dead anchors are errors, never silence: a path that matches nothing (or only excluded paths), an identifier that does not resolve, or a value its kind's resolver names no file for, is an error. When no installed component resolves a kind, or a kind's resolver gives no answer (point 2), each is reported separately from an identifier that does not resolve. Dead anchors are reported by both checks and by validation. Excluded paths, such as generated or vendored code, are ignored for anchoring and for the measures in point 8. An artefact under one is never asked for an answer, but its own anchors are still checked. Changing the excluded paths is itself a change to every path anchor whose files it moves in or out: narrowing them gives an anchor files it was never checked against, which it answers like any other change; widening them takes files from an anchor, which it answers when those files changed after its revalidation point while it stood on them, and is otherwise only reported. For this, each commit compared — the change check's base and head, an artefact's revalidation point and the latest commit — is read under the excluded paths set at that commit, and a changed file counts for an anchor only where both leave it in. Exclusions cover paths, so a record or artefact anchor is untouched by them, and so is an anchor of a registered kind, which names what it stands on by its value as a record anchor does. An anchor left matching only excluded paths is dead, reported with the exclusion as the reason; an artefact a narrowing brings back in is revalidated in that change, as a moved one is (point 3). An anchor broad enough to match most changes is warned about, because it would make every change a revalidation and teach people to update markers blindly.

### What is reported, and what fails

8. **Two measures, not failures.**
   - **Unanchored artefacts**, within the declared places. An artefact whose block gives a reason for having none (point 1) is listed apart, with its reason, and not counted; the count is of those without one.
   - **Uncovered surface:** paths within the *declared surface* that no artefact anchors to. The declared surface is what a component (in its package metadata) or the project (in the backbone configuration) says ought to be described.

   Both are reported and neither fails a check. Friction alone reads zero where nothing is anchored yet; these two measures show what remains.

9. **Debt is derived from git, never kept in a ledger.** *Deferred* debt originates at the deferral point; *stale* debt originates in the oldest commit from which a part of what the anchor stands on — one of its files, or, for an anchor to another artefact, that artefact's content — has differed, without returning, from what it was at the point it is measured from: the revalidation point, or a deferral point the revalidation point does not reach. A debt listing shows both with their author, date and change, oldest first. Deriving them walks each artefact's history back to where it was last added (point 3), since only there is it known where the value it carries was first carried.

10. **A tool-written status, on separate lines.** The block may carry a **`last-check`** sub-block that only the after-merge job writes: the state found — `current`, `stale` or `deferred`, where stale wins over deferred — the commit it was checked against, and where any staleness came from. It exists so that the debt is visible in the file and in git history, dated with its commit so it is never read as "true now". It is never read for friction — the check always recomputes. It is named for what it is rather than *status*, which is the defining component's own lifecycle field. It is written only when it changes, by a job the project runs after merges to its default branch, through one small reviewed change kept open and updated in place — or, where the project reviews nothing, a direct commit; that change passes the change check because the sub-block is inside the container and so is not content. The change check itself writes nothing, so branches see neither churn nor conflicts. Tool-written and people-written data sit on different lines, so they rarely conflict. The project configures when the job runs, including never.

11. **Truth-chain order.** Friction is reported upstream first, following the anchors between artefacts, so that what others depend on is revalidated first.

12. **Warning or enforcing, and who owns which finding.** The checks are read-only.
    - **The change check finds:** friction of the pull request, dead anchors of the pull request, a bump with nothing behind it, an anchor of the pull request whose kind no installed component resolves, an anchor whose resolver gave no answer, and an outdated base. In **warning mode** it reports them and passes. In **enforcing mode** it fails on the first five; an outdated base is reported, never failed, since the fix is to update the branch and run again. A resolver that gives no answer leaves the check unable to tell whether the pull request changed the anchor, so the check fails closed and says that a second run may clear it.
    - **Whose a dead anchor is.** A dead anchor is the pull request's when the check can lay it there: the pull request added it, or, for a kind the backbone resolves, removed what it resolved to. A resolver is asked about the head alone (point 5), so of an anchor of a registered kind that the pull request did not add, the check can tell only whether the pull request took its kind's resolver away; one that resolves to nothing at the head for any other reason is reported and not failed, as a dead anchor that was already there is the whole-repository check's.
    - **Reported only, in every mode:** the two measures, over-broad anchors, kept deferrals and their age, the answers the change wrote, each with its words (point 3), the whole-repository check's findings — it does not fail other work on friction that was already there.
    - **Validation owns:** a malformed block, an `unanchored-because` beside anchors, a friction block in a held document, a dangling deferral, a cycle between artefacts, an invalid mode value, a settings path outside the repository. These fail validation wherever the project runs it, in either mode, because the project can fix them.

    The check only becomes binding when the project makes it a required status in its continuous integration. That is the project's choice. An invalid mode value is a validation error, so enforcement is never switched off silently.

### Commands and settings

13. **Commands.** Everything this functionality does is reached through one command group named for it. Reading commands — the two checks, the debt listing, an explanation of one artefact's friction — never write. Writing is always a separate, explicit command that names what it writes: revalidate, defer, record the status. No writing happens as a side effect of checking — one operation per command, as the command-line design rules require (COR-004).

14. **Project settings.** This record owns one key in the backbone configuration (COR-048), named for the functionality. It holds the friction mode (default: warning), when the status job runs (default: never), the project's own anchored places, its declared surface, and its excluded paths (all default: none). It holds no folders of held documents (point 1): a component needs them because its files may sit inside places it did not declare and cannot narrow, in a configuration it does not write, while the project declares its own places and can narrow them, and keeps what must not count out of the measures with its excluded paths — an excluded file is still an artefact, read, and its anchors checked, only neither counted nor asked for an answer (point 7). The key is written by the project's own edits, or by backbone configuration commands under COR-048's consent rule. Validation checks that every path in it stays inside the repository. A place, the project's or a component's, is also never a synced tree — one the methodology's sync writes into the project, where every refresh would otherwise show up as friction in the project's own history; in the repository where the methodology itself is authored those trees are source, not copies, and may be places ([living-docs:DEC-001-living-docs-discipline] point 1).

15. **Dormant until used.** Where no artefact declares anchors, the check finds nothing and demands nothing.

## Rationale

**Why declared anchors, not inferred ones.** Inferring what a description is about, from filenames or text similarity, is guesswork that fails silently in both directions. A declared anchor is a claim someone made and can be checked. Where declarations are missing, the unanchored measure says so honestly.

**Why a timestamp whose point comes from git.** A commit identifier cannot be written into the commit it identifies. It also disappears from the main history on a squash merge or rebase. A content hash of the anchored inputs conflicts on every parallel change under a glob, and nobody can read it. A timestamp is readable and changes on every revalidation, while the commit that first wrote it is exactly the point git can answer questions about.

**Why the answer lives in the artefact.** A pull-request description is one tool's format: another tool, a hand-made pull request, or a local run has none. Reading the answer from the artefact needs nothing but the repository, and it puts the justification next to the thing it justifies, where the next reader finds it. A list of the answers shown to the person accepting a change is for that person; it is never input to the check.

**Why an outcome is stored even though it is derivable.** It is a presentation layer: a reader of the file, or of its history, sees what the last revalidation found without running anything. It is not memory; staleness is always recomputed, so a wrong outcome misleads nobody about the state of the artefact. Requiring the justification to change each time is what keeps `unchanged` from becoming a rubber stamp.

**Why an agent's answer is shown to a person, and when.** The justification is the one piece of judgment the tool cannot supply, and an agent can write a fluent one that is wrong; the check cannot tell, and a person reading it can. Asking before each answer an agent writes while making a change would stop the work at every artefact and teach the person to accept unread. So those answers are shown once, together, before the merge is authorised — which is why the list is the check's own and not the agent's account of what it wrote. An answer the change does not owe is outside what the person authorising the merge reviews, and where the answer is itself the task, asking interrupts nothing; so there the person accepts before the write. A reason for having no anchors is accepted first because no change owes it: it waives a measure, which is why it is listed apart.

**Why deferrals are per anchor and are re-stated on revalidation.** A deferral is a judgment about one anchor's change; a later change to the same anchor is a new question. Several reasons coexist and merge cleanly because each has its own line. Nesting them under the revalidation says what they are — postponements of what changed since that revalidation; re-stating them makes every revalidation decide which of them it keeps in view as debt.

**Why debt comes from git, not a ledger.** A ledger duplicates what git already answers and drifts from it whenever a change bypasses the check. The tool-written status is not a ledger: it is a dated snapshot for visibility, recomputed rather than trusted.

**Why the pull-request rule is local to the pull request.** "An anchor changed here, so the answer is here" explains itself to the author at the moment the fix is cheapest. Both checks ask the same question — does what an anchor stands on differ between two states, the base and the head for the change check, the revalidation point and the latest commit for the whole-repository check — so what a change leaves unanswered is, once merged, what the whole-repository check reports.

**Where the two checks part.** The two checks part in a few cases. The change check asks more where one change edits a file and moves it out of an anchor's reach, and where an artefact already stale has an anchor put back as it last answered for it. The whole-repository check reports more where an artefact moved, or was excluded, and came back between the two states the change check compares, since rename detection is a guess (point 3); where a line of work revalidates and then changes an anchor again, and lands with its commits kept; and where a conflict is resolved by keeping the line of work's revalidation over the one the base made since they parted, rather than revalidating the combined state as point 3 requires.

**Why the revalidation point follows the parsed value.** If formatting or file moves could advance the point, friction could be cleared without anyone revalidating. The point must move only when someone deliberately revalidates — and where a move could hide history, the move itself must revalidate.

**Why a written-back `at` is not a revalidation.** Every revalidation writes a new `at`. Writing an earlier value back — reverting a revalidation, most often — puts back an answer given against an earlier state; read as a new answer, it would cover every change since that state, those the reverted revalidation had answered and those nobody had. So the value keeps the point where the artefact first carried it, and the change check judges such a change against that point: reverting a revalidation owes again what it took back, and reverting it together with the change it answered owes nothing. A deferral put back is read the same way, by its anchor and reason. Which came first is read from the history, never from the timestamps: the timestamp is for people, it may be written by hand, and two people's clocks differ. Where the history holds two first carryings of one value that do not descend from one another, each answered what the anchors stood on where it was made, so an anchor has changed only where it differs from both.

**Why a change is a difference between two states.** Which commits touched an anchor depends on how a change lands: a merge keeps them, a squash or a rebase folds them into one. Counted by commits, an edit and its revert would be debt after one landing and nothing after the other, and the change check, which compares its base with its head, could agree with neither. What a reader meets is the artefact against what its anchors hold, so that is what both checks compare; the commits only date the debt. The revalidation point is itself a commit, so where a line of work revalidates and then changes an anchor again, how it lands still decides the point.

**Why the container is not content.** The after-merge job, another functionality's block, a role's bookkeeping about the artefact: none of them changes what the artefact says. Excluding the container is what lets the job write without waking every dependant, and what keeps the change check from flagging its own bookkeeping.

**Why an artefact accepted without anchors is listed apart, not counted or hidden.** Some artefacts have nothing to anchor to, such as a person's part in the work that no code carries out. Counted as unanchored, they keep the measure from ever reaching zero, and people learn to ignore it; left out silently, they would vanish from the report, and nobody could later see how many a person had waved through, or why. Listing them apart, each with its reason, keeps both the count and the judgment in view. The reason says why there are no anchors, so beside anchors it contradicts them, and validation refuses the pair.

**Why uncovered surface is declared, not everything.** Counting every file in the repository as needing description would make the measure pure noise on day one. The measure means something only against a surface someone has said ought to be described.

**Why dead anchors are errors.** A glob that matches nothing produces no friction, for ever. Silence would look like health.

**Why each commit is read under its own exclusions.** Reading an old state under today's excluded paths would let a widening erase friction nobody answered, and a narrowing raise friction from changes nobody could have been asked about. So the change to the excluded paths is read as a change, and the two directions differ. A narrowing gives an anchor files it was never checked against, so it is always answered. A widening only takes files away: nothing the artefact describes changed unless those files did while it stood on them — then that change is answered, dated from it and never from the widening; otherwise the widening is reported, so a routine exclusion does not ask every artefact over it for a revalidation that could say nothing new. An artefact under an excluded path owes no answer because the whole-repository check never judges it stale: asking it in the change check would make a pull request owe what the history never shows as debt, and the two checks would disagree. Its own anchors are still checked, since a dead anchor is never silence, and a change to its marker is judged like any other, since a stamp made while excluded is as blind as any. An artefact a narrowing brings back in was asked nothing while it was excluded, so, like a moved artefact, it revalidates in the change that brings it in.

**Why it is core.** Three kinds of component need it: those describing what the system must do, those keeping documentation true, and those checking whether a change owes documentation work. They must not depend on one another. Core is the only home that serves all three without one depending on another or each carrying its own copy. Its consumers are known, not speculative, so the usual wait for a pattern to recur before extracting it (COR-007) is not applied here. The mechanism names no discipline, so it makes sense in any project. Its first use needs no capability at all: an architectural decision record (COR-025) can anchor the code it governs today. Where nothing is anchored, it is dormant.

### Alternatives considered

- **Anchors on every statement inside a document.** Rejected. Precise, but the maintenance cost makes people stop, which recreates the drift. Precision comes instead from whoever revalidates the flagged artefact against the actual change.
- **Anchors per section, via markers inside the prose.** Rejected. It adds a second convention, parsed out of prose.
- **Storing each artefact's current-or-stale state as truth.** Rejected. Stored state duplicates what git already answers, and it drifts from git whenever a change bypasses the check. The tool-written status is a dated snapshot, not truth.
- **A commit identifier or a content hash as the marker.** Rejected; see Rationale.
- **Reading the answer from the pull-request description.** Rejected; see Rationale.
- **A bare marker change as an answer.** Rejected: it is indistinguishable from a blind bump; the justification, changed each time, is the answer.
- **A confirmation for each answer an agent writes while making a change.** Rejected. A stream of confirmations is accepted unread; the answers are shown together before the merge is authorised.
- **An agent's answer that no person is shown.** Rejected. A wrong justification then reaches the default branch's history unread, and the check cannot tell it from a right one.
- **A debt ledger, in one file or one file per entry.** Rejected. It duplicates git and drifts.
- **Recording stale debt as synthetic deferral entries.** Rejected. Deferral is deliberate postponement; stale debt is shown by the tool-written status instead, so the two are never confused.
- **Keeping either timestamp on a conflicting revalidation, the merge becoming the new point.** Rejected in favour of revalidating the combined state; the merge would claim a revalidation nobody made.
- **Organising the block per anchor, or splitting it strictly by writer.** Rejected. The first puts the tool and people on the same lines; the second adds a level that carries no meaning.
- **One copy per component.** Rejected. Separate engines drift apart, and the components would disagree about what is stale.
- **Excluding the artefact's path instead.** Rejected. Exclusion is per file, so it cannot waive one entry of a collection, and it keeps no reason beside the artefact.
- **The backbone holding each command to its obligations — keeping it off the network, stopping its writes.** Rejected. No backbone can hold a single command to them on every platform a project runs on, and a limit stated as enforced and not kept misleads more than an obligation stated as trusted.
- **An anchor changed whenever a commit after the point touched it.** Rejected; see Rationale. An edit and its revert would be debt or nothing according to how the change landed.
- **Telling a written-back `at` by its time being earlier than the one it replaces.** Rejected. A revalidation written by hand with an earlier-looking time would read as none, every revert of a revalidation would be stopped whether or not it brought debt back, and where two lines of work meet, whose clock ran ahead would decide.
- **A change check that reads no history.** Rejected. It cannot tell a written-back `at` from a new one, so it would pass the revert of a revalidation that brings back debt nobody answered, which the whole-repository check reports once the change merges.

## Implications

- **The backbone ships the friction checks** — the change check and the whole-repository check, each runnable locally — reading the blocks in the declared places. Its output includes a machine-readable form, so that other components can consume friction, uncovered surface and the artefacts' answers. For a change, that form lists every answer the change wrote, each with its words: the list that, under point 3, the person who authorises its merge is shown.
- **The backbone ships the schema** for the block, for single documents and collection entries. It is a surface change adopters can see, and existing documents are unaffected.
- **The backbone ships the writing commands** for revalidating, deferring and recording the status, and the after-merge status job a project may wire in.
- **Components that keep anchored artefacts** declare their places and surface, and any folders of held documents, in their own package metadata. They register their own anchor kinds and resolvers, and define how their artefacts are revalidated — including how their own revalidation vocabulary maps onto the two outcomes here. They may also decide what to do when a revalidation finds that the description was right and the change was wrong. A work-tracking component may render the artefacts' answers into its pull-request format, reading the machine-readable output for that; one through which a person accepts a change may show point 3's list there. A rendering answers nothing: an artefact's answer is on the artefact, and no check of this record reads the rendering.
- **Continuous integration** needs each artefact's history back to where it was last added (point 3) for the whole-repository check and the debt listing, since only there is it known where a value was first carried. The change check needs the diff, an up-to-date base and, for an artefact whose `at` or deferrals the change alters, that artefact's file history behind the base. In a clone whose history is cut short, a value first carried after the cut is read as first carried there and the checks say so; a value the file already carried where the history is cut has a point the checks cannot reach. Either check runs the resolver of each registered kind it meets, which reaches no network (point 2), so whatever a resolver needs is in place before the check runs.
- **The backbone configuration** gains the key from point 14.
- **The status report** can show friction, unanchored artefacts and uncovered surface.
