> **Partially superseded by [COR-062](COR-062-answers-in-own-files.md).** A change writes its answers in new files of its own, which it only adds, and never in the artefact. Overturned: that the answer lives in the artefact, where points 3, 4 and 16 put answers, and their rules on conflicts. Also overturned: that whoever merges two revalidations judges their combined state. That becomes debt, reported until a revalidation reads both. And point 4's "reaches" is read through what a revalidation read. Among what stands: anchors and what they stand on, the three answers and who decides them, and deferrals per anchor. So do the revalidation point read from git, both checks, and that no answer is read from a pull-request description. COR-062's "What this overturns, and what stands" lists each passage.

## Context

A document describing a system is true only *against* something: the code it explains, a decision it applies, a source it quotes, or another description it builds on. When that something changes and the description does not, the description goes stale. Nobody notices until a reader is misled. People forget to update what depends on what they changed.

Reviews do not catch this reliably. A review looks at the change in front of it, and the stale description is usually somewhere else. What catches it is a recorded link from the description to what makes it true, plus a check that fires when the target of that link changes and the description is not revalidated.

Several parts of a project need this: descriptions of what the system must do, the project's documentation, and the checks that ask whether a change needs documentation work. They are served by different components that must not depend on one another, so the mechanism has to be shared.

A link also matters the other way for some artefacts. A requirement links to the test that verifies it. When the requirement's threshold changes, the test may stop checking it, and nothing says so: a recorded link flags only the artefact that carries it.

## Decision

**Any artefact may declare its anchors (what makes it true) and when it was last revalidated against them. The backbone reports *friction* whenever an anchor has changed since that revalidation. The answer to friction lives in the artefact itself — never in a pull-request description.**

A component may also declare that a change to chosen fields of an artefact asks for a revisit of what the artefact links to. The change then edits each such target, or records on the artefact why the target still stands or which follow-up will revisit it (point 16).

Five terms recur. The **revalidation point** of an artefact is the commit where it first carried the parsed value of its `at` field, or each such commit where lines of work carried it first apart (point 3). The **deferral point** of a deferral entry is the commit that first introduced that entry (point 4). An artefact's **content** is its body text, compared textually, and its own front-matter fields, compared parsed — excluding everything in the methodology's container (point 5). What an anchor **stands on** is:
- for a path, the files it matches, each by its content and its mode (point 7 says which the excluded paths leave in)
- for a record, the record's content, or what one of its points stands on, where the anchor names that point (point 5)
- for another artefact, that artefact's content, or what one of its sections or its lead stands on, where the anchor names it (point 5)
- for a registered kind, the files its resolver names, each by its content and its mode (point 2)

A record's content is read as an artefact's is, whether or not a place holds the record. Nothing in the methodology's container (COR-053 point 10) counts. Where the record has no front matter that parses to a mapping at a state, its content there is its whole file.

A file's content, for a path anchor or an anchor of a registered kind, depends on whether a place holds the file. A place holds a file at a state where that state's places read it, held documents (point 1) and synced copies (point 14) aside. Each state's places are read from that state, as its excluded paths are (point 7).
- **Where a place holds the file at one or both of the states compared,** its content is read as an artefact's is: its body as text and its front matter's fields compared parsed. Nothing counts in a container where the records let one sit, whatever artefacts the file holds. That is the front matter's own, a collection entry's, or a rule's in a rule set (COR-051 point 2). Such a file with no front matter has its body and no fields. Where its front matter does not parse to a mapping, its content is its whole file.
- **Where a place holds it at neither state,** the file is compared as stored.

**The diff** of a pull request is the set of paths changed between its up-to-date base and its head, and the parsed before-and-after of every artefact in a declared place. For each record a record anchor names, and each file a place holds that a path anchor or an anchor of a registered kind stands on, it holds the text at the base and at the head too.

### What an artefact carries

#### 1. Artefacts

An artefact is either a document with front matter, or one keyed entry in a collection file whose front matter maps entries by id. Each artefact carries its own anchors and its own revalidation. A collection entry's content is its data entry together with the body section headed by its id, if there is one, so that editing an entry's prose is a change to it. The backbone looks for artefacts only in the **places declared to hold anchored artefacts**, so unrelated front matter elsewhere is never misread. Components declare their places in their own package metadata, relative to the document locations they resolve under COR-049; a project declares its own in the backbone configuration. A place may also name a **type** for the artefacts it holds, a declared name for what they are (refinement per COR-056). Friction never reads a type. A component may also declare, in the same way, folders of **held documents**: files that belong to it but are not artefacts, such as a log of reviews it has carried out. Such files often sit inside a place another component or the project declares, where they would otherwise be read as unanchored artefacts. The backbone lists each held document with the component that declares it, and no place reads one as an artefact — its own and the rule-set folders included — so neither measure (point 8) counts it. Excluded paths (point 7) reach held documents too: the listing marks one under an excluded path, and its component counts it no more than the measures count an excluded artefact. A held folder lies within one of the component's declared locations and never equals or encloses a documentation root or another declaration's place. A component's place may also declare links (point 16).

Everything this record owns in an artefact sits in **one functionality block, named `friction`**, inside the methodology's front-matter container (refinement per COR-053, point 10). For a document the container is in its front matter; for a collection entry it is inside the entry, so each entry carries its own block. The artefact's own fields — its id, status, whatever defines it — stay outside the container and belong to the component that defines the artefact. The functionality's key is the same word as its command group, so a reader sees one name in the file, in the command and in the configuration (the one-name-per-functionality rule of COR-053). The keys this record names are decided here because people write them; layout and casing beyond them belong to the schema the backbone ships. An artefact with nothing to anchor to may carry, instead of anchors, `unanchored-because: <reason>` in its block — written on a person's decision, accepted before it is written (point 3) — saying why it has none, such as a person's part in the work that no code carries out.

#### 2. Anchors

An artefact lists its anchors in its block, grouped by kind. The backbone resolves three kinds:
- a **path**: a file or glob, relative to the repository root, where `**` matches across folders;
- an identified **record**, such as a decision, or one **point** of it, named by the record's id, `#` and the point's id, as in `COR-058#4`;
- **another artefact**, by its id, or one **section** or the **lead** of an artefact that is a document. A section is named as the artefact is, then `#` and its heading's slug, as in `docs/guide.md#installing`. The lead is named as the artefact is, then a bare `#`, as in `docs/guide.md#`.

A document's sections and its lead are read from its body's headings outside fenced code:
- **A section** runs from its heading to the next heading of the same or a higher level.
- **A heading's slug** is its title, the text after its `#`s, in lower case. Every character but letters, digits, spaces and hyphens is dropped, and each space is made a hyphen.
- **An empty slug names no section.** A heading whose slug is empty, such as one made only of symbols, gives no name an anchor can use. So a section's name never meets the lead's.
- **The lead** is the body before its first heading, not counting a first-level heading that opens it. Such a title is part of the lead's text.

A record's point, and a document's section or lead, are **parts**: what `#` names in a record or artefact anchor's value. An anchor that names a part is a **part anchor**. One that names a record or an artefact whole is a **whole anchor**.

An artefact anchor's value splits at its last `#`. A value that names an artefact whole, `#` included, is read whole, so a `#` in an artefact's own name never reads as a part. A path anchor, and an anchor of a registered kind, name no part: a `#` in their value belongs to the value.

Some part anchors are refused, each with its reason (point 7):
- **a section or the lead of a collection file**, whose entries are artefacts, each named by its id. The refusal names the entry to use, where there is one. That is the entry whose id follows the `#`, or whose section holds the heading with the slug.
- **a section or the lead of a collection entry**, which is cited whole, by its id. An extension point a rule offers (COR-051 point 3), such as `RS-CMN-003#cause-location`, reads as such a section, so it is refused too.
- **a section or the lead of an artefact whose file a record anchor names**, such as a decision record a place holds. A record's parts are its points (COR-058 point 1), and a record anchor names them. The refusal names the record anchor to use. That is the point whose id follows the `#`, or whose heading has the slug, where the record holds one. Otherwise it is the whole record.

An anchor on a section or the lead of the artefact that carries it is a cycle, as is a record's anchor on itself or on one of its own points (point 5).

Capabilities may register further kinds, each with a resolver: a command registered in the capability's package metadata. A resolver takes the anchor value as its one subject, as COR-052 point 6 fixes for the commands the backbone queries. It answers with the files the anchor stands on in the state it is asked about: every file whose content decides what the value denotes. A resolver answers within a bounded time, which the backbone enforces. It needs no network, changes nothing in the project, and gives the same output for the same inputs: these are the resolver's obligations, which its capability declares on the command. The backbone requires the declaration before it runs the command and reports a missing one at validation; nothing in this contract holds a running command to them, so they are a declared and trusted contract, not a boundary, and a project that needs a boundary confines the commands where it runs them. Changing nothing in the project means the files the project owns and tracks: what a command, or the tooling that runs it, caches for itself is no change to the project. The limits exist so that a check gives the same answer wherever and whenever it runs and never hangs; they are not a confinement of code the project does not trust. A resolver fails closed: if it exits abnormally, times out, or returns output the backbone cannot read, it has given no answer — which is never an answer naming nothing — and the anchor is reported as having no answer, never as resolved; an artefact that carries one is not judged: the checks say so, never report it current, and the tool-written status records nothing for it (point 10). An artefact without anchors is *unanchored*: a state the backbone reports, not an error.

The block's fields are owned by this record. Their shape, for single documents and for collection entries, is fixed by a schema the backbone ships and validation applies strictly — a revalidation marked `unchanged` without its justification, or an empty revalidation, fails there. The friction check never skips an artefact it cannot parse. In a declared place, an unparsable or malformed block is a validation finding (point 12); the checks report it too, so it is never silent.

#### 3. The revalidation

An artefact records its last revalidation in a `revalidated` block, **written on a person's decision, or by an agent making a change and checked by a reviewer** — by hand, or through the revalidate and defer commands, as the bullet on who decides an answer sets out — and never by the after-merge job of point 10:
- **`at`** — a UTC timestamp, the marker. The timestamp is for people; the **revalidation point** is the commit where the artefact first carried the parsed value of `at` it carries — no commit it descends from carried it. Its history for this is its file's, renames followed, back to where the file, or the entry in it, was last added. What the artefact's anchors stood on at the revalidation point is what that revalidation answered. A commit that writes back a value the artefact carried before — as the revert of a revalidation does — is not a revalidation, and the value keeps its point. Where commits that do not descend from one another each first carried the value — a revalidation copied onto another line of work, say — each is a revalidation point, and an anchor has changed only where it differs from what it stood on at every one of them. Wherever this record measures from the revalidation point, an artefact with several is measured from each. Which came first is read from the history, never from the timestamps. Reformatting, reordering or moving the front matter is not a revalidation. `at` changes on every revalidation. An artefact with no `at` has as its revalidation point the commit that first introduced its block. Because rename detection is a guess that can hide earlier changes behind a later point, **moving an artefact** — renaming its file, or moving an entry between collection files — **requires a revalidation in the same change**.
- **`outcome`** — `updated` (the content changed with the revalidation) or `unchanged` (the content did not need to change). With `unchanged`, **`unchanged-because`** is required and must itself change in the same diff: the sentence saying why the content still holds against *this* change. It is the one piece of judgment the tool cannot supply, and the only safeguard against a blind marker bump.
- The outcome is a record of what happened, checked against the diff at the time (point 5); it is never read to compute staleness, which is always recomputed from git.
- When two lines of work both revalidate the same artefact and conflict, the person resolving the conflict **revalidates the combined state**. This is a rule for people that the check cannot verify; there is no automatic merge, because one would claim a revalidation that never happened.
- **Who decides an answer.** An answer an agent writes for its own change is checked by a reviewer other than that agent, and every other answer is a person's decision. An agent making a change may write, without asking first, the answers the change check asks of that change (points 6 and 16), and the revalidation of a combined state it owes after resolving a conflict. A reviewer other than that agent checks every `unchanged` and `deferred` reason among them against the change, and blocks the merge when one does not hold. The reviewer also checks each target the change revisited by changing it (point 16). On an artefact the change was asked about, the reviewer checks each deferral the change writes or rewords, and not one the change keeps as it was, which the reviewer of the change that wrote it was to check. The reviewer works from the change check's list of the answers (point 12), never from an account the agent composed. A deferral, or a `deferred` revisit entry (point 16), among them holds only if its reason names an open follow-up, one not closed. For each artefact the change revalidated as `updated`, the change's author says what changed in it, in one sentence, with the change, where the reviewer and the person who authorises the merge read it. The reviewer checks each sentence against the diff, and blocks the merge when an `updated` artefact has no sentence or its sentence does not match what changed. The person who authorises the change's merge into the default branch is told those sentences, and which artefacts are left out of date until which follow-up. They are also told which targets of a link are left out of date, until which follow-up (point 16). This is information, not a gate: a change with answers merges under the same authorisation as any other. Where work is committed to the default branch directly, the reviewer checks before the commit and blocks it as it would the merge. The person the agent works for is told before the commit. Which reviewer checks the answers is the project's choice. Two cases leave the agent's answers unchecked by any reviewer: a person skipped the review on record, or the project chose no such reviewer. That limit is accepted: the skip is a person's recorded choice, and choosing no reviewer is the project's. A person decides an answer an agent writes on an artefact its change was not asked about, and every reason for having no anchors (point 1). A person's decision is one the person was shown — the artefact, the outcome, and the justification or the reason, word for word — and accepted before it was written. The check verifies none of this: it reads the artefact, whoever wrote it, and cannot tell whether a reviewer or a person read it.

#### 4. Deferrals

Inside `revalidated`, a **`deferred`** list holds one entry per anchor whose friction is deliberately postponed: the anchor, written as its kind and value, and a reason.
- An entry defers the friction of one anchor as the anchor stood at its **deferral point**, the commit that first introduced the entry; rewording the reason does not move it. Where the anchor has changed since — what it stands on differs from what it stood on there (point 5) — that is new friction. An entry a commit puts back, with an anchor and a reason the artefact carried before — as reverting a revalidation that dropped it does — is not introduced there: it keeps the deferral point of the entry it puts back. An entry whose deferral point a revalidation point reaches — one kept through a revalidation — answers no friction, since that revalidation answered what it postponed; it stays listed as deferred debt (point 9) until removed.
- Only the reason is stored; the entry's origin — author, date, change — comes from git. Entries are kept sorted by anchor, so parallel branches deferring different anchors merge cleanly.
- Adding a deferral does not change `at`: it is not a revalidation. An artefact never yet revalidated may carry `deferred` without `at`.
- A revalidation **re-states the deferrals it keeps**: the block is rewritten, and an entry it keeps is kept deliberately and keeps its deferral point. The check warns about kept entries so that keeping them is a conscious act, not a habit. Removing an entry without revalidating brings that anchor's friction back. Removing an anchor removes its entry; a dangling entry, one naming no anchor of the artefact, is a validation error. Removing the artefact (point 6) removes its entries. Deferrals never expire on their own; their age is shown.

### What the checks compute

#### 5. When an anchor has changed, and what answers it

An anchor has changed when what it stands on differs between two states: the change check compares the base with the head — or, for an artefact whose `at` the pull request writes back, that value's revalidation point with the head (point 6) — the whole-repository check the revalidation point with the latest commit. An edit undone before the later state is no change, however many commits made and undid it. A file the excluded paths took from an anchor stands, in the later state, as it was when they took it (point 7).
- **A path anchor** has changed when a file it matches differs — in content or mode, or added or removed; a change to the excluded paths that moves files in or out of it counts too (point 7). A write to the container alone of a file a place holds, such as a revalidation of an artefact in it, changes nothing a path anchor stands on.
- **A record anchor** has changed when the record's content differs, followed across a rename. A point of a record is a part of its Decision headed by the point's id (COR-058 point 1). An anchor that names one follows the record across a rename too. It has changed only when what the point stands on differs. A point binds only as part of its record, so it stands on its section, and on what says whether and how the record binds:
  - the point's section: its heading and its text
  - the record's `status`, `supersedes`, `superseded_by` and `title` fields
  - the record's preamble, the body's text before its first section, and a section headed `Summary`, where it has one
  - the Decision's text outside every point and every stub of a retired point (point 7)

  Other changes to the record change nothing the point stands on. Such are changes to another point, a stub or the rest of the front matter, or to the Context, the Rationale or the Implications. That holds unless the change decides whether the record holds the point, as retiring it does. A point keeps its id wherever it sits in its record, so a move changes nothing either. A point the record does not hold at a state stands on nothing there. So does a retired point, at every state where its id is retired, whatever its stub says.
- **An anchor of a registered kind** has changed when a file its resolver names for it differs in content or mode, read as a path anchor's file is. A resolver is asked about one state, the later one, so the files are those it names there: one that has left its answer since the earlier state is not followed, since what the anchor stood on there is not known.
- **An artefact anchor** has changed when that artefact's **content** changed — its body, or its own fields, but nothing inside the methodology's container, whichever functionality's block it is. An upstream correction is exactly what dependants must see; another functionality's bookkeeping is not. An anchor that names a section or the lead of the artefact (point 2) has changed only when what that part stands on differs:
  - the part's text: a section's heading and its text, or the lead's text
  - the artefact's own fields, outside the container, as for its whole content

  A change elsewhere in the body changes nothing the part stands on. A section keeps its slug wherever it sits in its document, so a move that keeps its text changes nothing either. A section the artefact does not hold at a state stands on nothing there. So does a refused anchor (point 2), at a state where it is refused.
- **Cycles** between artefacts are errors, because a cycle has no order in which they could be revalidated. For cycles and the order of point 11, an artefact or record anchor counts as one on the whole artefact it names:
  - an anchor on a section or the lead of an artefact counts as one on that artefact
  - a record anchor, whole or on a point, counts as one on the record, where the record's file is an artefact (point 1)

  So an anchor on a section or the lead of its own artefact is a cycle, as an anchor on the artefact itself is. So is a record's anchor on itself or on one of its own points. A path anchor and an anchor of a registered kind name files, so neither is followed.
- **Three answers**, judged from the diff and, for whether an `at` is new, the artefact's history (point 6), clear friction: the artefact's content changed and `at` changed to a new value (*updated*); only `at` changed to a new value, with a new `unchanged-because` (*unchanged*); or a deferral covers the anchor (*deferred*, point 4). A new `at` with none of these behind it, or an `outcome` the diff contradicts, is reported as a bump with nothing behind it. An `at` written back to a value the artefact carried before is not new and answers nothing (point 3); point 6 says how such an artefact is judged.

#### 6. Friction, in two checks

- **The change check** works on the diff: every artefact with an anchor that changed in the pull request must carry one of the three answers in the same pull request. An artefact anchored to another artefact is included when what it anchors in that artefact changed in the pull request. That is the artefact's content, or, for an anchor on a section or the lead, what that part stands on. The cascade continues only where a revalidation itself changes content, whatever the kind of the anchors that reach the artefact's file. For a record anchor, the check reads the record at the base and at the head. It compares the record's content, or what the anchor's point stands on (point 5). An artefact new in the pull request counts as revalidated, whatever `at` it carries — one restored after its removal included. An artefact whose `at` the pull request writes back (point 3) is judged against that value's revalidation point instead of the base: it owes an answer for every anchor that differs between that point and the head, and only a deferral that covers the anchor (point 4) answers it. To tell a written-back value from a new one, and to find where a deferral was first introduced, the check reads that artefact's file history behind the base. Changing an artefact's own anchor list also requires a revalidation, because the artefact now claims different grounds. **Removing** an artefact — deleting it, or moving it out of the declared places — turns its dependants' anchors dead (point 7); what a component's own status values mean for an artefact that stays in place is the component's decision.
- **The whole-repository check** checks every artefact, at the latest commit, against its revalidation point with the rule in point 5.
- Either runs locally on demand. The change check's default base is the project's default branch, resolved as every reader resolves it; a base named for one run replaces it for that run only (refinement per COR-054). A pull-request result depends on the base it is compared against, so **friction results are valid only against an up-to-date base**: the check reports, as far as the repository it runs in can tell, when the base has moved on, and a project that enforces friction requires branches to be up to date, or merges through a queue that re-runs the check on the merge it is about to make. On such a merge, the check judges what each answer read against the change's own head. It does so on any merge of the change with its base that a host builds, too (refinement per COR-062).

Clearing friction means revalidating. *How* to revalidate belongs to the component that owns the artefact. A pull-request description may *render* the artefacts' answers — a work-tracking component may build its own documentation-impact section from them — but the check reads the artefacts, never the description, so it works for a pull request from any tool, with no description at all, and locally.

#### 16. A link may ask for a revisit of its targets when its source changes

An anchor flags the artefact that carries it when what it names changes. A component may declare that some anchors work the other way too. When chosen fields of the artefact change, the change asks for a revisit of what those anchors name.

- **A link, declared by a component on its place.** A component may declare a **link** on a place in its package metadata, for the artefacts the place holds. A link names two things:
  - the own fields that choose the link's **targets**, anchors of the artefact, in one of two ways.
    - **One field lists them.**
    - **One or more fields list those that stay out.** The targets are every anchor of the artefact but those that the named fields list.

    A field lists anchors, each by its value, written as the anchor writes it. A value names every anchor of the artefact that has it. A field the artefact does not write, or one that is no list of anchor values, lists nothing.
  - the **trigger fields**: the artefact's own fields whose change asks for a revisit of the targets.

  The artefact is the link's **source**. No link asks for a revisit unless a place declares it, so none does by default. A source takes the links of every place a component declares that matches its file at the head. A project declares no link on its own places.
- **What triggers it.** A link is triggered when one of its trigger fields differs between the base and the head, compared parsed. A field absent at one state and present at the other differs. Some sources trigger nothing:
  - a source new in the change, whose links were made against the new state. A source moved in a way rename detection cannot follow reads as new too (point 3).
  - a source the change removes, which has nothing left to record on
  - a source under an excluded path at the head, which owes no answer (point 7)

  A source is compared with itself across a move, so a move alone triggers nothing.
- **Which targets owe an answer.** Each target that a triggered link takes at the base and at the head, and that resolves at the head. A target the change adds to the link was linked against the new state, so it owes nothing. A dead target, or one whose resolver gives no answer, is a finding of its own already (points 7 and 12).
- **Two answers.** A target that owes an answer is revisited when one of these holds:
  - **It changed:** what it stands on differs between the base and the head, by the rule in point 5.
  - **The source records why:** an entry in the `revisited` list of the source's block names the target, by its kind and value, with an outcome and a reason. `unchanged` says why the target still stands. `deferred` leaves the target out of date, and its reason names an open follow-up that will revisit it (point 3). An entry answers only where the change wrote its reason: the reason differs from the base's for that target.

  A target that owes an answer and has neither is a finding of the change check (point 12).
- **The entries.** The list holds one entry per target, kept sorted by anchor, so parallel branches merge cleanly. One entry answers for a target whatever links take it. An entry stays until a later change rewrites it, so a later trigger needs a new reason.
  - **No revalidation.** An entry changes no content, moves no revalidation point and flags no dependant.
  - **Conflicts.** Two lines of work may each write the entry of one target, and conflict. Whoever resolves the conflict writes it again for the combined state, as point 3 asks of a revalidation.
- **What validation finds.** Where the source's places declare a link, validation fails:
  - an entry that names no target of those links
  - a second entry for one target
  - a link's field that is no list of anchor values
  - a value that no anchor of the source has, in a field that lists a link's targets

  Where they declare none, as after the component that declared it is uninstalled, the entries are reported and kept, never failed.
- **Who decides.** A target answered by its change is listed among the change's answers (point 12). The reviewer of point 3 checks that its change meets the change to the source. An entry for a target that owes an answer is an answer the change check asks of the change (point 3). A person decides any other entry an agent writes.
- **Only the change check asks for a revisit.** Whether a link was triggered is a fact about one change, as a bump is. The whole-repository check, the debt listing and the tool-written status (point 10) never read an entry.

#### 7. Dead anchors, excluded paths and over-broad anchors

Dead anchors are errors, never silence: a path that matches nothing (or only excluded paths), an identifier that does not resolve, or a value its kind's resolver names no file for, is an error. When no installed component resolves a kind, or a kind's resolver gives no answer (point 2), each is reported separately from an identifier that does not resolve. Dead anchors are reported by both checks, and validation fails those point 12 gives it. Excluded paths, such as generated or vendored code, are ignored for anchoring and for the measures in point 8. An artefact under one is never asked for an answer, but its own anchors are still checked. Changing the excluded paths is itself a change to every path anchor whose files it moves in or out: narrowing them gives an anchor files it was never checked against, which it answers like any other change; widening them takes files from an anchor, which it answers when what it stood on in those files changed after its revalidation point while it stood on them, and is otherwise only reported. For this, each commit compared — the change check's base and head, an artefact's revalidation point and the latest commit — is read under the excluded paths set at that commit, and a changed file counts for an anchor only where both leave it in. Exclusions cover paths, so a record or artefact anchor is untouched by them, and so is an anchor of a registered kind, which names what it stands on by its value as a record anchor does. An anchor left matching only excluded paths is dead, reported with the exclusion as the reason; an artefact a narrowing brings back in is revalidated in that change, as a moved one is (point 3). An anchor broad enough to match most changes is warned about, because it would make every change a revalidation and teach people to update markers blindly.

An anchor on a record's point is dead when the record holds no live point with that id. A point the record retires is the exception. Its id stays in the record's front matter, with the points that took its text, and a one-line stub stands where it was (COR-058 point 4). An anchor on a retired point stands on nothing (point 5). It is no dead anchor, since the record says where the point went. Validation warns of it until it is re-pointed, naming the retired point's successors. A record whose points are not yet headings holds no point an anchor can name, since their numbers are not permanent (COR-058 point 9). An anchor on an id that two live points of the record share is **ambiguous**, an error reported wherever a dead anchor is.

An anchor on a document's section is dead when no heading of the document has its slug. Unlike a point, a section has no permanent name, so a renamed heading is no move. It leaves the anchors on its section dead, since the section is gone under its old slug. An anchor on a slug that two headings of the document share is ambiguous, as one on a shared point id is. An anchor on the lead is dead only where an anchor on the whole artefact would be.

A refused anchor (point 2) is an error too, with its reason, reported wherever a dead anchor is.

### What is reported, and what fails

#### 8. Two measures, not failures

- **Unanchored artefacts**, within the declared places. An artefact whose block gives a reason for having none (point 1) is listed apart, with its reason, and not counted; the count is of those without one.
- **Uncovered surface:** paths within the *declared surface* that no artefact anchors to. The declared surface is what a component (in its package metadata) or the project (in the backbone configuration) says ought to be described.

Both are reported and neither fails a check. Friction alone reads zero where nothing is anchored yet; these two measures show what remains.

#### 9. Debt is derived from git, never kept in a ledger

*Deferred* debt originates at the deferral point. *Stale* debt originates in the oldest commit from which some of what the anchor stands on — the content or mode of one of its files, or the content of the record or the artefact it names — has differed, without returning, from what it was at the point it is measured from: the revalidation point, or a deferral point the revalidation point does not reach. For an anchor on one of a record's points, what the anchor stands on is what the point stands on (point 5). For an anchor on an artefact's section or lead, it is what the section or the lead stands on. Debt *answered apart* is two revalidations of one artefact, made without either reading the other. It originates in the first commit that holds both (refinement per COR-062). A debt listing shows each with its author, date and change, oldest first. Deriving them walks each artefact's history back to where it was last added (point 3), since only there is it known where the value it carries was first carried.

#### 10. A tool-written status, on separate lines

The block may carry a **`last-check`** sub-block that only the after-merge job writes: the state found — `current`, `stale` or `deferred`, where stale wins over deferred — the commit it was checked against, and where any staleness came from. It exists so that the debt is visible in the file and in git history, dated with its commit so it is never read as "true now". It is never read for friction — the check always recomputes. It is named for what it is rather than *status*, which is the defining component's own lifecycle field. It is written only when it changes, by a job the project runs after merges to its default branch, through one small reviewed change kept open and updated in place — or, where the project reviews nothing, a direct commit; that change passes the change check because the sub-block is inside the artefact's container, on which no anchor of any kind stands (point 5). The change check itself writes nothing, so branches see neither churn nor conflicts. Tool-written and people-written data sit on different lines, so they rarely conflict. The project configures when the job runs, including never.

#### 11. Truth-chain order

Friction is reported upstream first, following the anchors between artefacts, so that what others depend on is revalidated first. An anchor on an artefact's section or lead is followed as one on the whole artefact. A record anchor, whole or on a point, is followed as one on the record, where the record's file is an artefact (point 5).

#### 12. Warning or enforcing, and who owns which finding

The checks are read-only.
- **The change check finds:**
  - friction of the pull request
  - dead, ambiguous or refused anchors of the pull request
  - a bump with nothing behind it
  - an anchor of the pull request whose kind no installed component resolves
  - an anchor whose resolver gave no answer
  - a target of a triggered link that the change neither changed nor answered (point 16)
  - an outdated base

  In **warning mode** it reports them and passes. In **enforcing mode** it fails on the first six. An outdated base is reported, never failed, since the fix is to update the branch and run again. A resolver that gives no answer leaves the check unable to tell whether the pull request changed the anchor, so the check fails closed and says that a second run may clear it.
- **Whose a dead, ambiguous or refused anchor is.** A dead anchor is the pull request's when the check can lay it there: the pull request added it, or, for a kind the backbone resolves, removed what it resolved to. Renaming the heading of a section an anchor names removes what the anchor resolved to. A resolver is asked about the head alone (point 5), so of an anchor of a registered kind that the pull request did not add, the check can tell only whether the pull request took its kind's resolver away; one that resolves to nothing at the head for any other reason is reported and not failed, as a dead anchor that was already there is the whole-repository check's. An ambiguous anchor (point 7) is the pull request's when the pull request made it so. A pull request makes one so by adding the anchor, a point with the anchor's id, or a heading with its slug. A refused anchor is the pull request's when the pull request added it. It is also the pull request's when the pull request made what it names a record, a collection file or a collection entry. Otherwise each is the whole-repository check's, as a dead anchor that was already there is.
- **Reported only, in every mode:**
  - the two measures
  - over-broad anchors
  - kept deferrals and their age
  - the answers the change wrote, each with its words (point 3)
  - the targets the change revisited by changing them (point 16)
  - the whole-repository check's findings, since that check does not fail other work on friction that was already there
- **Validation owns:**
  - a malformed block
  - an `unanchored-because` beside anchors
  - a friction block in a held document
  - a dangling deferral
  - a revisit entry that names no target of a declared link, or repeats one (point 16)
  - a link's field that is no list of anchor values (point 16)
  - a value no anchor of its source has, in a field that lists a link's targets (point 16)
  - a cycle between artefacts
  - a part anchor that is dead, ambiguous or refused
  - an invalid mode value
  - a settings path outside the repository

  These fail validation wherever the project runs it, in either mode, because the project can fix them. Validation also warns of an anchor on a retired point (point 7). It reports revisit entries on a source whose places declare no link (point 16).

The check only becomes binding when the project makes it a required status in its continuous integration. That is the project's choice. An invalid mode value is a validation error, so enforcement is never switched off silently.

### Commands and settings

#### 13. Commands

Everything this functionality does is reached through one command group named for it. Reading commands — the two checks, the debt listing, an explanation of one artefact's friction — never write. For an anchor on a record's point, or on an artefact's section or lead, the explanation shows what changed in what that part stands on. It shows nothing else of the record or the artefact, so the answerer reads only what changed under the dependant. Writing is always a separate, explicit command that names what it writes: revalidate, defer, revisit, record the status. No writing happens as a side effect of checking — one operation per command, as the command-line design rules require (COR-004).

#### 14. Project settings

This record owns one key in the backbone configuration (COR-048), named for the functionality. It holds the friction mode (default: warning), when the status job runs (default: never), the project's own anchored places, its declared surface, and its excluded paths (all default: none). Each of the project's places may name a type (refinement per COR-056). It holds no folders of held documents (point 1): a component needs them because its files may sit inside places it did not declare and cannot narrow, in a configuration it does not write, while the project declares its own places and can narrow them, and keeps what must not count out of the measures with its excluded paths — an excluded file is still an artefact, read, and its anchors checked, only neither counted nor asked for an answer (point 7). The key is written by the project's own edits, or by backbone configuration commands under COR-048's consent rule. Two more writes touch only the types on the project's places, each with the consent COR-048 asks (refinement per COR-056). Uninstalling a component may take its types off them. A component's upgrade migration may rename one of its types there. Validation checks that every path in it stays inside the repository.

A place, the project's or a component's, is also never a synced tree. Sync writes such a tree into the project, from the methodology or from the external source a component is pinned to (COR-041). Were it a place, every refresh would show up as friction in the project's own history. A tree is source, not a copy, in the repository where it is authored, as the methodology's trees are where the methodology is authored. There it may be a place ([living-docs:DEC-001-living-docs-discipline] point 1).

#### 15. Dormant until used

Where no artefact declares anchors, the check finds nothing and demands nothing.

## Rationale

**Why declared anchors, not inferred ones.** Inferring what a description is about, from filenames or text similarity, is guesswork that fails silently in both directions. A declared anchor is a claim someone made and can be checked. Where declarations are missing, the unanchored measure says so honestly.

**Why a timestamp whose point comes from git.** A commit identifier cannot be written into the commit it identifies. It also disappears from the main history on a squash merge or rebase. A content hash of the anchored inputs conflicts on every parallel change under a glob, and nobody can read it. A timestamp is readable and changes on every revalidation, while the commit that first wrote it is exactly the point git can answer questions about.

**Why the answer lives in the artefact.** A pull-request description is one tool's format: another tool, a hand-made pull request, or a local run has none. Reading the answer from the artefact needs nothing but the repository, and it puts the justification next to the thing it justifies, where the next reader finds it. A list of the answers, and the sentences saying what changed, are for the reviewer and the person authorising the merge. Neither is input to the check.

**Why an outcome is stored even though it is derivable.** It is a presentation layer: a reader of the file, or of its history, sees what the last revalidation found without running anything. It is not memory; staleness is always recomputed, so a wrong outcome misleads nobody about the state of the artefact. Requiring the justification to change each time is what keeps `unchanged` from becoming a rubber stamp.

**Why a reviewer checks a change's answers, and the person is told what changed.** The justification is the one piece of judgment the tool cannot supply, and an agent can write a fluent one that is wrong. The check cannot tell. A reviewer other than that agent can, reading each reason beside the change it answers. Asking the person who authorises the merge to accept each answer asks them to redo that check without its context. Their acceptance adds little, and it holds every change that wrote an answer until they are back. Asking before each answer would stop the work at every artefact and teach the person to accept unread. What the person needs from a change's answers is what changed in the artefacts it updated, and which it leaves out of date until which follow-up. So they are told that, and authorise the merge as they authorise any other. The person learns what changed from each sentence on an updated artefact. A wrong sentence tells them wrong, and a missing one tells them nothing, so the reviewer blocks on either. A deferral names an open follow-up, so the person told of an artefact left out of date knows what will bring it up to date. A closed follow-up has landed or was dropped, so nothing is left for the artefact to wait on. The reviewer works from the check's own list, so no answer the change wrote escapes it. An answer the change does not owe answers no question the change raised, so the change's review is not where it is decided. Where the answer is itself the task, asking interrupts nothing. So there the person accepts before the write. A reason for having no anchors is accepted first because no change owes it: it waives a measure, which is why it is listed apart.

**Why deferrals are per anchor and are re-stated on revalidation.** A deferral is a judgment about one anchor's change; a later change to the same anchor is a new question. Several reasons coexist and merge cleanly because each has its own line. Nesting them under the revalidation says what they are — postponements of what changed since that revalidation; re-stating them makes every revalidation decide which of them it keeps in view as debt.

**Why debt comes from git, not a ledger.** A ledger duplicates what git already answers and drifts from it whenever a change bypasses the check. The tool-written status is not a ledger: it is a dated snapshot for visibility, recomputed rather than trusted. Nor are the names by which an answer says what it read. Each is honoured only where history agrees with it, so none is trusted as written (refinement per COR-062).

**Why the pull-request rule is local to the pull request.** "An anchor changed here, so the answer is here" explains itself to the author at the moment the fix is cheapest. Both checks ask the same question — does what an anchor stands on differ between two states, the base and the head for the change check, the revalidation point and the latest commit for the whole-repository check — so what a change leaves unanswered is, once merged, what the whole-repository check reports.

**Where the two checks part.** The two checks part in a few cases. The change check asks more where one change edits a file and moves it out of an anchor's reach; where an artefact already stale has an anchor put back as it last answered for it; where the line of work holding a copy of a revalidation (point 3) merges the line holding the original, bringing in the change the original answered; and where a change writes only the container of a file no place holds, and a place holds the file at the revalidation point or at the latest commit. The whole-repository check reports more where an artefact moved, or was excluded, and came back between the two states the change check compares, since rename detection is a guess (point 3); where a line of work revalidates and then changes an anchor again, and lands with its commits kept; where a conflict is resolved by keeping the line of work's revalidation over the one the base made since they parted, rather than revalidating the combined state as point 3 requires; and where a change writes only the container of a file a place holds at its base or its head, and a place holds the file at neither the revalidation point nor the latest commit. Only the change check asks for a revisit of a link's targets (point 16).

**Why a link may revisit its targets.** An anchor flags one side of a link. A changed target flags its source, and a changed source flags nothing it links to. So a requirement whose threshold is relaxed leaves the test that verifies it, and the decision that answers it, unvisited, and every check passes. A link back is no remedy. It would make a cycle (point 5), and what a target names, such as a test file, may carry no anchors at all. The question belongs to the change that alters the source, so the change check asks it.

**Why a link is declared, and never on by default.** Most anchors need no return visit. A guide anchors the code it explains and asks nothing of the code when the guide changes. Asked at every edit of a source, each target would draw a reason written blindly. The component that defines a kind of artefact knows which of its links bind both ways, so it declares them. A project's own places sit in the key point 14 owns, which holds no link, so a project declares none.

**Why own fields name the triggers and the targets.** Only what matters should trigger a link, such as a requirement's statement and its threshold, never the wording of its rationale. A field keeps its name, while a project may reword the labels and headings of a body. A field also says which anchors belong to the link. Every anchor of one kind would not. The record anchors of a requirement may hold both the decisions it rests on and those that answer it.

Fields may instead list the anchors that stay out. Where nearly every anchor of a source binds both ways, a field that lists the targets copies the anchors. An own field is content (point 5), so each anchor added or re-pointed would change the source's content and flag its dependants. Naming the few that stay out keeps the targets in the anchor list alone. The cost is that the form tells apart only the anchors its fields list. Every other anchor is a target, one added later included, whether the source rests on it or it answers the source. Still, a field can keep out any one anchor, where a kind cannot be split. A value no anchor has, in a field that lists what stays out, leaves nothing out. The check then asks more, never less, so validation does not fail it.

**Why a link is declared on a place, not on a type.** A project may give a type to its own places, and a migration may rename one (point 14). On a place, a link stays where its component declared it, so retyping a place never changes what a change owes. A link is friction's own concept. So it adds no concept to places beside friction's own and types, which would move places into a functionality of their own (COR-056 point 7). A source takes the links of every place a component declares that matches its file. So a broader place of the project's does not switch a component's link off. The cost is that an artefact in a project's place, given a component's type, takes none of that component's links.

**Why the reason lives on the source.** What a target names may be no artefact, such as a test file, or a record the project receives and cannot edit. The source is the one side that always holds a block. Its entries sit apart from `revalidated`, which says whether the source holds. An entry says whether a target holds, and a revalidation of the source does not re-state it.

**Why a reason answers only where the change rewrote it.** `unchanged-because` must change with each revalidation for the same reason (point 3). An outcome switched alone would let an old reason answer a new change.

**Why a target answered by its change is listed.** Any change to a target answers it, a reformat included. Listing it among the change's answers puts it before the reviewer, who checks that it meets the change to the source. A change that drops a target from a triggered link owes nothing for it, and the drop shows in the source's own diff.

**Why only the change check asks for a revisit.** Whether a link was triggered is a fact about one change: a field differed between two states. The whole-repository check compares each artefact with its revalidation point. To ask for a revisit, it would have to find, for each target, whether the target changed after each trigger. A target answered by its change leaves no mark. Whether a later commit counts would depend on how the change landed ("Why a change is a difference between two states" below).

The cost is that a target left unvisited is not reported again. That happens in warning mode, where the check is no required status, or where work is committed directly. A project that needs every revisit enforces the change check and makes it a required status (point 12).

**Why the revalidation point follows the parsed value.** If formatting or file moves could advance the point, friction could be cleared without anyone revalidating. The point must move only when someone deliberately revalidates — and where a move could hide history, the move itself must revalidate.

**Why a written-back `at` is not a revalidation.** Every revalidation writes a new `at`. Writing an earlier value back — reverting a revalidation, most often — puts back an answer given against an earlier state; read as a new answer, it would cover every change since that state, those the reverted revalidation had answered and those nobody had. So the value keeps the point where the artefact first carried it, and the change check judges such a change against that point: reverting a revalidation owes again what it took back, and reverting it together with the change it answered owes nothing. A deferral put back is read the same way, by its anchor and reason. Which came first is read from the history, never from the timestamps: the timestamp is for people, it may be written by hand, and two people's clocks differ. Where the history holds two first carryings of one value that do not descend from one another, each answered what the anchors stood on where it was made, so an anchor has changed only where it differs from both.

**Why a change is a difference between two states.** Which commits touched an anchor depends on how a change lands: a merge keeps them, a squash or a rebase folds them into one. Counted by commits, an edit and its revert would be debt after one landing and nothing after the other, and the change check, which compares its base with its head, could agree with neither. What a reader meets is the artefact against what its anchors hold, so that is what both checks compare; the commits only date the debt. The revalidation point is itself a commit, so where a line of work revalidates and then changes an anchor again, how it lands still decides the point.

**Why an anchor may name one point of a record.** A dependant often rests on one point of a record. Anchored to the whole record, it is flagged by every edit to the record. Its answerer then says, edit after edit, that the edit left that point alone. A point keeps its id for good (COR-058), so an anchor on it names the same point after any refinement.

The cost is a judgment. A dependant that names too few points misses a change, as a path anchor with too narrow a glob does. The whole record stays available to a dependant that rests on most of it.

**Why a point stands on more than its section.** A point binds only as part of its record. The record's status and supersession fields say whether it binds, and what it replaces or what replaces it. Its title, preamble and Summary say what the record decides. The Decision's text outside every point holds the lead and the definitions that every point refines.

A change to any of them can change what a point means without touching its text, so it reaches every point's dependants. The rest of the front matter says nothing of whether or how the record binds. Its fields name the record and who wrote it and when, keep the methodology's bookkeeping, or list the retired points. A retirement edits that list, and must flag only the retired point's dependants. A stub holds no point's text, so editing one flags no point's dependants.

**Why an anchor on a retired point stands on nothing.** Following the retired point's successors would need them read at every state, through chains of retirements, in an order among several. Standing on nothing differs from what the point stood on, so the dependant is flagged once. Re-pointing the anchor changes the anchor list, so it needs a revalidation (point 6). The record says where the point went, so the anchor is not dead. Validation names the successors until the anchor is re-pointed.

**Why an anchor may name a section of a document, or its lead.** A dependant often rests on one section of a document, or on what its lead says the document is for. Anchored to the whole document, it is flagged by every edit to it, as a dependant of a whole record is. The cost is the judgment a point anchor asks: a dependant that names too few parts misses a change.

**Why a section is named by its heading, with no permanent id.** A heading is what a reader of the document sees.
- **No marker.** A permanent id beside the heading would be a marker in the prose, which this record rejects (Alternatives considered).
- **A rename is never silent.** A renamed heading leaves a dead anchor, and the change that renamed it owns the error (point 12).
- **No sync crosses it.** A point needs a permanent id because a record anchor crosses a sync. A project anchors records it receives and cannot edit. An artefact anchor never crosses one, since a synced tree is never a place (point 14). So a section anchor names a document authored where the anchor is, and the change that renames its heading can mend the anchor. Renaming or removing a section's heading in a document the methodology or a component ships therefore needs no migration in a project that receives it (COR-010).
- **A heading a component requires.** A component may require a heading's words in a project's documents. A change that rewords such a heading leaves the anchors on it dead, and validation fails them until the project re-points them with a revalidation.

**Why the slug is the backbone's own rule.** Tools that render a heading's link differ at the edges. Some keep an underscore that this rule drops, and some number a second heading with one slug. A rule of the backbone's own reads the same wherever the checks run. The cost is that a link copied from such a tool may differ, which a dead anchor shows. Two headings with one slug make an anchor on it ambiguous, and renaming one of them mends it.

**Why the lead is named by a bare `#`.** The lead has no heading to name it by. No section is named by an empty slug, so a bare `#` never meets a section's name. A document's title is part of its lead's text. So a retitle flags the lead's dependants, and leaves their anchors alive.

**Why a section or the lead stands on its own text and its artefact's own fields.** An artefact's own fields say what it is and whether it holds, such as a status that withdraws it. A change to them can change what each section and the lead mean, so it reaches all their dependants. A document's body has no text that every section refines by rule, as the Decision's text outside every point is for a record's points. So a change elsewhere in the body reaches only the dependants of what it changed. A dependant that rests on more names more sections.

**Why cycles and truth-chain order ignore sections and leads.** An artefact is revalidated whole, so an order of revalidation is an order of whole artefacts. Two artefacts that anchor sections of each other have no such order, whichever sections they name. So an anchor on a section or the lead of its own artefact is a cycle. The artefact's own edits would flag it, and so would its own revalidation. An artefact rests on what lies outside it.

**Why cycles and truth-chain order follow a record anchor to a record that is an artefact.** A record a place holds is revalidated as any artefact is, so it takes a place in the order of revalidation. An artefact depends on it whether an artefact anchor or a record anchor names it. Read through artefact anchors alone, a cycle through a record anchor would go unseen, and the record could be reported after what rests on it. A record no place holds carries no anchors the checks read, so no cycle passes through it.

A path anchor, or one of a registered kind, names files, and may reach an artefact's file by where it sits. It declares no dependency on that artefact. Followed, a broad glob over a folder of documents would fail validation for cycles nobody declared.

**Why some part anchors are refused.** Each refused anchor names text that has a name already, or text that is no unit of its own.
- **A collection file's** entries are artefacts, each named by its id. A slug on the file would name an entry a second way, by a heading that can be renamed.
- **A collection entry** is cited whole, by its id, and an anchor names nothing finer than what people cite (Alternatives considered). An extension point names what a rule offers, not a section of its text (COR-051 point 3).
- **A record** a place holds is an artefact too. Its units are its points, and a record anchor names each point, or the record whole.
  - A slug on a point's heading would name the point a second way, by a slug that changes with the point's title. It would also stand on other ground than the point does (point 5). It would stand on all the record's own fields, and on none of its preamble, Summary or Decision text outside the point.
  - A record's other sections and its preamble are no unit the record decides by. A dependant that rests on one rests on the record whole.
  - The whole record keeps both anchors, a record anchor and an artefact anchor. Both stand on its content where its front matter parses to a mapping (point 5). Refusing either would fail anchors that projects hold.

**Why validation fails a part anchor that is dead, ambiguous or refused.** The project can always mend such an anchor.
- **The anchor** sits in an artefact in a place, the project's or a component's, never in a synced tree (point 14). So it can be mended where it is written, as every finding validation owns can (point 12).
- **A point** of a record a project receives by sync is retired, not dropped, where its authors run the numbering check (COR-058 point 8). So a sync seldom kills such an anchor.
- **A section** belongs to a document in a place too. So the change that renames its heading is the project's own, and validation fails it, whatever the friction mode.
- **A dead part anchor** fails validation whatever made it dead, its artefact gone included. Every other dead anchor is the checks' finding, which the friction mode governs (Alternatives considered).

The cost is that a heading rename which leaves an anchor dead fails validation in warning mode too. Two changes may each pass alone, one anchoring a section and the other renaming its heading. Merged, they leave the default branch failing validation until someone re-points the anchor. Up-to-date branches, or a merge queue, prevent it (point 6).

**Why the container is not content.** The after-merge job, another functionality's block, a role's bookkeeping about the artefact: none of them changes what the artefact says. Excluding the container is what lets the job write without waking every dependant, and what keeps the change check from flagging its own bookkeeping.

**Why a record anchor stands on the record's content.** A record a place holds is an artefact, so it may carry a friction block of its own. Each revalidation of the record writes that block. Were the block part of what a whole anchor stands on, a revalidation that keeps the record's content would still flag every such anchor. A point anchor does not stand on the container either, since a point stands on nothing in it.

A record is read this way whether or not a place holds it. A record a project receives by sync sits in no place there, yet may carry the block its source writes. Read by its whole file, it would flag the receiving project's anchors at each sync that brings a revalidation. Read one way in a place and another outside, a record moved across that line would flag its anchors, its text unchanged.

A record resolves by its file, so an anchor on a record with no front matter that parses to a mapping stays live. Its whole file is compared there, so the anchor is judged, never skipped.

**Why a path anchor stands on the content of a file a place holds.** Such an anchor, or one of a registered kind, may match an artefact's file. Each revalidation, deferral and status write changes that file's container. Read whole, the file would flag every such anchor at each of those writes. The anchor's artefact would answer bookkeeping, and its answer would write its own file's container, flagging the path anchors on that file in turn. The cascade would never stop where an `unchanged` revalidation stops it for an artefact or a record anchor. Read by its content, an artefact's file flags no such anchor for a write to its container alone, as it flags no artefact anchor.

What a container holds is bookkeeping about the artefact: its friction block, the status the after-merge job writes, a role's data (COR-053 point 10). No dependant rests on it, whichever kind of anchor names the file.

For a path anchor, a place decides how a file is read, not the file's shape. A path anchor names a file, not an artefact. Outside a place no validation reads a container (COR-053 point 10), so nothing there tells bookkeeping from what the file says. A record anchor differs: it names a record, read by its content wherever it sits.
- **A file no place holds** may carry a container as part of what it is, as a template carries the block it gives each artefact made from it. A dependant that anchors such a file rests on all of it, so it is compared as stored.
- **A placed file with no front matter** has its body and no fields, where a record's whole file is compared. So the change that gives a page its first front matter, holding only a container, flags nothing.
- **A file a change brings into a place, or takes out of one,** is read by its content at both states, since a place holds it at one of them. So the change that brings a file in and writes its first block, or takes it out and drops its block, flags nothing.
- **A file a project receives by sync**, a record or a component's document, sits in no place there (point 14). Each sync that brings its source's revalidation flags the path anchors on its file. The answers to that sit in places, so the cascade stops there. A dependant that rests on such a record anchors the record, which stands on its content wherever it sits.
- **Every container where the records let one sit** is left out, whatever artefacts the file holds. So adding or dropping a container at the top of a collection file changes nothing either. The cost is a mapping among a document's own fields that holds a key of the container's name. A path anchor leaves that key out, and an artefact anchor on the document counts it. A key of that name deeper still counts for both.

**Why an artefact accepted without anchors is listed apart, not counted or hidden.** Some artefacts have nothing to anchor to, such as a person's part in the work that no code carries out. Counted as unanchored, they keep the measure from ever reaching zero, and people learn to ignore it; left out silently, they would vanish from the report, and nobody could later see how many a person had waved through, or why. Listing them apart, each with its reason, keeps both the count and the judgment in view. The reason says why there are no anchors, so beside anchors it contradicts them, and validation refuses the pair.

**Why uncovered surface is declared, not everything.** Counting every file in the repository as needing description would make the measure pure noise on day one. The measure means something only against a surface someone has said ought to be described.

**Why dead anchors are errors.** A glob that matches nothing produces no friction, for ever. Silence would look like health.

**Why each commit is read under its own exclusions.** Reading an old state under today's excluded paths would let a widening erase friction nobody answered, and a narrowing raise friction from changes nobody could have been asked about. So the change to the excluded paths is read as a change, and the two directions differ. A narrowing gives an anchor files it was never checked against, so it is always answered. A widening only takes files away: nothing the artefact describes changed unless what it stood on in those files did while it stood on them — then that change is answered, dated from it and never from the widening; otherwise the widening is reported, so a routine exclusion does not ask every artefact over it for a revalidation that could say nothing new. An artefact under an excluded path owes no answer because the whole-repository check never judges it stale: asking it in the change check would make a pull request owe what the history never shows as debt, and the two checks would disagree. Its own anchors are still checked, since a dead anchor is never silence, and a change to its marker is judged like any other, since a stamp made while excluded is as blind as any. An artefact a narrowing brings back in was asked nothing while it was excluded, so, like a moved artefact, it revalidates in the change that brings it in.

**Why it is core.** Three kinds of component need it: those describing what the system must do, those keeping documentation true, and those checking whether a change owes documentation work. They must not depend on one another. Core is the only home that serves all three without one depending on another or each carrying its own copy. Its consumers are known, not speculative, so the usual wait for a pattern to recur before extracting it (COR-007) is not applied here. The mechanism names no discipline, so it makes sense in any project. Its first use needs no capability at all: an architectural decision record (COR-025) can anchor the code it governs today. Where nothing is anchored, it is dormant.

### Alternatives considered

- **Anchors on every statement inside a document.** Rejected. Precise, but the maintenance cost makes people stop, which recreates the drift. An anchor names a part people already cite, such as a record's point or a document's section, and nothing finer. Below that, precision comes from whoever revalidates the flagged artefact against the actual change.
- **A marker inside the prose naming each section.** Rejected. A marker adds a second convention, parsed out of prose. An anchor finds a section by what the document already shows. A record's point heading is no such marker. It adds no second convention: it is the form every point takes (COR-058 point 1), read under the guards COR-058 point 6 sets. An anchor finds the point's section by its id, as point 1 finds a collection entry's section. It finds a document's section by its heading's slug, and the document's lead by a bare `#`.
- **A point standing on its section alone.** Rejected. A superseded record, or a changed definition in the Decision's lead, would reach no dependant of its points.
- **A point standing on the record's whole front matter.** Rejected. A retirement edits the front matter, and would flag the dependants of every point.
- **A point standing on the whole record except its Context, Rationale and Implications.** Not taken. Any other section, such as a migration path, would flag the dependants of every point.
- **An anchor on a retired point following the point's successors, as a record anchor follows a rename.** Not taken. It spares only the warning until the anchor is re-pointed, and needs the successors read at every state, through chains of retirements.
- **The slug of a document's title as its lead's name.** Not taken. A title's section runs to the end of the document, and a retitle would kill every anchor on the lead.
- **A reserved name for the lead, such as `#lead`.** Not taken. A heading of that name would meet it.
- **A section or the lead of a record a place holds, read as the record's point,** by its heading's slug or by the point's id. Not taken. The slug follows the point's title, which a refinement may change, while the point's id is permanent. A section that is no point would have no point to be read as. Read by its id, the anchor would name one point by two kinds, on different ground (point 5). A record anchor names every point already.
- **Numbering a second heading with one slug, as some tools do.** Rejected. A heading added above would shift the numbers, and the anchor would name another section silently.
- **Cycles and truth-chain order judged between sections.** Rejected. An artefact is revalidated whole, so its sections give no order of revalidation.
- **Cycles and truth-chain order read through artefact anchors alone.** Rejected. A cycle that passes through a record anchor would go unseen, and its members have no order of revalidation.
- **Cycles and truth-chain order followed through path anchors and anchors of a registered kind.** Rejected. Such an anchor names files, not a dependency on an artefact, and a broad glob would fail validation for cycles nobody declared.
- **A whole record anchor standing on the record's file.** Rejected. Each revalidation of a record a place holds would flag every whole anchor on it.
- **A whole record anchor standing on the record's file without the container's lines.** Not taken. Finding those lines needs the front matter parsed anyway. A reformatted front matter would then flag a record anchor on a record but not an artefact anchor on it.
- **A whole record anchor that leaves out only the record's friction block.** Not taken. A role's block in the container is bookkeeping about the record too (COR-053 point 10). An artefact anchor ignores the whole container, and a record anchor reads a record the same way.
- **A record's content read only where a place holds the record, its file elsewhere.** Not taken. A record received by sync, or one moved into or out of a place, would flag its anchors for bookkeeping alone.
- **A path anchor, or one of a registered kind, standing on each file whole.** Rejected. Each revalidation of an artefact in a file it matches would flag it, and the cascade would go on through such anchors.
- **Every file read by its content, whether or not a place holds it, as a record is.** Rejected. A file no place holds, such as a template, may carry a container as part of what it is, and a change to it would reach no path anchor.
- **A file read with its container's lines dropped, as text.** Not taken. Finding those lines needs the front matter parsed anyway. A reformatted front matter would then flag a path anchor on an artefact's file but no artefact anchor on it.
- **Only the containers of the artefacts the file holds left out.** Not taken. Which those are follows the file's shape, so a container added at the top of a collection file would make its entries' containers count.
- **A file read by its content only where a place holds it at both states compared.** Not taken. The change that brings a file into a place and writes its first block would flag every path anchor on the file.
- **A file the methodology's sync writes read by its content, as a placed file is.** Not taken. Which files are synced copies is read from the install state, never from the state compared, and a synced template carries its container as part of what it is.
- **Every dead anchor failing validation, whole ones included.** Not taken. It would fail, in every mode, a dead whole anchor that a project keeps in warning mode.
- **Storing each artefact's current-or-stale state as truth.** Rejected. Stored state duplicates what git already answers, and it drifts from git whenever a change bypasses the check. The tool-written status is a dated snapshot, not truth.
- **A commit identifier or a content hash as the marker.** Rejected; see Rationale.
- **Reading the answer from the pull-request description.** Rejected; see Rationale.
- **A bare marker change as an answer.** Rejected: it is indistinguishable from a blind bump; the justification, changed each time, is the answer.
- **A confirmation for each answer an agent writes while making a change.** Rejected. A stream of confirmations is accepted unread. A reviewer checks the answers together, against the change.
- **Every answer a change wrote shown to the person who authorises its merge, word for word, and accepted by that authorisation.** Rejected. The person redoes the agent's check without its context, the acceptance adds little, and every change that wrote an answer waits until they are back.
- **A deferral the person accepts before the merge.** Rejected. Judging an agent's reason asks the person to redo the agent's check without its context. Every change that defers would wait for the person. The person is told each deferral and its follow-up, and the reviewer checks that each deferral the change writes names an open follow-up.
- **An agent's answer that nobody but its writer checks, as the rule.** Rejected. A wrong justification then reaches the default branch's history unchecked, and the check cannot tell it from a right one. The record accepts such an answer only by a choice someone is accountable for, as point 3 says: a person skips the review on record, or the project chooses no such reviewer.
- **The person who authorises the merge checks the answers when no reviewer does.** Rejected. It asks the person to redo the writer's check without its context, which is also why a deferral the person accepts before the merge is rejected. The person has neither that context nor the time to check the answers a change owes.
- **The agent writes no answers when no reviewer checks them, and hands the person the commands that would write them.** Rejected. Every change that owes an answer, in a project that chose no reviewer, would wait for the person to run those commands, a cost the reviewer exists to remove. The person would also run commands whose answers they cannot judge, so the answers would still go unchecked.
- **A debt ledger, in one file or one file per entry.** Rejected. It duplicates git and drifts.
- **Recording stale debt as synthetic deferral entries.** Rejected. Deferral is deliberate postponement; stale debt is shown by the tool-written status instead, so the two are never confused.
- **Keeping either timestamp on a conflicting revalidation, the merge becoming the new point.** Rejected in favour of revalidating the combined state; the merge would claim a revalidation nobody made.
- **Organising the block per anchor, or splitting it strictly by writer.** Rejected. The first puts the tool and people on the same lines; the second adds a level that carries no meaning.
- **One copy per component.** Rejected. Separate engines drift apart, and the components would disagree about what is stale.
- **A link back from each target to its source.** Rejected. It would make a cycle, and a target such as a test file carries no anchors.
- **Every link revisiting its targets.** Rejected. Most anchors need no return visit, and a reason asked at every edit is written blindly.
- **A link's targets taken as every anchor of one kind.** Not taken. One kind may mix what a source rests on with what answers it.
- **Targets always listed in a field.** Not taken. Where nearly every anchor binds both ways, the field copies the anchors, and each change to it flags the source's dependants.
- **Targets taken as every anchor but those on what the component's own places hold.** Not taken. Point 16 would gain a notion of where a target lies. Fields that list what stays out need none.
- **A link declared on a type.** Rejected. Friction never reads a type (point 1). A project may give a component's type to its own place, and a type may be renamed, so retyping would change what a change owes.
- **A link declared through a connection point (COR-053).** Rejected. A connection point is declared by a component that needs something from another. A link needs nothing from another component. Its owner declares it on its own place, in the block of the functionality that reads it.
- **A project declaring links on its own places.** Not taken. The project's places sit in the key point 14 owns, which holds no link. A project that keeps a kind of artefact whose links bind both ways can be given one there without breaking anything.
- **A link triggered by the labels or headings of a body.** Rejected. A project may relabel them, and a relabel would switch the signal off silently.
- **A link read by the whole-repository check too.** Rejected. It would have to tell, for each target, whether the target changed after each trigger, and that depends on how the change landed.
- **A revisit's reason kept among the source's deferrals.** Rejected. A deferral postpones the source's own friction, and a revalidation re-states it. A revisit answers for a target.
- **The reason kept on the target, where the target holds a block.** Rejected. Many targets hold none, such as a test file, and the answer would live in two places by the kind of target.
- **Excluding the artefact's path instead.** Rejected. Exclusion is per file, so it cannot waive one entry of a collection, and it keeps no reason beside the artefact.
- **The backbone holding each command to its obligations — keeping it off the network, stopping its writes.** Rejected. No backbone can hold a single command to them on every platform a project runs on, and a limit stated as enforced and not kept misleads more than an obligation stated as trusted.
- **An anchor changed whenever a commit after the point touched it.** Rejected; see Rationale. An edit and its revert would be debt or nothing according to how the change landed.
- **Telling a written-back `at` by its time being earlier than the one it replaces.** Rejected. A revalidation written by hand with an earlier-looking time would read as none, every revert of a revalidation would be stopped whether or not it brought debt back, and where two lines of work meet, whose clock ran ahead would decide.
- **A change check that reads no history.** Rejected. It cannot tell a written-back `at` from a new one, so it would pass the revert of a revalidation that brings back debt nobody answered, which the whole-repository check reports once the change merges.

## Implications

- **The backbone ships the friction checks** — the change check and the whole-repository check, each runnable locally — reading the blocks in the declared places. Its output includes a machine-readable form, so that other components can consume friction, uncovered surface and the artefacts' answers. For a change, that form lists every answer the change wrote, each with its words, and each target the change revisited by changing it (point 16): the list the reviewer of point 3 works from.
- **The backbone ships the schema** for the block, for single documents and collection entries. It is a surface change adopters can see, and existing documents are unaffected.
- **The backbone ships the writing commands** for revalidating, deferring, revisiting and recording the status, and the after-merge status job a project may wire in.
- **Components that keep anchored artefacts** declare their places and surface, and any folders of held documents, in their own package metadata. They register their own anchor kinds and resolvers, and define how their artefacts are revalidated — including how their own revalidation vocabulary maps onto the two outcomes here. They may also decide what to do when a revalidation finds that the description was right and the change was wrong. A work-tracking component may render the artefacts' answers into its pull-request format, reading the machine-readable output for that; one through which a change is reviewed and its merge authorised may show point 3's list there, with the sentence on what changed in each updated artefact. A rendering answers nothing: an artefact's answer is on the artefact, and no check of this record reads the rendering.
- **A component whose links bind both ways** declares each link on its places (point 16), and needs a backbone that reads the declaration. One that withdraws a link removes the entries that would dangle. One that renames a link's field moves that field in its artefacts. Both use a migration (COR-010).
- **Continuous integration** needs each artefact's history back to where it was last added (point 3) for the whole-repository check and the debt listing, since only there is it known where a value was first carried. The change check needs the diff, an up-to-date base and, for an artefact whose `at` or deferrals the change alters, that artefact's file history behind the base. In a clone whose history is cut short, a value first carried after the cut is read as first carried there and the checks say so; a value the file already carried where the history is cut has a point the checks cannot reach. Either check runs the resolver of each registered kind it meets, which reaches no network (point 2), so whatever a resolver needs is in place before the check runs.
- **The backbone configuration** gains the key from point 14.
- **The status report** can show friction, unanchored artefacts and uncovered surface.
