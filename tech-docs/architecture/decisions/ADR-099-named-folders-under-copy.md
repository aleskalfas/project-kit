## Summary

**In plain terms:** [ADR-093](ADR-093-writes-outside-the-repository.md) lets a person name, for one checkout, folders where the permission hook does not ask before a file tool writes outside the repository. [ADR-095](ADR-095-hook-out-of-reach.md) moves the hook's code and the model it judges by out of a sandboxed command's reach. A person accepts the two records together, in one change. This record says what a named folder does under that protection:

- **An agent's call to name a folder is denied.** The decision core, through the hook, and a native rule in every project deny an agent's call of the command that names one. A person names a folder from a terminal of their own, as ADR-093 has it. Removing one meets neither.
- **A named folder lifts only the file tools' ask.** The hook's guard on what judges later calls holds there as everywhere.
- **A list counts only out of a sandboxed command's reach,** and a folder that is, holds or lies inside a folder ADR-095 guards counts for nothing.
- **A named folder can be a way around the sandbox for every project.** Where a program outside the sandbox runs or reads it, an agent's unasked write there reaches what every project shares. Whoever names it accepts that, and ADR-093's choice to meet a host's need stands on three grounds.

**How far it holds.** The denies are an interlock. Where the harness sets no mark on its tools' processes, the naming command's own refusal is open, and only the denies hold, in the forms they recognize (point 5).

## Context

- **What ADR-093 decides.** A person names folders for a checkout through a command of the permission layer, which refuses where the harness's mark of a tool's process is present (ADR-093 point 4). The lists lie in a folder of pkit's in the user's state folder (point 2). In a named folder the hook has no opinion (point 2, "Silent there"). ADR-093 holds that naming a folder adds no route an agent lacks, since while the hook's own files lay in a sandboxed command's reach, such a command could drop the ask without the list (point 6, "What guards the list"; [project-kit#3178](https://github.com/aleskalfas/project-kit/issues/3178)).
- **What ADR-095 decides beneath it.** In a project that turns the hook on, the hook runs from a copy of the installed release, and the folder that holds the lists is one of the *guarded folders* kept out of a sandboxed command's reach (ADR-095 point 2). The hook's *guard on itself* denies a file tool's write into those folders, and asks before a write to the harness's settings or to what chooses the release's contents, and before a move into another tree (ADR-095 point 4). The naming command is served from the installed release (ADR-095 point 2). The decision core reads the commands that widen what the hook allows by a reading of their own, which errs away from a mention, over the matcher its guardrails use (ADR-095 point 3, "How a call is read"). So the gap ADR-093 leans on closes, save for what ADR-095 point 7 names.
- **The mark.** From 2.1.172 the harness marks each process its shell tools and hooks start, and no editor sets the mark in its terminals. A command line can clear it (ADR-093's Context, "What marks a tool's process"). On macOS `pkit` runs outside the sandbox, and the settings the adapter ships allow it with no prompt (ADR-093's Context, "The shell is beside the file tools").
- **Agent hosts.** On the host a trial measured, nobody answered an ask, the machines could not start the sandbox, and the host's guidance had its agent write in the home folder (ADR-093's Context, "What the trial measured"). ADR-093 meets that need with the named folders.

## Decision

**An agent's call to name a folder is denied, and a named folder lifts only ADR-093's ask: the hook's guard on itself holds there, a list counts only out of a sandboxed command's reach, and whoever names a folder accepts what it opens for every project.**

### 1. An agent's call that names a folder is denied

- **The core's deny.** The decision core denies a *shell call*, a call of any of the harness's tools that runs a command (ADR-095 point 3), that it reads as naming a folder through the command ADR-093 point 4 decides, to every subject and in every report of a verdict. It reads the call as it reads the commands ADR-095 point 3 interlocks ("How a call is read"), by a recognizer of the kind that point adds to the backbone's catalog. The copy's core gives the deny with no model, so the hook gives it in every state and every mode, whatever the harness marks (ADR-095 point 4), on each form the core reads. A call that reading reads in doubt, such as a PowerShell call whose quotes are typographic, gets no deny of the core's (ADR-095 point 3). Where the core cannot read what a runner runs, it gives ADR-025 point 7's verdict, naming the naming command among what it cannot rule out, on which the adapter asks, meeting the mode (ADR-095 point 3). Its reason gives the agent the line to hand to the person, who runs it from a terminal of their own, as ADR-093 point 4 has it.
- **The native deny.** The settings every project receives deny the plain form of that call, under each name ADR-095 point 3 reads the methodology's command by, whether or not the hook runs, among ADR-095 point 4's native locks.
  - **The runners' options.** Under each runner, the deny carries a wildcard for whatever text the call writes between the runner's name and the methodology's package, where the call names the package as its command, or between the runner's name and the option that names the package as the source of the methodology's command, whether that option takes the package after a space or after `=`. So it takes any options there, among them a version or a source that the source option gives before the package's name. It takes nothing written onto the package's name, and no text between the package and the naming form's words, unlike ADR-095 point 4's asks. Beside what passes the plain form under every name, such as an option of the command's own before the naming form's words, or one of the installer's before or among the words that name its runner, such as `tool run`, it leaves two kinds of runner's call: one that writes a version onto the package's name, or a source in its place, as the command or as the value of the source option that `pkit` follows; and one that writes an option, or a `--` that ends the runner's options, between the source option and the methodology's command.
  - **What those calls run.** A runner's call runs a release of the methodology where it names `pkit` after the source option. One that names the package as its command runs nothing while the package provides only `pkit`, and the wildcard takes it so that the deny holds should a release name an executable after the package. A runner's call of `pkit` runs the installed release by default once the methodology's tool is installed, so one with an option before the package can serve the naming command, and the wildcard denies it whether or not the hook runs. Some options set the installation aside, such as `--isolated`, or a `--with` or a `--python` the installation does not satisfy. A call with one of them fetches a release of its own, and so does a call that names a version or another source, save where the runner reuses the installation for it, as it may for the installed version. A release so fetched refuses the naming command, as every release that carries it does where it is not the installed one (ADR-095 point 2, "Served from the installed release"; "What binds the build" below). A call the wildcard does not take that runs the installed release, such as one with an option between the source option and the command, or a release its caller has made take itself for the installed one, passes the native deny, and meets the core's deny, on each form the core reads, where the hook runs, and the command's own refusal where the mark reaches it, so point 5 states what passes them all.
  - **Where it finds the call.** The harness's matching finds the call wherever its documentation says a subcommand lies, and the core denies it at each such place (ADR-095 point 4, "What a native rule catches").
- **Where the harness reads a heredoc's body as commands.** Where ADR-095's probe finds the harness's parse reading a line of a heredoc's body as a subcommand (ADR-095 point 6), the native deny refuses outright each commit message or pull request's body written through a heredoc that opens a line with the naming form, and nobody can approve a deny. That finding calls for a refinement of this record that weighs the native deny on that harness release.
- **Removal, and a listing where the command gives one, meet neither,** since removing a folder only gives an ask back, and a listing widens nothing. No such form's words begin with the naming form's words, and none is a flag of it, as ADR-095 point 4 has a form to be spared from a native rule ("What a native rule catches"). The native deny's wildcard for a runner's options stands before the methodology's package, or before the option that names it as the source, and none stands between the package and the naming form's words (above), so a later argument of such a form, or of another command, brings it under the deny only where the call is a runner's and the argument holds the naming form as a runner's call writes it after the runner's options, the package's name among it (Rationale, "Why the runners' wildcard stops where the call names the package"). This binds the name ADR-093 point 4 leaves to the build.
- **A request for help under the naming form** meets both denies, since the native rule catches it and the core denies every form the native rule catches (ADR-095 point 4).
- **Beside the command's own refusal.** Where the harness sets its mark, the command refuses an agent's call in every form that keeps the mark (ADR-093 point 4), and the denies refuse first what it would refuse. Where no mark reaches it, the denies refuse the forms they recognize (point 5). On Linux with the sandbox on, the command runs inside the sandbox unless the person excludes it, and a sandboxed call cannot reach the folder of lists (ADR-095 point 2), so there the deny refuses a call that would fail.
- **The agent's tool calls alone.** The denies judge shell calls alone. A command a person types into the harness's shell mode is none. Whether such a command carries the mark, and whether the hook or the native rules see it, ADR-095's probe finds (ADR-095 point 6). Where they do, the person names the folder from a terminal outside the harness.
- **An interlock, not a boundary,** as ADR-095 point 3's guards are: a form the core does not read, and the native rule does not name, passes both (point 5).

### 2. The hook's guard on itself holds in a named folder

- **What a named folder lifts:** ADR-093 point 1's ask, and nothing else. The hook's guard on itself holds for a target there as for a target anywhere, in every mode (ADR-095 point 4), and so do the native locks, which read no list. Where the core abstains, or the hook treats the call so (ADR-095 point 2, "One verdict"), and the guard gives nothing, the harness's own rules and mode decide, as ADR-093 point 2 has it.
- **What it costs an agent host.** A step of a host's guidance that writes through a file tool what the guard asks before is refused where nobody answers, or waits, and no named folder lifts it. Such steps include registering a connected server, editing the harness's settings, setting version control's identity in its configuration in the person's home, and editing the installer's own configuration. A write such as the trial's service file meets none of the guard's asks, and a named folder serves it as ADR-093 decides.
- **Accepted as a limit,** stated by its property ([ADR-091](ADR-091-no-host-component.md) point 4): a session with nobody to answer its asks makes none of the writes the guard asks before. A host whose guidance needs such a write makes it in its setup, outside any session, where no ask is put (ADR-091 point 7), as its setup names its folders there (ADR-093 point 4).

### 3. A list counts only out of a sandboxed command's reach, and names no guarded folder

- **Where a list counts.** The hook counts no list where the folder that holds the lists lies inside the per-user temp folder, which a sandboxed command writes by default, or overlaps the folder the session's anchor names, each by real path (ADR-095 point 2, "Not where a sandboxed command writes by default"). The overview names the folder of lists where it lies so. This adds to ADR-093 point 2's tests.
- **Which folders count.** A named folder that is, holds or lies inside any guarded folder counts for nothing, not only one that holds the lists' own folder. So a file tool's write into each meets ADR-093 point 1's ask beside the guard's deny and, at the folder's default place, the native deny. The naming command refuses such a folder, as it refuses one ADR-093 point 3 would not count (ADR-093 point 4). This widens ADR-093 point 3's test.
- **What reaches past it.** A working folder of the harness's, or a sandbox write grant, over the folder of lists opens it to sandboxed commands, a session's own folder among them (ADR-095 point 7, "A working folder or a write allowance over a guarded folder").

### 4. A named folder can be a way around the sandbox for every project, which its namer accepts

- **The route.** Where the hook runs from its copy, no sandboxed command alone drops ADR-093's ask, save through what ADR-095 point 7 names. So in a folder that a program outside the sandbox runs or reads, the ask puts a way around the sandbox before a person, and naming the folder opens it: an agent's file tool writes there unasked, and that program runs what it wrote with the person's full access. Such a program can write the guarded folders every project on the machine shares, so the folder reaches the protection of every project, not only its checkout's.
- **Who accepts it.** Whoever names such a folder accepts that, for every project on the machine (ADR-093 point 4, "Who accepts it"). The naming command says so on each naming (ADR-093 point 4, "Loud").
- **The list itself** adds no route an agent lacks, save through a call of the naming command that passes its refusal and the denies (point 5).
- **The overview** reports, in every project, every folder named for any checkout on the machine that it can see, with the checkout it was named for. It names the folder of lists it read, where its own environment places it, and says that it cannot see lists kept under another state home, such as one the harness's environment names (ADR-093's alternative "The overview alone as the report").
- **ADR-093's choice to meet a host's need stands,** on the three grounds the Rationale gives.

### 5. Where no mark reaches the naming command, only the denies hold

- **Where no mark reaches it:** under a harness that sets none, such as Claude Code before 2.1.172, and where a file the shell tool's shell reads at its start unsets the mark, such as the harness's snapshot of the person's shell or the file `BASH_ENV` names. Unsetting the mark passes the gestures' test of it too, where the anchor then holds (ADR-095 point 3). The harness's snapshot runs only in the agent's shell, inside the sandbox where one runs, so of it only the unsetting counts here. A file the person's own shells read as well, such as the one `BASH_ENV` names, is among the shell's startup files ADR-095 point 7 names as able to write the guarded folders.
- **What holds there:** the core's deny and the native deny, in the forms they recognize (point 1).
- **What passes them:**
  - a form the core does not read, or reads in doubt (ADR-095 point 3), such as a link to `pkit` under another name, or a call through an excluded command that runs code the core does not read, such as `uv run python3 -c …` (ADR-093 point 4), which on macOS runs outside the sandbox and could write the guarded folders itself, as a command the sandbox exempts (ADR-095 point 7);
  - a form the native deny does not name, in a session where the hook does not run, such as one in a project that leaves the hook off or one before the copy is made. Among such forms are a call with an option of the command's own before the naming form's words, or one of the installer's before or among the words that name its runner, such as `tool run`, and the two kinds of runner's call the deny's wildcard leaves (point 1, "The runners' options"). A call among them that names the package as its command runs nothing while the package provides only `pkit` (point 1, "What those calls run"). Of the others, one with an option of the command's own before the naming form's words, or of the installer's before or among its runner's words, can name a folder, save one whose option only prints, as a request for help or for the version does. One whose source option takes the package with a version, or a source in its place, names the folder where the runner runs the installed release for it, as it may for the installed version, and otherwise its release refuses the call. One with an option, or a `--`, between the source option and the methodology's command runs the installed release by default, and names the folder;
  - any form in a session whose settings carry no native lock, such as one started below a checkout's root, unless the person's own locks carry it;
  - an extension or a hook that answers for the person (ADR-095 point 7).
- **Where such a call lands.** It names the folder with no ask wherever the command runs outside the sandbox, as `pkit` does on macOS. Where the command runs inside the sandbox, the sandbox keeps the call from the folder of lists.
- **What it reaches.** The folder it names drops ADR-093's ask in that checkout, and where a program outside the sandbox runs or reads files there, it is point 4's route. Where the permission hook is on, the report at each session's start shows each folder the hook counts, and the overview each named folder it can see, after the fact (ADR-093 point 4).
- **A refusal under the session anchor as well** would close these calls too, at a cost that turns on which processes carry the anchor, which ADR-095's probe finds. A refinement of ADR-093 point 4 weighs it on that finding.

### 6. The tests

Tests hold that:

- the settings every project receives carry the native deny on the naming command's plain form, under each name ADR-095 point 3 reads the methodology's command by, with the wildcard for a runner's options that point 1 gives it and none between the package and the naming form's words, and no native rule on a form that removes or lists folders; how the harness's parse reads a mention is the probe's (ADR-095 point 6, and point 1 above);
- the core denies, through each tool that runs a command, a call it reads as naming a folder, in the forms and through the runners ADR-095 point 3 reads and at each place that reading finds a command, a substitution inside double quotes and a request for help under the naming form among them;
- the core's deny touches no call that removes a folder, nor one that only mentions the naming form in a quoted argument or in a heredoc's body that is data (ADR-095 point 3), such as a commit message or a pull request's body written through a heredoc inside a substitution inside double quotes, with `"` and `'` in the body, an escaped backtick or an escaped `$(` in a body behind an unquoted delimiter, escaped quotes inside a double-quoted argument, a body fed to a shell that runs a `-c` script or a script file, a later argument of another of the methodology's commands run through a runner, and a PowerShell call whose quotes are typographic or whose quoted text ends in a backslash;
- the hook counts no list where the folder of lists lies inside the per-user temp folder or overlaps the anchor's folder;
- a named folder that is, holds or lies inside a guarded folder counts for nothing, and the naming command refuses it;
- the hook's guard on itself denies and asks in a named folder as it does elsewhere.

## Rationale

**Why a deny, not an ask.** No agent's call that names a folder is meant to succeed. Under a harness that sets the mark, the command refuses it (ADR-093 point 4). Under one that sets none, ADR-093 still has a person name a folder at a terminal of their own, not by approving the agent's call (its Rationale, "Why the naming command refuses a tool call"). So a deny refuses nothing an ask could rightly let through, and it gains on each count where an ask falls short:

- **No prompt before a refusal.** Under a harness that sets the mark, an ask would have a person approve a call the command then refuses, the cost ADR-093 weighs against an ask rule (its alternative "An ask rule on the naming command"). A deny refuses first what the command would refuse.
- **It holds where the hook does not run.** The native deny holds in a project that leaves the hook off and before the copy is made, where under a harness that sets no mark nothing else refuses the plain call.
- **It rests on nobody's answer,** on each form the core reads. It puts nothing to a person, so it does not rest on `ask-reaches-person` ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), and no hook on the harness's permission requests can approve it. Where the core cannot read what a runner runs, its verdict meets the mode (point 1).
- **It needs no mark.** The core denies whatever the harness marks, so a harness that marks its hooks and not its shell's processes, or a shell that unsets the mark, changes nothing it gives. On Linux with the sandbox on, it refuses a call that would fail, where an ask would put a prompt before the failure.

The gestures ADR-095 point 3 interlocks take an ask instead, since a realizing that only narrows goes ahead under an anchor, so an agent's call of them can rightly succeed once a person answers the core's ask. The deny is an interlock, as the hook's other verdicts on a command are, and it changes nothing ADR-093 decides of the command: ADR-093 declines an ask rule on it, and decides no verdict of the hook's on it.

**Why the core reads it, as it reads the interlocked commands.** The deny concerns the methodology's own command and turns on nothing of the harness's, so it lives in the core beside the interlock's asks, read the same way, for the reasons ADR-095's Rationale gives ("Why the core reads the interlocked commands", "A mention is data"). The direction of that reading weighs most here: nobody can approve a deny, so a reading that took a mention for a call would refuse outright each commit message or pull request's body that names the naming form, in the runs nobody watches that write them. The same weight narrows the native deny's wildcard (below). What a missed call meets is point 5's. The native deny stays beside the core's, since the hook fails open where it cannot start ([ADR-002](ADR-002-permission-realizer-ownership.md) points 3 and 4).

**Why the runners' wildcard stops where the call names the package.** The deny weighs a call it misses against a mention it refuses outright (point 1, "The runners' options"):

- **A wildcard for the runners' options.** A runner's call of `pkit` with an option before the methodology's package runs the installed release by default, which can serve the naming command. With no wildcard there, such a call would name a folder unasked in a session where the hook does not run and the mark does not reach, outside the sandbox on macOS. Where the option sets the installation aside, or gives a version or another source before the package's name, the call runs the installed release or one that refuses the naming command, so denying it costs nothing. A call that names the package as its command runs nothing while the package provides only `pkit` (point 1, "What those calls run"), so the wildcard before it guards no call that runs, and is kept, at the cost below ("What the narrower one costs"), so that the deny holds should a release name an executable after the package.
- **No wider one.** The wildcard ADR-095 point 4's asks carry, before the package and after it, would also deny outright each call of another of the methodology's commands through a runner whose later argument mentions the naming form's words, such as a pull request's body. What it would add is each runner's call the narrower one leaves whose text carries the package's name before the naming form's words, such as one that writes an option of the command's own before the naming form's words, a version onto the package's name, or an option between the source option and the command, each of which runs as point 1 says ("What those calls run"); it would not add one with an option of the installer's before or among the words that name its runner, which neither wildcard takes.
- **None between the source option and the command.** A wildcard there would take the second kind, but would also deny outright each runner's call of another of the methodology's commands under the source option whose later argument mentions the naming form by the command's own name, the way an agent mentions it most. Nobody can approve that deny, so the call it would close is left to point 5.
- **What the narrower one costs.** It denies a mention only where a later argument of a runner's call holds the naming form as a runner's call writes it, the package's name among it. Such calls are rare, since an agent mentions the methodology's command by its own name, and each is denied outright, with nobody to approve it. What it leaves open, each runner's call it does not take, such as one with an option of the installer's before or among the words that name its runner, is point 5's.

**Why the guard holds in a named folder.** A named folder drops ADR-093's ask so that a host's guidance can write there where nobody answers. The guard covers what judges later calls in every project: what starts code outside the sandbox, what chooses what the release holds, and the guarded folders themselves. A named folder that lifted it would let a file tool write those unasked in every session that counts the folder. Nor can the guard give way where nobody answers or where the sandbox cannot start, as on the trial's host: the hook reads neither (ADR-091 point 6; ADR-095's alternative "Have the hook read whether the session's sandbox is on"), and a native rule holds in every session alike. So the cost falls on a host's guidance (point 2), which its setup meets outside any session.

**Why a list counts only out of a sandboxed command's reach.** A list drops an ask, so it widens what the hook allows, and ADR-095 point 1 keeps whatever widens it out of a sandboxed command's reach. ADR-093 point 2's tests keep out another account, a link and a shared temp folder. The per-user temp folder is in every sandboxed command's default write set, and the anchor's folder is in the session's own, so a list in either could be any of its sandboxed commands', and the hook counts none there.

**Why a folder over any guarded folder counts for nothing.** ADR-093 point 3 refuses a named folder that holds the lists' own folder, so that a file tool cannot rewrite a list unasked. The same lock is worth as much for every guarded folder, and more for the copy and the release it is made from.

- **What it adds.** The guard denies a file tool's write into a guarded folder in a named folder too (point 2), so the test adds a lock beside it, ADR-093 point 1's ask, which matters where the guard faults, or where the machine keeps the folder off its default place and no native deny names it.
- **Against the test as it stands, or none.** Kept for the lists alone, the test would guard the lesser folder better. Dropped, it would leave each folder to the guard and, at its default place, the native deny.
- **The cost.** A person names a narrower folder, such as one below `~/.local` rather than `~/.local` itself, as ADR-093 point 4 already asks, and the naming command says so at once, since it refuses a folder point 3 would not count.

**Why a named folder stays the person's to name, though it can be a route.** ADR-093 weighed meeting a host's need against keeping the ask everywhere on the premise that naming a folder gives an agent no route it lacks, which held while a sandboxed command could drop the ask through the hook's own files. Under ADR-095 the premise fails for a folder that a program outside the sandbox runs or reads (point 4). So this record has ADR-093 state that plainly, and has whoever names such a folder accept it for every project on the machine. ADR-093's choice to meet the need stands on three grounds:

- **Where the need was measured,** the host's machines cannot start the sandbox, so the protection holds nothing there, and naming the folder costs none of it.
- **Where the sandbox runs,** naming such a folder is a widening, which ADR-093 point 4 holds to the discipline [ADR-008](ADR-008-confinement-allowances.md) point 4 sets for one: an explicit gesture, loud, never committed and always reported, save for an agent's call that passes the command's refusal and the denies (point 5). Its message on each naming tells the namer how far the folder reaches.
- **Keeping the ask everywhere** costs what ADR-093 weighed: the host's step fails, or moves to the shell, where nothing of the methodology's reads its target (ADR-093's Rationale, "Why meet the need").

**Why the overview reports every checkout's folders.** A folder named for one checkout reaches the protection of every project, and would go unseen in their own state, as ADR-093 says of one list for every project (its alternative "One list for the user, for every project"). The report at each session's start shows only what that session's hook counts (ADR-093 point 4), so the overview shows the rest, and says what it cannot see.

### Alternatives considered

- **The command's own refusal alone, as ADR-093 decides.** Not taken.
  - *Its case:* no new rule, and nothing more for the core or the adapter's settings to carry. A deny matches only the forms it recognizes, as ADR-093 says of an ask rule's text.
  - *Its cost:* under a harness that sets no mark, or past a file that unsets it, nothing refuses the plain call, which on macOS runs outside the sandbox with no prompt. The deny refuses the plain forms there, and costs nothing where the mark is set, since it refuses first what the command would refuse.
- **Ask before the naming command in place of the deny,** in the hook or in a native rule. Not taken: either would put before a person a call ADR-093 has a person make at a terminal of their own, and under every release that sets the mark, an ask would have a person approve a call the command then refuses ("Why a deny, not an ask").
- **Give the native deny the wildcard ADR-095 point 4's asks carry,** for a runner's options, version or source. Not taken: it would deny outright each call of another of the methodology's commands through a runner whose later argument mentions the naming form, and would add only each runner's call the narrower wildcard leaves whose text carries the package's name before the naming form's words, such as one that writes an option of the command's own before the naming form's words, a version onto the package's name, or an option between the source option and the command; it would not add one with an option of the installer's before or among the words that name its runner, which neither wildcard takes (Rationale, "Why the runners' wildcard stops where the call names the package").
- **Give the native deny no runner's wildcard.** Not taken: a runner's call of `pkit` with an option before the package runs the installed release by default, which can serve the naming command, so such a call would pass the native deny, and in a session where the hook does not run and no mark reaches, name a folder unasked. The narrower wildcard costs only the rare call whose later argument holds the naming form as a runner's call writes it (the same Rationale).
- **Spare a read-only form under the naming form in the core's deny.** Not taken: the native rule catches it wherever the harness's matching finds the naming form (ADR-095 point 4, "What a native rule catches"), so sparing it in the core would part the reports from what the harness enforces.
- **Make the deny on naming a folder a guardrail of the backbone's catalog.** Not taken: a guardrail's readings err toward the deny (ADR-095 point 3), so a commit message or a pull request's body that names the naming form at the start of a line would be refused, and nobody can approve a deny. It would gain nothing: the native deny is merged into every project's settings either way.
- **Have the naming command refuse under the session anchor as well, as ADR-095 point 3's gestures do.** Not taken here: each person who names a folder where their own terminal carries the anchor, such as an editor's, would be refused, and which processes carry it ADR-095's probe finds.
