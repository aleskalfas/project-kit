## Summary

**In plain terms:** `pkit validate` becomes a registry. What validation is, how a component joins it and what fails it are the core's ([COR-055](../../../.pkit/decisions/core/COR-055-validation.md)); this record is how project-kit builds it. Each functionality registers one *validator* — a name, an order and a callable that reads the project and answers with summary lines and findings, each with a severity. The backbone registers twelve members; an installed component registers its own by naming a command it already registers. One renderer, one summary, only an `error` fails. The focused commands stay; the check aggregator calls `pkit validate` once beside the checks that read a diff.

## Context

The core defines validation as the project's one check of its own state against the invariants its records own, which the backbone's functionalities and installed components join by registering validators (COR-055); `pkit validate` is its command, one operation as the command-line rules ask ([COR-004](../../../.pkit/decisions/core/COR-004-cli-surface.md)). The living-documentation design note ([`.pkit/scratchpad/done/2026-09-26-software-analysis-living-docs-design.md`](../../../.pkit/scratchpad/done/2026-09-26-software-analysis-living-docs-design.md), its entry of 2026-09-28) decided that every functionality registers its validator there and the check gate calls it once, and [ADR-056](ADR-056-backbone-file-schemas-home.md) point 5 asked for its passes as members. Until now each Task added its pass by hand, five older validators had no place in the umbrella, and the reference-graph check — in it on `main` behind `--include-refs`, on by default — failed this repository on four false positives and twelve drift findings, so the aggregator (`scripts/check.sh`, the enforcement boundary of [ADR-019](ADR-019-enforcement-gate-mechanism-vs-boundary.md)) ran `schemas validate` and `decisions validate`, never `pkit validate` or `refs validate`.

## Decision

1. **One registry, one shape, in the binary.** `project_kit.validators` is the home. A `Validator` is a name, an order and a callable `Path → Outcome`; an `Outcome` is summary lines and `Finding`s, each a location relative to the project root (a path, `path:/json/pointer`, `path#entry`), a message, a severity and an optional label. It ships in the tool and propagates nothing ([ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 1; [ADR-020](ADR-020-process-engine-code-home.md)).

2. **Four severities; `error` is the one that fails.** That every finding carries one severity from a closed set shared by every validator, that exactly one severity fails, and that the record owning a check classifies its findings are the core's (COR-055 points 4 and 5). The set here is `error`, `warning`, `info` and `report`: `error` fails `pkit validate`; the other three print and never fail. A warning asks for attention (a drifted declaration; an alias another name shadows); an info states a fact; a report is what an owning record says is *reported rather than judged* ([COR-053](../../../.pkit/decisions/core/COR-053-connection-points.md) point 10, [COR-051](../../../.pkit/decisions/core/COR-051-rule-sets.md)). Of what a member answers, severity is all the umbrella reads to decide its exit.

3. **The backbone's members, in dependence order:** `manifests`, `schemas`, `configuration`, `packages`, `connections`, `versions`, `friction`, `rule-sets`, `decisions`, `refs`, `process`, `data` — what a later member reads, an earlier one checked, with one soft exception: `configuration` reads raw package declarations before `packages` validates them. The umbrella never changes what a member computes; the CLI reference's `validate` table says what each checks and which focused surface it keeps. `process` and `data` walk the repository, which their focused surfaces do not: `data` checks every claimed file in the repository and in the project-owned `project/` folders under `.pkit/`, skipping what nothing claims — the files of the working tree's one listing, the one friction discovery reads (ADR-057 point 2).

4. **An installed component registers its validators in package metadata**, under `validators:`, by naming a command it registers under `commands:`. That a component joins validation this way is the core's (COR-055 point 3); the block, its keys and the run are this record's. A component here is a capability or an adapter — every installed package is read, and the package schema admits both blocks on either kind — though only a capability's commands get a namespace from the dispatcher ([COR-021](../../../.pkit/decisions/core/COR-021-capability-command-dispatch.md)). An entry is `command` — a path through the tree, checked like every other command reference — and an optional `order`; the leaf's `help` is the validator's. A capability's validator is the same script as a focused surface (`pkit <capability> <command>`); an adapter's is runnable by its script's path. Because the entry names a `commands:` leaf, ADR-057 point 3 applies unchanged: the leaf declares the query contract on its own entry — the literal is **`query-contract: true`** — package validation reports a validator leaf without it, and the runner refuses it. The umbrella addresses the validator `<component>:<name>`, sorts it after the backbone's members unless its order says otherwise, and runs the script as a query with no subject: from the project root with the one argument `--json`, the offline marker set, in its own process group, bounded by the backbone's one command bound and killed as a group on timeout — or, when `pkit validate` itself runs inside another run, in the outermost run's group and bounded by the time that run has left (ADR-057 point 5) — reading one JSON findings document and nothing else from standard output, diagnostics on standard error. **No answer is an error finding, never a clean pass**, and no policy softens it (COR-055 point 6). Here no answer is a leaf without the declaration, an abnormal exit, a timeout, output that is not UTF-8, an answer that is not exactly that document. The query is one policy over the backbone's shared command runner (ADR-057 point 5): the process engine's predicates share its bounded run under their own policy, and the dispatcher shares only its lookup — a proxied command is neither bounded nor captured.

5. **One renderer, one summary; the umbrella's exit rule.** Every member prints under its heading through one renderer, one summary closes the report, and the exit code is 1 on errors only — the one failing severity (COR-055 point 5). The rule is the umbrella's: a focused surface keeps its own exit, as the same point allows a command run by itself — `refs validate` fails on any finding, drift included. `--only NAME` and `--skip NAME` address members; `--no-refs` is kept as `--skip refs`.

6. **The refs member's split.** Drift between an artifact's front matter and its body is a **warning**: the artifact deploys and resolves regardless, and the body parser is a heuristic. Everything that does not resolve is an **error**. The change is narrow: `pkit validate`'s own exit no longer fails on drift, while the gate gets stronger — the aggregator now runs the check, which it never did.

7. **Checks of a change are not validators.** `pkit friction check`, `pkit migrations check-diff` and `pkit release lint` compare with a base and answer about a *change*; a validator answers about the project's *state* and takes no base named for one run (COR-055 point 2) — mixed in, `pkit validate` would answer differently on the same state. A data point resolves inside `pkit validate`, and its command filler may read history and the default branch (COR-052 point 6). So the query policy removes the base override (`PKIT_CHECK_BASE`) from the environment of every filler and every validator it starts — under `pkit validate`, `pkit status` and `pkit connections resolve` alike — and the `connections` member names, for each such filler, the state it declared and the commit it was read at. Removing the override is the part of that rule the backbone enforces; that a validator reads nothing beyond the working tree except through such a point is its component's obligation, trusted. `pkit validate` therefore answers the same for the same working tree, HEAD, fetched history and default-branch commit, whatever base a pipeline named. The whole-repository friction check reports and never fails (COR-050 point 12) and needs every artefact's full history, so it is not a member; its findings reach `pkit validate` only as the obligations a filler reads from it. Nor is the process engine's check of one subject against a process's invariants, process health or the harness requirement report a member: the core keeps each outside validation, on a surface of its own (COR-055 point 1), so the `process` member checks definitions and never a subject. The diff-scoped checks stay their own lines of the aggregator, which calls `pkit validate` once and drops the lines it subsumes.

## Rationale

**Why a registry.** Five hand-wired passes had diverged in where errors printed, how a finding was located and how an unknown key was phrased, and the sixth would have diverged again. A registry makes the order visible in one place, lets the aggregator call one command so nothing registered can be forgotten there, and gives a capability a way in that does not touch the command.

**Why severity on the finding, not on the surface.** The reasoning is the core's (COR-055, "Why severity on the finding, classified by the owning record"): the same finding must mean the same wherever it prints. What this record adds is where each half sits — the exit rule in the umbrella, in one place, and the classification with the member that raised the finding.

**Why a validator names a command.** The core decides it (COR-055 point 3): a component registers what it can run in one place, and a second registry would be a second place for the command and its limits. In this realisation it would also be a second walker of the same tree. Naming the leaf makes a capability's validator a focused surface for free, lets package validation check the reference as it checks every other, and puts the declaration where ADR-057 asked for it.

**Why drift warns.** A gate that fails on a heuristic parser's reading of prose fails for the wrong reasons — that is why `--no-refs` existed. Drift is real and worth fixing at the source; it is not breakage, and the twelve instances on this repository are now visible in every run instead of hidden behind a flag.

**Why the callable takes only the root.** Every existing pass had that signature, and a capability's command has nothing else to receive. What several members read is shared without a parameter: within the umbrella's process each shared computation — the wiring, the data points — is made once per run and kept for its length, and a data point a capability's validator reads through `pkit connections resolve` comes from the run's cache rather than a second resolution (ADR-057 point 2).

**Why an ADR.** The core decides the contract: what validation owns, how a component joins it, that severity sits on the finding and exactly one severity fails, and that a validator giving no answer fails (COR-055). Where the registry lives, which members the backbone registers and in what order, how a validator's command is run and read, the renderer and — with the references — the literals are project-kit's realisation ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md)), at the altitude of ADR-056.

### Alternatives considered

- **Keep adding passes to the command.** Rejected: the divergence above, and no way in for a capability.
- **Register by import side effect.** Rejected: the order would live in import order, invisible and fragile.
- **A validator as its own script under `validators:`.** Closed by the core, which has a validator name a registered command (COR-055 point 3); here it would also be a second walker, with no place for the declaration ADR-057 puts on a `commands:` entry.
- **A run context passed to every member** (the wiring resolved once). Not taken: what members share is kept for the length of the run without a parameter — computed once per run inside the umbrella's process, and carried by the run's cache to the processes a capability's validator starts — homed with the computations themselves (ADR-057 point 2; COR-052 point 6 lets the resolver keep a value for the length of a run), so the callable keeps taking only the root.
- **Make `refs validate` fail on errors only.** Rejected: the focused surface's charter is the strict lint an author runs; changing its exit is a separate decision.

## Implications

- `project_kit.validators` holds the shape, the backbone's members, the package-metadata reader, the query runner and the renderer; `pkit validate` runs the registry.
- Validators are the first query commands to run, so the declaration's literal (`query-contract: true` on a `commands:` leaf), the offline marker (`PKIT_OFFLINE=1`, with `UV_OFFLINE=1` beside it so a `uv run --script` shebang resolves from uv's cache and never fetches) and provisioning (`pkit init` and `pkit sync` resolve every query command's environment once, online, through `uv sync --script`; a query whose environment is missing is reported as "not provisioned — run `pkit sync`", distinct from a command that answered nothing — #1092) are specified here and in the package-metadata reference — the lifecycle README's package table and literals section; ADR-057 point 3 points here. The package schema gains the block and the declaration; the packages member and the register pre-flight check them. Two shipped capabilities register a validator — living-docs (`living-docs:spaces`) and software-analysis (`software-analysis:artefacts`) — and no adapter does.
- `scripts/check.sh` calls `pkit validate` once and drops `schemas validate` and `decisions validate`: `schemas` is the identical computation (`validate_all(root, resolve=True)`), `decisions` the focused command's id-space check plus front matter. The diff-scoped lines stay. Keep `--skip` out of `check.sh`: an override belongs in an audit-trailed channel, not a bare flag (ADR-019 point 6).
- The query runner is one policy over the backbone's shared command runner (ADR-057 point 5); the `data` member lists the repository through the working tree's one listing (ADR-057 point 2).
- **The contract is core's; this record realises it.** COR-055 decides what validation owns and what stays outside it — the process engine's check of one subject, process health and the harness requirement report among them; that an installed component registers a validator by naming a command it registers; that a finding's severity comes from one shared set of which exactly one fails, on a broken invariant or an owed answer not given; and that a validator giving no answer fails. This record keeps the registry's home, the backbone's members and their order, how a validator's command is run and read, the renderer and, with the references, the literals.
- A member that needs what another computed reads it where it is kept for the run (ADR-057 point 2): the backbone's members in the umbrella's process, a capability's validator through a backbone reading command the run's cache serves. The run-context alternative stays closed.
- Accepted by the maintainer before the trunk builds on it ([PRJ-005](../../../.pkit/decisions/project/PRJ-005-adopt-adrs.md)).
