## Summary

**In plain terms:** the process engine finds where a subject is by asking every state's predicate "is the subject here?" — one script run per state. Where the states are mutually exclusive readings of one fact, as an issue's lifecycle state is, every script computes the same answer and all but one throw it away: `pkit process status` for one issue starts five scripts that each fetch the same issue, about five seconds. This record adds a second way to ask. A state's detection may declare `mode: classified`; its predicate then answers *which* state the subject is in, and the states that name the same predicate share one run. The mode is declared in the definition, never read off the answer, so an engine that does not know it refuses to resolve the position instead of misreading it. An answer the engine cannot place — a state the predicate does not detect, a missing or malformed value — is indeterminate, never "no position"; a predicate says "none of mine" by answering `null`. Nothing else about predicates changes: the same arguments, the same environment, a live read on every invocation.

## Context

`pkit process status` for one project-management issue takes about five seconds. The lifecycle has five states, each with its own detection command; each command starts, fetches the issue, infers the issue's state by the same precedence and reports whether that is *its* state. Six `gh` round trips make up about 70% of the time and six script start-ups about 20%. Every lifecycle verb pays it twice, once to read the position and once to record the move (#1249).

Four constraints bound any fix:

- **The live check is authoritative.** Position is derived from reality on every invocation ([COR-033](../../../.pkit/decisions/core/COR-033-process-substrate.md) point 3). The process reference allows a predicate to be run once per invocation and no caching beyond it.
- **The engine is content-free.** It reads a definition and runs the commands a capability registers; it does not know what a state means (COR-033's decision).
- **Predicates are run one way.** The engine threads the subject to every predicate ([COR-032](../../../.pkit/decisions/core/COR-032-keyed-process-subjects.md)), as its first argument, in the caller's environment but for the run's deadline — the predicate policy that [ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 5 keeps.
- **Drift fails closed.** The engine ships in the binary and definitions ship in the tree, so the two can be at different versions, and an engine must refuse what it does not recognise rather than pass it ([ADR-020](ADR-020-process-engine-code-home.md), Implications).

The last constraint decided the shape. A binary older than the project's content is a normal state: a raised pin leaves the installed tool where it was, and read-only commands still run. A capability's backbone floor is compared with the installed backbone's recorded version at install, upgrade and validation, never with the running binary. So a definition must be safe to hand to an engine older than itself.

The first design let a detection answer carry `state: "<id>"` with nothing in the definition saying so. An older engine reads such an answer as `result` absent, which is false: every issue would have a *determinate* "no position". From there the engine permits wildcard transitions, the health report stays silent, and nothing says why. The definition loader checks no shape at run time, and the one thing in a detection that an already-shipped engine refuses is a `mode` it does not know.

The shapes of what a predicate answers have been decided by architecture record before ([ADR-048](ADR-048-handoff-resolve-seam.md), the hand-off seam's two payloads).

## Decision

**A state's detection may declare `mode: classified`: its predicate answers with the state the subject is in. The engine reads that answer only when it resolves position, fails closed on any answer it cannot place, and project-management's issue lifecycle uses one such predicate for its five states.**

1. **The declaration.** `detection.mode` takes `classified` beside `inferred`. Both derive position from reality, live; they differ in the question the predicate is asked. Under `inferred` it is "is the subject in this state?", answered `{result, reason}`. Under `classified` it is "which state is the subject in?", answered `{state, reason}`, with `detail` optional as before. The mode is declared per state. The declaration selects how an answer is read; the shape of the answer never does.

2. **A classifier and its states.** A predicate is identified by its command and its `with` mapping, which is how the engine's per-invocation memo already keys it. The states whose `classified` detections name one predicate are that classifier's states. The engine runs a classifier once per subject per invocation and reads its one answer for each of its states.

3. **How an answer is read.** For a state S of a classifier:
   - `state` is S's id: S's detection is true.
   - `state` is the id of another of the classifier's states: S's detection is false.
   - `state` is `null`: S's detection is false. The classifier places the subject in none of its states. This is the only way to say so.
   - anything else is **indeterminate**: no `state` key; a value that is neither a string nor `null`; the empty string; a string that is not the id of one of the classifier's states — a state the definition does not declare, or one it declares but whose detection does not name this classifier. Ids are compared exactly, with no trimming and no case folding. The reason names the predicate and quotes what it answered, bounded and with control characters removed as its standard-error tail is.
   - a `result` beside `state` is not read, as an authorisation-artifact gate does not read one. Under `inferred`, a `state` beside `result` is not read. There is no precedence between the two keys, because the mode has already chosen.

4. **Where the reading applies, and where it never does.** It applies in one place: where the engine resolves position from a state's `detection`. Everything that needs a position gets it from that resolution — `status`, `can-move`, `move`, an invariant scoped to a state, the blocked overlay, an embedded inner process, a cascade member's outcome, the health report's confirmation of a candidate. It never applies to a transition gate, an invariant's check, a `resume_when`, an entry guard, a cascade's `members` or `membership`, or the hand-off seam's predicates. None of those carries a `mode`, and each is read as before whatever its answer contains.

5. **Mixed definitions keep the engine's one precedence rule.** A definition may mix the modes and may have more than one classifier. Each state's detection comes out true, false or indeterminate under its own mode. Position is then resolved by the rule the engine already has, unchanged: the first state in declaration order whose detection is true; failing that, indeterminate if any detection was; failing that, none. So an `inferred` state declared earlier that answers true wins over a classifier's state; of two classifiers that each place the subject, the one whose state is declared earlier wins; and a classifier that names a state not its own matches nothing — that is indeterminate under point 3.

6. **One run, and what `with` is.** The single run comes from the memo the engine already keeps for the length of one invocation; this record adds no cache. `with` is part of a predicate's identity and is not passed to the command, whose arguments stay the subject and `--json`. Detections that name one command with different `with` mappings are therefore different predicates and run separately. The process member of `pkit validate` reports a definition in which `classified` detections name one command under different `with` mappings, or in which one command is named under both modes.

7. **What a failed run shows.** A classifier that gives no answer — a non-zero exit, a timeout, no JSON object — leaves every one of its states indeterminate, with the one cause and the one standard-error tail. In `--json` output `position.unevaluated` keeps one entry per state, its shape unchanged, since consumers match on it. In the narrative views and in a refusal, the cause and what the predicate said are printed once per predicate, with the states it leaves unknown listed beside it. When a classifier answers `null` and no state matches, the narrative `status` shows the classifier's reason under "no position".

8. **Version skew.** An engine that does not know `classified` treats each such state as indeterminate and says the mode is not implemented. The position is then indeterminate: `move` refuses, the health report lists the subject as indeterminate, and a cascade holds its fold. That branch exists in every shipped engine, which is why the kind is declared in `mode` and not in a new key. A capability whose definition uses the mode declares the backbone it needs in its changeset; that floor guards install, upgrade and validation, and the fail-closed reading covers a binary older than the floor.

9. **project-management's lifecycle.** The capability ships one classifier command, and the five states of the issue lifecycle name it under `classified`. It reads the issue once. It answers the inferred state when that is one of the lifecycle's states, and `null` otherwise with the inferred value in the reason. When the read fails it writes the cause on standard error and exits non-zero. The five per-state detection commands stay registered, for a project's own override of the definition and for direct use. `move-issue` already treats an indeterminate engine position as it treats an unreachable engine — it infers locally by the same precedence and reports the engine's refusal as a warning — so the verbs keep working under an older binary; this record leaves that fallback as it is.

10. **What does not change.** The live check stays authoritative and nothing is cached beyond one invocation. A predicate still receives the subject and `--json`, in the caller's environment but for the deadline, bounded at thirty seconds. An `inferred` detection is read exactly as before. A move still reads position after the caller's side-effect, and `--from` still names the origin.

## Rationale

**Why a second question and not a shared read.** The five scripts repeat one computation because the engine can only ask about one state at a time. A read shared between the scripts would remove the repeated fetch and keep the repeated computation, and it would do so by giving predicates a place to leave data for each other — the first state the engine would broker between a capability's commands on this path. Today each predicate answers from reality alone, which is what lets each be judged and tested alone. Asking the question the capability can actually answer removes the repetition where it starts and leaves the runner as it is. It also gives one home to "which state is this issue in", the property ADR-057 point 2 asks of every computation readers must agree on.

**Why the definition declares it, in `mode`.** An answer that selects its own reading can be read two ways by two engines, or by one engine when both keys are present. A declaration cannot. Of the places a declaration could go, only `mode` is refused by engines already shipped: the schema forbids an unknown key in a detection, but the loader checks no shape at run time, and the schema file travels with the content, so an older engine would ignore a new key and read the answer as false. `mode` is the seam the engine was given for this: position resolution treats a mode it does not implement as indeterminate, never as a silent "not in this state".

**Why `null` for none, and indeterminate for the rest.** "No position" and "position unknown" lead to different places: from none the engine permits wildcard transitions and the health report drops the subject; from unknown it refuses and reports. A misspelt id, a stray label that infers a state the lifecycle does not have, or an id from a later version of the definition must not land on the permissive side. Making "none" something the predicate has to say on purpose keeps every accident on the refusing side.

**Why a classifier may name only its own states.** If it could name any declared state, a classifier naming a state whose own detector says no would yield a determinate "none" out of two readings that contradict each other. Limiting it to the states that name it makes that contradiction indeterminate and keeps the rule to one sentence.

**Why the precedence rule is left alone.** First-declared-wins is what the engine does for two `inferred` states that both answer true, and a shipped definition records that its order is load-bearing. Detecting ambiguity for one mode only would give two rules; detecting it for both changes how existing definitions resolve, which is a separate decision.

**Why an architecture record.** The change adds a payload shape and failure semantics to how position is resolved, across the backbone and a capability. ADR-048 is the precedent for deciding a predicate's payload in this decision space ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md)). What this record cannot decide is stated first under Implications.

### Alternatives considered

- **Read `state` whenever an answer carries it and no `result`, with nothing declared.** Rejected: an older engine reads every subject as determinately positionless; an answer carrying both keys would be true for every state; and an unrecognised state would read as "no position".
- **A new key beside `mode` in the detection.** Rejected: engines already shipped do not refuse it at run time.
- **Signal the kind by the answer's shape** — a JSON string in place of an object, which older engines happen to refuse. Rejected: it relies on an accident of error handling, gives up `reason` and `detail`, and tells the operator "not an object" where the truth is "upgrade".
- **Have the engine announce itself in the environment and the classifier refuse without it.** Rejected: fail-closed would rest on every predicate author remembering the check, and it adds an environment variable to the predicate policy.
- **A per-invocation read memo** — the engine passes predicates a private directory in a new environment variable, and the capability's tracker read goes through it. It needs no change to how position is read and degrades to today's behaviour under an older engine. Not chosen as the first step: it saves the same time while keeping the five runs, and it opens a channel between predicates that the engine cannot police. It is deferred rather than rejected (Implications), and is the design to build if the mode is not authorised.
- **The engine runs one declared subject read and pipes it to every predicate.** Rejected: a second channel beside the subject argument, one more script run than today, and the largest surface of the options.
- **Stop at the first matching state.** Rejected as the fix: it saves at most the states declared after the match.
- **Run detectors in-process, or in parallel.** Rejected: the first has the engine import capability code (ADR-020); the second still makes every fetch.

## Implications

- **Raised for the maintainer before acceptance.** `detection.mode` belongs to the shape contract every adopter's process definitions conform to. COR-033 point 5 names stored and hybrid detection as extension points, and its Implications make each "its own future decision"; it names no second inferred mode, and each earlier widening of the shape arrived with a core record. This record realises the mode; it does not authorise the widening. Whether a core record must — a new one, or a refinement of COR-033 — or the process reference may carry it under this record, as ADR-057 carried its reading of the network limit while the question was filed, is the maintainer's decision, made before this record is accepted. If the mode is not authorised, the read memo above is the design to build and this proposal is dropped.
- **Surfaces.** Backbone: position resolution in the engine, with the reading kept out of the function that gates, invariants, membership and `resume_when` share; the narrative and refusal rendering of point 7; the process member of `pkit validate` (point 6). The process reference: the `mode` line of the shape, the predicate-runner contract's list of readings, its failure paragraph and its performance paragraph. The shape contract: the `mode` enum and its description, the `detection` and `predicate` descriptions, and the `with` description, which says the mapping is passed to the command. The authoring stamp's payload example and the `--state` help text of `pkit process new`, which describe `inferred` and stay correct for what the stamp writes. project-management: the classifier command and its registration, the definition's five detections and its header comment, the predicate module's docstrings, the capability README's detector paragraph, and the test that enumerates the detection commands.
- **Changesets.** Backbone `minor`: an additive enum value and reading; no `schema_version` moves and nothing is renamed or removed, so no migration. project-management `minor`, with `requires_backbone: release`: a new command and a changed definition; the per-state commands remain, so a project's override at `mode: inferred` keeps working and needs no migration.
- **Tests that pin it.** Engine, with a fixture classifier that counts its runs: one run per `status`, per `can-move` and per cascade member; each of its states answered gives that position; `null` gives a determinate none; an undeclared id, a declared state that is not the classifier's, a wrong case, surrounding whitespace, the empty string, a number and a missing key each give indeterminate with the value in the reason; `state` with `result: true` reads by `state`; a failed run gives one run, one entry per state in `position.unevaluated`, one block in the narrative, and a refused `move`; the four mixed cases of point 5; detections with different `with` run separately and are reported by validation; a `state` key in the answer of a gate, an invariant, a membership test and a `resume_when` changes nothing; a failing classifier on a cascade member holds the fold; an unknown mode is indeterminate, which is the older engine's branch; two invocations around an answer that changes see the change; `move --from` after the side-effect. project-management: across the full truth table — the shipped labels, a remapped label, a derive binding, closed issues, milestones — the classifier agrees with the inference function and with each per-state command, whose existing parity tests stay untouched and are named in the pull request; the issue is fetched exactly once; a failed fetch exits non-zero with the cause on standard error.
- **project-management's record.** [project-management:DEC-033-rebind-issue-lifecycle-onto-process-substrate] D2 gives every state `mode: inferred` with its own detector; the capability refines that point when it adopts the mode.
- **Deferred.** The per-invocation read memo, which would also fold the gates' reads into the one fetch: a follow-up with its own record, since it changes the environment sentence of the predicate policy. Memoising the cascade fold within one invocation, which changes no behaviour and needs no record. Teaching `pkit process new` to stamp a classifier: the stamp writes one `inferred` stub per state, a definition adopts the mode by a shape edit ([COR-044](../../../.pkit/decisions/core/COR-044-process-authoring-layer.md) point 1), and stamp support waits for a second definition that wants it. A run-time check of the running binary against a capability's backbone floor.
