## Summary

**In plain terms:** the process engine finds where a subject is by asking every state's predicate "is the subject here?" — one script run per state. Where the states are mutually exclusive readings of one fact, as an issue's lifecycle state is, every script computes the same answer and all but one throw it away: `pkit process status` for one issue starts five scripts that each fetch the same issue, about five seconds. A state's detection may instead declare `mode: classified`; its predicate then answers *which* state the subject is in, and the states that name the same predicate share its one answer.

That the mode exists is the core record's decision, because the shape of a definition is every adopter's ([COR-033](../../../.pkit/decisions/core/COR-033-process-substrate.md) point 5). This record decides the rest: what such a predicate may answer and how an engine reads it, in any project, and then how project-kit's engine and its project-management capability realise it.

Three properties carry the design. The mode is declared in the definition, never read off the answer, so an engine that does not implement it leaves those states indeterminate; where every state uses the mode, that engine refuses to resolve a position. An answer the engine cannot read — a state the predicate does not detect, a missing or malformed value — leaves those states indeterminate as well, never "none of these"; a predicate says "none of mine" by answering `null`. Nothing else about predicates changes: they are started with the same arguments in the same environment, and reality is read live every time.

The refusal is the engine's. project-management's verbs do not stop on it: under a binary older than the mode they move issues on their own local inference, and each move the engine refuses to record leaves a warning and, where a journal is kept, a gap in it.

## Context

`pkit process status` for one project-management issue takes about five seconds. The lifecycle has five states, each with its own detection command; each command starts, fetches the issue, infers the issue's state by the same precedence and reports whether that is *its* state. A sixth run, the checkbox gate on a transition out of the current state, fetches the issue once more. The six `gh` round trips make up about 70% of the time and the six script start-ups about 20%. Every lifecycle verb pays it twice, once to read the position and once to record the move (#1249).

Five things bound any fix:

- **The shape is every adopter's.** The vocabulary of a definition belongs to the shape contract all definitions conform to, and the core record on the substrate owns it. That record names two detection modes that read reality live — `inferred`, which asks each state, and `classified`, which asks once which state — and leaves stored and hybrid detection unbuilt (COR-033 point 5).
- **The live check is authoritative.** Position is derived from reality on every invocation (COR-033 point 3). The process reference lets a predicate be evaluated at most once per command and arguments in an invocation, and keeps no position from one invocation to the next.
- **The engine is content-free.** It reads a definition and runs the commands a capability registers; it does not know what a state means (COR-033's decision).
- **Predicates are run one way.** The engine threads the subject to every predicate ([COR-032](../../../.pkit/decisions/core/COR-032-keyed-process-subjects.md)), as its first argument, in the caller's environment but for the run's deadline — the predicate policy that [ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 5 keeps.
- **Drift fails closed.** The engine ships in the binary and definitions ship in the tree, so the two can be at different versions ([ADR-020](ADR-020-process-engine-code-home.md)). That record requires the engine to refuse an unrecognised or schema-future gate. For a detection mode the engine does not implement, the core record sets the matching rule: the state is indeterminate, never "not in this state" (COR-033 point 5).

A binary older than the project's content is a normal state: a raised pin leaves the installed tool where it was, and read-only commands still run. A capability's backbone floor is compared with the installed backbone's recorded version at install, upgrade and validation, never with the running binary. So a definition must be safe to hand to an engine older than itself.

What an older engine does with a newer definition is narrow. The definition loader checks no shape at run time, and the shape contract's file travels with the content, so an engine passes over a key it does not know. The one thing in a detection it does not pass over is a `mode` it does not implement: it treats that state as indeterminate.

## Decision

**Under `mode: classified` a state's detection asks its predicate which state the subject is in. States that name the same predicate share its one answer, and an answer the engine cannot read leaves each of them indeterminate. project-management's issue lifecycle adopts the mode, with one such predicate for its five states.**

**What is decided here and what is not.** That `detection.mode` may be `classified`, and that an engine treats a mode it does not implement as indeterminate, are decided by the core record (COR-033 point 5). This record realises them and adds no word to the shape that the core record does not name. Points 1–8 are the contract: what a classifier in any project's definition may answer, and how an engine reads it. They reach adopters through the process reference. Points 9–14 are project-kit's own: how its engine runs and reports a classifier, and how its project-management capability adopts the mode.

### The contract: what a classifier answers and how an engine reads it

1. **The declaration.** A state's `detection.mode` is `inferred` or `classified`. Both read reality live on every invocation; they differ in the question the predicate is asked. Under `inferred` it is "is the subject in this state?", answered `{result, reason}`. Under `classified` it is "which state is the subject in?", answered `{state, reason}`. `detail` is optional under both. The mode is declared per state. The declared mode selects how an answer is read; the shape of the answer never does.

2. **A classifier and its states.** A **classifier** is a predicate that at least one state names in a `classified` detection; the states that name it are *its states*. Two detections name the same predicate when they name the same command with the same `with` mapping. The engine reads one answer from a classifier for all of its states. What `with` means to the command is not decided here: the shape contract describes it as arguments passed to the command, and the runner does not pass it (#1252).

3. **How a classifier's answer is read.** The one answer is read for each state S of the classifier:
   - `state` is S's id: S's detection is true.
   - `state` is the id of another of the classifier's states: S's detection is false.
   - `state` is `null`: the detection of every one of the classifier's states is false. The classifier places the subject in none of its states, and this is the only way to say so.
   - anything else is **unreadable**, and the detection of every one of the classifier's states is indeterminate: no `state` key; a value that is neither a string nor `null`; the empty string; a string that is not the id of one of the classifier's states — a state the definition does not declare, or one it declares but whose detection does not name this classifier. Ids are compared exactly, with no trimming and no case folding.
   - a `result` beside `state` is not read, as an authorisation-artifact gate does not read one. There is no precedence between the two keys, because the mode has already chosen.

4. **An `inferred` detection is read as before.** It is read by `result`; a `state` beside it is not read; and an answer with no `result` is false, not indeterminate. This record leaves that last rule alone, so the two modes differ: a missing `state` under `classified` is indeterminate, a missing `result` under `inferred` is false. One consequence: a classifier's command named under `inferred` reads as false for that state, and a definition that names it so for every state resolves every subject to a determinate "no position". The engine cannot tell, because it reads an answer by the declared mode.

5. **Where the reading applies.** In one place: where the engine resolves position from a state's `detection`. Everything else that needs a position takes it from that resolution. A predicate declared anywhere else in a definition carries no `mode`, and is read as before whatever its answer contains.

6. **Mixed definitions keep the engine's one precedence rule.** A definition may mix the modes and may have more than one classifier. Each state's detection comes out true, false or indeterminate under its own mode, and position is then resolved by the rule the engine already has, unchanged: the first state in declaration order whose detection is true; failing that, indeterminate if any detection was; failing that, none. Four cases follow:
   - An `inferred` state and a classifier's state are both true: the one declared earlier is the position.
   - Two classifiers each place the subject: the state declared earlier is the position.
   - A classifier names a state that is not its own — an `inferred` state, or another classifier's: its answer is unreadable (point 3) and its own states are indeterminate. It does not make the named state true.
   - One state's detection is indeterminate and another's is true: the position is the true state, determinately, wherever the two are declared. A failed or unreadable classifier therefore makes the position indeterminate only when no state outside it answers true.

7. **An engine that does not implement the mode.** It treats each `classified` state as indeterminate and says the mode is not implemented (COR-033 point 5). Where every state of a definition is `classified`, the position is indeterminate: `move` refuses, the health report lists the subject as indeterminate, and a cascade holds its fold. Where a definition mixes the modes, the last case of point 6 applies to that engine too: an `inferred` state that answers true is the position, which is a misreading wherever a `classified` state declared before it would have been true. A mixed definition is safe under such an engine only if its detections are mutually exclusive. A capability whose definition uses the mode declares the backbone it needs; that floor guards install, upgrade and validation, and this reading is all that guards a running binary older than the floor.

8. **What does not change.** The live check stays authoritative and no position is kept beyond one invocation. A predicate still receives the subject and `--json`, in the caller's environment but for the deadline, bounded at thirty seconds. A move still reads position after the caller's side-effect, and `--from` still names the origin.

### The realisation in project-kit

9. **One run for each reading of a subject's position.** While the engine reads one subject it keeps each predicate's answer in an answer memo, keyed on the command and its `with` mapping, and a classifier's states share the memo's one entry. The subject an invocation names has one memo for the whole invocation, so its classifier runs once however many of the engine's operations need the position. An embedded inner process and a cascade member get a fresh memo each time the engine resolves their position, and one invocation can resolve a cascade member more than once; a member's classifier runs once for each of those resolutions, not once for the invocation. This record adds no cache and changes the reach of none.

10. **Validation.** The process member of `pkit validate` reports a definition in which `classified` detections name one command with different `with` mappings — they are separate classifiers, each with only its own states — or in which one command is named under both modes.

11. **What a classifier without a readable answer shows.** A classifier that gives no answer — a non-zero exit, a timeout, no JSON object — leaves every one of its states indeterminate, with the one cause and the one standard-error tail. An unreadable answer is shown the same way; its reason names the predicate and quotes what it answered, bounded and with control characters removed as a standard-error tail is. In `--json` output `position.unevaluated` keeps one entry per state, its shape unchanged, since consumers match on it. In the narrative views and in a refusal, the cause and what the predicate said are printed once per classifier, with the states it leaves indeterminate listed beside it.

12. **What `null` shows.** When a classifier answers `null` and no state is true, the narrative `status` shows the classifier's reason under "no position".

13. **project-management adopts the mode.** The capability ships one classifier command, and the five states of the issue lifecycle name it under `classified`, in the release that ships the engine's support. The command reads the issue once, so detection fetches an issue once for each reading of its position — the first criterion of #1249. It answers the inferred state when that is one of the lifecycle's states. When the inference yields a value the lifecycle does not declare, it answers `null` with that value in the reason, which is what the five per-state commands say today, each answering false. When the read fails it writes the cause on standard error and exits non-zero. The five per-state detection commands stay registered, for a project's own override of the definition and for direct use. Every state's detection changes, so the definition's `version` rises: edits to a definition's states raise it ([COR-044](../../../.pkit/decisions/core/COR-044-process-authoring-layer.md) point 3). The file's `schema_version` does not move, since the file's shape is unchanged.

14. **project-management under a binary older than the mode.** The engine refuses to resolve an issue's position: all five states are indeterminate (point 7). The capability's verbs do not stop. The command that moves an issue between states treats an indeterminate engine position as it treats an unreachable engine: it infers the state locally, by the same precedence, and carries on. So under such a binary every lifecycle verb moves issues on local inference. The engine refuses to record each move, which leaves a warning carrying the engine's reason and, where the project keeps a journal, a gap in the journal. The closure cascade holds, because the fold cannot resolve its members, so no container closes by cascade until the binary is upgraded. This record leaves that fallback as it is.

## Rationale

**Why a second question and not a shared read.** The five commands repeat one computation because the engine can only ask about one state at a time. A read shared between the commands would remove the repeated fetch and keep the five runs, and it would do so by giving predicates somewhere to leave data for each other — the first data the engine would carry between a capability's commands on this path. Today each predicate answers from reality alone, which is what lets each be judged and tested alone. Asking the question the capability can actually answer removes the repetition where it starts and leaves the runner as it is.

**Why the definition declares it, in `mode`.** An answer that selects its own reading can be read two ways by two engines, or by one engine when both keys are present. A declaration cannot. Of the places a declaration could go, only `mode` is refused by engines already shipped: the schema forbids an unknown key in a detection, but the loader checks no shape at run time, and the schema file travels with the content, so an older engine would pass over a new key and read the answer as false. A mode an engine does not implement is different: the engine treats it as indeterminate, never as a silent "not in this state", which is the rule the core record sets for every mode.

**Why `null` for none, and indeterminate for the rest.** "No position" and an indeterminate position lead to different places: from none the engine permits wildcard transitions and the health report drops the subject; from indeterminate it refuses and reports. A misspelt id, a value of the wrong type, or an id from a later version of the definition must not read as "none of these". Making "none" something the classifier has to say on purpose keeps every accident in an answer from being read as "none". Two accidents lie outside an answer, and this record leaves both as they are: a classifier's command declared under `inferred` (point 4), and a true detection elsewhere in the definition deciding the position (point 6).

**Why a missing `result` stays false.** Reading it as indeterminate would give both modes one rule and close the gap point 4 names. It would also change how every existing definition reads an answer without `result`, so it is a decision about `inferred`, not about this mode.

**Why a classifier may name only its own states.** If it could name any declared state, a classifier naming a state whose own detector says no would yield a determinate "none" out of two readings that contradict each other. Limiting it to the states that name it makes that contradiction indeterminate and keeps the rule to one sentence.

**Why the precedence rule is left alone.** First-declared-wins is what the engine does for two `inferred` states that both answer true, and a shipped definition records that its order is load-bearing. A true detection winning over an indeterminate one is what it does when one of several detectors fails. Detecting ambiguity, or holding the position back, for one mode only would give two rules; doing it for both changes how existing definitions resolve, which is a separate decision.

**Why one run for each reading, not one for each invocation.** That is the reach the answer memo has. A fold resolves each member afresh under `inferred` as well, where it costs a run per state; the mode cuts that to one run per resolution. Letting a fold reuse a member's answers is an improvement to the fold, and is deferred with it.

**Why the core record names the mode and this record does the rest.** The shape is shared by every adopter's definitions, so a word in its vocabulary is a core decision. How an engine reads an answer, what it shows, and what one capability does with the mode are realisation, which this project records as architecture decisions ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md)). The hand-off seam was decided the same way: the core record fixed the fields of the contract, and [ADR-048](ADR-048-handoff-resolve-seam.md) then fixed what its two predicates answer.

### Alternatives considered

- **Read `state` whenever an answer carries it and no `result`, with nothing declared.** Rejected: an older engine reads every subject as determinately positionless; an answer carrying both keys would be true for every state; and an unrecognised state would read as "no position".
- **A new key beside `mode` in the detection.** Rejected: engines already shipped do not refuse it at run time.
- **Signal the mode by the answer's shape** — a JSON string in place of an object, which older engines happen to refuse. Rejected: it relies on an accident of error handling, gives up `reason` and `detail`, and tells the operator "not an object" where the truth is "upgrade".
- **Have the engine announce itself in the environment and the classifier refuse without it.** Rejected: fail-closed would rest on every predicate author remembering the check, and it adds an environment variable to the predicate policy.
- **A shared read** — the engine passes predicates a private directory in a new environment variable, and the capability's tracker read goes through it. It needs no change to how position is read and degrades to today's behaviour under an older engine. Not chosen: it removes the repeated fetch and keeps the five runs, and it opens a channel between predicates that the engine cannot police. This decision does not exclude it; on top of the mode it would also cover the gates' reads (Implications, Deferred).
- **The engine runs one declared subject read and pipes it to every predicate.** Rejected: a second channel beside the subject argument, one more script run than today, and the largest surface of the options.
- **Stop at the first matching state.** Rejected as the fix: it saves at most the states declared after the match.
- **Run detectors in-process, or in parallel.** Rejected: the first has the engine import capability code (ADR-020); the second still makes every fetch.

## Implications

- **This record stands on the core record.** The mode, and the rule for a mode an engine does not implement, are in the shape's vocabulary by COR-033 point 5. Without that text this record has nothing to realise, so it is accepted only once the core record carries it.
- **Where the reading lives.** The `state` reading belongs to position resolution alone. The reading that gates, invariant checks, membership tests and `resume_when` share does not gain it (point 5).
- **What an adopter reads changes with the engine.** The shape contract and the process reference describe the mode in the same change that ships the engine's support, and the process reference carries points 1–8. Which files that touches, and the tests that pin the behaviour, belong to the building issue (#1249).
- **Changesets.** Backbone `minor`: an additive enum value and reading; no `schema_version` moves and nothing is renamed or removed, so no migration. project-management `minor`, with `requires_backbone: release`, since it ships in the release that ships the engine's support: a new command and a changed definition; the per-state commands remain, so a project's override at `mode: inferred` keeps working and needs no migration.
- **project-management's record.** [project-management:DEC-033-rebind-issue-lifecycle-onto-process-substrate] D2 gives every state `mode: inferred` with its own detector, and its Implications call the order of states load-bearing because the engine returns the first matching detection. When the capability adopts the mode, its record owes three statements: that the five states name one classifier under `classified`; that the per-state detectors stay registered, and why; and what the order of states decides once one answer makes at most one of the five true. Whether that is a refinement of D2 or a record that supersedes it is the capability's to decide.
- **Deferred.** A shared read between a subject's predicates, which would fold the gates' reads into the one fetch: a follow-up with its own record, since it changes the environment sentence of the predicate policy. Letting a fold reuse a member's answers within one invocation: it changes no verdict and needs no record. Teaching `pkit process new` to stamp a classifier: the stamp writes one `inferred` stub per state, a definition adopts the mode by a hand edit to its states, which the authoring layer does not cover (COR-044 point 3 defers edits to an existing definition's states), and stamp support waits for a second definition that wants it. A run-time check of the running binary against a capability's backbone floor.
