## Summary

**In plain terms:** every final release takes the ordinary path, whatever candidates are out: a release PR from the default branch's head, which lands only what the release step wrote, onto the commit it was planned from, and which project-kit tags once it merges. No command asks which candidates are out. A candidate is cut from the head of the branch the release workflow is started on, once that branch has taken in the default branch's head. A cut's number counts every candidate the remote holds, so with `2.2.0rc1` cut from one branch, the next cut, from a branch with a breaking change, is `3.0.0rc2`. A tester enters a candidate only from a final release no newer than the one its branch last took in, and leaves it only by leaving the testers' branch in its own project, so a branch may change its migration scripts until it merges.

## Context

[PRJ-016](../../../.pkit/decisions/project/PRJ-016-candidates-hold-no-release.md) decides that a change that must be tested before it ships is tested on its own branch before it merges, that every final release is the ordinary release from the default branch's head, and that a project tries each candidate fresh, from a final release. [ADR-089](ADR-089-release-candidates.md) points 1, 2, 3 and 9 build the opposite. A candidate is cut from the default branch's head alone, a cut refuses while a line runs at another version, and the final release is cut from the last candidate's source commit and tagged before its pull request. The merge refuses what cannot wait, and every other release PR while a line runs.

ADR-089 points 5 and 8 move a project from each candidate to the next and on to the final release, each move running the final release's folder again. Scripts a candidate shipped kept add-only, and folders idempotent as a whole, keep those moves safe while no other release ships. Under PRJ-016 the default branch releases while candidates are out, and a branch merges once its testing passes, whether or not a release PR is open.

None of those points is built ([#2211](https://github.com/aleskalfas/project-kit/issues/2211)), and the default branch's ordinary release starts by hand. A release PR merged after another pull request landed since its plan, or after a commit was pushed onto its branch, would ship that change in its release, under versions the change's changesets did not move, against one version, one content ([COR-059](../../../.pkit/decisions/core/COR-059-version-transition.md) point 9; ADR-065 point 12), whether or not a candidate is out.

## Decision

**Every final release is the ordinary release PR, which lands only what the release step wrote, onto the commit its plan read; a candidate is cut from a branch that has taken in the default branch's head and numbered across every candidate; and a project enters a candidate only from a release no newer than the one its branch took in, and moves from it to no other release, so a branch's scripts are its own until it merges.**

### 1. A final release is planned and written from the default branch's head

`pkit release plan` and `apply` without `--pre` plan and write a final release from the default branch's head, as PRJ-016 point 1 sets, in every project that releases through `pkit release`. No cut, plan, write or merge reads which candidates are out.

### 2. A candidate is cut from a commit that has the default branch's head in its history

`pkit release plan --pre` and `apply --pre` plan from the commit they run at: the versions it records and the changesets pending in its tree, the default branch's and its own branch's (PRJ-016 point 3). They refuse, before writing anything, where the default branch's head, read from the remote, is not in that commit's history. The release workflow's pre-release run cuts from the head of the branch a person starts it on, once `pkit release check --base <default branch>` passes there, so no candidate carries a surface change no changeset moves. That run reads no label, so a branch whose pull request passes by `skip-changeset` is cut only once it carries a `none` changeset. This binds project-kit's own cut alone (ADR-089 point 2).

### 3. A cut's number counts every candidate

`N` is one past the highest number any candidate tag on the remote carries, whatever its version, and 1 where there is none. The counter refuses where it cannot read the remote's tags, and is project-kit's own.

### 4. A withdrawal is a tag, which `pkit upgrade --pre` passes by and `pkit pin` warns of

`pkit upgrade --pre` takes the newest release as ADR-089 point 8 sets, whatever branch a candidate was cut from, and passes by a withdrawn candidate. Each candidate's notes name `pkit pin <candidate>` as the way into it, beside ADR-089 point 8's first hop, and `pkit pin` warns where it names a withdrawn candidate. A person withdraws a candidate by pushing the tag `withdrawn/v<candidate>` on the candidate's commit (PRJ-016 point 5), and its Release says so. That tag is never moved or deleted either, and `pkit version untag` refuses a candidate's tag; a deletion by hand lies outside, as any act write access allows. The withdrawal's tag names no install, since no reader of release and candidate tags takes it for either (PRJ-004, as PRJ-016 refines it). The withdrawal is project-kit's, and the reading of it binds every project that tests a candidate.

### 5. A run without the input is the ordinary release run

The release workflow, started without its "pre-release" input, refuses on any branch but the default branch, and there opens the ordinary release PR. It first finishes the notes an earlier run left unpublished, and where that fails it says so and goes on. Past a pull request's cap, the release PR's body links its changelog section on its release branch, since its tag is cut only once it merges. The workflow is project-kit's own.

### 6. A release PR lands only what its release step wrote, onto the commit its plan read

- **The predicate.** A release lands sound where the commit it lands on is its plan's commit, and its change from that commit holds only the files and lines `pkit release apply` writes, plus answer files it adds. Its content half lives in the recogniser `pkit release check` already has for a diff that is only what `apply` writes, and one module holds the whole predicate (ADR-057 point 2).
- **The plan's commit.** `pkit release apply` prints a trailer line naming the commit of the default branch its plan read. The release commit and the release PR's body carry that line: the release workflow writes both, and the release README's manual sequence commits and opens the PR with the line `apply` printed. A reader matches the line anywhere in a message or a body, and finds the release commit on the release branch as the one commit that carries it.
- **`pkit release merge`** applies the predicate at its request, on every base, to the default branch's head read from the remote and the PR's head. It refuses a PR whose body lacks the trailer, or names another commit in it than its release commit does. On a base with a merge queue, it refuses to enqueue a release PR behind another pull request, so none lands ahead of it through the queue, whether or not the project's required check runs the queue's check. A direct merge carries the PR's body read just before the request (ADR-061 point 8), which #2211 builds in the landing if #1220 has not.
- **The queue's check.** A command under `pkit release`, which the build names, applies the predicate to a merge queued in a queue that squashes: to each squash commit from the group's base to its head whose subject is a `chore(release):` one, with its parent as the commit it lands on and the trailer in its own message as the plan's commit.
- **A missing trailer.** The queue's check refuses a `chore(release):` commit without one. Each refusal of a release without the trailer names the way on: run the release again, never amend the release commit.
- **The tag.** `pkit version tag` tags a final release only: the newest commit at or before HEAD on the default branch's first-parent history that changed `.pkit/VERSION`, named by the version that commit records. It refuses where HEAD is off that history or where that tag exists, so the release-tag workflow and the manual path tag one commit. A candidate's tag stays on the commit its cut made (ADR-089 point 9), which the pre-release run tags through `apply --pre --tag`. `apply --tag` without `--pre` is refused, naming `pkit version tag` after the merge, since a final release is tagged only once it lands.
- **The way on.** The release workflow, run while a release PR whose plan read an older head of the default branch is open, replaces that PR with one planned from the new head.
- **Where each binds.** `pkit release merge` binds every project that releases through `pkit release`. The queue's check binds where a project's required check runs it, as project-kit's will once its queue is on (ADR-078). The tag is project-kit's alone, since an adopter's release cuts no tag (ADR-089 point 2; the release README).

### 7. A project on a candidate moves to no other release

Every `pkit upgrade`, with or without `--pre`, and every raise by `pkit pin` refuses, before it writes anything, to move a project whose manifest records a candidate to any release but that candidate (PRJ-016 point 4). `pkit upgrade --pre` there targets that candidate, so it only finishes a move to it cut short. The message names the one way off PRJ-016 point 4 sets, for a project a candidate's `init` installed too. This binds every project that tests a candidate.

### 8. A branch's scripts are its own until it merges, and no release ships one stranded

A script a candidate shipped may be edited, renumbered, moved or removed until its branch merges, as any script on a branch. When the branch takes in the default branch, it moves each of its scripts out of a folder at or below the version the default branch now records. The guard below holds a branch above its fixed version, and `pkit migrations check-diff` holds it above the version the default branch records, as it holds any script a change adds.

- **The guard.** `pkit release plan` and `apply`, with and without `--pre`, refuse, before writing anything, where a tier holds a migration script the fixed version's commit did not hold, in a folder at or below the tier's fixed version, other than a script the project receives from elsewhere: by sync, or by a capability's install or upgrade. The refusal names a folder above the version the tier records, so the move passes `check-diff` too.
- **The fixed version,** the newest version whose scripts are fixed, and its commit, chosen per project by ADR-059's marker test:
  - in the methodology's source repository, the version the tier records at the newest final release tag, read from the remote's tags, and the commit of the first final release tag that carries that version. Candidate tags, `withdrawn/` tags and `latest` count for none. The guard refuses where it cannot read the remote's tags, as point 3's counter does, or the tag's commit.
  - in every other project, the version the default branch's head records, as `check-diff` reads it, and the first commit of the default branch's first-parent history that records it. The guard refuses where it cannot read that commit, including where the clone's history stops before it (ADR-081 point 6).
- **Where it binds:** every project that releases through `pkit release`.
- **The window on the default branch.** A pull request's checks read the default branch as it stood at their run, so a merge after a release can strand a script there, where it stays until the next release's plan refuses and a change moves it. A project that wants no such window requires each change to be up to date with its base, or merges through a queue whose run checks the merge. Otherwise it accepts the cost.

### 9. A candidate admits no project above its base

A cut records its base in the candidate's tree: the version the backbone and each component record at the commit it is cut from. The candidate's own upgrade reads the base from its own bundle, and keeps PRJ-016 point 4's limit on entry: it refuses, before it writes anything, where the window it would run for the backbone or for any component starts above the version the base records for it, and its message names entering from a final release at or below the base, or waiting for the next cut. No transition carries the base into a project's tree. project-kit's cut writes the base, and the refusal binds every project that enters a candidate.

### 10. A run on a branch runs that branch's code, so its checks guard against mistakes alone

A run started on a branch runs that branch's release workflow and the `pkit` it runs. So the run's own checks are an interlock against mistakes, not a defence against a branch that edits the release code:
- the history check and `pkit release check` (point 2);
- the counter (point 3);
- point 5's refusal off the default branch;
- the guard (point 8) and the cut's base (point 9);
- ADR-089 point 9's concurrency group.

Git's refusal of a push that would move a tag that exists, unless the push is forced, holds whatever code the branch runs. Point 6's refusals at the merge hold against a mistake that breaks point 5 alone. The release workflow and the `pkit` it runs force no push and delete no tag, so a cut whose branch keeps them as the default branch has them cannot give a pushed candidate tag a second content, even where its counter slipped. This binds project-kit's own workflows alone.

## Rationale

**Point 1.** Every part of ADR-089 point 3 existed because the final release shipped an older commit than the head. Those parts are the source commit found from the tags, the tag before the pull request, the squash of the tagged commit into a moved default branch, and the refusals of what cannot wait. Cut from the head, the final release needs none of them.

**Point 2.** A commit with the default branch's head in its history holds the versions that branch records and every changeset pending there, beside its own branch's. So its plan is the one the default branch's release would compute once the branch merges. The remote is read since a clone's copy of the default branch may lag behind it. A cut is the first to ship what its branch changed, where ADR-089 cut only what had merged past the changeset guard, so the cut runs that guard itself. The cost is a cut refused when a merge lands before it, run again once the branch takes in the new head.

**Point 3.** A counter for each backbone version kept candidates apart only while one line ran at a time (PRJ-016 point 5). A shared counter keeps them apart however branches' candidates overlap, from the remote's tags alone. Its cost is that a version's first candidate may not be `rc1`. No project moves from one candidate to another (point 7), so a cut answers to no earlier candidate: a component lower than in an earlier one, or a second cut of one commit, breaks no move. What a cut answers to is each final release made after it, which the cut's base keeps out (point 9).

**Point 4.** `pkit upgrade --pre` reads the remote's tags alone, as ADR-063 point 1's lookup does, and needs nothing of the host's own interface. A dropped branch's candidate may stay the newest for good, so a withdrawal must reach that lookup, and a tag on the candidate's commit puts it there, where a tag never moved keeps it. A git pattern such as `v*` also matches the tail of `withdrawn/v…`, which only a full reference keeps out. `--pre` takes the newest candidate, which may be another branch's, so the notes name the way in that reaches the candidate they describe, `pkit pin` (ADR-089 point 6). The pin warns rather than refuses, since a person who names a withdrawn candidate asked for that one.

**Point 5.** Only the run that ended a line pushed a final release's tag before its pull request, so without it a run without the input is the ordinary one. On another branch it would release what has not merged. A candidate's tag is fixed, so notes that cannot publish would otherwise stop every later run. A link at a tag cut later cannot resolve while the PR is reviewed. The branch link stops resolving once the PR merges and its branch is deleted, when the section is at the tag and on the default branch.

**Point 6.** A release PR consumes the changesets pending at the commit its plan read, and its tag takes the commit its merge leaves. A change merged after that commit, or pushed onto the release branch, would ship in the tag with its changesets pending and its migrations unrun, so the tag would not be the coherent state PRJ-002 D3 makes it, and a component the change touched would name two contents at one version, in any project that releases this way. PRJ-016 makes such a merge routine, since a branch merges once its testing passes. The history does not say which commit the plan read: answers may be committed after the release commit, a release may move only components, the host's button that updates a branch merges the default branch into it, and the queue squashes the PR's commits out of the merge it tests. So the step that read the plan writes its commit, and a release commit without it cannot be told from a stale one, nor mended by a line added by hand. Answers are the one thing a release branch takes after its release commit, so the predicate admits them beside what `apply` writes. The predicate judges which files and lines changed, and review judges their values, so a hand edit of a written value is a mistake review must catch, as point 10's interlock already accepts. Every check reads the plan's commit one way and applies one predicate (ADR-057 point 2). In the queue's run it holds in a batch, since a pull request queued ahead of the release lands as a squash commit between them, and it needs no fetch and reads no pull request (ADR-078 point 2). There the `chore(release):` subject marks a release, as it does for `pkit release merge`, so a release PR opened before the trailer existed is refused rather than passed unseen. Only a queue that squashes matters: `pkit release merge` refuses to enqueue unless the queue squashes with the PR's title and body (ADR-061 point 8), which also makes the `chore(release):` subject and the body's trailer reliable in the queue's message. A squash message the host builds, or a body with the line mid-text, leaves the trailer outside the last paragraph, where git reads trailers, so the reader matches it anywhere. The queue's check binds only where a project's required check runs it, so `pkit release merge`, which ships to every project, applies the predicate at its request on every base, and a release it enqueues with nothing ahead has nothing land first through the queue. Its refusal of a body without the trailer keeps the line in the squash commit's message the queue reads. A push may carry more than one merge, and the newest commit that changed `.pkit/VERSION` holds the release and nothing merged after it, so the target lives in `pkit version tag`, which every way of tagging a final release runs. The release workflow skips while a release PR is open, so a stale PR left open would hold every release. The costs: each commit that lands between a plan and its merge, even one that changes nothing the plan reads, means the release is planned, reviewed and run through CI again, and answers written on the replaced release branch are written again. A release the queue's check refuses fails its whole merge group, and the host may take out the pull requests batched behind it, to be enqueued again. A merge through the host's button or a plain `gh pr merge`, outside a squashing queue whose run holds the check, meets neither refusal. On the direct path, a merge that lands in the seconds between `pkit release merge`'s read of the remote's head and its merge request ships in the release's commit, since the host's merge request takes no condition on the base.

**Point 7.** A raise runs its target's upgrade through the bypass (ADR-049 point 5), so the refusal sits in every upgrade from the first candidate on, the candidate's own and each later release's, and in the pin's raise. A move cut short goes on with the command that started it (ADR-089 point 8), so `--pre` finishes the move to the recorded candidate and takes no newer one. The message names the one way off, so a tester who takes a later release to carry their branch learns that none does.

**Point 8.** A script in a folder at or below the version a project records runs for no project that upgrades past it, since the window runs only folders above that version (the lifecycle reference, "Which version a migration targets"). No project moves on from a candidate (point 7), and none enters one from above its cut's base (point 9), so each move into a candidate starts from a final release below every folder its branch's scripts sit in, wherever the branch has since put them. The default branch then numbers its scripts as it always has. COR-010's rule needs no change, though an edited script may meet its earlier version's output: leaving the testers' branch takes back the files git tracks, and the state left outside git, such as a label on the host or a file git ignores, arises only on a tester's opt-in path, a cost PRJ-016 accepts. A release with a stranded script ships a script no project runs, and a cut with one previews a release its branch cannot make as it stands. Every cut and every release passes through `plan` and `apply`, however the script was merged, so the guard holds where a pull request's checks, run before the release, cannot, and it adds no stop to a landing, so ADR-061 point 5 and ADR-081 point 7 stand. A version's scripts are fixed where those who take it receive it. project-kit's projects take a version through the tag that carries it (PRJ-004), so a version a release moved without a backbone tag reaches them with the next tag, whose window runs its folder. An adopter's components reach those who use them through a pin to a ref ([COR-041](../../../.pkit/decisions/core/COR-041-external-source-distribution.md)), and consumers who pin a ref on the default branch take a version at the first commit that records it, so that is where its scripts are fixed, however it merged. A clone whose history stops short of that commit would take a later one for it, and pass a script stranded between the two. The lifecycle reference's "already released" keeps its meaning: a version a release tag carries is at or below the version the default branch records, so the source repository's fixed version is never above the one `check-diff` reads, and a folder above the version the tier records passes both. The cost is that a consumer that pins a project-kit commit between a component-only release and the next tag runs a version no tag carries, an untagged install (PRJ-004).

**Point 9.** PRJ-016's Rationale for point 4 gives why no project enters from a final release made after the cut. Kept in the candidate's tree, the cut's base reaches the candidate's own upgrade, which reads nothing of the remote for it, and kept out of a project's tree, it is no file that validation or the next sync must know. Every way in runs that upgrade: `--pre`'s hand-over and a raise by `pkit pin` through the bypass (ADR-049 point 5), and the first hop as typed (ADR-089 point 8). So one refusal there holds them all, as point 7's does. The window, not the version a manifest records, is read, so a move to the candidate cut short still finishes.

**Point 10.** A run that `workflow_dispatch` starts takes its workflow file from the branch it runs on, and its `uv run pkit` runs that branch's code, so a branch can change any check of its own run. Starting the run needs write access, which already lets a person push a branch whose workflow runs with the same token and secrets, or move a tag from a clone, so a run from a branch reaches nothing that access did not already reach. The checks are an interlock against a mistake, as ADR-081 point 3 calls its own check. A tag already on the remote lies outside the run's code, so git's refusal holds whatever a slipped counter computed. It holds the candidate's tag alone, so a component version two candidates of different backbone versions both write still rests on the counter (PRJ-016 point 5).

### Alternatives considered

- **ADR-089 point 3's path for the final release at a candidate's version, beside ordinary releases.** Rejected: PRJ-016 tests a change before it merges, so no release needs it.
- **A candidate cut from a commit without the default branch's head in its history.** Rejected: it would preview a release the default branch cannot make.
- **The withdrawal read from the candidate's Release.** Not taken: `--pre` would read the host's interface beside the remote's tags.
- **`--pre` following the project's own branch, read from a tag beside each candidate's.** Not taken: a project on a candidate moves nowhere (point 7), so `--pre` only picks a way in, which `pkit pin` names exactly.
- **A candidate named to `pkit upgrade --pre`.** Not taken: `pkit pin` names one already (ADR-089 point 6).
- **A counter for each component.** Rejected: ADR-089 point 1 gives a cut one `N`, and the counter would read every candidate's tree.
- **The release PR's section linked at its head commit, which outlives the branch.** Not taken: the body is built before that commit exists.
- **A release PR brought level with the default branch by merging it in.** Rejected: it would bring in changesets its plan did not consume.
- **Merges into the default branch held while a release PR is open.** Not taken: every merge would wait out each release's review and run, where a replaced PR costs that one release a second run.
- **A release PR refused only where the commits since its plan's commit change what the plan reads.** Not taken: every reader would share a predicate over changesets, version cells, ranges, migration scripts and the changelog, in place of a check of a commit's identity and of a diff `pkit release check` already recognises.
- **The trailer carrying `apply`'s options, so each check runs `apply` again at the plan's commit and compares values.** Not taken: the trailer would carry `apply`'s options, and the check would be coupled to each write's options.
- **`pkit release merge` warning, rather than refusing, where it enqueues a release behind another pull request.** Not taken: where a project's required check does not run the queue's check, the release would still land stale.
- **Every pull request required to be up to date with its base, with a release PR's own check of its branch's history.** Not taken: the check would add one more run to every project's continuous integration for a path only the host's button reaches, and point 8 leaves that requirement to each project.
- **A stale release reported at the tag, without a refusal.** Not taken: a report adds a mechanism for a window of seconds.
- **The release-tag workflow refusing a release commit whose parent is not the plan's commit.** Not taken: the default branch would record a release no tag carries, with no sanctioned way on.
- **A refused tag mended, by the next plan taking an untagged backbone version as pending, or by the parent check moved into `pkit version tag`.** Not taken: no tag is refused.
- **A host rule that keeps release and candidate tags from being moved or deleted.** Not taken: one over every `v*` tag would break `pkit version untag --push` for a final release, and one over candidate tags alone can be added later with no change to this record.
- **The refusal of a move off a candidate in the plain upgrade alone.** Rejected: `--pre` and a raise by `pkit pin` make the same move.
- **A script a candidate shipped kept add-only, with the default branch's scripts numbered after it.** Rejected: a branch's script left in a folder the default branch released would run for no project upgrading past that release.
- **In the methodology's source repository, the fixed version taken as the version a tier records, with the commit that wrote it.** Rejected: after a release that moved only a component it would refuse scripts every project receives with the next tag, and a merge commit or a revert would give it another commit than the tag's.
- **Each candidate a final release overtakes withdrawn by a tag the release-tag workflow pushes,** so `--pre` passes it by. Not taken: `pkit pin` and the first hop would still enter it, where the cut's base reaches every way in.
- **`check-diff` run by the landing of a change,** in place of the guard. Rejected: project-management's merge verbs do not land through `pkit pull-request land`, a queue's run already checks the merge, and a stop the landing makes unasked needs a record that binds every landing (ADR-061 point 5), which ADR-081 point 7 declined for its own check.
- **A cut run by the default branch's workflow and `pkit` against the branch's tree.** Not taken: a candidate previews the release the branch's merge would make, which the branch's own release code makes once it merges.
