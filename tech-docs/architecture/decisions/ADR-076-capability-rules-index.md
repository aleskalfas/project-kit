## Summary

**In plain terms:** this record is how project-kit builds [COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md), under which a capability's operational rules load in every session where it is installed.
- **The file:** a capability's loaded file is `.pkit/capabilities/<name>/rules.md`, generated and checked as core's is.
- **The delivery:** the backbone renders one index, `.pkit/rules/capabilities.md`, that imports each installed capability's file, beside core's `core.md` and the project's `project.md`. `CLAUDE.md` reaches the index through one line, kept present after core's include. A capability's rules then load wherever core's do, and the index is committed with `.pkit/`, so it is present wherever core's file is.
- **The check:** validation fails an index out of step with the installed capabilities, an entry whose file is missing, or a `CLAUDE.md` without its line.
- **What binds:** install, sync and upgrade name the rules each loaded set newly binds, core's included.
- **The harness requirement:** Claude Code answers it at a cost, naming the sessions that skip `CLAUDE.md`, a confined run among them for every layer, and vouches for no version until a session is observed.

## Context

COR-070 decides that each adapter delivers an installed capability's loaded file to every session its harness starts, by the route that carries core's rules where the harness offers one, and that validation fails where a checkout's delivery is not in step. Its Implications leave to an architecture record:
- where the capability's loaded set and its loaded file live
- the form of the preface that names the capability's layer, and how validation reads a citation of its rules
- Claude Code's form of delivery, and what writes it and takes a capability out of it
- how the backbone learns an adapter's form, since it names no adapter's paths ([ADR-009](ADR-009-git-footprint-visibility.md) rule 1)
- where the check runs
- the harness requirement's entry and Claude Code's answer
- what brings existing projects level ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md))

These records and the adapters' reference set the shape this one fits:
- **The loaded file** is generated by one function, written by `pkit rule-sets generate` and checked by validation's `rule-sets` member where the set is authored ([ADR-075](ADR-075-generated-operational-rules.md) points 2 to 5).
- **Rule-set files are found by where they are** ([ADR-056](ADR-056-backbone-file-schemas-home.md) point 2).
- **Each validator is a member of `pkit validate`,** and `error` is the one severity that fails ([ADR-058](ADR-058-validator-registry.md) point 2).
- **A file the backbone renders for each project under `.pkit/`,** from the installed components' declarations, is the backbone's own and is never a synced copy: `.pkit/.gitignore` is rendered wholesale at each install and sync, and committed (ADR-009 rule 7). The ownership predicate answers it as not synced, as it does `rules/project.md`.
- **The lifecycle runs an adapter's primitives by name** (the adapters README, "Primitives the lifecycle calls"). `merge-claude-md.sh` inserts core's include, `@.pkit/rules/core.md`, into the project's `CLAUDE.md` where it is absent, with the project's own `@.pkit/rules/project.md` after it ([COR-002](../../../.pkit/decisions/core/COR-002-merge-delivery.md)).

What Claude Code does with these files, as read from its documentation of memory files, subagents, settings and the Agent SDK on 29 October 2026 ([memory](https://code.claude.com/docs/en/memory), [subagents](https://code.claude.com/docs/en/sub-agents), [SDK features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)):
- **Two routes:** a session loads the project's `CLAUDE.md`, with each file an `@` line in it imports, and imports within those, a path read from the importing file. It also loads every Markdown file under `.claude/rules/`, found recursively, that carries no `paths:` field.
- **Where both load:** in a session a person starts in the project, and in a subagent it starts from one, which loads every level of the `CLAUDE.md` hierarchy the main session loads. After the session's context is compacted, both are read again from disk.
- **Where neither does:**
  - the built-in Explore and Plan agents, and any agent definition that sets `omitClaudeMd`;
  - a file matched by the `claudeMdExcludes` setting, in any settings layer, and every project file where project instructions are set to `managed-only`;
  - `--bare` and `--safe-mode`;
  - a run whose `--setting-sources` leaves out `project`. The SDK's table of setting sources puts the project's `CLAUDE.md` and `.claude/rules/` under that one source. The adapter's confined runner passes `--setting-sources ""` (the adapter README, "The confined form's closed set of flags"), so a confined run holds neither route, and so no layer's rules, core's included. [ADR-066](ADR-066-unattended-agent-runner.md)'s "The person's instructions" records that instructions may reach a run, as a risk left open, not as an observation that they do.
- **External imports:** an import whose path resolves outside the session's working folder is external, and loads only once a person approves it at the start of an interactive session. Core's include and the index share that fate in a session started below the project's root.
- **An observation point:** the `InstructionsLoaded` hook fires when a `CLAUDE.md`, a file it imports or a `.claude/rules/` file is loaded, with load reasons such as `session_start` and `compact`, in a session whose settings register it.

## Decision

**A capability's loaded file is `rules.md` at the root of its tree, generated and checked as core's is. The backbone renders one index of the installed capabilities' loaded files at `.pkit/rules/capabilities.md`, in the form the adapter declares, and the Claude Code adapter's merge primitive keeps one line reaching it in the project's `CLAUDE.md`, after core's include. Validation's `rule-sets` member fails an index out of step with the installed capabilities, an entry whose file is missing, or a `CLAUDE.md` without its line.**

### 1. The capability's loaded set and its loaded file

- **The set:** a rule-set file in the capability's `rule-sets/` folder with `loaded: true`, found by the location rule as the capability's other sets are. The `rule-sets` member no longer refuses a set marked loaded in a capability's folder (refinement of ADR-075 point 6). A second loaded set in one capability's folder is refused, as it is in any component's.
- **Its name:** the capability's own, such as `SWE`. The finding that two sets share a name (COR-051 point 3) already refuses a set named `OPS` or any other set's name.
- **Its preface:** the prose before its first rule names the capability, and states how its rules stand to the other layers, in the sentence the rules README gives: its rules add to core's and never loosen them; where one cannot be kept with a rule of core's, core's binds; a project's rules add to these and never loosen them; where one cannot be kept with a rule of another capability's, the session stops the step and reports the clash. The projection carries it into the loaded file (ADR-075 point 3). The `rule-sets` member fails a capability's loaded set whose preface does not name its capability, where the set is authored. The rest of the sentence is judged by whoever accepts the set.
- **The file:** `.pkit/capabilities/<name>/rules.md`. Its path comes from the set's owner: the one function that gives each owner's loaded file gives a capability's from its name, where ADR-075 point 2 holds one constant for the backbone's (refinement of ADR-075 point 2).
- **Written and checked as core's:** `pkit rule-sets generate` writes it where the capability is authored, and the staleness check of ADR-075 point 5 fails it there when it differs from its set. Where the capability arrives by sync or install, the file arrives with it, and neither runs.
- **One answer to which capabilities ship one:** a reading command of the `rule-sets` group, `pkit rule-sets loaded [--json]`, lists each loaded set of a component the manifest registers, its owner and its loaded file, from the one function that gives each owner's loaded file ([ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 2). A capability unregistered with its files kept ([COR-031](../../../.pkit/decisions/core/COR-031-capability-origin.md)) is not in it, though its set is still found where it is. The index of point 2 and the check of point 4 both read this one answer, so a capability's file is delivered exactly where it is checked. Where the capability is authored, the `rule-sets` member fails a `rules.md` at a capability's root with no loaded set behind it, so a file left behind by a removed set is never delivered unchecked.
- **No front matter:** the projection writes none (ADR-075 point 3), so an import of the file brings its rules and nothing else.
- **No bare `@` in a statement:** a loaded file is imported, and Claude Code reads an `@` token in an imported file as an import of its own, recursively. So the `rule-sets` member refuses, in any loaded set's statements and prose, core's included, an `@` that opens a token outside code. A path written in backticks is code, and stays.
- **Citations:** validation's `refs` member reads the form COR-070 point 1 gives, `<capability>:RS-<SET>-NNN`, beside `backbone:RS-OPS-0NN`, and warns of a citation of a missing or retired rule (ADR-075 point 8).
- **Origins:** each rule's origin cites a record of the capability's own (`<capability>:DEC-NNN`), a core record, or gives the decider's words, never an architecture or project record. The set is validated in every project that installs it, where those would resolve against the project's own records (ADR-075 point 1).

### 2. The backbone renders an index, and `CLAUDE.md` includes it

- **The index:** `.pkit/rules/capabilities.md`, beside `core.md` and `project.md`. It holds, first, one marker line, an HTML comment saying the backbone renders it and that nobody edits it, which Claude Code drops from what it loads. Then one line per installed capability that ships a loaded set, in the form the adapter declares (point 3), for Claude Code `@../capabilities/<name>/rules.md`, a path read from the index's own folder, in the order of the capabilities' names. Nothing else: no heading, no prose (core rule 13). Where no installed capability ships one, it holds the marker alone.
- **Its owner:** the backbone, which renders it for each project from what is installed, as it renders `.pkit/.gitignore` (ADR-009 rule 7). It is no synced copy: the ownership predicate answers `rules/capabilities.md` as it answers `rules/project.md`, so sync never copies it from the methodology's source and the packaging leaves the source's own out of the bundle. The project never edits it.
- **When it is rendered:** whole, at each install, sync and upgrade, and at an uninstall after the capability is unregistered, so the render reads the manifest that no longer lists it. The first render refuses a file at the index's path that lacks the marker, and names it, since that file would be someone else's.
- **Present where core's is:** the index is committed with `.pkit/`, so every checkout that holds core's `core.md` holds it too: a fresh clone, a worktree, a continuous-integration checkout and the runner's clone. A private project hides `.pkit/` as a whole (ADR-009 point 3), the index with it, so it needs nothing more, and no window opens in which the index sits untracked and unhidden.
- **The line in `CLAUDE.md`:** `@.pkit/rules/capabilities.md`, kept present by `merge-claude-md.sh` directly after core's `@.pkit/rules/core.md`, inserted wherever it is absent. The rules then read in the order of their layers: core's, each capability's, the project's. Because it is inserted wherever it is absent, a project cannot opt out by deleting it (COR-070 point 3). It is inserted whenever the adapter is installed, whether or not a capability ships a loaded set yet, so the project's `CLAUDE.md` changes once, and the index carries every install and uninstall.
- **Holds the line:** a line of the file that is exactly the line once its surrounding white space is trimmed and a CRLF ending is read as `\n`, outside a fenced code block. A mention of the line in a code span, in a fence, or as part of a longer token does not hold it, since Claude Code imports none of these. The merge primitive's presence test and the check of point 4 both use this definition, and one set of test cases holds the shell test and the backbone's to it.
- **The depth:** `CLAUDE.md` imports the index, and the index imports each loaded file, so a capability's rules are two imports from `CLAUDE.md`, within the depth the documentation allows. Its imports resolve as core's does.

### 3. The merge primitive's change is safe over every state

`merge-claude-md.sh` today exits as soon as `CLAUDE.md` holds core's include. Its new step, inserting the index's line, reaches every existing project's `CLAUDE.md` at the next sync, so it keeps what each project's file is:
- **It writes through the file:** the new content is written into the existing `CLAUDE.md`, not moved over it. A `CLAUDE.md` that is a link keeps its link, and the line reaches the file it links to. Its mode stays as it was.
- **It adds the index's line alone:** where core's include is present, the step inserts only the index's line, after core's. It never puts `@.pkit/rules/project.md` back where a project removed it. Where core's include is absent, the primitive inserts core's, the index's and the project's lines as it inserts core's and the project's today.
- **Outside a fence:** where core's include sits only inside a fenced block or a code span, where Claude Code imports nothing, the step inserts nothing and reports it, naming the file, since only the project can say where its include belongs.
- **The minimal host:** the `CLAUDE.md` the primitive creates where none exists holds the index's line between core's and the project's.
- **An include moved into an imported file:** the primitive reads `CLAUDE.md` alone, as it does today. A project that moved core's include into a file `CLAUDE.md` imports, such as `AGENTS.md`, finds core's include and the index's line added to `CLAUDE.md` again. That limit is the primitive's already and is named in the adapter's README.

### 4. The adapter declares its form

- **The key:** the adapter's package metadata holds `loaded_rules:`, which gives the harness's syntax as data:
  - `entry:` the line for each capability's loaded file, with `{file}` for its path read from the index's folder, `@{file}`;
  - `host:` the file that reaches the index, `CLAUDE.md`, and `line:` the line that reaches it, `@{index}`.

  The package schema checks its shape. The index's path is the backbone's, fixed by its owner as core's loaded file's is (ADR-075 point 2), so no adapter names a path under `.pkit/`.
- **One function renders the index:** the backbone renders the index's content from the key and `pkit rule-sets loaded`, in one function beside the loaded-set projection. `pkit rule-sets loaded --index <adapter>` prints it. The lifecycle's render writes what it gives, and the check compares the file with the same function's output, so the two never disagree on what the index holds (ADR-075, "Why one function for the generator and the check").
- **What it says, and no more:** the key says that the adapter's harness reaches the installed capabilities' loaded files through one index that the host file reaches by one line. An adapter whose harness reaches them another way, or whose index needs a form another adapter's would clash with, needs a key of its own or a validator it registers ([ADR-058](ADR-058-validator-registry.md) point 4). That is decided with that adapter.
- **No key:** an adapter that declares none delivers no capability's rules, and the check warns of it (point 5).

### 5. Validation's `rule-sets` member checks the delivery

- **What fails:** an `error`, `loaded-rules-undelivered`, naming the adapter, the file and the sync that mends it, where:
  - the index differs from what point 4's function renders for the capabilities `pkit rule-sets loaded` lists, once line endings are read as `\n`;
  - an entry of the index names a loaded file the checkout does not hold;
  - the `host:` file does not hold the `line:`, by point 2's definition.
- **Where the index is not:** a checkout without it gets a summary line of the member saying so, since its sessions load no capability's rules. The index is committed with `.pkit/`, so that is a checkout where no render ran. A state is a summary line, not a finding, as the member's counts are ([ADR-058](ADR-058-validator-registry.md) point 1).
- **One function for it:** one function compares what an adapter declares it delivers with what the checkout holds, and gives the finding or the summary line. It is the methodology's first check of how the harness reaches what the methodology delivers. The next such check, of skills or agents, reuses it.
- **No declaration:** a registered adapter without `loaded_rules:` gets one `warning`, naming the adapter and each capability that ships a loaded set, since that harness's sessions load no capability's rules (COR-070 point 6).
- **Where it runs:** in every project, where the capability is authored and where it arrives by sync, since the index and the host file are the project's own state. It reads files only, never a session.
- **Why this member:** the member that holds the rule sets' checks already has loaded sets and their files as its subject (ADR-075 point 5), and one subject keeps one member (ADR-058). Delivery widens that subject to how a loaded file reaches a session, and the member's help text says so.

### 6. The lifecycle says which rules it newly binds

- **What it prints:** install, sync and upgrade print, for each loaded set they deliver, core's `OPS` and each capability's alike, the set's name and version and each rule it newly binds, changes or retires since the copy it replaces. A first install lists every accepted rule by id and title.
- **How it knows:** one function beside the loaded-set projection compares two readings of a set's accepted rules, by id, status and statement. It knows no layer. The lifecycle reads each set before it copies the new version, and prints the function's answer.
- **A harness that loads no capability's rules:** where no adapter in use declares `loaded_rules:`, the line for a capability's set says that its rules bind no session in this project, rather than list them as bound (COR-070 point 3).
- **Not a gate:** the line informs and stops nothing (COR-068 point 5).

### 7. The harness requirement, and Claude Code's answer

- **The requirement:** `.pkit/schemas/harness-requirements.yaml` holds `session-loads-rules`. Its behaviour is that each session the harness starts in a project holds every file the methodology places for the harness to load, from the session's start and for its whole length, compaction included. That covers a session a person starts, a delegated helper and an unattended run. Its evidence is the design dependency of COR-070 point 6.
- **Its observation point, `interposed-runtime`:** COR-070 point 6 places the truth where a session runs, in the session itself or in what the harness runs at its own points during it. The harness's own points reach more kinds of session than an agent's view of its own context does: Claude Code's `InstructionsLoaded` hook fires for each file loaded at a session's start and again after compaction, in a session a person starts and in a helper. A confined run registers no project hook, since it loads no project settings, so the confined case is observed through the adapter's probe and the run's stream, whose start report names what the run loaded (ADR-066 point 12). Out of session, the files are seen in place, not loaded.
- **Claude Code's answer:** `harness-support.yaml` answers it `at-cost`. Core's loaded file and every capability's reach a session by one route, `CLAUDE.md` and its imports, so the cost names that route's exceptions once (Context):
  - **Loaded:** in a session a person starts at the project's root, in a subagent dispatched from one with a definition of the project's, and after compaction.
  - **Not loaded, for every layer, core's included:**
    - Explore and Plan, and a definition that sets `omitClaudeMd`;
    - a run with `--bare` or `--safe-mode`;
    - a run whose `--setting-sources` leaves out `project`, the adapter's confined runner among them;
    - a file that `claudeMdExcludes` or `managed-only` drops;
    - a session started below the project's root whose person declined the external imports.
  - **Unobserved:** a session in a worktree under `.claude/worktrees/` also finds the main checkout's `CLAUDE.md` above it, and may load that checkout's index and loaded files beside its own. The rules of the checkout the session works in are the ones its change is judged by. Whether Claude Code loads both is unobserved, and the same holds of core's file.
  - **What the adopter keeps:**
    - `CLAUDE.md` and the index out of `claudeMdExcludes`;
    - the methodology's work dispatched to definitions that do not set `omitClaudeMd`;
    - the external imports approved where sessions start below the root.
- **Its range:** `harness_versions` stays empty until a session is observed holding an imported capability file, so it vouches for no version. Only whoever observes it widens the range, as COR-047 point 2 requires.
- **The report:** a requirement whose observation point the report cannot reach resolves `indeterminate` (COR-047 point 4). `pkit harness report` names the requirement with that reason, never as satisfied.

### 8. What brings existing projects level

- **The delivery:** the next sync or upgrade renders the index and runs `merge-claude-md.sh`, which inserts the line where it is absent, as point 3 says. Nothing is renamed or removed, so no migration is due.
- **A private project:** the index sits under `.pkit/`, which the private region already hides, so the region needs nothing new.
- **Versions:** the adapter, and each capability that ships a loaded set, needs the backbone that lifts ADR-075 point 6's refusal, renders the index and answers `pkit rule-sets loaded`, and declares that floor ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md) D4).
- **Nothing else:** the package schema gains an optional key, and a capability gains files, so no file that passes before the change fails after it (ADR-056 point 3).

## Rationale

**Why an index that `CLAUDE.md` includes.** Core's loaded file reaches a session through `CLAUDE.md`, and a capability's takes the same route where the harness offers it (COR-070 point 2). Through the include, a capability's rules load in exactly the sessions core's do, and miss exactly the ones core's miss, so the harness requirement names one route's exceptions once. The index holds paths, not copies, so what a session reads is the capability's own committed `rules.md`, and nothing deployed beside it can drift from it. One line in `CLAUDE.md` reaches every capability, so the project's file changes once, and uninstall never touches it.

**Why one line, kept present, and an index the backbone owns.** A line in `CLAUDE.md` for each capability would have to come out at uninstall, from a file the project writes (COR-070, "Why through a file or place of its own"). One line reaching a file the methodology owns never needs removing: the index carries every change of which capabilities are installed, and is rendered whole, since nothing else is in it. Keeping the line present wherever it is absent, as COR-002 keeps what it inserts, leaves no opt-out by deletion while the capability is installed.

**Why the line is inserted whenever the adapter is installed.** Inserting it only once a capability ships a loaded set would change the project's `CLAUDE.md` at an install, and leave a line the check must judge by what is installed. Inserted at the first sync that brings it, it changes the project's file once, and every later install and uninstall touches the index alone. An index that holds only its marker costs a session nothing.

**Why the line sits after core's include.** The rules then read in the order of their layers, core's above a capability's above the project's (COR-070 point 4), and a reader of `CLAUDE.md` sees all three together.

**Why `.pkit/rules/capabilities.md`.** The index must be present wherever core's loaded file is, or a session would hold core's rules and miss a capability's (COR-070 point 2). `.pkit/` is committed with the methodology's files, so a file there is in every checkout that holds core's. `.pkit/.gitignore` is the precedent: a file the backbone renders for each project from the installed components' declarations, committed, and never a synced copy (ADR-009 rule 7). The rules area already holds the loaded files a session reads, core's and the project's, so the three includes in `CLAUDE.md` name three files of one folder in the order of their layers. The harness's syntax enters the file only as the data the adapter's key gives (point 4).

**Why the merge primitive changes only what it must.** Its new step reaches files it never rewrote before. Writing through the file keeps a link and a mode the project chose, inserting the index's line alone keeps a removal the project made, and refusing an include it finds only in a fence leaves the project's choice to the project (core rule 5).

**Why the check is the backbone's, with the form declared.** The check must find the delivery in every project, for each adapter in use. A form written into the backbone would name an adapter's syntax in core, the layering ADR-009 rule 1 forbids. An adapter could register a validator of its own (ADR-058 point 4), and one whose harness reaches the files another way will. For an index reached by one line, though, one implementation in the backbone serves every adapter that delivers that way, and the backbone must warn of an adapter that declares no delivery in any case, which no adapter's validator can do for an adapter that has none.

**Why the backbone renders the index.** The lifecycle writes it and the check compares it, and two pieces of code that each built it could come to disagree. One function, with the harness's syntax given as data in the key, keeps them together, as one function serves the loaded file's generator and its check (ADR-075 point 2). The backbone owns `.pkit/`, so it renders the files there, as it renders `.pkit/.gitignore`.

**Why one reading command says which capabilities ship a loaded set.** The index and the check each need the answer, and the uninstall's render must leave the capability out. Two readings, a file's presence or a set's location for one and the manifest for the other, could disagree: a capability unregistered with its files kept, or a `rules.md` left behind by a removed set, would be imported in every session and checked by nothing. One answer from the backbone, filtered to what the manifest registers and read through a command as ADR-057 point 2 asks of a component's script, keeps the two together.

**Why an entry whose file is missing fails.** Claude Code skips an import whose file is not there, without a word. The index's text could match its render while a session loads none of a capability's rules. Checking each entry's file closes that.

**Why a bare `@` in a loaded set is refused.** A loaded file is imported, and an `@` token in it would be read as an import of its own: a handle or a mention would pull in a file, or raise an approval for one outside the project. A check reads it deterministically, so it fails rather than trusting every author to know the harness's import syntax.

**Why the preface is checked for the capability's name alone.** That the file names its capability is a fact a check can read. Whether the rest of the sentence states the layering rightly is prose, which the person accepting the set judges ([COR-055](../../../.pkit/decisions/core/COR-055-validation.md)).

**Why Claude Code's answer names one route's exceptions, and vouches for no version yet.** Core's file and a capability's reach a session by one route, so they load in the same sessions and miss the same ones, and one cost states it. The documentation says which sessions skip `CLAUDE.md`, a confined run among them, and an `at-cost` answer states them as what the adopter must keep in mind. Until a session is observed holding an imported capability file, an answer that vouched for every version would be the confident unchecked claim COR-047 point 5 warns of. The runner's tested range (ADR-066 point 12) is the precedent: empty until observed.

### Alternatives considered

- **A copy of each capability's file under `.claude/rules/pkit/`.** Rejected. Copies need a record of what the deploy wrote and a folder of their own in the footprint, and `.claude/` is kept out of version control in some projects, so a checkout could hold core's file and not the copies. Each copy is also a second file of a capability's rules, which a hand edit or an incomplete deploy can set apart from `rules.md`. The index holds paths, is committed with core's file, and is rendered whole.
- **The index at `.claude/pkit-rules.md`.** Rejected: a project that keeps `.claude/` out of version control, re-including only its skills and agents, would leave the index out of fresh clones, worktrees and continuous-integration checkouts, where core's file is present. A session there would be bound by core's rules and not a capability's.
- **A link at `.claude/rules/<capability>.md`.** Rejected: a link fails in a Windows checkout without `core.symlinks`, and claims a folder a project fills by hand.
- **The index under `.claude/rules/`.** Rejected: Claude Code loads that folder, so the rules would load twice.
- **A line for each capability in `CLAUDE.md`.** Rejected: uninstall would remove text from a file the project owns (COR-070).
- **The line only once a capability ships a loaded set.** Not taken, as "Why the line is inserted whenever the adapter is installed" says.
- **A deploy primitive of the adapter's writing the index.** Not taken: the index sits under `.pkit/`, which the backbone owns, and the backbone already renders the check's side of it.
- **The start hook, adding each file as context at `SessionStart` and `SubagentStart`.** Not taken: it is the one route to Explore and Plan, but what it adds is summarised away at compaction and capped in size, and an adopter's own entry for the event takes the baseline's place.
- **The delivery written in the backbone.** Rejected by ADR-009 rule 1.
- **A validator the Claude Code adapter registers** (ADR-058 point 4). Not taken for an index reached by one line, as "Why the check is the backbone's, with the form declared" says. It stays open to an adapter that reaches the files another way.
- **The check failing where the index is absent.** Rejected: that checkout is one no render ran in, which the next sync mends, and its sessions load core's rules as the index's absence leaves them.
- **Claude Code's answer as `full`, for every version.** Rejected, as "Why Claude Code's answer names one route's exceptions" says.
- **Carrying every layer's loaded files into a confined run's definition,** as the runner already carries the workspace sentence. Not decided here.
