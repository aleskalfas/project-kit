When one parser/selector feeds **both** a security-relevant gate and a read surface, the shared primitive is **permissive** (the safe default for the read surface), and **a gate-side reader selects only through a strict wrapper whose filters are required arguments** — so the fail-open default is *structurally unreachable* from a gate path. The realized instance is the DEC-028 reviewer-verdict selector in `_lib/agent_verdicts.py`. Its gate side is the merge gate (`done-work`) and two readers that must see the verdicts the gate reads: `review-pr`'s skip of a reviewer whose verdict still stands, and the landing command's hold on `[person]` findings. Its read side is the governed read surface, `show-pr --field review` and `review-history`. All of them agree on *which comment is a reviewer's current verdict*; only the gate side applies the marker / membership / author-exclusion filters that make it safe, and each gate-side reader decides what a stale verdict means for its own question. This ADR pins the discipline that keeps the gate un-foot-gunnable; it realizes DEC-028, and the selection DEC-055 point 3 asks of the hold, and changes neither.

## Context

[project-management:DEC-028-agent-as-approver-paths] fixes the reviewer-verdict grammar, the latest-verdict-per-reviewer selection (robust to comment order), and the gate-checker's freshness / membership / author-exclusion rules; [project-management:DEC-032-conditional-reviewer-requirements] resolves the required-reviewer set per PR. That selection logic lived **inline** in `done-work.py` (the merge gate). Issue #544 needed the *same* verdict — token + reasons — readable through the governed pm surface (`show-pr`), because an operator/agent could see the verdict label but had no allowed path to the reasons (raw `gh pr view --comments` is correctly denied). Two consumers needed the one selection; hand-rolling it twice would let the two drift on the invariant that must not — "which comment is a reviewer's current verdict" ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)).

Two further readers sit on the gate side without being the gate. `review-pr` skips a required reviewer whose current verdict the gate would still count (#1178). The landing command shows each `[person]` finding of the verdicts the gate reads, and holds a run authorised up front on them ([project-management:DEC-055-pr-lists-answers] point 3); the tags that mark a finding `[block]`, `[advisory]` or `[person]` are DEC-028's ("Finding tags"). Both readers must read the gate's own selection — its marker and its membership — yet both need a reviewer's current verdict *before* freshness drops it, because a stale verdict is exactly what they re-run or hold on.

The consumers differ on **filtering**, not on selection: the gate must drop stale, unmarked, non-required, and self-authored verdicts; the read surface legitimately wants *all* posted verdicts (latest per reviewer) so an operator sees the full picture. Extracting the shared selection into `_lib/agent_verdicts.py` raised the design question this ADR answers: how to share the selection without letting the read surface's permissiveness leak into the gate.

## Decision

**One shared selector; a gate-side reader reaches it only through a strict, required-argument wrapper.** Six points.

- **D1 — Permissive primitive, strict gate wrappers.** `latest_verdicts_per_reviewer(...)`, with `all_verdicts(...)`, the full sequence it reduces, is the shared, *permissive* selection primitive: no marker, membership or author-exclusion filter, and no freshness. A gate-side reader does **not** select through it. It selects through one of two strict wrappers: `gate_candidates(comments, *, local_reviewer_ok, remote_reviewer_ok)`, each required reviewer's current marked verdict before freshness is judged, and `gate_verdicts(comments, *, is_fresh, local_reviewer_ok, remote_reviewer_ok)`, which keeps the fresh ones. Their security-relevant filters are **required, non-defaulted** keyword arguments, and the marker requirement is fixed inside them — omitting a filter is a call-site error, not a silent fail-open. Whose verdicts the gate counts — a remote one from a baseline login that is not the PR's author, a local one from a name in the PR's resolved required set — is stated once (`gate_membership`), and the gate and the landing command's hold take their predicates from it. The permissive default is therefore structurally unreachable from a gate path. The burden of explicitness sits on the security-relevant path, not the read path.

- **D2 — The read surface is a superset, and says so.** `show-pr --field review` calls the permissive primitive directly and shows a **superset** of the gate's subset — including stale, unmarked and non-required verdicts; `--field review-history` shows the full sequence behind it. Both **annotate staleness** by the gate's own freshness rule (a verdict the merge gate will not count is marked so, with the reason), so an operator or agent is never misled that a stale `APPROVED` is mergeable.

- **D3 — Fail-closed stays with the caller.** The module is a pure selector that trusts the freshness predicate it is handed; it never decides fail-open-vs-closed. Each caller decides which way a verdict that does not stand fails, for its own question. The merge gate drops it: the freshness predicate it hands in (`_lib.verdict_freshness`, the rule DEC-028's "Stale-verdict handling" states) holds a verdict stale whenever it cannot decide, and `done-work` **refuses before calling the module** when the PR's head cannot be established. For the landing command's hold, dropping a stale verdict is the fail-open direction, since its `[person]` findings would never be shown; so the hold reads `gate_candidates`, never `gate_verdicts`, judges each verdict by the same freshness rule, and shows a stale one marked stale and holds on it ([project-management:DEC-055-pr-lists-answers] point 3). `review-pr`'s skip reads `gate_candidates` too, and runs again a reviewer whose verdict is stale.

- **D4 — Scope: posted comments only.** This module reads a **posted comment**: its first line, for the verdict, and its body's findings, for their tags (`findings`, DEC-028 "Finding tags"), so every reader tells a `[block]`, an `[advisory]` and a `[person]` finding apart alike. The tags never reach the selection: the verdict line alone decides the gate, and a reader reads the tags of a verdict the selection has already chosen. The module is **not** the raw-output "scan for the first grammar-matching line anywhere" extractor that `review-pr` owns (DEC-028's separate consumer-scan contract, which must tolerate agent preamble). Raw-output extraction must not be routed through this module.

- **D5 — One instance, not yet a promoted pattern.** This records *this* decision; it deliberately does **not** promote the strict/permissive split to a core (COR-level) pattern. Per COR-007, a second independent split earns the promotion; one instance is a recorded decision, and a further reader of this selector is not a second instance. The module lives in the pm capability's `_lib/` — all consumers are pm surfaces, so no backbone promotion (the same placement call [ADR-038](ADR-038-contribution-collector.md) made).

- **D6 — A gate-side reader reads the permissive primitive only for a question that cannot change what counts.** The landing command's hold reads it twice. At the start of a run authorised up front, it snapshots every verdict on the PR (`all_verdicts`). The snapshot answers only whether a verdict the strict selection yields later is one the run found then — the same in every parsed field, so an edited comment is another verdict — and a snapshot that cannot be read finds nothing, so a miss fails toward a stop. Before it resolves the PR's required reviewers, the hold asks whether any reviewer's latest marked verdict, from anyone, carries a `[person]` finding, and skips the strict read only when none does. That pre-check reads `marked_candidates`, the gate's selection before its membership predicates, and `gate_candidates` is that set filtered by them. The predicates key on the same reviewer identity as the latest-per-reviewer reduction, so the strict selection is a subset of what the pre-check reads by construction. A permissive read that could add a verdict to what counts, or drop one from it, is the anti-pattern D1 names.

## Rationale

**Why permissive-primitive + strict-wrapper rather than a safe-by-default single function.** The alternative — one function with the filters defaulted to safe values — was rejected: it makes the *read* surface the awkward caller (it must opt *out* of filters it never wants) and, worse, still leaves the gate one forgotten keyword-argument away from silent weakening (a caller who omits the freshness filter gets a plausible-looking but fail-open result). Inverting it puts the explicitness where the risk is: the read path gets the natural, permissive primitive, and the gate cannot be constructed without naming every safety filter. A missing filter on the gate path is a loud `TypeError` at construction, not a quiet hole discovered in production.

**Why share the selection at all (not just the grammar).** The invariant most likely to drift between two hand-rolled implementations is not the line grammar (a regex) but *latest-per-reviewer-by-timestamp* — the subtle, order-independent selection DEC-028 step 5 specifies. Sharing only the grammar would leave that subtlety duplicated; sharing the selection is the COR-007-correct cut. The critic + architect review confirmed the moved grammar is byte-identical to the deleted inline code and the gate's five DEC-028 filters are all preserved.

**Why two strict wrappers.** Some gate-side readers must see a required reviewer's current verdict whether or not it stands: `done-work`'s refusal names the stale verdict it did not count, `review-pr` runs again the reviewer it belongs to, and the landing command's hold shows its findings and holds on them. Handing them `gate_verdicts` would hide exactly the verdicts they act on; handing them the permissive primitive would let each re-derive the marker and membership filters. `gate_candidates` gives them the gate's selection before the freshness step, with the same required filters, and leaves what a stale verdict means to them (D3).

**Why a gate-side reader may read the permissive primitive at all (D6).** Resolving the PR's required reviewers costs several `gh` round trips and stops the landing when it fails. The hold runs on every landing, in either review mode, and most landings carry no `[person]` finding; such a landing should neither pay for nor be stopped by a resolution whose answer it does not use. The start-of-run snapshot asks whether a verdict was on the PR, which the strict selection does not sharpen. Neither read can add a verdict to what the hold acts on or drop one from it, which is the line D1 draws.

**Why this is ADR-worthy though it is one refactor.** The strict/permissive split is a non-obvious *safety* choice a reader cannot reconstruct from DEC-028 alone — DEC-028 says *what* the gate filters, not *why the shared selector is built so the gate cannot forget to filter*. Recording it is documentation-of-a-decision (the posture [ADR-038](ADR-038-contribution-collector.md) took for its family's rule), not premature generalisation — D5 explicitly withholds promotion.

### Alternatives considered

- **Single function, filters safe-by-default.** Rejected (see Rationale) — awkward for the read surface, still fail-openable by omission on the gate.
- **Share only the grammar; leave selection per-consumer.** Rejected — re-opens the latest-per-reviewer drift COR-007 is invoked to close.
- **Promote the split to a COR-level pattern now.** Rejected — one instance; COR-007 says wait for the second (D5).
- **Put the selector in the backbone.** Rejected — no non-pm consumer; speculative generality (ADR-038 rule 1).
- **The hold reads `gate_verdicts`.** Rejected — it drops a stale verdict, and with it the findings the person must be shown; for the hold, dropping is the fail-open direction (D3).
- **The hold's snapshot and pre-check go through the strict selection.** Rejected — the strict selection needs the resolved required set, so every landing would pay for, and could be stopped by, a resolution that only a `[person]` finding needs (D6).

## Implications

- **`_lib/agent_verdicts.py`** is the single source of truth for parsing and selecting *posted-comment* DEC-028 verdicts and for reading their findings' tags: the line grammar, the permissive primitive, the strict wrappers with the membership they take, and the tag reader.
- **`done-work`** calls `gate_verdicts` with `gate_membership`'s predicates and retains fail-closed freshness ownership; its refusal and its override audit describe the verdicts it judged through `gate_candidates` with the same predicates.
- **`review-pr`**'s skip reads `gate_candidates`, judged by the gate's freshness rule, so what it skips is what the gate counts.
- **The landing command's hold on `[person]` findings** reads `gate_candidates` with `gate_membership`'s predicates over the PR's resolved required set, judged by the gate's freshness rule; its start-of-run snapshot and its pre-check read the permissive primitive under D6.
- **`show-pr --field review`** and **`review-history`** call the permissive primitive, mark stale verdicts, and document the superset relationship.
- **A future gate-side reader** must go through `gate_candidates` or `gate_verdicts` (or an equally strict wrapper); selecting through the permissive primitive from a gate path is the anti-pattern this ADR names.
- **`review-pr`** keeps its own raw-output scan-anywhere extractor (D4) — it must not be routed through this module.
- **Stands on** DEC-028, DEC-032, DEC-055, COR-007, and ADR-038 (the shape-sibling) — all accepted.
