## Summary

**In plain terms:** [ADR-016](ADR-016-capability-contributed-intent-grants.md) lets an installed capability ship grants that the permission model composes for it, and [ADR-021](ADR-021-capability-contributed-privilege-definitions.md) lets it define privileges of its own. ADR-016 argues only a deny's safety on install, and ADR-021 gives a capability's reach over its own agents through its deny. Neither bounds a capability's allow, and the model's loader composes a capability's grant of any effect, to any subject, unchecked. This record lets a capability's grant also allow a privilege, on these terms:

- **Only tools the backbone lists, or a connected server's, only to its own agent.** The privilege is one the capability defines itself. It recognises tools by their names alone, written as a list, each of them on the backbone's list of the harness's tools a capability may allow, or a connected server's tool, and none that a privilege of the backbone's or of another capability's recognises. A tool joins that list only where it runs no command, reads or writes none of the person's files, reaches nothing outside the person's own sessions, changes no permission or mode of the session, stops or removes no work, and starts or schedules no work: no session, team, subagent, workflow, scheduled prompt or run, on a remote service or elsewhere. A message that wakes one of the person's own sessions, or resumes a subagent the session started, starts none, since what it reaches already exists and works under its own checks. The harness's own store of its sessions and messages is not one of the person's files. Every other tool of the harness's is refused, one it adds later among them, until the backbone lists it. A connected server's tool matches whatever server the session connects under that name, and may itself run commands. The agent is one the capability ships, and the allow carries no scope. The model's loader refuses any other allow of a capability's: that grant composes nothing and is named as rejected, and the fragment's other grants still compose.
- **In the model on install, binding only through a bound.** The allow comes into the model on install, as a deny does. It widens the agent's reach, so it binds only through a bound: a model a person realized, or, in a working run, the model the runner reads from the default branch. Any deny of the privilege to that agent, or to every agent, wins over it, and the hook's stricter verdict holds over it.
- **Reported as a widening.** The permissions overview reports it as a widening the capability contributes, so no agent's reach changes silently.

So a capability whose agent needs such a tool, which a strict posture would deny, carries the grant with it, and no project copies it by hand. This record overturns ADR-016 in part, where a capability's grants apply on install. It overturns ADR-021 in part, where a capability shapes only its own agents' reach, through its deny, and where a definition no grant references changes no decision: a privilege a capability defines that comes to recognise a tool another capability allows makes the loader refuse that allow. It completes in place the passages of ADR-016 whose words stay true, such as those that speak of a capability's deny alone, the account of where [ADR-087](ADR-087-agent-definition-picker.md)'s modules are loaded from, the account of what [ADR-095](ADR-095-hook-out-of-reach.md)'s bound holds, and the account of what [ADR-073](ADR-073-builder-runs.md)'s runner adds to a working run.

**Why an ADR.** What a capability's grant may carry, and how the model's loader composes, refuses and reports it, is a boundary of the backbone's permission model that binds every capability, an architecture record's question ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Distinct from PRJ"). A capability that allows a privilege reads the rule here, not in the record of the capability that first did, and the permissions README, which every project receives, carries it once built (Implications).

## Context

**Before this record.**

- **A capability's grants.** An installed capability may ship a grants fragment, which the model's loader composes, found through the installed components, before the active profile and the project's own grants (ADR-016 points 1 and 2). The operator's profile choice and manual grants win on the allow side, and a capability's deny survives by deny-wins (ADR-016's Decision). ADR-016 argues only a deny's safety on install: a deny narrows an agent's reach, so it applies on install under [ADR-008](ADR-008-confinement-allowances.md)'s narrowing class, and the overview reports which capability contributed it (ADR-016 point 7). ADR-016 point 1's guarantee, that the operator's intent is never narrowed away by a capability allow it did not ask for, does not hold of today's code where that allow carries a scope: the decision core denies a call at any allow that covers it but whose scope it falls outside, wherever that allow stands among the grants. This record's bar on a scope makes it hold for a capability's allow (point 1). Neither record bounds a capability's allow, and the loader composes a capability's grant of any effect, to any subject, unchecked.
- **A capability's privileges.** A capability may define privileges of its own, each scoped to the capability, adding to the catalog and overwriting nothing. ADR-021 gives its reach as over its own agents through its own deny grant (point 3), and the loader refuses a fragment's privilege past its bounds (ADR-021 points 2 and 3). A privilege a capability defines may recognise what another privilege recognises, and ADR-021 holds such a definition inert until a grant references it (point 4).
- **How a privilege recognises a call.** By a shell command's words, by the name of a tool, whatever its input, or by a file tool whose target lies in named folders (the permissions README, "Privileges and how they are recognized"). The catalog's schema writes a recogniser's names as a list, in which a tool matches by membership, so whether two privileges recognise one tool is a question of set membership. The decision core does not check that shape, and matches a name written as a single string as a part of a name.
- **The harness's tools.** The harness gives an agent some fifty tools, which the Claude Code adapter lists as the tools it knows (`known_tools` in its `tool-access.json`), and it adds more over time. Some run a command: the shell tool, the PowerShell tool and the tool that monitors a command make the shell calls ADR-095 point 3 defines, and a skill can run commands inline (ADR-095 point 4). Others read or write files, or start or schedule work, such as a subagent, a workflow, a scheduled prompt or a run on a remote service. A connected server's tools carry the harness's mark, a name of the form `mcp__<server>__<tool>` under Claude Code. The decision core reads a call of any tool but the shell tool as a call of a tool, recognised by the tool's name, so a privilege that names a tool recognises its calls whatever their input.
- **The posture.** The posture decides a call no grant covers: a strict posture denies it, and a lenient one leaves it to the harness's own rules, which may ask a person (the permissions README, "Grants and verdicts").
- **A widening waits for a bound.** The permission hook allows no more than its bound: a model a person realized, or, in a working run, the model the runner reads from the default branch. A change in the checkout that widens the model binds only once a person realizes it, and realizing shows each widening before it writes (ADR-095 point 3).

**The forcing case.** The project-management capability proposes that its agent hold a harness's tools for messaging other sessions and listing them, under every posture ([project-management:DEC-081-delegation-between-seats] point 2). A capability's deny cannot grant them.

**Terms.**

- **A capability's allow** is any grant in a capability's grants fragment whose effect is anything but exactly `deny`, as the decision core reads it: one whose effect is allow, one that names no effect, since a grant's effect is allow by default, and one with any other value.
- **An agent the capability ships** is the agent of a name whose definition, as the name-collision precedence picks it, is the capability's own (the agents README, "Name-collision precedence").
- **A recogniser of the tool kind** names tools, and recognises a call of one of them, whatever its input. The core does not read which names are the harness's: of each name such a recogniser gives, the loader checks only whether the backbone's list holds it, or whether it carries a connected server's mark.
- **The backbone's list** is its list of the harness's tools a capability may allow (point 1).
- **A connected server's tool** is one whose name carries the harness's mark of a tool a connected server gives: under Claude Code, a name of the form `mcp__<server>__<tool>`.
- *Realizing*, *a widening* and *a bound* are ADR-095's, and *the posture* is the permission model's.

## Decision

**A capability's grant may allow a privilege, but only one the capability defines itself, whose every recogniser is a list of tool names, each on the backbone's list or a connected server's tool, and none that a privilege of the backbone's or of another capability's recognises, only to an agent the capability ships, and with no scope. The allow comes into the model on install, as a deny does, binds only through a bound, and is reported as a widening the capability contributes. The model's loader refuses any other allow of a capability's, which then composes nothing and is named as rejected.**

### 1. A capability allows only tools the backbone lists, or a connected server's, and only to an agent it ships

- **What it may allow.** A capability's allow may name only a privilege that meets five conditions:
  1. the capability defines it itself (ADR-021);
  2. every recogniser it has is of the tool kind, its names written as a list, since the decision core matches a name written as a single string as a part of a name, so that a recogniser written as the string `NotebookEdit` recognises `Edit`;
  3. it has no shell-command recogniser, no file tool scoped to folders and no pattern;
  4. no privilege of the backbone's or of another installed capability's recognises any tool it names, as a tool or as a file tool scoped to folders, among the privileges of the catalog that each model the allow is composed into loads;
  5. each tool it names is on the backbone's list, or is a connected server's tool, as the harness marks one, a mark whose form the backbone keeps with the list, as data. Every other tool is refused, a tool the harness adds later among them, until the backbone lists it.
- **The backbone's list.** A tool of the harness's joins it only where it runs no command, reads or writes none of the person's files, reaches nothing outside the person's own sessions, changes no permission or mode of the session, stops or removes no work, and starts or schedules no work: no session, team, subagent, workflow, scheduled prompt or run, on a remote service or elsewhere. A message that wakes one of the person's own sessions, or resumes a subagent the session started, starts none, since what it reaches already exists and works under its own checks. The harness's own store of its sessions and messages is not one of the person's files. It joins by a backbone change that shows the tool meets that test, a surface change declared in its changeset ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md)). The backbone keeps the list beside the permission model's catalog, and the model's loader reads it; the build decides the exact place. The hook's own verdicts read nothing from it, and the shell calls stay as ADR-095 point 3 defines them, so the tool that invokes a skill stays under ADR-095 point 4's ask.
- **A connected server's tool** may be allowed. Its name matches whatever server the session connects under that name, one from the person's own settings among them, and such a tool may itself run commands. Realizing names each such allow as a widening before it binds (point 2), by the tool's name, not by the server behind it. In a working run no realizing report exists, and the allow binds once it reaches the default branch (ADR-073 point 2).
- **To whom, and how far.** It allows that privilege only to an agent the capability ships, and carries no scope. An allow covers a call outside its scope with a deny, so a capability's scoped allow would deny there what the operator allows.
- **Checked exactly, at each load.** The loader checks the five conditions exactly: each recogniser is a list, so a tool matches by set membership, against the backbone's list and the other privileges' lists alike, and a connected server's mark is read from the name. It checks them each time it loads the model. So where a privilege installed later, by the backbone or another capability, comes to recognise a tool the capability's privilege names, the loader refuses the allow from then on (point 4). A definition that no grant references then narrows another capability's agent. That narrowing fails closed: the allow composes nothing, and the read surface names it as rejected. So merging such a definition on install stays safe, since what it changes fails closed and is named as rejected: a narrowing, reported, of ADR-008's class.
- **The agent, read from the bound.** Realizing is served from the installed release, the environment the installer made for the methodology's tool, which holds the YAML library the picker's reader of records needs (ADR-095 point 2). It loads both modules, the picker and the lifecycle's reader, from the installed release, asks the picker which definition wins for each agent's name a capability's allow names, and keeps the answer in the snapshot, and, for a name it could not answer, which record it could not read. A runner keeps the same in the model it names. The loader reads the answer from the bound, and composes the allow only where the answer gives the capability's own definition. Where no bound binds, or the bound holds no answer for the name, the allow composes nothing, which fails closed in every case, and the read surface says why. Where realizing could not read a record the answer needs, such as a link, a file that is not a regular file, or records the installed release cannot read whole, the read surface says so and names the record, since another realizing does not give the answer while the record stays so. In a working run, where the default branch's backbone brings this check, the answer is missing only where the runner could not read a record at that branch's head, and the read surface names that record too. Otherwise, where no bound binds, the bound was kept before this record's build, or the allow was added since the last realizing, the allow waits on realizing, and the read surface says so, as ADR-095 point 4's "No bound" says the model is not in force. Of the agent test, the read surface names the allow as rejected where the answer gives another definition, or gives none that counts, as where the project skipped the capability's agent (point 4). So a change in the checkout to which definition wins takes effect at the next realizing, which delays a narrowing and never widens anything.
- **Not in a run's rules.** A run's rules carry, of a session's model, only the denies that bind on the run's agent ([ADR-066](ADR-066-unattended-agent-runner.md) points 3 and 5). So a capability's allow never enters a run's rules, and the privileges a capability declares for its runs, which no session's model composes, are none of condition 4's set. Where the hook judges a run's calls, it judges them by a session's model, a working run's being the one read from the default branch (ADR-073 point 2), which loads the session's catalog. So condition 4's set is that catalog wherever the allow is composed.
- **Its reach.** So a capability's allow reaches, for that agent, only tools the backbone lists, none of which runs a command, reads or writes the person's files, reaches outside the person's own sessions, changes a permission or mode of the session, stops or removes work, or starts or schedules work, as the list's test reads it, and connected servers' tools, each of which reaches whatever server the session connects under its name and may itself run commands. This record decides no bound on a capability's deny.

### 2. The allow comes in on install, and binds only through a bound

- **In the model as a deny is.** The allow comes into the model on install, in the capability's fragment, as a deny does (ADR-016 points 1 and 2), and composes once the bound holds the picker's answer for its agent (point 1).
- **A widening.** The allow widens the agent's reach, so ADR-008's narrowing class, by which ADR-016 point 7 applies a deny on install, does not cover it. ADR-008 governs confinement, and here the person's gesture is ADR-095's realizing, which shows each widening. The allow binds only through a bound: a model a person realized, realizing having shown it as a widening, or, in a working run, the model the runner reads from the default branch (ADR-095 point 3). So a capability's denies apply on install, and its allows only through a bound.
- **What it decides.** Once it binds, the allow decides a call that no grant of the operator's covers, which the posture would otherwise deny or leave to ask a person.
- **What holds over it.** Any deny of that privilege, to that agent or to every agent, wins over the allow by deny-wins, whether it is the capability's own, another capability's or the operator's. The hook's stricter verdict also holds over it: a lock's, and any ask the hook gives of its own (ADR-095 point 4). Guardrails and locks judge shell calls, which point 1 keeps out of the allow's reach.
- **Withdrawn by a deny.** The operator withdraws a capability's allow by a deny of the privilege to that agent. Revoking removes only the project's own grants, and so none of a capability's.

### 3. The read surface reports it as a widening the capability contributes

The model's read surface, the permissions overview among it, reports a capability's allow as a widening, with the capability that contributed it, as it reports a capability's deny (ADR-016 point 7). It reports an allow that waits on realizing as waiting, and of one whose answer is missing since realizing, or a runner, could not read a record, it names the record (point 1). It reports an allow outside the bound as rejected (point 4).

### 4. The loader refuses any other allow of a capability's

- **The refusal.** The model's loader refuses a capability's allow that names a privilege outside point 1's bound or a subject other than an agent the capability ships, and one that carries a scope. It judges a grant for each privilege it names, and refuses the grant where any of them falls outside the bound.
- **Only that grant.** A refused allow composes nothing, and the model's read surface names it as rejected, with its capability. The fragment's other grants, its denies among them, still compose. An allow whose agent the bound holds no answer for is not a refused allow: it composes nothing until the bound holds the answer, and the read surface says why, that it waits on realizing, or which record realizing, or a runner, could not read (point 1).
- **Where another definition wins.** Where the picker's answer that the bound holds gives, for the agent's name, the project's own definition, another capability's or core's, the agent is not one the capability ships, and the loader refuses the allow.
- **Within the loader's limits.** The check runs where the loader runs: on the standard library alone, from the copy, or, in a working run, from the project's tree at the default branch's head (ADR-016 point 3, as ADR-095 refines it). It reads only inputs of the kinds ADR-095 point 3's bound holds: the catalogs and the backbone's list as each judgement reads its inputs, so a list a sync narrows takes effect at once, and the picker's answer from the bound in each judgement (point 1).
- **A connected server's tool.** Its name matches whatever server the session connects under that name, one from the person's own settings among them, and such a tool may itself run commands. Realizing names the allow by the tool's name, not by the server behind it, so the allow reaches whatever server a session later connects under that name.
- **The agent, by its name.** The hook picks the subject by the agent's name (the permissions README, "Default-agent subject resolution"). An unmarked file at the deployed copy's place, which deploying never overwrites, may run under that name (the agents README, "Deploy mechanics"), so the allow reaches whatever runs under it. That is true of every grant to an agent.
- **Where the check does not run.** An installed release older than the build that brings this check composes a capability's allow unchecked. Where that release holds ADR-095's bound, only realizing's report of the widening shows such an allow, and where it does not, the allow binds as the model loads, as any capability's grant does before this record. In a working run, the default branch's backbone governs, and no realizing report exists: where that backbone predates the build, the allow composes unchecked into the model the runner reads from the default branch.

### What this overturns in ADR-016 and ADR-021, and what stands

Overturned, each a passage whose words this record makes untrue, for a capability's allow or for the loader's refusal of one, and the line each record gains points here (Implications):

- ADR-016's Summary, "Install the capability → its grants apply", since a capability's allow binds only through a bound (point 2);
- in ADR-021's Summary bullet on a guardrail, its last clause, "it shapes only its own agents' reach, through its own deny grant (ADR-016's channel, unchanged)", since it shapes that reach through its allow too, and a privilege it defines can have the loader refuse another capability's allow (point 1);
- ADR-021 point 3's "A capability's reach is over its own agents via its own deny grant", for the same reasons (point 1);
- ADR-021 point 4's "This does not let a capability narrow a third party's reach", "a capability fences behaviour only by *also* shipping a deny grant, and that grant (ADR-016's channel) is what binds", "the new definition is inert until a grant references it" and "the definition merely supplies the vocabulary", since a privilege a capability defines that comes to recognise a tool another capability allows has the loader refuse that allow, though no grant references the definition (point 1);
- ADR-021's Rationale, "an unused capability privilege changes *no* decision (it is allow-by-default vocabulary referenced by nothing until the capability's own grant names it), so the worst a capability can do is fence its own agents", for the same reason, and since a capability can also allow its agents named tools of its own, reported as a widening (points 1 and 3);
- ADR-021's Implications bullet "Narrowing-footing: a definition is not itself a narrowing", in that heading, in "*adding* an allow-by-default privilege narrows nothing — it changes no decision until a grant references it", in the footing "(inert vocabulary)" it gives the merge on install, and in "not on borrowed narrowing", for the same reason, and since that merge stays safe as a narrowing, reported, of ADR-008's class (point 1).

The narrowing these passages leave out fails closed: a refused allow composes nothing, and the read surface names it as rejected (point 4).

Refined in place: the passages the Implications name, their words left true.

Standing: the rest of each record. Among it are ADR-016's composition and its discovery through the installed components. So are ADR-021's merge of a capability's privileges, its bounds on them, the bans on a guardrail and on a lock (ADR-095 point 3) among them, and its attribution of them. In ADR-021 point 4, the overlap it permits stands, which deny-wins settles for each subject's grants, and so does its honest bound's clause "a capability can deny recognised commands **to the subjects its own grants name**". A privilege that shares a tool with another is merged as ADR-021 decides, on either side, and the loader refuses only a capability's allow of a privilege that names a tool a privilege of the backbone's or of another capability's recognises (point 1).

## Rationale

**Why a capability may allow at all.** An agent's reach is its capability's policy, and travels with the capability, as a deny of its own does (ADR-016). Left to each project, a strict posture would deny the call with no word, and every project that installs the capability would copy the same grant by hand, the hand-copy ADR-016 removed for a deny.

**Why only tools the backbone lists, or a connected server's, and only to its own agent.** A list of the tools a capability may allow fails closed: a tool the harness adds later is refused until a backbone change shows that it meets the test, as the hook's guard does not trust a tool the adapter does not know, and asks before a call of one whose input names a folder it denies (ADR-095 point 4). The test keeps out of a capability's allow every tool of the harness's that runs a command, reads or writes the person's files, reaches outside the person's own sessions, changes a permission or mode of the session, stops or removes work, or starts or schedules work, so the reach of each such tool stays the operator's. A tool's name matches by membership in a list, so a bound on tools named in lists, each on the backbone's list or carrying a connected server's mark, and none that a privilege of the backbone's or of another capability's recognises, is one the loader checks exactly, at every load. So the worst a capability can do through its allow is reach, for its own agent, the listed tools its own privilege names, and connected servers' tools, which reach whatever server the session connects under their names and may run commands, each reported as a widening and named by realizing before it binds, or, in a working run, where no realizing report exists, binding once it reaches the default branch (ADR-073 point 2). Through a definition, the worst it can do beyond its own agents is have the loader refuse another capability's allow of a tool it comes to recognise, which fails closed and is named as rejected. A refused allow composes nothing, so the agent keeps the reach it had without it, and the capability's denies still narrow it. The cost is that a capability whose agent needs a tool of the harness's not yet listed waits for a backbone release that lists it, and until then a project grants it by hand.

**Why the agent is read from the bound.** The picker reads the capabilities' records through a reader that needs the YAML library (ADR-087 point 1, whose alternatives reject a parser of them on the standard library), the hook's loader runs on the standard library ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 1, ADR-095 point 2), and realizing is served from the installed release, which holds the library and from which it loads both modules (ADR-095 point 2). Kept in the bound, the answer is an input the hook and every reader of the model share, and a change to which definition wins waits for the next realizing, which delays a narrowing and widens nothing.

**Why reported as a widening, and binding only through a bound.** Reported with the capability that contributed it, the allow changes no agent's reach silently, as the report of a deny keeps a narrowing in view (ADR-016 point 7). It binds only through a bound (ADR-095 point 3), so a person who realizes the model sees the allow before it binds, and in a working run it binds once it reaches the default branch, as any grant there does (ADR-073 point 2).

### Alternatives considered

- **Leave every allow to the project, and have a capability ship only the privilege's definition.** Not taken, as "Why a capability may allow at all" says.
- **Any recogniser, stated honestly.** A capability's allow may name a privilege it defines whatever its recognisers, and realizing shows each recogniser. Not taken: the bound keeps the reach of every tool of the harness's that the backbone does not list the operator's, a shell call's and a file tool's among it; what the narrow bound refuses costs a project one grant at setup; and widening the bound later takes a record for a real case, while narrowing it later breaks the capabilities that rely on it.
- **Any privilege that is neither a guardrail nor locked, to the capability's own agent.** Not taken, for the same reasons: such a privilege may recognise shell commands, file tools and tools another privilege shares.
- **A list of the tools refused,** the harness's tools that run a command, with every other tool open to a capability's allow but for those another privilege recognises. Not taken: such a list leaks, since tools of today that it does not name start agents, teams, workflows or runs, schedule work, publish outside the project or read files, more of them than a list of the tools refused can keep up with, and it fails open on every tool the harness adds, until the backbone names it.
- **Four conditions, stated honestly,** with no condition on which of the harness's tools the privilege names, so that realizing's report is all that shows an allow of one that runs a command. Not taken: the approval screen would then be the only guard on a capability reaching the harness's shell, which the narrow bound exists to keep the operator's.
- **Refuse a connected server's tools too.** Not taken: an agent built around a server the project connects would need a grant by hand at setup in every project, and such a tool reaches what the server the session connects under its name exposes, which realizing names, by the tool's name, before the allow binds. In a working run no realizing report exists, and the allow binds once it reaches the default branch (ADR-073 point 2).
- **The hook asks the picker at each load.** Not taken: the hook would need the YAML library the picker's reader of records needs, against ADR-014 point 1 and ADR-095 point 2, or a parser of the records on the standard library, which ADR-087's alternatives reject.
- **The project's own shadowing, read at once.** The loader could tell, with the standard library alone, that the project's own definition shadows the capability's agent, since the project's place always wins ([COR-013](../../../.pkit/decisions/core/COR-013-agent-architecture.md) point 8) and the picker reads which files exist; only the choice between two capabilities and the skips need the YAML reader. That narrowing would then take effect at once. Not taken: it edges toward a second picker, which ADR-087 point 3 bars, since every part that picks asks the picker and keeps no order of its own. Until the next realizing, the allow, which realizing showed before it bound, reaches the project's own definition under that name, which the project wrote itself.
- **A per-project opt-in on top of realizing.** Not taken: realizing is already the person's gesture, shown for each widening (point 2).
