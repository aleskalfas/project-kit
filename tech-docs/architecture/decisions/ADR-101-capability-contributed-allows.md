## Summary

**In plain terms:** [ADR-016](ADR-016-capability-contributed-intent-grants.md) lets an installed capability ship grants that the permission model composes for it, and [ADR-021](ADR-021-capability-contributed-privilege-definitions.md) lets it define privileges of its own. ADR-016 argues only a deny's safety on install, and ADR-021 gives a capability's reach over its own agents through its deny. Neither bounds a capability's allow, and the model's loader composes a capability's grant of any effect, to any subject, unchecked. This record lets a capability's grant also allow a privilege, on these terms:

- **Only tools of its own that run no command, only to its own agent.** The privilege is one the capability defines itself. It recognises tools by their names alone, written as a list, none of them a tool that runs a command, which the backbone lists, and none that another privilege recognises. A connected server's tool may be among them. The agent is one the capability ships, and the allow carries no scope. The model's loader refuses any other allow of a capability's: that grant composes nothing and is named as rejected, and the fragment's other grants still compose.
- **Composed on install, binding only through a bound.** The allow is composed into the model on install, as a deny is. It widens the agent's reach, so it binds only through a bound: a model a person realized, or, in a working run, the model the runner reads from the default branch. A deny in the model wins over it, and the hook's stricter verdict holds over it.
- **Reported as a widening.** The permissions overview reports it as a widening the capability contributes, so no agent's reach changes silently.

So a capability whose agent needs a tool that a strict posture would deny carries the grant with it, and no project copies it by hand. This record overturns ADR-016 in part, where a capability's grants apply on install. It overturns ADR-021 in part, where a capability shapes only its own agents' reach, through its deny, and where a definition no grant references changes no decision: a privilege a capability defines that comes to recognise a tool another capability allows makes the loader refuse that allow. It completes in place the passages of ADR-016 whose words stay true, such as those that speak of a capability's deny alone, and the account of where [ADR-087](ADR-087-agent-definition-picker.md)'s picker is loaded from.

**Why an ADR.** What a capability's grant may carry, and how the model's loader composes, refuses and reports it, is a boundary of the backbone's permission model that binds every capability, an architecture record's question ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Distinct from PRJ"). A capability that allows a privilege reads the rule here, not in the record of the capability that first did, and the permissions README, which every project receives, carries it once built (Implications).

## Context

**Before this record.**

- **A capability's grants.** An installed capability may ship a grants fragment, which the model's loader composes, found through the installed components, before the active profile and the project's own grants (ADR-016 points 1 and 2). The operator's profile choice and manual grants win on the allow side, and a capability's deny survives by deny-wins (ADR-016's Decision). ADR-016 argues only a deny's safety on install: a deny narrows an agent's reach, so it applies on install under [ADR-008](ADR-008-confinement-allowances.md)'s narrowing class, and the overview reports which capability contributed it (ADR-016 point 7). ADR-016 point 1's guarantee, that the operator's intent is never narrowed away by a capability allow it did not ask for, does not hold of today's code where that allow carries a scope: the decision core denies a call at the first allow whose scope the call falls outside, before it reads a later allow, and a capability's grants come before the operator's. This record's bar on a scope makes it hold for a capability's allow (point 1). Neither record bounds a capability's allow, and the loader composes a capability's grant of any effect, to any subject, unchecked.
- **A capability's privileges.** A capability may define privileges of its own, each scoped to the capability, adding to the catalog and overwriting nothing. ADR-021 gives its reach as over its own agents through its own deny grant (point 3), and the loader refuses a fragment's privilege past its bounds (ADR-021 points 2 and 3). A privilege a capability defines may recognise what another privilege recognises, and ADR-021 holds such a definition inert until a grant references it (point 4).
- **How a privilege recognises a call.** By a shell command's words, by the name of a tool, whatever its input, or by a file tool whose target lies in named folders (the permissions README, "Privileges and how they are recognized"). The catalog's schema writes a recogniser's names as a list, in which a tool matches by membership, so whether two privileges recognise one tool is a question of set membership. The decision core does not check that shape, and matches a name written as a single string as a part of a name.
- **The tools that run a command.** The harness's shell tool, its PowerShell tool and its tool that monitors a command make the shell calls [ADR-095](ADR-095-hook-out-of-reach.md) point 3 defines, and a skill can run commands inline (ADR-095 point 4). The decision core reads a call of any tool but the shell tool as a call of a tool, recognised by the tool's name, so a privilege that names one of those tools recognises its calls whatever command they run.
- **The posture.** The posture decides a call no grant covers: a strict posture denies it, and a lenient one leaves it to the harness's own rules, which may ask a person (the permissions README, "Grants and verdicts").
- **A widening waits for a bound.** The permission hook allows no more than its bound: a model a person realized, or, in a working run, the model the runner reads from the default branch. A change in the checkout that widens the model binds only once a person realizes it, and realizing shows each widening before it writes (ADR-095 point 3).

**The forcing case.** The project-management capability proposes that its agent hold a harness's tools for messaging other sessions and listing them, under every posture ([project-management:DEC-081-delegation-between-seats] point 2). A capability's deny cannot grant them.

**Terms.**

- **A capability's allow** is any grant in a capability's grants fragment whose effect is anything but exactly `deny`, as the decision core reads it: one whose effect is allow, one that names no effect, since a grant's effect is allow by default, and one with any other value.
- **An agent the capability ships** is the agent of a name whose definition, as the name-collision precedence picks it, is the capability's own (the agents README, "Name-collision precedence").
- **A recogniser of the tool kind** names tools, and recognises a call of one of them, whatever its input. The core cannot tell a harness's own tool from a connected server's, or from a name no harness gives, so the loader checks only the kind.
- **A tool that runs a command** is the harness's shell tool, its PowerShell tool or its tool that monitors a command, which make ADR-095 point 3's shell calls, its tool that invokes a skill, since a skill can run commands inline (ADR-095 point 4), or such a tool the harness adds later.
- *Realizing*, *a widening* and *a bound* are ADR-095's, and *the posture* is the permission model's.

## Decision

**A capability's grant may allow a privilege, but only one the capability defines itself, whose every recogniser is a list of tool names, none of them a tool that runs a command and none that another privilege recognises, only to an agent the capability ships, and with no scope. The allow is composed into the model on install, as a deny is, binds only through a bound, and is reported as a widening the capability contributes. The model's loader refuses any other allow of a capability's, which then composes nothing and is named as rejected.**

### 1. A capability allows only named tools of its own that run no command, and only to an agent it ships

- **What it may allow.** A capability's allow may name only a privilege that meets five conditions:
  1. the capability defines it itself (ADR-021);
  2. every recogniser it has is of the tool kind, its names written as a list, since the decision core matches a name written as a single string as a part of a name, so that a recogniser written as the string `NotebookEdit` recognises `Edit`;
  3. it has no shell-command recogniser, no file tool scoped to folders and no pattern;
  4. no other privilege recognises any tool it names, as a tool or as a file tool scoped to folders: no other privilege of the catalog that each model the allow is composed into loads, the backbone's and every installed capability's;
  5. it names no tool that runs a command (ADR-095 point 3, "A shell call"), as the backbone's one list of them gives it: `Bash`, `PowerShell`, `Monitor` and `Skill` under Claude Code, and each such tool the harness adds later. The tool that invokes a skill is on the list, since a skill can run commands inline (ADR-095 point 4). The loader and the hook read the same list.
- **A connected server's tool.** A tool of a server the project connects (`mcp__…` under Claude Code) may be allowed. It reaches only what that server exposes, and realizing names each such allow as a widening before it binds (point 2).
- **To whom, and how far.** It allows that privilege only to an agent the capability ships, and carries no scope. An allow covers a call outside its scope with a deny, so a capability's scoped allow would deny there what the operator allows.
- **Checked exactly, at each load.** The loader checks the five conditions exactly: each recogniser is a list, so a tool matches by set membership, and the tools that run a command are one list. It checks them each time it loads the model. So where a privilege installed later, by the backbone or another capability, comes to recognise a tool the capability's privilege names, the loader refuses the allow from then on (point 4). A definition that no grant references then narrows another capability's agent. That narrowing fails closed: the allow composes nothing, and the read surface names it as rejected.
- **The agent, read from the bound.** Realizing runs from the installed release, which holds the YAML library the picker's reader of records needs (ADR-087 points 1 and 2). It asks the picker which definition wins for each agent's name a capability's allow names, and keeps the answer in the snapshot. A runner keeps the same answer in the model it names. The loader reads the answer from the bound, and refuses the allow where the bound holds none. So a change in the checkout to which definition wins takes effect at the next realizing, which delays a narrowing and never widens anything.
- **Not in a run's rules.** A run's rules carry, of a session's model, only the denies that bind on the run's agent ([ADR-066](ADR-066-unattended-agent-runner.md) points 3 and 5). So a capability's allow never enters a run's rules, and the privileges a capability declares for its runs, which no session's model composes, are none of condition 4's set. Where the hook judges a run's calls, it judges them by a session's model, a working run's being the one read from the default branch ([ADR-073](ADR-073-builder-runs.md) point 2), which loads the session's catalog. So condition 4's set is that catalog wherever the allow is composed.
- **Its reach.** So a capability's allow reaches only those tools, none of which runs a command, for that agent. This record decides no bound on a capability's deny.

### 2. The allow is composed on install, and binds only through a bound

- **Composed as a deny is.** The allow is composed into the model on install, in the capability's fragment, as a deny is (ADR-016 points 1 and 2).
- **A widening.** The allow widens the agent's reach, so ADR-008's narrowing class, by which ADR-016 point 7 applies a deny on install, does not cover it. ADR-008 governs confinement, and here the person's gesture is ADR-095's realizing, which shows each widening. The allow binds only through a bound: a model a person realized, realizing having shown it as a widening, or, in a working run, the model the runner reads from the default branch (ADR-095 point 3). So a capability's denies apply on install, and its allows only through a bound.
- **What it decides.** Once it binds, the allow decides a call that no grant of the operator's covers, which the posture would otherwise deny or leave to ask a person.
- **What holds over it.** A deny in the model wins over it by deny-wins: the capability's own or the operator's. The hook's stricter verdict holds over it: a lock's, and any ask the hook gives of its own (ADR-095 point 4). Guardrails and locks judge shell calls, which point 1 keeps out of the allow's reach.
- **Withdrawn by a deny.** The operator withdraws a capability's allow by a deny of the privilege to that agent. Revoking removes only the project's own grants, and so none of a capability's.

### 3. The read surface reports it as a widening the capability contributes

The model's read surface, the permissions overview among it, reports a capability's allow as a widening, with the capability that contributed it, as it reports a capability's deny (ADR-016 point 7).

### 4. The loader refuses any other allow of a capability's

- **The refusal.** The model's loader refuses a capability's allow that names a privilege outside point 1's bound or a subject other than an agent the capability ships, and one that carries a scope. It judges a grant for each privilege it names, and refuses the grant where any of them falls outside the bound.
- **Only that grant.** A refused allow composes nothing, and the model's read surface names it as rejected, with its capability. The fragment's other grants, its denies among them, still compose.
- **Where another definition wins.** Where the picker's answer that the bound holds gives, for the agent's name, the project's own definition, another capability's or core's, the agent is not one the capability ships, and the loader refuses the allow.
- **Within the loader's limits.** The check runs where the loader runs: on the standard library alone, from the copy (ADR-016 point 3). It reads only inputs the model's bound holds (ADR-095 point 3): the catalogs for the privilege's conditions, and the picker's answer for the agent (point 1).
- **Tools the harness adds later.** Two bounds hold honestly. A tool that runs a command, which the harness adds later, meets condition 5 until the backbone adds it to its list. A tool that reads or writes files, which the harness adds later and no privilege recognises, meets condition 4 until a privilege does: condition 4 refuses today's file tools only because the backbone's privileges name them. Meanwhile, realizing shows such an allow as a widening before it binds (point 2), and the read surface reports it with its capability (point 3).
- **The agent, by its name.** The hook picks the subject by the agent's name (the permissions README, "Default-agent subject resolution"). An unmarked file at the deployed copy's place, which deploying never overwrites, may run under that name (the agents README, "Deploy mechanics"), so the allow reaches whatever runs under it. That is true of every grant to an agent.
- **Where the check does not run.** An installed release older than the build that brings this check composes a capability's allow unchecked. Where that release holds ADR-095's bound, only realizing's report of the widening shows such an allow, and where it does not, the allow binds as the model loads, as any capability's grant does before this record.

### What this overturns in ADR-016 and ADR-021, and what stands

Overturned, each a passage whose words this record makes untrue, for a capability's allow or for the loader's refusal of one, and the line each record gains points here (Implications):

- ADR-016's Summary, "Install the capability → its grants apply", since a capability's allow binds only through a bound (point 2);
- in ADR-021's Summary bullet on a guardrail, its last clause, "it shapes only its own agents' reach, through its own deny grant (ADR-016's channel, unchanged)", since it shapes that reach through its allow too, and a privilege it defines can have the loader refuse another capability's allow (point 1);
- ADR-021 point 3's "A capability's reach is over its own agents via its own deny grant", for the same reasons (point 1);
- ADR-021 point 4's "This does not let a capability narrow a third party's reach" and "the new definition is inert until a grant references it", since a privilege a capability defines that comes to recognise a tool another capability allows has the loader refuse that allow, though no grant references the definition (point 1);
- ADR-021's Rationale, "an unused capability privilege changes *no* decision (it is allow-by-default vocabulary referenced by nothing until the capability's own grant names it), so the worst a capability can do is fence its own agents", for the same reason, and since a capability can also allow its agents named tools of its own, reported as a widening (points 1 and 3);
- ADR-021's Implications bullet "Narrowing-footing: a definition is not itself a narrowing", in that heading, in "*adding* an allow-by-default privilege narrows nothing — it changes no decision until a grant references it", and in the footing "(inert vocabulary)" it gives the merge on install, for the same reason (point 1).

The narrowing these passages leave out fails closed: a refused allow composes nothing, and the read surface names it as rejected (point 4).

Refined in place: the passages the Implications name, their words left true.

Standing: the rest of each record. Among it are ADR-016's composition and its discovery through the installed components. So are ADR-021's merge of a capability's privileges, its bounds on them, the bans on a guardrail and on a lock (ADR-095 point 3) among them, and its attribution of them. In ADR-021 point 4, the overlap it permits stands, which deny-wins settles for each subject's grants, and so does its honest bound on what a capability's grants deny. A privilege that shares a tool with another is merged as ADR-021 decides, on either side, and the loader refuses only a capability's allow of a privilege that names the shared tool (point 1).

## Rationale

**Why a capability may allow at all.** An agent's reach is its capability's policy, and travels with the capability, as a deny of its own does (ADR-016). Left to each project, a strict posture would deny the call with no word, and every project that installs the capability would copy the same grant by hand, the hand-copy ADR-016 removed for a deny.

**Why only named tools of its own that run no command, and only to its own agent.** A tool's name matches by membership in a list, so a bound on tools named in lists, none of them on the backbone's list of tools that run a command and none that another privilege recognises, is one the loader checks exactly, at every load. Keeping out the tools that run a command keeps the reach of a shell call the operator's. So the worst a capability can do through its allow is reach, for its own agent, the tools its own privilege names, none of which runs a command, each reported as a widening; a connected server's tool among them reaches only what that server exposes. Through a definition, the worst it can do beyond its own agents is have the loader refuse another capability's allow of a tool it comes to recognise, which fails closed and is named as rejected. A refused allow composes nothing, so the agent keeps the reach it had without it, and the capability's denies still narrow it.

**Why the agent is read from the bound.** The picker reads the capabilities' records through a reader that needs the YAML library (ADR-087 point 1, whose alternatives reject a parser of them on the standard library), the hook's loader runs on the standard library ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 1, ADR-095 point 2), and realizing runs from the installed release, which holds the library. Kept in the bound, the answer is an input the hook and every reader of the model share, and a change to which definition wins waits for the next realizing, which delays a narrowing and widens nothing.

**Why reported as a widening, and binding only through a bound.** Reported with the capability that contributed it, the allow changes no agent's reach silently, as the report of a deny keeps a narrowing in view (ADR-016 point 7). It binds only through a bound (ADR-095 point 3), so a person who realizes the model sees the allow before it binds.

### Alternatives considered

- **Leave every allow to the project, and have a capability ship only the privilege's definition.** Not taken, as "Why a capability may allow at all" says.
- **Any recogniser, stated honestly.** A capability's allow may name a privilege it defines whatever its recognisers, and realizing shows each recogniser. Not taken: the bound keeps the reach of a shell call, and of the file tools the backbone's privileges name, the operator's, but for the tools the harness adds later (point 4); what the narrow bound refuses costs a project one grant at setup; and widening the bound later takes a record for a real case, while narrowing it later breaks the capabilities that rely on it.
- **Any privilege that is neither a guardrail nor locked, to the capability's own agent.** Not taken, for the same reasons: such a privilege may recognise shell commands, file tools and tools another privilege shares.
- **Four conditions, stated honestly,** with no condition on a tool that runs a command, so that realizing's report is all that shows an allow of one. Not taken: the approval screen would then be the only guard on a capability reaching a shell, which the narrow bound exists to keep the operator's.
- **Refuse a connected server's tools too.** Not taken: an agent built around a server the project connects would need a grant by hand at setup in every project, and such a tool reaches only what that server exposes, which realizing names before the allow binds.
- **The hook asks the picker at each load.** Not taken: the hook would need the YAML library the picker's reader of records needs, against ADR-014 point 1 and ADR-095 point 2, or a parser of the records on the standard library, which ADR-087's alternatives reject.
- **A per-project opt-in on top of realizing.** Not taken: realizing is already the person's gesture, shown for each widening (point 2).
