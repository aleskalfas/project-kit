## Summary

**In plain terms:** project-kit turns on, for its own repository, the two capabilities it ships for keeping analysis and documentation true — software-analysis (use cases, actors, journeys, glossary, revalidation; [software-analysis:DEC-001](../../../.pkit/capabilities/software-analysis/decisions/DEC-001-software-analysis-discipline.md)) and living-docs (documentation spaces by audience, anchored pages, reader-review; [living-docs:DEC-001](../../../.pkit/capabilities/living-docs/decisions/DEC-001-living-docs-discipline.md)) — before any downstream project does. Both are already registered in the manifest as incubated in this repository; this record fixes the topology they operate under: two roots (`docs/` for users, `tech-docs/` for maintainers), which files count as pages of which space, the stance that `.pkit/` is *source* here rather than a synced copy, where the analysis lives, and that the friction check runs in enforcing mode from the day it exists.

## Context

project-kit ships software-analysis and living-docs on core pieces accepted alongside them: the backbone configuration file ([COR-048](../../../.pkit/decisions/core/COR-048-backbone-configuration.md)), documentation roots ([COR-049](../../../.pkit/decisions/core/COR-049-documentation-roots.md)) and anchors-and-friction ([COR-050](../../../.pkit/decisions/core/COR-050-anchors-and-friction.md)). The maintainer chose project-kit as first adopter, ahead of the downstream project that asked for these capabilities (the design is in the scratchpad note `2026-09-26-software-analysis-living-docs-design`), so that rough edges are found here first.

project-kit's documentation does not sit in one place. Its user-facing material is the top-level `README.md` plus the adopter-facing READMEs under `.pkit/`. Its technical material is scattered: the architecture decisions (point 2 relocates them out of `docs/architecture/`), `CONTRIBUTING.md`, `CLAUDE.md` with the rule files it includes, and the decision corpora (`.pkit/decisions/`, capability `decisions/` folders). Two constraints shape the answer. The documentation-roots record requires roots to lie *outside* the methodology tree, so files under `.pkit/` can join a space only as declared places, never through a root (COR-049 point 1). And living-docs says trees that arrive as a synced copy are never places, so that a sync never shows up as friction (COR-050 point 14; living-docs DEC-001 point 1). In project-kit no sync copies into `.pkit/` ([ADR-059](ADR-059-methodology-source-repository.md)).

## Decision

1. **Roots.** User root `docs/`, internal root `tech-docs/`. `docs/` does not exist until the first user page lands, and validation warns of the missing root until then (COR-049 point 7). The architecture decisions sit at `tech-docs/architecture/decisions/` (point 2). Their location is an explicit overlay value, so changing the internal root moves no file (COR-049 point 6).
2. **Relocation of the architecture decisions to `tech-docs/architecture/decisions/`** happens in a dedicated reviewed pull request that rewrites references, and it lands *before* the roots are declared in the backbone configuration. Declaring `docs/` as the user root makes it a default place of the user space (living-docs DEC-001 point 1); relocating first avoids the architecture decisions sitting inside a user-space place while being technical material — living-docs' own record settles nested places (the most specific wins) and how out-of-root places are assigned, but relocating first keeps records out of the user space by construction. The rewrite touches shipped trees: kit-shipped READMEs, records and scripts cite these decisions by relative path, so the relocation is a diff on the propagation surface and declares a changeset (PRJ-002).
3. **Spaces — pages, artefacts and anchor targets.** A *page* is a document living-docs governs: reader and page-kind fields, the `LDOC` rules, reader-review. Decision records — COR, PRJ, capability DEC and ADR — and rule-set files in the sense of [COR-051](../../../.pkit/decisions/core/COR-051-rule-sets.md) are **not pages**. They are anchor targets of the `record` kind (COR-050 point 2), and — once they sit inside a root — artefacts the backbone scans: they may carry anchors and be friction-checked, and until they do they appear in the unanchored measure (COR-050 point 8). That count is accepted, not excluded; a record that anchors the code it governs is what the core record wants. The principle for the root-level project documents: *a document is a place of the space that matches its audience.*
   - The **technical space** is `tech-docs/`, plus the declared place `CONTRIBUTING.md`, which is also its entry point until `tech-docs/README.md` exists. `CLAUDE.md` and the operational rule files `.pkit/rules/*.md` are **not places**: `CLAUDE.md` is the harness's configuration file and the rule files are included into it and must start with prose (rule 13 of `core.md`), so they cannot carry front matter; pages anchor to them as `path` targets. Space definitions live under `tech-docs/`; the sub-path is `tech-docs/living-docs/` (living-docs' declared `definitions` location, recorded in its `docs-locations.yaml`), where the `user` and `technical` definitions sit as rule-set files inheriting `LDOC`.
   - The **user space** is `docs/`, plus the declared places `README.md` (its entry point) and the adopter-facing READMEs under `.pkit/`. The selecting principle for those: *a README an adopter reads in order to use an area, capability or adapter is a page; maintainer-facing sub-READMEs (templates, migrations) and skill or agent bodies are not.* The explicit list is written into the friction key of the backbone configuration, which is the source of truth; this record fixes the principle, not the inventory.
   - **`.pkit/` is source here, so its READMEs can be declared as places.** Trees that arrive as a synced copy are never places, so a sync never shows up as friction (COR-050 point 14; living-docs DEC-001 point 1). Whether a tree is a synced copy is judged not by its path but by the manifest's origin and by whether the repository is the methodology's own source, both answered by the lifecycle's synced-copy check. project-kit is that source: its `.pkit/` is the methodology's own tree, authored here and bundled from here, so no sync copies into it ([ADR-059](ADR-059-methodology-source-repository.md)). Origin alone would pass only a capability incubated here, as the two adopted here are (COR-031), or one not registered at all. It would refuse the backbone's own areas, which carry no origin, and a kit-shipped capability, whose origin reads as a copy. Those pass because this is the source repository. So the rule lets project-kit declare its `.pkit/` READMEs as places. Being a place grants no write authority. Which paths an agent may be granted depends on tier and manifest origin ([ADR-051](ADR-051-process-author-edit-authority.md)), with no exemption for the source repository. This stance is project-kit's alone and never propagates (COR-025).
   - **project-kit holds the analysis templates and structures it ships to its own writing rules.** Whoever writes software-analysis's templates, or the structures its kinds declare (software-analysis DEC-001 point 1), follows `WRITE`, project-kit's general writing rules (`tech-docs/rule-sets/writing.md`). These are the rules project-kit's analysis follows, and the shipped hints and examples are the first text a writer of that analysis reads. Ordinarily a project's rules reach only text that stays in the project. Here one reaches text that ships to every adopter, because the shipped trees are authored here. No rule set's scope can reach the templates or structures: a scope names, by place, the artefacts its rules apply to (COR-051 point 2), and a template or a declared structure is no artefact. So project-kit's operational rules (`.pkit/rules/project.md`) send the writers of both to `WRITE`, as they send the analysis's writers. Where a rule of `WRITE` would carry project-kit's own vocabulary or style into the shipped text, such as its glossary's terms or its labels, universal applicability wins and the text stays fit for any adopter (COR-014). The arrangement never reaches an adopter. `WRITE` and the operational rules are project-kit's own files, which no sync carries, and an adopter's own rule sets bind what its writers fill in.
   - The **scratchpad stays outside documentation.** Its notes are non-normative working drafts that retire once their question resolves (COR-012), so they are neither anchored nor friction-checked. The records and documents they produce are.
4. **Analysis.** project-kit's analysis lives at `tech-docs/analysis/` (the default sub-path under the internal root).
5. **Friction check: enforcing from the day it exists.** The pull request that ships the core friction check wires its change check into project-kit's aggregated check script, `scripts/check.sh` — the enforcement boundary [ADR-019](ADR-019-enforcement-gate-mechanism-vs-boundary.md) already pins — and the same pull request makes that check a **required status on `main`** (COR-050 point 12 makes the check binding only when the project does this — and since the aggregator is the unit GitHub requires, every check it already runs becomes a gate with it, which is intended) with the friction mode set to `enforcing`. The whole-repository check runs on `main` with the full history and reports without ever failing on what it finds (COR-050 point 12); its findings go to one tracking issue (the whole-repository report, below). Choosing enforcing at once is the project's prerogative (COR-050 points 12 and 14; the default is warning). The code-to-doc mapping keeps its present advisory setting until onboarding converts it to anchors ([project-management:DEC-053](../../../.pkit/capabilities/project-management/decisions/DEC-053-doc-check-slot.md)); the conversion produces surgical anchors on the surfaces a page actually describes, not ports of the broad tree-to-README rules the mapping deliberately keeps advisory.
   - **Up-to-date base.** The core record makes friction results valid only against an up-to-date base (COR-050 point 6). project-kit does **not** yet gate on that: the change check reports an outdated base and enforcing mode fails only on what it computed against the base it saw; a stale page that slips through when two pull requests land back to back is caught by the whole-repository check on `main` as stale debt. The intended end state is a **merge queue** that runs the check on the merge it is about to make — which also gives the coordination work a single merge path — and it arrives as its own Task, because the work-tracking capability's merge verb must enqueue rather than merge. Requiring branches to be up to date was rejected: under several clones landing pull requests, every merge would invalidate every other open pull request's checks.
   - **The whole-repository report.** The whole-repository check runs in a workflow of its own, apart from the required status: after every push to `main` and once a day, always on what `main` holds and with the full history, since a revalidation point can lie anywhere in it. The check is a function of `main`'s history, so the daily run finds nothing a push did not; it repeats a publication that failed and restores an issue changed by hand. The findings go to **one tracking issue**, its body rewritten in place, with no comment per run. The issue is open exactly while a finding needs an answer. Every finding needs one except two: a deferral, which is itself an answer (COR-050 point 5) and is listed in the body with its reason, and a finding the check reports as owing nothing. The two measures (COR-050 point 8) are in the body and never hold the issue open. With nothing needing an answer the issue is closed, and none is opened where none exists. The run fails only when the check cannot run, the issue cannot be written, or it finds more than one tracking issue — it then keeps the oldest in step and names them all. It never fails on what the check finds, and it is not a required status, so it gates nothing. The workflow, and what renders and publishes its findings, are project-kit's own pipeline tooling; none of it is part of what project-kit ships.
   - **No after-merge status job.** project-kit leaves the core's tool-written status (COR-050 point 10) at its default, *never*. Its declared places include shipped trees, so the job would write bookkeeping that syncs to every adopter and trip the changeset guard on each run, and the core key scopes when the job runs, not where it writes. Debt is read from the debt listing, the status report and the whole-repository report's tracking issue instead. Revisit after onboarding, from a concrete need for the in-file view; the shape to take then is a run scoped to non-shipped places, which would argue for a *where* scope on the core key.
   - **Escape hatch.** Enforcing mode fails a pull request only on the findings the core record assigns to the change check — friction of the pull request, its dead anchors, a marker bump with nothing behind it (COR-050 point 12). Validation findings — a malformed block, a dangling deferral, a cycle — sit outside the hatch: they fail the aggregator in either mode and are fixed, not waived. When the check fails for any other reason — it crashes, or a defect in anchor resolution or configuration — the maintainer flips the friction mode to `warning` in a one-line change disclosed in the pull request and files the defect; the flip is reverted with the fix.

## Rationale

Splitting the roots now gives project-kit the layout the living-docs separation rule asks for, and the same layout as the downstream adopter. Nothing moves on the split because existing locations are explicit; the one relocation that *is* wanted (the architecture decisions) is done once, deliberately, before it could be reported as friction or misplacement. Declaring the scattered files as places, instead of moving them, follows the "record, never move" principle of the documentation-roots record. Keeping records out of the page set keeps living-docs' page rules on prose that has readers, and keeps records where COR-050 already places them: as the things pages and analysis anchor to.

Enforcing from the start is honest costing, not bravado. Legitimate friction — an anchored surface changed, so the page must be revalidated — costs one revalidation, with its justification, in the same pull request; project-kit accepts that cost because every page and anchor here is produced by the tooling under test, and the revalidation *is* the work the capability exists to demand. What the enforcing mode must never do is fail on defects of the tool. Those are bugs in our anchors or our check, found here before any adopter meets them, and fixed at once under the escape hatch. Warning mode would let both kinds accumulate silently; project-kit gains nothing from tolerating noise it created.

**Why the whole-repository report goes to an issue, and is project tooling.** A report in a run's log is read by nobody; an issue that is open exactly while something needs an answer is seen when it matters and silent otherwise. A deferral that held it open would hold it open for good, since deferrals never expire (COR-050 point 4), and an issue that is always open says nothing. What renders and publishes the report is project-kit's own tooling because neither half belongs to the capabilities adopted here: the rendering is a view of the core check over every artefact, page or not, and keeping an issue is an act on the work tracker. Where each ships from is for the backbone and the work-tracking capability to decide, not this record.

**Why an ADR and not a PRJ.** Turning on shipped capabilities for project-kit's own repository has a project-record precedent (PRJ-009, the code-review panel), and COR-025 prefers pinning the architecturally-significant aspect as an ADR and the workflow-mechanical aspect as a PRJ. This record is placed as an ADR because its substance is documentation *topology* — which trees are roots, which files are pages of which space, that `.pkit/` is source and not a synced copy — which shapes the contributor's mental model of where truth lives and how it is checked (the classifier PRJ-005 gives project-kit; COR-025 for the namespace). Point 5 is workflow-mechanical and would, by COR-025's preference, be a PRJ; it is kept here, knowingly, because it follows from the same self-hosting stance and a one-paragraph PRJ cross-referencing this record would carry no independent decision.

### Alternatives considered

- **Keep both roots at `docs/` for now.** Rejected: the split is the intended layout, and doing it first avoids a second transition later.
- **Relocate the architecture decisions during onboarding, as one proposal among many.** Rejected in favour of a dedicated pull request first: a single reviewed move that rewrites the relative links of some fifty records is cheaper alone, and it removes the two-spaces overlap on day one.
- **Move the adopter-facing READMEs into the user root.** Rejected. They stay beside the areas they describe, as declared places.
- **Exclude `.pkit/` READMEs from documentation.** Rejected. They are project-kit's primary user-facing documentation.
- **Treat decision records as pages.** Rejected. Records have no reader field or page kind, and reader-review of a decision is the acceptance gate, not a documentation activity.
- **Exclude the decision folders from the unanchored measure.** Rejected. Records anchoring the code they govern is the intended end state; the count is the honest picture of the distance to it.
- **Hold the shipped analysis templates to no project rule.** Rejected. Every writer of project-kit's analysis would start from text written to looser rules than the analysis itself. Universal applicability is kept by the precedence in point 3, not by leaving the text unruled.
- **Warning mode first, enforcing after a clean period.** Rejected by the maintainer for the reasons above.

## Implications

- Adopting the capabilities here means onboarding project-kit's documentation: anchoring pages, converting the mapping, writing the space definitions, and proposing splits, all through reviewed changes.
- **An open question for onboarding.** The user-space READMEs link densely into the decision corpus, while living-docs' separation rule says user-facing navigation and search never lead into technical material (living-docs DEC-001 point 1). Onboarding settles it (living-docs DEC-001 point 8), not this record.
- **Anchors in shipped READMEs propagate.** Front matter written into `.pkit/**/README.md` reaches every adopter through sync. It is inert there. The backbone refuses a synced tree as a place, whoever declares it (COR-050 point 14). So no adopter resolves those anchors or meets the dead ones they would leave (COR-050 point 7). Adding that front matter is an observable surface change and declares a changeset (PRJ-002).
- **The relocation pull request** also updates the literal `docs/architecture/decisions/` path in PRJ-005 and the overlay's comments, and rewrites the inbound relative links from shipped trees. A later improvement, outside this record: shipped content citing project-kit ADRs by bare id resolved through the overlay, so the next move is a no-op in `.pkit/`.
- The first analysis artefacts are the multi-clone coordination use cases (the Task that writes them is #890, validating the coordination EPIC #943), under `tech-docs/analysis/`.
- **The roots are live.** The backbone configuration names the user root `docs/` and the internal root `tech-docs/`, and its friction key lists the places and excluded paths; living-docs' project configuration names each space's entry point and assigns every out-of-root place to its space (#1007).
