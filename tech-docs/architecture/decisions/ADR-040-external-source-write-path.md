## Summary

**In plain terms:** [COR-041](../../../.pkit/decisions/core/COR-041-external-source-distribution.md) decided the *semantics* of the `externally-sourced` origin — content is pulled whole, pinned to a ref, and reconciled by matching the pin rather than merging. This ADR is the project-kit **write-path contract** that realises those semantics: exactly *how* `pkit` fetches that content from a git source at its pinned ref, where the fetched subtree lands in the consumer, how the pin is recorded, and in what order the fetch and the compatibility gate run. It is the distribution-side member of the write-path-ADR family, the one-altitude-down twin of [ADR-039](ADR-039-pkit-entry-point-router.md)'s whole-kit `uvx project-kit@<pin>` resolver — a *capability* fetched at a pin instead of the *whole kit*.

The load-bearing rule is an **ordering**: fetch-at-pin first, then read the *fetched* manifest, then run [COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md)'s `requires_backbone` compatibility gate against the **consumer's** backbone, then activate or refuse. Compatibility now resolves against a manifest that did not exist locally until the fetch ran — a consumer cannot gate on content it has not yet pulled. Authentication for the interactive/local case leans wholly on [PRJ-004](../../../.pkit/decisions/project/PRJ-004-distribution-channel.md)'s existing GitHub auth (SSH / PAT); **unattended CI auth is explicitly out of scope** here, deferred to a PRJ successor exactly as PRJ-004 deferred its own cross-repo CI auth. A pin names one content, a tag or a commit, and only a version transition moves it ([COR-059](../../../.pkit/decisions/core/COR-059-version-transition.md)), fetching the new content before it writes anything. An unreachable source or an auth gap **degrades loudly and never bricks mid-command**, inheriting ADR-039's D2 posture, except in a transition, which refuses before it writes rather than move a pin to content it does not hold.

## Context

COR-041 fixed the universal semantics of the `externally-sourced` origin and — per COR-025 — delegated the project-specific fetch/auth/land/record write-path to a realising ADR. This is that ADR. It carries the *how* that COR-041 deliberately does not: the channel, the authentication model, the landing path, the pin record, and the failure posture, all of which are project-kit's own mechanism rather than adopter-universal principle.

The consumer that grounds this work (per the #131 review) is an organisation privately sharing an adopter-owned capability — a proprietary discipline or a company house-style — across its own repositories, maintained in one authoring repo and consumed whole everywhere internal, without publishing to the public kit and without forking it. That same content is `incubated-in-repo` in its authoring repo and `externally-sourced` in each consumer (COR-041); origin is a per-repo relationship, not a property of the bytes.

Two existing decisions set the shape this contract inherits. PRJ-004 fixed project-kit's *whole-kit* distribution channel — direct git URL on `github.com`, pinned by tag/branch/SHA, authenticated by the developer's existing GitHub auth, no registry. This ADR reuses that channel one altitude down: a single capability subtree at a pinned ref instead of the whole wheel. ADR-039's D2 fixed the failure posture for its whole-kit pin resolver — an unresolvable pin degrades to running self with a loud drift warning, never a hard fail mid-command. Externally-sourced fetch faces the identical hazard class (offline, untagged ref, auth gap) and adopts the identical answer, except in a transition (point 7).

The critic and architect reviewers ran on the design in the #131 review that produced COR-041 and this contract.

## Decision

**`pkit` fetches externally-sourced content whole from a git source at its pinned ref, lands it in the consumer's own capability subtree under a single owner, records the pin in install state, and gates activation on the fetched manifest — degrading loud when the source is unreachable, except in a transition, which refuses.** Seven points fix the write-path.

### 1. Fetch-at-pin; the pin is the source of truth

Content declared `externally-sourced` names a git source and a ref (tag, branch, or SHA — PRJ-004's pin forms, one altitude down). The pin the project records is that source and a ref that names one content: a tag or a commit. A branch names none, since a push moves it under the same name, the reason PRJ-004 keeps a release candidate off a branch. So the operation that records a pin resolves a branch to the commit at its tip and records that commit, and moving to a later tip is a transition that names the branch again. Every fetch takes the subtree at exactly a tag or a commit, never at a branch's tip, so the content a project holds moves only when its recorded pin moves. A tag pin rests on its author never moving the tag, as the whole kit's pin rests on disciplined tagging (ADR-039 D3).

The pin is the single source of truth for what the consumer holds; **an upgrade is a repointing of the pin**, nothing more — there is no separate "update" verb, only a new pinned ref reconciled by the match-the-pin case COR-041 established. An install records the pin, and never moves one already recorded. Only a version transition moves it, for the capability alone or together with the backbone, to a new ref, a new source or both (COR-059 point 3, in the order point 4 sets). Reconciliation brings the consumer's copy to exactly the pinned ref's content; it is never a merge (COR-001 forbids the merge/conflict machinery, and the content lands under a single owner so no conflict can arise).

### 2. Local fetch-auth leans on PRJ-004's existing GitHub auth; CI auth is out of scope

For the **interactive/local** case — a developer running `pkit sync`/install against a private source — authentication is the developer's *existing* GitHub credential exactly as PRJ-004 fixes for the whole kit: SSH key via `~/.ssh/config`, or PAT via the git credential helper for the HTTPS form. The fetch introduces **no new credential surface**; it reuses the one the developer already has for `git clone`. **Unattended CI authentication to a private source is explicitly out of scope of this ADR** — a PRJ successor owns it, consistent with PRJ-004 having deferred its own cross-repo CI auth to a per-adopter operational concern. Naming it here as deferred keeps the local path shippable without blocking on the CI credential-store design.

### 3. Landing + pin record

The fetched content lands at the consumer's `.pkit/capabilities/<name>/`, the path any capability occupies, held under a **single owner**: the pinned external source. The subtree's `project/` tier is not part of the fetched content, since that tier is the consumer's (COR-001, ADR-033 point 1). Match-the-pin is propagation (COR-059 point 2). So it overwrites the subtree wholesale outside the `project/` tier, never writes that tier, and never writes or removes the recorded pin (COR-059 point 1). The no-shared-files invariant (COR-001) holds unchanged, and the overwrite destroys no local work. The **pinned ref is recorded in install state** as non-derivable state per COR-010 — the ref cannot be re-derived from the consumer's config, so it belongs in the manifest (the same class as an opaque board UUID), and its diff is meaningful: repointing the pin is the visible upgrade gesture.

### 4. Ordering (load-bearing): fetch → read fetched manifest → compatibility-gate → activate-or-refuse

Compatibility resolution runs in a fixed order: (a) fetch-at-pin (point 1); (b) read the **fetched** content's manifest; (c) run COR-010's `requires_backbone` gate — the capability's declared range against the **consumer's** backbone version; (d) activate the capability, or refuse with the surfaced conflict for the adopter to address. The novel property this pins, and the reason ordering is load-bearing, is that **compatibility now evaluates a fetched manifest** — the manifest does not exist locally until step (a) completes, so a consumer cannot gate on content it has not yet pulled. The gate runs at fetch time, before the content is activated, as COR-041 sets. That holds wherever the fetch runs: at install, in the propagation sync runs at the recorded pin (COR-059 point 2), and in a transition. The fetch is simply the step that *materialises* the manifest the gate then reads.

**In a transition, the fetch comes first and the landing later.** A transition resolves every installed component's compatibility before it writes anything, externally-sourced ones included (COR-010 and COR-041). So it fetches a pin it moves before its first write, and later lands that same content, never fetching it twice. In a transition of the backbone, in the order ADR-065 point 4 sets:

- **Step 1, compatibility and collisions:** the transition fetches, to a place outside the project, the content at each pin it moves, and every check the step makes reads that content. A pin it does not move is read from the copy the project holds, and fetched only where no copy is there. A fetch that fails refuses the transition, which has written nothing (point 7).
- **Step 2, the target recorded:** each new pin is recorded with the backbone's target. It is part of the target the person chose, and nothing derives it from the backbone's.
- **Step 3, propagation at the target:** the content step 1 fetched lands, as point 3 sets. Nothing is fetched a second time, so the content that lands is the content that was gated.
- **Steps 4 to 6:** no migration of the capability runs, since no record places one (COR-059 point 3).
- **Step 9, the completion recorded:** the backbone's completion completes the pin's move too. Until it is recorded, the project is at no version (COR-059 point 6, and point 7 here).
- **Finishing an incomplete transition:** the next transition fetches in step 1, and lands in step 3, every pin the project records, since nothing records which pins the interrupted run moved.

**A transition of one externally-sourced capability alone** runs the guard (ADR-065 point 7), step 1 for that capability, step 3 for it, then records its new pin, then step 8. It records the pin once the content has landed, as a transition of one shipped capability records its version once its migrations finish (COR-059 point 3). So the pin it records never names content the project lacks. Interrupted before the pin is recorded, the project keeps its old pin, and the next sync brings the copy back to it.

### 5. The author owns the compatibility claim; the consumer validates it at fetch time

`requires_backbone` on externally-sourced content is an **authored claim**, declared and maintained by the author against the backbone lineage the author tests on; the consumer's gate (point 4) validates it at fetch time. The author repo's own backbone version is irrelevant to consumers — only the declared range is. Critically, **the auto-broaden that this session built does not fire in an author/adopter repo**: `release.py`'s `_broaden_kit_components_requires_backbone` (via `versioning.py`) walks kit-shipped `package.yaml` files and broadens their upper bound, but it runs **only on a project-kit backbone release**, not on a capability release in an author's repo. The mechanism does not compose across repos. So for externally-sourced content the range is a hand-authored claim, not an auto-maintained one; author-side tooling to keep it current on capability release is tracked as #494. Until that lands, an author who ships a capability tested against a newer backbone must widen the range by hand or consumers on that backbone will be refused at point 4.

### 6. Cross-source name collisions surface, never clobber

When two external sources, or an external source and a kit-shipped or incubated capability, claim the same `<name>` at the point-3 landing path, `pkit` **surfaces the collision** for the adopter to resolve rather than silently overwriting one with the other. This extends COR-031's collision rule (an incubated capability whose name collides with a newly kit-shipped one is surfaced, not skipped) to the externally-sourced origin. The single-owner landing (point 3) makes a *clean* fetch conflict-free; this point covers the distinct case of two *claimants* on the same name, which is an adopter decision, not a fetch mechanic.

### 7. Unreachable-source / auth-gap degradation inherits ADR-039 D2

A source that cannot be reached at fetch time — offline, an untagged/moved ref, or an auth gap (the CI case point 2 defers) — **warns loudly and degrades; it never hard-fails mid-command**. This is ADR-039's D2 posture, one altitude down: a degraded-but-running command beats a bricked one, and a fetch failure over one external source must not strand every other operation in the command. How a command meets the failure depends on the fetch:

- **Sync's fetch, at the pin the project records:** `pkit` continues with the copy already on disk, and its warning names the pin it could not reach.
- **An install's fetch:** nothing is recorded or landed for that capability, with a loud warning, and the rest of the command proceeds. So no recorded pin names content the project never received.
- **A transition's fetch:** the transition refuses in its step 1, before it writes anything (point 4). The refusal names the way on: reach the source and run it again, or move the backbone without that pin. A pin moves only to content the transition fetched and gated, as upgrade refuses under the router's fallback rather than move the project's pin to a release it never resolved (ADR-065 point 9). Refusing before any write strands no other operation, since none has run.

**What the project is at.** No fallback follows a repoint. So, through the operations of the core layer, a recorded pin runs ahead of the content the project holds in one state alone: a transition of the backbone interrupted after its step 2 recorded the new pin with the target, and before its completion. The project is then at no version, as COR-059 point 6 reads target and completion: the target names the new pin, and the project reaches it only once the completion is recorded. Sync's guard stops on that state (ADR-065 point 7), and the next transition finishes it (point 4), refusing again while the source cannot be reached. In every other state the project is at the pin it records. A copy that differs from that pin, after a local edit, an interrupted copy or a pin edited by hand, is out of line with it rather than at another version, and the next sync that reaches the source brings it in line (COR-059 point 2).

## Rationale

**Why fetch-at-pin rather than track-a-branch-tip.** The pin-as-source-of-truth model is PRJ-004's registry-free minimalism inherited deliberately (COR-041's rationale). A moving branch tip would make "what does the consumer hold" unanswerable without a network round-trip and would smuggle upgrades in silently; a pinned ref makes the held content a local fact and makes upgrade an explicit, diffable repoint of one recorded value (point 3). This is the same reason ADR-039 pins the whole kit by ref rather than tracking latest. A branch given as the ref keeps its convenience without that cost: the operation that records the pin resolves it to its commit (point 1), so the recorded pin names one content all the same, and taking the branch's later tip is a transition like any other repoint.

**Why the ordering is the load-bearing decision.** Every other point is a placement or a posture; point 4 is the one that could be got *wrong* in a way that wedges a consumer. Reading a *stale or absent* local manifest — or reading the *author repo's* backbone rather than the consumer's — would either refuse compatible content or activate incompatible content. Fixing the order (fetch, then read the fetched manifest, then gate against the consumer's backbone) is what makes compatibility resolution correct for content that arrives over the network. COR-041 states the principle that compatibility evaluates a fetched manifest; this ADR pins the *sequence* that realises it.

**Why a transition fetches in its first step, and records a pin with its target or last.** The gate must read the new pin's content before anything is written (COR-010), so the fetch belongs to step 1, and landing what step 1 fetched, rather than fetching again, keeps the gated content and the landed content one. A pin moved with the backbone is recorded with the target because nothing derives it from the backbone's target, where the target release fixes a shipped capability's version. Recorded later, an interrupted transition would lose the move the person chose, and the next one would gate the old pin against a target it may not fit. A transition of one capability has no completion of its own to mark a move under way, so it records the pin last, once the content has landed.

**Why local auth now and CI auth later.** The grounded consumer (#131) is a developer running sync locally; that path is fully served by the GitHub auth PRJ-004 already assumes, at zero new credential surface. Unattended CI auth is a genuinely harder problem (credential-store shape, deploy keys, token scoping) that PRJ-004 itself deferred one altitude up. Shipping the local path without blocking on the CI design is the same staged move PRJ-004 made; folding CI auth in here would couple a shippable contract to an unsettled one.

**Why surface collisions rather than pick a winner.** A silent clobber at the shared landing path would let one source's content vanish under another's with no signal — the exact failure COR-031 rejected for incubated-vs-kit-shipped names. The adopter is the only party that knows which claimant they meant; the write-path's job is to make the conflict visible, not to guess.

**Why inherit ADR-039's degradation posture, and why a transition refuses.** The failure class is identical (a pin that cannot resolve over the network) and ADR-039 already reasoned it to ground: a hard fail makes the tool *more* fragile than not having the feature, because a transient network gap would break unrelated work. Re-deriving a different posture here would fragment how project-kit handles pin-fetch failure across its two altitudes for no gain. The two altitudes make the same exception too. Under the router's fallback, every command runs on the installed pkit but upgrade, which refuses (ADR-065 point 9), since a transition that moved a pin to content it never fetched would record a version the project does not hold. A transition here refuses for that reason, and before any write, so it strands no other work.

### Alternatives considered

- **Merge the fetched content into a consumer-owned region.** Rejected at the principle level by COR-041/COR-001 — it is exactly the merge/conflict machinery the methodology structurally refuses. This ADR could not have chosen it; the single-owner landing (point 3) is what keeps match-the-pin conflict-free.
- **Gate compatibility before fetching (read a cached or declared range).** Rejected — there is no local manifest to read until the fetch runs; a cached range goes stale against a repointed pin, and gating on the *author repo's* backbone instead of the *declared* range validates the wrong thing. Fetch-then-read-fetched-manifest (point 4) is the only order that gates on current, correct content.
- **Auto-broaden `requires_backbone` for externally-sourced content the way kit releases do.** Rejected as unavailable, not merely unwanted — the broaden mechanism runs only on a project-kit backbone release and does not compose into an author's capability-release flow (point 5). Pretending it applied would leave authors believing a range was maintained that never ran. The honest position is an authored claim plus tracked author-side tooling (#494).
- **Block on unattended CI auth before shipping.** Rejected — couples a shippable local path to PRJ-004's already-deferred CI-credential design. Naming CI auth as out-of-scope (point 2) ships the grounded consumer's path now.
- **Hard-fail on an unreachable source.** Rejected for the same reason ADR-039 D2 rejected it — a transient fetch failure over one source must not brick the whole command.
- **Sync follows a branch pin's tip, read as no version moving.** Rejected: the content a project holds would move with no transition and nothing recorded, which COR-059 point 3 rules out and the first paragraph of this Rationale rejects.
- **Refuse a branch as a ref.** Not taken: resolving it to its commit costs one lookup, keeps PRJ-004's three ref forms one altitude down, and records a pin that names one content all the same.
- **A transition that degrades on an unreachable source, recording the new pin over the copy it holds.** Rejected: the recorded pin would name content the project does not hold, which the gate never read (point 4).
- **A completion recorded beside each pin.** Not taken: through the core layer's operations, a pin runs ahead of its content only in a transition of the backbone interrupted after step 2, which the backbone's completion already marks. The costs are that finishing such a transition fetches every pin, and that sync brings the copy to a pin edited by hand.

## Implications

- **`pkit`'s fetch/sync path gains the externally-sourced fetch step**, authored at implementation time once this record is accepted: fetch-at-pin (point 1), land at `.pkit/capabilities/<name>/` under single ownership outside its `project/` tier (point 3), record the pin in install state as non-derivable manifest state (point 3), and run the point-4 ordering wherever the content is fetched. A branch is recorded as the commit it resolved to (point 1), and a transition fetches a pin it moves in its first step, lands it later and refuses when the source cannot be reached (points 4 and 7). No code is pinned here; this is the design contract the implementation builds against.
- **The compatibility gate reads a fetched manifest** (point 4). This is the concrete realisation of the forward-pointer COR-041 added to COR-010 — compatibility resolution now evaluates content that arrives over the network, not only content already on disk.
- **`requires_backbone` on externally-sourced content is an authored claim** (point 5), and author-side tooling to keep it current on capability release is filed as **#494**. Until #494 lands, the range is maintained by hand; the auto-broaden in `release.py` / `versioning.py` does not fire outside a project-kit backbone release.
- **Unattended CI authentication is a deferred PRJ successor** (point 2), consistent with PRJ-004's own deferral of cross-repo CI auth. This ADR ships the interactive/local path only.
- **Name-collision surfacing extends COR-031's rule to this origin** (point 6); the lifecycle surfaces a same-named external/kit/incubated clash rather than skipping or clobbering.
- **Accepted by the maintainer before the trunk implementation builds against it** (per COR-041's realising-ADR delegation) — a forward design contract, not self-accepted. The fetch step, the pin record, the point-4 gate, the collision surfacing, and the point-7 degradation land citing this record once it is accepted.
- **Stands on** COR-041 (the origin semantics this realises — the *what* to this ADR's *how*), COR-010 (the `requires_backbone` gate that point 4 runs, and the compatibility resolution a transition runs before it writes anything), COR-059 (the recorded pin, out of propagation's reach, the transition that repoints it, and the reconciliation that brings the copy to it), ADR-065 (the transition's order, which point 4 places the fetch in, and the refusal under the router's fallback that point 7 follows), COR-001 (the no-merge / single-owner invariant, and the consumer's `project/` tier, that point 3 rests on), PRJ-004 (the git-URL channel and existing-GitHub-auth model points 1/2 inherit one altitude down), and ADR-039 D2 (the degrade-loud failure posture point 7 inherits). This ADR pins the write-path contract, not COR-041's principle — it must not accrete or restate the origin semantics; on-call reference: if a consumer holds content that does not match its recorded pin, or is refused against a backbone the author's declared range should cover, point 4, 5 or 7 is where to look first.
