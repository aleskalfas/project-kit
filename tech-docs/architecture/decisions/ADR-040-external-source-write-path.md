## Summary

**In plain terms:** [COR-041](../../../.pkit/decisions/core/COR-041-external-source-distribution.md) decided the *semantics* of the `externally-sourced` origin — content is pulled whole, pinned to a ref, and reconciled by matching the pin rather than merging. This ADR is the project-kit **write-path contract** that realises those semantics: exactly *how* `pkit` fetches that content from a git source at its pin, where the fetched subtree lands in the consumer, how the pin is recorded, and in what order the fetch and the compatibility gate run. It does for one *capability* what [ADR-039](ADR-039-pkit-entry-point-router.md)'s resolver does for the *whole kit* with `uvx project-kit@<pin>`: it fetches the content at a pin.

The load-bearing rule is an **ordering**: fetch-at-pin first, then read the *fetched* manifest, then run [COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md)'s `requires_backbone` compatibility gate against the **consumer's** backbone, then activate or refuse. Compatibility now resolves against a manifest that did not exist locally until the fetch ran — a consumer cannot gate on content it has not yet pulled. Authentication for the interactive/local case leans wholly on [PRJ-004](../../../.pkit/decisions/project/PRJ-004-distribution-channel.md)'s existing GitHub auth (SSH / PAT); **unattended CI auth is explicitly out of scope** here, deferred to a PRJ successor exactly as PRJ-004 deferred its own cross-repo CI auth. A pin records the commit its ref named, by its full id. Every later fetch at the pin takes that commit, whatever becomes of the ref, and says when the ref has moved on or is gone. Only a version transition moves a pin, where the person running it names the move ([COR-059](../../../.pkit/decisions/core/COR-059-version-transition.md)): the transition fetches the new content before it writes the project, and records the pin once that content has landed. An unreachable source, a commit it does not serve, or an auth gap **degrades loudly and never bricks mid-command**, inheriting ADR-039's D2 posture, except in a transition, which refuses before it writes the project rather than move a pin to content it never fetched.

## Context

COR-041 fixed the universal semantics of the `externally-sourced` origin and — per COR-025 — delegated the project-specific fetch/auth/land/record write-path to a realising ADR. This is that ADR. It carries the *how* that COR-041 deliberately does not: the channel, the authentication model, the landing path, the pin record, and the failure posture, all of which are project-kit's own mechanism rather than adopter-universal principle.

The consumer that grounds this work (per the #131 review) is an organisation privately sharing an adopter-owned capability — a proprietary discipline or a company house-style — across its own repositories, maintained in one authoring repo and consumed whole everywhere internal, without publishing to the public kit and without forking it. That same content is `incubated-in-repo` in its authoring repo and `externally-sourced` in each consumer (COR-041); origin is a per-repo relationship, not a property of the bytes.

Two existing decisions set the shape this contract inherits. PRJ-004 fixed project-kit's *whole-kit* distribution channel — direct git URL on `github.com`, pinned by tag/branch/SHA, authenticated by the developer's existing GitHub auth, no registry. This ADR reuses that channel one altitude down: a single capability subtree at a pin instead of the whole wheel. ADR-039's D2 fixed the failure posture for its whole-kit pin resolver — an unresolvable pin degrades to running self with a loud drift warning, never a hard fail mid-command. Externally-sourced fetch faces the identical hazard class (offline, untagged ref, auth gap) and adopts the identical answer, except in a transition (point 7).

The critic and architect reviewers ran on the design in the #131 review that produced COR-041 and this contract.

## Decision

**`pkit` fetches externally-sourced content whole from a git source at its pin, lands it in the consumer's own capability subtree under a single owner, records the pin in install state, and gates activation on the fetched manifest — degrading loud when the source is unreachable, except in a transition, which refuses.** Eight points fix the write-path.

### 1. Fetch-at-pin; the pin is the source of truth

Content declared `externally-sourced` names a git source and a ref (tag, branch, or SHA — PRJ-004's pin forms, one altitude down). The pin the project records is that source, that ref, and the commit the ref named, by its full id, when the operation recording the pin fetched it. Every later fetch at the pin takes that commit, whatever the ref names by then. A ref may come to name another commit: a branch is pushed to, a tag's author moves it, or a tag moves by design, as PRJ-004's `latest` does. Such a fetch reads the ref only to say when it has moved on, and to ask for the pin's commit by the ref while the ref still names it, asking by the commit's id otherwise, so the ref never chooses the content. The command that fetched reports the commit the ref names beside the one it took. A ref the source no longer holds is reported as a move is, the report saying the ref is gone, and the fetch takes the pin's commit where the source serves it. Where the source does not serve the pin's commit, the fetch takes nothing, and the command meets that as point 7 says. So the content a project holds moves only when its recorded pin moves, whatever then becomes of the ref. Only a commit names one content whatever its source does later, as PRJ-004 says of its own commit form, immune to tag edits. So a pin is read only where it records all three. A pin that records no commit would name whatever its ref names at each fetch, rather than one content, so sync does not read it (point 3).

The pin is the single source of truth for what the consumer holds; **an upgrade is a repointing of the pin**, nothing more — there is no separate "update" verb, only a new pin reconciled by the match-the-pin case COR-041 established. Who moves a pin is point 8's. A fetch whose content does not name the capability in its package metadata lands nothing, so a pin moved to another source names the capability its old pin named. Reconciliation brings the consumer's copy to exactly the pinned commit's content, where that content passes point 3's check; it is never a merge (COR-001 forbids the merge/conflict machinery, and the content lands under a single owner so no conflict can arise).

### 8. Only a transition moves a pin, where the person running it names the move

An install records the pin, and never moves one already recorded. Only a version transition moves it, for the capability alone or together with the backbone, to another commit of the same source or of another (COR-059 point 3, and point 4 here). A transition moves a pin only where the person running it names the move: a new source or ref, or the pin's own ref again, to take the commit that ref names then. A transition of the backbone never moves a pin unasked. Naming the move is the consent to its target (COR-059 point 4), and the target is the commit the ref names at the transition's one fetch (point 4), as an upgrade takes the latest release that resolves when it runs (ADR-065 point 9). So a branch as the ref keeps, one altitude down, the use PRJ-004 gives it, trying content before it lands: a person takes the branch's head by an explicit act, as installing the whole tool at a branch again does.

Which commands take a move is a record's of its own, refining ADR-065 points 1 and 9 (#3229). That record keeps two things. A move named in a pinned project's upgrade rides the hand-over ADR-065 point 9 sets: the record has the move reach the release that upgrade hands over to, or the hand-over refuse, so the move is never dropped. And `--force` keeps the scope ADR-065 point 6 gives it, over the gates of a moved pin as of any other move.

The commit a pin moves to may hold any version of the capability, an older one included, since no migration of an externally-sourced capability runs (COR-059 point 3). A record that places such migrations also says whether a pin may then move down.

### 2. Local fetch-auth leans on PRJ-004's existing GitHub auth; CI auth is out of scope

For the **interactive/local** case — a developer running `pkit sync`/install against a private source — authentication is the developer's *existing* GitHub credential exactly as PRJ-004 fixes for the whole kit: SSH key via `~/.ssh/config`, or PAT via the git credential helper for the HTTPS form. The fetch introduces **no new credential surface**; it reuses the one the developer already has for `git clone`. **Unattended CI authentication to a private source is explicitly out of scope of this ADR** — a PRJ successor owns it, consistent with PRJ-004 having deferred its own cross-repo CI auth to a per-adopter operational concern. Naming it here as deferred keeps the local path shippable without blocking on the CI credential-store design.

### 3. Landing + pin record

The fetched content lands at the consumer's `.pkit/capabilities/<name>/`, the path any capability occupies, held under a **single owner**: the pinned external source. The subtree's `project/` tier is not part of the fetched content, since that tier is the consumer's (COR-001, ADR-033 point 1). Match-the-pin is propagation (COR-059 point 2). So it overwrites the subtree wholesale outside the `project/` tier, never writes that tier, and never writes or removes the recorded pin (COR-059 point 1). The no-shared-files invariant (COR-001) holds unchanged, and the overwrite destroys no local work. Every landing writes the capability's package metadata last, so a copy whose landing was cut short still declares the version and the ranges of the content it held before (point 4). The **pin is recorded in install state**, with the version and the backbone range its content declares beside it, as non-derivable state per COR-010 — none of them can be re-derived from the consumer's config, so they belong in the manifest (the same class as an opaque board UUID), and their diff is meaningful: repointing the pin is the visible upgrade gesture.

**The project is at the pin it records.** An install records a pin once its content has landed, as a transition does (point 4), so no operation of the core layer records a pin before its content. A copy that differs from its pin, after a local edit or an interrupted landing, is out of line with it rather than at another version. The next sync its guard lets run brings it in line, where its fetch at the pin succeeds (point 1) and that content passes the check that follows. Sync lands a pin's content only where that content declares the version and the backbone range recorded beside the pin, as it copies a shipped capability only where its bundle ships the version the project records (ADR-065 point 1), and where that range admits the recorded backbone (point 4). It takes the pin and both values from the manifest alone, never from the copy, and reads a pin only where the manifest records its source, its ref and its commit (point 1). A manifest that records no pin that sync can read, or no version or no backbone range beside it, fails the check, whatever the content declares. Where the check fails, sync keeps the copy and says so, naming what it found. So a pin edited by hand moves no content to another version or backbone range. An edit that keeps both, or changes them with the pin, passes the check, and only the backbone's gate reads what it lands until the next transition reads the copy.

### 4. Ordering (load-bearing): fetch → read fetched manifest → compatibility-gate → activate-or-refuse

Compatibility resolution runs in a fixed order: (a) fetch-at-pin (point 1); (b) read the **fetched** content's manifest; (c) run COR-010's `requires_backbone` gate — the capability's declared range against the **consumer's** backbone version; (d) activate the capability, or refuse with the surfaced conflict for the adopter to address. The novel property this pins, and the reason ordering is load-bearing, is that **compatibility now evaluates a fetched manifest** — the manifest does not exist locally until step (a) completes, so a consumer cannot gate on content it has not yet pulled. The gate runs at fetch time, before the content is activated, as COR-041 sets. That holds wherever the fetch runs: at install, in the propagation sync runs at the recorded pin (COR-059 point 2), and in a transition. The fetch is simply the step that *materialises* the manifest the gate then reads.

**In a transition, the fetch comes before the first write, and the landing after it.** A transition makes every check before it writes the project: a transition of the backbone resolves every installed component's compatibility, externally-sourced ones included (COR-010 and COR-041), and every transition runs the dependency gates and the collision flow (ADR-065 point 6). So in every transition, of the backbone or of one capability:

- **A pin the transition moves** is fetched to a place outside the project before the transition writes the project, and every check the transition makes reads that content: compatibility, the dependency gates and the collision flow. A fetch that fails, or that finds no capability of that name, refuses the transition (points 1 and 7). A dry run fetches the same way, runs the checks on what it fetched, names the commit it fetched for each moved pin, and lands nothing. The run fetches again, and where a ref has moved since, it checks, lands and records the commit the ref names then, and its report names that commit. To take exactly the commit a dry run showed, the person names that commit by its full id.
- **The content that fetch took lands** in the transition's propagation, with the capability's skips and its package metadata last (point 3), and is never fetched twice. So the content that lands is the content that was gated.
- **The new pin is recorded once its content has landed,** as a shipped capability's manifest moves only when its migrations finish (COR-059 point 6). No migration of the capability runs, since no record places one (COR-059 point 3).
- **A pin the transition does not move is never fetched,** and nothing of it lands. A check that reads the capability reads its copy, as ADR-065 point 6 reads every capability that does not move. The dependency gates read the ranges each installed capability declares (COR-030), so every transition reads the copy of every such pin. The copy stands for the content an earlier fetch at that pin landed only as far as its declarations show, so the transition reads it only where the manifest records a pin it can read, as point 3 reads one, with a version and a backbone range beside it, and the copy declares that version and that range. Elsewhere the checks would read content the pin does not name, so the transition refuses before it writes the project. The refusal names the ways on: restore the copy or the manifest from version control; move that pin, in a transition of the backbone or of that capability alone; or, where the manifest records no pin it can read, uninstall the capability and install it again. A copy out of line in any other file is sync's to bring in line (point 3).

Where each of these falls among a transition's steps is ADR-065 point 4's.

**An install or a registration is no transition,** so its dependency gates read each externally-sourced copy as it stands, unchecked against its pin. Sync brings the copy in line (point 3).

### 5. The author owns the compatibility claim; the consumer validates it at fetch time

`requires_backbone` on externally-sourced content is an **authored claim**, declared and maintained by the author against the backbone lineage the author tests on; the consumer's gate (point 4) validates it at fetch time. The author repo's own backbone version is irrelevant to consumers — only the declared range is. **The author's release keeps the claim current, and nothing on the consumer's side does.** The release step widens the range when the author releases the capability (#494; [the release README](../../../.pkit/release/README.md)'s "The requires_backbone broaden — two shapes" says how), and a backbone release widens only the components it ships. So a consumer whose backbone the author's last release does not cover is refused at point 4 until a later release covers it.

### 6. Cross-source name collisions surface, never clobber

When two external sources, or an external source and a kit-shipped or incubated capability, claim the same `<name>` at the point-3 landing path, `pkit` **surfaces the collision** for the adopter to resolve rather than silently overwriting one with the other. This extends COR-031's collision rule (an incubated capability whose name collides with a newly kit-shipped one is surfaced, not skipped) to the externally-sourced origin. The single-owner landing (point 3) makes a *clean* fetch conflict-free; this point covers the distinct case of two *claimants* on the same name, which is an adopter decision, not a fetch mechanic.

### 7. Unreachable-source / auth-gap degradation inherits ADR-039 D2

A source that cannot be reached at fetch time — offline, a commit it does not serve, a ref it does not serve where the fetch takes the commit the ref names (an install's fetch, or a transition's of a pin it moves), or an auth gap (the CI case point 2 defers) — **never hard-fails mid-command: sync and install warn loudly and degrade, and a transition refuses before it writes the project.** At a recorded pin the ref chooses no content, so a ref that names another commit than the pin records, or that the source no longer holds, is none of these there: the fetch takes the pin's commit all the same, where the source serves it, and the command reports the move (point 1). This is ADR-039's D2 posture, one altitude down: a degraded-but-running command beats a bricked one, and a fetch failure over one external source must not strand every other operation in the command. How a command meets the failure depends on the fetch:

- **Sync's fetch, at the pin the project records:** `pkit` continues with the copy already on disk, and its warning names the pin it could not take, and why.
- **An install's fetch:** nothing is recorded or landed for that capability, with a loud warning, and the rest of the command proceeds. So no recorded pin names content the project never received.
- **A transition's fetch, of a pin it moves:** the transition refuses before it writes the project (point 4). A pin moves only to content the transition fetched and gated, as upgrade refuses under the router's fallback rather than move the project's version pin to a release it never resolved (ADR-065 point 9). The refusal names the ways on: reach the source and run the transition again, or, in a transition of the backbone where the pin the project holds passes the gate at the target, run it again without moving that pin. To stay, after a tool update that ran before the refusal (ADR-063), an unpinned project pins its recorded release with `pkit pin`, ADR-065 point 8's Stay remedy.
- **A pin the transition does not move** is never fetched (point 4), so a source that cannot be reached stops no transition that leaves its pin where it is.

## Rationale

**Why fetch-at-pin rather than track-a-branch-tip.** The pin-as-source-of-truth model is PRJ-004's registry-free minimalism inherited deliberately (COR-041's rationale). A moving branch tip would make "what does the consumer hold" unanswerable without a network round-trip and would smuggle upgrades in silently; a pin makes the held content a local fact and makes upgrade an explicit, diffable repoint of one recorded value (point 3). This is the same reason ADR-039 pins the whole kit by ref rather than tracking latest. Every ref keeps its convenience without that cost: the operation that records the pin records the commit the ref names (point 1), so neither a pushed branch nor a moved tag moves the held content, and taking a later commit is a transition like any other repoint.

**Why the pin records a commit, and every fetch at the pin takes that commit.** A recorded pin must name the content the project holds (COR-059 point 1). A branch moves with every push, and a tag moves whenever its author moves it: PRJ-004 moves project-kit's own `latest` by design. The whole kit's pin can rest on disciplined tagging (ADR-039 D3), since one release workflow cuts its tags, and an externally-sourced capability's author is bound by no such workflow. A commit's id names one content whatever the source does later, so recording the commit each ref names when the pin is recorded settles every ref form with one rule. Fetching that commit whatever the ref names keeps the pinned content fetchable for as long as the source serves the commit, which is COR-041's reproducible sharing, and lets reconciliation bring the copy to the recorded content whatever the ref has done (COR-059 point 2). The fetch asks for the commit by the ref while the ref names it, so a source that refuses a fetch of a commit by its id still serves every pin whose ref has not moved, and the content landed is the same either way. It asks for the commit by its id only where the ref has moved on or is gone, as it does for a ref given as a commit's id, and where the source refuses that fetch, or has dropped the commit, the fetch degrades as for any commit it does not serve (point 7). Reading the ref beside the fetch costs one lookup, and tells the person that the ref has moved on, or is gone, without anyone reading the source.

**Why a person names each pin a transition moves, and the run takes what the ref names then.** A transition that moved every pin to what its ref names would carry each pushed branch and each moved tag into the project with no one choosing it, the silent upgrade "Why fetch-at-pin rather than track-a-branch-tip" rejects. So the person names the move, and naming it is the consent (COR-059 point 4). A dry run writes nothing ([REQ-009](../../analysis/core/requirements/quality/REQ-009-preview-before-change.md)), so it cannot hand the commit it fetched to the run, and a ref can move between the two. The run takes the commit the ref names at its own fetch, and its report names it, as an upgrade takes the latest release when it runs (ADR-065 point 9). The collision flow asks about the run's own content, in the run (ADR-065 point 6), so no answer to a collision rests on what a dry run saw. `--force` is another matter: it is passed before the run's fetch, and overrides the gates' warnings on the run's own content (ADR-065 point 6), which match those the dry run showed only while the ref has not moved since. So a person who wants exactly what a dry run showed, its warnings included, names that commit.

**Why sync lands a pin's content only at the recorded version and backbone range, and gates it.** A pin moves only by a transition, which gates its content before recording it (point 4). Sync runs no dependency gate and no collision flow, so a pin edited by hand that sync followed to another version would land content those gates never read. Checking the version and the backbone range the content declares against those recorded beside the pin keeps sync where ADR-065 point 1 keeps it for a shipped capability: it copies content only at the version the project records. The range costs nothing to check, since the manifest records it with the version (ADR-065 point 2). The check reads two declarations, not the content, so an edit that keeps both passes it. Sync keeps point 4's backbone gate for what the check lets through: the gate reads the content sync is about to land, whatever an earlier check read.

**Why the ordering is the load-bearing decision.** Every other point is a placement or a posture; point 4 is the one that could be got *wrong* in a way that wedges a consumer. Reading a *stale or absent* local manifest — or reading the *author repo's* backbone rather than the consumer's — would either refuse compatible content or activate incompatible content. Fixing the order (fetch, then read the fetched manifest, then gate against the consumer's backbone) is what makes compatibility resolution correct for content that arrives over the network. COR-041 states the principle that compatibility evaluates a fetched manifest; this ADR pins the *sequence* that realises it.

**Why a transition fetches before it writes, and records a pin after its content lands.** The gate must read the new pin's content before the project is written (COR-010), so the fetch comes first, and landing what that fetch took, rather than fetching again, keeps the gated content and the landed content one. The pin is recorded once its content has landed, in both forms of transition, so a recorded pin always names content the project holds: COR-059 point 1 lets only the backbone's recorded version name a target the project has not reached.

**Why a move cut short is lost rather than kept.** A transition interrupted before it records a pin loses that move. The project keeps its old pin, and the landing writes the package metadata last, so a landing cut short leaves the copy declaring the old pin's version and ranges, which the next transition's checks read. That transition moves the pin only where the person names the move again, or refuses where the old pin does not fit its target, and the next sync brings the copy back to the old pin's commit, where its source serves it (point 1). Recorded with the backbone's target instead, the move would survive the interruption, but the pin would name content the project lacks, and finishing the transition would need every pin fetched: one unreachable source, even of a pin nobody moved, would hold the project at no version. A pin a transition does not move is never fetched for the same reason. Its content is in place, and sync keeps it in line.

**Why one copy out of line holds every transition.** A copy that declares another version or backbone range than its pin is refused rather than read (point 4). The refusal covers every pin a transition does not move, not only those whose ranges name a capability that moves: the dependency gates read the ranges every installed capability declares, and a copy out of line cannot be trusted to say whether it names one. So one copy out of line holds every transition until it is restored. One cut passes those checks: after the last write and before the pin's record, between two contents that declare one version and one backbone range. There the dependency gates read the new content's ranges on other capabilities, the next sync lands the old content where it can take it, and validation reports any range of the copy that does not hold (COR-030).

**Why local auth now and CI auth later.** The grounded consumer (#131) is a developer running sync locally; that path is fully served by the GitHub auth PRJ-004 already assumes, at zero new credential surface. Unattended CI auth is a genuinely harder problem (credential-store shape, deploy keys, token scoping) that PRJ-004 itself deferred one altitude up. Shipping the local path without blocking on the CI design is the same staged move PRJ-004 made; folding CI auth in here would couple a shippable contract to an unsettled one.

**Why surface collisions rather than pick a winner.** A silent clobber at the shared landing path would let one source's content vanish under another's with no signal — the exact failure COR-031 rejected for incubated-vs-kit-shipped names. The adopter is the only party that knows which claimant they meant; the write-path's job is to make the conflict visible, not to guess.

**Why inherit ADR-039's degradation posture, and why a transition refuses.** The failure class is identical (a pin that cannot resolve over the network) and ADR-039 already reasoned it to ground: a hard fail makes the tool *more* fragile than not having the feature, because a transient network gap would break unrelated work. Re-deriving a different posture here would fragment how project-kit handles pin-fetch failure across its two altitudes for no gain. The two altitudes make the same exception too. Under the router's fallback, every command runs on the installed pkit but upgrade, which refuses rather than move the project's version pin to a release it never resolved (ADR-065 point 9). A transition here refuses for the same reason, rather than record a capability's pin over content it never fetched or gated. It refuses before it writes the project, so the project stays as it was.

### Alternatives considered

- **Merge the fetched content into a consumer-owned region.** Rejected at the principle level by COR-041/COR-001 — it is exactly the merge/conflict machinery the methodology structurally refuses. This ADR could not have chosen it; the single-owner landing (point 3) is what keeps match-the-pin conflict-free.
- **Gate compatibility before fetching (read a cached or declared range).** Rejected — there is no local manifest to read until the fetch runs; a cached range goes stale against a repointed pin, and gating on the *author repo's* backbone instead of the *declared* range validates the wrong thing. Fetch-then-read-fetched-manifest (point 4) is the only order that gates on current, correct content.
- **Widen `requires_backbone` for externally-sourced content in the consumer, the way a backbone release widens the components it ships.** Rejected: the consumer would claim a compatibility the author never tested, and the claim is the author's (point 5). The author's own release widens it instead (#494).
- **Block on unattended CI auth before shipping.** Rejected — couples a shippable local path to PRJ-004's already-deferred CI-credential design. Naming CI auth as out-of-scope (point 2) ships the grounded consumer's path now.
- **Hard-fail sync or install on an unreachable source.** Rejected for the same reason ADR-039 D2 rejected it — a transient fetch failure over one source must not brick the whole command.
- **Sync follows a branch pin's tip, read as no version moving.** Rejected: the content a project holds would move with no transition and nothing recorded, which COR-059 point 3 rules out and "Why fetch-at-pin rather than track-a-branch-tip" above rejects.
- **Record only the ref the person named, and trust its author not to move a tag.** Not taken: a tag its author moves, or one that moves by design such as `latest`, would move the content sync lands with no transition, and the whole kit's tagging discipline binds no other author (ADR-039 D3).
- **Take the recorded commit only while the ref names it, and keep the copy otherwise.** Not taken: once the ref moves, sync can neither check nor repair the copy until a transition moves the pin, which for a branch begins with its next push. A move along one ref cut short, before the pin's record, would leave a copy sync never brings back, and no fetch could take the content the pin names again. What the rule would catch beyond point 1 is a hand edit of the commit that the ref does not name, an edit outside every operation (point 3), and an edit of both the ref and the commit passes it too. That is a cost point 1 takes: an edit of the commit alone can pass review in a pull request whose diff leaves the source and the ref as they were, and a host may serve by its id a commit the source's own refs never reached. Under point 1 that commit lands, where it declares the version and the backbone range recorded beside the pin (point 3), and the report that the ref names another commit is the only sign of the edit.
- **Read a pin that records no commit as following its ref.** Rejected: its content would move with the ref, with no transition, the branch-tracking rejected above, held only by point 3's check of two declarations. Sync reads no such pin (point 3).
- **Refuse a branch as a ref, or take one only as an input, resolved once into a pin whose ref is its commit.** Not taken: resolving it to its commit costs one lookup and records a pin that names one content all the same, and since every fetch at the pin takes that commit (point 1), the branch moving, or its deletion once it has landed, costs the project nothing while the source serves the commit. Kept as the ref, it lets a person take the branch's head again by naming that ref, and tells them when it has moved on.
- **Sync follows the recorded pin whatever version its content declares.** Rejected: a pin edited by hand would land content no gate read (point 3).
- **Record the id of the capability's subtree, or of its package metadata, beside the pin, and have every check compare it.** Not taken: the version and the backbone range recorded beside the pin already catch an edit, or a cut, that changes either. What passes them is an edit at one version and one backbone range, which a person makes by hand outside every operation, as an edit of any recorded version is, or the one cut the Rationale names, whose desync, if any, validation reports (COR-030), and which the next sync brings back to the pin's commit (point 1). The id would be recorded for those alone.
- **Drop sync's backbone gate, since a transition gated the pin's content when it recorded it.** Rejected: an edit the version check lets through, or a copy that misled a transition's checks, would land content no gate read against the backbone sync runs at (point 3).
- **Read a pin the transition does not move from what its manifest records, not from its copy.** Not taken: the manifest records the version and the backbone range, not the ranges on other capabilities, so the dependency gates would still read the copy. The copy is read only where it declares the version and the backbone range recorded beside the pin (point 4).
- **Refuse a move to an older version, as a transition refuses one for a component its bundle ships.** Not taken: a shipped component moves only forward because its migrations run only forward (ADR-065, "Why a transition refuses a component its bundle ships older"). No migration of an externally-sourced capability runs, so a move down strands nothing, and the gates read the content it lands. The capability's `project/` tier crosses a move in either direction as it is, since no migration converts it, so data a newer version wrote there meets the older content unconverted.
- **A transition that degrades on an unreachable source, recording the new pin over the copy it holds.** Rejected: the recorded pin would name content the project does not hold, which the gate never read (point 4).
- **Record a moved pin with the backbone's target, before its content lands.** Rejected: the pin would name content the project lacks, which COR-059 point 1 allows the backbone's recorded version alone, and finishing the transition would need every pin fetched, so one unreachable source would hold the project at no version.
- **A completion, or a mark of a landing under way, recorded beside each pin.** Not taken: no pin is recorded before its content lands (point 4). A landing cut short leaves the old pin's declarations in the copy, and one that finished before the pin's record is refused where its version or backbone range differs from those recorded. The next sync brings either back to the pin's commit (point 1). A transition of the backbone cut before the pin's record leaves its completion unrecorded, so sync's guard stops sync until the transition runs again (ADR-065 point 7). That run reads a copy cut short as it reads any, and refuses one that landed at another version or backbone range, whose ways on settle it instead (point 4): restore the copy from version control, or name the move again. So the mark would add state for the one cut the Rationale names.

## Implications

- **`pkit`'s fetch/sync path gains the externally-sourced fetch step:** fetch-at-pin and the pin it records (points 1 and 3), the landing under single ownership outside the capability's `project/` tier (point 3), the point-4 ordering wherever the content is fetched, a transition's move of a pin (points 4 and 8), and the failure posture (point 7). No code is pinned here; this is the design contract the implementation builds against.
- **Where the code differs** from this record in the fetch and in sync, #3349 brings it in line:
  - The fetch at a recorded pin takes what the ref names, and fails where that is another commit than the pin records, or where the source no longer holds the ref. Point 1 takes the pin's commit, by its id where the ref names another or is gone, and reports the move.
  - Sync's match of a pin keeps the copy and warns on either failure, where point 1 lands the pin's commit.
  - Sync's match reads a pin that records no commit, and the fetch takes what its ref names then. Point 3 reads no such pin.
  - Sync's match compares the version the fetched content declares with the one the project records, and checks only that the content's backbone range admits the recorded backbone. Point 3 also keeps the copy where that range is another than the one recorded beside the pin.
  - Sync's read of the recorded version falls back to the copy's package metadata where the manifest records no version. Point 3 fails the check on such a manifest, whatever the copy or the content declares.
- **Where the code differs** from this record otherwise, #3229 brings it in line:
  - The fetch refuses a branch as the ref, which point 1 takes.
  - No transition fetches, lands and records a pin it moves, or refuses where that fetch fails (points 4 and 7). #3229's record places the commands that take a move (point 8).
  - No transition refuses a copy out of line: each reads an externally-sourced capability's ranges from its copy as it stands (point 4).
- **Until #3349 lands, an install from another repository refuses** (#3359), so the default branch keeps releasing as [PRJ-016](../../../.pkit/decisions/project/PRJ-016-candidates-hold-no-release.md) decides, and #3349 removes the refusal. What merges into the default branch ships with its next release (PRJ-016 point 2), so the hold is on the install, not on a release: no release lets a project install a capability from another repository before the fetch takes the pin's recorded commit.
- **Until the commands that move a pin are built** (#3229), the way to take the commit a ref has moved on to is to uninstall the capability, then install it from the source and the ref, and point 1's report of a move names that way until then. It moves no recorded pin, since the uninstall leaves none (point 8). Its costs: the skips the capability's manifest records go with the manifest, and a capability that depends on this one can hold the uninstall.
- **The compatibility gate reads a fetched manifest** (point 4). This is the concrete realisation of the forward-pointer COR-041 added to COR-010 — compatibility resolution now evaluates content that arrives over the network, not only content already on disk.
- **`requires_backbone` on externally-sourced content is an authored claim** (point 5). The author's capability release keeps it current, by **#494**'s widening, and nothing on the consumer's side widens it.
- **Unattended CI authentication is a deferred PRJ successor** (point 2), consistent with PRJ-004's own deferral of cross-repo CI auth. This ADR ships the interactive/local path only.
- **Name-collision surfacing extends COR-031's rule to this origin** (point 6); the lifecycle surfaces a same-named external/kit/incubated clash rather than skipping or clobbering.
- **Each part the implementation builds cites this record,** among them the fetch step, the pin record, the point-4 gate, the collision surfacing and the point-7 degradation.
- **Stands on:**
  - COR-041: the origin semantics this realises, the *what* to this ADR's *how*
  - COR-010: the `requires_backbone` gate point 4 runs, and the compatibility a transition resolves before it writes the project
  - COR-059: the recorded pin, out of propagation's reach; the transition that moves it, and the consent naming its target gives (point 8); the reconciliation that brings the copy to it
  - ADR-065: the transition's steps, which place the fetch, the landing and the pin's record; its dependency gates and their `--force`; the hand-over through the bypass a named move rides; and the refusal under the router's fallback that point 7 follows
  - COR-001: the single owner, with no merge, and the consumer's `project/` tier, which point 3 rests on
  - COR-030: the dependency gates, which read the ranges every installed capability declares, and the validation that reports a desync
  - PRJ-004, one altitude down: the git-URL channel and its commit form, which point 1 inherits; the use of its branch form, which point 8 keeps; and the GitHub auth, which point 2 inherits
  - PRJ-016: what merges into the default branch ships with its next release, so the hold until #3349 lands is on the install, not on a release
  - ADR-039 D2: the degrade-loud posture point 7 inherits
- **This ADR pins the write-path contract, not COR-041's principle** — it must not accrete or restate the origin semantics. On-call reference: if a consumer holds content that does not match its recorded pin, or is refused against a backbone the author's declared range should cover, point 1, 3, 4, 5 or 7 is where to look first.
