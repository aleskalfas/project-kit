## Summary

**In plain terms:** a command that prints a document for a program to read, as `--json` does, makes a contract with each caller that reads it: the document's own keys, what each means, and the values a key may take where the document lists them, never its prose. A key or a value added misleads no caller, which ignores a key it does not read and never takes a value it does not know for one it knows. A key or a value that goes breaks callers, so it goes only as a declared breaking change of its component. A key or a value means one thing for good: a new meaning takes a new key, never an old one, in place or after it went.

The rule binds every command project-kit ships. Before it, each contract that stated part of the rule left out something another stated: one accepted record read a value it did not know as one it knew, and two let a key change its meaning in place. This record refines all three. Whether every component of every project owes the rule is raised for a core record.

**Why an ADR.** The documents commands print are how project-kit's components reach each other ([ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 1). An interface between components is what the project built, which is an architecture record's question ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Distinct from PRJ"). Only part of the rule binds code. The rest binds the records and references that decide each document, the changesets that ship a break and the review of a change. They are how the contract reaches a caller that cannot see the code, and how it is held where no test looks, so they stay with the interface they carry ("Why the change discipline stays with the interface"). The rule spans the backbone and several capabilities, so it is no one capability's record.

## Context

**The callers.** A capability's script never imports the backbone. It reaches the backbone's engines through their machine-readable reading commands (ADR-057 point 1). Agents, a project's pipeline and a person's own tooling read the same documents, and capabilities' commands print documents of their own, such as project-management's pre-check report. Each caller keys on the document: it finds what it needs by a key and decides on the value there.

**Each contract stated its own rule.**
- **The process status document** ([ADR-024](ADR-024-cli-prose-wrapping.md) point 4) is the surface a script keys on, never the human narrative. No presentation choice reaches it: it is byte-identical on a terminal of any width and in a pipe.
- **The hosting-service command's documents** ([ADR-061](ADR-061-hosting-service-acts-in-the-backbone.md) point 7), which project-management's landing reads. ADR-061 said that a caller decides on their fields, never on an exit code, that a field added keeps the version, and that a field removed or redefined raises it, as a breaking change that ships a migration.
- **The landing check's document** ([ADR-081](ADR-081-landing-check.md) point 8). ADR-081 gave it a version of its own, raised when a key a reader relies on changes its meaning or goes, never for a key added.
- **The configuration recorder's document** ([ADR-084](ADR-084-capability-config-contract.md) point 2) is what a capability's script decides on, and carries a schema version. The recorder was decided and not yet built, so its document is first printed under this record.
- **A data point's document,** as project-management reads it ([project-management:DEC-054-use-case-validation] point 3). DEC-054 said that a caller decides on its `outcome` and its fillers' `state`, never on the sentence in `why`, and that an outcome or a version it does not know reads as could not check. It read a filler's state as `inert` or not, so a state it did not know read as one that answered. The manifest reference gave every consumer the same advice: check that no filler's state is `inert`.
- **Pre-check's report,** in the record that issue #3193 drafts, which is proposed and binds nothing. The draft said that each check has a key that stays whatever its outcome or its wording, that a key added breaks no caller, that a key that goes or comes to name another check, and a changed outcome value, break one, and that a key is never reused.
- **The CLI reference** stated the version rule of the friction checks' reading documents, of the landing check's document and of a data point's document, in ADR-081's words. A value added to a listed set raised no version where the reference named how a reader reads one it does not know, as it did for an outcome, a finding kind and an artefact state. It named none for others, such as a filler's state, the cross-repository guard's verdicts and the default branch's sources. It called some sets closed, such as a data point's outcomes, though they may grow. It named how a reader reads a few keys a document lacks, such as `schema_version`, and no other.

**Where they differed.** They agreed on what they shared, and differed in what each left out. Only #3193's draft said that a key is never reused, yet it, ADR-061, ADR-081 and the CLI reference each let a key change its meaning in place. Only DEC-054 and the CLI reference said how a caller reads a value it does not know, and the CLI reference said it for some sets and not others. None said how a caller reads any other key it does not find. None said which keys are in the contract: one no caller is known to read, one that is data, or one whose reading an added key changes. The author of a new document found the rule only by reading whichever of these they happened to know. The architect's review of #3193's draft found the recurrence ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)), and issue #3250 asked for one rule.

## Decision

**A command's machine-readable output is a contract with each caller that reads it: its own keys, what each means, and the values of its sets, never its prose. A key or a value added misleads no caller. One that goes breaks callers, and is a breaking change of its component. A key or a value means one thing for good.**

### 1. What the rule covers

- **A command's document.** The rule covers each document a command prints for a program to read, on the command's request for machine-readable output. It covers every command project-kit ships: the backbone's, each capability's and each adapter's. This record calls that output the command's *document*. A document may have several *forms*, such as the one a run with no answer prints, or one an option selects.
- **Its callers** are whatever reads it: another component's script, an agent, a project's pipeline or a person's own tooling. Point 3 binds each caller project-kit ships, as it reads a document this rule covers, and not as it reads another program's output. A caller outside project-kit learns the contract where the command is documented (point 6).
- **Not covered:**
  - What a command prints for a backbone engine that runs it under the runner's policies (ADR-057 point 5). Its shape, and how the engine reads it, are set by the record that sets the engine's contract with the command, such as [COR-052](../../../.pkit/decisions/core/COR-052-slots.md) point 5 for a data point's value.
  - A document whose shape a protocol outside project-kit sets, such as the decision a harness's permission hook returns. The protocol is its contract.
  - A verdict an agent writes for a program to read, whose form its own record sets ([project-management:DEC-028-agent-as-approver-paths]). An agent is no command.
  - A command's exit codes, which each command's record sets, and a file a command writes, whose format is decided apart.

### 2. The contract is the document's own keys, never its prose

- **Its own keys.** A key is the document's own when the document's own shape fixes its name, whether or not every run prints it. Each own key a final release prints is in the contract, documented or not, with its meaning. A key's meaning includes the type of its value, and when that value is null.
- **Where a key is present is not its meaning.** A key that leaves a form it was in goes, and one that comes into a form is added (point 4).
- **A key that is data is a value.** A key drawn from a registry or a collection is data, whoever supplies the entry. Such keys include paths, ids, and the names of capabilities, types, validators and rules. In a mapping keyed so, the keys are values. They come and go with what they name, and whether one may go is its own contract's, such as its registry's. The mapping's own key, and the fields of each entry, are own keys.
- **A payload keeps its owner's contract.** A document may carry a value whose shape another owner sets, such as a data point's value under its definer's schema (COR-052 point 5), or an artefact's front matter. The contract holds the key that carries the payload, and that the payload is carried as its owner gave it. The keys inside it are its owner's.
- **Every set of values.** Where the contract lists the values a key may take, such as an outcome or a state, those values are the key's *set*, and each value's meaning is in the contract. Every set may gain a value (point 4).
- **The version,** where the document carries one of its own.
- **Order and framing, where stated.** A list's order is in the contract where the reference states one, or where another key indexes the list. The order of a mapping's keys, and how the document is framed on its stream, such as one line of JSON or several documents one per line, are in it where the reference states them. A caller still finds a key by its name, never by its place.
- **Not prose.** A value written for people, such as a reason, a label or a message, is in the contract by its key and its purpose, never by its words, which may change in any release. The human view is not in it either.
- **Not where it is printed.** What a document holds is the same on a terminal of any width, with colour or without, and in a pipe, as ADR-024 point 4 pins for the process status document.
- **From a final release.** A key or a value enters the contract when a final release first prints it. A release candidate previews what a release would ship ([PRJ-016](../../../.pkit/decisions/project/PRJ-016-candidates-hold-no-release.md) point 3), so a key that a later candidate or the final release drops or changes breaks nothing.

### 3. A caller reads by key, and never takes what it does not know for what it knows

- **By key.** A caller finds what it needs by its key. It decides on keys and on the values of their sets, never on a sentence for people, the place of a key or the human view. It may show a sentence to people.
- **A key it does not read,** it ignores.
- **A key it needs and does not find,** it reads as the contract says for that key. Where the contract says nothing, it reads it as *could not tell*, never as a default such as zero, false or empty.
- **A null that the key's contract does not explain,** it reads as could not tell, as it reads a value it does not know. A contract that says so from the start lets the key be null in a new case (point 4).
- **A value it does not know** it reads as the contract says for that set. Where the contract says nothing, it reads the value as could not tell: it learns nothing from it, and what rests on it stops or says that it could not tell. It never reads the value as one it knows.
- **A reading the contract names falls safe.** It claims no answer the document might not give. Such a reading fits a key added after a document first shipped, whose absence says only that a release before the key printed the document. So the CLI reference reads a document that lacks `schema_version`, where its command gained the key later, as version `1`.
- **A version it does not know** it refuses. It reads nothing from the document, and says which version it found.
- **A run that gives no document** tells it nothing, and it never reads that as an answer.

### 4. What is a breaking change, and what is not

- **Added: no breaking change.** A key added, to the document or to a form it was not in, a new form, and a value added to a set mislead no caller that reads as point 3 says. None raises a version.
  - **Only where the rest stands.** An addition that changes how an existing key reads changes that key's meaning, which point 5 rules out. A key that qualifies another, such as one that says a list is partial, is such an addition.
  - **A null in a new case** is an addition only where the key's contract reads a null it does not explain as could not tell (point 3). Elsewhere it changes the key's meaning, which point 5 rules out.
  - **A set that named no reading.** Some sets named no reading for a value a caller does not know before the CLI reference stated this rule. Each such set is marked where its command is documented (point 6), until it gains its first value. Such a set gains its first new value only in a release in which each caller project-kit ships reads such a value as point 3 says. The changeset that adds the value names the set in its note, and says that a caller that read the set as complete may misread the value. The change that adds it removes the set's mark.
- **Gone: a breaking change.** A key that goes, from the document or from a form it was in, and a value of a set that goes, each break a caller that relied on it.
  - **Declared.** It is a breaking change of the component that ships the command, and its changeset says so, at the `major` segment ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md) D2).
  - **The version rises** in the same change, where the document carries one of its own, and for no other change. It stops the callers point 3 does not reach ("Why the version still rises").
  - **No migration,** since a document is no installed state. Where a project's installed state names what goes, COR-010's test decides, as for any change ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md), "Migrations are mandatory on adopter-breaking surface changes").
- **A fix changes no meaning.** A change that makes a key give what its contract states, where it gave something else, is a fix. Only a key whose meaning the contract states can have one: an undocumented key means what it gives.

### 5. A key or a value means one thing for good

- **Never in place.** A key's meaning never changes, and neither does a value's in its set. A new meaning takes a new key, or a new value. The old one may stay beside it for as long as its callers need, and its going is then a break (point 4).
- **Never by return.** A key that went never comes back to name anything else in that document, at any version. A value that went never comes back to mean anything else in its set. Either may come back with the meaning it had.
- **Order and framing.** A stated order or framing never changes. A different one comes as a new form, which an option selects.
- **From this record on.** A meaning changed before this record was accepted stands under the version that marked it, such as what the friction checks' `since` document counts at its version `2` ("Why a meaning changed before this record stands").

### 6. Where each contract is stated

- **Where its command is documented:** the CLI reference for a backbone command, and the README of the capability or adapter for its own. For each document printed for a program, it names each own key with its meaning, each set with its values, the order and framing a caller may rely on, and the document's version where it has one. It names any reading other than could not tell of a key missing or a value a caller does not know, and each key whose unexplained null reads as could not tell.
- **The rule itself** is stated in the CLI reference, for every command project-kit ships, a capability's and an adapter's included. The CLI reference reaches every project that installs the methodology, and this record does not (COR-025, "Propagation isolation"). It also asks a component authored elsewhere, until the core decision (point 8), to read a backbone document as point 3 says.
- **In a record:** a record that decides a document decides what the document holds. For how the document stays stable, it cites this record and the CLI reference's statement, rather than state a rule of its own.

### 7. What checks it

- **A test for each document** pins, from the output the command prints, its own keys, the values of its sets, and each key and value that went. A change that removes one, or brings one back, fails the test until the same change updates it, beside the changeset that declares the break.
- **A test for each caller** project-kit ships gives it a document with a key it does not know, a value it does not know, a version it does not know, a key it needs left out, and no document at all. Each must read as point 3 says.
- **A caller that is a skill or an agent** has no such test. The reviewer of a change to it judges that it reads as point 3 says.
- **A meaning is review's.** No test sees that a key came to mean something else, so the reviewer of the change judges it.
- **Until the tests exist,** review alone checks. Building them is a follow-up (Implications).

### 8. The rule for components authored elsewhere is raised for a core record

- **What is universal here.** COR-025's first test, of scope, gives a core record each rule that any project adopting the methodology needs. A component authored elsewhere that reads a backbone document needs point 3, and one whose document other components read needs points 2, 4 and 5. So a core record decides such rules.
- **Adopted for what project-kit ships.** This record binds the components project-kit ships, and raises the rest for a core decision, as ADR-084 point 8 did with its recorder's rules.
- **The carrier until then** is the CLI reference's statement of the rule (point 6).
- **When to revisit:**
  - when that core decision is made;
  - when point 7's tests exist for every document project-kit ships, since the rule has then been checked on project-kit's own components;
  - or sooner, when a component project-kit ships first reads a document that a component authored elsewhere prints. That caller's safety then rests on a rule this record cannot bind.
- **Where it shows.** Nothing detects these. The second shows in the change that builds the last of point 7's tests. The third shows in a change that has a shipped component read such a document, and that change's reviewer checks for it. Components reach each other mostly through the backbone's reading commands (ADR-057 point 1), so the third may be rare.

## Rationale

**Why the document's own keys, documented or not.** A caller reads what it sees in the document, not only what the reference names. The author cannot see which keys a caller outside the repository reads, so a key the author judged unused may be one a pipeline decides on. Counting only the documented keys would break such callers without a word. Counting every own key costs the author a declared break for each key removed: for a backbone document, a backbone `major`. A key is the document's own by its shape, not by whether a run prints it, so a key printed only in some forms is still its own.

**Why a key that is data, and a payload, stay out.** A path or an id that keys a mapping comes and goes with the project's content. Held to the contract, deleting a file would break a caller, and a deleted path could never return. A key drawn from a registry, such as a type's name, is the registry's entry, and the registry's own contract says whether it may go ([COR-056](../../../.pkit/decisions/core/COR-056-artefact-types.md)). A payload's keys are set by its owner, such as a data point's definer, whose own contract governs them (COR-052 point 5). The command only carries them.

**Why prose stays out.** A sentence is written for its readers and reworded for them, in any release, by an edit nobody counts as a change of contract. A caller that matched it would break on such an edit. So each fact a caller needs has a key and a value of its own, as `outcome` sits beside `why` in a data point's document.

**Why an addition misleads no caller.** Commands grow. If each key added broke a caller, every caller would have to move with every release of the component it reads, and a capability that runs on a range of backbones could read none of them for long. A caller that ignores the keys it does not read, and never reads a value it does not know as one it knows, lets the document grow under it.
- **What it costs.** An addition may still stop a caller: a pipeline that meets a value it does not know says it could not tell, and goes red. The cost falls safe, as a check that gives no answer never passes (ADR-081 point 6).
- **Why only where the rest stands.** A caller that predates a key reads no key that qualifies another. It reads the other key as it always did, so a list marked partial has it take part of an answer for the whole. A value null in a new case misleads it the same way: it reads the new null as the null it knows. So a qualifying key changes the other key's meaning, and so does a new case of null.
- **Why where a key is present is not its meaning.** A key that leaves a form a caller reads is missing there, and the caller reads could not tell (point 3). So its going is a declared break, never a silent misread. A key that comes into a form, or a new form, is one more key a caller may ignore. Counting presence as meaning would forbid both, though neither misleads a caller. It would forbid a form a new option selects, and a new form for no answer that prints only the version and the problem.
- **Why a contract may read an unexplained null as could not tell.** Elsewhere, each new case in which a key's value may be null takes a new key, beside the one that keeps its meaning. A key whose contract says from the start that a null it does not explain reads as could not tell spares that cost, since its callers already read such a null safely.

**Why a missing key reads as its contract says.** Some keys came into a document after it first shipped, and their absence says something exact. Where a command's document gained `schema_version` after it first shipped, one without the key was printed by a release before it, and the CLI reference reads it as version `1`. Reading every missing key as could not tell would stop each caller of such a document, though none would misread it. A reading the contract names must fall safe, so it never takes a missing key for a default that passes. Where the contract names none, the caller cannot tell why the key is missing, so it reads could not tell. The CLI reference warns of the default: a caller that reads the process health report's interpretation form, which leaves `totals.missed` out, as a count of zero calls a red run clean.

**Why a value a caller does not know is never read as one it knows.** A value added may mean anything its author needed. Read as a known value, it is a guess that fails silently. An outcome read as resolved draws findings from a set that may be partial, and a state read as taken takes a filler's silence for an answer.

**Why every set may grow.** A set that may never grow makes each new value a break for every caller, though each can read it safely as could not tell. The cost of a set that grows falls on callers that read it as complete. Within project-kit, project-management's reading of a filler's state is one, and is refined below.
- **Why the first new value waits on project-kit's callers.** A value that comes before a caller's fix ships is read by that caller as one it knows. Ordered after every such fix, no caller project-kit ships misreads it.
- **Why a note, rather than a wait or a `major`.** A caller outside project-kit that read such a set as complete learns otherwise only from what it is told. A wait of one release tells no one. A project may upgrade across two releases at once, and a release may follow another at once (PRJ-016). A `major` for the changeset that states the rule reaches each capability authored elsewhere, whose range on the backbone excludes it (PRJ-002 D4). It reaches no agent, pipeline or person's tooling, and costs each such capability a release for sets that may never grow. A note in the changeset that adds the first value reaches whoever reads that release's notes, when the value comes, and costs nothing until then.
- **Why a mark.** Once the rule is stated, a set that named no reading reads where it is documented like any other. Without a mark, the author who adds its first value could not tell that the value owes a note, and a caller's author could not tell which sets it may have read as complete. The mark keeps such a set apart until the note is written.
- **What it costs.** A caller outside project-kit that read such a set as complete reads the first new value as one it knows, unless its author reads the note. Within project-kit, project-management at a version before its fix reads a filler state the backbone added as an answer. Such a pairing arises only for a component a project pins apart ([COR-059](../../../.pkit/decisions/core/COR-059-version-transition.md) point 7). It draws findings from a set that may be partial, and these are warnings only, since the point's inert policy is `fallback` (DEC-054 point 1).

**Why a key that goes is declared.** The changeset tells the people who upgrade the component that a caller may break. The document's version tells a caller at run time, where the document has one. Neither reaches every caller. Each release widens each shipped capability's range on the backbone to cover the backbone it ships (PRJ-002 D4), and agents, pipelines and a person's own tooling pin nothing. So the safety at run time rests on point 3: a caller that needs a key that went finds it missing, and reads could not tell.

**Why the version still rises.** A caller that reads as point 3 says needs no version to meet a key that went. The version is for the callers that do not. One outside project-kit is not bound by this record until the core decision (point 8). One written before this record may read a missing key as a default, as project-management's reading of a data point's document takes a missing `fillers` for an empty list until its follow-up (Implications). Only a version such a caller refuses stops it. The cost is that every caller of the document refuses it, one that never read the key that went included. A break is rare and declared, so the raise stays, and the core decision weighs it again.

**Why no migration.** COR-010 asks a migration of a change that breaks against a project's installed state, and a document is printed fresh by each run, so nothing installed holds it. Nor is a key part of a command's signature, whose breaking change COR-010 counts among its triggers. Its examples, a flag whose meaning inverts and a subcommand renamed, change how a command is called, and a call can be written into installed state, which the change then breaks. A key is what a run gives back, so a key that goes breaks a caller as it reads, which the changeset declares. Where installed state does name a key, COR-010's test decides (point 4). ADR-061 point 7 counted a field removed as a breaking command-line change, and so asked a migration of every such break, citing COR-010. Its edit corrects that fact (Implications).

**Why a key means one thing for good.** A key whose meaning changed reads, to a caller written before the change, as the meaning it knew. Nothing in the document tells it otherwise, unless the document carries a version the caller checks, and many carry none. A key that goes instead, beside a new key for the new meaning, is met as missing, which point 3 reads as could not tell. The old key may stay while its callers move, so no caller breaks at once. A key brought back with another meaning harms the same caller in the same way, and would pass as an addition besides.
- **Precedent.** A connection point's role is redefined only under a new name ([COR-053](../../../.pkit/decisions/core/COR-053-connection-points.md) point 5), and a rule's retired id is never reused ([COR-051](../../../.pkit/decisions/core/COR-051-rule-sets.md) point 3). Project-side, the over-broad anchor finding gave a second ground a finding kind of its own, so `bar` kept its meaning ([ADR-080](ADR-080-over-broad-anchor-flags.md)).
- **Why not as a record's point.** A record's point, and a rule's statement, may be amended under their ids ([COR-058](../../../.pkit/decisions/core/COR-058-record-points.md) point 3, COR-051 point 2), since the friction checks flag each artefact anchored on them ([COR-050](../../../.pkit/decisions/core/COR-050-anchors-and-friction.md)). A document's caller has no such check.

**Why a meaning changed before this record stands.** The `since` document's count changed under a version raised for it, which a caller that checks the version refuses until it knows it. [ADR-067](ADR-067-answers-only-short-check.md) point 4 foresaw that change, for when answers moved into files of their own, and [ADR-068](ADR-068-friction-answer-folder.md) moved them. No caller that checks the version misread it, and undoing it would break those that read version `2`.

**Why a fix changes no meaning.** A fix makes a key give what its contract states, which a caller written to the contract already expects. It is measured against the reference, where the rest of the rule counts what a caller sees. So a caller that relied on the wrong value is misread by the fix silently, and that is its cost. Without it no defect could be mended in place, and each would take a new key. The fix's changeset says what it fixes, so a caller's author can look.

**Why an ADR, not a convention entry.** How code prints a document, and how it reads one, are coding conventions, and the corpus may point to a convention a record holds ([PRJ-013](../../../.pkit/decisions/project/PRJ-013-coding-conventions.md) point 4). The rest of the rule binds what no code holds: the records and references that decide a document before any code prints it, and the changesets that ship a break. The corpus holds coding conventions only, so it cannot hold that part. A convention that later work builds on starts with its record anyway ([COR-065](../../../.pkit/decisions/core/COR-065-records-and-projection.md) point 3). So this record holds the rule, and the corpus points to it for the code.

**Why the change discipline stays with the interface.** COR-025 prefers a decision's workflow side in a PRJ record and its architectural side in an ADR, where both apply. This record's workflow side is three things: where each contract is stated (point 6), what a changeset says when a key or a value goes or a set that named no reading grows (point 4), and what review judges (point 7). Each is how the interface reaches a caller or is held to its terms. A caller that cannot see the code learns the contract only where it is stated, and learns of a break only from the changeset and the document's version. A change of meaning, which no test sees, is caught only by review. A PRJ record holding these would decide nothing that reads without this record, and a change to what counts as a break would amend both. How a project works stays where it is decided: PRJ-002 sets how a changeset declares a break and at which segment, and PRJ-016 what a candidate ships. This record names only what each owes the interface, and cites them.

**Why raised for a core record, rather than decided there now or left open.** Points 2 to 5 bind any component's author, so COR-025's first test, of scope, gives them to a core record. A core record now would bind every adopter's components on a rule project-kit has not yet checked on its own, since the tests of point 7 are not built. Leaving the question open would leave the rule's reach unstated: an author elsewhere reads the rule in the CLI reference, cannot tell whether it binds their own component, and finds nothing that says when that is decided. Raising it, as ADR-084 point 8 did, binds what project-kit ships, carries the rule to everyone through the CLI reference, and names when to revisit.

### Alternatives considered

- **A convention entry in the corpus, with no record.** Rejected: a convention starts with its record (COR-065 point 3), and the corpus holds coding conventions only, where most of the rule binds records, references and changesets.
- **A PRJ record, its rule stated in the corpus.** Rejected: an interface between components is architecture (COR-025, "Distinct from PRJ"), and the authors of the records that decide each document do not read the corpus.
- **This record for the interface, and a PRJ record for its change discipline,** as COR-025 prefers where both apply. Not taken: each part of the discipline is how the interface reaches its callers or is held to its terms, so the PRJ record would read only beside this one, and each change to one would amend the other ("Why the change discipline stays with the interface").
- **This record, with its rule in a rule set scoped over the CLI reference, the READMEs and the code that prints documents.** Not taken: the rule-set reviewer would be drawn onto each change to the CLI reference, which most backbone changes touch, and onto each change to that code, the cost PRJ-013 weighed against a rule set for conventions. Most of what it would judge, a key or a value that went, point 7's test checks mechanically. A meaning, which no test sees, is judged by the change's reviewer either way.
- **Each contract keeps its own rule.** Rejected: the statements differed on reuse, on a key missing and on a value a caller does not know, and the author of a new document found none of them by looking.
- **A version raised for every change, additions included.** Rejected: each caller would refuse each release for a key it never reads. The landing check's record and the CLI reference already rule it out.
- **Any change of meaning, in place or by return, as a declared break.** Rejected. It is one rule, and it keeps precedent. ADR-061 point 7, ADR-081 point 8, the CLI reference and #3193's draft allowed a change in place as a break. The friction checks' `since` document took one, at its version `2`. Its cost is each caller that reads no version: it reads the new meaning as the old, silently, and many documents carry no version.
- **A meaning changed in place as a declared break, while a key that went never comes back with another.** Rejected: a change in place and a return harm the same caller in the same way, so allowing one and ruling out the other rests on precedent alone.
- **Where a key is present, as part of its meaning.** Rejected: a key that leaves a form is met as missing, and one that comes into a form is ignored, so neither misleads a caller. It would forbid a new form of any kind.
- **A missing key read as could not tell, whatever its contract says.** Not taken: it gains one reading for every key. It would stop each caller of a document that predates a key added since, such as `schema_version`, where the contract can say exactly what the absence means.
- **Each new case of null as a new key, with no contract reading an unexplained null as could not tell.** Not taken: it costs a new key for each new case, where a key whose contract says so from the start lets its callers read such a null safely.
- **A set marked closed, so that a value added to it is a break, as the filler states could stay.** Not taken. It would spare DEC-054's refinement and the manifest reference's edit. Its cost is a `major` for each value such a set ever gains, or a new key for each under point 5.
- **A set that named no reading waits one release after the rule before its first new value.** Rejected: a wait tells no one, since a project may upgrade across both releases at once.
- **The changeset that states the rule declared `major`, for every set the rule opens.** Not taken: one `major` reaches each capability authored elsewhere through its range on the backbone, but no other caller. It costs each such capability a release for sets that may never grow.
- **The first value added to a set that named no reading, declared as a break.** Not taken: it costs a `major` of the set's component for each such set, and reaches no more callers than the `major` above.
- **No version raised for a key that goes.** Not taken: a caller that never read the key would keep reading the document, but a caller outside project-kit, or one written before this record, may read the missing key as a default.
- **A version on every document, as part of the rule.** Not taken: a caller that reads as point 3 says meets every break with no version. A version stops only a caller that does not, and where a document carries one, point 4 raises it. Whether a document needs one is left to the record that decides it.
- **A version on each document first printed after this record.** Not taken, for the same reason. It would also split the documents into two kinds by their age.
- **A schema for each document, with the keys that went, tested against its output.** Not taken as the rule's form: point 7's test pins the same keys at less cost. A document's record may give it a schema, which can serve as that test, and gives a caller outside project-kit an artefact to check against.
- **A marked place for keys outside the contract,** such as keys for debugging. Not taken: no document needs one yet, and a caller that can see a key may read it whatever its mark. The first document that needs one brings it, through a change to this record.
- **Exit codes under the same rule.** Not taken: a command's record sets its exit codes, and several make them the whole contract of a gate ([project-management:DEC-017-prerequisites-bootstrap-migrate-discipline]). Issue #3250 asks about machine-readable output. How exit codes stay stable is a question of its own.
- **A core record now, or the core question left open.** Not taken, as "Why raised for a core record" says.
