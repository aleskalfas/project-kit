## Summary

**In plain terms:** the methodology's source repository is the repository whose `.pkit/` is the methodology's own tree — authored there and bundled into the distribution from there, so no sync ever copies into it. Two tests recognise it, one on each side of the tool/tree boundary: the tool's, sync's test, asks whether the target is the parent of the source tree the running code resolves, and the tree's, a marker test for code that cannot ask that, looks for the package source beside the methodology's tree at the repository's root. The router's first route keeps the two answers equal, because wherever the markers are present it runs that repository's own code through its in-tree dispatcher.

## Context

Six places ask whether a repository is the methodology's own source. Sync's self-host path, upgrade's self-host branch and init's refusal to install into the source compare the target root with the folder the source tree is found in: the running package's own checkout first, the bundled tree otherwise ([ADR-033](ADR-033-official-install-bundles-content.md)). The router's first route ([ADR-039](ADR-039-pkit-entry-point-router.md)), upgrade's refusal to replace the tool inside a checkout ([ADR-061](ADR-061-upgrade-updates-the-tool.md) point 4) and the ownership predicate `is_methodology_source` (#1007) look for marker paths at the root instead. The predicate feeds `is_synced_copy`, which living-docs' place validation is to use to refuse a synced copy as a documentation place ([living-docs:DEC-001-living-docs-discipline] point 1). ADR-055 point 3 rests on that answer when it declares `.pkit/` to be source here.

Nothing recorded what the two answers recognise, or why they agree. They agree only because of route 1. With routing bypassed, sync can copy into a checkout that the predicate still calls source. The predicate also carries this distribution's package path, a literal nothing listed. The methodology keeps this distribution's names out of its records and lists them in the distribution's reference, which code carrying one cites ([COR-053](../../../.pkit/decisions/core/COR-053-connection-points.md), its vocabulary paragraph).

## Decision

1. **The definition.** The methodology's source repository is the repository whose `.pkit/` is the methodology's own tree: authored there, and bundled into the distribution from there, so no sync ever copies into it. Every clone and worktree of it qualifies. Two tests recognise it, one on each side of the tool/tree boundary; neither is the definition.
2. **Sync's test** (`project_kit.install.is_self_host`): the target is the parent of the source tree the running code resolves. It is exact whenever the running code is the repository's own, which route 1 makes the normal case. A bundled tree never has a project as its parent, so where the running code is an installed distribution the test says no in every repository, the source included. Consumers: sync's self-host path (deploy primitives only, no propagation), upgrade's self-host branch (which delegates to sync), init's refusal, and the refusal in the gap and `pkit pin`'s guard (point 3).
3. **The marker test** (the router's route 1, the ownership predicate, the refusal in the gap): the package source sits beside the methodology's tree, `.pkit/`, at the repository's root. An adopter has that tree, its dispatcher included, but never the package source. The in-tree dispatcher is not a marker: it is what route 1 execs to keep the two tests equal (point 4), not what tells the source from an adopter, so a checkout whose dispatcher has been deleted is still the source, and route 1's warning reports the dispatcher missing. The test answers the same for a checkout whichever code operates on it.
   - **The router's route 1** (`project_kit.router.is_source_checkout`) runs before any code is chosen, because choosing the code is its job.
   - **The ownership predicate** (`is_methodology_source` in `.pkit/lifecycle/ownership.py`) is loaded where the tool's package cannot be imported, for the reason [ADR-003](ADR-003-permission-core-code-home.md) gives.
   - **The refusal in the gap** (`project_kit.install.refuse_propagation_into_source`, #1070) asks the markers, through the router's function, after sync's test has said no, so it answers only in the gap, where the running code is not the repository's own; there sync and upgrade refuse rather than propagate. Both ask it right after their self-host branch — in upgrade, before the bypass guard, since both bypass paths into the gap skip what follows that guard. It replaces upgrade's self-update skip as the marker test's consumer there: the tool step now comes after the refusal, so it is never reached in a source checkout. `pkit pin` refuses where either test recognises the source, because the router never reads a pin in a tree the markers call source.

   The router's function and the predicate are two copies of one test, and a test holds them equal.
4. **Route 1 keeps the two tests equal.** When the markers are present, the router execs that checkout's dispatcher, which runs that checkout's package. The source tree the running code resolves is therefore that checkout's `.pkit/`, provided the resolver accepts that checkout's `.pkit/` as a source tree — it requires `decisions/` there, which a source tree always carries — and sync's test says yes. In the other direction, where sync's test says yes, the running code is that repository's package source and the tree it resolves is that repository's `.pkit/`, so the markers are present, dispatcher or not. A test holds the predicate to sync's own decision in a source-shaped tree and an adopter-shaped tree, under the condition route 1 establishes.
5. **The literal.** The package path the marker test reads and the dispatcher route 1 execs are this distribution's names: its package and its dispatcher ([PRJ-001](../../../.pkit/decisions/project/PRJ-001-cli-binary-name.md)). They are listed in the lifecycle README's table of the methodology's literals ("The methodology's literals"), and both copies of the marker test cite that table.

## Rationale

**Why the definition names the tree, not a test.** Sync's test gives the same checkout different answers depending on which code runs it: yes under the checkout's own code, no under another checkout's or the installed tool's. A definition cannot depend on that. The markers give one answer whichever code runs, but they describe what a source checkout looks like, not what makes it the source. What makes it the source is that the methodology's tree is authored there and bundled from there. Each test recognises that under its own condition, and point 4 is why the conditions coincide in normal use.

**Why not one function for all six.** The tool and the propagated tree are the boundary. The ownership predicate cannot import the tool. The router could load the tree-side predicate from its own bundled copy, but it would first have to find that copy. That means a second locator for the source tree on the router's stdlib-only hot path, to save a check of two paths. Loading the target's own copy would run whatever version that tree holds before routing, and a tree older than the predicate has none; the router needs its own copy regardless. Nor can sync's test move into either of them, because it has to know which code is running. The router decides that, and the predicate never learns it. So each test has one function, and the marker test exists in two copies held equal by a test.

**The gap, and why the markers do not close it.** Where the running code is not the repository's own, sync's test misses the source and sync breaks the invariant. Four paths reach it: an operator's `PKIT_NO_ROUTE=1`; `pkit pin` to a release newer than a checkout's recorded content, which runs that release's `upgrade` with routing bypassed ([ADR-062](ADR-062-projects-pinned-by-default.md)) and propagates it over the checkout; a dispatcher that is present but not executable, where route 1 falls back to the installed tool, whose sync then copies over the checkout; and a dispatcher that has been deleted, where route 1 falls back the same way. Keying sync on the markers would not close it. Sync would skip propagation, but it would also run foreign code as though it were the checkout's own. The honest answer there is a refusal, which carries out this record rather than revising it. The refusal is built by #1070.

**Why the dispatcher is not a marker.** A marker test that required the dispatcher would stop recognising the source on the fourth path, the one place the refusal in the gap needs it: the router would take the checkout for an adopter and the installed tool's sync would propagate over it. The package source alone already tells the source from an adopter, and point 4 holds without the dispatcher in the direction from sync's test to the markers. A checkout that carries the package source and no dispatcher is therefore the source, with the dispatcher reported missing — by route 1's fallback warning and by the refusal, which names restoring it from git.

### Alternatives considered

- **Sync's test as the definition.** Rejected. Its answer depends on which code runs, so the same checkout would be the source under its own code and an adopter under anyone else's.
- **Markers as the definition, with sync keyed on them.** Rejected. Sync's self-host path skips propagation because the running source *is* the target's state, and markers cannot establish that.
- **One shared function across the tool/tree boundary.** Rejected for the reasons above.
- **Leave both tests unrecorded, joined only by the router-versus-predicate test.** Rejected. That test holds one copy of the marker test to the other, not to sync's test, so sync's test could change and nothing would notice.
- **Recognise a deleted dispatcher by git's record that it is tracked but missing.** Rejected. An adopter tracks its dispatcher too, so the record tells a deleted dispatcher from a never-installed one but not the source from an adopter; that still takes the package source. It also puts a git subprocess on the router's stdlib-only hot path and into the ownership predicate, and a source exported without git history would lose it.
- **Report a checkout with the package source and no dispatcher as unrecognisable.** Rejected. It adds a third answer to a test whose consumers each ask a yes-or-no question, and each would have to decide what the third means. Recognised as the source, the checkout meets the answers already built for the gap: route 1's fallback warning and the refusal.

## Implications

- `install.is_self_host` replaces three copies of the comparison in sync, upgrade and init. Each consumer of either test cites this record, and the marker copies cite the literals table.
- `tests/test_lifecycle_ownership.py` holds the predicate equal to the router's markers and to sync's own decision.
- The gap is closed by a refusal where the two tests disagree, built by #1070. Sync and upgrade refuse to propagate over the methodology's source repository, naming both tests and the way the run reached the gap: the routing bypass (set by hand, or by a `pin` to a newer release or a pinned `upgrade`), an inherited loop guard, a dispatcher route 1 cannot exec — not executable, or deleted — or a start that never went through the router. No flag overrides the refusal — the gap is a defect path, not a choice — and its remedy is to run the checkout's own code, once a deleted dispatcher is restored. The capability verbs refuse the same way before anything else: `capabilities install`, `upgrade` and `register`, since each copies or registers a capability with the running code's tree (#1090), and `uninstall`, since that code would take a kit-shipped capability's subtree, here its source, for a copy and delete it (#1107). `pkit pin` refuses wherever either test recognises the source. Route 1's fallback warning points at repairing the dispatcher, not at `sync`, and names a deleted one as missing. `tests/test_source_repository_refusal.py` covers each path. It carries out this record and needs no revision of it.
- Under the checkout's own code, where sync's test holds, a capability's subtree lies in the tree the running code resolves (`capabilities.authored_in_source`): it is the capability's source, the tree install and upgrade copy from, never a copy of it. The capability verbs therefore act on it in place, never copying onto it or deleting it (#1107). `capabilities install` registers an unregistered capability with origin `kit-shipped` and copies nothing, stamping no install receipt into the authored tree. `upgrade` re-runs the deploy primitives and provisions the capability's query commands, with nothing copied and no migration run — sync's self-host path, for one capability. `uninstall` says which subtree it would have deleted and, once the operator confirms, unregisters the capability only; `--purge` is refused there, since a capability leaves the source through git. Unregistering rather than refusing outright is COR-031 D4's answer for authored work: uninstall deletes a subtree only because it is a disposable copy, and removes authored work by unregistering it in place, which `install` reverses. The confirmation is asked because a `kit-shipped` registration promises deletion and here it will not happen; an incubated one is unregistered in place as anywhere. Beneath the verbs, a capability copy whose source is its destination is refused for any caller, before its migrations run. `tests/test_capabilities_in_source.py` covers the three verbs.
- **Revisit** when route 1 changes or is retired; when the package source moves or is renamed; when the resolver's acceptance test changes; or when a second distribution of the methodology ships its own package. Each breaks the argument in point 4.
