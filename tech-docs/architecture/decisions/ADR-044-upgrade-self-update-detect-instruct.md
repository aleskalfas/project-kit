Refreshing a project's `.pkit/` **from the installed tool's bundled kit**, as `pkit upgrade` does, cannot update the *tool* itself, and that refresh alone can't even tell you the tool is behind: an adopter on a stale tool sees *"nothing to upgrade"* and has no idea the fix lives in a different command (`uv`). This ADR makes `pkit upgrade` **detect** a newer released tool and **update it**: in an interactive session it runs `uv tool install --force` itself and re-runs the upgrade under the new version — one command — and otherwise (a non-interactive session, `--no-self-update`, or an install that fails or is declined at the confinement sandbox's own prompt) it **prints the exact command** instead. Replacing the global binary every project on the machine shares does not disturb a pinned project: the per-project pin the router serves via `uvx` (**option D**, [ADR-049](ADR-049-per-project-version-pin.md)), which `pkit upgrade` writes by default, runs the project at its own version, not the global binary's. The self-update fires only on the un-pinned path; a pinned project's `pkit upgrade` advances its own pin and never touches the global tool.

## Context

Two distinct upgrades exist, done by two tools. The **tool** (the `uv`-installed wheel and its bundled `_kit` snapshot, [ADR-033](ADR-033-official-install-bundles-content.md)) is shared across *all* the user's projects; **`pkit upgrade`** ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md)) brings *one* project's `.pkit/` up to whatever that tool bundles. `pkit upgrade` reads the bundle and is fully **offline**; it has no path to update the tool or discover a newer release. The [ADR-039](ADR-039-pkit-entry-point-router.md) router already re-execs a *pinned* version of pkit via `uvx project-kit@<pin>` from a compiled-in distribution URL — so the fetch-a-released-version machinery exists — but nothing discovers "the latest," and the router's pin route is inert for adopters (they carry no `.pkit/VERSION` — it is not in the propagated install set, a fact surfaced during the #545 provenance work). The live failure: an adopter (AUJ) ran `pkit upgrade` against a tool bundling an older backbone, got *"Already at backbone vX; nothing to upgrade"*, and the remedy — a manual `uv tool install --force …@vY` — was neither run nor named.

A prior "fold the `uv tool install` into `pkit upgrade`" design was reviewed and **rejected**: its "pinned project → raise the pin" branch is inert (no adopter pin file exists), collapsing it to *always replace the global tool*; and replacing a shared binary as a silent side effect of a per-project command is a consent/blast-radius regression the sandbox would prompt on anyway. This ADR records the converged, narrower outcome.

## Decision

**`pkit upgrade` detects a newer released tool and updates it, instructing instead when it cannot or may not.**

- **D1 — Detect, best-effort, offline-safe.** `pkit upgrade` queries the release source (a `git ls-remote --tags` against the compiled-in distribution URL, the same URL the router already uses) for the latest tag. If the source is unreachable (offline, no credentials), it **degrades loudly and continues** with today's behaviour — sync the project from the current bundle — and never fails the command on the check. The network call is best-effort, not a gate.
- **D2 — Act on a stale tool; instruct as the fallback.** When the running tool is behind the latest release and self-update is allowed, `pkit upgrade` runs `uv tool install --force <url>@v<latest>` and then **re-execs the same command under the freshly-installed version**, so the content sync and pin run under the new bundle — one seamless command. The re-exec is guarded by a **dedicated `PKIT_SELF_UPDATED` interlock** (not the router's `PKIT_ROUTED` bypass — different loop, different scope), which terminates the self-update step **regardless of version comparison** (else an install-succeeds-but-version-skews infinite loop). Any non-zero `uv tool install` exit aborts the self-update — no re-exec — and the command falls back to the instruction below (a botched force-install can brick the shared binary). The self-update **honors the sandbox's own gate — pkit never allowlists `uv tool install --force` to suppress it** (core rules 14-15). `pkit upgrade` **degrades to instruct** — it prints the **exact command** to update the tool (`uv tool install --force <url>@v<latest>`, then re-run `pkit upgrade`) and *why*, and runs nothing further — when the session is **non-interactive** (no TTY, so a network install is never forced under automation/CI), when `--no-self-update` is passed, or when the install **fails or is declined** (the sandbox gates a global-binary mutation; a decline surfaces as a non-zero exit and degrades, never bricks). When the tool is current, it says so plainly instead of the ambiguous "nothing to upgrade."
- **D3 — uv-only, and scoped to a normal adopter install.** The self-update and the instruction assume a `uv`-tool install (per the uv-only distribution narrowing, PRJ-004). Both are **suppressed on a source checkout / self-host** (where reinstalling a released tag over working-tree code would be nonsensical — the router's route-1 / the upgrade self-host short-circuit already identify these). Where `pkit upgrade` only *prints a string* (D2's fallback), a mis-detected context degrades to a suboptimal message, never a destructive action.
- **D4 — Boundary: the tool, from its distribution URL.** Self-update concerns the **tool** (repointed from the compiled distribution URL); it never touches externally-sourced *content* ([COR-041](../../../.pkit/decisions/core/COR-041-external-source-distribution.md)). An install whose real upstream diverges from the compiled URL (a fork building its own wheel gets its own URL and is fine; a diverging source is not) is out of scope for the printed instruction's correctness — print-only sidesteps the "install from the wrong upstream" hazard entirely, which the self-update (D2) does not.
- **D5 — Self-update runs on the un-pinned path only, and alone outside a project.** Self-update fires only on the **un-pinned / non-routed-child** path (D1's staleness-check site, suppressed under the router bypass). A pinned project's `pkit upgrade` advances its own pin via `uvx` and never touches the global tool, so the [ADR-039](ADR-039-pkit-entry-point-router.md) multi-version-coexistence invariant (a project on an older pin runs that older version) holds. Run **outside any project**, `pkit upgrade` performs the tool self-update alone (via `run_tool_update`) instead of erroring on a missing project/manifest — the "just update my tool" case.

## Rationale

**Why act, with instruct as the fallback.** The friction that surfaced is *confusion* — "nothing happened, what do I run?" A printed command kills that completely and adds no mutation, no self-replace, no cross-project blast radius, no upstream-source hazard; it is what `pkit upgrade` does whenever the self-update cannot or may not run (D2). Acting saves the paste: one seamless command. The case against acting is blast radius — reinstalling the shared global binary moves every un-pinned project at once, a cross-project blast radius the sandbox gates anyway. **Pin-by-default** ([ADR-049](ADR-049-per-project-version-pin.md); shipped v1.145.0) insulates projects from the global tool: a pinned project runs its own version via the ADR-039 router's `uvx` re-exec and does not follow the global binary. So updating the tool does not disturb pinned projects, and blast radius gives no reason to withhold the action. Option D — the per-project pin the router serves via `uvx` (no global mutation, per-project scope, reproducible) — shipped as ADR-049, and the self-update completes the seamless end-state D pointed at.

**Why it layers above the router, leaving ADR-039 closed.** Self-update is a new upgrade-time behaviour that *calls* the router's fetch machinery (the compiled distribution URL, the `uvx` pattern) without changing the router's three-route / two-guard decision. The self-update's `PKIT_SELF_UPDATED` interlock is owned by the upgrade path, not the router — a distinct loop from route re-selection. So ADR-039 is unchanged; this composes on top.

**Why the sandbox's gate stays.** The sandbox prompt authorises the self-update's *mechanism* (network egress + global write). Suppressing it requires defeating a layer — the exact rule-14/15 violation. A prompt for a global-binary replacement is honest, not a defect to engineer away.

### Alternatives considered

- **Fold a silent `uv tool install` into `pkit upgrade` (auto-run, no prompt).** Rejected when the design was reviewed: inert pin branch → always-replace-the-global-tool, silent cross-project blast radius, sandbox prompts anyway. It differs from D2's self-update in installing in every session, CI included, with no `--no-self-update`, no degrade to the instruction, and on pinned projects too (D2, D5).
- **Instruct only — print the command, never install.** Not taken as the whole behaviour; it is D2's fallback. It kills the confusion with no new mutation. Its case against acting: the global install moves every un-pinned project at once; the sandbox gates it with its own prompt regardless, so acting saves a sandboxed operator nothing; and option D would retire the global-mutation path, so building it first is the wrong side of [COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)'s "don't build the heavier abstraction a successor removes." Pin-by-default (ADR-049) insulates pinned projects from the global tool, and with D shipped the self-update completes D's end-state rather than being retired by it.
- **A separate `pkit self-update` command.** Deferred: worth revisiting only if demand for a command-driven tool update appears after D; a per-project command touching the global tool is the scope tension D dissolves.
- **Do nothing (leave "nothing to upgrade").** Rejected: it is the confusing message that motivated this.

## Implications

- **`pkit upgrade`** gains a best-effort `git ls-remote --tags` staleness check against the compiled distribution URL, an offline-degrade path (warn + proceed with today's sync), a self-update when stale (`uv tool install --force`, then a re-exec under the new version), a "your tool is behind — run: …" instruction when it cannot or may not self-update, a `--no-self-update` flag that keeps it print-only, and a clear "tool is current" message when the tool is not stale. Run outside any project, it performs the tool update alone. Suppressed on source-checkout / self-host.
- **A sandbox-gated mutation, no network gate.** The check never fails the command. The permission surface includes `uv tool install`, which `pkit upgrade` may issue — only interactively and with a clean degrade, consistent with the sandbox's gating of global-binary mutations.
- **Depends on the uv-only narrowing** (PRJ-004 + PRJ-003 amended): the self-update and the printed instruction are `uv` commands.
- **Surface change → a backbone version bump** (a new observable `pkit upgrade` behaviour), declared via a changeset. Migration-free (additive behaviour; no state to bridge): the behaviour lives in the upgrading code, so an existing adopter gets it on their next `pkit upgrade` under a version that carries it.
- **Stands on** ADR-033, ADR-039, ADR-049, COR-007, COR-010, COR-041, PRJ-004 — all accepted (PRJ-004 amended alongside). ADR-039 is not reopened.
