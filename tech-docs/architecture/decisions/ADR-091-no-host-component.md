## Summary

**In plain terms:** an *agent host* is software outside pkit that starts harness sessions for a person and drives their turns, from a chat, a schedule, an editor or a pipeline, often with nobody at a terminal. DAM, which runs Claude Code in hosted machines, prompted this record, and is the one host whose needs were investigated. The test below was traced on three other kinds of host as well, and is written for any agent host.

project-kit ships no component for an agent host, neither an adapter nor a capability, and nothing it ships tests which agent host it runs under. An agent host that runs Claude Code still runs Claude Code, so the Claude Code adapter is the one that serves it. Running under an agent host is no discipline a project adopts, so no capability fits it.

One test, asked in order, places each need an agent host brings:

- A change that is right on every machine is made for every machine.
- Where pkit must act differently on some machines, it reads a property of the session or the machine, never the host's name.
- Where pkit depends on harness behaviour it can neither set nor read, such as an ask reaching a person who can answer it, the dependency becomes a harness requirement. The requirement reports the gap and does not close it.
- A step a machine needs because of how it was set up, such as installing pkit where a host's machines find it, belongs to that setup. pkit ships commands a setup may call, as any adopter calls them, and no host's setup: that goes in what the host offers for its own setup, such as a DAM Starter Kit, DAM's own package of setup steps.

A need not worth meeting is accepted as a limit, and stated by its property. The question is asked again once a second agent host's setup for pkit is written by project-kit or brought to project-kit's tracker.

One placement narrows a ruling the maintainer made during the investigation, and accepting this record accepts the narrowing. A project can limit who authorises in a chat turn to named senders only once the harness, or a signal any host can set, names each turn's sender. A host that names the sender only its own way does not open that setting, so under DAM it waits until the harness, or the protocol DAM drives it through, carries the sender (Implications).

This is project-kit's own ADR, and it holds its general rules here provisionally. The general rules are these:

- the term *agent host*;
- three lines no core record draws: running under a host is no discipline, nothing pkit ships tests which host it runs under, and a harness requirement's cost names the property, never the host;
- point 4's test;
- what point 7's first three bullets say of a host's setup: what counts as one, where it lives and what of pkit it may use.

An adopter who writes an adapter or a capability would need them, so the test that decides which kind of record a rule belongs in places them in a core record ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Scope test"). Holding them here falls short of that test. The shortfall is open work ([COR-065](../../../.pkit/decisions/core/COR-065-records-and-projection.md) point 4), held by the issue in which the maintainer decides whether the core records say where an agent host's needs belong (#3009). The rest of the record, points 3 and 5, point 7's last two bullets, point 8 and where the investigation's gaps fall, is project-kit's application, an ADR's in any case. The Implications say when #3009 falls due and how the shortfall closes.

## Context

**The terms.**

- **A harness** is the external tool that runs a methodology's sessions, its agents and their tool calls; Claude Code is one ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md), Context).
- **An agent host** is software outside pkit, one layer out from the harness, that starts harness sessions for a person and drives their turns, often with nobody at a terminal. It is a host only in that role: a pipeline that runs scripts and starts no harness session is no host there. It is not the harness, which COR-047 says hosts a session. Nor is it the hosting service that holds a project's repository ([ADR-061](ADR-061-hosting-service-acts-in-the-backbone.md)), or the machine a session runs on, which [ADR-010](ADR-010-host-environment-detection.md) calls the host. A person who runs the harness at a terminal of their own uses no agent host. Below, *host* alone always means an agent host, and the machine is called the machine.
- **A service that runs sessions, agents and tool calls itself,** rather than starting a harness that does, is a harness by COR-047's definition, whatever else it does, and gets an adapter of its own ([COR-005](../../../.pkit/decisions/core/COR-005-bundle-pattern.md)).
- **pkit** here is what project-kit ships to a project: the pkit command, the backbone, its adapters and its capabilities, with their rules, agents, skills and documents. Tooling that project-kit's own repository keeps for itself and ships nowhere is project-kit's as a project, as an adopter's own files are the adopter's. *Where pkit acts* covers an agent following pkit's instructions as much as a command.
- **pkit's own runner is no host.** It starts an agent for a command with nobody watching, but it is part of the harness's adapter ([ADR-066](ADR-066-unattended-agent-runner.md) point 1), and pkit names and sets the marker of its runs itself (ADR-066 point 8).

**What prompted it.** project-kit#3003 follows an investigation of running a pkit project in DAM's machines ([DAM](https://github.com/dam-agents/dam); the scratchpad note `2026-11-09-pkit-in-dam-containers`). Its gap 6 asked where pkit keeps what DAM needs, a bootstrap and a page on running there: in a capability, in the Claude Code adapter, or among the grades of the harness support declarations. The investigation's bounds left open a capability that bootstraps pkit in DAM.

**What the investigation found.** Few of its gaps are DAM's alone, and several hold more than one need:

- **Some are wrong on every machine,** a laptop's included. A session that runs as an agent granted a list of tools loses every other tool, the web tools and a connected server's among them. That was mended for every machine ([project-management:DEC-068-session-agent-tools]).
- **Some are differences pkit can read where it acts,** such as a shallow clone, or a session with no terminal.
- **Some are dependencies on behaviour pkit cannot see,** such as whether an ask reaches anyone in a turn that a chat message started.
- **Some are setup only DAM needs:** putting the repository where DAM starts its sessions, and installing pkit where DAM's machines find it.
- **Some it accepts as limits,** such as one checkout shared by every session on a machine.

**What the records already say.** An adapter is one harness's translation of the methodology's content ([COR-005](../../../.pkit/decisions/core/COR-005-bundle-pattern.md)). A capability is a discipline a project opts into ([COR-017](../../../.pkit/decisions/core/COR-017-capability-pattern.md)), and variants within one are its data ([COR-027](../../../.pkit/decisions/core/COR-027-alternative-impls-as-capability-data.md)). A dependency on the harness's behaviour, configuration that several parties can set among it, is declared as a harness requirement, in words any harness could meet (COR-047). No record says where a host's needs belong.

## Decision

**project-kit ships no component for an agent host, and nothing it ships tests which host it runs under. One test places each need a host brings: a change for every machine, a property pkit reads, a harness requirement that reports, or a step of the setup that prepared the machine. A need not worth meeting is a limit, stated by its property.**

### 1. No component is keyed to an agent host

- **An adapter per harness.** An adapter translates the methodology's content for the harness that reads it (COR-005). That content reaches a host's sessions through the harness, so the harness's adapter is the one that serves them.
- **A capability per discipline.** A project opts into a capability as a practice it adopts (COR-017). Running under a host is no practice: it says where a session runs, not how the project works.
- **So pkit ships none of these for a host:** an adapter, a capability, an area, variant data inside a capability, or a deployed file that differs by host. The capability that bootstraps pkit in one host, which the investigation left open, is among them.

### 2. Nothing pkit ships tests which agent host it runs under

- **No test of a host's identity.** pkit never tells one host from another, by a name, a variable, a path or a file, whoever sets it, the harness's vendor included. A host's names are foreign to pkit: its owner may change them without telling pkit, the risk COR-047 point 1 names, and a test by name misses the next host with the same property.
- **pkit's own values are properties.** A value pkit names and sets itself, such as the marker of an agent run (ADR-066 point 8), carries no such risk, and pkit reads it as a property (point 5).
- **Named as an example, never as a condition.** Anything of pkit's may name a host as an example, as this record names DAM as what prompted it. No step pkit takes or requires depends on one.

### 3. The adapter meets a harness by how it starts, never by who starts it

- **How the harness starts is the harness's fact.** A host may start the harness through its SDK or a protocol bridge rather than its terminal. Two facts of such a start decide whether the adapter serves it as it stands: whether it loads the project's settings, and whether the session's file tools are the harness's own or ones the bridge puts in their place. The adapter meets each way of starting as a way the harness starts, whoever starts it. Where one value of the harness's says both how it started and which host started it, pkit reads it for the way of starting and branches on no host it names (point 2).
- **A start that loads none of the project's files** leaves nothing of pkit in the session. The harness requirement that every session holds every layer's loaded rules reports it ([COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md) point 6), and only the host, its setup or the harness can close it.
- **A start whose file tools are a bridge's own** hides the session's writes from pkit's checks on the harness's file tools, and pkit does not learn the names of a bridge another maker ships (point 5). The dependency, that a session writes files through the harness's own tools, is then a harness requirement (point 6), whose cost names the property: a start that keeps the harness's own file tools.

### 4. One test places each need a host brings

Each gap a host shows is split into the needs it holds, and each need is asked these questions in order. The first that fits places it.

1. **Is there a change to pkit that is right on every machine?** Then pkit makes it, in the component that owns the behaviour, keyed to nothing, as the session agent's tools were mended ([project-management:DEC-068-session-agent-tools]). A change that stops pkit depending on behaviour a host takes away is one. So is a project setting, the same on every clone, whose default serves every machine.
2. **Must pkit act differently where some fact of the session or the machine holds?** Then it reads that property where it acts (point 5). *Must* is the test: a step pkit could take for a machine but need not, such as deepening a clone its setup made shallow, stays with the fourth question until a record of its own makes it pkit's.
3. **Does pkit still depend on harness behaviour it can neither set nor read?** Then the dependency is a harness requirement (point 6). A requirement reports the gap and does not close it: under a host that takes the behaviour away, the need stays unmet until the host, its setup or the harness keeps the behaviour.
4. **Is it a step a machine needs because of how it was set up?** Then the setup that prepared the machine holds it, which on a host's machines is the host's (point 7).

**A limit.** At any of the four, meeting a need may cost more than it is worth. It is then accepted as a limit by the person who accepts the change that states it, and that change says what meeting it would cost. It is stated by the property behind it, such as sessions that share one checkout, never by a host's name, on the page point 7 names.

### 5. What hosts vary, pkit reads as a property

- **A property** is a fact of a session or a machine that pkit reads where it acts. It is what pkit's own process shows, such as whether standard input and output are terminals ([ADR-063](ADR-063-upgrade-updates-the-tool.md) point 3) or whether the clone is shallow ([ADR-081](ADR-081-landing-check.md) point 6). Or it is what the harness reports, such as the session's anchor or its permission mode. Or it is a setting pkit keeps for one machine. A project setting is no property: it is the same on every clone.
- **Read under the name of what provides it.** A value the harness provides is read under a label naming that harness, so another harness changes the lookup and not the behaviour, as the backbone reads the session's anchor (ADR-061 point 6). A standard signal that many parties set may be read too, as pkit's own detection of the machine reads only such signals (ADR-010 point 6). A value only one host provides is not read (point 2).
- **A bridge's own values are the harness's only where the harness's maker ships the bridge.** A protocol bridge that starts the harness for a host is a way the harness starts (point 3). What its protocol defines is a standard that many parties speak, so pkit may read it as a standard signal. What a bridge adds of its own, such as the names of file tools it puts in place of the harness's, is read under the harness's label only where the harness's maker ships the bridge. From any other maker, pkit reads it no more than a value one host provides. A key a host writes in a field the protocol leaves open is that host's own.
- **Keyed to the property, the behaviour holds wherever the property does:** on a laptop, in a pipeline, in a container or under any host.

### 6. A dependency pkit can neither set nor read becomes a harness requirement

Some behaviour pkit depends on can be taken away by a host, and pkit cannot read it where it acts. An ask reaching a person who can answer it is one: a host that drives the harness may answer the harness's prompts itself, in a turn nobody watches.

- **Stated as the harness's behaviour,** in words any harness could meet, and answered by each adapter for its harness (COR-047 points 1 and 2). COR-047's Context names configuration that several parties set. A host that drives the harness is such a party, and this record reads what a host can take away as a cost of the harness's answer.
- **Admitted on COR-047's bar:** a demonstrated defect, or a design that rests on the behaviour, cited as evidence (COR-047 point 9).
- **Its cost names the property, never the host.** Where something a session or a machine holds can take the behaviour away, the adapter grades its harness's support as achievable at a cost, and the cost says what must be kept. The Claude Code adapter's answer to the confined run's requirement (ADR-066 point 13) is the pattern: its cost names the sandbox the operating system provides, so a machine without one lacks it, under any host (the adapter's README, ["Harness support"](../../../.pkit/adapters/claude-code/README.md#harness-support-harness-supportyaml)).
- **It reports, and does not mend** (COR-047 point 6). Point 4's third question says what that leaves.

### 7. A host's setup is the host's own

- **What counts:** a step a host's machines need because of how the host prepares them, such as putting the repository where that host starts its sessions, installing the pkit command where its machines find it, deepening the shallow clone its seed makes, or running that install from the host's own setup step.
- **Where it lives:** outside what pkit ships, in what the host offers for its own setup, such as a DAM Starter Kit in a repository of its own, or in the adopting project's own files. pkit ships none of it, and keeps none on every adopter's behalf. project-kit, as an adopter of itself, keeps its own setup in its project's files, as any adopter does.
- **What it may use of pkit** is pkit's public surface, as any adopter uses it: its commands and the files it documents.
- **What it writes when it runs** is what belongs to its machine, such as the pkit command's install, the clone's history, or a setting pkit keeps per machine, the last through pkit's own commands. It writes no file the project commits. Where it needs a project setting to hold some value, that value is the project's choice for every clone, which the setup may check and never sets.
- **pkit's page on running with nobody at the terminal** states the limits accepted under hosts, each by its property (point 4). It states too, as reference, that pkit keys no component and no test to a host, and why (points 1 and 2), so that an adopter who meets a host sees the line. It may describe the properties a host's machines need and the requirements its sessions must meet, with one host as its worked example (point 2).

### 8. The question returns with a second host

When a second host's setup for pkit is written by project-kit or brought to project-kit's tracker, the two setups are compared. What both need, and a property or a requirement can state, moves into pkit by point 4. A component for hosts is weighed again only for what they share that no property or requirement can state ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)).

## Rationale

**Why no adapter.** COR-017's Context calls adapters translation layers to external systems, today scoped to harnesses, and COR-005 keeps one adapter per harness. A host does read files of its own, such as a setup manifest or an onboarding page, but those prepare a machine, which is point 7's. The methodology's rules, agents and skills reach the session through the harness, whose adapter already translates them. So a host's adapter would hold setup, or the harness adapter's content again, and two adapters of one harness would write the same project files.

**Why no capability.** A capability is a discipline a project adopts (COR-017). A host says where a session runs, not how the project works, so a capability for one would key a component to a host under a discipline's name. COR-017 does not draw this line itself. Point 1 draws it for what project-kit ships ("Why an ADR, for now").

**Why no deployed variant.** A file that differs by host is chosen either by the host's identity, which point 2 rules out, or by a property, which is point 5 and no host's variant. Committed, it changes with whichever machine synced last. Kept per machine, as pkit keeps some settings out of version control ([ADR-032](ADR-032-per-machine-activation-routing-axis.md)), it may not be read where it is needed. The investigation's host-only variant of the session agent failed so: the permission hook it measured read the session's agent only from the committed settings.

**Why properties, not names.** A property holds under hosts nobody has seen yet, and on machines with none. A name holds for one product, which may change how it starts sessions without telling pkit (COR-047 point 1). ADR-010 point 6 already keeps pkit's detection of the machine to vendor-neutral signals. The same rule covers the harness's vendor when it is also the host: pkit reads the anchor its harness provides, and never a value that only says which host it is.

**Why a requirement for what pkit cannot read.** COR-047 is the carrier for a dependency on the harness's behaviour. Its graded answer with a cost says what a session must keep, with no host named, and admission on evidence keeps the set from filling with guesses about hosts. Reading a host's effect as a cost of the harness's answer stretches COR-047's several parties from those who configure the harness to those who drive it. COR-047 decides nothing against that, and the other way, a grade for each host, is rejected below.

**Why the test runs in that order.** A change right on every machine is the cheapest to keep, since nothing branches. A property comes next, since it branches only on a fact pkit sees. A requirement only reports, so it comes after every way pkit can act itself. The setup that prepared the machine takes what is left. A gap is split before it is placed, since its needs may fall to different questions, and placed whole it would go wherever its first need went. Installing pkit on a fresh machine holds four needs: a fetch of pkit's own releases, the clone's history, a folder on the path and the moment the install runs. They fall to different questions.

**Why setup goes to the host.** The steps that run before a session, placing the repository and installing the pkit command, are the host's own: they run before pkit can. The hook the adapter runs at each session's start ships to every adopter on that harness and runs in every session. Teaching it one host's setup would carry that host to all of them ([COR-014](../../../.pkit/decisions/core/COR-014-universal-applicability.md)). A host's setup changes when the host does, and writing no committed file keeps one machine's setup from changing another's clone.

**Why the test should hold beyond DAM.** DAM's needs are the only ones investigated. Traced on three other kinds of host, as reasoning rather than evidence, the test places each need without a component:

- **A pipeline that runs the harness on one prompt.** No terminal is a property pkit already reads. A shallow clone is one too, and where its history falls short pkit says so rather than answer (ADR-081 point 6). Deepening the clone and installing the pkit command are the pipeline's own setup.
- **An editor that drives the harness over a protocol bridge.** How the bridge starts the harness is the adapter's (point 3). Whether the session loads the project's files, whether it writes through the harness's own file tools, and whether an ask reaches the person at the editor, are requirements (points 3 and 6).
- **The harness vendor's own hosted sessions.** The anchor the harness sets is read under the harness's label, and no value that names the host is read.
- **pkit's own runner** is no host, and the marker of its runs is pkit's own property.

**Why wait for a second host's setup.** One host shows what it needs, not what hosts share. COR-007 extracts a common form once a shape recurs, and point 8 names that recurrence.

**Why an ADR, for now.**

- **Its general rules are not project-kit's alone.** They are the term *agent host* (Context), the three lines no core record draws, point 4's test, and what point 7's first three bullets say of a host's setup. The three lines are new to the methodology: running under a host is no discipline (point 1), nothing pkit ships tests which host it runs under (point 2), and a harness requirement's cost names the property, never the host (point 6). COR-017 scopes adapters to harnesses only "today", and no core record draws any of the three. Their reasons hold in any project: a host's names are foreign to every project, a host is no discipline for any capability, and a cost that names a host misleads under any adapter. So an adopter who writes an adapter or a capability would need the general rules, point 4's test above all, and COR-025's scope test places a rule another adopter would need in a core record ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Scope test").
- **The rest is project-kit's application.** Points 3 and 5, point 7's last two bullets, point 8 and where the investigation's gaps fall say how what project-kit ships meets a host. They rest on project-kit's own ADRs and its adapter's README, which no core record can rest on. Rules of that kind are an ADR's: COR-025's own worked example puts how project-kit's command finds the project's root in one, and this repository records its product's shape in ADRs ([PRJ-005](../../../.pkit/decisions/project/PRJ-005-adopt-adrs.md), its classifier). ADR-010 point 6 is of that kind too: it applies COR-014 to the machine signals project-kit's own command reads.
- **Each place costs something.** Kept here, the general rules reach no adopter as rules. What they decide reaches each adopter through what pkit ships, but an adopter who writes an adapter or a capability never reads them, and may key it to a host. Put in a core record now, a term drawn from the needs of one host, a product outside the methodology and the only one investigated, enters every project's vocabulary, and a wrong line costs every project to mend, where here it costs one (COR-025, "Propagation isolation"). While one host is all the evidence, the second cost is the larger: a second host or an adopter's question tests the term before every project carries it.
- **A narrower core record now does not escape that cost.** Written without the term, of whatever starts or surrounds the harness, the line that nothing shipped tests which host it runs under would take in the operating system. pkit reads the operating system's name as a fact of the machine, since the sandbox differs from one to the next, as its support for the macOS sandbox shows ([ADR-014](ADR-014-macos-sandbox-platform-stance.md)). Drawn to leave the operating system out, the line would draw the one the term draws, from the same one host. And the narrower record would leave out point 4's test, the rule an adopter would need most, which places the needs a host brings.
- **So the general rules are held here provisionally, and the shortfall is open work.** Holding them in an ADR falls short of COR-025's scope test. This record changes nothing COR-025 decides: the shortfall is recorded as open work ([COR-065](../../../.pkit/decisions/core/COR-065-records-and-projection.md) point 4), in the issue where the maintainer decides whether the core records say where an agent host's needs belong (#3009). ADR-061 point 3 is the precedent for the form: a placement adopted for project-kit provisionally, and raised for a core decision (#1222). Its shortfall was forced, since the core records it meets conflict. This one is chosen, for the costs weighed above: a core record could be proposed now. Since the form recurs, whether COR-025 should say how a project holds such a placement while the core decision waits is weighed in #3009 too (COR-007).

### Alternatives considered

- **A capability for the host,** shipping its bootstrap and a page on running there. Rejected: a host is no discipline (point 1).
- **A variant inside the Claude Code adapter,** deploying other files on the host's machines. Rejected: a host's identity or a property must choose it, and committed it changes with each sync ("Why no deployed variant").
- **An adapter for each host.** Rejected: the harness's adapter already translates the methodology content a host's sessions read, and two adapters of one harness would write the same project files.
- **A grade for each host in the harness support declarations.** Rejected: an answer is a harness's (COR-047 point 2), and a cost that names the property already says what a host may take away.
- **Recognise the host by name and branch on it.** Rejected: it ties pkit to a foreign name, and misses every other host with the same property (point 2).
- **Read a value only one host provides, under a label naming that host,** as pkit reads the harness's values under the harness's label. Rejected: the harness's label lives in the adapter pkit keeps for that harness, so another harness changes a lookup pkit already owns. A host's label needs a lookup kept for a product pkit has no component for, which is a component for a host in all but name (point 1), and a second host with the same property is missed until its label is added. Where many parties set one standard signal, pkit reads it (point 5).
- **Count every bridge made for a harness with that harness,** and read its own values, such as the names of its file tools, in the harness's adapter. Rejected: a bridge from another maker changes on its maker's releases, not the harness's, so the adapter would keep a lookup for a product pkit keeps no component for, the risk point 2 names. What its protocol defines, many parties set, and pkit reads it (point 5).
- **Support for one host in pkit, labelled and provisional,** as the backbone carries one hosting service. Rejected: the backbone needs the hosting service to land its own release, so its support could not wait for a second one (ADR-061 point 3). Nothing pkit does needs a host, and a host's setup runs before pkit, so it can live outside.
- **A host's setup kept in project-kit's repository for every adopter,** though it ships nowhere. Rejected: the setup changes on the host's releases, not pkit's. Kept here for every adopter, its upkeep and its breakage would be pkit's, a component for a host in all but shipping. project-kit's setup for its own project is its own project's files, as any adopter's is (point 7).
- **The session-start hook installs pkit under a host.** Rejected: the hook ships to every adopter on its harness, so it would carry one host's setup to all of them ("Why setup goes to the host").
- **A question of its own, "can pkit stop depending on it?", before the requirement.** Folded into the first question: to stop depending is itself a change right on every machine, and a question of its own would split one outcome in two.
- **A core record now, of the general rules.** Not taken, for now: adopters would need them, but they were drawn from one host, and a core record would put a term shaped by one product in every project. Held here, they reach no adopter as rules meanwhile, a cost the open work in #3009 carries ("Why an ADR, for now").
- **A narrower core record now, of the three lines without the term,** written of whatever starts or surrounds the harness. Not taken: so written, the line that nothing shipped tests which host it runs under takes in the operating system, whose name pkit reads as a fact of the machine, and the record leaves out point 4's test ("Why an ADR, for now").

## Implications

- **No accepted record is edited.** This record applies COR-005, COR-017, COR-027, COR-047 and COR-070 to a case none of them names. For what project-kit ships, it adds three lines none of them draws, and changes nothing any of them decides. Nor does it change what COR-025 decides: COR-025's scope test places the general rules in a core record, and holding them here is a shortfall from that test, recorded as open work in #3009 (COR-065 point 4; "Why an ADR, for now"). It supersedes nothing.
- **The investigation's gaps, placed by point 4:**
  - **Where pkit keeps what a host needs** (gap 6) is answered here.
  - **The session agent's tools** (gap 1) were mended for every machine ([project-management:DEC-068-session-agent-tools]).
  - **Writes outside the repository** (gap 2) go to the first question, by either of the investigation's ways. One is a narrower ask, right on every machine. The other is a list of folders where a write does not ask, a project setting whose default serves every machine. Where those folders differ from machine to machine, the list is kept per machine instead, a property by the second question. The trial on a live host (#3004) shows whether any is needed.
  - **The strict posture** (gap 3) holds two needs. The tools of a server whose name is known in advance, such as one present only while a step is pending, fall to the first question: a grant that matches a server's tools by a prefix would serve them on every machine. It changes the permission model, so it needs a record of its own, and until one is accepted and built they share the limit below. Servers whose names a project cannot know in advance, such as those a machine's owner adds, no prefix covers short of one that matches every server's tools, which is the lenient posture for them. They stay a limit, accepted below.
  - **Installing pkit on a fresh machine** (gap 4) splits. How the pkit command fetches its own releases is #3002's to decide. A shallow clone is a property pkit reads, and where its history falls short pkit says so rather than answer (ADR-081 point 6). Deepening the clone, wherever a setup cloned shallow, the folder on the path and the moment of the install are the setup's (point 7), since pkit deepens no clone itself. A record that made pkit deepen one would move that need to the second question (point 4).
  - **Who may authorise in a turn a chat started** (gap 5) holds two needs. *Who may authorise* is a project setting, the same on every clone, so the first question places it if its default serves every machine, as that question asks of any setting. Its values and its default are its own record's to decide, before it is built ([COR-065](../../../.pkit/decisions/core/COR-065-records-and-projection.md) point 3), and this record states neither. *Naming the senders whose word authorises* reads each turn's sender, a property by the second question. By point 5, pkit reads the sender only where the harness carries it into the session, or a standard signal many parties set carries it. Under a bridge, a sender field the bridge's protocol defines is such a signal, where the bridge carries it into the session apart from the message's words. pkit never reads the sender from a value only one host provides, a key the host writes in a field the protocol leaves open among them, nor from a message's words, which any message can imitate.
  - **The requirement that an ask reaches a person** meets COR-047 point 9's bar already, since the adapter's permission hook asks the person where a guardrail may hide ([ADR-025](ADR-025-segment-conservative-bash-allow.md) point 7). The change that declares it follows the trial on a live host (#3004), so its wording and the adapter's cost rest on what a host was seen to do.
- **The investigation's rubs that neither a gap nor a limit holds, placed by point 4:**
  - **Where the repository is put,** cloned into a folder below where the host starts its sessions (rub 1) or seeded into the home folder (rub 6), is the setup's (point 7).
  - **A sandbox turned on where the machine cannot provide one** (rub 3). The sandbox is a setting kept per machine ([ADR-032](ADR-032-per-machine-activation-routing-axis.md)), off on a fresh clone, so turning it on is that machine's own step (point 7), and the adapter's cost already names the sandbox the operating system provides (point 6).
  - **A model named for the session agent** (rub 10). A model a project names for an agent in its overlay is a project setting, the same on every clone. Its default names none, which serves every machine, so the first question finds nothing to change. Named for the session agent, it becomes each session's model on every machine, a host's included, where the machine may not serve it, and that is the project's choice. A machine's setting that forces one model on the agents a session starts outranks those a project names, and pkit depends on no particular model, so that costs only the project's choice.
  - **A bridge's own file tools** (rub 16) fall to the third question by point 3, if the trial on a live host (#3004) finds the bridge still puts them in place of the harness's. Whether an allow in the project's settings passes over the check the harness makes in its automatic mode (rub 15) waits on that trial too, and is placed once it is known.
- **This narrows the maintainer's ruling on gap 5, and accepting this record accepts the narrowing.** The ruling, in the investigation, opens the narrower setting once a host names each turn's sender. Under this record, a host that names the sender only its own way, such as through a tool of its own or a key of its own in a field a bridge's protocol leaves open, does not open it. A host opens it by handing the sender to the harness, which carries it into the session, or through a standard signal other hosts can set too, a field the bridge's protocol defines among them. Under DAM, which drives the harness through such a bridge, the setting therefore opens once the harness or that protocol carries the sender, and not through a key of DAM's own. To reject the narrowing is to let pkit read a value one host provides, which points 2 and 5 would then have to name as an exception.
- **The limits accepted with this record,** each stated by its property, with what meeting it would cost (point 4):
  - sessions that share one checkout, where pkit's seats and worktrees take each clone to have one owner at a time. Meeting it would redesign how seats and worktrees own a clone, for a layout found on one host;
  - a nested run on a machine that suspends what the harness did not start, which ends when the machine suspends. The one way the investigation found to keep such a run is one host's own command, which pkit may not depend on (point 2), and which a person or the host's setup may use;
  - a project that keeps pkit's files out of version control, whose fresh clone brings none of them. Meeting it would undo the project's own choice;
  - a project some of whose sessions run with nobody present to grant a tool at its first denial, and use tools whose names the project cannot know in advance. It keeps the lenient posture, and does so on every clone, since the posture is the project's. A grant that covered such tools would be that posture (gap 3).
- **Two of the investigation's limits are not limits under this record:**
  - **Another repository cloned inside a project's checkout,** which a commit of the whole tree takes in. A builder that commits only the paths its change touched keeps it out on every machine, so the first question places it, as a follow-up for the builder the software-engineering capability ships. That a session changes the other repository only once a person confirms it is COR-039's rule on every machine.
  - **A machine with no key to sign commits.** pkit requires no signed commits. A project whose own rules require them, as project-kit's do, places a key on its machines by its own setup, if it chooses to (point 7).
- **Keeping a host's setup working is its maker's.** pkit offers it what it offers every adopter: a public surface whose changes are declared ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md)) and, where they break, migrated ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md)), and a report, when asked, of the requirements its harness leaves unmet (COR-047 point 8). Who writes and keeps up a host's setup, and whether anything tests pkit on a live host, this record leaves open.
- **A DAM Starter Kit,** if one is made, is written in a repository of its own. Making it changes another repository, which a person confirms first ([COR-039](../../../.pkit/decisions/core/COR-039-session-repo-mutation-boundary.md)).
- **The core decision is the maintainer's, in #3009,** as ADR-061's is in #1222: whether the core records say where an agent host's needs belong. It falls due at whichever comes first: a second host's setup for pkit, written by project-kit or brought to project-kit's tracker, which point 8 waits for; or a question in that tracker, from an adopter authoring an adapter or a capability, on where a host's needs go. Nothing else bounds it: the maintainer may take it up sooner, and until it is decided the shortfall stays open, which #3009 shows. The shortfall closes in one of two ways, and a core record refused only for its wording or its term is neither:
  - **A core record holding the general rules is accepted.** This record is then refined to rest on it: its text of those rules narrows to how project-kit applies them, and cites the core record.
  - **This record stops holding a rule COR-025's scope test places in a core record.** #3009's decision says why each general rule stays out of the core records. This record is then refined to cut each rule found wrong, and to narrow the rest to what project-kit's own components do.
- **No changeset and no migration.** Nothing it decides changes a surface. One document follows its acceptance: pkit's page on running with nobody at the terminal (point 7), which states the limits above, and that pkit keys nothing to a host, and why.
