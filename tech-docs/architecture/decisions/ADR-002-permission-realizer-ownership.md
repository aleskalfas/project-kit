## Context

[COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) establishes permissions as a harness-neutral model the methodology owns, realized into each harness's native enforcement by that harness's adapter. The design that produced it was settled across ten rounds in the `2026-05-29-permission-meta-model.md` scratchpad note (Q1–Q10). COR-028 is harness-neutral by construction and deliberately defers the concrete realization to adapter documentation. This ADR records the *architecturally-significant boundary change* that the first realizer — the claude-code adapter — forces, named in COR-028's own implications as ADR-worthy.

The problem is one of file ownership. The claude-code realizer enforces the model through four layers, two of which write adopter-owned files: agent frontmatter (`.claude/agents/<name>.md`), a PreToolUse hook, and `.claude/settings.json`. The settings file is the sharp case. It is adopter-owned: the adopter hand-edits it, the harness reads exactly that one file, and the no-shared-files invariant (every file has exactly one owner) has held it as a whole-file project-owned artifact reached only through COR-002's append-only merge. To let the model become the truth — so that `apply` can *heal* drift, removing realized rules the model no longer declares — the realizer must own and regenerate a *portion* of that file while leaving the rest under the adopter's hand. COR-002's whole-file ownership model has no vocabulary for "one owner for part of a file, another owner for the rest."

Two distinct ownership scopes result, and conflating them would mis-place the boundary:

- The **PreToolUse hook file** is *always* realizer-owned, in every mode. It reads the model live at decision time, so it carries no stale state and there is no adopter content to preserve within it — it is an ordinary propagated, pkit-owned artifact.
- The **`permissions` region of `settings.json`** is owned by the realizer *only in managed mode*, and shared at finer-than-file granularity even then: the region is realizer-owned, the rest of the file stays adopter-owned.

The proposed status is the acceptance-gate gesture per [PRJ-005](../../../.pkit/decisions/project/PRJ-005-adopt-adrs.md); COR-028 (the principle) is already accepted, and this ADR records how its first realizer lands against project-kit's own ownership invariants. Because this is project-kit's own architecture-decision record, harness specifics are in scope here — unlike the harness-neutral COR.

## Decision

The claude-code realizer partitions ownership *within* `.claude/settings.json` rather than at the whole-file boundary, and splits the two ownership scopes cleanly.

**1. Intra-file ownership partition.** In **managed** mode the realizer owns an *authoritative region* of `settings.json` — the `permissions` block — and regenerates it **wholesale** on each `apply`: the prior region content is replaced, not unioned. The region holds the full session-wide allow set the additive path produces — the native baseline ∪ the deploy-time `Skill(...)` grants ∪ capability-overlay allows ∪ the model's projected allows — plus the guardrail denies, recomputed each run as the union of every merge source **except the live target** and **except per-machine-classified sources** ([ADR-032](ADR-032-per-machine-activation-routing-axis.md) Rule A: the active profile's grant layer projects to the per-machine `settings.local.json` even under managed mode, per [ADR-046](ADR-046-profile-realizer-output-routing.md)). Everything outside the region remains adopter-owned and is never touched. This is exactly one owner per region — the realizer for its region, the adopter for the rest — which preserves the no-shared-files invariant at finer-than-file granularity. Because the region is replaced wholesale, healing drift is the natural behaviour (rules no longer in any merge source simply do not reappear, and a grant hand-added to the live settings is not an input, so it does not survive) and a composition that emits nothing regenerates an empty region on the next run, with no stale-content reconciliation and no in-file markers. "Vanish" here is precise: while the project is in managed mode the region is *unconditionally regenerated from the current composition every run*, so a region whose composition emits nothing heals to empty — the realizer never recovers or subtracts "what it previously owned," it always rewrites a region computed from scratch. This is distinct from turning managed mode *off* (managed→additive), which is a separate mode change governed by additive's "only adds" contract, not by this tier; and distinct from uninstalling the realizer entirely, an uninstall-path concern. The strip-free property is a property of *regenerate-from-scratch within managed state*, not of source removal.

In **additive** mode (the default) the realizer only *adds* to `settings.json` through COR-002's existing append/union merge — guardrail denies plus the hook registration — and never removes or replaces. No region is owned; the file stays whole-file adopter-owned exactly as today. *(Scope qualification per [ADR-046](ADR-046-profile-realizer-output-routing.md): the never-removes contract governs the committed `settings.json`. Profile-derived realizer output routes to the per-machine `settings.local.json`, where `apply` holds provenance-scoped recompute-replace authority over its own ledgered entries only — the sole subtractive path, and never in this file.)*

**2. The hook/region boundary.** The PreToolUse hook file is realizer-owned in *both* modes — it is the live authority that reads the model at decision time, so it is always current and always pkit-managed, independent of how much of `settings.json` the realizer touches. The mode gates only the `settings.json` `permissions` region. The hook is registered through the top-level `hooks` key, which merges normally and is not part of the owned region, and registration is **opt-in**: the hook *script* is a propagated adapter file whose lifecycle `pkit sync` owns, but the PreToolUse hook is registered only when the adopter runs `pkit permissions enable` (and stripped by `pkit permissions disable`), never automatically — enforcement is the adopter's explicit, separately reversible choice, mirroring [DEC-030](../../../.pkit/capabilities/project-management/decisions/DEC-030-capability-contributed-adapter-overlays.md)'s default-agent toggle. This separation is load-bearing: the always-owned hook lets the default (`additive`) mode rely on a live authority without owning any region of the adopter's settings, so adopting the model is non-destructive while still enforcing the nuanced per-agent and per-directory rules.

**3. Fail-open / double-lock.** The hook fails *open* — on error, timeout, or malformed payload the call proceeds. Therefore non-negotiable denies (`sudo`, `rm -rf`, `git push --force`) are realized on **both** layers: the fail-open hook *and* the fail-closed native `settings.json` deny. The nuanced, evolving rules ride the hook (where fail-open is tolerable); the catastrophic denies are double-locked, so a hook bug, timeout, or version skew can never bypass them. The native deny stands on its own regardless of the hook's health.

**4. Two fault classes: a decision fault fails open, an enforcement-runtime fault fails loud.** Point 3's fail-open contract covers the *decision fault*: the hook ran, reached `decide()`, and hit an ambiguous, malformed or timeout case it cannot resolve, so it abstains — with the native double-locked denies standing regardless. The *enforcement-runtime fault* is a different class: the hook — a script with a runtime and dependencies — cannot start at all, so the entire intent model stops being consulted. That class **fails loud**: it is a diagnosed, surfaced state, so the operator learns that enforcement is not running rather than believing a dead hook is gating their calls. Every realizer of the [COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) model MUST keep the two classes apart, so a second adapter does not conflate them.

**5. Deny-wins composition.** Where an allow and a deny conflict — across the baseline-for-all and per-agent grants, or across layers — deny prevails. This is the model's composition rule (per COR-028) and it realizes cleanly because it matches Claude Code's own precedence: a hook `deny` overrides a settings `allow`, and a hook `allow` cannot override a settings `deny`. The double-lock above is the same rule read from the failure direction.

## Rationale

The partition is the only ownership stance that lets the model heal drift in `settings.json` without violating no-shared-files. The whole-file alternatives all fail:

- **Markers in the file** to delimit the realizer's content. Rejected for the same reason COR-002 rejected markers for fixed-path content: the no-shared-files invariant forbids two owners sharing a file mediated by in-file delimiters. Wholesale region replacement achieves the same "realizer owns this content" outcome without markers — the region is defined by its key (`permissions`), not by sentinels the adopter could disturb.
- **A separate realizer-owned file pulled in via include.** Rejected because the harness reads exactly one `settings.json`; there is no include mechanism to split a generated region into a sibling file the adopter also owns. (This is the same constraint COR-002 cites for why merge exists at all.)
- **Full-file generation** (the realizer owns all of `settings.json`). Rejected because it destroys adopter sovereignty over a file the adopter legitimately hand-edits — every adopter customisation outside permissions would be lost on `apply`. The partition confines realizer ownership to exactly the region the model is authoritative over.

**Why additive is the default and managed is opt-in.** Additive rides COR-002's existing append/union merge and owns no region, so introducing the realizer into an installed adopter removes nothing and changes nothing the adopter relied on — adoption is non-destructive, and the always-owned hook still provides the live authority. Managed mode is the stronger promise ("I never hand-edit settings; the model is the whole truth") and the one that requires the new ownership tier; it is therefore opt-in, chosen per project. Defaulting to managed would silently take ownership of a region of a file the adopter has been hand-editing — exactly the sovereignty loss the partition exists to bound.

**Why the managed region subsumes the additive baseline — the silent-deletion footgun.** A region holding only the model's projection plus the guardrail denies cannot reproduce the native baseline at the model's current fidelity: the catalog has no `Skill` privilege and no `Write`/`Edit`/`jq`/`ssh`/`mv`/`cp`/… privilege at all, and the deploy-time skill grants are computed in the merge primitive (`merge-settings.sh`), not in `project()`. Flipping an adopter to managed mode would then wholesale-delete the working-developer baseline (`gh`/`git`/`Read`/`Write`/`Skill(...)`/…) from native settings, leave the fail-**open** hook as the sole live authority for everything the model does not project, and silently revoke skill trust the adopter never asked to lose — contradicting the deploy-is-the-trust-signal principle the additive path depends on. Wholesale replacement at insufficient fidelity deletes content the adopter relies on; that is the silent-deletion footgun, and composing the region from everything the additive path provides is what keeps managed mode clear of it.

**Why excluding the live target is not strip-logic.** The managed composition differs from additive in exactly one input: additive unions the live target in, managed drops it — which is what makes drift heal. There is still no read-back-and-subtract of a previously-owned region and no per-source key attribution; the region is recomputed from scratch every run, so the strip-free property below holds. Per-machine-classified sources stay out of the committed union because wholesale regeneration would otherwise re-commit activation-derived rules on every run, reintroducing in a worse form the gap ADR-046 closes.

**Why the two fault classes are kept apart.** A blanket `except` catches both identically and silently abstains, which is right for one and wrong for the other. A decision fault leaves the double-lock standing, so abstaining is tolerable. A hook that cannot start stops the whole intent model while the operator believes enforcement is live — a boundary believed to hold that does not. Separating "the hook chose not to decide" from "the hook could not run at all" keeps point 3's decision-time fail-open contract and its double-lock intact while refusing to hide a dead enforcer.

## Implications

- **COR-002 authoritative-region tier is a hard dependency of managed mode.** The wholesale-replace region behaviour above is the *authoritative-region* delivery tier added to COR-002 by COR-028's refinement; this ADR's managed mode is its first concrete consumer. The additive default rides COR-002's pre-existing append behaviour unchanged and depends on no new tier.
- **DEC-030's strip-logic dissolves under managed mode.** [project-management:DEC-030](../../../.pkit/capabilities/project-management/decisions/DEC-030-capability-contributed-adapter-overlays.md) carried explicit `disable` strip-logic to remove a capability overlay's contributed keys, because the append-only merge could not distinguish a stale source contribution from a manual adopter edit. For the `permissions` region under a managed realizer that problem does not arise: while in managed mode the region is regenerated wholesale from its current composition (point 1) every run, so a composition that emits nothing heals the region to empty on the next `apply` — no strip-logic, no per-source attribution, no markers. This is strip-free precisely because the realizer never reads-back-and-subtracts a previously-owned region; it rewrites a region computed from scratch each run. (It is therefore *not* structurally identical to DEC-030's `disable` strip-logic, which operates on survivor top-level keys the merge primitive carries forward — `permissions` is not a survivor key in the merge, it is recomputed from scratch every run, so no key-subtraction step exists or is needed. The managed composition recomputes the region as the additive union of all merge sources *excluding the live target and excluding per-machine-classified sources* (point 1) — dropping the live target from the inputs is what heals drift, and it remains strip-free in the sense above: still no read-back-and-subtract of a previously-owned region, still no per-source key attribution. The mechanism is "regenerate this whole region from its composition," at the granularity of the single `permissions` top-level key.) Stopping ownership of the region — managed→additive — is a separate mode change, not this heal; uninstalling the realizer is an uninstall-path concern where the same lingering-key reality DEC-030 documents applies. DEC-030 already defers its reserved-`permissions`-key rule to COR-028 as the sanctioned owner of that region; the additive default contributes nothing to `permissions` beyond the baseline denies and skill grants DEC-030 already permits, so that rule stands unchanged for the default and for any adopter not running a managed realizer.
- **Introducing the realizer is a pure addition; COR-010 mandates no migration.** Because hook registration is opt-in (point 2), nothing is auto-registered and nothing in `settings.json` changes until the adopter runs `pkit permissions enable`; `pkit migrations check-diff` reports COVERED with no migration script. The project is in `additive` mode by default. With an empty model the hook abstains on unmodeled commands in lenient mode, deferring to the harness's normal flow, so enabling it with an empty model is a behavioural no-op. The `enable` / `disable` gestures are idempotent (re-running detects the state already in place and exits clean). The realizer does **not** auto-import existing grants into the model, which would launder possibly-over-broad live grants as declared intent; `import` remains an explicit, reviewed bootstrap path.
- **Managed mode is settled on paper and built on demand.** `apply` refuses managed mode with a "not yet implemented (#252)" error; additive is the shipped non-destructive default, and neither near-term adopter (`example-brownfield`, `example-greenfield`) needs wholesale ownership, so no code lands until a concrete adopter needs managed mode. Point 1 fixes the composition now so that whoever builds it cannot relitigate it into the silent-deletion footgun. The build MUST: (a) compose the region per point 1; (b) implement it in `merge-settings.sh` (or its COR-004 successor merge runtime) — the managed branch unions baseline ∪ skill grants ∪ overlay allows ∪ `project()` allows, excluding the live target and per-machine-classified sources, rather than swapping in the bare projection; (c) re-run `pkit migrations check-diff`, since the merge-primitive change is a surface change and may itself require a migration; (d) ship the heal and idempotency tests #252 names.
- **An enforcement-runtime fault is caught by a startup self-check.** `pkit permissions enable` and `pkit permissions sandbox enable` drive the hook script with a probe payload after registering it, and `pkit permissions overview` runs the same check, so a hook registered but dead on arrival is reported loudly rather than left to abstain on every call. The OS box has the same fault shape one layer down: Claude Code continues unconfined when the sandbox cannot initialise unless `failIfUnavailable: true` is set, so a box reported ON can be running unconfined. `sandbox enable` therefore sets `failIfUnavailable` and verifies *actual* confinement with a probe write that must be denied, not merely that the config reads ON. That layer is governed by [ADR-004](ADR-004-autonomy-intent-confinement.md) (the intent/confinement split) and [ADR-014](ADR-014-macos-sandbox-platform-stance.md) (the `failIfUnavailable` finding, evidence 6); this record governs the hook's fault classes, the intent half.
- **The concrete realization lives in the claude-code adapter docs, authored with the implementation.** Which model dimension each of the four layers carries (tool on/off → frontmatter; coarse session-wide allow + guardrail deny + domain rules → native settings; per-agent / per-directory / conditional → hook; unenforceable intent → out-of-harness report), the routing rule that picks the most-native faithful layer, the hook's abstain contract in lenient versus strict posture, and the per-adapter enforcement-capability declaration are adapter-documentation concerns, not this ADR's. This ADR fixes only the ownership boundary; the realization detail follows the implementation.
