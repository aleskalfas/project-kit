## Summary

COR-044 ships a core `process-author` agent that edits process definitions and predicate scripts living in adopter capability subtrees core cannot enumerate — and deferred the frontmatter question to an architecture record. This is that record. The mechanism reuses the existing overlay rather than inventing an ownership tier: **a new overlay category, `process-authoring-targets`, that the adopter populates with file-granular paths to their own definition files and predicate-script locations; the core agent's `owns:` carries only the category placeholder; the category ships as an explicit empty list, so the agent deploys owning nothing until the adopter opts in.** The safety constraint is file-granular and matches COR-044's own phrasing: **no path in the category may be sync-managed** — the no-shared-files invariant applied at the agent surface. Capability origin (COR-031) serves as the common-case mechanical test. Enforcement starts where overlay resolution already runs (deploy time); the reference-graph extension is scoped implementation work this record names honestly rather than claims as existing.

## Context

COR-044's owner-scoping has two layers: a *mechanical* layer (the agent edits only adopter-authored definitions and predicate scripts, never sync-managed ones) and a *discipline* layer (single definition per invocation — body discipline, not static metadata). The mechanical layer needs a frontmatter realization. The working precedent is the architect agent: core-shipped, `owns:` carrying overlay-resolved category placeholders, resolved by the deploy primitive's existing placeholder expansion — that half of the machinery exists today and is verified.

Two pieces of machinery this record *depends on* do **not** exist today, and the record scopes them as implementation rather than asserting them: the reference-graph check currently drops pattern-shaped `owns:` entries instead of resolving them (so it validates the placeholder, not the paths — drift against COR-013 rule 5's accepted "the bidirectional consistency check operates on resolved paths, not placeholders", which makes the build-out owed by an accepted core record independently of this one), and no ownership-overlap check walks `owns:` at all — the agents contract *documents* exactly-one-owner as the intended invariant, but nothing enforces it yet. The design below is written to be safe with today's machinery (deploy-time enforcement) and to define what the validator build-out must add.

What is new relative to the architect precedent: the target paths are plural and adopter-shaped (any number of capability subtrees, at file granularity), they contain *executable* artifacts (predicate scripts the engine later evaluates fail-closed), and other agents legitimately hold authority nearby (capability-shipped agents over their own subtrees; adopter agents over incubated ones).

## Decision

**The core `process-author` agent's `owns:` declares exactly one entry: the `<process-authoring-targets>` overlay category — an adopter-populated, file-granular list of the adopter's own process-definition files and predicate-script locations, shipped as an explicit empty list and constrained to non-sync-managed paths.**

1. **Empty-by-default, in the explicit form.** The overlay template ships `process-authoring-targets: []` — the explicit empty list, which resolves to an empty `owns:` and a deployed-but-inert agent. This form matters mechanically: a *bare* or *absent* key does not resolve, and the deploy primitive then skips the agent entirely. Fresh installs get the `[]` template; **existing adopters upgrade into the skip state** (sync cannot add keys to the project-owned overlay) and bring the agent up by adding the key — safe-by-default in both states, with the upgrade note carrying the one-line remediation. The overlay entry is the opt-in gesture: the metadata twin of COR-044's "the agent packages the authority the owner already exercises by hand."

2. **The constraint is "not sync-managed", file-granular.** No path in the category may resolve inside sync-managed content — the no-shared-files invariant applied at the agent surface, which is COR-044's mechanical layer verbatim. Capability origin (COR-031: `kit-shipped` vs `incubated-in-repo`) is the **common-case implementation** of the test, not its definition — which decides the edge instances correctly: adopter-owned `project/` content inside a kit-shipped capability is admissible (adopter-owned by tier, never sync-overwritten); a just-authored, not-yet-registered capability subtree is admissible (nothing sync-manages it); adopter territory *outside* any capability is mechanically admissible (core areas outside capabilities remain sync-managed and excluded like any other), though the substrate itself makes a non-capability path useless as a definition home (COR-033 addresses definitions as capability instances — the constraint does not need to re-forbid what the substrate already excludes).

3. **Enforcement lives where resolution lives — deploy time now, the reference-graph check as it learns resolution.** The sync-managed check runs at the deploy primitive's resolver, which is the one place overlay resolution exists today: a category entry into sync-managed content fails resolution loudly at deploy, before any session runs the agent. The **predicate itself is implemented once, in the lifecycle layer, and consumed by adapter resolvers** — sync-managed-ness requires the tier-ownership map (kit-shipped subtrees minus their `project/` carve-outs, core areas, install-state origin), and a per-adapter re-derivation would fork the ownership predicate and silently skip the check on future harnesses (design-once, the same shape as the health-walker rule, COR-042 point 5). The reference-graph build-out — resolving `owns:` placeholders, then enforcing exactly-one-owner over resolved paths — is **its own tracked task**, not a rider on the agent task: it realizes accepted COR-013 rule 5 corpus-wide and can surface pre-existing overlaps in any adopter install. This record pins its semantics: an `owns:` entry resolving to zero paths is *clean* (fresh installs must not fail CI by design); an entry whose category is **absent** from the overlay is likewise *clean* in validation — the deploy skip already surfaces it loudly, and an upgraded-not-yet-remediated install must not fail CI; **overlap = path-prefix containment across distinct agents' resolved sets**; overlaps are flagged, never arbitrated.

4. **Collision with kit-shipped capabilities' agents cannot arise; adopter-territory overlap is a real conflict, flagged not arbitrated.** A *kit-shipped* capability's subtree is sync-managed and can never appear in the category. An *incubated* capability's agents are the adopter's own — their paths may legitimately neighbour or overlap the category, and that (like any adopter agent owning paths the adopter also listed) is a genuine conflict: the overlap check (once resolution lands) flags it and the adopter resolves it in the overlay. No precedence rule is introduced; exactly-one-owner stays absolute.

5. **File-granular entries, not subtree grants — and `package.yaml` is out.** The category convention is definition files and predicate-script directories, not whole capability subtrees. Predicate **registration** in the owning capability's package is *stamp territory*: the deterministic scaffold/mutation commands write registration entries (COR-044's skill/command-pairing implication — "the command owns the stamp"), and when the agent needs a new predicate registered outside a scaffold, it routes through those commands — the same routing posture COR-044 sets for shape problems, extended here to registration — so the category never needs to include `package.yaml`, and the agent never edits it directly.

6. **The mechanical layer is a validation-time guarantee, an honest interlock at runtime.** Resolved `owns:` is methodology metadata, not a harness permission; nothing at runtime physically blocks an edit outside it. Both layers of COR-044's owner-scoping therefore share the COR-039 posture: the origin/sync-managed constraint is enforced at deploy/validation time and honoured as discipline at runtime; the single-target constraint stays body discipline outright. No runtime lease machinery is built.

7. **Core-introduced write-carrying categories are single-consumer by convention.** `process-authoring-targets` is referenced by exactly the agent this record names; a future *core* agent citing a write-carrying category a record it doesn't belong to introduced is a review-time red flag, recorded here so the reviewer stack has something to point at. The convention is deliberately scoped to categories a core record introduces — adopter-defined categories stay the adopter's to share across their own agents (top-level categories are shared by design; per-agent overrides replace a category's resolution for one agent), policed by the overlap check alone.

## Rationale

**Why an overlay category rather than a new mechanism.** The problem — core ships an agent whose write targets only the adopter can name — is the problem the overlay already solved for the architect agent's record paths, and deploy-side `owns:` placeholder resolution already exists. Reusing it is COR-007 pattern-extraction; a bespoke ownership tier would add a second vocabulary for write authority and force every future check to learn both.

**Why "not sync-managed" rather than "incubated origin".** The invariant being realized is file-granular (never edit what sync overwrites); capability origin is capability-granular and mis-decides real instances at the boundary — adopter content inside kit-shipped capabilities, the bootstrap window before an authored capability is registered. Defining the constraint by the invariant and using origin as the common-case test decides every traced instance correctly instead of patching them case by case.

**Why empty-by-default rather than a sensible guess.** Core guessing at adopter layouts (globbing capability schema directories) would grant authority over paths the adopter never nominated, make the answer depend on install state rather than declared intent, and collide with sync-managed trees before any check runs. An explicit empty list costs one overlay edit at first use and keeps the entire authority grant auditable in one project-owned file.

**Why enforcement starts at deploy time.** The deploy resolver is where resolution exists today, so the constraint bites immediately with no new mechanism; a misconfigured overlay fails at `pkit sync`, earlier and cheaper than any runtime refusal. The reference-graph extension is still owed — validation should not depend on an adopter running deploy — but claiming it as existing would repeat the spec/implementation drift this record instead names.

### Alternatives considered

- **Glob-based `owns:` over capability subtrees** — rejected: grants authority over paths the adopter never nominated, including sync-managed trees; the grant stops being declared intent auditable in one file.
- **A new ownership tier / per-invocation lease machinery** — rejected: per-invocation scoping is COR-044's discipline layer by design; runtime machinery for it contradicts the honest-interlock posture and adds a permanent mechanism for a body-discipline problem.
- **Per-capability registration** (each adopter capability's package nominates the agent) — rejected: spreads the grant across N files and makes `owns:` resolution walk install state; the overlay keeps it in the single file the agents contract already reads.
- **Advisory-only constraint** (document, don't validate) — rejected: the mechanical layer exists to be checked; vigilance is the failure mode, per the corpus's repeated experience.
- **Origin-as-definition** (constraint defined as incubated-in-repo origin) — rejected per the Rationale: right common case, wrong boundary instances.

## Implications

- The overlay template and agents reference documentation gain `process-authoring-targets: []` (explicit empty list) with the file-granularity convention and the single-consumer note; upgrade notes carry the existing-adopter remediation (add the key; agent is skipped until then — safe state, loud at deploy, no migration owed since absent-key-skip changes no existing behaviour, with `pkit migrations check-diff` gating the implementing diff regardless). Fresh installs deploy inert; upgraded installs skip until the key is added — both safe, the asymmetry stated in the upgrade note.
- The remediation surfaces the deploy skip advertises must be adjusted for this category: the adopt path cannot serve it (no conventional default exists for paths core cannot enumerate), and the reconcile stub flow should fill `process-authoring-targets: []` uncommented as the safe default, restoring fresh-install parity.
- The deploy primitive's resolver gains the sync-managed rejection for this category's entries — additive, shipped with the agent task; the sync-managed predicate is implemented once in the lifecycle layer and consumed by resolvers (Decision point 3).
- The reference-graph check's `owns:` resolution + exactly-one-owner overlap enforcement (prefix-containment semantics, empty-resolution clean) is **filed as its own task (#699)**, owed by COR-013 rule 5 corpus-wide and independent of this layer's deliverables; the agents README's present-tense "flags overlaps" claim is corrected in whichever change-set lands first, so the area spec stops overstating.
- **Acceptance-scope note:** accepting this record pins the validator semantics above for *every* agent, not just process-author — a realization of accepted COR-013 text, but with corpus-wide blast radius the accepter signs off on knowingly.
- The `process-author` agent declares `owns: [<process-authoring-targets>]` and nothing else; its body carries the single-target discipline, the route-registration-through-commands rule, and cites this record.
- Acceptance sequencing per COR-025: this record must be **accepted before** the agent's frontmatter cites it (the companion-record precedent — acceptance follows COR-044's, never precedes it).
- Versioning: the category, resolver rule, and validator work are adopter-observable surface when they ship with the implementing tasks; changesets ride those changes, not this record (PRJ-002).
