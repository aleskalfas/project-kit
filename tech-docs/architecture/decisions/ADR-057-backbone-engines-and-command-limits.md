## Summary

**In plain terms:** the machinery that keeps analysis and documentation true — artefact discovery and the friction checks, the wiring resolver of connection points, and the rule-set validator — ships inside the `pkit` tool, and each computation it performs has exactly one home that every reader calls. Commands a capability supplies for the backbone to *query* — a resolver for a new anchor kind, a filler for a data point — run under the query contract the core sets (COR-050 point 2): a time bound the backbone enforces, and three obligations the capability declares on the command — it needs no network, changes nothing in the project, and gives the same output for the same inputs. This record is how project-kit realises that contract: one constant declaration on the command's own registry entry, reported at validation when missing and refused before a run; a thirty-second bound over the whole tree of runs; an answer read failing closed; an offline marker; and a plain statement of what nothing here confines — no layer of this distribution stops a command from reaching the network, on any platform.

## Context

The core records of this milestone ask the backbone for engines: artefact discovery and friction ([COR-050](../../../.pkit/decisions/core/COR-050-anchors-and-friction.md)), the resolver of connection points ([COR-053](../../../.pkit/decisions/core/COR-053-connection-points.md), whose Implications ask that its placement be recorded "in the project's architecture decisions, as for the other resolvers"), and rule-set validation ([COR-051](../../../.pkit/decisions/core/COR-051-rule-sets.md)). The validators of the backbone file schemas are already placed ([ADR-056](ADR-056-backbone-file-schemas-home.md)). The process engine set the test for such engines: code ships in the binary unless something below the tool layer must import it ([ADR-020](ADR-020-process-engine-code-home.md)); the permission core is the counter-example that propagates because the hook imports it ([ADR-003](ADR-003-permission-core-code-home.md)).

The records also let capabilities supply commands the engines run. A resolver for an anchor kind (COR-050 point 2) and a command filler for a data point ([COR-052](../../../.pkit/decisions/core/COR-052-slots.md) point 6) are *queries*, and the core sets their contract. The backbone enforces a time bound and reads the answer failing closed. The command's capability declares on it that it needs no network, changes nothing in the project, and gives the same output for the same inputs. The backbone requires that declaration before it runs the command and reports a missing one at validation; it does not hold a running command to it — "a declared and trusted contract, not a boundary". A subscriber to an event (COR-053 point 9) is an *action* that writes. A runner of capability commands already exists: the process engine's predicate runner, which bounds and parses the predicates a capability registers — and those may reach the network, as the work tracker's gates reach its tracker.

The core leaves a project that needs a boundary to confine these commands where it runs them (COR-050 point 2). What this distribution offers for that is limited. Confinement is delegated to the harness's operating-system sandbox, which pkit manages but does not implement ([ADR-004](ADR-004-autonomy-intent-confinement.md)). Where that sandbox is on, it holds a whole session to one list of allowed hosts — every host any confinement toolkit opened — and is explicitly not a security boundary ([ADR-015](ADR-015-command-declared-network-egress.md)). On macOS the `pkit` and `uv` process tree runs outside the box, because `uv` cannot run inside it ([ADR-014](ADR-014-macos-sandbox-platform-stance.md), [ADR-027](ADR-027-required-sandbox-exclusion-auto-apply.md)). In a pipeline or a plain terminal there is no sandbox at all.

## Decision

1. **The engines ship in the binary.** Artefact discovery and its validation findings, the change check, the whole-repository check and the debt listing, the wiring resolver, and the rule-set validator are part of the `pkit` tool, alongside the validators ADR-056 places. Nothing below the tool layer imports them. Their consumers reach them as commands: people, agents, and the project's check aggregator and pipeline directly; capability scripts and migrations through the engines' machine-readable reading commands, never by importing the engine or re-walking the places themselves.

2. **One home per computation.** Where artefacts are and what they declare, how the wiring resolves, and how a version relation compares are each computed in exactly one module that every reader calls — the plans COR-053 promises are exact only because they run the live resolver. The homes:
   - **Which files the working tree holds** — one listing, `project_kit.working_tree`: the files git sees, tracked and untracked but not ignored. Validation — its configuration, friction, rule-set and data members — the friction writers and the change check's head all read it, so from one state of the repository they find the same artefacts and the same files. Where git gives no view of the working tree, no change check runs, and every file is listed; that is the one difference between the two listings, stated in the module and pinned by a test. A commit is listed from git's objects. A link is a file of any listing, never followed and never read as a document.
   - **Where artefacts and held documents are, and what artefacts declare** — artefact discovery, `project_kit.friction_discovery`: the settings, the places and the folders of held documents with their bounds, how a pattern matches a listing, and the reading of a file's text as artefacts, for the working tree and for history alike. The configuration pass judges the patterns discovery reads, by discovery's matching over the one listing.
   - **How the wiring resolves** — the resolver, `project_kit.connections`, resolved once per validate run. Container validation reads the active roles and point versions from it, and the configuration pass checks a provider or contributor selection against it — a contributor selection against the active provider's point and its contributors.
   - **How a version range compares** — the resolver's one relation (`range_admits`), which validation reports under its version relations and which the capability install and register gates, the capability upgrade's dependant check, the dependency check they share and the backbone upgrade's compatibility check all call, the upgrade reading a package file as the resolver reads it.

   - **How a data point resolves** — the second layer over the wiring, `project_kit.data_points`: the project filler, the contributions, the provider's default and command fillers combined by the point's policy, computed once per run — in a validate run, once across the reading commands its validators start too, through a cache the run keeps for its length (COR-052 point 6 lets the resolver keep a point's value for the length of a run), which records each resolution as its first asker made it and never one a command filler could not answer for want of the time that asker had left — and read by validation's `connections` member and by the status report (COR-052; the placement point 6 asked for).
   - **How the wiring is drawn** — one graph, `project_kit.wiring_graph`, built from the resolver and the process definitions: the process graph is its process-kind view through the same filters, so the two never disagree; each edge names its source (a definition's derived or annotated edge, or a resolved one) and how it stands (point 6's "source of each edge").

   - **What the default branch is, and what a comparison compares with** — `project_kit.default_branch` ([COR-054](../../../.pkit/decisions/core/COR-054-default-branch.md)): the declaration, read forgivingly; its resolution; and a comparison's base, with where HEAD left it and whether it moved on. The change check, the migration-coverage and changeset checks and the repository reading command call it, and every capability script reads it through that command. No other module resolves a base or computes a merge-base against it.

   The anchor-kind registry has one home too, which the friction checks and the rule-set validator both call.

3. **Query commands declare the query contract; the engine that runs one enforces the bound and reads the answer failing closed.** The contract is the core's: a time bound the backbone enforces, and three obligations the command's capability declares on it — it needs no network, changes nothing in the project, and gives the same output for the same inputs — a declaration the backbone requires before it runs the command and whose absence it reports at validation (COR-050 point 2 for a resolver, COR-052 point 6 for a filler). Here, a command a capability registers as an anchor-kind resolver or a data-point filler carries that declaration on its own entry in the capability's command registry, as one constant for the whole contract. The reference and the engines' messages name the contract's four limits *bounded, deterministic, read-only, needing no network*; read-only is their word for changing nothing in the project, so what a run keeps outside the project for its own length — the run's cache (point 2) — does not break it. The declaration grants nothing and writes nothing to the sandbox; egress stays on the confinement-toolkit path (ADR-015). Validation of package metadata reports a registered query command without it, when the author can still fix it; whichever engine runs one — the friction checks and rule-set validation for resolvers, data-point resolution (placed elsewhere) for fillers — refuses it, as the backstop. A query takes at most one positional subject: none for a filler, the anchor value for a resolver — as a process predicate takes its subject ([COR-052](../../../.pkit/decisions/core/COR-052-slots.md) point 6). When it runs one:
   - **time** is bounded by a fixed backbone constant, the same thirty seconds the predicate runner uses, and exceeding it kills the whole process group — a script with a `uv run --script` shebang starts its interpreter as a grandchild. A query run inside another run — a query that starts `pkit`, which runs a filler in turn — is bounded by the time its caller has left and killed with the outermost run's tree, by the shared runner's rule for nested runs (point 5);
   - **the answer** is parsed and validated against the shape of what was asked — for a resolver, the answer shape the backbone defines; for a filler, the point's schema its definer ships, inside the filler envelope ADR-056 places (COR-052 point 2); an abnormal exit, a timeout, or an unparsable or invalid answer is *no answer* — which is never an empty answer — and each caller applies its own record's rule to it: an anchor stays unresolved, a data point follows its inert policy;
   - **the environment** is marked offline, so a well-behaved command can tell.

   The literal of the declaration, the marker, the resolver's answer shape, and how a script's dependencies are made available before an offline run, belong to the reference and are specified with the first query command that runs: the declaration's literal, the marker and the provisioning are specified by [ADR-058](ADR-058-validator-registry.md), whose validators are the first query commands the backbone runs; the resolver's answer shape waits for the first resolver. No package key registers an anchor kind and its resolver, so for a resolver the report at validation and the refusal before a run have nothing to read — every kind outside the backbone's three is unresolved — and the key, the report and the run of a registered resolver arrive in one change, so a resolver is never registrable without the report (#1261).

4. **What nothing here confines, stated.** The three obligations are a declared and trusted contract, not a boundary, and a project that needs a boundary confines the commands where it runs them (COR-050 point 2). This distribution supplies no such boundary: no layer of it holds a single command to "no network". A sandbox, where one applies, admits every host the session allowed; on macOS the commands the engine starts run outside it; in a pipeline or a terminal nothing confines them. That a command changes nothing in the project and gives the same output for the same inputs is likewise declared, and judged in review. The engine's part — the report at validation, the refusal before a run, the time bound, the offline marker — is an honest interlock: the declaration is checked at validation and trusted at run time.

5. **Predicates stay on their own runner.** The process engine's predicates are not queries in this sense: they may reach the network, and the gate that reads them decides what their output means. They keep their runner and its policy. The runners should share one command lookup and one start, bound, capture and parse primitive — one mechanism with a policy per kind: query, predicate, the report builder's context read (a bounded read of one printed value, never a gate), and later subscriber (COR-053 point 11). That primitive is the backbone's command runner (one lookup of the `commands:` tree, one bounded run whose overrun kills the process group it runs in — its own, or inside another run the outermost run's — one parse), which the dispatcher, the predicate runner, package validation and the validator registry of [ADR-058](ADR-058-validator-registry.md) all read; the lifecycle README's "How a registered command is run" documents the contract and the policies.

   **One deadline and one kill across a tree of runs.** A command the runner starts may start `pkit` again, which runs a command in turn. Every run tells its command its deadline: its own end, less the time the command keeps to answer after something it started ran out. A run inside another inherits that deadline — it is bounded by the time its caller has left, never more than its own bound — and starts its command in the outermost run's process group rather than a group of its own. The outermost run owns the group: its kill, on its overrun or an interrupt, reaches the whole tree, and when its own command ends it ends whatever a nested run that did not end by itself — overrun, interrupted, or killed by anyone else — left running there. A nested run cannot kill a group it shares with its callers, so on an overrun it kills its command alone and leaves the rest to the outermost run. Each level's deadline comes before its caller's, so the command that overran is the one a no-answer names, with the bound it had — which may be the time its caller had left rather than its own — and its callers still answer in time. A deadline counts only inside a live run, so a variable left over in a shell never makes a run nested. What this does not reach — a process that leaves the group, a clock step between two levels — is stated in the lifecycle README, "A run inside a run".

6. **What this record places of COR-053, and what it leaves.** It places the resolver, and with it everything that reads the resolver: the graph, the status and validation lines, and the install and uninstall plans ship in the binary and call it (this record's points 1 and 2), and the wiring graph subsumes the process graph rather than sitting beside it (COR-053 point 7). The refresh of generated dependency lists and the event runner with its loop guard and chain report are placed by the Tasks that build them, in their own records, as are data-point resolution (combining fillers, precedence, the inert policy) and the source of each edge in the graph. Subscribers are actions, not queries: this record does not realise their limits; COR-053 point 9 sets them.

## Rationale

**Why the binary.** ADR-020's test is whether a consumer below the tool layer must import the code. None does: every reader of friction, wiring or rules is a `pkit` command, capability scripts already call `pkit` as a subprocess, and the project's check aggregator invokes the CLI. Shipping the engines in the tree would add a copy to version and a third version axis for nothing.

**Why one home each.** The value of a plan, a graph or a status line is that it agrees with what validation and the checks conclude. Two computations drift, and the one people trust — the plan before an install — would be the one that lies. Where two readings must differ — the working tree against a commit, or a working tree git gives no view of — the difference is stated once and pinned by a test, so it cannot drift into a disagreement.

**Why a declaration of the whole contract, on the command.** The core names three obligations for a capability to declare (COR-050 point 2); one constant that declares them together leaves no way to declare one and give the others no thought. A declaration on the command's own entry is literally per command, and a command used by two registrations is declared once. The report sits in the validation of package metadata, where it puts the requirement in front of the author; the refusal sits in each engine that runs a query, where it keeps a missed report from becoming a silent run.

**Why not decide from egress.** Refusing the commands of a capability that "holds egress" was considered and cannot work: confinement toolkits are per tool, not per capability ([ADR-008](ADR-008-confinement-allowances.md) rule 1), and egress is session-wide (ADR-015), so a grant is neither necessary nor sufficient for a given command to reach the network.

**Why the rest waits.** No capability registers an anchor kind or subscribes to an event yet. The registration of a kind, the resolver's answer shape and the event runner are best decided against their first real consumer.

**Why an ADR.** The core records fix the contract — which limit the backbone enforces, which obligations a capability declares, and that the declaration is required, reported and trusted — and leave where the engines live and how the contract is realised to the project; this is project-kit's realisation, at the altitude of ADR-020 and ADR-056 ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md)).

### Alternatives considered

- **Propagate the engines into the tree.** Rejected: no consumer below the tool layer; a third version axis for nothing (ADR-020).
- **Refuse commands by their capability's egress.** Rejected: toolkits are per tool (ADR-008 rule 1) and egress is session-wide (ADR-015); a grant says nothing about a command.
- **Start query commands under an operating-system sandbox from the engine.** Rejected: pkit manages but delegates confinement (ADR-004 points 2 and 3); a per-command confinement layer of its own would reopen that split and differ per platform. The harness's own box cannot host `uv` on macOS (ADR-014), which is why these commands run outside it.
- **Declare only "no network".** Rejected: the core names three obligations for a capability to declare (COR-050 point 2); declaring one leaves the other two undeclared and implies they need no thought.
- **A configurable time bound.** Rejected for this record: a project setting would be a backbone configuration key, which only a core record may own (COR-048 point 2).
- **Put subscribers under the query contract.** Rejected: a subscriber writes, so changing nothing in the project is not among its obligations and "no answer" cannot apply to effects. COR-053 point 9 sets a subscriber's own limits — a time bound the backbone enforces, failing closed, and the obligations to need no network and to act the same on the same inputs, which are the subscriber's to keep — beside the effect report, the opt-out and the loop guard. How a subscriber declares its obligations is decided with the runner that starts subscribers, whose record realises all of these.

## Implications

- The friction checks, the wiring resolver and the rule-set validator are modules of the binary; each computation has one home (point 2), and a new reader calls it rather than computing it again.
- The command primitive the runners share is built (point 5).
- The package-metadata reference gains the declaration's literal and the offline marker with ADR-058, whose validators are the first query commands. The package schema describes the declaration's key; the requirement is checked by validation's `packages` member, which reports the command a validator or a command filler names when it lacks the declaration. A resolver's command joins them, and its answer shape arrives, with the first resolver (point 3).
- The CLI reference's resolver-limits paragraph states what nothing confines as point 4 does, including macOS, and cites this record.
- **The contract is core's; this record realises it.** COR-050 point 2 states which limit the backbone enforces — the time bound — and which a command's capability declares — needing no network, changing nothing in the project, the same output for the same inputs — with the declaration required before a run, reported at validation when missing, and trusted while the command runs. COR-052 point 6 follows it for a command filler, and COR-053 point 9 for a subscriber, leaving how a subscriber declares its obligations to the runner that starts subscribers. Points 3 and 4 are project-kit's realisation: where the declaration is written and which check reports it, the bound and the marker, and what no layer of this distribution confines.
- **Recorded trigger to revisit.** If a consumer below the tool layer ever needs one of these engines in-process, ADR-020's test is reopened for that engine.
