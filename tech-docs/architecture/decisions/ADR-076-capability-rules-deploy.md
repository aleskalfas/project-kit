## Summary

**In plain terms:** this record is how project-kit builds [COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md), under which a capability's operational rules load in every session where it is installed.
- **The set and its file:** a capability's loaded set sits in its `rule-sets/` folder like its other sets, and its preface names the capability and its layer. Its loaded file is `.pkit/capabilities/<name>/rules.md`, written by `pkit rule-sets generate` and checked as core's is.
- **The deploy:** the Claude Code adapter copies that file to `.claude/rules/pkit/<name>.md`, a folder of its own that Claude Code reads at every session's start, through a deploy primitive of its own. Uninstall removes the copy.
- **The declaration:** the adapter's package metadata says where it deploys a capability's rules file. The backbone's check and the adapter's deploy both read it there, so the path is written once.
- **The check:** validation's `rule-sets` member fails an installed capability whose copy is missing or differs, where the adapter has deployed in the checkout. Where it has not, the member reports that.
- **What binds:** install, sync and upgrade name each capability's loaded set they deliver, and the rules it newly binds, changes or retires.
- **The harness requirement:** every session holds the loaded files from its start and for its whole length. Claude Code answers it at a cost, naming the sessions its documentation says load none of them, and vouches for no version until a session is observed. The report reads it as indeterminate.

## Context

COR-070 decides that each adapter deploys an installed capability's loaded file, through a place of its own, where its harness loads files into every session, and that validation fails where a checkout's deploy left it missing. Its Implications leave to an architecture record:
- where the capability's loaded set and its loaded file live
- the form of the preface that names the capability's layer, and of a citation of its rules
- Claude Code's place, and how the adapter deploys there and removes what it deployed
- how the backbone learns an adapter's place, since it names no adapter's paths ([ADR-009](ADR-009-git-footprint-visibility.md) rule 1)
- where the check runs, and how it tells a checkout where the adapter deployed
- the harness requirement's entry and Claude Code's answer
- what brings existing projects level ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md))

Five records set the shape this one fits:
- **The loaded file** is generated by one function, written by `pkit rule-sets generate` and checked by validation's `rule-sets` member where the set is authored ([ADR-075](ADR-075-generated-operational-rules.md) points 2 to 5).
- **Rule-set files are found by where they are** ([ADR-056](ADR-056-backbone-file-schemas-home.md) point 2).
- **Each validator is a member of `pkit validate`,** and `error` is the one severity that fails ([ADR-058](ADR-058-validator-registry.md) point 2).
- **A component declares what it deploys outside `.pkit/`** in its package metadata, and the backbone aggregates the declarations (ADR-009 rule 1). Only paths that make up project-kit's presence go there (ADR-009 points 1 and 5).
- **The lifecycle runs an adapter's primitives by name** (the adapters README, "Primitives the lifecycle calls").

What Claude Code does with these files, as read from its documentation of memory files, subagents and hooks on 29 October 2026 ([memory](https://code.claude.com/docs/en/memory), [subagents](https://code.claude.com/docs/en/sub-agents), [hooks](https://code.claude.com/docs/en/hooks)):
- **What it loads:** every Markdown file under the project's `.claude/rules/`, found recursively, that carries no `paths:` field in its front matter, at a session's start as it loads the project's `CLAUDE.md`. After the session's context is compacted, these files are read again from disk.
- **Where it loads them:** in a session a person starts in the project, and in a subagent it starts from one, which loads every level of the `CLAUDE.md` hierarchy the main session loads, project rules included.
- **Where it does not:** the built-in Explore and Plan agents, and any agent definition that sets `omitClaudeMd`. A file matched by the `claudeMdExcludes` setting, in any settings layer, is dropped, and so is every project file where project instructions are set to `managed-only`. Project rules are skipped where `--setting-sources` leaves out the project's. The adapter's confined runner always passes `--setting-sources ""` (the adapter README, "The confined form's closed set of flags").
- **Links:** git checks a committed symbolic link out as a plain text file unless `core.symlinks` is on, as it is not by default on Windows. A link whose target lies outside the folder the session starts in is treated as an external import, which loads only once a person approves it.
- **An observation point:** the `InstructionsLoaded` hook fires when a `CLAUDE.md` or `.claude/rules/` file is loaded, with load reasons such as `session_start` and `compact`.

## Decision

**A capability's loaded file is `rules.md` at the root of its tree, generated and checked as core's is. The Claude Code adapter copies it to `.claude/rules/pkit/<capability>.md` through a deploy primitive of its own, reads that place from its package metadata, and removes the copy at uninstall. Validation's `rule-sets` member fails an installed capability whose copy is missing or differs where the adapter has deployed, and reports a checkout where it has not.**

### 1. The capability's loaded set and its loaded file

- **The set:** a rule-set file in the capability's `rule-sets/` folder with `loaded: true`, found by the location rule as the capability's other sets are. The `rule-sets` member's refusal of a set marked loaded in a capability's folder (ADR-075 point 6) is lifted. A second loaded set in one capability's folder is refused, as it is in any component's.
- **Its name:** the capability's own, such as `SWE`. The finding that two sets share a name (COR-051 point 3) already refuses a set named `OPS` or any other set's name.
- **Its preface:** the prose before its first rule names the capability, and states how its rules stand to the other layers, in the sentence the rules README gives: its rules add to core's and never loosen them; where one cannot be kept with a rule of core's, core's binds; a project's rules add to these and never loosen them; where one cannot be kept with a rule of another capability's, the session stops the step and reports the clash. The projection carries it into the loaded file (ADR-075 point 3). The `rule-sets` member fails a capability's loaded set whose preface does not name its capability, where the set is authored. The rest of the sentence is judged by whoever accepts the set.
- **The file:** `.pkit/capabilities/<name>/rules.md`. Its path comes from the set's owner, as ADR-075 point 2 decides for every loaded set: the one function that gives each owner's loaded file gives a capability's from its name.
- **Written and checked as core's:** `pkit rule-sets generate` writes it where the capability is authored, and the staleness check of ADR-075 point 5 fails it there when it differs from its set. Where the capability arrives by sync or install, the file arrives with it, and neither runs.
- **No front matter:** the projection writes none (ADR-075 point 3). Here that is also what makes Claude Code load the file in every session: a `paths:` field would load it only beside the files it names.
- **Citations:** a capability's rule is cited `<capability>:RS-<SET>-NNN`, as a method set's rule is (COR-051 point 6). Validation's `refs` member reads that form beside `backbone:RS-OPS-0NN` and warns of a citation of a missing or retired rule (ADR-075 point 8). There is no form by capability and number, such as "software-engineering rule 2".
- **Origins:** each rule's origin cites a record of the capability's own (`<capability>:DEC-NNN`), a core record, or gives the decider's words, never an architecture or project record. The set is validated in every project that installs it, where those would resolve against the project's own records (ADR-075 point 1).

### 2. The Claude Code adapter copies the file into `.claude/rules/pkit/`

- **The primitive:** `deploy-rules.sh`, a fifth deploy primitive, which the lifecycle runs after `deploy-agents.sh`. The lifecycle's list of primitive names gains it. The script reads its place from the adapter's `loaded_rules:` key (point 3). For each capability the manifest registers whose `rules.md` exists, it writes a copy, byte for byte, at that place.
- **A copy, not a link:** a rules file has no placeholders to resolve, but a copy loads in a Windows checkout and in a session started below the project's root, where a link would not (Context). The check of point 4 compares the copy with its file, so a copy edited or left behind fails.
- **Its own folder:** `.claude/rules/pkit/` is the adapter's. Each run removes every file in it that is no registered capability's copy, and the folder once empty. A project's own files elsewhere under `.claude/rules/` never share a name with a copy, and the deploy never reads or writes them.
- **Undeploy:** `undeploy-capability.sh <name>` also removes `.claude/rules/pkit/<name>.md`, and the folder once empty.
- **The footprint:** `.claude/rules/pkit` joins the adapter's `footprint:`, and nothing else of `.claude/rules/` does (ADR-009 rule 1).
- **Version control:** a project that commits its deployed agents commits the copies the same way. project-kit's `.gitignore` and the next steps `pkit init` prints gain `!.claude/rules/` beside their re-includes of `.claude/skills/` and `.claude/agents/`.

### 3. The adapter declares where it deploys a capability's rules file

- **The key:** the adapter's package metadata gains `loaded_rules:`, a path from the project root that holds `{capability}` once: `.claude/rules/pkit/{capability}.md`. The package schema checks its shape.
- **What reads it:** the check of point 4, and the adapter's own `deploy-rules.sh` and `undeploy-capability.sh`. The backbone learns the place from the declaration and names no path of the adapter's (ADR-009 rule 1).
- **No key:** an adapter that declares none deploys no capability's rules file, and the check warns of it (point 4).

### 4. Validation's `rule-sets` member checks the deploy

- **Where the adapter has deployed:** a checkout holds a folder of the adapter's `footprint:` (for Claude Code, `.claude/skills`, `.claude/agents` or `.claude/rules/pkit`). There, for each capability the manifest registers that ships a loaded set, the path `loaded_rules:` gives with the capability's name must hold the bytes of the capability's `rules.md`, once line endings are read as `\n`. Otherwise it is an `error`, `loaded-file-undeployed`, naming the capability, the adapter, the path and the sync that deploys it.
- **Where it has not:** a checkout that holds no folder of the footprint, such as a clone that keeps `.claude/` out of version control, gets a report line saying that the adapter's deploy has not run there, so its sessions load none of its files.
- **No declaration:** a registered adapter without `loaded_rules:` gets a `warning` for each capability that ships a loaded set, naming the adapter, since that harness's sessions load no capability's rules (COR-070 point 6).
- **Where it runs:** in every project, where the capability is authored and where it arrives by sync, since the deploy is the project's own state. It reads files only, never a session.
- **Why this member:** loaded sets and their files are its subject already (ADR-075 point 5), and one subject keeps one member (ADR-058).

### 5. The lifecycle says which rules it newly binds

- **What it prints:** install, sync and upgrade print, for each capability whose loaded set they deliver, the set's name and version and each rule it newly binds, changes or retires since the copy it replaces. A first install lists every accepted rule by id and title.
- **How it knows:** one function beside the loaded-set projection compares two readings of a set's accepted rules, by id, status and statement. The lifecycle reads the set before it copies the new version, and prints the function's answer.
- **Not a gate:** the line informs and stops nothing (COR-068 point 5).

### 6. The harness requirement, and Claude Code's answer

- **The requirement:** `.pkit/schemas/harness-requirements.yaml` gains `session-loads-rules`. Its behaviour is that each session the harness starts in a project holds every file the methodology places for the harness to load, from the session's start and for its whole length, compaction included. That covers a session a person starts, a delegated helper and an unattended run. Its observation point is `in-session`, and its evidence is the design dependency of COR-070 point 6.
- **Claude Code's answer:** `harness-support.yaml` answers it `at-cost`. The cost names what Claude Code's documentation says (Context):
  - it holds for a session a person starts in the project, for a subagent it dispatches with a definition of the project's, and after compaction
  - it does not hold for the built-in Explore and Plan agents or a definition that sets `omitClaudeMd`, where `claudeMdExcludes` matches the copies or project instructions are `managed-only`, or in a run whose settings sources leave out the project's
  - the adapter's confined runner is such a run, so an unattended fixer's run loads none of these files
  - the adopter keeps the copies out of `claudeMdExcludes`, and dispatches the methodology's work to definitions that do not set `omitClaudeMd`
- **Its range:** `harness_versions` stays empty until a session is observed holding a copied file, so it vouches for no version. Only whoever observes it widens the range, as COR-047 point 2 requires. The `InstructionsLoaded` hook is the observation point (Context). Logging it, so a session can be observed, is a follow-up the build names.
- **The confined runner, a residual:** the runner passes no settings source, so a confined run loads no project instructions, core's included. Carrying only a capability's file into the definition the resolver writes, as it carries the workspace sentence, would give a fixer a capability's rules without core's. Whether the resolver carries the loaded files of every layer into a confined definition is one question for all of them, and the build names it as a follow-up.
- **The report:** an `in-session` requirement resolves `indeterminate` from outside a session (COR-047 point 4). `pkit harness report` names the requirement with that reason, never as satisfied.

### 7. What brings existing projects level

- **The deploy:** the next sync or upgrade runs the deploy primitives, so `deploy-rules.sh` copies each installed capability's file. Nothing is renamed or removed, so no migration is due for the copies.
- **A private project:** the exclude region of a project made private holds the footprint `pkit visibility private` wrote, and no sync rewrites it. An adapter migration, at the adapter version that adds `.claude/rules/pkit` to the footprint, adds that entry to the region where the region exists and lacks it. The copies then stay out of the project's commits. It acts on that sign alone and is idempotent (core rule 5).
- **Versions:** the adapter, and each capability that ships a loaded set, needs the backbone that lifts ADR-075 point 6's refusal and knows the fifth primitive. Their changesets say `requires_backbone: release` (PRJ-002 D4).
- **Nothing else:** the package schema gains an optional key, and a capability gains files, so no file that passes today fails (ADR-056 point 3).

## Rationale

**Why `rules.md` at the root of the capability's tree.** One loaded set to a component leaves one file, so a folder for it would hold one file. A capability's tree has no area of its own for rules, and the file's name says what a reader finds in it. The path is fixed by the owner, so no set can write another component's file (ADR-075, "Why the file's path is fixed by the set's owner").

**Why a folder of the adapter's own.** Claude Code reads `.claude/rules/` recursively, so a subfolder loads as the folder does. A folder of its own keeps a copy from ever sharing a name with a project's own rules file, and lets each run remove what it no longer deploys by the folder alone. It also keeps the footprint to what is project-kit's presence. A footprint naming all of `.claude/rules/` would have `pkit visibility private` offer to untrack a team's own rules files, and exclude every new one (ADR-009 points 1 and 5).

**Why a copy, not a link.** Agents are copied already. A link has two failure modes a copy does not: a Windows checkout without `core.symlinks` holds the link as a one-line text file, which Claude Code would load as a rule, and a link whose target lies outside the folder a session starts in waits for a person's approval. The byte-for-byte check catches a copy that drifts as surely as a broken link.

**Why a primitive of its own.** The lifecycle finds an adapter's primitives by name and runs each it finds, so an adapter whose harness has no such place ships none. A rules file is neither a skill nor an agent, and folding it into either deploy would give that script a second kind of content.

**Why the adapter declares the place, and its scripts read it.** The check must find the deployed file in every project, for each adapter in use. A path written into the backbone would name an adapter's place in core, the layering ADR-009 rule 1 forbids. Running an adapter's script from validation would make validation depend on what a script does. A declaration read from package metadata is data the package schema checks, as the footprint is. The scripts read the same key, so the path cannot differ between the deploy and the check.

**Why the check keys on the footprint's folders.** Where the adapter has deployed, a missing copy is a deploy left incomplete or a file removed by hand, which the next sync mends. A checkout that holds none of the adapter's folders, such as one that keeps `.claude/` out of version control, holds none of its skills or agents either. Its sessions load nothing of the adapter's, and only a deploy could change that. Failing there would fail it for a state no edit in the checkout sets (COR-070, "Why validation reports, rather than fails, where no deploy ran").

**Why the check runs where the capability arrives by sync too.** The staleness check runs only where the set is authored, because a project receives the set and its file together and edits neither. The deploy is different: the project's own sync writes it, and an interrupted sync or a harness folder the project cleared can each leave it missing.

**Why the preface is checked for the capability's name alone.** That the file names its capability is a fact a check can read. Whether the rest of the sentence states the layering rightly is prose, which the person accepting the set judges (COR-055).

**Why citations by id only.** COR-068 point 6 keeps "core rule N" and "project rule N" because records, documents and decided answers already cite them that way. No citation of a capability's operational rule exists yet, so none needs keeping. A form by capability and number would be one more form for the `refs` member to read, in prose where a capability's name and a number may mean something else.

**Why Claude Code's answer names its exceptions, and vouches for no version yet.** The documentation says which sessions load the files and which do not, and an `at-cost` answer states the second as what the adopter must keep in mind. No session has been observed holding a copy. An answer that vouched for every version would be the confident unchecked claim COR-047 point 5 warns of. The runner's tested range ([ADR-066](ADR-066-unattended-agent-runner.md) point 12) is the precedent: empty until observed.

**Why the confined runner is left a residual.** A confined run loads no project instructions, by the confined form's design (ADR-066). That covers core's loaded file as well as a capability's. Carrying a capability's file alone would leave an unattended fixer bound by the capability's rules and not by core's. One answer for all layers is a choice of its own, about the confined form, which this record does not make.

### Alternatives considered

- **The file at `.pkit/capabilities/<name>/rules/<name>.md`,** mirroring `.pkit/rules/core.md`. Not taken: a folder for one file, and a name said twice.
- **A link at `.claude/rules/<capability>.md`.** Rejected: a link fails in a Windows checkout and outside the folder a session starts in, as "Why a copy, not a link" says. A file directly in `.claude/rules/` could also share a name with a project's own, and would need the whole folder in the footprint.
- **Deploying the rules file in `deploy-skills.sh`.** Not taken: one primitive, one kind of content.
- **One index file of the adapter's own, reached by a single include inserted once in `CLAUDE.md`,** as COR-070 point 2 allows a harness with no such folder. Not taken for Claude Code: it reads `.claude/rules/` already, so no line in the project's file is needed.
- **The start hook, adding each file as context at `SessionStart` and `SubagentStart`.** Not taken: it is the one route to Explore and Plan, but what it adds is summarised away at compaction and capped in size, and an adopter's own entry for the event takes the baseline's place.
- **The deploy's place written in the backbone.** Rejected by ADR-009 rule 1.
- **The check as a mode of the adapter's deploy script.** Rejected: validation would run an adapter's script, and its result would rest on what the script does.
- **The check failing in every checkout.** Rejected, as "Why the check keys on the footprint's folders" says.
- **The resolver carrying a capability's file into each confined definition.** Not taken here, as "Why the confined runner is left a residual" says.
- **Claude Code's answer as `full`, for every version.** Rejected, as "Why Claude Code's answer names its exceptions" says.

  - **project-management** holds the work tracker's own requirements core rule 9 defers to "the installed work-tracking capability's documentation": linking a branch and a pull request to its issue, the labels, and the pull-request workflow (COR-009).
  - **Core rule 9** keeps its claim, conventional commits with one logical unit each, and branch naming, whose source is COR-008's operational reference. It points to COR-008 rather than to a capability's documentation, and names no capability.
