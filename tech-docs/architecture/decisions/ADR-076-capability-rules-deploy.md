## Summary

**In plain terms:** this record is how project-kit builds [COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md), under which a capability's operational rules load in every session where it is installed.
- **The file:** a capability's loaded file is `.pkit/capabilities/<name>/rules.md`, generated and checked as core's is.
- **The delivery:** the Claude Code adapter keeps one generated index, `.claude/pkit-rules.md`, that includes each installed capability's file, and `CLAUDE.md` reaches the index through one line inserted once after core's include. A capability's rules then load wherever core's do, an unattended confined run included.
- **The check:** validation fails an index out of step with the installed capabilities, or a `CLAUDE.md` without its line, where the index is in the checkout, and says so in a summary line where it is not.
- **What binds:** install, sync and upgrade name the rules each loaded set newly binds, core's included.
- **The harness requirement:** Claude Code answers it at a cost, naming the sessions that skip `CLAUDE.md`, and vouches for no version until a session is observed.

## Context

COR-070 decides that each adapter delivers an installed capability's loaded file to every session its harness starts, by the route that carries core's rules where the harness offers one, and that validation fails where a checkout's delivery is not in step. Its Implications leave to an architecture record:
- where the capability's loaded set and its loaded file live
- the form of the preface that names the capability's layer, and how validation reads a citation of its rules
- Claude Code's form of delivery, and how the adapter writes it and takes a capability out of it
- how the backbone learns an adapter's delivery, since it names no adapter's paths ([ADR-009](ADR-009-git-footprint-visibility.md) rule 1)
- where the check runs, and how it tells a checkout where the adapter delivered
- the harness requirement's entry and Claude Code's answer
- what brings existing projects level ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md))

These records and the adapters' reference set the shape this one fits:
- **The loaded file** is generated by one function, written by `pkit rule-sets generate` and checked by validation's `rule-sets` member where the set is authored ([ADR-075](ADR-075-generated-operational-rules.md) points 2 to 5).
- **Rule-set files are found by where they are** ([ADR-056](ADR-056-backbone-file-schemas-home.md) point 2).
- **Each validator is a member of `pkit validate`,** and `error` is the one severity that fails ([ADR-058](ADR-058-validator-registry.md) point 2).
- **A component declares what it deploys outside `.pkit/`** in its package metadata, and the backbone aggregates the declarations (ADR-009 rule 1). Only paths that make up project-kit's presence go there (ADR-009 points 1 and 5).
- **The lifecycle runs an adapter's primitives by name** (the adapters README, "Primitives the lifecycle calls"). `merge-claude-md.sh` inserts core's include, `@.pkit/rules/core.md`, into the project's `CLAUDE.md` where it is absent, and the project's own `@.pkit/rules/project.md` beside it ([COR-002](../../../.pkit/decisions/core/COR-002-merge-delivery.md)).

What Claude Code does with these files, as read from its documentation of memory files, subagents and hooks on 29 October 2026 ([memory](https://code.claude.com/docs/en/memory), [subagents](https://code.claude.com/docs/en/sub-agents), [hooks](https://code.claude.com/docs/en/hooks)):
- **Two routes:** a session loads the project's `CLAUDE.md`, with each file an `@` line in it imports, and imports within those, a path read from the importing file. It also loads every Markdown file under `.claude/rules/`, found recursively, that carries no `paths:` field.
- **Where both load:** in a session a person starts in the project, and in a subagent it starts from one, which loads every level of the `CLAUDE.md` hierarchy the main session loads. After the session's context is compacted, both are read again from disk.
- **Where neither does:** the built-in Explore and Plan agents, and any agent definition that sets `omitClaudeMd`. A file matched by the `claudeMdExcludes` setting, in any settings layer, is dropped, and so is every project file where project instructions are set to `managed-only`. `--bare` and `--safe-mode` skip `CLAUDE.md`.
- **Where the routes part:** project rules, the files under `.claude/rules/`, are skipped where `--setting-sources` leaves out the project's, and `CLAUDE.md` is not. The adapter's confined runner passes `--setting-sources ""` (the adapter README, "The confined form's closed set of flags"), and passes neither `--bare` nor `--safe-mode`. [ADR-066](ADR-066-unattended-agent-runner.md) says a confined run reads every `CLAUDE.md` above the folder it starts in ("The person's instructions"). So a confined run loads core's rules, through the include in `CLAUDE.md`, and would not load a file under `.claude/rules/`.
- **An observation point:** the `InstructionsLoaded` hook fires when a `CLAUDE.md`, a file it imports or a `.claude/rules/` file is loaded, with load reasons such as `session_start` and `compact`.

## Decision

**A capability's loaded file is `rules.md` at the root of its tree, generated and checked as core's is. The Claude Code adapter writes one index of its own, `.claude/pkit-rules.md`, that imports each installed capability's loaded file, and its merge primitive inserts one line reaching the index into the project's `CLAUDE.md`, once, after core's include. Validation's `rule-sets` member fails an index out of step with the installed capabilities, or a `CLAUDE.md` without its line, where the index is in the checkout, and says in a summary line where it is not.**

### 1. The capability's loaded set and its loaded file

- **The set:** a rule-set file in the capability's `rule-sets/` folder with `loaded: true`, found by the location rule as the capability's other sets are. The `rule-sets` member no longer refuses a set marked loaded in a capability's folder (refinement of ADR-075 point 6). A second loaded set in one capability's folder is refused, as it is in any component's.
- **Its name:** the capability's own, such as `SWE`. The finding that two sets share a name (COR-051 point 3) already refuses a set named `OPS` or any other set's name.
- **Its preface:** the prose before its first rule names the capability, and states how its rules stand to the other layers, in the sentence the rules README gives: its rules add to core's and never loosen them; where one cannot be kept with a rule of core's, core's binds; a project's rules add to these and never loosen them; where one cannot be kept with a rule of another capability's, the session stops the step and reports the clash. The projection carries it into the loaded file (ADR-075 point 3). The `rule-sets` member fails a capability's loaded set whose preface does not name its capability, where the set is authored. The rest of the sentence is judged by whoever accepts the set.
- **The file:** `.pkit/capabilities/<name>/rules.md`. Its path comes from the set's owner: the one function that gives each owner's loaded file gives a capability's from its name, where ADR-075 point 2 holds one constant for the backbone's (refinement of ADR-075 point 2).
- **Written and checked as core's:** `pkit rule-sets generate` writes it where the capability is authored, and the staleness check of ADR-075 point 5 fails it there when it differs from its set. Where the capability arrives by sync or install, the file arrives with it, and neither runs.
- **One answer to which capabilities ship one:** a reading command of the `rule-sets` group, `pkit rule-sets loaded [--json]`, lists each loaded set the project holds, its owner and its loaded file, from the one function that gives each owner's loaded file ([ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 2). The index of point 2 and the check of point 4 both read it, so a capability's file is delivered exactly where it is checked. Where the capability is authored, the `rule-sets` member fails a `rules.md` at a capability's root with no loaded set behind it, so a file left behind by a removed set is never delivered unchecked.
- **No front matter:** the projection writes none (ADR-075 point 3), so an import of the file brings its rules and nothing else.
- **Citations:** validation's `refs` member reads the form COR-070 point 1 gives, `<capability>:RS-<SET>-NNN`, beside `backbone:RS-OPS-0NN`, and warns of a citation of a missing or retired rule (ADR-075 point 8).
- **Origins:** each rule's origin cites a record of the capability's own (`<capability>:DEC-NNN`), a core record, or gives the decider's words, never an architecture or project record. The set is validated in every project that installs it, where those would resolve against the project's own records (ADR-075 point 1).

### 2. The Claude Code adapter keeps an index that `CLAUDE.md` includes

- **The index:** `.claude/pkit-rules.md`, a file of the adapter's own. It holds one line per installed capability that ships a loaded set, `@../.pkit/capabilities/<name>/rules.md`, a path read from the index's own folder, in the order of the capabilities' names, and nothing else: no heading, no prose (core rule 13). Where no installed capability ships one, it is empty.
- **The line in `CLAUDE.md`:** `@.claude/pkit-rules.md`, inserted once by `merge-claude-md.sh` directly after core's `@.pkit/rules/core.md`, where it is absent. The rules then read in the order of their layers: core's, each capability's, the project's. The primitive inserts each of its lines where that line is absent, and never removes or rewrites the project's text (COR-002). Once inserted, the line stays, and the index carries every install and uninstall.
- **Inserted whenever the adapter is installed,** whether or not a capability ships a loaded set yet. The project's `CLAUDE.md` then changes once, at the first sync that brings this, and never again for an install or an uninstall. An empty index costs a session nothing.
- **The depth:** `CLAUDE.md` imports the index, and the index imports each loaded file, so a capability's rules are two imports from `CLAUDE.md`, within the depth the documentation allows. Its imports resolve as core's does, so a session started below the project's root reads them as it reads core's.
- **The primitive that writes it:** `deploy-rules.sh`, a fifth deploy primitive, which the lifecycle runs after `deploy-agents.sh`, found by name. It writes the index whole, from `pkit rule-sets loaded --index claude-code` (point 3), at each install, sync and upgrade. The index is generated and the adapter's alone, so no record of what it wrote is kept: it is written again from what is installed.
- **Undeploy:** `undeploy-capability.sh <name>` writes the index again without the capability, as the deploy would once the manifest no longer registers it. The line in `CLAUDE.md` stays.
- **Not under `.claude/rules/`:** Claude Code loads every file there, so an index there would load each capability's rules twice, and the index would be loaded in sessions where `CLAUDE.md` is not.
- **The footprint:** `.claude/pkit-rules.md` is in the adapter's `footprint:` beside `.claude/skills`, `.claude/agents` and `CLAUDE.md` (ADR-009 rule 1).
- **Version control:** a project that commits its deployed agents commits the index the same way. project-kit's `.gitignore`, and the next steps `pkit init` prints, re-include `.claude/pkit-rules.md` beside `.claude/skills/` and `.claude/agents/`.

### 3. The adapter declares its delivery

- **The key:** the adapter's package metadata holds `loaded_rules:`, which names the delivery once:
  - `index:` the index's path from the project root, `.claude/pkit-rules.md`;
  - `entry:` the line for each capability's loaded file, with `{file}` for its path read from the index's folder, `@{file}`;
  - `host:` the file that reaches the index, `CLAUDE.md`, and `line:` the line that reaches it, `@.claude/pkit-rules.md`.

  The package schema checks its shape.
- **One function renders the index:** the backbone renders the index's content from the key and `pkit rule-sets loaded`, in one function beside the loaded-set projection. `pkit rule-sets loaded --index <adapter>` prints it. The deploy writes what it prints, and the check compares the file with the same function's output, so the two never disagree on what the index holds (ADR-075, "Why one function for the generator and the check").
- **What it says, and no more:** the key says that the adapter delivers each capability's loaded file through one index the host file reaches by one line. It names the harness's syntax only as data, so the backbone writes no `@` of its own. An adapter whose harness reaches the files another way, such as a place it reads at every start, needs a key of its own or a validator it registers ([ADR-058](ADR-058-validator-registry.md) point 4). That is decided with that adapter.
- **What reads it:** the function above, the check of point 4, and the adapter's own `merge-claude-md.sh` for the line. The backbone learns the delivery from the declaration and names no path of the adapter's (ADR-009 rule 1).
- **No key:** an adapter that declares none delivers no capability's rules, and the check warns of it (point 4).

### 4. Validation's `rule-sets` member checks the delivery

- **Keyed on the index:** where the file `index:` names is in the checkout, it must hold what point 3's function renders for the capabilities the manifest registers, once line endings are read as `\n`, and the `host:` file must hold the `line:`. Otherwise it is an `error`, `loaded-rules-undelivered`, naming the adapter, the file that differs or lacks its line, the capabilities concerned and the sync that mends it.
- **Where the index is not:** a checkout without it, such as one that keeps `.claude/` out of version control but for what it re-includes, gets a summary line of the member saying that the adapter's index is not there, so its sessions load no capability's rules. A state is a summary line, not a finding, as the member's counts are ([ADR-058](ADR-058-validator-registry.md) point 1).
- **One function for it:** one function compares what an adapter declares it delivers, at a destination, with what should be there, and gives the finding or the summary line. It is the methodology's first check of what a deploy leaves on the harness's side. The next such check, of skills or agents, reuses it.
- **No declaration:** a registered adapter without `loaded_rules:` gets one `warning`, naming the adapter and each capability that ships a loaded set, since that harness's sessions load no capability's rules (COR-070 point 6).
- **Where it runs:** in every project, where the capability is authored and where it arrives by sync, since the delivery is the project's own state. It reads files only, never a session.
- **Why this member:** the member that holds the rule sets' checks already has loaded sets and their files as its subject (ADR-075 point 5), and one subject keeps one member (ADR-058). The delivery of a loaded file widens that subject to where the file is delivered, and the member's help text says so.

### 5. The lifecycle says which rules it newly binds

- **What it prints:** install, sync and upgrade print, for each loaded set they deliver, core's `OPS` and each capability's alike, the set's name and version and each rule it newly binds, changes or retires since the copy it replaces. A first install lists every accepted rule by id and title.
- **How it knows:** one function beside the loaded-set projection compares two readings of a set's accepted rules, by id, status and statement. It knows no layer. The lifecycle reads each set before it copies the new version, and prints the function's answer.
- **A harness that loads no capability's rules:** where no adapter in use declares `loaded_rules:`, the line for a capability's set says that its rules bind no session in this project, rather than list them as bound (COR-070 point 3).
- **Not a gate:** the line informs and stops nothing (COR-068 point 5).

### 6. The harness requirement, and Claude Code's answer

- **The requirement:** `.pkit/schemas/harness-requirements.yaml` holds `session-loads-rules`. Its behaviour is that each session the harness starts in a project holds every file the methodology places for the harness to load, from the session's start and for its whole length, compaction included. That covers a session a person starts, a delegated helper and an unattended run. Its evidence is the design dependency of COR-070 point 6.
- **Its observation point, `interposed-runtime`:** COR-070 point 6 places the truth where a session runs, in the session itself or in what the harness runs at its own points during it. Of the two, the harness's own points reach every kind of session: Claude Code's `InstructionsLoaded` hook fires for each file loaded at a session's start and again after compaction (Context), in a helper and an unattended run as in a session a person starts. An agent inside a session sees its own context, not what a helper or an unattended run loaded, so `in-session` would place the truth where it cannot be read for those sessions. Out of session, the files are seen in place, not loaded.
- **Claude Code's answer:** `harness-support.yaml` answers it `at-cost`. Core's loaded file and every capability's reach a session by one route, `CLAUDE.md` and its imports, so the cost names that route's exceptions once (Context):
  - **Loaded:** in a session a person starts, in a subagent dispatched with a definition of the project's, after compaction, and, by ADR-066's account, in a confined run.
  - **Not loaded:** for Explore and Plan, a definition that sets `omitClaudeMd`, a run with `--bare` or `--safe-mode`, or where `claudeMdExcludes` or `managed-only` drop `CLAUDE.md` or the index.
  - **What the adopter keeps:** `CLAUDE.md` and the index out of `claudeMdExcludes`, and the methodology's work dispatched to definitions that do not set `omitClaudeMd`.
- **Its range:** `harness_versions` stays empty until a session is observed holding an imported capability file, so it vouches for no version. Only whoever observes it widens the range, as COR-047 point 2 requires. The `InstructionsLoaded` hook is where to observe it.
- **The report:** a requirement whose observation point the report cannot reach resolves `indeterminate` (COR-047 point 4). `pkit harness report` names the requirement with that reason, never as satisfied.

### 7. What brings existing projects level

- **The delivery:** the next sync or upgrade runs the primitives, so `merge-claude-md.sh` inserts the line where it is absent and `deploy-rules.sh` writes the index. Nothing is renamed or removed, so no migration is due.
- **A private project:** the exclude region of a project made private holds the footprint as it was when the region was written. ADR-009 point 3 has install write the region again, and the build makes that good where the projection falls short of it (COR-065 point 4): install and sync render the region again from the aggregated footprint wherever it is present, and leave a project with no region alone. That covers the index and every later growth of the footprint, so no adapter migration is due. Should a state remain that the next sync cannot mend, its migration is the backbone's, since the backbone owns the region.
- **Versions:** the adapter, and each capability that ships a loaded set, needs the backbone that lifts ADR-075 point 6's refusal, knows the fifth primitive and answers `pkit rule-sets loaded`, and declares that floor ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md) D4).
- **Nothing else:** the package schema gains an optional key, and a capability gains files, so no file that passes before the change fails after it (ADR-056 point 3).

## Rationale

**Why an index that `CLAUDE.md` includes.** Core's loaded file reaches a session through `CLAUDE.md`, and a capability's must take the same route where the harness offers it (COR-070 point 2). Claude Code's two routes part in a run that leaves out the project's settings: it skips `.claude/rules/` and still reads `CLAUDE.md`, as the adapter's confined runner does (Context). Through the include, a capability's rules load wherever core's do, and a fixer running confined is bound by both. Nothing is left to decide before the confined form's tested range widens (ADR-066 points 2 and 12).

**Why one line, inserted once, and an index of the adapter's own.** A line in `CLAUDE.md` for each capability would have to come out at uninstall, from a file the project writes (COR-070, "Why through a file or place of its own"). One line reaching the adapter's own file never needs removing: the index carries every change of which capabilities are installed, and the adapter writes the whole of it, since nothing else is in it.

**Why the line is inserted whenever the adapter is installed.** Inserting it only once a capability ships a loaded set would change the project's `CLAUDE.md` at an install, and leave a line the check must judge by what is installed. Inserted at the first sync that brings it, it changes the project's file once, and every later install and uninstall touches the adapter's index alone. Most projects install a capability that ships one, so the line would come in any case.

**Why the line sits after core's include.** The rules then read in the order of their layers, core's above a capability's above the project's (COR-070 point 4), and a reader of `CLAUDE.md` sees all three together.

**Why `.claude/pkit-rules.md`.** The index is generated for each project from what it installs, so it is no synced file, and a file under `.pkit/` outside the project's tier is a synced copy by the ownership rule (ADR-075 point 9). The project's tier is the project's own, and a file the adapter writes there would have two owners. `.claude/` is where the adapter already deploys for its harness, and a file directly in it, not under `.claude/rules/`, is loaded only through the line that reaches it. Its name is not `CLAUDE.md`, which Claude Code would load on its own.

**Why the check is the backbone's, with the delivery declared.** The check must find the delivery in every project, for each adapter in use. A path written into the backbone would name an adapter's place in core, the layering ADR-009 rule 1 forbids. An adapter could register a validator of its own (ADR-058 point 4), and one whose harness reaches the files another way will. For an index reached by one line, though, one implementation in the backbone serves every adapter that delivers that way, and the backbone must warn of an adapter that declares no delivery in any case, which no adapter's validator can do for an adapter that has none. A declaration read from package metadata is data the package schema checks, as the footprint is.

**Why the backbone renders the index.** The deploy writes the index and the check compares it, and two pieces of code that each built it could come to disagree. One function, with the harness's syntax given as data in the key, keeps them together, as one function serves the loaded file's generator and its check (ADR-075 point 2).

**Why one reading command says which capabilities ship a loaded set.** The index and the check each need the answer. Two readings, a file's presence for one and the set for the other, could disagree: a `rules.md` left behind by a removed set would be included in every session and checked by nothing. One answer from the backbone, read through a command as ADR-057 point 2 asks of a component's script, keeps the two together, and the refusal of a `rules.md` with no set behind it closes the case where they would differ.

**Why the check keys on the index.** Where the index is in the checkout, an index out of step is a deploy left incomplete or a file edited by hand, which the next sync mends, and a `CLAUDE.md` without its line is one the merge has not reached. A checkout without the index is one where the deploy never ran, or one whose project keeps it out of version control. Failing there would fail a healthy project for that choice (COR-070, "Why validation reports, rather than fails, where the delivery is absent").

**Why the check runs where the capability arrives by sync too.** The staleness check runs only where the set is authored, because a project receives the set and its file together and edits neither. The delivery is different: the project's own sync writes it, and an interrupted sync or a harness file the project cleared can each leave it out of step.

**Why the preface is checked for the capability's name alone.** That the file names its capability is a fact a check can read. Whether the rest of the sentence states the layering rightly is prose, which the person accepting the set judges ([COR-055](../../../.pkit/decisions/core/COR-055-validation.md)).

**Why Claude Code's answer names one route's exceptions, and vouches for no version yet.** Core's file and a capability's now reach a session by one route, so they load in the same sessions and miss the same ones, and one cost states it. The documentation says which sessions skip `CLAUDE.md`, and an `at-cost` answer states them as what the adopter must keep in mind. Until a session is observed holding an imported capability file, an answer that vouched for every version would be the confident unchecked claim COR-047 point 5 warns of. The runner's tested range (ADR-066 point 12) is the precedent: empty until observed.

### Alternatives considered

- **A copy of each capability's file under `.claude/rules/pkit/`.** Rejected: Claude Code skips `.claude/rules/` in a run that leaves out the project's settings, as the adapter's confined runner does, while it still reads `CLAUDE.md`. A confined run would be bound by core's rules and not by a capability's, the reverse of what a fixer working in a capability's area needs, and the gap would have to be closed before the confined form's tested range widened. The copies also needed a record of what the deploy wrote, a folder of their own in the footprint and a re-include of `.claude/rules/`.
- **A link at `.claude/rules/<capability>.md`.** Rejected for the same gap, and because a link fails in a Windows checkout without `core.symlinks` and outside the folder a session starts in.
- **The resolver carrying a capability's loaded file into each confined definition,** as it carries the workspace sentence. Rejected: it would carry one layer's rules into one kind of session by a path of its own, where the include carries every layer's to every session `CLAUDE.md` reaches.
- **A line for each capability in `CLAUDE.md`.** Rejected: uninstall would remove text from a file the project owns (COR-070).
- **The index under `.claude/rules/`.** Rejected: Claude Code loads that folder, so the rules would load twice.
- **The index under `.pkit/`.** Rejected, as "Why `.claude/pkit-rules.md`" says.
- **The line only once a capability ships a loaded set.** Not taken, as "Why the line is inserted whenever the adapter is installed" says.
- **The start hook, adding each file as context at `SessionStart` and `SubagentStart`.** Not taken: it is the one route to Explore and Plan, but what it adds is summarised away at compaction and capped in size, and an adopter's own entry for the event takes the baseline's place.
- **The delivery written in the backbone.** Rejected by ADR-009 rule 1.
- **A validator the Claude Code adapter registers** (ADR-058 point 4). Not taken for an index reached by one line, as "Why the check is the backbone's, with the delivery declared" says. It stays open to an adapter that reaches the files another way.
- **The check keyed on any file of the adapter's footprint.** Rejected: the footprint says what is project-kit's presence (ADR-009 point 1), not that a deploy ran, and a project may keep one of its files in version control and not another.
- **The check failing in every checkout.** Rejected, as "Why the check keys on the index" says.
- **An adapter migration for a private project's exclude region.** Rejected: it would repeat in an adapter's script the region's format, which the backbone owns, and mend this file alone, while every later growth of the footprint would leave the region behind again.
- **Claude Code's answer as `full`, for every version.** Rejected, as "Why Claude Code's answer names one route's exceptions" says.

## Implications

- **Which rules move, proposed for the person to accept.** The build proposes each rule change below in its pull request, and a person accepts each there (COR-066). This record says only where each would go, as COR-070 point 5 decides.
  - **software-engineering's loaded set** would hold a new rule, with an origin of its own, for what of project rule 2 holds wherever code is engineered: while building, a session runs the tests of what it changed and the project's fast checks, and leaves the full suite to where the project runs it, where it runs one. project-kit's `project.md` keeps what is project-kit's own, `scripts/check.sh` and its two-suite limit, and points to the capability's rule.
  - **project-management's loaded set** would hold the work tracker's own requirements that core rule 9 defers to "the installed work-tracking capability's documentation", beyond what [COR-008](../../../.pkit/decisions/core/COR-008-git-conventions.md) decides for every project: that a pull request's body opens with `Closes #<issue>`, by the bundle's template ([COR-009](../../../.pkit/decisions/core/COR-009-pr-workflow.md) point 3), and the label conventions. COR-009's other points, squash-merge, conventional titles, short-lived branches and pull requests recommended rather than enforced, bind wherever pull requests are used, so they stay core's.
  - **Branch naming stays core's.** The form `<type>/<issue-number>-<slug>`, its issue number and the rule that a branch has a related issue included, is decided by COR-008's operational reference for every project. Core rule 9 keeps its claim, conventional commits with one logical unit each, and points to COR-008 for branch naming rather than to a capability's documentation, naming no capability. COR-008 names one host's issues there; whether that reads true in every project is COR-008's question, which this record leaves to it.
  - **Core's set, `OPS`:** rule 12 would say the adapter delivers a capability's rules file beside skills and agents. Its preface would gain the statement of how the layers stand that COR-070's Implications give, and its closing paragraph, "Where these rules came from," would say a capability's operational rules are kept in its loaded file, not in its documentation.
- **`merge-claude-md.sh`** inserts each of its lines where that line is absent, not only when core's include is: a `CLAUDE.md` that holds core's include gains the index's line after it.
- **`pkit status`** reports the index and the capabilities it includes, beside the deployed skills and agents.
