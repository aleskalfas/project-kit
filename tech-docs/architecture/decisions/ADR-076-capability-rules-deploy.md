## Summary

**In plain terms:** this record is how project-kit builds [COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md), under which a capability's operational rules load in every session where it is installed.
- **The file:** a capability's loaded file is `.pkit/capabilities/<name>/rules.md`, generated and checked as core's is.
- **The deploy:** the Claude Code adapter copies it to `.claude/rules/pkit/<name>.md`, a folder of its own, and removes the copy at uninstall. The deploy and the check read the place from the adapter's package metadata, and which capabilities ship a set from one reading command.
- **The check:** validation fails a missing or differing copy where the copies' folder is in the checkout, and says so in a summary line where it is not.
- **What binds:** install, sync and upgrade name the rules each loaded set newly binds, core's included.
- **The harness requirement:** Claude Code answers it at a cost, route by route, and vouches for no version until a session is observed. How a confined run carries a capability's rules is decided before that run's tested range widens.

## Context

COR-070 decides that each adapter deploys an installed capability's loaded file, through a place of its own, where its harness loads files into every session, and that validation fails where a checkout's deploy left it missing. Its Implications leave to an architecture record:
- where the capability's loaded set and its loaded file live
- the form of the preface that names the capability's layer, and how validation reads a citation of its rules
- Claude Code's place, and how the adapter deploys there and removes what it deployed
- how the backbone learns an adapter's place, since it names no adapter's paths ([ADR-009](ADR-009-git-footprint-visibility.md) rule 1)
- where the check runs, and how it tells a checkout where the adapter deployed
- the harness requirement's entry and Claude Code's answer
- what brings existing projects level ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md))

Four records and the adapters' reference set the shape this one fits:
- **The loaded file** is generated by one function, written by `pkit rule-sets generate` and checked by validation's `rule-sets` member where the set is authored ([ADR-075](ADR-075-generated-operational-rules.md) points 2 to 5).
- **Rule-set files are found by where they are** ([ADR-056](ADR-056-backbone-file-schemas-home.md) point 2).
- **Each validator is a member of `pkit validate`,** and `error` is the one severity that fails ([ADR-058](ADR-058-validator-registry.md) point 2).
- **A component declares what it deploys outside `.pkit/`** in its package metadata, and the backbone aggregates the declarations (ADR-009 rule 1). Only paths that make up project-kit's presence go there (ADR-009 points 1 and 5).
- **The lifecycle runs an adapter's primitives by name** (the adapters README, "Primitives the lifecycle calls").

What Claude Code does with these files, as read from its documentation of memory files, subagents and hooks on 29 October 2026 ([memory](https://code.claude.com/docs/en/memory), [subagents](https://code.claude.com/docs/en/sub-agents), [hooks](https://code.claude.com/docs/en/hooks)):
- **What it loads:** every Markdown file under the project's `.claude/rules/`, found recursively, that carries no `paths:` field in its front matter, at a session's start as it loads the project's `CLAUDE.md`. After the session's context is compacted, these files are read again from disk.
- **Where it loads them:** in a session a person starts in the project, and in a subagent it starts from one, which loads every level of the `CLAUDE.md` hierarchy the main session loads, project rules included.
- **Where it does not:** the built-in Explore and Plan agents, and any agent definition that sets `omitClaudeMd`. A file matched by the `claudeMdExcludes` setting, in any settings layer, is dropped, and so is every project file where project instructions are set to `managed-only`. Project rules, the files under `.claude/rules/`, are skipped where `--setting-sources` leaves out the project's. The adapter's confined runner passes `--setting-sources ""` (the adapter README, "The confined form's closed set of flags").
- **What a confined run reads of `CLAUDE.md`:** the documentation says `--setting-sources` governs settings sources. Only `--bare` and `--safe-mode` are documented to skip `CLAUDE.md`, and the confined runner passes neither. [ADR-066](ADR-066-unattended-agent-runner.md) says a confined run reads every `CLAUDE.md` above the folder it starts in ("The person's instructions"). So such a run likely loads core's rules, through the include in `CLAUDE.md`, and not a capability's, under `.claude/rules/`. No run has been observed to settle it.
- **Links:** git checks a committed symbolic link out as a plain text file unless `core.symlinks` is on, as it is not by default on Windows. A link whose target lies outside the folder the session starts in is treated as an external import, which loads only once a person approves it.
- **An observation point:** the `InstructionsLoaded` hook fires when a `CLAUDE.md` or `.claude/rules/` file is loaded, with load reasons such as `session_start` and `compact`.

## Decision

**A capability's loaded file is `rules.md` at the root of its tree, generated and checked as core's is. The Claude Code adapter copies it to `.claude/rules/pkit/<capability>.md` through a deploy primitive of its own, reads that place from its package metadata, and removes the copy at uninstall. Validation's `rule-sets` member fails an installed capability whose copy is missing or differs where the copies' folder is in the checkout, and says in a summary line where it is not.**

### 1. The capability's loaded set and its loaded file

- **The set:** a rule-set file in the capability's `rule-sets/` folder with `loaded: true`, found by the location rule as the capability's other sets are. The `rule-sets` member no longer refuses a set marked loaded in a capability's folder (refinement of ADR-075 point 6). A second loaded set in one capability's folder is refused, as it is in any component's.
- **Its name:** the capability's own, such as `SWE`. The finding that two sets share a name (COR-051 point 3) already refuses a set named `OPS` or any other set's name.
- **Its preface:** the prose before its first rule names the capability, and states how its rules stand to the other layers, in the sentence the rules README gives: its rules add to core's and never loosen them; where one cannot be kept with a rule of core's, core's binds; a project's rules add to these and never loosen them; where one cannot be kept with a rule of another capability's, the session stops the step and reports the clash. The projection carries it into the loaded file (ADR-075 point 3). The `rule-sets` member fails a capability's loaded set whose preface does not name its capability, where the set is authored. The rest of the sentence is judged by whoever accepts the set.
- **The file:** `.pkit/capabilities/<name>/rules.md`. Its path comes from the set's owner: the one function that gives each owner's loaded file gives a capability's from its name, where ADR-075 point 2 holds one constant for the backbone's (refinement of ADR-075 point 2).
- **Written and checked as core's:** `pkit rule-sets generate` writes it where the capability is authored, and the staleness check of ADR-075 point 5 fails it there when it differs from its set. Where the capability arrives by sync or install, the file arrives with it, and neither runs.
- **One answer to which capabilities ship one:** a reading command of the `rule-sets` group, `pkit rule-sets loaded [--json]`, lists each loaded set the project holds, its owner and its loaded file, from the one function that gives each owner's loaded file ([ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 2). The deploy of point 2 and the check of point 4 both read it, so a capability's file is deployed exactly where it is checked. Where the capability is authored, the `rule-sets` member fails a `rules.md` at a capability's root with no loaded set behind it, so a file left behind by a removed set is never deployed unchecked.
- **No front matter:** the projection writes none (ADR-075 point 3). Here that is also what makes Claude Code load the file in every session: a `paths:` field would load it only beside the files it names.
- **Citations:** validation's `refs` member reads the form COR-070 point 1 gives, `<capability>:RS-<SET>-NNN`, beside `backbone:RS-OPS-0NN`, and warns of a citation of a missing or retired rule (ADR-075 point 8).
- **Origins:** each rule's origin cites a record of the capability's own (`<capability>:DEC-NNN`), a core record, or gives the decider's words, never an architecture or project record. The set is validated in every project that installs it, where those would resolve against the project's own records (ADR-075 point 1).

### 2. The Claude Code adapter copies the file into `.claude/rules/pkit/`

- **The primitive:** `deploy-rules.sh`, a fifth deploy primitive, which the lifecycle runs after `deploy-agents.sh`. The lifecycle's list of primitive names holds it. The script reads its place from the adapter's `loaded_rules:` key (point 3), and which capabilities ship a loaded set from `pkit rule-sets loaded --json` (point 1). For each such capability the manifest registers, it writes a copy of its loaded file, byte for byte, at that place.
- **A copy, not a link:** a rules file has no placeholders to resolve, but a copy loads in a Windows checkout and in a session started below the project's root, where a link would not (Context). The check of point 4 compares the copy with its file, so a copy edited or left behind fails.
- **Its own folder, and a record of what it wrote:** `.claude/rules/pkit/` is the adapter's. Beside the copies, the deploy keeps a record of the copies it wrote, in a file of its own whose name does not end in `.md`, so Claude Code loads no rules from it. Each run removes each copy the record names that is no longer a registered capability's, then writes the record again. A file in the folder that the record does not name is kept, with a `kept` line naming it, as `undeploy-capability.sh` keeps what it did not deploy. The folder goes once nothing but the record is left in it. A project's own files elsewhere under `.claude/rules/` are never read or written.
- **Undeploy:** `undeploy-capability.sh <name>` also removes the capability's copy where the record names it, and the folder as the deploy does.
- **The footprint:** `.claude/rules/pkit` is in the adapter's `footprint:`, and nothing else of `.claude/rules/` is (ADR-009 rule 1).
- **Version control:** a project that commits its deployed agents commits the copies the same way. project-kit's `.gitignore`, and the next steps `pkit init` prints, re-include `.claude/rules/` beside `.claude/skills/` and `.claude/agents/`.

### 3. The adapter declares where it deploys a capability's rules file

- **The key:** the adapter's package metadata holds `loaded_rules:`, a path from the project root that holds `{capability}` once: `.claude/rules/pkit/{capability}.md`. The package schema checks its shape.
- **Its contract, and no more:** the key says that the adapter deploys one copy, byte for byte, of each capability's loaded file, at the path the template gives with the capability's name. It says nothing of how a harness reaches the copy. An adapter whose harness reaches the files another way, such as one index file reached by a single include, which COR-070 point 2 allows, needs a key of its own or a validator it registers ([ADR-058](ADR-058-validator-registry.md) point 4). That is decided with that adapter.
- **What reads it:** the check of point 4, and the adapter's own `deploy-rules.sh` and `undeploy-capability.sh`. The backbone learns the place from the declaration and names no path of the adapter's (ADR-009 rule 1).
- **No key:** an adapter that declares none deploys no capability's rules file, and the check warns of it (point 4).

### 4. Validation's `rule-sets` member checks the deploy

- **Keyed on its own destination:** the folder the `loaded_rules:` template gives, `.claude/rules/pkit` for Claude Code. Where that folder is in the checkout, then for each capability the manifest registers that ships a loaded set (point 1), the path the template gives with the capability's name must hold the bytes of the capability's loaded file, once line endings are read as `\n`. Otherwise it is an `error`, `loaded-file-undeployed`, naming the capability, the adapter, the path and the sync that deploys it.
- **Where the folder is not:** a checkout without it, such as one that keeps `.claude/rules/` out of version control, gets a summary line of the member saying that the adapter's copies are not deployed there, so its sessions load no capability's rules. A state is a summary line, not a finding, as the member's counts are ([ADR-058](ADR-058-validator-registry.md) point 1).
- **One function for it:** one function compares what an adapter declares it deploys, at a destination, with what should be there, and gives the finding or the summary line. It is the methodology's first check of what a deploy leaves on the harness's side. The next such check, of skills or agents, reuses it.
- **No declaration:** a registered adapter without `loaded_rules:` gets one `warning`, naming the adapter and each capability that ships a loaded set, since that harness's sessions load no capability's rules (COR-070 point 6).
- **Where it runs:** in every project, where the capability is authored and where it arrives by sync, since the deploy is the project's own state. It reads files only, never a session.
- **Why this member:** the member that holds the rule sets' checks already has loaded sets and their files as its subject (ADR-075 point 5), and one subject keeps one member (ADR-058). The deploy of a loaded file widens that subject to where the file is deployed, and the member's help text says so.

### 5. The lifecycle says which rules it newly binds

- **What it prints:** install, sync and upgrade print, for each loaded set they deliver, core's `OPS` and each capability's alike, the set's name and version and each rule it newly binds, changes or retires since the copy it replaces. A first install lists every accepted rule by id and title.
- **How it knows:** one function beside the loaded-set projection compares two readings of a set's accepted rules, by id, status and statement. It knows no layer. The lifecycle reads each set before it copies the new version, and prints the function's answer.
- **A harness that loads no capability's rules:** where no adapter in use declares `loaded_rules:`, the line for a capability's set says that its rules bind no session in this project, rather than list them as bound (COR-070 point 3).
- **Not a gate:** the line informs and stops nothing (COR-068 point 5).

### 6. The harness requirement, and Claude Code's answer

- **The requirement:** `.pkit/schemas/harness-requirements.yaml` holds `session-loads-rules`. Its behaviour is that each session the harness starts in a project holds every file the methodology places for the harness to load, from the session's start and for its whole length, compaction included. That covers a session a person starts, a delegated helper and an unattended run. Its evidence is the design dependency of COR-070 point 6.
- **Its observation point, `interposed-runtime`:** COR-070 point 6 places the truth where a session runs, in the session itself or in what the harness runs at its own points during it. Of the two, the harness's own points reach every kind of session: Claude Code's `InstructionsLoaded` hook fires for each file loaded at a session's start and again after compaction (Context), in a helper and an unattended run as in a session a person starts. An agent inside a session sees its own context, not what a helper or an unattended run loaded, so `in-session` would place the truth where it cannot be read for those sessions. Out of session, the files are seen in place, not loaded.
- **Claude Code's answer, route by route:** `harness-support.yaml` answers it `at-cost`. The cost states what Claude Code's documentation says of each route by which a session gets the files (Context):
  - **Core's loaded file, through the include in `CLAUDE.md`:** loaded in a session a person starts, in a subagent dispatched with a definition of the project's, after compaction, and, by ADR-066's account, in a confined run. Not for Explore, Plan, a definition that sets `omitClaudeMd`, or where `claudeMdExcludes` or `managed-only` drop the file.
  - **A capability's copy, under `.claude/rules/pkit/`:** loaded in the same sessions, with the same exceptions, and not in a run whose settings sources leave out the project's, as the adapter's confined runner does.
  - **What the adopter keeps:** the copies out of `claudeMdExcludes`, and the methodology's work dispatched to definitions that do not set `omitClaudeMd`.
- **Its range:** `harness_versions` stays empty until a session is observed holding a copied file, so it vouches for no version. Only whoever observes it widens the range, as COR-047 point 2 requires. The `InstructionsLoaded` hook is where to observe it.
- **The confined run, a gap to close before its range widens:** by the documentation and ADR-066, a confined run is likely bound by core's rules and not by a capability's, the reverse of what a fixer working in a capability's area needs. The confined form is refused while its tested range is empty (ADR-066 points 2 and 12), so the gap binds no run until that range widens. How a confined run carries the capability's files is decided before it widens (Implications). One observed `--setting-sources ""` run, logging `InstructionsLoaded`, settles what such a run loads.
- **The report:** a requirement whose observation point the report cannot reach resolves `indeterminate` (COR-047 point 4). `pkit harness report` names the requirement with that reason, never as satisfied.

### 7. What brings existing projects level

- **The deploy:** the next sync or upgrade runs the deploy primitives, so `deploy-rules.sh` copies each installed capability's file. Nothing is renamed or removed, so no migration is due for the copies.
- **A private project:** the exclude region of a project made private holds the footprint as it was when the region was written. ADR-009 point 3 has install write the region again, and the build makes that good where the projection falls short of it (COR-065 point 4): install and sync render the region again from the aggregated footprint wherever it is present, and leave a project with no region alone. That covers this folder and every later growth of the footprint, so no adapter migration is due. Should a state remain that the next sync cannot mend, its migration is the backbone's, since the backbone owns the region.
- **Versions:** the adapter, and each capability that ships a loaded set, needs the backbone that lifts ADR-075 point 6's refusal, knows the fifth primitive and answers `pkit rule-sets loaded`, and declares that floor ([PRJ-002](../../../.pkit/decisions/project/PRJ-002-version-bump-policy.md) D4).
- **Nothing else:** the package schema gains an optional key, and a capability gains files, so no file that passes before the change fails after it (ADR-056 point 3).

## Rationale

**Why `rules.md` at the root of the capability's tree.** One loaded set to a component leaves one file, so a folder for it would hold one file. A capability's tree has no area of its own for rules, and the file's name says what a reader finds in it. The path is fixed by the owner, so no set can write another component's file (ADR-075, "Why the file's path is fixed by the set's owner").

**Why a folder of the adapter's own.** Claude Code reads `.claude/rules/` recursively, so a subfolder loads as the folder does. A folder of its own keeps a copy from ever sharing a name with a project's own rules file, and lets each run remove what it no longer deploys by the folder alone. It also keeps the footprint to what is project-kit's presence. A footprint naming all of `.claude/rules/` would have `pkit visibility private` offer to untrack a team's own rules files, and exclude every new one (ADR-009 points 1 and 5).

**Why a copy, not a link.** Agents are copied already. A link has two failure modes a copy does not: a Windows checkout without `core.symlinks` holds the link as a one-line text file, which Claude Code would load as a rule, and a link whose target lies outside the folder a session starts in waits for a person's approval. The byte-for-byte check catches a copy that drifts as surely as a broken link.

**Why a primitive of its own.** The lifecycle finds an adapter's primitives by name and runs each it finds, so an adapter whose harness has no such place ships none. A rules file is neither a skill nor an agent, and folding it into either deploy would give that script a second kind of content.

**Why the check is the backbone's, with the place declared.** The check must find the deployed file in every project, for each adapter in use. A path written into the backbone would name an adapter's place in core, the layering ADR-009 rule 1 forbids. An adapter could register a validator of its own (ADR-058 point 4), and one whose harness reaches the files another way will. For a copy at a path, though, one implementation in the backbone serves every adapter that deploys that way, and the backbone must warn of an adapter that declares no place in any case, which no adapter's validator can do for an adapter that has none. A declaration read from package metadata is data the package schema checks, as the footprint is. The scripts read the same key, so the path cannot differ between the deploy and the check.

**Why one reading command says which capabilities ship a loaded set.** The deploy and the check each need the answer. Two readings, a file's presence for one and the set for the other, could disagree: a `rules.md` left behind by a removed set would be deployed to every session and checked by nothing. One answer from the backbone, read through a command as ADR-057 point 2 asks of a component's script, keeps the two together, and the refusal of a `rules.md` with no set behind it closes the case where they would differ.

**Why the check keys on its own destination.** Where the copies' folder is in the checkout, a missing copy is a deploy left incomplete or a file removed by hand, which the next sync mends. A checkout without it is one where the deploy never ran, or one whose project keeps that folder out of version control. A project may keep `.claude/skills/` in version control and not `.claude/rules/`, so another of the adapter's folders is no sign that this one was deployed. Failing there would fail a healthy project for that choice (COR-070, "Why validation reports, rather than fails, where the place is absent").

**Why a record of what the deploy wrote.** The adapters' contract is that an adapter removes only what it deployed, and never what a project put there (the adapters README). Skills are known by their link's target and agents by a marker in each file, but a copy of a loaded file carries no mark, since the projection adds nothing to the set (ADR-075 point 3). A folder the project already had, or a file someone put in it, would otherwise be wiped on the first run. The record names what the deploy wrote, and its name keeps Claude Code from loading it as a rule.

**Why the check runs where the capability arrives by sync too.** The staleness check runs only where the set is authored, because a project receives the set and its file together and edits neither. The deploy is different: the project's own sync writes it, and an interrupted sync or a harness folder the project cleared can each leave it missing.

**Why the preface is checked for the capability's name alone.** That the file names its capability is a fact a check can read. Whether the rest of the sentence states the layering rightly is prose, which the person accepting the set judges ([COR-055](../../../.pkit/decisions/core/COR-055-validation.md)).

**Why Claude Code's answer names its exceptions route by route, and vouches for no version yet.** The documentation says which sessions load the files and which do not, and an `at-cost` answer states the second as what the adopter must keep in mind. Core's file and a capability's reach a session by different routes, an include in `CLAUDE.md` and a folder the harness reads, and the documentation treats the two differently in a run that leaves out the project's settings. One answer for both would hide that. Until a session is observed holding a copy, an answer that vouched for every version would be the confident unchecked claim COR-047 point 5 warns of. The runner's tested range (ADR-066 point 12) is the precedent: empty until observed.

**Why the confined run's gap is a precondition, not decided here.** What a confined run loads is unobserved, and the two accounts available point one way: core's rules through `CLAUDE.md`, a capability's not. Deciding now how a confined run carries a capability's files would rest on that unobserved reading. The gap binds no run while the confined form's tested range is empty. So the record keeps the place the maintainer chose, holds either way, and makes the decision a condition of widening the confined form's range. An observed run settles which of the ways under Alternatives closes it.

### Alternatives considered

- **The file at `.pkit/capabilities/<name>/rules/<name>.md`,** mirroring `.pkit/rules/core.md`. Not taken: a folder for one file, and a name said twice.
- **A link at `.claude/rules/<capability>.md`.** Rejected: a link fails in a Windows checkout and outside the folder a session starts in, as "Why a copy, not a link" says. A file directly in `.claude/rules/` could also share a name with a project's own, and would need the whole folder in the footprint.
- **Deploying the rules file in `deploy-skills.sh`.** Not taken: one primitive, one kind of content.
- **One index file of the adapter's own, reached by a single include inserted once in `CLAUDE.md`,** as COR-070 point 2 allows a harness with no such folder. Not taken for Claude Code: it reads `.claude/rules/` already, so no line in the project's file is needed. It is the way to close the confined run's gap if an observed run confirms that such a run loads `CLAUDE.md` and not `.claude/rules/` (point 6), since a capability's rules would then load wherever core's do. Adopting it would take the key of its own or the validator point 3 names.
- **The resolver carrying a capability's loaded file into each confined definition,** as it carries the workspace sentence. The other way to close the gap, decided with it before the confined range widens (point 6).
- **The start hook, adding each file as context at `SessionStart` and `SubagentStart`.** Not taken: it is the one route to Explore and Plan, but what it adds is summarised away at compaction and capped in size, and an adopter's own entry for the event takes the baseline's place.
- **The deploy's place written in the backbone.** Rejected by ADR-009 rule 1.
- **A validator the Claude Code adapter registers** (ADR-058 point 4). Not taken for a copy at a path, as "Why the check is the backbone's, with the place declared" says. It stays open to an adapter that reaches the files another way.
- **The check keyed on any folder of the adapter's footprint.** Rejected: the footprint says what is project-kit's presence (ADR-009 point 1), not that a deploy ran, and a project may keep one of its folders in version control and not another, as "Why the check keys on its own destination" says.
- **Removing every file in the copies' folder that is no registered capability's.** Rejected, as "Why a record of what the deploy wrote" says.
- **The check failing in every checkout.** Rejected, as "Why the check keys on its own destination" says.
- **An adapter migration for a private project's exclude region.** Rejected: it would repeat in an adapter's script the region's format, which the backbone owns, and mend this folder alone, while every later growth of the footprint would leave the region behind again.
- **Claude Code's answer as `full`, for every version.** Rejected, as "Why Claude Code's answer names its exceptions" says.

## Implications

- **Which rules move, proposed for the person to accept.** The build proposes each rule change below in its pull request, and a person accepts each there (COR-066). This record says only where each would go, as COR-070 point 5 decides.
  - **software-engineering's loaded set** would hold a new rule, with an origin of its own, for what of project rule 2 holds wherever code is engineered: while building, a session runs the tests of what it changed and the project's fast checks, and leaves the full suite to where the project runs it, where it runs one. project-kit's `project.md` keeps what is project-kit's own, `scripts/check.sh` and its two-suite limit, and points to the capability's rule.
  - **project-management's loaded set** would hold the work tracker's own requirements that core rule 9 defers to "the installed work-tracking capability's documentation", beyond what [COR-008](../../../.pkit/decisions/core/COR-008-git-conventions.md) decides for every project: that a pull request's body opens with `Closes #<issue>`, by the bundle's template ([COR-009](../../../.pkit/decisions/core/COR-009-pr-workflow.md) point 3), and the label conventions. COR-009's other points, squash-merge, conventional titles, short-lived branches and pull requests recommended rather than enforced, bind wherever pull requests are used, so they stay core's.
  - **Branch naming stays core's.** The form `<type>/<issue-number>-<slug>`, its issue number and the rule that a branch has a related issue included, is decided by COR-008's operational reference for every project. Core rule 9 keeps its claim, conventional commits with one logical unit each, and points to COR-008 for branch naming rather than to a capability's documentation, naming no capability. COR-008 names one host's issues there; whether that reads true in every project is COR-008's question, which this record leaves to it.
  - **Core's set, `OPS`:** rule 12 would say the adapter deploys a capability's rules file beside skills and agents. Its preface would gain the statement of how the layers stand that COR-070's Implications give, and its closing paragraph, "Where these rules came from," would say a capability's operational rules are kept in its loaded file, not in its documentation.
- **`pkit status`** reports each deployed rules file beside the deployed skills and agents.
- **The confined run carries a capability's files before its range widens.** How it does, by the resolver's definition or by the include-reached form (point 6), is decided in an issue of its own before ADR-066's tested range widens (ADR-066 points 2 and 12). Observing a session through the `InstructionsLoaded` hook, so the requirement's range can widen, is another.
- **ADR-009 point 3** holds once the build lands (point 7), and needs no edit.
- **ADR-075 points 2 and 6** gain forward pointers to this record once it is accepted.
- **The adapters README** says that a script's name is the lifecycle's whole contract with a primitive, while validation also reads where an adapter deploys a capability's rules file.
- **Stands on these records, all accepted:** COR-008, COR-009, COR-010, COR-047, COR-051, COR-055, COR-065, COR-066, COR-068, PRJ-002, ADR-009, ADR-056, ADR-057, ADR-058, ADR-066 and ADR-075, and on COR-070 once it is accepted.
