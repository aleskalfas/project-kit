## Summary

**In plain terms:** this record is how project-kit builds [COR-070](../../../.pkit/decisions/core/COR-070-capability-loaded-rules.md), under which a capability's operational rules load in every session where it is installed.
- **The set and its file:** a capability's loaded set sits in its `rule-sets/` folder like its other sets. Its loaded file is `.pkit/capabilities/<name>/rules.md`, written by `pkit rule-sets generate` and checked as core's is.
- **The deploy:** the Claude Code adapter links that file to `.claude/rules/<name>.md`, which Claude Code loads at every session's start, through a deploy primitive of its own. Uninstall removes the link.
- **The declaration:** the adapter's package metadata says where it deploys a capability's rules file, so the backbone can check the deploy without knowing `.claude/`.
- **The check:** validation's `rule-sets` member fails an installed capability whose file is missing at that place, or differs from the capability's file.
- **The harness requirement:** every session holds the loaded files from its start. Claude Code answers it vouching for no version until a session is observed holding one, and the report reads it as indeterminate.

## Context

COR-070 decides that each adapter deploys an installed capability's loaded file where its harness loads files at every session's start, and that validation fails where it is missing. Its Implications leave to an architecture record:
- where the capability's loaded set and its loaded file live
- Claude Code's place, and how the adapter deploys there and removes what it deployed
- how the backbone learns an adapter's place, since it names no adapter's paths ([ADR-009](ADR-009-git-footprint-visibility.md) rule 1)
- where the check runs
- the harness requirement's entry and Claude Code's answer
- what brings existing projects level ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md))

Five records set the shape this one fits:
- **The loaded file** is generated by one function, written by `pkit rule-sets generate` and checked by validation's `rule-sets` member where the set is authored ([ADR-075](ADR-075-generated-operational-rules.md) points 2 to 5).
- **Rule-set files are found by where they are** ([ADR-056](ADR-056-backbone-file-schemas-home.md) point 2).
- **Each validator is a member of `pkit validate`,** and `error` is the one severity that fails ([ADR-058](ADR-058-validator-registry.md) point 2).
- **A component declares what it deploys outside `.pkit/`** in its package metadata, and the backbone aggregates the declarations (ADR-009 rule 1).
- **The lifecycle runs an adapter's primitives by name** (the adapters README, "Primitives the lifecycle calls").

Claude Code loads, at the start of a session, every Markdown file in the project's `.claude/rules/` that carries no `paths:` field in its front matter, as it loads the project's `CLAUDE.md`. A file there may be a symbolic link into the repository. These are the facts the maintainer recorded on #2269, from Claude Code's documentation of its memory files.

## Decision

**A capability's loaded file is `rules.md` at the root of its tree, generated and checked as core's is. The Claude Code adapter links it to `.claude/rules/<capability>.md` through a deploy primitive of its own, declares that place in its package metadata, and removes the link at uninstall. Validation's `rule-sets` member fails an installed capability whose deployed file is missing or differs.**

### 1. The capability's loaded set and its loaded file

- **The set:** a rule-set file in the capability's `rule-sets/` folder with `loaded: true`, found by the location rule as the capability's other sets are. The `rule-sets` member's refusal of a set marked loaded in a capability's folder (ADR-075 point 6) is lifted. A second loaded set in one capability's folder is refused, as it is in any component's.
- **The file:** `.pkit/capabilities/<name>/rules.md`. Its path comes from the set's owner, as ADR-075 point 2 decides for every loaded set: the one function that gives each owner's loaded file gives a capability's from its name.
- **Written and checked as core's:** `pkit rule-sets generate` writes it where the capability is authored, and the staleness check of ADR-075 point 5 fails it there when it differs from its set. Where the capability arrives by sync, the file arrives with it, and neither runs.
- **No front matter:** the projection writes none (ADR-075 point 3). Here that is also what makes Claude Code load the file in every session: a `paths:` field would load it only beside the files it names.

### 2. The Claude Code adapter links the file into `.claude/rules/`

- **The primitive:** `deploy-rules.sh`, a fifth deploy primitive, which the lifecycle runs after `deploy-agents.sh`. For each capability the manifest registers whose `rules.md` exists, it writes the relative link `.claude/rules/<capability>.md`, pointing at `../../.pkit/capabilities/<capability>/rules.md`.
- **Stale removal:** each run removes a link of its own whose capability is no longer registered, or whose file is gone. Its own links are the symbolic links in `.claude/rules/` that point into `.pkit/capabilities/`.
- **The project's files:** a real file in `.claude/rules/`, or a link pointing elsewhere, is the project's, and the deploy never touches it. Where one takes a capability's name, the deploy writes no link and prints a `kept` line, and validation fails (point 4).
- **Undeploy:** `undeploy-capability.sh <name>` also removes `.claude/rules/<name>.md`, where it is the link into that capability.
- **The footprint:** `.claude/rules` joins the adapter's `footprint:` (ADR-009 rule 1).

### 3. The adapter declares where it deploys a capability's rules file

- **The key:** the adapter's package metadata gains `loaded_rules:`, a path from the project root that holds `{capability}` once, such as `.claude/rules/{capability}.md`. The package schema checks its shape.
- **What reads it:** the check of point 4, and nothing else. The backbone learns the place from the declaration and names no path of the adapter's (ADR-009 rule 1).
- **No key:** an adapter that declares none deploys no capability's rules file, and the check warns of it (point 4).

### 4. Validation's `rule-sets` member checks the deploy

- **The check:** for each capability the manifest registers that ships a loaded set, and for each adapter the manifest registers that declares `loaded_rules:`, the declared path with the capability's name must exist. Read through any link, it must hold the bytes of the capability's `rules.md`, once line endings are read as `\n`. Otherwise it is an `error`, `loaded-file-undeployed`, naming the capability, the adapter, the path and the sync that deploys it.
- **No declaration:** a registered adapter without `loaded_rules:` gets a `warning` for each capability that ships a loaded set, naming the adapter, since that harness's sessions load no capability's rules (COR-070 point 6).
- **Where it runs:** in every project, where the capability is authored and where it arrives by sync, since the deploy is the project's own state. It reads files only, never a session.
- **Why this member:** loaded sets and their files are its subject already (ADR-075 point 5), and one subject keeps one member (ADR-058).

### 5. The harness requirement, and Claude Code's answer

- **The requirement:** `.pkit/schemas/harness-requirements.yaml` gains `session-loads-rules`. Its behaviour is that each session the harness starts in a project holds every file the methodology places for the harness to load at session start, from the session's start. That covers a session a person starts, a delegated helper and an unattended run. Its observation point is `in-session`, and its evidence is the design dependency of COR-070 point 6.
- **Claude Code's answer:** `harness-support.yaml` answers it `at-cost`. The cost says that Claude Code's documentation has a session started in the project load these files, and that no source shows whether a delegated helper's context holds them. Its `harness_versions` stays empty until a session is observed holding a deployed file, so it vouches for no version. Only whoever observes it widens the range, as COR-047 point 2 requires.
- **The report:** an `in-session` requirement resolves `indeterminate` from outside a session (COR-047 point 4). `pkit harness report` names the requirement with that reason, never as satisfied.

### 6. What brings existing projects level

- **The deploy:** the next sync or upgrade runs the deploy primitives, so `deploy-rules.sh` links each installed capability's file. Nothing is renamed or removed, so no migration is due for the links.
- **A private project:** the exclude region of a project made private holds the footprint `pkit visibility private` wrote, and no sync rewrites it. An adapter migration, at the adapter version that adds `.claude/rules` to the footprint, adds that entry to the region where the region exists and lacks it. The links then stay out of the project's commits. It acts on that sign alone and is idempotent (core rule 5).
- **Nothing else:** the package schema gains an optional key, and a capability gains files, so no file that passes today fails (ADR-056 point 3).

## Rationale

**Why `rules.md` at the root of the capability's tree.** One loaded set to a component leaves one file, so a folder for it would hold one file. A capability's tree has no area of its own for rules, and the file's name says what a reader finds in it. The path is fixed by the owner, so no set can write another component's file (ADR-075, "Why the file's path is fixed by the set's owner").

**Why a link, not a copy.** An agent is copied because the deploy resolves placeholders in it. A rules file has none, and Claude Code follows a link in `.claude/rules/`. A link cannot drift from the file it points at, so the check reads only that it is there and right.

**Why a primitive of its own.** The lifecycle finds an adapter's primitives by name and runs each it finds, so an adapter whose harness has no such place ships none. A rules file is neither a skill nor an agent, and folding it into either deploy would give that script a second kind of content.

**Why the adapter declares the place.** The check must find the deployed file in every project, for each adapter in use. A path written into the backbone would name an adapter's place in core, the layering ADR-009 rule 1 forbids. Running an adapter's script from validation would make validation depend on what a script does. A declaration read from package metadata is data the package schema checks, as the footprint is.

**Why the check runs where the capability arrives by sync too.** The staleness check runs only where the set is authored, because a project receives the set and its file together and edits neither. The deploy is different: the project's own sync writes it, and a project file at the place, an interrupted sync or a harness folder the project cleared can each leave it missing.

**Why Claude Code vouches for no version yet.** The documentation covers a session started in the project. What a helper's context holds is not documented. An answer that vouched for every version would be the confident unchecked claim COR-047 point 5 warns of. The runner's tested range ([ADR-066](ADR-066-unattended-agent-runner.md) point 12) is the precedent: empty until observed.

### Alternatives considered

- **The file at `.pkit/capabilities/<name>/rules/<name>.md`,** mirroring `.pkit/rules/core.md`. Not taken: a folder for one file, and a name said twice.
- **A copy in `.claude/rules/`.** Not taken: a copy can drift, and nothing needs resolving.
- **Deploying the rules file in `deploy-skills.sh`.** Not taken: one primitive, one kind of content.
- **The deploy's place written in the backbone.** Rejected by ADR-009 rule 1.
- **The check as a mode of the adapter's deploy script.** Rejected: validation would run an adapter's script, and its result would rest on what the script does.
- **A folder of the adapter's own under `.claude/rules/`.** Not taken: the documentation the maintainer cited speaks of files in `.claude/rules/`. A capability's name stays clear of a project's own rules file there, which the deploy keeps and the check reports.
- **Claude Code's answer as `full`, for every version.** Rejected, as "Why Claude Code vouches for no version yet" says.
