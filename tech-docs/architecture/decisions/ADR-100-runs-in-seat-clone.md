## Summary

**In plain terms:** [project-management:DEC-082-pace-of-subagents] lets the project-manager agent run several subagents at once in a clone, up to a pace, and has the build and review commands hold the agent's calls to that pace from a register of the clone's runs. [ADR-073](ADR-073-builder-runs.md) built the build command for one build at a time in a seat's clone. This record says how a clone runs at a pace:

- **Builds at once, one for each Task.** Each build keeps a state file of its own, keyed by its Task, written under a lock of its own from its first state on. For the builds beside it, a build is refused only where a build of the same Task runs or waits, or the Task's earlier state still names a process that lives or cannot be read, or, on the agent's call, where no slot is free, and ADR-073's other refusals stand. A session acts on each build it finds as its work allows, and waits on none before other work.
- **Hand-backs take turns.** One hand-back at a time in a clone, each writing only its own reference and its Task's branch, and each pinned to the built commit the backbone's record of the run keeps (point 4).
- **One register, each run entered once.** A build's state file is its entry while it holds a slot. Each other run of a command on the agent's call, and each helper a lead dispatches, has one entry, written by what runs it. An entry counts while a process it names lives, a build's run and its checks among them, and a build's while its lock is held too. A run that outlives its helper's entry counts against the pace itself, so no run the register holds counts nowhere. A command reads the register and enters its run under one lock.
- **What the runtime folder steers.** What lies in the runtime folder can decide whether a command acts, never what it acts on. The state files and the register lie where a sandboxed command writes. So from what it reads there, a command outside the sandbox decides only whether it counts, waits, refuses, reports, posts on the Task's record, moves the Task's references or recovers a build. What each act acts on, and the runner it runs, it takes from the backbone's own record of each run, which no sandboxed command writes (point 5).
- **The agent's call is told by its session.** The adapter declares, as data the backbone reads, how a command finds the harness session whose shell runs it. A command that finds one runs on the agent's call, and any other run is a person's. The command the agent reads its pace with, once in each session before its first subagent, says whether it found the session, so a harness that does not find it from the session's own shell when the check runs is told to the person. A harness requirement records what this asks of the harness.

**Why an ADR.** The register spans the backbone, the adapter and the capability's commands: a declaration of the adapter, a reading the backbone gives, and the commands of project-management that count and start runs. How those parts share one clone's runs is what the project built, an architecture record's question ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Distinct from PRJ"). This record realises DEC-082 as ADR-073 realises [project-management:DEC-063-task-builder].

## Context

**What stands.**

- **One build at a time.** The build command starts a build in a clone of its own, detached, and keeps its state in one file of the seat's clone, which the seat polls with `--wait`. It allows one build at a time in a seat's clone, and refuses a second while one runs (ADR-073 point 5). A session that starts in a clone with a build in that file goes on from it before any other work.
- **The hand-back.** A build's commits come back through a temporary reference of the seat's clone, signed there, and move the Task's branch as a reference (ADR-073 point 8).
- **Reviewers and fixers.** The review and drift commands start each reviewer and each fixer as a process of the backbone's run command ([ADR-066](ADR-066-unattended-agent-runner.md) point 10). Reviewers run unconfined in the checkout, and in a seat's clone each in a clone of its own ([ADR-102](ADR-102-reviews-in-own-clone.md)).
- **The runtime folder.** The capability keeps a git-ignored folder in each working tree. It holds the clone's identity, with its key ([project-management:DEC-035-instance-ownership] point 1), and the build's state file. How a linked worktree reads its clone's identity is not decided ([project-management:DEC-059-topology-of-seats] point 6).
- **What a sandboxed command writes is not trusted outside the sandbox.** Code that runs outside the sandbox without a person choosing it, the methodology's own commands among it, never takes its code from a place a sandboxed command can write, takes a widening from such a place only where a person shown it makes it, and lets no sandboxed command choose or redirect where it writes. The rule binds every later architecture record ([ADR-095](ADR-095-hook-out-of-reach.md) point 1). The runtime folder lies in the working tree, which a sandboxed command writes (ADR-095 point 2, "Not where a sandboxed command writes by default"), and on macOS the methodology's command runs outside the sandbox ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 2).
- **No adapter declares a fact of a live session.** The folder a session is rooted in, its anchor ([ADR-034](ADR-034-foreign-repo-mutation-guard.md)), is read by the backbone's guard against changing another repository under the name of Claude Code's own variable, and the capability keeps a copy of that reading in its own guard. No adapter declares it for the backbone to read.
- **The harness's mark of a tool's process.** The backbone tells a process that the harness's shell tools or hooks started, and each process such a process starts, by the mark the harness sets in it ([ADR-093](ADR-093-writes-outside-the-repository.md)'s Context, "What marks a tool's process", and point 4). ADR-095 builds that test once, for the command that names a folder and for its interlock on widening (ADR-095 point 3). The mark names no session.
- **The harness requirements.** The core declares what it requires of the harness, and each adapter answers how far its harness meets it ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), as ADR-066 point 13 and ADR-073's Implications did for the runs they rest on.

**What DEC-082 decides.** One pace for each clone, all its sessions together, counted in slots. Every subagent the agent runs holds a slot while it runs, but a helper while it hands its slot to its own, a build keeps its slot through the build's checks, and a run a person starts themselves holds none. A register of the clone's runs, read by the build and review commands, holds the agent's calls to the pace, where a command can tell that call from a person's. A lead enters each helper with a share of its slots, and the runs a helper's commands start count within that share. A Task that waits holds no slot. DEC-082 leaves to this record a state file for each build, a `--wait` that names no Task, recovery over each build, how fetches, signing and hand-backs share one clone, the register's form, and the sign that tells the agent's call. DEC-082 rests on [project-management:DEC-081-delegation-between-seats], and both are accepted with this record.

**Terms.** *The agent*, *a subagent*, *the pace*, *a slot*, *the ceiling* and *the build's checks* are DEC-082's.

- **The clone** is the working tree a command runs in, with the capability's runtime folder there, whether or not that folder holds an identity yet: a clone makes its key only when it first claims ([project-management:DEC-058-state-issues] point 5). **Its runtime folder** is that folder.
- **An entry** is one record of the register (point 5).
- **A session's process** is the process of the harness session whose shell runs a command, as the adapter finds it (point 9).

## Decision

**In a clone, builds run at once, as many as the pace allows on the agent's call, one for each Task, each with a state file of its own, and hand-backs take turns. The clone counts the runs that take its slots in one register, which a command reads and enters its run in under one lock, and a command tells the agent's call by the harness session whose shell runs it. What a command outside the sandbox reads in the runtime folder decides only whether it acts, and what it acts on comes from the backbone's own record of each run.**

### 1. Builds run at once, one for each Task

- **As many as the pace allows.** On the agent's call, the build command starts a build only where a slot is free (points 5 and 7). A build a person starts themselves takes none (point 9), as DEC-082 point 1 has it. This holds in a seat's clone, and in a clone with no seat, which runs at the ceiling (DEC-082 point 8).
- **One for each Task.** A Task has at most one build that runs or waits, on its question or on its hand-back. A build of a Task whose earlier build runs or waits is refused (exit 1), since `--answer` resumes that build and `--hand-back` finishes it (ADR-073 points 7 and 8). So is a build of a Task whose earlier state still names a process that lives, a first build, a fix round (`--fix`) and a merge (`--merge`) alike, since its first state would write over the state that counts that process (point 6), and so is a build of a Task whose state file cannot be read (point 5). Each refusal names that state, as the refusal for no slot free names the entries that hold the slots. `--answer` is not refused so, since the build it resumes waits, and a build waits only once the runner has confirmed its run's sandbox empty before its clone's check, its harness having ended with its run, and its checks have ended, as the state records (point 5), so the state it writes over names no process that lives (ADR-073 point 1, and point 6's precedence).
- **No slot free.** On the agent's call, a build with no slot free is refused too (exit 1), with the pace and the count the command read and the entries that hold the slots, so the person sees which run holds each, and nothing starts. So is an `--answer` on the agent's call that finds no slot free for the run it would resume (point 7).
- **Each build's own.** Each build has its own state file, keyed by its Task, in the runtime folder, and its own temporary reference for its hand-back, named for its Task. Its clone and each run's settings folder are named for the build, its Task in its clone, and apart for each run that makes one. Each run's progress file lies in that run's settings folder, beside the backbone's record of the run (point 2): the run command writes it there, under the name the caller gives, and reports its path to the caller as the run starts. Where a Task's earlier build kept its clone, the earlier record and its clone stay beside the new build's, since each is named apart for its run, and a person removes kept clones (point 10). So two builds write nothing in common but the register and, through their hand-backs, the seat's repository (point 4).
- **The seat's checkout stays as it is.** Builds at once leave the seat's working tree clean and on the default branch, as ADR-073 point 8 keeps it. No reviewer works in it (refinement per [ADR-102](ADR-102-reviews-in-own-clone.md)).

### 2. Each build's state has one writer at a time, and each build is recovered once

- **A lock for each build.** A build's state file is written only under a lock of its own, which the operating system releases when its holder ends, however it ends. What this point says of the lock holds among the methodology's own commands, and point 10 says what a sandboxed command that removes the lock's file leaves. Its writers:
  - the command that writes the build's first state, the build command or `--answer` for a run it resumes, which takes the lock before it writes;
  - the detached process that command starts, which holds the lock while it lives;
  - `--hand-back`, for its hand-back;
  - a command that recovers the build (ADR-073 point 5).
- **No gap at the start.** The command that writes the first state holds the lock until it starts the detached process, and the lock passes to that process with no moment in which neither holds it, such as by a descriptor the process inherits. So a command that reads a build's first state finds its lock held, and never takes a build that is starting for one that is lost.
- **The detached process alone.** The lock passes to the detached process and to no process it starts: no run or check of the build inherits its descriptor, which is not opened for writing. So only a writer of the build holds the lock, and only while it lives.
- **The detached process names itself.** The command writes nothing in the state after it starts the detached process, and that process's first write under the lock names it there. Until then the state names the command. So the command's last write comes before the detached process's first. The detached process then names in the state the run's processes as the runner reaches them, the harness and each check's process, as the runner starts each and reports its id and start time (point 6).
- **Named before it runs.** The harness and each check's process are named in the state before they run anything: the runner holds each process it starts, for instance on a pipe from the detached process, until the detached process has written it into the state, and the held process exits where the pipe closes first. The backbone's run command relays that exchange, lets a held process go only once its caller does, and ends the held process where its caller's end of the pipe closes. So a detached process killed between the start of one and naming it leaves none running that the state does not name.
- **The first state comes before the build's event.** On the agent's call, the first state is the build's entry (point 5), written under the register's lock, under which no tracker call runs (point 7). So, for every build alike, it comes before the build's start event, or, for `--answer`, its resume event, which the command posts once it has let the register's lock go. The run still starts only once that event is posted (ADR-073 point 9). Once it is, the command records in the state that it is posted, and that is its last write before it starts the detached process. Where the event cannot be posted (exit 3), the command makes the state final itself before it exits, a first build at exit 3 and a resumed build back at its question (exit 6), as it stood before `--answer` ran, so no recovery reads it.
- **Recovered before its event.** ADR-073 point 9 posts an ending only for a build whose start event is posted. So a recovery reads from the state whether the event of the run that its latest first state begins is posted: the build's start event, or, for a run `--answer` resumes, its resume event. A state that does not record it gets no ending:
  - A first build becomes final, lost (exit 5), with no ending.
  - A resumed build goes back to waiting on its question (exit 6), as it stood before `--answer` ran, with the person's answer unspent. The Task's record, which shows no resume but in point 10's window, shows the question waiting too.
- **The lock tells the writers gone.** A command that reads a state that is not final, and takes its lock, knows that no writer lives, whichever process the state names. It reads the state again under the lock, and recovers that build as ADR-073 point 5's "Recovery" says, by the lock and not by a process's id, and as this point adds. So two commands that find one build at once recover it once. A count under the register's lock only tests a build's lock, and leaves the build's recovery until it has let the register's lock go (point 7).
- **Nothing left of the build's harness or sandboxes.** Before it marks a build lost, a recovery ends the build's harness where it still lives, and what is left of the build's sandbox and of its checks' sandboxes, a process in a session of its own among them, and confirms that none lives (ADR-073 point 1, and its probe). As point 5's rule has it, it ends only what the backbone's record of the build's runs confirms as the build's:
  - a process of the run or of a check, by its membership of a sandbox that the record names for the build or for one of its checks, as the runner tells it before a check (ADR-073 point 1);
  - the harness, which the sandbox does not hold, since it runs its hooks and file tools outside it (ADR-095's Context), by a file of that record's folder on its command line: the settings the runner wrote for this build (ADR-073 point 2).

  Where it cannot confirm that none is left, it marks the build lost all the same, not borne out (exit 5), its clone kept, as the runner does where it cannot (ADR-073 point 1). Either way the build's slot stays held while a process its state names lives (point 6), so marking the build final frees no slot that process holds.
- **The backbone's record of each run.** It lies in the run's settings folder, the guarded folder ADR-073 point 2's runner writes the run's settings to, which no sandboxed command writes (ADR-095 points 2 and 4):
  - **What it holds.** A record of its own for each run: which build and clone it is, the branch and commit the clone was made at, the head its runner was read from, its session, its caller and its sandboxes, and, while a hand-back may still bring it back, the commit the run ended built at. The backbone gives each run its own id, a first build, a resumed run, a fix round and a merge each one, and keys its records by clone, Task and run, the clone by its real path, as ADR-095 point 3's index records a folder. A record keeps the build's name, its Task in the clone it runs in, which the detached process passes the run command when it asks for the run; the build's clone; the branch and commit the clone was made at, which the caller of the run that made it passes (ADR-066 point 2), carried into a resumed run's record: those the command that starts the build found for the Task, as ADR-073 point 1 has its caller name them, passed to the detached process and never read from the runtime folder, and the same holds for the Task's branch at which `--answer`'s fallback makes its clone ("Where none is found"); the default branch's head the run's runner was read from (ADR-073 point 2); the harness session's id the run command got back (ADR-066 point 2); the run's caller, the detached process, by the id and start time the run command knows; and the commit the run command's own check of the clone saw at the branch's head (ADR-066 point 1, ADR-073 points 1 and 8), which the record keeps as the commit the run ended built at once that caller gives its word that the run ended built, taking only "built" on the caller's word and no commit. A run that ended built is one whose ending is built by ADR-073 point 6's precedence (exit 0 or 9): its result built, the clone's check and its checks bearing it out, and no call its own denies refused. The caller gives its word before its own hand-back begins. Where the record cannot keep it, the hand-back moves nothing, at exit 5, and the build is reported not borne out. The record keeps a built commit, from its caller's word, only while a hand-back may still bring it back. Whatever ends the build without moving the branch, at any ending but an exit 9 that leaves the build waiting on its hand-back, clears it before it posts its event:
    - a hand-back that ends at exit 5 or is given up;
    - a recovery that marks the build lost;
    - a recovery that finds the Task's branch already at the state's commits.

    The hand-back that moved the branch removes the record ("How long it lives"). Point 10 names where the clearing fails. The runner records there what identifies the run's sandbox and each check's as it starts them.
  - **How it is reached.** Only through the backbone's run command, given the clone and the Task alone: a command asks it, and takes what it acts on from its answer. Its call that starts no agent, which is no run, acts on every live record for them, so no field of the state chooses among them. It runs the runner read from the head each record names, so the runner that reads what it recorded is the one that recorded it. A record the run command cannot read whole confirms nothing and names no clone, so no command takes an earlier record's clone in its place, and the recovery then marks the build as it does where it cannot confirm that none is left (above). The call returns what the latest record names, the clone, the branch, the commits and the default branch's head among them, the latest by the backbone's own order of the ids it gives. The same call takes each word this point has a command give after the run (above, and "How long it lives"). `--hand-back` and `--answer` reach the record the same way, and take the latest record for the clone and the Task, and `--answer` resumes the session that record names. A resumed run's caller passes the default branch's head its build's start event names (ADR-073 point 7). Before it writes the build's first state, as its count of the slots comes before that state (point 7), `--answer` reads the latest record and compares that head with the head the record names. Where it cannot read the record whole, it refuses, with exit 1, and takes no fallback, and where the heads differ, it refuses, with exit 1. Either way the question stays unspent, as where no slot is free. Each of these refusals names the way out the records give, and where they give none, says that the question waits until a person acts (point 10). The run command's own refusal of a resume whose head is not the one the latest record names stays as the backstop: it comes once the resume event is posted, so the ending that follows closes the build at exit 7 (ADR-073 points 6 and 9), and the answer is spent. So nothing the folder holds chooses the code a resumed run runs. The session the state names only points the way.
  - **A live caller.** The call ends nothing of a run whose caller lives, and nothing for the clone and the Task while the latest record's caller lives, and says so. So ending what is left of an earlier record never ends a live resumed run in the same clone. A recovery or a hand-back that hears this marks nothing and leaves the build to its caller, and a `--hand-back` that hears it exits 1.
  - **How long it lives.** A record lives while a process it confirms as the build's lives, or while the clone it names exists. The backbone removes a record with its clone only on the word of the hand-back that fetched that clone's commits and moved the Task's branch to them, and with it every record that names that clone. That hand-back gives its word after its event and before it writes the build's final state, as a clearing comes before its event. It never removes one on what a state says, nor while a process it confirms as the build's lives. A record that no longer lives is removed when next read. A recovery that finds the Task's branch already at the commits the state names posts the hand-back event and keeps the clone, since it fetched nothing.
  - **Where none is found.** The call says so and ends nothing, and no command acts on the build's clone. A recovery then posts the hand-back event where the Task's branch holds the hand-back's commits, which needs no clone (ADR-073 point 5, "Recovery"). It gives any other hand-back under way up, with no clone acted on, as ADR-073 point 8's "A hand-back given up" does: it moves nothing and posts the given-up event that closes the wait, posting an exit-9 ending first only where the build has posted none, and the build command exits 1. Another command that recovers reports the given-up hand-back and keeps its own exit. A build whose event is not recorded as posted it treats as "Recovered before its event" says, and any other build is lost, not borne out (exit 5), with no clone acted on. `--hand-back` with no record gives the hand-back up in the same way, and `--answer` with no record takes ADR-073 point 7's fallback: a fresh builder, given the brief, the question and the answer, whose clone is made as a first build's is, at the Task's branch, without the earlier build's unreturned work.
- **The processes the state names only narrow.** They keep a slot held (point 6), and by point 5's rule never have a recovery end a process the backbone's record does not confirm, so a state written to name a process outside the build has no command end it. Of what names the build, only the Task and the clone come from the runtime folder: the Task from the state file's name, taken only as the tracker's issue id and matched as a key of the backbone's own records, joined into a name only as that id, and the clone as point 5's "The folder they find" says. So a state forged to name another build's harness, clone, settings or branch leads a recovery only to a run the backbone recorded under that Task in that clone, and a clone it made, with the branch it recorded, which only narrows.
- **A session goes on from every build.** A session that starts in a clone reads each build's state before it takes other work. It then acts on each as DEC-082 point 4 orders its slots: a finished build as work in flight, a build that waits as its wait asks, and a running build left to run while the session fills its other slots. It waits on no running build before other work.

### 3. `--wait` waits on one Task's build, or on whichever of the clone's ends first

- **With a Task,** it waits on that Task's build, as ADR-073 point 5's "Waiting" says, and exits with that build's code.
- **With no Task,** it waits on every build of the clone that runs when it starts. It returns once one of them ends, naming its Task, with that build's code; where several have ended when it reads, with the code of the first to end, by the times their states name. Where none ends within the time, it exits 8. Where none runs when it starts, it says so and exits 1.
- **Every wait lists the clone's builds,** each with its Task and its state, so a session finds a build that ended while it was not waiting.

### 4. Hand-backs take turns, and each writes only its own references

- **One at a time in a clone.** A hand-back takes a lock of the clone's for its whole span: its check of the build's clone, its fetch, its signing and its move of the Task's branch (ADR-073 point 8). The operating system releases the lock when its holder ends. A hand-back that waits for the lock holds no slot. What this point says of the lock holds among the methodology's own commands, as point 2 says of a build's lock (point 10, "A lock removed while held").
- **Its own references.** It fetches into its build's temporary reference, and moves only the branch the backbone's record of the run names (point 2), and only from the commit the branch held when the hand-back began, so a branch that moved meanwhile is not moved. It writes no file of the repository that git's other commands write too, such as the record of the last fetch.
- **The clone and the branch the backbone's record names.** Every command, a recovery, `--hand-back` and `--answer` among them, takes each clone it acts on, and each branch it moves, from the backbone's record of the run (point 2), as point 5's rule has it, and `--answer` resumes the session the latest record names. The clone and the session the state names only point the way.
- **Pinned to the record.** Every hand-back, a recovery's and `--hand-back`'s among them, moves nothing, and removes nothing, where the latest record for the clone and the Task keeps no commit a run ended built at (point 2), or where the head of the branch in the build's clone is not that commit, as ADR-073 point 8's pin moves nothing where that head is not the commit the ending event names. A hand-back that finds no record at all is given up, as point 2's "Where none is found" says, and takes no outcome of this pin. The ending event names that commit for a question's ending too, where a check ran (ADR-073 point 9), and a detached process that died during its own hand-back has posted no ending yet, so only the record tells a run that ended built, whatever the state says. So a state rewritten to name a hand-back under way, or to exit 9 before a `--hand-back`, over a build whose run did not end built, one that waits on its question among them, or over one whose built commit point 2's rule has cleared, has no hand-back move the Task's branch or remove the clone, but in the window point 10 names ("A built commit kept past its build"). A forged state over a waiting question still ends the question, by whichever ending ADR-073 point 5's recovery or point 8's hand-back gives it: the clone and the session are kept, and `--answer` is refused.
- **Git's other writers.** The seat's own commands write the same repository while builds run, such as a fetch of the default branch or a push. A hand-back that finds a lock of git's held waits and tries again, within a bound. One that still cannot write moves nothing, and the build waits on its hand-back (exit 9), as one that could not sign does, so `--hand-back` makes it again.
- **Signing in turn.** So a key that asks for its passphrase asks for one hand-back at a time. While its prompt is open, that hand-back holds the lock, and every other hand-back in the clone waits on the person.

### 5. One register: each run that takes a slot is entered once, by what runs it

- **Where it lives.** In the clone's runtime folder, beside its identity where it holds one, and never committed: the capability's runtime ignore list holds its entries ([ADR-009](ADR-009-git-footprint-visibility.md) point 7). The register is the entries there, with no list of its own. So whatever reads the clone's identity reads its register.
- **What the runtime folder steers.** The folder lies where a sandboxed command writes, so ADR-095 point 1 binds what a command outside the sandbox does with what it reads there (the Context). This record carries that point out by one rule, which points 2, 4 and 9 and the bullets below apply. Such a command:
  - decides from what it reads in the folder only whether it counts, waits, refuses, reports, posts on the Task's record, moves the Task's references or recovers a build, each of which the agent's own commands already do on its call (ADR-073 point 9's "No security boundary", and this record's point 9, "A guard, not a boundary");
  - acts on no process, no build's clone and no branch but those the backbone's record of the run names (point 2): it takes every process it ends, every clone it checks, fetches from, signs the commits of, removes or resumes a run in, and every branch it moves, from that record alone. The record alone chooses which process, clone, session and branch each act acts on; the Task comes from the state file's name, matched as a key of its records (point 2). The run's caller decides whether its processes are ended (point 2, "A live caller"), every hand-back is pinned to the record as point 4's "Pinned to the record" says, and a clone is removed only as point 2's "How long it lives" says;
  - runs no code that what it reads in the folder names, and of a run's code, only the runner read from the head the backbone's record names (point 2).

  Within the folder, it writes, reads and removes only the files the next bullets name, as they say. The rule holds within the folder the command finds, beside the members of ADR-095 point 1's class not yet mended that this point names.
- **Regular files, and no link.** The files of the runtime folder that this record and ADR-073 decide are the builds' state files and their locks, the register's entries and its lock, and the hand-back's lock. A command outside the sandbox writes each of them only as a regular file inside the folder, and the count removes only such a file, each following no link at the file, or at any folder between it and the working tree's root, that root taken by its real path, as ADR-095's own writers do (ADR-095 points 2 and 3). Each write of a state file or an entry replaces the file whole, by a rename inside the folder. So no link a sandboxed command makes, a hard link among them, leads a command outside the sandbox to write or remove anything outside the folder, or to write into a file of the person's (ADR-095 point 1).
- **Locks, made and never replaced.** A missing lock is made by an exclusive create inside the folder, following no link, never by a rename. Every lock is then opened without writing, only as a regular file inside the folder, following no link, and without waiting on the open, so a named pipe at a lock's path hangs nothing.
- **Reads too.** What a command outside the sandbox reads of these files, it reads only from a regular file, following no link, as ADR-095's realizing reads its inputs. An entry it cannot read so, a state file among them, counts as holding every slot, so nothing starts on the agent's call while it lies there, as a register that cannot be read lets nothing start (point 7), and a state file it cannot read refuses its Task's next build too (exit 1). Each refusal names the file and echoes nothing of it, as ADR-095's hook and overview echo nothing of an input they cannot read (ADR-095 point 3). So no link, and no named pipe, hangs the count while it holds the register's lock.
- **The clone's identity** and its key, which the folder holds too (DEC-035 point 1), are none of these files. Their writer is a member of ADR-095 point 1's class not yet mended: DEC-035 decides it, and only a record of project-management's or a core record can apply that point to it (ADR-095 point 1, "Its reach"), so this record decides nothing of it.
- **The folder they find.** The commands that write here, count and recover find the project's root, and so the runtime folder, and run version control, as every capability command does ([ADR-001](ADR-001-project-root-resolution.md), ADR-073 point 8), and the detached process, and `--hand-back` for its build, act in the folder their command found, and never find it again. Version control runs what the checkout's own configuration names, and that configuration can place the working tree elsewhere (ADR-095 point 2, "The root they act on"), so a sandboxed command can choose the folder these commands act on. That is one of the members of ADR-095 point 1's class not yet mended (ADR-095 point 1, "Its reach", and point 7): ADR-001 and ADR-073 decide it, and this record does not mend it.
- **The code they run.** The methodology's commands and the runner load their code from the checkout and its history, a place a sandboxed command writes, as ADR-073 point 10 says of a working run's hook and model. That too is a member of ADR-095 point 1's class not yet mended, which the adapter's enforcement declaration names (ADR-095 point 7), and this record does not mend it.
- **What an entry says:** what it counts, the slots it holds, the processes whose life bounds it (point 6), and, for a run within a helper's share, that helper's entry (point 8).
- **A build's state file is its entry while it holds a slot,** never a second record of the same run. It says whether the run it names started on the agent's call, the first run or one `--answer` resumed, and where it did, it holds one slot from its first state until the build's checks end, whose endings the state records (ADR-073 point 5), or until the build waits or ends before them. It holds none after: not while the build waits, on its question or on its hand-back, nor while it waits for the hand-back's lock or hands back, and once it has ended, none unless a process of its run or of its checks that its state names lives on (point 6). A state file that holds no slot, a person's build's among them, is no entry, though it still counts for the one build each Task may have (point 1).
- **A run of the review command or the drift command** on the agent's call has one entry, which that run writes before its first reviewer or fixer starts, and which names each reviewer's or fixer's process as it starts. It holds as many slots as that run has reviewers or fixers going at once, and lowers that count as its last ones end, never raising it (DEC-082 points 4 and 9).
- **A helper's entry** is written by the command the lead runs before it dispatches the helper, and holds the helper's share whole (point 8). The lead ends it when the helper returns, and the end of its session ends it at the latest (point 6).
- **What counts against the pace:** each entry's slots, but those of a run within a live helper's entry, which count within that helper's share alone. A run whose helper's entry no longer lives counts against the pace itself, for as long as it lives.

### 6. An entry counts only while a process it names lives, or its build's lock is held

- **Its processes.** Each entry names the processes whose life bounds it:
  - for a build, the processes its state names as point 2 says: the command that wrote its first state, then its detached process, and then the harness and each check's process;
  - for a review or a drift run, the command's own process and each reviewer's or fixer's it starts;
  - for a helper, the session's process (point 9).
- **Named so it is not mistaken.** A process is named by its id and the time it started, so an id the system gives another process later is not taken for it.
- **An entry lives while any process it names lives.** A review's or a drift run's entry whose command has ended, such as one that was killed, holds one slot for each of its reviewers or fixers that still lives. A build's entry whose detached process was killed lives while a process it names of its run or of its checks lives: until a recovery ends that process, or, where the recovery cannot confirm it is the build's, for as long as it lives (point 2).
- **A build's entry lives while its lock is held, too,** whichever process its state names. So the moment between the command's end and the detached process naming itself counts the build's slot (point 2).
- **An ended process counts for nothing,** however it ended. The next command that counts removes an entry none of whose processes lives, but for a build's state file, which counts while its lock is held and stays for its recovery (point 2).
- **No lapse.** No time limit ends an entry, since a run may outlast any bound.

### 7. A command reads the register and enters its run under one lock

- **One lock of the clone's,** which the operating system releases when its holder ends, so a holder that dies holds nothing up.
- **What it covers.** On the agent's call, the build command, for a build it starts or one `--answer` resumes, the review command and the command that enters a helper (point 8) each take the lock, count the slots the live entries hold, and take what they may: no more than the pace leaves free, nor than the cap the agent passes (DEC-082 points 1 and 4). Each writes its entry, a build's under that build's lock too (point 2), and lets the lock go, and its run starts only once its entry is written. Where it may take no slot, it starts nothing and says so, and the build command and `--answer` exit 1 (point 1). So two of these commands started together cannot both pass the pace. This holds among the methodology's own commands, as point 2 says of a build's lock (point 10, "A lock removed while held").
- **A build's lock is only tested.** The count tests each build's lock without waiting for it, and writes nothing in a build's state. A build whose state is not final, and whose lock the count finds free, counts no slot by its lock, only by a process its state names that lives (point 6). The command recovers that build only once it has let the register's lock go (point 2), since a recovery posts on the tracker. So every command that counts recovers the builds it finds so, the review command and the command that enters a helper among them, and a recovery may make a hand-back again, with its signing (ADR-073 point 5, "Recovery"), so a key that asks for its passphrase may ask while any of them runs.
- **One order for the locks.** A command waits for one build's lock at most, takes it (point 2) before the clone's two, the hand-back's (point 4) and the register's, and holds neither of those two while it waits for the other. A test takes a lock only without waiting, and lets it go at once, so the order binds the locks a command waits for. So a `--hand-back` and a recovery that makes the same hand-back again never wait on each other forever, and nor do a count under the register's lock and an `--answer` that holds its build's lock and waits for the register's.
- **Nothing slow under it.** The command reads the pace before it takes the lock, in the read that confirms its seat (DEC-082 point 7). While it holds the lock, it reads no tracker and waits on no run. A pace that changes in between binds from the next start, as a lowered pace does (DEC-082 point 9).
- **The drift command** enters its fixers under the same lock, within the cap passed, and refuses none past the pace (DEC-082 point 7). It takes the lock only to write its entry, and counts no slot, so it tests no build's lock, recovers no build, and makes no hand-back again, with its signing. So only the cap the agent passes it holds a drift run to the pace.
- **A register that cannot be read** lets nothing start on the agent's call, and the command says why.

### 8. A helper's share bounds what its commands start

- **Entered within the free slots.** The command that enters a helper takes the lock, and refuses a share past the slots free. It prints the entry's name, which the lead puts in the helper's brief beside the share (DEC-082 point 2).
- **Runs within the share.** The helper passes its entry to each command it calls. A command given a live helper's entry starts at most the share less the runs already running within it, writes its own entry within the share, and counts nothing against the pace. So the helper's own slot passes to its runs while they run. A run that outlives the helper's entry counts against the pace from then on (point 5).
- **No entry passed, or one no longer live:** the command counts against the pace, where the share is already held, and says so. A helper that leaves its entry off, or a lead that ended it early, costs slots and passes no pace.

### 9. A command tells the agent's call by the session whose shell runs it

- **The adapter finds the session.** The project's adapter declares how a command finds the harness session whose shell runs it, and that session's process. The declaration is data the backbone reads, as it reads an adapter's other declarations, running none of the adapter's code (the adapters README, "What an adapter declares as data"), and its fields are the build's. A command of the capability learns it from the backbone, so the command names no harness (ADR-066).
- **The first fact of a live session an adapter declares** (the Context). A session's anchor stays where it is. The same declaration could later carry the anchor, or the session's own name that DEC-081's measurement 2 asks after, and this record decides neither.
- **The session's messaging address.** The same declaration gives a command the messaging address the harness gives its session, and says how a message's reply address is brought into the form of that address. So a command of the capability compares them and names no harness (refinement per [project-management:DEC-084-seat-session-address](../../../.pkit/capabilities/project-management/decisions/DEC-084-seat-session-address.md)).
- **The agent's call.** A command that finds a session runs on the agent's call. Any other run is a person's: at their own terminal, or in a script or pipeline of theirs. So a person's run takes no slot, whatever its streams, and an agent's call is held whether or not its shell gives it a terminal.
- **It errs toward holding.** DEC-082's Terms make the agent the project-manager agent, or the definition a seat names, running the pm skill's procedures in a session. The sign finds every session, so it also holds a run that another agent's session in the clone starts, and a person's command through a session's shell (below). A run it so misreads takes a slot where one is free, and is refused where none is, so it never passes the pace.
- **The same process bounds a helper's entry** (point 6), so that entry ends with its session.
- **No session found, no hold.** Where no adapter declares how to find a command's session, no command can tell the agent's call. None holds a caller or enters a run, no helper is entered, and the agent holds itself to the pace, the gap DEC-082 point 7 names. Where a declared adapter's harness stops finding the session, the same follows. The check once in each session (below) tells the person of a harness that does not find it from the session's own shell when the check runs, and point 10 names what it does not see.
- **Checked once in each session.** The command the agent runs once, before its first subagent, to read its seat's state and its pace, or, in a clone with no seat, the ceiling (DEC-082 points 7, 8 and 10), also says whether it found the harness session it runs in, where an adapter declares how a command finds its session. Where the adapter declares it and the command found none, the agent tells the person once, and holds itself to the pace by its own count for the rest of the session (DEC-082 point 10).
- **A guard, not a boundary.** A command the person runs through the session's own shell counts as the agent's, and an agent can start a command outside its session's shell. Like the clash guard on a claim (DEC-035 point 6), the sign catches the mistakes of an agent that follows the procedure, and stops no agent that means to pass as a person. The pace bounds what runs cost, and is no protection of the sandbox. So how many runs start, which the register decides, is among the counts and refusals point 5's rule leaves to the runtime folder, and each run stays confined as ADR-073 decides. The adapter's declaration, which decides whose call each run is, is data of the checkout, not of the runtime folder. It steers only counts and refusals, so point 5's rule binds it as it binds the folder, and none of it runs.

### 10. What stays open

Each item says what holds the intent and what is left ([COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) point 3).

- **A linked worktree.** Its runtime folder is its own, so a session in a linked worktree of the clone counts in a register of its own, as it reads an identity of its own, until a record decides how a linked worktree reads its clone's (DEC-059 point 6). Sessions in two working trees of one clone may then each run the pace.
- **A helper the lead does not end.** Its entry holds its share until its session ends. That slows the clone, and starts nothing past the pace.
- **Subagents started through the harness's tools,** other than helpers, are counted by the agent alone, and no other session sees them (DEC-082 point 7).
- **Reviews of several changes at once.** In a seat's clone, each reviewer works in a clone of its own (ADR-102), so none writes under another or under the seat's own work. In a clone with no seat, reviews of several changes at once run their reviewers unconfined in its checkout (ADR-066 point 10), and a reviewer that writes there writes under the other reviews, until a record confines the reviewers' runs (ADR-073 point 10) (refinement per [ADR-102](ADR-102-reviews-in-own-clone.md)).
- **The seat's checkout beside reviewers.** No reviewer works in it (ADR-102) (refinement per [ADR-102](ADR-102-reviews-in-own-clone.md)).
- **What runs at once costs the machine.** Each build makes its own clone, caches and sandbox, and reaches its build's hosts, so the pace bounds disk, memory and network use only by bounding the runs. Kept clones stay until a person removes them, since no command removes one but the hand-back that brings its commits back (point 2, "How long it lives").
- **A command outside its session's shell** passes as a person's run (point 9).
- **A stop the session check does not see.** A stop that starts partway through a session, after the check once in each session (point 9), passes the agent's calls from then on as a person's, held only by the caps the agent passes each command (DEC-082 point 1), and nothing says so until a later session's check. A harness that finds the session from the session's own shell, but not from a helper's, passes every command a helper runs as a person's, held only by the caps the helper passes within its share, and no check says so.

A first build then has a start event on its Task with no ending, and a resumed build waits on its question again while its Task's record shows the resume, so its claim may lapse. Within the window, ADR-073 point 9's "**each ending,** of a build whose start event is posted" and point 5's "The resumed build is a running build, renewed while it runs and lost if its process dies" do not hold, as they did not in ADR-073's own window of one write, in which its detached process posted the event first and wrote the state after. The build's entry no longer counts it, since its state does not name it (point 6), and it stays inside the sandbox (ADR-073 point 10). ## Rationale

**Why builds at once, and one for each Task.** DEC-082 has a worker keep several Tasks in flight and run as many subagents as its pace allows, builders among them. One build at a time in a clone would hold every worker to one builder, whatever its pace. Each build already runs in a clone of its own, under its own rules, and comes back only through its hand-back, so builds of different Tasks share nothing but the repository they come back to. Two builds of one Task would race for its branch, its claim and its question, so a Task keeps one build. A build of a Task whose earlier state still names a process that lives is refused too, since a Task has one state file: its first state would write over the only state that names that process, which would then run on past the pace, counted nowhere. Carrying such processes forward as a slot of their own would add a second kind of entry, for a case the refusal settles. A build that waits keeps its Task until `--answer` or `--hand-back` ends the wait, since the Task's record on the tracker shows the wait, and its claim does not lapse while it does (ADR-073 point 5, "The claim").

**Why a build's state file is its entry.** A build already keeps its state in a file its process writes, which names the process and whether the build runs. A second record of the same run would be written at another moment, and could show a build running where its state shows it ended. One record of each run cannot disagree with itself. A state file that holds no slot is no entry, so a person's build, or one that waits, is in no register, and the Task's one build is still found by its state file.

**Why the first writer holds the build's lock until the detached process does.** The command that starts a build writes its first state before the process that runs it exists. A lock taken only by that process would leave a moment in which a state that is not final has no holder, and another session's command would recover a build that is only starting. A lock held from the first write, and passed with no gap, closes that moment. It passes to the detached process alone, since a run or a check that inherited it would hold it past that process's end: the lock would no longer tell the writers gone, a build whose process died would never be recovered, and a descriptor open for writing would let a sandboxed run write a file of the seat's clone (ADR-073 point 3). The command writes nothing after the start, and the detached process names itself, so the two never write the state at once. A build's entry lives while its lock is held, so a command killed after the start leaves no moment in which the build counts nowhere.

**Why an entry lives with its processes, and lapses at no time.** The register counts runs, and each run is bounded by a process. The operating system knows when a process ends, whether it finished, failed or was killed, so an entry bounded by its processes outlives neither its runs nor, for a helper, its session. A run can outlive what entered it, a reviewer its killed command, a build's run its killed detached process, or a build its helper's session, so an entry names each run's process, and a run whose helper's entry has ended counts against the pace itself. A lost build's slot frees only once every process its state names has ended, and no build of its Task writes over its state before then (point 1). A time limit would either outlast a dead run, whose slot nobody then uses, or end before a long one, so that the next command starts past the pace.

**Why one rule for what the runtime folder steers.** What a command outside the sandbox reads in the runtime folder may narrow what it does, widen it only where a person shown the widening makes it, and never choose or redirect where it writes (ADR-095 point 1, and the Context). Whether to count, wait, refuse, report, post on the Task's record, move the Task's references or recover a build is what the agent's own commands already decide on its call, and the Task's record is no security boundary (ADR-073 point 9), so a file forged there gains a sandboxed command nothing its agent lacks. What each act acts on, as point 5's rule lists it, reaches past that. So each comes from the backbone's record, in a folder no sandboxed command writes, whether a run's processes are ended is its caller's while it lives, every hand-back is pinned to the commit that record keeps (point 4), as the agent's own hand-back is, and the folder names no code to run. Within the folder, a lock is the one file each of its holders opens, so it is made by an exclusive create and never by a rename: a lock renamed into place while another command held the old one would let both hold it at once.

**Why the backbone keeps a record of each run.** Outside any run, nothing but the state says which build's sandboxes, settings and clone these are, and a state that named another live build's would have a recovery end that build, or fetch from, sign and remove a clone a sandboxed command chose. So the backbone keeps them, with the branch and commit the clone was made at, the run's caller, its harness session and the head its runner was read from, in the run's settings folder. Each run has its own id, since a resumed run, a fix round and a merge each run apart under one Task, and a recovery acts on every live record for the clone and the Task, so the state chooses none of them. A record lives while its clone exists or a process it confirms lives, so it is there while there is something to act on. Only the hand-back that fetched a clone's commits and moved the Task's branch to them removes the clone and its records, since it knows that by its own act, and every hand-back is pinned to the built commit the record keeps on its caller's word (point 4), since the ending event names a commit for a question too. So a state deleted, rewritten or forged, to name commits the branch already holds or a hand-back under way, removes no clone that holds unreturned commits or a session a question resumes in. Where none is found, a recovery has nothing to confirm, so it ends nothing and acts on no clone, and a hand-back it cannot make is given up rather than left waiting (ADR-073 point 8). A recovery or a hand-back that a removed lock let in ends nothing and marks nothing while the run's caller lives. The call runs the runner the record names, so the runner that reads what it recorded is the one that recorded it, whatever the default branch holds since, and a resume runs only under the head the latest record names, since `--answer` refuses one whose build's start event names another, before it spends the answer, and the run command refuses one whose caller passes another.

**Why the record keeps a built commit only while a hand-back may still bring it back.** A commit the record kept past its build would let a state forged later have a hand-back move the Task's branch to it and remove the clone, though the Task's record shows the build ended with no commit brought back. So whatever ends the build without moving the branch clears it, but at an exit 9 that leaves the build waiting on its hand-back, which `--hand-back` makes again (ADR-073 point 8). The cost: a state forged as not final over a build that waits at exit 9 leads a recovery to mark the build lost and clear its commit, so a later `--hand-back` cannot bring the build back. That forged recovery already posts exit 5, keeps the clone, and stays within what point 5's rule lets the folder steer. So the closure narrows what a forged state can do, and widens nothing.

**Why a recovery ends only what it confirms, and marks the build all the same.** A recovery that ended whatever its state named could be led by a state written to name a process of the person's to end it, so the names only point the way, and the recovery confirms what it ends by the backbone's record. A process of the run or of a check it confirms by the build's sandbox or a check's, as the runner does before a check. The checks run only once the run has ended (ADR-073 point 5), so what the runner finds then is what is left of a run once its harness has ended, a process in a session of its own among it, which a process group does not hold, so the recovery finds them as the runner does, not by a group. The harness the sandbox does not hold, so the recovery confirms it by the settings the runner wrote for this build, in a folder of the backbone's that the run does not write (ADR-073 point 2). It does not reach the harness's descendants as the runner does at its limit, from the harness it started (ADR-066 point 11), since a recovery would reach them only from the id the state names. A recovery that marked nothing until it confirmed would leave a state that is not final for good: every command in the clone would try it again, a `--wait` on it would exit 8 forever, and its Task would be refused a new build. So it marks the build not borne out, as the runner does where it cannot confirm (ADR-073 point 1), and the slot that a named process holds while it lives keeps the pace.

**Why one lock, and nothing slow under it.** Two commands that each count the register and then enter a run can both find the last slot free. A lock over the count and the entry closes that, and a lock the operating system releases cannot be left held by a run that died. A read of the tracker under the lock would hold every other command in the clone on the network. So the pace is read before, and a pace that changes in between is read one start late, as DEC-082 point 9 already allows. A recovery posts on the tracker too, so a count under the lock only tests each build's lock, without waiting, and leaves a recovery until after. One order for the locks a command waits for, among the clone's two and every build's, leaves no two commands each holding a lock the other waits for.

**Why hand-backs take turns.** A hand-back's check, fetch, signing and move are seconds of work on the one repository every build comes back to, beside the seat's own commands. Taking turns keeps each hand-back's check and move together, and a key that asks for its passphrase asks once at a time, at the cost of a hand-back that waits seconds for another, or, while a passphrase prompt is open, waits on the person who answers it. A hand-back that writes only its own references, from the commit it expects, stays out of the way of git's other writers. One that still cannot write waits on its hand-back, as one that could not sign does, so nothing is lost but time.

**Why the session, and not the terminal.** DEC-082 holds the agent's calls, and a person's own runs take no slot. The test of a terminal answers another question, whether a person can answer here ([project-management:DEC-069-when-fixers-start]'s Terms). It would hold a person's run in a script or a pipe as the agent's, and pass an agent's call where the harness's shell gives a terminal or the agent fakes one (ADR-066 point 11). What makes a call the agent's is the session whose shell runs it, so the commands read that. The register needs the session's process in any case, so that a helper's entry ends with its session, and one declaration of the adapter gives both.

**Why the declaration is data.** Every build and review command on the agent's call reads it, so reading it runs none of the adapter's code, as the backbone reads an adapter's other declarations. A registered command of the adapter, as its runner is, would put another process before every start.

**Why a harness requirement.** A declared adapter whose harness release stops finding the session would pass every call as a person's, with no pace held and no helper entered: a degraded result shaped like a correct one, which COR-047 exists to name. The requirement records that dependency, bounds the Claude Code adapter's answer to the versions the probe tested, and tells whoever adapts another harness what it must supply. The report cannot yet tell a harness that finds the session from one that stopped (point 12), and none resolves `satisfied` until an adapter gives the report a way to observe (the adapters README, "What the report says"). So the requirement is no alarm, and the check once in each session is how a stop is noticed.

**Why a check once in each session, and not at every command.** The command the agent runs before its first subagent already reads its seat's state and its pace, so saying there whether it found the session costs one line, and tells the person before any of the agent's runs passes as theirs. A check at every command would catch a stop partway through a session too, but every run would print more, and there would be more to build. So a stop that starts partway through a session, a stop in a helper's shell alone, and a session whose agent does not run the check, are left open (point 10).

**Why a helper's share is held whole.** The lead hands each helper a share of its free slots, and the helper may fill it at any moment, with no command of the lead's in between. Holding the share whole keeps the lead's other runs and the other helpers out of it, so a helper's command never finds its share taken. A helper's runs count within its share and not against the pace again, so the share is counted once.

### Alternatives considered

- **A register file of its own, beside the builds' state files.** Rejected, as "Why a build's state file is its entry" says.
- **Entries that lapse after a time, renewed while their runs run.** Rejected, as "Why an entry lives with its processes" says.
- **The test of a terminal as the sign of a person's run.** Not taken, as "Why the session, and not the terminal" says.
- **The harness's mark of a tool's process as the sign of the agent's call.** Rejected: the mark names no session and no session's process, which a helper's entry needs, to end with its session (point 6), while one declaration of the adapter gives both, as "Why the session, and not the terminal" says.
- **A flag the agent passes on each call, marking it as the agent's.** Rejected: a call that left it off would pass as a person's, which leaves the pace to the agent's own count, as DEC-082's "Why the commands hold the agent's calls" rejects.
- **Hand-backs at once, each to its own references.** Not taken: git's own locks would allow it, but two hand-backs would sign at once, and more writers would meet on the seat's repository at once, for a saving of seconds.
- **The register in the git folder that every working tree of the clone shares.** Not taken: it would decide how a linked worktree shares its clone's state, which DEC-059 point 6 leaves open, while the clone's identity sits in the runtime folder of its working tree.
- **A state file for each build rather than for each Task,** so that a Task could have several. Rejected, as "Why builds at once, and one for each Task" says.
- **A new build that replaces a Task's waiting build.** Rejected: the Task's record would still show its question or its hand-back waiting, and its claim would not lapse.
- **A new build that carries forward, as a slot of their own, the processes its Task's earlier state names.** Not taken, as "Why builds at once, and one for each Task" says: it adds a second kind of entry, for a case the refusal settles.
- **The harness's event at a subagent's end, ending a helper's entry.** Named, not decided: where an adapter declares such an event, it would end the entry with the helper rather than with the lead's call. A later record may decide it.
- **A command that ends its reviewers or fixers when it ends, in place of naming their processes.** Not taken: a command killed outright ends nothing, so its runs would count nowhere.
- **A recovery that ends each process, or process group, its state names.** Rejected, as "Why a recovery ends only what it confirms, and marks the build all the same" says: a group holds no process in a session of its own, and a state written to name a process of the person's would have a command outside the sandbox end it.
- **A recovery that marks nothing until it confirms that no process of the build is left.** Rejected, as the same paragraph says: the build's state would stay not final for good.
- **The clone a recovery's hand-back acts on, taken from the state and named among ADR-095 point 1's members not yet mended.** Not taken: it would leave a removal at a path a sandboxed command chose, a removal this record extends to every command that counts (point 7).
- **The builds' state files, the register and their locks in a folder of the backbone's that no sandboxed command writes.** Not taken: it would close only what a file there says or is, and only on macOS, leaving as they are what keys the folder, the clone's identity, the root found through version control and which runner runs, and on Linux, where the methodology's command runs inside the sandbox, the command could not write there (ADR-095 point 4). It would save little of this record and build nothing smaller. It would also overturn where ADR-073 point 5 keeps the state file, and change what ADR-095 counts as a guarded folder.
- **A hand-back pinned only to the ending event, with a state rewritten over a question named in point 10.** Not taken: the ending event names a commit for a question too, so a hand-back made again would move the Task's branch to a question's commits and remove the clone with the question's session, on what the runtime folder says, which point 5's rule rules out.
- **Where no record is found, the claim held until a person acts (exit 7).** Not taken: the build would wait on a hand-back its clone can no longer make, which ADR-073 point 8's "A hand-back given up" rules out.
- **A build's lock taken first by its detached process.** Rejected, as "Why the first writer holds the build's lock until the detached process does" says.
- **A build's lock that its runs and checks inherit too.** Rejected, as the same paragraph says: the lock would outlive the build's writers.
- **No harness requirement, the gap point 9 names standing for every harness.** Rejected, as "Why a harness requirement" says.
- **A check of the session at every command.** Rejected, as "Why a check once in each session, and not at every command" says: it catches a stop partway through a session, but every run prints more, and there is more to build.
- **The session's anchor moved onto the new declaration in this record.** Not taken: no record needs the anchor declared, and moving it would change the guard against changing another repository for a reason this record does not have.
