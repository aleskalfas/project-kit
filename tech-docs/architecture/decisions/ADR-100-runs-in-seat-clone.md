## Summary

**In plain terms:** [project-management:DEC-082-pace-of-subagents] lets the project-manager agent run several subagents at once in a clone, up to a pace, and has the build and review commands hold the agent's calls to that pace from a register of the clone's runs. [ADR-073](ADR-073-builder-runs.md) built the build command for one build at a time in a seat's clone. This record says how a clone runs at a pace:

- **Builds at once, one for each Task.** Each build keeps a state file of its own, keyed by its Task, written under a lock of its own from its first state on. For the builds beside it, a build is refused only where a build of the same Task runs or waits, or, on the agent's call, where no slot is free, and ADR-073's other refusals stand. A session acts on each build it finds as its work allows, and waits on none before other work.
- **Hand-backs take turns.** One hand-back at a time in a clone, each writing only its own reference and its Task's branch.
- **One register, each run entered once.** A build's state file is its entry while it holds a slot. Each other run of a command on the agent's call, and each helper a lead dispatches, has one entry, written by what runs it. An entry counts while a process it names lives, a build's run and its checks among them, and a build's while its lock is held too. A run that outlives its helper's entry counts against the pace itself, so no run the register holds counts nowhere. A command reads the register and enters its run under one lock.
- **The agent's call is told by its session.** The adapter declares, as data the backbone reads, how a command finds the harness session whose shell runs it. A command that finds one runs on the agent's call, and any other run is a person's. The command the agent reads its pace with, once in each session before its first subagent, says whether it found the session, so a harness that does not find it from the session's own shell when the check runs is told to the person. A harness requirement records what this asks of the harness.

**Why an ADR.** The register spans the backbone, the adapter and the capability's commands: a declaration of the adapter, a reading the backbone gives, and the commands of project-management that count and start runs. How those parts share one clone's runs is what the project built, an architecture record's question ([COR-025](../../../.pkit/decisions/core/COR-025-adr-decision-space.md), "Distinct from PRJ"). This record realises DEC-082 as ADR-073 realises [project-management:DEC-063-task-builder].

## Context

**What stands.**

- **One build at a time.** The build command starts a build in a clone of its own, detached, and keeps its state in one file of the seat's clone, which the seat polls with `--wait`. It allows one build at a time in a seat's clone, and refuses a second while one runs (ADR-073 point 5). A session that starts in a clone with a build in that file goes on from it before any other work.
- **The hand-back.** A build's commits come back through a temporary reference of the seat's clone, signed there, and move the Task's branch as a reference (ADR-073 point 8).
- **Reviewers and fixers.** The review and drift commands start each reviewer and each fixer as a process of the backbone's run command ([ADR-066](ADR-066-unattended-agent-runner.md) point 10). Reviewers run unconfined in the seat's checkout.
- **The runtime folder.** The capability keeps a git-ignored folder in each working tree. It holds the clone's identity, with its key ([project-management:DEC-035-instance-ownership] point 1), and the build's state file. How a linked worktree reads its clone's identity is not decided ([project-management:DEC-059-topology-of-seats] point 6).
- **What a sandboxed command writes is not trusted outside the sandbox.** Code that runs outside the sandbox without a person choosing it, the methodology's own commands among it, never takes its code from a place a sandboxed command can write, takes a widening from such a place only where a person shown it makes it, and lets no sandboxed command choose or redirect where it writes. The rule binds every later architecture record ([ADR-095](ADR-095-hook-out-of-reach.md) point 1). The runtime folder lies in the working tree, which a sandboxed command writes (ADR-095 point 2, "Not where a sandboxed command writes by default"), and on macOS the methodology's command runs outside the sandbox ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 2).
- **No adapter declares a fact of a live session.** The folder a session is rooted in, its anchor ([ADR-034](ADR-034-foreign-repo-mutation-guard.md)), is read by the backbone's guard against changing another repository under the name of Claude Code's own variable, and the capability keeps a copy of that reading in its own guard. No adapter declares it for the backbone to read.
- **The harness's mark of a tool's process.** The backbone tells a process that the harness's shell tools or hooks started, and each process such a process starts, by the mark the harness sets in it ([ADR-093](ADR-093-writes-outside-the-repository.md)'s Context, "What marks a tool's process", and point 4). ADR-095 builds that test once, for the command that names a folder and for its interlock on widening (ADR-095 point 3). The mark names no session.
- **The harness requirements.** The core declares what it requires of the harness, and each adapter answers how far its harness meets it ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), as ADR-066 point 13 and ADR-073's Implications did for the runs they rest on.

**What DEC-082 decides.** One pace for each clone, all its sessions together, counted in slots. Every subagent the agent runs holds a slot while it runs, but a helper while it hands its slot to its own, a build keeps its slot through the build's checks, and a run a person starts themselves holds none. A register of the clone's runs, read by the build and review commands, holds the agent's calls to the pace, where a command can tell that call from a person's. A lead enters each helper with a share of its slots, and the runs a helper's commands start count within that share. A Task that waits holds no slot. DEC-082 leaves to this record a state file for each build, a `--wait` that names no Task, recovery over each build, how fetches, signing and hand-backs share one clone, the register's form, and the sign that tells the agent's call. DEC-082 rests on [project-management:DEC-081-delegation-between-seats], and both are accepted with this record.

**Terms.** *The agent*, *a subagent*, *the pace*, *a slot*, *the ceiling* and *the build's checks* are DEC-082's.

- **The clone** is the working tree a command runs in, with the capability's runtime folder there, whether or not that folder holds an identity yet: a clone makes its key only when it first claims ([project-management:DEC-058-state-issues] point 5). **Its runtime folder** is that folder.
- **An entry** is one record of the register (point 5).
- **A session's process** is the process of the harness session whose shell runs a command, as the adapter finds it (point 9).

## Decision

**In a clone, builds run at once, as many as the pace allows on the agent's call, one for each Task, each with a state file of its own, and hand-backs take turns. The clone counts the runs that take its slots in one register: one entry for each run, written by what runs it, a build's state file being its entry while it holds a slot, and each entry counted while a process it names lives, a build's while its lock is held too. A command reads the register and enters its run under one lock, and tells the agent's call by the harness session whose shell runs it, as the adapter finds it, which the agent checks once in each session, on a harness requirement this record declares.**

### 1. Builds run at once, one for each Task

- **As many as the pace allows.** On the agent's call, the build command starts a build only where a slot is free (points 5 and 7). A build a person starts themselves takes none (point 9), as DEC-082 point 1 has it. This holds in a seat's clone, and in a clone with no seat, which runs at the ceiling (DEC-082 point 8).
- **One for each Task.** A Task has at most one build that runs or waits, on its question or on its hand-back. A build of a Task whose earlier build runs or waits is refused (exit 1), since `--answer` resumes that build and `--hand-back` finishes it (ADR-073 points 7 and 8).
- **No slot free.** On the agent's call, a build with no slot free is refused too (exit 1), with the pace and the count the command read and the entries that hold the slots, so the person sees which run holds each, and nothing starts. So is an `--answer` on the agent's call that finds no slot free for the run it would resume (point 7).
- **Each build's own.** Each build has its own state file, keyed by its Task, in the runtime folder. It has its own clone, settings folder and progress file, and its own temporary reference for its hand-back, named for its Task. So two builds write nothing in common but the register and, through their hand-backs, the seat's repository (point 4).
- **The seat's checkout stays as it is.** Builds at once leave the seat's working tree clean and on the default branch, as ADR-073 point 8 keeps it. What a reviewer may do to it is point 10's.

### 2. Each build's state has one writer at a time, and each build is recovered once

- **A lock for each build.** A build's state file is written only under a lock of its own, which the operating system releases when its holder ends, however it ends. Its writers:
  - the command that writes the build's first state, the build command or `--answer` for a run it resumes, which takes the lock before it writes;
  - the detached process that command starts, which holds the lock while it lives;
  - `--hand-back`, for its hand-back;
  - a command that recovers the build (ADR-073 point 5).
- **No gap at the start.** The command that writes the first state holds the lock until it starts the detached process, and the lock passes to that process with no moment in which neither holds it, such as by a descriptor the process inherits. So a command that reads a build's first state finds its lock held, and never takes a build that is starting for one that is lost.
- **The detached process alone.** The lock passes to the detached process and to no process it starts: no run or check of the build inherits its descriptor, which is not opened for writing. So only a writer of the build holds the lock, and only while it lives.
- **The detached process names itself.** The command writes nothing in the state after it starts the detached process, and that process's first write under the lock names it there. Until then the state names the command. So the command's last write comes before the detached process's first. The detached process then names in the state the run's processes as the runner reaches them, the harness and each check's process, as it starts each (point 6).
- **Named before it runs.** The harness and each check's process are named in the state before they run anything: each waits, for instance on a pipe from the detached process, until that process has written it into the state, and exits where the pipe closes first. So a detached process killed between starting one and naming it leaves none running that the state does not name.
- **The first state comes before the build's event.** On the agent's call, the first state is the build's entry (point 5), written under the register's lock, under which no tracker call runs (point 7). So, for every build alike, it comes before the build's start event, or, for `--answer`, its resume event, which the command posts once it has let the register's lock go. The run still starts only once that event is posted (ADR-073 point 9). Once it is, the command records in the state that it is posted, and that is its last write before it starts the detached process. Where the event cannot be posted (exit 3), the command makes the state final itself before it exits, a first build at exit 3 and a resumed build back at its question (exit 6), as it stood before `--answer` ran, so no recovery reads it.
- **Recovered before its event.** ADR-073 point 9 posts an ending only for a build whose start event is posted. So a recovery reads from the state whether the event of the run that its latest first state begins is posted: the build's start event, or, for a run `--answer` resumes, its resume event. A state that does not record it gets no ending:
  - A first build becomes final, lost (exit 5), with no ending.
  - A resumed build goes back to waiting on its question (exit 6), as it stood before `--answer` ran, with the person's answer unspent. The Task's record, which shows no resume, shows the question waiting too.
- **The lock tells the writers gone.** A command that reads a state that is not final, and takes its lock, knows that no writer lives, whichever process the state names. It reads the state again under the lock, and recovers that build as ADR-073 point 5's "Recovery" says, by the lock and not by a process's id, and as this point adds. So two commands that find one build at once recover it once. A count under the register's lock only tests a build's lock, and leaves the build's recovery until it has let the register's lock go (point 7).
- **Nothing of the build left.** Before it marks a build lost, a recovery ends what is left of the build's sandbox and of its checks' sandboxes, found as the runner finds them before a check, a process in a session of its own among them, and confirms that none lives (ADR-073 point 1, and its probe). The processes the state names only point the way: a recovery never ends a process it cannot confirm is the build's. Where it cannot confirm that none is left, it marks the build lost all the same, not borne out (exit 5), its clone kept, as the runner does where it cannot (ADR-073 point 1). Either way the build's slot stays held while a process its state names lives (point 6), so marking the build final frees no slot that process holds.
- **What the state names only narrows.** The state file lies where a sandboxed command writes, and a recovery runs outside the sandbox wherever the methodology's command does (the Context). So what the state names can keep a slot held, and never has a recovery end more than it finds of the build's sandboxes, as ADR-095 point 1 allows: a state written to name a process outside the build has no command end it.
- **A session goes on from every build.** A session that starts in a clone reads each build's state before it takes other work. It then acts on each as DEC-082 point 4 orders its slots: a finished build as work in flight, a build that waits as its wait asks, and a running build left to run while the session fills its other slots. It waits on no running build before other work.

### 3. `--wait` waits on one Task's build, or on whichever of the clone's ends first

- **With a Task,** it waits on that Task's build, as ADR-073 point 5's "Waiting" says, and exits with that build's code.
- **With no Task,** it waits on every build of the clone that runs when it starts. It returns once one of them ends, naming its Task, with that build's code; where several have ended when it reads, with the code of the first to end, by the times their states name. Where none ends within the time, it exits 8. Where none runs when it starts, it says so and exits 1.
- **Every wait lists the clone's builds,** each with its Task and its state, so a session finds a build that ended while it was not waiting.

### 4. Hand-backs take turns, and each writes only its own references

- **One at a time in a clone.** A hand-back takes a lock of the clone's for its whole span: its check of the build's clone, its fetch, its signing and its move of the Task's branch (ADR-073 point 8). The operating system releases the lock when its holder ends. A hand-back that waits for the lock holds no slot.
- **Its own references.** It fetches into its build's temporary reference, and moves the Task's branch only from the commit the branch held when the hand-back began, so a branch that moved meanwhile is not moved. It writes no file of the repository that git's other commands write too, such as the record of the last fetch.
- **Git's other writers.** The seat's own commands write the same repository while builds run, such as a fetch of the default branch or a push. A hand-back that finds a lock of git's held waits and tries again, within a bound. One that still cannot write moves nothing, and the build waits on its hand-back (exit 9), as one that could not sign does, so `--hand-back` makes it again.
- **Signing in turn.** So a key that asks for its passphrase asks for one hand-back at a time. While its prompt is open, that hand-back holds the lock, and every other hand-back in the clone waits on the person.

### 5. One register: each run that takes a slot is entered once, by what runs it

- **Where it lives.** In the clone's runtime folder, beside its identity where it holds one, and never committed. The register is the entries there, with no list of its own. So whatever reads the clone's identity reads its register.
- **Regular files, and no link.** Every writer of a build's state file, of a lock and of an entry writes only a regular file inside the runtime folder, and the count removes only such a file, each following no link, at the file or at the folder, as ADR-095's own writers do (ADR-095 points 2 and 3). So no link a sandboxed command makes leads a command outside the sandbox to write or remove anything outside the folder (ADR-095 point 1).
- **What an entry says:** what it counts, the slots it holds, the processes whose life bounds it (point 6), and, for a run within a helper's share, that helper's entry (point 8).
- **A build's state file is its entry while it holds a slot,** never a second record of the same run. It says whether the run it names started on the agent's call, the first run or one `--answer` resumed, and where it did, it holds one slot from its first state until the build's checks end, whose endings the state records (ADR-073 point 5), or until the build waits or ends before them. It holds none after: not while the build waits, on its question or on its hand-back, nor while it waits for the hand-back's lock or hands back, nor once it has ended, unless a process of its run or of its checks that its state names lives on (point 6). A state file that holds no slot, a person's build's among them, is no entry, though it still counts for the one build each Task may have (point 1).
- **A run of the review command or the drift command** on the agent's call has one entry, which that run writes before its first reviewer or fixer starts, and which names each reviewer's or fixer's process as it starts. It holds as many slots as that run has reviewers or fixers going at once, and lowers that count as its last ones end, never raising it (DEC-082 points 4 and 9).
- **A helper's entry** is written by the command the lead runs before it dispatches the helper, and holds the helper's share whole (point 8). The lead ends it when the helper returns, and the end of its session ends it at the latest (point 6).
- **What counts against the pace:** each entry's slots, but those of a run within a live helper's entry, which count within that helper's share alone. A run whose helper's entry no longer lives counts against the pace itself, for as long as it lives.

### 6. An entry counts only while a process it names lives, or its build's lock is held

- **Its processes.** Each entry names the processes whose life bounds it:
  - for a build, the command that wrote its first state, then its detached process, once that process names itself, and then the run's processes as the runner reaches them, the harness and each check's process, which the detached process names as it starts each, before each runs anything (point 2);
  - for a review or a drift run, the command's own process and each reviewer's or fixer's it starts;
  - for a helper, the session's process (point 9).
- **Named so it is not mistaken.** A process is named by its id and the time it started, so an id the system gives another process later is not taken for it.
- **An entry lives while any process it names lives.** A review's or a drift run's entry whose command has ended, such as one that was killed, holds one slot for each of its reviewers or fixers that still lives. A build's entry whose detached process was killed lives while a process it names of its run or of its checks lives: until a recovery ends that process, or, where the recovery cannot confirm it is the build's, for as long as it lives (point 2).
- **A build's entry lives while its lock is held, too,** whichever process its state names. So the moment between the command's end and the detached process naming itself counts the build's slot (point 2).
- **An ended process counts for nothing,** however it ended. The next command that counts removes an entry none of whose processes lives, but for a build's state file, which counts while its lock is held and stays for its recovery (point 2).
- **No lapse.** No time limit ends an entry, since a run may outlast any bound.

### 7. A command reads the register and enters its run under one lock

- **One lock of the clone's,** which the operating system releases when its holder ends, so a holder that dies holds nothing up.
- **What it covers.** On the agent's call, the build command, for a build it starts or one `--answer` resumes, the review command and the command that enters a helper (point 8) each take the lock, count the slots the live entries hold, and take what they may: no more than the pace leaves free, nor than the cap the agent passes (DEC-082 points 1 and 4). Each writes its entry, a build's under that build's lock too (point 2), and lets the lock go, and its run starts only once its entry is written. Where it may take no slot, it starts nothing and says so, and the build command and `--answer` exit 1 (point 1). So two of these commands started together cannot both pass the pace.
- **A build's lock is only tested.** The count tests each build's lock without waiting for it, and writes nothing in a build's state. A build whose state is not final, and whose lock the count finds free, counts no slot by its lock, only by a process its state names that lives (point 6). The command recovers that build only once it has let the register's lock go (point 2), since a recovery posts on the tracker. So every command that counts recovers the builds it finds so, the review command, the drift command and the command that enters a helper among them, and a recovery may make a hand-back again, with its signing (ADR-073 point 5, "Recovery"), so a key that asks for its passphrase may ask while any of them runs.
- **One order for the locks.** A command waits for one build's lock at most, takes it (point 2) before the clone's two, the hand-back's (point 4) and the register's, and holds neither of those two while it waits for the other. A test takes a lock only without waiting, and lets it go at once, so the order binds the locks a command waits for. So a `--hand-back` and a recovery that makes the same hand-back again never wait on each other forever, and nor do a count under the register's lock and an `--answer` that holds its build's lock and waits for the register's.
- **Nothing slow under it.** The command reads the pace before it takes the lock, in the read that confirms its seat (DEC-082 point 7). While it holds the lock, it reads no tracker and waits on no run. A pace that changes in between binds from the next start, as a lowered pace does (DEC-082 point 9).
- **The drift command** enters its fixers under the same lock, within the cap passed, and refuses none past the pace (DEC-082 point 7). So only the cap the agent passes it holds a drift run to the pace.
- **A register that cannot be read** lets nothing start on the agent's call, and the command says why.

### 8. A helper's share bounds what its commands start

- **Entered within the free slots.** The command that enters a helper takes the lock, and refuses a share past the slots free. It prints the entry's name, which the lead puts in the helper's brief beside the share (DEC-082 point 2).
- **Runs within the share.** The helper passes its entry to each command it calls. A command given a live helper's entry starts at most the share less the runs already running within it, writes its own entry within the share, and counts nothing against the pace. So the helper's own slot passes to its runs while they run. A run that outlives the helper's entry counts against the pace from then on (point 5).
- **No entry passed, or one no longer live:** the command counts against the pace, where the share is already held, and says so. A helper that leaves its entry off, or a lead that ended it early, costs slots and passes no pace.

### 9. A command tells the agent's call by the session whose shell runs it

- **The adapter finds the session.** The project's adapter declares how a command finds the harness session whose shell runs it, and that session's process. The declaration is data the backbone reads, as it reads an adapter's other declarations, running none of the adapter's code (the adapters README, "What an adapter declares as data"), and its fields are the build's. A command of the capability learns it from the backbone, so the command names no harness (ADR-066).
- **The first fact of a live session an adapter declares.** No adapter declares one today (the Context). A session's anchor stays where it is. The same declaration could later carry the anchor, or the session's own name that DEC-081's measurement 2 asks after, and this record decides neither.
- **The agent's call.** A command that finds a session runs on the agent's call. Any other run is a person's: at their own terminal, or in a script or pipeline of theirs. So a person's run takes no slot, whatever its streams, and an agent's call is held whether or not its shell gives it a terminal.
- **It errs toward holding.** DEC-082's Terms make the agent the project-manager agent, or the definition a seat names, running the pm skill's procedures in a session. The sign finds every session, so it also holds a run that another agent's session in the clone starts, and a person's command through a session's shell (below). A run it so misreads takes a slot where one is free, and is refused where none is, so it never passes the pace.
- **The same process bounds a helper's entry** (point 6), so that entry ends with its session.
- **No session found, no hold.** Where no adapter declares how to find a command's session, no command can tell the agent's call. None holds a caller or enters a run, no helper is entered, and the agent holds itself to the pace, the gap DEC-082 point 7 names. Where a declared adapter's harness stops finding the session, the same follows. The check once in each session (below) tells the person of a harness that does not find it from the session's own shell when the check runs, and point 10 names what it does not see.
- **Checked once in each session.** The command the agent runs once, before its first subagent, to read its seat's state and its pace, or, in a clone with no seat, the ceiling (DEC-082 points 7, 8 and 10), also says whether it found the harness session it runs in, where an adapter declares how a command finds its session. Where the adapter declares it and the command found none, the agent tells the person once, and holds itself to the pace by its own count for the rest of the session (DEC-082 point 10).
- **A guard, not a boundary.** A command the person runs through the session's own shell counts as the agent's, and an agent can start a command outside its session's shell. Like the clash guard on a claim (DEC-035 point 6), the sign catches the mistakes of an agent that follows the procedure, and stops no agent that means to pass as a person. The pace bounds what runs cost, and is no protection of the sandbox. So what the register and the adapter's declaration decide, how many runs start and whose call each is, falls outside ADR-095 point 1, and each run stays confined as ADR-073 decides, while what writes in the runtime folder and what a recovery ends keep to that point (points 2 and 5).

### 10. What stays open

Each item says what holds the intent and what is left ([COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) point 3).

- **A linked worktree.** Its runtime folder is its own, so a session in a linked worktree of the clone counts in a register of its own, as it reads an identity of its own, until a record decides how a linked worktree reads its clone's (DEC-059 point 6). Sessions in two working trees of one clone may then each run the pace.
- **A helper the lead does not end.** Its entry holds its share until its session ends. That slows the clone, and starts nothing past the pace.
- **Subagents started through the harness's tools,** other than helpers, are counted by the agent alone, and no other session sees them (DEC-082 point 7).
- **Reviews of several changes at once** run their reviewers unconfined in the seat's checkout (ADR-066 point 10). A reviewer that writes there writes under the other reviews and under the seat's own work, until a record confines the reviewers' runs (ADR-073 point 10).
- **The seat's checkout beside reviewers.** A reviewer that checks out its change in the seat's checkout, a case ADR-073 point 10 allows for, moves that working tree off the default branch while the seat goes on working. The agent's builds are then refused (exit 1), and the seat's own commands run from a build's unreviewed commits. This record does not settle it. A record settles it before the build relies on reviews running beside the seat's own work: that reviewers never check out in the seat's checkout, or that the agent's commands refuse while it is off the default branch.
- **What runs at once costs the machine.** Each build makes its own clone, caches and sandbox, and reaches its build's hosts, so the pace bounds disk, memory and network use only by bounding the runs.
- **A command outside its session's shell** passes as a person's run (point 9).
- **A stop the session check does not see.** The check once in each session (point 9) runs from the session's own shell, and tells the person of a harness that does not find the session there when the session's first subagent starts. A stop that starts partway through a session, after the check, passes the agent's calls from then on as a person's, held only by the caps the agent passes each command (DEC-082 point 1), and nothing says so until a later session's check. So too for every stop in a session whose agent does not run the check. A harness that finds the session from the session's own shell, but not from a helper's, passes every command a helper runs as a person's, held only by the caps the helper passes within its share, and no check says so.
- **An event posted and not yet recorded.** Where the event of the run a command starts, its build's start event or its resume event, is posted and the state does not record so, the build gets no ending. That happens where the command is killed after the post and before it records it, and a recovery then reads the state, and where the tracker accepted a post whose reply never came, and the command makes the state final itself (point 2). The window is one write of the state, or one reply. A first build then has a start event on its Task with no ending, and a resumed build waits on its question again while its Task's record shows the resume, so its claim may lapse. Within the window, ADR-073 point 9's "**each ending,** of a build whose start event is posted" and point 5's "lost if its process dies", of a resumed build, do not hold, as they did not in ADR-073's own window of one write, in which its detached process posted the event first and wrote the state after. A command or a recovery that read the Task's record for the build's event would close the window, and this record does not decide that.
- **A process left once its harness has ended.** A process of a build's run that lives on after the run's harness has ended, in a session of its own or not, has been re-parented, and nothing can confirm it is the build's. So a recovery ends none such (point 2), and the build's entry no longer counts it (point 6). Started inside the sandbox, it stays inside it (ADR-073 point 10).
- **A slot held by a process that never ends.** A build's slot stays held while a process its state names lives, whether or not a recovery can confirm it is the build's (point 2). A process that never ends, such as one outside the build that a state names, holds that slot for good, which slows the clone and starts nothing past the pace. The refusal of a build with no slot free names the entries that hold the slots, so the person sees which one does (point 1).

### 11. The probe

Before the build rests anything on them, a probe confirms on each platform the adapter supports:

- The adapter's declaration finds the session from a command the session's shell runs and from one a helper's shell runs, and finds none for a command a person runs at their own terminal. The session's process it names ends when the session ends.
- A process's id with its start time tells a live process from one that ended, and from another that took its id.
- A lock the operating system holds for a process in the runtime folder is released when that process is killed.
- A build's lock passes from the command that writes its first state to the detached process it starts with no gap: a `--wait` that reads that first state before the detached process has started, or before it has named itself, finds the lock held, and recovers nothing.
- A detached process killed while its run still lives releases the build's lock, the build's entry counts its slot while the run lives, and the recovery that follows ends what is left of the run's and the checks' sandboxes, found as the runner finds them, a run's process in a session of its own among them, and confirms none lives before it marks the build lost.
- A detached process killed between starting the harness or a check's process and naming it in the state leaves no such process running.
- A recovery of a state that names a process outside the build ends nothing of it.
- No process of a build's run or of its checks holds a descriptor of the runtime folder.
- A link at a state file, a lock, an entry or the runtime folder leads no writer, and no removal of an entry, to anything outside the folder.
- Two build commands started together on the agent's call, at a pace of one, start one build.
- A review command killed while its reviewers run leaves an entry that holds one slot for each reviewer still running.
- Two hand-backs started together take turns, and a hand-back beside the seat's own fetch and push moves only its own references.

A fact the probe disproves refines or supersedes this record.

### 12. The harness requirement

The commands hold the agent's calls only where the adapter's declaration finds the session (point 9). Where a declared adapter's harness stops finding it, every one of the agent's calls passes as a person's: no pace is held and no helper is entered, and only the check once in each session (point 9) says so, for a stop that holds in the session's own shell when the check runs (point 10). So the pace rests on a property of the harness ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), which this record words in terms any harness could meet:

> A command that a session's own shell runs, or the shell of a helper the session starts, can tell which session it runs within, and can name that session's process, which ends when the session ends.

- **Observation point:** inside a session, where a command its shell runs reads what the declaration finds.
- **Evidence:** this record's own design, a design dependency (COR-047 point 9): point 9's choice of the session as the sign of the agent's call, on which points 5 to 9 rest. DEC-082 point 7 needs some sign, and this record chose this one. It is no transient defect, so it names no retirement condition.
- **What depends on it:** the register's hold on the agent's calls, each helper's entry, and the end of a helper's entry with its session (points 5 to 9).
- **What it does.** It records the dependency, bounds the Claude Code adapter's answer to the versions the probe (point 11) tested, and tells whoever adapts another harness what to supply. - **Declared with DEC-082's build.** That build adds it to the requirement set. Each adapter answers it in its support declaration (the adapters README, "Harness requirements"). ## Rationale

**Why builds at once, and one for each Task.** DEC-082 has a worker keep several Tasks in flight and run as many subagents as its pace allows, builders among them. One build at a time in a clone would hold every worker to one builder, whatever its pace. Each build already runs in a clone of its own, under its own rules, and comes back only through its hand-back, so builds of different Tasks share nothing but the repository they come back to. Two builds of one Task would race for its branch, its claim and its question, so a Task keeps one build. A build that waits keeps its Task until `--answer` or `--hand-back` ends the wait, since the Task's record on the tracker shows the wait, and its claim does not lapse while it does (ADR-073 point 5, "The claim").

**Why a build's state file is its entry.** A build already keeps its state in a file its process writes, which names the process and whether the build runs. A second record of the same run would be written at another moment, and could show a build running where its state shows it ended. One record of each run cannot disagree with itself. A state file that holds no slot is no entry, so a person's build, or one that waits, is in no register, and the Task's one build is still found by its state file.

**Why the first writer holds the build's lock until the detached process does.** The command that starts a build writes its first state before the process that runs it exists. A lock taken only by that process would leave a moment in which a state that is not final has no holder, and another session's command would recover a build that is only starting. A lock held from the first write, and passed with no gap, closes that moment. It passes to the detached process alone, since a run or a check that inherited it would hold it past that process's end: the lock would no longer tell the writers gone, a build whose process died would never be recovered, and a descriptor open for writing would let a sandboxed run write a file of the seat's clone (ADR-073 point 3). The command writes nothing after the start, and the detached process names itself, so the two never write the state at once. A build's entry lives while its lock is held, so a command killed after the start leaves no moment in which the build counts nowhere.

**Why an entry lives with its processes, and lapses at no time.** The register counts runs, and each run is bounded by a process. The operating system knows when a process ends, whether it finished, failed or was killed, so an entry bounded by its processes outlives neither its runs nor, for a helper, its session. A run can outlive what entered it, a reviewer its killed command, a build's run its killed detached process, or a build its helper's session, so an entry names each run's process, and a run whose helper's entry has ended counts against the pace itself. Each process the state names is named there before it runs anything, so a detached process killed between starting one and naming it leaves none that counts nowhere. A recovery ends what it confirms is left of a build's run before it marks the build lost, and the build's slot stays held while a process its state names lives, so a lost build's slot frees only once every process its state names has ended. A time limit would either outlast a dead run, whose slot nobody then uses, or end before a long one, so that the next command starts past the pace.

**Why a recovery ends only what it confirms, and marks the build all the same.** The runtime folder lies where a sandboxed command writes, and the commands that read it run outside the sandbox wherever the methodology's command does, so what they read there may narrow what they do, widen it only where a person shown the widening makes it, and never choose or redirect where they write (ADR-095 point 1). A recovery that ended whatever its state named could be led by a state written to name a process of the person's to end it, so the names only point the way, and the recovery ends what it finds of the build's sandboxes, as the runner does. The runner reaches every process descended from the harness, one in a session of its own included (ADR-066 point 11), which a process group does not hold, so the recovery finds them as the runner does, not by a group. A recovery that marked nothing until it confirmed would leave a state that is not final for good: every command in the clone would try it again, a `--wait` on it would exit 8 forever, and its Task would be refused a new build. So it marks the build not borne out, as the runner does where it cannot confirm (ADR-073 point 1), and the slot that a named process holds while it lives keeps the pace. Writers that keep to regular files inside the folder, and follow no link, keep a link a sandboxed command made from redirecting a write or a removal.

**Why one lock, and nothing slow under it.** Two commands that each count the register and then enter a run can both find the last slot free. A lock over the count and the entry closes that, and a lock the operating system releases cannot be left held by a run that died. A read of the tracker under the lock would hold every other command in the clone on the network. So the pace is read before, and a pace that changes in between is read one start late, as DEC-082 point 9 already allows. A recovery posts on the tracker too, so a count under the lock only tests each build's lock, without waiting, and leaves a recovery until after. A command waits for one build's lock at most, taken first, and a test takes a lock only without waiting and lets it go at once, so among the clone's two locks and every build's, no two commands each hold a lock the other waits for.

**Why hand-backs take turns.** A hand-back's check, fetch, signing and move are seconds of work on the one repository every build comes back to, beside the seat's own commands. Taking turns keeps each hand-back's check and move together, and a key that asks for its passphrase asks once at a time, at the cost of a hand-back that waits seconds for another, or, while a passphrase prompt is open, waits on the person who answers it. A hand-back that writes only its own references, from the commit it expects, stays out of the way of git's other writers. One that still cannot write waits on its hand-back, as one that could not sign does, so nothing is lost but time.

**Why the session, and not the terminal.** DEC-082 holds the agent's calls, and a person's own runs take no slot. The test of a terminal answers another question, whether a person can answer here ([project-management:DEC-069-when-fixers-start]'s Terms). It would hold a person's run in a script or a pipe as the agent's, and pass an agent's call where the harness's shell gives a terminal or the agent fakes one (ADR-066 point 11). What makes a call the agent's is the session whose shell runs it, so the commands read that. The register needs the session's process in any case, so that a helper's entry ends with its session, and one declaration of the adapter gives both.

**Why the declaration is data.** Every build and review command on the agent's call reads it, so reading it runs none of the adapter's code, as the backbone reads an adapter's other declarations. A registered command of the adapter, as its runner is, would put another process before every start.

**Why a harness requirement.** A declared adapter whose harness release stops finding the session would pass every call as a person's, with no pace held and no helper entered: a degraded result shaped like a correct one, which COR-047 exists to name. The requirement records that dependency, bounds the Claude Code adapter's answer to the versions the probe tested, and tells whoever adapts another harness what it must supply. The report cannot yet tell a harness that finds the session from one that stopped: it reads files only, so an answer bounded to tested versions resolves `indeterminate` either way, and none resolves `satisfied` until an adapter gives the report a way to observe (the adapters README, "What the report says"). So the requirement is no alarm, and the check once in each session is how a stop is noticed.

**Why a check once in each session, and not at every command.** The command the agent runs before its first subagent already reads its seat's state and its pace, so saying there whether it found the session costs one line, and tells the person before any of the agent's runs passes as theirs. A check at every command would catch a stop partway through a session too, but every run would print more, and there would be more to build. So a stop that starts partway through a session, a stop in a helper's shell alone, and a session whose agent does not run the check, are left open (point 10).

**Why a helper's share is held whole.** The lead hands each helper a share of its free slots, and the helper may fill it at any moment, with no command of the lead's in between. Holding the share whole keeps the lead's other runs and the other helpers out of it, so a helper's command never finds its share taken. A helper's runs count within its share and not against the pace again, so the share is counted once.

### Alternatives considered

- **A register file of its own, beside the builds' state files.** Rejected, as "Why a build's state file is its entry" says.
- **Entries that lapse after a time, renewed while their runs run.** Rejected, as "Why an entry lives with its processes" says.
- **The test of a terminal as the sign of a person's run.** Not taken, as "Why the session, and not the terminal" says.
- **The harness's mark of a tool's process as the sign of the agent's call.** Rejected: the mark names no session and no session's process, which a helper's entry needs, to end with its session (point 6).
- **A flag the agent passes on each call, marking it as the agent's.** Rejected: a call that left it off would pass as a person's, which leaves the pace to the agent's own count, as DEC-082's "Why the commands hold the agent's calls" rejects.
- **Hand-backs at once, each to its own references.** Not taken: git's own locks would allow it, but two hand-backs would sign at once, and more writers would meet on the seat's repository at once, for a saving of seconds.
- **The register in the git folder that every working tree of the clone shares.** Not taken: it would decide how a linked worktree shares its clone's state, which DEC-059 point 6 leaves open, while the clone's identity sits in the runtime folder of its working tree.
- **A state file for each build rather than for each Task,** so that a Task could have several. Rejected, as "Why builds at once, and one for each Task" says.
- **A new build that replaces a Task's waiting build.** Rejected: the Task's record would still show its question or its hand-back waiting, and its claim would not lapse.
- **The harness's event at a subagent's end, ending a helper's entry.** Named, not decided: where an adapter declares such an event, it would end the entry with the helper rather than with the lead's call. A later record may decide it.
- **A command that ends its reviewers or fixers when it ends, in place of naming their processes.** Not taken: a command killed outright ends nothing, so its runs would count nowhere.
- **A recovery that ends each process, or process group, its state names.** Rejected, as "Why a recovery ends only what it confirms, and marks the build all the same" says: a group holds no process in a session of its own, and a state written to name a process of the person's would have a command outside the sandbox end it.
- **A recovery that marks nothing until it confirms that no process of the build is left.** Rejected, as the same paragraph says: the build's state would stay not final for good.
- **A build's lock taken first by its detached process.** Rejected, as "Why the first writer holds the build's lock until the detached process does" says.
- **A build's lock that its runs and checks inherit too.** Rejected, as the same paragraph says: the lock would outlive the build's writers.
- **No harness requirement, the gap point 9 names standing for every harness.** Rejected, as "Why a harness requirement" says.
- **A check of the session at every command.** Rejected, as "Why a check once in each session, and not at every command" says: it catches a stop partway through a session, but every run prints more, and there is more to build.
- **The session's anchor moved onto the new declaration in this record.** Not taken: no record needs the anchor declared, and moving it would change the guard against changing another repository for a reason this record does not have.
