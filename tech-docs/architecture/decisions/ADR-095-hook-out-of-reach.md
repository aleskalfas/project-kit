## Summary

**In plain terms:** the permission hook decides, before each tool call, whether an agent may make it. It runs outside the sandbox, yet its code and the permission model it judges by sit in the project's checkout, which a sandboxed command can write. So a confined command could change what judges the calls after it.

This record keeps what a sandboxed command writes away from what judges it:

- **The rule:** code that runs outside the sandbox without a person choosing it never comes from a place a sandboxed command can write. Nothing it reads from such a place widens what it allows, unless a person, shown the widening, makes it.
- **The code:** in a project that turns the permission hook on, the hook and the decision core run from a copy of the installed release, in a folder of the person's that no sandboxed command writes. The adapter's start hooks, in every project, run only the command their registration holds.
- **The native locks:** native rules in the settings every project receives ask before an agent's call that could change what judges later calls, and deny a file tool's write into what holds the copy and its source. They hold whether or not the hook runs, and so before the person has made the copy (point 4). The backbone prints the same rules for the person's own harness settings, which reach every session of theirs, and never writes that file.
- **The policy:** the model stays in the checkout, where people edit it. *Realizing* the model, the step that turns it into what the harness enforces, also keeps a snapshot of it out of reach. The hook allows no more than that snapshot. A change in the checkout that narrows the model takes effect at once, and one that widens it waits until a person realizes it.
- **The bound** is the model out of a sandboxed command's reach that the hook judges by: that snapshot, or in a working run the model its runner names. Nothing in the checkout chooses it.
- **With no bound,** the hook still gives the guardrail denies, its own asks, and the denies and asks of the checkout's model. Where a bound binds but cannot be used, it also asks on every other call.
- **Shared build caches** leave the committed sandbox settings, since the person's later runs execute what lands in them.
- **What a person notices.** Some asks hold in every mode, and refuse in a mode that asks nothing: before a call that asks to leave the sandbox, before a command that would widen the bound or the sandbox or install over the release, before an agent moves its session into another tree, before a file tool writes a settings file of the harness's, and wherever a bound binds but cannot be used. So a builder whose work edits such a settings file meets an ask, which a run nobody watches refuses. Realizing, making the copy, turning the hook on or off, widening the sandbox and the upgrade's install widen nothing from an agent's session, so the person runs them from their own terminal.

**How far it holds.** The copy, the snapshots and the installed release the copy is made from are one set for each person, which all their projects share. So the protection holds only while nothing else that runs outside the sandbox unchosen can write them. That asks of every session of the person's, in every project:

- that its sandbox is on, and its commands leave the sandbox only with a person's approval;
- that its file tools, and the tools it connects, cannot write them, or the harness's settings that start code outside the sandbox, unasked;
- that the harness runs no code in it from a place a sandboxed command writes, such as the settings of a tree it checks out from the repository's history and moves the session into.

The native locks keep the escape, the file tools and the agent's moves so in each session whose settings carry them. The harness takes a project's committed settings only from the folder a session starts in, so the project's locks, and its hook, hold in sessions started at a checkout's root (point 7). Only the person's own settings carry them to every session on the host, so the protection needs them wherever a session starts elsewhere.

It asks the same of whatever else can write them, which the file system decides, not the host: another host that shares the person's home, a container or virtual machine that mounts it, or, under WSL2, the person's tools on the Windows side, which no sandbox confines. Where an agent's session, or other code the person did not choose, runs there unsandboxed, the protection holds for no project of the person's. Nor does it hold against the methodology's own commands where they run outside the sandbox and load what a sandboxed command wrote, against a command the sandbox exempts, or against an extension of the harness's that the person installs and that answers the harness's asks in their place. On macOS the methodology's command and its toolchain's runner are both exempt (ADR-014 point 2), so there an agent's call of either runs outside the sandbox whatever the checkout holds, and nothing confines it: only the asks and the hook's judgement of the call stand in its way. Point 7 names each such gap. The permission overview reports what it can see of each, and never reports the protection as holding for the machine, since it cannot see the other sessions.

**What it rests on.** The harness keeps its own settings files out of a sandboxed command's direct reach, as its documentation states for the session's working folder and the folders above it, save under two switches of the person's own settings, which the overview reports. Of the gestures that write those files from sources in the checkout, this record mends only realizing (points 3 and 7). A probe confirms the precondition with the other facts point 6 names. If it disproves the precondition, a later record supersedes this one whole.

## Context

**What prompted it.** [project-kit#3178](https://github.com/aleskalfas/project-kit/issues/3178) found that no part of the permission layer lies out of a sandboxed command's reach. The parts are:

- the hook, which the harness runs before each tool call, and the adapter's other hooks, which it runs the same way;
- the decision core, which the hook and the permission commands share ([ADR-003](ADR-003-permission-core-code-home.md));
- the model ([COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) point 1), and every other input from which the core reads a verdict.

All of them sit in the checkout, and a sandboxed command writes its working folder. The harness runs hooks outside the sandbox, with the person's full access, as it runs file tools and connected servers. Both facts come from the harness's documentation, as [ADR-066](ADR-066-unattended-agent-runner.md)'s Context records it.

**Why it matters.** A boundary is only as strong as what enforces it. Whatever changes the hook, the core or the model changes what every later call is judged by. The intent axis would then rest on a boundary the confinement axis lets the agent move: the boundary believed but absent that [ADR-004](ADR-004-autonomy-intent-confinement.md) point 4 forbids.

**What it builds on.**

- **The guardrails** all come from the backbone's catalog, since a capability may not define one ([ADR-021](ADR-021-capability-contributed-privilege-definitions.md) point 3). So a release's catalog holds every guardrail that release ships.
- **A folder only the person writes.** ADR-066 point 7 keeps a run's clone in a folder of the backbone's, outside every checkout, that only the person's account writes.
- **The session anchor** is set by the harness when a session starts, and no change of folder moves it ([ADR-034](ADR-034-foreign-repo-mutation-guard.md) point 1). A command line can clear it for the commands it starts (ADR-034 point 5).
- **The entry point** picks which release serves a command, by the checkout it runs in and by the project's pin ([ADR-039](ADR-039-pkit-entry-point-router.md)), and routes every command alike ([ADR-049](ADR-049-per-project-version-pin.md) point 4).
- **The installed release** is one for each person on a machine. An upgrade replaces it for every project that follows it, while a pinned project runs its pin ([ADR-063](ADR-063-upgrade-updates-the-tool.md), [ADR-064](ADR-064-upgrade-pins-by-default.md)). *The installer* is the toolchain's runner that installs it, which the backbone's own upgrade also runs (ADR-063 point 2), and which ADR-014 point 2 exempts from the sandbox on macOS.
- **The project's root** is found from the folder a command runs in, by asking version control first ([ADR-001](ADR-001-project-root-resolution.md)). The hook runs no version control, and reads its marker by hand ([ADR-060](ADR-060-path-scoped-workspace-allow.md) point 8).
- **The per-command escape.** The harness lets a shell call ask to run outside the sandbox. The setup of autonomy seals that escape, and elsewhere it stays open ([ADR-028](ADR-028-seal-unsandboxed-escape-under-autonomy-posture.md) points 1 and 5), the call riding the normal permission flow ([ADR-005](ADR-005-permission-profile-surface.md)'s Rationale, "Why `failIfUnavailable: true`, not `allowUnsandboxedCommands: false`, carries the invariant"). By the harness's documentation, a native allow that matches the command approves such a call too, while a native ask on the request puts it to the person in every mode that asks anything, ahead of any allow, and refuses it in a mode that never asks.
- **Native rules outlast the hook.** By the harness's documentation, it weighs its own deny and ask rules whatever a hook returns. A hook that cannot start, fails or runs past the harness's limit lets the call proceed (ADR-002 points 3 and 4), unless its registration asks the harness to block the call instead, which the harness's documentation offers.
- **But not an extension that answers for the person.** By the same documentation, an extension the person installs into the harness, which it calls a mod, answers after the hooks. Where no managed settings, managed list of connected servers or organisation's login binds the session, such an extension can approve a call that a deny rule refuses or a hook blocked, and approve unasked one that an ask rule would put to the person. A prompt tool or callback that the session hands its asks to answers them in the person's place too.
- **Realizing as a step.** Activating a profile realizes the result by default ([ADR-005](ADR-005-permission-profile-surface.md) point 4), and the setup of autonomy composes that with turning the hook on ([ADR-007](ADR-007-setup-command-class.md)).

**uv's cache.** The uv toolkit's write allowance to uv's shared cache is classed narrowing. So setup applies it unasked ([ADR-008](ADR-008-confinement-allowances.md) point 3), and it lands in the committed settings ([ADR-029](ADR-029-move-mutable-sandbox-state-out-of-tracked-settings.md) point 1). Yet the person's later uv runs, outside any sandbox, execute what lands there (ADR-066's Rationale, "Why a command that starts `uv` fails on Linux, rather than gaining a cache"). On macOS, uv cannot run inside the sandbox at all ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 2), so the allowance serves no sandboxed uv there.

## Decision

**Nothing a sandboxed command can write becomes code that runs outside the sandbox unchosen, or widens what such code allows unless a person shown the widening makes it. So, in a project that turns the permission hook on, its sessions run the hook from a copy of the installed release, out of reach, and every hook allows no more than its bound: the model a person last realized, or in a working run the model its runner names. In every project, native rules ask before an agent's call that could change what judges later calls, a shell call that asks to leave the sandbox among them, and deny a file tool's write into what holds the copy and what it is made from, whether or not the hook runs.**

- **What this record mends:** the permission hook and the decision core where the hook is on, the interpreter the hook starts, the adapter's start hooks in every project, and how the commands that set the bound find their root (point 2); the bound the hook judges by, how it is chosen, what realizing writes and who runs it, and an interlock on the gestures that widen the bound or the sandbox or install over the release (point 3); the hook's own verdicts, its ask before a shell call that asks to leave the sandbox among them, and the native locks beside them in every project and, where the person adds them, in the person's own settings (point 4); and the write allowances the backbone ships, and those it writes whatever its data says (point 5). The rest of point 1's class stays open (point 7).
- **Its precondition.** The harness keeps its own settings files out of a sandboxed command's direct reach. They register the hooks and hold the native rules that [ADR-002](ADR-002-permission-realizer-ownership.md) point 3 and point 4 below rely on. The harness's documentation states it for the session's working folder and the folders above it, save where the person's own settings switch off the sandbox's isolation of files, or let a sandboxed command make nested namespaces, under which the documentation says not to rely on it. The overview reports either switch where it finds it. No accepted record establishes the precondition, so the record states it, and the probe confirms it (point 6). If the probe disproves it, a later record supersedes this one whole.

### 1. What a sandboxed command can write is never trusted outside the sandbox

- **The rule.** Code that runs outside the sandbox without a person choosing to run it never comes from a place a sandboxed command can write. Policy or configuration that such code reads from such a place may narrow what it allows, and widens it only where a person, shown the widening, makes it. Nor can a sandboxed command choose or redirect where such code writes.
- **Chosen and unchosen code.** A person chooses code only when they run the agent's work in the checkout as that work, its tests or its build for instance. All other code that runs outside the sandbox is unchosen: a hook, a tool's own configuration, a build a tool takes from a shared cache, and the methodology's own commands, whoever calls them, since a person who calls one means the methodology's code and not what a sandboxed command left in its place. The code that a command the sandbox exempts runs on an agent's call is unchosen too, and so is the code an agent's shell call runs outside the sandbox, unless a person, shown the call, approves it. A person who installs the methodology from a source checkout chooses that checkout's code as the methodology's, so there the protection holds only as point 7 says.
- **A write allowance,** an allowance that opens a place to sandboxed writes, widens the boundary where it opens a place this rule keeps out of reach, however it was classed.
- **Its reach.** The rule binds every later architecture record of the project's, and the members of its class that points 2 to 5 mend. Every other member stands as the record that decides it says, until a record applies the rule to it and takes it off point 7's list, which names each. A member that a core record decides takes the rule only through a core record that states it, since a core record rests on no architecture record. So does a member that a capability's record decides, since a capability's records reach projects that receive no architecture record.

### 2. The permission hook and the decision core run from a copy of the installed release

- **The copy.** The harness runs the permission hook from a copy in the *backbone's state folder*: a folder of the person's where the backbone keeps its own state, outside every checkout, which only the person's account writes, as ADR-066 point 7 keeps a run's clone. It lies outside the folders a sandboxed command writes by itself (ADR-066's Context), and no allowance the backbone ships, or writes whatever its data says, opens it (point 5). It holds the copy, point 3's snapshots and index, and what the hook writes. It holds no run's clone, nor the folder a runner keeps for a run's settings, hook and model ([ADR-073](ADR-073-builder-runs.md) points 1 and 2), so the hook's guard on itself (point 4) reaches no clone.
- **The guarded folders** are the backbone's state folder, the folder a runner keeps for each run's settings, hook and model (ADR-073 points 1 and 2), the installed release with the entry point that starts it, and the installation of each interpreter the copy or the release runs on, where the person's account can write it. What lies in each runs outside the sandbox unchosen, or bounds what such code allows, so each is kept as the state folder is: by the native deny and the hook's guard (point 4), and by no allowance the backbone ships or writes (point 5).
- **One for each person.** Every project of the person's shares the guarded folders, the copy and the release it is made from among them, and so does whatever else can write them. The file system draws that reach, not the host: another host that shares the person's home, a container or virtual machine that mounts it, and, under WSL2, the person's tools on the Windows side all reach it. Where this record says *the machine*, it means all that can write those folders. So whatever can write them, in any session of the person's or from anywhere that reaches them, bears on the protection of every project (point 7). A copy made on one host serves every host that reaches the folder, and remaking it there moves them all.
- **What the copy holds:** the permission hook, the decision core, the release's catalog, and what they need to start. The hook starts an interpreter named by a path fixed when the copy is made, never looked up on the session's path. It starts it isolated: with no folder of the person's own packages, no step that adds the packages installed beside the interpreter, no setting taken from the environment, and no script folder or working folder on its path, importing the core from the copy by the copy's path. So it loads only the copy and the interpreter's own library. Making the copy prefers an interpreter whose installation the person's account cannot write; where the account can write it, that installation is a guarded folder, and the overview reports it. On a host where no interpreter lies at that path, the hook cannot start.
- **Making the copy** is one operation, served from the installed release (below). It makes the copy from that release, replaces it whole, and carries each snapshot the index names into the copy's layout (point 3, "Across releases"). A command of its own runs it. The gesture that turns the hook on runs it as a step only where no copy exists: there it replaces no hook that runs, and starts, from the release the person installed, each project's hook that could not start. Realizing never makes it. It runs no code from the checkout, and makes the copy only outside the sandbox: inside it, it makes nothing and says so.
- **Remaking it moves every project.** Where a copy exists, remaking it changes the hook of every project on the machine that turns the hook on, and carries each snapshot into the new release's layout. So it shows what it would change, and takes the interlock that realizing takes (point 3, "Across releases" and "An interlock on widening").
- **The source stays where it is.** The core keeps the home ADR-003 gives it, and the hook its home in the adapter. The release bundles both from there ([ADR-033](ADR-033-official-install-bundles-content.md) point 1), and the copy is made from what the release bundles.
- **The registration.** In a project that turns the hook on, the committed settings register the permission hook from the copy, since running it is the project's choice (ADR-002 point 2). They name the copy by a location each machine resolves for its own person, never by a path in the checkout. Turning the hook off removes that registration alone.
- **The adapter's other hooks** run no code from the checkout, in any project. Each runs only the fixed command its registration holds: a program named by its absolute path, with the shell's own builtins where it needs a shell, which loads nothing from the checkout or from the session's path. What such a hook gives turns only on what that command can test, such as whether the methodology's command is on the session's path, so the start hook keeps its line naming the install script where that command is missing. No copy serves these hooks, and none can be missing. A hook of the adapter's that needs code of its own runs from the copy, and so only where the permission hook is on. The settings merge keeps the registrations so, a hook a later release adds among them.
- **A machine with no copy.** There the permission hook cannot start, which is the loud fault of ADR-002 point 4. That fault lets each call proceed, so there only the native locks and the guardrails' native denies hold (point 4, and point 7, "The window before the copy"). The permission overview's self-check reports it (ADR-002's Implications), and names the command that makes the copy. The overview also reports a copy that differs from the installed release, and says that either may have changed since the copy was made: a release installed since, a copy planted, or a release changed in place. So it names first the command that reinstalls the release from its source, taking nothing from a shared cache, and then the one that remakes the copy. The overview runs from that release, so a changed release can hide the difference; what keeps the release as it was installed is the native deny and the hook's guard (point 4).
- **Served from the installed release.** The entry point serves from the installed release, whatever the checkout or its pin say, each permission command that reports a verdict or a bound, realizes the model, makes the copy, or turns the hook on or off, as its own work or as a step of it, such as activating a profile. Where it cannot tell whether a permission command is one of them, it serves it from the installed release. A release from this record's build onward that is not the installed one refuses such a command, and names the installed release. A release tells whether it is the installed one from where it runs, against the installation the person made, never from a value the command's caller sets. Each such command loads the core from the installed release, as the workspace removal command takes its code from the running backbone ([ADR-060](ADR-060-path-scoped-workspace-allow.md) point 8). Every other permission command loads the core from the release that serves it, which is the project's own tree only where the project is itself a source checkout of the methodology whose own code the entry point runs (ADR-039).
- **Code at the release, content at the pin.** The code of those commands is the installed release's, while the model they read is the checkout's, at whatever version the checkout pins. A release reads a model whole only where it knows each of its keys and values. So each of those commands reads the model only where its release reads it whole, and writes it only in the layout it read: a command that reports names what it could not read, and one that writes refuses and names the installed release. The hook's copy reads the checkout's model the same way, and treats one it cannot read whole as one that will not load (point 3).
- **The root they act on.** Each of those commands finds the project's root by the search toward the filesystem root that ADR-001 falls back on, starting from the real path of the folder it runs in, as version control does, reading version control's marker by hand as the hook reads it (ADR-060 point 8), and taking the methodology's own marker only where no repository's marker encloses the folder. It runs no version control, since version control runs what the checkout's configuration names. It shows the folder it acts on. Its answer matches version control's in a folder reached through a link, a linked worktree, a submodule, and a methodology installed below a repository's root. It can part from version control's answer where something besides the markers in the folders moves that answer: the checkout's own configuration or the environment placing the repository or its working tree elsewhere, or version control declining a repository or stopping at a file system's boundary. There it takes the markers as they lie.
- **One verdict.** The core chooses the bound that binds a session, judges each call by it and by the checkout's model, and combines the two verdicts (point 3). The hook acts on the core's verdict, and adds the adapter's own verdicts (point 4). So a command that reports a verdict reports the core's, which is why ADR-003 keeps the decision in the core. A command that reports a verdict judges as the hook would for a session anchored in the root it finds, or in a folder named to it, and names the bound that binds there. What turns on the harness stays in the adapter: how an ask meets the session's mode ([ADR-025](ADR-025-segment-conservative-bash-allow.md) point 7, and point 3 below), the adapter's own asks, and its guard on itself.
- **Two copies of one source.** The hook's copy and the commands come from one installed release while the copy is current, so a report matches what the hook enforces. The overview names a copy that is not current. The shared conformance tests hold every caller of a release to one verdict on each of a fixed set of calls, *the conformance calls*.
- **One set at a time.** A hook finds once, when it starts, which copy it runs, and reads that copy's core, the index and the snapshots kept with it. Remaking the copy puts the new copy and the snapshots it carried in place in one step that a hook sees whole, so no hook runs one release's code over snapshots in another's layout.
- **What the hook reads, and from where.** Its code, the release's catalog, and point 3's index and snapshots come from the backbone's state folder. It takes the session anchor as the harness gives it, finds from it the root of the checkout that holds it, as those commands find theirs ("The root they act on"), and reads the checkout's model there. With no anchor it reads no checkout, and gives only point 4's verdicts. Where its registration names the model it judges by, it reads that model and no checkout (point 3).
- **What the hook writes,** it writes only into the backbone's state folder, following no link.
- **Its runtime** stays a zero-dependency script (ADR-014 point 1).
- **Its scope.** This point governs the hooks the project's settings register. A working run's hook, which its runner registers from outside the run's clone, stays as ADR-073 point 2 decides: its code, and the core it imports, come from the project's tree at the default branch's head, and it judges by the model its runner names (point 3).

### 3. The hook allows no more than its bound, a model out of a sandboxed command's reach

- **The model stays in the checkout.** It is the source of truth that people edit, review and commit (COR-028 point 1).
- **The bound.** A session's *bound* is the model out of a sandboxed command's reach that its hook judges by, beside the checkout's model or in its place: the snapshot that binds the session, or the model its runner names (both below). Where neither binds, no bound binds.
- **Realizing keeps a snapshot.** Realizing turns the model into what the harness enforces (COR-028 point 2), through an operation the methodology's commands provide (COR-028's Implications). It also keeps a *snapshot* of the model of the folder it realizes, in the backbone's state folder, and records that folder in an *index* there. The snapshot holds, as the checkout held it, every input from which the core reads a verdict, wherever the core reads it, the subject a call is judged for among them. It records its own layout, and the native rules realizing wrote. Realizing reads each input as a regular file inside the folder, following no link, and refuses an input it cannot read so. Each write replaces a snapshot, or the index, whole.
- **The folder it realizes** is the root found as point 2 says, which realizing shows before it writes, and the index records it by its real path. Realizing refuses a folder that holds no model, and one that overlaps the backbone's state folder, by real path. Turning the hook on refuses such a folder too.
- **The folder's identity.** With each folder, the index records an identity of it that no command inside the folder can change, and that no later folder at its path shares.
- **The index.** Its writers, realizing and remaking the copy, take one lock, which is freed when its holder ends. So no two of them lose each other's writes, and none writes a snapshot over one written after it read. Each writes a snapshot before the index entry that names it. An index that exists but will not load makes the hook treat each session as bound by a snapshot it cannot use (point 4). The overview names each snapshot that no entry of the index names, and each realized folder whose identity no longer matches.
- **Which snapshot binds.** A session is bound by the snapshot of the nearest realized folder that holds its anchor. The hook finds it through the index, by the real path of the anchor the harness gives it, and reads nothing in the checkout to choose it. That path resolves only the anchor and the folders above it, which no sandboxed command writes (point 6), so no link a sandboxed command makes steers the choice.
  - So a bound realized for a folder holds every session anchored in it or below it whose hook runs, a worktree made inside it or a repository kept inside it among them, unless a nearer folder below is realized. The hook runs only in a session whose settings register it, which the harness takes from the folder the session starts in or moves into (point 7, "Where a session starts").
  - Where that folder's identity does not match the index, its snapshot cannot be used (point 4), and no folder further up stands in for it.
  - Where the backbone's state folder and the folder the session is anchored in overlap, by real path, the snapshot that binds cannot be used (point 4). This catches a state a person brought about unawares, which the gestures' refusal above keeps them from making. It stops no session that can write the state folder, since such a session can write the copy that checks it.
  - Where no realized folder holds the anchor, or there is no anchor, no snapshot binds.
- **A bound a runner names.** Where the hook's registration names the model it judges by, and that model lies in a folder the backbone keeps for a run, outside every checkout, which only the person's account writes and the run does not write (ADR-073 point 2), that model is the session's bound, in place of a snapshot. No sandboxed command writes that folder either (point 6). The core judges each call by it alone, chooses no snapshot and reads no checkout. A working run's runner names so the model it read from the default branch. Where the named model lies anywhere else, or cannot be used, the hook treats the session as bound by a model it cannot use, and asks (point 4). The overview names each committed registration that names a model.
- **Which checkout judges.** The hook reads the model of the checkout that holds the anchor, whatever folder a call works in. Where a subagent works in a worktree under an anchor in its parent's checkout, the parent's snapshot and model judge its calls, and a narrowing that only the worktree holds does not reach them.
- **The verdict.** Where a snapshot binds, the core judges each call twice, by the snapshot and by the checkout's model, and gives the stricter verdict: deny is the strictest, then ask, then abstain, then allow. Where the snapshot allows a call and the checkout's model abstains on it, the core asks, as for a grant the checkout revoked. Where the two give one verdict, its reason names what each names.
  - **A change in the checkout that narrows the model** takes effect at once: a new deny denies, and a revoked grant asks until it is realized.
  - **The revoked grant's ask meets the session's mode** as ADR-025 point 7's ask does: in a mode in which the person chose not to be asked, the hook abstains on the call, and the harness's own rules decide it until the revocation is realized.
  - **A change that widens it,** such as a new grant or a more permissive active profile, takes effect only once realized.
  - **A sandboxed command** can thus make the hook stricter, and never less strict than the snapshot.
- **The order, and the budget.** The hook first gives what reads nothing in the checkout: its own verdicts by the copy's catalog (point 4), its ask before leaving the sandbox and the interlock's ask among them, then the bound's judgement. Only then does it read the checkout: the model's judgement, and the guardrails of the checkout's catalog. It reads each input there as realizing does, as a regular file inside the folder, following no link, and never waits on one. All of it runs within a budget, a share of the harness's limit for a hook, which the registration sets well above the budget. When the budget ends, the hook gives the verdict it has.
- **When the checkout's model fails.** Where it will not load, the copy's release cannot read it whole (point 2), it faults in the core, or it does not finish within the budget, the hook judges by the snapshot alone, or where no bound binds gives its own verdicts alone. That drops only a narrowing not yet realized, which holds only while the checkout holds it in any case. The hook's reasons and the overview echo nothing of an input they cannot read.
- **The reason names realizing.** Whenever the snapshot refuses what the checkout's model would allow, the hook's reason says so, and names the realizing command.
- **Only realizing widens.** Realizing is one operation, and only it writes a snapshot that allows more than the one in place. The realizing command runs it, and so does each command that realizes as a step of its own work, such as activating a profile. A command that only writes the model realizes nothing, and says what it left unrealized. Turning the hook on realizes nothing either: where the folder has no snapshot, it says so and names the realizing command. Realizing, wherever it runs:
  - shows each place where what it would write, the snapshot or the harness's native rules, allows more than what is in place, and counts as a widening any place it cannot compare;
  - judges the conformance calls by the snapshot it would write, within the budget, with the copy's core, or the installed release's where no copy exists, and writes nothing where that fails;
  - writes nothing where a copy exists that differs from the installed release, and says, as the overview does, that either may have changed (point 2);
  - runs no code from the checkout, and is served from the installed release (point 2);
  - realizes only outside the sandbox, and inside it realizes nothing and says so.
- **An interlock on widening.** Two guards keep an agent from widening the bound or the sandbox, or changing the release the copy is made from, unasked:
  - **In the gestures.** Where a session anchor is set at all, even empty, each command that realizes, as its own work or as a step of it, writes nothing where anything it would write allows more than what is in place. The operation that makes the copy makes none, whether or not one exists, since a first copy starts each project's hook that could not start and puts in force every snapshot on the machine. Each command that turns the hook on or off does nothing, since turning it on puts in force a bound that may allow what the native rules would ask. Each command that would leave the sandbox of the project's sessions wider than it is writes nothing either: turning it off, turning off its seal on the escape, or adding an exclusion or an allowance of either class while it is on, as its own work or as a step of it. The settings a runner writes for a run it starts are not among these. The backbone's upgrade installs no release, and prints the install command as it does without a terminal (ADR-063 point 3), since an install replaces the release every later copy is made from. Each refuses so, and names the person's own terminal. A realizing that only narrows goes ahead, and a command that also writes the model writes it and says what it left unrealized.
  - **In the hook, and natively.** The hook asks, in every mode, before a shell call it recognizes as one of the commands that realize, make the copy, turn the hook on or off, or widen the sandbox, or as an install over the release the copy is made from, the backbone's upgrade among them, which changes what every later copy holds. The native locks ask before the plain form of each such command in every project, whether or not the hook runs (point 4). Their ask on the installer names the plain form that installs the release, so the installer's calls for other tools meet none.
  - **An interlock, not a boundary,** as ADR-034 point 5 declares its guard: a command line can clear the anchor, and a form of the call that the hook does not recognize, and the native rules do not name, passes both asks. The commands that widen the sandbox, and the upgrade, are served by whatever release the entry point chooses, and one from before this record's build refuses nothing. The installer's own command, called directly, meets only the asks. Whether realizing a wider model, or widening the sandbox, takes a person's gesture, as a boundary, is decided with [project-kit#3179](https://github.com/aleskalfas/project-kit/issues/3179).
- **A narrowing not yet realized** holds only while the checkout holds it. The overview reads the snapshot back (COR-028 point 2), and names each place where it allows more than the checkout's model. It also names each native allow in force that no realizing showed.
- **Across releases.** The copy's core reads snapshots in its own release's layout. Making the copy, from a newer release or an older one, carries each snapshot into its release's layout, working from the snapshot alone, under the index's lock, and puts the copy and the carried snapshots in place together (point 2, "One set at a time"). It shows each carried snapshot by which, on the conformance calls, the new core allows what the copy it replaces did not allow by the snapshot it carried. Where no copy exists, a snapshot left from an earlier copy has nothing to compare with, so the carry counts it as a widening it cannot compare. The person keeps each such snapshot, as a widening they were shown, or marks it as one that cannot be used (point 4), named until its folder is realized again. The conformance calls are a sample: a carry can widen a call they do not cover, and there the protection rests on the release the person installed.

### 4. The hook's own verdicts, and the native locks beside them, hold in every state

- **The hook's own verdicts** are those the adapter's hook gives without a model.
  - **The guardrail deny,** the hook's half of the double lock (ADR-002 point 3), for every guardrail of the copy's catalog, and of the checkout's where it loads within the budget.
  - **Each ask the adapter makes of its own,** as the record that decides it says. Such are the ask where a shell call may hide a guardrail (ADR-025 point 7), sought among the same guardrails, and the ask before a file tool writes outside the session's repository, the adapter's realization of ADR-034 point 2, which holds in every mode ([project-kit#2004](https://github.com/aleskalfas/project-kit/issues/2004)). The ask before a shell call of a command that point 3's interlock covers is another.
  - **The ask before leaving the sandbox.** The hook asks, in every mode, before a shell call that asks to run outside the sandbox, or whose request to do so it cannot read, whatever the model or the native rules allow. Where the harness seals that escape (ADR-028), the call would run inside the sandbox in any case, so there the ask costs a prompt, and in a run nobody watches, the call.
  - **Its guard on itself.** The file tools run outside the sandbox. So the hook denies a file tool's write into the guarded folders (point 2), wherever the machine keeps them, by every path that names them or resolves into them; a file that shares its storage with another folder is left to point 7. It asks before a file tool writes a file from which the harness takes its settings or connected servers, at any path where the harness looks for one, in any folder, the person's own among them wherever the environment moves them, and before one writes the harness's own state file. It asks before a call of the harness's tool that moves the session into another tree, since the move takes that tree's settings with it. It asks too before a call of any other tool, such as a connected server's, whose input names one of the folders it denies; that catches only the plain form, so it is an interlock. Each holds in every mode, whatever the model allows. So a builder whose work edits such a file meets the ask, which a run nobody watches refuses. An install from source is left to point 7, since its release is a checkout the person works in.
- **Apart from one another.** Each of these runs on its own, so a fault in one drops neither the others nor a model's verdict.
- **The native locks.** The settings the adapter merges into every project, whether or not it turns the hook on, carry these native rules. The harness weighs them whatever a hook returns, so they hold where the hook does not run, cannot start, fails or runs past the harness's limit (the Context, "Native rules outlast the hook"):
  - an ask before a shell call that asks to run outside the sandbox;
  - an ask before a shell call of each command that point 3's interlock covers, in the plain form a native rule can name;
  - a deny on a file tool's write into the guarded folders, named by where the backbone and the installer keep them by default under the person's home. It names a run's folders for settings, hooks and models and not its clone, since the harness applies such a deny to sandboxed commands' writes too;
  - an ask before a file tool writes a file, in any folder, from which the harness takes its settings or connected servers, and before one writes the harness's own state file in the person's home;
  - an ask before a call of the harness's tool that moves the session into another tree.
  - By the harness's documentation, each ask puts the call to the person in every mode that asks anything, ahead of any allow, and refuses it in a mode that never asks. An extension that answers for the person can pass each of these rules (point 7).
  - Each is one half of a double lock, as ADR-002 point 3 makes of the guardrail denies: the hook's asks and its guard on itself are the other halves. Where a machine keeps a guarded folder elsewhere, the deny does not reach it, and the overview says so.
  - The ask before a move is an interlock: the person approves a move, not the settings the tree brings, so a tree whose settings a sandboxed command wrote passes it once approved (point 7).
- **The person's own locks.** The same rules, held in the person's own harness settings, reach every session of theirs on the host, in every project, a project that does not use the methodology, a session started outside a checkout's root and a checkout at an older commit among them, so the protection needs them wherever a project's locks do not reach. The backbone never writes that file. The command that makes the copy, and the overview, print the rules, naming each guarded folder where this machine keeps it, and the overview reports where it read the person's settings and whether they carry the rules. Beside them, they name the harness's write block as a lock the person may add: it refuses, in every session and every mode, a file tool's write outside the session's working folders and into any settings file of the harness's, and removes the harness's tool that moves a session into another tree. It closes more than the asks do, wherever a folder lies, at the cost of every such write the person would approve and of that tool, and the overview reports whether it is on.
- **The checkout still narrows.** Where no bound binds, and where one binds but cannot be used, the checkout's model still narrows, as point 1 lets it: its denies deny and its asks ask, within the budget, and its allows allow nothing.
- **No bound.** Where no bound binds the session (point 3), the hook allows nothing by the model, gives its own verdicts and the checkout's narrowing, and abstains on every other call, so the harness's native rules decide it. Each ask and deny it gives says that the model is not in force, and names the realizing command.
- **A bound that cannot be used.** Where a bound binds the session but the hook cannot judge a call by it, the hook asks on the call, in every mode, unless one of its own verdicts or the checkout's model denies it. Its reason says that the bound is not in force, and names the realizing command. The hook cannot judge by the bound where:
  - the folder's identity does not match the index, the snapshot's layout is not the copy's, the backbone's state folder and the anchor's folder overlap, or the model a registration names lies outside the folders the backbone keeps for runs (point 3);
  - the index, the snapshot or the named model will not load, or judging the call by it faults or does not finish within the budget.
- **Why these asks override the mode.** The ask where a bound cannot be used, the ask before leaving the sandbox, the ask before an interlocked command, and the guard's asks each hold in every mode. A mode is the person's choice about this session's calls, made while the bound held. A sandboxed command can bring about a bound that cannot be used. A call that leaves the sandbox, an interlocked command, a move into another tree or a write the guard sees can change the bound of every later session, on this machine and in every project. Deferring to the mode would let each of these pass the protection in exactly the modes that ask nothing. The hook's other asks follow ADR-025 point 7's rule for the mode, as point 3 does for a revoked grant.
- **Faults.** A fault in judging by the checkout's model or in one of the hook's own verdicts, or a payload the hook cannot read, is a decision fault (ADR-002 point 4): what faulted gives no verdict, and the rest stand. Where none stands, the hook abstains (ADR-002 point 3), save that a shell call whose request to leave the sandbox it cannot read gets the ask above. A bound the hook cannot judge by is no decision fault but the state above, since the bound is what the person chose. So an error or a timeout in judging by it, which faults the core whatever model it reads, makes the hook ask rather than let the call proceed. A hook that cannot start stays the loud fault of ADR-002 point 4.

### 5. A write allowance is narrowing only where nothing outside the sandbox runs what it lets in

- **The test.** A write allowance is narrowing only where no code outside the sandbox later runs, or reads as configuration, what a sandboxed command writes through it, unless that code first checks it against a value no sandboxed command can write. Every other write allowance is widening, and ADR-008 point 4 governs it: never committed, never applied unasked, always reported.
- **A shared build cache fails it.** A tool builds and installs from its shared cache what the person's later runs execute, outside any sandbox, without such a check. On macOS the session's own uv runs outside the sandbox too. So no toolkit the backbone ships carries an allowance for a shared cache, and no gesture of the backbone applies one from data it ships. The overview names such an allowance as a widening wherever it finds one.
- **The guarded folders.** No gesture of the backbone writes a write allowance that reaches a guarded folder (point 2), whatever the data naming it says. The overview names one wherever it finds it.
- **What this point leaves to the project's data.** The allowances a project chooses, and the toolkits it defines, are read from the checkout, which a sandboxed command writes, so how that data classes an allowance settles nothing. Setup applies them as ADR-008 point 3 decides, save one that reaches the folders above, and they stay open (point 7).
- **A cache for each checkout passes it.** Where a tool runs inside the sandbox, setup gives each checkout's sandboxed runs of it a cache of their own, which nothing outside the sandbox runs from. It does so only where no command of the session that starts that tool runs outside the sandbox. The setting reaches the session's sandboxed runs alone, through the session's settings, and never lies in a tool's configuration file in the checkout, which the person's own runs of the tool, the methodology's commands among them, would read. The setting is per machine ([ADR-032](ADR-032-per-machine-activation-routing-axis.md) Rule A).
- **On macOS** uv cannot run inside the sandbox, so losing its shared cache costs nothing there.

### 6. The tests, and the probe

- **Tests hold that a sandboxed command or a file tool, alone:**
  - cannot write the hook's copy, the core it runs, a snapshot, the index, or another guarded folder, at its default place in every project, and, where the permission hook is on, wherever the machine keeps it, save through storage a file shares with another folder and in an install from source (point 7);
  - cannot change which snapshot binds a session, by breaking, moving or redirecting what marks the checkout's root;
  - can change, break or stall any input of the checkout's model, and never make the hook give a verdict less strict than the bound's, nor keep it from judging by the bound within the budget;
  - meets, where no bound binds, the guardrail deny, the hook's own asks and the checkout's narrowing, and, where a bound binds but cannot be used, an ask;
  - cannot make a working run's hook judge by any model but the one its runner names, nor make any hook judge by a named model outside the folders the backbone keeps for runs;
  - cannot run a shell call that asks to leave the sandbox without the native ask, nor, where the permission hook is on, without the hook's ask.
- **Tests also hold:**
  - the settings every project receives carry the native locks, whether or not the project turns the hook on, and the rules printed for the person's own settings are the same, with each guarded folder named where this machine keeps it;
  - the native deny leaves a run's clone writable to the run's sandboxed commands;
  - the hook's interpreter starts isolated, and loads no person's package, no package installed beside it, and no setting from the environment;
  - under an anchor, the backbone's upgrade installs nothing, and prints the install command;
  - every command that reports a verdict reports the core's verdict, which the hook acts on;
  - each command that realizes, makes the copy, or turns the hook on or off, as its own work or as a step of it, runs no code from the checkout, takes no route that data in the checkout chooses, runs no version control, reads no input through a link, and refuses under an anchor what point 3's interlock refuses;
  - the root those commands find matches version control's answer in a folder reached through a link, a linked worktree, a submodule, and a methodology installed below a repository's root;
  - each command that would widen the sandbox of the project's sessions refuses under an anchor;
  - the entry point serves each such command from the installed release, in every form it accepts, and a release from this record's build onward that is not the installed one refuses it;
  - realizing shows what it would write to the native rules, writes no snapshot that the copy's core cannot judge within the budget, and writes nothing where the copy differs from the installed release, naming the release's reinstall before the copy's remaking, as the overview does;
  - remaking the copy shows each carried snapshot that allows more on the conformance calls than before, and keeps none of them that the person did not keep;
  - a realizing and a carry run at once lose neither one's writes;
  - a revoked grant asks in a mode that asks, and abstains in one in which the person chose not to be asked;
  - the adapter's start hooks load nothing from the checkout;
  - no toolkit the backbone ships carries an allowance that fails point 5's test, and no allowance the backbone writes reaches a guarded folder.
- **The probe.** A probe confirms the facts below on each harness release and platform, as ADR-066 point 12 does for an agent's run. On a release or platform no probe has confirmed, they rest on the harness's documentation, and the overview reports the protection as unconfirmed there.
  - the precondition: the harness keeps its settings files out of a sandboxed command's reach, whether it keeps those of a checkout nested in the command's working folder, and which of its switches void it, those that switch off the isolation of files or allow nested namespaces among them;
  - which of the harness's other files that carry code or approvals it keeps from a sandboxed command's writes, and whether it keeps the target of a link it loads such a file through, a skill's among them;
  - where the harness takes a project's settings for a session started below a checkout's root, in a worktree, and after a move into another tree; whether a move applies the tree's settings and hooks, and shows them first; which commit a new tree is checked out from; whether an ask rule on the tool that moves a session prompts before it makes a new tree; and whether a subagent the harness starts in a tree of its own takes that tree's settings and hooks;
  - the interpreter the copy names, started isolated, loads nothing from a folder the person's account writes where the account cannot write its installation, and where that path is a launcher that finds the interpreter, what the launcher reads to find it;
  - whether the harness asks before a file tool writes outside the session's working folders, whatever its rules allow, and what its write block refuses and removes;
  - a shell call's request to run outside the sandbox reaches the hook with the call, and where the harness seals the escape, the call runs inside the sandbox, and whether the native ask still fires there;
  - whether any other tool that runs a shell command can ask to run outside the sandbox, and whether the native ask matches its call;
  - a native ask prompts in every mode that asks anything, ahead of any allow, and refuses in a mode that never asks, a native rule can name a file in any folder at any depth, and a native deny on a file tool's write reaches the folder it names through a link, each whatever a hook returns; and whether a file the platform shares between folders carries a file tool's write past the deny;
  - in which setups an extension that answers for the person, or a prompt tool or callback, can answer the native rules and the hook's asks;
  - hooks run outside the sandbox;
  - the harness gives the hook the session anchor it set when the session started, and no value in its settings changes the anchor a hook receives;
  - a sandboxed command cannot remove the folder it works in and make it again;
  - the committed registration finds the person's copy at the checkout's root, in a subagent working in a worktree, and in a session started in a worktree, and which anchor each has;
  - no folder a sandboxed command writes by itself, and no allowance the backbone ships, reaches a guarded folder;
  - the platform gives each folder an identity that no later folder at its path shares;
  - a hook's ask prompts in every mode, whatever the native rules allow, and refuses a call where nobody can answer it;
  - a tool that runs inside the sandbox works with a cache of its own for the checkout;
  - the hook's judgements stay within its budget on the project's own model.
- **A fact the probe disproves** refines or supersedes this record, as the change to the decision requires. Where it disproves the precondition, a later record supersedes this one whole.

### 7. What stays open

Each gap is reported rather than hidden, as COR-028 point 3 asks. The permission overview and the adapter's enforcement declaration state each one that bears on the protection, for each platform. The overview reports what it can see of each from this machine's settings and this checkout, and says what it cannot see, such as the other sessions on the machine.

**Members of point 1's class.** Each stands as the record that decides it says, until a record applies point 1 to it and takes it off this list (point 1, "Its reach"). Follow-ups of project-kit#3178 take each up.

- **Code that runs outside the sandbox on a person's or an agent's call, and loads what a sandboxed command wrote.** A sandboxed command followed by such code reaches past the protection, the copy and the snapshots included.
  - The methodology's own commands load code and configuration from the checkout wherever they run outside the sandbox. For each command that point 2 does not serve from the installed release, data in the checkout also chooses the code, through the entry point's routes (ADR-039, ADR-049).
  - A command the sandbox exempts runs outside it on an agent's call, and the protection holds against that call only as far as the hook's judgement of it, which confines nothing (ADR-004's Rationale, "Why pkit delegates confinement rather than enforcing it"). The records that exempt a command decide when it is exempt ([ADR-027](ADR-027-required-sandbox-exclusion-auto-apply.md)), and the overview counts each (ADR-008 point 4). Where the installer is exempt, as on macOS, every agent's call of it runs outside the sandbox, whatever it runs, so any of its forms can write the guarded folders past the native deny, while the asks of point 3's interlock name only the plain form that installs the release.
  - The registration finds the copy, and the person's gestures find the installed release, through the environment the person's session or terminal starts with. Tooling of the person's that sets that environment from the checkout reaches both.
- **Code that the harness and other tools run or load on their own,** from files a sandboxed command may write. It needs no step of the person's, and where it runs in any project's session on the machine, it can write the guarded folders.
  - **A move into another tree.** The harness's tool that moves a session into a worktree takes that tree's settings and hooks with it, and makes a new tree from the repository's history, which a sandboxed command writes, or enters one already made, which a sandboxed command can make. So one call of the agent's can bring hooks that run outside the sandbox. The native locks and the hook ask before the move (point 4), which is an interlock, and the harness's write block removes the tool. A subagent the harness starts in a tree of its own, where it takes that tree's settings, which the probe finds, moves with no call to ask on.
  - **A skill's hooks.** The harness takes a project skill's hooks and pre-approvals from where the adapter deploys it, and uses them before the person trusts the folder. A core record has the adapter deploy each skill as a link into the checkout's own tree ([COR-006](../../../.pkit/decisions/core/COR-006-artifact-roles.md)), so unless the harness keeps the link's target from a sandboxed command's writes, which the probe finds, a sandboxed command can give a skill hooks that run outside the sandbox when an agent invokes it. Only a core record can apply point 1 to it (point 1, "Its reach").
- **The writers of the harness's settings.** The native rules decide every call the hook abstains on. The harness keeps its settings files from a sandboxed command's direct writes, and realizing shows and interlocks what it writes there (point 3). Other gestures write those files from sources in the checkout, and what they write there does not yet widen only as realizing does: the native rules, the sandbox's switches, exclusions and write allowances, and the hooks and the environment those files set. Those that widen the sandbox take point 3's interlock, which is no boundary. ADR-008 point 3 states one such gesture, which applies the allowances a project chooses (point 5).
- **A working run's hook** judges by the model at the default branch's head alone, read from the repository's history, and not by a model a person realized (ADR-073 point 2, point 3 above). ADR-073 point 10 states it.
- **A clone made for an agent's unconfined run** lies outside every realized folder, so its hook gives its own verdicts and the clone's narrowing (point 4). Where such a clone lies, and what its run loads from it, stays as ADR-066 point 10 decides, which ADR-066 point 11 states.

**Limits of the protection.** These are no members of point 1's class. Each says what holds it.

- **The window before the copy.** In a project that turns the hook on, from the sync that brings this record's build until the person makes the copy, the permission hook cannot start, and each call proceeds (ADR-002 point 4). None of the hook's own verdicts hold there, only the native locks and the guardrails' native denies (point 4). So whatever passes the native locks, as the other limits here name, can plant a copy, or change the release it is made from, and a planted copy ends the fault that tells the person to make one. The overview reports a copy that differs from the installed release, and realizing refuses on it, each naming the release's reinstall before the copy's remaking (points 2 and 3). The release's notes give the order: install the release, make the copy, and only then sync a project that turns the hook on.
- **Everything else that can write the guarded folders.** The guarded folders are one set for each person, as far as the file system reaches them (point 2), so whatever writes them passes the protection of every project on the machine. A session whose sandbox is off can, in any project. So can a call that leaves the sandbox unasked, a file tool's write that nothing guards, into those folders or into a settings file of the harness's, which starts code outside the sandbox, and an agent's move into a tree whose settings a sandboxed command wrote. Each can in a session whose settings carry no native lock, such as one in a project that does not use the methodology, one started where it reads none of the project's settings, or one in a checkout at an older commit (below), unless the person's own settings carry the locks, or the harness itself asks before such a write, which the probe finds (point 6). So can a connected tool, in any project, and an extension that answers for the person (below). The hook asks and guards only in the sessions of a project that turns it on. What runs outside every sandbox, such as the person's own terminal, another host, a container or the Windows side of WSL2, can write the folders too, since the sandbox bounds only what it confines. The overview reports a state folder on a file system it can tell another host shares, and whether the person's own settings carry the locks. A follow-up of project-kit#3178 decides how all of these keep the folders out of reach.
- **Where a session starts.** The harness takes a project's committed settings only from the folder a session starts in, or the tree it moves into, with no fallback to the folders above it. So a session started below a checkout's root, or above it, runs no permission hook and meets none of the project's locks, and only the person's own locks hold there. The overview cannot see where sessions start, and the release's notes say to start a session at a checkout's or a worktree's root.
- **A connected tool's write.** The harness runs connected servers outside the sandbox with the person's access, so a tool of one that writes files can write the guarded folders on an agent's call. The native locks name such a tool only by its name, and the hook asks only where the call's input names a guarded folder (point 4). The overview names each connected server it can see.
- **An extension that answers for the person.** An extension the person installs into the harness can approve a call past every native rule and the hook where no managed setting binds the session, and a prompt tool or callback that the session hands its asks to answers them in the person's place (the Context, "But not an extension that answers for the person"). Whatever the person installs as such holds the protection of every project in its hands. The overview names each it can see.
- **A session whose sandbox is off.** No command of it is sandboxed, so nothing of the protection holds against its shell, which writes whatever the person's account writes. The hook's judgement of a shell call confines nothing (ADR-004's Rationale). The overview reports the protection as absent wherever this machine's settings keep the sandbox off, and a follow-up of project-kit#3178 brings the sandbox posture the commands set up into agreement with the records that decide it.
- **Who widens.** Until project-kit#3179 is decided and built, nothing that is a boundary keeps an agent's call outside the sandbox from realizing a model that a sandboxed command widened, or from widening the sandbox: point 3's interlock can be passed, and a release from before this record's build realizes and widens under no interlock at all.
- **A working folder or a write allowance over a guarded folder,** by its path or through a file the platform shares between folders, opens it to sandboxed commands. Where the installer links the release's files from a tool's shared cache, a write into that cache changes the release by a path no deny names: a sandboxed command's where an allowance opens the cache, and a file tool's unasked. The gestures refuse to bind a folder that overlaps the state folder, and the hook treats a bound there as one it cannot use (point 3). The overview names each such folder or allowance it finds, and a release whose files share storage with another folder.
- **An install from source.** Where the methodology runs from a source checkout (ADR-033 point 2), the release the copy is made from is that checkout. There the protection holds only between the gestures that make the copy, the hook's guard does not reach that checkout, and the checkout bears the loud faults and the realizing steps all the same. The overview reports such an install.
- **A checkout at an older commit,** from before this record's build, registers the hooks as it did then, from its tree, and its settings carry no native lock. A session started there, or moved there, runs the start hooks from files a sandboxed command may write, and its escape and file tools meet no native lock but the person's own. So it passes the protection of every project on the machine, since its start hooks run whatever the locks hold. The overview reports such a registration, and the release's notes say to bring a checkout past this build before starting a session in it or moving one there.
- **A replaced realized folder.** A sandboxed command writes every folder below its working folder, so it can replace a realized folder nested there, and, where the probe finds it can, its working folder itself. The folder then gets point 4's asks until it is realized again. It widens nothing.
- **A narrowing that blocks.** A sandboxed command can narrow the checkout's model until the hook refuses or asks on every call, the calls that would repair it among them. Only the person's own terminal then recovers the session. It widens nothing.
- **A newer model under an older release.** After a project's pin moves past the installed release, the commands point 2 serves from it refuse a model that holds anything that release does not know, and the hook judges such a checkout's model as one that will not load, until the person updates the installed release and remakes the copy. It widens nothing.
- **The copies sync carries.** The permission hook and the core propagate into a project's tree with the trees they live in. A working run's hook runs them from there, read from the default branch's head (ADR-073 point 2), an install from source runs them from its checkout, and a checkout at an older commit registers them as it did then. Past those, no session's hook in a project that turns the permission hook on runs them from its tree. A follow-up of project-kit#3178 decides whether sync goes on carrying them, ADR-073 point 2 among what rests on them.

## Rationale

**Why the rule turns on who chose the code.** A person who runs the checkout's tests from their terminal runs what a sandboxed command may have written, and knows it: the checkout is the agent's work, which they review and run as such. A rule against all of that would bind no project. What the sandbox's protection needs is narrower: no code a person did not choose to run as the agent's work comes from where the agent can write. A person who calls a methodology command means the methodology's code, so that code is unchosen even on their call. Point 1 covers where such code writes as well as what it runs, since a write a sandboxed command can redirect changes a file it could not write itself.

**Why policy as well as code.** The model decides what the hook allows. A sandboxed command that could widen the model would gain what changing the code gains, without touching the code. So the rule covers both: the checkout may narrow at once, and only a person shown the widening widens.

**Why the code runs from a copy of the release.** Three ways keep the code out of reach: deny writes to its files where they lie, read it from history, or run it from elsewhere.

- **Denying sandboxed writes where the files lie** fails each command that moves a working tree across a change to them, such as a branch switch, a pull or a rebase, and sync where sync runs inside the sandbox. Such a command may stop partway. The harness's own settings files bear the same cost, but they seldom differ between branches, while the permission layer's change with each upgrade and each new grant. The file tools, which run outside the sandbox, would still need a guard of the hook's own.
- **Reading from the default branch** reads a git folder that sandboxed commands can write (ADR-066's Context).
- **The release** is installed outside every checkout, by a person. The installed release itself serves the commands that copy it, realize the model and report the bound, so data in the checkout cannot choose which release that is, though the session's environment can (point 7).
- **The cost:** a change to the hook or the core reaches a session only once it is released, installed and copied. Tests and CI still run the checkout's code, and in an install from source the release is the checkout.

**Why the start hooks run only what their registration holds, and the permission hook from the copy.** Each hook runs outside the sandbox with the person's access, so any of them left in a checkout could rewrite the copy and the snapshots. The state folder is shared by every project on the machine, so a hook left in any project's checkout reaches every project's protection, with no step of the person's. The start hooks need no code of their own: what they give turns only on what a fixed command can test, so their registration holds that command, and they run nothing from the checkout in any project, need no copy and fault on no machine. The permission hook needs the core, so it runs from the copy, and only in a project that turns it on, which accepts the copy's loud fault with it. Elsewhere that fault would land on every collaborator of a project that never chose the hook, and whether the sandbox is on is each machine's setting (ADR-032), while the registration is the project's.

**Why those commands are served from the installed release.** The entry point picks a release by data in the checkout: a source checkout's own code, or the project's pin (ADR-039 points 1 and 2). For the commands that make the copy and realize the model, that data would choose the code a person trusts to widen what the hook allows. For those that report the bound, it could choose a release that knows nothing of the copy or the snapshots, and so reports nothing. Served by the installed release, the choice stays with the person who installed it. The commands that only write the model keep the entry point's routes: they write the checkout, which a sandboxed command writes anyway, and nothing they write widens the hook until it is realized.

- **The cost.** The installed release is one for each person on a machine, so an install moves these commands, and the hook once the copy is remade, for every project there, pinned or not, where a pin otherwise keeps a project's version (ADR-064). After a project's pin moves past the installed release, these commands refuse a model that holds anything that release does not know, until the person updates it (point 7).

**Why that overturns routing every command alike.** ADR-049 point 4 routes every command, and its Rationale weighs a carve-out keyed on the command line against it on three counts. Each is answered here:

- **The command-agnostic contract.** It holds for every other command. For these, data in the checkout must not choose the code, which is the one thing a route by the pin does.
- **Unsafe in both directions.** The carve-out errs toward the installed release: a permission command it cannot place goes there. A release from this record's build onward that is not the installed one refuses such a command. An older release, which a pin may name, and a source checkout's own code, which the entry point's first route runs, refuse nothing, so a form the entry point misses can still run code the checkout chose. That is the interlock's gap, which point 7 states under "Who widens".
- **Reads are the most version-sensitive commands.** For these, the version that matters is the hook's. A report of the bound must match what the hook enforces, and both come from the installed release (point 2). These commands also read only what their release reads whole, and say what they could not read, so a mismatch with the pin shows rather than misleads. That is also the cost: ADR-039 D1's lock does not hold for them, since their code is the installed release's while the model is the checkout's at its pin.

**Why those commands read version control's marker by hand.** Version control runs what the checkout's configuration names (ADR-066's Context), and it has no switch that sets a repository's own configuration aside. These commands run no code from the checkout, so they run no version control, and read its marker as the hook already does (ADR-060 point 8). ADR-001 asks version control first because a search of its own gets symlinked paths, linked worktrees and submodules wrong, so these commands start from the real path, as version control does, and are held by test to version control's answer in those layouts, and take a repository's marker before the methodology's so that a methodology installed below a repository's root finds what version control finds (point 6). They part from version control's answer only where something besides the markers moves it: the checkout's own configuration, which these commands must not trust, the environment, which ADR-001 keeps out of the resolution, or version control's refusal of a repository or its stop at a file system's boundary, where these commands take the markers as they lie. So this refines ADR-001 rather than overturning it: its aim, version control's answer in the layouts it names, holds for these commands by test, and only the means differs. ADR-049 point 4 is overturned in part instead, since its Rationale weighs this very carve-out, and its reason, ADR-039 D1's lock of code to content, fails for these commands. The marker lies in the checkout, so a sandboxed command can move the root they find. Realizing shows the folder it acts on, refuses one with no model, and binds nothing to a folder the person did not see, so a moved root costs a refusal or a bound the person saw. The convenience of running from a subfolder holds for these commands too.

**Why the core gives the hook's verdict, and chooses its bound.** ADR-003 keeps the decision in the core so that its callers never diverge. Choosing the bound, judging by two models and combining the verdicts is decision, so it lives there too, and a command that reports a verdict reports the core's. The adapter adds only what turns on the harness. The hook's copy can differ from the installed release, so the overview reports when it does.

**Why the registration stays committed.**

- **Committed,** it reaches every clone and worktree, and running the hook stays the project's choice (ADR-002 point 2). Where a machine has no copy, the hook's failure to start is loud.
- **The cost:** each collaborator who pulls it meets that loud fault on every call, until they install the methodology and make the copy.
- **In each checkout's local settings,** a fresh clone or a new worktree would run with no hook and no fault.
- **In the person's own harness settings, outside every checkout,** with the project's choice kept beside the snapshots. This covers every clone and worktree with no committed path to rewrite, and spares collaborators without the methodology the loud fault. But running the hook would become each person's choice on each machine, so a collaborator who never turned it on would run with no hook and no fault. The backbone would also write a file the person owns outside the project, and the hook would run in every session on the machine, in every project.

**Why the hook judges by both the snapshot and the checkout.**

- **The checkout alone** is the gap this record closes.
- **The snapshot alone** keeps a revoked grant in force until someone realizes. That is a boundary believed but absent (ADR-004 point 4).
- **Falling back on any difference between the two** would drop the model at each pull, sync and branch switch. A narrowing would wait for a gesture it does not need.
- **The stricter of the two verdicts** lets the checkout narrow at once and widen only through realizing.
- **A revoked grant asks.** Where the snapshot allows a call and the checkout no longer does, abstaining would hand the call to the harness's native rules, which may hold the grant as realized. Asking lets the revocation reach those rules at once, since, by the harness's documentation, which the probe confirms (point 6), the harness prompts on a hook's ask whatever its rules allow. The cost: on a branch whose model lacks a grant the snapshot holds, each call of that grant asks, as that branch's model has it.
- **Except where the person chose not to be asked.** In such a mode a call never granted runs unasked, so a revoked grant that asked would be stricter than one never granted. The hook abstains there, as ADR-025 point 7 has it for its own ask, and the revocation waits for realizing where the native rules hold the grant.
- **The snapshot alone, when the checkout's model fails.** The snapshot lies out of reach and the checkout does not, so a failure on the checkout's side may cost no more than what the checkout alone holds. Judging by the snapshot alone loses only a narrowing not yet realized, which the checkout can drop in any case, and keeps every deny and ask the snapshot holds. The order and the budget keep a stall in the checkout from costing the snapshot's judgement.

**Why the bound is found from the anchor.** Which snapshot binds must rest on nothing a sandboxed command can write. What marks a checkout's root, and the configuration that moves a working tree, lie in the checkout, so a lookup through them could be broken to reach no bound, or steered to a wider one. The harness sets the anchor and no command moves it, and the index lies out of reach, so the choice rests on neither. The identity guards a reused path: another repository cloned where a realized one stood does not inherit its bound. A bound covers whatever is anchored inside its folder because the person realized it for that folder. A worktree or a repository kept inside it is work started there, and its own model can only narrow the bound. A person who wants a folder inside it bounded otherwise realizes that folder on its own. Where the state folder and the anchor's folder overlap, the session could write the bound itself, so the gestures refuse to bind such a folder, and the hook treats a bound there as unusable rather than trust it.

**Why a runner may name the bound.** A working run's hook judges by the model its runner read from the default branch, placed outside the run's clone (ADR-073 point 2). Its anchor is the clone, which nobody realized, so a choice through the index would give it no bound, and its checkout is the clone the builder writes. Naming the bound in the registration keeps ADR-073 point 2 as it decides. The named model must lie in a folder the backbone keeps for runs, which no sandboxed command writes. A registration is written from sources in the checkout (point 7), and a model named anywhere else, such as a temporary folder, could be one a sandboxed command wrote, behind a registration that looks like the real hook. A registration's writer can already register any code as the hook, so this opens no new way in, and the overview names each registration that names a model.

**Why a bound that cannot be used makes the hook ask.** With no bound, no person has realized one for the folder, as at the upgrade that brings this record's build, and the hook's own verdicts with the checkout's narrowing keep the session usable without flooding the person with prompts. Where a bound binds, it is what the person chose. Abstaining there would hand every call to the native rules and drop each deny and ask that only the bound holds. A state that a sandboxed command can bring about, such as a replaced folder, a stall past the budget or a realized model the core cannot judge, would then switch the bound off. Asking keeps the bound's absence loud, and refuses where nobody can answer. Realizing judges what it writes, so that a person does not put such a bound in place unawares.

- **The cost.** In that state an attended session prompts on each call until the cause clears or the person realizes the folder again, in every mode. A run nobody watches, such as a review in the person's checkout, is refused each call. The state follows a change to the folder or the release the bound was realized for: a re-clone at its path, a remount that changes its identity, a remade copy whose carried snapshot the person did not keep, or a sandboxed command's work. It also follows a fault of the copy's core on some shape of call, and a judgement that runs past the budget on a loaded machine. A re-clone, a remount and a sandboxed command's work each touch one project. A remade copy, a fault of the core and a loaded machine can touch every project on the machine at once, since one copy serves them all. Remaking shows each snapshot it would leave unusable before it acts (point 3), and realizing judges the conformance calls, but neither rules out a fault on a call they do not cover. The no-bound state is the common one, and the flood is what it avoids there.

**Why realizing is one operation, and why the interlock.** Each command that realized by a way of its own would be one more path to widen that an agent can reach. One operation, which shows each widening against what is in place, the native rules included, lets a person see what they realize, even where the model changed between their review and their realizing. A command that realizes as a step of its work, as activating a profile does by default, runs that operation, so it keeps ADR-005's composition and adds no path. Turning the hook off widens every call at once, and turning it on puts in force a bound that may allow what the native rules would ask, so both take the same interlock. A gesture that widens the sandbox of the project's sessions widens more still: one session with its sandbox off passes the protection of every project on the machine. So it takes the interlock too, though it writes the harness's settings, which point 7 leaves open. An install over the release changes what every later copy holds, and where the installer is exempt it runs past the native deny. So the backbone's upgrade installs nothing under an anchor, and the asks cover both the upgrade and the installer's own command, which the backbone cannot make refuse. The interlock costs the person a terminal for each widening, and closes the plain ways for an agent to widen unasked: the anchor in the gestures, the ask in the hook, and the native ask in every project. The native ask is what holds where the hook does not run, in a project that leaves it off and before the copy, against a command line that clears the anchor or a release from before this build, which refuses nothing; in the common case it costs a prompt before a refusal. Under an anchor, the setup of autonomy stops at a step that widens, as ADR-007 rule 4 has a step that cannot complete stop, and names the person's terminal. Each guard can be passed, so it is declared an interlock, as ADR-034 point 5 declares its guard.

**Why making the copy is an operation of its own, which realizing never runs.** Remaking the copy changes the hook of every project on the machine and carries every snapshot there, so it can widen what the hook allows in every project at once. Run as a side effect of realizing, it would let a realizing that only narrows, which goes ahead under an anchor, remake every project's hook on the machine. So it is one operation, which shows what it would change and takes the interlock. Under an anchor it makes no copy even where none exists: a first copy starts each project's hook that could not start, and puts every snapshot on the machine in force at once, and a snapshot its carry cannot compare would be kept by an agent's call rather than a person. Turning the hook on runs it only where no copy exists, and gains no realizing, since ADR-002 point 2 keeps the two gestures apart (ADR-007 rule 1), as activating a profile gains no turning on (ADR-005 point 4). The cost: after an install of a newer release, realizing refuses everywhere on the machine until the person remakes the copy, and a project whose hook is on but has no snapshot gets no grants until its person realizes.

**Why the hook's own verdicts hold in every state.** The guardrails are the catastrophic denies, and keeping the hook's half of their double lock costs nothing (ADR-002 point 3). The asks are the hook's own, and only the asks before leaving the sandbox and before an interlocked command, and the guard's asks on the harness's settings files and on a move into another tree, have a native rule beside them. Kept apart, no one fault takes the others with it. With no bound, asking on every call would flood the person with prompts approved unread ([project-kit#2002](https://github.com/aleskalfas/project-kit/issues/2002)), and denying every call would stop the session.

**Why a call that leaves the sandbox is asked, rather than the escape sealed.** Where the escape is open, a call that leaves the sandbox rides the normal permission flow (ADR-005's Rationale, "Why `failIfUnavailable: true`, not `allowUnsandboxedCommands: false`, carries the invariant"). By the harness's documentation, a native allow that matches the command then runs it unconfined and unasked, and it can write the guarded folders. Asking before such a call closes that path and leaves the escape a person's choice, the operator's stopgap ADR-028 point 5 keeps outside the setup of autonomy. Sealing it wherever the hook is on, or in every project, would overturn in part ADR-028 point 1's choice to seal it only under that setup. An ask in every project's settings meets point 1's two reasons for refusing a baseline seal:

- **Legitimate fail-over** still runs where someone watches: the call leaves the sandbox once a person approves it. In a run nobody watches it gives way: the call is refused, and runs inside the sandbox only when the agent issues it again without the request, as a sealed escape would have run it. There the protection of every project outweighs the fail-over point 1 kept.
- **The operator's choice of posture** keeps the escape open and its use theirs, one approval at a time. What it loses is a native allow approving the escape unasked, which is an agent's reach for it rather than the operator's deliberate use, the reach point 5 removes under the setup of autonomy. Outside that setup that reach passes every project's protection, through the guarded folders all projects share. So the record refines ADR-028 point 5 in place rather than overturning point 1.
- **The cost:** each call that asks to leave the sandbox prompts, in every mode that asks and in every project, even where a native allow would have run it, and a mode that never asks refuses it. The ask also gives up the reversibility ADR-028's Rationale keeps for the seal, "a posture choice rather than a revocation": a project's operator cannot drop it, since the settings every project receives carry it and an escape from any one project reaches the folders every project's protection rests on.

**Why native locks stand beside the hook.** The hook fails open where it cannot start, as before the person makes the copy, and where it fails or runs past the harness's limit (ADR-002 points 3 and 4). It also runs only in a project that turns it on, while the guarded folders are every project's. The harness weighs its own deny and ask rules whatever a hook returns. So the native locks keep the escape, the interlocked gestures and the file tools' writes into the guarded folders locked in every project's sessions that read them and in every state of the hook, and in particular in the window before the copy, where nothing else would guard the folder the copy goes into or the release it is made from. The copy's source needs the same lock as its destination: a release changed in place becomes every project's hook at the next remaking, and runs every gesture the person makes from their terminal, and so does the interpreter each runs on. Every settings or connected-servers file of the harness's needs an ask too, the person's own and each checkout's, since what it starts runs outside the sandbox, and the harness reloads hooks from it while a session runs, so a write to it reaches the guarded folders past the deny. A move into another tree needs one for the same reason, since it brings that tree's settings. The native rules are configuration that actually holds, so the hook's asks and guard beside them claim no boundary the configuration does not hold, which ADR-028 point 4 forbids. The hook is their second lock, as it is for the guardrail denies (ADR-002 point 3), and it still earns its place: it asks on a request it cannot read, guards the guarded folders wherever a machine keeps them and by every path that names them or resolves into them, where the native deny names only their default places, guards the person's own settings wherever the environment moves them, recognizes forms of the interlocked commands that the native rules do not name, and gives a reason. The native rules hold only as far as the probe confirms (point 6), and an extension that answers for the person passes them (point 7).

**Why the person's own locks are printed, not written.** The guarded folders are the person's, and every session of theirs can write them, while a project's settings reach only the sessions started at its root. Only the person's own harness settings match the folders' reach: there the locks hold in a project that does not use the methodology, in a session started outside every checkout, and in a checkout at an older commit, whose own settings carry none. The backbone prints them rather than writing them: that file is the person's, outside every project, and the backbone prints what belongs in a file it does not own, as ADR-060 prints the ignore line rather than write the project's ignore file, its "print, don't mutate". No hook runs from that file, so no copy's fault reaches every session. The cost: they hold only where the person adds them, so the overview reports whether they are in place, and the locks in every project's settings stay the default.

**Why the hook's interpreter starts isolated.** An interpreter loads more than the script it runs: its own library, the packages installed beside it, the person's own packages and the startup files among them, and whatever the environment names. Each lies outside the copy, and a file tool can write those the person's account owns, so the next start of the hook, in every project that turns it on, would run what was written there. Started isolated, the hook loads only the copy and the interpreter's own library, and where the account can write that library, it is guarded as the copy is.

**Why an agent's move into another tree is asked.** The harness moves a session's settings with it, so a move into a tree a sandboxed command made, or one checked out from history it wrote, brings hooks that run outside the sandbox, with one call of the agent's and no step of the person's. The start hooks are mended for exactly such a path (point 2), and here the record cannot mend what the harness loads, so it puts a person's step before the move. The step is an interlock, since the person approves a move and not the settings it brings. The harness's write block removes the tool, at the cost of every agent's move, so the record offers it among the person's own locks and leaves it to each project's choice.

**Why the protection is stated for the machine.** The state folder is one for each person, as far as the file system reaches it, so that one install feeds one copy for every project there. A folder for each project would narrow nothing, since what runs as the person outside a sandbox writes every folder the person writes. So whatever can write it in any project's session can pass every project's protection, and the record says so rather than claim a protection for one project that the others' sessions can undo. The machine is what the file system makes it: a home shared with another host, mounted into a container, or reached from the Windows side of WSL2 extends it, and nothing the backbone sees on one host tells it what the others run. Each session can keep the folder only as far as its own sandbox, its own escape, its own file tools and the tools it connects allow, which the native locks govern only in the sessions whose settings carry them, and the hook only where it runs. A guard that the backbone keeps over every session on the machine is left to a follow-up that the probe informs (point 7).

**Why the checkout still narrows where no bound is in force.** Point 1 lets a place a sandboxed command writes narrow what the hook allows, and a narrowing needs no person's gesture. So with no bound the checkout's denies and asks stand, and only its allows wait for realizing. A project then keeps the denies only its hook holds from the upgrade on, before its person realizes it.

**Why a clone made for a run gets no bound of its own.** Tying such a clone to the snapshot of the checkout it came from would give the clone a bound the hook would not otherwise hold. So only code out of the checkout's reach could record the tie, and only for a folder that code made. That means the backbone making such clones, which ADR-066 left to a follow-up and which would overturn part of its point 10. Such a run keeps the hook's own verdicts and its model's denies and asks (point 4), and what it loses is the model's grants, which do not count there yet in any case (ADR-066 point 11).

**Why a shared cache widens.** ADR-008 classed a build cache narrowing because it makes the box usable without enlarging the agent's reach. A cache whose contents the person's own runs later execute does enlarge it, since what a sandboxed command wrote there later runs unconfined. A cache for each checkout keeps the usability ADR-008 sought, at the cost of a download in each checkout's first run, and a cache shared by every project's sandboxed runs would carry one project's writes into another's. Point 5's test states the line that ADR-008's split was drawn to keep.

### Alternatives considered

- **Deny sandboxed writes to the permission files where they lie.** Rejected: each working-tree move across a change to them fails, as does sync inside the sandbox, and the file tools stay open.
- **Read the model and the code from the default branch's head.** Rejected: the git folder is open to sandboxed writes (ADR-066's Context), and a branch's own model would never apply.
- **Act on a snapshot of the model alone.** Rejected: a revoked grant stays in force until someone realizes.
- **Fall back on any difference between the snapshot and the checkout.** Rejected: every pull, sync and branch switch would drop the model.
- **Fall back whenever the checkout's model fails.** Rejected: a failure on the side a sandboxed command can write would then cost the bound kept out of its reach.
- **Let a revoked grant abstain until it is realized, in a mode that asks.** Rejected: the harness's native rules may hold the grant as realized, so the revocation would wait.
- **Find the bound through the checkout's root, as the backbone finds a project's root.** Rejected: what marks the root lies in the checkout, so a sandboxed command could break the lookup or steer it to a wider bound.
- **Find the folder to realize as other commands find their root, asking version control.** Rejected: version control runs what the checkout's configuration names, and none of its switches sets a repository's own configuration aside.
- **Ask version control with every program its configuration could name switched off.** Rejected: the list of such settings is version control's to grow, so the claim that these commands run no code from the checkout would rest on a list nobody here keeps.
- **Take the folder to realize from the person alone, finding no root.** Not taken: it would cost the convenience of running from a subfolder, while reading the marker by hand, and showing the folder, binds no folder the person did not see.
- **Let a working run's hook choose its bound through the index.** Rejected: nobody realized its clone, so it would get no bound, and ADR-073 point 2 would not hold.
- **Honour a model a registration names anywhere outside the anchor's folder.** Rejected: places outside it that a sandboxed command writes, such as a temporary folder, would serve.
- **Let only the worktrees of a realized checkout take its bound,** tied by data out of reach. Not taken: the bound is the person's for a folder, the anchored checkout's own model narrows it, and a tie for each worktree would ask a gesture for every worktree.
- **On an identity that does not match, take the next realized folder up.** Rejected: a bound realized for another folder would stand in, wider wherever that one is wider.
- **Fall back quietly where a bound binds but cannot be used.** Rejected: a sandboxed command could bring that state about, and drop every deny and ask that only the bound holds.
- **Defer to the session's mode where a bound cannot be used.** Rejected: a sandboxed command could bring that state about, and switch the bound off in the modes that ask nothing.
- **Ask on a revoked grant in every mode.** Rejected: where the person chose not to be asked, revoking a grant would make its call stricter than one never granted.
- **Treat a snapshot as unusable where the installed release lies inside the anchor's folder.** Not taken: an install from source would then ask on every call in its own checkout. The overview reports it.
- **Rely on the hook alone to catch a state folder that overlaps the anchor's folder.** Rejected: a session that can write the state folder can write the copy that checks it, so the gestures refuse to bind such a folder, and the hook's check only catches what a person made unawares.
- **Give only the hook's own verdicts where no bound binds.** Rejected: it drops the checkout's denies, which point 1 lets narrow at once.
- **Seal the per-command escape wherever the permission hook is on, or in every project.** Not taken: it would overturn in part ADR-028 point 1's choice to seal the escape under the setup of autonomy alone, and the native ask closes the same path in every project, at the cost of a prompt.
- **Leave a call that leaves the sandbox to the native allow rules.** Rejected: a native allow would run it unconfined and unasked, where it can write the state folder.
- **Lock the escape and the state folder in the hook alone.** Rejected: the hook lets each call proceed where it cannot start, as before the person makes the copy, and where it fails or runs past the harness's limit, and it runs only in a project that turns it on. A session could then plant the copy in exactly the window before it is made.
- **Register the permission hook so that the harness blocks the call where the hook cannot start, fails or runs past its limit.** Not taken here: it would turn ADR-002 point 4's loud fault into a refusal of every call, for every collaborator of a project that turns the hook on until each installs the methodology and makes the copy, and so overturn that point. The native locks close the path the window opens without it. A follow-up of project-kit#3178 may propose it.
- **Leave the gestures that widen the sandbox to the hook's ask alone.** Rejected: the hook runs only in a project that turns it on, while a session whose sandbox is off passes every project's protection.
- **Leave the interlocked commands to the release's refusal and the hook's ask, with no native ask.** Rejected: where the hook is off, and before the copy, the release's refusal alone would stand, which a command line that clears the anchor passes and a release from before this build never makes. A native ask costs a prompt before a refusal in the common case.
- **Ask before every call of a connected tool.** Not taken: a session's connected tools serve most of its work, and asking on each would flood the person with prompts approved unread. The hook asks where a call names a guarded folder, and the follow-up on the other sessions decides the rest.
- **Keep a state folder for each host.** Not taken here: what reaches a shared home also reaches every host's folder in it, so it would narrow nothing against the other hosts' sessions. The follow-up on the other sessions decides it.
- **Start the hook through the methodology's command on the session's path.** Rejected: the path, and the entry point's routes, may lead into code the checkout chooses, and the hook would need the methodology's runtime, which ADR-014 point 1 keeps it free of.
