## Summary

**In plain terms:** the permission hook decides, before each tool call, whether an agent may make it. It runs outside the sandbox, yet its code and the permission model it judges by sit in the project's checkout, which a sandboxed command can write. So a confined command could change what judges the calls after it.

This record keeps what a sandboxed command writes away from what judges it:

- **The rule:** code that runs outside the sandbox without a person choosing it never comes from a place a sandboxed command can write. Nothing it reads from such a place widens what it allows, unless a person, shown the widening, makes it.
- **The code:** in a project that turns the permission hook on, the hook and the decision core run from a copy of the installed release, in a folder of the person's that no sandboxed command writes. The adapter's start hooks run nothing from the checkout, in every project.
- **The policy:** the model stays in the checkout, where people edit it. *Realizing* the model, the step that turns it into what the harness enforces, also keeps a snapshot of it out of reach, and the hook allows no more than that snapshot. A change in the checkout that narrows the model takes effect at once, and one that widens it waits until a person realizes it.
- **The native locks:** the settings every project receives ask before, or deny, the calls that could change what judges later calls, in the forms a native rule can name, whether or not the hook runs. The backbone prints the same rules for the person's own harness settings, and never writes that file.
- **Shared build caches** leave the committed sandbox settings, since the person's later runs execute what lands in them.
- **What a person notices.** From an agent's session, nothing widens what the hook allows or the sandbox, makes the copy, installs over the release or names a folder where the hook puts no ask: the person does these from their own terminal. Asks before a call that leaves the sandbox, before a file tool writes the harness's settings or the installer's or version control's own configuration, and before an agent moves its session into another tree hold in every mode, so where nobody answers, those calls do not happen (Rationale, "What it costs an agent host").

**How far it holds.** The copy and the snapshots are one set for each person, shared by all their projects, so whatever else can write them unasked, in any session of the person's, passes the protection of every project. Point 7 names each gap, and the overview reports what it can see, never the protection as holding for the machine.

**What it rests on.** The harness keeps its own settings files out of a sandboxed command's direct reach, as its documentation states. A probe confirms this with the other facts point 6 names, and if it disproves it, a later record supersedes this one whole.

## Context

**What prompted it.** [project-kit#3178](https://github.com/aleskalfas/project-kit/issues/3178) found that no part of the permission layer lies out of a sandboxed command's reach. The parts are:

- the hook, which the harness runs before each tool call, and the adapter's other hooks, which it runs the same way;
- the decision core, which the hook and the permission commands share ([ADR-003](ADR-003-permission-core-code-home.md));
- the model ([COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md) point 1), and every other input from which the core reads a verdict.

All of them sit in the checkout, and a sandboxed command writes its working folder. The harness runs hooks outside the sandbox, with the person's full access, as it runs file tools and connected servers. Both facts come from the harness's documentation, as [ADR-066](ADR-066-unattended-agent-runner.md)'s Context records it.

**Why it matters.** A boundary is only as strong as what enforces it. Whatever changes the hook, the core or the model changes what every later call is judged by. The intent axis would then rest on a boundary the confinement axis lets the agent move: the boundary believed but absent that [ADR-004](ADR-004-autonomy-intent-confinement.md) point 4 forbids.

**What it builds on.**

- **The guardrails** all come from the backbone's catalog, since a capability may not define one ([ADR-021](ADR-021-capability-contributed-privilege-definitions.md) point 3). So a release's catalog holds every guardrail that release ships.
- **A folder only the person writes.** ADR-066 point 7 keeps a run's clone in a folder of the backbone's, outside every checkout, that only the person's account writes.
- **The session anchor** is set by the harness when a session starts, and no change of folder moves it ([ADR-034](ADR-034-foreign-repo-mutation-guard.md) point 1). The commands an agent starts through its shell tools read it (ADR-034's Context). A command line can clear it for the commands it starts (ADR-034 point 5). Which other processes carry it, a person's terminal in an editor among them, the harness's documentation does not say, and the probe finds (point 6).
- **The harness's mark of a tool's process.** From 2.1.172 the harness marks each process its shell tools and hooks start, every process those start inherits the mark, and no editor sets it in its terminals ([ADR-093](ADR-093-writes-outside-the-repository.md)'s Context, "What marks a tool's process"). The harness's documentation names among them the processes its shell tool, its PowerShell tool and its tool that monitors a command start, and the process of each hook command it runs, and lists the terminal multiplexer's sessions it starts as carrying another of its variables and not this one, which the probe confirms (point 6). The command that names a folder where the hook puts no ask refuses where the mark is present, even empty (ADR-093 point 4). A command line can clear the mark too, and under a harness that sets none, such as Claude Code before 2.1.172, that refusal is open to a tool call (ADR-093's Rationale, "The harness's own value").
- **The entry point** picks which release serves a command, by the checkout it runs in and by the project's pin ([ADR-039](ADR-039-pkit-entry-point-router.md)), and routes every command alike ([ADR-049](ADR-049-per-project-version-pin.md) point 4).
- **The installed release** is one for each person on a machine. An upgrade replaces it for every project that follows it, while a pinned project runs its pin ([ADR-063](ADR-063-upgrade-updates-the-tool.md), [ADR-064](ADR-064-upgrade-pins-by-default.md)). *The installer* is the toolchain's runner that installs it, which the backbone's own upgrade also runs (ADR-063 point 2), and which ADR-014 point 2 exempts from the sandbox on macOS. By its documentation, the installer's commands for tools take its configuration from the person's home and the system, and from the environment, which takes precedence, never from a project. The install fetches the release through version control, whose configuration in the person's home or the system, or in the environment, can redirect where it fetches from.
- **The project's root** is found from the folder a command runs in, by asking version control first ([ADR-001](ADR-001-project-root-resolution.md)). The hook runs no version control, and reads its marker by hand ([ADR-060](ADR-060-path-scoped-workspace-allow.md) point 8).
- **The per-command escape.** The harness lets a shell call ask to run outside the sandbox. The setup of autonomy seals that escape, and elsewhere it stays open ([ADR-028](ADR-028-seal-unsandboxed-escape-under-autonomy-posture.md) points 1 and 5), the call riding the normal permission flow ([ADR-005](ADR-005-permission-profile-surface.md)'s Rationale, "Why `failIfUnavailable: true`, not `allowUnsandboxedCommands: false`, carries the invariant"). By the harness's documentation, a native allow that matches the command approves such a call too, while a native ask on the request puts it to the person in every mode that asks anything, ahead of any allow, and refuses it in a mode that never asks.
- **Native rules outlast the hook.** By the harness's documentation, it weighs its own deny and ask rules whatever a hook returns. A hook that cannot start, fails or runs past the harness's limit lets the call proceed (ADR-002 points 3 and 4), unless its registration asks the harness to block the call instead, which the harness's documentation offers.
- **But not an extension that answers for the person.** By the same documentation, an extension the person installs into the harness, which it calls a mod, answers after the hooks. Where no managed settings, managed list of connected servers or organisation's login binds the session, such an extension can approve a call that a deny rule refuses or a hook blocked, and approve unasked one that an ask rule would put to the person. A prompt tool or callback that the session hands its asks to answers them in the person's place too, and so does a hook registered on the harness's permission requests, which the harness asks even where it denies in place of a prompt (ADR-093's Context, "A deny where nobody answers").
- **Realizing as a step.** Activating a profile realizes the result by default ([ADR-005](ADR-005-permission-profile-surface.md) point 4), and the setup of autonomy composes that with turning the hook on ([ADR-007](ADR-007-setup-command-class.md)).
- **Agent hosts.** An *agent host* starts harness sessions for a person and drives their turns, often with nobody at a terminal ([ADR-091](ADR-091-no-host-component.md)). On the one host a trial measured, an ask was refused at once in a turn a chat message started, or held a run until someone answered it; the host's machines cannot start the sandbox; and its guidance has the agent write in the home folder, such as a service file under `~/.config/rc/init.d` (#3004; ADR-093's Context, "What the trial measured"). ADR-093 meets that need with the folders a person names for a checkout, where its ask is not put.

**uv's cache.** The uv toolkit's write allowance to uv's shared cache is classed narrowing. So setup applies it unasked ([ADR-008](ADR-008-confinement-allowances.md) point 3), and it lands in the committed settings ([ADR-029](ADR-029-move-mutable-sandbox-state-out-of-tracked-settings.md) point 1). Yet the person's later uv runs, outside any sandbox, execute what lands there (ADR-066's Rationale, "Why a command that starts `uv` fails on Linux, rather than gaining a cache"). On macOS, uv cannot run inside the sandbox at all ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 2), so the allowance serves no sandboxed uv there.

## Decision

**Nothing a sandboxed command can write becomes code that runs outside the sandbox unchosen, or widens what such code allows unless a person shown the widening makes it: so the permission hook runs from a copy of the installed release and allows no more than a model kept out of reach, and the settings every project receives ask before, or deny, in the forms a native rule can name, the calls that could change what judges later calls.**

- **What this record mends:** the permission hook and the decision core where the hook is on, the interpreter the hook starts, the adapter's start hooks in every project, and which release serves the commands that set the bound or name a folder where the hook puts no ask, and how they find their root (point 2); the bound the hook judges by, how it is chosen, what realizing writes and who runs it, an interlock on the gestures that widen the bound or the sandbox or install over the release, and a deny on an agent's call that names a folder where the hook puts no ask (point 3); the hook's own verdicts, its ask before a shell call that asks to leave the sandbox among them, and the native locks beside them in every project and, where the person adds them, in the person's own settings (point 4); and the write allowances the backbone ships, and those it writes whatever its data says (point 5). The rest of point 1's class stays open (point 7).
- **Its precondition.** The harness keeps its own settings files out of a sandboxed command's direct reach. They register the hooks and hold the native rules that [ADR-002](ADR-002-permission-realizer-ownership.md) point 3 and point 4 below rely on. The harness's documentation states it for the session's working folder and the folders above it, save where the person's own settings switch off the sandbox's isolation of files, or let a sandboxed command make nested namespaces, under which the documentation says not to rely on it. The overview reports either switch where it finds it. No accepted record establishes the precondition, so the record states it, and the probe confirms it (point 6). If the probe disproves it, a later record supersedes this one whole.

### 1. What a sandboxed command can write is never trusted outside the sandbox

- **The rule.** Code that runs outside the sandbox without a person choosing to run it never comes from a place a sandboxed command can write. Policy or configuration that such code reads from such a place may narrow what it allows, and widens it only where a person, shown the widening, makes it. Nor can a sandboxed command choose or redirect where such code writes.
- **Chosen and unchosen code.** A person chooses code only when they run the agent's work in the checkout as that work, its tests or its build for instance. All other code that runs outside the sandbox is unchosen: a hook, a tool's own configuration, a build a tool takes from a shared cache, and the methodology's own commands, whoever calls them, since a person who calls one means the methodology's code and not what a sandboxed command left in its place. The code that a command the sandbox exempts runs on an agent's call is unchosen too, and so is the code an agent's shell call runs outside the sandbox, unless a person, shown the call, approves it. A person who installs the methodology from a source checkout chooses that checkout's code as the methodology's, so there the protection holds only as point 7 says.
- **A write allowance,** an allowance that opens a place to sandboxed writes, widens the boundary where it opens a place this rule keeps out of reach, however it was classed.
- **Its reach.** The rule binds every later architecture record of the project's, and the members of its class that points 2 to 5 mend. Every other member stands as the record that decides it says, until a record applies the rule to it and takes it off point 7's list, which names each. A member that a core record decides takes the rule only through a core record that states it, since a core record rests on no architecture record. A member that a capability's record decides takes it only through a record that reaches every project the capability reaches, the capability's own or a core record, since a capability's records reach projects that receive no architecture record.

### 2. The permission hook and the decision core run from a copy of the installed release

- **The copy.** The harness runs the permission hook from a copy in the *backbone's state folder*: a folder of the person's where the backbone keeps its own state, outside every checkout, which only the person's account writes, as ADR-066 point 7 keeps a run's clone. It lies outside the folders a sandboxed command writes by default (ADR-066's Context), and nothing rests on it where a machine places it inside one (below, "Not where a sandboxed command writes by default"). No allowance the backbone ships, or writes whatever its data says, opens it (point 5). It holds the copy, point 3's snapshots and index, and what the hook writes. It holds no run's clone, nor the folder a runner keeps for a run's settings, hook and model ([ADR-073](ADR-073-builder-runs.md) points 1 and 2), so the hook's guard on itself (point 4) reaches no clone.
- **The guarded folders** are the backbone's state folder, the folder a runner keeps for each run's settings, hook and model (ADR-073 points 1 and 2), the folder that holds the lists of folders a person names for a checkout, where the hook puts no ask (ADR-093 point 2), the installed release with the entry point that starts it, and, where the person's account can write them, the installer's own program, which the upgrade and the remedy below run, and the installation of each interpreter the copy or the release runs on. An interpreter's *installation* is the folder that holds it with its own library, and, for an environment made from another interpreter, that environment's configuration file and that interpreter's installation; the release's, where the installer manages it, lies under the person's home. What lies in each guarded folder runs outside the sandbox unchosen, or bounds what such code allows, so each is kept as the state folder is: by the native deny and the hook's guard (point 4), and by no allowance the backbone ships or writes (point 5). Version control's own program, which the install runs to fetch the release, is no guarded folder, and point 7 states it.
- **Not where a sandboxed command writes by default.** A sandboxed command writes, with no allowance, its working folder and all below it, and the per-user temp folder (ADR-093's Context, "What a sandboxed command writes"), whose place on each platform the probe finds (point 6). Where a machine keeps a guarded folder inside the per-user temp folder, by real path, making the copy makes nothing and says why. Where the hook finds the backbone's state folder there, it treats the session as bound by a snapshot it cannot use, as where that folder overlaps the anchor's folder (point 3). Where it finds the folder that holds the lists there, or overlapping the anchor's folder, it counts no list (ADR-093 point 2, which this record refines so). The overview names each guarded folder so placed. A working folder added, or a write allowance, over a guarded folder is point 7's.
- **The lists so take point 1's rule.** ADR-093's lists drop an ask, and so widen what the hook allows. Kept among the guarded folders, they lie out of a sandboxed command's reach, and nothing of the methodology's writes them but the command that names a folder. That command is served from the installed release (below), refuses a tool call by the harness's mark, says on each naming what a write in the folder meets (ADR-093 point 4), and meets a deny in the hook and in the native locks wherever it names a folder (point 3, "On the naming command, a deny"). So the folder that holds the lists is guarded as the copy's is, and the lists carry the limits point 7 states for the copy, and one more: where no mark reaches the command, a form of its call that the denies do not catch names a folder (point 7, "The naming command where no mark reaches it").
- **What chooses the release's contents.** The installer's own configuration and version control's, through which the install fetches the release, in the person's home and wherever else the person's account can write them, such as a system file under a package manager's prefix, choose what an install puts into a guarded folder, and so does the environment the install runs in. That configuration is no guarded folder, since the person edits it for their own tools. The native locks and the hook's guard ask before a file tool writes it in the person's home (point 4), and the reinstall the overview names as a remedy sets all of it aside, the environment among it (below).
- **One for each person.** Every project of the person's shares the guarded folders, the copy and the release it is made from among them, and so does whatever else can write them. The file system draws that reach, not the host: another host that shares the person's home, a container or virtual machine that mounts it, and, under WSL2, the person's tools on the Windows side all reach it. Where this record says *the machine*, it means all that can write those folders. So whatever can write them, in any session of the person's or from anywhere that reaches them, bears on the protection of every project (point 7). A copy made on one host serves every host that reaches the folder, and remaking it there moves them all.
- **What the copy holds:** the permission hook, the decision core, the release's catalog, and what they need to start.
  - **Its interpreter** is named by a path fixed when the copy is made, never looked up on the session's path: the interpreter itself, as a launcher would resolve it when the copy is made, and never a launcher, which picks one each time it starts. Making the copy prefers an interpreter whose installation the person's account cannot write; where it falls back to one the account can write, it says so, that installation is a guarded folder, and the overview reports it. On a host where no interpreter lies at that path, the hook cannot start.
  - **The copy's *starter*,** the program the registration's command runs, starts the interpreter with an emptied environment, passing on only the variables the hook reads: those that give the anchor and place the files and folders it guards or the per-user temp folder (above), the marker of an agent's run (ADR-066 point 8), and `HOME`, `PATH` and the state home, which ADR-093 points 2 and 3 read. It passes each as the harness set it: a variable set, even empty, stays set and as it was, and one unset stays unset. The hook reads the marker for presence, even empty (ADR-093 point 2), so a starter that dropped an empty marker would let a run count named folders, and one that set an unset marker would turn them off in every session. It passes the anchor with the same care.
  - **Isolated.** The starter starts the interpreter with no folder of the person's own packages, no step that adds the packages installed beside the interpreter, and no script folder or working folder on its path, importing the core from the copy by the copy's path. None of the variables it passes steers what an isolated interpreter loads, so the interpreter loads only the copy and its own library. The shell that runs the registration's command, and the platform's program loader as it starts that shell and the starter, read the environment the harness passes before any of this applies (point 7).
- **Making the copy** is one operation, served from the installed release (below). It makes the copy from that release, replaces it whole, and carries each snapshot the index names into the copy's layout (point 3, "Across releases"). A command of its own runs it. The gesture that turns the hook on runs it as a step only where no copy exists: there it replaces no hook that runs, and starts, from the release the person installed, each project's hook that could not start. Realizing never makes it. It runs no code from the checkout, and makes the copy only outside the sandbox: inside it, it makes nothing and says so. Nor does it make one where a guarded folder lies inside the per-user temp folder (above).
- **Remaking it moves every project.** Where a copy exists, remaking it changes the hook of every project on the machine that turns the hook on, and carries each snapshot into the new release's layout. So it shows what it would change, and takes the interlock that realizing takes (point 3, "Across releases" and "An interlock on widening").
- **The source stays where it is.** The core keeps the home ADR-003 gives it, and the hook its home in the adapter. The release bundles both from there ([ADR-033](ADR-033-official-install-bundles-content.md) point 1), and the copy is made from what the release bundles.
- **The registration.** In a project that turns the hook on, the committed settings register the permission hook from the copy, since running it is the project's choice (ADR-002 point 2). They name the copy by a location each machine resolves for its own person, never by a path in the checkout. Turning the hook off removes those registrations alone: the permission hook's, and those of the adapter's hooks that run from the copy beside it (below).
- **The adapter's other hooks** run no code from the checkout, in any project. Each that needs no code of its own runs only the fixed command its registration holds: a program named by its absolute path, with the shell's own builtins where it needs a shell, which loads nothing from the checkout or from the session's path. What such a hook gives turns only on what that command can test, such as whether the methodology's command is on the session's path, so the start hook keeps its line naming the install script where that command is missing. No copy serves such a hook, and none can be missing. A hook of the adapter's that needs code of its own runs from the copy, through the copy's starter, in the environment the starter gives the permission hook, and so only where the permission hook is on. The report ADR-093 point 4 has each session's start give, of the folders the permission hook counts there, is such a hook: it reads them by the same code in the same environment, and where the permission hook is off, that hook counts none, so there is nothing to report. The settings merge keeps the registrations so, a hook a later release adds among them.
- **A machine with no copy.** There the permission hook cannot start, which is the loud fault of ADR-002 point 4. That fault lets each call proceed, so there only the native locks and the guardrails' native denies hold (point 4, and point 7, "The window before the copy"). The permission overview's self-check reports it (ADR-002's Implications), and names the command that makes the copy. The overview also reports a copy that differs from the installed release, and says that either may have changed since the copy was made: a release installed since, a copy planted, or a release changed in place. So it names first the command that reinstalls the release from its source. That command runs the installer by its path with an emptied environment, passing on only what places the install, as the copy's starter runs the interpreter; it takes nothing from a shared cache, and sets aside the installer's and version control's own configuration, the system's as well as the person's. So a person who reaches the source only through such configuration or the environment, such as a mirror or a proxy, passes it on that command's line. Then the overview names the command that remakes the copy. The overview runs from that release, so a changed release can hide the difference; what keeps the release as it was installed is the native deny and the hook's guard (point 4).
- **Served from the installed release.** The entry point serves from the installed release, whatever the checkout or its pin say, each permission command that reports a verdict or a bound, realizes the model, makes the copy, turns the hook on or off, or names or removes a folder where the hook puts no ask (ADR-093 point 4), as its own work or as a step of it, such as activating a profile. Where it cannot tell whether a permission command is one of them, it serves it from the installed release. A release from this record's build onward that is not the installed one refuses such a command, and names the installed release. A release tells whether it is the installed one from where it runs, against the installation the person made, never from a value the command's caller sets. Each such command loads the core from the installed release, as the workspace removal command takes its code from the running backbone ([ADR-060](ADR-060-path-scoped-workspace-allow.md) point 8). Every other permission command loads the core from the release that serves it, which is the project's own tree only where the project is itself a source checkout of the methodology whose own code the entry point runs (ADR-039).
- **Code at the release, content at the pin.** The code of those commands is the installed release's, while the model they read is the checkout's, at whatever version the checkout pins. A release reads a model whole only where it knows each of its keys and values. So each of those commands reads the model only where its release reads it whole, and writes it only in the layout it read: a command that reports names what it could not read, and one that writes refuses and names the installed release. The hook's copy reads the checkout's model the same way, and treats one it cannot read whole as one that will not load (point 3).
- **The root they act on.** Each of those commands, the one that names a folder where the hook puts no ask among them, finds the project's root by the search toward the filesystem root that ADR-001 falls back on, starting from the real path of the folder it runs in, as version control does, reading version control's marker by hand as the hook reads it (ADR-060 point 8), and taking the methodology's own marker only where no repository's marker encloses the folder. It runs no version control, since version control runs what the checkout's configuration names. It shows the folder it acts on. Its answer matches version control's in a folder reached through a link, a linked worktree, a submodule, and a methodology installed below a repository's root. It can part from version control's answer where something besides the markers in the folders moves that answer: the checkout's own configuration or the environment placing the repository or its working tree elsewhere, or version control declining a repository or stopping at a file system's boundary. There it takes the markers as they lie.
- **One verdict.** The core chooses the bound that binds a session, judges each call by it and by the checkout's model, and combines the two verdicts (point 3). The hook acts on the core's verdict, and adds the adapter's own verdicts (point 4). So a command that reports a verdict reports the core's, which is why ADR-003 keeps the decision in the core. A command that reports a verdict judges as the hook would for a session anchored in the root it finds, or in a folder named to it, and names the bound that binds there. What turns on the harness stays in the adapter: how an ask meets the session's mode ([ADR-025](ADR-025-segment-conservative-bash-allow.md) point 7, and point 3 below), the adapter's own asks, and its guard on itself.
- **Two copies of one source.** The hook's copy and the commands come from one installed release while the copy is current, so a report matches what the hook enforces. The overview names a copy that is not current. The shared conformance tests hold every caller of a release to one verdict on each of a fixed set of calls, *the conformance calls*.
- **One set at a time.** A hook finds once, when it starts, which copy it runs, and reads that copy's core, the index and the snapshots kept with it. Remaking the copy puts the new copy and the snapshots it carried in place in one step that a hook sees whole, so no hook runs one release's code over snapshots in another's layout.
- **What the hook reads, and from where.** Its code, the release's catalog, and point 3's index and snapshots come from the backbone's state folder, and ADR-093's lists from the folder that holds them, a guarded folder too. Of the environment it reads only what the copy's starter passes on (above). It takes the session anchor as the harness gives it, finds from it the root of the checkout that holds it, as those commands find theirs ("The root they act on"), and reads the checkout's model there. With no anchor it reads no checkout, and gives only point 4's verdicts. Where its registration names the model it judges by, it reads that model and no checkout (point 3).
- **What the hook writes,** it writes only into the backbone's state folder, following no link.
- **Its runtime** stays a zero-dependency script (ADR-014 point 1).
- **Its scope.** This point governs the hooks the project's settings register. A working run's hook, which its runner registers from outside the run's clone, stays as ADR-073 point 2 decides: its code, and the core it imports, come from the project's tree at the default branch's head, and it judges by the model its runner names (point 3).

### 3. The hook allows no more than its bound, a model out of a sandboxed command's reach

- **The model stays in the checkout.** It is the source of truth that people edit, review and commit (COR-028 point 1).
- **The bound.** A session's *bound* is the model out of a sandboxed command's reach that its hook judges by, beside the checkout's model or in its place: the snapshot that binds the session, or the model its runner names (both below). Where neither binds, no bound binds.
- **Realizing keeps a snapshot.** Realizing turns the model into what the harness enforces (COR-028 point 2), through an operation the methodology's commands provide (COR-028's Implications). It also keeps a *snapshot* of the model of the folder it realizes, in the backbone's state folder, and records that folder in an *index* there. The snapshot holds, as the checkout held it, every input from which the core reads a verdict, wherever the core reads it, the subject a call is judged for among them. It records its own layout, and the native rules realizing wrote. Realizing reads each input as a regular file inside the folder, following no link, and refuses an input it cannot read so. Each write replaces a snapshot, or the index, whole.
- **The folder it realizes** is the root found as point 2 says, which realizing shows before it writes, and the index records it by its real path. Realizing refuses a folder that holds no model, and one that overlaps the backbone's state folder, by real path. Turning the hook on refuses such a folder too.
- **The folder's identity.** With each folder, the index records its identity on the file system, its device and inode, the identity by which ADR-093 point 2 matches a list to a folder, so the two records use one. No command inside the folder can change it. A later folder at its path shares it only where the platform gives that folder a removed one's device and inode, which the probe finds (point 6), and what it finds bears on ADR-093 point 2's match as well.
- **The index.** Its writers, realizing and remaking the copy, take one lock, which is freed when its holder ends. So no two of them lose each other's writes, and none writes a snapshot over one written after it read. Each writes a snapshot before the index entry that names it. An index that exists but will not load makes the hook treat each session as bound by a snapshot it cannot use (point 4). The overview names each snapshot that no entry of the index names, and each realized folder whose identity no longer matches.
- **Which snapshot binds.** A session is bound by the snapshot of the nearest realized folder that holds its anchor. The hook finds it through the index, by the real path of the anchor the harness gives it, and reads nothing in the checkout to choose it. That path resolves only the anchor and the folders above it, which no sandboxed command writes (point 6), so no link a sandboxed command makes steers the choice.
  - So a bound realized for a folder holds every session anchored in it or below it whose hook runs, a worktree made inside it or a repository kept inside it among them, unless a nearer folder below is realized. The hook runs only in a session whose settings register it, which the harness takes from the folder the session starts in or moves into (point 7, "Where a session starts").
  - Where that folder's identity does not match the index, its snapshot cannot be used (point 4), and no folder further up stands in for it.
  - Where the backbone's state folder and the folder the session is anchored in overlap, by real path, or the state folder lies inside the per-user temp folder (point 2, "Not where a sandboxed command writes by default"), the snapshot that binds cannot be used (point 4). This catches a state a person brought about unawares, which the gestures' refusal above keeps them from making. It stops no session that can write the state folder, since such a session can write the copy that checks it.
  - Where no realized folder holds the anchor, or there is no anchor, no snapshot binds.
- **A bound a runner names.** Where the hook's registration names the model it judges by, and that model lies in a folder the backbone keeps for a run, outside every checkout, which only the person's account writes and the run does not write (ADR-073 point 2), that model is the session's bound, in place of a snapshot. No sandboxed command writes that folder either (point 6). The core judges each call by it alone, chooses no snapshot and reads no checkout. A working run's runner names so the model it read from the default branch. Where the named model lies anywhere else, or cannot be used, the hook treats the session as bound by a model it cannot use, and asks (point 4). The overview names each committed registration that names a model.
- **Which checkout judges.** The hook reads the model of the checkout that holds the anchor, whatever folder a call works in. Where a subagent works in a worktree with its anchor in its parent's checkout, the parent's snapshot and model judge its calls, and a narrowing that only the worktree holds does not reach them.
- **The verdict.** Where a snapshot binds, the core judges each call twice, by the snapshot and by the checkout's model, and gives the stricter verdict: deny is the strictest, then ask, then abstain, then allow. Where the snapshot allows a call and the checkout's model abstains on it, the core asks, as for a grant the checkout revoked. Where the two give one verdict, its reason names what each names.
  - **A change in the checkout that narrows the model** takes effect at once: a new deny denies, and a revoked grant asks until it is realized.
  - **The revoked grant's ask meets the session's mode** as ADR-025 point 7's ask does: in a mode in which the person chose not to be asked, the hook abstains on the call, and the harness's own rules decide it until the revocation is realized.
  - **A change that widens it,** such as a new grant or a more permissive active profile, takes effect only once realized.
  - **A sandboxed command** can thus make the hook stricter, and never less strict than the snapshot.
- **The order, and the budget.** The hook first gives what reads nothing in the checkout: its own verdicts by the copy's catalog (point 4), its ask before leaving the sandbox and the interlock's ask among them, then the bound's judgement. Only then does it read the checkout: the model's judgement, and the guardrails of the checkout's catalog. It reads each input there as realizing does, as a regular file inside the folder, following no link, and never waits on one. All of it runs within a budget, a share of the harness's limit for a hook, which the registration sets well above the budget. When the budget ends, the hook gives the verdict it has. One of its own verdicts comes last: the ask before a built-in file tool writes outside the session's repository, which ADR-093 point 1 puts only where the core abstains, follows the core's verdict, and so the checkout's judgement, or, where that runs past the budget, the bound's judgement alone, in the room the harness's limit leaves above the budget.
- **When the checkout's model fails.** Where it will not load, the copy's release cannot read it whole (point 2), it faults in the core, or it does not finish within the budget, the hook judges by the snapshot alone, or where no bound binds gives its own verdicts alone. That drops only a narrowing not yet realized, which holds only while the checkout holds it in any case. The hook's reasons and the overview echo nothing of an input they cannot read.
- **The reason names realizing.** Whenever the snapshot refuses what the checkout's model would allow, the hook's reason says so, and names the realizing command.
- **Only realizing widens.** Realizing is one operation, and only it writes a snapshot that allows more than the one in place. The realizing command runs it, and so does each command that realizes as a step of its own work, such as activating a profile. A command that only writes the model realizes nothing, and says what it left unrealized. Turning the hook on realizes nothing either: where the folder has no snapshot, it says so and names the realizing command. Realizing, wherever it runs:
  - shows each place where what it would write, the snapshot or the harness's native rules, allows more than what is in place, and counts as a widening any place it cannot compare;
  - judges the conformance calls by the snapshot it would write, within the budget, with the copy's core, or the installed release's where no copy exists, and writes nothing where that fails;
  - writes nothing where a copy exists that differs from the installed release, and says, as the overview does, that either may have changed (point 2);
  - runs no code from the checkout, and is served from the installed release (point 2);
  - realizes only outside the sandbox, and inside it realizes nothing and says so.
- **An interlock on widening.** Two guards keep an agent from widening the bound or the sandbox, or changing the release the copy is made from, unasked:
  - **In the gestures.** Where a session anchor, or the harness's mark of a tool's process, is set at all, even empty, which this record calls *under an anchor*, each command that realizes, as its own work or as a step of it, writes nothing where anything it would write allows more than what is in place. The operation that makes the copy makes none, whether or not one exists, since a first copy starts each project's hook that could not start and puts in force every snapshot on the machine. Each command that turns the hook on or off does nothing, since turning it on puts in force a bound that may allow what the native rules would ask. Each command that would leave the sandbox of the project's sessions wider than it is writes nothing either: turning it off, turning off its seal on the escape, or adding an exclusion or an allowance of either class while it is on, as its own work or as a step of it. The settings a runner writes for a run it starts are not among these. The backbone's upgrade installs no release, and prints the install command as it does without a terminal (ADR-063 point 3), since an install replaces the release every later copy is made from. Each refuses so, and names the person's own terminal. A realizing that only narrows goes ahead, and a command that also writes the model writes it and says what it left unrealized. The test of the mark is the one ADR-093 point 4's refusal makes, built once for both (ADR-093's Implications).
  - **In the hook, and natively.** The hook asks, in every mode, before a shell call it recognizes as one of the commands that realize, make the copy, turn the hook on or off, or widen the sandbox, or as an install over the release the copy is made from, the backbone's upgrade among them, which changes what every later copy holds. The native locks ask before the plain form of each such command in every project, whether or not the hook runs (point 4). Their ask on the installer names the plain form that installs the release, so the installer's calls for other tools meet none.
  - **How the hook recognizes a call.** It reads a methodology command by that command's own argument grammar, in every form of the line the command accepts, and matches the program by its base name, that of the name the call gives and that of the target the name resolves to, as ADR-093 point 4 takes a link and its target alike. A *shell call* is a call of any of the harness's tools that runs a command: its shell tool, its PowerShell tool and its tool that monitors a command, the tools whose processes the harness marks (the Context, "The harness's mark of a tool's process").
  - **On the naming command, a deny.** The command that names a folder where the hook puts no ask takes neither of these guards, and meets a deny in their place. The hook denies, in every mode and whatever the harness marks, a shell call it recognizes as naming a folder through that command, and the native locks deny the plain form of that call in every project, whether or not the hook runs (point 4). A call that removes a folder meets neither, since removing one only gives an ask back. Where the harness sets its mark, the command refuses an agent's call in every form that keeps the mark (ADR-093 point 4), so the denies refuse first what it would refuse. Where no mark reaches it, the denies refuse the forms they recognize, and point 7 states the rest. On Linux with the sandbox on, the command runs inside the sandbox unless the person excludes it, and a sandboxed call cannot reach the folder that holds the lists (point 2), so there the deny refuses a call that would fail.
  - **An interlock, not a boundary,** as ADR-034 point 5 declares its guard: a command line can clear both the anchor and the mark, and a form of the call that the hook does not recognize, and the native rules do not name, passes the asks and the denies. The commands that widen the sandbox, and the upgrade, are served by whatever release the entry point chooses, and one from before this record's build refuses nothing. The installer's own command, called directly, meets only the asks. Whether realizing a wider model, or widening the sandbox, takes a person's gesture, as a boundary, is decided with [project-kit#3179](https://github.com/aleskalfas/project-kit/issues/3179).
- **A narrowing not yet realized** holds only while the checkout holds it. The overview reads the snapshot back (COR-028 point 2), and names each place where it allows more than the checkout's model. It also names each native allow in force that no realizing showed.
- **Across releases.** The copy's core reads snapshots in its own release's layout. Making the copy, from a newer release or an older one, carries each snapshot into its release's layout, working from the snapshot alone, under the index's lock, and puts the copy and the carried snapshots in place together (point 2, "One set at a time"). It shows each carried snapshot by which, on the conformance calls, the new core allows what the copy it replaces did not allow by the snapshot it carried. Where no copy exists, a snapshot left from an earlier copy has nothing to compare with, so the carry counts it as a widening it cannot compare. The person keeps each such snapshot, as a widening they were shown, or marks it as one that cannot be used (point 4), named until its folder is realized again. The conformance calls are a sample: a carry can widen a call they do not cover, and there the protection rests on the release the person installed.

### 4. The hook's own verdicts, and the native locks beside them, hold in every state

- **The hook's own verdicts** are those the adapter's hook gives without a model.
  - **The guardrail deny,** the hook's half of the double lock (ADR-002 point 3), for every guardrail of the copy's catalog, and of the checkout's where it loads within the budget.
  - **Each ask the adapter makes of its own,** as the record that decides it says. Such are the ask where a shell call may hide a guardrail (ADR-025 point 7), sought among the same guardrails, and the ask before a built-in file tool writes outside the session's repository, which holds in every mode save in a folder a person names for the checkout ([ADR-093](ADR-093-writes-outside-the-repository.md) points 1 and 2), and which, for a write into another repository, is the catch ADR-034 point 2 allows. The ask before a shell call of a command that point 3's interlock covers is another.
  - **The deny on naming a folder.** The hook denies, in every mode, a shell call it recognizes as naming a folder through the naming command (point 3, "On the naming command, a deny").
  - **The ask before leaving the sandbox.** The hook asks, in every mode, before a shell call that asks to run outside the sandbox, or whose request to do so it cannot read, whatever the model or the native rules allow. Where the harness seals that escape (ADR-028), the call would run inside the sandbox in any case, so there the ask costs a prompt, and in a run nobody watches, the call.
  - **Its guard on itself.** The file tools run outside the sandbox, so the hook guards what they could write that judges later calls. Each part holds in every mode, whatever the model allows, and in a folder a person names for the checkout too, where only ADR-093 point 1's ask is not put (ADR-093 point 2, which this record refines so):
    - **a deny** on a file tool's write into the guarded folders (point 2), wherever the machine keeps them, by every path that names them or resolves into them; a file that shares its storage with another folder is left to point 7;
    - **an ask** before a file tool writes a file from which the harness takes its settings or connected servers, at any path where the harness looks for one, in any folder, the person's own among them wherever the environment moves them, and before one writes the harness's own state file;
    - **an ask** before a file tool writes the installer's or version control's own configuration in the person's home, wherever the environment moves it, a file that configuration includes, or the file a link at its place leads to, since that configuration chooses what an install puts into the release (point 2);
    - **an ask** before a call of the harness's tool that moves the session into another tree, since the move takes that tree's settings with it;
    - **an ask** before a call of any other tool, such as a connected server's, whose input names one of the folders it denies. That catches only the plain form, so it is an interlock.
    - So a builder whose work edits such a file meets the ask, which a run nobody watches refuses. An install from source is left to point 7, since its release is a checkout the person works in.
- **Apart from one another.** Each of these runs on its own, so a fault in one drops neither the others nor a model's verdict.
- **The native locks.** The settings the adapter merges into every project, whether or not it turns the hook on, carry these native rules. The harness weighs them whatever a hook returns, so they hold where the hook does not run, cannot start, fails or runs past the harness's limit (the Context, "Native rules outlast the hook"):
  - an ask before a shell call that asks to run outside the sandbox;
  - an ask before a shell call of each command that point 3's interlock covers, in the plain form a native rule can name;
  - a deny on a shell call that names a folder through the naming command, in the plain form a native rule can name, and none on a call that removes one;
  - a deny on a file tool's write into the guarded folders, named at their default places under the person's home. It names a run's folders for settings, hooks and models and not its clone, since the harness applies such a deny to sandboxed commands' writes too, which the probe confirms, with whether the deny holds against a working folder or a write grant that covers the folder it names (point 6);
  - an ask before a file tool writes a file, in any folder, from which the harness takes its settings or connected servers, and before one writes the harness's own state file in the person's home;
  - an ask before a file tool writes the installer's or version control's own configuration, named by its default places in the person's home;
  - an ask before a call of the harness's tool that moves the session into another tree.
  - By the harness's documentation, each ask puts the call to the person in every mode that asks anything, ahead of any allow, and refuses it in a mode that never asks. An extension that answers for the person can pass each of these rules, and a hook on the harness's permission requests each of these asks (point 7). A deny puts nothing to the person, so no such hook answers it.
  - Each is one half of a double lock, as ADR-002 point 3 makes of the guardrail denies: the hook's asks and denies and its guard on itself are the other halves. Where a machine keeps a guarded folder elsewhere, such as an interpreter installed outside the installer's default place, the deny does not reach it, so only the hook, and the person's own locks where they carry it, guard it, and the overview says so. The asks on the installer's and version control's own configuration name its default places too, so a file it includes, or the file a link at its place leads to, meets only the hook's ask.
  - The ask before a move is an interlock: the person approves a move, not the settings the tree brings, so a tree whose settings a sandboxed command wrote passes it once approved (point 7).
- **The person's own locks.** The same rules, held in the person's own harness settings, reach every session of theirs on the host, in every project, a project that does not use the methodology, a session started outside a checkout's root and a checkout at an older commit among them, so the protection needs them wherever a project's locks do not reach. The backbone never writes that file. The command that makes the copy, and the overview, print the rules, naming each guarded folder where this machine keeps it, and the overview reports where it read the person's settings and whether they carry the rules. Beside them, they name the harness's write block as a lock the person may add: it refuses, in every session and every mode, a file tool's write outside the session's working folders and into any settings file of the harness's, and removes the harness's tool that moves a session into another tree. It closes more than the asks do, wherever a folder lies, at the cost of every such write the person would approve and of that tool. They also name three switches the person may set: one that keeps every session out of the harness's bypass mode, in which a file tool writes unasked whatever no ask rule names, the shell's startup files among them; one that removes its auto mode, in which a classifier of the harness's decides, in the person's place, each call no ask rule names; and one that stops skills from running commands inline. The overview reports whether the write block and each switch are on.
- **The checkout still narrows.** Where no bound binds, and where one binds but cannot be used, the checkout's model still narrows, as point 1 lets it: its denies deny and its asks ask, within the budget, and its allows allow nothing.
- **No bound.** Where no bound binds the session (point 3), the hook allows nothing by the model, gives its own verdicts and the checkout's narrowing, and abstains on every other call, so the harness's native rules decide it. Each ask and deny it gives says that the model is not in force, and names the realizing command.
- **A bound that cannot be used.** Where a bound binds the session but the hook cannot judge a call by it, the hook asks on the call, in every mode, unless one of its own verdicts or the checkout's model denies it. Its reason says that the bound is not in force, and names the realizing command. The hook cannot judge by the bound where:
  - the folder's identity does not match the index, the snapshot's layout is not the copy's, the backbone's state folder and the anchor's folder overlap, the state folder lies inside the per-user temp folder (point 2), or the model a registration names lies outside the folders the backbone keeps for runs (point 3);
  - the index, the snapshot or the named model will not load, or judging the call by it faults or does not finish within the budget.
- **Why these asks override the mode.** The ask where a bound cannot be used, the ask before leaving the sandbox, the ask before an interlocked command and the guard's asks each hold in every mode. A mode is the person's choice about this session's calls, made while the bound held. A sandboxed command can bring about a bound that cannot be used, and a call that leaves the sandbox, an interlocked command, a move into another tree or a write the guard sees can change the bound of every later session, on this machine and in every project. Deferring to the mode would let each of these pass the protection in exactly the modes that ask nothing. The hook's other asks meet the mode as the records that decide them say, as point 3 does for a revoked grant.
  - **Where nobody answers.** Each of these asks, and each native ask beside them, rests on the harness requirement that an ask reaches a person who can answer it (`ask-reaches-person`, [COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), as every other ask the hook puts does. Where nobody can answer, the call is refused or waits. The deny on naming a folder rests on nobody's answer.
- **Faults.** A fault in judging by the checkout's model or in one of the hook's own verdicts, or a payload the hook cannot read, is a decision fault (ADR-002 point 4): what faulted gives no verdict, and the rest stand. Where none stands, the hook abstains (ADR-002 point 3), save that a shell call whose request to leave the sandbox it cannot read gets the ask above. A bound the hook cannot judge by is no decision fault but the state above, since the bound is what the person chose. So an error or a timeout in judging by it, which faults the core whatever model it reads, makes the hook ask rather than let the call proceed. A hook that cannot start stays the loud fault of ADR-002 point 4.

### 5. A write allowance is narrowing only where nothing outside the sandbox runs what it lets in

- **The test.** A write allowance is narrowing only where no code outside the sandbox later runs, or reads as configuration, what a sandboxed command writes through it, unless that code first checks it against a value no sandboxed command can write. Every other write allowance is widening, and ADR-008 point 4 governs it: never committed, never applied unasked, always reported.
- **A shared build cache fails it.** A tool builds and installs from its shared cache what the person's later runs execute, outside any sandbox, without such a check. On macOS the session's own uv runs outside the sandbox too. So no toolkit the backbone ships carries an allowance for a shared cache, and no gesture of the backbone applies one from data it ships. The overview names such an allowance as a widening wherever it finds one. Where a person's sessions held such an allowance, what a sandboxed command wrote into the cache may already lie in the installed release, so before making the copy that person reinstalls the release with the command the overview names, which takes nothing from a shared cache (point 2).
- **The guarded folders.** No gesture of the backbone writes a write allowance that reaches a guarded folder (point 2), whatever the data naming it says. The overview names one wherever it finds it.
- **What this point leaves to the project's data.** The allowances a project chooses, and the toolkits it defines, are read from the checkout, which a sandboxed command writes, so how that data classes an allowance settles nothing. Setup applies them as ADR-008 point 3 decides, save one that reaches the folders above, and they stay open (point 7).
- **A cache for each checkout passes it.** Where a tool runs inside the sandbox, setup gives each checkout's sandboxed runs of it a cache of their own, which nothing outside the sandbox runs from. It does so only where no command of the session that starts that tool runs outside the sandbox. The setting reaches the session's sandboxed runs alone, through the session's settings, and never lies in a tool's configuration file in the checkout, which the person's own runs of the tool, the methodology's commands among them, would read. The setting is per machine ([ADR-032](ADR-032-per-machine-activation-routing-axis.md) Rule A).
- **On macOS** uv cannot run inside the sandbox, so losing its shared cache costs nothing there.

### 7. What stays open

Each gap is reported rather than hidden, as COR-028 point 3 asks. The permission overview and the adapter's enforcement declaration state each one that bears on the protection, for each platform. The overview reports what it can see of each from this machine's settings and this checkout, and says what it cannot see, such as the other sessions on the machine.

**Members of point 1's class.** Each stands as the record that decides it says, until a record applies point 1 to it and takes it off this list (point 1, "Its reach"). Follow-ups of project-kit#3178 take each up.

- **Code that runs outside the sandbox on a person's or an agent's call, and loads what a sandboxed command wrote.** A sandboxed command followed by such code reaches past the protection, the copy and the snapshots included.
  - The methodology's own commands load code and configuration from the checkout wherever they run outside the sandbox. For each command that point 2 does not serve from the installed release, data in the checkout also chooses the code, through the entry point's routes (ADR-039, ADR-049).
  - A command the sandbox exempts runs outside it on an agent's call, and the protection holds against that call only as far as the hook's judgement of it, which confines nothing (ADR-004's Rationale, "Why pkit delegates confinement rather than enforcing it"). ## Rationale

**Why the rule turns on who chose the code.** A person who runs the checkout's tests from their terminal runs what a sandboxed command may have written, and knows it: the checkout is the agent's work, which they review and run as such. A rule against all of that would bind no project. What the sandbox's protection needs is narrower: no code a person did not choose to run as the agent's work comes from where the agent can write. A person who calls a methodology command means the methodology's code, so that code is unchosen even on their call. Point 1 covers where such code writes as well as what it runs, since a write a sandboxed command can redirect changes a file it could not write itself.

**Why policy as well as code.** The model decides what the hook allows. A sandboxed command that could widen the model would gain what changing the code gains, without touching the code. So the rule covers both: the checkout may narrow at once, and only a person shown the widening widens.

**Why the code runs from a copy of the release.** Three ways keep the code out of reach: deny writes to its files where they lie, read it from history, or run it from elsewhere.

- **Denying sandboxed writes where the files lie** fails each command that moves a working tree across a change to them, such as a branch switch, a pull or a rebase, and sync where sync runs inside the sandbox. Such a command may stop partway. The harness's own settings files bear the same cost, but they seldom differ between branches, while the permission layer's change with each upgrade and each new grant. The file tools, which run outside the sandbox, would still need a guard of the hook's own.
- **Reading from the default branch** reads a git folder that sandboxed commands can write (ADR-066's Context).
- **The release** is installed outside every checkout, by a person. The installed release itself serves the commands that copy it, realize the model and report the bound, so data in the checkout cannot choose which release that is, though the session's environment can (point 7).
- **The cost:** a change to the hook or the core reaches a session only once it is released, installed and copied. Tests and CI still run the checkout's code, and in an install from source the release is the checkout.

**Why the start hooks run only what their registration holds, and the permission hook from the copy.** Each hook runs outside the sandbox with the person's access, so any of them left in a checkout could rewrite the copy and the snapshots. The state folder is shared by every project on the machine, so a hook left in any project's checkout reaches every project's protection, with no step of the person's. The start hooks that give only what a fixed command can test need no code of their own, so their registration holds that command, and they run nothing from the checkout in any project, need no copy and fault on no machine. The permission hook needs the core, so it runs from the copy, and only in a project that turns it on, which accepts the copy's loud fault with it. The report of the folders the permission hook counts must read them as that hook does (ADR-093 point 4), so it runs from the copy beside the hook, through the same starter, and only where the hook is on, the one place the hook counts any. Elsewhere that fault would land on every collaborator of a project that never chose the hook, and whether the sandbox is on is each machine's setting (ADR-032), while the registration is the project's.

**Why those commands are served from the installed release.** The entry point picks a release by data in the checkout: a source checkout's own code, or the project's pin (ADR-039 points 1 and 2). For the commands that make the copy and realize the model, that data would choose the code a person trusts to widen what the hook allows. For those that report the bound, it could choose a release that knows nothing of the copy or the snapshots, and so reports nothing. The command that names a folder where the hook puts no ask widens the hook at once, outside the checkout (ADR-093 point 2), and in a source checkout of the methodology its routes would run the checkout's own code, which a sandboxed command can write. Served with the copy from one release, its tests of a path and the hook's stay one table, as ADR-093 point 4 holds them. Its removal only gives an ask back, yet it is served the same way: it is a form of the same command, and the entry point errs toward the installed release where it cannot tell one form from another. Served by the installed release, the choice stays with the person who installed it. The commands that only write the model keep the entry point's routes: they write the checkout, which a sandboxed command writes anyway, and nothing they write widens the hook until it is realized.

- **The cost.** The installed release is one for each person on a machine, so an install moves these commands, and the hook once the copy is remade, for every project there, pinned or not, where a pin otherwise keeps a project's version (ADR-064). After a project's pin moves past the installed release, these commands refuse a model that holds anything that release does not know, until the person updates it (point 7).

**Why that overturns routing every command alike.** ADR-049 point 4 routes every command, and its Rationale weighs a carve-out keyed on the command line against it on three counts. Each is answered here:

- **The command-agnostic contract.** It holds for every other command. For these, data in the checkout must not choose the code, which is the one thing a route by the pin does.
- **Unsafe in both directions.** The carve-out errs toward the installed release: a permission command it cannot place goes there. A release from this record's build onward that is not the installed one refuses such a command. An older release, which a pin may name, and a source checkout's own code, which the entry point's first route runs, refuse nothing, so a form the entry point misses can still run code the checkout chose. That is the interlock's gap, which point 7 states under "Who widens".
- **Reads are the most version-sensitive commands.** For these, the version that matters is the hook's. A report of the bound must match what the hook enforces, and both come from the installed release (point 2). These commands also read only what their release reads whole, and say what they could not read, so a mismatch with the pin shows rather than misleads. That is also the cost: ADR-039 D1's lock does not hold for them, since their code is the installed release's while the model is the checkout's at its pin.

**Why those commands read version control's marker by hand.** Version control runs what the checkout's configuration names (ADR-066's Context), and it has no switch that sets a repository's own configuration aside. These commands run no code from the checkout, so they run no version control, and read its marker as the hook already does (ADR-060 point 8). ADR-001 asks version control first because a search of its own gets symlinked paths, linked worktrees and submodules wrong, so these commands start from the real path, as version control does, and are held by test to version control's answer in those layouts, and take a repository's marker before the methodology's so that a methodology installed below a repository's root finds what version control finds (point 6). They part from version control's answer only where something besides the markers moves it: the checkout's own configuration, which these commands must not trust, the environment, which ADR-001 keeps out of the resolution, or version control's refusal of a repository or its stop at a file system's boundary, where these commands take the markers as they lie. So this refines ADR-001 rather than overturning it: its aim, version control's answer in the layouts it names, holds for these commands by test, and only the means differs. ADR-049 point 4 is overturned in part instead, since its Rationale weighs this very carve-out, and its reason, ADR-039 D1's lock of code to content, fails for these commands. The marker lies in the checkout, so a sandboxed command can move the root they find. Realizing shows the folder it acts on, refuses one with no model, and binds nothing to a folder the person did not see, so a moved root costs a refusal or a bound the person saw. The convenience of running from a subfolder holds for these commands too.

**Why the core gives the hook's verdict, and chooses its bound.** ADR-003 keeps the decision in the core so that its callers never diverge. Choosing the bound, judging by two models and combining the verdicts is decision, so it lives there too, and a command that reports a verdict reports the core's. The adapter adds only what turns on the harness. The hook's copy can differ from the installed release, so the overview reports when it does.

**Why the registration stays committed.**

- **Committed,** it reaches every clone and worktree, and running the hook stays the project's choice (ADR-002 point 2). Where a machine has no copy, the hook's failure to start is loud.
- **The cost:** each collaborator who pulls it meets that loud fault on every call, until they install the methodology and make the copy.
- **In each checkout's local settings,** a fresh clone or a new worktree would run with no hook and no fault.
- **In the person's own harness settings, outside every checkout,** with the project's choice kept beside the snapshots. This covers every clone and worktree with no committed path to rewrite, and spares collaborators without the methodology the loud fault. But running the hook would become each person's choice on each machine, so a collaborator who never turned it on would run with no hook and no fault. The backbone would also write a file the person owns outside the project, and the hook would run in every session on the machine, in every project.

**Why the hook judges by both the snapshot and the checkout.**

- **The checkout alone** is the gap this record closes.
- **The snapshot alone** keeps a revoked grant in force until someone realizes. That is a boundary believed but absent (ADR-004 point 4).
- **Falling back on any difference between the two** would drop the model at each pull, sync and branch switch. A narrowing would wait for a gesture it does not need.
- **The stricter of the two verdicts** lets the checkout narrow at once and widen only through realizing.
- **A revoked grant asks.** Where the snapshot allows a call and the checkout no longer does, abstaining would hand the call to the harness's native rules, which may hold the grant as realized. Asking lets the revocation reach those rules at once, since, by the harness's documentation, which the probe confirms (point 6), the harness prompts on a hook's ask whatever its rules allow. The cost: on a branch whose model lacks a grant the snapshot holds, each call of that grant asks, as that branch's model has it.
- **Except where the person chose not to be asked.** In such a mode a call never granted runs unasked, so a revoked grant that asked would be stricter than one never granted. The hook abstains there, as ADR-025 point 7 has it for its own ask, and the revocation waits for realizing where the native rules hold the grant.
- **The snapshot alone, when the checkout's model fails.** The snapshot lies out of reach and the checkout does not, so a failure on the checkout's side may cost no more than what the checkout alone holds. Judging by the snapshot alone loses only a narrowing not yet realized, which the checkout can drop in any case, and keeps every deny and ask the snapshot holds. The order and the budget keep a stall in the checkout from costing the snapshot's judgement.

**Why the bound is found from the anchor.** Which snapshot binds must rest on nothing a sandboxed command can write. What marks a checkout's root, and the configuration that moves a working tree, lie in the checkout, so a lookup through them could be broken to reach no bound, or steered to a wider one. The harness sets the anchor and no command moves it, and the index lies out of reach, so the choice rests on neither. The identity guards a reused path: another repository cloned where a realized one stood does not inherit its bound, save where the platform gives the new folder the old one's device and inode. A bound so carried holds the later folder as the person realized it for that path, and its own model only narrows it, so it widens nothing past that bound. ADR-093's lists are matched by the same identity, so what the probe finds of it bears on both. A bound covers whatever is anchored inside its folder because the person realized it for that folder. A worktree or a repository kept inside it is work started there, and its own model can only narrow the bound. A person who wants a folder inside it bounded otherwise realizes that folder on its own. Where the state folder and the anchor's folder overlap, the session could write the bound itself, so the gestures refuse to bind such a folder, and the hook treats a bound there as unusable rather than trust it.

**Why a runner may name the bound.** A working run's hook judges by the model its runner read from the default branch, placed outside the run's clone (ADR-073 point 2). Its anchor is the clone, which nobody realized, so a choice through the index would give it no bound, and its checkout is the clone the builder writes. Naming the bound in the registration keeps ADR-073 point 2 as it decides. The named model must lie in a folder the backbone keeps for runs, which no sandboxed command writes. A registration is written from sources in the checkout (point 7), and a model named anywhere else, such as a temporary folder, could be one a sandboxed command wrote, behind a registration that looks like the real hook. A registration's writer can already register any code as the hook, so this opens no new way in, and the overview names each registration that names a model.

**Why a bound that cannot be used makes the hook ask.** With no bound, no person has realized one for the folder, as at the upgrade that brings this record's build, and the hook's own verdicts with the checkout's narrowing keep the session usable without flooding the person with prompts. Where a bound binds, it is what the person chose. Abstaining there would hand every call to the native rules and drop each deny and ask that only the bound holds. A state that a sandboxed command can bring about, such as a replaced folder, a stall past the budget or a realized model the core cannot judge, would then switch the bound off. Asking keeps the bound's absence loud, and refuses where nobody can answer. Realizing judges what it writes, so that a person does not put such a bound in place unawares.

- **The cost.** In that state an attended session prompts on each call until the cause clears or the person realizes the folder again, in every mode. A run nobody watches, such as a review in the person's checkout, is refused each call. The state follows a change to the folder or the release the bound was realized for: a re-clone at its path, a remount that changes its identity, a remade copy whose carried snapshot the person did not keep, or a sandboxed command's work. It also follows a fault of the copy's core on some shape of call, and a judgement that runs past the budget on a loaded machine. A re-clone, a remount and a sandboxed command's work each touch one project. A remade copy, a fault of the core and a loaded machine can touch every project on the machine at once, since one copy serves them all. Remaking shows each snapshot it would leave unusable before it acts (point 3), and realizing judges the conformance calls, but neither rules out a fault on a call they do not cover. The no-bound state is the common one, and the flood is what it avoids there.

**Why realizing is one operation, and why the interlock.** Each command that realized by a way of its own would be one more path to widen that an agent can reach. One operation, which shows each widening against what is in place, the native rules included, lets a person see what they realize, even where the model changed between their review and their realizing. A command that realizes as a step of its work, as activating a profile does by default, runs that operation, so it keeps ADR-005's composition and adds no path. Turning the hook off widens every call at once, and turning it on puts in force a bound that may allow what the native rules would ask, so both take the same interlock. A gesture that widens the sandbox of the project's sessions widens more still: one session with its sandbox off passes the protection of every project on the machine. So it takes the interlock too, though it writes the harness's settings, which point 7 leaves open. An install over the release changes what every later copy holds, and where the installer is exempt it runs past the native deny. So the backbone's upgrade installs nothing under an anchor, and the asks cover both the upgrade and the installer's own command, which the backbone cannot make refuse. The interlock costs the person a terminal for each widening, and closes the plain ways for an agent to widen unasked: the anchor and the mark in the gestures, the ask in the hook, and the native ask in every project. The gestures read both marks of an agent's call. The harness's mark is the one ADR-093 point 4's refusal reads, so the test is built once for both, and it holds where a command line clears the anchor alone, the bypass ADR-034 point 5 names; the anchor holds under a harness that sets no mark, or where a file the shell reads at its start unsets the mark (point 7). No editor sets the mark, so it refuses no person the anchor alone would not. Where the probe finds the anchor carried into a person's own terminal, such as an editor's, the gestures refuse there as well, and a refinement of this record weighs the mark alone. The native ask is what holds where the hook does not run, in a project that leaves it off and before the copy, against a command line that clears both marks or a release from before this build, which refuses nothing; in the common case it costs a prompt before a refusal. Under an anchor, the setup of autonomy stops at a step that widens, as ADR-007 rule 4 has a step that cannot complete stop, and names the person's terminal. Each guard can be passed, so it is declared an interlock, as ADR-034 point 5 declares its guard.

**Why making the copy is an operation of its own, which realizing never runs.** Remaking the copy changes the hook of every project on the machine and carries every snapshot there, so it can widen what the hook allows in every project at once. Run as a side effect of realizing, it would let a realizing that only narrows, which goes ahead under an anchor, remake every project's hook on the machine. So it is one operation, which shows what it would change and takes the interlock. Under an anchor it makes no copy even where none exists: a first copy starts each project's hook that could not start, and puts every snapshot on the machine in force at once, and a snapshot its carry cannot compare would be kept by an agent's call rather than a person. Turning the hook on runs it only where no copy exists, and gains no realizing, since ADR-002 point 2 keeps the two gestures apart (ADR-007 rule 1), as activating a profile gains no turning on (ADR-005 point 4). The cost: after an install of a newer release, realizing refuses everywhere on the machine until the person remakes the copy, and a project whose hook is on but has no snapshot gets no grants until its person realizes.

**Why the hook's own verdicts hold in every state.** The guardrails are the catastrophic denies, and keeping the hook's half of their double lock costs nothing (ADR-002 point 3). The asks and the deny on naming a folder are the hook's own, and only the asks before leaving the sandbox and before an interlocked command, the deny on naming a folder, and the guard's asks on the harness's settings files and its state file, on the installer's and version control's own configuration and on a move into another tree, have a native rule beside them. Kept apart, no one fault takes the others with it. With no bound, asking on every call would flood the person with prompts approved unread ([project-kit#2002](https://github.com/aleskalfas/project-kit/issues/2002)), and denying every call would stop the session.

**Why a call that leaves the sandbox is asked, rather than the escape sealed.** Where the escape is open, a call that leaves the sandbox rides the normal permission flow (ADR-005's Rationale, "Why `failIfUnavailable: true`, not `allowUnsandboxedCommands: false`, carries the invariant"). By the harness's documentation, a native allow that matches the command then runs it unconfined and unasked, and it can write the guarded folders. Asking before such a call closes that path and leaves the escape a person's choice, the operator's stopgap ADR-028 point 5 keeps outside the setup of autonomy. Sealing it wherever the hook is on, or in every project, would overturn in part ADR-028 point 1's choice to seal it only under that setup. An ask in every project's settings meets point 1's two reasons for refusing a baseline seal:

- **Legitimate fail-over** still runs where someone watches: the call leaves the sandbox once a person approves it. In a run nobody watches it gives way: the call is refused, and runs inside the sandbox only when the agent issues it again without the request, as a sealed escape would have run it. There the protection of every project outweighs the fail-over point 1 kept.
- **The operator's choice of posture** keeps the escape open and its use theirs, one approval at a time. What it loses is a native allow approving the escape unasked, which is an agent's reach for it rather than the operator's deliberate use, the reach point 5 removes under the setup of autonomy. Outside that setup that reach passes every project's protection, through the guarded folders all projects share. So the record refines ADR-028 point 5 in place rather than overturning point 1.
- **The cost:** each call that asks to leave the sandbox prompts, in every mode that asks and in every project, even where a native allow would have run it, and a mode that never asks refuses it. The ask also gives up the reversibility ADR-028's Rationale keeps for the seal, "a posture choice rather than a revocation": a project's operator cannot drop it, since the settings every project receives carry it and an escape from any one project reaches the guarded folders, which every project on the machine shares (point 2).

**Why native locks stand beside the hook.** The hook fails open where it cannot start, as before the person makes the copy, and where it fails or runs past the harness's limit (ADR-002 points 3 and 4). It also runs only in a project that turns it on, while the guarded folders are every project's. The harness weighs its own deny and ask rules whatever a hook returns. So the native locks keep the escape, the interlocked gestures, the naming command and the file tools' writes into the guarded folders locked in every project's sessions that read them and in every state of the hook, and in particular in the window before the copy, where nothing else would guard the folder the copy goes into or the release it is made from.

- **What needs a lock.** The copy's source needs the same lock as its destination: a release changed in place becomes every project's hook at the next remaking, and runs every gesture the person makes from their terminal. The interpreter each runs on needs it for the same reason, and so does the installer's program, which the upgrade and the remedy run. What chooses the source's contents, the installer's and version control's own configuration, needs an ask for the same reason. Every settings or connected-servers file of the harness's needs an ask too, the person's own and each checkout's, since what it starts runs outside the sandbox, and the harness reloads hooks from it while a session runs, so a write to it reaches the guarded folders past the deny. A move into another tree needs one for the same reason, since it brings that tree's settings.
- **What the remedy sets aside.** The reinstall the overview names as the remedy sets that configuration aside, with the environment, which the shell's startup files set and no ask of this record's guards, since a remedy that read them would reinstall what changed. The cost: a person who reaches a private source through a credential that configuration or the environment supplies can reach it through the remedy only with that credential on the command's line, where it does not belong, so they reinstall by a way of their own, which the overview cannot check.
- **The hook is their second lock,** as it is for the guardrail denies (ADR-002 point 3). The native rules are configuration that actually holds, so the hook's asks, denies and guard beside them claim no boundary the configuration does not hold, which ADR-028 point 4 forbids. The hook still earns its place: it asks on a request it cannot read, guards the guarded folders wherever a machine keeps them and by every path that names them or resolves into them, where the native deny names only their default places, guards the person's own settings, and the installer's and version control's own configuration, wherever the environment moves them, with the files that configuration includes and a link's target, recognizes forms of the interlocked commands and of the naming command that the native rules do not name, and gives a reason.
- **How far they hold.** The native rules hold only as far as the probe confirms (point 6), and an extension that answers for the person passes them (point 7).

**Why the person's own locks are printed, not written.** The guarded folders are the person's, and every session of theirs can write them, while a project's settings reach only the sessions started at its root. Only the person's own harness settings match the folders' reach: there the locks hold in a project that does not use the methodology, in a session started outside every checkout, and in a checkout at an older commit, whose own settings carry none. The backbone prints them rather than writing them: that file is the person's, outside every project, and the backbone prints what belongs in a file it does not own, as ADR-060 prints the ignore line rather than write the project's ignore file, its "print, don't mutate". No hook runs from that file, so no copy's fault reaches every session. The cost: they hold only where the person adds them, so the overview reports whether they are in place, and the locks in every project's settings stay the default.

**Why the hook's interpreter starts isolated.** An interpreter loads more than the script it runs: its own library, the packages installed beside it, the person's own packages and the startup files among them, and whatever the environment names. Each lies outside the copy, and a file tool can write those the person's account owns, so the next start of the hook, in every project that turns it on, would run what was written there. A launcher that picks the interpreter each time it starts, by the environment and the machine's state, would let either choose it. Named by its own path, started isolated and with an emptied environment, the interpreter loads only the copy and its own library, and where the account can write that library, it is guarded as the copy is. The variables the starter passes on are those the hook's own tests read, ADR-093's among them: without the marker of an agent's run the hook would count named folders in a review's run in the person's checkout, which ADR-093 rules out, and without `PATH` its test of the shell's path would exclude nothing. An isolated interpreter finds no code through any of them. The shell that runs the registration's command, and the platform's program loader, read the environment first, which no starter can empty before it runs, so point 7 states it.

**Why an agent's move into another tree is asked.** The harness moves a session's settings with it, so a move into a tree a sandboxed command made, or one checked out from history it wrote, brings hooks that run outside the sandbox, with one call of the agent's and no step of the person's. The start hooks are mended for exactly such a path (point 2), and here the record cannot mend what the harness loads, so it puts a person's step before the move. The step is an interlock, since the person approves a move and not the settings it brings. The harness's write block removes the tool, at the cost of every agent's move, so the record offers it among the person's own locks and leaves it to each project's choice.

**Why the protection is stated for the machine.** The state folder is one for each person, as far as the file system reaches it, so that one install feeds one copy for every project there. A folder for each project would narrow nothing, since what runs as the person outside a sandbox writes every folder the person writes. So whatever can write it in any project's session can pass every project's protection, and the record says so rather than claim a protection for one project that the others' sessions can undo. The machine is what the file system makes it: a home shared with another host, mounted into a container, or reached from the Windows side of WSL2 extends it, and nothing the backbone sees on one host tells it what the others run. Each session can keep the folder only as far as its own sandbox, its own escape, its own file tools and the tools it connects allow, which the native locks govern only in the sessions whose settings carry them, and the hook only where it runs. A guard that the backbone keeps over every session on the machine is left to a follow-up that the probe informs (point 7).

**What it costs an agent host.** ADR-093 lets a host's guidance write outside the repository through a file tool where nobody answers its ask (the Context, "Agent hosts"). This record narrows what a named folder lifts, on every machine: the hook's guard on itself and the native locks hold in a named folder too (point 4), and each of their asks holds in every mode, so where nobody answers, it is refused or holds the run, as the trial saw an ask do. A write such as the trial's service file meets none of them, and a named folder serves it as ADR-093 decides. A step of a host's guidance that writes through a file tool what the guard asks before, such as registering a connected server, editing the harness's settings, setting version control's identity in its configuration in the person's home, or editing the installer's own configuration, is refused, or waits, and no named folder lifts it. So is an agent's call of an interlocked gesture, a call that asks to leave the sandbox, and a move into another tree. On a host whose machines cannot start the sandbox, as the trial's cannot, the protection buys nothing in return, since nothing confines the shell there (point 7, "A session whose sandbox is off"), and an agent refused such a write may take it to the shell, where nothing of the methodology's reads its target (ADR-093's Rationale, "Or it goes to the shell"). The cost is accepted as a limit, stated by its property ([ADR-091](ADR-091-no-host-component.md) point 4): a session with nobody to answer its asks makes none of these writes or calls through the tools these asks cover. Meeting it would key the asks to what the hook cannot read, or lift them in a named folder (the alternative "Lift the guard's asks in a folder a person names, or where the sandbox cannot start"). A host whose guidance needs such a write makes it in its setup, outside any session, where no ask is put, by ADR-091's fourth question (ADR-091 point 7), as its setup names its folders there (ADR-093 point 4).

**Why a named folder stays the person's to name, though it can be a route.** ADR-093 weighed meeting a host's need against keeping the ask everywhere on the premise that naming a folder gives an agent no route it lacks, which held while a sandboxed command could drop the ask through the hook's own files. Where the hook runs from its copy, no sandboxed command alone drops that ask, save through what point 7 names. So for a folder that a program outside the sandbox runs or reads, the ask puts before a person a way around the sandbox, which naming the folder opens: a confined agent's file tool writes there unasked, and that program runs what it wrote with the person's full access, where it can write the guarded folders every project shares (point 7, "Everything else that can write the guarded folders"). The record has ADR-093 state that plainly, and has whoever names such a folder accept it for every project on the machine (Implications). It has the overview report, in every project, each folder named for any checkout on the machine that it can see, since a folder named for one checkout reaches the others' protection and would go unseen in their own state, as ADR-093 says of one list for every project (its alternative "One list for the user, for every project"). The overview names the folder of lists it read, and says it cannot see lists kept under another state home (point 7). ADR-093's choice to meet the need stands on three grounds:

- **Where the need was measured,** the host's machines cannot start the sandbox, so the protection holds nothing there, and naming the folder costs none of it ("What it costs an agent host").
- **Where the sandbox runs,** naming such a folder is a widening, which ADR-093 point 4 holds to the discipline ADR-008 point 4 sets for one: an explicit gesture, loud, never committed and always reported, save for an agent's call that passes the command's refusal and the denies before it (point 7, "The naming command where no mark reaches it"). Its message on each naming tells the namer how far the folder reaches (Implications).
- **Keeping the ask everywhere** costs what ADR-093 weighed: the host's step fails, or moves to the shell, where nothing of the methodology's reads its target (ADR-093's Rationale, "Why meet the need").

**Why the naming command meets a deny, not an ask.** No agent's call of the naming command is meant to succeed: under a harness that sets the mark, the command refuses it (ADR-093 point 4), and under one that sets none, ADR-093 still has a person name a folder at a terminal of their own, not by approving the agent's call (its Rationale, "Why the naming command refuses a tool call"). So a deny refuses nothing an ask could rightly let through, and it gains on each count where an ask falls short:

- **No prompt before a refusal.** Under a harness that sets the mark, an ask would have a person approve a call the command then refuses, the cost ADR-093 weighs against an ask rule (its alternative "An ask rule on the naming command"). A deny refuses first what the command would refuse.
- **It holds where the hook does not run.** The native deny holds in a project that leaves the hook off and before the copy is made, where under a harness that sets no mark nothing else refuses the plain call.
- **It rests on nobody's answer.** It puts nothing to a person, so it does not rest on `ask-reaches-person`, and no hook on the harness's permission requests can approve it.
- **It needs no mark.** The hook denies whatever the harness marks, so the copy's starter passes no mark on, and a harness that marks its hooks and not its shell's processes, or a shell that unsets the mark, changes nothing the hook gives. On Linux with the sandbox on, it refuses a call that would fail, where an ask would put a prompt before the failure.

The gestures point 3 interlocks take an ask rather than a deny, since a realizing that only narrows goes ahead under an anchor, so an agent's call of them can rightly succeed. The deny is an interlock, as the hook's other verdicts on a command are, and it refines nothing of ADR-093, which declines an ask rule on the command and decides no verdict of the hook's on it.

**Why the checkout still narrows where no bound is in force.** Point 1 lets a place a sandboxed command writes narrow what the hook allows, and a narrowing needs no person's gesture. So with no bound the checkout's denies and asks stand, and only its allows wait for realizing. A project then keeps the denies only its hook holds from the upgrade on, before its person realizes it.

**Why a clone made for a run gets no bound of its own.** Tying such a clone to the snapshot of the checkout it came from would give the clone a bound the hook would not otherwise hold. So only code out of the checkout's reach could record the tie, and only for a folder that code made. That means the backbone making such clones, which ADR-066 left to a follow-up and which would overturn part of its point 10. Such a run keeps the hook's own verdicts and its model's denies and asks (point 4), and what it loses is the model's grants, which do not count there yet in any case (ADR-066 point 11).

**Why a shared cache widens.** ADR-008 classed a build cache narrowing because it makes the box usable without enlarging the agent's reach. A cache whose contents the person's own runs later execute does enlarge it, since what a sandboxed command wrote there later runs unconfined. A cache for each checkout keeps the usability ADR-008 sought, at the cost of a download in each checkout's first run, and a cache shared by every project's sandboxed runs would carry one project's writes into another's. Point 5's test states the line that ADR-008's split was drawn to keep.

### Alternatives considered

- **Deny sandboxed writes to the permission files where they lie.** Rejected: each working-tree move across a change to them fails, as does sync inside the sandbox, and the file tools stay open.
- **Read the model and the code from the default branch's head.** Rejected: the git folder is open to sandboxed writes (ADR-066's Context), and a branch's own model would never apply.
- **Act on a snapshot of the model alone.** Rejected: a revoked grant stays in force until someone realizes.
- **Fall back on any difference between the snapshot and the checkout.** Rejected: every pull, sync and branch switch would drop the model.
- **Fall back whenever the checkout's model fails.** Rejected: a failure on the side a sandboxed command can write would then cost the bound kept out of its reach.
- **Let a revoked grant abstain until it is realized, in a mode that asks.** Rejected: the harness's native rules may hold the grant as realized, so the revocation would wait.
- **Find the bound through the checkout's root, as the backbone finds a project's root.** Rejected: what marks the root lies in the checkout, so a sandboxed command could break the lookup or steer it to a wider bound.
- **Find the folder to realize as other commands find their root, asking version control.** Rejected: version control runs what the checkout's configuration names, and none of its switches sets a repository's own configuration aside.
- **Ask version control with every program its configuration could name switched off.** Rejected: the list of such settings is version control's to grow, so the claim that these commands run no code from the checkout would rest on a list nobody here keeps.
- **Take the folder to realize from the person alone, finding no root.** Not taken: it would cost the convenience of running from a subfolder, while reading the marker by hand, and showing the folder, binds no folder the person did not see.
- **Let a working run's hook choose its bound through the index.** Rejected: nobody realized its clone, so it would get no bound, and ADR-073 point 2 would not hold.
- **Honour a model a registration names anywhere outside the anchor's folder.** Rejected: places outside it that a sandboxed command writes, such as a temporary folder, would serve.
- **Let only the worktrees of a realized checkout take its bound,** tied by data out of reach. Not taken: the bound is the person's for a folder, the anchored checkout's own model narrows it, and a tie for each worktree would ask a gesture for every worktree.
- **On an identity that does not match, take the next realized folder up.** Rejected: a bound realized for another folder would stand in, wider wherever that one is wider.
- **Fall back quietly where a bound binds but cannot be used.** Rejected: a sandboxed command could bring that state about, and drop every deny and ask that only the bound holds.
- **Defer to the session's mode where a bound cannot be used.** Rejected: a sandboxed command could bring that state about, and switch the bound off in the modes that ask nothing.
- **Ask on a revoked grant in every mode.** Rejected: where the person chose not to be asked, revoking a grant would make its call stricter than one never granted.
- **Treat a snapshot as unusable where the installed release lies inside the anchor's folder.** Not taken: an install from source would then ask on every call in its own checkout. The overview reports it.
- **Rely on the hook alone to catch a state folder that overlaps the anchor's folder.** Rejected: a session that can write the state folder can write the copy that checks it, so the gestures refuse to bind such a folder, and the hook's check only catches what a person made unawares.
- **Give only the hook's own verdicts where no bound binds.** Rejected: it drops the checkout's denies, which point 1 lets narrow at once.
- **Seal the per-command escape wherever the permission hook is on, or in every project.** Not taken: it would overturn in part ADR-028 point 1's choice to seal the escape under the setup of autonomy alone, and the native ask closes the same path in every project, at the cost of a prompt.
- **Leave a call that leaves the sandbox to the native allow rules.** Rejected: a native allow would run it unconfined and unasked, where it can write the state folder.
- **Lock the escape and the state folder in the hook alone.** Rejected: the hook lets each call proceed where it cannot start, as before the person makes the copy, and where it fails or runs past the harness's limit, and it runs only in a project that turns it on. A session could then plant the copy in exactly the window before it is made.
- **Register the permission hook so that the harness blocks the call where the hook cannot start, fails or runs past its limit.** Not taken here: it would turn ADR-002 point 4's loud fault into a refusal of every call, for every collaborator of a project that turns the hook on until each installs the methodology and makes the copy, and so overturn that point. The native locks close the path the window opens without it. A follow-up of project-kit#3178 may propose it.
- **Leave the gestures that widen the sandbox to the hook's ask alone.** Rejected: the hook runs only in a project that turns it on, while a session whose sandbox is off passes every project's protection.
- **Leave the interlocked commands to the release's refusal and the hook's ask, with no native ask.** Rejected: where the hook is off, and before the copy, the release's refusal alone would stand, which a command line that clears both marks passes and a release from before this build never makes. A native ask costs a prompt before a refusal in the common case.
- **Ask before every call of a connected tool.** Not taken: a session's connected tools serve most of its work, and asking on each would flood the person with prompts approved unread. The hook asks where a call names a guarded folder, and the follow-up on the other sessions decides the rest.
- **Keep a state folder for each host.** Not taken here: what reaches a shared home also reaches every host's folder in it, so it would narrow nothing against the other hosts' sessions. The follow-up on the other sessions decides it.
- **Start the hook through the methodology's command on the session's path.** Rejected: the path, and the entry point's routes, may lead into code the checkout chooses, and the hook would need the methodology's runtime, which ADR-014 point 1 keeps it free of.
- **Register the hook in each checkout's local settings, in place of the committed registration.** Not taken: a fresh clone or a new worktree would run with no hook and no fault, and running the hook would stop being the project's committed choice (ADR-002 point 2).
- **Write the native locks, or the hook's registration, into each checkout's local settings beside the committed ones,** which the harness reads at the repository's root wherever in it a session starts. Not taken here: shared state has one home, the committed settings ([ADR-032](ADR-032-per-machine-activation-routing-axis.md)), a second copy would reach only the checkouts the adapter set up on that machine, and a second registration would be one more file that turning the hook on and off keeps in step. What declining costs: a session started below a checkout's root meets none of the project's locks, so a collaborator who has not added the person's own locks runs there with no lock. The release's notes say to start sessions at a root, and the person's own locks reach every session.
- **Register the hook in the person's own harness settings, with the project's choice kept beside the snapshots.** Not taken: running the hook would become each person's choice, a collaborator who never turned it on would run with no hook and no fault, and the hook would run in every session on the machine.
- **Native locks in the person's own harness settings in place of every project's.** Not taken: they would hold only where the person adds them, so a collaborator who never did would run with no lock, where every project's settings reach each collaborator through sync, in each session started at a checkout's root. The person's own locks are taken beside them (point 4).
- **The backbone writes the native locks into the person's own harness settings.** Rejected: that file is the person's, outside every project, and the backbone prints what belongs in a file it does not own (ADR-060). Printing them, and reporting whether they are in place, leaves the choice and the file with the person.
- **A hook of the backbone's in the person's own harness settings, guarding every session on the machine.** Not taken here: a hook would run in every session on the machine and a fault of its copy would reach them all, and it would close no more than the person's own locks do against a session whose sandbox is off. By its documentation, the harness itself asks before a file tool's write outside the working folders only on the paths it protects, and only in some modes (ADR-093's Context, "The paths the permission system protects"), which the probe confirms (point 6), and the follow-up on the other sessions decides such a guard on its answer.
- **Put the harness's write block into every project's settings.** Not taken: the harness honours it from any scope, and it would close the file tools' half of the protection wherever the guarded folders lie, refuse a write into every settings file in every mode, and remove the tool that moves a session into another tree. But it would refuse, in every project, each write of an agent's file tools outside its working folders, which a person can otherwise approve, and each such write into a settings file, and take from every project the agent's moves into worktrees, which some projects' flows rest on. The asks close the plain paths at the cost of a prompt, the person's own locks name the block as one the person may add, and a project that accepts its cost sets it in its own settings.
- **Leave an agent's move into another tree to point 7, with no ask.** Rejected: one call of the agent's would bring hooks that run outside the sandbox, with no step of the person's, the path the start hooks are mended against.
- **Start the hook's interpreter as the person's other scripts start, with their packages and the environment's settings.** Rejected: what those load lies outside the copy, where a file tool writes, and the hook would run it at its next start in every project.
- **Decide in this record how skills and agents deploy, so that what the harness loads carries no hook or pre-approval written from the checkout.** Not taken here: core records decide how they deploy (COR-006; COR-013 point 5), as core rule 12 (RS-OPS-012) states, and only a core record can apply point 1 to them (point 1, "Its reach"). Deploying skills as copies, as agents are, would not close the path alone, since the deploy remakes each copy from the checkout. A follow-up of project-kit#3178 proposes it.
- **Have the hook ask before a file tool writes a skill's or an agent's source so that it carries hooks or pre-approvals.** Not taken here: the hook would judge the source as it parses it, not as the harness does, would see neither a script that an existing hook runs from the checkout nor a sandboxed command's write, and would hold only where the hook runs. The core record that decides how skills and agents deploy closes the path whole.
- **Have the move's ask read the target tree's settings, and refuse where they register any hook but the copy and the adapter's fixed commands.** Not taken: a move may take more than the tree's settings, its skills and agents among them, which the probe finds, so a check of the settings alone would show a tree as checked that is not; a project that registers hooks of its own would have every move refused; and a tree the move makes cannot be read before it exists.
