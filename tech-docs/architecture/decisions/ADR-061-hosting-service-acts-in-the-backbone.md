## Summary

**In plain terms:** everything the methodology does on the hosting service to land a pull request is implemented once, in the backbone: reading where the PR stands with its base branch's merge queue, merging it, handing it to the queue, waiting for the queue, taking it out again, and deleting its head branch once it has merged. The backbone offers it as the `pkit pull-request` command; a capability's scripts call that command, and the backbone's own code imports the module behind it. It works only for GitHub, through `gh`, and says so. That placement is provisional: core records put platform-specific pull-request conventions in capabilities, while the backbone's own release needs these acts, and the conflict is raised for a core decision. The command reads no host from any configuration; the caller's environment decides which host `gh` reaches. It stays out of `pkit repository`, which remains a local reading that needs no network. The command makes the requests and reports the facts it read; each caller keeps the decisions (when to land, which of those facts stop a landing, and what happens after the merge), states them as options of the call, and keeps five obligations that span its own steps. Its versioned JSON documents are the contract. Its subcommands that change the service run the cross-repository guard themselves, on a comparison that has its one home in the backbone. How a PR lands, one squash commit carrying its title and body, is COR-009's; this record realises it, except that a direct merge leaves the body to the service until the command passes it.

## Context

Two flows land pull requests: project-management's merge verbs and the backbone's release flow. A merge queue makes landing subtle. A merge request that succeeds may only have put the PR in the queue. A push after the checks ran must take the PR back out. And the queue builds the squash commit from repository settings, ignoring what the merge request passes. Two copies of this mechanic drifted apart, at a real cost: one took a successful merge request for a merge and deleted the head branch of a PR the queue had only taken in, which closes the PR and drops it from the queue (#1200). The queue is also the intended single path for merging ([ADR-055](ADR-055-first-adopter-analysis-and-living-docs.md) point 5), so every landing will meet these subtleties.

The `pull-request` command this record places is the backbone's first general command that acts on a hosting service. No record answers the questions it raises:

- where such acts belong;
- how they relate to `pkit repository`, which is local and needs no network ([COR-054](../../../.pkit/decisions/core/COR-054-default-branch.md));
- what tying a core command to one service means, when core content is meant for any adopter ([COR-014](../../../.pkit/decisions/core/COR-014-universal-applicability.md)) and platform-specific pull-request conventions live in capabilities ([COR-008](../../../.pkit/decisions/core/COR-008-git-conventions.md), [COR-009](../../../.pkit/decisions/core/COR-009-pr-workflow.md));
- where the host comes from;
- what the command cannot do for its callers;
- whether it guards against mutating another repository ([COR-039](../../../.pkit/decisions/core/COR-039-session-repo-mutation-boundary.md)).

How a PR lands is settled in core: one squash commit whose subject is the PR's title and whose body is its body (COR-009 points 1–2). Where the mechanic lives is not. The only statement that puts it in the backbone is a paragraph of project-management's [DEC-013](../../../.pkit/capabilities/project-management/decisions/DEC-013-branch-and-pr-conventions.md) ("One merge mechanic"), and a capability record cannot govern a process the backbone needs in order to ship ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md), the dependency direction).

## Decision

**The acts that land a pull request on the hosting service have one home: the backbone's `pull-request` command, realised for GitHub through `gh`, a placement adopted provisionally. Callers keep their own decisions, stated as options of the call, and five obligations. The JSON documents are the contract. The command guards the changes it makes.**

1. **One home.** The acts that land a pull request are computed in one backbone module and nowhere else. They are: reading where the PR stands with its base's merge queue; reading the repository's squash-commit defaults; the direct squash merge and the enqueue, each pinned to the head the caller checked; the wait for the queue's merge; taking a PR out of the queue; and deleting a merged PR's head branch on the service, only while its tip is the head the caller names. Capability scripts reach the module through `pkit pull-request --json`; the backbone's own code imports it. No caller asks `gh` for one of these acts itself; the deletion is the exception until the command makes it (#1220). [ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 1 has capability scripts reach the backbone's engines by command, and those engines only read. This command also changes the service, but the reasons hold unchanged: a capability script does not import the backbone's package, and a computation keeps one home (ADR-057 point 2). What a caller reads to decide *whether* to land (checks, approvals, mergeability) stays the caller's own, and so does the local branch, which is not on the hosting service.

2. **Separate from `repository`.** `pkit repository` answers from the project's declaration and git's local references, the remote-tracking reference first and the local branch only where there is no remote (COR-054 points 2 and 5), so it needs no network. The comparison the cross-repository guard makes (point 6) is read there too, because it is local in the same way: it answers from the session's anchor and the repository's own git configuration. A pull request's state is a fact held by the hosting service: it is read over the network and can change between two readings. So the two commands stay apart:
   - nothing under `repository` reaches the hosting service;
   - a reading of the default branch never falls back on the service's answer (COR-054 point 4);
   - no command bound by the query contract, which is bounded, deterministic, needing no network and read-only (ADR-057 point 3), calls `pull-request`: all its subcommands reach the network, and some change the service.

3. **GitHub only, through `gh`, labelled, provisionally.** The command is written for a repository hosted on GitHub: it uses GitHub's merge queue, GraphQL fields and squash-commit defaults. It sits in the backbone because the backbone's release lands a pull request, and a process the backbone needs in order to ship cannot depend on a capability an adopter may not install (COR-010). COR-008 and COR-009 put platform-specific pull-request and merge conventions in per-platform capabilities instead, and COR-014 lets content tied to one *harness* stay in core under a label, as an interim, without speaking to a hosting service. Only a core refinement settles a conflict between core records, so this placement is adopted provisionally and raised for a core decision (Implications). Meanwhile the command's reference is labelled GitHub-specific, and version 1 of its documents deliberately uses GitHub's vocabulary (`SQUASH`, `PR_TITLE`, the states of a queue entry). On another service `gh` cannot answer, the reading comes back unreadable, and nothing lands. **When to revisit:** when the core decision is made; and when a second hosting service is supported, at which point the command becomes the contract, with documents in a vocabulary of their own under a new `schema_version`, and `gh` becomes one implementation behind it.

4. **No hosting-service settings in the backbone.** The command runs `gh` from the caller's working directory, whose git remote names the repository, and in the caller's environment, which names the host (`GH_HOST`). The backbone keeps no setting for host, owner or repository. project-management keeps its host in its own configuration and passes it on through the environment ([DEC-023](../../../.pkit/capabilities/project-management/decisions/DEC-023-gh-host-and-owner.md)). If the backbone ever needs a configuration key of its own for this, only a core record can introduce it ([COR-048](../../../.pkit/decisions/core/COR-048-backbone-configuration.md) point 2).

5. **The command makes requests and reports facts; the caller decides.** The command sends requests, and reports what the service answers and what it read before it asked. Everything else belongs to the caller. That covers when to land: its gates, and which of the facts the command reports stop a landing (a head the queue dropped, a base that merges through a queue when the caller wants a direct merge, a PR already waiting in a queue that does not make COR-009's commit). The caller states each such choice as an option of the call. The command applies the options to the reading it takes just before a request, where no caller can stand, and ends the landing as refused, naming the fact. A stop the command makes without being asked comes from a record that binds every landing, never from the command itself. There are two: a landing makes no administrator merge on a base that merges through a queue, the single merge path (ADR-055 point 5), and it hands a PR only to a queue that makes COR-009's commit (point 8). On a base without a queue the command passes an administrator merge through as an operator override. The caller's part also covers what happens after a merge: moving issues, running hooks, and when the head branch is deleted. Every caller that lands a pull request keeps five obligations. They were first worked out for project-management's merge verbs ([DEC-026](../../../.pkit/capabilities/project-management/decisions/DEC-026-work-ownership-lifecycle.md), "Merging through a queue"); this record states them for every caller:
   - **Merged means the service says merged.** On a base that requires a queue, a merge request enqueues the PR and still reports success. So after a direct merge the caller reads the PR again, and runs nothing that follows a merge until a reading says merged.
   - **A PR whose head moved is taken out of the queue.** The requests and the wait are pinned to the head the caller's gates checked. If a reading shows another head, the caller takes the PR out of the queue, so commits nobody checked do not merge.
   - **An unconfirmed merge is reported as unconfirmed.** If a request got no answer, or the service cannot be read after a request it may have accepted, the caller reports the PR as neither queued nor merged. It runs nothing that follows a merge, and stops as accepted so that running it again completes the landing.
   - **The head branch is deleted only after the merge.** The caller deletes the head branch only once the service reports the PR merged. Deleting it earlier closes a queued PR.
   - **The remote head branch is deleted only at the head that merged.** The caller names the head that merged, and the command deletes the branch only while its tip is that head, as the caller checks for the local branch, so a push made after the merge is not lost.

   The steps that make up a landing (read, stop on what the options and the two rules refuse, merge or enqueue, wait, take the PR out if its head moved) belong in the command, as one sequence. Each caller first held a copy of them, and their move into the command was to follow a third caller or the first disagreement between the copies ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)). The copies disagreed: #1200 breached the first and fourth obligations. Until both callers land through the command's sequence and delete the head branch through the command (#1220), a caller holds its own copy of those steps, the deletion without the tip check among them, and a change to a copy is reviewed against these obligations. Where the callers differ by design (whether a dropped head is enqueued again, whether a PR already queued in a queue that does not make COR-009's commit is waited for, what is reported when a PR merged at another head), the difference is a caller's decision: an option of the call, or the caller's own wording of a fact the command reports.

6. **The command guards the changes it makes.** Every subcommand that changes the service's state runs the cross-repository guard before its request, whether it is called as a command or imported. A landing runs it once, before its first reading, so a request it comes to make late (taking a PR out of the queue after a long wait) never waits on a question nobody is there to answer. The guard compares the session's anchor with the repository of the directory `gh` runs in; an importing caller passes that directory explicitly. It asks at a terminal and refuses when there is none. It accepts a confirmation passed with the call, so a caller whose operator has already confirmed the change passes it on and nobody is asked twice (COR-039 points 1–2; [ADR-034](ADR-034-foreign-repo-mutation-guard.md) points 1 and 4). Where the harness provides no anchor (a plain terminal, a pipeline) there is no session to compare with, and the guard does not fire; its verdict then says undetermined, never that the repository is the session's own (COR-039 point 3). The readings and the wait change nothing, so they run no guard, and a dry run never asks: it ends as a run with nobody to ask would. The guard's comparison has its one home in the backbone, read through `pkit repository` (point 2), and the capability's guard reaches it by command rather than keeping a copy; this places the one extracted check of ADR-034's Implications. The backbone reads the anchor the harness provides under a label naming that harness (ADR-034 names Claude Code's), and its documents name only the anchor and the target, so another harness changes the lookup and not the contract. Each caller still guards the changes it makes itself. Until the comparison is read through `pkit repository` and the capability's guard reads it there by command (#1220), the capability's guard keeps a copy, and a test holds the copy and the backbone's comparison to one table of cases.

7. **The JSON documents are the contract.** With `--json`, each subcommand writes JSON documents, one per line, each carrying a `schema_version`. A caller decides on the documents' fields and refuses a version it does not know. A reading states its own conclusions (merged, queued, dropped at its current head), so no caller works them out again. A missing document means there was no answer: the request may or may not have been made, so the caller reads the PR before it decides. A command that makes several requests in one run writes a line before each, out before the request is sent, so a caller left without the last document can tell: with no such line, no request was made; with one and no outcome after it, the request may have been made, and the caller reports the PR as a reading shows it (merged, queued, or otherwise unconfirmed). That a request was not made is concluded only from two readings running. Exit codes are for a person at a terminal. One code may cover several outcomes, so no caller decides on an exit code. Adding a field keeps the version. Removing or redefining a field raises the version; that is a breaking command-line change, which ships a migration in the same change (COR-010, "Migrations are mandatory on adopter-breaking surface changes").

8. **COR-009's landing, realised.** A pull request lands as one squash commit whose subject is its title and whose body is its body (COR-009 points 1–2). The command merges only by squash, and the caller passes the subject. On a base that merges through a queue, the service composes the commit from the repository's squash-commit defaults and ignores what a request passes. So before it enqueues, the command checks that the queue squashes and that the defaults are `PR_TITLE` and `PR_BODY`, and ends the landing as refused otherwise; its document carries what it read. A PR it finds already in a queue gets no request, so what a queue that does not make that commit means there is the caller's choice (point 5): stop, or wait with a warning. Until the command's sequence makes the check (#1220), each caller makes it before it enqueues. A direct merge is to carry the PR body too: the body the PR has when the command reads it just before the request, not a copy a caller read earlier, so that both paths take the body at the merge. Until the command sees to that (#1220), a direct merge leaves the body to the service's default. On the queue path the service reads the title and the body at the merge, so nothing a request passes holds them to what a caller's gates read; the command makes no rule of a title or a body that changed since, and a caller that needs one checks the merge commit after the merge.

## Rationale

**Why the backbone.** Both callers need the mechanic, and they sit on different layers: one in a capability, one in the backbone. A backbone process cannot depend on a capability an adopter may not install (COR-010, the dependency direction), so the backbone is the only home both can reach. There is one home rather than two because drift here closes PRs (#1200), the reasoning behind one home per computation (ADR-057 point 2). Capability scripts run on their own and do not import the backbone's package. That is why they reach it by command, and why the documents (point 7) must be a stable contract.

**Why GitHub's vocabulary, and no adapter layer.** With only one service, a neutral vocabulary would just be GitHub's renamed. Merge queues, auto-merge and squash-commit defaults are GitHub's concepts. A second service, such as GitLab with its merge trains, would differ in ways one example cannot predict. COR-007 extracts a common form only once a pattern recurs, and point 3 names the recurrence that triggers it.

**Why the environment carries the host.** The capability already keeps its host and passes it on through the environment (DEC-023), and `gh` finds the repository from the git remote. A backbone key would duplicate a capability setting, and would need a core record (COR-048) for a fact the caller already has.

**Why the obligations are stated, with the move due.** Each obligation spans steps that belong to the caller: its gates before the merge and its follow-up after. Moving the shared steps into the command takes over the requests and the wait, not those steps, so the obligations bind every caller before and after the move. The two callers also reach the module differently: one as a separate process, where a request can go unanswered; the other by import. One list is what both are reviewed against across that difference.

**Why the caller's choices are options of the call (point 5).** The reading that matters is the one taken just before the request: a queue can be switched on, or a PR dropped from one, while a caller's gates run. Only the command stands there. A caller that kept its refusals to itself could apply them only to an earlier reading, and two callers would hold two copies of one judgement, which is how the copies of the mechanic drifted. So the choice stays the caller's and the stop is made where the fact is read; the command reports the fact with the stop, and each caller words it.

**Why the deletion is the command's (point 1).** #1200 was a head branch deleted too early, in one of two copies of the deletion. The tip check and the deletion are one act: a check in one process and a deletion in another leaves between them the very push the check protects. The deletion also changes the service, so it belongs behind the guard (point 6), which the release flow's own copy never ran. When to delete stays with the caller, after the steps of its own that must not be skipped.

**Why the command runs the guard (point 6).** COR-039 puts the check in the program that makes the change, and this command makes the hosting-service change every landing passes through. The gap COR-039 accepts is a raw tool used around the methodology, not one of the methodology's own commands, so an unguarded merge subcommand would be a hole in the protection, not one of its stated limits. A check in the command covers every caller, the backbone's release flow included, which runs none of its own. The comparison lives in the backbone because the backbone cannot reach a capability's library (COR-010), while a capability reaches the backbone by command.

### Alternatives considered

- **A hosting-service adapter layer now:** a neutral interface with GitHub as one implementation. Rejected: there is only one service, so the interface would be GitHub's shape under new names (point 3; COR-007).
- **Put the GitHub-specific acts in a per-platform capability** (COR-008, COR-009). Rejected for now: the backbone's release lands a pull request and cannot depend on a capability (COR-010). The conflict is raised for a core decision (#1222).
- **Keep the mechanic in the capability and copy it into the release flow.** Rejected: two copies drift, and this drift closed PRs. The backbone also cannot import a capability.
- **Put these acts under `repository`.** Rejected: it would add network acts to the command COR-054 made local and network-free, which commands bound by the query contract rely on (point 2).
- **Treat the command as plumbing and leave the guard to callers.** Rejected: that relies on every caller remembering to guard, and the backbone's own caller does not (point 6).
- **Let the capability's guard keep its copy of the comparison, held equal by a test.** Rejected as more than an interim: nothing below the tool layer imports the comparison, so it has one home like any other computation (ADR-057 point 2), and a test over a table holds two homes equal only on the cases someone thought to write down (point 6).
- **Give the command only the requests and the wait, and leave every refusal in the callers, over a reading of facts.** Rejected: the callers would judge an earlier reading than the one the request follows, and would keep two copies of the judgement (point 5).
- **Let callers decide on exit codes.** Rejected: one code can cover several outcomes. The wait ends with the same code whether the PR left the queue or its head moved, and only the second obliges the caller to take the PR out.

## Implications

- **References cite this record and COR-009.** The backbone's code and references cite this record for where landing on the hosting service lives, and COR-009 for how a PR lands. DEC-013 keeps the convention for project-management's verbs and cites this record for the mechanic.
- **Follow-up work (#1220)**, each closing a gap the Decision names:
  - the landing sequence in the command, with the callers' choices as its options, and both callers landing through it (point 5);
  - the head branch deleted by the command, only at the head the caller names (point 1; point 5, fifth obligation);
  - the PR body on a direct merge (point 8);
  - the capability's guard reading the comparison by command, in place of its copy (point 6).
- **Raised for a core decision (#1222).** COR-008 and COR-009 place platform-specific pull-request and merge conventions in per-platform capabilities. COR-010 places every process the backbone needs in order to ship in the backbone, and cutting a release lands a pull request. COR-014 lets harness-specific content stay in core under a label, as an interim, and does not speak to a hosting service. Any backbone that lands its own release through a hosting service meets this conflict, so the question is universal, not project-kit's alone: may core content act on one hosting service under a label naming it, and if not, where do the platform-specific acts a backbone process needs belong? This record adopts the labelled backbone placement for project-kit provisionally (point 3), and the maintainer decides in #1222 whether the core records say so.
