## Summary

**In plain terms:** everything the methodology does on the hosting service to land a pull request is implemented once, in the backbone: reading where the PR stands with its base branch's merge queue, merging it, handing it to the queue, waiting for the queue and taking it out again. The backbone offers it as the `pkit pull-request` command; a capability's scripts call that command, and the backbone's own code imports the module behind it. It works only for GitHub, through `gh`, and says so. That placement is provisional: core records put platform-specific pull-request conventions in capabilities, while the backbone's own release needs these acts, and the conflict is raised for a core decision. The command reads no host from any configuration; the caller's environment decides which host `gh` reaches. It stays out of `pkit repository`, which remains a local reading that needs no network. The command makes the requests; each caller keeps the decisions (when to land, and what happens after the merge) and five obligations that span its own steps. Its versioned JSON documents are the contract. Its subcommands that change the service are to run the cross-repository guard themselves; until they do, each caller runs its own and the CLI reference states the gap. How a PR lands, one squash commit carrying its title and body, is COR-009's; this record realises it, except that a direct merge leaves the body to the service until the command passes it.

## Context

Two flows land pull requests: project-management's merge verbs and the backbone's release flow. A merge queue makes landing subtle. A merge request that succeeds may only have put the PR in the queue. A push after the checks ran must take the PR back out. And the queue builds the squash commit from repository settings, ignoring what the merge request passes. Two copies of this mechanic drifted apart, at a real cost: one took a successful merge request for a merge and deleted the head branch of a PR the queue had only taken in, which closes the PR and drops it from the queue (#1200). The queue is also the intended single path for merging ([ADR-055](ADR-055-first-adopter-analysis-and-living-docs.md) point 5), so every landing will meet these subtleties.

The `pull-request` command this record places is the backbone's first general command that acts on a hosting service. No record answers the questions it raises:

- where such acts belong;
- how they relate to `pkit repository`, which is local and needs no network ([COR-054](../../../.pkit/decisions/core/COR-054-default-branch.md));
- what tying a core command to one service means, when core content is meant for any adopter ([COR-014](../../../.pkit/decisions/core/COR-014-universal-applicability.md)) and platform-specific pull-request conventions live in capabilities ([COR-008](../../../.pkit/decisions/core/COR-008-git-conventions.md), [COR-009](../../../.pkit/decisions/core/COR-009-pr-workflow.md));
- where the host comes from;
- what the command cannot do for its callers;
- whether it guards against mutating another repository ([COR-039](../../../.pkit/decisions/core/COR-039-session-repo-mutation-boundary.md)).

How a PR lands is settled in core: one squash commit whose subject is the PR's title and whose body is its body (COR-009 points 1–2). Where the mechanic lives is not. The only statement that puts it in the backbone is a paragraph of project-management's [DEC-013](../../../.pkit/capabilities/project-management/decisions/DEC-013-branch-and-pr-conventions.md) ("One merge mechanic"), and a capability record cannot govern a process the backbone needs in order to ship ([COR-010](../../../.pkit/decisions/core/COR-010-resource-lifecycle.md), the dependency direction).

## Decision

**The acts that land a pull request on the hosting service have one home: the backbone's `pull-request` command, realised for GitHub through `gh`, a placement adopted provisionally. Callers keep their own decisions and five obligations. The JSON documents are the contract. The command is to guard the changes it makes.**

1. **One home.** The acts that land a pull request are computed in one backbone module and nowhere else. They are: reading where the PR stands with its base's merge queue; reading the repository's squash-commit defaults; the direct squash merge and the enqueue, each pinned to the head the caller checked; the wait for the queue's merge; and taking a PR out of the queue. Capability scripts reach the module through `pkit pull-request --json`; the backbone's own code imports it. No caller asks `gh` for one of these acts itself. [ADR-057](ADR-057-backbone-engines-and-command-limits.md) point 1 has capability scripts reach the backbone's engines by command, and those engines only read. This command also changes the service, but the reasons hold unchanged: a capability script does not import the backbone's package, and a computation keeps one home (ADR-057 point 2). What a caller reads to decide *whether* to land (checks, approvals, mergeability) stays the caller's own.

2. **Separate from `repository`.** `pkit repository` answers from the project's declaration and git's local references, the remote-tracking reference first and the local branch only where there is no remote (COR-054 points 2 and 5), so it needs no network. A pull request's state is a fact held by the hosting service: it is read over the network and can change between two readings. So the two commands stay apart:
   - nothing under `repository` reaches the hosting service;
   - a reading of the default branch never falls back on the service's answer (COR-054 point 4);
   - no command bound by the query contract, which is bounded, deterministic, needing no network and read-only (ADR-057 point 3), calls `pull-request`: all its subcommands reach the network, and some change the service.

3. **GitHub only, through `gh`, labelled, provisionally.** The command is written for a repository hosted on GitHub: it uses GitHub's merge queue, GraphQL fields and squash-commit defaults. It sits in the backbone because the backbone's release lands a pull request, and a process the backbone needs in order to ship cannot depend on a capability an adopter may not install (COR-010). COR-008 and COR-009 put platform-specific pull-request and merge conventions in per-platform capabilities instead, and COR-014 lets content tied to one *harness* stay in core under a label, as an interim, without speaking to a hosting service. Only a core refinement settles a conflict between core records, so this placement is adopted provisionally and raised for a core decision (Implications). Meanwhile the command's reference is labelled GitHub-specific, and version 1 of its documents deliberately uses GitHub's vocabulary (`SQUASH`, `PR_TITLE`, the states of a queue entry). On another service `gh` cannot answer, the reading comes back unreadable, and nothing lands. **When to revisit:** when the core decision is made; and when a second hosting service is supported, at which point the command becomes the contract, with documents in a vocabulary of their own under a new `schema_version`, and `gh` becomes one implementation behind it.

4. **No hosting-service settings in the backbone.** The command runs `gh` from the caller's working directory, whose git remote names the repository, and in the caller's environment, which names the host (`GH_HOST`). The backbone keeps no setting for host, owner or repository. project-management keeps its host in its own configuration and passes it on through the environment ([DEC-023](../../../.pkit/capabilities/project-management/decisions/DEC-023-gh-host-and-owner.md)). If the backbone ever needs a configuration key of its own for this, only a core record can introduce it ([COR-048](../../../.pkit/decisions/core/COR-048-backbone-configuration.md) point 2).

5. **The command makes requests; the caller decides.** The command sends requests and reports what the service answers. Everything else belongs to the caller. That covers when to land: its gates, its refusals, whether to enqueue again a head the queue dropped, and whether to merge around branch protection. The command passes an administrator merge through as an operator override; a caller refuses it on a base that merges through a queue, the single merge path (ADR-055 point 5). The caller's part also covers what happens after a merge: moving issues, running hooks, deleting the head branch. Every caller that lands a pull request keeps five obligations. They were first worked out for project-management's merge verbs ([DEC-026](../../../.pkit/capabilities/project-management/decisions/DEC-026-work-ownership-lifecycle.md), "Merging through a queue"); this record states them for every caller:
   - **Merged means the service says merged.** On a base that requires a queue, a merge request enqueues the PR and still reports success. So after a direct merge the caller reads the PR again, and runs nothing that follows a merge until a reading says merged.
   - **A PR whose head moved is taken out of the queue.** The requests and the wait are pinned to the head the caller's gates checked. If a reading shows another head, the caller takes the PR out of the queue, so commits nobody checked do not merge.
   - **An unconfirmed merge is reported as unconfirmed.** If a request got no answer, or the service cannot be read after a request it may have accepted, the caller reports the PR as neither queued nor merged. It runs nothing that follows a merge, and stops as accepted so that running it again completes the landing.
   - **The head branch is deleted only after the merge.** The caller deletes the head branch only once the service reports the PR merged. Deleting it earlier closes a queued PR.
   - **The remote head branch is deleted only at the head that merged.** Before deleting it, the caller checks that its tip is the head that merged, as for the local branch, so a push made after the merge is not lost.

   The steps that make up a landing (read, refuse, merge or enqueue, wait, take the PR out if its head moved) are written once in each caller. Their move into the command was to follow a third caller or the first disagreement between the two copies ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)). The copies have disagreed: #1200 breached the first and fourth obligations. So the move is due, tracked in #1220 together with the remote-tip check, which neither copy makes yet. Until the move lands, a change to either copy is reviewed against these obligations. Where the copies differ by design (whether a dropped head is enqueued again, what is reported when a PR merged at another head), the difference is a caller's decision and stays with each caller after the move.

6. **The command guards the changes it makes.** Every subcommand that changes the service's state runs the cross-repository guard before its request, whether it is called as a command or imported. The guard asks at a terminal and refuses when there is none. It accepts a confirmation passed with the call, so a caller whose operator has already confirmed the change passes it on and nobody is asked twice (COR-039 points 1–2; [ADR-034](ADR-034-foreign-repo-mutation-guard.md) points 1 and 4). The readings and the wait change nothing, so they run no guard. The guard's comparison, the session's anchor against the repository the change targets, has its one home in the backbone, and the capability's guard reaches it by command rather than keeping a copy; this places the one extracted check of ADR-034's Implications. Each caller still guards the changes it makes itself. Until the command runs the guard and holds the comparison (#1220), every caller runs its own guard before it asks for a change, nobody calls these subcommands directly against a repository other than the session's, and every release that ships the command states that gap in its CLI reference.

7. **The JSON documents are the contract.** With `--json`, each subcommand writes JSON documents, one per line, each carrying a `schema_version`. A caller decides on the documents' fields and refuses a version it does not know. A reading states its own conclusions (merged, queued, dropped at its current head), so no caller works them out again. A missing document means there was no answer: the request may or may not have been made, so the caller reads the PR before it decides. Exit codes are for a person at a terminal. One code may cover several outcomes, so no caller decides on an exit code. Adding a field keeps the version. Removing or redefining a field raises the version; that is a breaking command-line change, which ships a migration in the same change (COR-010, "Migrations are mandatory on adopter-breaking surface changes").

8. **COR-009's landing, realised.** A pull request lands as one squash commit whose subject is its title and whose body is its body (COR-009 points 1–2). The command merges only by squash, and the caller passes the subject. On a base that merges through a queue, the service composes the commit from the repository's squash-commit defaults and ignores what a request passes, so a caller checks before it enqueues that the queue squashes and that the defaults are `PR_TITLE` and `PR_BODY`, and refuses otherwise. A direct merge is to carry the PR body too. Until the command passes the body, or callers check the defaults on a direct merge as well (#1220), a direct merge leaves the body to the service's default.

## Rationale

**Why the backbone.** Both callers need the mechanic, and they sit on different layers: one in a capability, one in the backbone. A backbone process cannot depend on a capability an adopter may not install (COR-010, the dependency direction), so the backbone is the only home both can reach. There is one home rather than two because drift here closes PRs (#1200), the reasoning behind one home per computation (ADR-057 point 2). Capability scripts run on their own and do not import the backbone's package. That is why they reach it by command, and why the documents (point 7) must be a stable contract.

**Why GitHub's vocabulary, and no adapter layer.** With only one service, a neutral vocabulary would just be GitHub's renamed. Merge queues, auto-merge and squash-commit defaults are GitHub's concepts. A second service, such as GitLab with its merge trains, would differ in ways one example cannot predict. COR-007 extracts a common form only once a pattern recurs, and point 3 names the recurrence that triggers it.

**Why the environment carries the host.** The capability already keeps its host and passes it on through the environment (DEC-023), and `gh` finds the repository from the git remote. A backbone key would duplicate a capability setting, and would need a core record (COR-048) for a fact the caller already has.

**Why the obligations are stated, with the move due.** Each obligation spans steps that belong to the caller: its gates before the merge and its follow-up after. Moving the shared steps into the command takes over the requests and the wait, not those steps, so the obligations bind every caller before and after the move. The two copies also reach the module differently: one as a separate process, where a request can go unanswered; the other by import. One list is what both are reviewed against across that difference.

**Why the command runs the guard (point 6).** COR-039 puts the check in the program that makes the change, and this command makes the hosting-service change every landing passes through. The gap COR-039 accepts is a raw tool used around the methodology, not one of the methodology's own commands, so an unguarded merge subcommand would be a hole in the protection, not one of its stated limits. A check in the command covers every caller, the backbone's release flow included, which runs none of its own. The comparison lives in the backbone because the backbone cannot reach a capability's library (COR-010), while a capability reaches the backbone by command.

### Alternatives considered

- **A hosting-service adapter layer now:** a neutral interface with GitHub as one implementation. Rejected: there is only one service, so the interface would be GitHub's shape under new names (point 3; COR-007).
- **Put the GitHub-specific acts in a per-platform capability** (COR-008, COR-009). Rejected for now: the backbone's release lands a pull request and cannot depend on a capability (COR-010). The conflict is raised for a core decision (#1222).
- **Keep the mechanic in the capability and copy it into the release flow.** Rejected: two copies drift, and this drift closed PRs. The backbone also cannot import a capability.
- **Put these acts under `repository`.** Rejected: it would add network acts to the command COR-054 made local and network-free, which commands bound by the query contract rely on (point 2).
- **Treat the command as plumbing and leave the guard to callers.** Rejected: that relies on every caller remembering to guard, and the backbone's own caller does not (point 6).
- **Let callers decide on exit codes.** Rejected: one code can cover several outcomes. The wait ends with the same code whether the PR left the queue or its head moved, and only the second obliges the caller to take the PR out.

## Implications

- **References cite this record and COR-009.** The backbone's code and references cite this record for where landing on the hosting service lives, and COR-009 for how a PR lands. DEC-013 keeps the convention for project-management's verbs and cites this record for the mechanic.
- **Follow-up work (#1220)**, each closing a gap the Decision names:
  - the guard, with a way to pass a confirmation, in every subcommand that changes the service, and the guard's comparison in the backbone (point 6); until then the backbone's release flow, which imports the module, runs no guard at all;
  - the landing steps moved into the command (point 5);
  - the remote-tip check before a head branch is deleted (point 5, fifth obligation);
  - the PR body on a direct merge (point 8).
- **Raised for a core decision (#1222).** COR-008 and COR-009 place platform-specific pull-request and merge conventions in per-platform capabilities. COR-010 places every process the backbone needs in order to ship in the backbone, and cutting a release lands a pull request. COR-014 lets harness-specific content stay in core under a label, as an interim, and does not speak to a hosting service. Any backbone that lands its own release through a hosting service meets this conflict, so the question is universal, not project-kit's alone: may core content act on one hosting service under a label naming it, and if not, where do the platform-specific acts a backbone process needs belong? This record adopts the labelled backbone placement for project-kit provisionally (point 3), and the maintainer decides in #1222 whether the core records say so.
