## Summary

**In plain terms:** with pkit's permission hook on, a Claude Code session asks a person before `Edit` or `Write` writes outside its repository, in every mode. Where nobody answers, as on an agent host's machines ([ADR-091](ADR-091-no-host-component.md) defines the term), the ask is refused in the person's place or stalls the run. A write the host's guidance asks for then never happens, or goes to the shell, where pkit reads no target.

This record keeps the ask and widens it to the other built-in file tools that write a file, as the adapter lists them, never an MCP server's. A person may name, for one checkout, folders where the ask is not put. None is named by default, and a write into another repository always asks. This narrows the ruling in #2004, which holds the ask everywhere outside the repository, and accepting the record accepts the narrowing.

The names are a list of pkit's own, kept per checkout in the user's state folder, outside every checkout. A person names a folder through a pkit command that refuses a call the harness's shell tools or hooks start. Only the permission hook reads the list, never in a run pkit starts, and each session's start reports it.

Whoever names a folder accepts that a file tool's write there meets no person, nor, in auto mode, that mode's check, and that a program outside the sandbox that runs or reads files there runs what an agent wrote. Naming one adds no route an agent lacks, and the list guards no more than the ask: until the hook's own files leave the shell's reach (#3178), a sandboxed command can drop the ask without the list.

## Context

**The ask.** With the permission hook on, the Claude Code adapter's hook asks a person before an `Edit` or a `Write` to an absolute path outside the session's repository: the folder the session's anchor names ([ADR-034](ADR-034-foreign-repo-mutation-guard.md) point 1), a checkout wherever the project is one. It asks only where the decision core abstained, and never denies.

- **What allows it.** ADR-034 point 2 allows such an ask for a write into another repository. The ruling in #2004 holds it for every path outside the repository, in every permission mode, auto and bypass included, as the one prompt where a write leaves the repository. In those two modes the hook's other ask, on a call that may hide a guardrail, gives way to the mode the person chose ([ADR-025](ADR-025-segment-conservative-bash-allow.md) point 7). This one does not.
- **What rests on it.** The wider ask is stated in the adapter's README and the hook, and in no record. The adapter gives every agent a sentence that tells it to keep intermediate files in the agent workspace, never in the scratch directory the harness names. The README leans on the ask behind that sentence: a write there that the sentence did not stop meets the ask, never a silent allow (the README, "The agent workspace"; #2026).
- **What it reads.** The hook checks `Edit` and `Write` alone. Other file tools write a file too, such as `NotebookEdit`, and the adapter's settings allow `MultiEdit` ([ADR-060](ADR-060-path-scoped-workspace-allow.md) point 1 lists both), so a write through either meets no ask of the hook's.

**What the hook stands on.** The hook's code, the decision core it loads and the model it reads lie in the checkout, and the sandbox protects none of them, so a sandboxed command can rewrite them. The hook runs outside the sandbox, and a fault while it loads the model makes it abstain before it asks (the adapter's README, "The double-lock"). On macOS the permission layer's commands run outside the sandbox too ([ADR-027](ADR-027-required-sandbox-exclusion-auto-apply.md)), and load the checkout's decision core (ADR-060 point 8). So where the sandbox runs, a command it confines can drop the ask, or run code of its own outside the sandbox, with no ask on the way (#3178).

**What the trial measured.** A trial on a live agent host (#3004) ran Claude Code 2.1.321, started through a protocol bridge, in auto mode, with the hook on.

- In a turn that a message in a chat channel started, the hook's ask before a `Write` outside the repository was refused at once. The harness recorded the refusal as the user's, and the turn went on.
- In a run with nobody at it, the ask waited in the host's approval inbox, which expires after 24 hours, and the run stalled until someone answered it.
- A shell call that an allow rule in the project's settings matched carried no verdict from the check auto mode makes. Only a call no rule covered carried one.
- The host's own guidance has its agent write in the home folder, such as a service file under `~/.config/rc/init.d`. Under the hook, that write never happens there through a file tool. The host's machines cannot start the sandbox (ADR-091's Implications, rub 3), so nothing confines a shell command's writes there.

**What the harness's documentation says.** Claude Code's documentation, read on 2026-11-14, states the following. Where it names the release a behaviour starts in, that release is given, and the trial's 2.1.321 is past each.

- **A working folder brings more than a write.** The harness's working folders are the one a session starts in and those added by `--add-dir`, by `/add-dir` or by the `permissions.additionalDirectories` setting. In each, the file tools read with no prompt, `acceptEdits` mode accepts file edits and common filesystem commands with no prompt, auto mode approves file edits with no rule, and sandboxed shell commands may write (the permissions page, "Working directories"; the permission modes page, on `acceptEdits` and on how auto mode's classifier evaluates actions; the sandboxing page, "Filesystem isolation").
- **What a sandboxed command writes.** Its working folder and all below it, the working folders added, the paths a sandbox write grant (`sandbox.filesystem.allowWrite`) names, merged across every settings scope, and the per-user temp folder. In its working folder that takes in the git folder, all but its hooks and its configuration, and in a linked worktree the main repository's shared git folder too, with the same two left out. Inside that set the sandbox still protects the files the harness loads its own configuration and code from, since "a command that could edit those files could grant itself permissions, or add a hook … that Claude Code runs outside the sandbox". pkit's files are not among them. A command runs outside the sandbox only where every command in the call matches one of the sandbox's exclusions (the sandboxing page, "Filesystem isolation", "Protected paths" and its section on `excludedCommands`).
- **What runs outside the sandbox.** The file tools, hooks and MCP servers, with the person's full access (the sandboxing page).
- **A rule decides first, in every mode.** A call that an allow, ask or deny rule matches is decided by that rule before auto mode's check, except chiefly a write to a protected path, which goes to the check (the permission modes page, "How the classifier evaluates actions", step 1). The adapter's settings allow `Edit`, `Write` and `MultiEdit` with no path, so a write through one of them is decided by that rule wherever it lands.
- **An ask rule holds in every mode.** Rules are taken in the order deny, ask, allow (the permissions page, "Manage permissions"), and a matching ask rule prompts even where a hook returned an allow ("Precedence among rules, hooks, and mods"). An explicit ask rule prompts in bypass mode, falls back to a prompt in auto mode where it matches a command's content, and is refused in `dontAsk` mode (the permission modes page). It still prompts for a sandboxed command whose content it matches (the sandboxing page, "Auto-allow mode"). It matches a command's text, so a call through another shell, or by the program's full path, escapes it (the permissions page, "What a Bash rule doesn't match").
- **The paths the permission system protects** are a short list, git's folders and configuration, the shells' startup files and the harness's own settings among them. A file tool's write there asks in the default and `acceptEdits` modes, goes to the check in auto mode, is refused in `dontAsk` mode and runs in bypass mode (the permission modes page, "Protected paths"). Folders such as `~/.ssh`, `~/.config/systemd` and `~/.local/bin` are not on it.
- **A block on writes outside the working folders.** From 2.1.314, `permissions.blockWritesOutsideWorkingDirectories`, set to `true` in any settings file the session loads, makes `Write`, `Edit` and `NotebookEdit` refuse a path outside the working folders in every mode, and a `false` elsewhere does not lift it. A working folder that only a repository's settings name, a tracked local settings file's included, does not pass the block. With the block on, the harness also removes its worktree tools (the settings reference, that key's entry).
- **A deny where nobody answers.** From 2.1.319, `permissions.denyInsteadOfPrompting`, set only in the user's or managed settings or with `--settings`, denies a call that would otherwise wait on a prompt, and the turn goes on. The denial tells the agent that the session has no approval surface. The harness then asks no permission callback a host provides, but it still asks a `PermissionRequest` hook, which it names as the way to approve calls from code, so a host can register one that allows a call in the person's place (the settings reference, that key's entry). That it denies a prompt a hook's ask forces follows from that wording, and was not observed.
- **What marks a tool's process.** From 2.1.172, the harness sets `CLAUDE_CODE_CHILD_SESSION` in each process its shell tools and its hooks start. It sets it in no stdio MCP server's process, and no editor's extension sets it. Another variable, `CLAUDECODE`, for which the page names no release, the harness sets in those processes and in its MCP servers', and an editor's extension sets it in the editor's terminals (the environment variables page). Every process those start inherits them, as it inherits any variable. A process started outside that tree, such as by a terminal multiplexer's server or the system's service manager, does not, and a terminal session first started from the harness's shell, such as a `screen` session, does.
- **Where the per-machine settings file lies.** The harness reads `.claude/settings.local.json` at the repository's root, at the main checkout's root from a worktree, and beside `.claude/settings.json` where the root is the home folder or is not the user's own. Before 2.1.211 it kept the file in the starting folder, and it still reads one left there (the settings page, "Where Claude Code keeps the local file in a git repository").
- **Where a session's settings and hooks come from.** A session started below the root loads none of the project's shared settings, where pkit registers its hook: the harness reads them only from the folder the session starts in (the permissions page, "Where output styles, hooks, and local settings load from"). From 2.1.246, a session moved with `/cd` takes the settings and hooks of the folder it moves to, with no fallback to the folders above it, and those hooks still get the folder it started in as the project folder, `CLAUDE_PROJECT_DIR` (the permissions page, "Move the session to another directory"). Only a person runs `/cd`.

**What bears on it.**

- **ADR-091 placed this gap,** its gap 2. By its first question it named two ways, a narrower ask and a list the project keeps, and where the folders differ from machine to machine it placed the list per machine instead, by its second question. It left to the trial whether any is needed. A need not worth meeting is accepted as a limit, stated with what meeting it would cost (ADR-091 point 4).
- **#3159's change declares a harness requirement** ([COR-047](../../../.pkit/decisions/core/COR-047-harness-requirement-declaration.md)), `ask-reaches-person`: an ask reaches a person who can answer it. Its evidence names the hook's two asks: where a call may hide a guardrail (ADR-025 point 7), and before a file tool writes outside the session's repository, which it rests on ADR-034 point 2 for a write into another repository and on the ruling in #2004 for any other path. The Claude Code adapter answers it as met at a cost: a session keeps a person who answers its asks.
- **The shell is beside the file tools.** An agent refused a file tool's write may reach the same file through the shell. The settings the adapter ships allow `cp`, `mv`, `mkdir` and `echo`, and nothing pkit runs reads where a shell command writes (ADR-025 point 3, ADR-060 point 4). Where the sandbox runs, it confines such a write to its write set. On macOS the `pkit` command itself runs outside the sandbox, which cannot host the `uv` it starts (ADR-027), and those settings allow it with no prompt.
- **pkit already keeps state outside every checkout.** An agent run's clone lies in a folder of pkit's that only the person's account writes, outside every working tree and never in the harness's shared temp folder ([ADR-066](ADR-066-unattended-agent-runner.md) point 7). The CLI reference places that folder in the user's state folder: the state home of the XDG Base Directory specification, `$XDG_STATE_HOME` where it names an absolute path, else `~/.local/state`.

## Decision

**The permission hook asks before a built-in file tool writes outside the session's repository, in every permission mode, except in a folder a person names for that checkout. The names are a list of pkit's own, kept outside every checkout, which a person writes through a pkit command that refuses a tool call, and which only the hook reads, never in a run pkit starts.**

### 1. The hook asks before a built-in file tool writes outside the repository

- **The ask.** The adapter's permission hook asks a person before a built-in file tool writes to an absolute path outside the session's repository. It asks only where the decision core abstained, and never denies.
- **Each built-in file tool that writes a file,** not `Edit` and `Write` alone: each of the harness's own tools that writes a file at a path its call carries, as the adapter's README lists them. A tool outside that list, such as one a later release of the harness adds, or any MCP server's, meets no ask of the hook's. That is a limit the README states, and the list grows as the adapter learns the harness's tools.
- **In every permission mode,** auto and bypass included, where the hook's ask on a hidden guardrail gives way (ADR-025 point 7). It is the one prompt where a write leaves the repository, as #2004 ruled.
- **Its parts.** For a write into another repository it is the catch ADR-034 point 2 allows, which this record widens from `Edit` and `Write` to each built-in file tool that writes a file (Implications). For a write anywhere else outside the repository it is this point's.
- **Its one exception** is a folder named for the session's checkout (point 2).
- **A check, not a wall.** An agent can step around it through the shell, where pkit reads no target, and, while the hook's own files lie in the tree a sandboxed command writes, by changing those files (Context). It checks intent, and confines nothing ([ADR-004](ADR-004-autonomy-intent-confinement.md)).

### 2. A checkout's list names folders where the ask is not put

- **pkit's own list.** A *named folder* is an entry of a list pkit keeps for one checkout: a folder outside the repository where the hook does not ask before a file tool writes. It is no setting of the harness's, and the harness, its sandbox and its modes do not read it.
- **In the user's state folder.** The lists lie in a folder of pkit's in the user's state folder (Context), outside every checkout. The hook counts no list unless pkit's folder and the list's file are each no link, the user's own and writable by no other account, and pkit's folder, resolved, lies in no shared temp folder and, by point 3's walk, in no working tree or git folder. The names of the folder and its files are the build's, and the CLI reference states them.
- **Kept for the folder the anchor names.** The hook reads only the list kept for the folder the session's anchor names: the checkout, or the project's folder where the project is no repository. A list is matched to that folder by its resolved path and by its identity on the file system, its device and inode, so neither a new folder at an old path nor a folder given a removed one's number takes a list. Each working tree of a clone has a list of its own.
- **None by default.** pkit names no folder, so a checkout keeps the ask until one is named for it (point 4).
- **Silent there.** For a target in a named folder the hook has no opinion, as for a target inside the repository. The decision core's verdict stands, and where the core abstains, the harness's own rules and mode decide. The hook never allows a call for lying in a named folder.
- **Never in a run pkit starts.** Where the marker of an agent run is set at all, even empty (ADR-066 point 8), the hook counts no named folder.

### 3. What a named folder covers

- **The target, read as the workspace reads its own.** The hook reads a target as the agent workspace's recogniser does (ADR-060 point 1): each symlink resolved, and an existing file with more than one link never inside.
- **Each entry, read the same way.** The hook resolves each entry of the list as it resolves a target, each time it reads the list, so a link swapped in after the naming changes nothing the tests see. An entry it cannot read as an absolute path counts for nothing.
- **In no repository.** A target counts as inside a named folder only where no folder from the target up to the filesystem's root holds a `.git` entry, or is itself a git folder, as a bare repository is. The hook tells a git folder by hand, as git does, and a test holds that reading to git's answer (point 5). So a write into any working tree or git folder but the session's own checkout asks wherever it lands, as [COR-039](../../../.pkit/decisions/core/COR-039-session-repo-mutation-boundary.md) keeps a change to another repository the operator's to confirm.
- **What the walk cannot see.** A working tree whose git folder lies elsewhere, such as a home folder tracked from a git folder kept apart, shows no sign of a repository the walk can read. Its owner keeps such a tree out of the folders they name. Where the home folder is itself a repository's working tree, the walk finds it, so no folder below it can be named and the need stays unmet on that machine.
- **A place, not the machine.** A named folder that is or holds the home folder, by the `HOME` variable or by the account the system records, or that holds the session's repository or the lists' own folder, counts for nothing. The first two would drop the ask across the machine rather than name a place, and the last would let a file tool rewrite the list unasked.
- **No folder of the shell's path.** A named folder counts for nothing where it is or holds a folder on the `PATH` the hook runs with. A file written there unasked becomes a command a later call may run, and one that runs outside the sandbox where a command the sandbox excludes is found by its name there (point 6). A folder on the path of the session's shell but not on the hook's, the hook cannot see, and its owner keeps it out of the folders they name.

### 4. A person names a folder, never at a tool call, and it is always reported

A named folder lets more run unasked on the intent axis. Where a program outside the sandbox runs or reads what lies in it, the folder opens a way around the sandbox too (point 6), a reduction of confinement in effect (ADR-004). So it is held to the discipline [ADR-008](ADR-008-confinement-allowances.md) point 4 sets for a widening: applied by an explicit gesture, loud, never committed, always reported.

- **The command.** A command of the permission layer's command group names a folder and removes one, for the project root pkit resolves from the folder it runs in ([ADR-001](ADR-001-project-root-resolution.md)). Nothing else of pkit's writes the list, its sync included. It takes its tests and its refusal from the running `pkit`'s own code, never from a file under the root it acts on, as the workspace's removal command does (ADR-060 point 8), and a test holds its tests and the hook's to one table of paths. The command's name and messages are the build's, and the CLI reference states them.
- **Never at a tool call.** The command refuses to name a folder where the harness's mark of a process its shell tools or hooks start is present, even empty (Context). So a person names one at a terminal of their own, and an agent that needs one named says which, for the person to run. Removing a folder only gives the ask back, so it is refused nowhere.
- **What the refusal reaches.** Every process the harness's shell tools and hooks start, and every process those start in turn. It does not reach:
  - a stdio MCP server's processes, which the harness does not mark, and which run outside the sandbox
  - a process started outside that tree, such as by a terminal multiplexer's server or the system's service manager, which runs outside the sandbox
  - a call that drops the mark first. The sandbox holds such a call, and keeps it from the list, except where no sandbox runs, or on macOS through an excluded command that runs others, such as `uv`, where only the permission layer and the rule against composing a command past a check hold it ([backbone:RS-OPS-015])
  - a harness that sets no mark, such as Claude Code before 2.1.172

  What runs outside the sandbox can write the named folders themselves (point 6), so of these only the last opens a route the list adds.
- **Its refusals besides.** A folder that point 3 would not count, one that lies in a repository, one it cannot resolve to an absolute path, and one that holds the program a command the sandbox excludes runs, as the machine resolves it: the link found on the path and its target alike, for each exclusion in the settings the command can read.
- **Loud.** On each naming it says what a write in the folder meets (point 6): a program outside the sandbox that runs or reads a file there, such as an excluded command reading its configuration or the system starting a service, runs what an agent wrote there unasked, so the narrowest folder the work needs is the one to name. Where the folder holds the system's temporary folder, it says too that the harness's scratch directory may lie there, so that an agent's intermediate file written there lands unasked, where the README leans on the ask to catch a write the adapter's sentence did not stop (Context). Where a working folder of the harness's, or a sandbox write grant, that it can read covers pkit's folder of lists, it says that sandboxed commands can then write the list. Run by a setup, the message reaches only the setup's log, so the reports are the check that holds.
- **Reported.** At each session's start, the hook the adapter runs there names each named folder the permission hook will count in that session, read by the same code in the same environment, so the report shows what the permission hook reads even where a terminal's environment names another state folder. pkit's overview of the permission layer lists each folder named for the checkout, and each entry the hook would not count, with why. The sandbox's status says too that the file tools, which run outside the sandbox, write unasked in each, and that a program outside the sandbox that reads there runs what they wrote, so that nobody reads the sandbox's boundary as holding there (ADR-008 point 6).
- **A host's setup uses it.** The setup that prepares a host's machines names the folders that host's guidance writes in through this command, as it uses any of pkit's public surface (ADR-091 point 7): outside any session, in the checkout the host's sessions start in, and with the user's state folder those sessions see. Whatever makes a new checkout names its folders again, so a host that clones for each task names them after each clone.
- **Who accepts it.** Whoever names a folder accepts what point 6 says of it, for that checkout: the machine's owner, or, where a host's setup names it, whoever chose to run that setup on their machines.
- **Other writers.** The lists are files of the user's own, so a person, or code the user runs outside a sandbox, can write them too. That code takes in an agent run in the unconfined form, which only the person's settings hold (ADR-066 point 11), and whose write would count in the person's later sessions. The hook cannot tell who wrote an entry and counts it by the same tests, so the reports are the one check on any writer but the command.

### 5. The hook reads the list, and the decision core stays as it is

- **Beside the ask.** The check lives where the ask does, in the hook. The decision core and its verdicts stay as they are (ADR-034 point 6), so the permission layer's probe, which drives the decision core alone, reports the core's abstain there, as it does wherever the hook asks.
- **Read by hand, and failing closed.** The hook runs without git, so it tells a git folder by hand, as it reads `.git` for the workspace (ADR-060 point 8), and a test holds that reading to git's own answer. Where it cannot resolve the session's folder or read its identity, or cannot read its list or pass point 2's tests on it, it counts no named folder.

### 6. What a write in a named folder meets

- **No ask, and where the harness's rules allow the tool, nothing else.** The harness decides a call its allow rules match by that rule first, in every mode, auto mode's check included, and the adapter's settings allow its main file-writing tools with no path. So under them such a write lands with no person, and in auto mode with no check, unless its path is one the harness guards itself (Context). A file tool those settings do not allow meets the harness's own flow.
- **Outside version control.** It leaves no diff for review and no commit to revert.
- **A way around the sandbox, where a program outside it reads the folder.** The file tools run outside the sandbox. Where another program that runs outside it runs or reads a file in a named folder, such as a command the sandbox excludes reading its configuration, the system starting a service, or a hook running a script, what an agent writes there unasked runs with the person's full access the next time that program runs. Point 3 keeps out the shell's path, and point 4 an excluded command's own program. Each other such folder its owner keeps out, warned on each naming (point 4).
- **The harness's settings do not change.** A named folder is no working folder of the harness's: its reads, its modes and its sandbox's write set treat it as before. Where the harness's block on writes outside the working folders is on, the harness refuses a write in a named folder, unless its owner names the folder as a working folder too, with what a working folder brings.
- **The shell's checks do not change.** The hook reads no shell command's target, and a named folder changes no check a shell command meets. What it changes for the shell is what a program outside the sandbox finds there (above).
- **The requirement binds no write there.** No ask is put in a named folder, so `ask-reaches-person` binds no write in one. It binds every other ask the hook puts.
- **What guards the list, and how far.**
  - It lies outside every checkout and every run's clone, so no commit, archive, template or shared git folder brings one. A run pkit starts counts none (point 2). A working run writes nothing outside its clone but through the hook's ask, which its mode refuses ([ADR-073](ADR-073-builder-runs.md) point 3), and a confined run only through the excluded commands ADR-066 point 11 leaves open, which could write the folders as well.
  - A file tool's write to the list meets the hook's ask, since no named folder may hold it (point 3), and the naming command refuses a tool call (point 4).
  - Whatever else can write the list can write the folders it would name. That is a command outside a sandbox, an excluded one or any where no sandbox runs. And while the hook's own files lie in the tree a sandboxed command writes, so is any command the sandbox confines: through those files it can drop the ask outright, or run code of its own outside the sandbox (Context; #3178).
  - So naming a folder adds no route an agent lacks, and the list guards no more than the ask it narrows: a check an agent can step around, not confinement the operating system enforces (ADR-004). Once the hook's own files leave the shell's reach, no command the sandbox confines can write the list either, wherever no working folder of the harness's or sandbox write grant covers pkit's folder of lists (point 4).

## Rationale

**Why meet the need.** On a machine where nobody answers, the ask does not do what it is for. It is meant to put each write outside the repository before a person. There it is refused in the person's place, and the harness records the refusal as theirs, or it holds a run for up to a day. It blocks the write as a deny would, and says a person refused it.

- **A host's setup can end the stall, but not the need.** It can set the harness to deny a call that would wait on a prompt (Context), a step of its machines by ADR-091's fourth question. The ask is then refused at once, the turn goes on, and the denial says the session has no approval surface rather than that a person refused. Two costs remain, and they are why the need is met.
- **The write does not happen.** The host's guidance asks for it, so the host's step fails in every pkit project.
- **Or it goes to the shell.** An agent that keeps the rule against composing a command to slip a gated mutation past the check ([backbone:RS-OPS-015]) stops there. One that does not reaches the file through the shell, where pkit reads neither the target nor the content, both of which a file tool's call shows. On the trial's host, no sandbox confines that either.
- **The list costs little.** None is named by default, so each machine with a person keeps the ask. pkit takes a folder of its own in the user's state folder, a file for each checkout that names a folder, a command and its reports. The hook reads more only on a file tool's write outside the repository, and each without git: the run's marker, the anchor folder's identity, pkit's folder and the list with point 2's tests on them, point 3's walks, and the `PATH` it runs with. A machine that names a folder takes point 6, a way around the sandbox among it where a program outside the sandbox reads the folder, and gives an agent no route it lacks.

**Where ADR-091's test places it.** Gap 2 holds three needs, and ADR-091 point 4 places each.

- **Whether a write in a given folder asks** differs from machine to machine, and from one checkout to the next, so it is a setting kept on one machine, which the hook reads where it acts: the second question.
- **Naming the folders a host's guidance writes in** is a step its machines need because of how the host prepares them, so it is that host's setup: the fourth question. So is setting the harness to deny what would wait on a person.
- **Every other ask** depends on a person to answer it, which pkit can neither set nor read: the third question, which `ask-reaches-person` answers.
- **Neither of the first question's ways** is right on every machine ("Alternatives considered").

**Why pkit's own list, and not the harness's working folders.** Claude Code's additional working directories look like the setting this needs, and pkit authors no parallel copy of a per-machine key the harness owns, but defers to it ([ADR-032](ADR-032-per-machine-activation-routing-axis.md) Rule B, its defer branch). That branch reaches a key with the value pkit needs, and this key holds a wider one.

- **What a working folder brings.** Named as a working folder, a folder is one the file tools read unasked, `acceptEdits` mode's shell commands change unasked, auto mode approves edits in with no rule, and every sandboxed shell command may write, which the committed settings run unasked (`autoAllowBashIfSandboxed`, ADR-032). That widens confinement, the boundary ADR-004 leaves to the operating system, which ADR-008 point 4 would report as a reduction of it. This record needs less: that the hook not ask.
- **What pkit's own list brings.** Read only by the hook, it drops the hook's ask and changes no setting of the harness's: its reads, its sandbox and its modes treat the folder as before. The way around the sandbox that a program outside it opens in the folder (point 6), a working folder opens too, with every sandboxed command's writes besides. Whether the hook asks is pkit's own state, so ADR-032 Rule B's sidecar branch places it, in a file of pkit's own, which git never tracks, kept where this record refines that branch to keep such state ("Why outside the checkout").
- **No second copy.** The two lists hold different values, so neither copies the other. A machine that wants a folder to be both names it in both, and takes the working folder's reach for the harness's part.
- **The harness's file would move under the hook.** The harness reads its per-machine settings from a file whose place depends on the layout and on its version (Context). Reading the same list, the hook would have to find the same file, and where it found another, the two would drift apart unseen. Which entries the harness counts there turns on whether git tracks that file too, which the hook could learn only by reading git's index by hand.
- **The cost** is that a named folder does not pass the harness's block on writes outside its working folders (point 6).

**Why outside the checkout, in the user's state folder.** A list that drops an ask widens what runs unasked, so it is kept per machine and never committed (ADR-032 Rule A). Committed, one repository would name folders, `~/.ssh` among them, for every clone, which is why a workspace folder may never be absolute or under `~` (ADR-060 point 2).

- **Not in the checkout.** A file in the tree, even one git ignores, a repository can commit, and so name folders for every clone. A file in the git folder, a git template or a repository shared with a group can bring or write. A run's clone holds both.
- **Out of the sandbox's reach, once the hook's own files are.** A sandboxed command writes its working folder, the git folder in it all but its hooks and its configuration, and from a linked worktree the main repository's shared git folder (Context), and the committed settings run such a command unasked (`autoAllowBashIfSandboxed`, ADR-032). So any such command could write a list in the checkout. While the hook's own files lie in the same reach, that route drops the ask with no list at all (#3178), so it tells no home from another. Once they leave it, the user's state folder keeps the list out of the shell's reach, and a home in the checkout would not.
- **Not in a run's clone.** A builder's run writes its clone, git folder included (ADR-073 point 3), and only the hook's ask, which its mode refuses, keeps its file tools there. A list in the clone would let the run widen its own rules, which ADR-073 point 2 rules out.
- **In the user's state folder.** No commit, archive, copied checkout or git template brings a file there, and no run's clone holds one. Point 2's tests keep out another account, a link and a shared temp folder, and no sandbox's default write set reaches it. pkit already keeps an agent run's clones there (Context), so it adds no new kind of place.
- **What reaches it all the same.** A working folder of the harness's, or a sandbox write grant, that covers the user's state folder opens it to sandboxed commands, and the hook cannot read every store the harness takes either from ("Why pkit's own list"). The command and the reports say so where they can read it (point 4), and keeping that folder out of both is the owner's, which the README says.
- **The active profile stays where it is,** in a file of the tree that git ignores (ADR-032 Rule B). A profile chooses among grants the project's committed configuration ships, and that configuration may name the profile itself, so a copy a commit brings grants nothing a commit could not. A named folder is any path on the machine. A sandboxed command can rewrite the profile's file, as it can the code and model that read it, so moving the profile alone would close nothing: it moves, if at all, with them (#3178).

**Why kept for the folder the anchor names, by its identity.** The harness sets the anchor when the session starts and hands it to the hook, and no command the session runs moves it there (ADR-034 point 1). Keyed to it, the list a session meets turns on nothing an agent can write. Matched by the folder's identity as well as its path, a person's word stays with the checkout they gave it for: a checkout made again at the same path, which may hold another project, starts with none, and a command the sandbox confines cannot replace the folder it works in. The layouts:

- **A session at a checkout's root, or a subagent in a worktree,** whose anchor stays at the checkout the session started in: that checkout's list.
- **A session started in a linked worktree:** that worktree's own list.
- **A pkit project with no repository:** its folder's list, as for a checkout, since the hook's ask needs no repository either.
- **A session started below the repository's root:** the project's shared settings, where pkit registers its hook, do not load (Context), so neither the ask nor the list reaches it. Moved to the root with `/cd`, it takes the root's hooks, but the command the adapter registers is found from the folder it started in, where pkit's hook does not lie, so no permission hook runs. That gap is the hook's own (#3180), and this record does not change it.
- **A session moved with `/cd` into a folder whose settings register no pkit hook,** a subfolder of its own checkout among them: no permission hook runs there, so neither the ask nor the list reaches it. That gap too is the hook's own (#3180).
- **A session moved with `/cd` into another pkit checkout:** the hook that runs is the starting checkout's, anchored there, so that checkout's list counts, and a write into the checkout it moved to is a write into another repository, which asks (point 3).
- **A run pkit starts:** no named folder (point 2).
- **Its costs.** A person with several worktrees names a folder in each. A checkout moved, made again or restored from a copy loses its list, which gives the ask back, and the reports show it. Turning the permission hook off leaves the list, unread until the hook is on again. A deleted checkout leaves a list that matches no folder and counts for nothing, until the command removes it.

**Why the naming command refuses a tool call.**

- **The route it closes.** On macOS `pkit` runs outside the sandbox (ADR-027), and the settings the adapter ships allow it with no prompt, so a naming command open to a tool call would be a confined agent's route to the list. Refused at a tool call, it is closed in every mode and every layout, whatever settings load, for every process the harness's shell tools and hooks start (point 4). While the hook's own files lie in the shell's reach, an agent has a way around the ask without it (#3178), and the refusal keeps the list from becoming one more.
- **Why that mark.** The harness sets it only in what its shell tools and hooks start, and no editor sets it, so a person at an editor's terminal names a folder as at any other. The other mark, `CLAUDECODE`, would reach a stdio MCP server's processes too and names no release, but an editor's extension sets it in the editor's terminals, so every person who works there would be refused, and what it adds, an MCP server, already runs outside the sandbox (point 4). The mark is read for presence, even empty, as ADR-066 point 8 reads the run's.
- **The harness's own value.** The mark is the harness's, read under the adapter's label as ADR-091 point 5 reads one, never a host's. A harness that sets none, such as Claude Code before 2.1.172, leaves the command open to a tool call, a limit the README states.
- **Why a mark, not a terminal.** The drift command tests for a terminal before it starts unconfined runs (ADR-066 point 11). A host's setup that names folders has no terminal, and an agent can fake one, as that point says.
- **The cost.** A person in a session names a folder at a terminal of their own, not by approving the agent's call. A terminal that inherits the mark refuses too, such as a `screen` session first started from the harness's shell.

**Why a run never counts a named folder.** A run pkit starts is unattended (ADR-066), and its work stays in its own folder. A review's run works in the person's own checkout (ADR-066 point 10), where that checkout's list would reach it, and another run may start at a path a list was kept for. The run's marker is pkit's own value, so pkit may read it (ADR-091 point 2). Reading it keeps each write a run makes outside its folder before the ask, wherever the run starts, and keeps a builder's file tools in its clone, as ADR-073 point 2 keeps what a builder writes from shaping its run.

**Why a write into a repository asks wherever it lands.** A checkout's list names places for that checkout's work. A write into another working tree or git folder changes a project whose own rules the session has not loaded, which COR-039 keeps the operator's to confirm, change by change. The workspace's test for a nested repository keeps it out the same way (ADR-060 point 3).

**Why the line stops at the home folder and the shell's path.** The test refuses a folder that names the machine rather than a place, since naming one would drop the ask everywhere, and a folder of the shell's path, whose files a later call may run. Which place below the home folder is safe to write unasked, `~/.config` or `~/.ssh`, differs from one machine to the next, and so does which program outside the sandbox reads which folder. No list of pkit's could judge that for every machine. So that judgment is the owner's, and the command says on each naming what a write there meets (point 4).

**Why the hook, and not the decision core.** The ask is the hook's, outside the core (ADR-034 point 6), so its exception lives beside it. The core is harness-neutral code that the hook and the permission layer's commands both run ([ADR-003](ADR-003-permission-core-code-home.md)), and the ask it would except is one adapter's.

**Why silent, and not an allow.** The need is only that the hook not ask. An allow from the hook would pass over the harness's own rules and mode for every write in the folder. Silent, the hook treats a named folder as it treats the repository, and the harness's protected paths, its deny rules and its mode stay in force.

### Alternatives considered

- **Keep the ask everywhere, and state its effect as a limit** (ADR-091 point 4). Not taken.
  - *Its case:* no list, no command and no new input for the hook. Every write outside the repository through a file tool goes on meeting a person, or not happening. A host's setup can set the harness to deny what would wait on a person, which ends the stall, and the refusal recorded as the person's, on that host's machines (Context).
  - *Its cost,* on every machine where nobody answers, with that setting or without it: the write the host's guidance asks for never happens through a file tool, and an agent may take it to the shell, where pkit reads no target.
  - *The limit would read:* a session with nobody to answer its asks writes outside its repository through a file tool only on a person's word.
  - *Meeting it costs* what points 2 to 6 build: a folder of pkit's in the user's state folder with a file for each checkout that names a folder, a command and its reports, more reads in the hook, and, on the machines that name a folder, writes there that meet no person, and in auto mode no check, with a way around the sandbox wherever a program outside it reads that folder. It gives an agent no route it lacks.
- **The harness's working folders,** read by the hook from the harness's per-machine settings file while git tracks no file there. Not taken.
  - *Its case:* one setting that the harness and the hook both read, kept in a file pkit already writes, and which passes the harness's block on writes outside the working folders.
  - *Its cost:* each named folder also widens confinement, and changes what the file tools read and `acceptEdits` mode's shell commands change unasked. The hook must find the file the harness reads, whose place changes with the layout and the harness's version, and read git's index by hand to tell whether git tracks it. And the harness takes working folders from stores the hook would not read, so the two would not hold one list anyway ("Why pkit's own list").
- **Defer to the harness's block on writes outside the working folders.** Where the block is on, the hook drops its ask outside the repository, keeps point 3's ask for a write into a repository, and the harness refuses each file tool's write outside its working folders, in every mode. Not taken.
  - *Its case:* pkit keeps no list. The harness reads every store, follows worktrees itself, and already refuses a folder that only a file a repository could bring names.
  - *Its cost:* the hook cannot read whether the block holds. A `true` in any file the session loads turns it on, managed settings and the command line among them, which the hook does not see, and a harness before 2.1.314 ignores it, while the hook cannot read the harness's version. Where the hook read a `true` that does not hold, a write outside the repository would land with no person and no check, on the very machines whose owner asked for a block. So the hook would rest on harness behaviour it cannot check. The folders the block lets through are working folders, with all they bring, and the block removes the harness's worktree tools. It stays open to any machine as a setting of the harness's own (point 6).
  - *Why the naming command may rest on the harness's mark where this may not rest on the block:* the hook cannot check either, but a misread costs less there. A harness that sets no mark leaves the naming command open to a tool call, a route to the list that matters only to an agent with no other way around the ask. A block wrongly read as on drops every ask outside the repository.
- **Ask only where the target lies in another repository,** a change right on every machine (ADR-091's first way), and the investigation's leaning before the trial. Rejected: every machine, a laptop with a person at it included, would lose the ask on every other write outside the repository, such as one to `~/.ssh/authorized_keys`, `~/.config/systemd/user`, `~/Library/LaunchAgents` or `~/.local/bin`. None of those is a protected path, so under the settings the adapter ships the harness lets such a write land unasked in every mode, and in auto mode nothing checks it (Context). A list kept per machine meets the host's need and costs a machine with a person nothing, which the narrower ask does not.
- **A list the project commits,** whose default serves every machine (ADR-091's second way). Rejected: a repository would name folders for every clone (ADR-060 point 2), and the folders a host's guidance writes in are that host's, not the project's.
- **pkit's own list in the clone's git folder,** where git tracks nothing. Not taken.
  - *Its case:* no commit, branch or checkout brings it, the hook already reads the git folder for the workspace (ADR-060 point 8), and every worktree of a clone shares one list.
  - *Its cost:* a git template or a repository shared with a group could bring or write a list, and a builder's run writes its own clone's git folder. A sandboxed command writes the git folder too, all but its hooks and its configuration, and from a linked worktree the main repository's shared one (Context), which the committed settings run unasked. The hook's own files share that last route for now (#3178), but once they leave the shell's reach, a list there would stay in it, two steps with no ask: name a folder, then write in it.
- **pkit's own list in the tree, in a file git ignores,** as pkit keeps the active profile (ADR-032 Rule B). Not taken: a repository can commit a file the tree ignores, and so name folders for every clone; a run's clone holds it; and it stays in the sandbox's reach, as a list in the git folder would.
- **Kept in the user's state folder but keyed to the clone's git folder,** so a person names a folder once for every worktree of a clone. Not taken: the hook would find the git folder through pointer files a sandboxed command can rewrite, from a linked worktree in the shared git folder itself, and so point a session at another clone's list. That harm stops at the lists a person named for their own checkouts, but it lets a command the sandbox confines choose which list counts. Naming a folder in each worktree costs only a person who works in several and names folders, and the need, a host's, which clones for each task, asks for no list shared across worktrees.
- **Keyed to the anchor's path alone.** Not taken: a checkout made again at the same path, which may hold another project, would take the folders named for the one before it, so a person's word would attach to a path, not to the checkout they gave it for.
- **One list for the user, for every project.** Not taken: a folder named for one project's sessions would drop the ask in every other project on the machine, unseen in that project's own state.
- **An ask rule on the naming command,** shipped in the adapter's settings, in place of the refusal or beside it. Not taken.
  - *Its case:* the harness's own rule, which prompts in every mode, bypass included, over a hook's allow and for a sandboxed command, and applies from the project's settings before the folder is trusted (Context). A person could approve an agent's call at a prompt that shows the folder, and under a harness that sets no mark it would still ask.
  - *Its cost, in place of the refusal:* it loads only with the project's shared settings, so a session that loads none, such as one started below the root, meets no ask. It matches a call's text, so a call through another shell or by the program's full path escapes it, where the refusal reads a mark every process of the call inherits.
  - *Its cost, beside the refusal:* under every release that sets the mark, the person approves a call the command then refuses. Under one that sets none it covers only a call written as its text, while a call that drops the mark, which the refusal misses, escapes the rule's text too.
- **Refuse on `CLAUDECODE` as well,** the mark that reaches a stdio MCP server's processes and names no release. Not taken: an MCP server already runs outside the sandbox, so its refusal closes no route, and every person at an editor's terminal, where an editor's extension sets that mark, would be refused ("Why the naming command refuses a tool call").
- **Refuse every folder that holds what a program outside the sandbox reads.** Not taken: which folders those are turns on each program and each machine, and no list of pkit's could name them for every machine. The shell's path and an excluded command's own program are the part pkit can tell (points 3 and 4), and the naming message names the rest.
- **The overview alone as the report.** Not taken: it runs in the terminal's environment, which may name another state folder than the harness's, so it could show a list the hook does not read, or miss one it does. The hook the adapter runs at each session's start reads the list as the permission hook does (point 4).
- **No test of the run's marker,** the list's place alone keeping runs from it. Not taken: no run's clone holds a list, but a review's run works in the person's own checkout, whose list would reach it, and a run may start at a path a list was kept for ("Why a run never counts a named folder").
- **The host answers the ask,** through a `PermissionRequest` hook, which the harness still asks where it denies in place of a prompt, or through an approval policy of its own (ADR-091's fourth question). Rejected: a host's answer can allow a write in the person's place, and the harness records the answer as the person's, so the ask would say a person approved what nobody saw. The requirement could not tell either, since until the harness says who answered, even a pass resolves `ask-reaches-person` indeterminate. A deny where nobody answers fails closed, and a named folder puts no ask at all, and is reported as named.
- **The decision core's path recogniser** (ADR-060 point 1). Rejected: its folders lie at a checkout's root, never absolute and never under `~` (ADR-060 point 2), it grants an allow where the need is only to drop an ask, and the core is harness-neutral, where the ask is one adapter's.
- **Drop the ask in auto and bypass mode,** as the hook drops its ask on a hidden guardrail. Rejected: under the settings the adapter ships, auto mode's check sees a write outside the repository only on a protected path (Context), so every other such write would meet nothing in auto mode, on every machine.
- **Deny where nobody answers,** in place of the ask. Rejected: the hook cannot read whether anyone answers (ADR-091 point 6), and a deny ends the stall and leaves the write undone. A host that wants that sets the harness to deny what would wait on a person, which reaches every ask.
- **An allow in a named folder,** in place of silence. Rejected: an allow from the hook would pass over the harness's own rules and mode for every write in the folder ("Why silent, and not an allow").

## Implications

- **ADR-091, refined in place.** Its Implications' bullet on gap 2 reads:

  > **Writes outside the repository** (gap 2) hold three needs (refinement per ADR-093). A person may name, for one checkout, folders outside the repository where a file tool's write does not ask, a setting kept on one machine, which the permission hook reads where it acts, by the second question. No folder is named by default. Naming the folders a host's guidance writes in is that host's setup (point 7). Every other ask depends on a person to answer it, by the third question, which the requirement that an ask reaches a person states. The trial on a live host (#3004) showed the need: the ask was refused in a person's place, or held a run until someone answered it.

  Its bullet on rubs 16 and 15 then reads as follows, so that the record nowhere says the trial is still to run:

  > **A bridge's own file tools** (rub 16) fall to the third question by point 3, if the trial on a live host (#3004) showed the bridge putting them in place of the harness's. Whether an allow in the project's settings passes over the check the harness makes in its automatic mode (rub 15) is placed on what that trial showed. A follow-up weighs the trial's answers and settles both (#3006).

  The edit changes the tense and names where the placing goes. This record places neither rub: rub 16 keeps the placement ADR-091 gave it, and rub 15 stays to be placed.

- **ADR-034, refined in place.** Its catch widens from `Edit` and `Write` to each built-in file tool that writes a file, since each carries its target's path in its call, the property ADR-034 gives as the reason for the catch. Its point 2 reads:

  > The PreToolUse hook MAY **prompt** on a call of a built-in file tool that writes a file, such as `Edit` or `Write`, whose `tool_input` carries an absolute path under a foreign repo (refinement per ADR-093). Such a tool carries the literal target path in its tool input (unlike a bash command, whose target is buried in argv the dumb segmenter does not parse — [ADR-025](ADR-025-segment-conservative-bash-allow.md)), so this one surface is honestly inspectable. It is a small catch covering only the file tools' surface; it does **not** cover bash / `uv` / `gh`, so it is explicitly **not** the lever — the self-guard (point 1) is. Naming it as a corner, not a wall, keeps the honesty discipline intact.

  Its other mentions of the catch change word for word:

  - its Summary's line of the decision: "(an Edit/Write to an absolute foreign path may prompt)" becomes "(a file tool's write to an absolute foreign path may prompt)";
  - its Decision's top line: "one honest Edit/Write catch" becomes "one honest catch on the file tools that write a file";
  - its point 6's second sentence reads "The only hook change is the additive foreign-path prompt on the file tools that write a file (point 2); the self-guard (point 1) lives in the mutating program, not the decision core.";
  - its first alternative: "(Edit/Write absolute foreign path, point 2)" becomes "(a file tool's write to an absolute foreign path, point 2)";

  - its bullet on other harnesses: "The Edit/Write hook corner" becomes "The file tools' hook corner";

Its sentence on what the implementing issue lands keeps "the hook's Edit/Write prompt", since that is what the issue lands, and gains after it "The build that follows ADR-093 widens that prompt to the other built-in file tools that write a file (refinement per ADR-093)."

  What the catch is stays as it was: a prompt on tools that carry their target's path, never the lever.
- **ADR-032, refined in place.** Its Rule B's sidecar branch gains a second home, outside the checkout, for one kind of pkit's state, and each sentence that names that branch's home says so:

  - The branch's lead reads "**pkit-owned state (the sidecar branch) → a per-machine file pkit authors, which git never tracks.**"
  - The branch keeps its sentence, and gains this one after it:
