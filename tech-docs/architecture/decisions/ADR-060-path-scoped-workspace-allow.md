## Summary

Agents need one place for their intermediate files where writing never makes the operator confirm anything, so the permission catalog gains a new kind of privilege — a *path-scoped allow*, recognised only when a file tool's target lies inside a named folder — and every shipped profile grants the agent workspace, `.agent-workspace/` at each checkout's root, to every agent. It reduces prompts on the allow side and confines nothing. A shell command writing into the folder is judged exactly as any other shell write; for the file tools, which the OS sandbox does not wrap, this allow *is* the gate inside the folder — so the folder counts only as the checkout itself holds it: never through a symlink, never from an absolute or climbing catalog entry, never in another repository or in one nested inside it. Files leave the folder through a backbone command, `pkit workspace remove`, which tests each path itself once the shell has expanded it, and removes nothing unless every path lies inside the folder and is neither a capability's lasting state nor a nested checkout. It is a `pkit` command like any other: the workspace privilege covers it no more than any other shell command. This is a refinement child of [ADR-004](ADR-004-autonomy-intent-confinement.md) and refines [ADR-005](ADR-005-permission-profile-surface.md)'s shipped-profile table; [ADR-025](ADR-025-segment-conservative-bash-allow.md) stands unchanged.

## Context

Issue #1043 recorded the cost: an agent keeps intermediate files somewhere — pull-request and issue bodies, scripts, captured output — and every write outside the working directory asks the operator, one file at a time, for the whole session, until the operator approves harmless confirmations without reading them. That is the confirmation fatigue the permission model exists to prevent ([COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md)). The harness's own per-session scratch directory did not help: it lies outside a subagent's working directory, and absolute allow rules written for it did not stop the prompts. The answer the issue settled on is one git-excluded folder per checkout that the permission model grants to every agent; the backbone declares and creates it (a rule in `rules/core.md`, `pkit init` / `sync` / `status`), the backbone's permission code grants it, and each adapter translates the grant.

Granting it needed something the catalog did not have. Privileges were recognised by the tool named (`recognize.tool`) or by the command's leading words (`recognize.bash`), and a grant's `directory` scope matches the request's *cwd* — and a scoped allow **denies** the privilege outside its scope. A `Write` / `Edit` grant scoped to the folder would therefore have denied every write elsewhere. The workspace needs the opposite: a privilege that exists only inside the folder and has no opinion outside it.

The first implementation also recognised shell writes into the folder — an `echo` / `printf` / `cat` redirected into it, a literal here-document, `rm` of files in it — and let such a write through [ADR-025](ADR-025-segment-conservative-bash-allow.md)'s leading-`cd` strip. Review proved that unsound (see Rationale), and the file tools already do the writing with the target in plain sight. They remove nothing, though: `rm` of a file is judged like any other shell command, and recursive `rm` is denied everywhere, so an agent could not clear what it kept there (#2360). The maintainer chose a backbone command that tests its own paths over any exception for `rm`. The folder is also shared: every agent working in the checkout writes there, and the project-management capability keeps its drift queue in it ([DEC-056](../../../.pkit/capabilities/project-management/decisions/DEC-056-drift-fixers.md) point 6). This record fixes the shape that remains.

As project-kit's own architecture record, harness specifics are in scope. It was accepted, as a child of foundational ADR-004, before the change it records merged, after the architect's review.

## Decision

**The catalog gains a path-scoped allow: a privilege recognised only for a listed file tool whose resolved target lies inside one of its folders at a checkout root. The agent workspace is its shipped instance, granted to every agent by every shipped profile, realised by the hook and never as a settings rule. Shell commands are out of it entirely: ADR-025 stands unchanged. Files leave the folder through a backbone command that tests each path after the shell has expanded it.**

### 1. Recognition from the target path, for the file tools only

A privilege may carry `recognize.path: {folders, tools}`. It is recognised for a request only when the request's tool is one of `tools` and the path the tool names — resolved against the request's working directory, symlinks resolved — lies strictly inside one of `folders`. It is never recognised for the tool alone, and never for a shell command. Outside its folders it has no opinion: a request there is decided exactly as without it. An existing file with more than one link is not recognised: a hard link planted in the folder would carry a write to its other name. The workspace lists `Read`, `Write`, `Edit`, `MultiEdit` and `NotebookEdit`.

### 2. The folder is the checkout's own

A folder is named relative to a checkout root, never absolute, never starting with `~`, never climbing out with `..`; the recogniser ignores any other entry, so a capability's catalog fragment ([ADR-021](ADR-021-capability-contributed-privilege-definitions.md)) cannot declare `/` or the directory above the project. The folder counts only when it is reached through no symlink — resolving `<resolved checkout>/<folder>` must change nothing — so a symlinked `.agent-workspace` is never the workspace. The shipped folder is a direct child of the checkout root.

### 3. Which checkouts count

The project root, and another working tree of the same repository: the main one, whose `.git` is the common git directory, or a linked worktree that git registered there — its `.git` pointer names `<common>/worktrees/<id>` and that entry points back at it. A planted `.git` pointer does not make a worktree, and another repository's workspace never counts (the cross-repository rule, `rules/core.md` rule 19). Nor does a repository or worktree nested inside the folder: when any directory from the folder down to the target holds a `.git` entry, the target is not in the workspace.

### 4. No Bash exception

ADR-025 stands unchanged. A shell write into the workspace fails closed like any other: after a stripped leading `cd`, a redirect into the folder or any other untrusted construct in the remainder abstains (ADR-025 point 2); without a `cd`, the command is decided on its own grants, and nothing about the folder grants it. An `rm` of a file there is decided the same way. So is point 10's removal command: nothing about the folder grants it, and it is decided as any `pkit` command is.

### 10. Removal through a backbone command that tests its own paths

`pkit workspace remove <path>...` removes each file or folder it is given, a folder with everything in it. It reads each path as the program receives it, once the shell has expanded it, taken against the directory it runs in. It tests every path before it removes any, and one refused path refuses the whole call: nothing is removed, and the command names each refused path and why.

- **Its root, and the session's repository.** It acts on the checkout `pkit` resolves as the project root from the directory it runs in ([ADR-001](ADR-001-project-root-resolution.md)), never on a root read from `CLAUDE_PROJECT_DIR` or any other variable the command line can set. Like the methodology's other commands that change state, it first runs the cross-repository guard: the session's anchor is the guard's comparand, never a root input ([ADR-034](ADR-034-foreign-repo-mutation-guard.md) point 1). A root in another repository than the anchor's is refused, or asked about at a terminal (ADR-034 point 4). The command takes no confirmation passed with the call, since a file name a pathname pattern expands to could carry one. Where the harness names no anchor, there is no session to compare with, and the guard does not fire ([ADR-061](ADR-061-hosting-service-acts-in-the-backbone.md) point 6).
- **Inside, as points 2 and 3 read it.** A path is inside only where the recogniser would place it: in the `.agent-workspace` of a checkout point 3 counts, as that checkout itself holds the folder, with no repository or worktree nested between the folder and the path. Another repository's workspace never counts. It removes only in the agent workspace, never in another folder a catalog entry lists.
- **The place a removal changes.** A write changes the file its target resolves to, so point 1 resolves every symlink. A removal changes an entry of a folder, so the command resolves the path's parent and takes its last part as written, any trailing slash dropped: a symlink it is given is removed as a link, never followed, and a last part of `.` or `..` is refused. A file with more than one link is removed like any other: removing one name leaves the file unchanged at its others, so point 1's exclusion guards writes only.
- **What it refuses besides:**
  - **The folder itself,** which nothing would replace until the next `pkit sync`.
  - **A capability's lasting state.** The folder is the checkout's, shared by every agent working in it, and some of what it holds must last, such as the drift queue that waits there for the person (DEC-056 point 6). A capability that keeps lasting state in the folder keeps it under a direct child named after itself. The command refuses any path at or under a child named after a capability the manifest registers, in the checkout the command runs in or in the one holding the path; a name read from either can only refuse more. So a pattern over the whole folder is refused wherever such a child stands, and an agent removes what it names.
  - **A nested checkout:** any path whose folder, or a folder below it, holds a `.git` entry, a repository or worktree that may hold work no commit has saved. The command walks the whole of each folder it would remove for such an entry before it removes anything. A worktree git registered is removed with `git worktree remove`, without `--force`, which is decided on its own grants. Git then removes only a worktree whose tracked files are unchanged and which holds no untracked file, and what it ignores goes with it. A repository made by `git init` or `git clone`, or a worktree git no longer knows, is the operator's to remove by hand.
- **A removal no swap can redirect.** The command opens the workspace folder that holds a path once, through no symlink. From that handle it reaches each part of the path's resolved parent without following a symlink, and removes with calls relative to the folder it reached, never by a path's name. Inside a folder it removes, a link is removed, never what it points at. On the way down, a part that has turned into a link since the test stops that path, which is reported as not removed. "Nothing is removed" holds for a refusal the tests find. An I/O error partway through can leave a removal partial, and the command reports what it removed.
- **Missing paths, and the exit status.** A path that would lie inside the folder but names nothing is reported and refuses nothing, so the same removal run again succeeds. A missing path outside the folder is refused like any outside path. A pathname pattern that matched nothing never reaches the command under zsh, whose `nomatch` stops the line; bash passes it on as written, a path that names nothing. The command exits `0` when every path it was given is gone, `1` when it refused the call or left a removal partial, and `2` on a usage error.
- **No option widens it.** A file whose name reads as an option, reached through a pathname pattern, can change how the command reports, narrow the call or stop it, and nothing more.
- **A `pkit` command like any other.** The permission model decides it as it decides every `pkit` command: the `kit` privilege recognises it, so it runs with no prompt wherever a profile grants that privilege, as `non-destructive` and `autonomous` do, and `read-only`'s strict posture denies it, as it denies every `pkit` command. The workspace privilege does not cover it (point 4). [ADR-025](ADR-025-segment-conservative-bash-allow.md) reads it as written: a leading `cd` is stripped, and an untrusted construct anywhere in the call, such as `$(`, a backtick or zsh's `=(…)`, keeps the grant from allowing it. A pathname pattern is matched as written, and the command tests what it expands to.
- **It confines nothing.** `pkit` may run outside the OS sandbox, as it does on macOS where the installed `uv` needs it ([ADR-014](ADR-014-macos-sandbox-platform-stance.md) point 2). There, as for the file tools (point 6), the command's own tests are all that keep a removal inside the folder.

### 5. Granted to `all` by every shipped profile

**Granted to `all` by every shipped profile**, `read-only` included — the folder is excluded from version control and holds nothing a commit can carry. ADR-005's shipped-profile table lists it (its point 5).

### 6. Realised by the hook, never as a settings rule

The projection reports a path-scoped grant as `runtime`: a session-wide `Write` or `Edit` rule would reach far beyond the folder. The Claude Code adapter emits no rule, because inside its working directory the harness already approves reads, accepted edits and sandboxed commands; an adapter whose harness does not would emit the narrowest path-scoped rule its harness offers. In a confined agent run, where the harness approves no write by itself, the Claude Code adapter emits such a rule for the run's workspace (refinement per [ADR-066](ADR-066-unattended-agent-runner.md)). The adapter's enforcement declaration names the dimension `path-scoped-allow` (hook, runtime) — explicitly **not** a confinement boundary: it only removes prompts. Shell reach is `filesystem-confinement`, the sandbox's ([ADR-004](ADR-004-autonomy-intent-confinement.md)); the file tools run outside the sandbox, so inside the folder the recogniser's precision (points 1–3) is what separates an allow from the rest of the disk.

### 7. A prompt there is a defect

Every agent is granted the workspace, so the diagnostic loop tags a deferred file-tool request whose target the recogniser places in the folder and reports it in its own DEFECTS band, ahead of every recommendation — never as an allowlist gap to tune around.

### 8. Code home, and one reading of `.git`

The recogniser lives in the shared decision core, `.pkit/permissions/decide.py` ([ADR-003](ADR-003-permission-core-code-home.md)'s same-code invariant). It enters through the tool branches only — `recognized_privileges` adds the path-scoped hits to a tool request's, and `hook_decide` passes the file tool's target and the project root; `decide()` itself is unchanged. The hook runs in-box without git ([ADR-014](ADR-014-macos-sandbox-platform-stance.md)), so it reads `.git` by hand; the backbone's answer from git itself is held to that reading by a conformance test. The removal command (point 10) takes its tests of what lies inside from the running `pkit`'s own code, never loaded from a file under the root it acts on, unlike `pkit permissions`, which loads the project's `decide.py`: a branch or another checkout may hold that file changed. A test holds the command's tests and the recogniser to one table of paths, so the two never disagree about the folder.

### 9. Excluded per clone; the committed ignore line is recommended, never written

`pkit init` and `pkit sync` exclude the folder in the common git directory's `info/exclude` — one entry for every worktree of the clone — and refuse a symlink in the folder's place. The project's committed `.gitignore` is the adopter's file, which the backbone never writes ([ADR-009](ADR-009-git-footprint-visibility.md)), so `init` recommends the line that covers every clone. Until a clone runs `init` or `sync`, or the project commits that line, the committed hook already grants a folder git does not yet ignore — the `git add -A` exposure ADR-009 closed for `.pkit/`; `pkit status` reports it. This is the fresh decision ADR-009's rule 7 requires for a runtime-local artifact outside `.pkit/`.

## Rationale

**Why a recogniser, not a grant scope.** A scope narrows where a privilege is *allowed* and denies it elsewhere — right for `docker` limited to a directory, wrong for a folder that should add an allow without taking any away. Putting the folder into recognition makes the privilege simply absent outside it, so a grant can neither reach nor deny a file elsewhere, and every other reader of the catalog (the settings projection, rule attribution) — which reads only `tool` and `bash` — cannot mistake it for a session-wide tool allow.

**Why the target path, not the working directory.** The working directory says nothing about where a file tool writes; an absolute `file_path` lands wherever it names. The file tools carry their target in plain sight, which is what makes them honestly inspectable ([ADR-034](ADR-034-foreign-repo-mutation-guard.md) relies on the same property for its cross-repository check).

**Why no shell recogniser.** A shell expands a command's words before it runs them, and the decision core's dumb splitter cannot see what they expand to — by design, since hosting a shell parser in the hook was rejected on altitude grounds (ADR-025 point 3). Review proved each attempt to read a shell write as "only a file in the folder" wrong:

- zsh process substitution, `echo =(touch PWNED) > .agent-workspace/x`, runs a command inside an emitter's argument with no `$(` on the line;
- zsh's `(e)` parameter flag and bash 5's `${…@P}` prompt expansion evaluate an escaped substitution at expansion time, again with no literal `$(`;
- `cd .agent-workspace/nope; rm -f *` read `*` relative to the `cd` directory, but when the `cd` fails, `;` runs `rm` in the original directory and empties the project root;
- and the architect's review found four more holes in the here-document reading.

Each is the composition problem ADR-025 names when it rejects the all-segments-safe widening as unsound; a blocklist, then an allowlist, of shell syntax only moves the boundary. The file tools do the same work with nothing to expand, and `rules/core.md` rule 15 already prefers the harness's dedicated tools over ad-hoc shell.

**Why removal is a command, and sound where `rm` was not.** The hook reads a command's text before the shell expands it, which is why no reading of `rm` into the folder holds. A program reads its arguments after expansion, as the paths it will act on, from the directory it runs in. Point 10 moves the test there, where the composition problem does not arise: whatever the shell made of the words, the command tests the result, and removes nothing unless every path lies inside. In the example above, `cd .agent-workspace/nope; pkit workspace remove *` expands `*` in the project root when the `cd` fails; every path then lies outside, and nothing is removed. Testing once is not enough where a folder can be swapped for a link between the test and the removal, so the removal walks from a handle on the folder and follows no link. The guardrail floor stays whole: recursive `rm` is denied everywhere, and the one recursive removal the backbone offers is bounded by its own code to the folder.

**Why the command takes no grant of its own.** A grant on a command's leading words allows whatever code those words reach, and for `pkit` they do not fix it. The router runs a source checkout's own dispatcher wherever the directory lies in one, and a pinned version wherever the project pins one ([ADR-039](ADR-039-pkit-entry-point-router.md)); ADR-025's leading-`cd` strip lets a `cd` before the command pick that directory. `read-only` grants nothing that runs code nobody vetted, so it allows no `pkit` command, this one included. Where `kit` is granted, it already allows every `pkit` command, so the command needs nothing more.

**Why the root is resolved as every command's is.** The tests trust the folder at the root. A root read from a variable would move with whatever the command line sets, which is why ADR-034 point 1 keeps the session's anchor a comparand and never a root input. As a comparand, the anchor catches the one handoff the tests cannot see: a `cd` into another repository, whose own workspace they would accept.

**Why lasting state is refused by name.** The folder is shared, and what one agent sees there it did not necessarily write. Some of it must outlast the session that wrote it: the drift queue keeps proposals, and the refusals the person gave, until each is decided (DEC-056 point 6). A command cannot tell lasting state from scratch by what a file holds. A name can: the queue already lies under its capability's name, so one convention marks lasting state and the manifest says which names are capabilities'. Refusing is the safe error, since a file left behind lies in a folder no commit carries. Core rule 16 asks agents to remove only what they wrote.

**Why a nested checkout is refused, not removed.** A worktree or clone in the folder may hold work no commit has saved, and removing a registered worktree's folder leaves git's record of it behind. For a registered worktree, `git worktree remove` without `--force` checks its tracked and untracked files and clears that record, though what git ignores goes unchecked; the command leaves that judgment to git rather than repeat it. For a clone, or a worktree git no longer knows, no command knows what it holds, so the operator decides.

**Why "the checkout's own" folder.** A hostile repository can commit `.agent-workspace` as a symlink to the home directory; if the grant followed it, every agent could write anywhere under it. A capability fragment declaring `/` or `..` would do the same from the catalog side. Refusing any folder not literally inside the resolved checkout closes both, and the registered-worktree check keeps a planted `.git` pointer from extending the grant to a directory git never made a worktree.

**Why every shipped profile, `read-only` included.** The workspace grant carries no repository change: the folder is excluded from version control, and the read-only tier's intent — nothing an agent does reaches the repository — is unchanged by it. Leaving it out would bring back, under the strictest profile, exactly the prompts #1043 removes.

**Why `path-scoped-allow`, not `path-confinement`.** ADR-004 and [ADR-019](ADR-019-enforcement-gate-mechanism-vs-boundary.md) insist a mechanism is declared for what it is. The hook keyed on a path reduces prompts; it bounds nothing an agent can reach — a shell command still writes wherever the sandbox lets it. Naming the dimension after confinement would invite exactly the misreading of a tighter allow path as a boundary that ADR-025 warns against.

### Alternatives considered

- **A `directory`-scoped `Write` / `Edit` grant.** Rejected — a scoped allow denies outside its scope, so it would deny every write elsewhere.
- **Recognising shell writes into the folder** (an emitter or `rm` whose every target lies inside, a literal here-document, and a leading-`cd` exception for them). Rejected — the proofs of concept above: arbitrary execution through an emitter's expanded arguments, and a deletion outside the folder when a `cd` fails. The first implementation of #1043 took this path; it is reverted, and ADR-025 needs no amendment.
- **An exception for `rm` scoped to the folder** (an `rm` whose every argument lies inside, or one behind `cd .agent-workspace`). Rejected — it is the shell reading rejected above, whose failed `cd` empties the project root; and a recursive `rm` would meet the guardrail floor and Claude Code's native deny all the same, so no folder could be removed.
- **A delete among the file tools.** Rejected — Claude Code's file tools write and edit and remove nothing, so there is no delete for point 1 to recognise.
- **A grant of the removal command by its leading words,** on `workspace` or on a privilege of its own, so that every shipped profile, `read-only` included, allows it unasked. Rejected — the words do not fix the code that runs: the router picks it by the directory (ADR-039), and ADR-025's leading-`cd` strip lets a `cd` pick the directory, so `read-only` would run code nobody vetted. On `workspace`, it would also make the privilege cover a shell command, which point 4 rules out.
- **A root from the session's anchor,** as the hook takes its own. Rejected — the anchor is a variable the command line can set, and ADR-034 point 1 keeps it a comparand, never a root input.
- **A marker file, or a field of the capability's manifest, for lasting state.** Not taken — a marker protects nothing a capability wrote before it learned to write one, and a manifest field grows the capability schema for its one user, the drift queue ([COR-007](../../../.pkit/decisions/core/COR-007-pattern-extraction.md)). The capability's name already marks it.
- **A confirmation passed with the call, for a root in another repository,** as other commands accept one (ADR-061 point 6). Not taken — a file name a pathname pattern expands to could carry it, so an option would widen the call. The question at a terminal remains.
- **A session-wide settings rule for the folder** (a `Write` / `Edit` allow on its path). Rejected for Claude Code — inside the working directory the harness already approves the folder, and a rule keyed on one checkout's absolute path neither covers worktrees nor stays inside the folder once written session-wide. The projection keeps the seam for a harness that needs one.
- **The harness's own per-session scratch directory.** Rejected — it lies outside a subagent's working directory, and allow rules written for it did not stop the prompts (#1043's field note).
- **Appending the ignore line to the adopter's `.gitignore`**, with a marker comment. Rejected — ADR-009 settled that no `.gitignore` the adopter owns is ever written, and [COR-002](../../../.pkit/decisions/core/COR-002-merge-delivery.md) rejected in-file markers; `init` prints the recommendation instead, pkit's standing "print, don't mutate" disposition toward adopter git state.

## Implications

- **A new catalog shape.** `recognize.path` joins `tool` and `bash` in the privilege-catalog schema, with `folders` and `tools` both required. It is a pure addition — no `schema_version` bump, no migration — and a surface change: the backbone's changeset declares the new privilege and the workspace, the claude-code adapter's the new enforcement dimension.
- **The verdict path moves only on the tool side.** `decide()` stays byte-identical to its prior form; `recognized_privileges` and `hook_decide` change in their tool branches only, and a test pins the shell verdicts to the previous decision core's. `pkit permissions probe` passes the project root as the live hook does, naming the subject it probes, so it demonstrates the workspace verdict.
- **A new backbone command.** `pkit workspace remove` lives beside the workspace's backbone code, in `src/project_kit/workspace_remove.py`. It is a pure addition — no `schema_version` bump, no migration, no change to the catalog or to any profile — and a surface change the backbone's changeset declares (#2360).
- **What else states it.** UC-028 states the removal at step 6 and in variant 6a, and anchors point 10 (`ADR-060#10`). Core rule 16, authored in `.pkit/rule-sets/ops.md` and generated into `.pkit/rules/core.md`, names the command, says that a capability may keep lasting state in the folder under its own name, and asks agents to remove only what they wrote. `.pkit/cli/README.md` documents the command. The permissions README's workspace section says how files leave the folder, and names the same use of it; DEC-056 asks both accounts to name it. The rule's wording is a person's to accept, as any change to an accepted rule is.
- **#1043's third criterion is met without shell redirects.** Its "create, read, edit and delete including shell redirects into it" is met for creating, reading and editing with the file tools and for deleting with point 10's command, and deliberately not for shell redirects, for the reasons above. Agents write the workspace with the file tools, as the rule and every agent body say, and remove from it with the command.
- **ADR-005 is refined in place,** not superseded: its point 5 has every shipped profile grant `workspace` to `all`. ADR-025 is unchanged.
- **Child of ADR-004; supersedes nothing.** The intent / confinement split, the fail-open hook with its fail-closed native denies, and the speed-bump-not-boundary posture are unchanged; this refines how the intent axis recognises one kind of request.
