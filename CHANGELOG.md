# Changelog

## 1.149.0 — 2026-08-24

### Added
- The deterministic command tier of COR-044's process-authoring layer (#683), under the existing `pkit process` namespace: `process new` scaffolds a lint-clean definition (subject incl. cardinality, states with meanings, transitions, entry/terminal marks) into a NAMED owning capability — erroring cleanly without one — with a fail-closed predicate stub for every evaluable the declared shape demands (detection always; gates / entry guards / resume_when / invariant checks when declared), each registered in the capability's package.yaml per the predicate-runner contract; `process couple` appends a `depends_on` entry to the invoker-named definition, with relation/mode validated against COR-038's closed vocabularies read as data from the shape contract; `process hand-off` adds a COR-042 contract (trigger + both seams, stubs scaffolded when new) to an existing coupling, validating the trigger against the upstream where resolvable. Neither mutation bumps the definition version (additive inert/report-only edits per COR-044), all three take `--dry-run`, and none ever overwrites an existing declaration or an existing predicate script. Transitions are addressed by their full `(from, to, trigger)` key, so two edges between one state pair are each independently gateable. And `process health --interpretation-only` re-renders the same health walk (a consumer of the walker per COR-042 point 5, never a parallel contract-walker) as the authoring completion signal: indeterminates only, misses not counted, plus a static check that both seams are registered, present, and no longer stubs — so the signal does not depend on which subjects happen to sit at the trigger. The default health run's exit contract is unchanged.
- A core `process` composite skill (COR-020 folder form) now walks the shape half of process authoring over the deterministic stamps (#685): `new` (subject, states and their meanings, transitions and who may make them, gates and their kind, invariants, waits — plus routing an adopter with no owning capability through capability authoring first, the judgment the stamp deliberately refuses), `couple` (a `depends_on` entry in your own definition, with the closed relation/mode vocabularies read from the shape contract and the required `why` pushed for purpose rather than restatement), and `hand-off` (a COR-042 contract, where that record's two authoring smells become questions the walkthrough will not complete without answers to: is this trigger stable, and would this candidate source fail loudly rather than silently return empty). The predicate logic behind each scaffolded stub is the forthcoming `process-author` agent's territory, not the skill's (COR-044); until it ships the walkthroughs point at the predicate-runner contract. Deferred operations are named in the dispatcher and listed authoritatively in the process area README, which now documents all three tiers of the layer.
- The process engine's journal is now the **canonical, provenance-carrying audit trail** (#697, DEC-049). Each move entry is stamped with the **pkit version** that governed it (best-effort — a version hiccup never blocks a move), so `pkit pm history` and `--check-drift` can attribute governed moves and sharpen the governed-vs-ungoverned boundary. The `journal_entry` schema documents the new `version` field.
- `pkit refs validate` now resolves an agent's `owns:` entries through the adopter overlay before checking them — a per-agent `overrides:` entry replacing the top-level default, through one shared helper the claude-code deploy resolver and the validator both use (pinned by a parity test that runs the real resolver, so the two cannot drift). On those resolved sets it enforces the exactly-one-owner invariant the agents area spec had stated in the present tense but never checked: cross-agent path-prefix containment is flagged, naming both agents, both paths, and the category a path came from. Conflicts are flagged, never arbitrated; nesting within one agent's own set is benign; an entry resolving to zero paths, or naming a category the overlay does not define, is clean (per ADR-051). Adopters whose overlay nests paths across agents may see new findings on first run (#699).
- `pkit process new` now stamps `subject.domain_ref` through a `--domain-ref <pointer>` flag (#716) — where the subject's *domain* data lives, kept distinct from the position the substrate tracks. Optional on either cardinality and free-form (the engine never interprets it, so carrying something is the only check the stamp can honestly make); omitting it writes no key, leaving a definition as valid and lint-clean as before. The authoring walkthrough now asks for the pointer instead of warning it cannot be stamped. Closing the same divergence from the other side, COR-044 point 3 is **amended**: the three structural composition blocks — subprocess embedding, cascade folds, open regions — are deferred for authoring in *any* definition, fresh or not, rather than claimed as fresh-definition surface the stamp never had. That deferral is authoring-only — the substrate resolves all three at runtime — and the process area README carries the authoritative list.
- The core `process-author` agent — COR-044's teeth tier, and the first producing agent at core: it writes the predicates behind every evaluable a process definition declares (detection, gates, entry guards, `resume_when`, invariant checks, both hand-off seams), fail-closed and read-only, routing shape problems back through the `process` skill rather than editing shape by hand. Its edit authority rides a new overlay category, `process-authoring-targets` (per ADR-051), which ships as an explicit empty list: the agent deploys owning nothing until you list your own definition files and predicate-script locations at file granularity. No entry may resolve into sync-managed content — the deploy resolver refuses it, names the offending path, and skips the agent, using a single sync-managed predicate now propagated at `.pkit/lifecycle/ownership.py` (origin-aware, so a kit-shipped capability's `project/` tree and an incubated or unregistered subtree are all admissible) rather than a per-adapter copy. `pkit agents reconcile --write` fills the category with `[]`, and `adopt` now says plainly that it cannot serve a category naming paths only you can enumerate. An install that predates the category upgrades into the deploy skip until the key is added — safe, loud, no migration owed (#686).
- **project-management 0.54.0** — `review-pr` now also delivers the reviewer verdict as a **native GitHub review** (`APPROVED → gh pr review --approve`, `CHANGES_REQUESTED → --request-changes`), not only the DEC-028 comment sentinel (#672, DEC-028 amended). The native review is what shows in the PR UI and satisfies branch-protection "required approving reviews" — closing the gap where an adopter's comment verdict didn't count and a native review had to be hand-posted. The comment (with the `<!-- pkit-verdict -->` marker) still drives `done-work`'s gate; the native review is added alongside it. It **degrades to comment-only** when the reviewer identity is the PR author (GitHub blocks self-approval of your own PR — native delivery is fully autonomous only on a non-author / bot identity) or on any gh failure; `--no-native` opts out.
- **project-management 0.54.0** — New `pkit project-management history <N>` (#698, DEC-049) — renders an issue's **engine journal**, the canonical pkit-governed audit trail of lifecycle moves, so the state log is **discoverable** without hand-reading the GitHub timeline (the #672 "looked unlogged" gap). `--check-drift` surfaces the **governance boundary**: it diffs the journal against the GitHub timeline's `state:*` label events and flags state changes with no journal entry — an ungoverned change (a manual label edit / raw `gh`), or a governed move the journal didn't record (drift accuracy sharpens once the journal is fully reliable, #697). Read-only.
- **project-management 0.54.0** — The adopter's `project/config.yaml` now ships a companion JSON Schema (`schemas/config.schema.json`), bound to the installed config path by a COR-023 `binds_to:` glob, so `pkit data validate` resolves it instead of reporting `no schema binding found` (#691, from #689). The schema enumerates every documented key — `default_branch`, the `gh:` host/owner block, the Projects-v2 board flag plus board id and cached node id, doc-path mappings, milestone categories, the review mode and registered agents, mesh peers, and the pre-close triage lead time — with `additionalProperties: false`, so an unknown or misspelled key is a loud refusal naming the offending key rather than a silent default. That closes the reported gap where `has_projects_v2_boards` (trailing `s`) validated fine and left the adopter in label-fallback mode until classification landed in the wrong substrate; `pre-check` covers value-level problems but cannot see a key that was never read. The required set mirrors `pre-check`'s, so the two gates agree, and `schemas/config.yaml` doubles as the shipped reference instance an adopter copies. The glob is anchored at the installed path rather than the `**/config.yaml` form the sibling schemas use, because `config.yaml` is a generic name that a bare glob would also claim on unrelated files.
- **project-management 0.54.0** — Audit-comment projection is now **configurable** via `audit.projection` in the pm project config (#696, DEC-049): `off` (no journal comments — engine journal only), `audit` (default — only override/authorisation justifications), or `full` (every pkit-governed move posts a **provenance-stamped** comment carrying the pkit version, making the governed-vs-ungoverned boundary fully visible on the issue). The engine journal records every move regardless of level — the knob controls only the GitHub comment projection. Completes the DEC-049 audit model (engine journal = canonical trail; comments = configurable projection).
- **project-management 0.54.0** — `set-field` now WRITES a Projects-v2 board single-select value (#724, from #723 and report #708), so a board-carried axis is populatable by a pkit verb instead of only by a hand-wired creation hook. `set-field <N> --priority High` under `has_projects_v2_board: true` resolves everything by NAME at runtime — the board number in config to the project node id, the field whose name matches the axis (`Priority` / `Workstream`, matched case-insensitively), the option whose name matches the value, and the issue's own card id — so no pre-resolved field or option ids have to be dug out of the API by hand. The write itself is issued by the existing sole constructor for a non-label substrate write (ADR-031), the same primitive the `set-board-field` hook uses; the reads live in a new board READ seam that `back-fill` and `adopt-existing` now share. `--dry-run` performs the same resolution (a read) and reports the concrete write it would make without touching the board. The honest-refusal posture is unchanged: a board-carried axis that cannot be set is `[refused]` with a non-zero exit and never `[ok]`, and each refusal names what was looked for AND what the board actually offers — the field list when there is no matching field, the option list when there is no matching option, the field type when it is not a single-select (text / number / date / iteration are out of scope), and gh's stderr verbatim on a scope or API failure. An issue with no card on the board (membership is a post-creation step) is refused with the exact `gh project item-add` command rather than added silently — putting an issue on a board is a membership decision, not a side effect of setting a field. An axis claimed by BOTH the board flag and a `label` binding in `substrate-map.yaml` is still refused rather than resolved by implementation order, pointing at `pre-check`, which fails on that conflict with both remediations. A call mixing substrates applies what it can and exits non-zero if anything was refused, naming what was and was not done.
- **project-management 0.54.0** — The reviewer-contribution predicate (DEC-032) now keys on the `type` classification axis alongside `workstream`, supports a `"*"` wildcard that matches every value of an axis (axis-present — forward-safe versus enumerating a fixed value set), and gains a new predicate KIND — a diff-property `floor` (#732, for [software-engineering:DEC-002]). A floor-carrying rule requires its reviewer whenever the PR's DIFF matches a property, independent of the closing issue's classification: the one floor kind, `touches-code`, fires when the diff touches any non-documentation file. Classification is code-suffix-dominant and fail-closed — a recognized source/config/schema/script suffix (`.py`, `.yaml`, `.json`, `.sh`, …) is always code even under a `docs/` directory; only a non-code asset that is doc-suffixed (`.md`/`.mdx`/`.markdown`/`.rst`) or under `docs/` reads as documentation; and any unknown or extensionless file counts as code (when in doubt, the floor fires). This backstops D1's classification gate-escape for a code-review reviewer: a code-touching PR filed against a `type:docs` or unclassified issue still pulls the floor reviewer into the required set. The resolver takes the PR's changed files as a new injected input, fetched only when a floor-carrying contribution is installed (a floor-free project pays no extra `gh` round-trip), and fails closed if the diff cannot be determined while a floor rule is present. The `review-contributions` schema expresses all three forms (a `type`-axis predicate, the wildcard, and the floor); existing `workstream` rules stay valid. Additive: a project with no `type`-keyed or floor-carrying contribution, or a non-matching PR, resolves exactly as before.
- **project-management 0.54.0** — Per-reviewer override on the merge gate (#735, project-management:DEC-050): `done-work --bypass-reviewer <name> --bypass-reason "<r>"` (repeatable) satisfies ONE named required reviewer's slot as a first-class `satisfied-by-override` state — distinct from a fresh APPROVED — while every other required reviewer in the resolved set still gates. It is a member of DEC-046's `--bypass` family (audited, reason-required, a parameterised repeatable target), NOT the whole-gate `--bypass` that discards the entire approval gate. Satisfied-by-override is a separate gate-checker input, never a synthetic APPROVED verdict, so it never corrupts the DEC-028 verdict record or the ADR-042 read surface. The override is ephemeral and merge-time — evaluated once against the currently-resolved set and current HEAD, never persisted for a later run to read back. A `--bypass-reviewer` name not in the freshly-resolved required set is a hard error naming the set; overriding every slot warns and steers to `--bypass`; an unresolvable set (broken contribution / undeployed agent) is left to the whole-gate `--bypass`. Before merging, a prose, verdict-grammar-distinct audit comment is posted per overridden reviewer, recording the operator (name + email), the reason, the overridden reviewer + provenance, and the reviewer's state at override time (none / a fresh CHANGES_REQUESTED / a stale APPROVED) with a link to the block comment when one exists — stamped per-reviewer(+reason) for idempotency. Widens DEC-032 D3's satisfaction predicate (amended in place) and extends DEC-046. Additive and migration-free: no override supplied is today's behaviour.
- **software-engineering 0.2.0** — The code-review panel ships ([software-engineering:DEC-002], #749): three read-only reviewer agents — `code-reviewer` (correctness/logic generalist plus general code quality and API-surface design), `security-reviewer` (auth, secrets-in-argv, `shell=True`/command injection, crypto misuse, dependency hygiene — the #715 harms), and `docs-reviewer` (documentation completeness, docs-match-behaviour, understandability, leaning on DEC-015's doc obligations). Each emits the DEC-028 verdict grammar (`Reviewer agent (local, <name>): APPROVED | CHANGES_REQUESTED` + the `<!-- pkit-verdict -->` marker) so it folds through pm's existing all-must-approve merge gate, and blocks only on objective failures in its remit — softer/subjective findings post as APPROVED-with-comments (DEC-002 D3). Universal review knowledge lives in each agent body; project-specific rules are read from the overlay-resolved `<project-conventions>` corpus (D4). The capability's new `review-contributions.yaml` registers the panel through pm's reviewer-contribution socket (DEC-032): code-reviewer + security-reviewer on the `touches-code` diff floor (any code-carrying PR, independent of classification — backstopping #715's mislabeled-issue gate-escape), docs-reviewer on the `type` wildcard (every classified PR). The capability now declares `requires_capabilities: project-management` (COR-030). Additive — a project without the panel installed, or a PR no rule matches, behaves as before.

### Changed
- COR-044 accepted: process authoring ships at core as a three-tier layer — deterministic authoring commands under the `pkit process` namespace, a composite skill for the declarative shape, and an owner-scoped `process-author` agent for the teeth. Design-ahead (`none`): the record fixes the shape and the sign-off rulings; no adopter-observable surface changes until the implementing tasks land, each of which carries its own changeset.
- **claude-code 0.6.0** — The agent resolver now refuses an overlay grant that resolves into sync-managed content, naming the offending path and skipping that agent rather than deploying an unchecked write authority (ADR-051). It consumes the single sync-managed predicate propagated at `.pkit/lifecycle/ownership.py` rather than re-deriving the rule, so this adapter and any future one cannot drift on what counts as adopter-owned. `deploy-agents.sh` reports the refusal distinctly from an undefined category, and the `adopt` hint no longer offers itself for a category naming paths only the adopter can enumerate (#686).
- **project-management 0.54.0** — Audit comments for state transitions are now **single and canonical** (#695, DEC-049). `move-issue` is the **sole audit-comment writer**: it renders one comment from the schema's `audit_comment_template` (a uniform `<!-- pkit-audit -->` marker + `Bypassed by <actor>: <reason>`), and wrappers like `promote-issue` pass the authorisation reason through via `--bypass-reason` instead of posting their own. This ends the #672 double-post (a wrapper hook comment *plus* a divergent `[audit]` line for one transition) and the drift between the posted format and the schema template — one audited mutation now yields exactly one audit comment in one format.
- **project-management 0.54.0** — The prerequisite gate is code, not documentation (#747). DEC-017 named `pre-check` the hard gate on every pm operation and the pm skill told the agent to refuse on a non-zero exit, but nothing enforced it: no script called pre-check, and a missing adopter config was silently read as an empty one, so an un-bootstrapped project was not refused — it quietly got defaults for the classification substrate, the board flag, review mode, doc mappings and workstreams. Now 60 of the 65 registered verbs call an explicit gate at the top of their entry point and refuse when prerequisites are unmet, with an error naming the exact command that fixes it (both the `pkit project-management bootstrap` form and the direct-script form) plus `pre-check` for the full diagnosis. Exempt, because each is either how a project BECOMES bootstrapped or how you diagnose why it is not: `bootstrap`, `pre-check`, `migrate`, `adopt-existing`, `self-test`. The read-only verbs (`show-*`, `list-workstreams`, `history`) and the engine-called predicates (`detect-*`, `gate-*`, `cascade-*`, `parent-active-descendant`, `context-workstream`) are gated too — a read that assumes kit labels misreports an adopter who remapped them, and a predicate answering "where is this issue?" from assumed defaults is the same silent-wrong-answer shape; a refusing predicate is read by the process engine as indeterminate and fails closed, which is the correct answer for a project that genuinely cannot say. "Bootstrapped" is two local file reads, no network and no API calls: a bootstrap STAMP that `bootstrap` writes on a clean completion (and `migrate` refreshes) at `project/bootstrap-stamp.yaml`, plus the adopter config still being shape-valid against its companion schema. The stamp records the capability version that bootstrapped, so an upgrade whose bootstrap obligations changed is detectable — surfaced as a `pre-check` warning rather than a refusal, since most upgrades change nothing about what bootstrap provisions. It also records the repository it was written for, so a stamp copied or seeded into a different repo is inert instead of opening the gate. Whether the setup is still HEALTHY (labels present, board resolving, host reachable) remains `pre-check`'s question, deliberately: a setup gate that fails when the tracker has a bad minute is worse than no gate. Installs made before this version are carried forward by a capability migration that writes a stamp marked as a presumption, so previously-working commands keep working; `context-workstream`'s contract narrows from "always exits 0" to "exits 0 on every derivation miss" (its backbone consumer already reads any non-zero exit as "no workstream", so that path is unchanged). A guard test enumerates every verb in `package.yaml` and asserts each one either calls the gate or appears on the exemption list with its reason, so a new verb cannot ship ungated.
- **software-engineering 0.2.0** — DEC-002 accepted: a code-review panel ships from software-engineering (code-reviewer + security-reviewer + docs-reviewer), registered via the reviewer-contribution socket and gating code-carrying PRs through the existing all-must-approve gate (closes #715). Design-ahead (`none`): the record fixes the panel, its home, and its per-agent block-threshold discipline; no adopter-observable surface changes until the implementing tasks land under EPIC #725, each carrying its own changeset.

### Fixed
- The `$schema` pointer a YAML carries is now validated, not just used to classify the file (#710). Previously an external pointer — a `# yaml-language-server: $schema=<path>` directive or a top-level `$schema:` key naming a schema other than the YAML's own companion — bought only the COR-018 companion exemption: nothing checked the file against the schema it named, so a hand-edited process definition was shape-checked by nothing. `pkit schemas validate` (both the project-wide gate and a path-scoped run) now validates every such instance against its declared target, resolved relative to the YAML's own directory, reporting findings against the instance's path with a JSON pointer into the offending position; a target that is missing, unreadable, not JSON, or not a valid Draft 2020-12 schema is itself a finding rather than a silent skip, and a remote (`https://`) pointer stays exempt and unvalidated. The companion exemption is unchanged — an instance still ships no companion of its own, including when named directly as the path argument. The shared process shape contract (`.pkit/schemas/_defs/process.schema.json`) gained the root constraints that make this bite: a `$defs`-only document accepts every instance, so the pointer stamped onto a definition validated nothing. Capability companions that cross-file `$ref` its `#/$defs/*` are unaffected by the root keywords. The cross-file reference passes stay pair-scoped (an instance has no namespace of its own); instance-side references remain `pkit data validate`'s surface per COR-029.
- The process-authoring layer no longer hands out a green light for work nothing watches (#713). `pkit process new` / `couple` / `hand-off` resolved the owning capability by directory existence alone, while contract discovery enumerates only capabilities the project **registers as components** — so a definition stamped into an authored-but-unregistered capability was real, correct, and invisible: every command succeeded, then `process health` reported "no hand-off contracts declared" and exited 0 over it. All three stamps now additionally require registration, refusing with `pkit capabilities register <name>` as the named remedy, and the three causes stay distinct (no `<capability>:` half in the address, no capability directory, a directory the project does not register). The gate shares discovery's own capability lookup rather than re-deriving it, fallback included — with no backbone manifest, or one listing no capabilities, the installed set is the filesystem scan, so a pre-manifest install stays authorable. Separately, a **scoped** health run that resolves to nothing is now indeterminate rather than clean: `--process <addr>` matching neither a walked definition nor any declared contract's endpoint reports a new `unresolved_scope` finding (narrative and `--json`, both the default and the `--interpretation-only` authoring view) and exits non-zero, naming the likely cause and its remedy — because naming an address is a claim that can fail, and what cannot be interpreted is never clean (COR-042). Determinate-empty is untouched: a bare run over zero declared contracts, and a scoped run against a definition that was walked and declares none, both stay clean at exit 0. Two adopter-observable consequences: a stamp into an unregistered capability now refuses where it used to succeed, and a scoped health run on a typo'd or unwalked address now exits 1 where it used to exit 0. The per-address operations (`status` / `move` / `validate`) are deliberately unchanged.
- `pkit report` composed outside a project no longer emits a misleading environment block, and the stage/submit messages now name where they read and write (#693, from #689). With no project root resolved, the compose warns loudly (naming the directory and the run-from-your-project-root fix) and the fenced environment block renders the project half as `NOT COLLECTED — composed outside a pkit project` instead of `backbone: unknown` / `adapter: none` / `capabilities: (none installed)` — values a maintainer read as facts about the reporter's install. The compose still proceeds (a report from a scratch directory beats no report), and the marker stays path-free, so the redaction discipline is unchanged. The `--yes` stage message adds two short lines naming the resolved project root (or `no project — <cwd>`) and the per-project draft store, and `report submit` names the store it read — in its list, its empty state, and its not-found error, which now points at running submit from the root the draft was staged under.
- The report environment block now marks the project half NOT COLLECTED whenever no backbone manifest is found — not only when no project root resolved (#702, follow-up to #693). A directory that is a git repo but carries no pkit install previously rendered `backbone: unknown` / `adapter: none` / `capabilities: (none installed)`, which a maintainer reads as a fact about the reporter's project rather than as "not collected".
- **project-management 0.54.0** — `done-work` now runs the DEC-007 checkbox close-gate as a pre-flight, closing the hole where the PR-merge path — the route every completed Task travels — merged without ever checking the closing issue's checkboxes (#734). The check happens BEFORE the squash-merge is authorised, which is the only place it can: GitHub's `Closes #N` auto-closes the issue on merge, so a check afterwards could only report a gate it had already let through. An unticked box refuses with exit 1, listing each unticked line and naming the remedy, and no merge is attempted; an issue with every box ticked, or with no checkboxes at all, merges exactly as before; an issue body that could not be read fails closed, since an unverifiable gate is not a satisfied one and the merge it guards is irreversible. `--skip-checkbox-gate` overrides it — discouraged, and deliberately the same flag name and semantics `close-issue` already carries so the two closure paths behave alike; the general `--bypass` does not clear it, matching how `--bypass` never clears a red CI. The rule itself now has ONE implementation (`scripts/_lib/checkbox_gate.py`) read by `close-issue`, `done-work`, `merge-pr` and the engine's `gate-checkboxes-ticked` predicate alike, replacing the four separate copies that could drift on what counts as an unticked box. The `review → done` transition's notes and that predicate's docstring now describe where the check actually runs, rather than the wiring that was only ever aspirational.
- **project-management 0.54.0** — The writer/reader substrate disagreement is now surfaced where the adopter can act on it (#709, from report #708). When `project/config.yaml` sets `has_projects_v2_board: true` while `project/substrate-map.yaml` binds a board-claimed axis (`priority`, `workstream`, `state`) to labels, each side silently believed itself: `create-issue` wrote no label, `set-field` reported `[ok] priority: … not set here` followed by `no change (all fields already set)`, nothing wrote the board field either, and `review-pr` hard-rejected on the missing label — a gate unsatisfiable by the capability's own verbs, whose only escape was a raw `gh issue edit`. `pre-check` now FAILS on that cross-substrate conflict, naming the axis, both claimants, and the consequence, with a remediation offering either single-substrate exit; it is a hard failure rather than a warning because pre-check is the prerequisite gate and this state makes the review gate unsatisfiable, and a warning would be lost in the passing run that hid the problem in the first place. Only `label` bindings conflict — an axis marked `unsupported: true` agrees with the writer, and `derive` / `title-prefix` bindings are not label reads — so a clean single-substrate config (board-only, labels-only brownfield, or greenfield) is unaffected. `set-field` now REFUSES a board-substrate axis instead of reporting success: non-zero exit, a `[refused]` line naming the board field to set instead and stating that the requested value was recorded nowhere, and a summary that no longer claims all fields are set. When a call mixes substrates (`--kind` is always label-backed), the label-substrate fields are still applied and the summary reports the partial application explicitly.
- **project-management 0.54.0** — The board-membership check no longer passes silently when membership cannot be determined (#740). Its condition fired only on a definite EMPTY projectItems list, so a null or malformed payload — an unreadable board, a token without the project scope, a partial API reply — skipped the check entirely and was indistinguishable from a satisfied one. An undeterminable payload now reports `board_membership.unverified` at DEC-019 own drift_severity (warning), worded distinctly from `.missing` so an adopter is never sent to add an issue that may already be on the board. No new severity, verdict token, exit code, or API call.
- **project-management 0.54.0** — A no-board brownfield adopter whose substrate map binds priority or workstream to their own labels no longer hits an unsatisfiable gate (#742): create-issue wrote the remapped label through the seam while validate-issue demanded the kit priority:*/workstream:* label, and pre-check could not detect it (its conflict check keys on a configured board). Both axes now resolve through the ADR-026 seam, exactly as type already did. An axis OMITTED from a present map now degrades instead of falling back to a kit-label demand, per DEC-036 D2. show-issue reports a label-bound axis by its resolved value rather than "unset / on board". Greenfield behaviour is unchanged.
- **project-management 0.54.0** — The `touches-code` diff floor no longer waves through an extensionless or unknown-suffix file under a `docs/` directory (#749): `docs/tools/helper` previously classified as documentation, so a code-carrying PR touching only such files escaped the code-review floor (fail-open). The classifier is now fail-closed there — under `docs/`, only a recognized documentation suffix (`.md`/`.rst`/…) or a recognized non-code asset suffix (image/diagram/font/PDF) is documentation; any extensionless or unknown-suffix file is treated as code, so the floor fires. A code suffix still dominates the `docs/` location as before; docs-only PRs are unaffected.

## 1.146.0 — 2026-08-09

### Changed
- **`pkit upgrade` now updates the pkit tool itself** when it is stale, instead of just printing the command (#638, ADR-044 amended). When the installed `pkit` is behind the latest release it runs `uv tool install --force …@v<latest>` and **re-runs the upgrade under the new version** — one seamless command, no manual step. ## 1.144.0 — 2026-08-07

### Added
- Per-project version pinning via a project-owned `.pkit/version-pin` directive (#605, ADR-049). A project opts into running a fixed pkit version by committing the directive; the entry-point router reads it (moving the pin source from `.pkit/VERSION` — the slot ADR-039 left to implementation) and re-execs the pinned version, so a global-tool upgrade no longer moves a pinned project. Two new commands manage it: `pkit pin [<version>]` and `pkit unpin` (removes the directive). With no argument `pin` freezes the project at its current *content* version (`manifest.yaml`'s `backbone_version`); with a `<version>` (a version number only — a single leading `v` is stripped, and branch/sha/pre-release tokens are refused since the router routes only a bare `v<semver>` tag) it dispatches on how the target orders against the content version — equal freezes in place, a newer version reconciles content forward (under that version's own code, via the `PKIT_NO_ROUTE=1` bypass) and then flips the pin last, and an older version is refused because migrations are forward-only (COR-010; roll back with `git checkout` of `.pkit/` instead). Both forms require the manifest. `pkit upgrade` in a pinned project now *auto-advances* the pin to the latest release with no `uv tool install` and no manual step: detected as the routed pinned child, it resolves the latest tag (ADR-044's `git ls-remote` check) and, when latest is newer than the pin, reconciles content forward under the target's own code (via the `PKIT_NO_ROUTE=1` bypass) then flips the pin last (never ahead of content; an interrupted raise is recovered by an idempotent re-run) — a clear no-op when already at latest, a distinct message when the pin sits ahead of the newest release, and a loud degrade (pin unchanged) when the release source is unreachable.
