## Summary

When the operator activates a permission profile, the realizer (`pkit permissions apply`) projects the profile's grants into native `permissions.allow` rules. Today those rules land in the committed `.claude/settings.json` — so on a repo that tracks that file, a per-machine activation produces tracked-file drift the operator must remember never to commit. This record routes them to their correct home: **allow rules whose only justification is the active profile realize into the gitignored `.claude/settings.local.json`, tracked by a pkit-owned provenance ledger, and are recompute-replaced on every `apply` so a profile switch or deactivation heals them away.** Rules justified by committed model state (adopter `grants.yaml`, capability fragments) keep realizing into the committed file exactly as before; guardrail denies stay committed and double-locked.

This is the routing family's third member — [ADR-029](ADR-029-move-mutable-sandbox-state-out-of-tracked-settings.md) routed the *sandbox block* by boundary effect; [ADR-032](ADR-032-per-machine-activation-routing-axis.md) routed *config/state* by value-provenance and operator activation; this record routes *realizer output* by the same ADR-032 Rule A classification (the rules' presence follows from an operator activation). It **qualifies [ADR-002](ADR-002-permission-realizer-ownership.md)'s additive-mode contract**: "never removes or replaces" now reads "never removes or replaces *in the committed file*; provenance-scoped recompute-replace *in the per-machine file, over pkit-authored entries only*." That qualification — subtractive authority in exactly one file, keyed to exactly one ledger — is the deliberate price of not converting visible tracked-file drift into invisible stale over-permission on the machine. The record was authored `status: proposed` and **accepted** via operator sign-off per the [PRJ-005](../../../.pkit/decisions/project/PRJ-005-adopt-adrs.md) acceptance gate; that sign-off also covers the two in-place ADR-002 edits this record mandates (Implications).

## Context

`profile activate` already treats the *pointer* as per-machine: ADR-032's `active_profile` worked instance routed it to a gitignored sidecar, because choosing an autonomy posture is an operator's personal risk stance, not a team default. But activation then runs `apply()`, which projects the **whole** model — guardrail denies, capability fragments, the profile's grant layer, and the adopter's `grants.yaml` — through one `project()` call and unions the resulting allow rules into the committed `.claude/settings.json` (ADR-002 additive mode). The profile's contribution to that projection is per-machine state by ADR-032 Rule A (its presence is an operator activation), yet it lands in the shared file.

For a conventional adopter whose `.claude/settings.json` is untracked, the destination is harmless. In a repo that tracks the file — project-kit's own self-host, and any adopter who commits it — the activation-derived widenings land as working-tree drift held out of commits only by operator vigilance: the same conditional-guarantee failure ADR-029 named and closed for sandbox widenings (its producing observation, verified here too: activating the `autonomous` profile added `Bash(docker:*)`, `Bash(docker-compose:*)`, `WebFetch`, `WebSearch` to the tracked file's working copy; `main` itself is clean).

The naive fix — route profile-derived rules additively into `settings.local.json` — closes the tracked-drift gap but opens a worse one, surfaced in adversarial review: `apply` never removes, and no deactivation verb exists, so switching from `autonomous` to `read-only` would leave the old profile's native auto-allows live on the machine with **no** git-status signal at all. The pre-fix failure at least showed up in `git status`; the naive fix hides it below the waterline. Healing requires selective removal, and ADR-008 rule 2 / ADR-029 condition 5 already established when selective removal is safe: **only when scoped by provenance** — the sandbox side's gitignored provenance sidecar plus provenance-scoped mutation (seal teardown, the `_required`-exclusion relocation pass) is the demonstrated pattern.

One more composition fact matters: the harness itself writes operator "always allow" choices into `settings.local.json`'s `permissions.allow`, so that array is genuinely co-owned. Any pkit mutation there must touch only entries pkit can prove it authored.

## Decision

**`apply()` becomes a single realizer with two routed destinations, and gains provenance-scoped recompute-replace authority in the per-machine file only.** Each condition is load-bearing.

1. **Routing by grant provenance, keyed to ADR-032 Rule A.** The model loader annotates profile-layer grants with their source (`_profile: <name>`, mirroring the existing `_capability` annotation; `decide()` ignores extra keys). `apply()` projects twice through the same `project()`: the full model, and the model minus profile grants. The profile-less projection (`committed_expected`) realizes additively into the committed `.claude/settings.json` exactly as today. The difference (`profile_expected` = full − committed) — the rules justified *only* by the active profile — realizes into the gitignored `.claude/settings.local.json`.

2. **Shared derivation stays committed.** Because `project()` is a per-grant monotone union, a rule derivable from both the profile and a committed source (adopter `grants.yaml`, capability fragment) lands in `committed_expected` and is never ledgered — deactivating the profile cannot heal away a rule the adopter independently declared. This is the model-side analogue of ADR-005's manual-grants-always-survive layering, and it is a property of the *subtraction*, not of any per-rule judgment: a future refactor must preserve the double-projection shape.

3. **Ledgered recompute-replace in the local file.** A pkit-owned gitignored sidecar in `.pkit/permissions/project/` (the ADR-032 Rule B sidecar branch; the `sandbox-provenance.yaml` pattern) records which local allow rules pkit authored for the profile. On every `apply`: rules in the ledger no longer in `profile_expected` are removed from `settings.local.json`; missing expected rules are added; the ledger is rewritten to the new set. Entries not in the ledger — the operator's own always-allows, harness-authored rules — are never touched. **This recompute-replace authority is exclusive to `apply` and scoped to ledger-recorded entries: one subtractive code path, ever.**

4. **The committed file's additive contract is untouched; overlap is skipped silently.** `apply` still never removes or replaces anything in `.claude/settings.json`. A profile-derived rule already present in the committed file (the baseline `git`/`gh`/`pkit` allows the merge primitive ships; historic drift) is silently skipped — committed presence is authoritative team state, and `apply` neither duplicates it locally nor advises relocation (the merge primitive's sources are invisible to `project()`, so "present in committed" is not evidence of drift).

5. **Reader scope is a named contract.** With realized state legitimately in two files, every consumer of live settings declares its scope: **committed-scope** for floor claims (the probe's native double-lock check — a deny present only in the per-machine file must never certify a floor other checkouts lack), **union-scope** for live-behaviour claims (`diff`'s applied/not-applied reconciliation; the diagnose report, which already reads the union). `diff`'s unjustified-rule attribution stays committed-scope so harness-authored local always-allows are not flagged as model violations.

6. **Managed mode composes with the routing.** The future managed region (ADR-002's #252 ruling) stays defined over the committed file's `permissions` key, but its composition excludes per-machine-classified sources: profile-derived `project()` allows route local even under managed mode. Without this, managed mode's wholesale regeneration would re-commit the profile's rules on every run — reintroducing this record's gap in a worse form. The #252 composition formula in ADR-002 is edited in place to say so (Implications).

7. **Guardrail denies are unaffected.** They realize committed and double-locked (ADR-002 fail-open/double-lock), on both layers, regardless of profile state.

## Rationale

**Why routing, why here.** The classification largely pre-exists: ADR-032 Rule A already says an operator activation routes per-machine, and its "a fourth per-machine field falls under this record by classification, not by amendment" clause covers new per-machine *state fields*. This record extends that classification one step — from state fields to *derived realizer output* (rules whose justification is an activation) — and adds the mechanism: the realizer becomes a two-destination writer, and a durable new artifact (the permissions provenance ledger) carries the healing. The mild classification extension plus the new mechanism is why this is a sibling record rather than a classification footnote. New-mechanism-plus-cross-record-composition is the same shape that made ADR-029 a sibling of ADR-008 rather than an amendment.

**Why recompute-replace instead of pure addition.** Pure additive routing relocates the vigilance gap instead of closing it: stale profile allows would accumulate invisibly in the local file across profile switches, with enforcement consequences (native allows bypass prompting regardless of the hook) and no git signal. The sandbox side already proved the safe removal pattern — provenance sidecar, mutation scoped to recorded-authored entries — and reusing it is COR-007 pattern-extraction, not invention.

**Why the harness merge makes the relocation behaviour-preserving.** The load-bearing harness fact is that `permissions.allow` rules from `settings.json` and `settings.local.json` *aggregate* — both files' rules apply (this is array aggregation, not scalar precedence). Evidence, per [COR-028](../../../.pkit/decisions/core/COR-028-permission-model-realization.md)'s honesty discipline in ADR-029's two-confidence-layer pattern: the harness documents `settings.local.json` as a merged personal-settings scope, and pkit's own diagnose report already treats the two-file union as "the live `permissions.allow`" (its prompted-vs-auto-allowed axis) — but that in-repo precedent is pkit's *mirror* of the harness merge, not the harness itself. If a future harness change made permission arrays replace across scopes, the mirror and the harness would diverge; recorded as residual risk rather than claimed away.

### Alternatives considered

- **Additive-only routing to the local file (no ledger, no removal).** Rejected — converts visible tracked-file drift into invisible stale over-permission across profile switches; the vigilance gap survives, relocated below the waterline.
- **Classify profile grants runtime-only (hook-enforced, no native realization).** Rejected — structurally cheapest (no routing, no ledger; the model is the only carrier and switches heal instantly), but it regresses the no-hook adopter path: with enforcement off, activating a profile would realize nothing natively and every profile-granted action would prompt. Realization-to-native is the documented purpose of `apply`; withdrawing it from profiles is a larger behaviour change than routing.
- **Relocate/remove profile-derived rules found in the committed file.** Rejected — `apply` cannot distinguish an adopter's deliberate committed hand-add from historic drift without provenance the committed file doesn't carry; removal there violates the additive contract this record deliberately preserves.
- **One-shot strip of the observed drift on `main`.** Rejected as unnecessary — the premise was checked and refuted: `main`'s committed file is clean; the four observed rules are working-tree drift, and convergence (restore the tracked file, re-run `apply`) is the mechanism, per ADR-029's own reasoning. The restore is an operator gesture documented in the implementing change, not an automated pass (unlike ADR-029's #275 there is no provenance tag on the old drift to key an automated relocation).

## Implications

- **ADR-002 is qualified, not superseded — two in-place edits ship with this record, both covered by its sign-off.** (a) The additive-mode paragraph gains a forward-pointer: additive mode's "never removes or replaces" is scoped to the committed file, with this record holding the per-machine exception. (b) The #252 managed-region composition formula is edited in place: per-machine-classified sources (the ADR-032 axis, OR-composed) are excluded from the committed union and route local even under managed mode. Per the ADR-032 correction-note precedent, the in-place ruling edit requires explicit re-sign-off — which this record's acceptance provides.
- **Write-ownership division, stated once:** the merge primitive owns committed additive contributions (baseline, skill grants, capability overlays); `apply` owns model-derived realization with routing; recompute-replace authority exists only in `apply`, only in the local file, only over ledgered entries.
- **A new gitignored sidecar ships** in `.pkit/permissions/project/` (the profile-realization ledger), riding the existing `runtime_ignore` pattern — a pure addition. As with ADR-029/ADR-032, the COR-010 relocation judgment for the change as a whole is deferred to the implementing change: `pkit migrations check-diff --include-working-tree --base main` gates it.
- **The ADR-002 additive-paragraph edit uses the lightweight parenthetical form** (the ADR-008-rule-4 forward-pointer precedent) rather than a blockquote change-note, deliberately: ADR-002's additive contract only ever spoke of `settings.json` — `settings.local.json` was never in its scope — so the edit is a scope *clarification* carrying a pointer to the record that owns the new authority, not a contract reversal. The #252 composition edit, which does change a normative build mandate, uses the blockquote update style.
- **Reader-scope sweep.** All consumers of the live-settings reader are swept once and pinned to their declared scope (committed vs union) per condition 5; new readers declare theirs at introduction.
- **The #399 whole-file-removal path goes dead by design** — `settings.local.json` now legitimately carries profile-realized allows, so it is never "purely overriding"; its docstring is updated to say so.
- **Out of scope, named deliberately:** `profile activate` also writes the profile's *posture* into tracked `config.yaml`. ADR-032 classifies posture as operator-invariant shared policy (committed); relitigating that is not this record.
- **Existing drift converges by operator gesture:** restore the tracked `settings.json` working copy, re-run `pkit permissions apply`; the rules re-realize into the local file and get ledgered.
- **Versioning:** surface change under PRJ-002 (adopter-observable relocation of realized rules + a new shipped sidecar artifact), same class as ADR-029/ADR-032's bumps.
