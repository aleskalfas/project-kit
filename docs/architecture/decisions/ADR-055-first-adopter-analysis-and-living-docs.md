## Summary

**In plain terms:** project-kit turns on the two capabilities it ships for keeping analysis and documentation true — software-analysis (use cases, actors, journeys, glossary, revalidation; [software-analysis:DEC-001](../../../.pkit/capabilities/software-analysis/decisions/DEC-001-software-analysis-discipline.md)) and living-docs (documentation spaces by audience, anchored pages, reader-review; [living-docs:DEC-001](../../../.pkit/capabilities/living-docs/decisions/DEC-001-living-docs-discipline.md)) — on its own repository, before any downstream project does. This record fixes project-kit's documentation topology under those capabilities: two roots (`docs/` for users, `tech-docs/` for maintainers), which scattered files count as pages of which space, the stance that `.pkit/` is *source* here rather than a synced copy, where the analysis lives, and that the friction check runs in enforcing mode from the day it exists.

## Context

project-kit ships software-analysis and living-docs on core pieces accepted alongside them: the backbone configuration file ([COR-048](../../../.pkit/decisions/core/COR-048-backbone-configuration.md)), documentation roots ([COR-049](../../../.pkit/decisions/core/COR-049-documentation-roots.md)) and anchors-and-friction ([COR-050](../../../.pkit/decisions/core/COR-050-anchors-and-friction.md)). The maintainer chose project-kit as first adopter, ahead of the downstream project that asked for these capabilities (the design is in the scratchpad note `2026-09-26-software-analysis-living-docs-design`), so that rough edges are found here first.

project-kit's documentation does not sit in one place. Its user-facing material is the top-level `README.md` plus the adopter-facing READMEs under `.pkit/`. Its technical material is scattered: `docs/architecture/` (the architecture decisions), `CONTRIBUTING.md`, `CLAUDE.md` and the rule files it includes, and the decision corpora (`.pkit/decisions/`, capability `decisions/` folders). Two constraints shape the answer. The documentation-roots record requires roots to lie *outside* the methodology tree, so files under `.pkit/` can join a space only as declared places, never through a root (COR-049 point 1). And living-docs says trees that sync manages are never places, so that a sync never shows up as friction — a rule whose *reason* does not arise in project-kit, where `.pkit/` is authored source and nothing syncs into it (living-docs DEC-001 point 1).

## Decision

1. **Roots.** User root `docs/`, internal root `tech-docs/`. Today `docs/` holds only technical material — the architecture decisions — and their location is an explicit overlay value, so changing the internal root moves no file (COR-049 point 6). The status report will list them as outside the internal root until they are relocated.
2. **Relocation of the architecture decisions to `tech-docs/architecture/decisions/`** happens in a dedicated reviewed pull request that rewrites references, and it lands *before* the roots are declared in the backbone configuration. Declaring `docs/` as the user root makes it a default place of the user space (living-docs DEC-001 point 1); relocating first avoids the architecture decisions sitting inside a user-space place while being technical material — living-docs defines no precedence between an enclosing default place and a nested declared one, and this record does not invent one (see Implications).
3. **Spaces — pages versus anchor targets.** A *page* is a document living-docs governs (reader and page-kind fields, the `LDOC` rules, reader-review). Decision records — COR, PRJ, capability DEC and ADR — are **not pages**: they are anchor targets of the `record` kind (COR-050 point 1) and members of the technical space's navigation. Rule sets are likewise anchor targets.
   - The **technical space** is `tech-docs/`, plus the declared places `CONTRIBUTING.md`, `CLAUDE.md` and `.pkit/rules/*.md`. Entry point: `CONTRIBUTING.md` until `tech-docs/README.md` exists. Space definitions live under `tech-docs/`; the exact sub-path is recorded on first onboarding proposal.
   - The **user space** is `docs/`, plus the declared places `README.md` and the adopter-facing READMEs under `.pkit/`. Entry point: `README.md`. The selecting principle for the `.pkit/` READMEs: *a README an adopter reads in order to use an area, capability or adapter is a page; maintainer-facing sub-READMEs (templates, migrations) and skill or agent bodies are not.* The initial explicit list is written into the friction key of the backbone configuration, which is the source of truth; this record fixes the principle, not the inventory.
   - Because project-kit *authors* `.pkit/`, the never-a-place rule for synced trees does not bind: its precondition (a synced copy) is absent. Should living-docs implement that rule as a check, the check must recognise in-repo source — the manifest records the capabilities as incubated in this repository (COR-031) — rather than key on the path alone. This stance is project-kit's alone; ADRs never propagate (COR-025).
   - The **scratchpad stays outside documentation.** Its notes are non-normative working drafts that retire once their question resolves (COR-012), so they are neither anchored nor friction-checked. The records and documents they produce are.
4. **Analysis.** project-kit's analysis lives at `tech-docs/analysis/` (the default sub-path under the internal root). Its first artefacts are the multi-clone coordination use cases that validate the coordination EPIC (#943, authored under #890).
5. **Friction check: enforcing from the day it exists.** The pull request that ships the core friction check wires it into project-kit's aggregated check script — the single required status, so there is one source of truth and no separate status that could block pull requests before it reports — with the mode key set to `enforcing` in the same pull request; before that pull request nothing is required. Whole-repository checks run on every push to `main` with full history and report without failing (COR-050 point 9). Choosing enforcing at once is the project's prerogative under the core record (COR-050 points 9–10; the default is warning). The code-to-doc mapping keeps its present per-rule enforcement flags until onboarding converts it to anchors ([project-management:DEC-053](../../../.pkit/capabilities/project-management/decisions/DEC-053-doc-check-slot.md)); the conversion produces surgical anchors on the surfaces a page actually describes, not ports of the broad tree-to-README rules the mapping deliberately keeps advisory.
   - **Escape hatch.** When the check itself is broken — it crashes, or fails on a malformed or dead anchor that is not the pull request's doing — the maintainer flips the mode key to `warning` in a one-line change disclosed in the pull request and files the defect; the flip is reverted with the fix.

## Rationale

Splitting the roots now gives project-kit the layout the living-docs separation rule asks for, and the same layout as the downstream adopter. Nothing moves on the split because existing locations are explicit; the one relocation that *is* wanted (the architecture decisions) is done once, deliberately, before it could be reported as friction or misplacement. Declaring the scattered files as places, instead of moving them, follows the "record, never move" principle of the documentation-roots record. Keeping records out of the page set keeps living-docs' page rules on prose that has readers, and keeps records where COR-050 already places them: as the things pages and analysis anchor to.

Enforcing from the start is honest costing, not bravado. Legitimate friction — an anchored surface changed, so the page must be rechecked — costs one marker update in the same pull request; project-kit accepts that cost because every page and anchor here is produced by the tooling under test, and the recheck *is* the work the capability exists to demand. What the enforcing mode must never do is fail on defects of the tool: a crash, a malformed anchor, a dead anchor introduced elsewhere. Those are bugs in our anchors or our check, found here before any adopter meets them, and fixed at once under the escape hatch. Warning mode would let both kinds accumulate silently; project-kit gains nothing from tolerating noise it created.

**Why an ADR and not a PRJ.** Turning on shipped capabilities for project-kit's own repository has a project-record precedent (PRJ-009, the code-review panel). This record is placed as an ADR because its substance is documentation *topology* — which trees are roots, which files are pages of which space, that `.pkit/` is source and not a synced copy — which shapes the contributor's mental model of where truth lives and how it is checked (COR-025's architecturally-significant test). The enforcement choice stays in the same record because it follows from the same self-hosting stance rather than from a workflow preference.

### Alternatives considered

- **Keep both roots at `docs/` for now.** Rejected: the split is the intended layout, and doing it first avoids a second transition later.
- **Relocate the architecture decisions during onboarding, as one proposal among many.** Rejected in favour of a dedicated pull request first: a single reviewed move that rewrites the relative links of some fifty records is cheaper alone, and it removes the two-spaces overlap on day one.
- **Move the adopter-facing READMEs into the user root.** Rejected. They stay beside the areas they describe, as declared places.
- **Exclude `.pkit/` READMEs from documentation.** Rejected. They are project-kit's primary user-facing documentation.
- **Treat decision records as pages.** Rejected. Records have no reader field or page kind, and reader-review of a decision is the acceptance gate, not a documentation activity.
- **Warning mode first, enforcing after a clean period.** Rejected by the maintainer for the reasons above.

## Implications

- Adopting the capabilities here means onboarding project-kit's documentation: anchoring pages, converting the mapping, writing the space definitions, and proposing splits, all through reviewed changes. Two findings for the capabilities are already visible and are filed as such rather than resolved here: living-docs must define precedence between an enclosing default place and a nested declared place; and the user-space READMEs link densely into the decision corpus, which the separation rule ("user-facing navigation never leads into technical material", living-docs DEC-001 point 1) will report on first check — resolving that is an onboarding decision, not this record's.
- **Anchors in shipped READMEs propagate.** Front matter written into `.pkit/**/README.md` reaches every adopter through sync. It is inert there — adopters do not declare `.pkit/` as a place — but an adopter who does would meet dead anchors (COR-050 point 6). Adding that front matter is an observable surface change and declares a changeset (PRJ-002).
- The first use cases are written into `tech-docs/analysis/use-case-model/`.
- The backbone configuration gains the documentation block (`user: docs/`, `internal: tech-docs/`) when the documentation-roots key is implemented — after the relocation pull request.
